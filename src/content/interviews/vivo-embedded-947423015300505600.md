### 《参考解析》

**malloc/new 这类题要答出「分配、初始化、释放」三层的差别，而不是只背语言归属。** malloc 只负责申请指定大小的原始内存，返回 `void*`，失败返回空指针，释放用 free；new 是表达式，先分配内存再调用构造函数初始化对象，失败抛 `bad_alloc`，释放用 delete 且会执行析构。两套机制不能混用：new 出来的对象用 free 释放、malloc 出来的内存用 delete 释放都是未定义行为。再往下一层是 `new[]` 与 `delete[]` 必须配对——数组的 delete[] 需要知道元素个数才能逐个析构，编译器通常在分配区前面多存一个 cookie；构造函数中途抛异常时运行时会自动回收已分配的内存，所以不用担心半构造对象泄漏。

**智能指针的重点是所有权模型，以及 shared_ptr 的循环引用。** unique_ptr 独占所有权，不可复制但可以 move 转移，开销与裸指针相同，是默认首选；shared_ptr 用引用计数共享所有权，计数增减是原子操作，所以有额外开销，且控制块与对象分开分配；weak_ptr 不增加引用计数，用来打破循环引用与观察对象是否还活着。两个对象互相持有 shared_ptr 时引用计数永远不会归零，对象泄漏，把其中一侧改成 weak_ptr 才能解开。还要知道 shared_ptr 不是「绝不泄漏」：`enable_shared_from_this` 用错、在构造期间把 this 交给 shared_ptr、以及自定义删除器管理不当，都会出问题。

**内存对齐要讲清「为什么」而不只是「有填充」。** CPU 访问对齐地址通常一次总线周期就能完成，跨边界访问要拆成两次甚至触发总线错误（部分架构上直接异常），所以编译器按类型的自然对齐要求插入填充字节，保证结构体每个成员落在对齐地址上、整体大小是其最大对齐数的整数倍。结构体成员按「大类型在前、小类型在后」排列能减少填充；`#pragma pack` 或 `__attribute__((packed))` 可以取消对齐，代价是访问变慢、在某些架构上取址会崩，通常只在协议报文、寄存器映射这类必须按字节布局的场景用。局部变量在栈上、全局与静态变量在数据段（已初始化 `.data`、未初始化 `.bss`）、字面量与常量在只读段、动态申请的在堆上——把这几个区一次说全，追问「static 变量什么时候初始化」也能接住。

**RTOS 任务切换要落到「上下文保存 + 调度决策」两件事。** 触发点通常是 SysTick 中断、任务主动让出（阻塞在信号量/延时）或更高优先级任务就绪。切换时把当前任务的寄存器现场（通用寄存器、栈指针、程序状态字，带 FPU 的还要保存浮点寄存器）压到它自己的任务栈上，把栈顶指针存进 TCB；调度器按优先级与就绪表选出下一个任务，从它的 TCB 取出栈顶恢复现场，最后异常返回。要能补一句「临界区要关中断或用调度锁保护就绪队列」，以及 Cortex-M 上 PendSV 专门用来做上下文切换、保证不在中断嵌套中间切。

**Oops 与 Panic 的区别，本质是「内核还能不能继续跑」。** Oops 是内核在异常路径上打印的现场（寄存器、调用栈、出错的地址与符号），如果发生在进程上下文且没持有会导致死锁的锁，内核杀掉当前进程后还能继续运行；Panic 是内核判定无法继续、主动停机（配置了 `panic=` 还会自动重启）。分析 Oops 先看 `PC is at` 定位出错指令，看 `Call trace` 找调用链，用 `addr2line` / `gdb vmlinux` 把地址还原成函数与行号，再看是空指针、非法地址还是 BUG_ON 触发。随机 Crash 的排查顺序一般是：先排除硬件（内存、电源、温度），再看是不是同一处代码、能不能用压测复现，然后打开 KASAN / lockdep / ftrace 缩小范围。怀疑 DDR 可以用 memtester 压测、降低频率或时序复跑、换板对比；怀疑 CPU 则看是否固定在同一指令、是否有 Cache/ECC 报错、换板是否复现。

**OOM 那道题要答出「为什么还有空闲内存也会 OOM」。** 触发 OOM Killer 的是内存分配在回收之后仍然无法满足，而不是「空闲内存为 0」——水位线机制要求保留 min/low 水位的空闲页给原子分配与回收自身使用，所以 `MemFree` 看起来还有不少时，一次大的 order 分配（连续物理页）仍可能失败；cgroup 内存限制、NUMA 节点内部分配、内存碎片同样会让分配失败。日志里要区分全局 OOM、cgroup OOM 与单次分配失败，看 `dmesg` 里的 `Out of memory: Killed process`、`oom_score` 与 cgroup 路径。优化方向是限制进程内存、调 `oom_score_adj`、减少大块连续分配、及时释放缓存。

**IO 优化不能一上来就加线程或加缓存，要先定位瓶颈在哪一层。** 先用 iostat / iotop / vmstat 看是吞吐打满、延迟高还是 IOPS 不够，用 `pidstat -d` 找到具体进程，再看是随机小 IO 还是顺序大 IO、是否频繁 fsync。对应手段不同：随机小 IO 可以合并、预读、换 SSD 或加 page cache；同步写多可以改成批量提交或异步；系统调用次数太多就批量读写减少陷入内核的次数。最后一定要回到业务对延迟与一致性的要求上做取舍。

**select/poll/epoll 的区别按「数据结构 + 就绪通知方式 + 时间复杂度」三条讲。** select 用位图，有 1024 个 fd 上限，每次调用都要把集合从用户态拷进内核并线性扫描，返回后还要自己遍历找就绪项；poll 用数组去掉了数量上限，但仍然要全量拷贝与线性扫描；epoll 在内核里维护红黑树存关注的 fd、就绪链表存已触发的事件，`epoll_wait` 只返回就绪的，复杂度与总 fd 数无关，适合大量连接里只有少数活跃的场景。要注意 epoll 的水平触发与边缘触发差别：边缘触发必须一次读到 `EAGAIN`，否则会漏事件。互斥锁会让等待者睡眠、适合临界区较长或可能阻塞的场景；自旋锁忙等不睡眠、适合临界区极短且不能在中断上下文睡眠的场合，单核上自旋锁基本没有意义。

**「CPU 占用不高但系统卡顿」是一道典型的排除题。** 常见原因：大量进程处于 D 状态等 IO（磁盘、NFS 卡住）、内存不足触发频繁回收与 swap、锁竞争导致线程排队、调度延迟（实时任务或中断风暴抢占）、网络或下游服务超时、GC 停顿。排查用 `top` 看 load average 与 D 状态进程数、`vmstat` 看 `wa` 与 `si/so`、`iostat -x` 看 await 与 util、`perf top` / `perf sched` 看热点与调度延迟、`cat /proc/interrupts` 看中断是否集中在某个核。回答时按「先看是等什么，再看是谁在等」的顺序讲，比罗列工具更有说服力。
