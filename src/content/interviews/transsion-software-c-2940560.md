### 《参考解析》

**跨目标跟踪的实现要点**：主流做法是「检测 + 关联」的 tracking-by-detection：每帧先跑检测器得到目标框，再用卡尔曼滤波按上一帧的速度预测本帧位置，用 IoU 或外观特征（ReID 嵌入）计算检测框与轨迹的代价矩阵，最后用匈牙利算法做全局最优匹配；匹配上的轨迹更新状态，未匹配的检测新建轨迹，连续若干帧未匹配的轨迹判定为丢失并删除。只靠 IoU 在遮挡、快速运动和密集场景下容易发生 ID 切换，加入外观特征可以显著提升鲁棒性，代价是每帧多一次特征提取的算力开销；卡尔曼的匀速运动模型对急转变向不准，需要调大过程噪声或改用扩展卡尔曼。跨镜头跟踪则要在这之上再加一层 ReID 检索与相机间的时空约束。这道题的重点不在算法名，而在能否说清「为什么这样关联」以及阈值、算力、误关联三者之间怎么权衡。

**Valgrind 与 ASAN 的差异，以及泄漏报告怎么读**：Valgrind 的 memcheck 是动态二进制插桩，程序在它合成的 CPU 上运行，因此不需要重新编译、可以附着到已有二进制，能检测未初始化读、堆越界、重复释放和泄漏，代价是十到三十倍的运行时间与额外内存，适合在 PC 上跑功能用例。ASAN 是编译期插桩（`-fsanitize=address -g`），编译器在每次访存前后插入对影子内存的检查，能精确抓到堆、栈、全局变量的越界与 use-after-free，速度约为原生的一到两倍，但必须重新编译、常驻内存开销大，资源受限的目标板往往放不下。泄漏报告的分级要能背下来：`definitely lost` 表示程序结束时已没有任何指针指向该块，属于真泄漏，必须修；`indirectly lost` 是被前者牵连的结构体内部块，根因解决后自然消失；`possibly lost` 是指向块内部的指针，可能是设计如此也可能真丢了，需要回看代码；`still reachable` 表示结束时仍有全局或静态指针可达，通常不算泄漏，但若长稳测试中它随运行时间单调增长，就说明有缓存只增不减，同样要处理。

**没有 Valgrind、ASAN 的嵌入式设备如何查内存问题**：要按「静态检查—运行期插桩—现场取证」三层回答。静态层面打开 `-Wall -Wextra`、`-fstack-usage`，配合 cppcheck、clang-tidy、Coverity 做空指针、越界和资源泄漏的模式匹配。运行期可自己对 `malloc/free` 做一层封装：块头写入魔数与长度、记录调用点（`__builtin_return_address`），周期统计已分配块数与峰值，退出或空闲时打印未释放的调用点；也可以在链接期用 `-Wl,--wrap=malloc` 拦截。再往下用 MMU/MPU 把可疑缓冲区所在页设为不可访问，越界立刻触发异常并保留现场；配合硬件 watchpoint 监视被踩的变量。现场取证靠 core dump 加 gdb 的 `bt`、`x` 定位崩溃点，以及看门狗与环形日志保留复位前的最后一段轨迹。要说明取舍：插桩有开销，量产固件用编译开关或采样方式保留一部分能力。

**二进制报文为什么不直接强转结构体指针**：四个层面的理由。其一，结构体成员之间存在编译器插入的填充字节，直接把线上报文按结构体解释，字段位置会随编译器与选项漂移；其二，端序不一致，网络字节序是大端，而 ARM、x86 是小端，整型字段必须先 `ntohl/ntohs` 转换；其三，C 的严格别名规则不允许用不兼容类型的指针访问同一块内存，开 `-O2` 后这类代码可能被优化出难以复现的错误；其四，报文长度来自外部、不可信，强转后按结构体读取等于放弃了长度校验。正确写法是按字段用 `memcpy` 取出到对齐的局部变量、显式转换端序、先校验魔数与长度再解析；即使使用 `__attribute__((packed))`，也只对整体拷贝安全，取成员仍应经 `memcpy`，因为在 ARM 上对非对齐地址的整型访问可能直接触发 fault 或被拆成多次总线操作。

**安全字符串函数与字符串接口的常见坑**：`strcpy/strcat/sprintf` 完全不检查目标容量，是溢出的主要来源；`strncpy` 在源串长度不小于 n 时不会补 `'\0'`，且会用 0 填满剩余空间，既有截断风险又有性能损失；`strncat` 的 n 指的是追加字符数而非目标剩余容量，按「缓冲区大小」传参是典型误用；`snprintf` 返回的是「原本想写入的长度」，返回值不小于缓冲区大小就说明发生了截断，必须据此判断而不是看写入内容。项目里通常统一封装一层：固定用 `snprintf`、传入 `sizeof(buf)`、检查返回值、失败即返回错误码，禁止裸用不安全版本。字符串接口另外几类坑是：把缓冲区大小与字符串长度混为一谈、用 `str` 系列处理含 0 字节的二进制数据、返回函数内局部数组的地址、多线程共用静态缓冲区（`strtok` 不可重入，应换 `strtok_r`）。

**AI 生成代码的可用率、缺陷类型与团队规范**：可用率要给出可复现的口径，例如按「编译通过、单测通过、人工评审通过」三级统计，并说明样本覆盖了哪类模块，否则数字没有意义。常见缺陷集中在几处：幻觉出不存在的 API 或参数（库版本与文档不符）、边界与错误处理缺失（不检查返回值、空指针、数组越界）、资源生命周期错误（申请未释放、句柄泄漏）、并发假设错误（共享状态无保护）、以及最危险的一类——逻辑自洽但与既有协议、状态机、硬件时序不匹配。检查手段是把 AI 产出当作初级同事的提交来审：小步生成、逐段 review、编译告警全开、静态分析与单测覆盖边界，内存管理、协议解析、安全相关模块强制双人评审。团队规范可以落到三点：明确可用与禁用的模块范围，要求提交时标注生成部分，在提示词里附上接口定义与编码规范以减少臆造。
