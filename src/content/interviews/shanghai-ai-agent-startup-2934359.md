3. 如果涉及用户积分的扣除与退还，需要如何设计相关数据表？

8. 图片生成任务应该设计哪些状态？

### 《参考解析》

**表设计**：`user`（余额、版本号）、`generation_task`（id、user_id、prompt、负向提示、模型、尺寸、状态、积分单价、扣费流水号、结果图 URL、错误码、创建/开始/结束时间、重试次数）、`credit_ledger`（流水表，每笔扣/退一条，含 task_id、金额、类型、幂等键）、`asset`（图片元数据与存储 key）、`model_config`（模型、单价、限流）。关键不是表多，而是「余额是派生值、流水是真源」——余额可由流水求和重建，这样对账永远有依据。

**积分一致性**：三阶段。提交时在一个本地事务里「写 task（状态 pending）+ 写扣费流水 + 扣余额（`UPDATE ... SET balance = balance - ? WHERE balance >= ?`，用条件更新防超扣）」，三步同库同事务，天然原子。执行由异步 worker 领任务，状态改 running。结束分两支：成功则写结果、状态 succeeded；失败则在一个事务里「写退款流水 + 加余额 + 状态 failed」，退款用 `task_id + 'refund'` 作唯一键保证只退一次。任务超时（worker 挂了）由巡检扫描 running 超时记录，按失败处理并退款。整体是「本地事务 + 状态机 + 幂等键 + 补偿扫描」，不需要分布式事务。

**异步任务与结果获取**：提交接口立刻返回 task_id，重活丢进队列（Redis Stream / MQ），worker 拉取调用模型、上传对象存储、回写状态。客户端通过「订阅 + 兜底轮询」拿结果：在线用 SSE 订阅该 task 的事件流，断线重连后先用一次 HTTP 查询兜底，避免丢事件。负载大时把状态放 Redis（带 TTL）扛读，DB 只做持久化。

**轮询 vs SSE vs WebSocket**：轮询实现最简单、兼容性好，但实时性差、请求浪费；SSE 单向、走普通 HTTP、自动重连、天然适配「服务端推结果」这种场景；WebSocket 双向、开销低，但要自己处理心跳、重连、网关超时。生图是一次请求、一次性结果，SSE 最合适；如果客户端还要中途取消、改参数，就上 WebSocket。答的时候补一句「网关/CDN 的 60 秒空闲断连」是实际踩过的坑，很加分。

**长事务的问题**：一是占着连接与锁，行锁/间隙锁持有时间变长，容易把并发压死；二是 undo 膨胀、MVCC 版本链变长，影响其他事务的快照读；三是超时回滚后业务状态不明；四是与外部调用（第三方模型 API）混在事务里，网络抖动直接拖垮连接池。所以要把外部调用移出事务，事务只包住 DB 的几次写，长流程用状态机推进。

**任务状态**：`pending → queued → running → succeeded / failed`，外加 `canceled`、`timeout`。状态迁移要单向、有审计（每次迁移记一条），并提供「已扣费未出图」的中间态查询，用户看到的是「生成中」而不是空白。
