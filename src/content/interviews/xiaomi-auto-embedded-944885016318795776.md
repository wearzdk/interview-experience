### 《参考解析》

**C 语言这几题的关键在于说清「为什么」**。static 修饰局部变量是把生命周期延长到程序结束、只初始化一次（C++11 起首次进入的初始化是线程安全的，裸机 C 里不保证）；修饰全局变量或函数是把符号变成内部链接，其他编译单元不可见，用来避免多文件重名——面试官常追问的是链接属性而非「存在静态存储区」。const 的三种写法看 `*` 与 const 的相对位置：`const int *p` 是指向常量的指针（值不可改、指针可改），`int * const p` 是指针常量（指针不可改、值可改），两者都 const 则都不可改。内存对齐的本质是硬件访问效率与原子性要求，计算规则是每个成员按自身对齐值对齐、结构体总大小按最大对齐值补齐。

**memcpy 不能处理重叠**，因为它是按字节（或字）顺序拷贝，当源和目的区间重叠时，前一次写入会污染后面还没读的源数据。重叠场景要用 `memmove`，它的实现会先判断方向，从尾部往前拷。大端小端的代码判断用联合体或指针强转：把 `int 1` 的地址当 `char*` 读第一个字节，得 1 是小端、得 0 是大端。

**volatile 与原子性的区分是高频点**：volatile 保证每次访问都真的去内存读/写、不被编译器优化进寄存器，适合中断与主循环共享的标志位、硬件寄存器；但它不保证原子性——`i++` 在 volatile 下仍然是读-改-写三步，多核或中断抢占下依然会丢更新。原子性要靠关中断、原子指令（LDREX/STREX、CAS）或锁。

**中断现场保存与嵌套**：Cortex-M 进入中断时硬件自动压栈 R0-R3、R12、LR、PC、xPSR（所谓的 stacking），软件只需保存剩余的 callee-saved 寄存器；支持嵌套靠的是优先级与硬件自动切换栈指针（MSP/PSP）。中断里不做耗时操作的原因是它会阻塞同优先级及更低优先级的中断、拉长中断延迟，正确做法是中断里只置标志或入队，处理放到主循环或任务里。

**优先级反转与继承**：低优先级任务持有互斥量时被高优先级任务抢占，中优先级任务又抢走了 CPU，导致高优先级任务实际上被中优先级拖住。优先级继承是让持锁的低优先级任务临时提升到等待者的优先级，让它尽快跑完释放锁；优先级天花板则是把锁的上限预先设好。FreeRTOS 的 mutex 内置优先级继承，二值信号量没有——这是选型时常被问的差别。

**Bootloader 跳转的完整动作**：先关中断、关外设（尤其是 SysTick 和已经配置的 DMA，否则跳到 APP 后它们还在跑）、清理挂起的中断标志；然后设置 MSP 为 APP 向量表的第一个字（初始栈顶）、把 APP 向量表地址写进 SCB->VTOR；最后取向量表第二个字（Reset_Handler）作为入口，跳转前通常用一个函数指针调用。不重设 MSP 的后果是栈还在 Bootloader 的区域里，APP 一开中断或深递归就可能踩坏数据；不重设 VTOR 则中断仍走 Bootloader 的向量表，APP 的中断全都不响应。

**固件包的完整性校验要分三层讲**：CRC 或哈希解决「传输/存储有没有出错」（完整性），数字签名解决「这份固件是不是我们签发的」（真实性），加密解决「固件内容会不会被逆向」（机密性）。只校验 CRC 防不住替换——攻击者改完固件重算 CRC 即可。公钥放在设备里要防替换，靠的是把公钥烧进不可改的区域（OTP、受保护的 Flash 扇区）或用设备唯一的密钥加密存储，并让信任根从 ROM 开始逐级校验，这就是安全启动的链条。

**A/B 分区的价值是回滚能力**：新固件写到备用分区，校验通过后改启动标志，试运行成功再确认；失败就切回原分区，设备永远有一个已知可用的版本。单分区设备只能靠「先把新固件完整写到一个暂存区、校验后再覆盖」，或者依赖外部恢复通道（USB、串口、诊断口），恢复能力弱得多。

**边下载边写 Flash 的风险是「写坏了没法回头」**：一旦写到一半断网或断电，应用分区已经被破坏，如果没有 Bootloader 保底就变砖。下载完整再写虽然需要双份存储空间，但能保证写之前的固件是完整的。折中做法是分块下载 + 校验每块 + 记录已写偏移，重启后从断点续写，但必须保证断点记录本身是原子更新的。

**Flash 擦除期间掉电，这个扇区处于未定义状态**——可能部分位已经是 1（擦除态）、部分还是 0，读出来的数据既不是旧内容也不是新内容。所以不能「擦完继续用」，必须重新擦除整个扇区再写。这也是为什么要用「擦除中」的状态标记，且这个标记本身要写在不会被这次擦除影响的地方（另一个扇区或带备份的标志区）。

**升级状态机要防的两个坑**：状态写到一半断电导致状态不一致、以及反复重启在两个版本间振荡。前者的解法是状态记录用「双份 + 序号 + CRC」或者写日志式追加，读取时取最后一条完整的；后者的解法是设置回滚次数上限，超过上限就锁定在当前版本并上报故障，等外部指令再动。

**试运行成功的判据不能只是「起来了」**：十秒后看门狗复位说明应用根本没跑通。业界的做法是让新固件在启动后主动上报健康状态（心跳、自检结果、关键任务是否起来），Bootloader 或升级管理模块收到确认才提交；等不到确认就按超时处理，切回旧版本。确认者可以是车端的升级管理模块，也可以是云端。

**多 ECU 的依赖与一致性**：升级顺序按依赖图做拓扑排序，被依赖的先升。回滚的传播是最难的部分——如果 A 升级后 B 依赖 A 的新版本才升，结果 A 回滚了，B 会因为找不到依赖而起不来。所以要区分「兼容性依赖」（B 的新版本能否在 A 的旧版本上工作）和「强绑定依赖」，前者允许不同步，后者必须作为一个事务整体回滚。

**CAN 传输失败与目标 ECU 死机的区分**：看的是响应而不只是发送成功——CAN 帧发送成功只说明总线上有人 ACK，不说明目标 ECU 处理了。要靠应用层的诊断响应（UDS 的 ResponsePending、超时）、以及周期性的心跳报文来判断对方是否还活着。

**升级流量与控制报文共存**：靠 CAN ID 的优先级（数值越小优先级越高，控制报文用更小的 ID）+ 发送节流 + 在总线上留带宽余量。车载以太网则用 VLAN 优先级或流量整形。

**存储空间不够放两份固件的折中**：差分升级（只下载与旧版本的差异，减少下载量但不减少存储需求）、压缩备份（把旧固件压缩后存放，恢复时解压）、或者外挂存储。差分升级失败能否恢复，取决于旧版本是否还在——如果差分是把旧版本改写成新版本，那中途失败就必须能重新下载完整包。

**防降级靠版本号 + 单调计数器**：不能只比版本字符串（可被伪造），要用不可回退的计数器存在受保护区域（OTP 或 eFuse），每次升级递增，Bootloader 要求新固件的计数器不小于当前值。签名校验通过只说明固件来源合法，不说明它能在当前硬件上跑——所以还需要硬件版本、外设配置、依赖版本的兼容性校验。

**异常测试的做法**：断电用可控电源或继电器切断、或用调试器在指定地址打断；写 Flash 失败用注入器或者改写驱动在指定次数后返回错误；总线异常用 CAN 干扰仪或软件模拟丢帧。关键是让这些异常可复现、可脚本化，才能进回归测试。
