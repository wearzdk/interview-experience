### 《面试题目》

1. 数仓方向：几个 KPI 的口径怎么定义、SQL 怎么写？
2. 设计一个高并发系统，你会怎么做？
3. 线程之间如何通信？
4. 场景题：设计一套 Agent 检测思路。

### 《参考解析》

**先看清岗位错配这件事**。JD 写的是数据平台/数仓，面试却很快切到后端题，说明这个团队的数据平台是「服务自动驾驶数据链路」的工程岗，数仓只是其中一块。准备这类岗位时，SQL 与指标口径够用就行，重点要放在服务端基础上。

**KPI 口径题答的是「定义 + 口径 + 边界」**，不是写 SQL。以最常见的「日活」为例：先定义什么算一次有效活跃（登录？有核心行为？），再定去重口径（按用户 ID 还是设备 ID）、时间口径（自然日按哪个时区切）、以及迟到数据怎么处理（T+1 重跑还是流式更正）。面试官追问的往往就是这些边界，能主动说出来比背 SQL 模板更有说服力。

**高并发系统设计**按四层铺开就够：接入层（限流、负载均衡、连接复用）、服务层（无状态化、缓存、异步化与消息队列削峰）、存储层（分库分表、读写分离、热点隔离）、以及保障层（降级、熔断、幂等与可观测）。自动驾驶数据平台的典型负载是「大批量写入 + 少量实时查询」，答题时如果能把这个特征点出来——写入走批量与分区表、查询走预聚合或列存——会显得真的想过业务。

**线程通信**要分清共享内存与消息传递两条路：共享内存靠锁、`synchronized`/`ReentrantLock`、条件变量（`wait/notify`、`Condition`）、`CountDownLatch`、`Semaphore`、阻塞队列；消息传递靠管道、Socket、消息队列。答题时给出选择依据：状态共享用锁和条件变量，解耦与削峰用队列，跨进程用消息中间件。

**「设计 Agent 检测思路」这类场景题，先问清「检测什么」**：是检测 Agent 的行为异常（越权调用、幻觉输出、无限循环），还是检测系统里是否存在 Agent 流量？前者按「指标 + 规则 + 模型」三层答：采集调用链与工具调用日志，定规则（调用次数、越权、超时、循环），再用异常检测兜住规则覆盖不到的形态，最后落到告警分级与人工复核。后者更偏流量识别，看 UA、请求节奏、会话连续性与工具调用特征。把问题拆清楚再答，比直接抛方案得分高。
