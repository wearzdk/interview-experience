### 《参考解析》

**单智能体还是多智能体，判据是决策权而不是工具数量。** 一个核心 Agent 内部挂了搜索、计算、记忆等一堆工具，只要「下一步做什么」始终由同一个决策循环拍板，它就还是单智能体——工具只是被调用的能力单元。多智能体的本质是把决策权切开，每个 Agent 有自己的目标、上下文和工具集。真正的收益往往来自上下文隔离：把几十个工具塞进一个 prompt，模型选错工具的概率会显著上升，拆成专职子 Agent 后每个 prompt 只需要认识自己那几个工具；代价是通信开销、状态同步和错误传播——A 的幻觉会被 B 当成事实继续推理下去。工程上比较稳的形态是「单智能体为主 + 少量窄职责子 Agent」，尤其是把校验单独做成一个 Agent 比自己查自己更有效，因为自查用的还是同一份上下文和同一个偏见。这里面试官容易追一句「多个 Agent 之间怎么传状态」，答案是结构化 handoff（明确字段的任务单）而不是自然语言转述，转述每传一手就丢一点信息。

**记忆分两层，难点在写入而不是检索。** 短期记忆就是上下文窗口：滚动保留最近 N 轮，超出后做摘要压缩。压缩的粒度要小心，按轮硬截会把一句话截成半句，按主题摘要更稳。真正吃 token 的通常不是对话本身而是工具返回值，所以裁剪应该发生在工具结果落进上下文之前（只留需要的字段、长文本截断），而不是事后压缩历史。长期记忆本质是一个「写—读」系统：写什么（事实、偏好、约束，不写寒暄和过程）、什么时候写（回合结束后异步抽取，不要卡在主链路上）、怎么防冲突（同一主题的新事实要覆盖旧的，带时间戳和来源，否则模型会同时召回「用户在上海」和「用户在北京」）。召回侧 top-k 不宜大，召回过量会把当前上下文稀释掉；返回结果要带时间和出处，让模型自己判断时效。

**ReAct 的循环很朴素，成本却常被低估。** 它是 Thought → Action → Observation 的交替，直到模型判断任务完成。每一轮都是一次完整前向，工具多、上下文长时单轮就要几秒；步数一多上下文线性膨胀，越到后面决策质量越差。它有四类典型病：输出格式不稳导致解析失败、空转或死循环（反复调同一个工具）、工具选错或参数填错、上下文爆炸。工程兜底是逐项对应的：JSON Schema 强约束加解析失败重试一次再降级；硬性最大步数加「无进展检测」（连续两步 observation 哈希相同就中断）；工具结果统一结构化裁剪，别让模型去读原始 HTML；状态落盘让中断可恢复；所有写操作带幂等键。还有一个必须能答出来的判断：ReAct 适合路径不可预知、要根据中间结果调整的任务，如果流程本来就是固定的，写成 workflow 更稳、更便宜、也更好测。

**改进路线各有各的前提。** Reflexion 在失败后让模型反思再试，前提是任务可重试且有可靠判定信号（单测、评分器）——没有信号时反思很容易退化成自我安慰。Plan-and-Execute 先出子任务 DAG 再逐步执行，全局性好、省调用，代价是计划错了要重规划，对环境突变的响应也慢。ReWOO 把推理和取数解耦，一次规划出所有变量依赖再一次执行，调用次数最少，但执行中拿到意外结果时改不了计划。选型判据可以归结成两句：任务可分解、步骤可预测就走 plan 类；强交互、每步依赖上一步结果就走 ReAct。生产系统里常见的是混合——外层用 plan 划阶段，阶段内部用 ReAct 处理不确定性。

**MCP 解决的是一张 M×N 的连接表。** 结构是 Host（承载 LLM 的应用）、Client（协议客户端）、Server（暴露能力的轻量程序），走 JSON-RPC 2.0，对外提供三个基元：Tools 是可执行函数、Resources 是可读数据、Prompts 是预置模板。价值在于把「每个应用 × 每个工具都要单独写适配」的 M×N 变成 M+N，一个 Server 写好，所有支持 MCP 的客户端都能用。工程细节比概念更值得说：工具的 description 和参数 schema 实际上就是 prompt，写得含糊模型就选错、填错，枚举值和示例一定要给全；工具数量一多，光定义就吃掉大量上下文，要做分组或按需加载；权限校验和审计必须放在 Server 侧，不能信任 Client；传输有本地 stdio 和远程 Streamable HTTP 两种，连接生命周期、超时、断线重连都要设计。被追问「和直接写 function call 有什么区别」时，答协议统一了发现与调用、能跨客户端复用；单机单应用时直接 function call 更轻，没必要上协议。

**Skill、MCP、Function Call 是三件事，别混着答。** MCP 管连接与能力边界（有哪些工具、参数长什么样），Skill 管方法与经验（这类任务按什么顺序做、哪些坑要避开），Function Call 管一次具体执行。Skill 是程序性知识的封装，关键机制是渐进式加载：正文只在需要时才读进上下文，否则装几十个 Skill 直接把窗口占满。所以好的 Skill 是「一句 description 决定要不要加载，正文写判断标准而不是罗列命令」。这三者的分工可以压缩成一句话记：MCP 管连接，Skill 管方法，Function Call 管执行。

**DeepSeek Harness 值得借的是「没有特权核心」这个约束。** 模型适配器、工具注册表、会话管理、智能体循环、沙箱、存储全部是插件，都可以被替换，运行在 Cordis 这类支持动态组合的元框架上。落到个人助理上有三点可直接抄：一是 append-only 的会话日志，只追加不修改，天然支持回放、分叉和从中断处恢复，调试 Agent 时比打日志有用得多；二是把工具执行放进沙箱，副作用与主进程隔离；三是模型适配器把「换模型」变成配置项而不是改代码。但要提醒一句，插件化不是免费的：接口边界要窄、要有契约测试，否则每加一个插件都是一次兼容性赌博；每多一层抽象就多一层可观测性负担，trace 必须能串起「模型决策 → 工具调用 → 插件内部」。

**Redis 的三种分布式形态要能说清边界。** 主从复制是一写多读，异步复制意味着故障切换时可能丢掉最后一段写，读写分离也要接受读到旧值，关键读走主库。哨兵在主从之上加监控和自动故障转移，要部署奇数个（至少 3 个）做多数派投票，客户端必须订阅切换事件并刷新连接池，否则切完还在往旧 master 写。Cluster 是官方分片方案，16384 个槽、key 经 CRC16 取模定位，客户端收到 MOVED 要更新路由表、收到 ASK 只对本次迁移中的 key 临时转向。最容易踩的坑是跨槽限制：MGET、事务、Lua 脚本里涉及的多个 key 必须落在同一个槽，所以设计 key 时用 hash tag 把相关的绑在一起，比如 `{user:1}:cart` 和 `{user:1}:order`。追问常到分布式锁——主从异步复制下锁可能丢，Redlock 又有时钟漂移和 GC 停顿的争议，生产上更常见的是单实例加 fencing token，或者干脆把强一致诉求交给 etcd / ZooKeeper。

**秒杀链路的骨架是「Redis 挡量、消息队列削峰、数据库只做流水」。** 请求进来先做前端限流和资格校验，然后到 Redis 做库存预检与原子扣减，扣成功就发消息、返回排队中，后台消费落库生成订单，客户端轮询结果。这里有个细节值得点出来：原帖方案是「先查库存、再抢分布式锁、再 decr」，其实 Lua 里 `get` + 判断 + `decr` 本身就是原子的，额外加一把锁只多了一次 RTT 和一轮锁竞争，锁应该留给「跨多个 key 或多个资源」的场景。不超卖只是底线，真正难的是少卖和回补：下单超时未支付的库存要还回去，回补必须带幂等标记，否则重复消费会把库存加两次；消息要保证不丢（本地消息表或事务消息），消费端按业务唯一键去重；单个库存 key 撑不住十万级 QPS 时要分片（把 1000 库存拆成 10 个 key），扣减随机选片、失败换片。另外这里的 Redis 是权威库存源而不是缓存，落库只是流水，别在数据库上再判一次库存。

**RAG 的价值在半条链路之外——每一步都有自己的失败模式。** 离线侧是解析、切分、嵌入、入库（带 metadata）；在线侧是 query 处理、多路召回、融合、rerank、拼 context、生成、给引用。解析阶段表格和扫描件最容易丢结构；切分阶段固定长度会把跨段语义切断，父子块（小块检索、大块喂模型）就是为了解这个矛盾；嵌入阶段通用模型对专业术语和型号区分度差；召回阶段只走向量会漏掉精确串（错误码、型号、人名），所以要和 BM25 混；生成阶段上下文太长会稀释重点，模型也倾向不忠实，必须给引用并要求「无据不答」。整套东西想调得动，前提是有一个 golden set 和拆开的指标（recall@k、答案忠实度、端到端时延），否则改 chunk size 只能靠感觉。

**Query Rewrite 的四类手法，收益和代价不成正比。** 指代消解解决多轮里的省略（「它多少钱」补成「上一轮那台机器多少钱」），便宜且收益稳定，应该先做；术语归一把口语换成知识库里的正式说法；多 query 扩展从同义和不同角度生成几条检索词再合并去重；HyDE 先让模型生成一个假设答案、再用假设答案去检索，对短查询和术语鸿沟效果明显，代价是多一次生成、延迟接近翻倍；step-back 则先问一个更抽象的问题拿到背景，再回答具体问题。坑有两个：改写会引入漂移，把用户没问的东西加进去，反而跑偏；多 query 会放大延迟和重复召回，所以要有开关和预算控制。改写结果一定要落日志，不然线上效果变差时无法定位是哪一步的锅。

**召回优化和耗时优化，最后往往收敛到同一件事：少检索一点。** 召回侧的标准组合是混合检索加 RRF 融合（按名次而不是分数融合，避免两路分数量纲不一致），metadata 过滤（时间、权限、版本）必须放在召回前，否则 top-k 会被不该看的内容占满；精排用 cross-encoder 只对 top50~100 做，全量重排的成本没人付得起。耗时侧先分段打点，分清检索和生成各占多少再动手：检索用 ANN（HNSW 的 M 与 efSearch 就是召回率和延迟的两个旋钮）、embedding 离线预算、多路召回并行、热门 query 结果缓存；生成侧用 prefix cache 复用 system prompt、控制 context 长度、流式输出降低感知延迟。实践中把 top-k 从 20 降到 5、把 context 压紧，经常是又快又准——上下文塞得越满，模型越容易在无关段落里迷路。
