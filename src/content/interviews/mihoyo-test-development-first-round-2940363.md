### 《参考解析》

**栈与堆、new 与 malloc 是两组不同维度的问题。** 栈由编译器自动管理，随函数调用分配与释放，地址连续、分配只需移动栈指针，速度快，但空间有限（Linux 默认线程栈 8MB，Windows 默认 1MB），递归过深或大数组会栈溢出。堆由运行时分配器管理，生命周期手动控制，空间大但分配要走空闲链表或伙伴系统，存在元数据开销与碎片，访问局部性也不如栈。`new` 是 C++ 运算符，分配后调用构造函数，失败抛 `std::bad_alloc`，返回具体类型指针，释放用 `delete` 并调用析构；`malloc` 是 C 库函数，只分配指定字节数，失败返回 `nullptr`，需要 `sizeof` 与强制转换，释放用 `free` 且不调用析构。`new[]` 必须配 `delete[]`，否则只析构第一个元素；底层 `operator new` 通常还是调用 `malloc`，但两者语义不同，`new` 可以被类或全局重载，placement new 还能在已有内存上构造对象。嵌入式场景更关心的是避免在中断和热路径里动态分配，而不是背这两组差异。

**从源文件到进程要经过预处理、编译、汇编、链接、装载五步。** 预处理展开宏与头文件、处理条件编译；编译做词法、语法、语义分析，生成中间表示并优化，最终产出汇编代码；汇编器把汇编翻译成目标文件，其中包含机器码、符号表与重定位信息；链接器做符号解析与重定位，把多个目标文件和静态库合并，或留下对动态库的引用，生成可执行文件；运行时装载器把段映射进地址空间，动态链接器完成符号绑定，从入口 `_start` 走到 `main`。C++ 还多出模板实例化与名字修饰（name mangling），这也是「编译通过但链接报 undefined reference」的常见来源：声明存在、定义缺失，或者签名因命名空间、const、参数类型而不匹配。静态链接把库代码复制进可执行文件，体积大但部署简单；动态链接共享库、节省内存，但依赖运行环境的库版本。

**C# 单例的关键是构造私有化与线程安全的初始化。** 饿汉式用 `static readonly` 字段在类型初始化时创建实例，CLR 保证类型初始化线程安全，写法简单，但会在首次访问类型时即创建，可能提前占用资源。懒汉式需要延迟到第一次使用，朴素写法在多线程下会创建多个实例；加锁的双重检查必须把实例字段声明为 `volatile`，否则可能读到已赋值但构造尚未完成的半成品对象；更稳妥的是 `Lazy<T>` 配 `LazyThreadSafetyMode.ExecutionAndPublication`，或静态内部类利用 CLR 的延迟初始化。单例的代价是隐藏依赖、难以替换与测试、并发下可能成为瓶颈，现代 C# 项目更常用 DI 容器注册 Singleton 生命周期，而不是在业务类里直接取静态实例。GC 方面，.NET 采用分代回收：小对象在第 0 代分配，存活后晋升到第 1、2 代，大对象进入 LOH；回收以标记—压缩为主，第 0 代回收频繁且快，第 2 代与 LOH 成本高。`async/await` 不是多线程，而是编译器把方法改写成状态机：遇到未完成的 `await` 就返回调用方、释放线程，任务完成后在捕获的同步上下文或线程池上继续执行；CPU 密集任务不应靠它提速，`async void` 只应用于事件处理器，库代码应使用 `ConfigureAwait(false)` 避免不必要的上下文切换。

**进程、线程、协程的差别在调度层次与切换成本。** 进程是资源分配单位，有独立地址空间、文件描述符与信号处理，进程间通信需要管道、消息队列、共享内存或 socket；线程是调度单位，同进程内共享地址空间与堆，各有栈、寄存器和线程本地存储，切换需陷入内核、成本在微秒级，共享数据要加锁；协程是用户态的协作式调度，切换只保存少量寄存器与栈，成本在纳秒级，适合高并发 IO，但一个协程阻塞会拖住整个调度线程，需要运行时或框架保证不让阻塞调用混进来。C# 的 async 状态机、Go 的 goroutine、C++20 的无栈协程都属于这一层，区别在于是否有栈、由谁调度、能否跨线程恢复。

**区间反转链表用一次遍历完成。** 建哑节点指向 head，先走 `left-1` 步找到反转区间的前驱 `pre`，再从 `pre->next` 开始，把区间内的节点依次头插到 `pre` 之后：记录 `cur`，每轮把 `cur->next` 摘下插入 `pre->next`，重复 `right-left+1` 次，最后返回 `dummy->next`。时间复杂度 O(n)，空间 O(1)。边界要覆盖 `left == 1`（哑节点保证前驱存在）、`left == right`（不反转）、区间到尾节点。测试视角还要补：空链表、单节点、越界参数、反转后 `next` 是否成环、原头尾指针是否正确，这些正是测试开发岗位在写完算法后通常会被追问的点。

**AI 参与测试流程要分清「生成」与「判定」。** 能落地的环节包括：根据需求与接口文档生成用例草稿、把失败日志聚类后归因、为 UI 自动化生成或修复选择器、对截图做视觉断言、从缺陷单里抽取复现步骤。真正难的是判定标准：LLM 生成的用例需要人去定义覆盖口径，LLM 判断「这像不像 bug」需要可复现的证据链，否则只是把噪声从一层搬到另一层。较稳的做法是把 AI 放在「提议」位置，执行、断言与准入仍由确定性程序和人负责；Agent 化的测试流程通常是规划器拆解测试目标、执行器调用工具跑用例、校验器比对结果，失败后回到规划器重新生成，并设置步数与成本上限。面试中被问到「有没有做过 Agent 项目」时，能说清这套分工与失败兜底，比罗列工具名更有价值。
