### 《参考解析》

**ThreadLocal 的结构与那个「弱引用」问题。** 每个 `Thread` 内部持有一个 `ThreadLocalMap`，key 是 `ThreadLocal` 对象本身（被包装成 `WeakReference`），value 是线程私有的数据，所以隔离的载体是线程而不是 ThreadLocal——这也是「同一个 ThreadLocal 在不同线程里拿到不同值」的原因。`ThreadLocalMap` 没有链表，冲突用开放寻址（线性探测）解决，这也是它用 `ThreadLocal` 的 `threadLocalHashCode` 增量做下标的理由。为什么 key 用弱引用：如果 key 是强引用，那么只要线程还活着（线程池里的核心线程几乎永远活着），外部即使把 `ThreadLocal` 引用置空，map 里仍然强引用着它，这个 key 就永远回收不掉。弱引用让 key 在外部没有强引用时能被 GC 回收，避免 key 泄漏。但关键要补上后半句：**value 是强引用**，key 被回收后 Entry 变成 key 为 null 的 stale entry，value 依旧无法访问也不会自动回收——所以真正的泄漏是 value 造成的，`ThreadLocalMap` 只在 `set/get/remove` 时顺带清理一部分 stale entry（探测式清理），清理不保证彻底。结论是必须显式 `remove`，尤其在 Web 容器和线程池里，一个请求用完不清理，下一个请求可能读到上一个请求的数据，这既是内存泄漏也是数据串号事故。

**MQ 不用 ack 能不能保证可靠？这题的正确姿势是先拆解「可靠」的定义。** 消息可靠性是一条链：生产端要拿到 Broker 的确认（同步发送或异步回调加重试），Broker 端要落盘与多副本（同步刷盘、主从同步复制），消费端要「业务处理成功之后」才提交位点。ack 正是第三段的机制，取消 ack（自动确认或 no-ack 模式）意味着消息一投出就被标记为已消费，一旦消费端处理失败或进程崩溃，这条消息就永久丢了。所以「不用 ack 保证可靠」严格来说做不到端到端可靠，只能靠几种补偿把风险压小：消费端做幂等（用业务唯一键去重），业务失败就主动记录到重试表或死信队列由定时任务补偿；用「先入库再处理」的本地消息表模式自己维护状态；对账系统定期比对上下游数据找出缺口。另一种理解是「不做逐条手动 ack，而是批量 ack」，那就要用「处理完一批再确认」的顺序保证批内不丢。答这题时先反问澄清对方指的是哪一层，比直接背 Kafka 与 RocketMQ 的 ack 差异更稳。

**LRU 的原理一行话：哈希表加双向链表，查和动都是 O(1)。** 哈希表负责 O(1) 定位节点，双向链表维护使用顺序，新访问的节点移到头部，淘汰时取尾部。手写的注意点是用哈希表存 `key -> node` 而不是存值、以及哨兵头尾节点能免掉大量判空。但工程里的 LRU 几乎都是「近似 LRU」：Redis 为了省内存不维护真正的链表，而是随机采样若干 key 挑最久未使用的淘汰（`maxmemory-samples`，采样越大越接近真 LRU）；MySQL 的 Buffer Pool 用的是改良版 LRU，把链表分成 young（热）与 old（冷）两段，新页先插到 old 区的中间点，并且经过多次访问才晋升到 young 区，目的是防止全表扫描或预读把热数据冲掉；Caffeine 这类本地缓存更进一步用 W-TinyLFU，用频率加窗口来避免「偶发的一次扫描污染整个缓存」。LRU 的固有弱点是「一次大范围扫描会冲掉热数据」，这是它和 LFU 的核心差别：LFU 看频率不看最近性，但需要处理历史热点的衰减。应用场景可以举：Redis 缓存淘汰、数据库与操作系统的页/块缓存、CPU 缓存替换、以及本地缓存库的淘汰策略。

**Redis 的内存淘汰策略一共八种，要按「淘汰范围 × 算法」两维记。** 范围上分 `allkeys-*`（所有 key 都可能被淘汰，适合纯缓存用途）与 `volatile-*`（只在设置了过期时间的 key 里淘汰，适合 Redis 兼作存储的场景）；算法上有 `lru`（最近最少使用，实际是带 24 位时间戳的近似实现）、`lfu`（最少使用频率，用计数器加概率递增和定期衰减，适合热点数据稳定的场景）、`random`（随机淘汰）、`ttl`（优先淘汰剩余存活时间短的）。此外还有 `noeviction`：内存打满时写入直接报错，适合把 Redis 当可靠存储用的场景。选择和配置的要点：`maxmemory` 必须设置（否则默认不限制直到 OOM），缓存场景推荐 `allkeys-lfu` 或 `allkeys-lru`，`volatile-*` 的坑是如果大量 key 没有过期时间，内存打满时可能只剩很少的候选可淘汰甚至报错。要能顺着追问说清「淘汰」与「过期删除」是两回事：过期是惰性删除加定时抽样清理，淘汰是内存达到上限后的策略，二者都靠采样实现，所以两者都不精确。

**被问到家庭、身高、入党、成绩这类问题怎么处理。** 这些问题在技术面里出现，通常对应三类考察：稳定性与长期意愿（家庭所在地、能否接受异地派驻）、抗压与服从性（优缺点、自我评价）、以及单位特有的倾向（国企、事业单位对党员身份、在校表现看得更重）。应对原则是简短、如实、不辩解、不情绪化：一句话给出事实，能顺势接到岗位相关的内容就接（比如「家在本地，父母都在本地工作，所以我对长期留在本地发展没有顾虑」）；确实不愿意回答的私人信息（身高这类与岗位能力无关的问题）可以礼貌地把话题拉回工作相关，不必对抗也不必编造。面完把这类问题的密度记下来，它本身就是判断团队风格的信息——技术面里个人问题占比过高，往往说明这家单位的评价重心不在技术深度。

**五年规划怎么答才不像背稿。** 面试官问这个不是要听「三年主管五年总监」，而是想知道你有没有与岗位对齐的成长路径、以及对节奏的现实预期。稳妥的结构是三层：近一年把业务与技术基础打牢、能独立承接模块并保证质量；两到三年在某个方向上形成自己的专长（结合岗位说，比如高并发或数据链路）、能主导跨模块的改造；更远则是把技术判断力和带人的能力补上。关键是要有「怎么达成」而非只有「达成什么」——比如提到通过项目复盘、代码评审和读源码来补体系化能力，并且说清这条路径与该团队的实际业务是一致的。作者这场技术问题里唯一没答上来的是 MQ 不用 ack 那问，这也提示了准备重点：消息中间件不该只背模型，丢消息与重复消费的每一种组合都要能说清。
