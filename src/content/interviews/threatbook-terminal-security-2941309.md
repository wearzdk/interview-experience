### 《面试题目》

1. 说一个你项目中遇到的难点，还有你是怎么利用 WinDbg 或者其他调试工具解决的？
2. 重复打开进程句柄、重复关闭进程句柄会有什么问题？
3. 一般是怎么使用 dmp 文件（以及另一个文件）来查崩溃的？
4. 环 3 层跨进程资源共享的方法有哪些？
5. APC 注入让线程进入可提醒状态的 API，能多说几个吗？
6. 动态多态：链表构造节点时传空指针，构造函数没有用引用的情况下，访问构造的节点会产生什么问题？怎么解决？
7. 访问 0x1000 以下的进程空间为什么会异常？

### 《参考解析》

**用 WinDbg 定位项目难点**：讲一个具体的崩溃案例：现象（偶发崩溃、错误码）、如何拿到 dump（任务管理器或 WER 配置、`procdump`、`MiniDumpWriteDump`）、如何在 WinDbg 中分析（`!analyze -v` 看异常类型与栈、`kb` 看调用栈、`!heap` 与 `!address` 看内存、`dt` 看结构体、`.ecxr` 切换异常上下文）。结论要落到根因（空指针解引用、释放后使用、栈溢出、堆损坏）与修复，以及如何验证。没有 dump 时可以用页堆（gflags + Application Verifier）让越界立即崩溃，便于复现。

**重复打开/关闭句柄**：每次 `OpenProcess` 等调用都会在进程句柄表中新增一项并增加内核对象引用计数；只打开不关闭会泄漏句柄，最终耗尽句柄表（表现为后续打开失败）。重复关闭同一个句柄是更严重的问题：句柄值可能已被系统复用给另一个对象，第二次 `CloseHandle` 会关掉别人的句柄，造成难以定位的故障；调试器下会报 `STATUS_INVALID_HANDLE`。正确做法是成对管理、用 RAII 封装、关闭后置空，且不要跨线程关闭同一句柄。

**dump 分析**：用户态崩溃通常生成 minidump（.dmp），配合符号文件（.pdb）才能还原函数名与行号。分析流程是设置符号路径（`srv*` 指向微软符号服务器 + 自己的 pdb）、打开 dump、`!analyze -v`、查看异常记录与调用栈、检查相关对象的生命周期。全内存 dump 能看到更多堆数据但体积大。若只有崩溃转储没有 pdb，只能看模块与偏移，定位困难，所以发布版本要归档对应 pdb。

**环 3 跨进程资源共享**：常见方式有文件映射（`CreateFileMapping` + `MapViewOfFile`，共享内存）、命名管道、邮槽、WM_COPYDATA 消息、COM、Socket（本机回环）、以及通过驱动做内核中转。共享内存最快，但要自己做同步（命名互斥量、信号量、事件）；窗口消息适合小数据；COM 适合需要接口调用的场景。选择依据是数据量、同步需求与安全边界（是否要跨会话、是否要权限隔离）。

**APC 注入与可提醒状态**：APC（异步过程调用）排队到目标线程后，线程必须处于可提醒状态才会执行。让线程进入可提醒状态的 API 包括 `SleepEx(TRUE)`、`WaitForSingleObjectEx(..., TRUE)`、`WaitForMultipleObjectsEx(..., TRUE)`、`SignalObjectAndWait(..., TRUE)`、`MsgWaitForMultipleObjectsEx` 的 alertable 参数，以及 `NtTestAlert`（触发当前线程的 APC 队列）。APC 注入的流程是 `OpenProcess` → `VirtualAllocEx` 写入 shellcode/DLL 路径 → `QueueUserAPC` 到目标线程 → 等待线程进入可提醒状态。这也是终端安全产品重点监控的行为。

**动态多态与空指针构造**：题目描述的场景是链表节点构造时传入空指针，构造函数参数不是引用，于是发生了对空指针的解引用（拷贝构造或成员访问），触发访问违例。若参数写成引用，传空指针在调用点就是未定义行为，但通常会在进入函数前就崩溃，反而更容易暴露。根因是调用方没有校验指针，或构造函数承担了不该承担的职责。解法是在入口校验（断言或返回错误）、用引用表达「不可为空」的契约、用智能指针明确所有权，以及在链表操作里区分「头插/尾插」对空表的处理。

**访问低地址异常**：Windows 用户态进程的低 64KB（0x00000000–0x0000FFFF）被系统保留，用于捕获空指针与无效指针的解引用，任何访问都会触发访问违例。这不是硬件限制，而是操作系统有意留下的保护区，便于把「野指针」变成确定性崩溃而不是静默破坏内存。调试时看到异常地址在低地址区，基本可以直接判断为空指针加上偏移后的访问。
