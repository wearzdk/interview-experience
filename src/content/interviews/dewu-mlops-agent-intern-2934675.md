### 《参考解析》

**「记录当前操作人」有四种来源，要能说清各自信任边界**：一是登录态里带（Session 里的 userId、JWT 的 sub），由服务端从 cookie 或 Authorization 头解出，可信；二是网关注入的请求头（如 X-User-Id），前提是只有网关能写、外部请求的该头必须被剥掉；三是业务参数显式传入，最不可信，必须服务端校验；四是审计埋点在前端采集的账号信息，只能用于展示与埋点，绝不能当权限依据。答这道题的关键是区分「认证信息」与「审计信息」：前者必须服务端解出，后者可以前端上报但要标明不可信。

**Cookie、Session、JWT 的关系**：Cookie 是浏览器侧的存储与自动携带机制，本身不是认证方案；Session 是服务端保存会话状态、客户端只拿一个 sessionId（通常放在 Cookie 里），优点是服务端可随时失效、能存较多状态，缺点是有状态、需要共享存储；JWT 是自包含的签名令牌，服务端无状态校验，适合多服务横向扩展，缺点是签发后难撤销、载荷可被读取（不能放敏感信息）、续期要额外设计 refresh token。工程上常见组合是「短期 access token + 长期 refresh token」，并把登出、改密做成黑名单或版本号失效。

**一个 HTTP 请求到查库的链路**：浏览器解析 URL 并查 DNS（浏览器缓存、系统缓存、hosts、递归解析）→ 拿到 IP 后建立 TCP 连接（三次握手是客户端与服务端之间，经过的每一跳只是转发，不参与握手）→ 如果是 HTTPS，再在 TCP 之上做 TLS 握手，校验证书并协商会话密钥 → 发出 HTTP 请求，经过可能存在的 CDN、负载均衡、网关（鉴权、限流）→ 到达应用服务，框架路由到 controller，参数校验后调 service，查缓存（未命中再查库），ORM 生成 SQL 走连接池 → 数据库解析、优化器选索引、执行器取数据（可能回表）→ 结果逐层封装成响应，按 Content-Length 或 chunked 返回，连接按 keep-alive 复用或关闭。面试官追问「握手是谁跟谁握」就是在考你有没有把这句背成口头禅。

**让模型稳定输出 JSON 的工程手段，由弱到强**：提示词层给 schema 示例与「只输出 JSON」约束；调用层优先用厂商的结构化输出能力（response_format / JSON mode / tool calling 的入参 schema）；校验层在服务端用 JSON Schema 校验并对失败重试；兜底层做截断修复（补齐括号、去掉 markdown 代码块包裹）与降级到人工；评测层统计解析成功率而不是靠感觉。只靠提示词必然有一定比例失败，真正稳的是「约束生成 + 强校验 + 有界重试」。

**数据质量这类问题要能给出可执行的观测口径**：先说清 valid data 的判据来自哪（业务规则、schema 校验、抽样人工标定、与线上真实数据分布比对），再说度量指标（字段缺失率、格式非法率、分布偏移、重复率、与源数据的对账差异），最后说怎么闭环（每日跑批产出质量报告、阈值告警、坏样本回流到评测集）。如果验证是脚本做的，就要说清规则覆盖了什么、脚本管不了的语义正确性靠什么补——通常是抽样人工评审。

**读代码题的高频问题点**：调用大模型 API 做代码 review 这种脚本，生产化时要盯住——密钥硬编码、无超时与重试、没有限流与并发控制、prompt 拼接导致超长上下文被截断、返回未校验就直接写回仓库、错误被吞掉、日志里打印了源码或密钥、成本不可控（没有 token 统计）、以及评审结论缺少可追溯的输入快照。面试官问「放到生产会怎样」，想听的就是这些工程缺口，而不是语法错误。
