### 《面试题目》

1. 自我介绍。
2. 能不能提前实习一个月？想做开发还是运维？
3. `select count(*), count(column), count(1)` 有什么区别？
4. 看你都是在互联网实习，为什么投递金融行业？
5. 实习经历里有跨端，具体讲讲跨端做了什么？
6. 输入 URL 到页面渲染的全过程是怎样的？
7. 在两家公司实习，感觉有什么差别？

### 《参考解析》

**`count(*)`、`count(1)`、`count(column)` 的差别在语义和扫描方式两层**。语义上，`count(*)` 与 `count(1)` 统计行数，不判断任何列是否为 NULL，两者结果永远相同；`count(column)` 只统计该列非 NULL 的行，列里有 NULL 时结果会小。执行上，InnoDB 不保存表的总行数（MVCC 下每个事务看到的行数不同，无法维护单一计数），`count(*)` 与 `count(1)` 都由优化器选择代价最小的索引做扫描，通常是最小的二级索引——二级索引叶子节点只存索引列与主键，比聚簇索引整行更小，扫描的页更少；`count(column)` 必须真正读出该列的值判断是否为 NULL，如果这一列上没有可用的索引，就只能回表或全表扫描，代价明显更高。所以「`count(1)` 比 `count(*)` 快」是流传很广的错误结论，MySQL 官方文档明确说两者等价。面试官若追问大表计数，答案不是硬 count：用一张计数表在业务事务里同步增减、用近似统计、或者把统计请求放到从库；`count(column)` 的写法本身就该避免，需要非空计数时加 `where column is not null` 更清楚。

**输入 URL 到页面渲染要按网络与渲染两段讲，中间点出阻塞**。网络段：浏览器查 DNS（先本地缓存、hosts，再递归查询），拿到 IP 后建 TCP 连接（三次握手），HTTPS 还要 TLS 握手协商密钥，然后发 HTTP 请求，服务端可能经过负载均衡、缓存、应用层处理再返回响应，浏览器根据状态码与缓存头决定是否使用本地副本。渲染段：解析 HTML 构建 DOM，解析 CSS 构建 CSSOM，两者合成渲染树（不可见元素如 `display:none` 不进入），接着布局计算每个节点的几何位置，再绘制成图层、由合成器合成上屏。要主动补充两个关键点：脚本默认阻塞 HTML 解析，`defer` 让脚本在解析完成后按顺序执行、`async` 下载完就执行且不保证顺序；样式与布局变化会触发重排（reflow），只改颜色这类属性只触发重绘，用 `transform`、`opacity` 做动画可以只走合成层，代价最低。再深一层可以提关键渲染路径优化：减少阻塞资源、预加载、把首屏关键 CSS 内联。

**为什么从互联网转金融，答动机不要贬低任何一方**。可信的答法是讲「匹配」：金融信息系统的特点是强一致、可审计、变更谨慎，自己更适应这种把正确性放在第一位的工程节奏；同时说明自己对业务的理解——交易所与登记结算类系统的核心是交易与登记的准确、对账的严密，技术栈上常见 Oracle、DB2 与信创环境，愿意投入去补。反过来把互联网说成「太卷、不稳定」会显得是在逃避，也不符合面试官想听的稳定性判断。被问到「开发还是运维」，如果没有强烈偏好，就答「先做开发打底，愿意承担运维值班」，并给出理由：开发和运维在同一套系统上，理解部署与故障处理能让开发写出更可运维的代码。

**跨端经历要讲清「跨的是什么端、难在哪」**。常见形态有三种：React Native / Flutter 这类自绘或桥接式跨平台框架、小程序与 H5 的多端复用、以及一套业务逻辑同时跑在桌面端与移动端。面试官想听的是差异处理，不是「用过某框架」：同一套代码在不同端的布局与手势差异、原生能力通过桥接调用的边界、发版节奏不同导致的多版本兼容、以及埋点与错误监控如何统一。答的时候挑一个具体功能，说清「原本两端各写一遍 → 改成共享哪一层 → 省了什么、又新添了什么成本」。

**两家公司实习的差别，落到流程与工程文化上比落到「氛围好」上更有说服力**。可以比较代码评审的严格程度、需求到上线的链路长短、测试与灰度的覆盖方式、故障复盘是否真的追到根因、文档与知识沉淀的习惯。诚实说出「上一家发布更自由、这一家评审更重」，再补一句自己因此养成的习惯，比一味夸其中一家更像有判断力的人。

**这场面试的形态值得注意**：五六个面试官轮流问一两个问题、每人十几分钟，说明每一轮的问题都由不同角色出，覆盖面广而深度有限，回答要短、结论先行。帖主提到的学历压力是这类统一招聘的常态，能做的就是把自己那段实习讲到「有具体数字、有取舍、有反思」，这是短时间内最难被比较掉的部分。
