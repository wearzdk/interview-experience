### 《面试题目》

1. 通过一段实习或者项目经历介绍一下你的工作。
2. Linux 环境下排查 CPU、IO 的命令有哪些？
3. 为什么选择分布式限流方案？
4. 你认为通过这段实习自己得到了哪些成长？
5. 场景题：支付系统和订单系统两个系统，怎么保证一致性？如果其中一个失败了怎么办？
6. 场景题：给 10000 个带 id 的文件，可以通过一个工具根据文档得到关键词，现在需要在单机系统里根据关键词找出哪些文档包含它（考察并发、map）。

### 《参考解析》

**排查 CPU 与 IO。** 先分诊再深入：`uptime` 看 load average 和几个核的比值，`top` 看 `%us`（用户态算力）、`%sy`（内核态，系统调用或锁竞争多）、`%wa`（等 IO）、`%si`（软中断，网络包多）。CPU 高的下一步是定位线程：`top -Hp <pid>` 找最热的线程号，转成十六进制去 `jstack` 里对栈，或 `pidstat -t -p <pid> 1` 直接看线程级占用；再往下 `perf top -p <pid>` 看热点函数。IO 高的路径是 `iostat -x 1` 看每块盘的 `%util`、`await`、`r/s`、`w/s`，`iotop -o` 找是哪个进程在写，`pidstat -d` 看进程级读写，`vmstat 1` 看 `bi/bo` 和 `wa`，`df -h` 排除磁盘写满，`lsof -p` 看句柄是否泄漏。两个反直觉点值得说：`%wa` 高不一定是磁盘慢，CPU 空闲等 IO 也会把 wa 顶高，要看 `await` 和 `%util` 才能确认；load 高也不一定是 CPU 忙，大量不可中断睡眠（D 状态）同样拉高 load。

**支付与订单的一致性。** 先明确不能上强一致：XA/2PC 在跨服务场景下同步阻塞、协调者单点、性能差，互联网业务基本不用。工程上走最终一致，四件套：① 本地消息表——订单库在同一个本地事务里写订单和一条待投递消息，事务提交后由投递器发 MQ，发失败就重试，保证「订单成功则消息一定发得出去」；② 消费端幂等——支付侧用业务单号做唯一索引或去重表，重复消息只生效一次；③ 状态机——待支付/已支付/已关闭，所有状态迁移用带条件的更新（`where status = '待支付'`），防止重复回调把已关闭的单改成已支付；④ 对账——按分钟级做增量对账、日终做全量对账，差异自动补单或退款。如果其中一个失败：优先正向补偿（重试 + 主动查询对方状态确认，很多「失败」其实是超时未知），补偿不了就反向冲正（退款/释放库存），仍然处理不了的进人工队列并留全链路流水。答题时一定要说「不确定的失败不能当失败处理，要先查再定」，以及「任何一步都不能 catch 住异常当成功」，这是面试官最想听的两句。

**单机并发处理一万个文件。** 这题的关键是先判断瓶颈不在并发数：10k 个文件在单机上，瓶颈是磁盘 IO 和那个外部关键词工具进程，线程开太多只会把磁盘打得更散。方案：固定大小线程池（IO 密集型，线程数取 2×CPU 到 32，配**有界**队列加拒绝策略，绝不用 `Executors.newFixedThreadPool` 的无界队列），每个任务「读文件 → 调工具拿关键词 → 写入倒排表」；倒排表用 `ConcurrentHashMap<String, Set<String>>`，写入用 `computeIfAbsent(k, x -> ConcurrentHashMap.newKeySet()).add(fileId)` 保证原子；主线程用 `CountDownLatch` 或 `CompletableFuture.allOf` 等全部完成再输出。对那个外部工具进程要加信号量限流（比如同时 8 个），否则 fork 出一万个进程直接拖垮机器，调用要设超时和失败重试。文件读取用流式或 `mmap`，注意编码和句柄释放（try-with-resources）。如果文件散在多个磁盘，按目录分片提交任务能让顺序读更连续。最后报复杂度：时间 O(总字节数 / 磁盘带宽)，空间 O(关键词数 × 文档数)，内存放不下就换成分片落盘再合并。

**为什么选分布式限流。** 单机限流（Guava `RateLimiter`、Sentinel 单机模式）在集群下每台各放各的，总放行量随实例数线性放大，一扩容阈值就失真；而下游数据库、第三方接口的容量是全局固定的，需要全局配额。分布式限流的实现：Redis + Lua 做令牌桶或滑动窗口（Lua 保证「取令牌 + 扣减」原子），Sentinel 集群流控用独立 token server 统一发配额，或者在网关层统一限。算法取舍要能说：固定窗口有临界突刺，滑动窗口精确但占内存，漏桶输出恒定速率，令牌桶允许一定突发、最适合对外 API。选它还有一个现实理由：限流要能动态调阈值、能按接口/租户/来源分维度，这些能力单机方案做不到。
