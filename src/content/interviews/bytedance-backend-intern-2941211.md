### 《参考解析》

**CI/CD 与触发链路**：CI 是持续集成——代码合入前自动完成构建、静态检查、单测与制品产出；CD 是持续交付/部署——制品自动发布到环境。Code Review Agent 通常挂在 CI 的某个阶段：MR 创建或更新触发流水线，拉取 diff、按仓库与语言路由规则、并行调用模型、把结果以行内评论回写，必要时以检查项阻断合入。触发范围要区分全量审查与增量审查：只审 diff 成本低、噪声小，但会漏掉跨文件的架构问题；全量审查看得全，但会把未改动的历史问题一并报出，造成大量噪声。合理做法是默认增量 + 对改动文件做上下文扩展（调用方、被调用方、相关规范），全量审查作为定期任务。

**规范冲突谁来定**：平台侧应只固化「安全与正确性」底线（空指针、资源泄漏、明显的并发错误、注入风险），业务规范（命名、分层、日志格式）由仓库自己声明并优先。冲突的处理不是让模型猜，而是规则分层 + 来源标注：每条 Issue 标明依据的是哪条规范，业务规范与平台底线冲突时按优先级裁决，并把裁决理由展示给用户。修复历史代码影响大时，Agent 只报新增/改动行，历史问题单独成「技术债清单」由人排期，不阻断合入。最终决定权在用户：提供「忽略此规则」「本文件豁免」的显式操作，并把这类反馈作为规则迭代的输入，而不是让模型反复争论。

**准确率口径**：讨论 43.8% 之前必须先定义分母——是「报出的 Issue 中被用户判定正确」的比例（精确率），还是「真实问题中被报出」的比例（召回率），评测集从哪来、由谁标注、样本量多少。只报精确率会诱导「少报」，只报召回率会诱导「全报」，所以要看 P/R/F1 与人工抽查，还要看「每个 MR 平均报出条数」「用户处理一条 Issue 的耗时」「被忽略率」。与同行对比时，公开数据往往口径不同（有的按文件、有的按 Issue、有的只统计高置信问题），不能直接横比；更有意义的是同一批评测集上的前后对比。31.7% 到 43.8% 的提升要能归因到具体改动（加了仓库规范、加了历史案例检索、改了提示词或分档阈值），否则数字不可复现。

**向量化检索是否只是绕过**：把历史 Issue 向量化后检索相似案例，本质是用「过去被判定为误报/正确的样本」给当前判断提供上下文，属于检索增强，不是绕过识别。但如果只靠过滤把不确定的报出项删掉，精确率上升、召回率下降，等于把问题藏起来。健康的做法是两条腿：识别侧改进（规范结构化、上下文补全、分文件分组并行），过滤侧用案例校准阈值，并同时监控召回。

**LRU 带过期**：题目没写 O(1) 时不要自己加约束，先确认需求：容量上限、get/put 语义、过期是惰性删除还是定时清理、是否线程安全。O(1) 的实现是哈希表 + 双向链表：哈希表存 key 到节点，链表头是最新使用、尾是最久未用；get 命中后把节点移到头部，put 时若 key 存在则更新并移到头部，不存在则插入头部，超容量删除尾节点。带 TTL 时每个节点存过期时间戳，get 时先检查是否过期，过期则删除并返回未命中（惰性）；另起一个定时任务或时间轮定期清理，避免大量过期键长期占用内存。Java 里可以用 `LinkedHashMap` 的 `accessOrder=true` 加 `removeEldestEntry` 快速实现，面试要求手写时再展开双向链表。并发场景要加锁或分段，注意「读时移动节点」也是写操作。

**Java 线程与操作系统线程**：Java 线程在传统实现中是一对一映射到内核线程（`Thread.start` 最终调用 `pthread_create`），调度由操作系统负责，所以 Java 的线程优先级只是建议、`Thread.yield` 只是提示。进程是资源分配单位（地址空间、文件描述符），线程是调度单位，共享进程资源。通信方式：进程间用管道、消息队列、共享内存、信号、socket；线程间用共享内存加同步（synchronized、Lock、volatile、CAS）、wait/notify、BlockingQueue。

**虚拟线程**：JDK 21 正式引入的虚拟线程由 JVM 调度，多个虚拟线程复用到少量载体线程（ForkJoinPool），阻塞时自动让出载体线程，适合 IO 密集、数量巨大的任务；它不减少 CPU 计算时间，也不适合长时间持有 synchronized 阻塞或做 CPU 密集计算。它降低的是「线程栈内存」与「上下文切换」的成本，但没有消除阻塞本身，底层 IO 仍要走操作系统的多路复用。实习中是否用过要如实回答，没用过就说清楚它的适用边界与和平台线程的区别。
