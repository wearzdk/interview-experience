### 《面试题目》

1. 举一个你修过的印象最深的 bug，讲讲过程和思路。
2. 无人机值守项目里的 AI 模型是你自己搭的吗？怎么选的 SCRFD500M，对比依据是什么？
3. 识别耗时多久？这是实验室项目还是实际落地的？
4. SQLite 是选型选出来的还是顺手用的？轻量化体现在哪？数据量多大？存的是什么？
5. 双 Agent 工作流从 0 到 1 怎么搭起来的？
6. 写测试用例的标准是什么？
7. 这套流程对效率提升大概多少？你在里面具体做了哪些工作？
8. 为什么要分两个 Agent？遇到过什么困难？
9. 既然能拆两个，为什么不继续拆成三个四个？易用性、泛用性这些为什么不也交给 Agent？
10. 单元测试更偏向发现新 bug 还是回归测试？

### 《参考解析》

**「印象最深的 bug」要选有排查层次的**，讲法按「现象 → 复现 → 缩小范围 → 定位根因 → 修复 → 防复发」：好例子是并发下的偶发崩溃（用日志与 core dump 定位到无锁队列的 ABA）、或只在客户现场出现的时序问题（用示波器 / 抓包定位）。避免选「拼写错误」这类无过程的 bug。

**模型选型要给出可比较的维度**：SCRFD 系列是轻量人脸检测（不同宽度与深度对应 500M / 2.5G / 10G 等 FLOPs 档位），选择依据应是「目标场景的人脸尺寸分布 + 端侧算力预算 + 精度要求」三者取交集，并给出对比实验（几个候选在自建验证集上的 mAP / 召回与实测推理耗时）。被追问「对比依据」时，能说出「在什么设备上、什么输入分辨率下、用了多少张验证图」才算数，只说「网上说它效果好」会立刻被识破。

**SQLite 的轻量化体现在**：单文件、无需独立服务进程、零配置、SQL 引擎与库一起编译进程序、事务靠文件锁；适合端侧 / 单机小数据量与强一致的小事务，不适合高并发写。数据量级要能报出来（行数、日增、库文件大小、查询模式），并说明为什么不选 MySQL 或本地文件（需要 SQL 查询与事务、但不想维护服务）。

**「为什么不继续拆成三个四个 Agent」是这套方案最关键的追问**，正确答案是权衡：拆得越多，每个 agent 的上下文越窄、决策越清晰，但每次交接都要付信息损耗（谁负责什么、交接格式、失败回滚），调试与成本也线性增长；划分的依据应该是「职责边界是否稳定、交接的信息能否被明确表达」，而不是「越细越好」。易用性、泛用性这类主观判断更适合留在人这里定规则，交给 agent 反而不可控。

**单元测试偏发现新 bug 还是回归**：两者都有，但工程上主要价值在回归——固定住已有行为，让重构与新增不破坏旧逻辑；能发现新 bug 的是「用例设计阶段」（边界、异常、并发），不是跑单测本身。这个区分答清楚，说明你真的写过单测而不是背概念。
