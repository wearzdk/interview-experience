### 《面试题目》

1. 实习经历深挖：这个点具体是怎么做的、为什么这么做？（追问约 10 分钟）
2. 手撕：无重复字符的最长子串，输出具体子串和长度，考虑空字符串，ACM 模式。
3. 场景题：从零设计一个登录页面，说说你的设计思路。
4. Kafka lag 积压怎么办？

### 《参考解析》

**实习被揪着一个点追问**：面试官通常不是要你重复结论，而是在验证「这是你做的还是你背的」。有效应对是把「决策链」讲出来：当时的约束是什么（时间、人力、存量系统）、有哪几个备选方案、为什么选这个、代价是什么、上线后指标怎么变、如果重来会改哪里。如果确实不清楚某个细节，直接说「这块是同事负责，我只知道接口约定」，比现编安全——编出来的细节经不起第二层追问。

**无重复字符的最长子串**：滑动窗口。右指针右移扩大窗口，用哈希表记录字符最近出现的位置；遇到重复字符时，左指针跳到「该字符上次出现位置 + 1」（注意左指针不能回退，取 `max(left, last[pos] + 1)`）；每步更新最大长度并记录起点，最后截取子串。时间复杂度 O(n)，空间 O(字符集大小)。ACM 模式要自己读输入（可能带引号或空格）、自己输出结果，注意空串返回空串与长度 0、全相同字符、含空格与符号的情况。要能说出为什么用「上次位置 + 1」而不是「左指针 + 1」——后者会漏掉更短的重复。

**设计一个登录页面**：面试官说考察设计思路，那就按层次讲。前端：手机号/邮箱 + 密码或验证码两种方式，输入校验（格式、长度）、防重复提交、密码可见切换、记住登录、第三方登录入口、错误提示不泄露「账号是否存在」；安全：HTTPS、密码加盐哈希存储（bcrypt/argon2）、验证码与频控（同一 IP/账号的尝试次数）、风控（异地登录、设备指纹）、CSRF 防护、登录态用 HttpOnly Cookie 或短期 access token + 长期 refresh token。后端：账号体系（手机号/邮箱/第三方 openid 绑定）、登录接口（校验 → 生成 token → 写 session/Redis）、失败计数与锁定、审计日志。可用性：限流、降级（验证码服务挂了的兜底）、多活。如果要展开，可以讲「登录态怎么续期」「多端登录与互踢」「注销与改密后使旧 token 失效」——这些是面试官容易继续追问的点。

**Kafka lag 积压**：先判断原因：消费者处理慢（下游依赖慢、单条处理重、GC/线程阻塞）、消费者数量不足或分区数不够（消费者数不能超过分区数）、突发流量、消费者频繁 rebalance、消息体过大。应急手段：扩容消费者（增加实例，但要先加分区）、提高单次拉取批量与并行度、把重逻辑异步化或降级、临时跳过非关键消息（需业务确认）、增加分区数（注意 key 的顺序性会被破坏）。根治：优化消费逻辑（批量写库、减少 RPC）、按 key 拆分热点、给下游加缓存与限流、监控 lag 与消费耗时并告警。还要能说清楚「lag 是消息数还是时间」「怎么用 `kafka-consumer-groups.sh` 看每个分区的 lag」。

**这场面试的教训**：手撕题临时换题、要求输出子串、ACM 模式，说明现在大厂更看重「能不能在真实环境里写对」而不是背模板；场景题不要急着写代码，先问清约束（用户量、是否需要第三方登录、是否有风控要求），再分层给方案。帖主「跟她胡扯了 10 分钟」的经历提示：被追问时如果抓不住意图，可以主动确认「您是想了解方案选型，还是具体实现细节」，把对话拉回可回答的范围。
