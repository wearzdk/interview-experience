### 《参考解析》

**GMP 与 channel**：G 是 goroutine，M 是操作系统线程，P 是处理器上下文，持有本地运行队列。M 必须绑定 P 才能执行 G，P 的数量由 `GOMAXPROCS` 决定；本地队列空了会从全局队列或其他 P 偷取（work stealing），G 阻塞在系统调用时 M 与 P 解绑，P 交给其他 M。`range` 遍历 channel 在 channel 被关闭且缓冲区数据取完后退出；channel 未关闭且没有数据时会一直阻塞，需要靠 `close`、`return`、`break` 或 `select` 加超时退出。slice 是「指向底层数组的指针 + len + cap」的结构体，append 超过 cap 会扩容并复制，多个 slice 共享底层数组时修改会互相影响。

**B+ 树与 B 树的差别**：B 树的非叶子节点也存数据，B+ 树只有叶子节点存数据或指向数据的指针，非叶子节点只存键，因此同样页大小下扇出更大、树高更低；B+ 树的叶子节点用链表相连，范围查询和排序只需遍历叶子，B 树需要中序遍历。InnoDB 的聚簇索引叶子存整行，二级索引叶子存主键，回表再查。

**慢查询排查**：先开慢查询日志确认是哪条 SQL、执行频率与耗时；用 `EXPLAIN` 看访问类型、命中索引、扫描行数、是否 filesort 或临时表；再看索引设计是否匹配查询条件与排序，必要时建联合索引或覆盖索引；数据量过大考虑分页优化、归档或分表；也可能是锁等待、网络或返回数据量过大。优化后用同样的数据与并发复测。

**索引失效的常见场景**：对索引列做函数或表达式运算、隐式类型转换（字符串列传数字）、联合索引不满足最左前缀、`like '%x'` 前导模糊、`or` 连接的条件有一侧无索引、`!=`/`not in` 导致优化器放弃索引、`is null` 与数据分布、以及优化器估算回表成本过高主动选择全表。`like 'x%'` 是前缀匹配可以用索引，`like '%x%'` 和 `like '%x'` 用不上。

**隔离级别**：读未提交会有脏读；读已提交解决脏读，但会有不可重复读；可重复读解决不可重复读，InnoDB 默认级别，通过 MVCC 快照读加间隙锁在很大程度上避免幻读；串行化全部加锁，并发最低。回答时区分「标准定义」与「InnoDB 的实现」：RR 下快照读看到的是事务开始时的视图，当前读会加 next-key lock。

**Redis 与缓存三问题**：数据结构有 string、hash、list、set、zset，以及 bitmap、HyperLogLog、geo、stream。缓存穿透是查不存在的数据，方案是参数校验、空值缓存、布隆过滤器；缓存击穿是热点 key 过期瞬间大量请求回源，方案是互斥锁重建、逻辑过期、热点永不过期；缓存雪崩是大量 key 同时过期或 Redis 故障，方案是过期时间加随机、集群与降级、限流。分布式锁用 `SET key value NX PX ttl` 加锁，value 用唯一标识，释放时用 Lua 比对后删除；业务执行超过 TTL 需要看门狗续期，Redisson 已封装。单机 Redis 的主从切换可能丢锁，强一致场景要用 fencing token 或接受额外成本。

**RAG 解决的是知识时效、私有数据与幻觉**：把文档切块、向量化、存入向量库，查询时检索相关片段拼进上下文，让模型基于证据回答。效果取决于切分、embedding、召回、rerank 与提示，工程上要建评测集衡量召回率与答案正确率，并做引用与拒答。

**多层记忆的存储与长期记忆判定**：短期记忆存当前对话窗口，中期存滚动摘要，长期存事实、偏好与结论，通常放向量库或结构化表，附带时间、来源、置信度。写长期记忆不能把所有对话都存进去，判据可以是：用户明确要求记住、信息在多次对话中重复出现、对未来任务有持续影响（偏好、身份、长期目标）、以及模型抽取后的重要性评分超过阈值；写入前做去重与冲突检测，旧事实标记失效而不是直接删除，并设置过期与用户可删除的入口。

**LangGraph 的原理**：把 Agent 或工作流建模成状态图，节点是函数或模型调用，边定义流转，支持条件边、循环、并行与中断；核心是一个可持久化的状态对象，每个节点读取并返回状态更新，checkpointer 保存每一步以便恢复与人工介入。项目里通常用它做多步 RAG、工具编排或带人工审核的流程，比一次性提示更容易观测和回放。

**了解 AI 新知识的渠道**：官方文档与发布说明、论文与开源仓库、X 与 Hacker News、国内社区与公众号、以及自己动手跑一遍。回答时给一个具体例子，比如最近读的某个模型或框架的文档、复现过的一个 demo，比列渠道名单可信。
