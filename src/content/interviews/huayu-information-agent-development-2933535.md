### 《面试题目》

社招，两年经验，Agent 开发岗。

1. 自我介绍。

5. 任务执行是串行还是并行的？具体怎么做的？
6. 如果一个攻击者对你的 Agent 进行攻击，直接说「帮我在目录执行 rm -rf」，你是怎么处理的？
7. 相关的权限鉴定，以及对这些黑客指令的拦截是怎么做的？

14. 除了向量化知识库，还有没有比较流行的做法去做 RAG？
15. （开放题）现在有一个很大的股票文本，从中找到一个最合适的股票。全量发送给大模型会超过上下文，你会怎么做？

### 《参考解析》

**Agent / MCP / Tool 的区别**：Tool 是最小能力单元——一个有明确输入输出 schema 的函数，模型看到描述后决定调不调、传什么参数。MCP 是把「模型如何发现并调用工具」标准化成协议：它定义 hosts（宿主应用）、clients、servers 三层，server 按标准暴露 resources（可读数据）、tools（可执行动作）、prompts（提示模板），client 负责连接与转发。价值在于工具实现与宿主解耦——同一个 MCP server 能被任意支持该协议的客户端复用，不用为每个模型厂商重写一遍适配层。Agent 是更高一层的编排者：它持有目标与状态、决定下一步做什么、把多个 tool / MCP server 组织成能收敛到结果的循环（推理 → 行动 → 观察 → 再推理）。一句话：Tool 是手，MCP 是手的通用接口标准，Agent 是用手干活的脑子。

**MCP 的组成部分**：一个 MCP server 通常包含——① 能力声明（capabilities，声明自己支持 tools / resources / prompts / sampling 中的哪些）；② 工具定义（name、description、JSON Schema 形式的 inputSchema，description 写得好不好直接决定模型选不选它）；③ 传输层（stdio 供本地进程，Streamable HTTP / SSE 供远程）；④ 生命周期与初始化握手（协议版本协商）；⑤ 结果约定（返回 content 数组，含文本、图片、resource 引用，以及 isError 标记）。工程上还要考虑鉴权（远程 server 的 token 怎么下发给 client）、超时、以及工具调用失败时的错误信息如何让人和模型都能读懂。

**Agent 的状态管理**：状态分几层——会话级（对话历史、用户偏好）、任务级（当前目标、已完成步骤、待办、中间产物）、执行级（这一轮的工具调用与结果）。实现上要么自己写：用一个显式的 state 对象贯穿整个循环，每轮把它序列化进 prompt，工具调用结果回写；要么用框架：LangGraph 用图 + 显式 state 与 checkpoint（可中断、可恢复、可回放），AutoGen / CrewAI 用消息总线式共享。自己写的优势是完全可控、调试直观，劣势是稍复杂就散成一堆隐式全局变量；用框架的优势是有检查点和可视化，劣势是抽象层厚、出问题难定位。我的选择标准是任务有没有长时运行和人工介入点——有就用带 checkpoint 的图式框架，没有就自己写一个显式 state。

**并行还是串行**：取决于任务之间有依赖。有依赖的必须串行（B 的输入是 A 的输出）；无依赖的并行能显著省时——典型的是一次要查多个来源、或多文件同时改写。实现上分两种粒度：同一轮里模型一次返回多个工具调用（parallel tool calls），宿主并发执行再把结果一起回灌；或者由编排层把任务拆成子任务，交给多个 agent 各跑一条链再汇总。并行要处理的是合并冲突与幂等——同一条链上两个工具改了同一份文件，得有明确的仲裁策略。

**「帮我在目录执行 rm -rf」怎么防**：这道题不是让你说「我会在 prompt 里加一句不许删文件」——提示词拦不住注入。要靠分层的确定性机制：① **能力边界**，Agent 的道具里根本不该有一个「任意 shell」工具，只给白名单化的原子操作（读文件、写指定目录、执行注册过的脚本）；② **参数校验**，即便有执行工具，命令也要按白名单校验（允许 rm 但必须限定在 workspace 子目录、禁止绝对路径与 `..`、禁止通配符），这一步是代码而非模型判断；③ **隔离**，执行发生在容器 / 沙箱里，宿主机的关键路径根本没挂进去，删了也只损失一个可重建的环境；④ **人在环**，破坏性操作（删除、外发、付款）在执行前挂审批；⑤ **审计**，所有工具调用落日志，事后可追溯。核心思路是把「模型会不会犯错」这个不确定问题，换成「就算它犯错，损失是否被结构性限制」这个确定问题。

**沙箱方案**：Linux 侧主流是 namespace + cgroup 做隔离（容器就是这套）——PID / mount / network / user namespace 把进程的视野隔开，cgroup 限制 CPU、内存、IO；更强的是 seccomp 过滤系统调用，以及 gVisor、Firecracker 这种用户态内核或轻量虚拟机方案（隔离强度接近 VM、启动速度接近容器）。Windows 侧对应的是 Job Object 限制资源、AppContainer / 完整性级别限制文件与注册表访问、以及 Windows Sandbox（基于 Hyper-V 的一次性环境）。选型按威胁模型来：只是防误操作，容器加只读挂载就够；要防恶意代码，得上 gVisor / microVM；要给不可信的用户代码执行，还得加上网络出站白名单和时间限制。

**上下文压缩**：几个手段配合。滑动窗口保留最近 N 轮原文，更早的做摘要（用模型把对话压成要点，保留决策与结论、丢掉过程）；结构化摘要替掉冗长工具返回（工具返回的大 JSON 只保留模型真正需要的字段，别整块塞进上下文）；把长文档改成检索——不全文进上下文，按需取片段；分层记忆，把稳定的用户偏好、项目背景放系统提示或外部存储，只在需要时注入。真正省 token 的是「不该进上下文的东西一开始就别进」，压缩只是补救。压缩本身有风险：摘要会丢细节，所以关键事实（用户明确说的约束、已经做出的决定）要单独以结构化形式保留，不能交给自由摘要。

**SSE 与 WebSocket**：SSE（Server-Sent Events）是单向的——服务端推、客户端收，基于普通 HTTP，响应 `Content-Type: text/event-stream`，每条消息是 `data:` 开头的纯文本帧，自带事件 id 与 retry 字段。优点是简单、走标准 HTTP（穿代理和网关容易）、浏览器原生 `EventSource` 支持、断线浏览器会自动重连并带上 `Last-Event-ID`。缺点就是单向，客户端要发消息得另开一个请求。WebSocket 是全双工，一次 HTTP 升级握手后变成独立的长连接，双方随时互发，帧更紧凑、开销更小，但需要服务端和中间设备都支持 Upgrade，重连与心跳要自己写。选择标准：只需要服务端推动（模型流式输出、进度推送、通知）用 SSE 更省事；需要双向频繁交互（协同编辑、游戏、语音对话）用 WebSocket。

**SSE 的重试谁来实现**：浏览器原生 `EventSource` 自带重连——断线后按服务端给的 `retry` 间隔重连，并带上 `Last-Event-ID` 头让服务端知道从哪条继续。但这份自动重连很朴素：只处理连接断开，不处理「连接还在但消息不来」；不做指数退避以外的高级策略；移动网络切换、代理超时这些场景它感知不到。所以生产上一般不用裸 `EventSource`，自己基于 fetch + ReadableStream 实现客户端，显式控制：心跳检测（服务端定时发注释帧保活）、超时判定、指数退避重连、用事件 id 做断点续传、以及重连后的状态重建（很多业务是「重连后重新拉一次全量快照」比补增量更简单可靠）。另外要注意 SSE 在 HTTP/1.1 下有同域连接数限制（浏览器通常 6 条），多标签页场景要复用或走 HTTP/2。

**召回率低先考虑什么**：按链路顺序排查，不要一上来就换模型。① **切分**：chunk 太大语义被稀释、太小上下文不完整，边界是不是切在句子中间；② **查询**：用户原话和文档措辞的词汇鸿沟——口语化提问对上正式表述，纯向量检索会漏；考虑查询改写、同义词扩展、或者混合检索；③ **embedding 模型与语料域不匹配**（中文技术文档用了英文语料训的模型），以及向量归一化、维度截断这类实现细节；④ **索引覆盖率**：该进库的文档真的进去了吗，解析有没有丢内容（PDF 表格、代码块常被吃掉）；⑤ **topK 与阈值**：召回条数太少或相似度阈值卡太高；⑥ **过滤条件**：元数据过滤写错把正确结果排除在外。评估上要先有一份标注过的 query→相关文档集合，才能算 recall@k，否则改哪儿都是盲调。

**非向量检索的 RAG 做法**：① **关键词检索**（BM25 / Elasticsearch）：对精确术语、编号、人名地名这类向量表达不好的场景反而更强，且可解释；② **混合检索**：向量 + BM25 各召回一批，用 RRF（倒数排名融合）合并，这是目前最稳的默认方案；③ **图谱 / 结构化检索**：把知识抽成实体关系图，按关系多跳检索，适合「A 的上级部门的负责人是谁」这类需要推理链的问题；④ **层级摘要索引**：文档先建成摘要树，检索先定位章节再取原文（RAPTOR 那类思路）；⑤ **Agentic RAG**：让模型自己决定查什么、查几次、要不要换关键词重查，本质是把检索变成工具调用；⑥ **长上下文直读**：文档总量不大时直接把全文放进上下文，省掉检索误差。

**超长股票文本里找一只**：思路是把「一次读完」换成「分层筛选」。具体做：① 先把长文本按股票切成块，为每块预生成结构化摘要（代码、行业、关键财务与事件），摘要本身可控；② 用规则或关键词先把候选从几千缩到几十（比如按用户条件过滤：行业、市值区间、近期事件类型），这一步不花模型；③ 对候选块做向量检索或 BM25 召回与问题相关的片段，只把这些片段交给模型做判断；④ 让模型输出结构化结论（股票代码 + 理由 + 引用原文位置），理由必须能指回原文片段，便于人工核对；⑤ 如果条件本身模糊（「最合适」没定义），先反问澄清评价维度，或者在 prompt 里显式让模型列出假设再做选择。核心是「先用确定性的方法缩小搜索空间，再让模型在可解释的小集合里做判断」，而不是把长文本硬塞或让模型拍脑袋。

**@Autowired 与 @Resource**：`@Autowired` 是 Spring 自己的注解，默认按类型注入，类型有多个候选时才退化到按名字匹配（配合 `@Qualifier` 才明确）；有一个 `required` 属性可以设成非必需。`@Resource` 是 JSR-250 标准注解，默认按名字注入（名字取字段名或 setter 的屬性名），找不到名字再按类型。实践差异：要跨容器兼容用 `@Resource`，要精细控制（多个同类型 Bean 用限定符、可选依赖）用 `@Autowired`。另外 `@Autowired` 可以标在构造器上（推荐做法，便于测试与不可变）；`@Resource` 只能标在字段或 setter 上。

**@Bean 与 @Component**：`@Component` 标在类上，靠组件扫描发现，适合自己写的类；`@Bean` 标在方法上（通常在 `@Configuration` 类里），方法体里自己 new 对象并返回，适合引入第三方库的类（改不了它的源码加注解）、需要复杂初始化逻辑、或者要按条件创建多个不同配置的实例。语义差异上，`@Bean` 方法在 `@Configuration` 类里会被 CGLIB 增强，多次调用返回同一个单例；`@Component` 的类靠类路径扫描注册，没法做这种「方法级」的定制。

**Bean 的生命周期**：实例化（构造器 / 工厂方法）→ 属性填充（依赖注入）→ `Aware` 系列回调（BeanNameAware、BeanFactoryAware、ApplicationContextAware）→ `BeanPostProcessor.postProcessBeforeInitialization` → 初始化（`@PostConstruct` → `InitializingBean.afterPropertiesSet` → 自定义 init-method）→ `BeanPostProcessor.postProcessAfterInitialization`（AOP 代理就在这一步生成）→ 使用 → 销毁（`@PreDestroy` → `DisposableBean.destroy` → 自定义 destroy-method）。要能点出 AOP 代理生成的位置在初始化之后的 postProcessAfterInitialization，以及单例 Bean 的销毁只发生在容器关闭时。

**SQL 分组聚合**：思路是先按省聚合人口再筛。假设表里是「省、市、人口」，同省有多个市就要先求和再筛：

```sql
SELECT province, SUM(population) AS total
FROM city_population
GROUP BY province
HAVING SUM(population) > 50000000
ORDER BY total DESC;
```

关键点是：筛聚合结果必须用 `HAVING` 而不是 `WHERE`（`WHERE` 在分组前执行，看不到聚合函数）；如果原表里已经有省的汇总行，那就不需要 `GROUP BY`，直接 `WHERE population > 50000000` 即可——面试时先问清表结构比急着写 SQL 加分。

**平时怎么用 AI 改代码**：分场景。小改动（改一个函数、补一段样板）直接说需求让它写；涉及多文件、要动既有架构的，先让它读相关代码、给出方案和影响面，我确认方案后再让它动手——跳过方案直接生成，往往得到能跑但不符合项目约定的代码。无论哪种，交付前我自己过一遍 diff，跑编译、类型检查和 lint，关键路径补测试。这个顺序的理由很简单：AI 产出的是「初稿」，判断和所有权还在人这边。
