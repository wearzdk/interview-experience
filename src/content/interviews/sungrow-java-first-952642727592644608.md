### 《参考解析》

**MyBatis 两级缓存**：一级缓存默认开启，作用域是 `SqlSession`，同一个会话内相同的查询在缓存未失效时直接取本地结果；执行更新或提交、回滚事务会清空相关缓存，不同 `SqlSession` 之间不共享。二级缓存作用在 Mapper 命名空间上，可以跨会话共享，但需要显式配置，且要求实体可序列化，跨服务改数据时很难保证及时失效。实际业务里通常不依赖二级缓存，热点数据交给 Redis，用过期时间和更新策略管理，避免两套缓存叠加后不一致的排查成本。

**缓存与数据库不一致**：常用 Cache Aside——读时先查缓存，未命中再查库回填；写时先更新数据库，成功后再删除缓存，而不是同时更新两份。仍有并发窗口：线程 A 删缓存后，线程 B 读到旧值并回填。一致性要求高的场景要加并发控制、版本号或基于消息队列的补偿，缓存再设合理 TTL 作为兜底。方案取决于业务能容忍多长的延迟。

**提交页面卡顿的排查**：先分层定位，不要直接认定数据库慢。浏览器开发者工具看 Network：请求有没有发出、卡在建连、等待响应还是下载；接口耗时确实长，再看服务端日志与链路追踪。典型原因是接口里同步调用了外部通知服务且没有超时。把非核心逻辑异步化、补超时与重试后响应就稳定了，但异步化要同时处理消息丢失与重复消费。

**Explain 的 type**：反映访问数据的方式，常见取值从好到差大致是 `system`、`const`、`eq_ref`、`ref`、`range`、`index`、`ALL`。主键或唯一索引等值查询可能是 `const`；关联查询中被驱动表按唯一索引匹配单行是 `eq_ref`；普通索引等值查询是 `ref`；索引范围扫描是 `range`；`index` 是全索引扫描，`ALL` 是全表扫描。不能只看 type 排序，还要结合 `rows`、`filtered`、`Extra` 与实际耗时，优化器的选择受数据分布和统计信息影响。

**接口幂等**：前端置灰解决不了网络重试和多客户端同时提交。后端让客户端携带唯一请求编号，用数据库唯一约束或 Redis 原子操作识别重复；订单这类关键业务更倾向数据库唯一约束作为最终保护。还要定义失败后如何重试、重复请求返回什么——通常保存请求与业务状态的对应关系，重试时返回首次的处理结果。
