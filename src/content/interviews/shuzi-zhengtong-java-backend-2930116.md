### 《参考解析》

**滑动窗口保“最近”，摘要保“久远”，两者要叠加结构化状态而不是二选一。** 滑动窗口是只保留最近 N 轮对话或最近若干 token，优点是实现简单、近期指代和细节完整，缺点是一旦超出窗口，早期约定就丢了；摘要则把更早的对话压缩成一段自然语言，能覆盖长历史，但会丢细节、可能被模型改写，而且摘要有“滚雪球”误差。工程上常用组合：系统约束常驻，最近几轮保留原文，更早的对话做滚动摘要，另外单独维护实体表/槽位（用户、订单、金额、时间、已确认参数）和未完成事项，摘要只作补充。压缩后要验证关键信息没丢，可以设计探针问题：关键实体还在不在、用户否定过的方案会不会被重新推荐、约束条件是否仍遵守、指代能否正确消解；离线用固定对话集对比压缩前后的任务成功率和实体召回，线上看追问率、纠错率和人工兜底率。重要会话保留原始记录，摘要出问题时能回到原文重压，而不是在错误摘要上继续滚。

**MCP 返回过大，正确的方向是“让工具少返回”，而不是“让模型硬吃”。** 首先在协议层做分页、过滤、字段裁剪和排序，只取当前任务需要的字段；工具描述里写清默认 limit 和最大 limit，返回结构带 `has_more`、`next_cursor`、总量估算。其次在编排层做预算：给每次工具结果设 token 上限，超限就截断并保留 schema、统计摘要和少量样本，同时把完整结果落到对象存储/工作区，返回一个可回查的句柄，让模型按需二次取。第三，对结构化数据先做本地聚合（计数、分组、Top-K），再把聚合结果给模型；对日志先按错误码/请求 ID 过滤，不要整包塞。还要有降级：工具超时或返回异常时，明确告诉模型“数据不完整”，让它追问或缩小范围，而不是编造。关键指标是工具结果的 token 分布、截断率、二次取数率，以及因为上下文不足导致的失败率；把这几项接进 trace，才能判断是工具设计问题还是模型不会用。

**单表上亿，先看访问模式，再决定索引、分区、分库分表还是归档。** 如果查询都能命中索引且是点查/小范围，优先做覆盖索引、联合索引、避免回表和深分页；如果是时间范围查询，按时间分区，冷数据归档或放到对象存储/OLAP；如果写入量和并发都很高，考虑分库分表，选好分片键避免跨分片查询和热点；读多写少可以加缓存或读写分离。加索引的代价是写放大（每次 insert/update 都要维护索引）、占空间、拖慢优化器、增加锁的范围，所以不是越多越好，通常按高频查询建联合索引，定期清理无用索引。InnoDB 的行锁是加在索引项上的：命中唯一索引等值查询锁一行，范围查询在 RR 下可能加 next-key lock（记录锁 + 间隙锁），如果 where 条件没有走索引，就会扫描大量行甚至退化成锁很多记录；DDL 还会拿 metadata lock。锁竞争常见于热点行更新（库存、计数器）、同一区间的间隙锁、长事务持有锁、以及二级索引过多导致的加锁路径变长。解决思路是缩短事务、把热点更新串行化或拆成多行（分段计数）、用乐观锁/版本号、减少不必要的索引、把非核心更新异步化。

**Docker 镜像分层是“每条构建指令一层、只读层共享、容器层可写”。** 镜像由一系列只读层叠加而成，底层是基础 OS，中间是 JRE、依赖、应用文件，最上面是容器启动时的可写层；overlay2 这类存储驱动把多层合并成一个文件系统视图，相同层可以在多个镜像/容器间复用。Dockerfile 里 `RUN`、`COPY`、`ADD` 都会产生新层，所以把变化少的指令放前面、把 `COPY` 依赖文件和 `COPY` 源码分开，能最大化缓存命中；多阶段构建让编译工具只留在 builder 阶段，最终镜像只拷贝产物；再用 slim/distroless 基础镜像、合并 `RUN`、清理包缓存、`.dockerignore` 排除无用文件，体积就下来了。“减小体积”具体指减少镜像层数和每层内容，尤其别把源码、测试、构建缓存、包管理缓存带进最终镜像。和直接分发 fat JAR 相比：fat JAR 只包含应用和依赖，要求目标机器已有合适 JRE，包小、启动直接，但环境不一致时容易出问题；镜像把 OS、JRE、应用一起打包，部署一致、隔离性好、可回滚，代价是体积大、构建和拉取慢、需要容器运行时。生产上常见做法是“瘦 JAR + 精简基础镜像”，而不是把整个 JDK 和构建工具都塞进去。

**多级缓存是用容量换延迟，用一致性换吞吐，结构通常是本地 + 分布式 + 数据库。** L1 用 Caffeine/Guava 放在应用进程内，纳秒到微秒级，适合极热、变化少的数据；L2 用 Redis 等集中式缓存，毫秒级，容量大、多实例共享；最底下是数据库。读路径先 L1、再 L2、最后回源并回填；写路径常用 cache-aside：先更新数据库，再删除缓存，必要时延迟双删或订阅 binlog 异步失效，L1 通过广播/消息通知各实例失效。为什么需要多级：减少网络往返、扛住热点 key、在 Redis 故障时本地还能兜一段；代价是一致性更难，尤其是本地缓存各实例失效时间不一致。还要处理穿透（空值缓存 + 布隆过滤器）、击穿（互斥重建/逻辑过期）、雪崩（过期时间加随机、熔断降级）。限流则是另一套：令牌桶允许突发、漏桶平滑输出、固定/滑动窗口统计简单但有边界突刺；分布式限流用 Redis + Lua 保证原子性，按用户、IP、接口、租户分维度，本地再加一层令牌桶减少 Redis 压力。限流误差主要来自时钟漂移、网络延迟、Redis 故障降级、窗口边界和突发流量，评估时看实际通过 QPS 与目标值的偏差、误杀率、P99 延迟和拒绝后的重试行为；必要时用并发度自适应或队列背压，而不是只靠一个固定阈值。

**异步任务写多个存储，不一定要“全部成功”，但要定义清楚一致性级别和失败后的状态。** 如果业务要求强一致，就不该用异步多写，应该走单一事务源或分布式事务（2PC/TCC），代价是复杂度和可用性；更多场景是最终一致：本地事务写业务库 + outbox 消息表，后台投递 MQ，各消费者幂等消费，失败重试 + 死信队列 + 人工补偿，定时对账修数据。状态机要明确“待处理、处理中、成功、失败、已补偿”，每一步可重入；下游写入用业务唯一键做幂等，避免重复消息造成脏数据。接口延迟突然暴涨，排查顺序是：先看监控确定是全局还是单接口、单实例，再看 trace 找耗时最长的 span，区分是应用、数据库、缓存、下游还是网络；应用侧看 GC、线程池、连接池、CPU/负载、锁竞争，数据库看慢查询、锁等待、连接数，缓存看命中率和 Redis 延迟，下游看超时和重试风暴。常见原因包括慢 SQL/缺索引、锁等待、GC 停顿、线程池或连接池耗尽、下游超时、序列化大对象、缓存击穿、流量突增和发布变更。定位时用对比法（和昨天/上一个版本比）、分段法（逐层打点）和现场法（thread dump、heap dump、火焰图），先止血再根因。

**AI 编程适合“放大已经会的东西”，不适合替代对核心逻辑的判断。** 日常可以用它生成样板代码、单测、SQL、正则、脚本、重构建议和日志分析，也可以让它先解释一段陌生代码；关键是把它当草稿，所有输出都要过编译、lint、单测和 code review，小步提交，方便回滚。手写和 AI 辅助的边界可以这样分：核心算法、并发、安全、资金相关逻辑自己写并逐行理解；重复性、边界清晰的代码交给 AI 加速；让 AI 先写测试再写实现，或者自己写实现让 AI 找边界。团队协作题则按“目标拆解—责任人—里程碑—风险”回答：把任务拆到可验收的粒度，明确谁负责什么、依赖是什么，设中间检查点和缓冲，遇到阻塞及时升级；带两个人时，自己承担最难的模块，同时留时间做 review 和联调，别把所有事揽在自己身上。转专业这类问题照实说动机和补课路径即可，重点是把“为什么现在能做这个岗位”讲清楚。
