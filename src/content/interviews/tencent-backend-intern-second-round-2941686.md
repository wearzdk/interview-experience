### 《面试题目》

1. 手撕：被三整除求最大和。
2. 手撕：数组中重复的数据。
3. 讲一个实习或自己项目中比较有技术挑战性的完整 case，包含需求背景、技术方案思考、落地效果。
4. 你觉得这个 case 里面，你的技术挑战是什么？

7. 有了解过热点 key 的问题吗？它是一个怎样的现象？

11. 普通热点 key 使用本地缓存、读写分离之后，集群其余节点依旧低负载，存在负载不均衡，有什么解法？

### 《参考解析》

**被三整除求最大和**：常见做法是先把所有数求和，若和能被 3 整除即为答案；否则按模 3 的余数分类——删除一个最小的余 1 数、或删除一个最小的余 2 数；也可以删两个余 2 数（等价于余 1）或两个余 1 数（等价于余 2），取两者中较小的损失。实现时维护每组最小的两个值即可，时间 O(n)。要点是「删一个」与「删两个」两种修正都要考虑，只考虑删一个会漏解。

**数组中重复的数据**：如果值域是 1..n 且只重复一次，经典解法是把值当索引做原地标记（访问到 `nums[i]` 时把 `nums[abs(nums[i])-1]` 取负，第二次访问即为重复），时间 O(n)、空间 O(1)；通用解法是哈希表 O(n) 空间，或排序后相邻比较 O(n log n)。回答时先说清数据约束再选解法，比直接写哈希更容易得分。

**「最有技术挑战性的 Case」怎么讲**：用四段式——背景（业务目标与当时的瓶颈，给出量级）、方案思考（至少两个候选方案与取舍依据，说明为什么放弃另一个）、落地（你具体改了哪些模块，遇到什么坑，怎么验证）、效果（可量化的指标变化）。面试官追问「你的技术挑战是什么」时，答案要落在「决策点」上，例如一致性方案选了最终一致并承担了对账成本，而不是「这个需求很难」。

**Redis 集群架构**：Cluster 模式把 key 空间切成 16384 个槽，每个 master 负责一段槽，slot 由 `CRC16(key) mod 16384` 决定；每个 master 带从节点做副本，节点间用 gossip 协议交换状态，超过半数 master 认为某节点失联才标记为 FAIL 并触发从节点晋升。客户端缓存槽位映射，收到 MOVED 重定向后更新，ASK 用于槽迁移过程中的临时跳转。跨槽的 `mget`、事务、Lua 会失败，需要用 hash tag 把相关 key 固定到同一槽。

**热点 Key 是什么**：某个 key 的访问量在短时间内远超其他 key（明星塌房、爆款商品、秒杀库存），导致该 key 所在的单个节点 CPU、带宽打满，而集群其他节点空闲——分片解决的是「总量」，解决不了「单点集中」。大 Key 是另一回事：value 过大（几 MB 的 hash、几十万元素的 zset），会造成单次操作阻塞、网络拥塞、删除时卡顿。

**大 Key 拆子 Key**：按业务维度分片成 `key:0..N`，用 `hash(userId) % N` 路由，读时只读一个子 key，聚合场景才读全部；或者按时间分桶（`key:20261117`）避免单 key 无限增长；列表类拆成固定长度的分页块（`list:part:0`、`part:1`），用计数维护长度。要点是拆完之后要能回答「怎么取全量」和「怎么保证原子性」这两个追问。

**普通热点 Key 的解法**：本地缓存（Caffeine / Guava，带短过期与容量上限，多实例各存一份，容忍短暂不一致）；读多写少且可接受旧值时把热点数据推送到客户端或 CDN；对同一 key 的并发回源做合并（singleflight）与互斥重建；把 value 拆成多份打散到不同节点再在应用层聚合（热点 key 打散）；写热点则可以合并写、异步落库、按库存分桶预扣。

**把读打到从节点**：Redis 侧用 `READONLY` 让客户端在从节点上执行读命令，客户端 SDK 支持读写分离配置；MySQL 侧则是主从复制 + 读写分离中间件或在应用内按注解路由到从库。要说明代价：从节点有复制延迟，刚写完立刻读可能读到旧值（写后读一致性要回主库，或用会话粘滞）。

**读写分离后仍不均衡的解法**：这正是热点 key 的本质——数据只在某一个分片上。做法是「把一份数据变成多份」：热点 key 加随机后缀复制 N 份（`key:0..N` 内容相同），读时随机选一份，写时更新所有副本或用版本号；多级缓存把请求挡在应用侧（本地缓存 + 集中缓存 + 限流）；对同一热点 key 的请求做请求合并与队列化，只放少量请求到底层；实在不行把该 key 的逻辑拆开（比如秒杀库存分桶，每桶独立扣减）。

**Kafka 高吞吐的原因**：顺序写盘 + 页缓存（写入进 OS page cache，靠内核刷盘）；零拷贝（`sendfile` 把页缓存直接送到网卡，省掉用户态拷贝）；批量与压缩（producer 端 batch + snappy/lz4/zstd）；分区并行；稀疏索引（`.index` 只存相对偏移，按偏移二分定位）；日志分段 + 顺序追加、消费端按 offset 顺序读，几乎不随机 IO。

**Consumer Group 与消费关系**：Consumer Group 是消费的逻辑单元，组内消费者共同分摊订阅 Topic 的分区，每条消息在**一个组内**只被消费一次，不同组之间互不影响（各自维护 offset），这就是「广播 vs 集群消费」的区别。一个 Consumer Group 可以订阅多个 Topic（Kafka 允许，但通常一个组订一个主题族更好管理）。**一个分区在同一时刻只能被组内一个消费者消费**，所以组内消费者数超过分区数时多出来的消费者空闲；一个消费者可以消费多个分区。这也是为什么分区数是消费并行度的上限。
