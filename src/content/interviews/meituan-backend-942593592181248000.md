### 《参考解析》

**1. Copy-On-Write 与缓存设计。** COW 的核心是「读共享、写复制」：多个读者共享同一份数据，写者先复制一份再改，改完原子替换指针，读者要么看到旧版本要么看到新版本，不会读到半成品。Java 的 `CopyOnWriteArrayList` 就是每次写都复制整个数组，适合读多写少、数据量小的场景（比如监听器列表），写多时会频繁复制、内存抖动。Redis 的 `BGSAVE` 也是 COW：fork 出子进程共享页表，父进程写时复制页面。浏览器里的「CSS 匹配缓存」是另一个层面的缓存——把选择器匹配结果按元素/规则缓存，DOM 变化时按失效范围清理，设计要点是缓存的 key（元素 + 规则集 + 状态伪类）、失效粒度（避免一个 class 变化就全量失效）、以及内存上限。

**2. 线程池、锁与原子变量。** 线程池设计关注：核心/最大线程数、有界队列、拒绝策略、线程命名（便于排查）、异常处理、以及池的隔离（不同业务不共用）。用锁的判断是「有没有共享可变状态、临界区是否真的需要互斥」：无状态服务、局部变量、不可变对象都不需要锁；能用原子变量/CAS 解决的单变量计数不要用锁；读多写少可以用读写锁或 COW；跨进程才考虑分布式锁。原子变量（`AtomicInteger`、`LongAdder`）靠 CPU 的 CAS 指令保证单变量原子性，`LongAdder` 在高并发下用分段累加降低竞争，最后求和。

**3. 消息顺序、可靠性与表设计。** 保证顺序的三要素：同一业务键路由到同一分区/队列（Kafka 用 key 做 partition，RocketMQ 用顺序队列）、单分区内单消费者串行消费、消费失败不要跳过（否则顺序断裂）。不丢消息要三段都做：生产端确认（acks=all + 重试）、Broker 持久化与副本（`min.insync.replicas`）、消费端手动提交 offset（处理成功再提交）。表设计先定访问模式：主键选择、避免大宽表、冷热字段分离、必要的冗余（减少 join）、以及分库分表的 shard key；数据量大时先看能不能归档/分区，再考虑分片。索引失效的典型场景：对列做函数/运算、隐式类型转换、`like '%x'` 前导通配、联合索引不满足最左前缀、`or` 两边有一边没索引、以及优化器判断全表扫更便宜。

**4. MVCC。** InnoDB 给每行加隐藏的 `DB_TRX_ID`（最后修改的事务 id）和 `DB_ROLL_PTR`（指向 undo log 的版本链）。快照读时，事务拿着自己的 read view（活跃事务 id 列表、最小/最大事务 id），沿版本链找「对当前事务可见」的版本：已提交且早于快照的可见，未提交或晚于快照的不可见，继续沿 undo 找。RC 每次查询生成新 read view，RR 在第一次查询时生成并复用，所以 RR 能避免不可重复读；幻读靠间隙锁（当前读）或快照读的版本可见性来规避。MVCC 只作用于快照读，`select ... for update`、`update`、`delete` 走当前读并加锁。

**5. synchronized、动态绑定与 volatile。** `synchronized` 修饰实例方法锁的是 `this` 对象，修饰静态方法锁的是 `Class` 对象（类只有一个，所以是全局锁），修饰代码块锁的是括号里的对象。锁信息存在对象头的 Mark Word 里：偏向锁记录线程 id，轻量级锁记录指向栈上 Lock Record 的指针，重量级锁指向 monitor；JVM 通过 CAS 修改 Mark Word 来抢锁，失败则膨胀升级。多态的动态绑定靠虚方法表（vtable）：每个类有一张方法表，对象头里的类型指针指向类元数据，调用虚方法时按运行时类型查表，找到子类重写后的入口。`volatile` 保证可见性和有序性：JVM 层插入内存屏障，硬件层靠缓存一致性协议（MESI）让其他核的缓存行失效，写操作直接写回主存。`execute` 提交 `Runnable` 且不返回结果、异常会直接抛给线程池的未捕获异常处理器；`submit` 提交 `Callable` 返回 `Future`，异常被封装在 Future 里，不 `get` 就看不到。

**6. 内存、系统调用与 TCP。** 进程申请的内存超过物理内存时，操作系统用虚拟内存 + 按需分页：先只分配虚拟地址空间，访问时缺页中断再加载；物理内存不够就把不活跃页换出到 swap（或直接 OOM kill）。系统调用流程：用户态把系统调用号放进寄存器、执行 `syscall` 指令陷入内核 → 内核保存用户态上下文（寄存器、栈指针、返回地址）到内核栈 → 按调用号查系统调用表执行 → 参数通过寄存器/用户态指针传入，内核用 `copy_from_user` 校验并拷贝（`read` 的 fd 用来查进程的文件描述符表）→ 返回时恢复上下文、把返回值放回寄存器、切回用户态继续执行下一条指令。上下文保存在内核栈和 `task_struct` 的 `thread_struct` 里（x86 保存 rsp/rip/rflags 等）。TCP 第四次挥手（客户端最后的 ACK）丢失时，服务端停在 `LAST_ACK` 并超时重传第三次挥手（FIN+ACK）；客户端已经进入 `TIME_WAIT`，收到重传的 FIN 会再回一个 ACK，所以不会卡死，只是服务端晚一点关闭。

**7. InnoDB 日志与落盘顺序。** redo log 是物理逻辑日志，记录页的修改，保证崩溃恢复（WAL）；undo log 记录旧版本，用于回滚和 MVCC；binlog 是 server 层的逻辑日志，记录语句/行变更，用于主从复制和归档。提交顺序：先写 redo（prepare 状态）→ 写 binlog → redo 标记 commit，即两阶段提交（2PC），保证 crash 后 redo 与 binlog 一致；组提交（group commit）把多个事务的 fsync 合并以降低开销。

**8. Redis 淘汰与 LFU。** 淘汰策略八种：`noeviction`（写满报错）、`allkeys-lru`、`allkeys-lfu`、`allkeys-random`、`volatile-lru`、`volatile-lfu`、`volatile-random`、`volatile-ttl`。LRU 的不足是「偶发一次全量扫描会把冷数据顶成热数据」（缓存污染）；LFU 按访问频率淘汰，能抵抗偶发访问，但老数据的计数会一直累积、新数据难以出头。Redis 的 LFU 用 8 bit 存计数（概率递增，到 255 饱和）加 16 bit 存「上次衰减时间」，按 `lfu-log-factor` 控制增长难度、`lfu-decay-time` 控制衰减，避免计数无限累积。它不增加额外内存（复用 LRU 字段），但计数是近似值（概率递增 + 定时衰减），所以「准确」只能做到趋势正确；需要精确计数就得自己维护哈希表，代价是内存和复杂度。

**9. 手撕：盛最多水的容器。** 双指针从两端向中间收：面积 = `min(h[l], h[r]) * (r - l)`，每次移动较矮的一侧（因为移动高的一侧不可能让面积变大），O(n) 时间、O(1) 空间。要能解释为什么移动矮的一侧不会漏掉最优解：矮边是当前面积的瓶颈，固定它、换更高的边只会让宽度变小，所以以它为一边的最优解已经枚举过了。

**10. 工程与 AI 协作。** 埋点数据一般走「客户端上报 → 网关/日志服务 → Kafka → 数仓（Hive/Iceberg）」，底层是列式存储 + 分区，丢失靠客户端本地缓存重发和服务端幂等去重。AI 生成代码质量不高的常见原因：上下文不足（没给足相关文件和规范）、任务粒度过大（一次改太多处，注意力分散）、缺少验证（没有测试/编译反馈）、以及模型对项目约定不熟。改进靠「小步任务 + 明确验收 + 工具反馈闭环」：每次只让它改一处、改完跑测试和 lint、失败把错误信息回灌；规范用 lint/模板固化，而不是只写在提示词里。
