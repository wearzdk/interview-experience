### 《参考解析》

**全链路可观测这题，答「三支柱 + 一条 traceId」比罗列工具重要。** 落地顺序是：统一埋点规范（traceId 由网关生成并透传，跨线程、跨消息、跨 RPC 都要带），指标（Metrics）回答「有没有问题」，链路（Tracing）回答「问题在哪个环节」，日志（Logging）回答「具体是什么错」。三者用 traceId 串起来，日志里必须打 traceId 和 spanId，否则出了问题还是靠人肉 grep。工程上要注意采样：全量 trace 在高 QPS 下成本不可接受，常用「头部采样 + 慢请求/错误请求强制采样」，保证异常样本不丢。再往上一层才是「异常定位」：告警只负责发现，定位要靠「指标突变 → 关联 trace → 落到具体 span → 拉该 span 的日志」这条固定路径，能把 MTTR 从小时级压到分钟级。

**智能告警 Agent 的边界要先划清楚，否则会做成一个不可信的玩具。** 合理架构是「规则/阈值层做兜底 + 模型层做归因与降噪」：底层仍然用 Prometheus 之类的阈值和基线检测触发事件，模型只负责三件事——把同一时间窗内的多条告警聚成一个事件（降噪）、按历史工单检索相似故障给出可能根因（RAG）、生成排查建议并附上相关看板和日志链接。必须保留「人在环」：模型给出的结论要带证据（指标曲线、异常 span、日志片段），不能只给一句「可能是数据库慢」。要防止模型胡编，工具调用必须受限在一个白名单里（查指标、查日志、查最近变更），并且所有输出都要求引用来源。这套东西的价值不在「自动修复」，而在把值班人的前 10 分钟检索工作省掉。

**断点续传与分片：把「状态」落到服务端而不是客户端。** 分片一般按固定大小切（如 5MB），最后一片可能不足；每片独立算校验和（MD5/CRC32），上传时带 `uploadId + partNumber`。第四份失败时，服务端已经落盘的前三片保持有效，客户端只重传第四片；全部分片完成后调一次 `complete`，服务端按 partNumber 顺序合并并校验整体 ETag。关键是两点：一是「秒传」——上传前先用文件哈希查一次是否已存在；二是「分片记录的持久化」，uploadId 与已上传分片列表要落库（或 Redis），否则客户端换设备、进程重启就续不上。并发上传这题的正确答法是分场景：内网小文件串行更快（省掉连接建立与调度开销），大文件并发能打满带宽但要限制并发数（通常 4-8），真正的卡点常在接收端的磁盘写入与单连接窗口，而不是网络本身。

**零拷贝要能说出「省掉了哪几次拷贝」。** 传统 `read + write` 是 4 次上下文切换、4 次数据拷贝（磁盘→内核页缓存→用户缓冲→socket 缓冲→网卡）。`sendfile` 把「内核页缓存→socket 缓冲」这一步也省掉（DMA gather），变成 2 次切换 2 次拷贝；`splice` 借助管道在两个 fd 之间搬数据，适合代理转发；`mmap + write` 省掉一次 CPU 拷贝但仍有切换。面试官追问「零拷贝的函数」时，答 `sendfile(2)`、`splice(2)`、`mmap(2)`，并说明它们各自适用 Nginx 静态文件、Kafka 日志发送这类场景。

**「让 MySQL 无上限」是个陷阱题，正确答法是承认单机上限并给出分层方案。** 单机上限来自三处：单表 B+ 树深度带来的 IO 放大、写放大与 redo/undo 的刷盘能力、以及连接数与锁竞争。往上走的顺序是：读写分离（主写从读，解决读扩展）、分库分表（按用户或订单维度水平切，解决写与容量）、冷热分离（历史数据归档到列存/对象存储）、以及把「无限增长」的查询需求迁到 ES/ClickHouse 这类专为分析设计的引擎。真正的「无上限」不存在，工程上追求的是「按业务维度可线性扩展 + 有明确的分片键」。回答时最好点出分片键选择的代价：按用户分片则跨用户查询要聚合，按时间分片则热点集中。

**`rm -rf` 后磁盘没释放，标准答案是「文件还有进程持有」。** Linux 的文件是 inode + 链接计数，`rm` 只是把目录项删掉、链接计数减一，只要还有进程持有该文件的 fd（常见是被重定向的日志、被 `tail -f` 打开的文件、被删了但还在写的服务日志），inode 和数据块就不会回收。排查用 `lsof +L1` 或 `lsof | grep deleted` 找到持有进程，处理方式是重启/让它重新打开文件，或者 `: > /proc/<pid>/fd/<n>` 把内容清空（注意不要直接覆盖 inode）。另一个易混的原因是「文件系统层面有快照或延迟分配」，但绝大多数线上场景就是前者。
