### 《参考解析》

**三种并发控制。** 悲观锁默认冲突会发生，读或写之前先加锁（`SELECT ... FOR UPDATE`、行锁、表锁），优点是简单可靠，缺点是持锁时间长、并发度低、容易死锁。乐观锁假设冲突少，不加锁，更新时用版本号或时间戳做条件（`UPDATE ... SET v = v + 1 WHERE id = ? AND version = ?`），失败就重试，优点是并发度高，缺点是冲突多时重试成本高。MVCC 是数据库层面的多版本并发控制：每行记录带事务版本信息，读操作读取事务开始时的可见版本（快照读），写操作产生新版本，读写互不阻塞，解决了「读不加锁也能得到一致视图」的问题，但带来了版本链清理（purge）与长事务导致 undo 膨胀的问题。三者不是替代关系：MVCC 让普通读不用锁，写写冲突仍靠锁，业务层再按冲突概率选乐观或悲观。

**索引失效的常见场景。** 在索引列上做函数或运算（`WHERE DATE(create_time) = ...`）、隐式类型转换（字符串列用数字比较）、`LIKE '%xxx'` 前缀模糊、联合索引不满足最左前缀、`OR` 连接的列没有全部建索引、`!=` 或 `NOT IN` 导致优化器放弃索引、数据分布倾斜使优化器判断全表扫描更便宜、以及字符集不一致导致 JOIN 无法用索引。优化方法：把函数移到常量侧或建函数索引、联合索引按「等值在前、范围在后」排列、用覆盖索引减少回表、分页深翻用「延迟关联」或游标、统计信息及时更新、必要时用 `EXPLAIN` 验证而不是凭经验。

**AI 辅助编程的质量保证。** 分四层：输入层给足上下文（相关文件、接口约定、编码规范），让模型在约束内生成；生成层要求小步产出（一次一个函数或一个改动），便于 review；验证层必须跑编译、单测、lint 与类型检查，关键路径手动跑一遍；治理层建立团队规范（禁止直接提交未 review 的生成代码、敏感信息不进 prompt、依赖变更需人工确认）。工程性上还要看可维护性：命名、错误处理、日志、边界条件，这些是模型最容易偷懒的地方。

**缓存击穿与穿透、雪崩的区别。** 击穿是某个热点 key 过期瞬间大量请求打到数据库；解决方案是互斥锁重建（只让一个请求去查库，其余等待）、逻辑过期（不设物理 TTL，异步刷新）、热点数据永不过期 + 后台更新。穿透是查询不存在的数据，缓存与数据库都没有，解决方案是缓存空值（短 TTL）或布隆过滤器。雪崩是大量 key 同时过期或缓存整体不可用，解决方案是过期时间加随机抖动、多级缓存、熔断降级、集群高可用。

**代码生成平台为什么先做前端。** 前端的验收标准是可视的，生成结果能立即渲染、用户能直接判断好坏，反馈闭环短；后端涉及数据模型、事务、权限、部署，错误代价高且难以自动验证。用 RAG 的原因是把「设计规范、组件库文档、历史页面、业务术语」检索进上下文，让生成结果符合既有风格与约束，而不是每次从零猜。用户只有模糊需求时，靠「结构化澄清 + 多轮迭代」：先让用户选模板或参考图，生成第一版后让用户在预览上指哪改哪（局部重生成而不是整页重来），把每次修改沉淀成偏好。

**多模型兼容与结构化输出。** 差异主要在工具调用的协议（function calling 的字段格式、是否支持并行调用、是否支持强制指定工具）与结构化输出的可靠性（JSON mode、schema 约束）。兼容层要做三件事：统一内部工具描述格式，按模型能力做适配（不支持 function calling 的走提示词 + 解析）；对输出做 schema 校验，缺字段时按策略处理（重试并明确指出缺哪个字段、用默认值补齐并标记、或降级为纯文本回答）；对不同模型的错误码与限流做统一封装。模型要求 9 个字段只返回 8 个时，正确做法是校验失败后带着「缺 field_x」的反馈重试一次，仍失败则返回部分结果并标注缺失，而不是静默补默认值。

**记忆分层与 Token 成本。** 短期记忆是当前会话的上下文（对话历史、工具结果、任务状态），受窗口限制，需要压缩与裁剪；长期记忆是跨会话的知识（用户偏好、历史结论、领域知识），存在外部存储里按需检索。固定 Prompt 前缀的意义是命中提示缓存：系统提示与工具表放在最前且保持不变，可变内容追加在后面，缓存命中后这部分 token 按更低价格计费、首字延迟也更低。降低多轮成本的手段：压缩历史、把大段工具结果替换为摘要或引用、限制检索条数、对简单请求路由到小模型、把重复的静态内容前置以命中缓存。

**RocketMQ 与 Kafka。** Kafka 为高吞吐设计，分区顺序写、批量发送、零拷贝，适合日志、流式数据、事件总线；它的消息模型是分区 + 消费组，顺序性只保证分区内，事务与延迟消息支持较弱。RocketMQ 在事务消息、延迟消息、消息重试与死信、消息过滤上更完整，适合业务系统里的订单、支付这类需要可靠投递与定时触发的场景。选择依据是「吞吐优先还是业务语义优先」。

**中序遍历的非递归实现。** 用显式栈模拟递归：从根开始一路向左把节点压栈，直到为空；弹出栈顶访问，然后转向其右子树，重复。时间复杂度 O(n)，空间 O(h)。另一种写法是 Morris 遍历，利用叶子节点的空右指针做线索，空间 O(1)，但会临时修改树结构，适合对空间敏感且允许改动的场景。
