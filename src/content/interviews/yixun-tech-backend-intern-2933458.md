### 《参考解析》

**去重要先问清「去什么重」**：内容去重（文档 / 文章按正文指纹，如 SHA-256 或 simhash / MinHash 近似去重）、请求去重（幂等键 + Redis `SETNX`，防重复提交）、数据入库去重（唯一索引 + `INSERT ... ON DUPLICATE KEY UPDATE`，或先查后插加分布式锁）。工程上常用「两层」：入口用 Redis 挡短期重复，落库用唯一约束兜底，近似文本再用向量或 simhash 判相似。

**线上 404 / 500 / 503 的定位是三条完全不同的路径**：404 先看路由与网关转发（路径重写、大小写、末尾斜杠、CDN 缓存了旧路由），再看资源是否真被下线；500 是服务端异常，去日志按 traceId 捞栈、看是否是空指针 / 依赖超时 / 数据库连接耗尽；503 通常是上游不可用或限流熔断，看网关与负载均衡的健康检查、实例是否全部不健康、是否触发了限流。通用动作是「看监控大盘 → 拿 traceId 定位到具体实例 → 看该实例日志与依赖状态 → 复现」。

**「让 Agent 输出指定格式文章」的设计重点是约束前置**：把目标格式写成结构化 schema（章节、字数、必须包含的字段），用模板 + few-shot 示例固定结构，分两步——先让模型输出大纲并校验，再按大纲逐节生成；生成后用程序校验（正则 / JSON Schema / 字数），不合格自动重试并带上失败原因。这样比一次性让模型「写一篇格式正确的文章」稳定得多。

**大文档的处理是「切分 + 检索 + 局部生成」**：先抽文本、按标题层级切块、超长块再按 token 拆并保留重叠；生成时不是把所有块塞进去，而是先检索与目标相关的块，按章节任务逐块生成再汇总；对必须看全文的任务（如总结）用 map-reduce：分块摘要 → 归并摘要 → 生成终稿，并记录每段来源以便核对。

**上下文与记忆裁剪**的原则是「保留决策与结论、丢弃冗余过程」：短期上下文按轮次 + token 双阈值裁剪（保留 system、最近 N 轮、以及被引用过的工具结果），长期记忆抽取成结构化事实（用户偏好、已确认的结论）存外部，检索相关记忆再注入；工具的大结果先摘要再进上下文，原文留在可回查的存储里。这三层是面试里最容易被追问「具体怎么定阈值」的地方，答「按模型上下文窗口的 60%~70% 设软阈值，超了就触发压缩」比较实在。
