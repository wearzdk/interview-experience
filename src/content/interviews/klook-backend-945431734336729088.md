### 《面试题目》

1. 项目对抢购高并发有经验，抢购怎么做、怎么解决高并发？
2. 做高并发时基于 IP 限流，公司里几百上千人同网段抢购，难道都封掉？
3. Redis 里扣减完库存但用户没支付 / 钱不够 / 不想买，怎么处理？
4. 把正确库存回传 Redis 时也有人同时在扣减，怎么处理 Redis 并发问题？
5. 表格怎么 embedding 处理？
6. RAG 里写数据的人和问问题的人表述不一致、文本匹配度不高怎么办？
7. RAG 中商家信息写「不能吃花生」，用户问「我对某些东西过敏」，怎么让系统 get 到意思？
8. 上面过敏源场景还有没有优化方案？
9. HashMap 的槽怎么来的？怎么计算出来的？

### 《参考解析》

**抢购的高并发**

分三层答。入口层：静态资源上 CDN、活动页做成静态化、按钮置灰防重复提交，网关按「用户 + 设备 + 接口」限流，把绝大部分流量挡在业务之外。中间层：库存预热进 Redis，扣减用 Lua 脚本把「查库存 + 判断 + 扣减」合成一次原子操作，避免 check-then-set 的竞态；库存按活动拆成多段分片，降低单 key 热点。落库层：MQ 削峰，订单异步入库，用订单号做幂等键。

**IP 限流误伤同网段**

IP 是弱标识，公司出口、校园网、运营商 NAT 后面是成千上万人。改法是分层限流：默认按用户维度（登录 uid / 设备指纹）限，IP 只做「异常放大」的粗粒度阈值（比如单 IP 每秒超过正常人均十倍才拦），并且分级处置——先排队、再验证码、最后才拒绝。再加白名单与灰度，被误伤的用户能申诉。核心是把「限流」从封 IP 变成控制并发与排队。

**Redis 预扣后用户不付款**

标准做法是预扣 + 过期回补：扣减时同时写一条带 TTL 的占位记录（或把订单号写进活动的已售集合），订单超时未支付就由延时消息把库存加回去，加回时同样走 Lua 保证幂等（用订单号去重，避免重复回补）。再加一道对账：Redis 库存与 DB 已售数量定期核对，不一致就以 DB 为真修正，并把差异写告警。「钱不够 / 不想买」本质上是「未支付」的子集，处理路径相同。

**库存回传时的并发**

回补不是简单 `INCR`：它和正在进行的扣减会互相覆盖。用 Lua 把「校验占位记录存在 → 加回 → 删占位」做成原子操作；如果业务上允许多次回补，就用 `SETNX` 式的幂等键。更稳的做法是把库存的唯一真源放在 DB（带条件的 `UPDATE ... WHERE stock > 0`），Redis 只做流量过滤，回补以 DB 结果为准重刷缓存，避免两套账长期漂移。

**表格的 embedding**

表格不能整块丢进向量库。常见做法有三种：按行转成「表名 + 列名: 值」的自然语言句子后逐行 embedding（适合查询单条记录）；把表结构和列名单独 embedding，让模型先选表再用 SQL 取数（text-to-SQL 路线，适合聚合查询）；对小表做整表序列化 + 摘要 embedding（适合问答式检索）。工业上常是「schema 检索 + SQL 生成」为主、「行级语义」为辅，两种都存，按问题类型路由。

**表述不一致与语义匹配**

写库的人和提问的人用词不同，纯文本相似度必然掉。解法是混合检索：BM25 保证关键词命中，向量检索保证语义召回，再用交叉编码器重排；同时做 query 改写（同义词、缩写展开、指代消解）和索引侧的「问题化改写」——入库时让模型把一条事实改写成若干可能的问法一起向量化。领域词表（别名、品牌名、商品同义词）用词表兜底比纯模型可靠。

**过敏原语义**

「不能吃花生」和「我对某些东西过敏」之间没有字面重合，靠向量也不稳，正确做法是引入结构化的领域本体：把过敏原建成实体（花生、坚果、乳制品…），商品/商家信息抽取成「含有什么」的结构化字段，用户 query 先做意图识别（是否为过敏约束），再落到实体上做集合运算。这一步不是检索问题，是知识表示问题。优化方向：允许用户维护自己的过敏档案、对模糊表述（「有点过敏」）做风险分级并默认从严、给答案附上依据（哪条商品信息说了含花生）。

**HashMap 的槽位**

`hash = h ^ (h >>> 16)`，即把高 16 位异或到低 16 位做扰动，让高位也参与定位；然后用 `(n - 1) & hash` 取槽，n 是容量且必须是 2 的幂，这样取模等价于按位与、更快。这也解释了为什么扩容是翻倍：元素要么留在原位，要么移动 `oldCap` 距离。冲突链长度到 8 且容量 ≥ 64 时链表转红黑树。
