### 《参考解析》

**为什么自研而不套框架**：LangChain、LangGraph 的价值是快速拼装与现成的工具生态，代价是依赖重、版本变动快、调试链路长（出问题时要穿过框架的多层封装）。用 C++ 自研的合理理由通常是三点：需要嵌入已有的 C++ 桌面应用、对启动延迟与内存有硬约束、要把 Agent 能力做成可控的 SDK 分发给工业客户。回答时不能只说「性能好」，要给出量化的对比（二进制体积、冷启动时间、内存占用）与工程理由（部署环境不能装 Python、需要静态链接、要能离线运行）。同时要承认自研的代价：工具调用、重试、流式输出、上下文裁剪这些都要自己实现并维护。

**Provider 的扩展设计**：本质是「面向接口 + 注册表」。先定义 Provider 抽象（`chat`、`stream`、`embed` 等纯虚函数，入参出参与具体厂商无关），各厂商实现派生类，用工厂或注册表按名称创建；注册可以用静态注册宏（每个实现文件在编译期把构造器登记进 map），也可以用配置文件显式注册。新增一个厂商只需要新增一个实现文件、不动调用方，符合开闭原则。策略模式用于「同一个任务有多种可替换算法」（如不同的上下文裁剪策略、不同的重试策略），与 Provider 的工厂/注册表是两件事，回答时要把两者的职责分清，避免把设计模式名词堆在一起。

**Qt 嵌入 VTK 的遮挡问题**：VTK 的 `QVTKOpenGLNativeWidget` 用原生窗口承载 OpenGL 上下文，原生子窗口与 Qt 的绘制体系不在同一套合成里，会出现层级（Z-order）错乱、悬浮控件被盖住、透明背景变黑。常见解法是改用 `QVTKOpenGLWidget`（离屏渲染到 FBO，再作为 Qt 控件合成）、给上层控件设置 `WA_NativeWindow` 提升为原生窗口、或在嵌入后调整窗口标志与父子关系。根因往往与图形驱动、Qt 版本、VTK 版本的组合有关，要说明排查过程：先确认是绘制顺序问题还是原生窗口合成问题，再用最小示例复现。

**像素到物理面积的换算**：若相机光轴垂直于被测平面且距离固定，用标定得到的「每像素对应的物理长度」（mm/px）平方后乘缺陷像素数即可；更严谨的做法是用相机内参把像素坐标反投影到相机坐标系，结合深度图或已知工作距离还原三维点，再在平面上计算面积（多边形面积或三角剖分求和）。有深度数据时逐像素反投影更准，能处理倾斜。回答时要区分「平面假设」与「任意曲面」两种情形，并说明标定误差、镜头畸变、透视形变各自的修正方式。

**凸起与凹陷**：固定工作距离的二维测量假设缺陷在同一平面上，凸起会让局部离相机更近、放大像素尺寸，凹陷则相反，直接乘固定比例会系统性偏大或偏小。处理方式是用深度图或结构光得到每个像素的真实深度，按深度逐点反投影计算曲面面积；没有深度时可用多视角或光度立体补，或者只报「投影面积」并在结果里注明测量口径。工程上还要给出误差范围，而不是一个看似精确的数字。

**工业 Agent 与知识库**：项目初期知识少、问题集中，直接把关键文档与规则放进系统提示或少量示例（few-shot）最有效，成本低、可控；后期文档规模上来、问题发散，才需要检索（向量 + 关键词混合）与结构化知识（设备型号、工艺参数、故障码表）。上下文过长的处理不是一味截断，而是分层：固定规则常驻、检索结果按相关性取 Top-K 并压缩、历史对话做摘要。幻觉的控制靠「让模型基于检索到的原文回答并给出出处」、对关键字段做程序化校验、以及把不确定的结论交给人工确认。用 JSON 传先验知识还是拼字符串，取决于是否需要程序消费：需要校验与复用就用结构化字段，只是提示用途则字符串更直接。
