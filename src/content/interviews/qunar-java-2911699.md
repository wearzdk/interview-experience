### 《参考解析》

**线程池参数要和任务特征一起讲**

先说明任务主要消耗 CPU，还是等待数据库、网络。再结合请求量、任务耗时、下游并发上限和可接受排队时间设置线程与队列容量，用压测检查吞吐、尾延迟和拒绝次数。固定线程池、单线程池默认使用无界队列，持续积压会消耗内存；缓存线程池则要留意线程数量增长。定时任务还要考虑任务耗时、异常和取消后的清理。

**虚拟线程的收益来自减少等待占用**

Java 21 的虚拟线程由 JVM 调度到平台线程上，适合大量需要等待 I/O 的任务。它不能让 CPU 密集计算凭空变快，下游数据库连接数等限制也依然存在。ThreadLocal 可以使用，但每个虚拟线程都保存大对象，会放大内存开销；不要用它为海量任务各缓存一份昂贵资源。虚拟线程通常按任务创建，限流应针对受限资源本身。相关设计说明见 [OpenJDK JEP 444](https://openjdk.org/jeps/444)。

**从慢请求找到耗时所在**

先选一条真实慢请求，用链路追踪或分段耗时区分排队、业务计算、数据库和远程调用。下游调用耗时高，还需核对连接池等待、网络建立连接和对端处理时间。CPU 高时，针对平台线程可用 `top -H -p <pid>` 找线程，再将线程编号转为十六进制，与线程转储中的 `nid` 对照。虚拟线程不与操作系统线程一一对应，需要结合支持虚拟线程的转储和性能分析工具。连续采样比单次堆栈更有意义，也要用 GC 日志和分配速率排除回收压力。

**深分页为什么越翻越慢**

`LIMIT offset, size` 往往要先读取并跳过前面的记录。偏移量越大，扫描、排序或回表的成本可能越高；具体瓶颈要看执行计划，不能把所有深分页都归结为 CPU。连续翻页可用稳定排序键加唯一键作为游标；必须随机跳页时，再评估覆盖索引、先取主键后回表等方案。

**日期区间合并**

先把日期解析为可比较的时间或日期值，明确区间是否包含端点。按起点排序，维护当前区间的最晚终点；下一段重叠就延长终点，否则输出当前段并开始新段。排序耗时 O(n log n)。相邻但不重叠的日期是否合并，要按题目约定处理。
