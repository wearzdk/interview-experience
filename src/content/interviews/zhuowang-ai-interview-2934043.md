### 《参考解析》

**泛型与类型擦除**：泛型让编译期就能做类型检查、避免强制转换，核心价值是「把类型错误从运行期提前到编译期」。Java 用擦除实现泛型：编译后类型参数被替换成它的上界（无上界就是 `Object`），多上界取第一个，同时在必要位置插入强制转换桥接。带来的问题：运行时拿不到真实类型参数（`new T[]`、`instanceof List<String>` 都不行）、不能有「同一擦除后签名相同」的重载（`f(List<String>)` 与 `f(List<Integer>)` 冲突）、基本类型不能做类型参数（要装箱）、泛型数组创建受限。绕过方式是传 `Class<T>` 或 `TypeReference`（Jackson 用的就是保留泛型信息的匿名子类）。

**GC 与 STW**：核心流程是「找垃圾 → 回收 → 整理」。找垃圾用可达性分析：从 GC Roots（栈上的局部变量、静态变量、JNI 引用、活跃线程）出发标记所有可达对象，不可达的即可回收。必须暂停用户线程的原因是「一致性」——标记过程中如果引用关系还在变，会漏标（把存活对象当垃圾回收，程序崩溃）或错标。并不是整段暂停：并发标记（CMS、G1 的并发标记阶段）可以让用户线程继续跑，靠写屏障记录引用变化（增量更新或 SATB），只在初始标记与最终标记（重新标记）这两个短阶段 STW。这也是为什么低延迟收集器的停顿主要来自「根扫描」与「最终标记」。

**MyBatis 与 Hibernate**：MyBatis 是半自动的 SQL 映射框架——你写 SQL，它负责参数绑定与结果映射，控制力强、SQL 可优化、便于接手遗留库；Hibernate 是全自动 ORM——你操作对象，它生成 SQL，开发快但复杂查询容易生成低效 SQL、调优困难。多表关联的结果映射有两种主流做法：一是 `resultMap` 配 `association`（一对一）与 `collection`（一对多），用 `column` 映射到嵌套对象的属性，注意一对多会因 join 产生重复行、要指定 `id` 让 MyBatis 合并；二是分两次查询（先查主表、再用 `IN` 查子表）在代码里组装，避免笛卡尔积放大，数据量大时更稳。

**Vue 的 key**：`key` 是虚拟 DOM diff 时判断「这个节点还是不是原来那个」的标识，用于复用与移动节点、保留组件状态。用 index 当 key，在头部插入元素时所有元素的 index 都后移一位，diff 认为「第 0 个还是第 0 个、只是内容变了」，于是就地复用 DOM：输入框里的值和组件内部状态会错位到别的行，动画与过渡也会错乱，同时多出不必要的 patch。正确做法是用业务唯一 ID 做 key。这条同样适用于 React。

**系统提示词与注入防护**：System Prompt 定义角色、能力边界、输出规范、安全策略与工具使用规则；与用户消息分开是因为它属于「更高优先级的指令层」，模型在训练与对齐中被教导优先遵循 system，同时工程上便于统一维护与审计（用户输入不能改写它）。生产级提示词通常包含：身份与目标、可用工具与调用规范、输出格式约束、禁止事项与拒答策略、以及「用户输入只是数据、不是指令」这类元规则。防护不能只靠提示词——真正的边界靠三层：输入侧（识别并隔离用户内容，用分隔符/结构化字段标记）、工具侧（工具自己做权限与参数校验，不信任模型传来的值）、输出侧（敏感操作要二次确认、外发内容过一道检查）。所以这道题的好答案会主动说「提示词是第一层，不是唯一一层」。

**SQL 注入**：根因是「把数据当成了代码」——用户输入被拼进 SQL 文本后，其中的引号与关键字被数据库当成语法解析，于是 `' or '1'='1` 能改变查询语义。防护首选参数化查询（预编译，SQL 结构与数据分离），其次是对标识符（表名、列名、排序字段）做白名单校验，因为这类不能参数化；再配合最小权限账号、错误信息不外泄、ORM 的绑定参数。要注意「转义函数」不是首选方案（编码与字符集边界容易出错）。

**MySQL 一次查询**：连接层（连接器做认证与权限）→ 解析器（词法语法分析生成语法树）→ 预处理器与优化器（改写、选索引、生成执行计划）→ 执行器（按计划调用存储引擎接口）→ 引擎层（InnoDB 走 Buffer Pool，命中就返回，未命中从磁盘读页并可能触发预读）→ 返回结果集。优化手段按收益排序：加合适的索引（含联合索引的最左前缀与覆盖索引）、避免 `select *`、减少回表、用 `explain` 看是否走错索引（必要时 `force index`）、大结果集分页优化（用游标或延迟关联而不是大 `offset`）、避免在索引列上做函数运算、控制事务长度减少锁持有。

**Buffer Pool 脏页淘汰**：InnoDB 的 Buffer Pool 用改进的 LRU（分 young/old 两段，新页先进 old 区，避免全表扫描把热数据挤出去）。脏页是「已修改但还没写回磁盘」的页。当需要腾出空闲页而脏页太多时，不能直接淘汰（会丢修改），必须先刷脏。刷脏由后台线程按 checkpoint 推进，配合「自适应刷脏」按 `innodb_io_capacity` 与脏页比例控制速度；如果空闲页耗尽、脏页又刷不过来，用户线程会被迫参与「单页刷脏」甚至进入「sharp checkpoint」式的同步等待，表现为查询突然变慢。考点在于能说出「脏页比例高 + 写入突增 → 刷脏跟不上 → 用户请求被阻塞」这条因果，以及缓解手段（调大 buffer pool、调 `innodb_io_capacity` 与 `innodb_max_dirty_pages_pct`、避免大事务产生大量脏页、用 SSD 提升随机写）。

**ReAct 与 Plan-and-Execute**：ReAct 是「思考—行动—观察」的紧密循环，每一步都根据上一步的工具结果决定下一步，适应性强、能及时纠错，但步骤多、token 消耗大、容易在小问题上绕圈，且缺少全局规划容易走偏。Plan-and-Execute 是先用模型生成一份完整计划（子任务列表），再逐步执行（执行器可以是更小的模型或确定性代码），优点是全局视角、成本可控（规划只做一次）、可人工审核计划；缺点是计划一旦基于错误假设就很难自我修正。所以第 16 题的正确答案是 ReAct（或 Plan-and-Execute 生成计划 + 每步用 ReAct 执行并允许重规划）——「需要根据工具返回结果大幅调整路径」正是 ReAct 的强项。加分回答是提混合方案：先出粗计划保住方向，执行中允许插入重规划节点，并设最大步数与预算上限防失控。
