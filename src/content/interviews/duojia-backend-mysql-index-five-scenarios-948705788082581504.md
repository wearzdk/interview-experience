### 《面试题目》

1. 你做过 SQL 优化，那讲讲索引在什么情况下会失效？
2. 这些失效场景你实际遇到过几次？分别是怎么发现的？
3. `WHERE phone = 13800000000` 而 `phone` 是 varchar，会走索引吗？
4. `WHERE DATE(create_time) >= '2024-03-01'` 与范围写法有什么区别？
5. 联合索引 `(a, b, c)` 下，`WHERE a = 1 AND c = 2` 能用上几列？`WHERE a > 1 AND b = 2` 呢？
6. `OR` 连接两个字段，其中一个没索引，怎么处理？
7. 有索引但百万级数据查询仍然全表扫描，为什么？
8. 系统排查索引问题的步骤是什么？

### 《参考解析》

**场景一：隐式类型转换。** `phone` 是 `varchar(20)` 且有索引，`WHERE phone = 13800000000` 仍然全表扫描——右边是数字字面量，MySQL 会把字符串列转成数字再比较，等价于在列上套了转换函数。改成 `phone = '13800000000'` 立刻变成 `ref`。判断特征：`key` 是 NULL 而 `possible_keys` 有值，先怀疑类型。工程上的防法是入参校验带类型约束，不要指望 ORM 兜底。

**场景二：函数或运算包住索引列。** `WHERE DATE(create_time) >= '2024-03-01'` 中 `create_time` 被函数包住，优化器无法用索引做范围定位，改为 `create_time >= '2024-03-01 00:00:00'` 即可。需要区分的是函数作用在常量上（`WHERE create_time >= NOW() - INTERVAL 7 DAY`）——列是干净的，索引照样可用。真正要警惕的是函数出现在等号左边。

**场景三：最左前缀被跳过，且有多种变体。** `(a, b, c)` 索引下：`WHERE b = 1 AND c = 2` 一列都用不上；`WHERE a = 1 AND c = 2` 只能用 a（`key_len` 会暴露这一点）；`WHERE a > 1 AND b = 2` 中 a 是范围，b 不能用于定位；`WHERE a = 1 ORDER BY b` 可以借索引顺序避免排序，但 `ORDER BY c` 不行。设计索引时先想清等值条件与范围条件，等值列放前面，范围列放最后，别为了「覆盖全」把五六个字段堆进去。

**场景四：OR 连接了无索引列。** `WHERE category_id = 3 OR brand = 'xxx'` 中 `brand` 没有索引，优化器权衡后很可能直接全表扫描，因为 `OR` 要求两侧都能走索引才划算。解法是给 `brand` 加索引（低区分度时通常不值得）或拆成两条 SQL 用 `UNION ALL` 合并。作者补了一个细节：`UNION` 会去重因而更慢，`UNION ALL` 配合业务层去重往往更快，但要看结果集大小，最好两种都 `EXPLAIN` 一次再定。

**场景五：区分度太低，优化器主动放弃。** `status` 只有 0/1/2 三个取值，单独建索引后查询百万级数据仍然全表扫描，`possible_keys` 有索引而 `key` 为 NULL。用 `SHOW INDEX` 看 `Cardinality`（基数）能确认值分布。低区分度字段单独建索引基本没意义，除非配合其他列做联合索引，或者该值极度倾斜（99% 都是 0，只查 1% 时才有效）。

**三步排查法。** 先 `EXPLAIN` 看 `type` 与 `key`，判断是「用不上」还是「不想用」；再 `SHOW WARNINGS` 看优化器改写后的 SQL；最后结合 `SHOW INDEX` 的 `Cardinality` 判断值分布。作者强调不要迷信「索引失效清单」——同一条 SQL 在不同数据分布下表现可能完全不同，把 B+ 树的排序规则与优化器成本模型想清楚，比记住十条结论可靠。
