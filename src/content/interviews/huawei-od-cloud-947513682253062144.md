### 《参考解析》

**虚拟化与容器**：虚拟化在硬件之上跑 Hypervisor，每个虚拟机有独立内核与完整系统镜像，隔离强、启动慢（分钟级）、资源开销大；容器共享宿主机内核，靠 namespace 做隔离、cgroups 做资源限制，启动快（秒级）、密度高、镜像分层复用。选型看需求：需要跑异构操作系统、强隔离、合规要求高的多租户场景用虚拟机；微服务、弹性伸缩、持续交付用容器。生产中常见是「虚拟机里跑容器」，兼顾隔离与效率。

**CPU 打满的排查顺序**：先 `top` 看整体负载与最耗 CPU 的进程；`top -H -p <pid>` 看该进程内哪个线程高；区分用户态高还是内核态高（`%us` 与 `%sy`）。用户态高就抓线程栈（`jstack` 或 `gdb`、`perf top`、`perf record`）定位热点函数；内核态高看上下文切换（`vmstat`、`pidstat -w`）、系统调用（`strace -c`）、软中断（`/proc/softirqs`，常见于网络收包）与 IO 等待（`iostat`）。还要排除外部因素：是否有定时任务、是否有突发流量、是否被限流前的重试打爆。结论要能落到「是哪个进程、哪个线程、哪段代码或哪类系统调用」，而不是停在「CPU 高」。

**Pod Pending 的排查**：按调度链路逐层看。先 `kubectl describe pod` 看 Events，这是最快的信息源。常见原因分四类：资源不足（节点 CPU/内存不够，或 requests 设得过大）；调度约束不满足（nodeSelector、亲和性与反亲和性、污点与容忍）；存储挂不上（PVC 未绑定、StorageClass 不存在、多可用区与节点不在同一区）；镜像拉取失败或配额超限（ResourceQuota、LimitRange）。区分方法是看事件文案：`Insufficient cpu` 是资源，`node(s) had taint` 是污点，`waiting for volume` 是存储。回答时承认「生产上没遇到过、是文档里看到的」比编造强，面试官关心的是你的排查路径是否成立。

**滚动更新与回滚**：Deployment 通过 ReplicaSet 管理 Pod，更新时创建新 ReplicaSet，按 `maxSurge` 与 `maxUnavailable` 逐步扩新缩旧；配合 readinessProbe 保证新 Pod 就绪后才接流量，配合 `minReadySeconds` 与 `progressDeadlineSeconds` 防止坏版本全量铺开。回滚用 `kubectl rollout undo`，也可以 `--to-revision` 回到指定版本，`kubectl rollout status` 观察进度、`kubectl rollout history` 查历史。要注意数据库变更不随应用回滚，所以 schema 变更必须向前兼容。

**Service 类型**：ClusterIP 是集群内虚拟 IP，供集群内部访问；NodePort 在每个节点上开一个固定端口，从集群外通过「节点 IP 加端口」访问，适合测试或没有负载均衡的环境；LoadBalancer 在云上申请外部负载均衡器；ExternalName 做 DNS 别名。生产对外一般用 Ingress 加 Ingress Controller 统一入口，而不是直接暴露 NodePort。

**PV / PVC 与 StatefulSet**：PV 是集群层面的存储资源，PVC 是用户对存储的申请，两者通过 StorageClass 动态供给或静态绑定，绑定后 PVC 与 PV 一一对应。StatefulSet 给每个 Pod 固定的序号与稳定的网络标识（`pod-0`、`pod-1` 加 Headless Service 的 DNS），并要求每个 Pod 有自己的存储，所以用 `volumeClaimTemplates` 为每个副本生成独立 PVC——这样 Pod 重建后仍能挂回原来的数据。无状态服务用 Deployment 共享存储卷即可，不需要 StatefulSet。

**上云后晚高峰延迟抖动**：按「先分清范围、再看资源、再看依赖、最后怀疑网络」的顺序。看监控曲线是整体抬升还是少数实例尖刺，整体抬升说明是共享资源或下游瓶颈，尖刺说明是单实例问题。资源侧看 CPU 的 throttling（容器被 cgroup 限流是最常见的隐性原因）、内存是否触发回收、磁盘 IO 与连接数。依赖侧看慢查询、下游 RT、连接池耗尽、重试风暴。网络侧看丢包、重传、跨可用区调用、NAT 与负载均衡的连接复用。上云场景特有的坑：CPU requests/limits 设得过低导致节流、节点间带宽打满、存储 IOPS 受限、安全组或 NAT 会话数上限。排查要有数据：对比高峰与低谷的同一指标，做单变量验证。
