### 《面试题目》

1. 简单介绍实习经历，你主要负责哪部分？
2. 开发或部署时遇到过线上故障吗？举一个例子，说说怎么发现、定位和修复。
3. 多个任务的传输数据怎么区分？每一部分需要单独标识吗？
4. 传到一半中断，部分数据已经保存，重传时怎么判断哪些数据可以复用？进度根据已有数据判断，还是单独记录？
5. 如果重传的数据和上次留下的数据重复，哪些可以合并，哪些需要清理？
6. 把一批数据交给后台异步保存，接收方立刻复用同一块内存接收下一批，这样安全吗？
7. 如果每一部分都已经保存成功，为什么最后仍可能合并失败？
8. 怎么把已有业务流程封装成 Agent 能执行的能力？拆分流程后，底层工具还能共用吗？
9. 同一个流程被重复触发时，怎么保证执行的幂等性？
10. 场景越来越多时，是让 Agent 专门处理一类任务，还是集成多种能力？
11. 能否先根据用户问题筛选候选能力，再执行选中的流程？这样能把上下文控制在什么范围？
12. 任务由 Agent 触发，还是独立运行？调用是定期发起，还是按需触发？
13. 创建任务的请求超时，但服务端可能已经创建成功，只是响应没收到，怎么确认并更新任务状态？

### 《参考解析》

**断点续传的设计**：每个传输任务有全局 ID，每个分片有序号、偏移、长度与校验和，元数据单独存储（任务 ID、总分片数、已完成分片、每片哈希、版本）。重传时先拉取服务端的分片清单，按「序号 + 哈希」判断哪些已存在且完整，只补缺失或校验失败的分片；进度以服务端持久化的清单为准，不能只靠客户端内存或文件大小推断，因为文件大小相同不代表内容一致。重复分片按哈希去重，冲突时以校验通过且版本更新的一份为准，旧分片标记为待清理，合并前统一校验整体哈希。合并失败常见原因是分片缺失、顺序错、元数据与数据不一致、并发写入或存储配额不足；即使每片都成功，也要在合并前做完整性校验，并把合并做成可重试的幂等操作。

**异步保存时复用内存不安全**：后台线程还在读这块缓冲区，接收方就写入下一批，会出现数据被覆盖、读到半新半旧的内容。要么让后台线程拥有缓冲区所有权（拷贝或转移），要么用引用计数/引用传递，等消费完再归还池；用对象池时归还前必须确认没有未完成的读写。根本上是生命周期管理问题，不是加锁就能解决。

**业务流程封装成 Agent 能力**：把流程拆成「查询类、计算类、写入类」工具，每个工具有清晰的输入输出、错误码、权限与幂等键；流程编排保留确定性，模型只负责选择与填参，关键节点加校验与人工确认。拆分后底层工具可以共用，但要避免工具过细导致模型选择困难，按业务动作聚合到合适粒度。

**幂等**：用业务唯一键（订单号、任务 ID、请求 ID）做幂等键，服务端在事务内先查后写或依赖唯一索引；重复请求返回同一结果，而不是重复执行副作用；异步任务记录状态机，重复触发只推进一次；外部调用带幂等标识，超时后先查询再重试。幂等要覆盖创建、执行、回调、补偿全链路。

**能力选择与上下文**：能力多时先做路由，按用户问题检索候选工具（关键词、向量、规则），只把相关的几个工具 schema 注入上下文，减少选择困难与 token；单 Agent 集成多能力适合关联任务，专门 Agent 适合边界清晰、上下文长的场景。路由本身可以用小模型或规则，失败再回退到全量工具。

**任务触发与超时确认**：任务可以由 Agent 按需触发，也可以由调度器定期触发，取决于时效与成本；创建请求超时后用幂等键查询任务状态，服务端要提供按请求 ID 查询的接口，查到已创建就更新本地状态，查不到再重试；重试仍带同一幂等键，避免重复创建。最终一致性靠对账任务兜底。
