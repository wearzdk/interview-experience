### 《参考解析》

**Redis 为什么快**：纯内存操作，省掉磁盘 IO；单线程处理命令，避免了锁竞争与上下文切换（6.0 起网络 IO 多线程，命令执行仍是单线程）；IO 多路复用（epoll）支撑高并发连接；数据结构针对场景优化——SDS 带长度信息、跳表做有序集合、listpack 压缩小对象、渐进式 rehash 避免长停顿。答题时要补一句「单线程的代价」：一个慢命令（`KEYS *`、大 key 的 `HGETALL`、复杂度高的 `ZRANGE`）会阻塞所有请求，所以线上禁用 `KEYS`，用 `SCAN` 分批，并且要监控大 key 与热 key。

**穿透、击穿、雪崩**：穿透是查不存在的数据，请求绕过缓存直打数据库——缓存空值并设较短过期、布隆过滤器前置拦截、参数校验；击穿是热点 key 过期瞬间大量并发穿透——互斥锁重建（只放一个线程回源）、逻辑过期 + 异步刷新、热点 key 永不过期；雪崩是大量 key 同时过期或缓存整体不可用——过期时间加随机抖动、多级缓存、缓存集群高可用、限流降级兜底。三者要分清触发条件，很多候选人把击穿和雪崩混着答。

**RDB 与 AOF**：RDB 是某一时刻的全量快照，文件紧凑、恢复快、对主进程影响可通过 fork + COW 控制，但会丢最后一次快照之后的数据；AOF 追加写命令，`appendfsync` 有 always / everysec / no 三档，everysec 最多丢 1 秒，文件更大、恢复更慢，需要周期性重写压缩。生产常用混合持久化（AOF 里前半段是 RDB 格式、后半段是增量命令），兼顾恢复速度与数据安全。要能说出 fork 的阻塞与 COW 在大内存实例上的拷贝开销。

**Redis 分布式锁**：`SET key value NX PX ttl` 一条命令完成加锁与过期，value 存唯一标识（UUID + 线程 id），解锁用 Lua 脚本先比对 value 再删，避免误删别人的锁；业务可能超时则要靠看门狗续期。已知局限：主从异步复制下主节点宕机可能丢锁（需要 RedLock 或改用带 fencing token 的方案）；锁过期而业务未完成时仍会并发进入，所以关键资源最好再加一层数据库层的乐观锁或唯一约束兜底。

**集群下的缓存一致性**：常用 Cache Aside——读先查缓存，未命中查库回填；写先更新数据库再删缓存，删失败进重试队列或靠 binlog 订阅补偿。延迟双删用于缓解「删缓存后、主从同步完成前」被旧值回填的窗口。强一致要求高时要么加分布式锁串行化读写，要么直接读主库；跨集群（多活）时通常只能做到最终一致，要明确业务能容忍的陈旧时间。回答时讲清「为什么是删而不是更新缓存」（并发写导致旧值覆盖新值）与「先删缓存为什么不行」（并发读会回填旧值）。

**重复消费**：MQ 的语义通常是 at-least-once，重复不可避免，所以消费端必须幂等。手段：业务唯一键 + 数据库唯一索引（最可靠）、Redis `SETNX` 记录已处理的 messageId（要设过期并注意与业务的原子性）、状态机校验（只允许从待支付流转到已支付）、版本号或乐观锁。要说明「幂等不是去重」：去重表只能挡住完全相同的消息，真正的幂等是让同一操作执行多次结果一致。

**顺序性**：全局顺序只能单分区单消费者，代价是吞吐；业务上更常见的是分区内有序——按业务主键（订单号）哈希到同一分区，消费端单线程处理该分区，或用内存队列按 key 分发到固定线程。要处理重试导致的乱序：失败消息不能直接丢回队尾重投，应进重试队列或阻塞该分区。跨分区乱序（如同一订单的支付回调与状态变更分别落在不同分区）必须在消费端按业务规则排序或丢弃过期状态，这一点常被追问。

**分布式事务**：2PC/XA 强一致但性能差、协调者单点；TCC 需要业务实现 Try/Confirm/Cancel 三个接口，侵入大但可控；可靠消息最终一致（本地消息表 + 定时投递 + 消费幂等）最常用；Saga 适合长流程、每步有补偿；最大努力通知适合对账类场景。选型看一致性要求与业务复杂度：资金类倾向 TCC 或强一致方案，订单与库存这类可用可靠消息 + 对账兜底。答题时讲清自己项目里选了哪种、为什么、怎么处理中间态。

**限流、熔断、降级**：限流控制入口速率（令牌桶、漏桶、滑动窗口），保护自身不被压垮；熔断是针对下游依赖的失败率阈值，打开后快速失败、定期半开放量探测，避免雪崩式等待；降级是在资源不足时关闭非核心功能、返回兜底数据。三者常配合使用：先限流挡住超额流量，下游异常时熔断，整体过载时降级非核心链路。

**幂等设计**：唯一键（业务单号 + 唯一索引）、token 机制（提交前取 token、提交时消费）、状态机（只允许合法流转）、乐观锁版本号、分布式锁（短时间窗口内串行）。要区分「接口幂等」与「业务幂等」：接口层挡重复请求，业务层还要保证同一语义的操作重复执行不出错。

**秒杀系统**：分层削流——前端限购与按钮防抖、网关限流、库存预热到 Redis、Lua 脚本原子扣减、扣减成功才发 MQ 异步下单、数据库最终落库并用唯一索引防超卖。要点是「库存判断与扣减必须在同一次原子操作里」，以及失败补偿与对账；热点商品可做库存分桶（把一份库存拆成多份分散到多个 key）提升并发。答题时按「流量入口 → 缓存层 → 异步层 → 存储层 → 兜底」讲，比堆名词清楚。

**接口 RT 从 50ms 涨到 2s**：先看是全线还是个别接口，再按依赖分段——应用自身（GC、线程池满、连接池耗尽、锁竞争）、下游（数据库慢查询、缓存命中率下降、第三方超时）、流量（突增、热点数据）、发布（配置或版本变更）。工具链是监控与链路追踪定位到那段耗时，再 `jstack`、`jstat`、慢查询日志、连接池指标逐层看。要给出「先止血后定位」的顺序：限流、回滚、扩容可以立刻做，根因分析随后。

**CPU 100%**：`top -Hp` 找线程，线程 id 转十六进制后在 `jstack` 里定位栈，区分是业务热点循环、GC 线程（说明内存问题）、还是正则回溯 / 序列化这类隐藏开销。若是 GC 导致，转去看 GC 日志与堆；若是业务代码，看是否有死循环、频繁创建对象、锁自旋。

**百万数据导出**：不要一次性 `SELECT *` 到内存。流式查询（JDBC 游标 / MyBatis `ResultHandler`）、按主键分页或分片并行、边查边写（SXSSF 这类流式 Excel 写、CSV 流式输出）、限制单次导出量并走异步任务 + 下载链接。要提防「分页越翻越慢」（`LIMIT offset` 深分页），改用游标式 `WHERE id > ?`。

**短链与高可用**：发号（自增、号段、雪花）后做 62 进制转换，或用哈希 + 冲突重试；存储用 KV，读多写少可以加多级缓存；跳转用 302 便于统计，301 减少服务端压力；高可用靠多副本、缓存兜底与限流；防滥用要有域名黑名单与频控。扩展问题通常落在「同一个长链要不要复用同一个短码」与「统计怎么做」。

**订单超时关闭**：定时扫表最简单但有延迟与压力；延时消息（RocketMQ 延时级别、RabbitMQ 死信队列）精度较好；Redis 过期监听不可靠（过期事件不保证及时）；时间轮适合海量短延时任务。无论哪种，关闭前必须再校验订单状态，避免与支付回调竞争——用状态机 + 乐观锁保证只有一方成功。

**登录态管理**：Session 集中存储（Redis）或 JWT 无状态令牌；JWT 的注销与续期需要额外机制（黑名单、短过期 + refresh token）；多端登录要设计互斥或并存策略；网关统一校验，业务服务只信任网关注入的身份。要讲清「无状态换来的代价是不能主动失效」。

**热点 key**：先发现（代理层或客户端统计、Redis `MONITOR` 采样、`hotkeys` 命令），再分散——本地缓存挡一层、key 加随机后缀拆成多个副本、读写分离到多个从节点、必要时把热点数据下沉到业务侧做聚合。要注意「加后缀」只对读有效，写场景会造成一致性复杂度。

**无损发布**：注册中心先摘流再停进程、优雅停机（处理完在途请求、关闭线程池）、就绪探针与存活探针分离、连接池与长连接要主动排空、数据库变更用兼容式双写或扩展字段。灰度与快速回滚是配套手段，发布窗口避开业务高峰。

**支付回调系统的核心模块**：接入层（验签、幂等、限流）、订单状态机（合法流转与并发控制）、回调处理（异步化、失败重试与退避、死信）、对账（与渠道账单定时比对、差错处理）、通知下游（可靠消息 + 幂等）、可观测（成功率、延迟、差错告警）。要强调「回调不可信」：可能重复、乱序、延迟甚至丢失，所以既要幂等，也要有主动查单兜底。

**场景题的答题结构**：结论先行（我会先限流、异步削峰、Redis 预扣库存），再讲原理与替代方案，然后落到细节（key 设计、过期策略、失败补偿），最后主动说风险（超卖、热点 key、Redis 宕机）。没有唯一标准答案，面试官看的是「有没有结构、有没有边界意识、能不能落到工程细节」。
