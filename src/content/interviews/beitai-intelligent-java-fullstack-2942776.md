### 《参考解析》

**WMS 的业务闭环**：入库侧（预约、收货、质检、上架）与出库侧（订单下发、库存分配、波次、拣选、复核、打包、发运）构成主链路。系统间的闭环通常是：上游 ERP/OMS 下发出库单 → WMS 做库存预占与任务拆分 → 生成拣选任务并调度设备 → 通过接口向 WCS 下发搬运/分拣指令 → WCS 执行后回调执行结果 → WMS 更新任务与库存状态 → 回传上游发货结果。数据获取靠接口（订单、库存）与设备事件（扫码、光电、称重），下发靠 HTTP/RPC 或消息队列。

**回调失败怎么处理**：核心是「不能丢、不能重、不能乱」。设计上分四层：一是可靠投递，下发时写本地消息表或事务消息，保证业务与消息一致；二是确认与重试，回调带唯一业务号做幂等，失败按指数退避重试并设上限；三是兜底对账，定时任务扫描长时间未回调的指令，主动查询 WCS 状态或转人工；四是告警与可观测，记录每条指令的下发时间、重试次数、最终状态。若 WCS 长时间不可用，要有降级策略（暂停下发、切人工通道、限制新任务进入）。

**自己设计失败处理链路**：先定义状态机（待下发、已下发、执行中、成功、失败、超时、已取消），每个状态迁移都要有触发条件与幂等键；再定重试策略（哪些错误可重试、哪些直接失败、最大次数与间隔）；然后是补偿（自动补偿任务 + 人工干预入口）；最后是监控指标（下发成功率、回调时延、超时率、积压量）。如果让我实现，会用消息队列做异步解耦、用状态机驱动流转、用定时任务做超时扫描，所有外部调用都带幂等与超时。

**Redis 在项目里的用法**：常见四类——缓存（热点数据、字典表）、分布式锁（避免重复下发或并发修改）、计数器与限流（接口调用量、库存扣减的预校验）、会话与临时状态（登录态、任务的中间状态）。回答时要说明具体 key 的设计、过期策略与一致性处理，而不是只列用途。

**雪崩、穿透、击穿**：雪崩是大量 key 同时过期或 Redis 宕机导致请求全打到数据库，解决靠过期时间加随机、多级缓存、熔断降级与集群高可用；穿透是查询不存在的数据，缓存不命中每次都打库，解决靠空值缓存、布隆过滤器与参数校验；击穿是单个热点 key 过期瞬间大量并发回源，解决靠互斥锁重建、逻辑过期与热点永不过期。三者容易混淆，答的时候先把定义分清再讲方案。

**AI 编程的看法与人角色**：比较客观的说法是：AI 在样板代码、单测、脚手架、日志分析与文档上提效明显，但在需求理解、架构取舍、边界条件、性能与安全上仍需要人判断；风险在于生成代码的隐蔽错误与依赖引入。人的角色是定义问题与验收标准、做设计与技术选型、review 关键路径、并对上线结果负责。面试官追问「人充当什么角色」，想听的是你有没有把 AI 当工具而不是替身。
