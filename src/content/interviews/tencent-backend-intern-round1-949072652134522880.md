### 《参考解析》

**手撕最长无重复子串**：滑动窗口加哈希表记录字符最近一次出现的位置。右指针扩张时，若字符已在窗口内，左指针跳到「该字符上次位置 + 1」，同时更新最大长度。复杂度 O(n)，空间 O(字符集)。注意左指针只能右移不能回退，否则会算错。

**JDK 17 的选型理由**：17 是 LTS 版本，支持周期长；相比 8 有 ZGC、G1 的成熟改进、密封类与 record 等语言特性、以及更强的容器感知（`UseContainerSupport` 默认开启）。回答时补一句「升级的主要成本在依赖兼容与反射相关框架」，比只说「17 新」完整。

**HashMap 的并发死循环**：JDK 7 的头插法在扩容时会把链表顺序反转，两个线程同时扩容就可能让链表形成环，之后 `get` 遍历到环上会无限循环、CPU 打满。JDK 8 改成尾插法并引入红黑树，成环问题消失，但并发写仍会丢数据、size 计数错误，所以它依然不是线程安全的。要说明「JDK 8 修的是成环，不是并发安全」。

**ConcurrentHashMap 的实现**：JDK 7 用分段锁（Segment 继承 ReentrantLock）；JDK 8 改为 CAS + synchronized 锁单个桶的头节点，扩容时支持多线程协助迁移（`transfer`），size 用 `baseCount + CounterCell` 分散计数。读操作基本无锁，靠 volatile 保证可见性。

**元空间的升级背景**：JDK 8 用元空间取代永久代，把类的元数据移到本地内存。永久代的问题是大小固定、难以预估，动态生成类多（反射、CGLIB、JSP）时容易 `PermGen space` OOM；元空间默认不设上限（受本地内存约束），并可通过 `MaxMetaspaceSize` 控制，同时把字符串常量池移到了堆里。

**两个栈为什么分开**：虚拟机栈执行 Java 方法，本地方法栈执行 native 方法，两者在规范上是不同区域，便于分别设置大小（`-Xss`）与分别统计；HotSpot 把两者合并实现，但规范保留区分。Java 运行时确实会嵌入 C/C++：JVM 本身由 C++ 实现，native 方法通过 JNI 调用本地库，`Unsafe`、NIO 的 DirectBuffer 也都落在本地内存。

**内存泄漏的常见场景**：静态集合持有对象、缓存无淘汰策略、ThreadLocal 未 `remove` 导致线程池里的线程一直持有、监听器与回调注册后未注销、连接或流未关闭、`equals` 与 `hashCode` 实现不一致导致集合里「查不到也删不掉」。

**RAG 与索引追问**：RAG 解决的是「模型不知道私有或最新知识」与「生成缺乏依据」两个问题，链路是文档切分、向量化、检索、拼进上下文再生成。Faiss 常用 `IndexFlatL2`（精确、适合小规模）与 `IndexIVFFlat`（倒排加聚类，需要训练，适合大规模），规模到百万级要考虑量化索引（PQ）。倒排索引之所以叫「倒排」，是因为它从「文档到词」反转为「词到文档列表」，用词快速定位包含它的文档。文本切分按固定长度、按段落或按语义边界，需要设置重叠窗口避免把一句话切断。
