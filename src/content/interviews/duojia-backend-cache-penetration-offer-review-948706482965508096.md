### 《面试题目》

1. 有恶意请求一直查不存在的 ID，会发生什么？
2. 那你怎么解决？
3. 空值的 key 如果每天有几百万个不同的随机 ID，Redis 内存怎么办？
4. 你说用布隆过滤器，那数据新增了怎么加进去？删除了怎么办？
5. 布隆过滤器说「存在」但实际不存在，这个误判你怎么兜？
6. 缓存穿透、缓存击穿、缓存雪崩有什么区别？
7. 如果让你落地，会怎么分层设计？

### 《参考解析》

**穿透的核心矛盾是「查不到」无法证明「不存在」。** 任何缓存都拦不住随机 ID，因为缓存只能记录「查过什么」，不能枚举「可能存在什么」。空值缓存是把「不存在」也变成一种缓存内容，布隆过滤器则是把判断提前到缓存之前。

**空值缓存的有效性取决于 ID 空间。** 如果 ID 是自增的，攻击者随便编就能绕过；如果 ID 是雪花算法生成的长整型，随机碰撞概率极低，空值缓存就非常有效。所以这一招不是万能，要看 ID 的生成方式。内存问题有两条缓解：空值 TTL 压短（几十秒足够挡住瞬时重复请求），以及对同一 IP 的异常查询在网关层限流。

**布隆过滤器的三个现实问题。** 一是只能加不能删，商品下架后旧数据还在里面，误判率会随时间上升，标准实现不支持删除，只能用计数布隆或定期重建；二是定时全量重建存在窗口期，新写入的数据会漏，需要双 buffer 切换避免「过滤器为空、所有请求放行」；三是误判率随元素数量增长，容量要按预估峰值留余量，不能按当前量配置。

**误判的兜底很轻。** 布隆过滤器只有假阳性、没有假阴性：它说不存在就一定不存在，说存在可能是误判。误判的代价只是一次多走的数据库查询，只要数据库前面还有连接池与限流兜着，不会造成雪崩。这也是它适合放在最前面的原因——用极低的成本挡掉绝大多数确定不存在的请求。

**分层落地的参考实现。** 参数校验（非法 ID 直接拒绝，不进缓存）→ 查缓存（命中空值标记直接返回）→ 布隆过滤器（判定不存在则写入短 TTL 空值并返回）→ 回源加互斥锁（防止同一 key 并发击穿，失败重试要有次数上限）→ 写回缓存（空值短 TTL，正常数据长 TTL）→ 释放锁。要说明每层的失效条件：空值缓存怕随机 ID 刷内存、布隆过滤器怕更新窗口、互斥锁怕锁超时与死锁。

**三个概念要分清。** 穿透是 key 本身不存在，缓存与数据库都没有；击穿是单个热点 key 过期瞬间，并发全部打到数据库；雪崩是大量 key 同时过期或 Redis 整体不可用，流量整体打穿。解法不通用：穿透用参数校验、空值缓存、布隆过滤器；击穿用互斥锁重建、逻辑过期；雪崩用 TTL 打散、多级缓存、熔断降级。

**这次被问住的根子不在知识点。** 作者复盘说：所有回答都停在「应该这么做」，没想过「这么做的代价是什么」。空值缓存的内存成本、布隆过滤器的更新窗口、重建期间的一致性问题，才是面试官真正在测的东西。给每个方案补一句「它在什么情况下失效、失效后靠什么兜底」，是最省力的准备方式。
