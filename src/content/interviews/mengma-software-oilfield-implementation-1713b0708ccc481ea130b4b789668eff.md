### 《面试题目》

1. 自我介绍。
2. 什么时候毕业？实习是在校还是别的？几年制学历？学校位置在哪，家在哪？
3. 你的民族是什么？工作地在新疆你怎么考虑？
4. 大数据专业的专业课学得怎么样？
5. Spark 和 Hadoop 分别是什么场景用的？
6. 实习项目的业务场景和业务情况是什么？设备是干嘛用的？
7. Postman 怎么测接口？
8. 返回值是 401 或者 403 怎么处理？
9. 写过哪些文档？
10. 你对油田现场驻场的理解和认识是什么？
11. 驻场现场是多项目并行的，当项目出现多个问题，你怎么安排优先级、怎么沟通？
12. 后端支撑场景下，你作为现场第一技术人员，内部沟通时出现了问题，你会用什么样的形式呈现？
13. 你有什么想问的吗？（问的是岗位发展路径）
14. 期望薪资。

### 《参考解析》

**实施岗面试的第一道筛子是「你会不会真的来、能不能待住」，不是技术。** 所以前半程的问题全都指向同一个判断：毕业时间能否对上项目排期、学校与家庭位置离工作地多远、能不能接受长期驻场（帖子里明确问到了新疆）、民族与生活习惯是否涉及现场安排。这类问题没有标准答案，但答法有讲究——给出确定的日期与范围，比说「都可以」可信得多；对驻场要表达真实的理解（工作地随项目走、现场节奏由客户和工期决定、需要长期在外面）而不是口号式的「我不怕吃苦」。面试官在意的是招进来三个月就走的成本，所以稳定性表达要落到具体事实上（家庭支持、过往在外实习经历、对工作地已做过了解）。

**Spark 与 Hadoop 的场景区分是这轮唯一的大数据八股。** 标准答法是按「计算模型 + 适用场景」对比：Hadoop 生态里 HDFS 解决分布式存储、MapReduce 解决磁盘批处理，适合超大规模、能容忍高延迟的离线任务，一次计算落一次盘；Spark 用内存做 RDD/DAG 计算、支持迭代和多轮复用，适合迭代式算法、交互式查询和批流一体的任务，速度优势主要来自减少磁盘 IO。说清「数据量不大、时效要求高的场景反而不该上 Spark」这种反例，比背参数更能显示理解。实施岗的追问一般会落到实际项目：数据从哪来、跑多久、出问题怎么排查。

**Postman 测接口要答到「可复用、可回归」，而不是点一下 Send。** 完整说法是：先建 Collection 按模块分组，用环境变量管理不同环境的 base URL、token、租户参数；请求层面配好 method、path、header（`Content-Type`、鉴权头）、body（JSON/表单）和前置脚本（登录拿 token 后写入环境变量）；断言写在 Tests 里，校验状态码、响应字段、业务码而不只是看 200；多个请求之间的取值用变量传递；最后用 Collection Runner 批量跑或导出给同事回归。实施岗问这个，本质是在确认你到了客户现场能不能自己验证「接口通不通」，因为很多现场问题的第一现场判据就是接口。

**401 与 403 是两类完全不同的故障，处理动作不能混。** 401 是未认证：token 缺失、过期、被顶号，或者是请求头没带对——处理是重新登录/刷新 token、检查鉴权头与环境变量，然后重放请求。403 是已认证但无权限：账号没有该资源或该接口的授权，或者是 IP/白名单限制、签名不对、账号被停用——处理是核对账号角色与授权范围、找管理员开权限，反复重试没有意义。现场实施的正确姿势是：先看响应体里的业务码与错误信息（很多系统会在 401/403 里返回具体原因），能自己解决就解决，涉及权限变更的一律走客户方的授权流程并留下记录，别自己改配置绕过去。

**多项目并行的优先级，要给出可解释的排序规则而不是「按重要程度」。** 现场常见的排序依据是几条的组合：影响面（是否阻断客户核心业务、影响多少用户）＞ 时间承诺（客户有没有对外承诺的节点）＞ 可绕过性（有没有临时替代方案）＞ 解决成本。判完给出明确的处理顺序和预期时间，同时做两件最容易漏的事：一是把并行的问题统一登记（一张清单，谁报的、影响什么、当前状态、负责人），避免口头承诺散落各处；二是主动升级——超出自己权限或时间窗的问题要按约定路径上报给后端或项目经理，不能捂着。面试官问「怎么沟通」，想听的就是登记、同步、升级这三件事。

**「内部沟通出问题用什么形式呈现」考的是书面化能力。** 现场第一技术人员的角色是客户与研发之间的翻译器，所以呈现要区分对象：给后端的应该是可复现的技术描述（环境、账号、接口、请求参数、响应、日志、时间点），给项目经理的应该是影响与时间（影响哪个客户的哪个流程、什么时候必须解决、有没有临时方案）。形式上一律落成书面（工单、邮件、群消息带结构化模板），口头沟通完要补一条记录，因为现场问题的责任边界最容易在执行中模糊。附带说一句追问常客：出问题先止损再定位，客户侧先用替代流程保证业务不断。

**写过的文档要有名字。** 实施岗的文档产出通常是这几类：需求确认单、实施方案/部署手册、接口与联调记录、测试记录与缺陷清单、用户操作手册、验收报告、运维交接记录。答的时候报真实写过的种类和大致篇幅即可，如果写过的不多，就说清你在项目里实际整理过什么（比如把客户提的问题整理成清单并附复现步骤），比硬凑文档类型好。

**驻场的理解要答「做什么」而不是「多辛苦」。** 可以按三类职责讲：上线与交付（环境部署、数据初始化、接口联调、验收配合）、运维支撑（日常巡检、问题响应、版本升级）、客户关系（需求收集与反馈、培训与答疑、把客户的口头诉求转成可执行的需求）。现场与研发的区别在于「你是客户看到的那张脸」，所以响应速度和沟通质量本身就是交付的一部分。

**原帖给出的岗位发展路径信息**：试用期 3 个月，有专门的指导老师带着熟悉技术框架、业务和项目；技术路线可以从技术运维、技术研发走到 FDE/AI 实施顾问、项目经理、产品经理。团队划分上，整个技术组十二三个人，其中有两三个业务人员，技术人员是主力，测试一般由业务和技术共同承担，业务主要负责与客户沟通对接。这类信息最好在反问环节主动问清（转正标准、驻场周期与轮换机制、奖金与差旅标准），因为它们直接决定这份工作干不干得下去。期望薪资的回答原则是先给一个区间再给依据（当地实施岗的行情、自己的实习与技术能力、驻场性质带来的额外付出），不要只报一个数字然后被压。
