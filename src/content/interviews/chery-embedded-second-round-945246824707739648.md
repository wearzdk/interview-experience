### 《面试题目》

1. 简单介绍一下你最近做的嵌入式项目，以及你负责的模块边界？
2. 如果 Flash 里程序偶尔跑飞或跑到未知地址，你会怎么排查？
3. 讲一下从复位到 main 的启动过程，你项目里 Boot 和应用是怎么衔接的？
4. volatile 和 const 有什么区别？什么场景必须用 volatile？
5. FreeRTOS 里队列、信号量、事件组分别适合什么场景？
6. CAN 总线仲裁怎么工作？如果节点一直发高优先级报文会有什么影响？

### 《参考解析》

**开场那道「模块边界」，是在给你的技术信用定价**

答成「我写了驱动」就浪费了。顺序是：项目目标、硬件平台、系统架构，再明确自己负责哪块（驱动、通信、应用逻辑还是诊断），接着说和其他人的接口——输入什么、输出什么、时序要求、验收标准，最后一句给结果：有没有上车验证、指标是否达标。接口和验收标准是关键，它把「我写了一段代码」变成「这段要在 10 ms 周期内完成采样并通过 CAN 上报，超时算失败」，难度和你的位置一下就清楚了。

**程序跑飞：先分型，再顺证据链倒推**

三类排查路径不同：硬 Fault、看门狗复位、跳到非法地址后的 SoftFault。然后看证据：复位原因寄存器、Fault Status、出错瞬间的 PC/LR 与栈内容——PC 指向哪、LR 说明从哪跳来，能区分空指针、栈溢出和函数指针被改坏。再查静态配置：向量表与重定向、启动文件、链接脚本的段地址、中断优先级分组、任务栈大小。再查动态破坏：DMA 越界、中断里改坏全局变量或函数指针。最后用复现路径收敛：上电必现、跑久才现（更像内存踩踏或泄漏）、还是特定业务触发（更像并发）。加分点是让人看到你按证据走，不是靠猜和反复重启。

**从复位到 main，以及 Boot 与 App 的边界**

复位后从向量表取复位向量、初始化 MSP，进 Reset_Handler；启动文件把 .data 从 Flash 搬到 RAM、清 .bss，然后才到 main。有 Bootloader 时多一层：判断升级标志、校验应用区完整性（CRC 或签名）、确认无误再跳 App。两者要约定四件事——分区地址、向量表重定向（App 里设 VTOR）、共享参数区、升级失败的回滚。跳转前关中断、清外设现场，跳过去后 App 重新初始化时钟和外设。最常见的 bug 是 Boot 开了外设没关，App 初始化时状态不对。

**FreeRTOS 四种原语，按「传什么、等什么」选**

传数据用队列（拷贝传值、可缓存多条、自带阻塞唤醒），单纯通知用二值信号量，数资源用计数信号量，保护临界资源用互斥量——它带优先级继承，能缓解优先级反转，这才是这题真正的考点。多个条件要同时满足才继续，用事件组。任务通知比信号量更省，但只能一对一。

**两个容易被追到底的基础题**

volatile 管「编译器不许把它缓存进寄存器、不许合并或重排读写」，const 管「这段代码不许改它」，两者正交，`volatile const` 就是只读寄存器。必须用的场景：外设寄存器、中断里改而主循环读的标志位、DMA 目标缓冲区。但要说明它不给原子性和内存序，复杂共享数据仍要靠临界区，否则会被追一句「加了 volatile 就线程安全了吗」。CAN 仲裁是 ID 逐位比较、显性位覆盖隐性位，ID 小的赢，输的节点退出发送转为接收、等总线空闲自动重试，所以仲裁本身不破坏报文。追问「一直发高优先级会怎样」，答案是低优先级报文被持续推迟甚至饿死、实时性失效；解法是按周期与截止时间分配 ID、对发送限流。
