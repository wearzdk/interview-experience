### 《参考解析》

**RR 与幻读**：InnoDB 在 RR 下用 MVCC 快照读 + 间隙锁（Next-Key Lock）应对幻读。快照读在事务第一次读时生成 ReadView，之后一直用同一份快照，所以看不到别的事务新插入的行；当前读（`SELECT ... FOR UPDATE`、`UPDATE`、`DELETE`）靠间隙锁阻止范围内插入。因此「完全避免」要分读法：快照读不会幻读，当前读靠锁也不会，但两种读法混用、或先快照读再当前读，仍可能看到新数据。串行化才是彻底方案，代价是并发度。

**Kafka 重复消费**：消费端至少一次投递，重复不可避免，幂等要落在业务侧。用消息里的业务唯一键（订单号、请求 ID）建唯一索引或写去重表，处理与落库在同一事务里；Redis `SETNX` 可做前置拦截但不能作为唯一保障。消费逻辑本身要可重入：状态机按「当前状态 → 目标状态」判断，而不是无条件累加。

**库存放 Redis**：活动场景的扣减是高频、强并发的短事务，MySQL 行锁会把请求排成队列，热点行还会放大锁等待。Redis 单线程执行 + Lua 脚本能把「判断 + 扣减」做成原子操作，QPS 高一个量级。代价是要处理与 MySQL 的最终一致：预扣成功后异步落库，失败要有可追踪、且本身幂等的补偿，否则重复回补会把库存补多。

**RAG 还是微调**：活动规则、退订政策这类知识问答优先 RAG——内容更新频繁，微调每次都要重训且不一定记住最新版本。RAG 要做好文档切分粒度、召回质量、重排序与出处可查。实时数据（订单状态）不能靠 RAG，应通过 Function Calling 调后端接口查询；涉及修改还要加身份校验与权限控制。微调适合固定风格与领域表达，不适合承载会变的业务事实。

**Lua 锁与 Redisson**：原生方案是 `SET key value NX PX` 加锁，释放时用 Lua 比对持有者再删除，避免误删别人的锁。难点在锁过期：业务执行 15 秒而锁只有 10 秒，锁会被别人拿走，互斥性被破坏。Redisson 提供 Watchdog 自动续期、可重入、等待通知，业务代码简单很多。但长时间 GC、网络分区下旧线程仍可能继续执行，涉及资金与关键库存还要靠数据库条件更新、版本号或 Fencing Token 兜底。

**@Transactional 失效**：常见原因有四类——同类内部 `this` 调用绕过代理；异常被捕获未抛出，拦截器认为正常结束而提交；抛的是受检异常，默认不回滚（需 `rollbackFor`）；方法不是 public 或类未被 Spring 管理。线程池里异步执行时事务上下文不会传播，也要单独处理。

**索引失效与判断**：对索引列做函数计算或隐式类型转换、联合索引不满足最左前缀、`LIKE '%abc'` 前置模糊，都可能用不上索引。不能机械套结论，要看版本、数据分布与执行计划：先 `EXPLAIN` 看访问类型、实际索引、预估行数与是否额外排序，必要时 `EXPLAIN ANALYZE` 看真实耗时。判断标准不是「有没有走索引」，而是扫了多少行、回表多少次。

**消息积压**：先分清是生产突增还是消费变慢。看消费者组 Lag、生产与消费速率、消费者日志。流量没变而 Lag 持续涨，多半是消费端依赖变慢（慢 SQL 最常见），此时加消费线程只会把数据库压垮。瓶颈确在计算能力再扩实例，但有效并行度受分区数限制。还要排查反复重试的异常消息，用重试 Topic、死信队列与人工补偿避免一条坏消息阻塞整个分区。

**多 Agent 通信**：同进程内可以直接方法调用或用框架的编排机制；跨服务用 HTTP、gRPC 或消息队列；A2A 面向 Agent 互操作，MCP 规范的是模型与工具、数据源的集成，两者关注点不同。真正的难点不是把消息发出去，而是维护任务 ID、上下文、超时与失败重试——子 Agent 失败后主 Agent 要能判断重试、换工具还是交还用户，而不是无限等待。

**重复下单**：前端防抖只是体验优化。后端设计幂等键：预约请求 ID，或按业务规则用「用户 ID + 活动 ID」建联合唯一索引兜底。超时不能直接判失败，服务端可能已创建成功只是响应丢了，所以要保存请求与订单状态的对应关系，重试时返回首次结果。Redis 只能降低并发冲突，最终正确性靠数据库约束与事务。

**预扣库存与超卖**：关键是不能把「检查」和「扣减」拆成两步——`GET` 判库存再 `DECR`，两个请求会读到同一份库存。用 Lua 脚本原子执行判断与扣减。预扣成功后要可靠记录并推动异步落库；Kafka 积压时用户看到的是「处理中」而不是「预约成功」，所以要有明确的预约状态与积压监控，消费者保持幂等。最终写库失败要有补偿任务恢复库存，补偿本身也必须幂等。

**死锁定位**：典型成因是多个事务以相反顺序锁多张表（A 先订单后库存，B 先库存后订单）形成循环等待。InnoDB 有死锁检测，发现后回滚其中一个事务。线上先看 `SHOW ENGINE INNODB STATUS` 的 LATEST DETECTED DEADLOCK 段，拿到两个事务的 SQL、持有与等待的锁；再结合应用日志定位代码。解法是统一加锁顺序、缩短事务、给条件更新加合适索引减少锁范围，并在业务层对死锁错误做有限重试。
