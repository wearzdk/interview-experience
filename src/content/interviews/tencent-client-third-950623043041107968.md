### 《面试题目》

1. 讲一个你负责的客户端模块，它的边界是什么？为什么这样分层？
2. 冷启动慢，你会从哪些方面优化？怎么量化收益？
3. 页面卡顿怎么定位？主线程上的耗时怎么抓？
4. 内存泄漏和内存抖动分别怎么发现、怎么治理？
5. 崩溃率怎么降？线上崩溃怎么归因和修复？
6. 包体积过大，有哪些可行的优化手段？各自的代价是什么？
7. 弱网环境下怎么保证体验？超时、重试、缓存怎么配合？
8. 跨端方案（Flutter、React Native、原生）怎么选？你做过什么取舍？
9. 客户端怎么做灰度发布和回滚？
10. 一个功能上线后崩溃率上升，你怎么排查？
11. 客户端与服务端的接口怎么设计才不容易出兼容问题？
12. 未来想做客户端架构还是业务？为什么？

### 《参考解析》

**三面会从「做了什么」转向「为什么这样做」。** 同样的优化项，初级答法是罗列手段（预加载、懒加载、图片压缩），高级答法是给出定位过程、收益数字与代价：优化前多少、优化后多少、用什么工具测的、引入了什么复杂度或维护成本。准备两三个真正做过的案例，把数据与取舍讲透，比覆盖十个方向更有说服力。

**启动优化**分阶段：进程创建与 Application 初始化、首页渲染、数据请求。先埋点拿到各阶段耗时（冷启动到首帧、到可交互），再按「必须同步」与「可以延后」拆分初始化任务，能异步的放线程池、能懒加载的延到首屏之后、能合并的合并；类加载与资源解码是常见大头，可以用启动基线 profile、资源预加载、减少反射。收益以「首帧时间」「可交互时间」衡量，并说明对内存与电量的影响。

**卡顿定位**：主线程上的耗时操作是根因，手段包括 BlockCanary 一类的 Looper 监控、Choreographer 帧回调、系统 trace（Perfetto / systrace）与线上帧率采样。常见问题是大图解码、复杂布局、频繁 GC、锁竞争、同步 IO。优化方向是减少布局层级、异步加载、对象复用、把重计算移出主线程；同时要防止「为了不卡而到处开线程」带来的调度与内存问题。

**内存**：泄漏用 LeakCanary 或 MAT 查引用链，常见来源是静态持有 Activity / Context、未注销的监听器、线程与 Handler、匿名内部类；抖动来自频繁创建临时对象（字符串拼接、循环内建集合、图片反复解码），治理靠对象池、复用、减少装箱。线上看内存水位、GC 次数与耗时、OOM 率。

**崩溃治理**：先分类（Java / Native / ANR / 启动崩溃），再看 Top 崩溃的堆栈与设备分布，区分是自身代码、系统兼容还是三方 SDK。修复路径是复现、定位、修复、灰度验证；无法立即修复的用开关降级。指标看崩溃率（崩溃设备数 / 活跃设备数）与用户影响面，而不是只看总量。

**包体积**：资源压缩与混淆、移除无用资源与重复依赖、图片格式与按需下发、so 裁剪与动态加载、代码混淆与 R8、插件化拆分。每个手段都有代价：动态下发增加复杂度与合规风险，插件化影响启动与稳定性，so 裁剪要覆盖机型。回答时说明你的取舍依据。

**弱网体验**：连接复用与 HTTP/2 多路复用、请求合并、超时分级、指数退避重试（仅对幂等请求）、本地缓存与乐观更新、失败态与重试入口的交互设计。指标看请求成功率、P95 耗时、白屏率，而不是只看平均值。

**跨端选型**：原生性能与系统能力最好，但双端成本高；Flutter 渲染一致、性能接近原生，但包体积与原生混合成本高；React Native 开发效率高、动态性强，但复杂交互与性能敏感场景受限；Hybrid 适合内容型页面。选型看团队规模、迭代频率、性能要求、是否需要动态发布，以及长期维护成本。

**灰度与回滚**：按用户 ID / 设备 / 地域分批放量，配置与代码分离，关键功能带开关；监控崩溃率、核心转化、接口错误率，设定自动止损阈值；回滚要能在不发版的情况下完成（开关、配置、热修复），否则灰度失去意义。

**上线后崩溃率上升的排查**：先确认影响版本与机型分布，对比灰度组与对照组的崩溃堆栈，检查本次改动的初始化顺序、权限、三方 SDK 升级、so 加载；必要时关闭开关止血，再定位。

**接口兼容**：字段只增不删、提供默认值、版本号与灰度、客户端对未知字段容错、服务端不依赖客户端的严格校验。老版本客户端会长期存在，接口设计要按「至少兼容 N 个版本」来考虑。

**职业方向**：无论选架构还是业务，都要给出具体理由与近期动作（补哪块能力、想解决什么问题）。三面面试官更在意你是否清楚自己要什么，而不是答案本身。
