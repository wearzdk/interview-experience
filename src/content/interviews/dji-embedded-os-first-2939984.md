### 《参考解析》

**硬实时与软实时**：硬实时是「错过截止时间就是失败」，例如电机控制环、传感器同步采样、安全相关的急停；软实时是「偶尔延迟可接受，但平均要快」，例如视频编码、UI 刷新、日志上报。判断依据是业务后果，不是时间长短。Linux 默认不是硬实时（调度与中断关闭区不可控），要硬实时通常用 RTOS（FreeRTOS、RT-Thread、Zephyr）或 Linux + PREEMPT_RT + 隔离 CPU 核。

**Linux 与 RTOS 的选型**：Linux 生态完整（文件系统、网络、驱动、AI 推理框架），适合做「大脑」——图像处理、网络、复杂业务；RTOS 确定性强、资源占用小，适合做「小脑」——电机控制、传感器采集、实时通信。常见架构是异构：RTOS 核跑实时任务，Linux 核跑应用与算法，两者通过共享内存 / RPMsg / 核间中断通信。选型时讲清楚「哪些任务必须确定性、哪些可以容忍延迟」。

**启动流程**：上电 → BootROM（固化代码，加载 SPL/一级引导）→ SPL/U-Boot（初始化 DDR、时钟、串口，加载内核）→ 内核解压与 `start_kernel`（初始化内存管理、调度、驱动模型）→ 挂载 rootfs → init 进程（systemd/busybox init）→ 用户态服务与应用。要能说出设备树在这一步的作用：U-Boot 把 dtb 传给内核，内核据此注册 platform device，匹配驱动。

**内核裁剪**：去掉不需要的驱动、文件系统、网络协议、调试符号，减小镜像体积、缩短启动时间、降低攻击面与内存占用。做法是用 `menuconfig` 关掉用不到的模块，或用 `make localmodconfig` 按当前硬件自动裁剪；裁剪后要验证功能不缺失（外设、文件系统、网络），并注意保留必要的依赖（比如某个驱动依赖的子系统）。

**设备树**：描述硬件的「数据」而不是代码。新外设要在对应节点里写 `compatible`（用于匹配驱动）、`reg`（寄存器地址与长度）、`interrupts`（中断号与触发方式）、`clocks`、`pinctrl`（引脚复用）、`dmas`、电源域等，还要在 `status` 里置 `okay`。`compatible` 是最关键的——驱动靠它匹配。

**驱动与用户态通信**：`ioctl` 适合命令式的控制与少量参数；`sysfs`/`procfs` 适合暴露状态与简单配置（可读可写文件）；`mmap` 适合共享大块内存（帧缓冲、DMA buffer）；`netlink` 适合异步事件；`read/write` 适合流式数据。选择依据是数据量、方向（控制 vs 数据）、是否需要异步通知。

**系统卡死的排查**：先看现象——完全无响应、串口有没有输出、看门狗有没有复位、`top` 里 CPU 是否 100%、`dmesg` 有没有 oops/panic。确认不是应用问题的方法：用串口或 JTAG 看内核是否还在调度（`SysRq` 的 `show-blocked-tasks`、`show-registers`），看是否有软锁检测（`soft lockup`）、硬锁（`hard lockup`）、RCU stall 的打印；如果内核日志停在某个驱动调用，基本可定位到内核/驱动；用 `perf`/`ftrace` 看最后执行的函数；用 kdump 抓 vmcore 分析调用栈。

**周期性丢帧定位**：先量化——丢帧发生在采集、传输、处理还是显示；看时间戳间隔是否均匀、队列是否溢出、CPU 占用与频率是否抖动、内存带宽是否打满、温度是否触发降频。工具：`ftrace` 跟踪调度与中断延迟、`perf stat` 看 cache miss 与上下文切换、`vmstat` 看 IO 等待、`dmesg` 看驱动报错。常见原因：中断延迟、锁竞争、内存拷贝过多、DMA buffer 不够、算法单帧超时。

**性能工具**：`top` 看整体 CPU/内存与进程占用；`vmstat` 看上下文切换、运行队列、swap、IO；`perf` 做采样分析找热点函数、统计 cache miss 与分支预测；`ftrace` 跟踪内核函数调用与调度延迟（`function_graph`、`irqsoff`、`sched_switch`）。回答要带「我用它定位过什么问题」。

**mmap**：把文件或设备内存映射到进程地址空间，读写内存即读写文件/设备，省掉 `read/write` 的内核态拷贝。图像场景里，摄像头驱动把 DMA buffer 映射给用户态，算法直接在这块内存上处理，避免「驱动拷到用户态再拷进算法」的两次拷贝；配合 `VIDIOC_QBUF/DQBUF` 做零拷贝采集。

**页缓存**：内核把读写的文件页缓存在内存里，读命中直接返回，写先写缓存、由回写线程刷盘（`dirty_ratio` 控制阈值）。大量写文件的问题：脏页堆积导致回写时 IO 抖动、内存被页缓存占满触发回收、突然断电丢数据（未 fsync）、`write` 返回成功不代表落盘。嵌入式场景要控制脏页比例、必要时用 `O_DIRECT` 或 `fsync`，并注意 flash 寿命。

**中断上半部与下半部**：上半部（hardirq）在关中断上下文执行，要极快——只做「确认中断、读状态、清标志、把工作排进下半部」；下半部（softirq/tasklet/workqueue/threaded irq）在开中断下执行耗时逻辑。tasklet 在 softirq 上下文、不能睡眠；workqueue 在进程上下文、可以睡眠，适合需要 IO 或锁的操作；threaded irq 把中断处理线程化，可被调度与优先级控制。放错地方的典型后果是中断延迟变大、系统卡顿。

**共享内存的一致性**：多进程共享一块内存时，要解决「同时读写」与「读到一半被改」。手段：互斥锁（`pthread_mutex` 配 `PTHREAD_PROCESS_SHARED`）、信号量、原子操作（`std::atomic` + 内存序）、无锁环形队列（单生产者单消费者用 head/tail 指针 + 内存屏障）、双缓冲 + 序号（写完切换指针）。要说明「为什么不用普通变量」——编译器与 CPU 都会重排，必须用屏障或原子类型。

**采集到算法端的 buffer 设计**：典型是「多缓冲池 + 环形队列」：驱动侧维护 N 个 DMA buffer（如 4~8 个），采集完成把 buffer 入队，算法侧出队处理，处理完归还。要考虑：buffer 数量与大小（按帧率与最大延迟算）、队列满时的策略（丢最旧/丢最新/阻塞）、时间戳与帧号（用于对齐与丢帧统计）、内存对齐与 cache line（避免伪共享）、零拷贝（传指针而不是拷数据）、异常恢复（算法崩溃后 buffer 要能回收）。

**DMA 与 cache 一致性**：DMA 让外设直接读写内存，CPU 不参与搬运，可以同时做计算。问题在于 CPU cache 与内存可能不一致：CPU 写的数据还在 cache 里没落到内存，DMA 读到旧数据；DMA 写入内存后，CPU cache 里还是旧值。解决：使用一致性内存（`dma_alloc_coherent`）、在传输前后做 cache 操作（`dma_sync_single_for_device/cpu`）、或使用带 IOMMU 的平台；非一致性架构（ARM）尤其要注意。

**AI 在嵌入式里的价值与风险**：价值在「读手册与源码」「生成样板驱动代码」「分析日志与崩溃栈」「写测试脚本」「解释晦涩的寄存器位定义」；风险在「幻觉出不存在的寄存器/API」「不了解硬件时序与并发约束」「生成的代码没有考虑实时性与内存限制」「把敏感固件或原理图贴进外部模型」。边界是：AI 出草稿，人审时序与边界，所有改动上板验证。
