### 《参考解析》

**为什么有明确文档还要 RAG**：完整文档直接塞给模型有三个问题：上下文窗口有限，长文档会挤掉指令和其他材料；无关内容会稀释注意力，增加幻觉和答偏；成本与延迟随 token 线性上升，且每次重复处理同一份文档很浪费。RAG 先检索出与当前问题相关的片段，把“找信息”和“用信息回答”拆开，既降低 token，又能给答案附来源。即使输入对象明确，也需要切块，因为问题往往只涉及文档的某几节；检索的作用是定位到那几节。如果文档很短、问题覆盖全文，确实可以绕过检索直接全文输入，但要在评测里验证效果和成本。

**切分与混合检索**：按文档结构切（标题、段落、表格、代码块）比固定字数更保语义；块太大召回不准、太小丢上下文，常见做法是 300~800 字、overlap 10%~20%，再用评测集调。每个块带 doc_id、版本、章节路径、权限标签。检索用向量召回语义相近的内容，用 BM25/关键词召回专有名词、型号、编号，两路结果融合（RRF 或加权）后重排，取 top-k 交给模型。召回之后通常还要做去重、按版本过滤、按权限过滤、邻接块扩展和上下文压缩，不是直接拼接。

**知识库与版本**：搭建流程是解析（PDF 用版面分析，扫描件走 OCR）、清洗（去页眉页脚、乱码）、切分、嵌入、入库、建索引、评测。版本管理用“文档 ID + 版本号 + 生效时间”，检索时只召回当前生效版本；更新时先写新版本、灰度验证、再切别名，旧版本保留可回滚。不同版本不要默认混在一起，否则同一问题会召回互相矛盾的内容；如果业务需要对比，就在提示词里明确标注版本并让模型分别引用。

**Workflow 与框架**：工作流把任务拆成明确节点：解析、检索、重排、生成、校验、落库，每个节点有输入输出 schema、超时、重试和状态记录。用 LangGraph 这类框架的好处是状态管理和可视化，坏处是抽象层多、调试难；业务逻辑固定、节点不多时直接写编排代码更可控。是否用框架要看团队维护能力和需求变化速度，不要为了用而用。状态记录建议落一张任务表：任务 ID、当前节点、输入摘要、输出摘要、耗时、错误、重试次数，支持断点续跑和人工接管。

**Docker 与隔离**：Docker 把应用和依赖打包成镜像，部署时用 compose 或 K8s 编排；要注意镜像分层、非 root 运行、密钥不要打进镜像、数据卷持久化、健康检查和日志采集。Workspace 隔离至少三层：数据层按 workspace_id 做行级隔离或独立 schema/collection，检索时强制带过滤条件；计算层限制每个空间的并发、内存和超时；权限层做成员角色与资源鉴权。只靠前端传 workspace_id 不安全，服务端必须从登录态推导并校验。

**质量评测**：功能测试验证“流程通不通”（接口、状态、异常分支），AI 评测验证“答得好不好”（召回率、忠实度、答案相关性、任务成功率、时延与成本）。评测集要覆盖正常、边界、对抗和线上坏例；确定性部分写规则断言，语义部分用 LLM-as-judge 加人工抽检。每次改切分、模型、提示词都跑同一套评测，记录版本，避免“感觉变好了”。
