4. 介绍一下你的项目。
5. 文件上传的流程是什么，有什么注意点，做了哪些优化？
6. 你的 Agent 项目涉及了哪些能力？

### 《参考解析》

**支付流程的要点是「状态机 + 幂等 + 异步通知」**：下单生成订单号（业务单号 + 支付渠道单号）、调起支付、渠道异步回调（必须验签、必须幂等处理重复回调）、更新订单状态并发放权益（放在同一事务或用本地消息表保证最终一致）、超时未支付关单、退款走反向流程。前端侧要处理「回调回来了但页面没刷新」的情况。

**刷新页面恢复支付状态**不能只靠本地变量：页面加载时按订单号查服务端状态（这就是「以服务端为准」），凭据（token / 订单号）可以从 URL 参数或本地存储里取；若支付进行中，轮询或长连接订阅状态变化，超时给出明确提示。关键是别让用户看到「支付成功但权益没到」的空窗——用一个中间态「处理中」并在后端确认后再跳转。

**文件上传的注意点与优化**：类型与大小前置校验（前端只做体验，服务端必须再校验）、分片 + 断点续传 + 秒传（hash 比对）、并发度控制与失败重试、进度与取消、走对象存储直传（后端只签发临时凭证，避免流量过服务）、图片压缩与格式转换、CDN 加速与就近上传点。前端还要处理「关掉页面再回来继续传」的持久化。

**Agent 的记忆 / 协作 / 权限三问要分开答**：记忆分短期（上下文窗口，按轮次与 token 裁剪）、长期（用户偏好与事实抽成结构化条目存外部，检索注入）、以及任务态（执行进度写入状态存储）；协作多 agent 时用「编排者 + 专家 agent」或共享黑板，靠明确的消息契约避免互相覆盖；权限按工具分级——只读工具默认可调，写操作与外部副作用需要审批或白名单，参数要校验并把每次调用记入审计。

**RAG 切片要按文件类型区分**：Markdown / HTML 按标题层级切最自然；PDF 要先处理分栏、页眉页脚、表格与扫描件 OCR，表格单独成块或转成结构化描述；代码按函数 / 类切；Excel 按行或按 sheet 语义切。overlap 的作用是防止答案被切断，通常取块长的 10%~20%，结构化文本可以小一些、连续叙述文本要大一些；块太大召回精度下降、太小上下文不足，这是要按评测调的参数。

**向量检索 vs ES**：ES 强在倒排索引的字面匹配、过滤与聚合、以及成熟的运维生态，适合精确词、编号、过滤条件；向量检索强在语义相似与同义改写，但不可解释、对精确匹配弱、更新成本高。生产上两者是互补关系：ES 做关键词召回 + 过滤，向量库做语义召回，再融合重排——这也解释了为什么「只上向量库」在真实业务里经常不够。
