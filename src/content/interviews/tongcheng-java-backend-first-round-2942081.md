### 《参考解析》

**HashMap 的底层与 0.75**：JDK 8 是数组 + 链表 + 红黑树，`put` 时按 `hash(key)` 扰动后与 `(n-1)` 做与运算定位桶，冲突时尾插链表，链表长度到 8 且数组长度到 64 时转红黑树，扩容时按 2 倍扩容并把节点拆成高低位两条链。负载因子 0.75 是空间与时间的折中：太小则频繁扩容、浪费内存，太大则冲突概率上升、查询退化。调到 1 意味着表快满了才扩容，哈希冲突显著增加（泊松分布下链表变长），查询从 O(1) 退化，且扩容前那段区间性能最差；同时 `resize` 更晚发生，单次扩容搬移的数据更多。0.75 配合容量为 2 的幂，能让 `(n-1) & hash` 分布较均匀。

**Redis 结构与场景**：String（缓存对象、计数器、分布式锁的 SETNX）、Hash（对象字段局部更新，如用户属性）、List（消息队列、时间线）、Set（去重、交并集、抽奖）、ZSet（排行榜、延迟队列、带权重的范围查询）、Bitmap（签到、布尔统计）、HyperLogLog（UV 估算）、Stream（消息流）。回答时把「结构 + 一条命令 + 一个业务场景」绑在一起说。

**穿透、击穿、雪崩**：穿透是查不存在的数据，请求全部打到数据库——缓存空值（短 TTL）、布隆过滤器前置拦截、参数校验；击穿是热点 key 过期瞬间大量请求打库——互斥锁/单飞（只让一个请求回源）、逻辑过期（异步刷新）、热点永不过期；雪崩是大量 key 同时过期或 Redis 整体故障——过期时间加随机抖动、多级缓存、集群与哨兵、限流降级。三者常被混淆，回答时先给一句定义再给方案。

**布隆过滤器与误判**：布隆过滤器用多个哈希函数把元素映射到位数组，判断「可能存在 / 一定不存在」，因此有假阳性、没有假阴性。误判率约为 `(1 - e^(-kn/m))^k`，降低误判的手段是增大位数组（m）、选择合适数量的哈希函数（k ≈ 0.69·m/n）、以及用计数布隆或分片布隆。它不能删除元素（除非计数版），也不适合元素集合频繁变动的场景。

**JVM 回收与 GC Root**：判断对象可回收用可达性分析，从 GC Root 出发不可达即可回收；引用计数因循环引用被弃用。GC Root 包括虚拟机栈中局部变量表引用的对象、方法区静态属性引用的对象、常量引用的对象、本地方法栈 JNI 引用的对象、活跃线程、以及同步锁持有的对象等。回收算法有标记-清除（碎片）、复制（新生代，浪费一半空间）、标记-整理（老年代）、分代收集。收集器从 Serial、Parallel 到 CMS、G1、ZGC，按停顿目标选。

**对象何时进老年代**：大对象直接进（超过 `PretenureSizeThreshold`）、长期存活的对象年龄达到阈值（默认 15，`MaxTenuringThreshold`）、动态年龄判定（Survivor 中同龄对象总和超过一半则直接晋升）、Survivor 空间不足时的分配担保。G1/ZGC 没有严格的新老年代分区语义，按 region 回收。

**MySQL 慢查询排查**：先 `explain` 看执行计划（type、key、rows、Extra 里的 filesort/temporary），再看慢查询日志与 `performance_schema`；确认是否有索引缺失、索引失效（函数、隐式类型转换、前导模糊、联合索引最左前缀断裂）、回表过多（考虑覆盖索引）、数据量过大（分页深翻、分区、归档）。接口变慢则先分层定位：网关、应用（线程池满、GC、锁等待）、DB（慢 SQL、连接池）、下游依赖，用链路追踪与耗时打点确定瓶颈，别一上来就改 SQL。

**复杂 SQL 优化**：把查询拆成「过滤—关联—排序—分页」四段分别看。过滤条件尽量走索引、把选择性高的放前面；关联用小结果集驱动大表、确保关联字段有索引且类型一致；排序尽量用索引顺序避免 filesort；深分页用游标（`where id > last_id`）或延迟关联；必要时用物化视图/汇总表/缓存换实时性。改完用真实数据量压测对比，别只看 `explain` 的估算。

**ES 与 binlog 同步延迟**：ES 适合全文检索、聚合与多条件筛选，不适合当主存储。同步链路常见是业务写库后发消息，或 canal 订阅 binlog 投递 MQ 再写 ES。ES 本身近实时（refresh 默认 1 秒），加上 MQ 与消费耗时，端到端延迟通常在秒级。对实时性要求高的场景（下单后立刻按状态查）不能只依赖 ES，要回源数据库或用「写库后同步双写 + 版本号」；对账与补偿（定时比对、失败重放、幂等写入）是必备的。回答时说明业务对延迟的容忍度，再决定同步还是异步。

**线程池参数与流程**：核心参数是 `corePoolSize`、`maximumPoolSize`、`keepAliveTime`、`workQueue`、`threadFactory`、`handler`。提交任务时：当前线程数小于核心数就新建线程；否则入队；队列满且线程数小于最大数就新建非核心线程；再满则执行拒绝策略。关键点是「先入队再加线程」，所以用无界队列时 `maximumPoolSize` 形同虚设，容易 OOM。参数要按任务类型（CPU 密集 / IO 密集）与下游承载定，并配监控（活跃线程、队列长度、拒绝次数）。

**HTTP 与 HTTPS**：HTTPS 是 HTTP over TLS，默认 443。TLS 握手用非对称加密协商出对称密钥，之后用对称加密传数据，兼顾安全与性能；证书由 CA 签发，用来验证服务端身份、防中间人。HTTP 明文传输、可被窃听篡改；HTTPS 提供机密性、完整性、身份认证，代价是握手延迟与证书管理（可用会话复用、TLS 1.3 的 1-RTT/0-RTT 缓解）。HTTP/2、HTTP/3 都要求 HTTPS。

**AI 编码与线上排查**：AI 编码要能说出具体用法与边界——用它写样板、补测试、读陌生代码、生成 SQL 初稿，但涉及金额、权限、并发、事务的代码必须人工确认，且要看它有没有偷偷吞异常、加业务上不存在的兜底。线上问题排查按「止损—定位—修复—复盘」：先看监控与告警确认影响面，必要时降级/回滚/切流量；再用日志、链路追踪、指标三层定位到具体服务与方法；复现后小流量验证修复；最后补监控与用例防止复发。
