### 《面试题目》

1. 用户快速同时请求两个不同的筛选数据会怎么样？具体如何处理竞态？
2. 讲讲用户从筛选数据到请求再到取得数据的具体流程。
3. 地图筛选和选项筛选怎么设计的？刷新后数据是否能保持一致？
4. 如果用户刷新界面，筛选条件还能保留在页面当中吗？
5. 让你设计刷新之后还能保留筛选条件的话，该怎么设计？
6. 项目用户权限分离的选型是怎样的？如何进行角色的权限控制（A 有权限、B 没有权限时，相关按钮等模块该怎么设计）？
7. 没有权限的话，该校验哪些内容？
8. 有没有多人开发经验？
9. 熟不熟悉 git 操作？

### 《参考解析》

**竞态的本质是「后发请求先回」覆盖了「先发请求」的结果。** 处理方式分三层：入口用防抖或节流减少无意义请求；请求侧用 AbortController 取消旧请求，或给每次请求打自增 requestId，只有最新 id 的响应能写 store；状态侧把筛选条件作为唯一数据源，响应回来时校验它对应的 query key 是否仍是当前 key。只靠 debounce 不够，因为两个不同筛选可能间隔超过防抖窗口；只靠取消也不够，服务端可能已经处理完，所以要有「最新写赢」的兜底。loading 和 error 同样要按请求维度管理，否则旧请求的报错会把新结果清空。

**筛选到取数的流程要能画成状态机。** 用户操作 → 更新筛选状态（可序列化）→ 生成 query key（排序、去空值、归一化）→ 命中缓存直接使用，否则发请求 → 响应校验 key → 写缓存与视图 → 渲染。地图筛选与选项筛选应该是两个受控输入源，共享同一份筛选模型；地图视野变化要做防抖和精度取整，否则拖动一次就发一串请求。刷新保持则把筛选写进 URL query，天然支持分享、前进后退和刷新恢复；地图中心、缩放、多选这类复杂状态可以同时存 sessionStorage，但首屏要以 URL 为准做 hydration，避免服务端渲染与客户端状态不一致导致闪烁。

**权限控制的前端部分只负责体验，安全边界必须在服务端。** 选型上常见 RBAC（角色—权限点）和 ABAC（属性或数据范围）；按钮级用权限点控制显隐，路由级做守卫，接口级必须每次校验。A 有权限、B 没有时，前端要同时处理「看不到」和「看得到但不能操作」：菜单和按钮隐藏或禁用并给原因，直接访问 URL 要落到 403 页，接口返回 403 要有统一拦截。校验内容包括身份、角色与权限点、数据归属（这条记录是不是你的）、操作状态（是否已提交）以及租户隔离。前端隐藏不能当安全措施，因为请求可以伪造。

**多人协作与 Git 的答法要给具体习惯。** 分支按需求切、小步提交、提交前 rebase 到最新主干并跑 lint 和单测；冲突处理先理解双方意图再合并，不直接覆盖；公共组件或接口变更要提前打招呼，必要时拆 PR；提交信息写清动机与影响面。没有多人经验就讲清自己怎么模拟：多人分支、代码评审、冲突演练，以及实际用过的命令和流程。面试官问这题不是考命令背诵，而是看你有没有「不把别人代码冲掉」的意识。
