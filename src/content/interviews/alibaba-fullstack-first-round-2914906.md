### 《参考解析》

**知识图谱与 RAG 的区别**：两者都是给模型补外部信息，但组织方式不同。RAG 的组织方式是基于**文本片段的向量相似度**，回答依据是「哪段文字和问题像」，擅长语义模糊的开放问答、文档摘要、跨文档检索；缺点是片段之间没有结构、多跳问题容易断链（A 的答案需要先找到 B 再找 C），也不擅长「精确的枚举与关系推理」。知识图谱把信息组织成**实体—关系—实体**的三元组，擅长多跳关联、精确关系查询、结构化约束（谁调用了谁、属于哪个模块、影响面有多大），且可以做可解释的路径溯源；代价是构建与维护成本高（需要抽取、对齐、消歧、持续更新），覆盖面不如文本。实践中常见的是混合：图谱负责「找到相关节点和路径」，RAG 负责「把节点相关的文本证据取回来喂给模型」，即 GraphRAG 的思路——先在图谱上做关系扩展（拿到 A 的上下游），再用向量检索取这些节点的文本上下文。答题时把「检索单位是片段 vs 节点与边」「擅长语义相似 vs 擅长关系推理」这两句对立说清楚，再给一个混合方案，基本就完整了。

**可插拔的 Agent Harness 怎么设计**：核心是「把易变的业务知识和稳定的运行时分离」。稳定的部分：主循环、工具调用协议、上下文与压缩、错误重试、可观测（轨迹、token、成本）、权限与沙箱，这些做成框架。易变的部分抽成插件：① 提示层——每个业务一个系统提示模板 + 输出 schema；② 能力层——工具集合按业务注册（同一套工具接口，不同实现/不同开关）；③ 知识层——接入不同知识库或 Skill 文档，按需注入；④ 校验层——每个业务自定义的验收规则（字段必填、口径校验、调用白名单）。插件通过统一接口注册（名称、描述、触发条件、参数 schema、执行函数），harness 只按描述做路由和注入，不感知业务细节；这样换业务只改配置和知识，不动运行时。工程上要注意：插件要有版本与灰度、失败要能降级为不带插件的基线能力、每个插件的上下文预算要可控，否则「可插拔」会变成上下文爆炸。

**长流程可靠性**：常见方案可以按层次说。① 状态持久化：把工作流状态存成可恢复的检查点（步骤 id、输入输出、已完成集合），任何一步失败都能从最近检查点续跑，而不是从头开始。② 幂等与去重：每个步骤带业务唯一键，重复执行不产生副作用（这一点和分布式任务的要求一致）。③ 编排层重试策略：区分可重试（网络、限流）与不可重试（参数错误、权限不足）错误，配指数退避 + 抖动、最大次数、超时与熔断，避免重试风暴。④ 补偿事务（Saga）：长流程跨服务时不做分布式事务，而是为每步定义补偿动作，失败按反向顺序补偿，同时保证补偿本身幂等。⑤ 人机协同：把高风险或低置信度的步骤设计成「暂停等人工确认」，确认后从检查点继续。⑥ 可观测与告警：全链路 trace、步骤级耗时与失败率、卡住的任务要有超时清扫（僵尸任务回收）。进一步扩展的方向：动态重规划（失败后不是重试而是换路径）、并行分支与合并的冲突处理、状态迁移的版本兼容（工作流定义升级后老实例怎么办）、以及成本与延迟预算约束下的调度。

**LCP 与「预加载反而更快」的原理**：要先纠正一个常见误解：懒加载的本意是**不加载视口外的图片**，如果首屏 LCP 元素本身被标成了懒加载，那它的加载会被推迟到 IntersectionObserver 回调、甚至等 JS 执行和 hydration 之后才发起请求，LCP 自然被推后几秒——把它改成预加载（`<img fetchpriority="high">` 或 `<link rel="preload" as="image">`）等于让浏览器在解析 HTML 阶段就发起请求，省掉的正是「等 JS 执行 + 触发懒加载回调」这段串行时间，所以 LCP 减少几秒是合理的。至于「提前加载为什么不会增加总加载时间」：图片请求是并行的，只要不抢占关键资源带宽，提前发起只是把空闲的水管用起来，总字节数没变；反而更早开始下载能更快完成。注意点是：`preload` 用在 LCP 图上是对的，滥用会挤占带宽反而变慢；懒加载的图片是否计入 LCP，取决于它是不是 LCP 元素——LCP 只统计视口内最大的内容元素，如果它因为懒加载晚渲染，LCP 时间就会被推迟（这正是要避免的）；非 LCP 的图片懒加载不影响该指标。

**虚拟列表与滚动加载**：滚动加载（无限滚动）解决的是「数据分页获取」——滚到底部再请求下一页，DOM 节点持续增长；虚拟列表解决的是「DOM 节点太多导致渲染卡顿」——只渲染可视区域加上下缓冲区内的节点，其余用空白占位撑起总高度，滚动时按 `scrollTop` 计算起始索引并复用节点（`translateY` 或 `padding-top` 偏移）。实现关键点：① 已知项高时用「起始索引 = floor(scrollTop / itemHeight)」，不定高需要测量并维护位置缓存（或先用估算值再校正）；② 用一个上下各留若干项的缓冲区减少快速滚动白屏；③ 监听 `scroll` 要做 `requestAnimationFrame` 节流，且不要同步读取 `scrollTop` 触发布局抖动（读写分离或用 `IntersectionObserver` 做哨兵）；④ 总高度 = 项数 × 项高，保证滚动条长度正确；⑤ 配合 `key` 稳定复用、图片懒加载、以及滚动位置的保存恢复。两者可以叠加使用：虚拟列表负责渲染，滚动加载负责取数。

**HTTP 强缓存、协商缓存与 304**：强缓存由响应头 `Cache-Control`（`max-age=秒`、`s-maxage`、`immutable`、`no-cache`、`no-store`、`public`/`private`、`stale-while-revalidate`）和 `Expires`（绝对时间，已被 `Cache-Control` 覆盖）控制，命中时浏览器**不发起请求**，直接读本地副本（网络面板显示 from disk/memory cache）。协商缓存是强缓存过期后的兜底：浏览器带上 `If-None-Match`（值来自上次响应的 `ETag`）和 `If-Modified-Since`（值来自 `Last-Modified`）去问服务端，服务端比对后如果资源没变就返回 **304 Not Modified**（无响应体，只有头部），浏览器用本地副本；变了则返回 200 和新内容。一次 304 的完整过程：请求携带条件头 → 服务端比对 ETag/时间 → 命中未变更 → 304 + 新的 `Cache-Control`/`ETag`（刷新缓存时长）→ 浏览器更新缓存元数据并用本地副本渲染。要点：`ETag` 优先级高于 `Last-Modified`（后者精度只到秒，且文件内容不变但修改时间变化时会误判、被编辑后改回内容也会误判）；`Last-Modified` 属于**协商缓存**；实际部署口径一般是「HTML 用 `no-cache` + ETag 走协商、带 hash 的静态资源用 `max-age=31536000, immutable` 走强缓存」。

**构建性能优化（Vite/Webpack）**：① 减少工作量——按需引入与 tree-shaking（`sideEffects: false`、避免 `import *`）、用更快的编译器（SWC/esbuild 替 babel-loader 和 ts-loader）、`cache: { type: 'filesystem' }` 持久化缓存、`include/exclude` 收窄 loader 范围；② 减少模块数量——合理拆包（`splitChunks` 把 react/vendor 抽出来）、用 externals 或 CDN 外置大依赖、按路由动态 `import()`、Monorepo 里只构建改动的包（Turborepo/Nx 的增量与远程缓存）；③ 并行与增量——`thread-loader`/`parallel`、开发阶段用 Vite 的 esbuild 预构建 + 原生 ESM 按需编译，只处理被请求的模块；④ 分析与定位——`speed-measure-webpack-plugin`、`vite --profile` / `rollup-plugin-visualizer` 先量后调，别凭感觉加插件。顺带回答「Vite 生产为什么用 Rollup」：开发环境用 esbuild 预构建依赖 + 原生 ESM 按需转换是为了快，但生产打包需要成熟的代码分割、tree-shaking、CSS 处理与多种输出格式一致性，Rollup 在这些方面更完善；新版本 Vite 也在往 Rolldown（Rust 版 Rollup）迁移。

**为什么很多 AI 框架选 TypeScript 而不是 Java / Python**：可以从三个角度答。① 交付形态——很多 AI 工具/框架面向 Web 与桌面端，需要同时跑在浏览器、Node、边缘运行时，TS 编译到 JS 后天然跨端，Java 需要额外运行时、Python 在浏览器里没有原生位置；② 生态与类型——AI 应用的复杂度主要来自「工具调用、流式数据、多协议适配」这类编排与类型约束，TS 的结构化类型 + 异步流（async iterator/Streams）表达力好，且前后端共享类型（schema 即类型），Java 类型强但异步流式与 JSON 生态更笨重；③ 协作与语料——确实如面试官追问的，开源语料多会带来训练和补全上的正反馈（模型更熟 TypeScript，生成质量更高、迭代更快），但这不是唯一原因：Python 的语料同样多，只是 Python 更适合做训练/推理侧（框架生态、GPU 库），TS 更适合做应用编排侧。所以准确表述是「分层」：模型训练与推理用 Python，上层 Agent/工具链/前端一体化的编排层用 TypeScript。

**面试复盘**：这场面试的典型特征是**沿简历逐层深挖**——面试官不停追问「你是怎么做度量的」「对照组怎么实现的」「为什么不是另一个方案」，很多问题都是顺着上一句回答衍生出来的。应对策略：简历上每一条都要有可量化的定义与对照实验设计（自己说不出度量方式，就会被判定为「只是主观感受」）；讲性能优化时把「指标怎么测、基线多少、改完多少、为什么有效」当成固定四段；被反问「是吗？」时不要顺着点头，先确认对方理解是否与自己一致再补充。
