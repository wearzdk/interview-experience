### 《参考解析》

**为什么是 B+ 树**：磁盘按页读取，索引结构的目标是「用最少的 IO 定位」。B+ 树是多叉平衡树，一个 16KB 的页能放几百个键，三层就能索引千万级数据，查找只需 3 次 IO；数据全在叶子节点且叶子间用链表相连，范围查询只需顺着链表扫，不用回树；相比 B 树，非叶节点不存数据、扇出更大、树更矮；相比红黑树/AVL（二叉、树高 log₂n，千万级要 20 多层），B+ 树的 IO 次数少一个数量级；相比哈希索引，它支持范围与排序。

**聚簇 vs 非聚簇**：InnoDB 的主键索引就是聚簇索引，叶子节点直接存整行数据，一张表只有一个；二级索引的叶子存的是索引列 + 主键值，查非索引列要「回表」再查一次聚簇索引。MyISAM 的索引都是非聚簇的，叶子存行地址。

**主键重排序**：InnoDB 按主键顺序组织数据，插入一个中间值的主键会导致页分裂——把一页拆成两页、搬移数据、更新父节点，代价高且产生碎片。所以推荐自增 / 趋势递增主键（雪花 ID 也满足趋势递增）。「为什么不用指针」：多一次跳转就多一次 IO，而且指针要额外空间、要维护；顺序存储让范围扫描能顺序读，这是 B+ 树设计的根本。重排序的数据拷贝确实是变慢的直接原因。

**非聚簇索引的范围查询**：支持。二级索引本身是有序的，`WHERE age > 20` 可以在 age 索引上做范围扫描，只是每一行都要回表取其他列（除非是覆盖索引）。所以「范围查询慢」的根因是回表次数多，而不是索引结构不支持。

**联合索引 (a,b,c)**：按 `(a,b,c)` 依次排序建 B+ 树，叶子节点存 `(a,b,c,主键)`。`a = 1, b > 2, c = 3`：a 是等值，能在树上定位到 a=1 的区间；b 是范围，从 b>2 的位置开始顺序扫；但 c 在这个范围里已经无序（b 每个值下 c 才有顺序），所以 c=3 只能在回表后过滤（或走 ICP 索引条件下推，在存储引擎层过滤以减少回表）。最左前缀原则：跳过 a 直接用 b、c 不行；范围列之后的列无法继续用于定位。

**Spring Boot 自动装配**：`@SpringBootApplication` 是组合注解，含 `@EnableAutoConfiguration`，它通过 `@Import(AutoConfigurationImportSelector.class)` 读取 classpath 下所有 jar 的 `META-INF/spring/org.springframework.boot.autoconfigure.AutoConfiguration.imports`（2.7 之前是 `spring.factories`），拿到候选配置类列表，再用 `@ConditionalOnClass`、`@ConditionalOnMissingBean`、`@ConditionalOnProperty` 等条件注解决定哪些真正生效，最后注册 Bean 定义。所以 main 函数不需要额外注解，`@SpringBootApplication` 一个就够。
