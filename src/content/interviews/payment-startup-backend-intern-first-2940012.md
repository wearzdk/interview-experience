### 《面试题目》

1. 自我介绍。
2. 介绍一下简历上的第一个 Agent 项目：主要解决什么问题？整体流程是什么？
3. 简要讲一下一笔订单的「流水过程」。可以按自己的理解，说说相关表结构和需要注意的事项。
4. 如果支付或转账接口突然来了很多请求，比如瞬间有一百个请求，你会怎么处理？怎么避免重复扣款？
5. 支付场景中会用到很多 Webhook。如果请求出现丢失、乱序或者重复，该怎么处理？
6. 反问。

### 《参考解析》

**订单流水过程**：用户下单（创建订单，状态「待支付」，写订单表：订单号、用户、金额、商品、状态、创建时间、过期时间）→ 调起支付（生成支付单，关联渠道与商户单号，状态「支付中」）→ 渠道回调（校验签名、幂等、更新支付单为成功、更新订单为「已支付」、写资金流水/账务分录）→ 发货或开通权益（可能异步）→ 对账（与渠道账单核对，处理单边账）→ 退款/售后。核心表：订单表、支付单表、资金流水表（只追加、不可改，记录每笔变动与余额）、退款单表、对账表。注意事项：金额用「分」存整数避免浮点误差；订单号与渠道单号都要唯一索引；状态流转要幂等；所有变动都要有流水可追溯；超时未支付要关单并释放库存。

**瞬间一百个请求与避免重复扣款**：分两层。第一层是「控制并发」：接口限流（令牌桶/漏桶）、按用户维度加分布式锁或串行化（同一用户同一时间只处理一个支付请求）、库存或余额用 Redis 预扣 + Lua 保证原子。第二层是「幂等」：客户端带幂等键（requestId），服务端用唯一索引或 Redis `SETNX` 去重；支付单与订单状态机保证「已支付」不能再次支付；调渠道时用商户订单号做幂等，渠道侧天然去重；回调处理要校验「当前状态」再更新（CAS 或 `update ... where status='待支付'`）。一百个请求不算高并发，真正要防的是「同一笔订单被重复提交」和「回调重复到达」。

**Webhook 丢失、乱序、重复**：丢失——渠道通常会重试，服务端要返回明确的成功响应（处理完再返回 200），并做定时对账/主动查询补偿；乱序——用「事件时间 + 版本号/状态机」判断是否可应用，旧状态不能覆盖新状态（例如「支付成功」不能被迟到的「支付中」覆盖）；重复——按事件 ID 或「订单号 + 事件类型」做幂等，落库前去重表或唯一索引。工程上还要：验签防伪造、限制来源 IP、记录原始报文以便排查、异步处理但保证最终一致、设置处理超时与死信队列。

**这类小厂面试的特点**：问题少但都在业务点上，考察的是「你有没有真的想过支付场景」。回答时先给流程再给细节，主动提「幂等、对账、状态机、流水不可变」这四个词，基本就能覆盖面试官的关注点。Agent 项目被问到时，用「解决什么问题 → 流程 → 效果」三段讲，不要一上来讲技术栈。
