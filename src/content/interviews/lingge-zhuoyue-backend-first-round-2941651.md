### 《参考解析》

**隔离级别与幻读**：SQL 标准四个级别是读未提交、读已提交、可重复读、串行化；对应的问题是脏读、不可重复读、幻读。InnoDB 默认可重复读，用 MVCC（每行隐藏的 `trx_id` + 版本链 + ReadView）解决快照读下的不可重复读与幻读；但**当前读**（`select ... for update`、`update`、`delete`）仍可能遇到幻读，靠间隙锁（Next-Key Lock = 记录锁 + 间隙锁）来阻塞插入。所以标准答案是「快照读靠 MVCC、当前读靠间隙锁，两者合起来让 RR 在 InnoDB 上基本避免了幻读」，注意 RR 下 ReadView 只在第一次快照读时创建，RC 下每条语句都重建。

**建索引的注意事项**：按选择性高的列建（区分度低的列如性别、状态单独建索引往往没用）；遵循最左前缀，联合索引把等值条件多、选择性高的列放前面；避免在索引列上做函数、隐式类型转换与前缀模糊（`%x`），否则索引失效；控制索引数量（每次写入都要维护所有索引）；长字符串用前缀索引；区分度低的列可以放在联合索引的尾部当覆盖列；尽量让查询走覆盖索引减少回表。索引种类按结构分 B+ 树、哈希、全文、空间；按物理组织分聚簇（主键）与二级索引；按约束分唯一、主键、普通、联合、前缀。

**主键索引与非主键索引的叶子节点**：InnoDB 是索引组织表，主键索引（聚簇索引）的叶子节点存整行数据；二级索引的叶子节点存索引列 + 主键值，因此二级索引查非索引列需要「回表」再按主键查一次。这解释了为什么覆盖索引能省一次回表、为什么主键要短（二级索引都要带主键）、为什么建议用自增主键（避免页分裂与随机写）。

**三种日志**：redo log 是 InnoDB 的物理日志，记录「某页某偏移改成了什么」，环形写、用于崩溃恢复与 WAL（先写日志再刷脏页）；undo log 是逻辑日志，记录反向操作，用于回滚与 MVCC 的版本链；binlog 是 MySQL Server 层的逻辑日志，记录语句或行变更，用于主从复制与按时间点恢复。数据结构上 binlog 是事件序列（Row 格式记录前后镜像，Statement 格式记录 SQL），redo log 是固定大小的环形块、按 LSN 顺序追加的物理页修改记录。两阶段提交保证 binlog 与 redo log 一致。

**Redis 数据结构与部署**：基础类型 string、list、hash、set、zset，扩展有 bitmap、HyperLogLog、GEO、Stream。部署方式有单机、主从（读写分离、无自动故障转移）、哨兵（监控 + 自动选主）、集群（Cluster，16384 个槽分片，客户端按 key 路由）。切片集群就是 Cluster 的分片：每个 master 负责一段槽位，key 用 CRC16 取模映射到槽；跨槽的多 key 操作要用 hash tag 把相关 key 强制落到同一槽。

**旁路缓存与读写缓存**：旁路缓存（Cache-Aside）是应用自己管缓存——读时先查缓存、未命中查库并回填；写时**先更新数据库再删除缓存**（而不是更新缓存），并给缓存设过期时间兜底。删缓存仍可能不一致（读请求在删之前拿到旧值又回填），常用延迟双删或订阅 binlog 异步失效；强一致要求高时给 key 加互斥锁防击穿。读写缓存（Read/Write-Through）是写操作同时写缓存、由缓存层同步落库，一致性好但写放大、缓存故障影响写路径，适合写少读多且能接受缓存层承担写流量的场景。此外缓存击穿（热点 key 过期瞬间打穿）、穿透（查不存在的 key，用布隆过滤器或空值缓存）、雪崩（大量 key 同时过期，加随机过期时间）是必答的三件套。

**二叉树层序遍历**：用队列，先把根入队，循环弹出节点、记录值、把左右子节点入队；按层输出时在内层循环里先取当前队列长度，处理完这一层的所有节点再进入下一层。复杂度 O(n) 时间、O(宽度) 空间。变体（之字形、右视图、每层最大值）都在这套模板上加一两行。
