### 《参考解析》

**GC 与对象晋升：把「什么时候进老年代」答全**

GC 这块要按「分代结构 → 回收算法 → 晋升条件 → 排查手段」来讲。堆分新生代（Eden + 两个 Survivor）和老年代，新生代用复制算法因为大多数对象朝生夕死，老年代用标记整理（CMS 用标记清除）。对象进入老年代有四种典型路径：一是年龄达到阈值（默认 15，每熬过一次 Minor GC 加一岁）；二是大对象直接进老年代（`PretenureSizeThreshold`，避免在 Eden 与 Survivor 之间反复复制大块内存）；三是动态年龄判定——Survivor 中相同年龄对象的总大小超过 Survivor 空间一半时，该年龄及以上的对象直接晋升，这条最容易被漏掉；四是 Survivor 空间不足时的分配担保，剩余对象被挪进老年代。回收策略上要讲清 Minor GC、Major/Full GC 的触发条件与代价差别，以及 Full GC 频繁的常见原因（老年代增长快、元空间不足、显式 `System.gc()`、CMS 并发失败退化）。OOM 的排查要落到工具：`jmap -dump` 或 `-XX:+HeapDumpOnOutOfMemoryError` 拿堆快照，用 MAT 看支配树找大对象与引用链，区分是内存泄漏（对象被不该持有的引用挂住）还是内存溢出（确实不够）；常见的几类 OOM 也要点一下——堆溢出、元空间（动态生成类过多）、直接内存（NIO/Netty）、以及「unable to create new native thread」。

**进程、线程、协程与 ThreadLocal**

进程是资源分配的基本单位、拥有独立地址空间，线程是调度的基本单位、共享进程内存，协程是用户态的轻量调度单元，切换不陷入内核、由运行时或语言自己调度，代价比线程小得多，适合高并发 IO。关于「应用 A 和应用 B 会不会共用一个线程」要分情况：不同进程之间的线程本来就互不相干；同一个 JVM 进程内，是否共用取决于线程池的归属——用共享的公共线程池（比如某些框架内部的默认池、ForkJoinPool.commonPool）时不同业务逻辑会跑在同一个线程上，这也是为什么线程池要按业务隔离、命名，并避免在共享线程上放 ThreadLocal 或依赖线程本地状态。ThreadLocal 的特点是「每个线程一份独立的变量副本」，底层是 Thread 对象里的 `ThreadLocalMap`，key 是 ThreadLocal 本身的弱引用、value 是强引用，所以用完必须 `remove()`，否则在线程池里会被下一个任务读到脏数据，且 key 被回收后 value 无法访问会造成内存泄漏。它的数据其他线程默认访问不到——但这不是安全机制：`InheritableThreadLocal` 会把值传给子线程，线程池里子线程复用更会让「继承」变成污染；真正的跨线程传递要靠显式传参或专门的上下文传递组件。典型的正确用法是放数据库连接、用户上下文、traceId 这类「跟本次请求绑定」的东西，并在 `finally` 里清理。

**Redis 热点榜与跨机房缓存：「为什么不用 id 直接查」**

排行榜类的需求标准答案是 ZSet（有序集合），底层跳表加哈希，`ZINCRBY` 累加热度、`ZREVRANGE` 取 Top N、`ZREVRANK` 查排名，复杂度都是对数级。要顺手讲清几个工程细节：热点商品的热度通常来自多种行为（浏览、加购、下单）加权，别把原始点击直接累加；写入要防热点 key 打爆单分片，可以按商品 ID 哈希打散到多个 ZSet 再合并，或者用定时批量聚合而不是每次请求都写；榜单要做冷启动与兜底（缓存过期时回源、榜单为空时给默认位次）；如果要求实时性不高，用定时任务算好再整体替换，比每次读写都动 Redis 更稳。追问一般会落到「ZSet 和 List 有什么区别」——List 只能按插入顺序取，没法按分数排序，也没法 O(logN) 查排名。

跨机房缓存那几问是典型的「顺着你的项目往下挖」，回答的关键是把背景、旧状态、新状态、以及为什么这么改讲成一条链。扫码确认这类场景的特点是同一次操作要在多个机房可见——用户在 A 机房发起、确认动作可能落在 B 机房，如果只在本地机房写缓存，另一个机房读不到就会重复弹出确认或判定失败。所以「全机房写」解决的是多机房数据可见性与一致性，而不是查询性能。「为什么不能用买家/商家 id 查」问的是数据分片策略：如果按 id 哈希分片，同一条扫码记录只落在一个分片，跨机房读就要走跨机房查询（延迟高、还可能失败），而全机房写是把一份小体积、短生命周期的状态复制到各机房本地，用写放大换读延迟与可用性。要主动说清代价与兜底：写多份会有一致性窗口，靠过期时间、版本号或「以主机房为准 + 异步同步」来收敛；数据量要小（比如只记状态和短期 token），不能把大对象全机房复制。最后补上效果度量——优化前后跨机房读的 P99、确认失败率、以及回退方案，这些比「加了缓存」有说服力。

**手撕：单向链表的增删查与反转**

实现要点是把边界处理干净，写之前先跟面试官对齐接口（是否带头节点、删除是按值还是按位置、是否允许重复值）。反转给两个版本：迭代版用 `prev/cur/next` 三个指针边走边改指向，O(n) 时间 O(1) 空间；递归版代码短但栈深度是 O(n)，长链表有溢出风险，面试里以迭代版为主、递归版作为补充说明。要主动覆盖的用例：空链表、只有一个节点、删除头节点、删除不存在的值、反转后再反转应当还原。写完可以用一句「如果要求线程安全，就在头尾分别加锁而不是锁整条链」收尾，显示你意识到并发场景的存在。
