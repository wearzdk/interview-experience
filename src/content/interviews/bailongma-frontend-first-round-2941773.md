### 《参考解析》

**iframe 父子通信**：父调子用 `iframe.contentWindow.postMessage(msg, targetOrigin)`，子调父用 `window.parent.postMessage(...)`；接收方监听 `message` 事件，`event.data` 取数据、`event.origin` 必须校验白名单（否则任何页面都能给你发消息）、`event.source` 可回发。跨域的 iframe 不能直接读写对方的 DOM 与变量，同源才能直接访问。

**window 是不是同一个**：不是。每个 browsing context（每个 iframe、每个窗口）有独立的 `window` 对象，`iframe.contentWindow` 是子窗口的全局对象，`window.parent` / `window.top` 是父级的引用。同源时你可以拿到引用并读写它的变量与 DOM，跨域时引用存在但大多数属性访问会抛跨域错误，只能通过 `postMessage` 通信——这正是隔离的边界。

**iframe 加载完成**：`iframe.onload`（或 `addEventListener('load')`）在文档与资源加载后触发；`load` 事件的 `event.target` 是 iframe 元素，可从中取 `src`、`contentWindow`、`contentDocument`。要更早感知可以用 `readystatechange`（`interactive` / `complete`）或子页面在 `DOMContentLoaded` 后主动 `postMessage` 通知父级；注意 `src` 改变或 `srcdoc` 重设都会重新触发 load，动态插入的 iframe 要防止 onload 绑得太晚。

**多子应用样式统一**：先用设计 token（CSS 变量：颜色、间距、圆角、字号）作为唯一来源，子应用只引用变量不写死值；再用一层基础样式包（reset + 变量定义 + 公共组件）通过 CDN 或 npm 统一引入；历史应用逐步迁移——先并行注入变量并做视觉回归比对，再按模块替换硬编码值。隔离手段按场景选：iframe 天然隔离但通信与性能成本高，Shadow DOM 隔离样式但全局样式与事件要额外处理，qiankun 这类微前端用沙箱做样式与 JS 隔离（运行时动态 `style` 打 scoped 前缀）。

**主 Agent 与子 Agent 的分工**：主 Agent 负责理解意图、拆解任务、编排与汇总、与用户交互、决定何时调用哪个子 Agent；子 Agent 负责单一领域的深挖（检索、代码生成、测试、文档解析），有独立的上下文与工具集，只回传结构化结论。划分依据是「上下文隔离」与「工具权限收敛」——子 Agent 的输出要能被主 Agent 校验，而不是把大量原始材料倒回主上下文。

**从 PRD 到代码的工作流**：需求解析（抽取功能点与约束、识别缺失信息）→ 检索（找相关代码、接口定义、设计规范）→ 方案产出（改哪些文件、接口契约、数据结构）→ 人工确认方案 → 分步实现（每个文件一个可验证的小步）→ 自检（类型检查、lint、单测、本地运行）→ 人工 review 与合并。人工必须参与的环节是：需求澄清、方案确认、关键逻辑 review、上线决策；其余可以自动化但要有可回滚的边界。

**平台视角除了 token 还看什么**：效果（任务成功率、返工率）、可靠性（工具调用失败率、重试与降级）、可观测性（每一步的输入输出与耗时、trace）、安全与权限（工具能碰哪些资源、如何防止提示注入越权）、成本结构（缓存命中率、模型分级路由）、数据闭环（失败案例回流成评测集）、以及版本管理（提示词与工具变更的回归测试）。

**RAG 的流程与指标**：流程是解析 → 分块 → 向量化 → 索引 → 召回（向量 + 关键词）→ 重排 → 拼上下文 → 生成 → 引用与校验。指标分两段：检索段看召回率 Recall@K、精确率、MRR / NDCG、命中片段的覆盖率；生成段看忠实度（答案是否被检索内容支持）、答案相关性、引用准确率、以及端到端的人工评分。工程上还要监控「无召回」比例与平均上下文长度（直接关系成本）。

**为什么需要 RAG**：模型的知识有截止时间、不含私有数据、无法引用来源、参数里存不住长尾事实且容易编造；微调能注入风格与能力但更新成本高、难以溯源。RAG 用「检索外部知识 + 生成时引用」解决知识时效、私有数据与可溯源性三个问题，代价是引入检索质量这个新的失败点。

**Harness 是什么**：指包在模型外面、让它能稳定完成任务的工程层——工具定义与调用协议、上下文组装与压缩、状态与记忆管理、错误处理与重试、权限与沙箱、评测与可观测性。落地的能力通常包括工具注册与 schema 校验、结构化输出约束、多轮状态机、失败重试与降级、trace 记录与回放。

**工具很多时模型怎么选、怎么省 token**：选工具靠「名称 + 描述 + 参数 schema」的可读性，工具描述要写清「什么时候用、什么时候不要用」；数量多时先做一层检索（按用户请求召回候选工具）或分组（先选类别再选具体工具），而不是全部塞进系统提示。上下文按需注入：工具描述分层（常驻的少数 + 可检索的多数）、检索到的文档片段动态拼装、历史消息做摘要压缩，并给缓存友好的稳定前缀。

**Vue 与 React 的核心区别**：React 是「UI = f(state)」，靠不可变数据与显式 `setState` 触发重渲染，需要自己管理依赖与 memo；Vue 用响应式系统（Vue 2 的 `defineProperty`、Vue 3 的 Proxy）自动追踪依赖、细粒度更新，模板编译做静态提升。生态上 React 更依赖社区选型（状态管理、路由），Vue 提供官方全家桶；心智负担上 React 要求理解渲染与副作用，Vue 上手更快但响应式边界（如新增属性、解构丢失响应性）容易踩坑。

**首屏慢怎么定位**：Chrome DevTools 的 Performance 面板看主线程长任务与关键渲染路径，Lighthouse 看 LCP / FCP / TBT / CLS 的评分与建议，Network 面板看资源瀑布（首屏请求数、串行依赖、体积、是否走缓存与压缩），Coverage 看未使用的 JS / CSS 占比，Performance Insights 定位 LCP 元素与其阻塞原因。常见结论是「JS 包太大 + 关键请求串行 + 首屏渲染被同步脚本阻塞」。

**优化动作**：路由级代码分割与动态 `import`、按需引入组件库、Tree shaking 与移除重复依赖、图片压缩与懒加载、字体子集化与 `font-display`、关键 CSS 内联 + 其余异步、预加载关键资源（`preload` / `prefetch` / `modulepreload`）、SSR 或静态化首屏、CDN 与长缓存（内容哈希文件名）、接口并行与骨架屏。每项都要给出前后指标对比。

**AI 对前端的影响（开放题）**：可以给出有依据的判断——前端产出多为「结构化的 UI 代码」，模式固定、可验证（能跑起来、能截图比对），因此生成的成功率高、替代感最强；后端涉及数据一致性、并发、线上故障与权限，验证成本高，AI 更多是助手。至于岗位划分，趋势是「职责按交付结果合并、专业深度仍在」，前端不会消失，但只做页面切片的岗位会减少。

**Loop Engineering**：指的是把「生成—执行—观测—修正」做成闭环的工程实践：让模型能拿到运行结果（测试输出、报错、截图），据此自我修正，并把失败的案例沉淀成规则或评测集。它解决的是「一次生成不可靠」的问题，而不是让模型一次答对。
