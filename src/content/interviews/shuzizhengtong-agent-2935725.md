### 《面试题目》

1. 自我介绍。
2. 实习主要做的什么工作？举个做过的最有挑战性的任务。
3. 这里面 HTTP 和 DDS 分别都传什么？
4. 如果 DDS 失败了，你会怎么定位问题？
5. 你对前端框架和 APP 开发掌握吗？
6. 讲讲 paperX 这个软件从上传 PDF 到检索问答的流程。
7. 为什么用 RabbitMQ？是你选型的吗？为什么不用其他 MQ？
8. 拒答和引用校验的设计是为什么？为什么选择 LangGraph？
9. 数据安全脱敏的设计是怎样的？

### 《参考解析》

1. **HTTP 与 DDS 的分工**：HTTP 走请求响应，适合控制面——上传、查询状态、拿结果；DDS 是发布订阅的实时数据总线，带 QoS（可靠性、时限、历史深度），适合数据面——高频、低延迟、多订阅者的实时流。两者混用的系统里，控制指令走 HTTP，数据流走 DDS 是常见分层。

2. **DDS 失败怎么定位**：先确认是发现失败还是传输失败——域 ID、partition、topic 名是否一致，QoS 是否匹配（可靠性设成 best effort 会静默丢包），再看订阅者是否存活、网络是否通、有没有达到资源上限。排查顺序是「能不能发现 → 能不能匹配 QoS → 数据有没有发出去 → 有没有收到」，工具上用 DDS 自带的监控或抓包。

3. **PDF 到问答的链路**：上传后先解析（文本层优先，扫描件走 OCR），按语义或标题层级切块并保留元数据（页码、章节），做 embedding 入向量库，同时建关键词索引；提问时先做查询改写，混合检索召回，rerank 排序，取 top-k 拼进提示并附上引用来源，模型生成后做引用校验，不通过则拒答。

4. **为什么用 RabbitMQ**：解耦上传解析这种耗时任务、削峰、失败重试，且团队已有运维经验。选型对比要能说出来：Kafka 吞吐更高适合日志流但不适合单条消息的复杂路由和延迟队列；RocketMQ 事务消息强、国内生态好；RabbitMQ 路由灵活、延迟队列和确认机制成熟，量级不大的业务链路够用。

5. **拒答与引用校验**：RAG 最大的风险是模型在检索不到依据时编造。做法是要求每个结论都能对应到检索片段，生成后校验引用是否真实存在、是否支持该结论，不满足就拒答或降级为「未找到相关内容」。这比事后审核便宜，也比 prompt 里写「不要编造」可靠。

6. **为什么用 LangGraph**：需要显式的状态机和分支（检索→判断是否足够→再检索或生成→校验→拒答），LangGraph 把节点、边和状态管理显式化，便于调试和插入人工确认；相比自己写 while 循环，它的可观测性和断点恢复更好。

7. **数据脱敏**：入口识别手机号、身份证、银行卡等敏感字段并做掩码或令牌化，日志和向量库里不落原文；按角色做字段级权限，检索时先过滤再召回，避免越权内容进入上下文；脱敏映射表单独存放并审计访问。
