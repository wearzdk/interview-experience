### 《参考解析》

**「graph 恢复 vs session 恢复」这道追问在问什么。** 面试官在区分两种恢复语义：一种是「流程编排层的恢复」——图的节点执行到哪、哪些已完成、下一步走哪条边，这是确定性的代码状态；另一种是「Agent 会话层的恢复」——模型的对话历史、记忆、工具调用上下文，这是半结构化的语义状态。只做前者，恢复后能继续跑流程，但模型可能「忘了刚才聊到哪」，于是重复提问或前后矛盾；只做后者，历史都在，但不知道流程进行到哪一步，可能重复执行副作用。完整方案是两者都存，并在恢复时把「流程状态」渲染成一句明确的上下文告诉模型（「你正在进行第 3/5 步，已完成 A、B，用户刚才确认了 C」）。

**记忆连续性怎么保。** 三个手段：① 把关键事实结构化（不是靠原文），比如「用户选择的方案 ID、已确认的金额、拒绝过的选项」，存成 KV 并在每轮注入；② 消息带轮次与会话 ID，拼接时按序、分段摘要；③ 恢复时先做一次「状态对账」——把存储的状态与外部真实状态（订单是否已创建、文件是否已上传）比对，不一致就以外部为准，避免「记忆说做了、其实没做」。这条最容易被忽略，但生产上最常见的事故就是它。

**等待用户很久的 Agent 怎么设计。** 把「长等待」当成一种正常状态而不是异常：请求进来时创建 `run`，遇到需要用户输入的节点就把状态落库、释放连接（不能让一个 socket 挂一天），并生成一个可恢复的令牌（深链/通知）。用户回来时凭令牌恢复。配套要有 TTL 与过期清理、状态版本号（配置变了旧 run 要能识别）、以及幂等（用户重复点击不重复执行）。这就是「事件驱动的持久化工作流」，不是「一个长连接跑到底」。

**防幻觉的四层设计。** ① 输入层——检索到的事实作为唯一依据，要求引用来源，没有依据就允许说「不知道」；② 决策层——把开放式生成改成受约束的选择（枚举、schema、工具参数），缩小自由发挥空间；③ 执行层——工具调用前做参数校验与权限校验，调用后校验返回、失败要能被感知（超时、非 2xx、字段缺失都要显式处理），不能让模型「假设成功」继续往下走；④ 输出层——关键数字/结论做程序化核对（与检索片段或数据库比对），不一致就降级为「需要人工确认」。补一句：防幻觉不能只靠提示词，提示词只能降低概率，兜底要靠程序和流程。

**Tool call 调错怎么处理。** 分错误类型：参数格式错（用 schema 校验直接拒绝并回灌错误信息，让模型改正）、参数语义错（比如查错了用户，要有权限与范围校验，越权直接拒绝而不是交给模型判断）、工具本身失败（重试有上限、退避、区分可重试与不可重试）、以及「模型选错了工具」（在返回里附上可用工具清单与选择提示，或加一个路由器先用规则/小模型定工具）。所有调用要有 trace，事后能复现「为什么选了它」。

**Skill 的生产流程。** 一个可复用的顺序：领域建模（这个 skill 负责哪类任务、输入输出是什么、边界在哪）→ 写 Spec（触发条件、步骤、可用工具、成功判据、失败处理）→ 写最小版本 → 用真实样例跑（至少覆盖正常、边界、恶意输入三类）→ 评估（准确率、遵循率、平均步数、成本）→ 上线 → 监控（成功率、人工接管率、异常分布）→ 迭代（把失败案例沉淀成评测用例，改提示词或加工具）。关键认知：skill 不是一段提示词，而是「提示词 + 工具 + 校验 + 评测集」的打包。

**怎么评估与监控。** 评估要分层：能力层（能不能做完）、质量层（结果对不对、格式对不对）、效率层（步数、token、时延）、安全层（越权、注入、敏感信息）。上线后监控同样分这四层，并保留抽样人工评审。没有评测集的 skill 不算上线，只能算实验。

**Skill 怎么自动进化。** 三步闭环：收集（线上失败样本 + 用户反馈 + 人工标注）→ 归因（分成「知识缺失、工具缺失、提示词歧义、模型能力不足」四类）→ 自动生成候选改动（补示例、改指令、加工具）→ 用评测集回归 → 通过才发布。可用的技术包括 few-shot 自动挑选、提示词优化（OPRO/APE 这类）、以及把成功轨迹蒸馏成示例。难点在「评测集要能覆盖真实分布」和「改动不能过拟合」，所以每次进化都要留一份 held-out 集。回答时给出这套闭环比报论文名更有用。

**多 Agent 范式。** 常见四种：主管-工人（supervisor/worker，一个编排者派活、汇总）、流水线（pipeline，按阶段串行，每段专职）、辩论/评审（多角色互评后收敛）、以及层级（agent 树，每层负责不同粒度）。Sub-Agent 适合「子任务边界清晰、上下文可独立、结果可校验」的场景，比如代码检索、单文件重构、资料汇总；不适合需要全局上下文强相关的任务。主给子的输入要「少而准」：只传任务目标、必要约束、以及子任务需要的文件/片段，用结构化字段而不是整段对话；返回只要求「结果 + 证据 + 未解决项」，中间过程不往上带，避免上下文爆炸。

**分布式事务怎么答。** 先给结论：订单 + 库存这种跨服务场景，优先「最终一致 + 补偿」，而不是强一致。方案对比：本地消息表（可靠消息，业务侵入小，要消费端幂等）、事务消息（RocketMQ，半消息 + 回查）、TCC（Try 预占、Confirm 确认、Cancel 释放，控制力强但要写三个接口并处理悬挂/空回滚/幂等）、Saga（长流程编排 + 补偿，适合多步）、Seata AT（自动 undo log，简单但全局锁影响性能）。选型依据是「一致性要求 + 业务能否接受中间态 + 补偿成本」。要能说清 TCC 的三个坑：空回滚（Try 没执行就收到 Cancel，要记录事务状态直接返回成功）、悬挂（Cancel 先于 Try 到达，要拒绝后续 Try）、幂等（重复 Confirm/Cancel 结果一致）。

**缓存与 DB 一致性。** 常见策略是 Cache Aside：读时未命中回源并回填，写时「先更新 DB 再删除缓存」。为什么会不一致：并发下「读旧值回填」覆盖了删除（延迟双删缓解）、删除失败、主从延迟。更强的方案是订阅 binlog 异步失效（Canal），把「删缓存」从业务代码里解耦；对一致性要求极高的场景干脆不让缓存做判断依据。全量加载 + 异步同步适合「读多写少、数据量小」的配置类数据，不适合频繁变更的业务数据。

**Redis 锁与 Redlock。** 单实例是 `SET key val NX PX ttl` + Lua 校验删除；主从架构下主节点写完还没同步就宕机，锁会丢，Redlock 用「多数派独立节点加锁成功 + 总耗时小于 TTL」来降低这个风险，但它在网络分区与时钟漂移下仍有争议（Martin Kleppmann 的批评）。工程结论：锁用来减少并发冲突，正确性靠「幂等 + 唯一约束 + 状态机」兜底；对强一致要求高的资源，用数据库行锁/乐观锁版本号更可靠。

**Zset 与跳表。** Zset 是「字典（member→score）+ 跳表（按 score 排序）」双结构，字典保证 O(1) 查分数，跳表保证按分数范围查询与排名。跳表是多层链表：底层是完整有序链表，每层以概率 1/2 向上建索引，查找从最高层开始，向右走到超过目标就下降一层，期望 O(log n)。插入时先找到每层的前驱节点，随机决定新节点的层数（层数不超过当前最大层 +1），然后在各层插入并更新前向指针与 span（用于 ZRANK）。删除反向操作。相比红黑树，跳表实现简单、范围查询天然有序、并发下更容易做无锁（各层独立更新）。

**MQ 能不能不丢。** 只能做到「尽量不丢」，要靠三段各自保证：生产端（同步发送 + 重试 + 确认机制，或事务消息）、Broker（刷盘策略：同步刷盘 + 主从同步复制，`acks=all`）、消费端（处理完再提交位点，失败重试，幂等消费）。任何一段用异步都可能丢。所以「不丢」等于「不丢 + 可能重复」，业务必须幂等。

**只有一个消费者在消费的所有可能原因。** ① 分区/队列数只有 1（或者远少于消费者数）；② 分区分配不均——消费者加入/退出触发 rebalance 后分配策略导致倾斜，或某些消费者订阅了不同的 tag/filter；③ 消费能力差异——某台机器处理快、其他机器卡在下游超时，导致 lag 集中；④ 消费线程数配置不同（有的实例 `consumeThreadMin/Max` 设得很小）；⑤ 消息 key 高度集中，几乎所有消息都路由到同一个分区；⑥ 部分消费者根本没启动成功或订阅关系不一致（group 名不同、topic 名不同）；⑦ 消费被限流/被熔断，实际在处理但速率极低；⑧ 客户端版本差异导致的分配协议不一致。排查顺序是先看「分区分配结果」，再看「各实例的消费 TPS 与耗时」，最后看订阅配置。

**ConcurrentHashMap。** JDK 8 的实现是「数组 + 链表 + 红黑树」，锁粒度降到单个桶：`put` 时若桶为空用 CAS 直接放头节点，否则 `synchronized` 锁住该桶的头节点再插入；链表长度 ≥8 且数组长度 ≥64 时转红黑树（否则先扩容），查询 O(log n)。哈希冲突用链地址法，`spread` 把高位异或到低位减少碰撞。size 用 `baseCount + CounterCell[]` 分段计数（类似 LongAdder）避免热点。扩容支持多线程协助迁移（`ForwardingNode` 标记已迁移的桶）。CAS 的「比对再覆盖」就是 `compareAndSwapObject/Int`：只有当内存中的值等于期望值时才写入新值，否则失败重试，依赖 CPU 的 `cmpxchg` 指令。ABA 问题是一个值从 A 改成 B 又改回 A，CAS 以为没变过；解法是加版本号（`AtomicStampedReference`）或用 `AtomicMarkableReference` 标记是否被改过。

**AI coding 的 loop（举新需求）。** 读需求与相关代码 → 写一份可验收的 SPEC（接口、数据结构、边界、测试用例）→ 让模型出最小实现 → 跑测试 → 按失败项逐个修 → 自查 diff（范围、异常处理、无关改动）→ 补文档与测试 → 提交。把「验收标准」写成可执行脚本是关键，否则人只能靠读代码判断对错。
