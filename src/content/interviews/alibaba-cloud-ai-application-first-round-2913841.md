### 《参考解析》

**wait/notify 实现栈的常见错误**：① `wait()` 必须放在 `while (!条件)` 里而不是 `if` 里——被唤醒后条件可能已经被别的线程改掉，JDK 也允许虚假唤醒，用 `if` 会直接走错分支；② 必须持有同一个对象的 monitor（同一个 `synchronized` 锁）才能调 `wait/notify`，否则抛 `IllegalMonitorStateException`；③ 生产者和消费者共用一个条件队列时用 `notify()` 只唤醒一个线程，可能唤醒的是同类线程导致双方都睡死，规范做法是 `notifyAll()`，或者用 `ReentrantLock` 的 `notFull` / `notEmpty` 两个 `Condition`；④ 修改状态和通知的先后顺序、异常路径下的锁释放、以及栈满/栈空的判断条件都要写对；⑤ 工程上根本不该手写，直接用 `ArrayBlockingQueue` / `LinkedBlockingQueue`。

**红包算法（100 元 / 10 人 / 单人 ≤ 90）**：先做可行性判断——总额 100 落在 `[10 × 最小额, 10 × 90]` 区间内，有解。常用两种做法：① 二倍均值 + 上限修正：每次随机区间取 `[0.01, min(剩余均值 × 2, 90, 剩余金额 − 0.01 × 剩余人数)]`，最后一人拿剩余；这个写法天然保证每人 ≥ 0.01 且不超过上限。② 先切分后修正：按二倍均值切出 10 份，把超过 90 的部分回收再分配给未达上限的人，直到收敛。实现上必须用「分」做整数运算避免浮点误差，并且每一步都校验「剩余金额 ≥ 剩余人数 × 0.01」，否则后面必然出现负数或无解。可以补一句产品视角：真实红包还会要求方差可控（不要出现一人 90 其余人分 10）和并发安全（用 Redis 原子扣减预分配总额）。

**大模型幻觉与缓解**：幻觉指模型生成了流畅但不真实、无出处的内容，来源包括预训练语料中的噪声与长尾知识缺失、解码采样的随机性、以及「必须回答」的指令压力。缓解手段分四层：检索层——RAG 引入外部事实并要求给出引用；工具层——用检索/计算/代码执行做事实核验，让模型「查了再说」；解码层——降低温度、约束解码、self-consistency 多次采样投票；训练层——SFT/RLHF 教会模型说「不知道」，做事实性对齐；产品层——展示引用来源、给出置信度、关键场景人工复核。要强调这些手段只能降低概率，不能根除。

**RAG 的完整流程**：离线侧是文档接入（PDF/HTML/表格的解析与版面还原）→ 清洗去噪 → 切分（按标题层级/语义切，保留重叠窗口）→ 生成 embedding → 写入向量库并带上元数据；在线侧是 query 改写与扩展 → 多路召回（向量 + BM25 关键词混合）→ 重排（cross-encoder 精排、去重、多样性）→ 上下文拼装（截断、加引用标记）→ LLM 生成 → 后处理（引用校验、无依据则拒答）。工程上还要有增量更新、权限过滤（不同用户可见文档不同）、缓存，以及一套评测集（检索命中率、答案忠实度、拒答率）。

**怎么在同事 A、B 的两套 RAG 之间选**：从五个层面打分：效果（离线评测集 + 人工盲评 + bad case 分布）、成本（单次查询的模型/向量库/重排开销，含 token 单价）、性能（端到端 P95 延迟、吞吐、并发下的稳定性）、工程（可维护性、增量更新与数据同步、可观测性、与现有工具链的契合度）、风险（数据安全与权限、供应商锁定、幻觉兜底策略）。落地方式是先定义权重和评测集，再跑线上 A/B 实验用真实业务指标（解决率、人工转接率、满意度）决定，而不是靠 demo 观感拍板。

**MCP**：Model Context Protocol，一套把「模型如何调用外部工具与数据」标准化的开放协议。结构是 client-server：宿主应用（IDE、Agent 框架）里的 MCP client 通过 stdio 或 HTTP+SSE 连接到 MCP server，server 暴露三类能力——tools（可调用的函数，带 JSON Schema 描述参数）、resources（可读取的数据/文件）、prompts（预置提示模板）。价值在于把原来 M×N 的适配工作变成 M+N：工具提供方写一次 server，所有支持 MCP 的宿主都能用，同时权限边界更清晰、便于审计。

**几十亿商品的库表设计**：先定访问路径再定存储——按商品 ID 查详情、按卖家查列表、按类目/关键词搜索，这三条路径的 QPS 与延迟要求不同，通常对应不同系统（分片 MySQL 存商品主数据 + 缓存 + 搜索引擎承载检索）。具体考虑：① 分片键选择，按商品 ID 哈希能保证均匀但按卖家查会跨片，按卖家 ID 分片则热点卖家会倾斜，常用折中是商品 ID 分片 + 卖家维度建异构索引表（用 binlog 同步）；② 全局唯一 ID（雪花算法/号段模式）与路由表；③ 冷热分离与大字段外置，详情/富文本/图片走对象存储，宽表只留列表与检索字段；④ 读写分离 + 多级缓存（本地缓存 + Redis），热点商品单独做本地缓存防击穿；⑤ 写入异步化：binlog → MQ → 搜索引擎，保证最终一致；⑥ 扩容与变更：预分片、在线 DDL、双写 + 数据校验 + 灰度切流。答题时先说清「先问清查询模式，再谈分片」，比直接背分库分表方案更得分。
