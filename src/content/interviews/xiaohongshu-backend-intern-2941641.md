### 《面试题目》

1. API 从发送到响应有哪些耗时？你觉得包含哪些环节？
2. 项目相关：写扩散是怎么实现的？
3. 如果一个大 V 的粉丝有百万，怎么把帖子推送给每个粉丝？
4. 场景题：设计一个排行榜，按实时点赞量排序。
5. 追问：ZSet 里的字段如何设计，业务含义是什么？
6. 场景题：小红书要给每一个用户发一条通知，如何实现？
7. 追问：用户只能看到一条 +1 的提示，只有点进通知才能看到内容，怎么设计？
8. 为什么会想到用 Redis 缓存？

### 《参考解析》

**一次 API 请求的耗时构成**：客户端侧有 DNS 解析、TCP 握手、TLS 握手、请求排队；网络传输有 RTT 与带宽（首字节时间 TTFB 与完整响应时间是两个指标）；服务端有网关鉴权与限流、业务逻辑、下游调用（RPC / DB / 缓存，多个串行调用会累加）、序列化；回程还有响应体大小与客户端渲染。回答时按「客户端 → 网络 → 服务端 → 回程」分层，再说每一层最常用的优化手段（连接复用、CDN、批量与并行下游调用、缓存、分页与字段裁剪），比只答「首字和完全返回」完整得多。

**写扩散与百万粉丝的大 V**：写扩散（fan-out on write）是发帖时把内容写进每个粉丝的收件箱，读时直接读自己的收件箱，读路径极短；代价是写放大，百万粉丝就是百万次写。工程上的标准答案是**推拉结合**：普通用户走写扩散保证读快；粉丝数超过阈值的大 V 走读扩散——发帖只写自己的发件箱，粉丝拉取时在「自己的收件箱」和「关注的大 V 列表」两处归并（读时合并 + 缓存结果）。此外收件箱写入要异步化（消息队列削峰）、按活跃度分层（长期不活跃的粉丝不写，登录时再补），以及限制收件箱长度（只保留最近 N 条）。

**ZSet 排行榜的字段设计**：`ZADD rank:note:20261117 <点赞数> <noteId>`，member 是被排序对象的唯一标识（笔记 ID），score 是排序依据（点赞数）。点赞时 `ZINCRBY` 原子加一，取榜 `ZREVRANGE key 0 49 WITHSCORES`，取某条排名 `ZREVRANK`。要注意的三点：score 相同会导致顺序不稳定，用「分数 + 时间戳」拼成复合 score 或用 tie-break 规则；分页不要用 `ZRANGE offset` 深翻（O(logN + offset)），按上一页最后一个 score 用 `ZREVRANGEBYSCORE` 续取；榜单规模大时按维度分片（如按领域 / 地域分 key），冷热分离，并设置过期时间。ZSet 底层是跳表 + 哈希表，这也解释了为什么面试官会顺手问跳表。

**全站广播通知与「只显示一条 +1」**：给每个用户写一条通知记录是典型的写扩散，用户量大时不可行。正确做法是**拉模式 + 未读计数**：维护一个全局通知列表（或按类型分几个列表），每个用户只存一个「已读到的位置游标」和一个未读计数；每次有新通知只对在线用户推一条「有新消息」的信号并把计数加一，用户点进通知页时拉取列表并按游标计算未读。这样写成本从「用户数」降到「1 次全局写 + 在线推送」，读成本由用户实际打开时才付出。计数用 Redis 的 `INCR` 维护，落库做异步对账。

**为什么用 Redis 缓存**：要落到「这个场景下省掉了什么」。排行榜的读远多于写、且要求毫秒级返回排序结果，用 MySQL 每次 `order by count desc limit 50` 都要扫描与排序，Redis ZSet 用跳表把排名与区间查询做到 O(logN)，点赞的自增也天然原子。回答时补一句边界：Redis 不是唯一存储，榜单是派生数据，可从 DB 重建；持久化与主从切换后要用 DB 对账修复，避免把缓存当账本。
