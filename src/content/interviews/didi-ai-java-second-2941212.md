### 《参考解析》

**为什么还要硬编码**：模型擅长理解与生成，不擅长「必须每次都对」的确定性问题。数据清洗中的字段映射、单位换算、枚举归一、时间格式、必填校验，用代码做是确定且可测试的，交给模型则每次结果可能不同、还会引入幻觉；规则还承担合规与审计要求（谁能看到什么、哪些结论必须留痕）。合理分工是：确定性的抽取、校验、路由用代码，语义理解、归纳、生成用模型，模型输出再过一遍代码校验。被问「Prompt 足够明确还会不会幻觉」时，答案是会——幻觉来自模型对未见信息的补全，不来自指令不清；指令只能降低概率，不能消除，所以关键字段必须由程序校验或人工确认。

**总结的生成时机与落点**：预生成适合结果稳定、可离线计算的场景（面试结束后统一生成报告），成本可控、失败可重试；实时更新适合需要随对话推进的场景，但每次调用都要带全上下文、成本高、延迟敏感。工程上常用「增量摘要 + 终稿生成」：过程中按轮次或时间窗做增量摘要，结束时基于摘要与关键片段生成终稿。结果落库要存版本、模型、提示词版本与输入摘要，便于复现与追责。

**工作流耗时与并发**：先把耗时拆开（模型调用、检索、数据拉取、后处理），再针对最大项优化：能并行的节点并行（如多个维度同时抽取）、能缓存的缓存（相同输入与配置命中缓存）、模型调用做流式与超时控制、长任务异步化并给前端进度。并发控制要有限流（按用户、按下游）、队列与优先级、失败重试与熔断；任务状态机要能恢复，进程重启后未完成任务可续跑。

**岗位识别与路由**：先做规则兜底（关键词、岗位字典、公司库精确匹配），命中即走确定路径；未命中再用模型分类，输出限定在枚举集合内并给出置信度，低置信度走通用路径或追问。路由结果要可观测（记录命中规则、模型输出、最终路径），便于发现分类漂移。

**用 AI 接手历史系统**：先建索引（目录结构、模块职责、接口清单、数据表关系），再让 AI 基于检索回答具体问题，而不是把整个仓库丢进上下文。有效做法是「从调用链入手」：给一个入口（接口、定时任务、页面），让 AI 追出调用链与数据流，再由人核对关键分支。要防范 AI 编造不存在的函数与配置，所有结论回到源码行号验证。

**AI 代码的把关**：分三层——生成时给足约束（接口签名、类型、现有工具函数、禁止引入的依赖）；生成后跑确定性检查（编译、类型、lint、单测、集成测试）；合入前人工看关键路径（边界、错误处理、并发、权限）。对表结构与索引的审核要点是：字段类型与长度是否匹配业务、是否可空、默认值、唯一约束、索引是否覆盖真实查询（看 where/order by/join 的列顺序）、写入放大的代价、以及上线与回滚方案（大表加索引要评估锁与耗时）。AI 给的建议必须用执行计划验证。

**线上功能异常借助 AI**：先收集事实（错误日志、请求 ID、时间窗、影响面、最近变更），再让 AI 在给定证据内做假设排序，而不是让它自由发挥。排查路径是「最近变更 → 依赖状态 → 数据异常 → 代码缺陷」，每一步都用日志或数据验证。AI 的价值在快速读大量日志、比对代码差异、生成复现步骤，最终判断仍由人做。

**Java 线程安全**：不可变对象、线程封闭（ThreadLocal、栈上变量）、同步（synchronized、ReentrantLock）、原子类与 CAS、并发容器（ConcurrentHashMap、BlockingQueue）、以及用消息队列把并发变成串行。要讲清 `volatile` 只保证可见性与禁止重排、不保证原子性；`ConcurrentHashMap` 的分段/CAS 演进与复合操作要用原子方法（`computeIfAbsent`）而不是「先 get 再 put」。

**分布式并发安全**：单机锁在多实例下失效，需要分布式锁（Redis 的 SET NX PX + Lua 释放、ZooKeeper 临时顺序节点）或把并发收敛到单点（按业务键哈希到同一实例、数据库唯一约束、队列串行消费）。分布式锁要处理锁过期与业务未完成（看门狗续期或 fencing token）、主从切换丢锁、以及重入问题。更强一致的方案是数据库乐观锁/悲观锁或状态机（`UPDATE ... WHERE status = ?`），用影响行数判断是否抢到。

**线程池场景**：适合把「提交与执行解耦」的任务——异步通知、批量计算、IO 密集的远程调用聚合、需要限流的后台任务。不适合长时间阻塞且需要严格顺序的任务，也不适合 CPU 密集且数量巨大的计算（会争抢核）。参数按任务类型定，队列必须有界，拒绝策略要明确（调用方执行、降级、丢弃并记录），并监控活跃线程数、队列长度、拒绝次数与任务耗时。
