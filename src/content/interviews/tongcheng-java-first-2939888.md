### 《参考解析》

**集合体系与线程安全**：`List` 里 `ArrayList` 基于数组、随机访问快、扩容 1.5 倍；`LinkedList` 基于双向链表，头尾操作快但随机访问要遍历。`Map` 里 `HashMap` 数组 + 链表 + 红黑树，链表长度到 8 且容量到 64 才树化；`TreeMap` 按 key 有序，红黑树实现，增删查 O(log n)。`Set` 基本是 `Map` 的包装。线程安全的老实现是 `Vector`、`Hashtable`、`Collections.synchronizedXxx`（整表加锁、性能差），并发场景用 `ConcurrentHashMap`、`CopyOnWriteArrayList`、`ConcurrentLinkedQueue`。`ArrayList`、`HashMap`、`LinkedList` 都不是线程安全的，多线程写会出现覆盖、丢元素甚至死循环（JDK 7 的 HashMap 扩容）。

**ConcurrentHashMap 的实现**：JDK 8 之后是「Node 数组 + 链表 + 红黑树」，用 CAS + `synchronized` 锁单个桶头节点，锁粒度是桶而不是整表；`size` 用 `baseCount` 加 `CounterCell` 分散计数，避免所有线程争同一个变量；扩容支持多线程协助迁移（`ForwardingNode` 标记已迁移的桶）。get 不加锁，靠 volatile 读保证可见性。它保证单次操作的原子性，但「先查再改」这类复合操作要用 `computeIfAbsent`、`merge`、`putIfAbsent` 或外部加锁。

**异步任务怎么拿请求上下文**：请求上下文一般放在 `ThreadLocal` 里，线程池复用线程、任务在别的线程执行，直接读会拿到旧值或 null。解决方案有三层：手动把上下文作为参数传进任务（最稳，但要改签名）；用 `TaskDecorator`（Spring）在提交任务时捕获当前线程的上下文并在任务内 set/restore；用 `TransmittableThreadLocal`（TTL）配合它提供的线程池包装，解决「线程池复用导致上下文串味」的问题。要注意在任务结束的 finally 里清理，否则线程池复用时会把上一个请求的上下文带给下一个请求。

**线程不安全什么时候发生**：共享可变状态 + 多线程并发读写 + 缺少同步。典型有三类：复合操作的竞态（i++ 的读改写不是原子操作）、可见性（一个线程改了标志位另一个线程看不到，需要 volatile 或锁）、有序性（指令重排导致半初始化对象被发布，双重检查单例要加 volatile）。不变对象、线程封闭（局部变量）、`ThreadLocal`、不可变集合都不会有这个问题。

**堆与栈**：堆存对象实例和数组，线程共享，是 GC 的主战场，分新生代（Eden + Survivor）与老年代；虚拟机栈是线程私有的，每个方法调用一个栈帧，存局部变量表、操作数栈、动态链接、返回地址。`StackOverflowError` 来自栈深度超限（递归过深），`OutOfMemoryError` 来自堆或元空间不足。

**InnoDB 的存储**：默认页 16KB，磁盘与内存以页为单位交换。数据按主键组织成聚簇索引，叶子节点直接存整行；二级索引叶子存主键值，回表再查聚簇索引。所以「数据和索引是同一棵树」，表就是主键索引。页内是记录链表 + 页目录（稀疏槽位做二分），页间是 B+ 树；非叶子只存键和页号，扇出大、层数低，三到四层就能撑住上亿行。

**主键索引与唯一索引**：相同点是都要求唯一、都建 B+ 树、都能加速等值查询。区别在于主键索引是聚簇索引、叶子存整行，一张表只有一个；唯一索引是二级索引、叶子存主键值，需要回表，一张表可以有多个，且允许多个 NULL（NULL 不参与唯一性判断）。主键不允许 NULL，通常自增或由业务生成；唯一索引常用于业务唯一约束（订单号、手机号）。

**索引失效的常见场景**：对索引列做函数或运算（`where date(create_time)=...`、`where id+1=...`）、隐式类型转换（字符串列传数字）、`like '%xxx'` 前导通配、`or` 连接的条件中有一侧没索引、联合索引不满足最左前缀、范围查询之后的列用不上索引、`is null` / `!=` / `not in` 在某些数据分布下会选择全表、优化器估算回表成本过高时主动放弃索引。字符集或排序规则不一致的 join 也会失效。

**怎么看用了哪个索引**：`explain` 看 `key`（实际使用的索引）、`possible_keys`、`rows`（估算扫描行数）、`type`（`ref`、`range`、`index`、`ALL`）、`Extra`（`Using index` 覆盖索引、`Using filesort`、`Using temporary`）；MySQL 8 可以用 `explain analyze` 看真实执行耗时，或用优化器追踪 `optimizer_trace` 看为什么选了这个索引。指定索引用 `force index(idx_name)`，但它是提示不是强制，优化器认为代价过高时仍可能不用；生产上更常见的是改写 SQL 或调整索引，而不是长期 force。

**参数调优**：面试官问「实际做过吗」是想听具体动作与结果。可讲的点：慢查询日志定位 Top SQL、`innodb_buffer_pool_size` 调到物理内存的 60%~70%、`innodb_flush_log_at_trx_commit` 与 `sync_binlog` 在安全与吞吐间取舍、连接池大小与 `max_connections`、大事务拆分、`innodb_io_capacity` 适配 SSD。每一条都要带「改前多少、改后多少、怎么观测」，只报参数名等于没做过。

**策略模式**：把一组可互换的算法抽象成接口，运行时按条件选择实现，消除大段 if-else。项目里常见做法是「接口 + 多个实现类 + 一个 Map 注册表（Spring 注入后按类型放到 `Map<String, Strategy>`）」，调用方只依赖接口。扩展新策略时只加一个类，不改调用方，符合开闭原则；代价是类变多、需要治理命名与注册。

**Redis Lua 的用途**：把「读—判断—写」合成一次原子执行，避免并发下的检查与更新分离。典型场景是库存扣减（判断库存 > 0 再减）、令牌桶限流、分布式锁的加锁与解锁、幂等键的 setnx + 过期。Lua 在 Redis 单线程里执行，天然串行，但脚本要短，长脚本会阻塞其他请求；集群模式下脚本涉及的所有 key 必须在同一个 slot（用 hash tag）。

**为什么引入 RabbitMQ**：解耦（下单后发消息，积分、通知、风控各自消费）、削峰（突发流量先进队列，消费端按能力拉取）、异步（把非核心链路从主流程摘出去降低 RT）、最终一致（配合本地消息表或事务消息）。代价是系统复杂度上升：消息丢失、重复、乱序、积压都要处理。

**幂等**：同一请求执行一次和执行多次的结果一致。做法分几层：数据库唯一索引兜底（最可靠）；业务状态机（已支付不能再支付）；Redis `setnx` 或去重表记录请求号（注意过期时间与原子性）；乐观锁版本号；消息消费侧用「消息 ID + 消费记录表」。真正的幂等键要选业务上唯一的维度（订单号、外部流水号），而不是时间戳或随机数。

**两段实习怎么比较**：不要只夸后一段。给一个维度对比：第一段让你建立了工程习惯（代码规范、评审、测试），第二段让你独立负责一个模块、学会在不确定需求下推进。用具体例子说明「提升」是什么——从「按文档实现」到「能自己定义问题并给出方案」。

**AI 工具与模型**：可以按用途分层讲：对话与写作（通用大模型）、代码补全（IDE 插件）、Agent 编程（会读写文件、跑命令的工具）、检索（联网搜索）。差异在上下文长度、工具调用能力、延迟与价格、中文语料质量。回答时最好带一个真实对比：同一个任务两个模型各做一遍，谁漏了边界、谁多绕了步骤。

**Agent Harness**：Harness 是「模型之外的执行骨架」——它负责把用户请求变成一轮轮模型调用，提供工具（读写文件、执行命令、检索）、维护消息历史与上下文压缩、处理工具结果回填、做权限与沙箱、记录轨迹与成本。模型只负责决策，Harness 负责让决策能落地并被观测。项目里可以从「工具注册与 schema、循环终止条件、错误重试、上下文裁剪、评测与回放」几个点讲自己做了什么。

**考研计划**：如实回答即可，重点是把选择和职业目标连起来——想尽早进工程体系就说清楚为什么实践优先，想补基础就说清楚缺什么、怎么补。不要贬低读研，也不要给一个和简历矛盾的答案。
