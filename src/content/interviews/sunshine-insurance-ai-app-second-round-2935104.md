### 《参考解析》

**RAG 的整体流程要按「离线建库 + 在线问答 + 评测」三段讲。** 离线：多源采集（文档、网页、工单、数据库）→ 解析清洗 → 分块（语义切分、父子块、保留标题层级与表格结构）→ 向量化并写入向量库（带来源、版本、权限、时效等元数据）。在线：query 理解（改写、纠错、意图分类）→ 混合召回（向量 + 关键词）→ 过滤（权限、时间、版本）→ 精排（cross-encoder）→ 上下文装配（去重、截断、引用标记）→ 生成（约束只依据给定材料、无依据就说不知道）→ 后处理（引用回填、敏感词、格式校验）。评测：召回层看 Recall@K 与 MRR，生成层看忠实度/相关性（人工标注或 LLM-as-judge），工程层看 P99 延迟、单次成本与失败率。任何一环没有指标，答起来都像背概念。

**MCP 选路的两层决策要分清「模型选」和「代码选」。** 工具多的时候不能把所有工具一次性塞给模型——工具描述会挤爆上下文，模型也容易乱调。工程上的做法是两层：第一层用代码做确定性过滤（按用户权限、当前场景、业务线筛出候选集，甚至按关键词/意图先路由到工具组），第二层才是模型在候选集里选择，靠的是工具名与 description 里写清的「什么时候用、什么时候不要用」。进一步可以做「工具检索」：把工具描述向量化，按 query 检索 top-k 工具再交给模型。要做好还得有：参数 JSON Schema 严格定义、必填项校验由代码兜（不靠模型自觉）、工具粒度不要太细（避免组合爆炸）、以及调用日志与命中率统计来持续优化描述。

**意图澄清提升准确率的核心是「少问、准问、问在关键槽位上」。** 维护一张槽位表（业务对象、时间范围、关键标识），每轮只检查还缺哪些必填槽位，用一两个问题补齐；高置信度时不要澄清（否则体验极差），低置信度或多解时才澄清。澄清问题要自然、给选项而不是开放式审问；用户改口时要能覆盖旧槽位并清空依赖它的下游结果；设置最大澄清轮数，超过就转人工或给默认值并说明假设。效果度量上要看「澄清后一次答对率」与「平均澄清轮数」的权衡——澄清次数上升但准确率不涨，就是问错了地方。

**用不用框架，答「看场景与团队」比站队更好。** 手搓（直接用模型 SDK + 自己的工具注册与循环）胜在可控、可调试、依赖少，适合工具集固定、行为要求严格的业务；框架（LangGraph、LlamaIndex、AutoGen、Spring AI 等）胜在预制了图编排、状态管理、记忆、回调与可观测，适合流程复杂、需要多 Agent 协作或快速迭代的场景。实际项目里常见折中：主干用轻量自研的编排（把「模型循环 + 工具表 + 状态机」写清楚），只在检索、评测这类成熟能力上引库。

**工具调用失败要分类处理，而不是统一重试。** 先分四类：① 参数错误（模型给错 schema）——把校验错误原文回给模型让它自我修正，重试一次，仍错就降级；② 权限/前置条件不满足——不要重试，直接把原因告知用户并给下一步建议；③ 外部临时故障（超时、5xx、限流）——指数退避重试 + 熔断，必要时切备用工具；④ 结果为空但调用成功——这不叫失败，要区分「没查到」和「查失败」。另外三条工程纪律：重试必须幂等（写操作带幂等键）、设置最大步数与总超时防止无限循环、每次失败都要落 trace 便于回放。

**上下文与长短期记忆要分层设计。** 短期是当前会话的上下文窗口：靠裁剪策略（保留系统提示 + 最近 N 轮 + 与当前问题相关的历史片段）、摘要压缩（把早前多轮压成要点）、以及结构化状态（把已确认的槽位与结论放进状态对象，而不是散在对话里）。长期是跨会话记忆：只存稳定事实与重要结论（偏好、身份、在做的项目），带来源与时间戳，用检索按需注入而不是全量塞。写入要经过抽取 → 置信度 → 确认/规则；更新要有冲突消解（用户显式更正优先）与 TTL；用户要能查看与删除。最容易被追问的是「怎么防止模型猜的东西被当成用户事实」——答案是模型推断只进候选区，标 provenance，未经确认不参与强约束。

**Redis 分布式锁与数据一致性要一起答。** 锁的三要素：互斥（`SET key value NX PX` 或 Redisson 的 Lua 脚本）、超时与续期（租期大于业务耗时预估 + 看门狗续期）、安全释放（校验 value 是自己的再删，用 Lua 保证原子）。单机 Redis 在主从切换时可能丢锁，严谨场景用 Redlock（有争议）或 fencing token（下游用单调递增令牌拒绝过期持有者）。一致性上要区分「锁保护的临界区」与「缓存与 DB 的一致性」两件事：后者常用先更新 DB 再删缓存 + 延迟双删、订阅 binlog 补偿，接受最终一致；强一致只能靠把关键写收敛到单点事务或数据库约束。

**常用 Agent 框架的回答要带上选型理由。** LangChain/LangGraph（图编排、状态机、生态最全）、LlamaIndex（检索与索引能力最强）、AutoGen / CrewAI（多 Agent 对话与分工）、OpenAI Agents SDK / Anthropic 的工具循环（轻量、贴近模型原生能力）、Spring AI / LangChain4j（Java 体系）。选型看四点：编排复杂度、可观测与回放能力、团队语言栈、以及锁版本后的升级成本。

**hook 与 CLAUDE.md 的区别是「触发时机」与「承载内容」都不同。** CLAUDE.md 是给模型的**常驻上下文**：项目约定、命令、目录结构、注意事项，每次会话都会读进上下文，作用是「让模型知道规矩」。hook 是给宿主程序的**事件回调**：在工具调用前后、会话开始/结束等生命周期节点上执行确定性脚本，可以用来做格式化、lint、拦截危险命令、注入额外上下文、记录审计，作用是「让系统强制执行规矩」。一句话概括：CLAUDE.md 是软的、靠模型遵守；hook 是硬的、由程序执行。答题时补一句「重要的约束不能只写在文档里，要落到 hook 或 CI 这类机器可判的位置」，正好呼应 AI 工程的基本纪律。

**HRBP 那几题考的是稳定性与动机一致性。** 老家、base 地、投了哪些行业，本质上是在判断你会不会来、来了会不会走，回答要和简历与前面的技术面一致（比如前面说做过保险 AI 项目，这里就别把互联网排第一）。爱好与最近看的书要能讲出细节，说「看书」却说不出一本就很减分。整场 20 分钟，节奏很快，技术题基本不给展开空间，所以每题的答案要有一句能立刻抓住重点的结论句。
