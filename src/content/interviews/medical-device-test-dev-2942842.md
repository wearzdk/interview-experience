### 《参考解析》

**从需求到用例的拆解**：先做需求分析，把需求文档拆成「业务规则 + 数据约束 + 异常分支」，标出可测点；再按维度铺用例——功能覆盖主流程、分支与边界，性能看响应时间、吞吐与并发下的资源占用，安全关注越权、注入、敏感数据明文与传输加密，UI 关注布局、文案、交互反馈与多分辨率，兼容性覆盖浏览器、系统版本、设备与网络条件。每个用例写清前置条件、步骤、预期结果与优先级，需求与用例用矩阵双向映射，最后评审补漏。

**级联功能不能只做界面黑盒**：级联（省市区、父子分类）正确性往往在数据层出错——前端展示对但接口返回了非法组合、数据库里落了脏的父子关系。至少要在三个层面校验：接口返回的层级与字段是否与规则一致、数据库关联字段与冗余字段是否同步更新、级联删除或禁用后历史数据如何处理。用 SQL 直接查关联表验证，比只看页面可靠。

**用事务验证异常场景**：在测试库上显式开启事务，执行被测操作后不提交，另开一个会话观察其他连接看到的数据（验证隔离级别与未提交读），再制造接口超时或异常中断，检查是否留下半写的数据；最后回滚清理。业务代码里若没有正确的事务边界，异常时会出现「主表已写、子表未写」的脏数据，这类问题只能靠构造异常并查库发现。

**死锁规避**：破坏四个必要条件之一即可——互斥难以消除，主要靠破坏「请求并保持」（一次性申请全部资源）、「不可剥夺」（持锁超时后释放重试）、「循环等待」（给资源编号，所有线程按同一顺序申请）。工程上更常用的是给锁加超时（`tryLock(timeout)`）、缩小临界区、避免在持锁期间调用外部服务或获取第二把锁。排查用 `jstack` 看线程互相持有的锁，数据库侧看 `SHOW ENGINE INNODB STATUS` 里的最近一次死锁。

**判定表**：先列条件桩（影响结果的所有输入条件，如会员等级、订单金额、是否有券），再列动作桩（系统要执行的动作，如打折、免运费、拒绝），然后枚举条件的取值组合，合并结果相同的规则，删掉不可能出现的组合，每一列就是一条用例。它适合业务规则多、条件互相组合的场景（优惠券叠加、审批流），能避免漏掉组合分支。

**状态码 200 不等于业务成功**：HTTP 200 只说明请求被服务端正常处理并返回，业务结果在响应体里（`code`、`success`、`bizCode`）。常见坑是网关或框架把业务异常包装成 200，前端只看状态码就当成成功。校验要三层：链路层看状态码与耗时，协议层看响应结构与字段类型是否符合契约，业务层比对数据库或下游系统的实际状态——例如下单接口返回成功，还要查订单表是否真的落库、库存是否扣减、消息是否发出。

**覆盖率口径**：用例执行率只说明「写了的都跑了」，需求覆盖率才反映「需求都被测了」。做法是把需求拆成可测点清单（一个需求拆成若干验证点），每个验证点关联至少一条用例，覆盖率 = 已关联验证点 / 全部验证点。反推缺口时按模块列「需求条目—验证点—用例」三列，没有用例的验证点即缺口；再结合线上缺陷反查——某个模块线上问题多而用例少，就是覆盖不足的信号。

**为什么选 Playwright**：相比 Selenium，Playwright 自带等待与自动重试、支持多浏览器同一套 API、能直接拦截与修改网络请求、内置 trace 与视频录制，调试成本低；对 AI 生成的脚本也更友好——选择器推荐基于角色与文本（`getByRole`、`getByText`），比脆弱的 CSS 路径稳定。代价是生态与社区规模小于 Selenium，部分老旧浏览器与企业内嵌浏览器不支持。
