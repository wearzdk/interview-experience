### 《参考解析》

**Redis 幂等的 key 与删除顺序。** 幂等的本质是「同一业务键在窗口内只允许成功执行一次」，key 的 TTL 就是这个窗口的长度。窗口必须大于「最大可能处理时长 + 下游重试延迟」，否则会出现锁已过期、业务还在跑的并发窗口，第二个请求拿到锁后重复执行。正确做法有三条：其一，TTL 用 P99 处理时长乘一个安全系数，并配合超时熔断，让业务不可能运行超过 TTL；其二，删除时用 Lua 脚本比对 value（或 fencing token）再删，避免 A 的锁过期后被 B 拿到、A 处理完把 B 的锁删掉；其三，value 里放单调递增的 token，写业务数据时校验 token 未被更新，即「锁 + 版本号」双重保护。先删 key 再处理业务的问题在于把幂等窗口缩小到了处理完成之前——一旦删除成功而业务失败，重试进来就是新的一次执行；不删、靠 TTL 自然过期的问题则是失败场景下窗口内无法重试，需要额外的失败标记位。实践上更稳的方案是用「状态机 + 唯一索引」兜底：数据库层面用业务唯一键做最终幂等，Redis 只做前置的快速拦截，不把它当成唯一防线。

**Agent 的停止条件要当成一套降级策略。** 面试官连问四层，指向的是「停止」不是一个 if，而是多层条件的组合：模型自身输出终止信号（stop token、显式的 finish 动作）；状态机判定目标条件已满足（需要抽取的字段齐了、该调用的工具都返回了、校验通过）；预算耗尽（最大轮次、最大 token、最大时长）；外部强制中断（用户取消、风控、超时）。关键在每一层都要有对应的输出状态，不能把「预算耗尽」伪装成「任务完成」。返回给用户时应当给出结构化结果：已完成的部分、未完成的步骤、失败原因、可继续的入口（例如「已查到 3 条中的 2 条，是否继续」），而不是一段看起来完整实则残缺的答案。工程上还要区分「可重试的未完成」与「不可重试的失败」，前者允许用户点继续，后者要明确报错。

**线程池参数与 IO 密集型的线程数。** 线程池满员后的行为由拒绝策略决定，JDK 默认是 `AbortPolicy`（抛 `RejectedExecutionException`）；此外还有 `CallerRunsPolicy`（调用线程自己执行，天然反压）、`DiscardPolicy`、`DiscardOldestPolicy`。队列无界时最大线程数确实永远用不上——任务先在队列里排队，只有队列满了才会扩到 maximumPoolSize，这是很多人配错的地方。参数推导的依据是利特尔法则：并发线程数 ≈ QPS × 平均 RT（秒）。IO 密集型任务的 RT 大部分在等待，所以线程数可以远大于 CPU 核数，常见经验值是核数 × (1 + 等待时间/计算时间)，但更可靠的是先按 QPS × RT 估算，再用压测验证。CPU 密集型则接近核数（或核数 + 1）。配完必须配套：有界队列、明确的拒绝策略、线程池隔离（不同下游不共用）、以及队列长度和拒绝数的监控。

**上下文压缩的评估。** 「压缩完再答一遍看答案对不对」只能证明结果可用，不能证明依据没丢，因为模型可能用压缩后的残缺上下文猜对。可操作的评估分三层：事实层用抽取式比对，把压缩前后的事实三元组（实体、数值、时间、约束）抽出来做集合差异；指令层用规则校验，检查系统约束、禁用项、输出格式是否仍在；推理层才看最终结果，但要求模型同时输出依据链（引用了哪几条上下文），再人工或模型评审依据链是否完整。工程上还可以做「压缩前后同题对照」：同一批问题分别用原始上下文和压缩后上下文各答一次，比较答案一致性、依据引用覆盖率与 token 节省比例，把三者放在一张表里看，避免为了省 token 牺牲正确率。

**Skill 与 workflow 的取舍。** workflow 是确定性编排：步骤、分支、调用顺序由代码写死，优点是可控、可测、成本可预估，缺点是无法处理长尾、每加一种情况就要改代码。Skill 是把「这类任务该怎么做」的知识与流程交给模型按需加载，由模型决定顺序与工具选择，优点是覆盖面广、维护成本低。把 workflow 改成 Skill 的常见动机是分支爆炸与维护负担：原来几十个 if 分支，每来一个新场景就要发版。边界划分的原则是「确定性逻辑进代码，判断与表达进 Skill」：权限校验、计费、幂等、数据读写这些必须确定的行为放代码；怎么写、按什么顺序问、遇到异常怎么补救放 Skill。判断一个 Skill 写得好不好，看三点：新模型能否零样本按它做事（可复现性）、同一输入多次执行结果是否稳定（稳定性）、出错时能否定位到 Skill 的哪一条（可诊断性）。自测手段是构造一组意图覆盖用例跑离线评测，成本控制靠小模型初筛加人工复核高分与低分两端。

**带抖动与幂等的重试器。** 作者自陈的三个问题都成立：抖动加在固定值上等于没加，正确做法是 full jitter（`sleep = random(0, base * 2^n)`）或至少 decorrelated jitter，目的是把重试打散、避免重试风暴同步；不可重试的错误（参数校验失败、4xx 业务错误）必须白名单式分类，只对超时、限流、5xx、连接失败重试；幂等键必须在进入重试器之前生成一次并透传，不能在每次重试里重新生成。完整实现还需要：最大重试次数与总时长上限、尊重下游返回的 `Retry-After`、熔断与半开（连续失败到阈值就停止重试直接失败）、以及重试指标（次数、成功率、放大倍数）。面试官那句「会把下游打死」指的是重试放大：下游 500 时如果每一层都重试 3 次，三层叠加就是 27 倍流量，所以重试只应放在最外层，内层失败要快速向上抛。
