### 《参考解析》

1. **JVM 高 CPU 排查**：先用 `top -H -p <pid>` 找到高 CPU 线程的十进制 ID，再用 `printf '%x\n' <tid>` 转成十六进制，在 `jstack <pid>` 输出中搜索对应的 `nid=0x...`。结合线程状态和连续多次栈快照，判断是死循环、频繁 GC、锁竞争还是热点方法；内存泄漏则配合 `jcmd`、`jmap` 和堆转储分析工具定位持续增长的对象及其引用链。
2. **CAS 与 ABA**：CAS 比较内存中的当前值与期望值，相等时原子写入新值，否则失败重试。ABA 表示值从 A 变为 B 又变回 A，单纯比较值无法发现中间变化；可用带版本戳的 `AtomicStampedReference`，其 `compareAndSet` 依次接收期望引用、新引用、期望版本戳和新版本戳。
3. **Redis 持久化**：RDB 定期生成紧凑快照，恢复快但可能丢失最近一次快照后的数据；AOF 追加写命令，可按刷盘策略缩小数据丢失窗口，但文件和恢复成本更高。fork 后通过操作系统的写时复制保留快照视图；AOF 则通过重写把同一 key 的历史命令压缩为能恢复当前状态的最小命令集合。
4. **Netty 线程模型**：boss 线程组负责监听端口和接收连接，把建立好的 Channel 注册给 worker；worker 线程组中的 EventLoop 负责连接上的读写事件和 ChannelPipeline 回调。耗时业务不能阻塞 I/O EventLoop，应提交到独立业务线程池并把结果安全地写回 Channel。
5. **订单超时系统**：订单创建与库存预占需要可幂等，超时任务按到期时间分片存储或进入支持定时投递的消息链路。消费者收到超时事件后必须以数据库中的订单状态为准，通过条件更新只把仍未支付的订单从待支付改为已取消；只有状态更新成功的一方释放库存。任意时长可用时间轮、分层时间桶或定时任务扫描到期索引实现，不能假定 RocketMQ 固定延时等级支持任意时间。
6. **消息可靠性验证**：给消息分配全链路唯一 ID，记录生产成功、Broker 确认、消费成功和业务落库四个阶段的计数与延迟。通过阶段间差值、积压量、重试与死信数量、抽样对账和故障注入定位丢失窗口，再决定是否需要本地消息表、事务消息或补偿任务。
