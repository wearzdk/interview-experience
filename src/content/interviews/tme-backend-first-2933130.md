### 《参考解析》

**算法两题：换题是在给你第二次机会**

字符串相乘考的是竖式乘法的工程化实现：结果数组开到 m+n 长度，逐位相乘后统一处理进位，注意前导零和「任何数乘 0 返回 0」；难的不是算法，是下标不越界、进位不丢。接雨水是双指针或单调栈的经典题：双指针维护左右最大高度、每次移动较矮的一侧，O(n) 时间 O(1) 空间；单调栈按「行」算积水，好解释但容易写错下标。第一题卡住时，把思路口述出来再承认卡点，比沉默硬写划算——面试官换一道同档题，本质是想看思维过程，不是在记录你答不出。

**海量流水表分库分表：先定分片键，再谈扩容**

流水表的特点是只追加、按时间查、量大且冷热分明。分片键常取「用户 ID + 时间」的组合：按用户哈希分片保证同一用户的流水落在同一库，按时间分区或按月分表负责冷热分离。要交代四件事：全局唯一 ID（雪花或号段，别用数据库自增）；跨分片查询（运营报表走离线数仓或 ES，不在线上做全分片扫描）；扩容（双倍扩容或一致性哈希，先双写再迁移，避免停服）；分布式事务（同库本地事务，跨库最终一致加对账）。分库分表不是目的，先问清数据量和查询模式——几千万行加对索引就能撑住的表不该上分片。

**Redis 集群与丢数据：异步复制是根因**

常见架构有三种：主从解决读扩展与备份，哨兵解决故障自动切换，Cluster 用 16384 个槽做分片，客户端按 key 的 CRC16 取模路由，跨槽的多 key 操作要用 hash tag 绑到同一个槽。丢数据主要来自异步复制——主节点写完就回客户端，尚未同步给从节点时宕机，这部分就没了；哨兵切换时旧主恢复后重新接入，还可能覆盖新主的数据。缓解靠 WAIT 命令或 min-replicas-to-write 限制「至少 N 个副本确认才算写成功」，代价是延迟上升。持久化上 RDB 是快照、恢复快但会丢最后一次快照之后的写；AOF 记命令，everysec 最多丢一秒，always 最安全但吞吐差，生产多用混合持久化。这两问其实是一问：先问会不会丢，再问丢了怎么办，答案都指向持久化、副本确认与业务侧幂等重放。

**穿透、击穿、雪崩：三个问题三种解法**

穿透是查一个不存在的 key，请求绕过缓存直达数据库——用布隆过滤器挡，或把空结果短暂缓存；击穿是某个热点 key 恰好过期，瞬间大量请求同时回源重建——用互斥锁只放一个请求进去（注意锁超时与双重检查），或逻辑过期加异步刷新，让读请求先拿旧值；雪崩是大量 key 同时失效或缓存整体不可用——过期时间加随机抖动、多级缓存、集群高可用，再加限流降级兜底。三者容易混，答题时先给一句判据再展开，比三条并列背方案更容易讲清。

**三种日志：层级不同，职责不同**

redo log 是 InnoDB 的物理日志，记「某页被改成了什么」，配合 WAL 让事务提交时只写日志不刷脏页，崩溃后用它前滚；undo log 是逻辑日志，记反向操作，支撑回滚与 MVCC 快照读；binlog 是 Server 层的逻辑日志，记语句或行变更，用于主从复制和按时间点恢复。最容易考的是两阶段提交：redo 写完置 prepare，binlog 落盘成功才把 redo 置 commit，崩溃恢复时两份日志才对得上，主从也不会出现主库有、从库没有的差异。追问常落在「binlog 为什么替代不了 redo」——一个是逻辑记录、随机写，一个是页级物理记录、顺序写，恢复速度与语义都不同。

**AI 辅助开发与多模态 RAG：考的是边界感**

从 PRD 到上线借 AI，要拆成阶段讲：需求澄清时让模型列歧义清单和验收标准草案；设计时让它出接口与表结构的候选方案，由人拍板；编码时生成样板代码和单测；联调时用它读日志、比对差异。质量保证不能只说「我会 review」，要给机制：小步提交、每个 PR 带测试、CI 卡 lint 与覆盖率、对生成代码做依赖与安全检查、关键路径人工复核。PRD 不清晰时，先列出必须由产品确认的问题清单，附上自己的默认假设和影响面，把选择题抛回去而不是猜着做。多模态 RAG 的思路是先对齐再检索：图片和视频抽帧后用 CLIP 一类模型编码到与文本同一向量空间，或为每段素材生成文字描述再走文本检索；召回时做文本与图像混合，再用多模态模型重排和生成；工程上还要定切片粒度（单帧没意义，按镜头或段落切）、存储方案与延迟预算。
