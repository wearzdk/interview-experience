### 《面试题目》

1. 说说索引失效的场景。
2. 你在索引列上做过函数运算吗？当时怎么发现的？
3. `WHERE DATE(create_time) = '2024-05-20'` 为什么用不上索引？怎么改写？
4. 隐式类型转换「最阴」在哪？怎么排查出来？
5. 为什么反向（int 列传字符串）不失效？
6. 联合索引 (a, b, c)，`WHERE a = 1 AND b > 10 AND c = 2` 里 c 还能用上吗？
7. 设计联合索引时列的顺序怎么排？
8. 你判断一次慢查询是不是索引失效，看哪几样东西？

### 《参考解析》

**函数包裹索引列**：订单列表页要按天查询，写成 `WHERE DATE(create_time) = '2024-05-20'`，`create_time` 上明明有索引，`EXPLAIN` 却是 `type=ALL`、`key=NULL`。原因很朴素：B+ 树里存的是原始值，把整列套进 `DATE()` 之后，每一行都要先算函数值才轮到比较，索引的有序性就用不上了。改成左闭右开区间后 `type` 变成 `range`。同类写法还有 `id + 1 = 100`、`amount * 2 > 500`。

**隐式转换最阴的地方**：`t_user.phone` 是 `varchar(20)` 且有索引，前端把手机号当数字传过来，SQL 写成 `WHERE phone = 13800000000`（没有引号）。结果是全表扫描，但 SQL 看起来干干净净，没有任何函数，光看语句发现不了。原因还是同一类：字符串列与数字比较时列被转成数字。排查手段是把 `EXPLAIN` 之后的 `SHOW WARNINGS` 也打出来，能看到优化器重写后的语句里带着 `cast(...)`。帖主后来在 DAO 层统一做参数类型校验，字符串字段一律用 `String` 入参。

**范围截断的机制**：联合索引 `(a, b, c)` 上 `WHERE a = 1 AND b > 10 AND c = 2`，a 是等值不影响，b 走范围扫描，c 在「不同的 b 值之间」不是全局有序的，因此只能作为过滤条件，不能用来缩小扫描区间。注意区分：这不是 c 没建索引，而是在这一次查询里用不上索引的有序性。

**联合索引的排列原则**：等值条件列放前面，范围条件列尽量往后放，`ORDER BY` 用到的列紧跟在等值列后面。但这只是默认原则，实际要看业务查询分布——如果某个范围列几乎每条 SQL 都带，把它放最后即可，没必要为了「覆盖全部列」硬凑一个超长索引。索引列越多，写入维护成本越高。

**判断三样东西**：`EXPLAIN` 的 `type` 与 `key` 告诉我「有没有走」；`rows` 的估算行数告诉我「走了多少」；`SHOW WARNINGS` 里优化器重写后的语句告诉我「为什么没走」。三步基本能覆盖常见情况，比背清单可靠。

**本质一句话**：索引失效的本质是优化器没法用 B+ 树的有序性做定位，只能逐行判断。函数包裹、隐式转换、前缀断裂，都是这条本质的不同表现形式。
