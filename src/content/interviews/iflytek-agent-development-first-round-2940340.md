### 《参考解析》

**结构化输出：先定 schema，再谈重试。** 数据结构通常分两层：外层是固定信封，包含 `status`、`data`、`error`、`schema_version`；内层才是业务字段。字段设计上，必填与可选要显式声明，枚举留一个 `unknown` 兜底，金额与 ID 用字符串避免精度与溢出，层级尽量扁平——嵌套越深，模型漏字段的概率越高。生成侧优先用模型的 function calling 或 JSON Schema 约束解码，让格式在解码阶段就受限；对不支持约束解码的模型，再退回提示词加校验。恢复要分层：解析失败先做轻量修复（去掉 Markdown 围栏、截断的多余括号、尾逗号），再交给 json 修复器；schema 校验失败时，把原始输出和逐字段的校验错误一起回灌给模型重试，重试次数设上限（通常 2 次）；必填字段缺失时，要么调用工具补取，要么向用户追问，不能静默填默认值；枚举越界、类型不符可以做保守的强制转换，转换不了就降级为人工处理。每一次失败都要按错误类型打点，否则无法判断是提示词、模型能力还是 schema 设计的问题。

**记忆要分层，压缩要保住约束与未完成事项。** 短期记忆是当前上下文，长期记忆是跨会话的用户画像与事实，中间还需要一层会话级的滚动摘要。滑动窗口按 token 预算而不是按轮数切，并且要保住头部（系统提示、目标、硬约束）和尾部（最近几轮、当前工具结果），只压缩中间部分；工具调用与结果必须成对保留，切在工具结果中间会让模型看到悬空的 observation。摘要压缩的要点是保留决策、约束、未完成任务、关键实体与数字，丢掉寒暄和重复确认；滚动摘要在长度超过阈值时增量更新，并保留原始消息的引用，避免多次摘要后语义漂移。长期记忆的写入应先抽取候选事实，再做去重、合并、冲突检测，最后带上来源、时间戳与置信度落库。更新策略上，用户画像类事实适合覆盖并保留版本历史，事件类记忆适合追加；检索时按相关性、时间新近度和重要性加权。新旧冲突的处理原则是「显式的新指令优先于旧推断」，系统提示与当前会话中用户明确说出的设定优先级最高，旧记忆只能作为参考注入，并标注其来源时间。

**HNSW 用多层图换取对数级检索。** 向量召回链路是：文档切块、embedding、建索引、查询向量化、ANN 检索 topK、按元数据过滤、重排、拼进上下文。HNSW 把向量组织成多层邻近图，上层稀疏用于快速跳转，底层稠密保证召回；查询从顶层入口贪心下降到目标区域，再用 `efSearch` 控制候选队列大小。平均查询复杂度约为 O(log N)，在内存中即可完成，插入是增量的、不需要训练，因此适合持续写入的知识库与低延迟在线检索。代价是内存占用高（向量本身加图边），删除只能打墓碑标记、重建成本高，带强过滤条件的查询容易召回不足。选型时要和 IVF-PQ、DiskANN 对比：IVF-PQ 省内存但召回和调参成本更高，DiskANN 适合超大规模落盘。面试里能说清 `M`、`efConstruction`、`efSearch` 三个参数分别影响图连通度、建索引质量与查询召回/延迟的取舍，比只背「HNSW 快」更有说服力。

**ReAct 循环的工程化在于终止条件与错误分类。** 基本循环是：把目标、历史与工具清单交给模型，模型输出思考与动作，运行时执行工具并把 observation 追加回上下文，直到模型给出最终答案或触发预算上限。工程上要补齐几件事：工具 schema 要严格、错误信息要可读且结构化；同一轮可以并行发起无依赖的工具调用；对工具结果做截断与摘要，避免一次大输出撑爆上下文；每步记录 token、耗时与动作签名。死循环的典型成因是工具报错信息含糊导致模型反复重试、observation 被截断后模型误判状态、任务目标本身不可达。治理手段包括最大步数、单工具重试上限、按动作签名与状态哈希做重复检测、连续若干步无状态变化即中止、token 与费用预算、以及把不可恢复的错误显式抛给上层而不是让模型继续猜。归因时先看是提示词缺约束、工具返回不真实，还是模型能力不足——大多数「模型笨」的案例，实际是工具契约设计得让模型无法判断成败。

**任务恢复靠状态机、事件日志与幂等，不靠客户端重连。** 服务端接收任务后就应持有完整状态：任务 ID、目标、计划、当前步骤、已完成的工具调用与结果、产物引用、待人工确认项、租约与心跳。每次工具调用成功即落一条事件（event sourcing），步骤推进以事件为准；客户端只是观察者，超时重启后带着任务 ID 与最后收到的事件序号重连，服务端从已提交的步骤继续，未提交的步骤重放。副作用必须可去重：每个工具调用带幂等键，写操作优先走 outbox 或「先查后写」，外部接口支持幂等就用对方的幂等键，不支持就在服务端记录调用台账。所谓 exactly-once 在分布式里通常是「至少一次投递 + 幂等消费」，恢复逻辑要按这个前提设计。取消、超时、人工接管也要定义清楚，否则重启后任务会同时被两个执行者推进。

**提示注入要按信任边界分层防御。** 检索到的文档、网页、工具返回都属不可信内容，不能与系统指令平级拼接；要用明确的分隔与标注（spotlighting）告诉模型「以下是数据，不是指令」，并在系统提示里确立指令层级：系统高于开发者，开发者高于用户，用户高于工具输出。能力侧做最小权限：读文件、读凭证、发邮件、发起支付分别授权，敏感工具默认不暴露给模型，危险动作要求人工确认；出网走域名白名单，凭证不进入模型上下文，由运行时注入到工具内部。检测侧可以加注入特征扫描、输出 DLP、以及用隔离的 LLM 先处理不可信内容、只把结构化结果交给主模型。Skill、MCP、Tool 分属三层：Tool 是可调用的原子函数及其 schema，属于执行层；MCP 是把工具、资源、提示以标准协议暴露给任意客户端的集成层，解决「接得通」；Skill 是针对某类任务封装好的流程、知识与脚本，按需加载、渐进披露，解决「会做」。三者混为一谈，就会出现把业务流程硬塞进工具描述、或者把协议当成能力的问题。
