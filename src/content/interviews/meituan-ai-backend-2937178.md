### 《面试题目》

1. 请做自我介绍。
2. 选一个最熟悉的项目，讲清输入、关键模块、数据流、输出、难点，以及如何验证正确性。
3. 将模型生成的代码放进沙箱，就一定安全吗？还有哪些潜在风险？
4. 原方案为什么频繁分配完整 Frame？你的方案具体减少了哪部分分配？
5. 如果后续模块尚未读完，上游就把 Buffer 放回池中，会发生什么？
6. 调用方提供的 Buffer 容量不足时怎么办？
7. Agent 流式响应为什么会出现重复序列化？
8. pprof 中相关函数的 alloc_space 占比从 40% 降到 16.7%，是否意味着系统总内存下降？
9. 如果流式返回 100 个片段，是否需要把完整响应序列化 100 次？
10. Agent 调用工具超时后能直接重试吗？应该如何处理？
11. 哪些操作是幂等的？修改文件、追加内容分别如何判断？重复执行追加操作会怎样？
12. 你所说的「五层 Context 压缩」和「三层 Memory 管理」分别是什么？

### 《参考解析》

**沙箱不等于安全**：沙箱只约束了执行环境，不约束意图。剩余风险至少有四类：一是网络，沙箱内仍可能外连并把数据带出，需要出网代理与域名白名单；二是资源，CPU、内存、磁盘、进程数不设上限会把宿主拖垮；三是逃逸面，内核漏洞、挂载目录过宽、特权容器都会让隔离失效；四是供应链与提示注入，模型被网页内容诱导执行危险命令，或装入了恶意依赖。因此除了隔离，还要有命令准入、路径白名单、产物审计与人工确认高风险操作。

**Frame 分配与池化**：原方案每个数据包都新分配一块完整 Frame，包含头部与预留空间，短包占多数时浪费明显。优化点通常在三处：按大小分级复用缓冲、把头部与载荷拆开避免整体拷贝、以及减少中间层转发时的二次分配。收益要能对应到具体分配点，而不是笼统说「用了池」。

**回池时仍未读完**：上游把 Buffer 放回池中后，池会把它分配给新的写入方，正在读的模块会读到被覆盖的数据，表现为偶发的数据错乱或协议解析失败。这类问题在压测里往往不复现，只在并发高时出现。正确做法是引用计数或所有权移交：谁持有谁负责释放，归还只减计数，计数归零才真正回池；或者用代际号校验，读侧发现代际变化即报错而不是静默读脏数据。

**容量不足**：三种处理各有语义。分片继续写适用于流式场景，但要保证下游能重组；扩容并拷贝适用于可以重新分配的场景，代价是一次拷贝；返回明确错误让调用方重试适用于契约清晰的接口。关键是不要让框架静默截断，截断会造成难以定位的数据丢失。

**重复序列化**：流式响应每一帧都触发一次「把当前累计结果整体编码」，n 个片段就是 1+2+…+n 的工作量，属于典型的 O(n²)。改成增量编码、只编码本次新增片段，或者先累积到阈值再统一编码一次，都能把复杂度降回线性。

**alloc_space 下降不等于总内存下降**：pprof 的 alloc_space 是采样估算的累计分配字节数，下降说明分配压力变小，但常驻内存还取决于对象存活时间、GC 是否把内存归还操作系统、以及池化本身持有的空闲缓冲。要证明总内存下降，得看 RSS、heap_inuse、GC 次数与 pause 的同期变化，并做关闭池化的对照实验。

**100 个片段是否需要 100 次全量序列化**：不需要，也不应该。正确做法是维护一个可追加的编码器或先收集再一次性序列化；如果协议要求逐帧下发，就只序列化增量部分，并保证下游能按帧拼接。

**工具超时与重试**：超时不等于失败，请求可能已经在服务端执行完，只是响应没回来。非幂等操作直接重试会造成重复写入。处理方式是给每次调用带幂等键、重试前先查询执行状态、只对明确幂等的操作自动重试，并把「未知结果」作为一种独立状态交给上层决策。

**幂等判断**：读操作天然幂等；覆盖写文件在内容确定时近似幂等，但依赖当前内容的操作（如「在第一行插入」）不幂等；追加写完全不幂等，重试一次就多一段内容。判断依据是「同一请求执行两次，系统的可观察状态是否相同」，而不是操作名称。追加类操作要靠去重键或版本号做条件写入。

**Context 与 Memory 的分层**：Context 是本次请求窗口内的信息组织，常见五层是 system 指令、任务与约束、近期对话、检索到的资料、工具结果；Memory 是跨请求持久化的信息，常见三类是会话工作记忆、历史情节记忆、稳定画像与偏好。两者的关系是 Memory 按需检索后进入 Context，而不是把所有历史都塞进窗口。
