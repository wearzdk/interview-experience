### 《参考解析》

**「自己做了哪些改写」怎么答**：面试官在验证项目的真实性与你的贡献度。有效答法是给出「原始方案—遇到的问题—你的改动—验证结果」四段：比如原始框架的记忆只做向量召回，长对话里事实被截断，你改成了「事实表 + 摘要 + 近期原文」三层，并补了冲突覆盖规则；改动后用一组需要早期信息的问答做了对比，准确率从多少到多少。要能指出原实现的不足与你的取舍，而不是复述 README。如果确实是参考开源实现，如实说明参考了哪一部分、自己补了哪一部分，比含糊其辞更安全。

**记忆管理的分层**：常见做法是把记忆分成三层——工作记忆（当前上下文窗口内的最近若干轮原文）、情景记忆（历史对话的摘要，按段滚动生成）、语义记忆（抽取成结构化事实，如用户偏好、已确认的结论、关键实体）。检索时按当前问题召回相关情景与事实，拼进上下文。spine / refold / ace 这类具体方案可以按「如何组织层级、如何压缩、如何检索」三问来讲，重点说清你的实现里「什么进事实表、什么进摘要、什么丢弃」，以及冲突时以谁为准。

**项目做了多久 + 是否看论文**：这个问题在判断你是不是「刚看完论文就来包装」。回答要给时间线（什么时候开始、迭代了几个版本、每版解决了什么问题），并说清论文里的方法在你的场景里哪部分不适用（比如论文假设长上下文、你的模型上下文小，所以要更强的压缩）。不要背论文名词，讲你实际踩的坑。

**Redis 底层**：单线程事件循环 + epoll 多路复用处理连接；数据结构上 String 用 SDS（记录长度、预分配、二进制安全）、Hash 小数据用 listpack 大数据用哈希表、ZSet 用跳表 + 字典、List 用 quicklist（listpack 组成的双向链表）、Set 用 intset 或哈希表。过期是惰性 + 定期抽样，淘汰按 `maxmemory-policy`。持久化 RDB 快照与 AOF 日志，主从异步复制，哨兵/集群做高可用与分片。要能按「为什么快、内存怎么省、故障时丢什么」三条线讲。

**MySQL 底层**：InnoDB 以聚簇索引组织数据，主键索引叶子节点存整行，二级索引叶子存主键；页为单位（默认 16KB），Buffer Pool 缓存页，修改先写 redo log（WAL）再异步刷脏页，undo log 支持回滚与 MVCC；binlog 做归档与复制。事务靠 redo（持久性）、undo + 读视图（隔离性）、锁（一致性）。MVCC 用隐藏的事务 ID 与 undo 版本链加 ReadView 实现快照读。索引是 B+ 树，联合索引按列顺序排序。这些是「MySQL 底层」的标准答法，回答时挑与项目相关的部分展开。

**课程表与「输出不能完成的节点」**：本质是拓扑排序 + 环检测。建图（先修课指向后续课）、统计入度，把入度为 0 的课入队，BFS 逐个出队并减邻居入度；遍历结束后入度仍大于 0 的节点就是环上的节点（不能完成）。注意「输出不能完成的节点」与「输出拓扑序」不同：只输出拓扑序会漏掉环里的节点，要在 BFS 结束后收集 `indegree[i] > 0` 的所有节点。手写时先把函数签名、输入格式、返回值定好，再写主逻辑，最后用两个用例（无环、有环、自环）跑一遍；帖主「框架搭好但编译没过」说明平时要练到能一次写对语法与边界。

**有真实用户的项目怎么答**：如果没有，不要编。可以给「有真实使用场景」的替代：课程项目被同学实际使用、开源仓库有人提 issue 与 PR、给开源项目提交过被合并的补丁（并说清改了哪个模块、为什么被接受）、给社团或实验室做的工具。编造「有用户」在追问下极易露馅（用户量、留存、部署在哪、怎么运维都答不上）。帖主自述「github 开源贡献是编的」，这属于高风险动作，不值得。

**怎么学习**：给出可验证的方法而不是口号：看官方文档与源码（能说出最近读的一个模块）、跟一个系统性课程（MIT 6.824、CSAPP 之类）、用项目验证（学完 Raft 就实现一个 KV 存储）、写笔记与复盘。面试官问这题是在看你的信息源与自驱方式，答「刷面经」会减分。
