### 《面试题目》

1. 你先讲一下你们秒杀系统的全链路，从用户点按钮到订单落库，每一层做了什么？
2. 1000 件库存、10 万人抢，你怎么防超卖？库存分桶具体怎么分？
3. 缓存穿透、击穿、雪崩，你在项目里分别用什么手段解决的？
4. Redis 和 DB 的一致性你们怎么保证？为什么是删缓存而不是更新缓存？
5. MQ 削峰你们怎么做的？如果消费端积压了 500 万条消息，你怎么处理？
6. 手撕：单生产者单消费者的无锁环形队列怎么写？
7. 手撕：最小堆的 push 和 pop 怎么实现？
8. 追问：10 亿个整数里找最大的 k 个，怎么做？

### 《参考解析》

**秒杀全链路**。分五层讲：接入层把静态页全部推 CDN，按钮先置灰并在本地做倒计时，开抢前才放行；网关层按 userId 与 IP 双维度令牌桶限流，超阈值直接返回「活动太火爆」，挡掉绝大部分流量；扣减层把库存预热到 Redis，用 Lua 脚本把「判断余量 + 扣减 + 记录用户已购」做成一次原子操作，整个判断在内存里完成，数据库不参与；异步落单层在扣减成功后只投一条 MQ 消息并返回「排队中」，消费者按序创建订单、扣真实库存、写流水；结果层由前端轮询或长连接推送「成功/失败/排队中」。要点是把「抢」和「买」分开：抢是内存里的原子操作，买是异步的持久化，两者之间用消息队列解耦，并靠订单表的唯一索引兜住重复消费。

**防超卖与库存分桶**。1000 件拆成 10 个桶各 100 件，请求按 `userId` 哈希取模落到固定桶——同一个用户永远打同一个桶，桶内用 Lua 做「余量 > 0 才减」，单 key 热点被打散，锁冲突与 Redis 单分片压力都降一个数量级。数据库侧再用 `update stock = stock - 1 where stock > 0`，靠影响行数判断是否成功，行锁是最后一道防线；订单表对 `(user_id, item_id)` 建唯一索引，库存字段加非负约束。桶之间余量不均时做二次调度（跨桶借还），或者干脆做「预扣 + 回补」：先扣再校验总量，失败回滚。原则是宁可少卖不能超卖，超卖的补偿成本远高于少卖。

**缓存穿透、击穿、雪崩**。穿透是查不存在的数据，请求全部落到数据库：用布隆过滤器挡掉绝大多数非法 key，剩下的把空结果缓存一小段时间（如 60 秒）并加随机 TTL，同时对明显非法的 id 在入口做格式校验。击穿是热点 key 过期瞬间大量并发回源：用 singleflight 把同一 key 的请求合并成一次，或逻辑过期（value 里带过期时间，后台异步重建，读到的始终是旧值不阻塞）。雪崩是大批 key 同时过期或 Redis 整体不可用：TTL 加 0~300 秒随机，做本地缓存兜底，配熔断降级与限流，Redis 不可用时直接返回兜底数据而不是把压力转给数据库。

**为什么删缓存而不是更新缓存**。先更新数据库再删缓存（Cache Aside）是主流：删除是幂等且廉价的，更新缓存则要处理并发写的覆盖问题——两个请求几乎同时写库，后写库的先更新缓存，缓存里就留下旧值。此外很多缓存值是聚合计算的结果（多表 join、排序、计数），更新成本远高于删除后按需重建，而且「更新了但没人读」会白做功。剩下的窗口是「删缓存后、下次读之前」有请求把旧值读回缓存，处理方式是延迟双删（更新后删一次，隔几百毫秒再删一次）或订阅 binlog 用 Canal 异步删，删除失败进 MQ 重试、多次失败告警。要承认边界：这套方案给的是最终一致，如果业务连 1 秒脏读都不能接受，说明这条读路径不该上缓存。

**MQ 削峰与积压处理**。削峰的原理是「写入端全量入队、消费端按自身能力匀速消费」，峰值 10 万 QPS 写进 MQ，消费端按 2 万 QPS 处理，队列就是缓冲池；前提是消息不丢——生产端开同步刷盘或 `acks=all`，消费端手动提交位点并做幂等。积压 500 万条的处理顺序：先看是不是消费端变慢（下游超时、数据库慢查询、代码里的同步调用），修根因永远优先于扩容；再看分区数，消费者数量不能超过分区数，需要先扩分区；还不够就起临时消费者把消息转存到新 topic，用更多线程并行消费，处理完再切回原链路；最后是保护措施——消费端自己限流避免打挂数据库，重试 3 次进死信，监控 lag 超过阈值就告警，别等积压到千万才动手。注意扩分区会改变 key 的路由，依赖顺序的消息要谨慎。

**无锁环形队列（SPSC）**。数据结构是定长数组加 `head`、`tail` 两个 `std::atomic<size_t>`，容量取 2 的幂，用 `& (N-1)` 代替取模。生产者只写 `tail`、消费者只写 `head`，各读对方的索引：生产者先写数据，再 `store(tail, std::memory_order_release)`；消费者 `load(tail, std::memory_order_acquire)` 之后再读数据，用 acquire-release 建立写数据的 happens-before。空满判断牺牲一个槽位：`head == tail` 为空，`(tail + 1) & (N-1) == head` 为满。两个索引用 `alignas(64)` 分开，避免伪共享把性能拉回加锁水平。这套写法只对单生产者单消费者成立；多生产者必须上 CAS 循环，或者用 ticket 机制 + 序号数组。

**最小堆的 push 与 pop**。用数组存完全二叉树，下标 i 的左右子节点是 `2i+1`、`2i+2`，父节点是 `(i-1)/2`，不需要指针，缓存友好。`push` 放到数组尾部，与父节点比较、更小就交换，一路上浮到满足堆序；`pop` 取走堆顶，把尾元素搬到堆顶，再与较小的子节点交换、一路下沉。两者都是 O(log n)。建堆从最后一个非叶节点（`n/2 - 1`）开始向前下沉，整体是 O(n) 而不是 O(n log n)。C++ 里 `std::priority_queue` 默认是大顶堆，要小顶堆得传 `std::greater<int>`；要原地建堆用 `std::make_heap` 与 `std::push_heap`/`pop_heap` 配合 `vector`。

**10 亿个整数里找最大的 k 个**。先问清约束：k 有多大、内存有多少、能不能用外部存储。三种答法：k 很小（比如 100）时用一个大小为 k 的小顶堆流式扫描，堆顶是当前第 k 大，遇到更大的就替换并下沉，时间 O(n log k)、内存 O(k)；数据范围有限（比如都是 32 位整数）时用位图或计数排序，按值域从高到低扫，O(n + 值域)；内存放不下且 k 很大时走分治——把数据按高几位哈希或范围切成若干文件，分别求每块的前 k 大再归并，或用外部排序。如果是「找最大的一个」则直接一次遍历 O(n)。答题时把「题目没说内存限制」这一点主动点出来，再按不同假设给方案，比直接背堆更稳。
