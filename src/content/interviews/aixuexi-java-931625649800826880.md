### 《参考解析》

1. **多关键词匹配怎么优化**：`indexOf` 逐个关键词扫一遍是 O(关键词数 × 文本长度)，一万个关键词必然扛不住。可用的方案按适用面排序：
   - **AC 自动机（Aho-Corasick）**：先把所有关键词建成 Trie，再补 fail 指针，然后对文本做一次线性扫描就能同时命中全部模式串。时间复杂度是 O(文本长度 + 命中数)，这是这个问题最标准的答案。
   - **前缀树 / 双数组 Trie**：如果关键词之间有明显公共前缀，能省掉大量重复比较。
   - **正则合并**：把关键词拼成一个大正则交给 RE2 / Hyperscan 这类引擎，适合关键词数量中等且变更不频繁的场景。
   - **哈希 + 滑动窗口**：只做「是否包含」而不需要知道命中了哪个词时，可以先按关键词长度分组、把文本切成等长片段做哈希比对，实现简单但覆盖不全。
   实际工程里还有一层：关键词表可能上万条且频繁变，所以通常把 AC 自动机预编译好常驻内存，变更时双缓冲切换，避免每次请求重建。
2. **分片键怎么选**：目标是三件事同时满足——数据均匀、查询能带上分片键（避免全库扫描）、后续能扩容。常用的分片键是业务主键（商户 ID、用户 ID、订单 ID），因为它几乎出现在所有查询条件里。选完之后要专门检查倾斜：如果某个商户的数据量比中位数高一两个数量级，按 ID 取模会把压力全压在一个库上，这时可以对该商户做二次分片（比如 `merchant_id + 子键` 组合），或者在分片键前面加一个盐值把热点打散。
3. **数据倾斜的针对性处理**：先量化再处理，别凭感觉拆。手段有几种：热点单独拆库/拆表（大商户走独立分片）；分片键加盐（在 key 前拼一个 0~N 的随机前缀，查询时同时查 N 个分片再聚合，读放大换写均衡）；把大商户的明细按时间二次分区；以及冷热分离，把历史数据归档出去。要注意「盐值方案」会让范围查询变复杂，得先确认业务查询模式能不能接受。
4. **XXL-JOB 为什么能秒级触发**：核心是调度中心的时间轮 + 预读机制。调度中心不是每秒扫一遍全表，而是把所有待触发任务按触发时间放进时间轮，到点才唤醒对应任务；同时会对「未来 5 秒内要触发」的任务做预读（`preReadCount`），提前从数据库拉到内存，避免每次触发都查库。执行器侧定期心跳注册，调度中心按路由策略（轮询 / 一致性哈希 / 分片广播）选一台下发。要注意的是它本质仍是「准点」而不是硬实时，秒级触发会有毫秒到百毫秒级的抖动。
5. **SQL 优化的一般流程**：先确认这条 SQL 在业务上是不是必须这么写（能不能减少返回列、能不能加过滤条件下推）；然后 `EXPLAIN` 看访问类型、估算行数、是否回表、是否出现 `Using filesort` / `Using temporary`；接着检查索引设计是否匹配 `where` + `order by` + `group by`，必要时建覆盖索引；最后看数据量和统计信息。常见改写有：深分页改游标、子查询改 join、`or` 改 `union all`、避免在索引列上做函数运算。
6. **预期走 A 索引却没走**：可能的原因是统计信息过期导致优化器估错行数、A 索引的选择性确实差、条件里发生了隐式类型转换或函数运算让 A 失效、返回列太多导致回表成本高于全表扫、以及存在一个更优的覆盖索引。排查手段是 `EXPLAIN` + `EXPLAIN ANALYZE` 对比估算与实际、`ANALYZE TABLE` 刷新统计信息、必要时用 `FORCE INDEX` 验证假设。`FORCE INDEX` 可以强制走指定索引，但它只是验证工具，长期方案应该改 SQL 或改索引，因为强制之后数据分布一变就会变成新的坑。
7. **缓存穿透 / 击穿 / 雪崩**：穿透查的是不存在的数据，用布隆过滤器或空值缓存挡；击穿是单个热点 key 过期瞬间的并发冲击，用互斥锁或逻辑过期；雪崩是大量 key 同时失效或集群整体故障，用随机过期时间、多级缓存、限流降级。锁加在「缓存未命中之后、回源之前」这一段：拿到锁的线程去查库并回填缓存，没拿到的短暂等待后重试读缓存。要注意锁的粒度按 key 走，别用一把全局锁；另外锁内要设超时，否则回源卡住会把整个缓存层拖死。
