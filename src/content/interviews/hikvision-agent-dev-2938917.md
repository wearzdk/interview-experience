### 《面试题目》

1. 自我介绍。
2. 讲一下你对于多 Agent 的了解，你是如何设计的，实际的运行原理是什么？
3. 如果我想跨设备协作，比如一台电脑的 Agent 到另外一台电脑上 Agent 工作，应该怎么做？
4. 你有过多个 Agent 互相协作、自动化处理任务的经验吗？讲述一下。
5. 讲一下你在日常生活中怎么利用 AI 提效的，比如辅助游戏、组会任务、课堂作业等等。
6. 对于 Skill 分层，你是如何进行设计的，每一层的内容是什么？分层的目的或者作用是什么？
7. 除了从网上的 Skill 进行改编，你有没有自己完整独立设计过 Skill，怎么设计的？
8. Agent 会混淆对于 Skill 的选择，具体是多少体量的 Skill 会出现这种情况，你觉得原因是什么？具体的场景是什么？
9. 市面流行的 Agent 了解吗？他们各自的优劣势可以讲一下吗？
10. 团队成员介绍部门业务（约 10 分钟）。
11. 反问：作为实习生，进入之后日常主要负责的事情是什么？

### 《参考解析》

**多 Agent 的设计要讲清分工与通信**：常见形态有三种——主从（一个编排者拆任务、派给专职 Agent、汇总结果）、对等（Agent 之间通过消息总线协商）、流水线（按阶段串行，每段一个 Agent）。运行原理要落到机制：任务如何拆解（规划器或固定流程）、上下文如何传递（共享状态、消息、还是只传摘要）、冲突如何裁决（谁有最终决定权）、失败如何重试与兜底。回答时给一个真实例子：目标是什么、拆成几个角色、每个角色用什么工具、跑一次多久、哪一步最容易出错。没有实践就如实说理解程度，比编一个架构更安全。

**跨设备协作的落点是「把执行能力暴露成服务」**：两台机器之间不能直接共享进程，做法是在目标设备上跑一个 Agent 运行时（或执行器），暴露受鉴权的接口（HTTP/WebSocket/RPC）接收任务、执行工具、回传结果；发起方只负责编排与结果汇总。要处理的关键问题：身份与授权（谁能在这台机器上执行什么）、能力发现（对方有哪些工具与权限）、断连与超时（长任务要能查询状态而不是一直挂着）、以及安全边界（文件读写、命令执行要限定工作目录与白名单，不能把整台机器交出去）。

**Skill 分层的目的是控制上下文与责任边界**：可以分三层——能力层（原子工具：读文件、跑命令、查接口）、领域层（把原子能力组合成业务动作：查一次发布状态、生成一份周报）、场景层（面向具体任务的流程与判断标准：值班排障、代码评审）。分层的作用是让模型在每一层只看到需要的信息：上下文里先给场景与领域 Skill 的摘要，选中后再加载细节，避免一次塞入全部说明导致选择困难与 token 膨胀；同时每层可以独立测试与复用。

**Skill 数量与选择准确率**：没有放之四海皆准的阈值，但经验上同一层可选 Skill 超过二三十个、且描述高度相似时，选错会明显增多；到上百个时几乎一定要做检索或分类路由。原因是模型在候选集里做的是语义匹配，描述越相近越难区分，而上下文里候选越多，注意力越分散。缓解手段：给每个 Skill 写清「什么时候用、什么时候不用」与反例；把大集合按领域分组，先选组再选 Skill；用检索把候选缩到 5 到 10 个；对高频混淆对做专门的评测集，每次改描述都跑一遍。

**主流 Agent 的优劣势**：可以从三个维度比较——执行环境（本地终端、浏览器、IDE 还是纯对话）、扩展方式（MCP 工具、Skill 指令、插件）、以及自主程度（单轮问答、带工具的循环、还是长任务自主规划）。优势通常在某一环做得深（比如终端操作或代码库理解），劣势是跨环境能力弱、长任务稳定性差、或成本高。评价时结合自己的使用场景说，比如「做仓库级改动时更看重它对代码结构与测试的理解」，比罗列功能表更有说服力。

**日常 AI 提效要具体到动作**：说清三件事——什么任务、原来怎么做、用 AI 之后省了什么。例如组会纪要：录音转写后用模型按「结论、待办、负责人」结构化，再人工核对；课堂作业：先让模型解释概念与给反例，再自己推导，避免直接抄答案；写代码：用 AI 生成样板与测试，自己负责设计与评审。面试官问这题是在看你是不是真的把工具用进了工作流，而不是只会聊天。
