### 《参考解析》

**麻将判胡代码的改法**：这类题的评分点不在「会不会打麻将」，而在能不能把一个业务规则拆成「可枚举的牌型 + 可替换的规则」。先定位 bug 通常是这几类：手牌张数校验缺失（非 3n+2 也往下算）、将牌（对子）只试了一次没有回溯、顺子判定跨花色、吃碰杠之后的副露没参与胡牌计算、七对/十三幺这类特殊牌型被写死在主流程里。改法是重构成「输入标准化（花色 + 点数 + 张数计数数组）→ 牌型判定器列表 → 每个判定器独立实现」的结构。追问的动态配置就是把它推到数据层：每种胡牌规则描述成可配置项（需要的面子数、将牌数、是否允许特殊牌型、每种牌型的成立条件用「计数数组的谓词」表达），规则表存配置中心，判定引擎按配置装配。要说清取舍：完全数据驱动会让规则难以表达组合逻辑，实用做法是「结构配置化 + 谓词插件化」。

**RAG 链路**：离线侧是文档解析（PDF/HTML 转结构、去噪、保留标题层级）→ 切片（按语义边界切，带父子关系，块大小与重叠按文档类型调）→ 向量化 → 写向量库并保留元数据（来源、时间、权限）。在线侧是 query 改写（多轮指代消解、同义扩展）→ 混合召回（向量召回 + 关键词 BM25，两路结果融合）→ 重排（cross-encoder 或模型打分，取 Top-N）→ 上下文装配（按 token 预算裁剪、去重、带引用编号）→ 生成（要求引用来源）→ 后处理（引用校验、无据不答）。工程上还要有：权限过滤（检索前就按用户可读范围过滤，不能靠生成后删）、增量更新与失效、评测集（召回率、答案正确率、无答案时的拒答率）。

**MySQL 索引**：InnoDB 用 B+ 树。选它而不是 B 树的原因：非叶子节点只存键不存数据，同样大小的页能放更多键，树更矮（三四层就能撑起千万级），磁盘 IO 次数更少；叶子节点用双向链表串起来，范围查询和排序可以顺序扫描，B 树要中序遍历跳着读。索引不一定生效：对列做函数或运算（`where date(create_time) = ...`）、隐式类型转换（字符串列与数字比较）、`like '%x%'` 前置通配、联合索引不满足最左前缀、区分度太低（优化器判断全表扫更便宜）、`or` 混了没索引的列。判断手段是 `explain` 看 `type` 与 `key`，以及 `optimizer_trace`。

**缓存三大问题**：穿透（查不存在的 key，每次都打到 DB）→ 布隆过滤器前置拦截 + 空值缓存（短 TTL）；击穿（热点 key 过期瞬间大量并发回源）→ 逻辑过期（不真删、异步重建）+ 互斥锁（只放一个请求回源）；雪崩（大量 key 同时过期或缓存集群挂）→ TTL 加随机抖动 + 多级缓存 + 熔断降级 + 集群高可用。还有一致性（Cache Aside 先更 DB 再删缓存）与热 key（本地缓存 + 分片副本）。

**布隆过滤器 + 双重判定锁 + 空值缓存**：请求进来先查布隆过滤器，判定「一定不存在」就直接返回（省掉一次 Redis 查询）；可能存在则查 Redis，命中返回；未命中就抢分布式锁（双重判定：抢到锁后再查一次缓存，防止前一个请求已经回填），抢到的回源查 DB 并回填，没抢到的短暂休眠后重试。布隆过滤器原理是一个位数组加 k 个哈希函数，插入时把 k 个位置置 1，查询时若有一位为 0 则一定不存在、全为 1 则可能存在（有假阳性、无假阴性）。工程细节：布隆过滤器不能删除元素，所以要用计数布隆或定期重建；假阳性率与位数组大小、哈希个数、元素数量有关，要按预估元素量算容量。

**MQ 与重复消费**：MQ 在这里的作用是削峰（把突发的写请求缓冲，让 DB 按自己的节奏消费）、解耦（下游通知、索引更新、统计不阻塞主链路）、异步（把非关键路径移出用户等待窗口）、可靠（持久化 + 重试 + 死信）。重复消费的来源是「生产者重发」和「消费者 ack 前宕机」，只能做到 at-least-once，所以必须幂等：用业务唯一键建唯一索引、或维护「消息 ID → 处理状态」表，处理前先查/插入，冲突即跳过；对更新类操作改成「按最终状态覆盖」而不是「增量累加」。

**限流器代码排错**：固定窗口计数器的典型 bug 是窗口边界双倍流量（前一窗口最后一秒和下一窗口第一秒各放满），以及计数更新不是原子操作（读-改-写之间有竞态，多线程下实际放行数超过阈值）。滑动窗口要检查时间戳队列的清理时机（否则内存无限增长）与并发安全。令牌桶/漏桶的常见问题是：令牌补充用「每次请求时按时间差补」而不是定时器，但计算里把时钟回拨或纳秒/毫秒混用，导致补多或补少；桶容量与速率参数在运行时可改时缺少原子替换；分布式场景下每台机器本地限流，总量是 N 倍。修法：计数类用 Redis + Lua 保证原子，或本地用原子变量 + CAS；时间统一用单调时钟；分布式限流要按「总配额 / 实例数」下发并允许小幅漂移。

**简易检索系统的设计要点**：题目小，但要看是不是分层清楚——文档入库（切词、建倒排或直接调向量库）、索引结构（倒排表 `term → [docId, tf]`，或向量索引）、查询处理（分词、停用词、同义扩展）、打分（TF-IDF/BM25，说得出 `idf` 与长度归一化的作用）、结果排序与分页、以及增量更新。加分项是主动说「先用现成引擎（Lucene/ES）在真实场景更合理，手写是为了看清原理」。
