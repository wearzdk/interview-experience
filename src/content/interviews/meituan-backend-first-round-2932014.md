### 《参考解析》

**断点续跑的设计要点。** 把一次长任务拆成「节点 + 边」的图，每个节点执行完就把「节点 ID、输入哈希、输出、状态（成功/失败/待重试）」写进持久化存储（DB 或带持久化的 KV），并把整体进度记成 checkpoint。恢复时从最后一个成功 checkpoint 往后重放，已完成的节点直接读缓存结果、不再调模型。要处理三件事：幂等（同一节点重复执行结果一致，靠输入哈希做去重键）、副作用隔离（发消息、扣款这类外部动作放在节点外层，标记「已提交」后才推进 checkpoint）、以及版本兼容（提示词或工具变了，旧 checkpoint 是否还能续）。面试时补一句「我们用事件流记录每一步、结果是可重放的状态机」，比说「存了个断点」更清楚。

**对话隔离与「一次还是两次」。** 隔离靠 `tenantId + userId + conversationId` 三段键，`conversationId` 在用户新开一轮时生成并随每次请求带上；服务端所有记忆、向量检索、缓存 key 都必须带这个键，避免跨会话串味。「是两次还是一次对话」本质是会话边界判定：显式方案是前端在用户点「新对话」或超时（如 30 分钟无交互）时换 ID；隐式方案是看语义连续性——把上一条用户消息与当前消息做相似度/意图分类，低于阈值判为新会话。生产上通常以显式 ID 为主、隐式判定只用来提示用户「要不要新开一个对话」，不要用模型猜状态。

**防「把第二个识别成第一个」。** 这是上下文串位问题，三层解决：① 消息显式编号——每条消息带 `seq` 与 `role`，拼上下文时按 seq 排、并给模型明确的「第 1 轮/第 2 轮」标记；② 摘要替代原文——长对话用「按会话分段的摘要 + 最近 N 轮原文」，每段摘要带会话 ID，避免两段内容混在同一段文字里；③ 结构化引用——让模型在输出时引用 `messageId`，服务端校验引用的 ID 是否属于当前会话，越界就丢弃重答。别指望一句「注意不要混淆」的提示词能解决。

**幻觉的处理。** 分「事前、事中、事后」：事前用 RAG 给事实依据、要求引用来源、把工具返回值作为唯一事实源；事中做校验——结构化输出用 schema 校验、数字/金额/时间做格式与范围检查、关键结论与检索片段做一致性比对；事后做人审或抽样评估，把错例回流成评测集与提示词修正。面向用户的产品还要有「不确定就说不知道」的兜底话术，以及可追溯的证据展示（点了能看原文）。

**「用户确认后走模型还是走代码」。** 涉及资金、下单、提交这类有副作用的动作，一律走确定性代码：用户确认后由后端校验参数、落库、调用下游接口，模型只负责「把用户意图翻译成结构化参数」，不参与执行。好处是可审计、可幂等、失败可重试，也避免模型在最后一刻改写参数。

**binlog 同步 + 对账的不一致来源。** 常见六类：① 同步链路丢事件（binlog 过期、位点回退、消费异常没重试）；② 乱序（同一行多次变更被并发消费，后到的旧值覆盖新值）；③ 重复（至少一次语义，消费端没做幂等）；④ 事务边界（一个业务操作跨多表，下游只看到部分）；⑤ 字段映射/类型精度（金额精度、时区、枚举）；⑥ 上下游的删除语义不一致（硬删 vs 软删）。处理上：消费端按主键 + 版本号/时间戳做「旧值不覆盖新值」，幂等键去重，位点与延迟做监控，对账按「业务主键 + 关键字段」比对而不是整行比对。

**MQ 乱序怎么解。** 顺序性只能靠「同一业务键落到同一分区/队列 + 单线程消费」来保证：生产端用业务主键（订单号、门店 ID）做分区键，消费端每个分区一个消费线程、串行处理，失败时阻塞该分区而不是跳过，避免后面的消息先提交。代价是热点键会倾斜，所以要选基数足够大的键（比如 `门店ID + 业务类型`），并监控分区积压的分布。真要全序就只能单分区，吞吐上不去，一般不划算。

**分区键粒度太粗怎么办。** 先量：看各分区消费速率的 P99 与积压分布，确认是否真的倾斜。缓解手段有：键加盐（`key + hash(子维度) % N` 拆成 N 个子流，但要注意同一实体的顺序仍需保证，所以只能在「同一实体内部可并行」的维度上加盐）、二级路由（网关按实体把消息投到固定 worker）、或者把重实体单独拆主题。回答时要承认「顺序与并行是取舍」，别声称两者都能拿满。

**对账时间窗口与补偿。** 窗口由业务容忍度倒推：支付类通常秒级到分钟级，账务类可以 T+1。窗口内允许「暂时不一致」，窗口外必须归零。准实时对账解决不了的场景：跨天批量业务、上游延迟补发、需要人工审核的差异（金额对但明细缺失）、以及「两边都改了但都没错」的口径差异。补偿分自动与人工——自动走「以权威源为准重放/回滚」，人工走差异工单 + 双人复核。核心是每条差异都要有状态（待处理/处理中/已闭环）与超时升级。

**MQ 积压时的对账风险。** 大量门店同时开通会造成消费延迟，如果对账任务在同一时刻跑，会把「还没消费到」误判成「不一致」，进而触发大量补偿、把下游打爆。规避：对账前先取消费位点与延迟水位，延迟超过阈值就跳过本轮或只对「已确认消费完成」的分区；补偿加限流与合并（同一主键的多条差异合并成一条）；监控上加「积压量 + 补偿量」的联动告警，积压高时自动降级为只记录不补偿。

**双跑灰度与额度冲突。** 双跑适合「读多写少、结果可对比」的环节：查询、计价、风控打分可以双跑并比对差异；写环节（下单、扣款、扣库存）不能真双跑，只能「影子写」——新链路写到影子表/影子账户，不产生真实副作用。带额度或库存的业务更要小心：两边都真实扣减会重复消耗额度。做法是「额度只在一个权威源扣」，另一条链路只做校验与记录，比对结果不一致时以权威源为准并告警。

**降级策略的边界。** 降级要分级：非核心（推荐、营销、日志）可关；核心校验（风控、限额、库存）不能直接关，只能「降级为异步校验 + 事后拦截」，并且要把降级期间的订单打标，事后补偿性审核。降级必须带自动恢复条件与止损阈值（错误率、资损预估），并明确「谁有权开、开了谁盯」。回答时强调「降级不是关校验，是换一种更便宜的校验」，这句话能区分有没有真正做过。

**为什么多个 ES。** 通常是按业务域或数据规模拆的：不同业务线字段与查询模式差异大、单集群分片数与会话数有上限、故障隔离与独立扩容的需要。代价是跨集群的联合查询与一致性维护成本上升。要能说出「拆的理由」和「拆完之后怎么解决跨域检索」（应用层聚合、或者宽表冗余）。

**天级同步改 MQ 的动机。** 天级批量的问题：延迟高（业务当天看不到）、批量窗口对 DB 压力集中、失败重跑成本大。改成 CDC/MQ 后能做到准实时，但引入了乱序、重复、堆积这些新问题，所以同时要补幂等、顺序与监控。答这题的关键是「说清 trade-off，而不是只说新方案更好」。

**ES 的可用性。** 集群层：至少 3 个 master-eligible 节点避免脑裂、副本数 ≥1、分片分配感知机架/可用区、写入用 `wait_for_active_shards`、查询加超时与降级；数据层：主分片写完后同步到副本（`refresh` 控制可见性、`translog` 保证持久化），主分片故障时由 master 提升副本；应用层：客户端配多个节点、失败重试与熔断，关键查询走缓存。要能讲清「写一致性参数（`consistency`/`wait_for_active_shards`）与读一致性（`refresh=wait_for`）各解决什么问题」。

**本地消息表 + 定时任务解决什么。** 解决「本地事务与消息发送无法原子」的问题：业务写库与「写一条待发送消息」在同一个本地事务里提交，定时任务扫表把消息投到 MQ，投递成功才标记已发送，失败按退避重试。它保证的是「至少一次投递」，所以消费端必须幂等。相比事务消息（RocketMQ）实现简单、不绑定中间件，代价是有一张表要扫、延迟取决于扫描间隔。

**为什么不直接让大模型出完整方案。** 需求宽泛时模型会自己补齐假设，产出的方案看起来完整但和真实约束脱节（数据规模、存量系统、合规、成本）。正确姿势是先人工收敛问题：明确目标、边界、验收标准，把大需求拆成可验证的小任务，再让模型在每个小任务上产出候选方案，人做取舍。AI 适合「在明确约束下快速产出多个候选」，不适合「替你决定约束」。

**AI Coding 的 SOP。** 一段可复述的流程：读需求与存量代码 → 写一页 SPEC（目标、接口、数据结构、边界、验收用例）→ 让模型先出最小可运行版本 → 跑测试/样例 → 按失败项逐个修（一次只改一个点）→ 自查 diff（有没有偷偷改无关文件、有没有吞异常）→ 补测试与注释 → 提交。工具上善用规则文件（项目约定写进 `AGENTS.md` 之类）、把可复用的流程沉淀成 skill、把「验收标准」写成可执行脚本而不是口头描述。核心心法是「你负责定义正确，模型负责搬砖」。
