### 《面试题目》

1. 说说 TCP 三次握手。
2. 为什么不能是两次？两次握手会有什么问题？
3. 半连接队列满了，服务端会怎么表现？全连接队列呢？
4. TIME_WAIT 为什么是 2MSL？如果最后一个 ACK 丢了会怎样？
5. 线上服务端出现大量 TIME_WAIT 怎么办？`tcp_tw_reuse` 能解决吗？
6. TCP 粘包怎么解决？
7. 先说清楚：粘包是 TCP 的问题吗？
8. 半包怎么处理？长度字段有什么坑？

### 《参考解析》

**为什么不能两次握手**：两次握手下，服务端发出 `SYN+ACK` 后就认为连接已建立，会为它分配资源；但客户端可能因网络延迟早已放弃这个连接，服务端却一直等着。更严重的是攻击者可以大量伪造源 IP 发 `SYN`，服务端每收到一个就分配资源，队列很快被打满，正常用户的 `SYN` 全被丢掉，这就是 SYN Flood。第三个 `ACK` 让服务端确认「对端真的收到了我的 `SYN+ACK`」，避免被伪造源地址白白占用资源；常见缓解手段是启用 `tcp_syncookies`。

**两个队列要分清**：半连接队列装的是收到 `SYN`、还没收到 `ACK` 的连接；全连接队列装的是三次握手完成、等应用层 `accept()` 的连接。半连接队列满时新连接进不来，客户端表现为 `connect` 超时；全连接队列满时，某些内核版本会直接丢掉客户端的 `ACK` 让客户端重传，表现为连接建立变慢。帖主遇到过接口调外部 HTTP 服务、超时时间设太长导致线程池打满、`accept` 跟不上，监控上连接建立耗时抖动，最后查出是全连接队列溢出，`netstat -s | grep -i listen` 能看到 overflow 计数。

**TIME_WAIT 与 2MSL**：主动关闭方发完最后一个 `ACK` 进入 `TIME_WAIT`。若这个 `ACK` 丢失，被动关闭方会重传 `FIN`，主动关闭方还在 `TIME_WAIT` 状态，可以再回一个 `ACK` 并重新计时；等 2MSL 就是等「最坏情况下 `FIN` 重传一来一回」的时间。另一个作用是让这条连接四元组上的旧报文在网络里自然消亡，避免新连接收到残留数据。

**大量 TIME_WAIT 的处理**：先看是谁主动关闭的——短连接或响应头带 `Connection: close` 时，`TIME_WAIT` 堆在服务端是正常现象。再考虑内核参数：`net.ipv4.tcp_tw_reuse` 可以复用处于 `TIME_WAIT` 的连接发起新连接，但只对主动发起连接的一方有效且依赖时间戳；`tcp_tw_recycle` 在 NAT 环境下会误杀，现在基本不建议开。帖主那次是日志上报服务用短连接，`ss -s` 看到一万多个 `TIME_WAIT`，最后不是调参数解决的，而是改成连接池复用长连接，问题直接消失。

**粘包不是 TCP 的缺陷**：TCP 是字节流协议，只保证字节有序到达，不保留应用层消息边界。所谓「粘包」「拆包」本质是应用层没有定义消息边界，UDP 才有消息边界。解法三类：固定长度、分隔符（如 `\r\n`，HTTP 头就是这么做的）、长度前缀（先读 4 字节长度再读 body），第三种最通用。

**半包与字节序**：一次 `read` 可能只读到半个长度头，也可能读到 1.5 个包，缓冲区要自己维护，读够一个完整包再交给业务。帖主手写这个状态机时踩的坑是长度字段的字节序——写的时候用 `ByteBuffer` 默认大端，读的时候忘了，解析出来长度是个天文数字，直接把缓冲区撑爆。

**这类问题的答法**：先给结论，再说机制，最后落到「我在哪里见过它、怎么处理的」。看任何一个协议细节都问自己一句：如果这里出问题，我在哪条监控指标上能看见它？
