### 《参考解析》

**哪一类 Agent 最有价值**：判断标准是「是否嵌进了真实的生产流程并承担可度量的产出」。价值最高的通常是替代重复判断、且结果可校验的环节，例如 ETL 链路的异常监控与归因、文档检索总结、代码评审的辅助检查。纯对话型 Agent 价值有限，因为它不改变流程；能触发动作、留痕、被复核的 Agent 才能沉淀成基础设施。

**看板与监控的落地价值**：回答要区分底座与上层。底层的数据链路、可视化与定位能力已经跑通，能支撑业务优化；上层基于这套底座持续迭代 Agent 能力，用数据变化验证改动效果。评估指标不能只有时效性——快不等于好，还要看准确率、漏报率、人工复核比例与实际挽回的损失。

**Agent 测试的完整场景**：流程是明确被测能力与成功标准 → 构造输入（真实需求文档、边界与对抗样例）→ 执行并采集轨迹（调用的 Skill、召回的知识、生成的 SQL）→ 校验结果（SQL 能否执行、口径是否正确、输出是否符合格式）→ 回归。用例来源要两者结合：核心路径与已知缺陷由人提前写好保证覆盖，变体与长尾由 Agent 生成扩充，但生成的用例必须人工筛选后才能进回归集。

**权限隔离的覆盖度**：只测少量账号确实不足。做法是按角色 × 资源 × 操作三个维度建矩阵，用等价类划分挑代表账号，再补越权路径（直接构造他人文档 ID、跨部门检索、公共记忆与私有记忆混用）。覆盖度用矩阵的已覆盖格子比例衡量，而不是账号数量；高风险组合（跨部门、写操作）必须全测。

**文档检索 Agent 的隔离实例**：准备两个部门各自的文档与两个只有本部门权限的账号，用 A 账号检索 B 部门的关键词，期望结果为空且不出现标题摘要；再用公共知识库内容验证双方都能命中。还要测共享会话与记忆：同一会话切换账号后，历史上下文不得把上一个账号的文档内容带出来。
