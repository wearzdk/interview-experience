### 《面试题目》

1. 事务有哪些隔离级别？主要差别是什么？
2. 同一个事务里读两次，中间有人改了数据，两次可能分别读到什么？
3. 快照读和当前读有什么区别？
4. `FOR UPDATE` 的时候还允许读吗？它是快照读还是当前读？
5. RAG 的召回指标有没有做过评估？应该怎样说明？

### 《参考解析》

**四种隔离级别与「读两次」**：读未提交（RU）能读到别人未提交的数据，会出现脏读；读已提交（RC）只能读到已提交的版本，同一事务两次读之间别人提交了修改，第二次就能读到新值，即不可重复读；可重复读（RR）在事务第一次快照读时建立一致性视图，之后同一事务里的普通查询都读这个视图，值不变，但可能出现幻读（同一条件下第二次查出更多行）；串行化（SERIALIZABLE）用加锁或 SSI 让事务串行执行，代价是并发度骤降。InnoDB 默认 RR。回答时把「读两次分别读到什么」对应到具体级别：RU 两次都可能变且可能读到脏数据；RC 第一次读到旧值、第二次读到新值；RR 两次都是旧值；串行化下如果并发写会阻塞或回滚。

**快照读与当前读的本质区别在读哪一份数据**：普通 `SELECT` 是快照读，走 MVCC——按 read view 判断版本可见性，从 undo log 里的版本链取历史版本，不加锁；`SELECT ... FOR UPDATE`、`SELECT ... FOR SHARE`、`UPDATE`、`DELETE`、`INSERT` 是当前读，读最新已提交版本并加锁。RC 与 RR 的差别在于 read view 的生成时机：RC 每条语句新建一次，RR 在事务里第一次快照读时建一次并复用。这也解释了为什么 RR 下同一事务重复读结果不变，而 RC 会变。

**`FOR UPDATE` 之后别人还能不能读**：要分清语句类型。其他事务的普通快照读通常不被阻塞，它们读的是 undo 里的旧版本，这正是 MVCC 的意义；其他事务的 `FOR UPDATE`、`UPDATE`、`DELETE` 在锁冲突时会等待或超时；`FOR SHARE` 与排他锁互斥，也会等。加锁范围取决于索引与隔离级别：命中唯一索引等值条件时是行锁（record lock），范围条件或非唯一索引在 RR 下退化成 next-key lock（记录锁 + 间隙锁），能防住幻读但更容易死锁；没有命中索引会锁住扫描到的所有行甚至全表。被问到这里，最好补一句「间隙锁只在 RR 及以下的可重复读语义里出现，RC 基本没有间隙锁」。

**RAG 召回评估要先把「找得对不对」和「答得好不好」拆开**：第一阶段只评检索，构造一个 golden set——一批真实 query，每题人工标注哪些文档（chunk）算相关，通常几十到几百条就够起步，按业务分层抽样（高频、长尾、多跳、含专有名词）。指标看 Recall@K（前 K 条里覆盖了多少应召回的文档，K 取 3/5/10）、MRR（第一个相关结果排名的倒数）、nDCG（考虑排序位置与分级相关性）、Hit Rate（前 K 是否至少含一条相关）。第二阶段评生成：忠实度（回答是否只依据检索内容、有没有编造）、答案相关性、引用命中率，用 LLM 裁判加人工抽样校准。

**这道题真正区分人的是「怎么归因失败」**：召回差要先定位在哪一环——是知识库里本来就没有（覆盖问题）、切分粒度不对（chunk 太大稀释、太小丢上下文）、查询改写没做（口语化问题没扩成关键词）、还是 embedding 与业务领域不匹配（换成 bge-m3 或加稀疏检索做混合）。工程上做离线评测回归：每次改切分、改 embedding、改 rerank 都跑同一套 golden set 看指标变化，再上线上 A/B 看点击与会话完成率。面试里能说出「先建小规模标注集、用 Recall@K 做基线、按失败样本分类归因」，比只报一个指标名要可信得多。
