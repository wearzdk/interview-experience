### 《参考解析》

**成本问题怎么答**：面试官连问三题「能不能不用大模型」「怎么减少对模型的依赖」，考的是成本意识与架构分层。可答的路径有：把任务分层——确定性任务（分类、抽取、规则可覆盖的匹配）用规则或小模型，只有开放语义才用大模型；缓存——把高频相同或近义 query 的答案缓存起来（语义缓存用向量相似度命中），命中率往往很高；预计算——离线把常见问题与内容做索引或预生成，在线只做检索；检索优先——能用关键词 / 向量检索拿到答案的就不进模型，即 RAG 的「先检索、必要时才生成」；路由降级——按 query 复杂度路由到不同规模的模型。搜索场景还可以用倒排索引 + 语义向量混合、query 改写减少无效调用、以及把「答不了」明确拒答而不是硬生成。

**制造 MySQL 死锁**：两个事务以相反顺序更新同两行即可。会话 A 执行 `begin; update t set x=1 where id=1; update t set x=1 where id=2;`，会话 B 执行 `begin; update t set x=1 where id=2; update t set x=1 where id=1;`，两个会话都提交前互相等待对方持有的行锁，InnoDB 检测到循环等待后回滚其中一个并报 `Deadlock found when trying to get lock`。死锁的四个必要条件在数据库里对应：互斥（行锁独占）、持有并等待（拿到 id=1 后等 id=2）、不可剥夺（锁不能强制夺走）、循环等待（A 等 B、B 等 A）。避免方式是统一加锁顺序、缩短事务、给操作加唯一索引减少间隙锁、必要时用 `SELECT ... FOR UPDATE` 显式加锁并设置 `innodb_lock_wait_timeout`。至于「事务是否分别运行在两个线程」，是的——每个连接由独立线程处理，死锁是跨连接的锁竞争，单线程内不会自我死锁。

**Prompt 优化方法**：常见手段有：明确角色与目标、给出输出格式（JSON schema / 示例）、提供少量示例（few-shot）、把复杂任务拆步（Chain of Thought / 分步指令）、限定边界（只依据给定资料回答、不知道就说不知道）、以及结构化输入（用标签或分隔符区分指令与数据）。调优方法上要能说清流程：固定评测集 → 改一个变量 → 对比效果与成本 → 保留胜出的版本，而不是凭感觉改。工程侧还有超参（temperature、top_p）、上下文裁剪与缓存、以及用更小的模型承担简单任务。

**贝叶斯与开放问题**：贝叶斯定理是 `P(A|B) = P(B|A)P(A)/P(B)`，核心是「用新证据更新先验得到后验」。落到工程上，垃圾邮件过滤、风控、推荐里的 CTR 平滑、以及 A/B 实验的贝叶斯分析都是它的应用。面试官问这类问题，往往是想知道你是否有跨学科的兴趣与思考习惯，答法上体现「先验 + 证据 → 更新」的直觉，再举一个实际例子就够了。

**这一轮的特点**：全程没有多少硬技术题，一半以上时间在聊项目和经历——这说明面试官在做「匹配度与潜力的判断」。这种面试的准备重点不是刷八股，而是把简历上的每一条都准备好被追问三层，尤其是项目要能回答「和别人的差别在哪、成本多少、为什么这么设计」。面试官问数学物理课外书、贝叶斯，也在侧面观察学习习惯，诚实作答比硬凑答案好。
