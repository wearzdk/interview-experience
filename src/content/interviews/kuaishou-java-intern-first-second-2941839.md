### 《参考解析》

**缓存击穿与雪崩**：击穿是单个热点 key 过期的一瞬间，大量请求同时穿透到数据库；解法是互斥重建（分布式锁，只放一个请求回源）、逻辑过期（值里带过期时间，异步刷新，读到的仍是旧值）、热点 key 不设过期加后台更新。雪崩是大量 key 在同一时间失效，或缓存服务整体不可用，导致请求全部打到数据库；解法是过期时间加随机抖动、多级缓存、缓存集群高可用、熔断降级与限流。穿透则是查根本不存在的数据，用布隆过滤器或空值缓存，三者别混。

**单实例 Redis 为什么还需要分布式锁**：锁保护的是「对共享资源的互斥访问」，不是 Redis 本身。只要有两个进程（两个 JVM、两个 Pod、定时任务与 Web 服务）会同时改同一份资源，JVM 内的 `synchronized` 就管不住，需要一把跨进程的锁；Redis 单实例也能提供这个互斥。如果确认只有一个应用进程、且只用多线程，本地锁就够，不必上 Redis。回答时把「锁的对象、持有者、超时、可重入、失败重试」讲清：`SET key value NX PX ttl` 加锁，value 放持有者标识，解锁用 Lua 比对后删除，避免误删别人的锁；业务超时用看门狗续期；强一致场景还要考虑主从切换丢锁，必要时用 fencing token。

**进程间通信**：同一台机器上常用管道 / 命名管道、Unix domain socket、共享内存、信号、消息队列；跨机器用 TCP / UDP socket、HTTP、RPC、消息中间件。Java 后端与 MySQL 之间是 TCP 上的 MySQL 协议，JDBC 驱动把 SQL 与参数按协议编码，经连接池复用一个长连接；本机部署时也可以走 Unix socket。数据库连接是有状态的长连接，所以连接池、超时、断线重连都要配置。

**日志里数 error 行数**：`grep -c "ERROR" app.log`，忽略大小写用 `grep -ci`；只看某天可以 `grep "2026-11-17" app.log | grep -c "ERROR"`；文件很大时用 `rg -c "ERROR" app.log` 更快。用 AI 做这件事，正确的用法不是让它背命令，而是让它生成一条可验证的命令或小脚本，再用 `wc -l`、抽样 `head` 对照，确认统计口径（是否包含堆栈行、是否区分大小写、是否跨滚动文件）与预期一致。

**AI 代码怎么验收**：核心是「验收标准由人定，证据可复现」。先写清接口契约、错误码、边界条件与性能要求；让 AI 产出计划，但人只读变更清单与关键决策，不逐字读它生成的所有文档。测试不能只让 AI 自证：关键用例由人独立编写或补充，用真实调用、历史数据回放、故障注入来验证；对 AI 写的测试做覆盖率与变异检查，防止测试只验证实现。另一个 AI 的审阅只能作为补充信号，它的每条意见都要能落到具体代码行或可复现的失败上，最终是否合并由人负责。否则就会出现面试官说的「传话筒」：两个会话之间复制粘贴，谁都没有真正判断。

**Agent 工具调用模块怎么做**：按「注册 — 描述 — 校验 — 执行 — 观测」拆。工具注册表维护名称、描述、JSON Schema 参数、权限与超时；调用前做参数校验与权限检查，调用中做超时、重试、幂等（幂等键）与并发限制，调用后把结果归一化成模型能读的结构，错误要区分「参数错、权限错、下游错、超时」并回传给模型决定是否重试；全链路记录 traceId、耗时、入参与结果摘要。安全上，工具描述与返回内容都是不可信输入，要在执行层做权限与参数边界校验，不能只靠提示词。面试里能把这几个边界说清，比让 AI 生成一堆代码更能证明你会做。

**内存泄露与栈问题**：Java 的内存泄露常见于长生命周期集合只增不减、ThreadLocal 用完不 `remove`、监听器 / 回调注册后不注销、连接与流未关闭、缓存没有上限、静态字段持有大对象。排查看堆增长趋势、GC 后老年代是否持续上涨，用 `jmap -histo` 看对象数量，必要时 dump 后用 MAT 找支配树与 GC Root 引用链。关于「栈占用高且常栈溢出」：先分清是线程栈内存、堆还是 CPU——`jstack` 看线程数与栈深度，若大量线程卡在同一递归或重复帧，就是递归过深或循环调用（也可能是 AOP / 序列化 / `toString` 的循环引用）；`StackOverflowError` 是栈帧耗尽，不是堆 OOM。优化方向是改递归为迭代、限制递归深度、减少大局部变量、修复循环依赖、控制线程数；调 `-Xss` 只能缓解，不能治根。如果面试官说的是内存占用 90%，则按堆 / 非堆 / 元空间分别看，结合 GC 日志判断是泄漏还是容量不足。

**GC**：分代假设下，新生代用复制算法做 Minor GC，对象在 Survivor 间晋升；老年代用标记清除或标记整理。收集器从 Serial、Parallel 到 CMS，再到以 Region 划分、可设停顿目标的 G1，以及追求低停顿的 ZGC / Shenandoah。回答时把「回收什么（可达性分析）、在哪里回收（分代 / Region）、什么时候触发（ Eden 满、老年代不足、元空间不足、显式调用）、停顿与吞吐怎么权衡」讲成一条线，再补一个自己调过的参数或看过的 GC 日志。

**合并链表**：用哨兵节点迭代合并，比较两个链表当前节点，把较小的接到结果尾部，指针后移；一条走完后把另一条剩余部分整体接上。时间 O(n+m)，空间 O(1)。注意判空、不要断链、不要新建节点（除非题目要求深拷贝）。
