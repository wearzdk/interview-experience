### 《参考解析》

**预编译为什么防不住 order by**：预编译（Prepared Statement）的防护原理是「SQL 结构与数据分离」——语句模板先发给数据库解析、生成执行计划，参数后到，数据库永远把参数当值处理，不参与语法解析。所以它能防住的是「值的位置」上的注入，比如 `WHERE id = ?`。`ORDER BY` 后面跟的是**标识符**（列名）或排序方向（ASC/DESC），属于 SQL 语法结构的一部分，不是值，参数化绑定在这里不合法。同样的坑还有表名、列名、`LIMIT` 的偏移（部分数据库可以绑）。正确做法是白名单映射：前端传 `sort=create_time`，后端查一张允许的字段表，映射成真实列名，传不进来的一律拒绝；排序方向同样枚举化。

**SSRF 与 DNS 重绑定**：SSRF 是服务端替攻击者发请求——应用有个「抓取 URL 内容」或「加载远程图片」的功能，攻击者把 URL 指向内网地址（`127.0.0.1`、`169.254.169.254` 云元数据、内网网段），借服务端的网络位置访问它本来够不到的资源。经典防护是黑名单（禁 localhost、内网段）或白名单（只允许指定域名）。DNS 重绑定专门打这类防护：攻击者控制一个域名，第一次解析返回公网 IP 通过校验，紧接着把 DNS 记录改成内网 IP，服务端第二次解析（实际发请求时）就打到内网去了。所以校验 DNS 和实际请求之间只要有时间差就能被利用。正确防护是**解析后校验 IP 再锁定 IP 连接**（把校验过的 IP 直接用于建连，或 pin 住解析结果），而不是「查一次域名 → 之后随便发」；同时禁跳转（或对每一跳都重新校验）、封禁元数据服务地址、用独立的出网代理并做协议与端口白名单。

**无文件上传时的文件包含**：文件包含（`include($_GET['page'])`）不依赖上传功能，能利用的路径有好几条。① **日志投毒**：把 PHP 代码写进 access log（UA 或 URL 里带 payload），再包含日志文件——前提是日志路径可预测且可读。② **临时文件**：PHP 处理上传时会生成临时文件并自动删除，但在删除前的窗口内可以用包含读到；对无上传点的场景，可以通过构造 multipart 请求让 PHP 先落地临时文件再包含（这是经典的 LFI to RCE 手法）。③ **`php://filter` 链**：不需要包含恶意内容，直接 `php://filter/convert.base64-encode/resource=index.php` 读源码；进阶用法是构造过滤器链把任意内容编码成恶意 PHP 写进文件（filter chain 生成器那套）。④ **`/proc/self/environ`、session 文件**：能控制环境变量或 session 内容时同样可用。防护是根上的：不要用用户输入拼文件路径，改成白名单映射；`open_basedir` 限制可访问目录；关掉 `allow_url_include`。

**ServiceAccount 与特权容器逃逸**：ServiceAccount 是 K8s 里 Pod 访问 API Server 的身份凭证，默认以 volume 形式挂在容器内（`/var/run/secrets/kubernetes.io/serviceaccount/token`）。拿到这个 token 就等于以该 SA 的权限调 API。如果 RBAC 给得过宽——比如允许创建 Pod、允许 `pods/exec`、允许读 Secret，攻击者就能横向：用高权限 SA 起一个挂载宿主机目录、`privileged: true` 或 `hostPID: true` 的 Pod，直接读宿主机文件系统或进宿主机命名空间，完成容器逃逸。加固方向：默认不自动挂载 token（`automountServiceAccountToken: false`），按需最小权限绑定 Role，禁用 `privileged` 与 `hostPath`（用 PodSecurity Admission / OPA 强制），审计 `pods/exec` 与 Secret 读取。

**CSP 与绕过**：CSP 是通过响应头（或 meta）声明「本页允许从哪些源加载脚本 / 样式 / 图片 / 连接」的策略，核心是 `script-src`，配合 nonce / hash / strict-dynamic 能把 XSS 的危害压到「注入的脚本不执行」。绕过往往出在配置疏漏：用了 `unsafe-inline`（内联脚本可直接跑）、`unsafe-eval`；白名单里放了可上传的 CDN 或 JSONP 端点（在受信任域上托管恶意脚本）；`base-uri` 没限制导致可以改 `<base>`；`script-src` 允许了 `data:` 或宽松的通配子域。另外即使脚本执行被拦住，还有 CSS 注入、`<meta>` 重定向、DOM clobbering 这类不靠脚本的路径可以外带数据。

**HTTP 请求走私与 POST 分段**：根源是前后端对「一个请求在哪里结束」理解不一致。前端（反向代理）和后端（应用服务器）各自按自己认的 `Content-Length` 或 `Transfer-Encoding` 切分请求体，两者标准不同时，一部分字节被前端当成下一个请求的开头，走私进后端。经典组合是 `CL.TE`（前端信 CL、后端信 TE）和 `TE.CL`。防护是让中间设备统一标准、拒绝同时出现 CL 与 TE 的请求、拒绝畸形的 chunked 编码。POST 分段属于把请求体切成多段传输的手法，用来绕过只看单段的 WAF 规则。

**黑盒 Agent 的敏感操作拦截**：分两层。第一层是**模型外的确定性管控**——Agent 的动作空间本身做收敛（不给任意 shell，只给白名单化的原子工具）；工具入参做结构校验与危险模式识别（路径穿越、绝对路径、通配删除、内网地址、外发目的地）；破坏性动作挂人在环审批。第二层是**流量网关识别**——Agent 的所有出站请求走统一网关，按目的地做域名 / IP 白名单与内网段封禁，按内容做敏感数据外泄检测（身份证、密钥、源码片段），按行为做速率与异常模式识别（短时间内枚举大量接口、频繁访问敏感端点）。网关的价值是它不依赖 Agent 的判断，即便模型被注入带偏，出站这一关还能拦。

**为什么不多挖 SRC**：面试官问这句，往往在探你是不是真的在打真实目标。答的时候要能说清目标和方法的对应关系：真实 SRC 是黑盒、有授权边界、要产出可复现的漏洞报告；平时练的是靶场和 CTF，更偏技巧堆叠。把「企业生产环境的渗透」和「CTF 拿 flag」的区别讲清楚，比报漏洞数量有说服力。

**企业内做 AI for Security 与外部攻击视角的差异**：外部（红队 / 挖 SRC）的目标是「能出洞就行」，一次成功即可，不要求稳定、不要求覆盖、可以猛打；企业内的建设目标是「能安全地、持续地干活」——权限边界要清楚，误报率高就跑不下去，召回率（真实威胁的覆盖率）比单点爆破重要，还要能审计、能回滚、能和既有 SOC 流程对接。落地顺序通常是先把确定性的部分做扎实（资产梳理、日志汇聚、已知漏洞的自动检测），再让 AI 处理需要判断的环节（告警降噪、报告生成、模糊信息下的优先级排序）。
