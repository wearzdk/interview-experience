### 《面试题目》

1. 你平时写 SQL 有没有关注过执行计划？说几个索引失效的场景。
2. 最近一次你实际遇到的失效是什么？
3. 为什么 `varchar` 字段传 `Long` 会失效？是「类型不一致就失效」吗？
4. 在索引列上套函数为什么就废了？`WHERE left(order_no, 6) = 'abc123'` 算不算最左前缀？
5. 联合索引 (a, b, c) 走全三个字段时，`key_len` 怎么算？
6. `WHERE a > 10 AND b = 2` 里 b 还能用于定位吗？
7. `OR` 和前导模糊分别要注意什么？
8. 有索引但优化器不走，算失效吗？

### 《参考解析》

**varchar 传 Long**：用户表 `phone` 是 `varchar(20)`，接口用 `Long` 接手机号后拼进 SQL，本地数据量小测不出来，上线后开始慢查询报警。`EXPLAIN` 显示 `type=ALL`、`key=NULL`。原因是一方字符串一方数字时，MySQL 把字符串侧转成数字比较，等于在索引列上套了 `CAST(phone AS SIGNED)`。改法是参数按字符串传。关键结论要记准：不是「类型不一致就失效」，而是「谁被转换」——字符串列被转才失效，int 列传字符串转的是常量侧，索引照用。

**索引列套函数**：统计某天注册量写成 `WHERE date(create_time) = '2024-05-11'`，`create_time` 上有索引也用不上，改成左闭右开区间即可。同类还有 `substring`、`ifnull`、`id + 1 = 10`。判断标准一句话：索引按列值排序，你在列上算出新值，排序就与你无关了。`WHERE left(order_no, 6) = 'abc123'` 虽然长得像前缀匹配，但 `left()` 是函数，同样用不上索引。

**最左前缀与 `key_len`**：`WHERE b = 2 AND c = 3` 跳过 a，联合索引直接不适用；`WHERE a = 1 AND c = 3` 中 a 用得上、c 用不上，`key_len` 只算 a 那一段。`key_len` 的计算与字段类型、是否可空、字符集有关：`int` 非空占 4 字节，`varchar(n)` 在 `utf8mb4` 下是 `4n + 2`（长度前缀）再加 1（可空标记）。面试时能按字段类型推算，说明真的看过执行计划。

**范围截断**：`WHERE a > 10 AND b = 2`，联合索引 `(a, b)` 中 a 走范围后，b 在区间内不是全局有序的，不能继续二分定位，只能过滤。这不是索引坏了，而是有序性在范围之后局部丢失。

**OR 与前导模糊**：`WHERE a = 1 OR b = 2`，b 没索引时整条 SQL 大概率退化成全表扫，因为 OR 要求两边都能走索引；前导模糊 `LIKE '%xx'` 用不上索引，而 `LIKE 'xx%'` 虽然能用，但匹配范围太大时优化器算完成本一样会放弃。

**「有索引但优化器不走」**：严格说不算失效，是代价问题。回表次数太多、区分度太低（性别、状态位）、统计信息过期，优化器都会主动选全表扫。排查顺序应该是先看 `type` 与 `key`，再看 `rows` 与 `filtered`，最后才怀疑 SQL 写法——因为原因往往不在语法上，而在数据分布上。

**这场面试的收获**：八股能背出来只说明看过；能讲出自己哪条 SQL 慢过、`EXPLAIN` 里看到什么、改完变成什么样，才说明真的用过。
