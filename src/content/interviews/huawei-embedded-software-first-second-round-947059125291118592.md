### 《参考解析》

**指针与数组、二级指针。** 数组名在大多数表达式里退化为指向首元素的指针，但数组不是指针：`sizeof(arr)` 是整块大小、`&arr` 类型是数组指针、数组不能被赋值。函数形参写成 `int a[]` 实际等价于 `int *a`，传的是首地址，长度信息丢失，所以必须另传长度。二级指针的典型场景是「在被调函数里修改调用方的指针本身」：动态分配后回传（`void alloc(char **p)`）、在链表头插/删除时修改头指针、以及二维数组或字符串数组的传参。

**free 之后继续访问。** 是未定义行为。free 只是把这块内存归还分配器，指针本身不变，内容可能还在也可能被分配器改写（tcache/free list 的 fd 指针通常就写在前 8/16 字节），访问会读到垃圾数据；再次 free 会 double free 破坏堆结构；如果是 mmap 的大块还可能直接触发段错误。规范做法是 free 后立刻置 NULL，访问前判空。

**结构体内存对齐。** 规则是每个成员的偏移是其对齐值的整数倍，结构体总大小是其最大对齐值的整数倍（还要考虑编译器与 `#pragma pack`）。优化排布就是把成员按对齐值从大到小排列，减少填充；小成员可以合并或用位域。嵌入式里还要注意编译器是否插入 padding 影响与硬件寄存器的映射，跨设备传输的结构体要显式 pack 并处理字节序。

**互斥锁的内核实现。** Linux 上用户态互斥锁的慢路径走 futex：先原子地 CAS 抢用户态的一个 int 字，抢不到就进入内核 `futex_wait`，把自己挂到该地址对应的等待队列上睡眠；持锁者释放时原子改字并 `futex_wake` 唤醒等待者。所以「加锁失败的线程」不是自旋，而是被挂起进入睡眠态（TASK_INTERRUPTIBLE/UNINTERRUPTIBLE），由调度器在唤醒后重新竞争。自旋锁则相反，忙等不睡眠，适合临界区极短且不可睡眠的场景（内核中断上下文），在用户态多核短临界区也有用（pthread_spinlock）。

**死锁与检测。** 四个必要条件：互斥、持有并等待、不可剥夺、循环等待。工程上最有效的是破坏循环等待——所有锁定义全局顺序、按序加锁；其次是加锁带超时（`pthread_mutex_timedlock`）、用 `trylock` 失败就释放已持有的锁重试。检测可以靠运行时记录「线程 → 持有的锁 → 等待的锁」构成有向图，发现环就告警；静态分析工具（如 Clang Thread Safety Analysis）能在编译期发现顺序不一致。

**原子操作与内存屏障。** 原子操作靠 CPU 指令（x86 的 `LOCK CMPXCHG`、ARM 的 `LDXR/STXR` 或 LSE 的 `CAS`）保证读改写不被打断，无锁竞争时只是一条指令，比加锁（进内核 futex）开销小得多；但高竞争下 CAS 失败重试会空转。`volatile` 只保证不被编译器优化掉、每次从内存读，不保证原子性和顺序，所以不能保证线程安全。内存屏障用于约束 CPU 与编译器的重排：`smp_mb()` 全屏障、`smp_rmb/wmb()` 单向屏障，常用在无锁队列的生产者/消费者两侧（写完数据再更新 tail 索引）、以及驱动里写寄存器后需要确保顺序的场景。

**TCP 可靠传输与流控拥塞控制的配合。** 可靠传输靠序号 + 确认 + 超时重传 + 校验和 + 去重排序。发送方维护拥塞窗口 cwnd 和接收方通告窗口 rwnd，实际可发送窗口取两者最小值：rwnd 防止把接收方打爆（流量控制），cwnd 防止把网络打爆（拥塞控制）。滑动窗口让发送方可以连续发送多个未被确认的段，提高带宽时延积的利用率；拥塞控制则根据丢包/延迟动态调整 cwnd。慢启动是让 cwnd 从 1 开始指数增长，快速探测可用带宽，避免一上来就大流量造成拥塞崩溃；之后进入拥塞避免（线性增长）、快速重传与快速恢复。

**TIME_WAIT 与 2MSL。** 主动关闭方进入 TIME_WAIT 等待 2MSL，作用有两个：一是保证最后一个 ACK 能到达对端，如果 ACK 丢了，对端会重传 FIN，此时还能响应；二是让本连接四元组的旧报文在网络中消亡，避免新连接收到旧连接的迷路报文。MSL 是报文最大生存时间，2MSL 覆盖一个来回。服务器大量 TIME_WAIT 通常是因为服务端主动关闭了大量短连接（如 HTTP 短连接、反向代理到后端不复用连接）。处理：开启 `tcp_tw_reuse`（仅对出向连接有效）、调大 `ip_local_port_range`、用连接池/长连接复用、让客户端先关闭（`SO_LINGER` 要慎用）、检查是否有异常断连。不要用 `tcp_tw_recycle`（NAT 环境下会误杀）。

**进程内存一直涨的定位。** 先区分是堆、栈、还是 mmap：`top`/`ps` 看 RSS 趋势，`pmap -x <pid>` 或 `/proc/<pid>/smaps` 看各段增长；怀疑堆泄漏就用 Valgrind memcheck（开发期）、ASan/LSan（编译期插桩）、或 mtrace；生产环境可用 jemalloc/tcmalloc 的 heap profile 或 gdb 抓 heap 统计。配合 `malloc_stats`、`mallinfo2` 看分配器内部状态。如果是 C++ 还要排查容器只增不减、缓存没有上限、事件注册后没注销。最后用「压测复现 + 分批开关功能」缩小范围，拿到调用栈再改。

**select/poll/epoll。** select 用位图、有 1024 fd 上限，每次调用都要把 fd 集合从用户态拷到内核并线性扫描，返回后还要再扫一遍找就绪的。poll 用数组去掉上限，但拷贝和线性扫描依旧。epoll 在内核用红黑树管理注册的 fd（`epoll_ctl` 增删是 O(log n)），就绪的 fd 挂到一条就绪链表上，`epoll_wait` 直接取链表，无需遍历全部 fd；边缘触发（ET）配合非阻塞 IO 可以进一步减少系统调用。所以 epoll 高效的核心是「注册与等待分离 + 回调驱动就绪队列」，适合大量连接但活跃比例低的场景。
