### 《面试题目》

1. 能否满足在北京实习六个月、每月 4k 的条件？
2. 场景题：你有做过电商平台的项目吗？商城项目里，订单如何防止「设计多点」（重复下单）？
3. 详细说一说后端加锁。
4. 说一说数据库的类型。
5. 反问。

### 《参考解析》

**订单防重**：分三层来答，面试官一般就想听这个结构。① 前端与入口层：按钮置灰、提交后跳转，但这只能减少误触，不能作为保证。② 接口层幂等：客户端生成幂等 token（或订单号），服务端用 `SETNX` / 唯一索引把它落库，重复请求直接返回上一次结果；同一用户对同一 SKU 的短时间重复提交用频控或「用户 + 商品 + 时间窗」的唯一键拦住。③ 数据层兜底：订单表对幂等键建唯一索引，插入冲突即视为重复；库存扣减用「`UPDATE stock SET num = num - 1 WHERE id = ? AND num >= 1`」这种带条件的原子更新，避免超卖。④ 分布式场景：跨服务时用分布式锁（Redis `SET key val NX PX` + Lua 释放，或 Redisson 看门狗续期）保护「查库存 → 建单 → 扣减」这个临界区，并强调锁的粒度要按商品或用户，不要一把全局锁。最后补一句「先做幂等，再谈锁」——幂等是业务语义上的保证，锁只是实现手段。

**后端加锁**：按范围分层讲。单机：`synchronized`（对象头 Mark Word，偏向锁/轻量级锁/重量级锁升级，JDK 15 后偏向锁默认关闭）、`ReentrantLock`（AQS + CAS + 双向队列，可中断、可超时、可公平）。数据库：行锁（InnoDB 基于索引加锁，没走索引会退化成表锁或间隙锁）、乐观锁（版本号 / `UPDATE ... WHERE version = ?`）、悲观锁（`SELECT ... FOR UPDATE`）。分布式：Redis 锁（注意锁超时与业务耗时、释放要校验持有者）、ZooKeeper 临时顺序节点、数据库唯一索引。要能说清各自代价：本地锁快但只能保护单进程；数据库锁简单但压不住高并发；分布式锁有网络开销与脑裂风险。

**数据库类型**：可以分两个维度答。按数据模型：关系型（MySQL、PostgreSQL，强事务与约束）、键值（Redis、TiKV）、文档（MongoDB）、列式（ClickHouse、HBase，适合分析与大数据量扫描）、搜索引擎（Elasticsearch，倒排索引做全文检索）、时序（InfluxDB、TDengine，按时间分区与压缩）。按业务选型：交易类要事务与一致性走 MySQL；缓存与计数走 Redis；日志与检索走 ES；报表分析走 ClickHouse。再说清 MySQL 的存储引擎差异：InnoDB 支持事务、行锁、外键、聚簇索引；MyISAM 只有表锁、不支持事务，现在基本不用。

**复盘**：电话面没有手撕、节奏很快，第一句就在确认实习条件（城市、时长、薪资），答得犹豫基本就结束了。场景题要主动分层（入口 / 接口 / 数据 / 分布式），并给一个能落地的具体方案（唯一索引 + 条件更新），比罗列「可以用锁」有说服力。
