### 《参考解析》

**JVM 内存结构与 OOM 分布**：线程私有的有程序计数器、虚拟机栈、本地方法栈，线程共享的有堆与方法区。程序计数器是唯一不会 OOM 的区域；虚拟机栈溢出通常是递归过深，抛 `StackOverflowError`（严格说不是 OOM）；堆 OOM 分两类——`Java heap space` 是对象存活总量超过上限，`GC overhead limit exceeded` 是 GC 花掉大量时间却回收不到 2% 的空间；方法区（JDK 8 之后是元空间）OOM 常见于动态生成类太多（CGLIB 代理、热部署）；直接内存溢出在 Netty 这类用堆外内存的场景里出现，报错文案是 `Direct buffer memory`。

**GC 收集器选型**：Serial 单线程、Stop The World，适合客户端与小堆；Parallel 吞吐优先，适合批处理型后台任务；CMS 以最短停顿为目标，标记清除、有碎片与并发模式失败问题，JDK 9 起废弃；G1 把堆切成 Region，按回收收益优先收集，可设定目标停顿时间（`-XX:MaxGCPauseMillis`），适合 4GB 以上的服务端堆；ZGC 与 Shenandoah 是染色指针 / 读屏障的低延迟收集器，停顿基本与堆大小无关，代价是吞吐略低、需要更大堆余量。回答要点是「按业务指标选」：延迟敏感选 G1/ZGC，吞吐敏感选 Parallel，并说明升级收集器要结合 GC 日志与压测验证，不能只凭参数表。

**双亲委派与打破**：类加载请求先交给父加载器，父加载器加载不到才由自己加载，作用是保证核心类不被篡改（自己写的 `java.lang.String` 永远不会被加载）。打破的三种典型场景：JDBC 的 `DriverManager` 需要加载厂商实现，用线程上下文类加载器（SPI）；Tomcat 为实现 Web 应用隔离，每个应用一个 WebAppClassLoader，先自己加载再委派；OSGi 的网状委派。答题时说清「为什么打破」比背「怎么打破」更重要。

**Full GC 频繁的排查路径**：先用 `jstat -gcutil` 或 GC 日志确认频率与回收效果，再看堆与各代占用（`jmap -heap`）、对象直方图（`jmap -histo`），必要时 dump 堆用 MAT 找支配树上的大对象。常见原因：堆设置过小、晋升过快（新生代太小或 Survivor 比例不当）、大对象直接进老年代、元空间不足、显式 `System.gc()`、缓存无界增长、`ThreadLocal` 与静态集合导致的对象长期存活。修复要落到具体那一类，不能只说「调大堆」——调大堆往往只是把问题推后。

**内存泄漏与内存溢出的区别**：溢出是结果，泄漏是原因之一。泄漏指对象已经不再使用但仍被引用、无法回收，表现是「每次 Full GC 后老年代占用仍然上涨」；溢出指申请内存超过上限，可能因为泄漏累积，也可能只是瞬时数据量过大（一次查全表、大文件读入内存）。定位手段一致：堆 dump + 支配树分析，对照两次 dump 的增量找持续增长的对象与持有它的引用链。

**IOC 与 AOP**：IOC 是控制反转，对象的创建与依赖装配交给容器，实现方式有 XML、注解、Java Config，本质是一张 BeanDefinition 注册表加依赖注入；AOP 是面向切面，把日志、事务、鉴权这类横切逻辑从业务里抽出来，Spring AOP 默认用 JDK 动态代理（目标类实现接口时）或 CGLIB（无接口或强制 `proxyTargetClass`），在 Bean 初始化后生成代理对象。要能说清「AOP 只对容器管理的外部调用生效」——同类内部方法互调走的是 this，不经过代理，切面不生效，这也是 `@Transactional` 失效的头号原因。

**Bean 生命周期与三级缓存**：实例化 → 属性填充 → `BeanNameAware` 等回调 → `BeanPostProcessor` 前置 → `init-method` / `@PostConstruct` → 后置处理（AOP 代理在这里生成）→ 使用 → 销毁。循环依赖的解决靠三级缓存：一级放完整 Bean，二级放提前暴露的半成品，三级放能产出该 Bean 代理的 `ObjectFactory`。之所以要三级而不是两级，是为了在需要 AOP 时延迟到真正发生循环引用才生成代理，保证注入到别人手里的是代理对象。构造器注入的循环依赖无法解决，只能改字段注入或用 `@Lazy`。

**Spring Boot 自动配置**：`@SpringBootApplication` 包含 `@EnableAutoConfiguration`，它通过 `AutoConfigurationImportSelector` 读取 `META-INF/spring/org.springframework.boot.autoconfigure.AutoConfiguration.imports`（2.7 之前是 `spring.factories`），拿到候选配置类后按 `@ConditionalOnClass`、`@ConditionalOnMissingBean`、`@ConditionalOnProperty` 等条件筛选，命中的才注册。自定义 starter 就是提供这样一个 imports 文件加一组带条件的配置类。能讲清「条件装配 + 用户配置优先」这两点，这道题就到位了。

**`@Transactional` 失效场景**：同类内部方法调用（不经过代理）、方法非 public（CGLIB 代理对 private/protected 无效）、异常被 catch 后没有重新抛出、抛的是受检异常而默认只回滚 `RuntimeException` 与 `Error`、类没有被 Spring 管理、多线程里调用（事务绑定在 ThreadLocal 上）、数据库引擎不支持事务（MyISAM）、传播行为设置不当（如 `REQUIRES_NEW` 与 `NESTED` 混用）、只读事务里做写操作。

**MySQL 索引为什么用 B+ 树**：与二叉树比，B+ 树是多路平衡树，树高很低（三层能存千万级），一次查询只需少量磁盘 IO；与 B 树比，B+ 树的非叶子节点只存键、不存数据，同样大小的页能放更多键，扇出更大、树更矮，且数据全部在叶子节点并用链表相连，范围查询与排序只需顺序扫描叶子；与哈希索引比，B+ 树支持范围查询与最左前缀匹配。答题时补一句「聚簇索引的叶子存整行、二级索引的叶子存主键」，以及回表与覆盖索引的关系。

**隔离级别与幻读**：读未提交、读已提交、可重复读、串行化。MySQL 默认可重复读，靠 MVCC 的快照读实现可重复读，靠间隙锁（Next-Key Lock）在加锁读时防幻读——所以「RR 到底有没有幻读」要分快照读和当前读回答。读已提交每次快照读都取最新快照，因此同一事务内两次读到不同结果；串行化读加共享锁、写加排他锁，并发度最低。

**慢 SQL 的排查顺序**：先确认是单条慢还是整体慢——开慢查询日志（`long_query_time`、`log_queries_not_using_indexes`），用 `EXPLAIN` 看 `type`、`key`、`rows`、`Extra`（`Using filesort`、`Using temporary` 是要警觉的信号），再考虑 `EXPLAIN ANALYZE` 看真实耗时分布。常见修复：补或调整联合索引（按最左前缀与选择性设计）、避免索引列上做函数运算与隐式类型转换、把 `SELECT *` 收窄为覆盖索引、大分页改成基于上次最大 id 的游标分页、拆分大事务、必要时做冷热分离或归档。要强调索引不是越多越好：写放大、优化器选择成本、空间占用都是代价。

**分库分表后的 ID**：UUID 无中心但无序、占空间，做主键会导致 InnoDB 页分裂；数据库自增步长多实例可用但扩容麻烦；号段模式（一次取一批 ID 缓存在本地）兼顾有序与吞吐，是常见选择；雪花算法（时间戳 + 机器号 + 序列）有序且高性能，但要处理时钟回拨与机器号分配。回答时要说明业务对 ID 的要求（是否暴露给用户、是否需要趋势递增），再选方案。

**乐观锁与悲观锁**：悲观锁假定冲突多，先加锁再操作（`SELECT ... FOR UPDATE`、分布式锁），适合写多、冲突频繁、一致性要求高的场景，代价是阻塞与死锁风险；乐观锁假定冲突少，读时带版本号，更新时 `WHERE version = ?` 校验，失败重试，适合读多写少。库存扣减这类场景更稳的做法是 `UPDATE stock SET count = count - 1 WHERE id = ? AND count >= 1`，把判断与扣减合成一条原子语句。

**总监面的答题结构**：这类面试的问题本身不难，考的是结构与边界。每题按「结论先行 → 原理 → 场景 → 风险」四段讲：结论一句话给判断，原理说清机制，场景结合自己做过的项目，风险与替代方案说明你知道边界在哪。不确定的直接说「这一层我没深入过，我了解到的是……」，比含糊带过更安全——被追问一句就露的答案，比承认不知道扣分更多。
