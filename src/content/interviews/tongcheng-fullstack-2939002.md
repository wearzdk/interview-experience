### 《参考解析》

**为什么把检索拆成子 Agent**：三个理由。一是上下文隔离——检索过程会产生大量候选文档与中间判断，如果把原始结果全塞进主 Agent 的上下文，主 Agent 的推理预算会被噪声占满，拆出去之后只回传压缩后的结论。二是工具集合分离——检索要用到向量库、关键词库、爬取、重排等多个工具，主 Agent 需要的是规划与写作工具，混在一起会让工具选择变差。三是可独立评测与替换——召回质量、重排策略可以单独跑评测集，改检索不影响主流程。代价是延迟增加、错误传播（子 Agent 漏召回主 Agent 无从察觉）、以及结果回传时的信息损失，所以设计上要给出结构化的回传契约：命中片段 + 来源 + 置信度 + 未命中的查询，主 Agent 据此决定是否再检索一轮。

**子 Agent 的上下文也会爆**：解法不是调大窗口，而是控制「进入子 Agent 的内容」。① 检索结果先做截断与摘要，按段落切分后只保留命中片段而非整篇；② 把「读文档」做成可按需调用的工具（先看目录与摘要，再决定读哪一节），避免一次性灌入；③ 多轮检索之间只保留结构化的中间状态（已确认的事实、待验证的假设），丢弃原始文本；④ 设置轮次与 token 预算上限，超限时强制收敛并输出「信息不足」而不是继续堆内容。

**怎么验证检索结果可信**：分三层。检索层看召回指标（Recall@k、MRR）与来源覆盖，是否只命中单一来源；生成层要求逐句给出引用，校验每个结论在原文中能否定位到；业务层做抽样人工评估与失败案例复盘。工程上还可以做交叉验证——同一问题用向量召回与关键词召回各跑一次，两者结论一致时置信度高，冲突时触发人工或补充检索。要强调「可信度是一个需要标注数据才能校准的量」，不能只靠模型自评。

**双路召回与降级**：双路指向量召回（语义相似）与关键词/BM25 召回（字面匹配）并行，再合并去重后重排。两路互补的原因是向量对专有名词、编号、代码符号不敏感，关键词对同义改写不敏感。降级逻辑通常在两处：当向量库超时或不可用时，退回纯关键词检索并标记「语义召回缺失」；当两路结果都很弱（分数低于阈值）时，不强行生成，直接返回「未检索到相关内容」并给出可以换个问法或补充材料的提示。降级必须显式记录，否则主 Agent 会把「没召回到」误当成「没有这个知识」。

**检索轮次与停止条件**：常见策略是「最多 N 轮 + 满足任一终止条件即停」。终止条件包括：本轮新增的高相关片段数低于阈值（信息增益收敛）、核心问题已被覆盖（对照问题拆解出的子问题清单）、连续两轮查询改写后结果高度重合、预算耗尽。要避免两个极端——固定只跑一轮会在首次查询措辞不佳时漏掉关键信息，无限迭代会让延迟不可控。工程上把「停止」交给一个轻量的判定（规则 + 小模型打分）比让主模型自由决定更稳定。

**bundle 体积治理**：先用工具量化再动手——`webpack-bundle-analyzer` 或 `rollup-plugin-visualizer` 出体积树，`source-map-explorer` 定位到具体模块，`--stats` 看 chunk 划分。判断冗余的常见信号：同一依赖的多个版本同时存在、整包引入但只用了几个函数（lodash、moment、icon 库）、被重复打包进多个 chunk 的公共代码、打进主包但只在某个路由用到的重型组件、未被 tree-shaking 掉的无副作用标记缺失。治理手段：按路由动态 `import()`、把公共依赖提取到 vendor chunk、用 ESM 版本替换 CJS、把重型库换成轻量替代或按需引入、用 `sideEffects: false` 与 `externals`、以及图片与字体走 CDN。优化后要用构建产物体积与真实用户的首屏指标（LCP、TTI）两头对比，只看 bundle 数字会忽略运行时开销。

**输入 URL 到页面可交互**：URL 解析与缓存检查（强缓存、协商缓存）→ DNS 解析（浏览器缓存、系统缓存、递归查询）→ 建立 TCP 连接（三次握手，HTTPS 再加 TLS 握手）→ 发送 HTTP 请求 → 服务端处理并返回 HTML → 浏览器解析 HTML 构建 DOM、遇到 CSS 构建 CSSOM、遇到脚本按 `defer`/`async` 决定是否阻塞 → 合成渲染树 → 布局 → 绘制 → 合成上屏 → 加载子资源并执行 JS 完成 hydration，进入可交互。答题时说的是「关键路径与阻塞点」：DNS 与连接建立影响首字节，CSS 阻塞渲染，同步脚本阻塞解析，字体与首屏图片影响 LCP。

**首屏优化**：网络层用 CDN、HTTP/2 或 HTTP/3、压缩（Brotli）、预连接与预加载关键资源；资源层做代码分割、首屏关键 CSS 内联、图片用合适格式与尺寸并加 `loading="lazy"`（首屏图不加）、字体 `font-display: swap` 并子集化；渲染层用 SSR/SSG 减少白屏、骨架屏改善感知、避免布局抖动（预设宽高）。检测用 Lighthouse、WebPageTest 与真实用户监控（RUM）的 LCP/INP/CLS；对比要在同一网络与设备条件下跑前后两版，并看真实用户分位数而不是只看实验室数据。

**内存泄漏排查**：先用 Chrome DevTools 的 Memory 面板做三次快照（操作前、操作中、操作后），对比保留对象数量找出持续增长的类；用 Allocation instrumentation on timeline 看分配热点。前端常见泄漏源：未解绑的事件监听与定时器、闭包持有大对象、全局缓存与 Map 只增不减、被遗忘的 WebSocket 与 observer、Detached DOM（节点从文档移除但 JS 仍引用）。React 场景还要查 `useEffect` 缺少清理函数、订阅未取消。定位后用 `WeakMap`/`WeakRef`、在卸载时显式清理、给缓存加 LRU 上限。

**CORS 预检的触发条件**：请求方法不是 GET/HEAD/POST 之一，或 POST 的 `Content-Type` 不是 `application/x-www-form-urlencoded`、`multipart/form-data`、`text/plain` 之一，或带有自定义请求头，或 `XMLHttpRequest.upload` 绑定了监听器，都会先发 `OPTIONS` 预检。预检请求不携带 Cookie 与业务头，只带 `Access-Control-Request-Method` 与 `Access-Control-Request-Headers`，服务端用 `Access-Control-Allow-*` 与 `Access-Control-Max-Age` 回应。凭证请求（`withCredentials: true` 或 `credentials: 'include'`）会携带该域名下的 Cookie（含 HttpOnly）、TLS 客户端证书、以及 HTTP 认证信息；此时服务端 `Access-Control-Allow-Origin` 必须是具体源，不能为 `*`，且要设置 `Access-Control-Allow-Credentials: true`。

**两个鸡蛋 100 层楼**：经典答案是 14 次。设第一次在 x 层扔，之后每次增加 x-1、x-2……层，使得最坏情况下总次数满足 x + (x-1) + … + 1 ≥ 100，即 x(x+1)/2 ≥ 100，解得 x = 14。第一次 14 层，第二次 27 层，第三次 39 层，依此类推；第一个蛋碎了就用第二个蛋在上一段的区间内逐层线性试探，总次数不超过 14。答题时先讲思路（让每次失败的剩余试探次数相等），再给具体楼层序列，最后说明这是最坏情况下的最优解。
