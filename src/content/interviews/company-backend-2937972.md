### 《参考解析》

**12 秒到 650 毫秒要讲成「定位—拆分—验证」三段**：定位靠三样东西——接口链路的耗时打点（网关、应用、SQL、外部调用各一段）、慢查询日志与执行计划、以及线程栈采样（连续抓取阻塞点）。常见瓶颈是「同步解析大文件 + 逐条写库 + 同步调用下游」串在一条请求里，于是把可异步的部分切出去：文件直传对象存储只做校验，落一条任务记录后立即返回，解析与入库交给消费者。650 毫秒的构成要能说清：上传与校验、元数据入库、任务投递，各自多少毫秒；异步段的耗时用任务完成时间单独统计，不要混进接口 RT。

**Kafka 的重消费要区分「位点」与「业务状态」**：位点只表示「这个分区消费到哪」，提交位点 5 意味着 0 到 4 都不会再被这个消费组投递。所以「5 号先完成先提交」在单分区串行消费下不会发生——同一分区同一时刻只有一个消费者，位点只能顺序推进；如果业务上确实出现乱序完成，说明用了多分区或多线程消费，那就要放弃「位点即完成」的假设。正确做法是业务侧维护任务状态机（待处理、处理中、成功、失败、可重试），用任务表加状态字段做补偿：定时扫描超时未完成的任务重新投递，消费失败时不要提交位点或投递到重试主题（带重试次数与退避），超过次数进死信队列。幂等靠唯一业务键（任务 id + 步骤）在写库时做 `insert ... on conflict do nothing` 或先查状态再执行，保证重复消费不产生副作用。

**一个 Partition 只能被同一消费组内的一个消费者消费**：这是 Kafka 的分区分配语义，目的是保证分区内顺序；多个实例要并行就增加分区数，让实例数与分区数匹配。消费者确实按位点拉取，`auto.offset.reset` 只决定没有位点时从最早还是最新开始；「按时间戳取」需要显式用 `offsetsForTimes` 查询。回答这一串追问的关键是承认边界：位点提交是「至多一次 / 至少一次」的取舍，业务上的「恰好一次」要靠幂等写来实现。

**分布式锁要能说清「不加会怎样」**：锁的粒度按业务键（用户 id + 文件指纹）而不是全局，避免所有上传串行；过期时间要大于最长处理时间并配看门狗续期，释放时用 Lua 比对持有者再删除，防止误删他人的锁。加锁的真正价值是防止「同一份数据被并发创建两条任务」和「同一任务被两个消费者同时处理」。但锁不能替代幂等——锁失效（过期、Redis 主从切换）时唯一索引是最后一道防线；两者的分工是锁降低冲突概率、唯一约束保证正确性。追问「唯一键从哪来」时，要说明是服务端按用户与文件内容哈希生成的，不是客户端传的。

**文件去重靠内容指纹而不是文件名**：客户端算 SHA-256（大文件分片算、再算分片清单的哈希），服务端二次校验；同一用户同一指纹在有效期内直接返回已有任务。改了几个字哈希就变，识别不出来是正常的——要按「同内容」去重就不该指望近似匹配，需要近似去重则用 SimHash 或向量相似度，并明确误判代价。

**混合检索的选型要落到「为什么不用另一个」**：BM25 解决的是专业术语、编号、缩写这类精确匹配，向量解决语义改写与同义表达，Rerank 用交叉编码器对候选做精排。选 MongoDB 做关键词侧，通常是因为已有文档存储、需要按元数据做多条件过滤、团队运维成本低；代价是 BM25 能力弱于 Elasticsearch（没有成熟的倒排索引与分词生态、相关性调优空间小），数据量大时应迁到 ES 或 OpenSearch。Milvus 支持标量过滤（等于、范围）但不做全文相关性排序，两者职责不同。权重不宜固定：按 query 是否含编号/专有名词、以及两路的分数分布动态调整，或者用 RRF 做排名融合，再用 Rerank 统一打分。召回率从 72% 到 85% 要拆开归因——分别测「只加 BM25」「只做问题重写」「两者都加」，否则说不清收益来自哪一步。
