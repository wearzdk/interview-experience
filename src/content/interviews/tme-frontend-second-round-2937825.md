### 《参考解析》

**矩形布局的行列划分**：这道题在 15 分钟内不要求写出生产级代码，重点是先说清判定口径。可以把问题转成两次一维投影：把所有矩形的横向区间 `[x, x + width]` 收集起来，按起点排序后合并重叠或相接的区间，得到若干条列区间；纵向区间 `[y, y + height]` 同样处理，得到行区间。随后遍历每个矩形，用它的中心点（或左上角）落在哪条行区间、哪条列区间，把下标分别放进对应的行数组与列数组。整体复杂度 O(n log n)，主要开销在排序。作答前需要向面试官确认三件事：矩形是否允许重叠、坐标是否都是整数、行与列是各返回一个二维数组还是统一返回一个。若布局存在像素级误差，合并区间时要留一个容差，例如 1px 以内的间隙视为同一行；若矩形允许跨行跨列，则不能只按中心点归属，需要改成区间包含关系判定。

**微前端的 JS 隔离**：主流做法有三类。第一类是快照沙箱，子应用挂载时记录 `window` 上已有属性的快照，卸载时把新增属性删除、被修改的属性还原；实现简单，但同一时刻只能激活一个子应用，多个子应用并行时会互相覆盖。第二类是 Proxy 沙箱，为每个子应用创建一个 `fakeWindow`，用 `Proxy` 拦截 `get`、`set`、`has` 等操作，读优先取子应用自己的写入、没有再回落到真实 `window`，写只落在 `fakeWindow` 上；qiankun 的多实例模式就是这一思路，可以支持多个子应用同时运行。第三类是 iframe 沙箱，利用浏览器原生的独立 `window` 与样式环境做彻底隔离，代价是 DOM 结构、路由、弹窗和通信都要额外适配。此外还有 `with` 加 `eval` 改变作用域链的做法（qiankun 的早期实现）、ES Module 天然独立的模块作用域，以及仍在提案阶段的 ShadowRealm。回答时要把「隔离 window 全局变量」与「隔离 DOM 事件、定时器、网络请求」区分开：只代理 `window` 并不能阻止子应用往 `document` 上挂监听，完整的沙箱还要劫持 `document.addEventListener`、`setTimeout` 等副作用并在卸载时统一清理。

**微前端的 CSS 隔离**：常见方案按隔离强度递增依次是：命名约定（BEM、统一前缀）、构建期加选择器前缀（`postcss-prefix-selector`）、CSS Modules 或 scoped 的哈希类名、运行时动态加载与卸载子应用样式表、Shadow DOM。qiankun 提供两种开箱选项：`experimentalStyleIsolation` 给子应用样式统一加上容器选择器前缀，改造成本低但管不住 `body`、`html` 这类全局选择器；`strictStyleIsolation` 用 Shadow DOM 包裹子应用容器，隔离彻底，但子应用内的弹窗挂到 `document.body` 时会丢失样式，第三方组件库也可能因为取不到外部样式而出问题。工程上更常见的组合是「构建期前缀 + 运行时样式表随子应用生命周期挂载卸载」，并把全局样式收敛到主应用统一提供，避免各子应用各自重置 `box-sizing` 与字体。

**文件指纹的计算与作用**：浏览器端常用 `spark-md5` 做增量哈希：用 `File.slice` 把文件切成固定大小的块（通常 2MB 左右），逐块读成 `ArrayBuffer` 喂给 `SparkMD5.ArrayBuffer`，最后得到 32 位十六进制摘要；整个过程放在 Web Worker 里执行，避免大文件计算时阻塞主线程。也可以直接用 `crypto.subtle.digest('SHA-256', buffer)`，但需要一次性把整个文件读进内存，大文件容易触发内存压力。工程上常做两级：先抽首块、中间块、尾块算一个快速指纹用于秒传探测，命中后再做全量校验。指纹的用途有四个：秒传（服务端已存在同一文件时直接返回文件地址）、断点续传（按分片记录已上传位置并用分片哈希校验）、去重存储（相同内容只存一份）、完整性校验（上传完成后比对，防止传输损坏）。追问「如何自己实现」时，除了分块与增量更新，还要说明哈希算法的选择理由：MD5 计算快但抗碰撞性弱，适合做内容去重；SHA-256 更安全但更慢，适合做完整性校验。

**多宿主 JSBridge 的统一封装**：核心是加一层适配器。先定义与宿主无关的能力接口，例如 `invoke(method, params)`、`on(event, handler)`，内部统一返回 Promise；再为每个宿主实现一个 adapter，负责探测宿主标识（UA、注入对象是否存在、握手结果）并调用该宿主 SDK 的真实方法。上层业务只依赖接口，不感知宿主差异。回调管理用自增的 `callbackId` 建立映射表，Native 回包时按 id 找到对应的 `resolve`/`reject`，并设置超时定时器，超时后清理映射并抛出可识别的错误码。按需加载有两种做法：一是运行时探测后动态 `import()` 对应 SDK 的 chunk；二是由宿主在页面加载时注入统一命名空间，H5 只做能力检测。前者适合包体积敏感的场景，后者适合宿主版本不可控、需要尽早完成握手的场景。底层通信机制按平台分：Android 常见 `addJavascriptInterface` 注入对象、拦截 `shouldOverrideUrlLoading` 解析自定义 scheme、拦截 `prompt`；iOS 常见 `WKScriptMessageHandler`、`WKURLSchemeHandler`、拦截 iframe 的 `src` 跳转。排查「调用后没有结果」时按链路逐段确认：注入对象是否存在、握手是否完成、方法名与参数是否被正确序列化、Native 是否真的收到、回调 id 是否对上、是否被页面跳转或 WebView 重建打断；最后看 Native 侧日志与 SDK 版本兼容性。生产上要有超时兜底与降级路径，不能让业务 Promise 永久挂起。

**Agent 的上下文压缩**：常见策略可以按「丢弃、概括、外置、检索」四类整理。丢弃类是滑动窗口，只保留系统提示与最近若干轮，简单但会丢早期约束；概括类是对更早的对话做滚动摘要，把摘要放在窗口头部，需要控制摘要本身的长度与信息损失；外置类是把任务状态、已确认事实、工具结果提炼成结构化的 JSON 或清单，用状态替代原始对话；检索类是把历史消息或知识写入向量库，每轮按当前问题召回相关片段。此外还有几种工程手段：对工具返回的大结果做截断或只保留结构化字段、把长文档拆给子 Agent 分段处理后汇总（Map-Reduce）、对重复的模板化内容做去重。选择时要区分「必须精确记住的」与「可以概括的」：用户明确给出的约束、已经执行过的副作用、当前任务进度属于前者，闲聊与中间推理属于后者。压缩策略还要与缓存配合，稳定的前缀不要反复改写，否则每轮都会击穿提示词缓存。

**RAG 的适用场景、准确度与局限**：RAG 适合知识密集、需要引用出处、内容会持续更新且模型参数里没有的场景，例如企业制度与产品文档问答、客服知识库、代码库检索、法规与论文辅助阅读。它不适合需要实时数据、强多跳推理、或者要求对全量数据做统计的任务，这些更适合接工具查询或直接用结构化数据库。检索准确度的影响因素贯穿整条链路：文档解析质量（PDF 表格、扫描件、页眉页脚）、切分策略（块大小、重叠、是否按标题层级切）、嵌入模型与领域语料的匹配度、查询改写与扩展、是否做混合检索（BM25 与向量互补）、是否加 rerank、元数据过滤（时间、部门、权限）、TopK 与上下文拼装顺序。实践中提升最大的一步往往不是换嵌入模型，而是把文档解析与切分做好，并在检索后加一层重排。多模态知识库的处理方式取决于检索目标：图片可以走 OCR 提取文字、用多模态模型生成描述后作文本检索，或直接用 CLIP 这类图文向量模型；表格应保留结构（转 Markdown 或 JSON）而不是拍平成文本；音视频先转写并保留时间戳，关键帧单独建索引。RAG 的局限也要说清：召回不到就一定答不好，切分会破坏跨段语义，多跳问题需要多次检索与推理编排，模型可能忽略检索内容而凭参数记忆作答，权限控制要贯穿到检索层，端到端评估也比纯生成更难。

**非父子组件通信**：框架内常见五类：状态提升到共同祖先再逐层传递；Context（Vue 的 provide/inject）跨层注入；全局状态库（Redux、Zustand、Pinia）；事件总线（`mitt`、自定义 EventEmitter）；通过 `ref` 暴露方法由父组件调用子组件。状态提升的关键是「状态放在所有消费者的最近公共祖先」，并且只提升真正需要共享的那部分，避免把整个页面状态都堆到顶层导致无关组件重渲染。只用原生能力时，可选方案包括：基于 `EventTarget` 实现事件总线，组件订阅自定义事件、另一组件 `dispatchEvent`；用 `CustomEvent` 配合 DOM 事件冒泡，把消息派发到共同的容器或 `window`；用 `BroadcastChannel` 做同源跨标签页通信；用 `storage` 事件监听其他标签页对 `localStorage` 的修改；用 `postMessage` 处理 iframe 与 Worker；用 `MutationObserver` 观察 DOM 属性变化作为兜底。面试官继续追问时，要能说出各自的边界：事件总线要手动解绑否则内存泄漏，`storage` 事件只在其他标签页触发，`BroadcastChannel` 有浏览器兼容性要求。

**Zustand 的实现机制**：`create` 接收一个初始化函数，返回一个 React hook。内部用一个闭包保存当前状态对象，`setState` 把部分更新合并成新对象（保持不可变更新），然后同步通知所有订阅者；`getState` 直接返回闭包里的引用。React 侧通过 `useSyncExternalStore` 订阅 store，把 `getSnapshot` 与 `subscribe` 交给 React，从而在并发渲染下避免撕裂（tearing）。选择器 `useStore(selector)` 会在每次状态变化时执行 selector，并用 `Object.is` 比较结果，相等就不触发重渲染；需要比较对象或数组时传入自定义 `equalityFn`（v5 改用 `useShallow`）。它不依赖 Provider，store 是模块级单例，因此可以在组件外直接调用 `getState`/`setState`，适合需要非 React 代码读写状态的场景。中间件（persist、devtools、immer）本质是对 `set`/`get` 与初始化函数做高阶包装。

**localStorage 变化的监听**：`localStorage` 的修改会触发同源其他标签页的 `storage` 事件，回调参数里有 `key`、`oldValue`、`newValue`、`url`，可以据此做跨标签页同步；但当前页面自己修改时不会触发该事件，所以写入方需要额外派发一个自定义事件，或者把读写封装成统一模块，在 `setItem` 后手动通知本页订阅者。更现代的做法是用 `BroadcastChannel`，语义清晰且不依赖存储；兼容性要求高时可以用 `storage` 事件加轮询兜底。要注意 `storage` 事件只在同源、且确实是值发生变化时触发，写入相同值不会触发；另外它不适合传输大对象，序列化与解析的成本会随数据量上升。

**性能优化与上传模块的答法**：性能题不要只报数字，要讲清「指标基线、瓶颈定位、改动、回归验证」四步：用什么指标衡量（首屏 LCP、交互 INP、长任务数量、包体积），怎么定位（Performance 面板、Lighthouse、埋点），改了什么（拆包与懒加载、图片格式与尺寸、减少主线程长任务、缓存策略），改完指标变化与如何防止回退。上传模块的拆分要落到职责边界：UI 层只负责选择文件、展示进度与错误，逻辑层封装队列、并发控制、分片、重试、暂停恢复、哈希计算与状态机，两层通过明确的输入输出与事件契约通信；逻辑层不依赖具体组件，因此可以复用到不同页面甚至非 React 环境。复用的关键是依赖注入与可测试性：把上传 API、并发数、分片大小作为参数传入，逻辑层用纯 TypeScript 实现并配单元测试。
