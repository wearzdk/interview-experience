### 《面试题目》

1. 用 TypeScript 写一个支持撤销重做的数据管理器。
2. 用 TypeScript 写一个异步任务依赖调度器。
3. 用户点击“导出录像”后，导出可能持续几分钟，当前方案是前端一直等待服务端返回文件地址。这种设计可能存在哪些问题？
4. 如果把导出设计成异步任务，前端和服务端之间应该如何交互？
5. 如何处理用户重复点击、离开页面或重新进入页面的情况？
6. 前端应该如何获取并展示导出进度、成功或失败状态？
7. 多个客户端同时查看同一个导出任务时，如何保证看到的任务状态一致？
8. 导出完成后的文件如果有有效期，前后端应该如何处理文件过期？

### 《参考解析》

**撤销重做用命令模式或不可变快照都可以，关键是把“操作”和“状态”分开。** 命令模式为每个操作实现 `do/undo`，维护 `undoStack` 和 `redoStack`：执行新操作时压入 undo 栈并清空 redo 栈，撤销时弹出 undo 栈执行反向操作并压入 redo 栈，重做则反过来。优点是内存小、能合并连续操作；缺点是实现成本高，复杂操作的逆运算容易写错。不可变快照每次保存完整状态，实现简单、天然支持跳转，但大对象会吃内存，需要限制历史长度或做结构共享。工程上还要考虑批量操作、事务边界、持久化和多人协作，别只写一个只能处理字符串的 demo。

**异步任务调度器的核心是 DAG 和并发控制。** 先把任务建成有向图，记录每个任务的依赖数和后继；入度为 0 的任务进入就绪队列，按并发上限启动，完成后把后继任务的依赖数减一，减到 0 就入队。启动前要做环检测，有环直接报错，否则会永远等不到就绪。每个任务要有状态机（pending/running/success/failed/cancelled）、超时、重试和错误传播；某个任务失败时，是让依赖它的任务全部失败，还是跳过并继续无关分支，要提前定义。`Promise` 池只能控制并发数，不能表达依赖，所以 DAG 调度要自己维护依赖计数或使用拓扑排序。

**长耗时导出不应该让 HTTP 请求一直挂着。** 同步等待的问题很直接：网关和浏览器都有超时，连接占用资源，用户刷新就丢结果，服务端也无法在客户端断开后安全取消任务。异步化后，前端提交导出请求，服务端立刻返回 `202 + jobId`，任务进入队列；前端通过轮询、SSE 或 WebSocket 获取进度和结果。提交时要带幂等键，防止用户连点生成多个任务；任务状态要持久化，用户离开页面再回来可以按 jobId 恢复。多客户端查看同一任务时，服务端以任务状态为唯一事实源，前端不要各自维护一份进度，最好用版本号或事件序号做增量更新。

**进度展示要让用户知道“还在跑”而不是“卡死了”。** 服务端把任务拆成阶段，返回百分比、当前阶段、已处理数量和预计剩余时间；前端用进度条加文字，失败时给出可操作的错误信息和重试入口。文件有效期要在响应里明确 `expiresAt`，前端提前提示，过期后给出重新生成按钮；服务端用签名 URL 限制访问，并定期清理过期文件。不要只在内存里存任务状态，进程重启就全丢；也不要把大文件直接塞进 JSON，返回下载地址即可。
