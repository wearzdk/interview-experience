### 《参考解析》

**单例与包装类比较**：单例的写法要能说出五种并知道各自的问题——饿汉（类加载即创建，简单但可能浪费）、懒汉加锁（线程安全但每次加锁慢）、双重检查加 `volatile`（防止指令重排导致拿到未初始化对象）、静态内部类（利用类加载机制，延迟且线程安全）、枚举（天然防反射与反序列化破坏，Effective Java 推荐）。适合单例的是无状态或全局唯一的基础设施：配置中心、连接池、日志器、缓存管理器、注册表；不适合的是有请求上下文或需要隔离的数据。`long` 与 `Long` 用 `==`：两边都是 `Long` 时比较引用，超出 −128～127 缓存区间的值即使数值相同也不相等；一边是 `long` 时会发生拆箱，比较的是值；用 `equals()` 比较的是值，但对象为 `null` 时会 NPE。工程结论是统一用 `Objects.equals` 或先判空，别在包装类型上用 `==`。

**消息可靠性与 ACK 时机**：RabbitMQ 丢消息有三个环节，对应三处保障——生产端开 publisher confirm 加 mandatory/return 回调确认到达 exchange 与 queue；Broker 侧把 exchange、queue、消息都设为持久化，并用 quorum queue 或镜像队列防单点；消费端关闭自动 ACK，改为业务处理成功后手动 ACK。ACK 太早（收到就确认）会在处理失败时丢消息，ACK 太晚会在消费者崩溃时重复投递，所以正确姿势是「处理完成再 ACK」，并让消费逻辑幂等（唯一键去重表、状态机判断、乐观锁版本号）。失败重试要有限次，超过阈值进死信队列人工或异步补偿，避免无限 requeue 打满队列。

**缓存穿透与分布式锁**：穿透是查不存在的数据，每次都打到数据库——解法是参数校验、布隆过滤器挡掉一定不存在的 key、把空结果缓存一个短 TTL、对异常高频的 key 限流；要区分击穿（热点 key 过期瞬间大量回源，用互斥锁或逻辑过期）与雪崩（大量 key 同时过期，用随机 TTL 与多级缓存）。分布式事务按一致性强度选：强一致用 2PC/XA（性能差、协调者单点），业务侵入小的用本地消息表或 RocketMQ 事务消息做最终一致，跨服务长流程用 Saga（每个步骤配补偿），TCC 适合资金类需要预留资源的场景；无论哪种都要保证幂等与补偿可重入。`SET NX EX` 的关键在原子性：分两条命令时，若 `SETNX` 成功后客户端崩溃，锁就永不过期，后续所有请求被死锁；Redis 2.6.12 起 `SET key value NX EX seconds` 一条命令完成「不存在则设置 + 设过期」。解锁要用 Lua 先比对 value（客户端唯一标识）再删除，防止误删别人的锁；业务时间不确定时用看门狗续期。

**数据库 Owner 视角的优化要分层给**：面试官要的是「六个以上互不重复的方向」，可以按这条线展开——① SQL 与索引：慢查询日志与 `explain` 定位，补联合索引、避免索引失效、消除回表；② 表结构：字段类型收窄、大字段拆出、适度反范式冗余减少 join、控制列数与行宽；③ 数据生命周期：冷热分离、历史归档、分区表、按时间分表；④ 架构层：读写分离、分库分表（选好分片键，避免跨分片查询与分布式事务）、引入缓存与异步削峰；⑤ 连接与参数：连接池大小、`innodb_buffer_pool_size`、刷盘策略、超时与重试；⑥ 治理与流程：上线评审、DDL 变更窗口与在线 DDL 工具、慢查询告警、长事务监控与 kill、多团队共用时的库表权限与配额。大表除了归档分区，还能做水平拆分、把历史数据迁到列存或 OLAP、用覆盖索引减少回表、把统计类查询从主库挪走。

**直播间点赞的设计**：前端做本地乐观更新与节流合并（点击立即 +1，几百毫秒内的连点合并成一次请求，失败回滚），总数用长连接或轮询增量拉取，不要每次点赞都请求全量。后端把计数放 Redis：`INCR` 或 `HINCRBY` 单 key 在峰值下会成为热点，按房间号分片成 N 个 key 求和，或把增量先写本地聚合再批量提交。落库异步化——消息队列削峰，消费端按房间维度批量累加，最终一致即可（点赞数允许短暂延迟）。幂等与防刷分两层：按用户与房间做去重或限频（同一用户连续点赞在业务上通常允许，但要限速），风控侧识别脚本与异常频率。容量评估要给数字：峰值 QPS、单 key 写入上限、批量落库的批次大小与延迟容忍度。

**上下文窗口与知识组织**：窗口不是越大越好。成本与延迟随 token 线性甚至超线性增长；长上下文存在「中间遗忘」（lost in the middle），关键信息放在中段时召回率下降；KV Cache 的显存占用随长度线性增长，直接压低并发；训练数据里长文样本的分布也影响效果。正确做法是按任务选长度，配合检索（只放相关内容）、摘要压缩、分段处理与结构化提示。Ontology（本体/知识图谱）适合实体与关系明确、需要多跳推理与强约束的业务（组织架构、商品类目、风控规则），可校验、可解释，但建设与维护成本高、覆盖不了非结构化文本；向量检索式的知识组织适合文档问答与语义模糊匹配，建设快、召回广，但缺乏精确推理。生产上常把两者混合：先用 ontology 做实体归一与约束，再用检索补充上下文。

**原地删除重复元素（每个最多保留两次）**：有序数组用双指针，`slow` 指向下一个可写位置，`fast` 扫描；因为最多保留两次，比较 `nums[fast]` 与 `nums[slow-2]`，不同就写入并前移。时间 O(n)、空间 O(1)。

```java
int slow = 0;
for (int fast = 0; fast < nums.length; fast++) {
    if (slow < 2 || nums[fast] != nums[slow - 2]) {
        nums[slow++] = nums[fast];
    }
}
return slow;
```

边界要提：数组长度小于 2 时直接返回；题目若说「最多保留 k 次」，把 `2` 换成 `k`；若数组无序，先排序或改用哈希计数。这道题在字节出现频率很高，变体是「删除所有重复」与「保留一次」，建议三种一起练。
