### 《参考解析》

**== 与 equals**：`==` 对基本类型比较值，对引用类型比较地址；`equals` 是 Object 的方法，默认实现等同 `==`，String、Integer 等类重写为比较内容。要点补充：重写 equals 必须重写 hashCode，否则放进 HashMap 会找不到；Integer 缓存 -128 到 127，超出范围用 `==` 比较会返回 false，这是常见陷阱。

**线程安全与实例**：线程安全的本质是多个线程访问共享可变状态时，不出现竞态与可见性问题。保证手段：不可变对象、局部变量（栈封闭）、同步（synchronized、Lock）、原子类与 CAS、并发容器、线程安全的数据结构。举实例：库存扣减用 `synchronized` 或数据库行锁加版本号；计数用 `AtomicLong` 或 LongAdder；缓存更新用「先更新库再删缓存」加延迟双删。要能说出为什么选这个手段而不是别的。

**创建线程的方式**：继承 Thread、实现 Runnable、实现 Callable 配合 FutureTask（有返回值与异常）、通过线程池提交任务、CompletableFuture 编排。生产上一律用线程池，不直接 new Thread。

**线程池参数与拒绝**：核心线程数、最大线程数、空闲存活时间与单位、任务队列、线程工厂、拒绝策略。执行流程：核心线程未满则新建；核心满了进队列；队列满了且未到最大线程数则新建非核心线程；都满了触发拒绝。拒绝策略四种见前述。参数设置要看任务是 CPU 密集还是 IO 密集：CPU 密集约为核数加一，IO 密集按「核数 ×（1 + 等待时间/计算时间）」估算，并以压测为准。队列必须设容量，无界队列会让最大线程数失效并可能 OOM。

**GC 机制与算法**：JVM 把堆分新生代（Eden 与两个 Survivor）和老年代。对象优先在 Eden 分配，Minor GC 时存活对象复制到 Survivor 并增加年龄，达到阈值晋升老年代；大对象直接进老年代。回收算法有标记清除（产生碎片）、复制（新生代用，浪费一半空间但快）、标记整理（老年代用，无碎片但移动对象成本高）、分代收集。判定垃圾用可达性分析，从 GC Roots（栈引用、静态变量、常量、JNI 引用）出发不可达即可回收。垃圾收集器从 Serial、Parallel、CMS 到 G1、ZGC。

**G1 原理**：把堆划分为大小相等的 Region（默认约 2048 个），每个 Region 可以是 Eden、Survivor、Old 或 Humongous（存大对象）。G1 不再物理分代但逻辑上保留新生代与老年代。它维护每个 Region 的回收价值（回收能释放的空间与耗时之比），在「停顿时间目标」约束下优先回收价值高的 Region，这就是 Garbage First 的含义。回收分 Young GC、Mixed GC（同时回收部分老年代 Region）与 Full GC（单线程或并行兜底，应尽量避免）。关键技术是 Remembered Set 记录跨 Region 引用、SATB 并发标记处理漏标。调优参数 `-XX:MaxGCPauseMillis` 设目标停顿，`-XX:InitiatingHeapOccupancyPercent` 控制并发标记启动阈值。

**最左前缀原则**：联合索引 (a,b,c) 按 a、b、c 的顺序排序，所以能用于 a、a+b、a+b+c 的等值与范围查询；跳过 a 直接用 b 无法使用索引（除非有索引跳跃扫描这类优化器特性，且条件受限）。范围查询会截断后续列的使用：`a = 1 and b > 2 and c = 3` 中 c 无法用于索引定位，但可以被索引下推用于过滤。

**JOIN 优化**：先看执行计划确认驱动表与连接方式。优化方向：给连接字段建索引（被驱动表的连接列必须有索引，否则每行都全表扫）；小表驱动大表，减少外层循环次数；只查需要的列，尽量走覆盖索引；减少回表，必要时用延迟关联；把能在子查询里先过滤的条件提前，缩小中间结果；避免在连接列上做函数或类型转换；数据量大时考虑冗余字段或宽表，把 join 变成单表查询；分页场景避免大偏移量。

**Full GC 频繁的排查**：先确认现象：用 `jstat -gcutil` 看各区占用与 GC 次数耗时，`-XX:+PrintGCDetails` 或 GC 日志看每次回收前后变化。可能原因：内存泄漏（老年代持续上涨、Full GC 后降不下来）、大对象直接进老年代、晋升过快（Survivor 太小或年龄阈值太低）、元空间不足、显式调用 System.gc、堆设置过小。定位手段：heap dump 后用 MAT 看支配树与最大对象，找持有链；对比多次 dump 看哪个类实例持续增长。修复要落到代码：断开静态集合的引用、限制缓存容量、改用软引用或弱引用、调大新生代或调整晋升阈值。

**Redis ZSet 做滑动窗口限流**：Key 设计为 `rate:limit:{ip}:{api}` 或 `rate:limit:{ip}`，member 用「时间戳-随机数」保证唯一，score 用毫秒时间戳。每次请求用 Lua 脚本原子执行：`ZREMRANGEBYSCORE key 0 now-window` 清掉窗口外的记录，`ZCARD key` 取当前数量，小于阈值则 `ZADD` 并设置过期时间，否则拒绝。返回剩余配额。要点：脚本保证原子性；给 key 设过期避免冷 IP 占内存；窗口大小与阈值按接口分级；分布式下限流要接受 Redis 的网络开销，热点 IP 可以加本地令牌桶做二级缓冲；超大规模可用滑动窗口计数（分桶）近似替代，省内存。
