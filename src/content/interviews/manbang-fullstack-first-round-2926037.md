### 《参考解析》

**意图识别：先定边界，再谈模型**

问「意图识别怎么实现」时，面试官想听的是你有没有把问题定义清楚。可落地的答法分三层。一是先枚举意图集合与兜底策略：把业务里真实出现的用户说法聚类成有限个意图，剩下的全部归到「未知」，未知不是失败，而是走澄清追问或转人工的入口。二是实现路线按成本排序：关键词与正则兜高频明确表达，轻量文本分类模型处理有监督样本充足的场景，样本少、意图边界模糊时用大模型加结构化输出，把意图连同槽位、置信度一起返回。三是工程约束：阈值以下的低置信结果不硬判，多轮对话里要带上下文（上一轮意图与已填槽位），线上被纠正的样本要回流做迭代。讲完链路再补一句评测方式：用混淆矩阵看哪两类意图互相误判，比只看整体准确率有用得多。

**Dify 这类编排平台：它解决的是「谁来串流程」**

回答 Dify 怎么用时不要停在「拖了几个节点」，要说清它在系统里的位置：它把模型调用、提示词、知识库检索、变量与条件分支、工具调用编排成一条可视化流程，对外暴露成 HTTP API，业务后端只负责鉴权、计费与数据落库。典型链路是「用户输入 → 意图识别与改写 → 知识库检索 → 拼上下文 → 生成 → 结构化后处理」。真正体现工程能力的是边界划分：与业务无关的提示词与检索策略放在编排里，权限、计费、审计、关键的幂等与事务必须留在自己的服务里。可观测性也要提——每次调用都能拿到完整的调用链与 token 消耗，否则线上调不动。被追问「为什么不直接写代码调模型」时答权衡：编排平台换来迭代速度和可视化调试，代价是多一层黑盒与部署依赖；当流量、成本或定制需求超过它的承载能力，就该把关键链路收回来自己实现。

**聚簇索引与非聚簇索引：从 B+ 树叶子节点装什么说起**

聚簇索引的组织方式决定了 InnoDB 的很多行为：主键索引的叶子节点直接存放整行数据，所以按主键查一次树查找就拿到数据；二级索引的叶子节点只存索引列加主键值，要取非索引列就得拿主键再回表一次。由此能自然推出几个高频结论——主键要短且单调递增，短是为了让所有二级索引都小，递增是为了避免随机插入造成页分裂；没有显式主键时 InnoDB 会选唯一非空索引或生成隐藏 rowid，所以显式定义主键不是可选项；覆盖索引（查询列都在索引里）能免掉回表，是常见的优化手段；联合索引要遵守最左前缀，范围查询之后的列用不上排序。如果被问到 MyISAM，一句话带过：它的索引都是非聚簇的，数据文件与索引文件分离，没有「主键即数据」这回事。

**幂等与慢 SQL：两个都要落到具体方案**

幂等的标准答法从「重复请求会从哪来」讲起：用户连点、网络重试、消息重投、定时任务重跑。方案按场景选：写库用唯一索引或去重表挡重复，让数据库做最终裁决，最可靠；状态流转用「只允许从 A 到 B」的条件更新，看影响行数判断是否真的执行；接口层用幂等键加分布式锁防并发重复；消息消费侧用业务唯一键记录已处理。要补上幂等键的生成与保存位置（客户端生成、服务端落库并设过期），以及幂等与重试的关系——能安全重试的前提就是幂等。

慢 SQL 是四步：先靠慢查询日志与 performance_schema 抓真身，再用 `EXPLAIN` 看执行计划（type、key、rows、Extra 里的 Using filesort 与 Using temporary），然后改索引或改 SQL（去掉函数与隐式类型转换导致的索引失效、避免 `select *`、大偏移分页改游标或延迟关联），最后看是否需要结构层面的调整（分表、归档冷数据、读写分离）。回答时最好带一个自己调过的例子：优化前多少毫秒、做了什么、优化后多少。

**中间件、项目叙事与这场面试的复盘**

中间件那一问答得实在反而更好：说清 Redis 用来做什么（缓存什么数据、过期与更新策略、怎么防穿透与雪崩），以及为什么没上消息队列（量级不够、同步调用可接受），比堆一串名词安全得多——面试官问这个只是想摸你的知识边界，答「听过但没用过」不会被扣分，硬编一定被追问穿。项目部分有两个高频点：一是「为什么做这个项目、为什么取这个名字」在考动机与真实性，讲清触发场景、你解决的那一步、有没有人真的在用；二是意图识别、Dify 这些技术点要能画出一条从输入到输出的完整链路，每层的输入输出都说清楚。没有实习这点不必回避：把项目当成实习来讲——目标、你的角色、量化的结果、踩过的坑，比解释「为什么没实习」更有说服力。算法题没写完也不等于结束：先讲思路、复杂度、边界与测试用例，说明如果继续会怎么写，很多时候面试官要看的就是这个过程。这一场面试官全程引导、不会的题也不为难，但结果仍是未通过，说明流程性问答答得顺并不等于技术深度够——把项目里的技术决策和量化结果准备好，才是决定性的那一层。
