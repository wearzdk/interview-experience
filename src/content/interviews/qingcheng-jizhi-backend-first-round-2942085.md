### 《参考解析》

**线程池任务的通知与同步**：常见三种模型——提交后返回 future，调用方阻塞等待（`condition_variable` + 完成标志，简单但占线程）；回调 / 完成队列（worker 执行完把结果推进无锁队列，由 IO 线程统一收割，适合事件驱动）；协程或 Promise（把等待变成挂起，不占线程）。选择依据是「谁在等、等多久、并发量多大」：高并发短任务用回调或协程避免线程膨胀，低并发或需要顺序语义时用 future 更直观。要说明同步原语的选择（mutex + condvar 的惊群、无锁队列的 ABA、内存序）。

**怎么判断到了性能极限**：先定义指标——吞吐（QPS）、延迟分位（P50/P95/P99）、错误率、资源利用率（CPU、内存、网络、磁盘 IO）。做阶梯加压，画「并发数—QPS—P99」曲线：QPS 不再随并发上升、P99 开始陡增、错误率抬头，三者同时出现的拐点就是容量上限。单看 CPU 不够，还要看是否已排队（runqueue 长度、`load average`、CPU 的 `steal`、线程池队列长度）。

**CPU 打满还是请求排队**：CPU 打满看 `us`（用户态）与 `sy`（内核态）是否长期接近 100%、runqueue 是否大于核数、上下文切换是否暴涨；请求排队看线程池活跃线程与队列长度、连接等待数、P99 是否在 CPU 未满时就已升高（说明瓶颈在别处，如锁竞争、下游、GC）。工具上 `top`/`pidstat`、`vmstat`、`perf`、`eBPF` 火焰图能区分「算得慢」与「等得久」。

**K8s 横向扩容**：HPA 按指标扩副本，最常用 CPU / 内存利用率，进阶用自定义指标（QPS、队列长度、延迟）或外部指标（消息积压）。配置要点：`minReplicas`/`maxReplicas`、目标利用率（CPU 60%~70% 留缓冲）、`behavior` 里的扩容与缩容窗口（扩容要快、缩容要慢，避免抖动）、`scaleUp` 每次最多加多少。局限是 HPA 只能扩副本，扩不了单机容量；冷启动慢的服务要配预热与就绪探针，或提前扩容（cron 定时）。集群层面还有 Cluster Autoscaler 负责加节点，扩容链路要端到端打通。

**三个实例扩到六个还是缩到一两个**：看「单实例容量 × 副本数」与「流量曲线 + 冗余要求」。先算出单实例在目标 P99 下的安全 QPS，再用当前峰值除以它得到所需副本数，向上取整并留一个冗余（N+1）。缩容要满足两个条件：缩后单实例负载仍在安全线内、且缩容窗口内不会因流量波动触发再次扩容。还要考虑最小副本数（高可用至少 2）、发布时的滚动更新余量、以及有状态服务的分片约束。

**CPU 高但其他指标低**：典型是「算得太多」——死循环或忙等（自旋锁、轮询）、正则回溯、序列化/压缩、加密、GC 线程占 CPU（此时看 GC 日志与堆）、频繁系统调用或上下文切换（`sy` 高）、日志同步刷盘、容器 CPU limit 导致的 throttling（`cpu.stat` 里的 `nr_throttled`）。排查顺序是火焰图看热点函数，再看是否被限流、是否有锁自旋。

**CPU 低但大量失败或排队**：说明瓶颈不在计算，而在「等待」或「拒绝」。可能原因：连接数或文件描述符耗尽（`ulimit`、`TIME_WAIT` 堆积）、线程池队列满触发拒绝、下游依赖超时（数据库连接池耗尽、RPC 超时）、锁竞争导致线程挂起、DNS 解析慢、网络丢包与重传、容器内存 limit 触发 OOMKill。排查用「分层看指标 + 抓包 + 日志错误码」，别只盯 CPU。

**Redis 的更新与过期**：更新是单线程顺序执行命令，`SET` 覆盖旧值；过期策略是「惰性删除 + 定期删除」——访问时检查过期时间，后台每秒若干次随机抽样删除，因此过期键不保证立刻释放内存。淘汰策略 `maxmemory-policy` 决定内存满时怎么处理（`allkeys-lru`、`volatile-lru`、`allkeys-lfu`、`noeviction` 等）。持久化有 RDB 快照与 AOF 日志（`appendfsync` 三档），主从复制是异步的，故障切换可能丢少量数据。

**RPC 框架解决什么**：把「跨进程调用」伪装成本地方法调用，统一处理序列化、网络传输、服务发现、负载均衡、超时重试、熔断限流、链路追踪。自研的目的通常是「可控」——协议与序列化可定制、能嵌进现有治理体系、减少对重量级框架的依赖；代价是要自己维护兼容性、可观测性与多语言支持。回答时要说清「哪些是自研的、哪些复用了现成组件」。

**Protobuf 的维护**：字段编号一旦发布就不能改、不能复用（删掉的编号要 `reserved`），新增字段用新编号并保证向后兼容（老客户端忽略未知字段）；不要改字段类型（除非兼容的类型变更）；用独立的 proto 仓库或目录 + CI 做 breaking change 检查（`buf breaking`）；版本化包名（`v1`、`v2`）；生成代码随构建产出，不手工改。多人协作时按文件或服务划分 owner，编号段按模块预分配，冲突在 CI 阶段就拦下。

**ZooKeeper 的定位与树形结构**：ZK 提供强一致的分布式协调能力——临时节点做服务注册（会话断开自动删除）、顺序节点做队列与选主、Watcher 做变更通知、分布式锁与配置管理。树形路径可以设计成 `/service/{serviceName}/{instanceId}`，方法级可以用 `/service/{service}/{method}/{provider}`，但要注意节点数量与 Watcher 风暴。ZK 不适合存大量数据（每个节点建议小于 1MB），也不适合高频写。

**原子广播（ZAB）**：ZAB 分两个阶段——崩溃恢复（选主，保证已提交事务不丢）与消息广播（Leader 收到写请求生成事务提案，广播给 Follower，超过半数 ACK 后提交并通知）。它保证顺序性与线性一致性写，读可以从 Follower 读（可能读到旧数据，需要 `sync`）。与 Raft 的区别是 ZAB 偏「主备 + 广播」，Raft 的日志复制与选主更统一，工程上两者解决的问题高度重叠。

**注册中心的单点故障**：客户端侧要缓存服务列表（本地快照）并支持「注册中心不可用时继续用旧列表」，避免整体不可用；服务端部署奇数节点（3 或 5）组成 quorum，容忍 (n-1)/2 个节点故障；跨机房部署要考虑脑裂与延迟，用 observer 节点扩展读能力；配合健康检查与摘除（临时节点 + 心跳），以及变更通知的兜底轮询。三节点挂一个仍可写（2/3 多数），挂两个则只读不可写；五节点容忍两个。要点是「注册中心挂了不能导致业务挂」，所以客户端容错比集群规模更重要。
