### 《参考解析》

**Iceberg 与 Hudi 的区别**：两者都是数据湖表格式，都解决 Hive 表「没有事务、快照回溯要存多份全量、Schema 演进困难」的问题，差异在写入模型与主打场景。Iceberg 以元数据树（metadata file → manifest list → manifest file → data file）组织快照，提交是元数据层的原子替换，不依赖 HDFS 的 rename，适合大批量批写、时间旅行和引擎中立（Spark / Flink / Trino / Hive 都能读同一张表）。Hudi 以文件组（file group）+ 时间线（timeline）组织，围绕 upsert 设计，COW 表写时合并、MOR 表写日志文件后异步 compaction，更适合高频更新、需要近实时入湖的场景，代价是 compaction 与清理需要额外调度。选型看写入模式：以追加为主的离线数仓选 Iceberg，主键更新频繁、要求分钟级可见的选 Hudi；还要考虑团队现有引擎与运维能力，别只看压测数字。

**Flink 反压的排查与处理**：反压是下游消费速度低于上游生产速度，背压沿算子链向上传导。排查顺序是先在 Flink UI 看反压指标定位到具体算子（红色高负载），再看该算子的 inPoolUsage / outPoolUsage 与 busy、backpressured 比例，然后查 GC、checkpoint 时长与对齐时间、是否数据倾斜（各 subtask 处理量差异）、是否外部存储写入慢（维表查询、Sink 批量参数过小）。处理手段按瓶颈位置选：Sink 慢就调大 batch、开异步 IO、加并行度或先落 Kafka 缓冲；数据倾斜就加盐打散 key 或两阶段聚合；资源不足就提高并行度与 slot、拆分算子链；checkpoint 慢则调大超时、开启非对齐 checkpoint（unaligned checkpoint）或换增量快照。要强调的是加并行度不是万能解——并行度受上游分区数与 Sink 承载能力约束，盲目加只会把压力推到下游。

**Kafka 分区流量不均**：根因通常是 key 设计不合理（少数 key 承载大部分流量）或生产者分区器与业务分布不匹配。先看各分区的字节速率与堆积（`kafka-consumer-groups --describe` 看 lag 分布），确认是生产端倾斜还是消费端处理不均。治理办法：换高基数 key（如用户 ID 加随机后缀）、生产端自定义分区器、把热点 key 单独拆 topic 并单独扩容消费者、消费端合并小消息批量处理。若只是短时突发，可临时增加分区并重平衡，但要注意增加分区会改变 key 到分区的映射，顺序性语义会受影响。

**数仓分层**：分层的目的是解耦、复用与可排障——每层职责单一，上游变更只影响相邻层；同一份明细被多个应用复用；出问题时能按层定位是采集、清洗还是聚合错了。常见四层：ODS 贴源（保留原始数据、只做轻量规整）、DWD 明细（清洗、去重、维度关联后的宽表）、聚合层（按主题与粒度做轻度汇总，也叫 DWS）、ADS 应用层（面向报表与接口的结果表）；维度表单独维护（如部门、项目），避免在每个事实表里重复存描述。分层不是越多越好，层数要匹配团队规模，小团队三四层足够，层太多会让链路变长、时效变差、排障成本上升。

**「碰到新技术怎么学习」**：给出可复用的方法而不是态度——先读官方文档把整体架构与核心概念过一遍，再找一个最小可跑的样例（官方 quickstart 或本地 docker 环境）动手验证，然后把遇到的问题记下来带着问题看源码或社区 issue，最后在项目里落地并复盘。这样答的好处是可验证：面试官追问「你最近这样学过什么」时能立刻给出一项具体的、有产出的例子。

**为什么选大数据、最大挑战**：这类动机题要给「具体触发点 + 长期判断」，不要只说行业前景。例如从一次实习里处理慢查询开始，发现瓶颈在数据组织方式，于是往下追到存储与计算引擎，逐步形成方向偏好。挑战题按 STAR 讲：背景（数据量、时限）、难点（技术或协作）、你做的动作、量化结果，最后补一句如果重来会怎么改。
