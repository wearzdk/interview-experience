### 《参考解析》

**多智能体协同，先讲拓扑再讲通信**。常见的三种形态：主管式（一个 supervisor 负责拆解与分派，子 Agent 各自带工具，结果回给主管汇总）、交接式（handoff，当前 Agent 判断该换人时把控制权和上下文一起交出去）、群聊式（多个角色轮流发言、由裁判收敛）。选哪种取决于任务有没有明确的阶段边界——流水线清晰的用主管式，跨领域咨询类的用交接式，需要多视角辩论的才用群聊。工程上真正难的不是分工，而是三件事：上下文怎么裁（不能把全部历史塞给每个子 Agent，要按角色给最小必要上下文）、什么时候停（要有最大轮次和收敛判据，否则两个 Agent 会互相客气到超时）、失败怎么传（子 Agent 失败要能带着原因回到上游，而不是吞掉返回一句「处理失败」）。

**意图路由不要只输出一个标签**。可用的实现有三类：规则/关键词匹配（快、可解释，适合高频固定说法）、小模型分类（微调过的分类头，延迟低）、向量相似度检索（把用户话 embed 后跟意图样例比对，冷启动友好）。生产上通常是组合：规则先兜明显 case，向量召回候选意图，再用小模型在候选里做精排。更关键的是输出结构——除了意图标签，还要给置信度和已抽到的槽位，让下游知道这一跳是确定的还是猜的。只返回单标签的路由器，在遇到「我要改签顺便问下行李额」这种话时一定会错。

**路由判错怎么兜底，面试官最爱追**。分三级：置信度高且槽位齐 → 直接执行；置信度中等或槽位缺 → 走澄清追问（把候选意图列出来让用户选，或只追问缺的那个槽位），而不是硬猜；置信度低或明显超出范围 → 兜到通用问答或转人工，并记一条可用于回流的路由日志。另外两个工程细节要主动说：一是**可观测性**，每次路由都要落 trace（原文、候选意图、分数、最终决策、后续是否被用户纠正），否则没法算准确率；二是**破坏性操作的二次确认**，改签、退款、下单这类动作即使路由置信度很高也要用户确认一次。准确率的口径也要说清楚：离线用标注集算 top-1 与 top-3，线上看「用户是否在下一轮纠正了意图」这个隐式反馈，两者不能混着报。

**一条请求多个意图，本质是任务编排**。步骤是：意图拆解（让模型把一句话拆成子任务列表，标注依赖关系）、排序（有依赖的串行、无依赖的并行）、逐个执行、结果合并成一段话或分条返回。容易踩的坑：拆得太碎（把「查订单并改地址」拆成五个子任务，用户等不及）、顺序错（先退款再查是否可退）、部分失败的处理（一个子任务失败，是整体回滚还是给部分结果 + 说明）。涉及钱的场景一定要在合并结果后加一次整体确认，而不是每个子任务各问一遍。

**架构与适配层，考的是解耦意识**。适配层是防腐层：把模型厂商、工具、渠道的差异收敛成一套内部接口——统一的 chat/stream 调用、统一的工具描述格式、统一的错误码、统一的超时与重试策略、统一的 token 计量。实现上用注册表 + 能力声明（每个 provider 声明自己支持流式/函数调用/多模态），别用 if-else 堆厂商分支；换模型只改配置不动业务代码，这是面试官想听到的那句话。架构图讲的时候按「接入层 → 编排层 → 能力层（模型/工具/检索）→ 数据层」四层说，每层一句话讲职责，比堆名词有效。

**历史记录导出与海量数据**。同步 `select` 全量再拼字符串是最容易被否的答法，正确姿势是异步：提交导出任务进队列 → 游标分页（按 `id > last_id` 而不是 `offset`）流式读 → 边读边写 NDJSON/CSV 到对象存储 → 完成后给一个带过期时间的签名下载链接 → 任务状态有状态机（排队/生成中/完成/失败/过期）。再加几条：按时间分区裁剪、只导出必要字段、大字段截断、单用户并发导出限流、导出文件定期清理。如果被问「为什么不直接查库」，答案是长事务会拖垮主库、大结果集会把内存打爆。

**收益量化别只说「效率提升了」**。按环节拆：人工处理一次要多久、Agent 处理一次要多久、一次解决率、平均往返轮次、转人工率、用户满意度。数据来源可以是埋点日志的前后对比，也可以是小流量 A/B。要主动交代口径的局限——样本期是否赶上大促、用户结构有没有变，否则一个漂亮的百分比反而会被追问穿。RAG 全链路、评测体系与框架选型那几问的答法，见《携程 Agent 开发一面真题：RAG 召回率、上下文工程与 LangGraph 选型》。
