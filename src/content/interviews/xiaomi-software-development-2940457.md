### 《参考解析》

**螺旋矩阵**：按层模拟最稳，维护上、下、左、右四个边界，依次从左到右、从上到下、从右到左、从下到上遍历，每走完一条边就收缩对应边界；循环条件是 `top <= bottom && left <= right`，单行或单列时要在最后两条边上做判断，否则会重复输出。时间复杂度 O(mn)，每个元素访问一次；除输出数组外额外空间 O(1)。递归写法按「一圈一圈剥」也可以，但边界处理更容易出错。面试时先说出思路与边界，再动手写，比直接敲代码更稳。

**JWT 流程**：登录时服务端校验账号密码，用密钥对 `header.payload.signature` 签名，把 token 返回给客户端；客户端此后在 `Authorization: Bearer <token>` 中携带；服务端验签并检查 `exp`、签发者等声明，通过后从 payload 取出用户标识。payload 只是 Base64 编码而非加密，任何人都能解开，所以不能放手机号、身份证号这类敏感信息。token 一旦签发，在过期前无法单方面作废，需要短有效期加刷新令牌，或者维护一个黑名单。密钥轮换时要支持多把密钥并存，否则全量用户会被强制登出。

**JWT 与 Session 的区别**：Session 把状态存在服务端，客户端只持有 sessionId，服务端可随时失效，代价是要共享存储（Redis）才能水平扩展；JWT 是自包含的无状态凭证，服务端不存副本，天然适合多实例与跨域，代价是注销、改权限、封号这类操作无法立即生效。安全面上，Session 主要防 CSRF（配合 SameSite、CSRF token），JWT 存在 localStorage 时主要防 XSS；放在 HttpOnly Cookie 里则又回到 CSRF 问题。选型看场景：后台管理、需要强制下线的系统用 Session 更合适；开放 API、多端共用、服务间调用用 JWT 更合适，配合短过期与刷新机制。

**死信队列的逻辑**：消息被消费者显式拒绝且不重新入队、超过 TTL 未消费、队列长度超限、或重试次数超过上限时， broker 会把消息路由到配置的死信交换机（DLX），再进入死信队列，由独立的消费者做告警、落库、人工补偿或延迟重试。核心处理逻辑通常是：记录失败原因与原始消息、区分可重试与不可重试错误、对可重试的按退避策略重新投递、对不可重试的进入人工队列。

**进程崩溃时队列的状态**：结果取决于持久化与确认机制。交换机、队列、消息三者都声明为持久化，且生产者开启 publisher confirm、消费者使用手动 ack 时，未 ack 的消息在连接断开后会被 broker 重新入队并标记 redelivered，其他消费者可以继续消费，代价是可能重复投递，业务必须做幂等（唯一键、去重表、状态机）。如果消息未持久化，或消费者用了自动 ack，崩溃时正在处理的消息就直接丢失。还要注意「已 ack 但业务未完成」的窗口：ack 放在业务提交之后，或者用本地消息表、事务消息来保证一致性。

**`@Transactional` 失效场景**：同类内部方法调用不走代理，注解不生效；方法不是 public（部分代理模式下）；异常被 `catch` 吞掉没有抛出；默认只对 `RuntimeException` 和 `Error` 回滚，受检异常要显式写 `rollbackFor`；类没有被 Spring 管理、或用了不支持事务的存储引擎；在事务方法里另起线程执行；传播行为配置不当，例如内层 `REQUIRES_NEW` 与外层事务相互独立。还有一个容易被忽略的点：事务提交发生在方法返回之后，若在事务内发送消息或调用外部接口，可能出现「消息已发出、数据库回滚」的不一致，应改为提交后触发。

**项目难点与复盘**：按「现象—排查—根因—解决—复盘」讲。现象要具体（接口 P99 从 200ms 涨到 2s、某类消息偶发重复消费），排查要说出用了什么手段（日志、链路追踪、压测、监控指标），根因要落到机制层面而不是「加了个缓存就好了」，复盘给出后续改进（加监控、补测试、改设计）。面试官真正想听的是判断过程，而不是项目规模。

**AI 编程的看法**：AI 在样板代码、单测、文档、陌生 API 的用法上收益明显，能显著压缩重复劳动；风险在于生成的代码可能调用不存在的接口、隐式假设业务规则、把错误处理写成空实现，且代码量越大 review 成本越高。合理用法是把它当作需要 review 的初级合作者：先让它解释思路与边界，再让它写实现与测试，关键路径（并发、事务、安全、计费）自己把关，团队层面则要补上静态检查与测试覆盖。若私下写过 Agent 或工具，讲清触发方式、工具定义、失败重试与上下文管理，比罗列工具名更有说服力。
