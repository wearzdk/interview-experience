### 《参考解析》

**架构抽象的落点**：把 Agent 运行抽象为「状态 + 节点 + 边」的图，节点只有几类——模型调用、工具调用、条件判断、终止；ReAct 是「模型调用 → 解析 action → 工具调用 → 回填 observation → 再进模型」的自环，Plan-and-Execute 是「规划节点产出一张步骤表 → 逐步执行 → 失败回规划」的两段结构。业务方显式指定时给的是工作流标识加配置（最大步数、终止条件、可用工具集、是否允许并行工具调用），框架按注册表取对应的图实例；需要定制时允许传入自定义图，而不是在同一个循环里塞一堆 if。

**上下文压缩**：先定触发条件（token 占比、轮数、工具结果累计长度），再定策略。常用组合是保留 system 与最近若干轮原文、把更早的对话压成摘要、对超长工具结果做截断或二次摘要、把稳定的结构化状态（任务清单、已确认事实、文件路径）外置到 scratchpad 而不是留在对话里。压缩必须发生在轮次边界，且保证 tool_call 与 tool_result 成对，否则模型会报参数缺失；压缩后要重新计数 token 并保持消息前缀稳定，否则整段缓存失效，成本反而上升。

**Function Calling 的框架能力**：从类型或装饰器生成 JSON Schema、调用前做参数校验并把校验错误回传给模型、支持并行工具调用与流式增量解析、提供超时与取消、把工具结果裁剪成模型可读的短结构、统一错误码、按权限决定哪些工具对该用户可见，以及工具调用的审计日志。参数校验失败不要让框架直接抛异常终止，应作为一条工具结果返回，让模型自行修正。

**工具召回**：工具数量到几十上百个后，全量塞进 system 会挤占上下文并降低选择准确率。做法是分层：先按命名空间或服务选一组，再用工具描述向量召回 top-k，最后只把选中工具的完整 schema 放进本轮请求；也可以两阶段，第一阶段只给工具名与一句话描述做选择，第二阶段再给完整 schema。召回应带规则兜底（最近使用、显式指定的工具集），并把工具表缓存在稳定前缀里。

**长程任务与 ReAct**：ReAct 每一步只看局部观察，没有全局计划，任务一长就容易重复动作、偏离目标、上下文爆炸。判断是否拆分规划与执行的信号很直接：步骤数超过十来步、步骤之间有依赖关系需要排布、需要跨会话恢复、需要人工审批节点、或者失败重试的代价高。短任务和探索性任务仍适合 ReAct，因为计划本身在信息不足时没有意义。

**多 Agent 上下文共享**：共享结构化事实而不是复制完整对话。主 Agent 维护一份共享状态（目标、约束、已完成步骤、产物位置），子 Agent 启动时只拿与自身任务相关的最小上下文和明确的交付契约，返回摘要与产物引用而不是全量轨迹。把全部上下文交给每个子 Agent 会让 token 成本随 Agent 数线性增长，也会让子 Agent 被无关信息干扰。

**记忆分层**：工作记忆是当前会话的对话与临时状态；情节记忆是按时间索引的历史事件与问答；语义记忆是从事件中归纳出的稳定画像、偏好与习惯；程序记忆是可复用的技能与提示模板。一个月前的问答属于情节记忆，跨 Session 使用时按查询改写后做向量召回，再叠加时间衰减与相关性阈值，注入时标注时间与来源，避免把过期结论当成当前事实。

**事件与画像不宜混存**：事件带时间、可增删、可能只反映一次偶发情况；画像是归纳后的属性，需要置信度、来源与更新策略。混在一起最直接的后果是一次临时偏好被写成长期画像，之后每次对话都被错误地个性化。合理做法是事件表独立存储并可回溯，画像由事件定期归纳生成，冲突时以近期高置信度证据覆盖，并允许用户查看与纠正。
