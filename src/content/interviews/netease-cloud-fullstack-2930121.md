### 《参考解析》

**缓存穿透、击穿、雪崩的区别**：三者都是「请求打到数据库」，但成因完全不同，答题时先把区别说清再给对策。

- **穿透**：查的数据**根本不存在**（比如恶意传一个不存在的 id），缓存里没有、数据库里也没有，每次请求都穿过缓存打库。对策是缓存空值（短 TTL）挡住重复的无效查询，加布隆过滤器在入口就判掉不存在的 key，以及对入参做合法性校验、对异常高的查询频率做限流。
- **击穿**：某**一个热点 key 过期**的瞬间，大量并发请求同时落到数据库上。对策是热点 key 不设过期（或逻辑过期，后台异步续期），或者用互斥锁（Redis `SET NX`）让只有一个请求去回源、其余等待，再加单飞（single-flight）在进程内合并同 key 的并发请求。
- **雪崩**：**大量 key 同时失效**（统一过期时间）或缓存服务整体不可用，请求全部涌向数据库。对策是过期时间加随机抖动打散、多级缓存（本地 + Redis）兜住第一波、缓存集群做高可用与多副本、以及对数据库侧做限流与降级（返回兜底数据而不是直接压垮）。

**Redis 数据错了要回滚，但还有大量请求进来**：这题的陷阱是「回滚」这个动作本身——Redis 不是事务数据库，没有回滚语义，你能做的是「修正值」并控制修正过程中不被旧值继续污染。分几步：

第一，**止血**：先确认错误的范围和影响面。如果只是某个 key 的缓存值过时（数据库是对的），直接删掉这个 key 让下次读回源即可，不需要「回滚」；如果是数据库本身写错了，那要先修数据库（走补偿事务 / 反向操作），再处理缓存。

第二，**别在流量高峰直接重建**：大量请求进来时立刻删 key 会导致缓存击穿。做法是先把 key 标成「正在修复」（逻辑过期：写一个带过期标记的值，读取方看到标记就回源并异步重建，或者返回降级数据），再用互斥锁让只有一个请求去执行重建，其他请求等待或读旧值。

第三，**保证顺序与一致性**：修复时先更新数据库、再删缓存（或写新值），并用版本号 / 时间戳防止旧请求把过期数据写回缓存（这是并发下的经典坑：A 读到旧库值 → B 修复了库 → A 把旧值写进缓存）。可以给写入带版本，缓存里存版本号，只有更高版本才能覆盖。

第四，**善后**：核对数据一致性（对账脚本扫一遍受影响范围）、补监控（这类错误应该有告警）、复盘为什么会产生错误数据（是并发写、还是代码逻辑错），因为防住产生比事后修更省。

**「调用外部类导致 Spring 事务失效」怎么回事**：Spring 的声明式事务是靠 AOP 代理实现的——只有**通过代理对象调用**的方法才会被事务拦截器包住。典型失效场景有一串：① 同类内部方法调用（`this.methodB()`），走的是原始对象不是代理，事务注解不生效；② 方法不是 `public`（Spring 的代理默认只拦 public）；③ 异常被自己 `catch` 掉了没抛出去，事务管理器看不到异常就不会回滚（默认只对 `RuntimeException` 和 `Error` 回滚，受检异常要显式配 `rollbackFor`）；④ 类没被 Spring 管理（自己 `new` 出来的）；⑤ 数据库引擎不支持事务（MyISAM）；⑥ 传播行为配置不当（`REQUIRES_NEW` 之外的嵌套）。

题目说的「调用外部类事务失效」通常指这几种变体：把需要事务的方法抽到另一个类里，但那个类没有被 Spring 注入（`new` 出来的），或者调用方持有的是自己 new 的实例而不是注入的代理；也可能是跨类调用时外层方法没有事务、内层方法有 `@Transactional` 但类的代理没生效（比如内部类、匿名类、或用了 CGLIB 代理却把类设成 `final`）。

修复路径：确保跨类调用走注入的代理对象而不是自己 new；需要同内部方法互调事务时，把自己注入自己（`@Lazy` 自引用）或拆到独立 Bean；把 `catch` 里的异常重新抛出，或显式 `TransactionAspectSupport.currentTransactionStatus().setRollbackOnly()`；在 `@Transactional(rollbackFor = Exception.class)` 里声明要回滚的异常类型；用 `AopContext.currentProxy()` 或 `TransactionTemplate` 显式控制。

面试时的加分点是能说清「为什么失效」的机制——代理边界在哪里断掉，而不是背一堆场景。

**模型产生幻觉的原因**：分几个层面看，答的时候分层比罗列更清楚。

**训练层面**：预训练的目标是「预测下一个 token」，优化的是词序列的似然而不是事实正确性——模型学的是「什么话听起来像真的」，不是「什么是真的」。训练数据里本身有错误、过时信息、以及大量似是而非的表述，模型照单全收。知识还有截止时间，问它训练之后的事它就无据可依，只能顺着语言模式编。

**推理层面**：自回归生成是逐 token 采样，一旦前面出现一个偏掉的 token，后面的内容会围绕这个错误「自圆其说」——这就是为什么幻觉往往连贯、细节丰富、听起来特别可信。另外模型缺少「我不知道」的校准能力：它被训练成总要给出答案，而不是在没把握时拒答。

**上下文层面**：检索到的内容不对（RAG 召回错了）、上下文太长关键信息被淹没、或者提示词本身有误导，都会让它基于错误的依据生成。

**对齐层面**：RLHF 之类的对齐倾向于让回答「有帮助、符合用户期待」，这在一定程度上鼓励了「编一个答案」而不是「承认不知道」。

**怎么缓解**（这半段是拉开差距的地方）：给模型可依据的材料（检索增强），并要求引用出处；把「无法确定时明说」写进指令；用结构化输出约束格式，再用程序校验；关键结论走交叉验证（多次采样比对、或用另一个模型审计）；对事实性内容在生成后再做一次检索核对；以及最实际的——把高风险场景（金额、法条、医疗）放在人工复核环节里。
