### 《参考解析》

**AI Coding 在遗留系统里的边界**：优势集中在机械性工作上——读懂老代码、补单测、生成样板与适配层、批量重命名和迁移、把散落逻辑整理成文档，能显著缩短上手时间。风险同样具体：模型没见过你们的隐式约定，容易改掉看似冗余实则兜底的逻辑；生成代码可能忽略事务边界、幂等和异常清理；还会自信地引用不存在的 API。控制手段是把它当实习生而不是作者：改动粒度尽量小、一次只做一件事，先补特征测试（characterization test）把现在的行为锁住再动代码；依赖编译、静态扫描和全量测试作为硬闸门；review 时重点看资源与事务边界、错误分支和并发假设；上线走灰度与可回滚，关键链路保留开关。能讲出「先建立测试护栏再让 AI 动遗留代码」，这题就答到位了。

**Spring Cloud 一次调用的全流程与容错**：调用方从注册中心（Nacos/Eureka）拿到 B 的实例列表，经负载均衡选一个实例，通过 Feign/RestTemplate 发出 HTTP 请求，服务端经网关或直连进入 B 的业务逻辑，响应按原路返回。容错要分层讲：超时分为连接超时与读超时，还要有整体调用超时（比如用超时线程或信号量兜住），超时值从下游 P99 推出来；重试只能用在幂等接口上，限制次数并加退避与抖动，否则会放大故障；熔断用 Sentinel 或 Resilience4j，按失败率与慢调用比例打开断路器，半开状态放少量流量试探；降级是熔断后的兜底，返回缓存值、默认值或友好错误，业务上要能接受；幂等靠调用方生成的幂等键加服务端唯一索引，先把「创建」变成带客户端 ID 的 upsert，再谈重试。链路追踪则是在入口生成 Trace ID 放进请求头（如 swtraceid），沿途透传，通过 agent 字节码增强记录 span。

**连接池大小与 SQL 优化**：连接池不是越大越好，数据库的并发处理能力受 CPU 核数与磁盘 IO 限制。常用估算式是「连接数 ≈ CPU 核数 × (1 + 平均等待时间 / 平均服务时间)」，即按 IO 等待比例放大，先按这个起点压测再调；HikariCP 还要设最小空闲、最大生命周期（小于数据库 wait_timeout，避免用到已被服务端断开的连接）、连接超时与泄漏检测。SQL 侧先定位慢查询（慢日志、APM、explain），优化顺序是：先看能不能加合适的联合索引并满足最左前缀和覆盖索引，再减少回表；多表关联控制表数量与驱动表选择，避免在 WHERE 里对大表做函数运算或隐式类型转换导致索引失效；深分页用游标（where id > last_id）替代 limit 大偏移；实在无法优化再考虑冗余字段、汇总表或读写分离。

**RocketMQ 事务消息与本地消息表**：事务消息解决的是「本地事务提交」与「消息发送」两个动作不在一个事务里的问题。流程是：生产者先发半消息（对消费者不可见），Broker 落盘后回 ACK；生产者执行本地事务，再按结果向 Broker 提交 commit 或 rollback；如果生产者此时挂掉或提交失败，Broker 会定时回查生产者的事务状态接口，由它按本地事务结果决定最终提交还是回滚。这样保证的是「本地事务成功则消息最终可见」。不用事务消息时的替代方案是本地消息表：在同一个本地事务里写业务数据 + 一条待发送消息记录，然后由定时任务或独立线程扫描未发送记录投递到 MQ，投递成功后更新状态，失败按退避重试。两种方案都要求消费端幂等（唯一索引或去重表），并配补偿与人工兜底，才能保证最终一致。

**Redis 分布式锁与线程池参数**：Redis 加 Lua 的优点是脚本在服务端原子执行、减少网络往返、可复用逻辑；缺点是脚本执行会阻塞其他命令（要短小）、集群下多 key 必须落在同一分片、调试与版本管理麻烦。正确加锁是 SET key value NX PX ttl，value 用唯一标识（如 UUID + 线程 ID），释放时用 Lua 比对 value 再删除，避免误删别人的锁；业务超过 TTL 要有续期（看门狗）或改为状态机；单实例主从切换存在丢锁窗口，强一致场景用 Redlock 或改走数据库乐观锁。线程池要先定用途再定参数：CPU 密集型核心线程数约为核数 + 1，IO 密集型约为核数 × (1 + 等待时间/计算时间)，队列要有界并明确拒绝策略（CallerRunsPolicy 或落库重试），线程命名与监控（活跃数、队列积压）必备。ZSet 排行榜用跳表 + 哈希实现有序与 O(1) 取分，Pipeline 则把多条命令一次发送减少 RTT，但它不保证原子性，需要原子就上 Lua 或 MULTI/EXEC。

**RAG 排查、Agent 记忆与审核指标**：RAG 召回差要按链路逐段排查：数据清洗（噪声、OCR 错误、重复文档先去重）、切分（chunk 过大导致语义稀释、过小导致上下文断裂，按结构切并用重叠窗口）、检索（向量模型是否匹配语料语言与领域、是否需要混合 BM25 兜住关键词与编号）、融合与重排（RRF 融合、cross-encoder 重排取 Top N）、最后才是生成侧的 prompt 与引用约束。评估要分层看召回率与命中率，才能判断是检索问题还是生成问题。Agent 记忆可以分四层：上下文是本次推理窗口内的信息，状态是任务执行中的结构化进度，短期记忆是会话内的历史与实体，长期记忆是跨会话沉淀的用户偏好与知识；写入要设门槛（重要性与置信度、去重与冲突检测、超时过期），召回要按相关性 + 时效 + 权限过滤，并把冲突显式呈现而不是静默覆盖。内容审核效果不能只看「识别率」，要同时给出准确率与召回率、混淆矩阵与误杀率，说明标注口径与人工抽检样本量，附上线上灰度对比数据；只报一个提升百分比而不讲口径，面试官一定会继续追。
