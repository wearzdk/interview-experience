### 《参考解析》

**IM 耗时排查**：不要一上来就怀疑代码。先用 traceId 把一次请求的完整链路串起来，看耗时集中在网络接收、任务排队、业务处理还是消息持久化。线程池排队时间上升，查工作线程数、队列长度与是否存在阻塞调用；数据库耗时上升，查慢 SQL、索引命中与连接池等待；还要看客户端慢连接——发送缓冲区长期积压时，服务端处理再快消息也发不出去，需要结合连接状态与发送队列长度分析。横向对比同时段的连接数、消息量与发布记录，确认是否是流量突增或某个版本引入。

**epoll 与 select**：两者都是 IO 多路复用，本身不会让单次 IO 变快，价值在于一个线程管理多个描述符，避免每连接一线程。`select` 每次调用都要传入整个描述符集合，返回后应用还要遍历找出就绪项，且有 `FD_SETSIZE` 限制；`epoll` 把注册与等待拆开，用红黑树管理监听集合、就绪链表返回事件，只处理真正活跃的连接，在连接多而活跃少的场景优势明显。但 epoll 并非任何情况下都更快：需要选择 LT 或 ET，ET 配合非阻塞 Socket 时必须读写到 `EAGAIN`，否则数据留在缓冲区却等不到下一次通知；连接数很少时两者的差距可以忽略。

**日志系统设计**：日志是还原偶发问题的主要依据，设计要同时考虑可读性、性能与定位能力。按 DEBUG、INFO、WARN、ERROR 分级，固定记录时间、线程、traceId、请求标识、模块与错误码；高并发下不要由业务线程同步写盘，用异步 Appender 把日志写入有界队列，由独立线程批量落盘，并明确队列满时的策略。还要处理轮转与保留、服务退出时的刷盘、敏感字段脱敏，以及日志量过大时的采样。日志系统本身也可能成为瓶颈，需要监控队列积压与丢弃计数。

**智能指针与内存泄漏**：智能指针减少的是「忘记释放」这一类问题，不能保证没有泄漏。`unique_ptr` 独占所有权、离开作用域释放、只可移动；`shared_ptr` 通过控制块维护强引用计数，计数归零时销毁对象，弱引用计数归零时销毁控制块。典型漏网场景是循环引用：两个对象互相持有 `shared_ptr`，外部引用释放后计数仍不归零；用 `weak_ptr` 打破环，`weak_ptr` 不增加强引用计数，使用前 `lock()` 提升。此外还有把同一裸指针交给两个 `shared_ptr`、在构造中 `this` 逃逸、以及非内存资源未用 RAII 封装等问题。工程上优先用栈对象与 `unique_ptr`，明确所有权再考虑共享。

**线程池积压**：线程池的价值是复用线程、控制并发度，线程数并非越多越好，CPU 密集型任务线程过多只会增加上下文切换。实现上是任务队列 + 工作线程集合 + 条件变量，工作者空闲时等待，提交任务后唤醒。积压时先看队列长度、任务执行耗时与 CPU 利用率，再决定扩容：IO 密集型可适当增加线程；若阻塞来自数据库连接池不足，单纯加线程会让问题更严重。生产环境要有有界队列与拒绝策略（拒绝、丢弃最旧、调用方执行），避免流量突增把内存撑爆；同时处理线程退出、任务异常与服务关闭时的资源回收。

**Redis 未读数一致性**：未读数看似一个计数器，实际涉及消息重试、多端登录、并发已读与缓存一致性。消息因超时被重复投递时，直接 `INCR` 会重复累加，计数更新必须与消息唯一标识、幂等处理结合。设计上区分「消息真实状态」与「未读计数」这类派生状态：数据库持久化消息与已读游标，Redis 承担高频查询与计数加速；多端标记已读时按会话维护单调递增的已读位置，避免旧请求覆盖新状态；缓存异常或服务重启后要能基于消息记录重建未读数，不能把 Redis 当作唯一事实来源。

**C++ 与 C 的区别**：C 是面向过程的语言，核心是函数、结构体与手动内存管理；C++ 在兼容 C 的基础上提供类与对象、继承与多态、模板、异常、RAII 与标准库容器，支持泛型编程与零成本抽象。实际开发倾向 C++ 的原因是：RAII 让资源释放与对象生命周期绑定，减少泄漏；模板与容器在编译期完成类型检查与内联，性能接近手写代码；命名空间、引用、`const` 与更强的类型系统降低大型工程的维护成本。C 仍在驱动、嵌入式、ABI 边界与需要精确控制内存布局的场景中不可替代。
