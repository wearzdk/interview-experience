### 《面试题目》

1. 介绍一个 Agent 项目，用了什么框架，为什么选它？
2. Agent 有哪些核心组成？一次任务从输入到结束，完整流程怎么走？
3. Planning 是框架做的，还是模型做的？
4. 短期记忆和长期记忆有什么区别？Function Call 的请求和结果放在哪？
5. MCP 和自己写工具怎么取舍，什么场景用哪个？
6. RAG 召回阶段怎么调参，怎么判断调完有没有用？
7. 手撕：合并两个有序数组。

### 《参考解析》

Agent 的核心组成可以按「一个循环 + 四个部件」讲：模型（决策）、上下文（system、历史、工具定义）、工具（可执行的动作）、状态与记忆（跨轮、跨会话的事实），以及外面那层运行时（循环控制、超时预算、错误处理、可观测）。一次任务的流程：收到输入 → 组装上下文 → 模型输出计划或工具调用 → 运行时执行工具并把结果回填 → 模型判断是否完成 → 未完成继续下一轮，完成则生成结果。能顺着一次真实任务把这圈走一遍，比背定义强得多。

Planning 那题要分开讲：计划的内容（做什么、分几步）由模型生成，计划的执行（按顺序跑、记录进度、失败重试或跳步、判断终止）由程序负责。这也是「别让模型管状态」的原因——把执行状态放在代码里，模型只读不写，才能做到可恢复、可观测、可中断。框架（如 LangGraph）提供的就是这套状态机式的执行骨架。

记忆题的关键是「谁在什么时候读它」：短期记忆是本次会话的上下文，工具调用请求与结果都以消息形式追加在历史里（角色为 assistant 的 tool_call 与 tool 角色返回），模型下一轮就能看到；长期记忆是跨会话持久化的用户偏好、事实、历史结论，通常落库或向量库，在需要时检索注入，而不是每轮全量塞进 prompt。

MCP 与自写工具的取舍：MCP 适合「已有服务/数据源要被多个 Agent 复用」——协议统一、有现成 server、能跨团队接入；自写工具适合业务强相关、需要精确控制输入校验与副作用的动作，一行函数加 schema 最省事。判断依据是复用范围、维护归属和是否需要跨进程/跨语言，而不是「MCP 更高级」。

RAG 召回调参要成套：切分粒度与重叠、召回数量 top-k、是否加 BM25/向量混合、是否加重排、是否做查询改写。判断有没有用必须靠评测集：构造问题与正确文档的标注集，看召回率/命中率（Recall@k、MRR）而不是看最终答案「感觉变好了」——因为最终答案的变化可能来自生成侧，混淆了就白调。

手撕合并有序数组用双指针从后往前写最稳（`nums1` 预留了尾部空间时）：`i` 指向 `nums1` 有效尾部、`j` 指向 `nums2` 尾部、`k` 指向合并后的末尾，比较后放大值，避免覆盖还没处理的数据。普通合并则新建数组从头写。这题常考的就是「从后往前」这个技巧和边界处理。

作者自己的复盘抓到了重点：Planning 要分开讲模型与程序的分工，合并数组要练从后往前写。这两点确实是这场的采分点。
