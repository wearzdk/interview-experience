### 《参考解析》

**Agent 与 Workflow 的边界**

普通聊天机器人是无状态（或只带短窗口）的单轮补全，Agent 多出三样东西：面向目标的自主多步决策、调用工具产生副作用的能力、跨轮次的状态。组件上至少要有模型、提示词与上下文装配、工具注册与调用、执行循环、状态存储，以及一层约束与可观测（步数、预算、权限、Trace）。ReAct 是「思考—行动—观察」的循环，适合路径不可预测、需要边探边试的任务；Plan and Execute 先出一份计划再逐步执行，好处是计划可检查、依赖能提前暴露、部分步骤可并行，适合步骤多但结构清晰的任务；Reflexion 在执行失败后自我批判再修正，适合反馈明确、结果可验证的任务（编译、跑测试、查询有确定结果）。复杂任务通常是组合：外层规划、内层 ReAct 执行、关键节点插反思。选 Workflow 还是 Agent 的判据是路径可预测性和错误代价——路径固定、要可复现可审计的场景用 Workflow 更稳，路径开放且错误可回滚时才上 Agent；不少号称 Agent 的项目其实是 Workflow 加几个判断节点，能主动指出这一点是加分项。

**上下文工程与 Harness**

提示词工程管单次输入怎么写，上下文工程管窗口里放什么、放多少、按什么顺序放，Harness 则是模型之外那层执行框架：编排模型与工具调用、装配上下文、管理重试与终止、持久化状态与埋点。不能把所有历史都交给模型的原因有三条：窗口有限、成本随 token 线性上涨、噪声会稀释注意力并诱发无关联想。手段是滑动窗口加摘要压缩、按当前任务检索相关记忆、对工具结果做结构化裁剪（只留关键字段）。Harness 需要管理的内容包括工具注册与权限、步数与预算上限、失败重试与终止条件、状态存储，以及 Workspace 与抽象文件系统——后者让所有工具通过统一读写接口访问文件，屏蔽本地磁盘、沙箱与远程环境的差异，工具代码因此不必关心运行环境。一次请求的完整链路一般是：意图识别 → 路由到对应处理器 → 装配上下文 → 循环「模型决策、工具调用、结果回填」→ 校验输出 → 写回状态与记忆。

**RAG 全链路：切分、混合检索与融合**

入库侧是解析、切分、向量化、写库；检索侧是召回、融合、重排、过滤；生成侧还要处理引用与兜底。切分是质量的第一道闸：块太小丢上下文，太大稀释相关性；递归字符切分按分隔符优先级（段落、换行、句号、空格）逐级降级，块大小与重叠要按文档类型调。Markdown 按标题层级切、代码按函数和类切、PDF 还要先处理双栏和表格。相邻块扩展与父子文档检索解决同一个问题——命中块的信息不全：前者召回后补前后文，后者用小块做索引、返回大块作为上下文，区别在索引粒度和返回粒度是否解耦。混合检索的必要性在于向量擅长语义相似、关键词擅长精确术语；只用向量，遇到型号、错误码、人名这类查询就会失手。PostgreSQL 侧要讲清 tsvector 是文档的词位表示、tsquery 是查询条件、GIN 是倒排索引，中文必须先解决分词。两路分数不能直接相加，是因为量纲和分布不同，RRF 用排名倒数融合、只看名次不看绝对分数，因此更稳。Rerank 放在召回与融合之后，因为它贵且只能处理少量候选，先用便宜的召回把候选压到几十条再精排收益最大。答不准时按链路隔离排查：正确片段有没有被召回、召回片段有没有进最终上下文、进了上下文模型有没有用好——分别对应切分与索引、组装与截断、提示词与指令冲突三类问题。检索不到可靠内容时要能兜底，明确说没有依据并给出可选项，而不是让模型自由发挥。

**记忆分层与冲突处理**

分层是因为用途不同：短期会话记忆服务当前任务的连贯，中期记忆承载当前项目状态，长期偏好跨会话稳定，跨对话语义记忆则是可复用的知识。写入必须过判定：换个时间是否仍然成立、是否跨会话有用、用户是否明确要求记住。像「你知道我偏好什么吗」这类元问题不能当偏好写入，它没有提供新事实——做法是把写入与读取分开，写入只从用户的陈述里抽取，并对问句形态做过滤。冲突以时间和显式确认为准：新近且用户明确表达过的覆盖旧的，旧记忆标成 Outdated 而不是物理删除，需要时还能追溯。用 Active、Outdated、Conflicted、Deleted 这类状态机比布尔值好，因为它能表达「有冲突待确认」。跨对话语义记忆要做去重与相似归并，同一件事只留一条并合并来源，召回时降权，避免它压过当前会话的明确指令。读链路和写链路分开设计的原因也在这里：读要快、按需、可降权，写要准、可异步、可二次确认，混在一起会互相拖累。

**工具调用、Skill/MCP 与安全边界**

Function Calling 的链路是：把工具的 schema 作为元信息给模型，模型输出结构化的调用意图（并不真正执行），后端校验参数、鉴权、执行，再把结果回填给模型继续推理——模型只负责决定调什么，执行与权限必须留在后端。Skill 是把某类任务的方法、步骤与约束组织成可加载的文件，按需渐进加载：名称与描述常驻用于路由，正文在需要时才读，脚本按需执行，既不占窗口又能沉淀程序性知识。MCP 规定客户端与服务端之间工具、资源、提示模板如何暴露与调用：Tools 是可执行动作、Resources 是可读数据、Prompts 是预置模板；A2A 面向 Agent 之间的对等协作，解决的是任务委派与结果交接，不是模型与工具的连接。提示词注入分直接注入（用户输入里藏指令）和间接注入（模型读到的网页、文档里藏指令），防范要三层一起上：输入侧做来源标记与净化，提示层明确外部内容只是数据不是指令，权限层给工具最小权限并对敏感写操作要求人工确认。最关键的仍是权限层，前两层都可能被绕过。工具权限为什么不能交给模型判断——模型看不到真实身份与授权边界，它的输出只是概率判断，而权限是确定性规则，必须由后端按调用者身份裁决。防死循环靠硬约束：最大步数、重复动作检测（同一工具同一参数连续出现就终止）、无进展检测（状态没变化就停）、预算上限；触发后转人工或明确失败，而不是继续烧 token。

**模型分工与成本控制**

省成本按收益排序：先砍无效调用（工具结果裁剪、避免重复检索、缓存高频问答与嵌入结果），再谈模型降级，最后才考虑微调这类重投入。大小模型的分工原则是「难度高、错误代价高的环节用强模型，格式转换、分类、抽取、改写这类有明确判据的环节用小模型」，路由本身可以用规则或小模型完成。预训练、微调、提示词工程不是替代关系：预训练给通用能力，微调注入领域风格和格式约束，提示词工程解决当下任务的指令与示例；大多数业务问题的性价比排序是提示词与检索优化在前、微调在后。
