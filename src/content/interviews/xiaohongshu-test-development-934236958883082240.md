### 《参考解析》

1. **TDD 要讲成流程而不是口号**：先写一个会失败的测试（红），再写刚好让它通过的最小实现（绿），最后重构去掉重复（重构），循环推进。举例子时挑一个有明确输入输出的函数最省事，比如价格计算或字符串校验：先写「满减后金额等于预期」的断言，跑起来失败，补实现让它过，再把硬编码的分支重构成配置。面试官追问时通常想知道你怎么处理「测试写不出来」的情况——那就说明需求本身没定义清楚，先补接口契约。

2. **CI/CD 要答环节和质量门**：pipeline 的骨架是拉代码、依赖安装、静态检查（lint / 类型检查）、单元测试、构建、集成或端到端测试、制品归档、部署到测试环境、灰度或分批发布、回归与回滚。保证质量靠三道闸：本地提交前钩子挡住低级问题，CI 上失败即阻断合并，发布阶段用灰度加监控指标（错误率、核心链路成功率）决定是否继续。只说「自动化跑测试」会被追问测试用例的选取标准和失败如何归因。

3. **测试用例设计要用方法论兜底**：等价类划分、边界值、判定表与因果图、场景法、错误推测，再叠加状态迁移（订单、支付这类多状态对象）。答的时候给一个具体对象走一遍，比如登录功能：正常、密码错误、账号锁定、验证码过期、并发登录，每个用例写清前置条件、步骤和预期结果，并说明优先级怎么排。

4. **测试开发与传统测试的区别要落在「造工具」**：传统测试偏执行与业务验证，测试开发要把重复验证沉淀成框架、平台和工具，所以额外技能是编码能力、测试框架与持续集成、接口与性能测试、以及对被测系统架构的理解。核心能力可以答「定位问题的能力」打头——能看日志、能抓包、能从监控和链路上缩小范围，这比会写脚本更稀缺。

5. **前端工程化的题在测开岗上是在探广度**：懒加载的好处是首屏只加载必要资源、把 JS 和 CSS 拆成多个 chunk 按需拉取，代价是请求变多、要处理加载态；keep-alive 缓存组件实例、保留状态与滚动位置，和 v-if（销毁重建）、v-show（只切 display、状态仍在但组件不销毁）是三种不同取舍；自定义图片懒加载一般用 IntersectionObserver 或滚动监听加滚动节流，注意兜底和兼容性。

6. **事件循环那题是经典陷阱，要一次答全三问**：循环里用 var 声明下标、在 setTimeout 里打印，输出的是循环结束后的同一个最终值——因为 var 是函数作用域，四个回调共享一个变量，且回调是宏任务要等同步代码跑完。要输出 0 1 2 3，把 var 换成 let（每轮一个块级作用域），或者用立即执行函数 / `setTimeout` 的第三个参数把值传进去。要每隔约一秒输出一个，就让延迟随轮次递增（`i * 1000`），或者改用 setInterval 并注意清理定时器。

7. **用户研究类问题要区分「数据说什么」和「人为什么」**：混合研究方案是先定量定位（分层看指标变化范围：笔记类型、封面质量、标签、时长、人群），再定性解释（深度访谈、可用性测试、评论语义分析）。样本代表性靠分层抽样与配额控制，别只抓活跃用户。验证「审美疲劳」这类假设，要看多个独立证据是否指向同一结论——热门笔记风格的变化轨迹、停留时长与完播率、同一批创作者的互动变化，只靠一条数据不能定论；反驳「算法调整」也一样，用同期不同垂类、不同人群、不同入口的对照来说明问题范围。
