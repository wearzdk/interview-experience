### 《参考解析》

**三态熔断与降级链：阈值要按「窗口内的失败率」定，恢复要留半开探测。** 三态指关闭（正常放行）、打开（直接走降级）、半开（放少量探测流量）。阈值设计的标准做法是滑动窗口内失败率超过阈值且请求数达到最小样本量才熔断（例如 10 秒窗口、失败率 > 50%、最少 20 次请求），避免低流量下的偶发错误误杀；「两次就熔断」更适合下游明确快速失败的场景，代价是抖动敏感。恢复必须有半开态：打开后经过冷却时间（指数退避）放行少量请求，成功率达到阈值才回到关闭，否则继续打开——没有半开态的熔断会变成永久降级。降级链按优先级排（本地缓存 → 备用模型/备用接口 → 兜底文案），每一级都要有超时与独立开关，并且把「当前处在哪一级」暴露成指标。

**性能数字必须能说清测法。** 重构前后对比要交代：压测工具与场景（并发数、数据量、读写比例）、指标（P50/P99、QPS、错误率）、观测点（应用侧、DB 侧）。常见口径是「同一份数据集、同样的并发、跑 5 分钟取稳态」，改前改后各跑一轮。只说「快了很多」在二面会被追穿。

**编译型 vs 解释型的关键在「什么时候翻译」。** 编译型在运行前一次性翻译成机器码（C/C++/Go），启动前完成优化、运行期没有翻译开销；解释型在运行时逐行翻译成机器码或字节码解释执行（Python/JS），启动快、跨平台好、但单次执行慢。Java 是混合型：先编译成字节码，由 JVM 解释执行，热点代码再由 JIT 编译成本地码——答出这一层才算答全。JVM 里还有 AOT、GraalVM 这类补充方向。

**Java 控制线程的方法要按新旧两套答。** 传统 API：`Thread.start/sleep/join/interrupt`、`synchronized` + `wait/notify/notifyAll`、`Thread.yield`、`setDaemon`。现代并发工具：`ExecutorService`（提交任务、`shutdown`/`awaitTermination`）、`Future.get(timeout)` 与 `cancel`、`CompletableFuture`（编排与超时）、`Lock/Condition`（`lockInterruptibly`、`await/signal`）、`Semaphore`、`CountDownLatch`、`CyclicBarrier`、`Atomic*` 与 `LongAdder`。要强调 stop/suspend 已废弃，正确的中断方式是协作式的 `interrupt` + 检查中断标志。

**线程池大小：先分任务类型，再用压测校准。** CPU 密集型约 `N+1`（N 为核数），IO 密集型按 `N × (1 + 等待时间/计算时间)` 估算，混合型拆成两个池隔离。真正要考虑的因素是：任务的平均耗时与 P99、下游能承受的并发、内存（队列长度 × 任务对象大小）、以及超时与拒绝策略。队列必须有界，否则高负载时是延迟飙升而不是快速失败。

**双路检索并行的实现与容错。** 实现层用 `CompletableFuture.supplyAsync` 分别跑两路（或 `invokeAll`），用 `orTimeout` 设总超时，用 `exceptionally`/`handle` 做单路降级。容错策略要明确：一路超时就只用另一路的结果（并打点记录降级），两路都失败则走缓存或返回明确的失败而不是空结果；关键是超时预算要小于整体 SLA（比如整体 800ms，则每路超时 500ms，留出融合时间），并且失败的那一路要能区分「超时」与「返回空」——后者不该降级。

**Spring 注解原理：注解只是元数据，干活的是反射与代理。** 定义层是 `@interface` 加元注解（`@Retention(RUNTIME)` 才能被运行时读到）；处理层靠 `ClassPathScanningCandidateComponentProvider` 扫描、`BeanDefinition` 注册、`BeanPostProcessor` 与 `BeanFactoryPostProcessor` 在容器生命周期里读取注解并做增强（`@Autowired` 由 `AutowiredAnnotationBeanPostProcessor` 注入、`@Transactional` 由 AOP 生成代理）。要能说出「注解本身不生效，必须有处理器」这句话。

**Spring Boot 自动装配：`@SpringBootApplication` 是三合一。** 其中 `@EnableAutoConfiguration` 通过 `AutoConfigurationImportSelector` 读取 `META-INF/spring/org.springframework.boot.autoconfigure.AutoConfiguration.imports`（Spring Boot 2.7 之前是 `spring.factories`），拿到候选配置类后按 `@ConditionalOnClass`、`@ConditionalOnMissingBean`、`@ConditionalOnProperty` 等条件筛选，命中的才注册成 Bean。自己用到的场景可以是「封装一个 starter，把数据源与序列化配置打包，业务方引依赖即生效」，这比只背机制更有说服力。

**Redis 缓存的三类问题与对策要成对答。** 穿透（查不存在的数据打穿到 DB）：缓存空值 + 布隆过滤器 + 参数校验。击穿（热点 key 过期瞬间大量请求）：互斥重建（`SETNX` 只让一个线程回源）+ 逻辑过期（不设 TTL，异步刷新）+ 热点永不过期。雪崩（大量 key 同时过期或 Redis 挂）：TTL 加随机抖动、多级缓存、熔断降级、集群高可用。再补一致性问题：先更新 DB 再删缓存 + 延迟双删，接受最终一致并用订阅 binlog 做补偿。

**Redisson 看门狗解决的是「业务没跑完锁先过期」。** 加锁时不指定 `leaseTime` 就会启用看门狗：后台任务每 `lockWatchdogTimeout/3`（默认 30s/3 = 10s）给锁续期一次，直到显式 `unlock` 或客户端宕机（宕机后不再续期，锁自然过期）。注意两点：指定了 `leaseTime` 就不启用看门狗；续期依赖客户端存活，所以对「进程假死」不设防——严谨场景要配 fencing token 或业务侧幂等。

**MySQL 索引类型与不适用场景。** 按结构分 B+Tree（默认，范围与等值都好）、哈希（等值 O(1)、不支持范围）、全文（倒排，`MATCH AGAINST`）、空间（R-Tree）；按语义分主键（聚簇）、唯一、普通、联合、覆盖（索引本身含所需列，免回表）、前缀。不适用/失效的典型：区分度极低的列（性别）、频繁更新的列（维护成本）、选择性差的 `like '%x'` 前导通配、在索引列上做函数或隐式类型转换、`or` 连接非索引列、复合索引不满足最左前缀、数据量极小的表（全表扫更快）、以及写多读少的表（索引拖慢写入）。

**N+1 的发现与优化。** 发现靠慢查询日志与 APM（一次请求里同一个 SQL 执行了几十上百次），或在 ORM 层开 SQL 日志统计。优化：改成一次批量查询（`IN` 查询或 `JOIN`），在 MyBatis 里用 `collection` 的嵌套查询改成嵌套结果映射，或者业务层先收集 id 再批量取；随后用缓存兜住重复访问。要注意 `IN` 的参数不宜过多（分批），以及 JOIN 后结果集膨胀导致的内存问题。

**「接口变慢但没日志」的排查顺序。** 先判断范围：是所有接口还是单个接口、是否与流量相关、是否集中在某个实例。然后从外到内：网关/负载均衡的耗时与错误率 → 应用侧 APM 的 span 拆分（找最慢的一段）→ 线程栈采样（`jstack` 连续采几次看卡在哪个方法）→ 依赖侧（DB 慢查询、Redis 延迟、下游 RT、连接池等待）→ JVM（GC 日志与 safepoint）。没有日志就先加最小侵入的埋点或用 `arthas` 的 `trace` 动态定位，而不是先改代码。

**AI 辅助编程对长期维护的挑战，答「同质化、责任、可读性」三条。** 同质化：大量代码由同一批模型生成，风格与结构趋同但不一定符合本仓约定，长期看是隐性技术债。责任：提交者未必理解生成的逻辑，出事故时排查能力断档。可读性：AI 倾向生成「能跑但冗长」的实现，重复代码与过度抽象都会增加维护成本。对策是机器可判的门（类型、lint、单测、构建）+ 明确的最小改动约束 + review 只看 diff + 关键路径要求人能逐行讲清。

**实时路况的设计题要区分「数据从哪来」和「怎么用」。** 数据来源：① 浮动车/司机端 GPS 轨迹（最常见），按路段聚合速度；② 交管与地图合作方的路况事件（事故、管制）；③ 用户上报与历史统计。处理链路：轨迹清洗与地图匹配（把 GPS 点吸附到路段）→ 按时间窗聚合每段的速度/流量 → 与历史同期对比判定拥堵等级 → 分发到查询侧（按 tile 或路段 id 缓存）。「历史数据怎么体现实时」的关键是：历史数据用作**基线**（同一路段同一时段的常态速度），实时数据与基线的偏离才是「拥堵」；同时用历史数据补足采样稀疏的路段（推断），并用它做 ETA 的回归特征。「实时」的代价是延迟与覆盖率的取舍：采样密度不够的路段只能靠推断，推断结果要标注置信度。红绿灯倒计时则是另一套：要么接交管信号机的实时数据，要么用车端轨迹统计「某路口某相位红灯/绿灯的时长分布」，再对齐当前相位与相位差做倒计时预测——本质是周期估计问题，精度受相位切换策略变化影响。

**规划与偏好题（老项目 vs 新项目、三五年规划、技术热点）没有标准答案，但要「具体、前后一致」。** 老项目/新项目的答法可以给条件式：新项目适合建立架构判断，老项目适合练在约束里改造的能力，两者都需要；三五年规划分技术深度与工程影响两条线，别说「当架构师」这种头衔式目标；技术热点要选你真读过文档的（比如 Agent 的工具调用、RAG 的评测、推理成本优化），并准备一个「它的边界在哪」的判断。
