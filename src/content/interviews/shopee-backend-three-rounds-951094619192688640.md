### 《参考解析》

**数组、链表、队列与栈**：数组内存连续、支持 O(1) 随机访问、缓存友好，但中间插入删除要搬移（O(n)），扩容要整体复制；链表节点分散、插入删除只改指针（O(1)，前提是已持有前驱），代价是额外指针开销、缓存不友好、随机访问 O(n)。队列是 FIFO，栈是 LIFO；工程上的取舍是「用数组实现队列要处理假溢出（环形缓冲区），用链表实现栈会有频繁分配」。能补一句「CPU 缓存行让数组在遍历场景下快一个数量级」，比只背复杂度更有说服力。

**用数组实现队列**：维护 `head`、`tail` 与 `size`，入队写 `data[tail]` 后 `tail = (tail + 1) % capacity`，出队取 `data[head]` 后 `head` 前移，`size == capacity` 为满、`size == 0` 为空。用 `size` 而不是靠 `head == tail` 判空，可以区分「空」与「满」；容量不足时按 2 倍扩容并把元素按序搬到新数组。这道题之后常被追问「无锁队列怎么做」——单生产者单消费者用环形缓冲加读写指针与内存屏障即可，多生产者要用 CAS 或分段。

**HashMap 的实现、冲突与扩容**：JDK 8 是数组 + 链表 + 红黑树，`hash(key)` 做扰动（高 16 位异或低 16 位）后与 `(n-1)` 做与运算定位桶。冲突的根因是桶数量有限而 key 空间无限，不同 hash 落到同一桶就挂链；链表长度到 8 且容量 ≥ 64 时树化，退化到 6 时还原。负载因子 0.75 是时间与空间的折中：太高冲突多、查询退化，太低浪费内存且扩容频繁。扩容是容量翻倍，JDK 8 利用「扩容后索引要么不变、要么多一个旧容量」的性质把节点拆成高低两条链，不需要重新计算 hash。并发问题要讲清：`HashMap` 非线程安全，JDK 7 头插法在并发扩容时会成环导致 CPU 100%，JDK 8 改尾插仍会丢数据；并发场景用 `ConcurrentHashMap`（CAS + synchronized 锁桶，扩容时多线程协助迁移）。

**「哪些任务适合交给 AI」要有判据**：看四件事——可验证性（输出能否被自动检查，代码能跑测试、文案不能）、容错度（错了的代价与可逆性）、上下文可得性（所需信息是否在模型能看到的范围里）、以及是否涉及强合规或不可逆操作。适合的是草稿生成、分类打标、摘要、检索问答、代码补全与重构建议、日志初筛；不适合的是资金操作、权限变更、对外承诺、需要实时精确计算的场景，这些可以让 AI 出建议、人来执行。判断标准写成清单，比凭感觉说「看情况」专业得多。

**AI 产出的验收与 Review 瓶颈**：验收靠三层——机器可验证的信号（编译、单测、类型检查、lint、静态扫描、评测集打分）、结构化的人工抽查（按风险分层抽样，高风险全查、低风险抽 10%）、以及线上指标回归（错误率、延迟、用户反馈）。Review 跟不上产出时，正确做法不是降低标准，而是把「可自动判定的部分」自动化，把人的注意力集中到设计取舍与边界条件上；再配合小批量提交、可回滚发布、灰度与特性开关，让错误的影响面可控。这条思路同样适用于 AI 写的代码与 AI 生成的内容。

**让 AI 定位线上故障**：前提是把可观测性接进去——指标、日志、链路追踪、变更记录都要能被工具化查询，且给 AI 的权限是只读的、有审计的。流程是「假设—取证—验证」：先根据现象列出可能的原因，再调工具拉取对应时间窗的指标与日志，找到异常点后验证（对比基线、检查同期变更、看是否可复现），最后给出证据链而不是结论。判断 AI 说得对不对，看它引用的证据是否指向同一时间与同一维度、结论能否被独立复现、以及是否与已知变更对得上。避免复发靠复盘产出可执行的检查项（告警规则、自动化巡检、混沌演练、发布卡点），而不是靠记住这一次的原因。

**MCP 里工具 Schema 怎么到模型手上**：MCP 是客户端与服务端之间的协议（JSON-RPC 2.0，传输可以是 stdio 或 HTTP/SSE），服务端通过 `tools/list` 暴露工具名、描述与 JSON Schema；主机侧的客户端在建立会话时拉取这份清单，把它转换成模型能理解的工具定义（例如 OpenAI 的 `tools` 字段或 Anthropic 的 tool use 结构）注入到请求里，模型在推理中决定调用哪个工具并给出参数，客户端执行 `tools/call` 后把结果回填进对话。触发时机是「模型自己判断需要调用」，不是服务端推送；服务端只能在清单变化时发 `notifications/tools/list_changed`，由客户端决定是否重新拉取。

**MCP Server 能不能主动发消息**：协议本身是双向的。在同一条已建立的会话里，服务端可以发通知（资源更新、清单变更、进度）与请求（采样 sampling、向用户提问 elicitation、读取 roots），但前提是客户端实现了对应能力并在初始化时声明；服务端无法主动建立连接，也不能跨会话推送。长任务用进度通知把状态回传给客户端；如果业务真的需要「服务端主动找用户」，只能在 MCP 之外再挂一条通道（webhook、消息队列、SSE 长连接），由客户端或业务系统接收后再触发下一次会话。这一题区分的是「读过协议」和「真的写过 Server」。

**Pipeline 与命令存放位置**：Pipeline 是把多条命令一次性写入、一次性读取，省掉每条命令的往返时延（RTT），服务端仍然逐条顺序执行；它不保证原子性——一批命令中间可能插入其他客户端的命令，中途某条失败时前面的已经生效且不会回滚，网络中断时客户端也无法确定哪些执行了。要原子性得用 `MULTI/EXEC`（事务，但不支持回滚，只是打包执行）或 Lua 脚本（服务端一次执行完，中间不插入其他命令）。「命令保存在哪里」问的是 Redis 的内部结构：客户端发来的字节先进入该连接的输入缓冲区（`querybuf`），解析成 `argv` 后交给命令表执行；回复写到输出缓冲区（client output buffer），持久化时写 AOF 缓冲区（`aof_buf`），主从复制时写复制积压缓冲区（`repl_backlog`）。回答时把这几个缓冲区区分开，就能看出是不是只背了「单线程」三个字。

**评测集怎么建**：从真实流量采样而不是自己编题——按场景与难度分层（高频、长尾、边界、对抗），每条样本带上输入、期望输出或判定标准、以及来源与版本；规模上先求「有」再求「全」，几十到几百条就能跑起来，关键是可持续更新（线上 bad case 回流、定期复审标注）。指标要区分检索与生成、正确性与可用性，并给出置信区间；离线评测用固定集做回归，线上用 A/B 与人工抽检校准，避免「离线涨了线上没动」。

**Redis 延迟队列与热 Key**：延迟队列的经典实现是 ZSET，成员是任务 ID、score 是到期时间戳，消费者用 `ZRANGEBYSCORE key 0 now LIMIT n` 取出到期任务，再用 Lua 脚本「取出并删除」保证不被重复消费；失败任务重新入队或进重试队列（带退避的 score），消费端要做幂等。更完整的是「ZSET 做定时 + LIST 做就绪」的两级结构（Redisson 的 RDelayedQueue 就是这个思路），避免消费者反复轮询空 ZSET。热 Key 的处理分三层：写侧分片（key 加随机后缀拆成 N 个，读时聚合）、读侧加本地缓存并批量合并请求、以及限流与降级；再配合热点探测（采样统计、代理层统计）提前发现。要说明代价：分片会让聚合变复杂、本地缓存有一致性延迟，选型取决于能否接受最终一致。
