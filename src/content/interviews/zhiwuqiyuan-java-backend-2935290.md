### 《参考解析》

**第 2 题别答成「我用了 LangChain」**

RAG 的编排要按数据流讲，而不是按框架讲。一条能过面试的链路是：文档接入（PDF / Word / 网页的解析与清洗，表格与图片要不要单独处理）→ 分块（按标题层级还是固定窗口、chunk 多大、有没有重叠）→ 向量化（用哪个 embedding 模型、维度、要不要同时建关键词索引）→ 存储（向量库选型、元数据里存哪些字段）→ 召回（top-k、是否混合检索、要不要 rerank）→ 组装 prompt（上下文怎么截断、引用怎么标注）→ 生成（模型、温度、流式）→ 后处理与评估。每一段都能说清「为什么这么选、换一种会差在哪」，就已经比背组件名高一档。

**第 3 题：文档版本是 RAG 项目最容易烂掉的地方**

只做「覆盖写」的系统，用户问到已作废的条款时答不出来或者答错。可行的做法是给每个文档一个逻辑 id + 版本号，新版本入库时把旧版本的向量标记为失效（不是物理删除，保留可追溯），检索时只召回有效版本；如果业务需要「历史上曾经怎么规定」，再按时间范围放宽。另一个常被忽略的点是**增量更新**：整库重建在文档量大时跑不动，需要能定位到「哪个 chunk 变了」，只重算受影响的部分。

**第 4、5 题：预处理和改写是效果差异最大的两步**

预处理主要是四件事：纠错（错别字、语音转写的同音错）、指代消解（「它」「这个」指前文的什么）、意图判断（是不是在问知识库里的东西，不是就直接兜底）、以及把长问题拆成子查询。改写的提示词要给**约束而不是愿望**：明确输出只有改写后的问题、不许回答问题本身、保留原问题里的专有名词与数字、给出两三个不同角度的改写。识别类的提示词则相反，要它输出结构化的标签（意图 + 置信度 + 是否需要检索），方便下游用代码分支，而不是靠模型自由发挥。

**第 6 题：prompt 的「历史演变」考的是你有没有工程化**

理想的答案是：prompt 存在配置里而不是代码里，有版本号，每次改动配一批固定的回归用例，改完跑一遍对比通过率，坏了能回滚。演变过程一般是三个阶段——最初靠堆指令、后来发现指令互相打架就改成结构化分区（角色 / 任务 / 约束 / 输出格式 / 示例）、再后来把能写成代码校验的部分从 prompt 里拿出去，只留模型真正需要判断的东西。

**第 7 题：可观测性要答到「一次请求能串起来」**

一条请求应该能用一个 trace id 串起：入口参数、改写后的查询、召回命中的文档 id 与分数、最终 prompt 的 token 数、模型返回、耗时、失败原因。日志之外还要有指标：召回命中率、空召回率、平均上下文长度、首字延迟与总延迟的 P50/P95、token 消耗（输入 / 输出 / 缓存命中分开记）。这些指标决定了出问题时你是靠猜还是靠看。

**第 8、9 题：Agent 的测试不是写单测**

Agent 的输出不确定，测的是「行为边界」而不是「等于某个字符串」。可用的分层是：① 工具层单测——每个工具函数输入输出确定，正常写单测；② 轨迹测试——给定任务，检查它调了哪些工具、有没有走不该走的分支、有没有死循环；③ 结果评测——一批带标准答案的样例，用规则或 LLM 当裁判打分，跑通过率。第 9 题问框架，答「自己搭的回归集 + 规则断言 + LLM 裁判」比硬编一个框架名更真实；关键是能说清用例从哪来（线上真实请求采样 + 人工构造的边界case）、怎么防回归（每次改 prompt 或换模型都跑一遍）。

**第 10 题：上线数据要具体到口径**

token 消耗要说清是每请求还是每会话、输入输出分开、有没有命中缓存（缓存命中的单价通常只有未命中的十分之一，不分开算会高估成本）；延迟要给首字延迟和完整响应两个数，并说明是 P50 还是 P95——只报平均值在面试里基本等于没测。

**第 15、23 题：AI 写代码的比例怎么答**

这两题表面在问工具，实际在探「你对 AI 产出的掌控力」。答比例之前先说分工：样板代码、样式调整、单测、重构这类让 AI 写，涉及状态机、并发、权限、数据一致性这些核心逻辑自己写并逐行 review。被问到「CSS 调整效果怎么样」时，给一个具体的对比（一句话描述需求 vs 改了三版才对）比笼统说「还行」可信得多。第 23 题问代码多少是 AI 写的，本质上是在问「你能不能为这些代码负责」——答「AI 写的部分我也能讲清每一行为什么这么写」是唯一安全的答案。

**第 19、21 题：模型与框架的对比要有判断而不是站队**

ChatGPT 与 Claude 的差异，落到工程上无非几件事：长上下文里的指令遵循、工具调用的稳定性与并行调用、结构化输出的可靠性、以及代码场景下的改动幅度（是只改该改的，还是顺手重写一片）。这几条各自给一个自己踩过的例子，比背评测分数有用。第 21 题问 AI 相关前端框架，答 Vercel AI SDK 这类流式与工具调用的封装、以及 SSE / WebSocket 在前端的处理方式，就能接上前面第 7 题的可观测性话题。

**第 24-26 题：别把这几个问题当寒暄**

公司要求、base 地、工作强度三连问，是在给「匹配度」打分，也是在为定薪和后续流程做准备。答的时候保持和前面一致：如果你说看重技术深度，就别在同一条里说只想找不加班的；上一份工作强度如实说，但落点放在「我能接受什么样的节奏、为什么」，而不是抱怨。这几题答得干脆，前面技术部分的可信度也会更高。
