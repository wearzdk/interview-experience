### 《参考解析》

**限流：为什么没用 Redis，以及怎么用 Redis 做**

被问「为什么不用 Redis」时，关键是把成本和收益讲平衡，而不是一句「单机够用」。可以这样组织：当前流量在单机可承受范围内，限流放在进程内（令牌桶 + 本地计数）延迟是纳秒级，不引入网络往返和 Redis 故障时的可用性问题；代价是多实例部署时每台各自计数，总阈值会放大，所以只适合流量分配均匀的场景。要真做分布式限流，设计要点是：用 Redis 的 Lua 脚本保证「读-判断-写」原子执行，避免 GET 与 SET 之间的竞态；算法选滑动窗口（ZSET 存时间戳，或按秒分桶的两个计数器做加权）或令牌桶（存令牌数与上次填充时间，按差值补桶）；键带过期时间防止内存膨胀；同时考虑 Redis 不可用时的降级——本地限流兜底，绝不因为限流组件挂了就放全量流量进来。

**线上问题排查要能讲出「顺序」**

Crash 类问题的标准链路：先确认影响面与可复现条件（哪台机器、什么请求、什么版本），再看有没有 core dump 或崩溃日志拿到调用栈，结合符号表定位到函数与行；没有 core 就用日志与监控反推最后几个动作，必要时通过压测或回放复现。定位到可疑代码后再看是空指针、越界、并发竞争还是资源耗尽（fd、连接数、内存）。修复之后补三件事：单测或回归用例、监控指标与告警、以及同类问题的全局排查。面试官追问「完整流程」，其实是在看你会不会跳过「先确认影响面」直接改代码。

**TCP：一个词和一条数据流**

「一个词概括 TCP 最核心的特点」，答「可靠」最稳，但要给出支撑：序号与确认保证不丢不乱、超时重传与快速重传保证丢了能补、滑动窗口做流量控制、拥塞控制适配网络。UDP 则是无连接、不保证顺序与到达、开销小、支持广播组播，适合实时音视频、DNS、游戏这类「宁可丢也不要等」的场景。选型判断按三条：能不能容忍丢包与乱序、需不需要按序可靠交付、对延迟的敏感度。

手写协议栈的架构图一般分四层：链路/驱动层（收发包、网卡缓冲）、IP 层（分片重组、路由）、TCP 层（连接状态机、序号与确认、重传队列、滑动窗口、拥塞窗口）、Socket API 层（阻塞/非阻塞读写、accept/connect）。数据流讲发送侧：应用 write → 发送缓冲 → 按 MSS 分段并打序号 → 进入重传队列 → 受拥塞窗口和接收窗口共同约束发出 → 收到 ACK 后移动 `snd_una` 并释放；接收侧：收到段后按序号插入乱序队列 → 连续段交付应用 → 回 ACK 并更新 `rwnd`。快速重传的实现要点是收到三个重复 ACK 立即重发而不等超时，配合 SACK 能只补缺口。

**Web Server：epoll 那三个词要讲成一个因果链**

架构是主线程 `accept` 拿连接、交给 epoll 监听，工作线程池从任务队列取就绪事件处理，队列起削峰和线程复用作用。用 epoll 而不是 select/poll 的原因是它用内核事件表 + 就绪链表，复杂度与「活跃连接数」相关而不是「注册连接数」，且不用每次把 fd 集合从用户态拷进内核。

ET 与 LT 的区别是：LT 只要缓冲区还有数据就一直通知，ET 只在状态变化时通知一次，所以 ET 必须配非阻塞 IO 并循环读到 `EAGAIN`，否则剩余数据永远等不到下一次通知。EPOLLONESHOT 解决的是多线程下的竞争：一个连接被多个工作线程同时处理会出现数据错乱，注册 ONESHOT 后事件只触发一次，处理完再重新注册。能把「ET + 非阻塞 + 循环读」和「ONESHOT + 重新注册」讲成一对因果，而不是三个孤立名词，这题就答到位了。

**这场面试的复盘价值**

原帖作者的自我总结很准：架构图和数据流画得不好、讲 Web Server 时不够笃定。这类「讲自己的项目」的题，准备方式不是背结论而是练画图——拿一张白纸，三分钟内画出模块、箭头、数据流向，边画边讲，每个模块能接住「它为什么在这里、去掉会怎样」。面试官让你画图，考的正是你脑子里有没有这张图。
