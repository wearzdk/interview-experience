### 《参考解析》

**为什么用 RAG 而不是微调或长上下文**：RAG 解决的是「知识频繁变化且需要溯源」的问题。领域知识库（产品文档、内部规范、FAQ）更新快，微调一次成本高、周期长，而且模型参数里存的知识无法引用出处、容易过时；把所有文档塞进长上下文则受窗口限制、成本和延迟都随长度上升，检索精度也会下降。RAG 把「知识」与「推理」解耦：检索负责召回相关片段，模型负责基于片段作答，更新知识只需重建索引。它的难点不在链路而在检索质量——切分粒度、embedding 选型、混合检索（向量 + 关键词）、rerank、以及召回为空时如何降级。

**Workflow 与 Agent 的取舍**：能用固定流程解决的不要交给自主 Agent。Workflow 是可预测的编排（步骤固定、分支明确、每步可测），延迟与成本可控、失败可定位；Agent 适合步骤不确定、需要模型自行决定调用哪些工具的场景。实践中常见的是混合：外层用 Workflow 框住主要阶段，内层在需要判断的环节交给 Agent。用开源框架（LangGraph 一类）能省编排与状态管理的活，但要看清楚它的抽象是否与你的观测、重试、持久化需求匹配，很多团队最后会把关键链路收回到自己可控的实现上。

**记忆持久化**：分三层——会话内上下文（消息历史，随请求发送，受窗口限制）、会话级持久化（把对话与中间状态写入数据库或对象存储，按 session 恢复）、长期记忆（抽取事实、偏好、结论，写入结构化存储或向量库，按用户检索注入）。工程上要解决的是：写什么（原始消息还是摘要）、何时写（每轮、每 N 轮、会话结束）、怎么取（按用户 + 相关性检索、控制注入长度）、以及隐私与过期策略。把全部历史都塞回去是最差的做法，成本高且会稀释关键信息。

**上下文管理可以借鉴什么**：主流编码 Agent 的做法有三点值得学——一是前缀稳定，system prompt 与工具定义在一场会话内不变，只往后追加，从而命中上游的 Prompt Cache；二是压缩，接近窗口上限时做摘要或裁剪工具返回的大块内容（保留结论、丢掉原始日志）；三是有选择地重新读取，需要细节时再按需读文件或检索，而不是一开始全量加载。这套思路可以直接迁移到业务 Agent：稳定前缀 + 增量追加 + 按需检索。

**Agent loop 的错误处理**：按错误来源分层。工具层：超时、限流、返回格式不符、权限不足，分别对应重试（带退避与上限）、降级到备用工具、schema 校验后让模型修正参数、以及向用户说明；模型层：输出不是合法 JSON 或调用了不存在的工具，用结构化输出约束 + 解析失败重问；规划层：反复调用同一工具、陷入循环，用步数上限与重复检测打断；业务层：结果不符合预期，用校验器或二次模型检查。所有错误都要记录下来形成坏 case 集，改完之后跑回归。核心原则是「失败要显式」，不能让 Agent 编一个看起来成功的结果。

**Spec 驱动开发里什么重要**：重要的是约束与验收——目标与范围、输入输出契约、边界与异常、验收标准、不可更改的依赖与约定；不重要的是实现细节与文件级步骤，因为这些应该由执行者根据代码现状决定，写死了反而会随代码变化而过时。Spec 的价值在于把「要什么」和「怎么做」分开，让评审聚焦在需求与接口上。

**代码可持续演进**：可维护性靠几件具体的事：模块边界清晰、依赖方向单一；关键决策有文档（为什么这么选，替代方案是什么）；测试覆盖核心路径与边界；配置与代码分离；以及持续的小步重构。被追问时给一个你实际做过的例子，比列原则有效。

**职业倾向与信息渠道**：研究与工程的取舍要给出判断依据——你更喜欢把能力落到可用系统上，还是更享受方法创新；两者都做过的人可以说明自己在前者上的优势（工程落地、评测、成本控制）。前沿资讯说具体来源（官方模型文档与发布说明、论文、开源项目、技术博客），并给一个你最近关注的具体方向与自己的判断，避免罗列名词。
