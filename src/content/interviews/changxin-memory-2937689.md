### 《参考解析》

**接手项目的推进顺序**：先读文档与代码结构、把本地环境跑起来，跑通主流程和测试；再找原负责人、产品、测试各聊一次，确认业务目标、当前风险与历史坑；然后列一份「现状—风险—里程碑」清单，按「先止血、再优化」排优先级，选一个小的可验证改动先合入，建立信任；最后把关键决策和运行手册补进文档。回答时要体现你如何在不熟悉代码的情况下降低风险，比如先加日志与测试、再动核心逻辑。

**代码 review 的检查顺序**：先看正确性与边界（空值、越界、并发、幂等、事务边界），再看错误处理是否吞异常、是否有资源泄漏，然后看 SQL 与索引、接口兼容性、日志与可观测性，最后看可读性与命名。评审时按严重程度标注「必须改、建议改、可选」，小 PR 优先，配合自动化 lint、单测与静态检查，避免把 review 变成风格争论。作为作者，提交前自己先过一遍 diff，把背景与验证方式写进描述。

**重写与重载**：重载（overload）发生在同一个类里，方法名相同、参数列表不同，编译期静态分派，返回类型不同不构成重载；重写（override）发生在子类与父类或接口实现之间，方法签名相同，运行期按实际对象类型动态分派，访问权限不能收窄、不能抛出更宽的受检异常。常见的追问是「重载看编译期类型、重写看运行期类型」，可以用一段父类引用指向子类对象的例子说明。

**where 与 having**：where 在分组之前过滤行，不能直接使用聚合函数（窗口函数另说）；having 在 group by 之后过滤分组，可以使用聚合函数。能放在 where 的条件不要放到 having，前者更早减少数据量。SQL 执行顺序大致是 from、where、group by、having、select、order by、limit。

**MySQL upsert**：常用 `INSERT INTO t (a,b) VALUES (1,2) ON DUPLICATE KEY UPDATE b = VALUES(b)`，依赖主键或唯一索引判断冲突；MySQL 8.0.20 起 `VALUES()` 被标记为过时，可用别名写法 `INSERT INTO t (a,b) VALUES (1,2) AS new ON DUPLICATE KEY UPDATE b = new.b`。`REPLACE INTO` 也能实现类似效果，但它是删除再插入，会触发删除触发器、丢失未指定列的值、影响自增与级联，生产上慎用。

**团队 AI 转型的讲法**：按「场景—工具—流程—度量」讲。场景选重复度高、验证成本低的，比如单测生成、代码评审辅助、接口文档、日志排查、需求转用例；工具上区分补全、对话、Agent，接入内部代码库与知识库；流程上明确「AI 产出必须经过 review 与测试」，敏感代码不出内网；度量看采纳率、返工率、交付周期与缺陷率，而不是只看生成了多少行代码。

**对 AI coding 的看法**：它在样板代码、测试、重构、跨语言翻译上提效明显，但生成结果的对错需要人来判断，尤其是在不熟悉的代码库和边界条件下。合理的用法是把任务拆小、给足上下文与约束、要求它先给方案再写代码，并用编译、测试、类型检查做验证；不适合直接把未审查的代码合入核心链路。回答时结合自己真实的用法与踩过的坑，比表态「拥抱 AI」更有信息量。
