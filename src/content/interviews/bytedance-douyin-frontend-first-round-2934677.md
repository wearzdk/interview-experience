### 《面试题目》

1. 自我介绍，介绍竞赛、三段实习以及个人自研 AI Agent 项目。
2. 深挖腾讯 PC-QQ Electron 迁移 QT 的 CSS 下沉项目：讲清楚项目背景、旧方案存在什么问题、自己设计的新整体方案、底层渲染架构、IPC 通信流程。
3. 本地测试得到的性能收益是多少，性能专项优化做了哪些工作？
4. Vue 前端 + SpringBoot 后端的全栈项目，如果要部署上线，完整流程是什么？
5. Nginx 反向代理原理，一台服务器如何承载多个不同域名的服务？
6. 手写编码：不使用原生 setTimeout，基于 Date.now + requestAnimationFrame 实现简易 setTimeout 与 clearTimeout。
7. 反问环节：团队业务、AI Agent 落地场景、团队人员规模、校招生的发展方向。

### 《参考解析》

**Electron 迁 QT 的项目讲法**：这类项目面试官想听的是「你为什么动、怎么拆、代价是什么」，不是「我参与了迁移」。按四段讲：背景与问题——Electron 把 Chromium 和 Node 各带一份，安装包大、常驻内存高，多进程模型在低配 Windows 上启动和切页都吃亏，老方案的样式散落在各业务页面里，主题切换要改一堆 CSS；方案——把通用 UI 能力下沉成统一的样式层（设计 token → 一套受控的 CSS 子集 → 编译成 QT 侧可消费的样式表/属性），业务只描述「是什么组件、什么状态」，不再直接写裸样式；渲染架构——UI 线程、布局、绘制、合成各自负责什么，哪些控件走原生、哪些保留 Web 容器，跨进程边界在哪；IPC——主进程与渲染进程之间传什么（命令、事件、状态同步）、用什么通道（命名管道/共享内存/消息队列）、如何做序列化、超时、背压和错误回传。最后补一句取舍：哪些模块迁、哪些暂时保留，为什么这样切风险最低。

**性能收益怎么报**：不要只报一个「提升了 40%」，要报口径：测的是冷启动还是热启动、首屏可交互还是首帧、机器配置与系统版本、样本量和分位数（p50/p95）。常用指标是启动耗时、常驻内存、页面切换耗时、帧率与长任务数、安装包体积。方法上先做基线采集（同一台机器、同一批操作、多次取中位数），再做单变量优化，每项优化单独 A/B，避免把多个改动的收益混在一起；用 profiler 找真正的热点，而不是凭感觉换实现。性能专项可以按「启动阶段删依赖与并行初始化、渲染阶段减少布局与重绘、内存阶段查泄漏与大对象缓存、包体阶段做裁剪与懒加载」四类讲，每类给一个具体动作和对应指标。

**Vue + SpringBoot 上线流程**：前端 `vite build` 产出静态资源，按环境注入 `VITE_` 变量，产物传 CDN 或放到 Nginx 的静态目录，`index.html` 配短缓存、带 hash 的资源配长缓存；后端打成可执行 jar，用 systemd 或容器运行，数据库迁移用 Flyway/Liquibase 在发布前执行，配置走环境变量或配置中心，密钥不进仓库。入口用 Nginx 做 TLS 终止和反向代理：`/api` 转发到后端 upstream，其余走静态目录，开 gzip/brotli、HTTP/2、WebSocket upgrade，配好超时与请求体上限。发布流程是 CI 构建 → 制品归档 → 预发验证 → 灰度/滚动发布 → 健康检查 → 观察日志与指标 → 出问题回滚上一版；监控至少要有接口错误率、延迟分位、机器资源与前端 JS 错误上报。

**Nginx 多域名与反向代理**：一台机器多个域名靠 `server` 块加 `server_name` 区分，HTTP 层看 Host 头，HTTPS 层靠 TLS 的 SNI 在握手阶段选证书，所以每个域名要有对应的 `listen 443 ssl` 与证书配置。反向代理的核心是 `proxy_pass`：把请求转发到 `upstream` 里的一组后端，`proxy_set_header Host $host`、`X-Real-IP`、`X-Forwarded-For`、`X-Forwarded-Proto` 把原始信息带给后端；上游可以做轮询、权重、最少连接、健康检查，失败重试与超时要显式配。静态资源单独 `location` 配缓存和 `try_files`，SPA 要把未命中的路径回落到 `index.html`；WebSocket 需要 `Upgrade` 与 `Connection` 头透传。多域名共用入口时还要注意默认 server 兜底、证书自动续期、以及限流与访问日志按域名拆分。

**手写 setTimeout**：核心是「自己维护一个任务表，用 rAF 的每帧回调检查到期时间」。数据结构用 `Map<id, {callback, due, args}>`，`setTimeout(fn, delay)` 生成自增 id、记录 `due = Date.now() + delay`，返回 id；启动一个 rAF 循环，每帧取 `now`，遍历任务表把 `due <= now` 的任务取出来执行并从表中删除；`clearTimeout(id)` 直接从表里删。几个坑要主动说：rAF 的粒度约 16.7ms，小于一帧的延时不可能精确；页面切到后台时 rAF 会暂停，定时器会整体延后，可以在 `visibilitychange` 时用原生 `setTimeout` 兜底或补算到期任务；回调里抛错不能打断整个循环，要 try/catch 后继续；回调中新增/删除任务要避免遍历时修改 Map，先收集再执行；长时间运行的循环在任务表为空时可以停掉 rAF，下一次 setTimeout 再启动，省电。如果面试官追问「为什么要用 rAF」，答「让回调对齐渲染帧、避免定时器在两次绘制之间插入造成抖动，同时能在主线程繁忙时自然降频」。

**反问环节**：问团队当前最核心的业务目标、AI Agent 在业务里的真实落地场景与衡量指标、团队规模和校招生的培养路径。反问不是走过场，选一两个你真正关心的点，顺着面试里聊到的技术栈追问，比泛泛问「团队氛围怎么样」更能留下印象。
