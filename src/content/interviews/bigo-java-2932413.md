### 《参考解析》

**跨岗投递能过简历关，靠的是「工程底子可迁移」**。数据开发常见的技术栈（SQL、分布式、调度、存储）与 Java 后端有大量重叠，写简历时要把可迁移的部分前置：JVM 调优、并发、服务化、接口性能这些词比「数仓分层」更容易让后端面试官对上号。作者进面本身就是证据——不用因为是数开背景就不敢投后端。

**一二面全是八股时，答题要带「一个具体场景」**。八股的标准答案是及格线，真正拉开差距的是「我在项目里怎么遇到、怎么验证」。以常见的高频点为例：`HashMap` 讲扩容与哈希冲突时要能说出 1.8 的红黑树退化条件；`synchronized` 讲偏向锁/轻量级锁时要能对上实际的锁升级场景；线程池讲参数时要说清队列满了之后的拒绝策略在你项目里怎么选。每个点配一句「线上出过什么问题」，八股就变成了经验。

**主管面直接手撕多线程多进程，说明这个岗位对并发是真需求**。准备时至少要能手写三类代码：生产者-消费者（`BlockingQueue` 或 `wait/notify` 两版）、多线程按序打印（`Condition` 或 `Semaphore`）、以及一个带超时与重试的并发任务聚合（`CompletableFuture` + 线程池）。多进程部分通常会落到进程间通信（管道、共享内存、Socket）与守护/重启策略上，答题时把「为什么选多进程而不是多线程」讲清楚——隔离性、崩溃影响面、以及 Python/GIL 这类语言限制是常见的决定因素。

**关于「优化也要写出代码」**，可以在写完后主动补三项：消除伪共享（填充或按 cacheline 对齐）、减少锁竞争（分段锁、无锁 CAS、`LongAdder`）、以及避免上下文切换（线程数与 CPU 核数匹配、用异步替代阻塞）。面试官要的不是面面俱到，而是你能不能把「优化」落到具体代码行。

**最后那条行业判断值得单独记**：数开 HC 收缩、AI 工具吃掉了大量取数与报表工作，是今年不少人的共同感受。对个人来说，往「工程 + 平台」方向挪（服务化、存储引擎、任务调度、AI 数据链路的工程化）比只深耕 SQL 更抗周期。
