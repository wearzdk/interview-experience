### 《参考解析》

**UE 为什么要设计蓝图**：蓝图本质是一套给非程序角色用的可视化脚本层，把「事件的响应链」画成节点图。它的价值不在替代 C++，而在把「策划改一个数值或流程」的成本从「等程序排期、编译、出包」降到「编辑期内改完立刻看效果」。同一个人在 UE 里的典型分工是：性能敏感、需要调试和版本控制的逻辑写 C++，暴露成 `UFUNCTION` / `UPROPERTY` 给蓝图调用；玩法拼接、UI 状态机、原型验证用蓝图，迭代速度快且不需要美术或策划会写代码。代价也明确：蓝图是二进制资产，diff 和 code review 困难；节点图一复杂就不可读；执行效率低于 C++（虚拟机解释执行），所以热路径要下沉。这套「C++ 做底座 + 蓝图做胶水」的分层，是引擎在「专业开发者」和「内容生产者」之间划的边界。

**UObject 与 TArray**：UObject 是 UE 里几乎所有需要被反射、被 GC 管理、被序列化的对象的基类。它靠 `UClass` 提供运行时类型信息（反射），靠 `UPROPERTY` 标记让 GC 知道该追踪哪些引用。GC 不是引用计数，是标记-清除：从根集合（GameInstance、World、玩家控制器等）出发，顺着 `UPROPERTY` 标记的指针遍历对象图，没被标记到的对象被回收——所以一个裸 `UObject*` 是不被 GC 保护的，得挂成 `UPROPERTY` 才会被追踪。`TArray` 是引擎自己的动态数组，语义像 `std::vector` 但配套了 UE 的内存分配器、序列化支持、以及 `TArray<TObjectPtr<T>>` 这种能参与 GC 遍历的元素类型；对象在 `TArray` 里扩容时是整体搬迁，所以别存指向元素的裸指针。

**UE 的智能指针与 UObject 管理**：UE 有一整套仿 STL 的智能指针——`TSharedPtr` / `TSharedRef` / `TWeakPtr` 管非 UObject 的普通对象，`TUniquePtr` 管独占所有权，语义对齐 `std::shared_ptr` 那一套但支持引擎自己的线程安全与分配策略。**UObject 不走 shared ptr**：它们的生命周期归 GC，用 `TSharedPtr` 包 UObject 是双重所有权，会导致引用计数和 GC 互相踩。需要弱引用外部对象用 `TWeakObjectPtr`（不阻止 GC，用之前判 `IsValid()` 防悬空）。想把 UObject 放进容器参与 GC，用 `TObjectPtr<T>` 或 `TStrongObjectPtr`。判断标准很简单：这个对象会被 GC 追踪吗？会就是 UObject 体系，不用智能指针。

**三次握手里对可靠传输有贡献的部分**：握手不只是「确认双方能收发」，它同时完成了三件让可靠传输成为可能的事：一是**交换初始序列号（ISN）**，双方各自的 ISN 成为后续所有数据段的编号起点，序列号是可靠传输的地基——没有编号就无从判断丢没丢、重不重；二是**确认双向可达**，第三次握手的 ACK 让客户端确认服务端收到了自己的 ISN，同时服务端也知道客户端收到了自己的 ISN；三是**协商 MSS 与窗口**，MSS 决定单个段的大小上限，窗口通告决定了发送方在收到确认前能发多少，这是流量控制与滑动窗口的起点。此外随机生成的 ISN 还顺带提供了对伪造连接的防护。

**游戏引擎为什么偏 UDP**：实时游戏的要害是「最新状态优先、旧数据过期即废」。TCP 的可靠性是有代价的：一条包丢了会阻塞后续所有数据（队头阻塞），重传本身又增加延迟——等一个已经不再有意义的旧包重传成功，玩家的位置早就变了，收到也没用。UDP 允许直接把过期状态丢掉、只发最新的，延迟最优。在 UDP 上做可靠要自己按需要挑：关键事件（技能释放、开箱结算）走带序列号 + 确认 + 重传的可靠通道；位置/朝向这类高频状态走不可靠通道，丢了就让下一次覆盖；加序号检测乱序和重复，重复丢弃、乱序按需重排或直接忽略过期包。工程上通常分多个通道（可靠的、不可靠有序的、不可靠无序的），按数据语义分流。

**HTTP3 换 UDP 的动因**：HTTP2 的多路复用把多个流塞进一条 TCP 连接，但 TCP 只看字节流、不知道流边界。一个包丢了，后面所有流的数据都得等重传——这就是 TCP 层的队头阻塞，多路复用反而把「一条流卡住」放大成「所有流卡住」。再加上中间设备对 TCP 的干预（老旧代理、丢包误判）、TCP 握手加 TLS 握手要多个 RTT，慢启动对短连接也不友好。QUIC 建在 UDP 上，把加密和传输握在一起（1-RTT，重连可 0-RTT），丢包只影响那一条流（流级独立），连接靠 Connection ID 而不是四元组标识，所以换网（WiFi 切 4G）连接不断。代价是 UDP 在很多网络里被限速或封禁，回退和探测是工程上要处理的问题。

**怎么平衡新卡牌的机制与数值**：从测开的角度，先明确这张卡定义了什么博弈——它是节奏卡（压缩对手反应时间）、资源卡（换费比）还是答案卡（专克某一类构筑）。机制层面测的是「边界与交互」：与已有卡牌的相互作用有没有意外组合（某个 buff 叠到这张卡上会是什么效果）、极端条件下的表现（场上全是单位 / 场上没有单位）、结算顺序有没有歧义。数值层面不能只看单卡强度，要看它进入主流卡组后整体胜率和出场率——用模拟对局（AI 互打大批量）先筛出明显失衡的点，再靠小范围灰度看真实玩家的使用率与胜率偏离。平衡的目标不是每张卡都五五开，是让强势卡组有克制关系、让玩家有多种可行解。

**氪金玩家的等级压制怎么平衡**：这是手游商业化和竞技公平的结构性矛盾。可行的做法分三层：赛制上把等级影响圈在非竞技模式里，竞技/天梯用统一等级或按卡等分池匹配（同样等级的对手池），让付费买的是「更快的进度和解锁」而不是「对战优势」；机制上让等级差带来的优势有封顶（等级差超过 N 级不再线性增伤），避免低等级玩家完全打不动；心理层面用补偿性匹配（连败后给相对好打的对手）与明确的进度反馈，让不付费的玩家看到自己在追。测试侧要验的是匹配算法在极端分布下（高等级玩家多、低等级玩家少的时间段）会不会把新手反复扔给碾压局。

**怎么约束 AI 的输入输出**：输入侧把需求拆细、用规格说明（spec / 接口约定 / 验收条件）把「要什么」写死，而不是丢一句话让它猜；上下文该给的文件、类型、既有实现给全，不该给的不塞。输出侧不靠「求它写对」，靠工程手段收口：让 AI 一次性只做小粒度改动，每一块都能独立跑通；用编译、类型检查、lint、测试这些确定性关卡当场判对错；重要逻辑必须人工逐行 review，尤其是权限、金额、并发这类错了代价大的地方。发现同类问题反复出现时，把规则沉淀成仓库里的 AGENTS.md，让下一次的输入自带宽约束。一句总结：把 AI 当有产出但不可信的协作者，验证成本要预先算进流程。
