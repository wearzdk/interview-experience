### 《参考解析》

**分布式锁要讲清「三件事」**：互斥怎么保证（SET key value NX PX 原子加锁，或 Redisson 的 lua 脚本）、超时与续期怎么处理（租期要大于业务耗时的预估，配合看门狗续期，避免业务没做完锁先过期）、释放怎么安全（校验 value 是自己的再删，用 Lua 保证原子）。更严谨的方案要提 fencing token：即使锁误判，下游也能用单调递增的令牌拒绝过期持有者的写入。异步线程池要讲隔离：不同业务用不同池，避免一个慢下游拖垮全部；配齐核心线程数、队列、拒绝策略与监控（活跃线程、队列长度、拒绝次数）。

**性能优化的回答必须有前后对照**：说清优化前的瓶颈定位方法（压测 + 火焰图 + 慢查询），改了什么（缓存、批量、索引、异步、连接池、序列化），指标变成多少（QPS、P99、CPU、DB 负载），以及代价（一致性延迟、内存、复杂度）。没有数字的「优化了性能」在二面会被追穿。

**Agent 质量评测要分层**：任务级看成功率与端到端耗时，步骤级看工具调用正确率与无效调用次数，输出级看人工抽检或 LLM-as-judge 打分，成本级看每任务 token 与费用。评测集要覆盖真实分布并保留历史失败案例做回归，否则指标只会随样本漂移。

**AI 编码的质量约束靠「机器可判的门」**：类型检查、lint、单测、构建、契约测试这些必须先过；再叠一层「改动范围约束」——让它先读相关文件、输出改动计划、只允许改指定文件，禁止顺手格式化无关代码；review 只看 diff 并对照计划。防止不必要改动最有效的三条：给明确的最小改动指令、禁止运行格式化与批量重命名、以及提交前用 `git diff --stat` 检查波及面。

**Redis 快在哪、快多少**：纯内存访问、单线程事件循环避免锁竞争与上下文切换、IO 多路复用、高效的数据结构（跳表、紧凑编码）、协议简单。数量级上，单实例读写在 10 万 QPS 量级，MySQL 单机点查通常在千到万级，差一到两个数量级——但这只是「单条简单命令」的对比，复杂查询和事务语义完全不同。

**「为什么不直接用 Redis 存数据」要答持久性与一致性**：Redis 的持久化是 RDB 快照 + AOF 日志，RDB 会丢最后一次快照之后的数据，AOF everysec 也可能丢约 1 秒；主从复制是异步的，故障切换可能丢写；没有跨 key 的强事务与成熟的行级约束、外键、复杂查询与 join。所以 Redis 适合做缓存、会话、计数、排行榜、队列，核心账务数据仍要落在有 WAL、有事务、有备份的关系库。

**集群方案与主从同步**：主从（读写分离、异步复制）、哨兵（监控 + 自动故障转移，仍是单主）、Cluster（16384 个槽分片，多主多从，支持水平扩展但有跨槽操作限制）。主从同步分两步：首次全量（主库 fork 生成 RDB 传给从库，期间增量写进 replication buffer）与之后增量（传播命令流，靠 repl_backlog 支持断线重连的部分重同步）。默认异步，所以 `WAIT` 命令只能降低丢写概率，做不到强一致。
