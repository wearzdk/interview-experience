### 《面试题目》

1. 简单介绍一下自己，以及做过的 Agent 项目。
2. 你在团队里是什么角色？目前主要负责 Agent 开发吗？
3. 你会写前端吗？之前有没有做过前端开发？
4. 看你的项目主要使用 Java，为什么以 Java 技术栈为主？有没有用过 Python 等其他技术栈？
5. 展开讲一下最近做的 Agent 项目，包括完整的技术方案和整体架构。
6. 为什么选择 Neo4j 来实现这套方案？图数据库在这里承担什么职责？是不是通过不同节点之间的关系进行查询，再由不同节点对应不同的工具调用？
7. 现在已经有 LangGraph 这样的图式 Agent 运行时框架，为什么没有选择它，而是采用当前方案？
8. 这个项目最大的技术难点是什么？有没有遇到比较有挑战性的问题？
9. 调用工具时，有没有出现过选错工具，或者本来不需要调用工具却调用了的情况？
10. 整个执行链路里，有没有反复推理、观察反馈和重试的过程？比如工具参数传错时，如果直接拒绝执行，是不是这次请求就失败了？有没有让模型观察错误、接收反馈再纠正的过程？
11. 图谱是怎么建设出来的？整个建设过程大致是什么样的？
12. 建模阶段是由领域专家来做吗？有没有采用一些方法论，比如本体（Ontology）？
13. 实体和关系的抽取，是人工完成，还是交给大模型完成？
14. 你提到大模型会「辅助提取草稿」，具体是什么意思？这个过程是怎么做的？
15. 在这个过程中，语义消歧是怎么处理的？
16. 项目里有没有遇到过上下文溢出的情况？你们是怎么解决的？
17. 你提到会用结构化对象承接上下文，这个对象的主要结构是什么？包含哪些字段？也就是说会把原来的上下文信息转成结构化状态来传递，对吗？
18. 最近讨论比较多的 Agent 新框架、自学习方向，你了解过吗？平时会关注哪些新开源的框架或者模型？
19. 新框架内置的 Trace 插件，与独立的可观测平台有什么区别？
20. 你刚才提到的新技术，具体会用到哪些场景？

### 《参考解析》

1. **为什么选 Neo4j**：当业务知识天然是实体和关系（设备、部件、故障、处置方案），用图数据库能直接表达多跳关系并做路径查询，比在关系库里反复 join 更自然。Agent 侧的价值是把「有哪些实体、彼此什么关系、可以调哪些工具」变成可查询的结构，而不是把知识塞进提示词。风险是运维成本和写入复杂度，所以只把需要多跳推理的部分放进图。

2. **为什么不用 LangGraph**：如果业务已经在 Java 栈上、需要复用已有的服务治理和权限体系，引一个 Python 运行时成本很高；自研的控制流可以精确控制状态持久化和并发。要能承认代价——自己实现了状态管理、断点恢复和可观测，维护成本在自己身上。反过来如果团队没有强绑定，LangGraph 这类框架能省很多事。

3. **工具选错或不该调却调了**：原因通常是工具描述含糊、工具数量太多、提示里没有「什么时候不该调」的说明。解法是收紧描述和参数 schema、给正反例、按场景分组暴露工具，以及在循环里加「已有信息是否足够」的判断。

4. **参数错误后的重试与纠正**：工具报错不应该直接终止，而要把结构化错误（哪个字段、期望什么）回传给模型让它修正一次；连续失败再降级。这是把错误当反馈，而不是当失败。要注意限制重试次数，避免无限循环。

5. **图谱建设**：先定本体（实体类型、关系类型、约束），再由领域专家确认；抽取上先用规则和词典做高置信部分，大模型辅助生成草稿（候选实体、候选关系、出处），人工审核后入库。语义消歧靠上下文、别名表和实体链接（把「A 型号的控制器」链接到具体实体），冲突时以权威数据源为准。

6. **上下文溢出怎么解决**：分层——稳定内容（系统提示、工具定义）放前缀并保持冻结，会变的状态用结构化对象追加，长工具结果落文件只留摘要和引用，接近上限时压缩中间轮次并保留关键结论。结构化状态对象通常包含任务目标、当前进度、已确认的事实、待办、以及引用列表。

7. **内置 Trace 与独立可观测平台**：框架内置的 Trace 只覆盖框架内的调用链，方便开发调试；独立平台能跨服务采集、长期存储、做聚合分析和告警，还能关联业务指标。生产环境两者都要：内置的用于单次调试，平台的用于趋势与归因。

8. **技术难点怎么讲**：挑一个有时间线和取舍的——比如多跳查询的延迟、图谱更新的幂等、工具调用的确定性。按「现象 → 排查 → 方案 → 结果 → 代价」讲，别只说「很难但解决了」。

9. **技术栈选择**：Java 为主通常是团队与基础设施的约束（服务治理、监控、发布体系），Python 用于模型侧实验和数据处理。要能说出两边怎么协作——模型服务化后被 Java 侧调用，而不是混在一套代码里。
