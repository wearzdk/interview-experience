### 《参考解析》

**车载测试与互联网测试的差别**：互联网产品错了可以发版回滚，车错了可能出人命，所以测试的重心从"功能对不对"扩展到"边界与失效下是否安全"。具体差在四处：一是验证分层，同一功能要在仿真（SIL/HIL）、台架、封闭场地、公开道路各验一遍，仿真跑量、实车验真；二是场景驱动，用例来自真实路况与事故库（切入、鬼探头、雨雾、隧道、施工），覆盖度和接管率比代码覆盖率更被看重；三是版本节奏受 OTA 影响，要测升级中断、断电、回滚、跨版本兼容；四是合规与追溯，测试记录要能对应到需求和版本，出问题要能倒查。

**缺陷管理答出生命周期**：一张合格的问题单至少包含标题、环境（车型/软件版本/硬件配置）、复现步骤、预期与实际结果、日志与证据（截图、视频、CAN 报文、诊断日志）、严重级别与优先级。分级常用 Blocker（整车/系统不可用）、Critical（核心功能失效且有安全风险）、Major（主要功能异常但有规避方案）、Minor（体验瑕疵）、Cosmetic（文案界面）。流转是 New → Open → In Progress → Fixed → Verified → Closed，关闭前必须回归验证。加分的是讲"根因分类"：需求理解错、代码缺陷、环境问题、偶发时序，不同根因对应不同的改进动作，而不是反复重开单子。

**测试流程与计划**：流程是需求评审 → 测试计划 → 用例设计 → 环境搭建 → 冒烟 → 执行 → 提缺陷 → 回归 → 测试报告 → 发布评审。计划要写清四件事：范围（测什么、不测什么）、策略（功能/性能/稳定性/兼容性/安全各占多少）、资源（车、台架、账号、人力、场地）、风险（进度紧时优先保安全相关功能）。实施阶段的抓手是每日缺陷同步、变更点重点回归、以及用测试报告给出可发布的质量结论——不是"跑完了"，而是"还剩哪些风险、能不能发"。

**测试团队与协作**：典型结构是测试负责人之下分功能测试（座舱/车控/互联）、智驾测试（行车/泊车/感知）、自动化与工具、性能与稳定性、路测与场地、质量运营（度量与复盘）。测试要对齐产品、研发、算法、整车集成几方，所以沟通成本很高，能不能把"问题现象 + 复现条件 + 影响面"讲清楚，比会不会用工具更影响效率。

**工具栈怎么答**：分两层说更立体。通用层：接口用 Postman/JMeter/requests，自动化用 Pytest/Selenium/Appium，CI 用 Jenkins/GitLab CI，缺陷用 Jira/禅道，性能用 JMeter/Locust。车载层：总线工具 CANoe/CANalyzer，协议 CAN/LIN/以太网、UDS 诊断、OBD，在环测试 MIL/SIL/HIL 台架，场景仿真与数据回放，脚本用 Python/Shell/CAPL。没实操过的就说"了解原理、能上手"，别硬装熟练——面试官顺着问两个细节就能分辨。

**软性问题怎么答**：城市选择给明确答案并表达可调配；行业看法讲"电动化上半场结束、智能化下半场开始，OTA 让测试从守门员变成共建者"；职业规划按"0-1 年跟项目熟悉流程工具、1-3 年独立负责模块、3-5 年做自动化平台或场景库"来讲；期望薪资校招不要先报死数，先讲更看重成长与平台，再表示相信公司有完整体系，心里对区间有数即可。
