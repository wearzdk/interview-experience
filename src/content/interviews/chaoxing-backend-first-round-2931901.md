### 《面试题目》

1. 先做一下自我介绍。
2. 介绍一下你的项目。
3. 项目中某个功能的设计流程是怎样的？
4. AI 工作流中途输出异常怎么解决？重试需要考虑哪些场景？
5. 结构化输出是怎么做的？上下文怎么管理？
6. 讲另一个功能的设计流程。
7. OOM 的处理思路是什么？之前为什么出现、后来怎么做的？
8. 任务状态怎么存？任务更新怎么做？中断怎么恢复？保留现场用了哪些字段？
9. 编排功能和工作流都是怎么做的？
10. 场景题：需要 count 一张大表，怎么做？
11. 追问：如果 select 语句很复杂怎么应对？如果查询很频繁怎么应对？
12. Redis 和数据库怎么确保一致？
13. 追问：刚刚只说了查询很频繁的情况，那么如果 SQL 很复杂呢？

### 《参考解析》

**AI 工作流中途输出异常。** 先分类：模型返回格式不合规（JSON 截断、字段缺失、类型错）、模型拒答/空返回、上游超时或限流、以及「内容对但业务校验不过」。处理上分三层：① 节点级——每次模型调用都要求结构化输出（JSON schema / function calling），拿到后立刻校验，不合规就把「错误信息 + 期望格式」回灌给模型重试（限次数，比如 2 次）；② 流程级——节点失败不直接让整条流程挂掉，而是进入「可重试 / 可跳过 / 需人工」三种分支之一，状态落库；③ 兜底层——重试耗尽后降级（用规则模板、返回部分结果、转人工），并把失败样本记下来做评测。重试要考虑的场景：幂等（重试不能重复产生副作用，用请求 ID + 唯一约束）、退避（指数退避 + 抖动，避免打爆上游）、可重试性（400 类参数错误重试没用，429/5xx/超时才重试）、以及预算（重试会翻倍消耗 token，要有总预算上限）。

**结构化输出与上下文管理。** 结构化输出优先用模型原生的 JSON mode / function calling / 约束解码，而不是「提示词里写请返回 JSON」然后正则抠；拿到后必须过 schema 校验（类型、必填、枚举、长度），并做业务校验（金额范围、ID 是否存在）。上下文管理的核心是「分层 + 按需」：系统提示（稳定）→ 会话摘要（压缩）→ 最近若干轮原文 → 当前任务输入；关键实体（订单号、金额、用户选择）单独存结构化字段，永不压缩；长文档用检索按需拉取片段，而不是整篇塞进去。

**OOM 的处理思路。** 先分清是 JVM 堆 OOM（`java.lang.OutOfMemoryError: Java heap space`）、元空间、直接内存，还是容器被 cgroup OOMKilled（进程直接消失、没有 Java 异常）。排查顺序：看 GC 日志与堆使用曲线（是缓慢上涨的泄漏，还是瞬时尖峰）、拿 heap dump 用 MAT 看支配树与最大对象、对照最近变更（新上线的大查询、缓存没设上限、批量任务一次拉全量）。常见根因与对策：一次性 `select *` 全表加载 → 改分页/流式；本地缓存无上限 → 换 Guava/Caffeine 带容量与过期；集合只增不减 → 加清理；大文件/大响应体 → 流式处理；线程池队列无界 → 有界 + 拒绝策略；容器内存限制小于 JVM 配额 → 用 `MaxRAMPercentage` 对齐。修复后要有回归：压测同样的流量看堆曲线是否平稳。

**任务状态怎么存、中断怎么恢复。** 状态用「状态机 + 版本号」：`PENDING/RUNNING/PAUSED/SUCCESS/FAILED`，每次更新带 `version` 做乐观锁（`update ... where id=? and version=?`），避免并发覆盖。要保留的现场字段：当前节点/步骤、已完成步骤的输出摘要或引用（结果存对象存储，库里存 key）、输入参数快照、重试次数、最后更新时间、失败原因、以及幂等键。中断恢复时按 `id + version` 读回状态，从「最后一个成功步骤」往后重放；对外部副作用（发消息、扣款、调第三方）要在执行前先落「意图」、执行后落「结果」，恢复时先对账再决定是否重做。

**大表 count 怎么做。** 三种思路按精度取舍：① 精确但要快——用覆盖索引（`select count(*) from t` 走最小的二级索引，减少回表；`count(1)` 与 `count(*)` 在 InnoDB 里等价，`count(列)` 还要判空）；② 近似——`explain` 的 rows 估算、或维护统计表（定时任务累加、按分片存增量）；③ 业务上不需要精确时用「缓存 + 定期刷新」，接受 TTL 内的误差。为什么 InnoDB 的 `count(*)` 慢：MVCC 下不同事务看到的行数不同，无法像 MyISAM 那样存一个总数，必须扫索引逐行判断可见性。

**复杂 SQL 与高频查询。** 复杂查询（多表 join、聚合）：先看执行计划（是否走索引、有没有 filesort/临时表），能拆就拆成「先过滤出小结果集，再关联」；把聚合结果预计算成宽表或物化视图（定时或增量刷新）；对「高分部」的数据单独维护统计字段，长尾部分走近似统计——这正是作者答的「分布统计 + 高频部分持久化」。高频查询：加缓存（本地 + Redis 两级）、读写分离、把热点数据放窄表、接口层做限流与合并请求。要强调「缓存只挡读，写的正确性仍要靠数据库」。

**Redis 与数据库一致性。** 常用 Cache Aside：读未命中回源并回填；写「先更新 DB，再删除缓存」，并配延迟双删（更新后延迟几百毫秒再删一次，覆盖并发读回填的旧值）。为什么不「更新缓存」而是「删除缓存」：并发写会把旧值写进缓存，删除更安全（下次读回源拿最新）。更强的一致性靠订阅 binlog 异步失效（Canal），把缓存失效从业务代码解耦，并加对账任务定期修复。极端要求强一致的场景，就不要让缓存参与判断（只做展示加速），或者用「版本号 + 读时校验」。

**这场面试的启示。** 时长预告不值钱——写着 15–30 分钟也可能面 50 分钟，项目要按「能被追问三层」的标准准备：功能设计 → 异常与边界 → 数据一致性/恢复。作者的答法有个好习惯：先给结论（用临时表或维护统计字段）、再补方案分层（Redis 挡第一波、明细表做真相），这种「先结论后分层」的表达在连续追问下不容易乱。
