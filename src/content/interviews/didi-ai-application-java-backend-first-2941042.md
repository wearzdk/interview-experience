### 《参考解析》

**多种数据格式要不要先标准化**：要，而且这一步的收益比换模型大。上游格式不统一时，模型每次看到的输入分布都在变，输出质量自然不稳，问题还会被误判成「模型不行」。做法是先在接入层做 schema 归一：把各来源的字段映射到统一模型（字段名、类型、单位、时间格式、空值语义），保留原始报文以便回溯，再在统一结构上做抽取与生成。归一层还能顺手做质量校验（必填、范围、枚举），把脏数据挡在模型之前。

**同一份数据生成内容是否一致**：默认不一致——采样有随机性，提示词里塞入的上下文顺序、长度也会影响输出。是否需要一致取决于业务：需要可复现（比如生成结构化结论、多次生成要做一致性比对）就把温度调到接近 0、固定输出 schema、固定上下文拼装顺序，并用缓存按输入哈希复用结果；需要多样性（比如生成多种文案）才放开温度。不管哪种，都要在评测里区分「随机波动」与「质量下降」，否则调参会调成玄学。

**怎么保证生成内容满足用户需要**：把「满足需要」拆成可判定的指标，而不是靠感觉。先定义成功标准（结论是否覆盖用户问的要点、字段是否齐全、有无事实错误），再建三层保障：生成侧用结构化输出与要点清单约束覆盖范围；校验侧做规则检查（必填、引用是否能在原文找到、数字是否与源数据一致）；反馈侧收集线上 badcase，定期抽检并回流成评测集。调优的顺序是先补数据与提示词里的判定标准，再考虑换模型——多数「不满足需要」是输入信息不足或标准没说清。

**校验规则来自需求还是开发中提炼**：两者都有，但要说清各占什么位置。需求阶段能确定的是业务硬约束（金额、权限、必填、合规口径），这些必须写进规则并前置校验；开发与线上运行中提炼出来的是模型容易出错的那一类（特定字段的表述歧义、跨字段一致性、引用错位），它们来自 badcase 归纳，属于持续迭代的部分。回答时给一个具体例子最好：某类字段模型总把单位写错，于是加一条单位一致性校验，并把它写进提示词的正例。

**DDD 与 Agent 是什么关系，改到了哪一层**：DDD 提供的是领域语言与边界——实体、聚合、领域服务把业务概念说清楚；Agent 需要的是「模型能理解并安全调用的能力」，所以自然的结合点是把聚合上的领域能力暴露成带语义的工具（意图明确、入参收敛、有副作用声明），而不是把 Controller 接口原样丢给模型。追问「只在上层聚合还是改了底层」，要如实回答：如果只是加了一层工具封装与编排，那就是上层聚合，原有领域模型没动；如果为了让能力可被复用而重构了服务边界、抽了防腐层，那底层也动了。面试官问这句是在核实你是否真的理解自己改动的边界，不要含糊。

**Agent 辅助研发的工作流**：有没有标准化流程，回答要落到可复现的环节。典型的是「需求 → 让 Agent 读相关代码与文档给出改动方案 → 人工确认方案 → Agent 生成改动与测试 → 本地跑测试与本仓 lint → 人工 review 关键 diff」。价值不在生成速度，而在把重复的检索、样板代码、测试补齐交给它；风险在它自信地编造不存在的 API，所以流程里必须有「读真实代码」「跑真实测试」两道锚点。

**怎么校验 AI 给出的专业内容**：分三层，越靠前越便宜。第一层靠可验证的事实——数字、引用、API 签名、论文结论，直接回原文或官方文档核对；第二层靠交叉来源，同一结论让模型换一种提法或换一个来源再确认；第三层靠领域判断，自己没把握的部分交给人或查权威资料。要强调的是「不能靠模型自己说自己对」，自我检查只能发现格式问题，发现不了错误的事实。

**AI 节省了时间还是被返工抵消**：要给出可量化的判断，而不是表态。做法是记录两类时间：AI 参与前后的任务耗时，以及 AI 产出被打回重做的比例与原因。经验上，越是边界清楚、有现成测试与规范的任务，净收益越明显；越是需要跨系统判断、隐含约定多的任务，返工成本越高。回答时可以补一句：真正的收益来自把校验和测试前置，而不是让模型一次写对。

**个人小系统与企业系统的差别**：个人项目可以容忍不确定、可以自己兜底、出问题重跑一次就好；企业系统要求可观测、可回滚、可审计、多人协作与长期维护，任何一次模型的异常输出都可能变成线上事故。所以同一套 AI 能力在企业的落地要多出权限控制、灰度、监控与留痕，成本主要花在这些「不性感」的部分。

**关注 AI 之后还要不要后端基础**：要，而且边界判断更依赖基础。模型调用只是链路里的一环，超时、重试、幂等、并发、缓存、事务、限流仍然决定系统能不能扛住；中间件与框架的价值在于它们已经把这些问题解过一遍，知道它们的语义边界（比如缓存一致性、消息重复消费、分布式事务的代价）才能判断什么时候该用、什么时候不该用。可以给一个具体的例子收尾：模型接口超时时间设多少、重试会不会造成重复写入，这类问题只有懂后端的人能回答对。

**反问**：团队业务方向（两轮车）决定你做的 AI 应用面向什么场景，是调度、运维还是用户侧；能力提升重点的问题可以顺势说明自己想补的是「把 AI 能力落到有 SLA 的系统里」这一块，比问晋升路径更贴岗位。
