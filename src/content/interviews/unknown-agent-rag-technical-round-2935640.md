### 《面试题目》

1. Agent RAG 和传统的 RAG 有什么区别？
2. LangChain 和 LangGraph 你了解多少？用过哪一部分？
3. 你对 harness 架构的了解有多少？
4. 上下文窗口管理的方式有哪些？（直接截断、memory.md 文件、摘要）
5. Agent 和 LLM 的底层交流方式是怎样的？LLM 在底层是怎么生成答案的？

### 《参考解析》

这场面试的失败点写得很诚实：项目都停在应用层，一问机制就塌。这类追问恰恰是现在 Agent 岗的分水岭——会用框架的人很多，能解释框架为什么这么做的人少。

Agent RAG 与传统 RAG 的差别不在检索器，而在「谁决定检索」。传统 RAG 是一条固定流水线：问题进来 → 检索 top-k → 拼进 prompt → 生成。Agent RAG 把检索变成模型可以调用的工具：它自己判断要不要查、查什么、查几次，看完结果再决定是否继续，还可以组合多个数据源、做查询改写与结果校验。代价是延迟和成本不可预测、需要终止条件与失败兜底，所以工程上要设最大轮次、工具调用预算和「查不到就直说」的降级路径。

LangChain 提供的是组件与链式编排（模型、提示、检索器、工具的抽象），LangGraph 把流程建模成状态机/图：节点是步骤、边是条件跳转，天然支持循环、人工介入和断点恢复。回答时最好给出选择依据——线性流程用链式足够，需要循环、分支、多角色协作或可恢复执行时才上图。

harness 在这里指的是「跑模型的执行外壳」：它负责把对话历史与工具定义组装成请求、解析流式输出与工具调用、执行工具并把结果回填、管理上下文预算与重试。理解这一层，才知道为什么工具描述写法、历史顺序、消息角色会直接影响模型表现。

上下文管理的三种常见手段要讲清取舍：直接截断最简单但会丢早期关键信息，通常保 system 与最近若干轮；摘要（滚动总结）能压缩但会引入信息损失与二次生成成本；外部 memory 文件/向量库把长期事实存出去，按需检索回来，最灵活但要处理一致性与召回质量。真实系统往往是组合：system 与工具表固定不动，历史按「最近窗口 + 摘要 + 按需检索」拼装，这样还能吃到前缀缓存的好处。

最后一题考的是对生成机制的理解：模型按 token 逐个预测下一个 token 的概率分布，采样（温度、top-p）决定选择，自回归地把输出接回输入直到停止符或长度上限；上下文里的每个 token 都会参与注意力计算，所以「说了什么、顺序如何」直接改变输出。答不出实现细节没关系，但要能说清这套机制导致的后果：上下文越长越贵越慢、模型没有真正的记忆、工具结果必须显式回填给它。
