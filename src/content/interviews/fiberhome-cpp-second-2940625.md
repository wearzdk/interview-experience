### 《面试题目》

1. 简单做一下自我介绍。
2. 介绍你的核心项目，以及相关业务内容的设计。
3. 设备并发场景下，如何解决数据一致性问题？
4. 你的项目大多偏向应用层开发，但岗位侧重网卡收包、报文处理，这个区别你怎么处理？
5. 项目大部分是视觉、车载业务场景，为什么选择 C 与 C++ 开发岗位？
6. 你的意向工作地点是哪里？

### 《参考解析》

**并发场景下的数据一致性怎么答**：先分层再给方案，比直接抛锁名更清楚。单机多线程层面，先判断是「互斥」还是「同步」：共享计数与状态机迁移用互斥量或原子操作，读多写少用读写锁或 RCU，高频小消息用无锁队列，但要说明内存序（`memory_order`）与伪共享（缓存行对齐）的代价。多进程层面用共享内存加信号量或文件锁，注意进程崩溃后的锁释放与超时。多设备或分布式层面，先确定一致性要求：强一致需要共识或两阶段提交，代价是时延与可用性；多数设备场景实际采用最终一致，靠版本号或时间戳解决冲突、靠幂等与重试保证不重复生效、靠消息队列的有序投递与去重表兜底。最后要说验证方式：并发压测、故障注入（断网、掉电、进程被杀）、以及用日志和序列号回放核对状态。设备并发题最容易被追问的是「掉电瞬间如何保证不丢不重」，答法是先落盘再确认、写日志后改状态、以及恢复时的重放与去重。

**应用层开发与网卡收包、报文处理的差异如何衔接**：差异在于所处数据通路的位置。应用层关心业务语义、协议格式与接口契约；收包路径关心的是中断与轮询的切换（NAPI）、DMA 环形缓冲区、`skb` 的分配与拷贝、协议栈分层解析、以及高性能场景下的零拷贝或旁路方案（`mmap`、`sendfile`、AF_XDP、DPDK 轮询）。可迁移的能力其实不少：报文编解码本身就是应用层天天在做的事（字节序、长度校验、TLV 与校验和），线程模型与队列设计、内存池与生命周期管理、用 `perf` 与抓包做性能分析，这些都是同一套功底。回答时先承认差异，再给具体的学习路径——读内核网络子系统与驱动模型、用抓包工具分析真实流量、自己写一个抓包或转发程序验证理解——最后举一个已有的相近经验作为佐证。空泛地说「我学习能力强」没有说服力，能说出「我打算从哪一层入手、用什么项目验证」才可以。

**为什么从视觉、车载转向 C 与 C++ 开发**：动机要落在长期技术方向与已有证据上，不要贬低原领域，也不要只说兴趣。可以这样组织：先在项目中接触到 C 与 C++ 承担的模块（性能敏感的推理后处理、设备端通信、内存与线程管理），发现自己更愿意深究资源与性能这一层；再做了一点主动投入（读过内存模型与并发相关的书、用 C++ 重写过某个模块并给出耗时对比）；最后说明这个岗位吸引你的具体点（协议与报文处理贴近系统底层，能长期积累）。如果被追问「视觉经验是否浪费」，应答成互补：视觉项目带来的数据处理与工程化经验仍然有效，而底层能力是希望补上的方向。这类问题面试官真正在确认的是稳定性——你会不会干半年又想转回去。

**自我介绍、项目介绍与地点类问题的处理**：自我介绍控制在两分钟内，结构是「学校与方向一句话、两个项目各两句话（做什么、我负责什么、一个可量化结果）、为什么投这个岗位一句话」，不要复述简历全文。项目介绍要预留钩子：主动说明业务背景与整体设计，再聚焦自己负责的模块，讲清一个关键技术决策与它的代价，面试官的追问自然会落到你准备好的地方。意向工作地点要给明确答案与可核查的理由（家庭所在地、长期发展、已在该城市有生活基础），含糊或「都可以」会被理解为没有规划；若确实有多个可选，给出排序与条件，而不是把选择权推回给面试官。
