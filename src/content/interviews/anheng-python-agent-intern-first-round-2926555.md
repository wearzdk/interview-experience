### 《参考解析》

**大模型返回结果不靠谱怎么处理**。分三层答。**约束输出**：用结构化输出（JSON Schema / function calling）、枚举约束、少样本示例把模型的自由度压下来，能确定性校验的字段用代码二次校验（格式、范围、必填）。**多重校验**：语义类结果用模型评审加少量人工校准，关键结论要求模型给出依据（引用原文片段、给出中间推理或工具调用记录），再做一次自我一致性检查（同一输入采样多次看结论是否稳定，或换一个模型交叉验证）。**工程兜底**：把评测集做成回归门禁（任何 prompt / 模型 / 参数改动都跑一遍），记录每次调用的输入、输出、耗时与 token，便于回溯；失败要能降级（重试、换模型、退回到规则逻辑），并且把 badcase 定期回流进评测集。要强调的是「不要指望模型 100% 正确，而要让系统在模型出错时可观测、可回滚」。

**Agent 上下文膨胀与裁剪策略**。先说清为什么膨胀：多轮工具调用会把每轮的请求与返回都堆进上下文（工具返回往往很长，比如网页正文、数据库查询结果），token 线性增长带来成本、延迟与「中间信息被稀释」的质量下降。处理策略按优先级排：一是**只保留必要信息**，工具返回做摘要或结构化抽取（只留字段而不是整页文本），超长结果截断并保留指针以便按需再查；二是**滚动窗口 + 摘要**，保留最近 N 轮原文，更早的对话压缩成一段摘要；三是**分层记忆**，把长期事实（用户偏好、任务目标）写进外部存储或系统提示，用时检索，而不是常驻上下文；四是**子 Agent 隔离**，把一次性的重活（读大文件、批量检索）交给子任务，只把结论返回主流程；五是**预算与截断策略**，为每轮设定 token 预算，超限时按重要性丢弃（先丢旧工具结果、再丢旧对话），并保证不切断工具调用与结果的配对结构。回答时补一句「裁剪本身要可测」：用同一批任务对比裁剪前后的成功率与成本，别只盯着 token 数下降。

**「代码是不是 AI 写的」怎么答**。这是当下高频问题，答得含糊会被怀疑实际能力。稳妥的框架是分场景 + 讲清审阅方式：脚手架、样式、样板 CRUD、类型定义、测试用例草稿大量用 AI；涉及状态管理、并发、性能与安全边界的部分自己写并逐行 review。要能说出实际的协作方式：先让 AI 解释陌生代码与方案对比，自己定方案；生成后跑通、写测试、看 diff；发现自己看不懂的代码就不合并。可以补一句风险意识：AI 生成的代码容易在边界条件、错误处理与依赖版本上出问题，因此必须自己承担最终正确性。

**「分到的项目组不是 Agent 方向」怎么答**。这类问题的标准答法是先接受事实、再给出你的判断依据。可以说清自己对这个岗位的期待是「在真实业务里做 AI 相关能力的落地」，ToB 政企控制台虽然不是 Agent 工具，但同样有集成大模型能力、做内部效能工具的空间；同时把关注点放在「能学到什么、能产出什么」上，而不是职位名称。要避免表现出对分配不满意或者含糊其辞地「都可以」。面试官给的两条反馈值得记下来：计算机基础要继续巩固（说明基础八股仍会考，转行或偏业务方向的同学容易忽略）、AI 项目经验要提炼（讲清楚你的方案带来的价值与你的思考，而不是只描述做了什么功能）。

**岗位信息不对称的处理**。原帖里有两个值得注意的信号：面试官的技术方向与被投递岗位不一致（Vue 前端面 Python Agent），以及岗位说明写的是 Agent 开发但实际项目组做政企控制台、技术栈以 Vue 为主、大小周、无转正承诺。面试中遇到这种信息落差，值得在反问环节直接问清：入职后具体进哪个团队、日常做什么、有没有转正名额与评估标准、加班与排班制度。这些信息比职位名称重要，问清楚比事后后悔好。
