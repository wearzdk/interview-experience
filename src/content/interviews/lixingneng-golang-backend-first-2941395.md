### 《参考解析》

**微服务边界与 Saga**。边界按业务能力与数据所有权划分，不按技术分层：一个服务独占自己的库表，跨服务只走接口或事件，避免共享库；典型拆法是网关 / 用户与鉴权 / 订单 / 支付 / 通知这类「各自有一份状态、变更频率不同」的切分。Saga 用于跨服务的长事务：把一个大事务拆成一串本地事务，每一步配一个补偿动作，正向失败就按逆序补偿。两种协调方式——编排式（一个协调者按状态机逐步调用）与协同式（各服务监听事件自行推进）。它保证的是最终一致性，不是原子性：中间态对外可见，所以要配合幂等键、补偿重试与人工兜底；金额类操作还要在补偿前先查对方是否已经成功，避免「补偿了一次实际已成功的扣款」。项目里适合用在「下单 → 扣库存 → 扣款 → 发券」这种跨库链路，而不是单库内的转账（那种用本地事务更简单）。

**一万个用户发消息**。不能在一个请求里同步循环调用下游：先落一张待发消息表（或用 MQ），用分片 + 并发 worker 消费，每个消费者按用户分批拉取、限制并发与 QPS，失败进入重试队列并带退避，超过次数进死信。要做到可重入：每条消息带唯一键，下游按唯一键去重。调用方只负责写库 + 投递事件并立即返回，发送进度与结果异步回写。

**支付调用阻塞时的第二次请求**。核心是幂等 + 状态机：业务单号作为幂等键，落库时唯一约束挡住重复创建；状态走「待支付 → 支付中 → 成功 / 失败」，第二次请求进来先读状态，若已是「支付中」就直接返回处理中让客户端轮询，而不是再发起一次扣款。并发进来时要靠分布式锁或数据库行锁把「检查状态 + 置为支付中」做成原子操作；对外部支付网关的调用要设超时（context deadline），超时后状态置为「未知」，由对账任务按商户单号去查真实结果，避免「我方以为失败、实际已扣款」的重复支付。

**JWT 透传与 gRPC 拦截器**。链路是：HTTP 网关校验一次令牌、把原始 JWT 放进 gRPC metadata（`authorization: Bearer <token>` 或只放 token）；服务端一元拦截器在进入 handler 前从 `metadata.FromIncomingContext` 取出令牌，校验签名与算法（只允许预期算法，挡住 `alg=none` 与算法混淆）、过期时间、签发者，再用公钥或共享密钥验签，解析出 subject / 角色放进 context；业务 handler 只从 context 读身份，不自己解析。需要往下一跳传时，客户端拦截器把 context 里的令牌写回 metadata，注意不要重复加 `Bearer` 前缀、也不要无脑透传到外部不可信服务。

**长调用链的日志**。靠 trace/span：入口生成 trace id（或从上游取），每次跨进程调用把 trace id 与 span id 塞进 metadata，客户端与服务端拦截器负责注入与提取，日志里统一带 trace id 与当前 span，就能把一条链路串起来。服务端拦截器底层就是 gRPC 的 middleware 机制：`grpc.UnaryServerInterceptor` 是一个 `func(ctx, req, info, handler)` 形式的函数，拦截器链在注册时按顺序包一层，调用 `handler(ctx, req)` 继续向内，所以「进 handler 前」与「handler 返回后」都能插逻辑，正好用来打日志、计时、上报 metrics、做鉴权与限流；流式接口对应 `StreamServerInterceptor`，要在 `RecvMsg` / `SendMsg` 的包装里做。

**panic 与 goroutine 隔离**。Go 里 panic 只沿发起它的那个 goroutine 的调用栈展开，不会传播到别的 goroutine，所以 A 请求 panic 不会直接让 B 请求失败；但如果没有 recover，A 所在 goroutine 崩溃会让整个进程退出，进程一死所有请求都没了。服务端每请求一个 goroutine，handler 层用 defer + recover 兜住，把 panic 转成 500 并打印堆栈，其他请求照常处理；recover 只对当前 goroutine 有效，写在别的 goroutine 里的 defer 拦不住本 goroutine 的 panic，所以每个自行 `go func()` 的地方都要自带 recover、不能让它逃出去。

**GMP 调度**。G 是 goroutine（栈、指令位置、状态），M 是操作系统线程（真正执行代码的实体），P 是逻辑处理器（持有本地可运行队列与内存分配缓存，数量默认 `GOMAXPROCS`）。M 必须绑定 P 才能执行 G；本地队列空了会从全局队列取，或从其他 P 的本地队列偷一半（work stealing）；遇到阻塞系统调用时 M 会与 P 解绑，P 交给其他 M 继续跑，阻塞返回后 G 重新排队。`channel` 操作、`mutex`、`syscall` 等会让 G 让出；网络 IO 靠 netpoller 唤醒，不占一个线程空转。所以 goroutine 的创建成本远低于线程（初始栈 2KB，按需增长），但也因此不能把「一个 goroutine 一个数据库连接」这种设计随意堆量。

**slice 与 map 的传递**。Go 只有值传递。slice 是一个三字段的描述符（指针、长度、容量），传参复制的是描述符：函数内修改已有元素会影响调用方（共享底层数组），但 `append` 导致扩容后只改本地描述符，调用方看不到新长度；想在函数内改长度要传 `*[]T` 或返回新切片。map 是「指向 hmap 的指针」，传参复制的就是这个指针，所以增删改都作用在同一份数据上；但 map 不能原地替换成另一个 map，重新赋值同样只改本地变量。

**make 与 new**。`new(T)` 分配一块 T 的零值内存并返回 `*T`，只做分配、不做初始化；`make` 只用于 slice / map / channel，返回的是类型本身（不是指针），并完成内部结构初始化（slice 的长度容量、map 的桶、channel 的缓冲区）。所以 `*new([]int)` 是一个指向 nil 切片的指针，而 `make([]int, 3)` 是一个长度为 3 的切片。

**nil 与已关闭 channel**。往 nil channel 收发都会永久阻塞（select 里这一支永远不选中，可用来动态关掉某个分支）；向已关闭的 channel 发送会 panic（`send on closed channel`），从已关闭的 channel 接收不会阻塞，会立刻拿到剩余缓冲数据，取完后一直返回零值与 `ok=false`。所以关闭 channel 只能由发送方做，且要保证没有其他发送者；多个发送者时用 `sync.Once` 或单独的关闭信号 channel。

**select 加 default**。不一定永不阻塞：`select` 在所有 case 都不可达时才走 `default`；加了 `default` 后，如果没有 case 就绪会立刻执行 default 而不是等待，所以在「轮询 + 非阻塞尝试」时表现为不阻塞。但如果某个 case 已经就绪（缓冲 channel 有数据、有 goroutine 在等），仍然会执行那个 case，甚至可能在多个就绪 case 中随机选一个。要真正不阻塞地尝试发送用 `select { case ch <- v: default: }`，注意它可能丢消息。

**error 比较**。优先用 `errors.Is` 判断「是不是某个哨兵错误」（它沿 `Unwrap` 链逐层比对，包装过的错误也能命中），用 `errors.As` 取出具体类型再读字段；直接 `==` 只对同一个错误值或未包装的哨兵错误成立，`fmt.Errorf("%w")` 包装之后 `==` 就失效了。不要用字符串比较判断错误类型；自定义错误要实现 `Is` / `As` 时注意 nil 与指针接收者的语义。

**长循环里 defer 关闭文件**。`defer` 是压进当前函数的 defer 栈，函数返回时才按后进先出执行，所以在循环里写 `defer f.Close()` 会让所有文件句柄一直开到这个函数结束，长循环直接耗尽文件描述符，后续 `Open` 报 `too many open files`。正确做法是把「打开 → 处理 → 关闭」收进一个函数（或用闭包 / 匿名函数）让 defer 在每轮结束时执行，或者显式 `Close` 并检查错误。

**负载均衡算法**。轮询与加权轮询（按权重平滑调度，如平滑加权轮询避免突发）、随机与加权随机、最少连接 / 最少请求（按当前负载选最闲的，需要实时统计）、一致性哈希（同一 key 固定落到同一节点，节点增减只影响邻近区间，配虚拟节点摊平）、最快响应时间（按 RT 或 EWMA 动态选）、以及带健康检查与熔断的复合策略。服务端侧的「负载均衡」还包括客户端侧的服务发现 + 本地负载均衡，配合重试要注意别把重试打到已过载的节点上。

**token 计费的小数精度**。金额与单价都不能用 float64：二进制浮点无法精确表示 0.1 这类十进制小数，7、8 位小数相乘累加后误差会累积到分位，对账就对不上。做法是整数化——把单价按最小计价单位（如 1e-8 美元或「厘」）存成整数，token 数也是整数，乘法用 `int64` 或 `big.Int`（超出 64 位时），只在展示时做一次除法与四舍五入；Go 里可以用 `decimal` 库（定点十进制）或直接把 1e-8 单位当整数记账。累计时避免「每笔先四舍五入再求和」，应保留高精度累加、结算时统一取整，否则大量小额请求会系统性地少算或多算。
