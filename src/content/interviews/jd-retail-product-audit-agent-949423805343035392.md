### 《面试题目》

1. 你这个审核系统，输入是什么？纯文本还是带图？
2. 一张商品图里同时有文字、logo、水印、二维码，你怎么分别处理？
3. OCR 识别错了，比如把「0」认成「O」，后面链路会怎么样？
4. 你会不会把 OCR 结果直接喂给模型？不喂的话，中间那一层做了什么？
5. 图和文冲突：图片写「纯棉」，详情写「聚酯纤维」，你信谁？这个冲突你自己判过吗，还是靠规则？
6. 规则引擎有多少条规则？谁维护？规则之间打架了怎么办，优先级怎么定？
7. 新增一条规则，怎么验证不会误伤历史商品？有没有跑过全量回归？跑一次多久？
8. 模型和规则谁先谁后？为什么这么排？
9. 模型判「不确定」的时候，走人工还是走规则？
10. 人工审核队列一天多少单？人均处理多少？
11. 审核人疲劳之后准确率会掉，你怎么发现？怎么衡量一个审核人靠不靠谱？
12. 误杀一个正常商品，商家损失是什么？漏放一个违规商品，平台损失是什么？这两个损失不对等，你的阈值往哪边偏？

### 《参考解析》

**指标口径要先说分母。** 92.3% 必须先回答是准确率、召回率还是通过率，分母是全部商品、模型判定的商品还是人工复核过的商品。测试集要说明规模、抽样方式、标注人、标注规范与一致性（如 Cohen's kappa），以及是否按品类、违规类型分层。把「规则兜住的部分」算进模型指标会高估模型能力，需要单独报告模型判定、规则判定、人工判定的分布。要证明提升来自自己的改动，做同模型同数据集的 A/B，固定随机种子与阈值，比较混淆矩阵与业务指标，而不是只看一个总数。

**图文冲突不能只靠单一来源。** 图片里的文字、logo、水印、二维码分别走 OCR、检测、解码，OCR 结果要做纠错与置信度过滤，低置信度不直接喂模型；图文冲突时按品类规则与证据强度裁决，例如以资质文件、详情页的结构化参数为准，图片作为辅助；无法裁决的进入人工。冲突样本要沉淀成评测集，否则规则改了也无法验证。

**规则引擎要治理。** 规则数量增长后会出现重复、冲突、失效；需要唯一 ID、优先级、适用范围、负责人、生效时间、灰度与回滚。新增规则先在小流量或历史样本上回放，测误杀率与漏放率，再全量；规则之间冲突时按优先级与特异性排序，并把冲突记录暴露给维护者。模型与规则的顺序取决于目标：规则在前做硬约束（违禁词、资质缺失），模型在后做语义判断；或模型先判、规则兜底处理不确定与高风险类目。

**误杀与漏放的成本不对称，阈值要由业务定。** 误杀影响商家体验与 GMV，漏放带来合规与平台风险；两者的代价要用数据量化（申诉率、赔付、监管处罚），由业务签字确定阈值，而不是算法同学拍一个 0.8。阈值调整要做离线回放与线上灰度，观察通过率、误杀率、人工队列长度的变化。

**系统设计按请求链路拆。** 上传与审核异步化，商家页面显示「审核中」，用业务单号加内容哈希做幂等；分片键在商家 ID 与时间之间权衡，大商家打爆分片可以用二次哈希或独立分片；ES 与数据库的一致性用事务消息或本地消息表，双写失败由补偿任务修复；MQ 消费要幂等，失败重试并设死信队列；线程池按任务类型隔离，OCR 属于 IO 与 CPU 混合，线程数不宜照搬 CPU 核数；虚拟线程适合阻塞 IO，但 `synchronized` 与本地方法可能钉住载体线程，ThreadLocal 在虚拟线程上仍随线程生命周期，需要清理。

**P99 排查先分层。** 看入口 QPS 与错误率、线程池与连接池、下游 RT、GC 日志与 safepoint、CPU 与内存、慢查询；用 trace 把一次请求的各段耗时拆开，区分「等下游」与「自己算」。缓存命中率下降而 QPS 不变，可能是 key 设计变化、过期时间集中、数据分布变化或缓存被穿透。

**手撕执行器的结构。** 每个 key 一条队列，队列上挂「是否已有 worker」标志，避免一个 key 起多个线程；任务带 id 与取消标志，排队中的直接移除，运行中的只能协作式取消；停机先关闭入口，再等队列排空，最后放哨兵结束 worker。追问的四个点：单 key 大量任务会占满线程，需要限制每 key 并发或把队列做公平调度；key 数量大时不能一线程一 key，改用固定线程池加就绪队列；第三方库不可取消时只能在任务协议层要求可中断，或隔离到独立进程；`submit` 与 `shutdown` 竞态要用同一把锁保护「检查 closed 与入队」两步。帖主记下的那句「取消得在任务协议层定好，不是执行器能补的」，是这道题的核心。
