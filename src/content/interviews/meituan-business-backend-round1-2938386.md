### 《参考解析》

**Agent 嵌入流程还是独立应用**：嵌入已有流程意味着 Agent 只是流程中的一个节点，输入输出要与上下游系统的数据结构对齐，失败要能回退到人工；独立应用则要自己承担入口、权限、状态管理与结果展示。回答时说明选择理由：嵌入式的优势是复用既有业务规则与数据、用户无迁移成本，代价是与主流程耦合、迭代受发布节奏约束。

**规则与大模型的边界**：确定性判断（金额阈值、字段必填、状态机流转、黑名单）交给规则，模糊判断（语义归类、摘要生成、异常描述理解）交给模型。边界要写清楚：模型只输出候选与理由，规则做最终裁决；模型输出必须带证据字段，便于回溯。

**LLM 节点为什么慢**：生成是自回归的，逐 token 输出，耗时与输出长度线性相关；输入越长首字延迟越高；工具调用会引入额外往返；并发高时受上游限流与排队影响。优化方向是缩短输出（结构化字段代替长文本）、并行化互不依赖的调用、缓存稳定的前缀、把非必要步骤移出主链路。

**Summary 是否落库**：实时生成适合一次展示、不需要回溯的场景；落库适合需要审计、复查、被下游引用的场景。落库要存「输入摘要 + 模型版本 + 提示词版本 + 生成时间」，否则出问题无法复现。

**Agent Loop 的核心概念**：目标与终止条件、观察（工具返回与环境状态）、决策（下一步动作）、动作执行、状态与记忆、错误处理与重试上限。没有采用 Loop 通常是因为任务路径固定，用 Workflow 更可控、成本更低。

**插件化与依赖**：插件化的目标是「新增能力不改主流程」。实现上定义统一的接口（输入、输出、生命周期钩子），由注册表管理；依赖关系用声明式依赖加拓扑排序加载，缺失依赖时降级或报错而不是静默跳过。可插拔的关键是插件之间只通过接口通信，不共享内部状态。

**Codex 执行中插入新消息**：这类 Agent 通常把用户消息追加到对话历史，在当前工具调用返回后由下一轮模型调用读取；若正在流式生成，则要么打断当前生成并重新规划，要么排队到本轮结束后处理。设计上要区分「补充信息」与「改变目标」，后者需要显式中断并确认。

**三线程循环打印 ABC**：用一把锁加三个条件变量，每个线程等待自己的轮次，打印后修改轮次并 `signalAll`；或用三个信号量按 A→B→C→A 的顺序互相 release。要点是「谁在什么条件下等待、打印后唤醒谁」，写代码时把轮次状态放在共享变量里并保证在锁内修改。

**Doublewrite Buffer**：InnoDB 刷脏页前先把页写到双写缓冲（内存中的一块区域，顺序写到共享表空间的连续区域），再写到数据文件的实际位置。若写入过程中断电导致页损坏，重启时可以从双写区恢复完整页。它解决的是「部分写（partial write）」问题，代价是额外的写放大，可以通过参数关闭但会降低崩溃安全性。

**AI Coding 的实操方法**：面对「缓存热点数据一致性验证」这种模糊需求，先澄清四件事：验证什么（一致性窗口、最终一致时间）、数据规模与并发、允许的误差、验收方式。然后让 AI 先产出最小可运行版本（单线程模拟读写 + 断言），跑通后再逐步加并发、加故障注入。控制输出过长的方法是把任务拆成小步、每步给明确的输入输出与验收条件，而不是一次性要求「设计完整系统」。

**排期不足怎么答**：先拆解硬指标对应的最小交付范围，明确「必须做」与「可以后置」；用数据说明现有排期下的风险与取舍，让业务方参与决策；给出分期方案与时间点，而不是直接拒绝或默默加班。
