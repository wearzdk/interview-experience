### 《参考解析》

**「项目是不是在校完成的」在确认可讲边界与你的贡献**。面试官不是歧视校内项目，而是在判断两件事：这段经历能不能经得起深挖（有没有真实用户、真实数据、真实故障），以及你在其中的角色是主导还是参与。回答时先给归属与时间（课程项目、实验室课题、竞赛、个人开源），再明确边界：哪些代码是你写的、哪些是同伴写的、哪些是调用的开源组件，最后给可验证的结果（用户量、任务成功率、延迟、成本）。如果项目确实只在学校跑过，不必包装成生产系统，直接说明规模与限制，再把「如果上线我会先补哪三件事」讲出来，反而显得清楚。

**项目架构按「请求进来—规划—工具—状态—输出」五段讲**，每段说清你的决策而不是罗列技术栈：入口怎么鉴权与限流；规划器怎么把用户目标拆成子任务、用什么表示计划；工具层有哪些工具、schema 怎么定义、失败怎么返回给模型；状态与记忆存在哪里（会话表、向量库、对象存储）、怎么裁剪上下文；输出怎么校验与回传。然后落到你负责的模块，给一个具体的技术难点与解法，比如「工具返回过长导致上下文爆炸，我做了结果摘要加引用 id，token 降了六成而成功率不变」。面试官顺着追问时，优先讲权衡与数字，不要背架构图。

**Harness 是模型之外的那层运行时脚手架**。模型只负责「给定上下文生成下一步」，剩下的事——把用户目标变成循环、把工具描述成模型能调用的格式、管理上下文与记忆、控制权限与沙箱、记录每一步的轨迹、跑评测与回归——都由 Harness 承担。可以把它类比成操作系统之于程序：模型是 CPU，Harness 提供调度、内存管理、系统调用与审计。对 Harness 的理解深度，体现在你能说出「同一个模型换一套 Harness，任务成功率能差出一大截」，以及为什么工程投入要放在这层：工具描述的一次改写、上下文裁剪策略的一次调整，往往比换模型更省钱。

**Harness 的核心组件可以按职责列七块**：Agent Loop（决定何时继续、何时停止，含最大轮次、超时、重复动作检测）、工具注册与调用层（schema、参数校验、结果序列化、错误分类）、上下文与记忆管理（系统提示词、历史裁剪、摘要、长期记忆检索）、规划与任务分解（计划表示、子任务依赖、重规划）、执行环境（沙箱、文件系统、网络与浏览器等运行时能力）、权限与审批（哪些操作需要人确认、审计日志）、可观测与评测（trace、指标、数据集、回归）。如果只能讲三个，就讲循环、工具、上下文，这三块决定绝大多数失败。

**多 Agent 的核心优势是上下文隔离与并行，不是「更聪明」**。单 Agent 处理长任务时，所有中间结果都挤在一个上下文里，越往后越容易丢早期约束；拆成多 Agent 后，每个子 Agent 只拿自己需要的切片，上下文干净、可并行、可独立重试；专业化也带来工具集更小、提示词更聚焦的好处。代价同样要讲：协调开销（谁拆任务、结果怎么合并）、错误传播（上游一个错判断会让下游全错）、一致性与幂等（并发写同一资源）、评测更难（要评整体还要评每一段）。判断要不要拆的标准是「子任务是否可独立验证、是否需要不同的工具与上下文」，两个都不满足时拆了只会更差。

**校验类 Agent 的设计要点是「规则优先、模型兜底、失败可回退」**。先定义输入输出的契约（schema、必填字段、取值范围），能用程序校验的一律用程序：格式、枚举、数值区间、交叉引用是否存在；程序判不了的语义问题（事实是否一致、结论是否有依据）再交给模型，并且最好用与生成不同的模型或不同的提示词做交叉校验，避免同一个模型自己批自己。输出要带置信度与理由，低置信度进入人工复核队列；校验失败时返回具体原因给上游 Agent 重试，而不是只回一个 false。最后要有校验集与回归：把历史误判样本沉淀成用例，每次改提示词都跑一遍。

**任务队列的幂等靠「唯一键 + 状态机 + 去重记录」三层**。第一层是幂等键：由业务唯一标识推导（订单号 + 操作类型，或客户端生成的 requestId），同一键重复投递只处理一次；第二层是持久化去重，数据库唯一索引或去重表，插入冲突即视为已处理；第三层是状态机，任务只能从待处理流转到处理中再到完成，重复消息进来时先查状态，已完成直接返回结果。消息队列的「至少一次」投递语义决定了消费端必须幂等，不能指望「恰好一次」。还要处理两个边角：处理中的任务要有租约与超时，宕机后能被重新领取；重复请求要能返回第一次的结果（结果缓存），而不是简单丢弃。

**Cache Breakpoint 的本质是「让前缀一个字节都不变」**。大模型推理的缓存按前缀匹配，命中要求从第一个 token 开始完全一致，所以系统提示词、工具定义、few-shot 示例这些固定内容必须放在最前面并冻结，任何动态内容（时间戳、用户名、随机 id、排序不稳定的列表）放到后面；断点打在固定段落的末尾，让缓存覆盖最长的那段前缀。会话内不要重排历史消息、不要在每个请求里重写系统提示词。稳定 80% 命中率的做法是把它当指标管起来：按请求记录「缓存命中的 token 数 ÷ 总输入 token 数」，按场景与用户分桶看，命中率掉了就去查是哪段前缀变了（发版改了提示词、工具列表顺序变了、注入了时间）。还要说明口径：命中率是按 token 算还是按请求算、是否只统计多轮会话的第二轮之后，否则 80% 这个数字没有意义。

**32 轮这个阈值应当来自实验而不是拍脑袋**。合理的答法是给出确定依据的过程：先定义指标（任务成功率、约束遗忘率、单轮成本、延迟），再跑一组对照——把同一批任务分别限制在 8、16、32、64 轮上下文，看成功率在第几轮之后开始下降、成本在第几轮之后超过收益，取拐点作为默认值；同时说明 32 不是硬截断，而是触发压缩策略的阈值：超过之后做摘要、把早期轮次转成结构化记忆、或按相关性检索回填。如果这个数字是团队沿用的经验值，就坦白说「沿用的是经验值，我会用上面的方法复核」，比编一个实验更可信。

**并发抢任务防重复领取有四种常见手段**：数据库层面用 `SELECT ... FOR UPDATE SKIP LOCKED` 或乐观锁（带版本号的条件更新，更新行数为 0 说明被别人抢走）；Redis 层面用 `SET NX PX` 抢锁加租约，锁的 value 带持有者标识，超时自动释放；任务状态用 CAS 流转（待领取 → 已领取，只有一次能成功）；消费端再用幂等键兜底。要讲清租约与续期：领取后设一个可见性超时，处理者定期续租，宕机后租约到期任务自动回到队列；但续租不能无限延长，否则死任务永远不回收。最后补一句监控：重复执行率、任务积压、租约过期次数都要有指标。

**MRR（Mean Reciprocal Rank）算的是「第一个正确结果排在第几」的倒数平均**。对每个查询，找到第一个相关结果的排名 r，取 1/r；如果前 k 个里没有相关结果则记 0；所有查询取平均。举例：三个查询的第一个相关结果分别排在第 1、第 2、第 5，MRR = (1/1 + 1/2 + 1/5) / 3 ≈ 0.567。它只看第一个正确项，适合「只有一个正确答案」的检索与问答场景；有多个相关结果时用 MAP 或 NDCG 更合适。回答时补一句 MRR@k（只看前 k 个）以及它和 Hit Rate、Recall 的区别，基本就完整了。

**LangFuse 排查 badcase 的路径是「先筛后看再回归」**：在 trace 列表里按分数、延迟、成本、用户反馈筛选出问题会话；点进单条 trace 看完整链路——每一步的输入输出、工具调用、token 与耗时，定位是检索没召回、工具选错、上下文丢失还是模型幻觉；把同类问题打上标签聚类，统计影响面；修完后把样本加入 dataset，用 LangFuse 的评测跑一遍回归，对比修复前后的分数。它的价值在于把「一步一屏的日志」变成可检索的结构化轨迹，所以平时就要把 sessionId、userId、prompt 版本、模型版本写进 trace 的 metadata，否则出事时筛不出来。

**算法题**：岛屿数量用 DFS/BFS 遍历网格，遇到陆地就计数并把连通的陆地标记为已访问，时间 O(mn)；也可以用一个并查集把相邻陆地合并后统计集合数，适合需要动态连通的变体。对称二叉树用递归最简洁：判断左右子树是否互为镜像（左的左对右的右、左的右对右的左），注意空节点与单侧为空的情况；迭代写法用队列成对入队，每次取两个节点比较。两题都要先确认输入规模与是否允许修改原数组，再动手写。
