### 《参考解析》

**InnoDB 与 MyISAM 的区别**：InnoDB 支持事务、行级锁、外键、崩溃恢复与 MVCC，索引与数据同在聚簇索引（主键 B+ 树的叶子节点就是行数据），二级索引叶子存主键值需要回表；MyISAM 不支持事务与外键，只有表级锁，索引与数据分离，二级索引叶子存行地址，计数用表级计数器所以 `COUNT(*)` 快，适合读多写少且不容忍事务的场景。现代业务几乎一律选 InnoDB，MyISAM 只在只读归档或临时表场景还有意义。

**持久化靠 redo log 的两阶段提交**：事务修改先写内存中的 Buffer Pool 并把变更记入 redo log（顺序写），提交时 redo log 按 `innodb_flush_log_at_trx_commit = 1` 刷盘，脏页由后台线程异步刷回磁盘。即使刷脏前宕机，重启时用 redo log 重放已提交事务、用 undo log 回滚未提交事务。redo log 是物理日志（记录页的字节变更），采用循环写，`write pos` 追上 `checkpoint` 时触发刷脏。这样设计的好处是把随机的页写转成顺序的日志写，兼顾性能与持久性。

**undo log 的作用**：两个——事务回滚与 MVCC。回滚时按 undo 记录的反向操作恢复数据；MVCC 时把 undo 记录串成版本链，配合 ReadView 判断当前事务能看到哪个版本。undo 记录还分 insert undo（只用于回滚，提交后可立即清理）与 update undo（支撑 MVCC，需等无活跃读事务后才能 purge）。

**MVCC 的实现**：每行有隐藏列 `DB_TRX_ID`（最后修改它的事务 id）与 `DB_ROLL_PTR`（指向 undo 版本链）。一致性读时生成 ReadView，记录当前活跃事务 id 列表与最小/最大事务 id；沿版本链向前找第一个「对当前事务可见」的版本——已提交且早于 ReadView 创建、或就是自己修改的。RC 隔离级别每次查询都新建 ReadView，RR 只在事务第一次查询时创建，这就是「RR 可重复读」的来源。快照读走 MVCC，当前读（`SELECT ... FOR UPDATE`、`UPDATE`、`DELETE`）走锁。

**SQL 优化**：见上一则同题回答的思路——慢查询日志发现问题、`EXPLAIN` 看 `type/key/rows/Extra` 定位、联合索引最左前缀、避免索引列上的函数与隐式转换、覆盖索引减少回表、深分页改游标、大事务拆小，最后用优化前后的耗时与扫描行数验证。

**Redis 的数据结构与用法**：String（缓存对象、计数器、分布式锁的 SETNX）、Hash（对象的字段级更新，如购物车）、List（简单的消息队列、时间线）、Set（去重、共同好友的交集并集）、ZSet（排行榜、延迟队列、按分数范围查询）、以及 Bitmap（签到、活跃标记）、HyperLogLog（UV 估算）、Stream（带消费组的消息流）。要说清每种结构的典型命令与复杂度，以及「为什么用这个结构而不是 String 存 JSON」——字段级更新与内存开销是主要理由。

**缓存一致性**：主流方案是 Cache Aside：读时先查缓存、未命中查库并回填；写时先更新数据库、再删除缓存（而不是更新缓存，避免并发写导致的中间态覆盖）。删除失败要有补偿（重试队列、订阅 binlog 异步删）。强一致要求高的场景可以延迟双删（更新后删一次，短延迟再删一次以覆盖并发读回填的旧值），或对同一 key 加分布式锁串行化。要讲清「先删缓存再更新库」在并发读下会把旧值回填，因此不推荐。

**秒杀的不超卖与一人一单**：库存预热到 Redis，扣减用 Lua 脚本把「判断库存 → 扣减 → 记录用户购买标记」做成原子操作，`DECR` 返回值小于 0 即失败；一人一单用 `SETNX` 或 Set 记录 `userId + 商品 id`，与扣库存放在同一个 Lua 里保证原子。Redis 扣减成功后发消息到 MQ，由消费者异步落库创建订单，数据库侧再用唯一索引（用户 id + 商品 id）与 `UPDATE stock SET stock = stock - 1 WHERE stock > 0` 做最终兜底。要强调两道防线都要有：Redis 挡流量，数据库唯一索引与条件更新挡一致性。

**重复下单的原因**：用户重复点击、客户端重试、网关超时重试、MQ 消息重复投递、以及分布式事务的补偿重放。解决靠幂等：下单接口要求客户端传幂等键（或用「用户 + 商品 + 活动」作为业务唯一键），服务端用唯一索引或 Redis 的 SETNX 拦截，消费侧按消息 id 去重，并对已成功的请求直接返回同一结果。

**HashMap 与 ConcurrentHashMap**：HashMap 是数组 + 链表 + 红黑树，默认容量 16、负载因子 0.75，扩容翻倍并按 hash 高低位拆分链表，链表长度到 8 且容量不小于 64 时树化、退到 6 时退化；1.8 的 hash 扰动只做一次高 16 位异或，插入改为尾插。ConcurrentHashMap 在 1.8 用 CAS + synchronized 锁单个桶头节点，取代了 1.7 的分段锁；size 用 baseCount + CounterCell 分散计数；扩容支持多线程协助迁移（ForwardingNode 标记）。它保证单次操作原子，但复合操作（先查后改）仍需外部加锁或 `computeIfAbsent` 这类原子方法。

**带过期时间的 LRU**：结构是哈希表 + 双向链表，哈希表存 key 到节点的映射，链表头部放最近使用、尾部放最久未使用，读写都先移到头部，插入超容量时删尾部。加过期时间有两种做法：一是每个节点存 `expireAt`，读取时惰性判断并删除；二是再加一个按过期时间排序的结构（最小堆或时间轮）做主动清理。伪代码要写清 `get` 的三个分支（不存在、已过期、命中并前移）、`put` 的更新与新增、以及容量满时淘汰。面试里说清「惰性删除 + 定期清理」的组合比只写 LRU 更完整。

**秒杀系统设计的整体结构**：分层削峰。前端做按钮防重、静态资源 CDN 化、活动开始前预约；网关层做限流（令牌桶）与黑名单；服务层做库存预热、Redis 原子扣减、用户维度频控；异步层用 MQ 削峰、消费者落库建单；数据库层用唯一索引与条件更新兜底，订单表按活动分表。配套要有：超卖与少卖的核对任务、未支付订单的超时关闭（延迟队列）、以及压测与降级预案（Redis 故障时是否直接拒绝而不是打到数据库）。

**P99 激增的排查**：先看影响面（哪些接口、哪些机器、哪个时间段），再看依赖（数据库慢查询、Redis 延迟、下游 RPC、MQ 堆积），再看自身（GC 日志与线程栈、连接池是否耗尽、线程池队列是否满、是否有大对象或锁竞争），最后看流量（是否有突增、是否有缓存击穿）。应急动作按「先止损再定位」：限流降级非核心接口、扩容、切流量、必要时回滚最近的发布。工具链是 APM 链路追踪定位慢在哪一段、`arthas` 看方法耗时、`jstack` 看线程阻塞、慢查询日志与 `redis-cli --latency`。回答时把「可能原因清单 + 每一步看什么指标」讲出来，比只说「查日志」有说服力。
