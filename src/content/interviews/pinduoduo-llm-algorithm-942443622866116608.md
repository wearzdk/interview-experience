### 《面试题目》

1. 模型引入内化机制的核心设计目标是什么？只是为了省上下文 token 吗？
2. 长期对通用知识做内化迭代，会不会累积知识偏差，最后变成幻觉？怎么规避？
3. 相比纯外化检索、纯上下文填充，你这个内化架构除了省 token，真正的业务增益在哪？
4. 传统 RL、常规对齐已经能满足迭代需求了，你这套内化 + Agent 的新增流程，不可替代性是什么？
5. 你整套框架的 Agentic 特性具体落在哪些模块？怎么体现自主决策和任务拆解？
6. 训练流程明显耗时不均衡，算力大量压在 rollout 推理上，GPU 利用率偏低，你有优化方案吗？
7. 你设计了哪些可量化指标，验证内化带来的真实提升？
8. 抛开 token 节省和工程优化，从模型智能性和任务泛化性角度，说内化为什么必要？
9. 你这套自动化迭代框架，本质上是不是等价于自动搜参、自动调参？差异化在哪？
10. 如果让你把这个方案砍掉一半，你砍哪一半？

### 《参考解析》

**内化的目标不是省 token，而是把推理期的计算前移到训练期。** 外化检索是「每次用到就去查」，上下文填充是「把资料塞进 prompt」，内化则是让模型把稳定的知识、格式和技能固化进参数，推理时直接调用。判断什么该内化有三条标准：出现频率高、内容稳定、可验证；反之，时效性强、长尾、需要出处的事实应该留在检索侧。内化的收益是延迟低、成本可控、不依赖检索链路可用，代价是更新慢、难以追溯、容易把错误固化。所以「核心设计目标」应该表述成「在可验证的稳定任务上，用参数承载能力，降低推理期对外部上下文的依赖」，省 token 只是副产物。

**长期内化会累积偏差，因为每一轮都在用自己的输出当下一轮的输入。** 错误来源有三类：数据里的噪声、标注或奖励模型的偏好偏差、以及模型对自身生成的过度自信。缓解要把内化做成有版本的流水线：数据带来源与时间戳，训练前后跑固定 canary 集和事实一致性评测，设置回滚阈值；对高风险知识保留检索兜底和「无出处就拒答」；用新旧模型对照、人工抽检和置信度门控，避免模型崩塌式的自我强化。关键不是承诺「不出错」，而是做到「出错可发现、可回滚、可隔离」，并且让内化的知识边界可解释。

**相对纯检索的业务增益要能被度量，否则就只是架构偏好。** 可以列四类：一是延迟与成本，少一次检索往返、少几千 token；二是稳定性，检索服务抖动时仍能回答常见问题；三是行为一致性，固定格式、术语、流程不漂移；四是多步任务的成功率，内化的技能减少每步的提示负担。但每一类都要有对照：同一批 query 开或关内化、同模型同解码参数，比较任务成功率、人工修改次数、P95 延迟、单任务成本。如果只有 token 下降而成功率没变，那业务增益就只在成本侧，不要把它说成「模型变聪明了」。

**和 RL、对齐相比，内化的不可替代性在「知识与技能的写入」而不是「偏好对齐」。** RLHF 主要优化人类偏好和安全性，奖励信号是「回答好不好」；内化解决的是「模型会不会这件事、记不记得这个事实」，需要可验证的任务和稳定的数据分布。Agent 流程再提供任务拆解、工具调用和结果校验，把「一次生成」变成「可执行、可检查的轨迹」。所以差异化不该说「我们更自动」，而要说清楚：我们有一个可验证的任务集、一条能把执行结果转成训练信号的闭环、以及一套能证明泛化的评测；没有这三样，和内化、自动搜参没有本质区别。

**Agentic 特性要落到具体模块，而不是贴标签。** 自主决策体现在 Planner 根据状态选择下一步和工具，任务拆解体现在把目标变成可执行子任务与依赖图，反思体现在失败后基于错误类型重规划，记忆体现在跨轮保留约束和已验证结论。同时要有约束：可重规划的范围、不可重复执行的步骤、工具参数的 schema 校验、高风险操作的人工确认。自主性越强，越需要状态机和可观测性，否则「智能」会变成不可调试的随机性。

**Rollout 占满 GPU 是训练与推理耦合的典型问题，优化要动调度而不是只换卡。** 手段包括异步或离策略 rollout 与训练解耦、连续批处理提高解码吞吐、KV cache 分页与前缀复用、投机解码和小模型草稿、按难度分层采样并跳过已通过的样本、控制生成长度与早停、训练与推理共卡时做弹性配额。代价是 off-policy 的 staleness 会影响收敛，需要重要性修正或限制版本差；投机解码会引入接受率与正确性权衡。回答时给「吞吐—新鲜度—效果」三角，而不是只报 GPU 利用率。

**指标要区分「内化是否发生」和「内化是否有用」。** 前者看训练集外的事实召回、格式遵循、技能任务的 zero-shot 表现；后者看端到端任务成功率、人工修改率、幻觉率或无出处回答率、P95 延迟、单任务 token 成本，以及 OOD 泛化。评测要做消融（去掉内化、去掉 Agent、去掉检索）、固定随机种子与样本量、给置信区间；上线用灰度与留存、负反馈做长期验证。只报一个「提升 20%」而没有基线、分层和显著性，面试官会继续追问。

**「砍掉一半」考的是边际收益判断。** 我会先砍「广而浅」的通用知识内化和复杂的多 Agent 编排，保留可验证的任务闭环、评测与回滚、以及高频高价值的场景内化；理由是前者的边际收益低、维护成本高、错误更难发现，后者直接决定系统能不能稳定交付。判断标准可以统一成三句：不做会损失什么、做了能提升哪个指标、坏了能不能回滚。三句答不上来的模块，就是该砍的那一半。
