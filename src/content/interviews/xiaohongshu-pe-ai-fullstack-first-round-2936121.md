### 《参考解析》

**召回 95% 的设计与副作用。** 高召回通常是多路并集：关键词/BM25 精确匹配、向量召回、规则与同义词扩展、业务字段过滤，各路结果融合后取 topN，再加上阈值放宽和 query 改写。召回率高说明「该找到的基本都找到了」，但副作用是噪声进入候选，精排压力变大、误召回会带偏生成；同时阈值放宽会让长尾 query 也返回一堆弱相关内容。所以指标要成对看：召回率提升是否伴随 precision/NDCG 下降、下游答案的事实性有没有变差、平均上下文长度与延迟成本涨了多少。评估上要有分层的标注集（热门、长尾、否定式 query），不能只看一个总数。

**提升精度的措施。** 加交叉编码器重排（bi-encoder 召回 + cross-encoder 精排）、用 LLM 做相关性判定与片段筛选、按业务字段做硬过滤、对 query 做意图分类后走不同索引、给检索结果加时效与权威性权重、设置动态 topK 与相似度阈值、对重复片段做去重合并、把用户反馈（点赞点踩）回灌成排序特征。

**为什么不用向量召回。** 取决于数据形态：如果是编号、型号、错误码、人名这类精确 token，向量会把「A123」和「A132」映射得很近，反而不如倒排索引；如果语料短且领域术语多、embedding 模型没在这个领域训练过，语义召回质量会明显下降；如果要求可解释、可审计（为什么召回这条），关键词匹配的命中理由更清楚；向量检索还有额外的基础设施成本（向量库、embedding 服务、更新同步）。合理的架构往往是混合检索而不是二选一。

**LangGraph 防循环与发散。** 用图编排时显式定义状态与终止条件：给每个节点设置最大执行次数与全局步数上限、用条件边判断「信息是否足够」并在满足时走向 END、给工具调用加超时与失败重试上限、对同一工具同一参数的重复调用做去重（缓存或直接短路）、用 supervisor 模式让一个调度节点决定下一步而不是让子 Agent 自由互相调用。再加成本护栏：token/费用预算耗尽即终止，并把中断原因返回给用户。

**多 Agent 的兜底与记忆。** 兜底：每个子 Agent 有超时和异常捕获，失败时返回结构化错误而不是让整条链挂掉；关键步骤有降级路径（换模型、走规则、转人工）；写入类操作要有幂等与回滚。记忆：分短期（会话窗口）、长期（摘要或向量库）、任务态（图状态里的中间结果）。信息丢失的常见原因是上下文截断和摘要丢细节，处理办法是把关键事实结构化存下来（实体、约束、已确认的决策）而不是只存自然语言摘要，并在每轮把「当前生效的需求」显式放回上下文。

**QPS 上涨的优化顺序。** 先测量再优化：看是 CPU、连接数、慢查询还是锁竞争。手段分层——接入层限流与缓存（CDN、本地缓存、Redis）、读多写少的场景加缓存并处理一致性、数据库加索引与消除慢查询、读写分离、热点数据拆分、连接池调优、把同步调用改异步或批处理、必要时分库分表。注意缓存雪崩与击穿、以及缓存与库的一致性策略。

**索引失效的常见场景。** 在索引列上用函数或运算（`WHERE DATE(create_time)=...`）、隐式类型转换（字符串列传数字）、`LIKE '%xx'` 前置通配、`OR` 连接的条件有一侧无索引、联合索引不满足最左前缀、范围查询之后的列无法用于定位、`!=`/`NOT IN` 导致优化器放弃索引、数据区分度太低时优化器选择全表扫描、统计信息过期。判断依据是 `EXPLAIN` 的 type 与 key，而不是凭经验猜。

**低基数字段建索引。** 单列索引在性别这种只有两三个值的字段上通常没用：优化器会判断走索引回表的成本高于全表扫描，直接放弃。有效的场景是：作为联合索引的一部分且前置有高区分度列（如 `(user_id, gender)`，用于覆盖索引或排序）、配合覆盖索引避免回表、数据分布极度倾斜且查询只取极少数值（如「状态 = 待处理」只占 0.1%）、或者用于分区/位图索引。回答时把「区分度 = 不同值个数 / 总行数」这个判据说清楚。

**SDD（规格驱动开发）。** 核心是先把需求写成机器和人都能读的规格（接口、数据结构、验收条件、边界），再让 AI 依据规格生成实现与测试，人负责审规格和验收。优势：需求歧义提前暴露、生成结果可验证、文档与代码同步、返工成本低。风险：规格写得过度形式化会拖慢节奏、规格与实现漂移后失效、AI 会「按字面实现」而忽略隐含约束、评审规格的能力要求更高。

**AI 提效的评估。** 不能只看「写了多少行」。可用的指标：需求从进入到合并的周期时间、每个任务的返工轮次、代码评审意见数与缺陷密度、测试覆盖率与线上事故率、开发者主观时间分配（重复劳动占比）。最可靠的是同一批任务做对照（同样需求，用与不用 AI 各做一遍），并区分「生成快但审查慢」和「整体交付快」。

**效率损失在哪。** 读与审 AI 代码的时间、上下文准备（把项目约定讲清楚）、生成结果不符合架构需要重写、调试 AI 引入的隐蔽 bug、以及评审时的心理负担。改善：把项目规范、目录结构、示例代码固化成可复用的上下文；让 AI 先出方案再写码；用类型检查和测试做自动验收；把任务切小，一次只让它改一个文件/一个函数。

**技术分歧。** 用 STAR 讲：分歧点是什么（方案 A 快但难维护、方案 B 稳但工期长），各自依据（压测数据、线上案例、维护成本），怎么收敛（拉第三方评审、做小范围 PoC 用数据说话、按影响面拆成两期）。重点体现「对事不对人、用证据决策」。

**职业规划与 AI 时代的挑战。** 规划要具体到能力而不是职位：深入一个业务领域 + 补齐系统设计与稳定性能力 + 把 AI 工程化（评测、可观测、成本）做成专长。挑战可以讲：代码供给变多后，瓶颈转移到需求判断、系统设计与质量把关；AI 生成的不确定性要求更强的测试与可观测能力；成本与延迟成为架构约束。除了写代码，更该关注业务理解、数据与指标、系统边界与安全、以及如何把 AI 可靠地嵌进生产链路。
