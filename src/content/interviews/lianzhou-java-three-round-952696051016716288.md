### 《参考解析》

**批量查询从 1.5s 到 265ms 的归因**：面试官连问三轮「降幅来自并行还是 SQL」「单看 SQL 降了多少」「有没有优化前后对比」，考的是能不能把性能收益拆开。合理的答法是先给出分段耗时：优化前一次请求里的 N 次串行远程调用各占多少、SQL 各占多少；然后分别说明两类改动——把无依赖的远程调用改成并发（线程池 + `CompletableFuture`，注意隔离与超时），把循环里的单条 SQL 合成批量查询或 `IN` 查询（减少网络往返与解析开销）。归因时用「只上并行」和「只改 SQL」两组对照实验，或按 trace 里的 span 耗时求和，别把总降幅含糊地都算给并行。还要说明测试方式：压测工具、并发数、数据量、P50/P95，以及是否在同一环境下对比。

**并发聚合的失败处理**：远程调用并发化之后必须定义失败语义。常见做法是给每个子调用设置独立超时，用 `CompletableFuture.allOf` 加 `exceptionally` / `handle` 做降级，明确哪些字段缺失可以返回部分结果、哪些必须整体失败；超时时间要小于接口总超时，避免线程池被慢调用占满；对下游做熔断与限流，线程池按下游隔离，避免一个下游抖动拖垮全部请求。

**Full GC 治理的完整路径**：从监控发现（GC 日志或 Prometheus 的 GC 次数、停顿时间、老年代占用曲线）→ 确认是全量 GC 频繁还是单次停顿过长 → 用 `jstat -gcutil`、`jmap -histo`、堆 dump 配合 MAT 找大对象与引用链 → 定位是缓存无界、大查询一次性加载、还是对象创建速率过高 → 修复（加容量上限与过期、改分页/流式、减少临时对象）→ 验证（同样压测下的 GC 次数、停顿、老年代增长斜率，以及业务指标）。回答时把「怎么发现、怎么定位、改了什么、怎么证明有效」四段讲全，比只背 GC 算法更有说服力。

**流式输出与 500ms 聚合**：上游按 token 或小片段流式返回，下游（机器人、平台方）往往要求整段消息或固定节奏的推送，所以要在中间做缓冲聚合。500ms 是一个折中：太短会把碎片直接透传、增加下游调用与消息条数；太长会让用户觉得「分析过程不可见」、首字延迟变高。回答时要说明这个值是怎么定的（下游接口的频率限制、消息大小、用户可感知的延迟），以及聚合层如何做（按时间窗口或按句子边界 flush，结束时强制 flush 尾部）。

**线程池与核心线程回收**：`ThreadPoolExecutor` 的核心参数是核心线程数、最大线程数、空闲存活时间、工作队列、线程工厂与拒绝策略；任务提交后先看核心线程是否已满，未满则新建核心线程，满了进队列，队列满了再扩到最大线程数，仍满则执行拒绝策略（Abort、CallerRuns、Discard、DiscardOldest，或自定义）。核心线程默认即使空闲也常驻，想让它在空闲后回收要调用 `allowCoreThreadTimeOut(true)`，并把 keepAliveTime 设成期望的空闲时间；注意这会带来频繁创建销毁线程的开销，低流量场景才适合。三类业务共用一个线程池的问题是互相挤占：A 类慢任务占满队列后，B 类任务只能排队或触发拒绝，所以按业务拆分线程池并各自设容量与拒绝策略，或者用信号量做隔离。

**事务隔离级别与慢 SQL**：标准四级是读未提交、读已提交、可重复读、串行化，MySQL InnoDB 默认可重复读，用 MVCC 实现快照读、用间隙锁处理当前读的幻读。项目里选哪一级要看业务：大多数互联网业务用读已提交以降低锁冲突，依赖唯一约束与业务幂等兜底。慢 SQL 排查的顺序是：先开慢查询日志拿到具体 SQL 与执行时间，用 `EXPLAIN` 看访问类型、命中索引、扫描行数、是否 filesort / 临时表；再检查索引设计（最左前缀、区分度、覆盖索引）、SQL 写法（函数包裹列、隐式类型转换、`%like%`、大 `IN`、深分页）、以及数据量与统计信息；最后用 `optimizer_trace` 或强制索引验证，改完再压测对比。

**Lua 扣库存与一人一单**：Redis 单线程执行 Lua 脚本保证整段逻辑的原子性。脚本里依次做：校验用户是否已下单（`SISMEMBER` 或 `SETNX` 占位）、校验库存是否大于 0（`GET` 或 `DECR` 前判断）、扣减库存（`DECRBY`）、把用户写入已购集合。任何一步不满足就返回失败码，不产生部分写入。一次扣多张时把数量作为参数传入，脚本内统一判断与扣减，避免多次调用之间被插入。Redis 成功而 MySQL 失败时，靠本地消息表 / 事务消息 / 补偿任务把 Redis 的扣减回滚（把库存加回、把用户从已购集合移除），并记录流水保证可重放；也可以改成先落 MySQL 再删缓存，或用 Redis 做预扣、MySQL 做最终账本并定时对账。

**括号匹配与 Deque**：用栈保存尚未匹配的左括号，遇到右括号时检查栈顶是否为对应的左括号，遍历结束后栈必须为空。用 `Deque<Character>` 而不是 `Stack`：`Stack` 继承自 `Vector`，所有方法加 `synchronized`，单线程场景下有额外开销，且它的迭代顺序与栈语义容易混用；`Deque` 接口的 `push/pop/peek` 语义清晰，`ArrayDeque` 基于循环数组、无锁、性能更好。面试官追问「为什么更倾向 Deque」就是考这一点。

**可重入分布式锁**：核心是用一个 Hash 保存「锁持有者标识 → 重入次数」，`tryLock` 时用 Lua 原子地判断 key 是否存在：不存在则写入 `{owner: 1}` 并设过期；存在且 owner 是自己则 `HINCRBY` 加一；否则失败。`unlock` 同样用 Lua：owner 不匹配直接返回失败，匹配则计数减一，减到 0 删除 key。并发安全靠 Redis 单线程执行脚本；过期时间用 `PEXPIRE` 每次重入时刷新（看门狗），并记录过期时刻用于判断。要说明单点 Redis 在主从切换时可能丢锁，强一致场景需要 fencing token 或 RedLock 之类的方案。

**共识算法与「换跳板机」追问**：这类问题考的是方案边界。如果扣分机制基于节点 ID 或固定 IP，攻击者更换跳板机确实能绕过，说明信任模型建立在可伪造的身份上；正确的方向是把惩罚绑定到可验证的行为凭证（签名、押金、共识层的投票记录）而不是网络位置，或者用准入控制与信誉体系抬高攻击成本。回答时先承认边界，再给出改进方向，不要硬说「防得住」。

**三面综合题**：「和 AI 磨合」要落到具体做法——如何写清约束、如何验证 AI 产出、哪些环节交给人复核；「最难的挑战」用 STAR 讲一个能说清取舍与结果的问题；「重复 @ 提问者」这类细节题是在验证经历的真实性，如实说明记忆 / 状态是怎么存的、为什么会重复触发、后来怎么修。
