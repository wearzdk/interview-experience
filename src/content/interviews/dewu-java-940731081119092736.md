### 《参考解析》

**ReAct 与 Plan-and-Execute**：ReAct 是「想一步、做一步」——模型输出思考加动作，拿到工具结果后再进入下一轮，好处是灵活、能根据中间结果转向，代价是每一步都要一次模型调用，长任务容易绕圈且总延迟高。Plan-and-Execute 是先把任务拆成完整计划再逐步执行，方向感强、可以并行、能提前评估代价，但计划一旦基于错误假设就会整体跑偏，需要能重规划的机制。实践里常做混合：高层用计划保证不跑偏，每一小步内部用 ReAct 保证灵活。判断标准很实在——任务边界清晰、步骤可枚举就走 Plan-and-Execute，环境反馈会改变目标的走 ReAct。

**意图识别怎么做**：轻量做法是规则加小模型分层：先关键词和正则拦掉高频明确意图，再用一个小的分类模型（或者 embedding + 向量检索召回相似问法 / 聚类原型）做粗分类，只有低置信度的那部分才交给大模型仲裁，这样能同时拿到成本和准确率。评测要分别算「分类准确率」和「仲裁调用率」，后者决定成本；评测集要分层抽样、覆盖长尾，样本少的时候用交叉验证、或者人工构造对抗样本扩增，别只看一个总体准确率。上线后要拿真实流量的 badcase 回流迭代，并保留人工兜底。

**AI 代码质量怎么保证**：重点不在「让 AI 别写错」，而在「写错了能拦住、范围可控」。工程上有几层：把任务粒度切小、一次只改一个明确的点；改之前先让它给设计方案，人确认后再动手；用 lint、typecheck、单测当硬闸门，不过就不合并；限制改动范围（先约定要改的文件，diff 超出就人工介入）；小步提交、方便回滚。测试本身也要防「同源作弊」——AI 写的测试常常断言偏弱，所以要问清覆盖了哪些分支，关键路径补上人工写的验收用例。TDD 是先写测试再写实现、以测试驱动设计；SDD 在团队里通常指先写规格 / 设计文档再实现，AI 时代它的价值反而更高，因为规格是给模型的最强约束。

**泛型与擦除**：Java 泛型的直接来源是 C++ 模板和集合框架的类型安全需求，JDK 5 引入，解决的是「取出来还要强转、类型错误要到运行时才炸」的问题。它的优势是编译期类型检查、省掉强制转换、提高代码复用（一套集合类服务所有类型）。擦除的由来是兼容性：为了不破坏已有字节码，泛型信息只存在于编译期，运行时 `List<String>` 和 `List<Integer>` 是同一个类。带来四个后果：运行时拿不到泛型实参（所以 RTTI 里看不到，需要用 `TypeReference` / `ParameterizedType` 绕）；不能 `new T()`、不能建泛型数组；静态成员不能用类的类型参数；重载时 `method(List<String>)` 和 `method(List<Integer>)` 签名冲突。桥接方法是编译器为擦除后多态生成的补充手段。

**RAG 准确率怎么提升**：这一段最好按链路拆开答。离线侧：文档解析要保结构（表格、标题层级别丢），切分按语义而不是硬切固定长度，chunk 加标题上下文与元数据，入库时做去重和清洗。检索侧：query 改写（多路改写、HyDE、指代消解）、混合检索（BM25 关键词 + 向量语义）互补、加 rerank 模型精排、按元数据过滤缩小范围。生成侧：把引用片段贴上、约束「只依据上下文回答」、上下文太长时做压缩而不是硬塞。评测要能定位问题：把「检索失败」和「生成失败」分开算，用带标注答案的评测集看召回率、MRR、忠实度。至于「有些问题答得准、有些不准」，最典型的三个原因是：知识库里根本没有这条内容（应该拒答却硬答）、chunk 切得让关键信息跨块断裂（召回不完整）、以及问题涉及跨文档多跳推理（单次检索拿不到全部证据）。作者这轮面试的落点就在这里：面试官要听的不是「我用了向量库」，而是能不能定位到具体环节。

**这轮的复盘**：面试官完全不问八股，全部围绕简历与项目追问，属于典型的「深度面」。这种面试挂人的原因往往不是知识点不会，而是项目讲不出深度——产出是什么、谁在用、量级多少、你独立解决了什么。准备方法是把简历上每个关键词都准备到能往下讲两层，并且准备好「最近半年钻研最深的一件事」这类需要真实沉淀的问题。作者最后提到道心破碎、缓了两天才写面经，其实这类反馈本身就是信号：项目深度不够时，先把一个真实的小系统做透，比铺开三个浅项目更有用。
