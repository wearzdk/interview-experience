### 《面试题目》

1. 自我介绍（一分钟）。
2. 为什么是三级架构，主 Agent 直接调工具不行吗？编排层本质上是人工写的路由表吗？
3. 编排层单独做成一个 Agent，代价是什么？为什么不用规则路由，长尾占比多少？
4. 上下文从主 Agent 传到子 Agent，怎么保证不丢？slot 谁定义的，新场景来了怎么办？
5. 上下文太长怎么裁？抽取本身用模型，模型抽错了呢？校验错了呢？
6. 工具 schema 写多细、description 多长？两个工具名字很像、语义不同，模型老选错怎么办？
7. 工具升级、参数加了必填字段，历史会话怎么办？模型怎么知道该用哪个版本？
8. 工具调用超时，重试几次？重试时幂等怎么保证？
9. 参数哈希里有一个时间戳字段每次都变，幂等键就失效了怎么办？排除易变字段会不会撞键？
10. 高危操作（退款、改价、发券）怎么拦？二次确认是人点还是模型点？一天两万单人点得过来吗？
11. 权限模型怎么做的，RBAC 还是 ABAC？Agent 以谁的身份调工具，越权怎么防？
12. Agent 越权有哪几种，你防住了哪几种？跨用户把 A 的结论用到 B 身上怎么防？
13. Prompt injection：用户让 Agent 忽略之前指令怎么防？文档里藏一句注入呢？
14. 子 Agent 返回的结论，你怎么知道是对的？抽样比例多少，发现问题怎么回溯？
15. 评测集怎么造、多少条、覆盖哪些场景？回流数据有偏吗？
16. 上线怎么灰度、看什么指标？成本怎么算，一次任务多少钱？毛利多少？
17. 延迟 8 秒用户等不了，怎么优化？并发工具调用会不会让工具侧压力翻倍？
18. 这套东西如果明天让你重写，你会改哪？
19. 手撕：工具调度器。给一批工具，每个工具有依赖列表和并发配额，按依赖顺序执行、不超过总并发上限，返回每个工具的结果，要求处理环检测和单个工具失败时的下游跳过。

### 《参考解析》

**三级架构的价值与代价。** 分层编排的核心收益不是「更智能」，而是缩小候选集：四十多个工具的 schema 一次塞进上下文，工具描述本身就占几千 token，模型的选择准确率会明显下降；先由主 Agent 选「域」，再由域内编排层选具体工具，等于把一次四十选一拆成两次小规模选择。面试官点破「这层本质是路由表」是准确的——如果这层只做静态映射，那它的价值就限于候选集裁剪与权限边界。代价也很实在：多一跳带来数百毫秒延迟、上下文在层间传递会有损耗、每层都要单独评测与维护。规则路由与模型路由的取舍应按长尾占比算账：如果九成请求能被规则覆盖，用规则处理大多数、模型只兜长尾，成本与延迟都更低；模型路由适合意图分布长尾且变化快的场景。回答这类问题要能给出量化的账，而不是只说「更灵活」。

**上下文传递的关键是契约而非容器。** 用结构化 slot 传递只是形式，真正要解决的是「谁定义、怎么演进、丢了怎么发现」。可行的做法是把 slot 定义成版本化的 schema（字段、类型、必填、来源），主 Agent 填、子 Agent 只读，新增场景时扩展 schema 而不是改代码；同时每个 slot 带来源标记（来自用户原话、来自工具结果、来自模型推断），下游可以据此判断可信度。防止丢失要靠契约测试：对每个 slot 构造「必填缺失」「类型错误」「超长」的用例，验证子 Agent 会明确报错而不是静默用空值继续。新场景来了如果 slot 不够用，正确做法是让子 Agent 返回「缺什么信息」并回问，而不是让主 Agent 猜。

**工具 schema 与工具选择。** 工具描述不是越长越好。模型对工具的选择依赖名称、一句话用途与参数名，描述过长会稀释关键信息、增加 token 成本，也会让相似工具更难区分。经验做法是：名称用「动词 + 对象」且语义唯一，描述控制在一两句话内说清「什么时候用、什么时候不用」，参数给类型、枚举与一个最短示例，把长篇说明放到工具返回的错误信息里按需暴露。两个工具容易混时，最有效的是改名与合并（把相似能力合成一个带 `mode` 参数的工具），其次是在描述里写反例。改名的代价是历史 prompt 与评测集要同步更新，所以要建立工具注册表与版本号：注册表里同时挂 v1/v2，工具描述里带版本，历史会话按会话开始时冻结的工具表执行（这与多轮缓存的设计一致），新会话用新版本。工具参数加必填字段属于破坏性变更，应当新版本 + 迁移期双版本并存，而不是原地改。

**幂等键的设计。** `trace_id + 工具名 + 参数哈希` 的方向是对的，问题在于参数里含时间戳、随机数、分页游标这类易变字段。处理原则是「先规范化再哈希」：对参数做规范化（字段排序、去掉已知易变字段、时间戳截断到业务可接受的粒度、浮点归一化），并且幂等键要以业务实体为主键而不是以请求为主键——退款用订单号 + 金额 + 操作类型，改价用商品 ID + 目标价，这样即使参数里带了时间也不会撞。排除易变字段导致不同请求撞键的风险，用「业务主键 + 操作类型」自然规避；真正无法确定业务键的场景，才退化为参数哈希并在服务端做冲突检测（键相同但参数不同则报冲突而不是静默复用）。幂等键要在进入重试之前生成一次并透传，重试时复用。

**高危操作与越权。** 高危操作的多层拦截是合理的（模型层禁止、编排层白名单、执行层二次确认），但「人点」在日均两万单的量级上不可行，实际应按风险分级：低金额、低影响的操作走自动化 + 事后审计，高金额、不可逆的操作走人工审批或延迟执行窗口（例如给用户 5 分钟撤销期）。权限上，Agent 不应以系统身份无条件调用工具，而应携带「用户身份 + 代理授权范围」的双重凭证，工具侧做数据行级过滤（只能读写该用户或该租户的数据）。越权的类型至少四类：调用未授权工具、拿到越权数据、伪造身份、把 A 用户的结论用到 B 用户身上。第四类最隐蔽，防护靠「结果归属校验」：子 Agent 的返回必须带 tenant/user 标记，编排层在合并结论时校验归属，跨用户复用直接拒绝。Prompt injection 的防护是分层的：输入侧检测明显指令、系统提示与用户内容隔离、工具返回内容标注为「数据」而非「指令」、高危操作强制走二次校验；但必须承认文档内嵌注入无法完全防住，所以防线要放在「即使被注入也做不了危险动作」上，即最小权限与审批，而不是靠提示词。

**评测集、灰度与成本。** 评测集的结构应是「人工构造 + 线上回流 + 对抗样本」三层，人工部分保证覆盖意图与边界，回流部分保证贴近真实分布，对抗部分专门覆盖注入、越权、超长上下文。回流数据天然有偏（都是出过问题的），所以要按线上流量分布做重加权，并保留一批「从没出过问题」的常规样本做回归。灰度看四类指标：任务完成率、平均轮次、人工接管率、P99 延迟，同时看单位任务成本。成本估算要拆输入与输出：平均轮次 × 每轮上下文 token × 单价，工具调用与重试另计；毛利要算上人工接管与失败重试的成本，只报单次调用成本会低估。

**工具调度器的手撕要点。** 结构上分三部分：依赖图（邻接表 + 入度）、就绪队列（入度为 0 且配额允许）、资源账本（每个工具声明的并发配额与全局并发上限）。执行循环是「取出就绪工具 → 申请配额 → 提交执行 → 完成后释放配额、把下游入度减一」。环检测用拓扑排序的剩余节点数判断，剩余不为 0 即存在环，应报错而不是死等。面试官提示的「把等待和执行分开」正是死锁的解法：如果父工具占着配额等子工具，而子工具又在等配额，就会互相卡死；两阶段做法是先只做依赖解析与配额预留（不占用执行槽），再统一提交执行，或者把「等待子工具」的父任务从配额账本中释放、只保留逻辑依赖。单个工具失败时，下游直接标记为 skipped 并向上传播原因，不要让它一直等依赖。

**如果重写会改哪。** 一个诚实的回答是「砍掉不必要的编排层，改成规则 + 小模型分类」：如果九成请求能规则命中，多一层的延迟与维护成本就不划算。判断标准是长尾占比与规则覆盖率的变化趋势——长尾在缩小就继续用规则，长尾稳定且规则维护成本上升才值得上模型编排。
