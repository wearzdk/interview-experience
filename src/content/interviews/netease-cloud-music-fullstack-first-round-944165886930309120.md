### 《参考解析》

**「一条消息发出去 Agent 如何响应」是 Agent 岗的核心题，要把一次请求拆成可观测的步骤。** 完整链路是：消息进入 → 组装上下文（系统提示、历史、工具定义、检索结果）→ 调模型 → 模型返回文本或工具调用 → 执行工具（带超时、重试、权限校验）→ 把工具结果回填到上下文 → 再次调模型 → 直到模型输出最终答案或达到步数/时间上限。每一步都要能说出「这里可能出什么问题、怎么兜」：上下文超长要裁剪或摘要、工具失败要区分可重试（网络）与不可重试（参数错）、模型反复调用同一工具要检测死循环并中断、整轮要有总超时。面试官问这题想确认的不是你会不会调 API，而是你有没有真正跑过一条生产链路。

**harness、hook、MCP、记忆这四件套，答清各自的职责边界。** harness 是「执行器」——负责把模型的意图变成真实的进程/文件/网络操作，提供沙箱、权限、超时与日志；hook 是「生命周期钩子」——在工具调用前后、会话开始结束、上下文压缩时插入自定义逻辑，常见用途是审计、脱敏、注入额外上下文、拦截危险操作；MCP 是「工具与资源的接入口协议」——把外部系统（数据库、内部 API、文件系统）以标准化的 server 形式暴露给模型，好处是工具实现与模型解耦、可跨客户端复用；记忆分短期（上下文内的对话）与长期（落库的事实、偏好、历史任务），长期记忆的关键是「什么时候写、什么时候读」——按重要性打分写入、按语义检索读出，而不是把所有历史都塞回上下文。

**上下文工程与 multi-agent 要落到「为什么拆」。** 上下文工程解决的是「有限窗口里放什么」：系统提示要短而硬（角色、约束、输出格式），历史做滚动摘要，检索结果按相关性截断并带来源，工具定义按当前任务动态加载（工具太多会显著拉低选择准确率）。multi-agent 的常见形态是「 orchestrator + 子 agent」，拆分的理由通常是：任务阶段差异大（规划 vs 执行 vs 校验）、上下文需要隔离（子 agent 只看自己那部分，避免互相污染）、以及并行（多个子任务同时跑）。代价要主动说：多一跳延迟、错误会跨 agent 传播、调试变难、成本翻倍。所以判断标准是「单 agent 加工具是否真的做不好」，而不是「多 agent 更高级」。

**RAG 答成一条数据流，别只背定义。** 离线侧：文档切分（按语义而非固定长度）、向量化、入向量库并保留元数据（来源、时间、权限）；在线侧：query 改写（把口语问题变成检索友好的表达）→ 召回（向量 + 关键词混合检索，纯向量对专有名词不敏感）→ 重排（cross-encoder 或规则）→ 裁剪进上下文 → 生成并要求引用来源。工程上的关键点是评测：准备一批「问题 + 标准答案 + 应命中文档」的集合，分别看召回率与最终答案正确率，否则调参全靠感觉。项目里如果只是「把文档塞进提示词」，就如实说是长上下文方案而不是 RAG。

**「怎么防止 Claude 封号」这类问题，考的是你对账号与出口的理解。** 实际影响封号的因素通常是：出口 IP 的纯洁度（机房 IP、频繁跨国切换最危险）、并发与请求节奏（短时间大量请求像脚本）、多账号同 IP、以及支付方式异常。工程上的做法是固定出口（住宅或稳定专线）、控制并发与退避重试、把重试与限流做在客户端、避免多账号共用一条出口。这类问题没有标准答案，能说出「哪些行为会触发风控、我怎么把它做成稳定可控」就够，不要给具体的规避教程。
