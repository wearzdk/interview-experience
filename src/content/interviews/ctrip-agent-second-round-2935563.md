### 《面试题目》

1. 简单做一下自我介绍。
2. 介绍一下 Agent 项目的场景。
3. Agent 内部做了领域路由，如果路由模型分错、语义模糊的问题被误分到别的领域，是不是就无法挽回？
4. 怎么发现 Agent 的准确性问题、做问题归因分类？
5. 如果要把 badcase 发现、排查流程进一步自动化，可以在哪些点做优化？
6. 这个项目里 workflow 和 Agent 循环是怎么分工的？
7. Agent 可以调用哪些工具？工具是谁开发的？
8. 外部 API 封装成 Agent 可调用工具，需要做哪些封装工作？
9. Agent 经常只定位到表层原因，怎么深挖根因？
10. Agent 依赖的故障库不完善时怎么处理？Agent 能不能自己调用工具排查？
11. Agent 的 skill 是按照什么粒度划分的？
12. Agent 线上能独立解决多少比例的性能问题？是否需要人工复核？人和 Agent 结论有分歧怎么处理？
13. 项目 2 为什么要用多 Agent 架构？
14. AI 领域更新很快，你的自学方式是什么？
15. 最近关注哪些新模型/架构？有没有上手尝试落地？
16. 对比过其他 Agent 框架，为什么选择 LangGraph？
17. 你还有什么想问的？

### 《参考解析》

这场面试的题全是「你做的系统在真实环境里靠什么不出事」，非常适合作为 Agent 工程的复习清单。

路由误分能不能挽回：能，前提是别把路由做成不可逆的分叉。做法是分流后保留「重路由」出口——下游在证据不足或置信度低时可以把控制权交回路由层，附上失败原因与已收集的信息；同时路由本身要输出置信度与候选领域，低置信度走澄清提问而不是硬选。这样误分只是多一次往返，不是最终错误。

发现准确性问题靠三层：线上埋点（每次请求的意图、工具调用、结果、用户反馈/纠正）、用户显式反馈与人工巡检抽样、离线评测集回归。归因分类最好先定一套固定标签（路由错、检索错、工具参数错、工具执行失败、生成幻觉、知识缺失、用户表述歧义），这样每周的 badcase 才能统计出分布，优化才有优先级。

自动化排查的抓手：把每次请求的全链路产物留痕并可回放、对重复出现的失败模式做聚类、对可自动判定的错误（工具报错、参数校验失败、空结果）直接打标签、把典型 badcase 沉淀成评测用例。人只需要看「新型失败」。

workflow 与 Agent 循环的分工是这类系统的设计核心：确定性的步骤（鉴权、取数、格式化、写库）交给 workflow，需要判断和探索的部分（要不要查、查什么、结论是什么）交给模型循环。这样既有可预测性又不失灵活，也便于逐步扩大模型负责的范围。

工具封装那题要说清「接口 ≠ 工具」：要给模型看的名字与描述（什么时候用、不要什么时候用）、参数 schema 与枚举、必填与默认值、返回结果的裁剪与结构化错误、幂等与超时、权限与审计。外部 API 常见的坑是返回体太大、错误码语义不清、分页要模型自己翻——这些都要在封装层处理掉。

「只定位到表层原因」是 Agent 做运维/排障的通病：解法是强制多跳证据链（每个结论必须挂一条可验证的观测，如日志片段、指标曲线、命令输出），并要求模型在给出结论前回答「还有什么可能」；不确定就继续调工具，而不是猜。

故障库不完善时，正确方向是「让 Agent 会查」而不是「等库补全」：给它通用排查工具（查日志、查指标、查配置、查变更历史）与检索入口，把故障库当成加速器而不是唯一知识源。

skill 的粒度按「一类任务一个 skill」划，而不是按单个 API：一个 skill 应当包含触发条件、步骤、常用命令与判据，粒度太细会互相重叠，太粗则无法复用。

线上独立解决比例与人工复核是必须诚实回答的运营指标：给出你统计的口径（按工单数还是按问题类型）、复核策略（新类型全复核、成熟类型抽样）、以及分歧处理（人工结论回灌成评测用例与知识，定期统计一致率）。这部分答得越具体，越像真运营过一个系统。

多 Agent 架构的理由通常是「职责与上下文隔离」：不同子 Agent 有各自的工具集与提示词，避免一个巨型 prompt 里工具互相干扰；代价是通信成本与错误传播，需要明确的消息协议与总控。LangGraph 的选型对比可以说清它相对链式框架的优势（图结构、状态、可恢复、人工介入），以及相对其他方案的取舍。

自学方式与关注新模型那两问，重点不是报菜名，而是展示「你怎么判断一个东西值不值得用」：先在沙箱里做最小验证，跑一组自己的评测用例，再决定是否引入。
