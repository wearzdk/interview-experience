### 《参考解析》

**缓存 Key 设计**：Key 要有命名空间、业务标识、版本和维度，例如 `业务:对象:ID:版本`，避免不同环境/租户串 key。用 MD5 是为了定长、隐藏原始参数、降低超长 key 的存储和网络开销，也方便分片；代价是可读性差、有碰撞概率（工程上可忽略，但敏感场景要加盐或改用 SHA-256）。不是所有 key 都要预缓存，按需加载 + 空值缓存 + 布隆过滤器更常见；容量按热点数据量、平均 value 大小、命中率和内存上限估算，配合 TTL 和淘汰策略。

**Caffeine 与 LFU**：Caffeine 用 ConcurrentHashMap 存数据，读缓冲和写缓冲批量更新访问记录，淘汰策略是 W-TinyLFU：先用频率草图（Count-Min Sketch）做准入，再用 LRU 窗口和分段 LRU 维护主空间，兼顾命中率和内存。LFU 按访问频率淘汰，低频新数据容易被饿死，所以 Caffeine 用窗口 + 频率草图缓解。是否需要维护每个 key 的访问次数？精确计数内存开销大，近似计数更划算。

**事务消息**：RocketMQ 事务消息解决「本地事务和发消息」的原子性：先发半消息，Broker 暂不投递；执行本地事务后提交或回滚；Broker 回查本地事务状态，防止生产者宕机导致消息悬空。用 MQ 而不是同步状态变更，是为了解耦、削峰、异步补偿和最终一致；代价是延迟、重复消费和运维复杂度。消费者必须幂等。

**两数相加**：链表逆序存储，双指针逐位相加，`sum = x + y + carry`，当前位 `sum % 10`，`carry = sum / 10`；循环结束后如果 `carry` 不为 0，再补一个值为 1 的节点。边界是两条链表长度不同、全 9、空链表。
