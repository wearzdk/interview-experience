### 《参考解析》

**1. 工具调用的底层原理**。模型本身不会执行任何东西，所谓 function calling 是一次「约定格式的文本生成 + 宿主程序执行」的闭环：调用前把可用工具的名称、用途描述和参数 JSON Schema 一并放进请求；模型决定调用时，输出的不是自然语言而是结构化的调用意图（工具名 + 参数），宿主程序解析并做参数校验（类型、必填、范围、权限），校验通过才真正执行，把执行结果作为一条 tool 角色的消息回灌给模型，模型再基于结果继续推理或给出最终答复。因此能被模型「调用」的前提是三件事写清楚：工具描述要说明「什么时候用、什么时候别用」，参数 schema 要有枚举和边界，返回值要精简（几 KB 的工具输出会迅速吃满上下文）。编排多次调用有两种形态：一种是 ReAct 式边想边做，路径动态但容易绕路；另一种是先规划出调用序列再逐步执行（或把无依赖的调用并发发出），可控、可审计、延迟低，适合流程固定的场景。工程上必须有的护栏是最大调用步数、单步超时、失败重试上限，以及写操作（下单、发消息、改配置）的幂等键与人工确认开关。

**2. 多 Agent 协作：通信、确定性与适用场景**。单 Agent 适合工具数有限、步骤线性的任务，省 token 也好调试；多 Agent 在两类场景才划算——上下文需要隔离（不同角色各持有大段不同的资料，塞进一个上下文会互相冲淡）和职责需要互相校验（执行与审核分离能显著降低同源偏差）。中心式（一个 Orchestrator 调度若干 Worker）结构简单、全局状态好管、易于观测，缺点是调度器容易成为瓶颈与单点，且它对每个子任务都要有足够理解；分布式（Agent 之间点对点协商、或用黑板/消息总线共享状态）扩展性好、能并行，但全局状态难以收敛，调试困难，还会出现「两个 Agent 互相等对方」或反复扯皮的活锁。让通信结果明确且可验证的做法是不让 Agent 用自由文本对话：每个 Agent 的输入输出都按固定 schema（Pydantic / JSON Schema）定义，字段有类型与枚举约束，宿主程序做 schema 校验，不合法就带错误信息打回重试；跨 Agent 传递的是结构化产物（任务单、草稿、审核意见、证据 id），自然语言只作为其中的说明字段。降低自然语言不确定性还有几招：把「结论」和「理由」分开字段，结论用枚举或布尔，理由才自由文本；用有限的共享词汇表（任务状态机只有 pending/running/blocked/done）；用确定性代码做路由和状态流转，只在需要判断的地方调用模型；交接时要求给出证据引用（哪个文件、哪一行、哪条检索结果），没有引用一律视为无效产出。

**3. 记忆系统的分级与自动沉淀**。按生命周期分三层：工作记忆就是当前上下文窗口，实现上是消息列表加裁剪策略，回答完即弃；短期/会话记忆是本次会话跨轮次的信息，通常落在会话状态对象或 Redis 里，会话结束归档；长期记忆跨会话存在外部存储，回答「这个用户是谁、之前遇到过什么」这类问题。长期记忆的技术形态有两种：一种是结构化事实（用户偏好、常用参数、历史结论），写进关系库或 KV，读取时按用户 id 直接查出拼进 prompt，准确、便宜、可控；另一种是向量化记忆，把交互片段 embedding 后入库，按当前问题做相似检索召回，覆盖面广但会引入噪声。写入策略才是难点：不是每轮对话都值得记，通常用规则（用户显式说「记住」、出现稳定偏好、任务结论）加模型抽取（让模型输出「值得长期记住的事实」的结构化清单）双通道，写之前先做去重与冲突检测——新事实与旧事实矛盾时要么覆盖要么保留时间戳，否则记忆会自相矛盾。自动沉淀可以做，但必须可查看、可编辑、可删除，否则一旦沉淀了错误结论，后续所有会话都会被污染，而且用户无从纠正。

**4. Agent 自主改代码与领域知识衔接**。Agent 做代码修改的可靠形态不是让它直接改主分支，而是「定位 → 生成补丁 → 验证 → 提交」：先用检索（代码搜索、符号索引、调用图）定位相关文件与函数，让模型输出结构化补丁（unified diff 或明确的文件与替换块），宿主程序做语法解析与编译检查，再跑单测与静态检查，最后才落到分支上并生成 PR 供人 review。验证这一环是分水岭：没有测试的项目要先补一个能跑的最小验证（编译通过 + 关键路径的 smoke test），否则「改完了」没有任何客观依据。领域知识衔接有两条路，实际应该组合用：从代码反向总结（读现有实现、README、接口定义，提取出业务规则与约束）成本低、跟代码同步，但覆盖面受限于代码里写得清的部分，隐含约定和线上踩坑经验抽不出来；额外搭知识库（把需求文档、设计评审、运维手册、历史事故复盘入库做 RAG）覆盖广、能沉淀非代码知识，代价是要维护、会过期。合理的分工是：接口与数据结构以代码为唯一事实来源，业务流程与边界规则放知识库，二者冲突时以代码为准并在回答里标注冲突点。MCP 的定位是把外部能力（知识库、SQL、内部 API、工单系统）以统一协议暴露给 Agent，让工具接入与模型解耦；Skill 的定位是封装「一类任务怎么做」的流程与提示词资产，可复用、可组合、可版本管理。两者都接上之后，系统的复杂点从「模型不够聪明」转移到状态与编排：工具数量一多，选错工具、参数填错、多工具结果互相矛盾、上下文被工具输出撑爆，以及权限与审计（Agent 用谁的身份查了哪张表、动了什么数据），这些都要靠显式契约、结果校验和可观测来治。

**5. 反复澄清需求时的上下文管理**。多轮澄清会让消息列表线性膨胀，必须主动管理。可用的组合拳是：把「已经确认的需求」从对话里抽出来，固化成一份结构化的需求状态（目标、约束、已确认项、待确认项），每轮只把这几十行状态 + 最近几轮原文送进模型，历史消息归档进存储；重复澄清是重要信号——如果同一个问题被问第二次，说明状态里没有正确落地上一轮的答案，要检查抽取逻辑而不是继续追问用户；对超长会话按 token 水位触发滚动摘要，摘要中保留决策与理由、丢弃过程性寒暄；必要时用检索式记忆，把用户很早前提过的细节在需要时召回。另外要给会话设一个明确的出口：需求确认到可执行的程度就产出结构化任务单并让用户确认，避免无限追问把用户和 token 一起耗掉。

**6. 手撕：二叉树的最近公共祖先**。思路分两种。递归解法（推荐，代码短且不易错）：函数语义定义为「在以 root 为根的子树中寻找 p、q 的 LCA」，若 root 为空或等于 p 或 q 则返回 root；递归左右子树得到 left 与 right；若左右都非空，说明 p、q 分居两侧，当前 root 就是 LCA；若只有一侧非空，就把那一侧的结果往上返回。时间复杂度 O(n)，空间复杂度是递归栈 O(h)。迭代解法是先用哈希表记录每个节点到父节点的映射，再从 p 往上走到根记录路径，最后让 q 往上走，遇到的第一个在路径中出现的节点就是 LCA。面试时值得主动说的边界：p 或 q 不在树中、p 就是 q、树退化成链表导致递归深度过大（此时迭代或加显式栈更稳），以及如果是「二叉搜索树的 LCA」可以不用递归——利用大小关系从根往下走，两个值都小于当前节点就往左，都大于就往右，分裂点即 LCA，复杂度同样是 O(h) 但常数更小。
