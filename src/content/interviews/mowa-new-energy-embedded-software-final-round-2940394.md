### 《参考解析》

**C 与 C++ 的取舍要看团队、工具链与失效代价。** C 的优势是语义透明、编译产物可预测、工具链成熟、几乎任何芯片都有编译器，运行时不需要异常、RTTI 与全局构造，代码体积和栈使用容易估算；代价是抽象能力弱，资源释放靠手工，接口靠约定，大型项目容易退化成全局状态与宏。C++ 提供 RAII、类型安全、模板与编译期计算、命名空间与更强的抽象，能在不牺牲性能的前提下把资源生命周期交给编译器；代价是语言复杂度高、编译变慢、二进制增大、ABI 与工具链兼容性更麻烦，异常与 RTTI 在嵌入式中通常关闭，随之失去部分标准库能力。实际项目中常见组合是：驱动与中断层用 C，业务与状态机用 C++ 的零开销抽象（`constexpr`、模板、强类型枚举、RAII 封装外设句柄），并约定不用堆、不用异常、不在热路径用虚函数。回答「使用感受」时，落到「哪种失效模式更不能接受」比争论语言优劣更有说服力。

**嵌入式的设计模式以状态机、观察者和策略最常用。** 状态机适合协议解析、设备上下电流程、故障恢复：把状态、事件、动作、迁移条件列成表，用一个 `switch` 或函数指针表驱动，状态迁移图同时可作为测试覆盖的依据；比嵌套 `if/else` 更容易审查，也能避免漏掉异常事件。观察者适合传感器数据分发、按键事件、告警通知：发布者维护回调列表，订阅者注册与注销，双方解耦；要明确回调在中断还是任务上下文执行，中断里只投递事件，耗时处理放到任务。策略模式用一组函数指针或接口实现可替换的算法（不同传感器、不同通信链路、不同控制律），避免在业务里堆条件分支。其他常见的有单例（管理唯一硬件资源，注意多线程初始化）、工厂（按型号创建驱动）、命令（把硬件操作排队串行化）、以及 C++ 的 RAII 守卫。模式的判断标准是它是否降低了耦合与出错面，而不是是否出现在设计模式教材里。

**MQTT 云端认证要同时解决「设备是谁」和「能访问什么」。** 最基础的是 `clientId` 加用户名密码，broker 侧查库或接认证服务；密码不能硬编码在固件里，通常一机一密，出厂时写入唯一密钥或安全芯片。更常见的是在 TLS 之上做认证：客户端校验服务端证书，服务端可选校验客户端证书（双向 TLS），证书里带设备身份；或者用设备三元组（产品 ID、设备名、设备密钥）向平台换取短期 token，再以 token 作为 MQTT 密码，token 过期后重新申请。平台侧还要做 ACL：限制设备只能发布自己的上行主题、只能订阅自己的下行主题，禁止通配符越权；对连接频率、消息速率、payload 大小做限制，防止被拿去做放大攻击。安全工程上要注意证书轮换与吊销、时间同步（否则证书校验失败）、防重放（时间戳加随机数）、以及密钥不落日志。排查连接失败时按顺序看：网络与 DNS、TLS 握手、clientId 冲突（会把前一个连接踢下线）、用户名密码或 token、ACL 拒绝，broker 日志通常能直接给出拒绝原因。

**通信协议的选择要按层级拆开看。** 现场层常见 UART/RS485 上的 Modbus RTU、CAN 上的自定义协议或 CANopen、SPI/I2C 连接板内器件；网关层做协议转换与数据清洗；云端接入常用 MQTT，配置下发与文件传输可能用 HTTP，资源极受限时用 CoAP。判断依据是距离、节点数、实时性、可靠性与生态：CAN 适合多节点、短报文、有仲裁与错误恢复的车载与工业控制；RS485 加 Modbus 适合低速、少量寄存器的传感器网络；MQTT 适合广域、弱网、一对多分发。设备部署则要回答「跑在什么硬件、装在哪里、怎么升级」：是现场网关、边缘盒子还是电池管理系统的主控板，镜像是烧录还是 OTA，是否有 A/B 分区与回滚，断网时能否本地自治，现场掉电后能否恢复。能把这些讲清楚，说明候选人真的到过现场，而不是只写过 demo。

**技术文档的核心是让接手的人能独立完成部署与排障。** 一个完整项目通常有需求规格、系统架构与模块划分、接口控制文档（ICD，定义报文格式、字段、周期、超时与错误码）、通信协议说明、硬件接口与引脚定义、测试计划与测试报告、部署与运维手册、版本发布说明与变更记录。核心章节包括：系统边界与外部依赖、关键时序（上电、握手、故障恢复）、数据结构与状态机、异常处理与降级策略、资源占用（Flash、RAM、CPU、带宽）、以及已知限制。文档不是写完就结束，接口变更要同步版本号与兼容性说明，测试报告要能追溯到需求条目。团队分工上，按模块边界划分比按人划分更稳：驱动、协议、业务、测试各有 owner，接口先定再并行开发，联调阶段用日志与抓包对齐事实；人员分配的理由应落在「谁熟悉哪层、风险在哪、如何备份」，而不是简单按人头摊派。
