### 《参考解析》

**60 个问题不是 60 个知识点，是一条追问链**

三块内容看着跨度很大——MCP 与 Skill、LangGraph 与向量检索、知识图谱与训练成本——其实是同一种问法：先让你讲实现，再一层层问「为什么这么设计、换个做法行不行、在你这点数据量上还成立吗」。大量「对吧？」不是让你点头，是给你一个台阶，你确认了他就往下挖一层。应对这种面，把每个设计说成「取舍 + 边界条件」，比背架构图有用得多。

**MCP Client 与工具上下文：谁在什么时候把 tools 放进请求**

这块要讲清三个动作。第一是发现：Client 连上 Server 后取工具清单，拿到工具名、描述和参数的 JSON Schema。第二是注入：工具定义是随 request 一起发过去的（放在请求的 tools 字段里），不是写在用户 prompt 里，模型看到的是结构化的能力列表而不是一段散文。第三是调用与回灌：模型返回一个 tool call，里面是工具名和参数 JSON，由 Client 真正执行，结果作为工具结果消息追加进对话，再发起下一轮。

面试官连追的正是这条链最含糊的接缝：只在 query 里给了一个 MCP name，模型上下文里既没有工具名也没有入参 schema，它凭什么正确组装参数？唯一站得住的答案是「必须有一刻把 schema 取回来放进 tools」，否则就是让模型猜参数名，不可靠也没法校验。他接着问「为什么不把取回来的信息写进 SQL、不直接写进 Skill」，考的是单一来源：写死之后工具一升级，提示词里的描述就静默过期，而且没有任何地方会报错；经过 MCP 层是为了让能力描述跟着 Server 走，我们能改的只有调度策略，不是把远端契约抄一份到本地。二次请求不再经过 Server 那问要答得干净：会话内可以缓存工具清单，但要能说出缓存有效期与失效条件，而不是「应该不会吧」。

**为什么用向量库，而不是直接塞进 prompt**

这一串问了七八遍：多少条数据、20 条也要用向量检索吗、未来增长多少、为什么不放 SQL、为什么要用向量数据库。诚实的顺序是先承认边界：如果现在只有 6 到 20 条、结构固定、更新不频繁，塞进 prompt 或者查 SQL 都更简单、更准、更便宜。再讲为什么还是引入：条目会随用户叠加工作流线性增长，条目本身是自然语言描述而不是严格字段，召回要按语义相近而不是字面相等，而且上下文预算有限不可能全塞。

更关键的是把「向量库承载什么」说清楚：它承载候选筛选，不承载事实来源。流程是先召回 top-k，再用结构化字段（版本、状态、权限）过滤，最后取正文。被问「商家库版本」「会不会同时有三四个版本」时，要说明版本是元数据、参与过滤，不是靠相似度区分——这一句能挡掉后面一半的追问。最后给量化边界：涨到多少条、查询延迟要求多少、召回率掉多少就必须上，把「为了将来」这种空话换成一个可验证的阈值。

**知识图谱相对 RAG 的边界**

追问路径很典型：什么情况下用图谱、为什么现在 Agent 里用得少、两跳而已大模型自己也能跳、那是不是只省了 token 和耗时。别吹图谱，讲边界：RAG 擅长找到相关的一段文字，不擅长表达多实体之间的确定关系与约束；图谱擅长的是关系显式、可枚举、可校验，以及跳数可控（两三跳）且要求结果确定、可解释、可审计的场景，比如设备与部件的从属、故障码到处置步骤的映射。

「大模型自己也能跳两跳」的代价是不稳定：同样输入两次结果可能不同，跳错一步无法定位，每次还得把候选文本整段读进上下文。图谱的收益是把这一步变成一次确定性的图查询，省 token 和耗时只是副产品，真正的价值是可复现、可追责。同时主动交代成本：图谱要建、要清洗、要维护 schema，抽取错了会一路传下去，所以只在「关系稳定 + 查询高频 + 错了代价大」时才划算。准确率那题要能说清口径：多少条标注样本、命中判定标准是什么、无法判定的 case 有没有排除——说不清定义的数字等于没有数字。

**被一层层追问设计动机时怎么应对**

三个动作。一是把「当时的选择」和「现在的最优解」分开：「当时只有 20 条，先上向量库是给增长留余量；如果重做，我会先用 SQL 加规则，到几百条再切。」这比硬撑体面，也比顺着面试官改口可信。二是不确定就说不确定，但给验证方式：「这个我没测过，要验证我会做 A/B，看召回率和端到端成功率」，把「不知道」变成「知道怎么知道」。三是被指出问题时先接住再补证据，不辩解：「你说得对，这里确实没考虑并发写入，当时写入是单线程批处理，所以没暴露。」整场里那些「对吧」的引导，该确认的确认，该补充的补充——他要看的是你有没有自己的判断，而不是能不能一路点头到底。
