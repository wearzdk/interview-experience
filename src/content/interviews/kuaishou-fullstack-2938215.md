### 《参考解析》

**先序遍历还原二叉树要区分给了什么信息**。如果序列里带空节点占位（常见写法是 `#`），直接按下标递归构建即可：读一个值，遇到占位符返回空，否则建节点、递归左子树、再递归右子树，每个元素访问一次，时间 O(n)。如果只给先序遍历、且已知是二叉搜索树，就利用「先序的第一个元素是根，后续元素被根值切成小于根与大于根两段」的分治结论，从第二个元素起递归时带上 `(lower, upper)` 上下界，整体仍是 O(n)。更快的写法是单调栈：维护一条从根到当前节点的路径，新元素比栈顶小就挂成栈顶的左孩子，否则不断弹出直到栈顶大于新元素、挂成最后弹出节点的右孩子，每个节点进出栈各一次，O(n) 且不需要递归。面试时要先说清题目给的是哪一种序列，两种解法对应的输入形态完全不同。

**分布式锁的 Key 与 TTL 是设计题，要连着业务讲**。Key 的粒度取被保护的资源（订单号、用户 id、任务 id），不要用一个大 Key 锁全表；Key 要带业务前缀，避免不同业务撞车。TTL 不能拍一个数，要取「P99 执行时间 + 余量」，并明确超时后的语义是「锁失效但业务还在跑」而不是「业务被中止」。自研组件的底层无非是 `SET key value NX PX ttl` 加 Lua 脚本做「比对 value 再删除」的原子释放；面试官追问底层实现时，要能背出这三步以及为什么释放必须用 Lua（查询与删除之间锁可能已过期并被别人拿到）。

**Redisson 的续期就是看门狗**。不显式传 `leaseTime` 时，加锁会用默认的 `lockWatchdogTimeout`（30 秒）作为 TTL，并起一个定时任务在三分之一周期（10 秒）处把 TTL 重置回 30 秒，只要持锁的客户端进程还活着就会一直续。显式传了 `leaseTime` 就不再续期，到期自动释放。所以「不设置过期时间」在 Redisson 里并不是真的没有 TTL，而是靠看门狗维持；如果进程被 kill -9 或发生长时间 Full GC，续期停摆，锁仍会到期释放——这正是「业务未完成锁就过期」的来源。工程上的应对是：业务侧做幂等（版本号、唯一约束、状态机只允许前进），把锁当成「减少并发」的优化而不是「保证互斥」的唯一手段；对强一致场景改用带 fencing token 的方案，或直接换 etcd / ZooKeeper 这类基于共识的锁。

**主从切换丢锁是 Redis 锁的固有缺陷，不要试图用单机 Redis 修好它**。Redis 主从是异步复制，客户端在主节点加锁成功后主节点立刻宕机，这条写入可能还没到从节点，从节点升主后同一个 Key 是空的，另一个客户端就能拿到锁。可选的处理有三个层次：一是 RedLock，向多个相互独立的 master 依次加锁，超过半数成功且总耗时小于 TTL 才算持有，代价是依赖多个独立实例、时钟漂移与 GC 停顿仍会影响正确性，学界对它的安全性一直有争议；二是 fencing token，每次加锁生成单调递增的序号，下游存储在执行写操作时校验序号大于已见过的最大值，过期持有者的写入会被拒绝；三是承认锁只是性能优化，用数据库唯一索引或状态机条件更新兜底。答题时把「锁解决的是效率问题、正确性要靠幂等与版本号」这句话讲出来，比罗列方案更能体现判断力。

**线程池的工作流程**是固定的六步：任务进来先看当前线程数是否小于核心线程数，是则新建核心线程执行；否则尝试入队；队列满再看是否小于最大线程数，是则新建非核心线程；仍满则交给拒绝策略。要能顺带说出四种拒绝策略（直接抛异常、调用者线程执行、丢弃、丢弃最老）以及为什么生产上更常用自定义策略做降级或落盘。

**参数设计要能被数字追问**。并发线程数按 `QPS × 平均耗时` 估并发量，再用 `N × (1 + 等待时间/计算时间)` 修正：I/O 密集型可以开到 CPU 核数的数倍，CPU 密集型贴近核数。队列必须有界，无界队列会把「线程池满」翻译成「内存涨到 OOM」；核心线程与最大线程相差过大时，非核心线程的创建与销毁会带来抖动，`allowCoreThreadTimeOut` 与 `keepAlive` 要一起说明。面试官问 QPS，答不出精确值就说量级与峰值时段，并说明这个数字是怎么从监控里取的。

**上下文透传与防串用是两件事**。透传解决「任务提交时的 ThreadLocal 在池线程里读不到」，标准做法是用 `TransmittableThreadLocal` 配合 `TtlExecutors` 包装线程池，或在 `ThreadPoolTaskExecutor` 上挂 `TaskDecorator`，在提交时抓取、执行前设置、执行后恢复。防串用解决「池线程被下一个任务复用后仍带着上一个任务的上下文」，所以必须在 `finally` 里恢复而不是简单 remove，`TtlExecutors` 的 restore 语义就是为此设计的；如果用了 MDC，还要一并清理，否则日志里的 traceId 会张冠李戴。

**服务宕机时内存队列里的任务一定会丢**，这不是线程池能解决的问题，要提「任务先落库或进 MQ 再异步执行」：消息队列的 ack 机制保证至少一次投递，消费者按任务 id 幂等；落库方案则用状态机（待执行 / 执行中 / 成功 / 失败）加定时扫表补偿，扫到「执行中超过阈值」的记录重新投递，并靠乐观锁防止重复执行。答题时先承认丢失，再给持久化与补偿，比声称「线程池能保证不丢」可信。

**图片异步转存的状态流转**可以按「待转存 → 转存中 → 成功 / 失败（可重试）→ 死信或人工处理」来讲，关键点有三：状态迁移用带条件的更新（`where status = '待转存'`）保证只有一个执行者能推进；重试次数与退避时间写进记录，超过上限进死信并告警；幂等键取源 URL 的 hash 或业务 id，重复投递时先查是否已成功。面试官问「转存到一半宕机怎么办」，答案是状态停在「转存中」，由超时扫描重新置为待转存，目标对象按幂等键覆盖写。

**AI 编码的工作流要讲成可复现的流程**：先让模型读仓库里的约定文件（目录规范、类型来源、禁止事项），再小步改动、每步跑测试与 lint，最后人工 review 差异。真正决定质量的是「上下文怎么给」——把领域术语、接口契约、数据表含义写成仓库内的文档，让模型按路径去读，而不是每次在对话里口述一遍；改动完后要求它输出变更摘要与影响面，落进 changelog 或设计记录。面试官问「怎么沉淀业务背景」，就答「沉淀到代码旁边、能被下一次自动读到的地方」，这也是团队把提示词当工程资产管理的方式。
