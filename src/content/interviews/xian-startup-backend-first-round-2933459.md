### 《参考解析》

**大模型做重排序要讲清「为什么值得多花一次调用」**：召回阶段用向量或 BM25 拿 top50，精排让模型按「是否直接回答了问题」打分或直接输出排序，prompt 里给查询 + 候选片段、要求输出 JSON 分数与理由、限制打分维度（相关性、信息量、时效）；代价是延迟和不稳定，所以线上要做超时降级到原顺序、结果缓存、并把候选数控制在小几十条。相比 cross-encoder 重排模型，LLM 重排更懂意图但更贵更慢。

**B+ 树那套要一次说完**：磁盘 IO 是瓶颈，B+ 树非叶子节点只存键、扇出大、树高三层就能撑千万级；叶子节点用双向链表串起来，范围查询和排序友好；所有数据在叶子、查询路径长度一致，性能稳定。对比 B 树（节点存数据、扇出小）、哈希（只支持等值）、跳表（内存友好但磁盘不友好）。

**慢 SQL 排查顺序**：先确认是否偶发（连接池耗尽、锁等待、网络），再 `EXPLAIN` 看 type / key / rows / Extra，`SHOW PROFILE` 或 `performance_schema` 看各阶段耗时，`SHOW PROCESSLIST` 抓正在跑的慢查询；优化手段是补/改索引（联合索引顺序、覆盖索引）、改写 SQL（避免函数、避免 `select *`、拆大事务）、分页深翻用游标、必要时空 archive 冷热分离。

**秒杀的核心是「把流量挡在数据库前面」**：前端限流与按钮防重、网关层限流与黑名单、库存预热到 Redis、Lua 脚本原子扣减（判断 + 扣减 + 记录用户），扣成功再异步落库下单（消息队列），未支付超时回补库存；防超卖靠原子扣减 + 数据库唯一约束兜底，防刷靠用户维度限流与风控。

**MySQL 与 Redis 双写一致性**：常规做法是「先更新数据库再删缓存」（Cache Aside）+ 延迟双删 + 订阅 binlog（Canal）异步删缓存，容忍短暂不一致；强一致要么把库存的唯一真相放数据库、Redis 只做「预扣令牌」并在失败时回滚，要么用分布式事务（TCC / 本地消息表 / Seata）以性能换一致性——面试里明确说出「强一致必然牺牲可用性与吞吐」是加分项。

**JWT 防伪造**：签名算法用 HMAC-SHA256 或 RS256，密钥只在服务端；验证时先校验签名再校验 `exp`、`iss`、`aud`，禁用 `none` 算法（历史上的经典漏洞）；还要处理注销（黑名单 / 短有效期 + refresh token）、防重放（jti + 一次性 nonce）。ThreadLocal 存用户上下文要注意线程池复用导致的串号，用完必须 `remove()`（`try/finally`），这也是后来很多人改成显式传参或 RequestScope 的原因。

**Agent 工作流**的骨架是「规划 → 选工具 → 执行 → 观察结果 → 再规划」的循环，配上终止条件（步数上限、目标达成判断）、错误处理（工具失败重试或换路）、上下文管理（摘要压缩）。答这一题时把「工具描述写得好不好直接决定调用准确率」讲出来，比复述 ReAct 名词更有说服力。
