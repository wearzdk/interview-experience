### 《参考解析》

这组题是 C++ 一面的标准开局，考的是语言细节背后的设计意图，而不是名词解释。

const 要按位置讲：修饰变量/引用/指针（区分「指针本身 const」和「指向的内容 const」）、修饰成员函数（承诺不修改对象状态，因此只能调用其他 const 成员，需要改的成员标 mutable，典型是缓存和计数器）、以及 const 返回值。它的价值是让编译器替你守住契约：查询类接口标 const 之后，「这个方法改了对象」会直接编译报错，也让重载可以按 const 分流。

static 的语义随位置变化：静态局部变量生命周期延长到程序结束且只初始化一次（函数级单例、懒初始化）；文件作用域的 static 收窄链接可见性；类的静态成员属于类而不属于对象，所以类内只是声明、必须类外给唯一一份定义——多个翻译单元各自看到内联定义会违 ODR；静态成员函数没有 this，不能访问非静态成员。C++17 起 `inline static` 允许类内定义，这是现代写法。

inline 的关键认知是「它是建议不是命令」：编译器会拒绝内联大函数、递归函数、被取地址的函数，它换取的是调用开销换代码体积。和宏的本质差别在语义：宏是文本替换，没有类型检查、没有作用域、参数可能被多次求值产生副作用；内联是真正的函数，调试信息完整、类型安全。头文件里定义非 inline 函数会在多翻译单元时重复定义报链接错，inline 正是为解决 ODR 而存在。

命名空间解决大型项目和第三方库的符号冲突。坑集中在 `using namespace std;` 写在头文件里——所有包含它的翻译单元都被污染，`count`、`distance`、`swap` 这类名字会莫名歧义。工程规范是头文件里只 `using std::string;` 这样引入单个符号，或者干脆全写限定名；文件内部私有改用匿名命名空间，比 static 更现代。

减少编译依赖的第一杠杆是前置声明：头文件里能 `class Foo;` 就不 include，只有需要完整类型（继承、按值成员、sizeof、成员访问）时才包含定义。PIMPL 是这套思路的极致——把实现藏在 impl 指针后面，头文件零依赖，改实现不触发下游重编，代价是一次指针跳转和手工管理生命周期（用 unique_ptr 解决）。原则是正确性优先，拿不准就 include。

多态的动态绑定发生在运行时：编译器只知道「调虚表的第几项」，具体走哪一项由对象的 vptr 决定。能提前确定的场景（对象的具体类型已知、类型标了 final、去虚化优化）编译器会直接调用。这里必须补一句实践建议：重写时函数签名不一致会「静默造出一个新函数」而不是覆盖，加 `override` 让编译器把关，这是面试官很爱听的细节。

初始化列表与赋值的区别在于「构造一次还是构造两次」：初始化列表直接调用成员相应的构造函数；在函数体里赋值则是先默认构造再赋值，对自定义类型多一次构造 + 一次赋值，const 成员和引用成员更是只能走初始化列表。顺带说清成员初始化顺序由声明顺序决定，与列表书写顺序无关——这个坑很多人踩过。
