### 《参考解析》

**热 key 看访问量，大 key 看体积与操作成本**

一个值很小的 key 也可能因为访问集中压满实例；一个访问不频繁的集合，也可能因为成员过多导致传输或删除耗时。先确认是读热点、写热点，还是单次命令成本高。读热点可评估本地缓存与失效机制；计数写热点可在允许聚合的业务里拆分；大集合则从数据拆分、分页访问和生命周期入手。

**多 Agent 要说明任务怎么汇合**

先把整体任务、各角色输入输出和共享状态画清楚，再说明谁判断完成、失败怎样上报、冲突结果怎样处理。如果几个角色只是重复阅读同一份材料，需要解释分工带来的具体收益。拿自己的项目举例，比只说“多个智能体协作”更有说服力。

**starter 与自动配置不是同一个概念**

starter 提供一组便于引入的依赖，自动配置根据类路径、已有 Bean 与配置属性等条件组织应用。面试时可以选一个自己接过的组件，讲从添加依赖到形成可用 Bean 的过程，再说明需要自定义时如何覆盖默认行为。

**存储引擎比较落到事务需求**

InnoDB 支持事务、外键以及面向行的锁机制，适合需要事务一致性的业务。MyISAM 的事务和并发控制能力不同。实际查询是否高效，仍取决于表结构、索引、数据分布与访问方式，不能仅凭引擎名称下结论。
