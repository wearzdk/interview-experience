### 《参考解析》

**feed 用 ZSet 而不是纯推拉**：纯推模式写扩散——发一条帖要给所有粉丝的收件箱塞一份，大 V 发帖就是一次写风暴，存储也会随粉丝数放大；纯拉模式读扩散——每次刷新要合并全部关注对象的发件箱，关注几千人时延迟顶不住。项目里用的是推拉结合：普通用户发帖走写扩散进粉丝收件箱，大 V 走读扩散、刷新时现拉。收件箱本身用 ZSet，score 取发布时间戳，`ZREVRANGEBYSCORE` 按游标翻页天然有序、O(logN + M) 拿到一页，分页游标直接就是 score 边界，不用 offset 越翻越慢；成员是帖子 id，去重由 set 语义免费提供（同一条帖重复投递不会出现两次）。用 List 就没这个好处：有序性要靠自己维护、去重要额外查一次、按时间游标翻页也无从下手。

**写完数据库缓存更新失败**：单靠「更新缓存」或「删缓存」这一步都不可能绝对可靠，只能把不一致窗口压小并兜底。工程上的组合是：先更新数据库、再删缓存（Cache-Aside），删失败就重试——重试放消息队列，带指数退避；同时给缓存 key 设过期时间，让最坏情况下的不一致有上界。要更严就上 binlog 订阅（Canal / Debezium）异步补偿删除，把「删缓存」从业务代码里摘出去，业务侧只负责写库。反过来「先删缓存再写库」在并发下更糟：删完到写库之间读请求会把旧值重新加载回缓存，反而长期不一致。答这题的关键是承认最终一致、说清窗口多大、失败怎么兜。

**Lua 脚本执行到一半报错**：Redis 保证脚本原子执行——执行期间不会插入别的命令，但**它不保证脚本内部回滚**。Lua 脚本里已经写进去的命令不会因为后面一行报错而撤销，所以设计脚本时要把校验全部前置：先在脚本开头把所有参数和前置条件验完（key 是否存在、库存够不够、状态对不对），验过再动手写。实在有中途失败可能，就只写幂等操作，或者把写操作按「能整体重试」设计——脚本整体重跑一遍结果不变。另一种常见做法是用 `pcall` 包住可能失败的部分，把错误吞进返回值判断，避免半个事务落库后调用方不知道状态。

**消费者异步下单失败**：分级处理。可重试的（下游超时、锁冲突）走延迟重试队列，指数退避，限制次数；不可重试的（库存不足、参数非法）直接落死信并回滚已占用的资源（把预扣的库存还回去）。关键是**幂等**：消息带唯一业务号，消费方用「业务号 + 状态」做去重表或 Redis setnx，重复投递只生效一次。还要防消息丢失——生产端本地消息表或事务消息保证「业务落库」和「消息发出」同生共死，消费端手动 ack、处理完才提交位点。库存这种强一致资源建议用「预扣 + 确认」两阶段，超时未确认自动回补。

**P99 = 356ms 的口径**：P99 是把这段时间所有请求的响应时间排序后取 99% 分位那个值——意思是 99% 的请求都快于 356ms，最慢的 1% 比它更慢。它比平均值有用，因为平均会被长尾拉平，掩盖掉一小撮用户卡死的事实。测量上分两个位置：服务端埋点（请求进入 → 响应写完）只能看到自己那一段，网络与客户端渲染看不到；要贴近体感得在客户端打点。统计窗口一般按分钟聚合再算分位，直方图（如 HDR Histogram）比保留原始样本省内存。追查长尾时不能只看 P99，要把慢请求抽样出来看是慢在 DB、下游 RPC 还是 GC。

**ZSet 底层与跳表**：ZSet 是「跳表 + 哈希表」双结构。跳表按 score 有序存放成员，支持 O(logN) 的插入、删除和范围查询；哈希表存「成员 → score」的映射，让 `ZSCORE` 这类按成员查分值的操作也是 O(1)。只用跳表的话按成员定位要先扫或者额外二分；只用哈希表则拿不到有序性。跳表相比平衡树的好处是实现简单、范围查询时能顺着底层链表顺序走、并发改造容易（不用旋转），代价是常数因子略大、内存占用比压缩结构高。底层链表节点过多时会转成 listpack 压缩存储，省内存。

**MVCC 与读已提交**：能。InnoDB 的 MVCC 靠三个东西：行上的隐藏事务 id（DB_TRX_ID）、undo log 里的历史版本链、以及 ReadView。读已提交（RC）**每条语句**生成一个新 ReadView，所以同一条事务里两次查询能看到别人新提交的数据；可重复读（RR）在事务第一条快照读时生成一次 ReadView 并复用整个事务，所以两次查询结果一致。两者都用版本链 + ReadView 判断可见性，差别只在 ReadView 的生成时机。补充一个常被追问的点：RR 下当前读（`SELECT ... FOR UPDATE`）读的是最新版本，靠的是间隙锁而不是 MVCC。

**Kafka rebalance 与重复消费**：rebalance 是消费组内分区重新分配的过程，触发条件是成员进出、订阅的 topic 分区数变化、或者心跳超时被踢出组。rebalance 本身会造成重复消费：新成员加入时，老成员必须先把已分配的分区交还（revoke），如果此时它已经拉了一批消息但还没提交位点，这批消息就会被重新分配给别的消费者再消费一遍。所以语义上是 at-least-once。降低影响的办法：用增量协作式 rebalance（CooperativeStickyAssignor）避免全局 stop-the-world；把 `max.poll.interval.ms` 调大到覆盖单批处理耗时，避免处理慢被判死；消费逻辑本身做成幂等，这是最根本的一层。

**消息积压排查**：先分清是「生产变快」还是「消费变慢」。看消费 lag 曲线：如果 lag 是台阶式上涨，通常是消费者卡住或频繁 rebalance；如果匀速上涨，则是产能超过消费能力。消费者侧查：有没有消费线程抛异常后一直重试同一条（毒消息）、有没有下游依赖（DB、第三方接口）变慢拖住整批、GC 或 Full GC 是否变频繁、分区数是否少于消费线程数导致部分线程空转。应急手段依次是：扩容消费者（不超过分区数）、临时把消息转存到新 topic 用更多分区并行处理、非核心业务先降级丢消息（前提是能补）。事后要加的是消费耗时监控和毒消息的自动进死信。

**GET 能不能带请求体**：HTTP 规范没有禁止，但语义上未定义——RFC 7231 说 GET 的 payload 没有定义的语义，很多实现（缓存、代理、部分服务端框架）会直接丢弃或拒绝。所以工程上不该依赖它：要传复杂查询条件用 POST，或者把条件编码进 query string。真正会被带 body 的场景是 Elasticsearch 的 `_search` 这类自家约定的接口。常见请求头可以从几个维度说：内容协商（Accept、Content-Type、Accept-Encoding）、认证（Authorization、Cookie）、缓存（Cache-Control、If-None-Match、If-Modified-Since）、链路追踪（Traceparent、X-Request-Id）、客户端信息（User-Agent、Referer、Origin）。

**JWT**：三段式 `header.payload.signature`，各自 base64url 编码。header 声明算法，payload 放 claims（sub、exp、iat 以及业务自定义字段），signature 是对前两段用密钥（HMAC）或私钥（RSA/ECDSA）签出来的。服务端不存会话，验签 + 校验 exp 就知道令牌合法，天然适合无状态横向扩展。代价是**签发后无法单方面撤销**——要踢人只能等过期，或者额外维护黑名单（那就又回到有状态）。所以实践上 access token 给很短的有效期（分钟级），配一个长效 refresh token 存服务端可撤销；敏感操作再要求二次校验。payload 是明文可读的，不能放密码之类的秘密。

**慢查询排查**：先确认是不是真慢——`slow_query_log` 按 `long_query_time` 抓出来，用 `mysqldumpslow` 或 pt-query-digest 聚合，按总耗时排序（次数多的小慢查询往往比偶发的大慢查询更值得治）。单条用 `EXPLAIN` 看执行计划：type 是不是 ALL（全表扫）、key 有没有用上索引、rows 估算多少、Extra 里有没有 Using filesort / Using temporary。常见根因是索引缺失或失效（函数包裹列、隐式类型转换、前导模糊 LIKE、OR 混了无索引列、复合索引不满足最左前缀），其次是回表太多（该上覆盖索引）、数据量增长导致统计信息过期（`ANALYZE TABLE`）、以及锁等待而非执行慢。
