### 《参考解析》

**分库分表要解决什么，ShardingSphere 在其中做什么。** 单表数据量过大时，B+ 树变深、DDL 与备份变慢、单机磁盘和连接数见顶；分库分表把数据按分片键水平拆开，代价是跨库 JOIN、分布式事务、全局唯一 ID、跨分片排序分页和扩容迁移。ShardingSphere 处在应用与数据库之间，做 SQL 解析、路由、改写、结果归并，并提供分布式事务与数据迁移能力。回答时先说痛点，再说它把哪些痛点接走、哪些仍然留给业务，比背功能列表更有说服力。

**SQL 查重名与最左前缀。** 查 name 相同的 user 用 `SELECT name FROM user GROUP BY name HAVING COUNT(*) > 1`；如果要看具体用户，用 `SELECT * FROM user WHERE name IN (SELECT name FROM user GROUP BY name HAVING COUNT(*) > 1)` 或窗口函数 `COUNT(*) OVER (PARTITION BY name)`。判断是否走索引看联合索引的列顺序：查询条件从最左列开始且连续、范围条件之后的列不再用于定位，`LIKE '%x'` 与对列做函数运算会使索引失效。分析执行计划看 `type`、`key`、`rows`、`Extra`，不要只看「有没有索引」这一项。

**Redis 过期与淘汰是两套机制。** TTL 到期由定期删除（周期性随机抽查）加惰性删除（访问时发现过期再删）共同处理，不保证到点立即释放内存。内存达到 `maxmemory` 时触发淘汰策略，如 `allkeys-lru`、`volatile-lru`、`allkeys-lfu`；`noeviction` 下写入会直接报错。面试里把「过期删除」和「内存淘汰」分开讲，说明各自触发条件与适用场景。

**IO 多路复用与 Redis 单线程。** Redis 用 epoll 这类多路复用器在一个线程里等待多个连接的就绪事件，事件到达后按顺序处理命令，避免为每个连接创建线程的上下文切换与锁竞争。命令执行是单线程的，网络读写、持久化、部分删除可以用后台线程或子进程。慢命令会阻塞全部请求，因此要避免 `keys *`、大 key 删除、复杂度高的 Lua 脚本。

**Kafka 的顺序性与消费模型。** topic 分成多个 partition，每个 partition 内有序，消费组内一个 partition 只被一个消费者消费，因此「全局有序」需要单 partition 或按业务键路由到同一 partition。生产者用 `acks` 与幂等 producer 控制可靠性；消费者位移提交决定至少一次或至多一次语义；重复消费要靠业务幂等。积压时先看消费者数量与 partition 数是否匹配、单条处理耗时、是否有慢下游，再决定扩消费者还是扩 partition。

**虚拟内存、懒分配与写时复制。** 虚拟内存给每个进程独立的地址空间，通过页表映射到物理页，好处是隔离、按需分配、可以大于物理内存。`malloc` 只拿到虚拟地址，首次访问触发缺页中断才分配物理页（懒分配）。`fork` 后父子进程共享只读页，任一方写入触发写时复制，复制出新页。内存碎片分内部碎片（分配器按固定大小取整造成的浪费）与外部碎片（空闲块零散、无法满足大块请求）；解决手段包括分级空闲链表、伙伴系统、slab、对象池，以及减少频繁分配释放。

**MySQL 并发状态流转用条件更新实现 CAS。** 表里有 id、status，要求「A 改完后 B 再改必须失败」，本质是状态机上的乐观并发控制：`UPDATE t SET status = 2, version = version + 1 WHERE id = ? AND status = 1`，受影响行数为 0 说明状态已被别人改过，B 的更新失败。行锁、阻塞队列也能做，但会引入等待与死锁面；CAS 无阻塞、失败可重试，适合状态跃迁。若需要「改完通知 B」，用事务内更新加事务提交后的消息投递（事务消息或本地消息表），不要在事务提交前发通知。

**搜索旋转排序数组。** 数组原本升序、在某点旋转，仍可用二分：取中点后判断左半段是否有序（`nums[l] <= nums[mid]`），若有序且目标落在区间内则收缩右边界，否则收缩左边界；右半段有序时对称处理。边界用 `l <= r`、`mid = l + (r - l) / 2`，注意重复元素会让「哪半有序」判断失效，需要单独收缩。
