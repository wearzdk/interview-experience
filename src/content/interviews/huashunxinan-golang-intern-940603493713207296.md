### 《参考解析》

**为什么用 Gin 做网关：答「性能 + 中间件生态 + 可控」，并说清什么场景不该自己写。** Gin 基于 `net/http`，路由是压缩前缀树（radix tree），匹配快；中间件是一条显式的 `c.Next()` 链，鉴权、日志、限流、恢复都好插；`Context` 对象池化复用、内存分配少，压测下 QPS 有优势；而且它不隐藏 HTTP 语义，排查问题直观。对比时要给出取舍：Echo/Fiber 更快（Fiber 基于 fasthttp，不兼容 `net/http` 生态，中间件与库要另找）；Beego 大而全、约定重；gRPC-Gateway 只适合把 gRPC 暴露成 REST；真要做功能完整的网关（动态路由、熔断、插件、控制台），成熟方案是 APISIX / Kong / Envoy，自研 Gin 网关的优势只在「链路短、逻辑自己可控、和内部鉴权体系贴合」。回答里最好带一句自己项目真实碰到的点，比如「选 Gin 是因为要复用已有的 JWT 中间件和统一响应封装」。

**etcd vs Nacos：先讲注册发现的机制，再讲一致性与生态的取舍。** 注册发现的本质是「服务注册（写）+ 健康发现（探测）+ 客户端订阅（变更通知）」。etcd 是 Raft 强一致的 KV，靠租约（lease）续约、`Watch` 推变更，实例要自己起心跳：`Grant` 租约 → `Put` 带租约的 key → 定时 `KeepAlive`，租约过期自动摘除。它没有控制台、没有内置健康检查、没有配置分组，注册与发现逻辑要自己写。Nacos 面向服务治理：临时实例走心跳、持久实例走主动探活，支持 AP/CP 切换（Distro / Raft）、命名空间与分组、权重与元数据、配置中心，控制台完善，Java 生态友好。选 etcd 的典型理由是「已经在 K8s/Go 体系里、只想要一个可靠的 KV + watch」，选 Nacos 是「要有现成的注册中心与配置中心」。要能说出两个坑：watch 断连后必须重新拉全量再续 watch，否则丢变更；租约续约因为网络抖动失败会导致健康实例被误摘，所以 TTL 与重试要留余量。如果部署在 K8s 里，还要知道 Service + CoreDNS 本身就能做一层服务发现。

**容器化部署与 MySQL 排障：把「重启策略」和「数据卷」讲出来。** 服务器重启后容器起不来，根因几乎都是没有配 restart policy——`docker run` 默认 `--restart no`，生产要写 `always` 或 `unless-stopped`（后者在你手动 stop 后不会自动拉起），用了 compose 就在 `restart:` 里配，systemd 托管的话 `systemctl enable` 开自启。重启后查状态的标准动作：`docker ps -a` 看容器列表与 `Exited (码)`、`docker inspect` 看 ExitCode / RestartCount / OOMKilled、`docker logs --tail 200 -f` 看退出前日志、`docker compose ps`、`docker stats` 看资源；有 healthcheck 的话看 `docker inspect --format '{{json .State.Health}}'`。要在容器里的 MySQL 执行语句：`docker exec -it <容器名> mysql -uroot -p`（镜像不同客户端路径不同，MariaDB 是 `mariadb`），密码走 `MYSQL_ROOT_PASSWORD` 环境变量；生产更稳的做法是宿主机装客户端 `mysql -h 127.0.0.1 -P 3306 -u…`，或者 `docker exec <容器> sh -c 'mysql -e "..."'` 写进脚本。一定要顺带提「数据必须挂 volume」，否则容器重建数据就没了——这是面试官最想听的那一句。

**Redis Stream 比 List 队列强在哪。** Stream 是 append-only 的消息日志，`XADD` 写、`XREADGROUP` 按消费组读、`XACK` 确认，天生支持多消费组（同组内分摊、跨组各读一份）、未确认消息表（PEL）以及 `XCLAIM` / `XAUTOCLAIM` 认领超时消息，还能按 ID 回溯与重放——这几样正好补上 `LPUSH/BRPOP` 队列「消息取走就没了、没有 ack、失败就丢」的短板，也补上 Pub/Sub 不持久化的问题。工程上要注意：`XADD` 时用 `MAXLEN ~ N` 近似裁剪，否则内存只增不减；消费失败不 `XACK` 会让 PEL 越堆越大，要监控并定期清理；它没有 Kafka 那种分区与跨分区顺序保证，量级大了还是该上专业 MQ。答这题时给一个具体用法（比如订单状态变更通知），并说清「为什么不用 List」就完整了。

**AI 编程的三阶段分配、review 冲突与工程师能力。** 精力分配的合理答法是「需求与验收标准最多、实现最少、review 与验证居中偏多」并说明理由：把接口、边界与验收标准写清楚，AI 才不会跑偏，返工成本远大于多花的那十分钟；实现交给 AI 提效最明显；评审与测试是人类最不能省的一环。代码评审不止看代码，还要看方案与选型是否仍然成立——发现问题时别急着重写，先判断是「方案错了」还是「实现偏了」：方案错就停下来重做设计（用一个小 spike 验证关键假设，成本可控），实现偏就局部修。AI 评审与自己的判断冲突时，靠可验证的证据裁决：写最小对照实现、跑基准或测试、列出双方方案满足与不满足的约束，把结论沉淀成仓库里的 ADR / 规范 / 提示词，下次不用重新吵。团队层面：小 PR、明确的评审清单、自动化门禁（lint、测试、安全扫描）顶掉机械检查，让人专注设计与边界。至于「agent = LLM + harness」，可以认同但补一句：LLM 提供能力上限，harness 决定它能不能被可靠地用起来——上下文管理、工具、状态与记忆、失败重试与校验、权限与可观测性，缺一项就只是个会说人话的模型。聊到「工程师要具备什么能力」时，落到五个词：问题定义与拆解、系统设计与取舍、验证与判断（会不会用测试和度量证明东西对）、领域与业务理解、以及把 AI 当工具用的工程习惯。

**B+ 树与 B 树的区别，以及什么是回表。** B 树每个节点既存键也存数据，一个节点能放的键少、树更高；B+ 树只有叶子节点存数据（或数据指针），内部节点只存键，所以扇出更大、树更矮、磁盘 IO 更少；B+ 树的叶子节点用双向链表串起来，天然支持范围扫描和排序，B 树要中序遍历。另外 B+ 树所有查询都走到叶子，路径长度稳定，性能可预期。回表指的是：二级索引的叶子只存索引列和主键，如果查询要的列不全在索引里，就必须拿主键再回聚簇索引捞一次行数据——每行多一次随机 IO，代价高。对应的优化方向是覆盖索引（把要查的列都放进索引，`EXPLAIN` 里看到 `Using index` 就是没回表）、或把二级索引直接建成需要的列组合；`EXPLAIN` 的 `type` 出现 `ALL`、`Extra` 出现 `Using filesort`/`Using temporary`，通常就是该改索引或改写的信号。
