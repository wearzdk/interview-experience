### 《参考解析》

**为什么不能把数据直接交给模型，还要写代码规则**：模型擅长处理非结构化文本、做语义归一与归纳，但它的输出不稳定、不可审计，也不能保证业务约束。规则负责的是「确定的那部分」——字段映射、枚举校验、金额与权限、必须满足的业务前置条件；模型负责「规则写不出来的那部分」——多源格式的语义对齐、异构字段的归一、长文本抽取。二者是分层而不是二选一：规则先做硬约束与兜底，模型在约束内填充；模型输出再过一层强校验，校验不过就走人工或降级，而不是把错数据写进业务系统。

**生成结果怎么进入 Java 业务系统**：把模型调用当成一个有自己的失败语义的外部依赖。链路是「结构化输出（JSON Schema / 函数调用）→ 服务端 schema 校验 → 业务规则强校验 → 幂等落库或调用既有接口」。关键点是别让模型直接写库：模型只产出候选结构，落库由后端服务按业务事务裁决；同时要有超时、重试、幂等键、可回滚，以及全链路的输入输出留档，出问题能定位到是哪一步、哪条数据。

**拿不到的信息怎么处理**：先区分「拿不到」是权限问题、接口缺失还是数据本身不存在。工程上分三层：能从其他来源推导或关联的，补一次关联查询；推不出来的，输出里显式留空并标记不确定，绝不编造；业务上必须有值的，转人工确认或走降级分支。这条最容易被追问「会不会模型编一个」，所以回答要把「不编造」落成机制——字段级必填校验 + 低置信度转人工，而不是靠提示词要求模型老实。

**多智能体怎么分工**：Supervisor 负责意图识别、任务拆解与路由，决定这一轮交给谁、什么时候收口；Planner 产出可执行步骤与依赖关系；Executor 按步骤调用具体工具（日志查询、指标拉取、变更记录），把结果回填。核心设计不在「分了几个角色」，而在状态怎么传：共享一份结构化任务状态（每步的输入、输出、置信度、失败原因），Supervisor 依据状态决定重试、换路或终止。举个完整例子：用户报「某航班排障」，Supervisor 判定为排障类 → Planner 拆成「定位航班 → 拉取该航班链路日志 → 比对同期指标 → 关联变更 → 汇总」→ Executor 逐步调工具 → 中间某步查不到数据时回填失败原因，Supervisor 决定走关联查询还是直接输出已确认的部分。讲这类项目时一定要说清哪些是自己实现的：编排、状态机、工具封装、失败重试通常是自己写的，底层模型与框架是调用的。

**Harness 与模型的关系（本场关键追问）**：模型能力越强，Harness 承担的事情不是变少而是上移。原来 Harness 在做「替模型补能力」——拆步骤、约束格式、兜底重试；模型把这些内化之后，Harness 的价值转到三处：一是上下文与工具面，决定模型看到什么、能做什么（工具粒度、权限边界、上下文裁剪策略）；二是确定性与治理，业务不允许的概率性结果要靠校验、幂等、审计、可回滚兜住；三是评测与反馈闭环，把线上失败案例变成可复用的评测集与规则。可以把关系说成「模型决定能力上限，Harness 决定这份能力在业务里能不能稳定兑现」。如果说未来方向，落点在本体化与 AI Native：把业务概念与操作抽成模型可理解的语义层（而不是把接口原样暴露），让 Agent 按业务意图调用，而不是按技术接口拼装。

**「为什么没保研 / 为什么二战」这类问题**：面试官问的是决策逻辑与自我认知，不是成绩单。回答按「当时的约束 → 我的判断 → 结果与复盘」三段讲：说清客观条件（保研名额、绩点排名、课程短板），给出自己当时的取舍理由，再讲这段经历带来的可验证改变（比如自学能力、目标拆解）。不要贬低学校或同学，也不要只剩情绪。

**对公司的了解**：至少说到对方当前的主营方向与正在投入的产品线，并和自己的项目挂上钩。科大讯飞的核心是语音与认知智能，近年重心在星火大模型与教育、医疗、办公等行业的落地，以及国产算力上的模型训练与推理适配。可以顺着说「我的多智能体项目里工具编排与失败恢复的做法，和行业 Agent 落地要解决的问题是同一类」，把话题拉回自己的可验证经验。

**反问**：两个反问都指向「我进来做什么、能不能成长」——团队近期主攻方向决定你前半年做什么，新人是否有从零到一的机会决定成长速度。这两个问题比问薪资、问加班更能留下印象，也方便自己在后续流程里判断。
