### 《参考解析》

**qiankun 的隔离**：JS 侧用 Proxy 给每个子应用造一个假的 `window`，读写都落在自己的沙箱对象上，全局变量互不污染；同时劫持 `document` 的部分方法做样式与节点归属标记。样式侧用 `scoped` 给子应用的选择器加前缀，或用 Shadow DOM 做严格隔离（qiankun 的 `strictStyleIsolation`）。局限要敢说：Proxy 沙箱挡不住直接操作真实 `document`、也挡不住 `window.location` 这类原生对象；`eval` / `new Function` 里的全局访问仍可能穿透。替代方案还有 iframe（天然隔离但通信、弹窗、路由都麻烦）、Web Components、Module Federation（构建期共享，运行期不隔离）。

**性能优化怎么讲**：先给测量口径再讲手段。用 Performance 面板能拆出 TTFB、资源加载、主线程长任务、渲染各段占比；「优化前主要集中在哪」要有数字（比如首屏 2.8s 里 1.4s 是 JS 解析执行、0.6s 是串行请求）。手段按收益排序：路由级懒加载 + 预取、把大依赖拆包并做 CDN、接口并行与 BFF 聚合、关键 CSS 内联、图片响应式与懒加载、长列表虚拟化。验证上，实验室数据（Lighthouse）看趋势、真实用户监控（web-vitals：LCP/INP/CLS 的 p75）看结论，两边都要有。

**埋点起止点**：起点是路由切换或点击触发的时刻（`performance.mark`），终点按目标定义——「模块可见」应取首次渲染出内容的帧（`requestAnimationFrame` 后一次 mark 或 `PerformanceObserver` 的 LCP），「接口可用」取关键数据到位的时刻。判断挂载完成可以用 Vue 的 `mounted` / React 的 `useEffect`（DOM 已提交但未必绘制完），更准的是 `nextTick` 后再等一帧。用 `performance.measure` 把这些点连起来，数据才好归因。

**AI 迁移代码的坑**：出问题集中在三类阶段——上下文不全时（AI 只看到被迁的文件，不知道调用方约定）会漏改依赖；批量改写时（一次几百行）语义漂移难以逐行 review；以及「顺手优化」，把没让你改的逻辑也重写了。控制办法：把迁移拆成小步、每步有可执行的验收（类型检查 + 单测 + 关键页面回归）、diff 必须人能逐段读懂、公共契约先冻结。判断过度设计看两点：是否引入了当前需求用不到的抽象层，以及删掉它之后功能是否仍然完整——如果删掉没影响，那就是多余的。

**两道字符串压缩**：都是单次遍历、双指针。第一题用 `prev` 记当前字符、遇到不同就输出并重置；第二题在切换时统计计数，`count > 1` 才拼数字。面试时先把边界写出来（空串、单字符、全相同），再写主循环，最后各跑一个用例，比追求花哨写法稳。
