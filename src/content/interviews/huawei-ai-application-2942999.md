### 《参考解析》

**输入真实、模型仍然出错时，代码与模型怎么分工**：模型出错一般不在「读不懂输入」，而在三处——业务依据没有被结构化（上游给的是一段自由文本，口径散落在各处）、判定标准没有被显式建模（同一类问题靠 Prompt 里的自然语言描述，边界模糊）、以及缺少可验证的收敛手段。所以治理顺序是先把业务依据整理成结构化字段与规则表（字段化、枚举化、可回溯来源），能确定性判定的部分交给代码（正则、字典匹配、规则引擎、阈值），只把需要语义理解的部分交给模型，并且要求模型输出结构化结果（JSON Schema 约束、枚举、必填字段），再用二次校验或规则回查兜底。衡量治理效果要有对照：同一批离线样本上治理前后的错误率、错在哪一类，而不是只看线上「感觉好了」。

**多 Agent 的分工与协调**：Supervisor 负责意图识别与路由，决定当前这一步交给谁、什么时候终止；Planner 把目标拆成有序子任务，产出可执行的步骤清单；Executor 只负责执行单步并返回结果。协调的关键是共享一份显式状态（任务清单、已完成步骤、中间产物），每一步的输入输出都走这份状态而不是靠对话历史传递，这样任意一步失败都能重放，也能限制上下文长度。多 Agent 相比单体流程的价值在于职责隔离与可观测——每一步都有明确的输入输出和判定标准，出错时能定位到是规划错了还是执行错了；代价是调度开销、状态一致性与更长的链路，如果任务本身就是单步转换，多 Agent 只会增加失败面。

**「约束单步执行、阻断幻觉」的落地**：核心是把「让模型自由决定下一步做什么」换成「模型只能从当前允许的动作集合里选一个」。具体做法：把工具与动作定义成有限集合，每一步只暴露当前状态合法的动作；要求模型输出结构化调用（动作名 + 参数），由程序校验参数合法性与前置条件，不合法就拒绝并回灌错误信息；执行结果由程序回读确认（接口返回、页面状态、数据库记录），模型自述成功不算数；对事实性字段禁止模型生成，一律从检索结果或库里取。再加一条「无依据即拒答」的出口，让模型在检索不到支撑时明确说不知道，而不是补全一个像样的答案。

**其他降低幻觉的手段**：检索增强并在回答里带出处，让内容可回查；把长任务拆成短步骤，每步只让模型做一个小判断；用规则或小模型做前置过滤，缩小模型的选择空间；同一问题多次采样或换模型交叉验证，对不一致的结果降级或转人工；对数值、日期、ID 这类字段做格式与范围校验；以及最容易被忽略的一条——把评测集固定下来，每次改动都跑一遍，靠数据判断某条措施是否真的降低了错误率。

**RAG 与向量库选型**：RAG 的完整链路是文档解析（版式、表格、标题层级）→ 切分（按语义边界而不是固定字数，保留标题与上下文）→ 向量化 → 检索（向量召回 + 关键词召回混合，再加重排）→ 组装提示并附出处。切分与召回质量决定上限，很多「RAG 答不准」其实是切碎了上下文或只做了向量召回。向量库选型看四点：数据量级与召回延迟、是否需要标量过滤与混合检索、是否要自建运维、以及和现有技术栈的契合度。中小规模、单机可跑、需要元数据过滤的场景用 pgvector 或 Milvus 单机版就够；规模上亿、要高可用与多副本时再上分布式集群，并单独做索引参数与分片调优。选型理由要能说出「为什么不选另一个」，不能只说「社区常用」。

**在 Java 开发中使用 AI 编程**：日常用于三类事情——写模板化的样板代码（DTO、Mapper、单元测试骨架）、读陌生代码（让它先解释调用链再动手改）、以及生成重复性脚本与 SQL。用法上有两条纪律：一是把上下文喂准（相关文件、接口定义、约束条件），让它在明确边界内生成；二是生成结果必须自己过一遍并跑测试，尤其是并发、事务、异常分支这类它容易想当然的地方。代码评审时把它当协作者而不是权威，改动范围要小而可回滚。

**岛屿数量（DFS）**：遍历整个网格，遇到值为陆地的格子就把计数加一，然后从该格出发做深度优先搜索，把与之连通的所有陆地都标记为已访问。标记可以直接把陆地改成水，省掉一个 `visited` 数组，也避免了重复访问；四个方向用方向数组统一处理，进入递归前先做边界与「是否为陆地」的判断。时间复杂度 O(m×n)，每个格子最多被访问常数次；空间复杂度最坏 O(m×n)（全为陆地时递归深度可达格子总数）。网格很大时把递归改成显式栈的迭代 DFS，或改用 BFS 逐层扩散，也可以并查集把相邻陆地合并后统计集合数量——并查集在需要动态加陆地（如「岛屿数量 II」）时更合适。

**为什么先讲思路再写代码**：面试官允许只写主体逻辑但要求讲解，说明考察点在于能否把问题抽象成「遍历 + 连通性标记」并说清边界。写之前先用一两句话定下算法与复杂度，写的时候把边界判断放在显眼位置，写完主动说明哪部分是主体、哪些工程细节（输入解析、异常处理）被省略，比闷头写完整代码更能体现工程判断。
