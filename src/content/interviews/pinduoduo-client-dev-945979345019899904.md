### 《参考解析》

**WebSocket 与 HTTP**：两者不是互斥的两套东西，WebSocket 建连的第一步就是 HTTP——客户端发 `Connection: Upgrade` 与 `Upgrade: websocket`（附 `Sec-WebSocket-Key`），服务端同意后回 `101 Switching Protocols`，此后这条 TCP 连接不再走请求-响应模型，转入 WebSocket 帧协议（opcode 区分文本 / 二进制 / ping / pong / close，客户端帧要掩码）。HTTP 的语义是客户端发问、服务端作答，即便 HTTP/2 有多路复用、服务端推送也仍然是请求语义；WebSocket 建连后双方对等，都可以主动发消息，适合聊天、实时通知、状态同步、进度推送。容易混的一点是「长连接」不等于 WebSocket：HTTP/1.1 的 Keep-Alive 也在复用 TCP，但每次通信仍是完整的请求与响应。还有一点常被忽略——WebSocket 不保证可靠：需要自己用心跳（ping / pong）判活、断了要重连、重连后要按序列号补拉断线期间漏掉的消息，并做消息去重。生产上真正复杂的从来不是建连，而是连接生命周期管理。

**JDK 8 的 HashMap 与红黑树**：数组下标由 `(n - 1) & hash` 决定，所以容量必须是 2 的幂，取模才能退化成位运算。JDK 8 之前冲突全走链表，一旦大量 key 落进同一个桶，查询就退化到 O(n)；JDK 8 在链表长度达到 8 且数组容量达到 64 时把桶转成红黑树，把最坏查询压到 O(log n)。注意「长度到 8」并不必然树化：容量还小的时候优先扩容，因为很多冲突本来就只是 table 太小造成的，扩容重排之后可能自然消失。一次 `get` 的路径是：先拿 key 的 hash 做扰动（高 16 位异或到低位，让高位也参与下标计算），定位桶；桶空直接 miss；桶首节点的 hash 与 key 都匹配就返回；否则看是树节点就走红黑树查找，是链表就顺序比对。扩容时还有个巧妙的优化：容量翻倍后节点新位置要么留在原 index、要么变成 `index + oldCap`，只需看 hash 中新增那一位是 0 还是 1，不必重算下标。

**Java 读写文件**：按数据形态分流——图片、压缩包、视频走字节流（`InputStream` / `OutputStream`），文本走字符流（`Reader` / `Writer`）或 NIO 的 `Files`。小文本可以 `Files.readString(path, UTF_8)` 一把读完；大文件绝不能 `readAllBytes()`，否则整个文件进堆，2GB 的文件在 1GB 堆里必然 OOM。标准写法是带缓冲的循环读：`BufferedInputStream` 套 `Files.newInputStream`，每次读 8KB 一块。要讲清缓冲的意义——它减少的是应用层频繁小块系统调用的次数，不是绕过操作系统的页缓存。大文件复制可以用 `FileChannel.transferTo / transferFrom`，某些路径下能减少用户态与内核态之间的拷贝，但算不算「零拷贝」取决于操作系统与 JDK 实现。写侧有个容易漏的点：`write()` 返回只代表数据进了 JVM 缓冲或页缓存，不代表落盘；日志、WAL 这类强持久化场景要显式 `flush()`、必要时 `FileChannel.force(true)`，而 fsync 的代价必须算进吞吐预算。

**CPU 不高但偶发卡顿**：CPU 不高恰恰说明瓶颈不是算力，而是线程在等。第一步不是改代码而是抓证据：连续取几次 thread dump，看卡顿窗口里线程都停在哪。大量线程 `BLOCKED` 指向锁竞争，需要看锁持有者的栈；大量 `WAITING` / `TIMED_WAITING` 则要区分是在等线程池任务、等 Future、等 Condition 还是等网络。典型病灶是主线程停在 `FutureTask.get()`，而这个 Future 跑的是网络请求——后台线程确实异步了，UI 线程又同步等结果，界面照样卡。第二块必须查 GC：平均 CPU 低不代表没有 Stop-The-World，频繁 Young GC 或一次长 Full GC 在用户侧就是间歇卡顿，用 GC 日志、JFR、jstat 看暂停时间和对象分配速率。第三块是 IO 与网络：磁盘慢、DNS 解析、socket read timeout 都会表现为「不耗 CPU 但没响应」。定位的关键是把线程状态、GC 时间点、IO 延迟对齐到同一条时间线上，而不是凭经验猜。

**输入 URL 到页面呈现**：先解析 URL（协议、域名、端口、路径、查询参数），查本地是否已有可复用连接。没有就解析域名：浏览器缓存 → 系统 hosts 与 DNS 缓存 → 本地 resolver → 递归查询权威服务器。拿到 IP 后建 TCP 连接（三次握手），HTTPS 再叠一层 TLS 握手（版本与密码套件协商、证书链校验、密钥交换）。之后才发出 HTTP 请求，中间可能经过 CDN、负载均衡、反向代理再到应用服务器。响应回来后浏览器解析 HTML 构建 DOM，遇到 CSS 构建 CSSOM，两者合成渲染树，再走布局与绘制；JS 可能阻塞解析（除非 async / defer），图片字体等资源继续加载。所以一次「回车」往往对应几十个请求，首屏时间由关键渲染路径上的资源决定，而不是单个 HTML 的返回速度。现代浏览器还会做 DNS 预取、连接预建、资源优先级调度，HTTP/2 与 HTTP/3（QUIC）则分别从多路复用和减少握手往返两个方向压缩这段耗时。
