### 《参考解析》

**1. ReAct 与 Plan 模式的区别**。ReAct 是「想一步、做一步」的交替循环：模型输出一段推理，调用一个工具，观察结果后继续推理，路径随执行结果动态调整，适合环境不确定、需要边查边改的任务。Plan 模式先让模型把整个任务拆成步骤清单，再逐步执行，好处是全局可控、步骤可审核可复用、能提前发现依赖冲突，代价是一旦环境与规划时的假设不符，整份计划都可能要重做。工程上常见的组合是外层 Plan 定框架、内层 ReAct 处理每一步里的不确定性。

**2. 短期记忆与长期记忆**。短期记忆就是当前会话的上下文窗口，实现上是消息列表加上必要的裁剪与摘要——上下文快满时把早期对话压缩成摘要，保留最近若干轮原文。长期记忆要跨会话，通常走「写入—检索」两条路：写入时把值得记住的事实抽取成结构化条目或向量存进外部库，检索时按当前 query 召回相关条目再拼进 prompt。关键的设计点是写入策略（什么值得记、去重与更新怎么做）和召回精度，而不是向量库选型。

**3. Kafka 的投递成功与不重不漏**。生产者侧设置 `acks=all` 并开启重试，配合 `enable.idempotence=true` 让 broker 用 PID + 序列号去重，实现生产端幂等；同时把 `min.insync.replicas` 调到 2 以上，避免只写到一个副本就算成功。顺序性只在单分区内成立，要保序就得按业务键指定分区键，让同一实体的消息落到同一分区，且消费者端 `max.in.flight.requests` 不要超过 1。消费侧要做到「至少一次 + 业务幂等」，不能指望 broker 保证恰好一次——业务层用唯一键或状态机去重才是可靠做法。

**4. Redis 主从切换导致锁丢失**。主从复制是异步的，主节点写入锁之后还没同步到从节点就宕机，从节点升主后这把锁就消失了，另一个客户端能同时拿到锁。处理方式分三档：接受风险但保证业务幂等（大多数场景够用）；用 Redlock 向多数派节点加锁，代价是延迟上升且仍有争议；改用 ZooKeeper、etcd 这类基于共识协议的协调服务，牺牲性能换严格的互斥语义。答题时把「最终还是要把下游操作用 fencing token 或唯一约束保护起来」讲出来，比只背 Redlock 更能加分。

**5. 一人一单的分布式锁**。先想清楚有没有必要上锁：如果数据库上有「用户 + 商品」的唯一约束，那么用 `INSERT ... ON DUPLICATE KEY` 或捕获唯一键冲突就能天然幂等，锁反而是多余的。真要上锁，用 `SET key value NX PX` 加锁、value 存请求唯一标识、Lua 脚本比对后再删，锁的粒度按用户而不是按商品，避免热点商品变成全局串行。再加一层「先查后写」的快速失败路径，把绝大多数重复请求挡在 Redis 层。

**6. TCP 为什么可靠**。可靠不是单点机制，是一整套配合：序号与确认保证不丢，超时重传与快速重传负责补，滑动窗口做流量控制，拥塞窗口（慢启动、拥塞避免、快恢复）防止把网络打爆，校验和发现传输错误，三次握手与四次挥手保证连接的建立和释放双方都确认到位。三次握手存在的意义是让双方都能确认「自己的发送和接收能力都正常」，并同步初始序号；两次做不到这一点。

**7. 模型成本与效果的平衡**。面试里要给出可执行的分层策略，而不是「用便宜的模型」这种空话：按任务难度路由到不同档位的模型（简单分类走小模型，复杂推理走大模型），能规则判定的先走规则；对结果做缓存与复用，相同的输入不重复调用；对准确率要求高的环节引入人工抽检或双模型交叉验证，把人工成本花在模型拿不准的少数样本上。同时要能答出「怎么衡量」——用离线评测集看准确率，用线上埋点看人工修正率，两个数字一起决定要不要升级模型。
