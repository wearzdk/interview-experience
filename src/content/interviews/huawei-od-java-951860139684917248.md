### 《参考解析》

**机考三题**：第一题是分割型动态规划或回溯，先预处理前缀和，再判断区间 ASCII 和是否为水仙花数（三位数各位立方和等于自身，如 153、370、371、407），注意 ASCII 和的范围与空子串处理。第二题是结构体排序，按总分降序、同分按规则（通常是编号或输入顺序）稳定排序，注意总分相同与并列名次的判定。第三题是二进制不进位加法，等价于按位异或，题目要求两人分得重量相等即异或和相等，且哥哥尽量大；先把所有数异或得到总异或，若不为 0 则无法均分，为 0 时把最高位的 1 分给哥哥一侧可使哥哥最大——本质是贪心加按位分组。机考的关键是先把题意与边界读清，再写可运行的暴力解并自测。

**RabbitMQ 异步解耦**：以判题系统为例，提交代码后先把任务写入数据库并投递消息，接口立即返回任务 ID；消费者拉取消息、执行判题、回写结果。好处是削峰（突发提交不压垮判题机）、解耦（提交服务不关心判题实现）、可重试与可扩展（加消费者即可扩容）。代价是要处理消息丢失（生产者确认、持久化、消费者手动 ack）、重复消费（幂等键 + 状态机）、顺序（同一题目的多次提交按用户维度保序）与积压监控。

**Redis 缓存**：适合缓存热点且读多写少的数据，如题目详情、用户信息、排行榜。更新策略常用 Cache Aside：读时未命中查库回填，写时先更新数据库再删除缓存（而不是更新缓存），并给缓存设过期时间兜底。穿透是查不存在的数据打穿到库，用布隆过滤器或缓存空值；击穿是热点 key 失效瞬间大量请求打到库，用互斥锁重建或逻辑过期；雪崩是大量 key 同时失效，给过期时间加随机抖动并做多级缓存。

**Docker 资源限制**：`--memory`、`--memory-swap` 限制内存，`--cpus` 或 `--cpu-quota`/`--cpu-period` 限制 CPU，`--pids-limit` 限制进程数，`--network none` 断网，`--read-only` 加 `--tmpfs` 限制写入，配合非 root 用户、seccomp/AppArmor 与 cgroup 版本确认。仅靠 Docker 隔离对不可信代码不够，通常还要叠加命名空间隔离、系统调用过滤与运行时限。

**JWT 与 ThreadLocal**：JWT 由 header、payload、signature 三段 Base64URL 组成，服务端用密钥验签并校验 `exp`、`iss`、`aud`，不依赖服务端会话。拦截器解析令牌后把用户信息放入 ThreadLocal，业务代码随处可取、无需层层传参；请求结束必须 `remove()`，否则线程池复用线程会导致用户信息串号与内存泄漏。

**设计模式**：工厂用于按类型创建不同实现（如不同语言的判题器），调用方只依赖接口；策略用于封装可替换的算法（如不同判题策略、不同计费规则），通过上下文选择；代理用于在调用前后加横切逻辑（权限、日志、缓存、事务）。回答要落到项目中的具体类与场景，以及「不加这个模式会怎样」。

**代码沙箱 API**：接口设计为提交任务（返回任务 ID）与查询结果两段式，提交接口幂等（客户端带请求 ID），结果接口返回状态机（排队、运行、成功、失败、超时）。高可用靠无状态服务多副本 + 队列缓冲 + 判题机池化，加限流与配额防止单用户刷爆；可观测性要有队列深度、判题耗时、失败率。

**防超卖**：Redis 侧用 Lua 脚本把「读库存 + 判断 + 扣减」做成原子操作，或用 `DECR` 后判断返回值小于 0 再回补；进一步用预扣库存 + 异步落库。数据库悲观锁（`SELECT ... FOR UPDATE`）一致性强但串行化、吞吐低；乐观锁（版本号或 `UPDATE ... WHERE stock > 0`）无锁等待、适合冲突少的场景，冲突多时重试成本高。实际系统常是 Redis 挡流量、数据库做最终一致性校验。

**强制终止**：协作式中断依赖被终止方配合，恶意代码可以忽略中断或死循环。更强制的方案是进程隔离（每次判题起独立进程或容器），超时直接 `SIGKILL` 杀进程组，配合 cgroup 限制资源；容器方案还能限制文件系统与网络。注意杀进程要杀整个进程组，避免子进程残留。

**判题可靠性**：消息队列的 at-least-once 语义要求消费幂等；判题机消费后先置「处理中」并记录租约，宕机后由超时扫描重新投递；结果写回用状态机加版本号，避免旧结果覆盖新结果。同时要有死信队列与人工补偿入口。

**亿级订单表**：数据库层做索引优化（用户 ID + 时间联合索引，避免回表）、分区（按时间或用户哈希）、冷热分离（历史订单归档到冷表或对象存储）、分页优化（用游标/上次最大 ID 代替大偏移量）。架构层做分库分表（按用户 ID 分片，保证同一用户订单落在同一库）、读写分离、把列表查询放到搜索或 OLAP 系统、对历史订单做异步导出。回答时先给查询模式，再给方案，避免直接说「分库分表」。

**排班手撕**：这是带约束的计数问题，用状态压缩 DP 或回溯加剪枝：状态为「第几天、上一组是谁、各组已安排次数」，约束是某些人只能在特定天、不能连续两天同一组。数据量小时回溯即可，注意输出方案数而不是方案本身，用记忆化避免重复计算。
