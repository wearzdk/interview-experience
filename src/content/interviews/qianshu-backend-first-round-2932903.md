### 《面试题目》

1. 自我介绍。
2. 讲一下你做的文件系统项目。
3. 现场用 20 多分钟、在一个 class 里复现项目的主要功能。

### 《参考解析》

**这道「现场复现」考的不是记忆力，是抽象能力**。一个两千多行、核心一千行的文件系统，面试官当然知道二十分钟写不完，他要看的是你能不能把系统拆成几层、每层的最小接口是什么、哪些是本质复杂度、哪些只是工程量。答「写不完」是对的，但只答这一句就浪费了这次机会——正确的反应是先接住约束，再给方案。

**文件系统的最小骨架其实只有五块**：块设备抽象（`read_block` / `write_block`）、超级块与 inode 表（记录文件元数据与块指针）、块位图（空闲块分配）、目录（名字到 inode 号的映射）、以及文件操作（create / open / write / read / unlink）。用一个 class 完全装得下：内部用几个数组或 `std::map` 代替磁盘结构，块设备用一段连续内存模拟，`write` 沿 inode 的块指针链追加、必要时分配新块，`read` 按偏移算出块号再拷贝出来。真正写起来不超过一百行，但它把设计讲清楚了——这就是面试官想看的「主要功能」。

**接这类题的正确开场是问清边界**：用什么语言、能不能用标准库容器、允许伪代码还是必须跑通、评分看结构还是看功能、时间从什么时候开始算。这几个问题的答案会直接改变写法：如果接受伪代码，就把接口和数据结构的定义写全、关键路径用注释标出；如果必须可运行，就先砍掉权限、日志、崩溃恢复，只保留 create / write / read 一条路径跑通。不问就埋头写，很可能在错误的粒度上耗光时间。

**被要求压缩时，主动提出分层交付**：第一层是接口签名和数据结构（三分钟），第二层是 create / write / read 主路径（十分钟），第三层是边界（块用完、文件跨块、重复删除、并发写）。边说边写，每写一个结构就说一句「这里我为什么用 inode 而不是直接存块列表」。面试官打断你也没关系，他打断的地方就是他关心的地方。

**项目讲述本身也要按这个结构组织**：目标与约束（支持多大文件、单机还是分布式、有没有崩溃一致性要求）→ 架构与模块划分 → 关键数据结构与算法（inode 布局、空闲块分配策略、目录查找）→ 难点与取舍（日志 vs 写时复制、缓存一致性、并发粒度）→ 怎么测的（断电模拟、fio、正确性用例）→ 如果重做会改什么。这条线讲完，面试官很难问出「你项目里到底做了什么」这种问题。

**最后一点判断**：要求二十分钟复现千行项目，确实不属于常见面法，有可能是压力测试，也有可能是面试官想快速确认项目是不是本人做的（自己写的能画出骨架，抄的只能背代码）。不管是哪种，抱怨都不产生价值，能当场把骨架画出来的人，反而会把这道「离谱题」变成加分项。面完可以如实记录这家公司的面试风格，作为后续投递的参考。
