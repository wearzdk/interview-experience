### 《参考解析》

**ConcurrentHashMap 与线程池：两个最容易被追问细节的八股**

ConcurrentHashMap 的答题线要按版本分开。JDK 1.7 是 Segment 数组加分段锁，每个 Segment 继承 ReentrantLock 并各自持有一个哈希表，并发度等于段数（默认 16），扩容只能段内做，段数固定导致内存开销大、并发度受限。JDK 1.8 取消分段，结构变成 Node 数组加链表加红黑树：写入空桶用 CAS 无锁完成，桶内冲突时只 `synchronized` 锁住该桶的头节点，锁粒度细到一个桶；链表长度超过 8 且数组长度达到 64 时转红黑树，查询从 O(n) 降到 O(log n)；扩容允许多线程协同迁移，靠 `ForwardingNode` 标记已迁移的桶让其他线程来帮忙搬；`size` 统计也换掉了 1.7 的「多次尝试加锁兜底」，改成 `baseCount` 加 `CounterCell` 数组分散热点计数。追问一般落在「为什么锁头节点」「为什么不允许 null 键值」：前者因为锁头节点就同时保护了该桶的链表操作，后者因为并发下无法区分「键不存在」与「值为 null」，而 `get` 又是无锁的。

线程池要答成一条任务流转链：提交任务后先看核心线程数是否已满，未满就新建线程；满了进阻塞队列；队列也满再看是否达到最大线程数，未达就扩容临时线程；再满才走拒绝策略（Abort、CallerRuns、Discard、DiscardOldest，默认 Abort，生产上常用自定义策略落库加告警）。配套要讲清：为什么不用 `Executors` 的几个快捷工厂（固定线程池用无界队列会 OOM、缓存线程池线程数不受控），参数怎么估（CPU 密集接近核数加一，IO 密集按「等待时间/计算时间」的比值放大），以及监控（活跃线程数、队列长度、拒绝次数这三个指标比日志更早暴露问题）。被问「线程池里的异常去哪了」时答：`execute` 会抛到未捕获异常处理器，`submit` 会被包进 Future 吞掉，所以要么显式 `get`，要么在任务内部兜异常——这是实际排障时踩过的坑。

**Redis 数据结构与消息队列的选型**

Redis 的结构题不要只报类型，要顺手把底层编码和适用场景带上：String 适合缓存对象序列化、计数器（`INCR` 原子）与分布式锁（`SET NX PX`）；Hash 适合存对象的字段并单独更新（小对象用 listpack 编码，省内存）；List 是双向链表，可以做简单的队列与最新列表；Set 做去重与交并集（共同好友、标签）；ZSet 靠跳表加哈希，是做排行榜、延时队列（score 存时间戳）的首选；再往上是 Bitmap（签到、活跃位图）、HyperLogLog（基数统计，误差可接受时省内存）、GEO 与 Stream（消费组语义的轻量消息队列）。要能说出 listpack/quicklist/skiplist 这些编码以及元素数量或长度超阈值后会转换，这类细节是拉开差距的地方。

消息队列的选型要落到「可靠性和吞吐要求」上。Redis 的 List 是最简单的生产者消费者，但没有消费确认，进程挂了消息就丢；Pub/Sub 不持久化、离线即丢；真要当队列用应该用 Stream，它有消费组、ACK 与 pending 列表，能做重投。Kafka、RocketMQ 这类专业队列解决的是持久化、堆积、顺序与重放：分区数决定并行度，同一个 key 落同一分区才有局部顺序，所以「订单要按用户维度保序」这类需求是靠选 key 实现的；可靠性由 acks、副本数与 ISR 保证，生产端开幂等、消费端做去重（业务唯一键或偏移量落库）才能真正做到「至少一次」下的业务正确；堆积的排查路径是先看消费 lag、区分是生产突增还是消费变慢，再决定扩分区、扩消费者还是优化消费逻辑。答题时可以主动说一句：选型的判据是「能不能接受丢、能不能接受重、要不要顺序、峰值和均值差多少」，比直接报产品名有用。

**下单幂等与防重复：从令牌到唯一索引的分层设计**

这道场景题的答法是从外到内分层，先给结论再解释每一层的必要性。第一层是客户端防抖与按钮置灰，它只改善体验，绝不能当防线（网络重试、用户多开、接口被直接调用都能绕过）。第二层是服务端令牌：进入下单页时向服务端申请一个一次性 token，提交时在 Redis 用 Lua 脚本原子地「查并删」，重复提交拿不到 token 就被挡在业务逻辑之外，这一层解决的是同一用户短时间内的重复点击与重试。第三层也是最关键的一层——业务幂等键加数据库唯一索引：为每次下单生成一个业务唯一号（客户端请求号、或「用户 + 商品 + 活动」的业务组合键），订单表上建唯一索引，插入冲突就说明重复，直接返回已存在的订单；因为只有数据库的唯一约束在并发下是不可绕过的，所以它是最终兜底，别的层都只是减少无效流量。第四层是并发下的状态控制：用状态机约束订单状态迁移，配合乐观锁版本号或 `update ... where status = 待支付` 这种条件更新，避免同一订单被支付回调与超时关单同时改；用分布式锁时锁的粒度要按用户或订单号而不是全局，且必须有超时与续期，并且要清醒地认识到锁只能降低冲突概率、不能替代唯一索引。

还要覆盖几个真实变体，面试官常顺着追问：支付与退款回调天然会重复投递，靠「回调流水号 + 处理结果表」做幂等；超时场景下客户端已超时但服务端实际成功，正确做法是用请求号回查订单而不是重新下单；如果用消息队列削峰，消费端必须按业务单号去重，因为至少一次投递一定会带来重复。把这些说全，比只答一句「加分布式锁」高一个层次。

**实习中用 AI 怎么保证需求实现的准确性**

这题考的其实是工程纪律，而不是你对工具熟不熟。可以按四步讲。第一，需求先由人写成可验收的规格：输入输出、边界条件、异常分支、数据口径、以及验收标准，先有这份「判定标准」再让 AI 动手，因为 AI 最擅长的是实现而不是替你澄清需求。第二，让 AI 先产出方案与影响面清单（改哪些文件、涉及哪些上下游、有哪些假设），人 review 过方案之后再让它写代码，把「想」和「写」分开，能挡掉大部分返工。第三，把 AI 的产出放进已有的质量闸门里：单测与边界用例先定好，生成的代码必须过 lint、类型检查、评审，关键路径人工复核；同时要求它标出不确定的假设，对拿不准的地方用文档或实验去验证，而不是接受一个看起来合理的解释。第四，小步提交、可回滚，并对效果做度量——返工率、缺陷密度、交付周期与之前对比，别只说「效率提高了」。

一句话总结可以放在最后：把 AI 放进既有的工程约束里，而不是为了让 AI 好用来放宽约束。反过来讲「哪些场景不交给 AI」也很有说服力，比如涉及权限、资金、数据删除的逻辑，以及团队没有测试覆盖的历史代码，这些地方的正确性无法快速验证。

**八股之外的节奏提醒**

这轮面试只有四十分钟且明确说了「八股很常规、项目不深挖」，说明对方的考察重心在表达与工程判断：八股题要答得短而准，主动停在自己有把握的边界上，别为了凑时长展开没把握的细节；场景题和 AI 相关的开放题才是真正拉开差距的地方，答的时候把「分层防御」「以数据库约束为兜底」「先有验收标准再有实现」这类原则摆出来，再补一两个自己踩过的具体例子，比堆砌名词更有效。八股没答上来也不必纠缠，直接说清自己知道的那部分和不确定的边界，把时间留给开放题。
