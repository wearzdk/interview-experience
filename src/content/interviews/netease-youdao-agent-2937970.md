### 《参考解析》

**cordis 的热加载属于工程层面**：JavaScript 语言本身没有「卸载模块」的语义，`require` 缓存只能删除引用，模块执行时注册的定时器、事件监听、全局变量不会自动消失。所以插件框架要做的是在工程层提供生命周期——把插件注册的一切副作用包装成可撤销的 effect，卸载时统一 dispose，再重新加载新版本模块。判断依据是「换掉插件后进程不重启、旧副作用消失」，这靠的是依赖注入容器加生命周期管理，不是语言特性。卸载后能否回到初始状态，取决于插件是否把所有副作用都登记为可撤销；漏登记的（比如直接 `setInterval`、写全局单例）就会残留。

**记忆分四类，别只答「向量库」**：按持续时间和作用分——工作记忆（当前上下文窗口内的消息与工具结果）、情景记忆（历史会话与事件，按时间或任务索引）、语义记忆（事实与知识，通常向量化或结构化存储）、程序记忆（怎么做事的技能与提示模板）。主流实现是「短期上下文 + 长期存储 + 检索注入」：写入侧做摘要、抽取实体与事实、去重与冲突处理；读取侧按当前 query 做混合检索（向量 + 关键词 + 时间衰减），必要时多跳。

**多跳检索靠「查询分解 + 迭代检索」**：先把复合问题拆成有依赖的子问题，逐跳检索并用上一跳的答案改写下一跳的查询（IRCoT、Self-Ask 这类做法），每跳都要判断证据是否足够、是否需要回溯；工程上要控制跳数与预算，并保留每跳的证据链以便溯源。教育场景的典型多跳是「这个学生这道题为什么错 → 涉及哪个知识点 → 该知识点的前置概念是什么」。

**workflow 与 agent 的边界是「路径是否可预先枚举」**：步骤固定、可审计、要求稳定的用 workflow（编排图、状态机），例如批改、组卷、内容审核；需要根据中间结果动态决定下一步、工具组合不确定的用 agent，例如答疑、排障。实践里常用「workflow 骨架 + agent 节点」：外层用确定性流程保证可控，内层把开放决策交给模型。多 Agent 的适用条件是子任务可独立、上下文可隔离、收益大于通信成本；难点在上下文传递（传什么、传多少）、状态一致性、错误传播与调试。

**RAG 与文件系统做记忆的取舍**：RAG 的优势是写入即索引、按语义召回、跨用户隔离靠元数据过滤，缺点是更新与删除要同步索引、精确查询（按 id、按时间范围）不如结构化存储；文件系统适合让 Agent 自己组织长文档与工作区（读写、编辑、版本），但检索靠遍历与文件名，规模一大就退化成线性扫描。多租户场景下文件系统的问题更明显：目录隔离依赖路径拼接，越权只需构造一个相对路径，配额、并发写、备份与迁移都很难按租户切分；而 RAG 的隔离可以在检索层用 tenant_id 强制过滤，配合行级权限与加密。

**上下文动态注入控权限的本质是「能力随身份变化」**：把用户身份、角色、数据范围解析成一份权限清单，在构造系统提示与工具表时按清单裁剪——没有权限的工具根本不出现在上下文里，检索时在查询层加 tenant 与数据域过滤，而不是靠模型自觉不越权。效果衡量要看越权请求的拦截率、正常任务的完成率、以及注入后上下文的 token 增量；只报拦截率不看完成率，会把「全部拒绝」当成好结果。

**千万级用户的记忆系统要先做冷热分层**：热数据（最近会话、当前任务状态）放 KV 或内存并设 TTL；温数据（近几个月的事实与摘要）放向量库加元数据索引；冷数据归档到对象存储，按需回捞。写入侧做异步管道（消息队列 + 批量 embedding），读取侧做多级缓存与查询裁剪；按用户分片并限制单用户记忆条数与检索预算，避免头部用户拖垮集群。合规上要能按用户删除、导出与审计。

**「100 道错题」这类长上下文的处理**：不要全塞进窗口，先按知识点聚类，再按错误频次与最近时间排序，只把「高频错题 + 典型错因 + 对应知识点」注入；其余留作可检索索引，由模型按需查询。回答时给出「摘要层 + 索引层 + 原文层」的三层结构，并说明每层的 token 预算。

**模型输出错误脚本的兜底**：脚本生成后先做静态检查与沙箱试运行（限制文件系统、网络与执行时长），失败则把报错回灌给模型重试并限制次数；对不可逆操作要求人工确认，并保留上一版可用脚本用于回滚。并发高导致队列阻塞时，按优先级分队列、给交互式请求预留配额、对批量任务做限流与背压，必要时降级到同步小模型或直接告知用户排队时长。
