### 《参考解析》

**JSON 驱动的动态 UI 渲染与交互回传**

这套方案的本质是「模型产出受约束的结构，前端按结构渲染组件」。链路：模型返回带类型标识和参数的 JSON（组件名 + 属性 + 数据 + 动作声明），前端有一份组件注册表，按类型映射到真实组件；JSON 用 schema 或结构化输出约束，解析失败要有降级（提示重试、回退成纯文本），并把解析成功率、失败样本记进日志。交互回传是这套方案的难点：按钮的「动作」不能由模型自由编一个 URL，而应声明成后端预定义的动作标识，前端用映射表把动作 id 换成真实接口与参数，入参再按 schema 校验；用户编辑后的状态先落本地，再按动作提交到后端并落库，同时把用户改过的值回灌进会话上下文，保证模型下一轮看到的是最新状态。要能对比业界路线：OpenAI 的交互式组件依赖客户端预置组件与结构化输出，A2UI 这类方案把「组件描述 + 动作绑定」标准化，好处是前端不必为每个新组件发版、安全边界收敛在注册表内，代价是表达能力受注册表限制。面试官追问「UI 怎么和后端映射」，正确的回答是映射表与动作 id 由后端契约决定，模型只负责选择，不负责拼接口。

**流式渲染与增量输出的坑**

流式输出把「一次完整结果」拆成「边生成边渲染」，体验好但引入四类问题：结构不完整（JSON 流到一半不是合法 JSON，不能直接 `JSON.parse`，要用增量解析器或先按 Markdown 增量渲染再在结束帧替换成组件）、渲染抖动（卡片高度反复变化、闪烁，要靠占位骨架与最小高度约束）、顺序与依赖（后到的字段依赖前面的字段，要按声明顺序渲染并处理字段缺失）、以及错误可恢复性（流中断时要有明确的失败态与重试入口，而不是留下半张卡片）。工程上把「文本通道」和「结构通道」分开：Markdown 走增量渲染，结构化卡片走「先收完整帧再挂载」，并给每个可交互组件一个稳定 key，避免流式重渲染时把用户已经输入的内容冲掉。指标上要监控首字延迟、结构帧到达率、解析失败率与中断率，否则只看「流式很流畅」是自欺。

**MCP、Skill、CLI、plugin 的边界与加载策略**

四者解决的是不同问题：MCP 是工具与资源的接入协议，适合需要独立进程、统一鉴权、跨应用复用的能力（数据库查询、第三方 API）；Skill 是写给模型的说明文档与资源包，适合承载业务规则、流程步骤和多文件参考资料，本质上靠上下文生效；CLI 是最原始的形态，能力确定、可组合、可被脚本与人共用，适合本地确定性操作（构建、部署、代码生成）；plugin 是宿主应用的扩展点，由宿主加载并定义生命周期，适合与宿主深度耦合的能力（编辑器、IDE、浏览器扩展）。选型判据：能力是否需要跨应用复用、是否有凭据与权限边界、是否需要确定性执行。Skill 的组成一般包含元数据（名称与「何时使用」的描述）、正文指令（步骤、约束、输出格式）、可选脚本与参考资料，写法上把触发条件写在最前面、步骤可执行、边界写清。加载数量是硬约束：每个 Skill 的描述都进系统提示，几十个描述的 token 开销与选择噪声就很大，正确做法是分级——常驻少量高层索引，按需展开正文，用检索或显式路由选出候选；100 个 MCP 同理，靠命名空间、按会话授权和懒加载，只把当前任务相关的工具暴露给模型。「怎么让 Agent 精确匹配到 MCP」的答案是描述与命名要写清适用与不适用场景，并把工具选择纳入评测，而不是靠模型自己猜。

**Agent Loop 防死循环与 ReAct、Workflow、Replan 的适用场景**

防死循环不能只靠步数上限，要多层兜底：①重复检测，对「工具名 + 关键参数」做哈希，连续 N 次相同调用就中断；②无进展检测，比对每轮的状态或产物是否变化，长时间无变化即停止；③预算约束，同时卡步数、token 与墙钟时间；④错误熔断，同一个工具连续失败就换路或直接上报；⑤状态校验，要求每轮必须产生可验证的进展（新增信息、状态迁移），否则回退；⑥人工介入点，在关键写操作前暂停等确认。选型上：ReAct 适合信息获取路径不确定、需要根据反馈调整的开放任务，代价是轮次多、延迟与成本不可控；Workflow 适合步骤可枚举、要求可复现与可审计的流程；Replan 适合计划容易失效的场景（外部状态变化、长任务中途环境改变），代价是额外一次规划调用与上下文膨胀。回答时把判据说清楚（路径能否穷举、失败代价、实时反馈需求），比背定义更有说服力。

**从 URL 到页面的全链路与逐节点优化**

链路按顺序：DNS 解析 → TCP 握手（HTTPS 再加 TLS）→ 发 HTTP 请求 → 服务端处理并返回 HTML → 浏览器解析 HTML、构建 DOM 与 CSSOM → 遇到资源发起请求（JS 阻塞、CSS 阻塞）→ 执行 JS → 布局与绘制 → 合成上屏。逐节点优化：DNS 用 DNS 预解析、减少域名数、加长 TTL 与就近解析；连接层用 CDN 边缘节点、HTTP/2 多路复用、TLS 1.3 与会话复用、连接预热；请求层做资源合并与按需加载、缓存（强缓存与协商缓存、ETag）、压缩（gzip/brotli）、接口合并与并行；服务端做静态资源直出、SSR 或流式渲染、结果缓存；渲染层把阻塞脚本改成 defer/async、关键 CSS 内联、图片懒加载与预加载、避免布局抖动、用骨架屏提升体感。怎么测是这题的加分项：用 Lighthouse 与 WebPageTest 拿 Lab 数据、用 RUM 与 PerformanceObserver 拿真实用户的 LCP、INP、CLS，把优化前后按同一环境对比；再对照 Nginx 日志与服务端耗时把「网络慢」和「后端慢」分开，避免拍脑袋优化。批量图片请求的场景则答：合并成雪碧图或按需懒加载、用同一域名的 HTTP/2 连接复用减少建连、加缓存与 CDN 命中率、用响应式图片按屏幕尺寸取合适分辨率、通过预加载可视区图片拉齐首屏。

**手撕：闭包计数器与子序列计数**

闭包计数器用一个外层函数持有私有变量，内层函数每次调用自增并返回：`function A() { let n = 0; return function () { return ++n; } }`（题干是「A 每调用一次返回一、二、三」，等价写法是 `const A = (() => { let n = 0; return () => ++n; })()`）。要点是讲清闭包为什么能保住状态（内层函数持有对外层作用域变量的引用，外层执行完栈帧销毁但变量被引用而保留）、`var` 与 `let` 在循环里的差异、以及内存角度（闭包会让变量常驻，不再需要时置空引用避免泄漏）。「字符串 s 到子序列 t 的删除方案数」是标准的二维 DP：`dp[i][j]` 表示 s 的前 i 个字符中凑出 t 的前 j 个字符的方案数，边界 `dp[i][0] = 1`；当 `s[i-1] == t[j-1]` 时 `dp[i][j] = dp[i-1][j-1] + dp[i-1][j]`（用这个字符或不用），否则 `dp[i][j] = dp[i-1][j]`。先讲清状态定义与转移含义再写代码，并主动提边界（t 为空、s 比 t 短则结果为 0）与空间优化（只保留上一行），数据量大时注意取模。
