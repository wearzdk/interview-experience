### 《参考解析》

**Java 21 的主要变化**：Java 21 是长期支持版本，正式落地的特性集中在语法与并发两块。语言侧有 switch 的模式匹配（JEP 441）与记录模式（JEP 440），可以在 case 中按类型解构并配合密封类做穷尽性检查；集合侧引入 SequencedCollection（JEP 431），为 List、Deque、LinkedHashSet 提供统一的 first/last 与逆序视图。并发侧虚拟线程转正（JEP 444），结构化并发与作用域值仍为预览。运行时侧有分代 ZGC（JEP 439），把 ZGC 的分代假设补上以改善分配密集型负载的吞吐。此外还有密钥封装机制 API（JEP 452）、准备禁止动态加载 agent（JEP 451）与废弃 Windows 32 位 x86 移植（JEP 449）。回答时按「语法、并发、运行时」三层组织，比逐条罗列 JEP 编号更清晰。

**虚拟线程的适用边界**：虚拟线程由 JVM 调度到少量载体线程上，遇到阻塞式 IO 时卸载而不是占住载体线程，因此适合高并发、以等待为主的请求处理；创建成本低，不需要池化，用 Executors.newVirtualThreadPerTaskExecutor 按任务创建即可。边界同样明确：CPU 密集型任务不会因为换成虚拟线程而变快，反而失去池化带来的并发限制；依赖 ThreadLocal 缓存大对象会造成内存放大；Java 21 中在 synchronized 块内阻塞会钉住载体线程（该问题在后续版本通过 JEP 491 解决），高并发场景应改用 ReentrantLock；部分本地方法（如文件 IO 的某些路径）仍会钉住。被问到「有没有实际用过」时，应给出具体场景、压测数据与遇到的问题，而不是只描述原理。

**设计原则与落地例子**：常被问到的有单一职责、开闭原则、里氏替换、接口隔离、依赖倒置，配合高内聚低耦合与组合优于继承。举例要具体到改动前后：例如把订单导出的多种格式从 if-else 改为策略接口加工厂，新增格式只需增加实现类，满足开闭原则；把第三方支付回调的解析隔离在适配层，领域模型不依赖外部报文结构，属于依赖倒置与防腐；把一个承担查询、校验、落库的巨型服务拆成三个职责单一的类，属于单一职责。避免把「用了 Spring 所以符合依赖倒置」当作例子，框架只是手段。

**HashMap 的线程不安全**：并发写入时主要体现在三处。其一是扩容：JDK 7 的头插法在并发 rehash 时可能形成环形链表，后续 get 会死循环打满 CPU；JDK 8 改为尾插并对链表长度做树化，成环问题消失，但并发扩容仍可能丢失节点或让同一桶的数据互相覆盖。其二是 size 计数与 modCount：++size 不是原子操作，并发 put 会少计，fast-fail 的迭代器也可能误判。其三是可见性：一个线程 put 之后另一个线程未必立即读到，get 返回 null 并不代表键不存在。解决办法是改用 ConcurrentHashMap（CAS 加桶头 synchronized，只锁单个桶），或用 Collections.synchronizedMap 做整体加锁；读多写少且允许短暂不一致时也可以每个线程持有独立副本再合并。

**HashSet 与集合选型**：HashSet 内部就是一个 HashMap，元素作为 key、值统一为占位对象，因此去重依赖 hashCode 与 equals 的一致性：只重写 equals 不重写 hashCode 会导致重复元素被放进不同桶，去重失效。它不保证顺序，需要插入顺序用 LinkedHashSet，需要排序用 TreeSet（要求元素可比较或传入 Comparator）。并发场景没有现成的线程安全实现，用 ConcurrentHashMap.newKeySet 或 Collections.newSetFromMap。选型时把「是否需要顺序、是否允许 null、是否并发、查找复杂度要求」四个问题答清楚，比背底层结构更符合面试官的考察意图。

**RabbitMQ 的消费模式与顺序消费**：消费模式分推与拉：basic.consume 由 broker 主动推送，是默认方式，吞吐高；basic.get 由客户端轮询拉取，适合低频或按需取用。按消费关系又分竞争消费（同一队列多个消费者轮询分摊，用于削峰与并行）与广播（fanout 交换器把消息复制到多个队列，每个队列各自消费一份）。确认方式分手动 ack 与自动 ack，配合 prefetch 限制未确认消息数量，避免消费者被压垮。顺序性无法靠「开多个消费者」实现，可行做法是：同一业务键的消息路由到同一队列（按 key 哈希，或用一致性哈希交换器），该队列只部署一个消费者且 concurrency 为 1；消费端内部不再并行处理同一键的消息；重试与死信会打破顺序，需要串行重试或把失败消息暂存后按序补偿。集群与镜像队列只保证可用性，不改变单队列内的顺序语义。

**Redis 题的准备方向**：原帖未记录具体题干，从网易 Java 一面的常见问法看，Redis 通常落在四处。缓存三兄弟：穿透（查询不存在的数据，用布隆过滤器或空值缓存）、击穿（热点键过期瞬间大量请求落库，用互斥重建或逻辑过期）、雪崩（大批键同时失效，用过期时间加随机抖动与多级缓存）。缓存与数据库一致性：旁路缓存下先更新库再删缓存，配合延迟双删或订阅 binlog 补偿，强一致要求高时不宜把缓存当唯一数据源。分布式锁：SET NX PX 加锁、Lua 脚本比对值后释放、续期与锁超时的取舍。持久化与淘汰：RDB 与 AOF 的差异、maxmemory-policy 的选择、大 key 与热 key 的识别与拆分。

**手撕与反问**：一面手撕通常是一道中等难度的数组、字符串、链表或二叉树题，也可能要求用两个线程交替打印。作答时先说思路与复杂度，再写代码，边界条件（空输入、单元素、重复值、整型溢出）主动说明，写完后自己举一个用例走一遍。反问环节问工作内容与对新人的预期，可以进一步落到具体方向：团队当前业务、新人前三个月通常承担什么、代码评审与发布流程、是否有导师制。这类问题既确认匹配度，也让面试官看到对岗位的真实关注。
