### 《参考解析》

**本体化 Action 解决的是「接口给不了模型的东西」**。原有 HTTP / JSF 接口是给工程师看的：方法名是技术语义、入参是技术类型、组合是否合法只写在文档和代码里。直接把这类接口当工具暴露给模型，模型不知道业务含义、不知道哪些参数组合有效、也不知道调用的副作用与权限边界，只能靠提示词猜。领域对象（本体）提供统一的概念与关系，解决同名异义、异名同义；Action 在接口之上包一层模型可理解的意图、收敛过的入参 Schema、副作用与权限声明，再映射到底层 HTTP / JSF 调用。回答「选一个 Action 讲完整链路」时按「业务入口 → 参数校验与鉴权 → 领域对象组装 → 底层服务调用 → 结果归一化 → 落库与审计」这条线讲，每一步说清自己改了什么、为什么这样改。

**Action 与 MCP 的区别**：MCP 是「工具如何被发现、描述与调用」的协议，解决的是连接与互操作；它不负责业务语义建模、参数收敛、权限与治理。Action 是业务侧的语义封装层，可以经 MCP 协议暴露，但两者不在一个层面。面试官追问「是不是差不多」，要点是：MCP 让工具可被调用，Action 让工具可被正确、安全地调用。工具市场同理——发布与安装只是分发问题，真正难的是版本兼容、权限授予、调用配额和回滚。

**Action 的权限控制要分三层**：① 功能层，谁能调用哪个 Action（RBAC / 应用授权）；② 数据层，同一次调用能看到哪些行、哪些字段（租户隔离、数据权限过滤），敏感字段在返回前脱敏；③ 执行层，下游服务再做一次鉴权与参数校验，不能只信上游或提示词。审计记录调用者、入参摘要、命中的数据范围与结果，便于追责。Prompt 层的「不要访问敏感信息」不是安全边界。

**AI 编程如何减少交互轮次**：轮次多的根因通常不是模型笨，而是任务边界不清、上下文不足、反馈太慢。可做的有四件事。① 把需求写成可验收的规格：输入输出、边界条件、不许改的文件、验收命令。② 给足上下文：相关代码、既有约定、同类实现示例，而不是让模型自己猜架构。③ 把判断交给可执行校验：类型检查、lint、单测、契约测试、构建与回放，让模型在闭环里自己改到绿，而不是人去逐轮读 diff。④ 拆小步：一次一个可独立验证的改动，提交信息与计划先对齐。所谓「两三轮做到 99%」在开放需求上不现实，能做到的是把「正确性」外化成测试与门禁，人只审关键决策与最终 diff；这一点要如实回答，别承诺一个兑现不了的准确率。

**点赞事件重复与乱序：关键是把「状态」改成「可引用的事件」**。作者最初的方案是二态点赞（同一用户对同一文章只有赞 / 未赞），用 eventId 去重、版本号过滤旧事件。这个方案在「允许多次点赞」的语义下不成立：先赞、再取消、再赞时，取消到底撤销哪一次赞，版本号答不出来。正确的建模是：每一次点赞生成一个独立的 `likeId`（由客户端生成，作为幂等键），取消事件必须携带它要撤销的 `likeId`；同一 `(userId, articleId)` 上维护单调递增的 `seq`，服务端按 `seq` 排序。消费侧三件事：① 幂等，`eventId` 唯一索引，重复投递直接丢弃；② 有序，同一聚合键的 `seq` 有缺口时暂存（Redis ZSET 或 MQ 单分区单键），等前置事件到达再回放，超过超时阈值则回查源状态补齐；③ 可恢复，事件先落流水表（append-only），计数由「基线快照 + 增量回放」得到，而不是直接 `+1/-1` 更新一个数。展示层「我有没有赞」取该用户最新有效事件，总赞数取聚合结果，两者允许短暂不一致但必须最终一致。

**这场面试的分歧点值得记住**：面试官先给了「点赞、取消、再点赞」的场景，作者按二态点赞回答，被明确纠正「有些业务允许多次点赞，正向与逆向操作之间应当有对应关系」。遇到这类开放设计题，第一步不是急着给方案，而是先把业务语义问清：是二态还是可重复点赞、是否要求实时准确、事件由谁产生、是否允许延迟。语义不同，方案完全不同；先确认再设计，比事后补字段更能体现工程判断。
