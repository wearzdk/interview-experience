### 《参考解析》

**HTTPS 与 HTTP 的差异**：HTTP 是明文传输，HTTPS 是 HTTP 加上 TLS，提供加密、完整性校验与身份认证。连接过程的差异在于多了一次 TLS 握手：TCP 三次握手之后，客户端发 ClientHello（支持的版本、密码套件、随机数、SNI），服务端回 ServerHello（选定的套件、随机数）与证书链，客户端校验证书（链式信任、域名匹配、有效期、吊销状态），然后用密钥交换算法协商出会话密钥（RSA 密钥交换已不推荐，现用 ECDHE 提供前向安全），双方发 ChangeCipherSpec 与 Finished 完成握手，之后才传 HTTP 报文。TLS 1.3 把握手压缩到 1-RTT（会话复用可 0-RTT），并移除了不安全的套件。性能代价是握手延迟与加解密开销，优化手段是会话复用（session ticket）、TLS 1.3、OCSP stapling、以及连接池复用。

**Java 内存管理与栈**：JVM 内存分线程私有的程序计数器、虚拟机栈、本地方法栈，与线程共享的堆、方法区（元空间）。栈按帧组织，每帧存局部变量表、操作数栈、动态链接、返回地址；基本类型与对象引用存在栈上，对象本体在堆上。栈是线程私有的，随方法调用入栈出栈，生命周期确定；堆由 GC 管理。应用场景上要能区分：递归过深或局部变量过大导致 `StackOverflowError`；对象创建过多导致堆增长与 GC 频繁；逃逸分析可以让未逃逸的对象在栈上分配（标量替换），这是 JIT 的优化而不是语言保证。

**循环引用与可达性分析**：Java 的引用计数并不是 GC 的依据，主流收集器用可达性分析——从 GC Roots（栈上的引用、静态变量、常量、JNI 引用等）出发标记可达对象，不可达的才回收。因此两个对象互相引用但都不可达时会被一起回收，不存在循环引用导致泄漏的问题。这与引用计数方案（如 Objective-C 的 ARC、Python 的引用计数）不同，后者需要弱引用或手动打破循环。iOS 侧的循环引用（block 捕获 self、delegate 强引用）要靠 `weak`/`unowned` 解决，这一点在跨平台对比时容易被问到。

**HashMap 的应用场景**：按 key 做 O(1) 查找与去重——缓存、计数（词频）、索引（id 到对象的映射）、分组聚合、去重、以及作为集合运算的基础。要注意它的限制：非线程安全（并发写会丢数据甚至死循环，1.8 已修复死循环但仍不安全）、无序（需要顺序用 LinkedHashMap，需要排序用 TreeMap）、key 必须正确实现 `hashCode` 与 `equals`、扩容时有一次性开销（可预设初始容量避免反复扩容）。

**同步/异步、串行/并行**：同步是调用方等待结果返回才继续；异步是发起后立即返回、结果通过回调或 Future 通知。串行是任务按顺序一个接一个执行（单线程队列）；并行是多个任务在同一时刻真正同时执行（多核多线程）。组合起来有四种典型形态：串行同步（最简单）、串行异步（单队列加回调，如 iOS 的主队列）、并行同步（多线程各自阻塞，容易耗尽线程池）、并行异步（任务提交到线程池，回调通知）。举例要具体：网络请求是异步（发起后不阻塞主线程），数据库连接池的查询是并行（多个连接同时执行），而 UI 更新必须回到串行主队列。iOS 里对应 GCD 的 serial queue 与 concurrent queue。

**乐观锁与悲观锁**：悲观锁假设冲突频繁，读写前先加锁（`SELECT ... FOR UPDATE`、`synchronized`），保证强一致但并发度低、有死锁风险。乐观锁假设冲突少，读时不加锁，写入时校验版本号或 CAS（`UPDATE ... SET version = version + 1 WHERE id = ? AND version = ?`），冲突则重试；收益是读多写少场景下吞吐显著提升、无长期持锁。代价是冲突高时重试成本上升、以及 ABA 问题（用版本号而不是值比较可避免）。验证改动是否正向要有对照：同一压测脚本、同一数据量与硬件，比较改动前后的 QPS、P99、冲突重试率与错误率；只看 QPS 上升不够，还要确认数据正确（无超卖、无丢失更新）。回答「QPS 是多少」要报具体数字与测试条件，没有实测就如实说未做压测。

**AI Coding 占比怎么答**：给出估算口径（按新增代码行、按提交数、或按功能点），说明哪些部分用它（模板代码、测试、脚本）与哪些不用（核心逻辑、涉及安全与并发的部分），并补一句质量保障（评审、类型检查、单测）。只报一个百分比而不说口径，会被追问到底。
