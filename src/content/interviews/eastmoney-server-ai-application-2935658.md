### 《参考解析》

Text-to-SQL 的准确性要拆成两层答：SQL 语法正确不等于业务正确。落地做法通常是「schema 精简 + 检索式召回」——不把整库表结构塞进 prompt，而是先按用户问题召回相关表和字段注释，再让模型生成；执行前过一遍语法与权限校验（只读、超时、行数上限、禁止 DDL），执行后把结果与问题对齐检查（行数为空、字段错位、聚合单位不符都是常见失败面）。想再进一步就是建 golden set：把历史上问过的问题和人工确认的正确 SQL 存下来，改一次 prompt 或换一次模型都跑这批回归，用执行结果一致率而不是人来肉眼判断。

多表关联的难点是模型不知道该 join 哪张表。实用的解法是在元数据里补「业务语义层」：表与表的关系、常用 join key、指标口径（GMV 到底算哪张表哪个字段），把裸 DDL 变成带注释的可检索知识；检索时按问题召回 join 路径而不是召回全量表。只靠 SQL 表达不了的复杂计算，正确方向是把模型的能力边界划清——让它生成可执行的分析计划（取数 + 计算步骤），把计算交给代码或 Pandas/数仓函数，而不是硬拧成一条巨长的 SQL。

多轮上下文的平衡点在于「状态外置」：把已确认的筛选条件、指标、时间范围抽成结构化槽位，每轮只带槽位和最近一两轮对话，历史原文按需检索而不是全量拼接；话题切换用分类器或轻量判断（新问题是否引用了上文实体）来分流，切换后清空槽位。这套做法同时解决了上下文膨胀和旧上下文污染。

MCP 工具一多，最先坏的是选择准确率：几十个工具塞进 prompt，模型会挑错工具、漏传必填参数，token 成本也线性上涨。工程上的处理是分层——按场景把工具分组、只暴露当前任务相关的一组，工具描述写成「什么时候用/不用」，配合后端做参数校验与幂等，失败时把结构化错误回给模型让它自我修正。Java 做 AI 应用的优势在工程侧（线程模型成熟、生态和治理完善、和公司既有服务同栈），劣势在新框架与 SDK 更新滞后、Python 侧的实验生态更全，答的时候给出你们场景下的取舍比站队有用。

八股部分都是常规考点。LEFT JOIN 那条要答准：ON 里的条件只影响右表能否匹配上（匹配不上仍然保留左表行，右表字段为 NULL），WHERE 里的条件是在 join 结果上过滤，会把本该保留的左表行一起过滤掉，所以两者结果通常不同；要把右表的筛选当成「匹配条件」就放 ON，要过滤最终结果就放 WHERE。MyBatis 的动态 LIKE 用 `concat('%', #{kw}, '%')` 或 `bind` 拼，别用 `${}`；多参数 IN 用 `<foreach collection="list" item="id" open="(" separator="," close=")">#{id}</foreach>`。JVM 排查就是 jps 定位、jstat -gcutil 看各区占用与 GC 频率、jmap dump 配合 MAT 找大对象、jstack 看线程栈，回答时把「先看什么指标、再拿什么证据」的顺序讲出来。

二面那句「怎么定位是意图、模型、Prompt 还是知识库的问题」是整场最有含金量的一题：正确答法是分而治之——先把一次请求的各段产物留痕（识别出的意图、召回的文档与分数、最终 prompt、模型原始输出），再逐段单独回放：换一个确定的意图看下游是否正常，换一份确定的知识看生成是否正常，用离线样本跑同一 prompt 看模型稳定性。有这套链路，故障定位从猜变成查。

HRBP 那一轮作者自己复盘「答得太烂」，问题出在公司功课没做：金融行业认知、东方财富与天天基金的业务差异、为什么异地实习，这些都不是临场能编的。准备方法是面试前把公司财报或产品线过一遍，准备两三个能对上岗位的真实观点，比背企业愿景有效。
