### 《参考解析》

**AI 工具怎么用**：按场景分层说——写代码用 IDE 内的补全与对话，读陌生代码库用能检索全仓的 Agent，写文档与总结用长上下文模型，查资料用带联网检索的工具。讲一个具体流程比列工具名更有说服力：先让模型读相关文件、产出计划，人审计划，再分步实现、每步跑测试。

**AI 拆分任务不准怎么处理**：任务拆错通常有三个原因：上下文不足（模型不知道代码结构）、目标模糊（验收标准没写）、任务粒度太大。处理办法是把「评估」前置——先让模型输出计划与它需要的上下文，人工补齐缺失信息；再把任务切成「一次改动能在十分钟内验证」的大小；执行中用编译、单测、lint 做即时反馈，失败就把错误原文回灌给它重试；最后用固定的一组任务做回归，比较改动前后的成功率与返工次数。

**ES 深分页**：`from + size` 深翻页时每个分片都要取出 `from + size` 条再全局排序，越翻越慢且有 `max_result_window`（默认 10000）限制。方案：`search_after`（用上一页最后一条的排序值做游标，适合顺序翻页、不支持随机跳页）；`scroll`（快照式遍历，适合导出，会占资源、不能实时）；`point in time + search_after`（PIT 保持索引视图一致，官方推荐）；业务上限制最大页数、或改成「按时间/ID 范围过滤」而不是纯 offset。讲优化效果要带数字：P99 从多少降到多少、命中多少 QPS、集群负载变化。

**性能变慢怎么排查**：先分层定位——入口看监控（RT、QPS、错误率、超时），应用看线程栈（`jstack`）、GC 日志、慢 SQL、外部依赖耗时，系统看 CPU、内存、IO、网络（`top`、`vmstat`、`iostat`、`ss`），中间件看 Redis 慢查询、MQ 积压、ES 慢日志。方法上先做「时间线对齐」：变慢从几点开始、之前有没有发布/配置变更/流量变化；再做「单请求拆解」：把一次请求的各段耗时打点，找出占比最大的那一段。避免一上来就调参数。

**缓存三兄弟**：穿透是查一个不存在的 key，每次都打到数据库——缓存空值（短 TTL）或布隆过滤器前置拦截。击穿是热点 key 过期瞬间大量请求同时回源——加互斥锁只放一个请求重建，或用逻辑过期 + 异步刷新，热点 key 也可以预热、永不过期。雪崩是大量 key 同时过期或缓存集群挂掉——过期时间加随机抖动、多级缓存、缓存集群高可用、限流降级兜底。

**事务一致性**：单库靠本地事务（`@Transactional`，注意传播行为、自调用失效、异常回滚规则）。跨服务靠分布式事务（2PC/Seata AT、TCC、Saga、本地消息表 + MQ）。缓存与数据库之间没有事务，只能靠「先写库再删缓存 + 延迟双删 + binlog 订阅 + 对账」把不一致窗口压小。帖主答的「分布式锁 + 数据库乐观锁」是并发控制手段，能防并发写冲突，但不等于事务一致性，回答时要把两者分开。

**设计模式**：不要背 23 种。挑项目里真用过的讲：策略模式（多种计费/风控规则）、工厂 + 注册表（按类型创建处理器）、模板方法（流程固定的业务骨架）、责任链（审批/过滤链）、观察者（事件解耦）、单例（Spring 默认单例，注意无状态）。每个都说清楚「解决了什么、代价是什么」。

**线程池**：七个核心参数——核心线程数、最大线程数、空闲存活时间、时间单位、工作队列、线程工厂、拒绝策略。执行顺序是「核心线程 → 队列 → 扩展到最大线程 → 拒绝」。参数怎么定：CPU 密集型接近核数，IO 密集型按「核数 × (1 + 等待时间/计算时间)」估算，但最终要靠压测。必须用有界队列 + 自定义线程工厂（带业务名，方便排查）+ 明确的拒绝策略（CallerRuns 或降级），并且监控活跃线程数、队列长度、拒绝次数。

**JVM 优化**：先有指标再谈优化。常见动作：根据堆大小与对象存活特征选收集器（低延迟场景 G1/ZGC），设置 `-Xms=-Xmx` 避免动态扩缩，合理设置新生代比例与晋升阈值，用 `-XX:+HeapDumpOnOutOfMemoryError` 保留现场，用 MAT 分析 dominator tree 找大对象。真正的优化往往在代码层：减少临时对象、避免大对象直接进老年代、控制缓存大小。调参前先看 GC 日志的停顿分布。

**Flink 实时性**：Flink 是事件驱动的流处理，靠「事件时间 + 水位线（watermark）」处理乱序，靠 checkpoint 做 exactly-once（barrier 对齐 + 状态后端），靠反压机制（信用制/背压）自适应下游速度。「保证实时性」落到工程上是：端到端延迟监控（source 到 sink 的时间差）、并行度与 slot 配置、状态大小控制（用 RocksDB 增量 checkpoint）、水位线延迟容忍度设置、以及算子链与网络缓冲调优。

**高并发系统怎么评估与设计**：先量化目标——QPS、并发连接数、P99 延迟、数据量、读写比、可用性要求。然后分层设计：接入层 CDN + 负载均衡（DNS/GSLB、Nginx/LVS）、静态资源就近分发；应用层无状态 + 水平扩容 + 限流熔断降级；缓存层多级（本地 Caffeine + Redis 集群），热点隔离；数据层读写分离、分库分表、索引优化、冷热分离；异步层 MQ 削峰、任务队列；最后是容量评估（按峰值 × 冗余系数）、压测验证、故障演练与降级预案。帖主复盘说「应该从 CDN 说起、多重缓存设计」，方向是对的——高并发面试要按请求链路从外到内讲，而不是从线程池讲起。
