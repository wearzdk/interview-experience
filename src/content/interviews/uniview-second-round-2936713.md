### 《面试题目》

**一面（常规八股）**

1. Redis 常见缓存问题（穿透 / 击穿 / 雪崩）及其解决方案。
2. MySQL 优化。
3. HashMap 的底层原理。
4. 常见集合类型及区别。
5. 悲观锁与乐观锁。
6. Spring 三级缓存。
7. AI 开发的使用习惯与规范。
8. 项目 / 实习简单问一下。

**二面（HR 面）**

1. 能不能加班？（公司有每周固定加班）
2. 对无普调的了解与接受程度。
3. 期望薪资。
4. 其他常规 HR 问题。

结果：表现犹豫，回答「接受偶尔加班」，让等通知，随后收到感谢信，挂了。

### 《参考解析》

**这场面试最值得复盘的不是八股，而是 HR 面的预期管理。** 公司明确说了「有每周固定加班」「无普调」，这不是在闲聊，而是在确认你入职后会不会因为这两点离职。回答「接受偶尔加班」在对方听来等于「我不接受你们这种加班」，而这类岗位的招聘成本很高，HR 会直接选择预期更匹配的候选人。正确的做法不是硬说「我特别爱加班」，而是给一个有条件的、可信的接受：先确认节奏（「是项目期集中加班，还是常态每周固定几天」），再表达自己的判断（「如果是项目交付期的强度，我可以配合；我也会通过提前拆解任务来减少无效加班」）。既不撒谎，也不把话说死。

**「无普调」这类信息要当场问清而不是含糊过去。** 可以问「调薪机制是怎样的——是只有晋升才调，还是有年度评审」，把不确定性变成具体规则，再决定自己能不能接受。薪资问题给区间而不是死数，并说明依据（同岗位市场行情 + 自己的实习与项目经历）。

**Redis 三大缓存问题要一次答完「现象—原因—方案」。** 穿透是查不存在的数据，请求全打到数据库，方案是缓存空值（带短 TTL）、布隆过滤器、接口层参数校验；击穿是某个热点 key 过期瞬间大量请求打库，方案是互斥锁/单飞（只让一个请求回源，其余等待）、逻辑过期 + 异步更新、热点 key 永不过期；雪崩是大量 key 同时失效或缓存集群故障，方案是过期时间加随机抖动、多级缓存、缓存高可用与熔断降级、预热。再补一致性：先更新数据库再删缓存（Cache Aside），延迟双删应对主从延迟，强一致场景用 canal 订阅 binlog 异步刷新。

**MySQL 优化按「SQL—索引—表结构—架构」四层讲。** SQL 层：避免 `select *`、避免在索引列上做函数运算与隐式类型转换、用 `explain` 看 type/rows/Extra（出现 `Using filesort`、`Using temporary` 要警惕）；索引层：联合索引遵循最左前缀、区分度高的列在前、覆盖索引减少回表、避免冗余索引；表结构层：字段类型尽量小、大字段拆表、冷热分离；架构层：读写分离、分库分表、缓存。要能说出「索引不是越多越好」——写入要维护索引、优化器选择成本也会上升。

**HashMap 要讲到「结构 + 扩容 + 树化 + 并发问题」。** JDK 1.8 是数组 + 链表 + 红黑树，哈希扰动函数把高位参与运算减少碰撞，索引用 `(n-1) & hash`；默认容量 16、负载因子 0.75，超过阈值扩容为两倍并重新分布（1.8 用高低位拆分，避免重新计算 hash）；链表长度到 8 且数组长度 ≥ 64 才树化，退化阈值是 6，取这两个数是为了在泊松分布下兼顾查询效率与转换开销；HashMap 线程不安全（1.7 扩容可能成环，1.8 会丢数据），并发场景用 ConcurrentHashMap（1.8 用 CAS + synchronized 锁单个桶）。

**常见集合按「是否有序、是否可重复、是否线程安全、底层结构」做表。** ArrayList（数组、随机访问快、扩容 1.5 倍）、LinkedList（双向链表、头尾操作快、随机访问慢）、HashMap / LinkedHashMap（插入序或访问序）/ TreeMap（红黑树、按 key 排序）、HashSet / TreeSet、ArrayDeque（双端队列，做栈和队列都比 Stack/LinkedList 好）、ConcurrentHashMap、CopyOnWriteArrayList（读多写少）。被追问时能说出「为什么 ArrayDeque 不适合存 null」「CopyOnWrite 的写时复制代价」就够深了。

**悲观锁与乐观锁的区别在「什么时候加锁」。** 悲观锁假设冲突一定会发生，读写前先加锁（数据库的 `select ... for update`、Java 的 synchronized），并发低但冲突多时简单可靠；乐观锁假设冲突少，先操作、提交时用版本号或 CAS 校验，冲突就重试（`update ... where version = ?`），适合读多写少。要能说出乐观锁的两个坑：ABA 问题（用版本号而不是值比较可解）与高冲突下的重试风暴。

**Spring 三级缓存解决的是单例 Bean 的循环依赖。** 一级是成品池（singletonObjects），二级是提前暴露的半成品（earlySingletonObjects），三级是对象工厂（singletonFactories，用于生成 AOP 代理）。A 依赖 B、B 依赖 A 时，A 实例化后先把工厂放进三级缓存，再去注入 B，B 需要 A 时从三级缓存拿到（必要时生成代理）并升到二级，B 完成后 A 继续完成初始化。要补一句边界：构造器注入的循环依赖解决不了，原型 Bean 也不行，Spring Boot 2.6 之后默认禁止循环依赖，正规做法是重构依赖关系。

**「AI 开发的使用习惯与规范」这题现在很常见，答法要落到可控性。** 说清哪些交给 AI（样板代码、单测、文档、脚本）、哪些自己写（核心逻辑、并发与事务、安全边界）、怎么验证（跑测试、看 diff、构造边界用例）、以及团队规范（不把敏感数据贴进对话、生成代码要过 review 与静态扫描、依赖要锁版本）。能提一句「AI 生成的代码最容易在异常路径和边界条件上出问题，所以我会专门补这两类测试」，会显得是真用过而不是跟风。
