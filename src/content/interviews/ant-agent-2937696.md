### 《面试题目》

2. read 工具要读取一个 10MB 的文件，全放进上下文会爆，怎么解决？
3. edit 工具在用户和 Agent 同时修改一份文件时，覆写问题怎么解决？
4. bash 工具怎么适配不同操作系统，比如 macOS、Windows、Linux？
5. 没有 diff 的 edit 操作怎么比较？为什么比较原文不如比较原文的 hash？
6. 怎么测评一个 harness 的效果？

### 《参考解析》

**元工具设计的差异要落到「粒度与安全边界」**。read 类工具通常是「路径 + 可选行范围」，返回带行号的内容并在超长时截断，差异在于是否默认全文件、是否做语法高亮、是否支持图片与 PDF；edit 类工具分两种路线，一种要求 old_string 在文件中唯一再做精确替换（Claude Code 的 Edit），另一种用补丁格式描述上下文与增删行（Codex 的 apply_patch），前者简单但对重复文本敏感，后者能表达多处修改但对格式要求高；bash 类工具差异在是否保持持久 shell 会话、超时与输出截断策略、是否默认沙箱、是否允许后台任务。回答时不要背各家源码，讲清设计取舍即可。

**读 10MB 文件不能整体入上下文**。做法是分层：先给结构（文件树、符号表、大纲、行数），再按需读取片段（offset/limit、head/tail），用 grep 定位关键行；对超大日志做聚合与采样，先统计错误类型与时间分布；对长文档做分段摘要再按问题回溯原文。必要时把文件处理交给脚本或子 agent，只把结论带回主上下文。核心原则是「上下文里只放当前决策需要的信息」。

**并发编辑用乐观并发控制**。编辑前记录文件的版本（mtime、大小、内容 hash），写入时用 compare-and-swap：先重新读取并比对 hash，一致才原子替换，不一致就放弃本次修改、重新读取后再让模型基于新内容重做。更严格的做法是文件锁或租约，编辑期间加锁、结束释放；多人协作场景可以走分支与三方合并。关键在于「检测到冲突要报错并重试」，不能静默覆盖。

**bash 跨平台适配**：启动时探测操作系统与可用 shell，Linux/macOS 用 bash/zsh，Windows 优先 PowerShell，其次 cmd，装了 Git Bash 或 WSL 才用 bash；路径分隔符、换行符、命令差异（`ls`/`dir`、`rm`/`del`、环境变量语法）要做抽象；工具描述里写清当前平台与可用命令，让模型自己选择；对不支持的命令返回明确错误而不是假装成功。更稳的做法是把常用操作做成跨平台工具，shell 只作为兜底。

**hash 比较解决的是「改了什么」之外的「改之前是什么」**。没有 diff 的编辑（比如格式化、二进制写入、整段替换）无法用文本差异判断是否发生了并发修改；比较原文是 O(n) 且可能被同样的内容骗过（用户改了又改回），比较内容 hash 能在写入前快速判断文件是否还是 Agent 读到的那一版，成本低且确定。hash 只能检测变化，不能合并变化，所以仍需「检测到不一致就重读重做」。

**harness 评测**：先定义任务集与成功判据（测试通过、文件内容匹配、接口返回正确），再控制变量——同一模型、同一任务、只换 harness；记录成功率、平均步数、token 成本、时延、人工接管率与失败类型；用固定随机种子与隔离环境保证可复现，抽样人工复核自动判分的准确性。

**5000 个任务一夜跑完**：本质是并行度与成本工程。把任务做成可独立运行的容器镜像与固定输入，按机器与配额分片，用队列调度，失败重试与断点续跑；先跑冒烟子集验证判分器，再全量；对模型调用做批处理与缓存，能并行的工具调用并行；用抢占式实例扩容，设总预算与超时，优先保证「每个任务都有结论」而不是「每个都跑满」。如果一夜资源不够，就分层抽样并在报告中说明置信区间，不能伪造全量结果。

**远程沙箱的取舍**：远端提供隔离与安全（不可信代码不碰宿主）、环境一致（镜像固定依赖）、多客户端复用与集中治理（配额、快照、审计），代价是网络延迟与文件同步。本地沙箱启动快、访问本地文件方便，但隔离弱、环境漂移、难以统一回收。合理架构是混合：默认远端隔离执行，需要本地文件或低延迟交互时用本地受限沙箱，敏感凭据只留在近端。

**为什么不把整个 loop 放远端**：loop 里有模型调用、工具调度、用户交互与凭据，放在远端会增加每步往返延迟、把密钥集中到远端、让客户端状态同步变复杂；而工具执行才是需要隔离的部分。所以常见做法是「控制面在近端、执行面在远端」，按风险把工具分区。

**RAG 的增强与 query 改写**：增强可以分检索前、检索中、检索后——检索前做查询改写、同义扩展、HyDE、问题分解；检索中做混合检索（BM25 + 向量）、多路召回、按元数据过滤；检索后做 rerank、去重、压缩、按证据组织答案。query 改写的具体做法包括：指代消解（把「它」补成实体）、口语转书面、拆多意图问题、生成同义词与上下位词、用模型生成假设答案再做向量检索，以及保留原始 query 与改写 query 双路召回。改写效果要用召回率对比验证，不能只凭感觉。
