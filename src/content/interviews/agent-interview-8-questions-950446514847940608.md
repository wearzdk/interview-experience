### 《面试题目》

1. Agent 的基本架构是什么？
2. ReAct 和 Function Calling 有什么区别？
3. 多 Agent 系统怎么设计？
4. Agent 的记忆机制怎么做？
5. 工具调用失败了怎么处理？
6. Agent 的效果怎么评估？
7. 上下文太长怎么办？
8. Agent 的安全问题怎么防？

### 《参考解析》

**基本架构**：按「感知—规划—记忆—工具」四层拆。感知层负责把输入（文本、语音、截图、结构化事件）转成模型能处理的表示；规划层负责任务分解与决策，主流是 ReAct 循环（想一步、调一个工具、看结果、再想）或 plan-and-execute（先出完整计划再逐步执行，适合步骤明确的长任务）；记忆层分短期（当前上下文窗口）与长期（向量库、结构化存储、用户画像）；工具层是 function calling 的 schema 设计与执行沙箱。每一层都要能说出坑：规划层容易死循环或反复调用同一工具，记忆层容易召回噪声、上下文被旧信息污染，工具层容易参数错位、返回值过大撑爆上下文。

**ReAct 与 Function Calling**：两者不是对立关系。Function Calling 是模型层的「结构化输出能力」——模型按给定 schema 输出要调用的函数名与参数，由外部执行；ReAct 是叠加在这之上的「推理—行动」循环范式，模型在思考与工具调用之间交替，直到能回答。可以理解为 Function Calling 提供了「手」，ReAct 规定了「怎么用手」。追问「什么场景不用 ReAct」：任务简单、一次调用就能完成（分类、抽取、单轮问答）时不需要循环，循环只会增加延迟与成本；工具调用有严格顺序、可以用工作流编排时，也不必让模型自由循环。

**多 Agent 设计**：先反问需求边界（要解决什么问题、为什么单 Agent 不够），再讲编排模式：中心化 router（一个调度者分发任务给专家 Agent）、流水线（检索 → 分析 → 写作 → 审核串行）、自由协作（Agent 之间互相发消息，最难控）。设计重点是任务分解的粒度（每个 Agent 的上下文要独立可理解）与消息传递格式（结构化、带来源与置信度）。什么时候不该用：单 Agent + 清晰的工具列表能解决就别拆；拆完需要大量来回传上下文、错误在链路里放大、成本翻几倍时不划算。

**记忆机制**：分三层——短期靠上下文窗口，中期靠会话摘要压缩（超过阈值时把早期对话总结成一段，保留关键事实与未完成事项），长期靠向量库/知识库检索（按语义召回历史片段）。要有参数感：窗口多大、超了按什么规则裁剪（先丢工具返回的大块内容，再丢旧轮次，保留 system 与最近 N 轮）、摘要用什么模型、多久触发一次、检索 top-k 取多少、怎么去重（相同事实只留最新）、怎么失效（过期、被用户更正、来源被删除）。

**工具调用失败处理**：分三类。参数错误——用 JSON Schema 校验，失败时把校验错误原文回灌给模型重试（限制重试次数）；工具本身挂了——超时、重试、降级到备用工具或直接告诉用户「这个功能暂时不可用」；模型幻觉调用了不存在的工具——用白名单校验工具名，不存在就返回可用工具列表让它重选。能说出具体报错形态会明显加分：JSON 被截断导致解析失败、参数类型错位（该传字符串传了对象）、超时堆栈、权限被拒。

**效果评估**：两条线。结果评估看任务完成率、答案正确率、人工抽检合格率；轨迹评估看调了哪些工具、步骤数是否合理、有没有多余或遗漏的调用、失败发生在哪一步。方法上有规则断言（结果包含某字段、数值在范围内）、LLM-as-judge（要有评分 rubric，并主动说明它的偏差：偏长回答、偏自信表述、对格式敏感）、以及人工标注的小样本金标准。没有评估方案基本等于没做过 Agent——面试官会追问「你怎么知道改动之后变好了」。

**上下文太长**：方案有递进关系：先裁剪旧轮次（保留 system、最近 N 轮、以及被引用过的内容）；再把关键信息结构化（把长文档压成字段表、把工具返回的大 JSON 只留需要的字段）；然后分段摘要（滚动摘要 + 关键事实清单）；最后是 RAG 外挂（把不需要常驻的信息放到检索里，按需召回）。每种方案都要能说代价：裁剪会丢信息，摘要会失真且多一次模型调用，RAG 增加检索延迟且可能召回不全。工程上还要注意「缓存友好」——system 与工具表在一次会话内不要变，否则前缀缓存全失效。

**安全**：三条线。提示注入——用户输入永远作为数据而不是指令，工具返回的内容也要标记为不可信；高危操作（删库、转账、发消息）必须人工确认，不能只靠提示词约束。权限越权——工具最小权限（只读工具不给写权限）、按用户身份做数据隔离、敏感工具单独审批。敏感操作失控——输出过滤（PII、密钥）、操作审计（谁在什么时候调了什么）、速率限制与熔断。

**避坑提示**：只背概念不给方案，追问一轮就露馅；没碰过框架没关系，但至少要能说出一个具体参数或报错形态；模板背得太整齐会被打乱顺序追问。真正有效的准备是拿自己做过的项目，把上面八个问题各答一遍，每个答案都带一个具体数字或一次真实故障。
