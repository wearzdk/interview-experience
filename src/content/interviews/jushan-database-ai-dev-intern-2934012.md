### 《参考解析》

**AI 编码的用法**：把它当"结对的人"而不是"自动补全"。日常分三类场景：一是样板与脚手架（CRUD、DTO 转换、配置类、单测骨架），这类产出可预期、改起来快；二是读代码与排查，把报错栈、相关文件、复现步骤一起喂进去让它先给假设，再自己验证；三是重构与迁移，先让它列改动清单和影响面，再小步提交。关键是每条产出都要过编译、过测试、过自己的 review，尤其是并发、事务、异常分支这些它容易写得"看起来对"的地方。

**上下文太长的处理**：先分清是"会话太长"还是"要喂的代码太多"。会话长了就开新会话并带上结论摘要，而不是让历史一直滚；代码多了就做检索式投喂——只给真正相关的文件、接口定义和调用链，必要时用 `@文件` 或仓库检索工具，而不是整包贴进去。工程上更稳的做法是把规范沉淀成仓库里的规则文件（编码约定、目录结构、常用命令），让模型每次自动带上，减少重复解释；再配合分任务拆解，一次只让它改一个模块，上下文自然就短了。

**JVM 调优**：调优的前提是拿到数据，不是先改参数。常规路径是先看 GC 日志（`-Xlog:gc*`）确认是 Young GC 频繁、老年代增长快还是 Full GC 停顿长，再看堆快照定位大对象；工具上 `jstat -gcutil` 看趋势、`jmap`/`jcmd` 拿 dump、`arthas` 在线看方法耗时。常见手段：新生代偏小就调 `-Xmn` 或 SurvivorRatio，对象存活久就把老年代调大或换 G1/ZGC，泄漏类的只能靠 dump 找引用链，调参数没用。上线前的压测基线比任何参数都重要。

**缓存穿透、击穿、雪崩**：三者坏在不同层。穿透是查一个数据库里也不存在的 key，每次都打到 DB——用布隆过滤器或空值缓存（短 TTL）挡住；击穿是某个热点 key 过期瞬间大量并发回源——用互斥锁/单飞（singleflight）只放一个请求回源，或者热点 key 逻辑过期不物理过期；雪崩是大量 key 同时失效或缓存整体挂掉——给 TTL 加随机抖动、做多级缓存（本地 Caffeine + Redis）、集群高可用与限流降级。答的时候要点出各自的触发条件，只背名词很容易被追问"你这个方案为什么能挡住"。

**MVCC**：InnoDB 在可重复读下靠 undo log 版本链 + ReadView 做快照读。每行有隐藏的 `DB_TRX_ID` 和 `DB_ROLL_PTR`，修改时旧版本通过回滚指针串成链；事务第一次快照读时生成 ReadView，记录当时活跃的事务 id 集合，沿版本链找到第一个"对当前事务可见"的版本（已提交且早于视图创建，或就是自己改的）。RC 与 RR 的差别只在 ReadView 的生成时机：RC 每条语句都重新生成，RR 只在事务第一次快照读时生成。当前读（`select ... for update`、update、delete）不走 MVCC，读最新版本并加锁。

**隔离级别与死锁**：InnoDB 默认是可重复读（RR），并且用间隙锁（next-key lock）在很大程度上规避了幻读。死锁四个必要条件：互斥、请求并保持、不可剥夺、循环等待。工程上破环最实用的是"固定加锁顺序"和"缩短事务、减少锁范围"，数据库层还有死锁检测（`innodb_deadlock_detect`）主动回滚代价小的事务。

**Spring 里的设计模式**：Bean 默认单例（单例模式）、`BeanFactory`/`FactoryBean`（工厂）、AOP 用 JDK 动态代理或 CGLIB（代理）、`JdbcTemplate`/`RestTemplate`（模板方法）、事件机制（观察者）、`Resource` 加载（策略）、`ApplicationContext` 启动时的责任链式后置处理器。策略模式在业务里最常用：把不同渠道/不同计费规则抽成同一接口的多个实现，用 Map<枚举, 实现> 注入，避免 if-else 堆叠；适配器模式用于对接外部系统，把第三方 SDK 的入参出参包装成内部统一契约，换供应商时只改适配层。
