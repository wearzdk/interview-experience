### 《面试题目》

1. 流水线执行顺序：编译、构建必须先执行完，再做 Code Review 吗？它们之间有什么依赖？
2. 项目角色：你在 Code Review 项目中承担什么角色？具体负责哪些部分？
3. 仓库规范审查：这个能力具体是什么？之前 Chat 模式输入的是单个文件的 diff 吗？
4. 历史噪声的来源：为什么会检测到历史问题？为什么不直接只审查 diff 中修改的内容？
5. 客户端的特殊性：为什么客户端比后端产生更多问题、更难审查？
6. 语言与类型系统：为什么认为客户端不是强类型？具体是什么语言？为什么把 Kotlin、Swift 理解成弱类型？是否混淆了客户端与前端？
7. 判断依据：你说客户端审查更难，实际观察到了什么现象？
8. 历史噪声的解决方案：后来如何解决？仓库规范审查的具体逻辑是什么？规范文档由谁生成？
9. 上线范围与阻断机制：已经在全公司上线了吗？Android、iOS 都覆盖了吗？是否强制卡合入？
10. 审查效果：如何评估 Code Review 准不准？用户实际反馈怎么样？
11. 评测集来源与标签质量：测试集从哪里来？AI 最初生成的 Issue 本身可能有错，如何判定？
12. 用户随意打标：用户把问题全部标成「暂不解决」或误报，怎么处理？会不会影响后续迭代？
13. 人工复核的可靠性：你们会自己再检查吗？不了解客户端背景、历史规范，如何判断？最终是不是仍然依赖模型？
14. 指标与优化过程：三个阶段的准确率、召回率、F1 怎么计算？每个阶段分别因为什么改动而提升？
15. 未匹配的新问题：新生成的 Issue 不在评测集中，怎么归类？是否计入准确率分母？你采用哪种口径？
16. 评测集是否完备：最初候选问题由 AI 生成，AI 漏掉的问题怎么补？有没有考虑让多人独立人工 Review，建立更完整的基准？
17. 多次提交与增量审查：一个 MR 分多次 commit 提交，如何审查？为什么全量审查会使问题数量放大？增量审查是否包含之前提交的上下文？
18. 自研 Agent 的价值：直接把 MR 发给 Codex、Claude，相比之下你们有什么优势？
19. 规则与提示词控制：把规则写进仓库规范文档不就可以了吗？为什么还需要自研 Agent、控制系统提示词？
20. 开发框架与运行方式：基于什么框架开发？是否通过脚本拉代码、在容器中执行？为什么不做成常驻服务？
21. 真实线上反馈：接入仓库后有没有做用户调查？用户标为正确、历史问题、误报的比例是多少？看过多个 MR 的平均数据吗？
22. 如何证明工具有用：如果用户不接受审查结果、全部跳过，怎么证明建设有价值？缺少规范约束时，怎么判断工具到底有没有用？
23. 错误反馈的治理：如何防止用户故意标误报，污染评测集与迭代指标？线上又如何处理这种行为？
24. 推广与整体规划：后续怎么让更多团队使用？整个 Code Review 的规划是什么？如果业务可以用自己的 Agent，为什么选择你们？
25. 历史案例检索的扩展：向量检索能力实际做到了什么程度？案例筛选、入库能否自动化？每接一个仓库都要重新积累数据吗？
26. 不同仓库的效果差异：为什么切到 Agent 模式后，后端仓库产生的 Issue 反而减少？
27. 竞品与开源选型：准确率约 43% 算什么水平？跟谁比较，对方数据如何？为什么不直接用 OpenCodeReview？为什么认为这类评测、选型不属于你的工作？应该由谁考虑？
28. 上一段实习与语言实践：宝信实习做了什么？现在主要写 Python 还是 Go？Java 与 Python 有哪些区别？自己用 Go 写过工具吗？做客户端审查，会学习 Kotlin、Swift 吗？
29. Java 实现 LRU 缓存：按示例运行并核对输出。为什么某个位置输出了 2，而不是 -1？错误在哪里？平时如何排查这类问题？修改后验证过了吗？
30. 用自己的 Code Review 审查现场代码：它会提出什么问题？除了刚才的 bug，还有什么？会检查代码规范、仓库风格一致性吗？为什么不会？
31. 代码风格：每个人风格不同会有问题吗？你觉得自己刚才这段代码的风格有问题吗？
32. AI 编程的掌控：如何确保 AI 生成的代码正确？平时如何与 AI 交互？怎样控制实现边界？
33. 人工 Review 的范围：AI 生成代码后，你会自己再审查吗？代码量大时，是只看函数用途、再主要依赖 AI 吗？
34. 日常工作与代码的读者：这类需求多吗，平时主要做什么？现在的代码应该主要给人看，还是给 AI 看？

### 《参考解析》

**流水线与审查的依赖**：静态审查不依赖编译产物，只要拿到 diff 与仓库上下文就可以跑，所以可以与编译并行；但依赖类型信息、调用链、跨文件语义的检查需要编译产物或索引，这时要排在构建之后。合理的流水线是「拉取代码 → 并行（静态检查 / 编译 / 单测 / Agent 审查）→ 汇总结果 → 合入门禁」，Agent 失败不应阻塞构建，反之亦然；用独立的检查项让用户能区分是谁拦的。

**历史噪声的根因**：模型看到整个文件而不是 diff 时，会把没改动的老代码一并报出；即使只给 diff，模型也会因为上下文不足去检查周边代码，从而带出历史问题。解法是明确输入边界（只对新增/修改行报问题，且要求行号落在 diff 范围内）、对上下文做只读标注（告诉模型这些行不可评论）、把历史问题单独成清单不阻断合入。全量审查只在定期任务或专项治理时跑。

**客户端为何更难审**：不是「弱类型」——Kotlin、Swift 都是强类型语言。真正的差异在于：客户端代码大量依赖框架生命周期与 UI 状态，正确性往往取决于运行时时序而非类型；同一段逻辑在不同设备、系统版本、屏幕尺寸下表现不同；可测试性差，单元测试覆盖率低；跨端协议与原生桥接层的错误难以静态发现。回答时要把「强/弱类型」的说法纠正过来，用具体现象说明（生命周期回调顺序、主线程阻塞、内存与渲染性能问题）。

**评测集与标注**：初始评测集若由模型生成候选，会带上模型自身的盲区——它漏掉的问题永远不会进入评测集，导致指标虚高。补法是引入独立来源：人工从历史 bug、线上事故、Review 评论中抽取；多个评审者独立标注并计算一致性（Cohen's kappa）；定期用新样本做盲测。标注规范要写清「什么算问题、严重级别、是否属于本次改动」，否则不同人标出来的口径无法合并。

**乱打标的治理**：用户的「误报」反馈不能直接当标签，要先做可信度分层：同一用户的历史准确率、是否有文字说明、是否与人工抽查一致。对批量全标误报的行为做异常检测（同一时间窗大量相同操作），这类反馈只记录不进入训练/评测。同时提供更细的反馈选项（不是问题、历史问题、已修复、规则不适用），让反馈本身携带信息。

**指标口径**：精确率 = 报出且正确 / 报出总数；召回率 = 报出且正确 / 真实问题总数；F1 是两者的调和平均。评测集之外的新问题无法判定对错，应单列为「未标注」，不计入分母，但要统计其占比——占比过高说明评测集失效。还要看业务指标：每个 MR 的报出条数、用户处理时长、忽略率、阻断导致的返工。

**与直接用通用模型的区别**：通用模型（Codex、Claude）能读 diff 并给建议，但缺少三样东西：仓库规范与历史决策（这家公司为什么这样写）、稳定的评测与回归（改了提示词是否更好）、与流程的集成（行内评论、门禁、豁免、追踪）。自研的价值在于把组织知识固化、把效果量化、把反馈闭环，而不是模型本身更强。若业务方用自己的 Agent，平台应转向提供规范、评测集与集成能力。

**Java LRU 手撕的坑**：常见错误是 `get` 命中后没有把节点移到最近使用端，导致淘汰顺序错误；`put` 更新已有 key 时没有移动位置；用 `-1` 作为未命中返回值但与合法值冲突；容量为 0 或负数未处理；`LinkedHashMap` 的 `removeEldestEntry` 在 `accessOrder=false` 时按插入顺序淘汰而不是访问顺序。面试官问「为什么输出 2 而不是 -1」，通常是访问顺序未更新或容量判断写成了 `>=`。排查方法是按操作序列逐步打印链表顺序与 map 内容，而不是盯着代码看；修改后必须重跑示例并补边界用例。

**代码是给人看还是给 AI 看**：两者不冲突但优先级不同。给人看要求命名清晰、结构可读、注释解释意图与取舍；给 AI 看要求上下文自洽、类型明确、避免隐式约定。可维护的代码首先服务于人，AI 只是新增的读者；为了迎合模型而牺牲可读性是本末倒置。
