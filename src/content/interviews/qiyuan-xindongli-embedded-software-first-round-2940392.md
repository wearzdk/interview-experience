### 《参考解析》

**const 与 volatile 约束的是编译器优化的两个不同方向。** `const` 是对程序的承诺：该对象在初始化后不再通过这个名称修改，编译器因此可以把读取提到循环外、把值折叠进指令，并把它放进只读段；但它不保证底层存储真的不可变——通过其他指针、`mprotect` 或硬件写入仍可能改变，`const_cast` 去掉限定后修改 const 对象属于未定义行为。`volatile` 告诉编译器每次访问都必须真正发生、不得缓存、不得删除、不得重排相对顺序，典型用于 MMIO 寄存器、中断与主循环共享的标志、由硬件更新的变量；它不提供原子性，也不提供跨核内存屏障，多核同步仍需 `atomic` 与屏障指令。两者可以叠加：`const volatile` 表示程序不写、但值可能被外部改变，常见于只读的状态寄存器。`sizeof` 是运算符，编译期求值（C99 变长数组除外），作用于数组名得到整个数组大小，作用于指针得到指针宽度；`strlen` 是运行期函数，从首地址开始数到第一个 `\0`，遇不到终止符就越界。嵌入式里把 `sizeof(buf)` 与 `strlen(buf)` 混用、或者把数组传到函数后退化成指针再用 `sizeof`，都是很常见的错误。

**嵌入式内存泄漏的根因多在生命周期与错误路径。** 动态分配后忘记释放、释放后继续使用、在中断里分配导致堆碎片、异常或提前 return 跳过了释放、重复初始化覆盖了指针、以及第三方库内部缓存只增不减，都是常见来源。规避手段首先是设计上尽量静态分配：编译期确定缓冲区大小，用内存池或固定块分配器替代通用 `malloc`，在启动阶段一次性分配；必须动态分配时，把所有权集中到少数模块，C 中用统一的 `xxx_create/xxx_destroy` 配对并记录分配点，C++ 中用 RAII 与智能指针，禁止在 ISR 中分配与释放。运行期要有可观测性：记录当前分配块数、历史峰值、剩余堆空间与栈水位，长时间老化测试观察是否单调下降，开 `configUSE_MALLOC_FAILED_HOOK` 与栈溢出钩子，必要时在主机侧用 Valgrind、ASan 跑单元测试。代码规范上开 MISRA 检查、禁止裸 `malloc`、所有错误分支统一走 `goto cleanup` 或单一出口，能把大部分泄漏挡在评审阶段。

**FreeRTOS 的调度是优先级抢占加可选时间片。** 任务状态有运行（Running）、就绪（Ready）、阻塞（Blocked）、挂起（Suspended），删除或尚未创建的任务可视为休眠（Dormant）。调度器每次 tick 中断或任务主动让出时，从就绪链表中选优先级最高的任务；同优先级任务在 `configUSE_TIME_SLICING` 开启时按时间片轮转，`configUSE_PREEMPTION` 关闭则退化为协作式。任务调用 `vTaskDelay`、等待队列/信号量/通知且带超时时进入阻塞态，超时或事件到达后回到就绪；`vTaskSuspend` 进入挂起态，只能由其他任务恢复。上下文切换在 PendSV 异常里完成，SVC 用于启动第一个任务；Cortex-M 硬件自动保存部分寄存器，剩余由软件压栈。要留意优先级反转：高优先级任务等一把被低优先级任务持有的普通二值信号量会被长时间阻塞，互斥量（mutex）带优先级继承可以缓解；中断服务程序里只能调用 `FromISR` 版本并在退出时触发 `portYIELD_FROM_ISR`。

**IPC 选型看阻塞语义、数据量与参与者数量。** 队列用于任务间传递固定大小的消息，支持多生产者多消费者、可阻塞带超时，适合命令与采样数据；二值信号量用于事件通知与资源计数，计数信号量用于管理多个同类资源；互斥量用于临界区保护并带优先级继承，递归互斥量允许同一任务重复获取；事件组用位图等待多个事件的组合，适合「多个条件都满足才继续」；流缓冲区与消息缓冲区用于字节流或变长消息，适合串口、网络收包。任务通知是直接写在目标任务控制块里的 32 位值，速度最快、几乎不占额外 RAM，可以模拟二值/计数信号量、事件组和轻量队列；局限是一个任务只有一个通知槽（带索引的通知可缓解），不能广播给多个任务，也不适合需要排队保存多条消息的场景。实际项目里通常是「中断用通知唤醒处理任务，任务间用队列传数据，临界区用互斥量」，而不是所有机制混用。

**Socket 服务端要处理完整生命周期与部分读写。** 流程是 `socket()` 创建套接字，`setsockopt(SO_REUSEADDR)` 允许快速重启，`bind()` 绑定地址与端口，`listen()` 设置 backlog，循环 `accept()` 取连接，之后 `recv/send` 收发，最后 `close()`。工程上要处理：`accept` 返回 `EINTR` 时重试；TCP 是字节流，一次 `recv` 不保证读到完整报文，需要长度前缀或分隔符做粘包拆包，并循环读写直到满足长度；`send` 可能短写，要处理返回值；忽略 `SIGPIPE` 或用 `MSG_NOSIGNAL`，避免对端关闭导致进程退出；`SO_REUSEADDR` 之外还要考虑 `SO_KEEPALIVE` 与业务心跳；高并发用 `epoll` 边缘触发配非阻塞 IO，或用线程池加阻塞 IO；关闭要区分 `shutdown` 与 `close`，并处理半关闭与 TIME_WAIT。字节序、结构体对齐与协议版本也要在协议设计阶段定清楚。多线程侧则要理解 `pthread_create`、join/detach、互斥量与条件变量、读写锁、原子操作、线程局部存储，以及线程池的队列与拒绝策略；共享数据加锁的粒度、锁顺序（避免死锁）、伪共享、CPU 亲和性与实时优先级，都是嵌入式 Linux 上会真实遇到的问题。

**端侧 AI 的链路是「解码—预处理—推理—后处理—编码推流」。** 视频侧从 RTSP 或摄像头拉流，硬解码（Jetson 用 NVDEC，RK 用 MPP）得到 NV12 帧，缩放到模型输入尺寸并做归一化，送 NPU/GPU 推理，后处理做 NMS、跟踪或分割，再把结果叠加回画面，用硬件编码器推 RTSP/RTMP/WebRTC。链路上要尽量零拷贝：DMA-BUF、RGA 或 NVDEC 直出，避免每帧在 CPU 上做一次 `memcpy` 与色彩转换；用多线程或流水线把解码、推理、编码重叠起来，按帧率与延迟做丢帧策略。Jetson 与 RK3588 的差异主要在工具链与运行时：Jetson 走 JetPack，模型经 TensorRT 构建 engine，支持 FP16/INT8 校准，CUDA 生态完整， profiling 用 Nsight；RK3588 走 RKNN-Toolkit2 在 x86 主机上把 ONNX 等模型转成 `.rknn`，做 INT8 量化需要校准集，板上用 RKNN Runtime 与 `librknnrt`，算子覆盖与动态 shape 支持相对受限，常见做法是替换不支持的算子、固定输入尺寸、在 CPU 上补后处理。拿到新平台能否独立部署，判断标准是：能否跑通「模型转换—量化—精度对齐—板上推理—性能 profiling—与业务链路集成」全流程，并能定位算子不支持、量化掉点、内存带宽瓶颈这三类问题。
