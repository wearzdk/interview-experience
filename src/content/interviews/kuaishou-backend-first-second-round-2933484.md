### 《参考解析》

**「20 步上限 vs 补查 3 轮」考的是你分不分得清两种控制流**：Agent 步数是整个「思考-调用工具-观察」循环的全局预算，防的是无限循环与成本失控；RAG 补查轮数是检索子流程内部的局部预算，防的是「检索不到就一直换 query」的死循环。前者超限要终止任务并给用户交代，后者超限要带着已有证据作答或明确说「资料里没有」。两者都要有单调递减的计数器和可观测的日志。

**SSE 推流为什么能「请求线程返回了还在推」**：HTTP 响应是一个流，Servlet 3 的 `AsyncContext` 或 Spring 的 `SseEmitter`/`ResponseBodyEmitter` 把请求线程释放回容器，但连接和输出流仍然活着，后台线程（或响应式流）继续往里写；关键是超时与清理——设置 emitter 超时、客户端断开时移除监听、写出失败要吞掉并清理资源。用 WebFlux / Flux 更自然，因为整条链路是非阻塞的。若前端在网关后面，还要关掉代理缓冲（`X-Accel-Buffering: no`）、设置 `text/event-stream` 与心跳。

**用户隔离与几亿用户的存储**：会话按 `userId + conversationId` 分区，向量库按租户字段过滤（metadata filter），缓存 key 带用户前缀，权限校验在检索前而不是生成后。海量问答不要全量入库热库——冷数据归档到对象存储 / ClickHouse，热会话放 Redis 并设 TTL，正文与向量分表；写入走异步队列批量落库。缓存过期后「用户回来接着聊」要靠落库的最近 N 轮对话重建上下文，而不是假设缓存还在。

**topK 的依据**要说成实验与预算共同决定的：先用 20 测召回率，再看上下文 token 预算与延迟，最终取 5~10 并配 rerank；相关性判断可以是分数阈值 + 让模型在生成前先判断「资料是否足够」，不足则明确拒答而不是硬编。

**索引下推（ICP）**：MySQL 5.6 起在存储引擎层就用索引中的列做条件下推，减少回表次数——例如 `where name like '张%' and age = 20` 在联合索引 `(name, age)` 上，age 的过滤在引擎层完成再看是否需要回表，`EXPLAIN` 的 Extra 里出现 `Using index condition`。**四种引用**：强引用（不回收）、软引用（内存不足时回收，适合缓存）、弱引用（下次 GC 必回收，ThreadLocalMap 的 key 用它）、虚引用（只为回收时收到通知，配合 ReferenceQueue 管理堆外内存）。**ThreadLocal** 每个线程一个 `ThreadLocalMap`，key 是弱引用的 ThreadLocal 本身，value 强引用，所以线程池复用时必须 `remove()` 防内存泄漏与串号。**公平锁**靠 `hasQueuedPredecessors()` 判断队列里有没有更早的等待者，非公平锁在 `lock()` 时先 CAS 抢一次再入队，这正是它吞吐更高的原因（减少线程唤醒的上下文切换），代价是可能饿死。
