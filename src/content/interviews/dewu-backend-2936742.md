### 《参考解析》

**自进化系统的评测数据集**：自进化（自我迭代）的前提是有一把稳定的尺子，数据集要分层建设。第一层是人工标注的金标准集，规模小但覆盖核心能力，改动前后都必须跑；第二层是线上回流集，把真实请求里的失败样本、用户差评、人工复核打回的案例沉淀下来，每条带输入、上下文、期望行为与来源；第三层是对抗集，专门构造边界、诱导、越权、多轮歧义的样本，用来防止指标虚高。数据集本身要版本化，样本带时间戳与场景标签，避免训练集与评测集混在一起造成泄漏。指标上确定性可判的（工具调用是否正确、参数是否合法、是否越权、耗时与 token）写成断言，语义类的用模型评审加抽样人工校准，评审模型与被评模型不能同源。自进化闭环是「失败样本回流 → 归因 → 改提示词或工具 → 回归」，没有回流通道的自我迭代只是在原地打转。

**Agent 自动化评测体系**：一条完整的评测链路分四段。构造：用例由人工、线上回流、合成三类来源组成，合成用例要有种子与约束，避免生成一批同质样本。执行：每个用例在隔离环境跑，固定随机种子与工具桩，记录完整轨迹（每步模型输入输出、工具调用与结果、耗时与 token）。判定：分规则判定与模型判定，规则判定查工具名、参数、状态码、最终产物；模型判定给评分维度与锚点，要求给出理由，必要时双模型交叉。统计：按能力维度、场景、难度切片看通过率与回归差异，重点看「改 A 是否弄坏 B」，同时看成本（每用例 token 与耗时）。工程上要把评测做成 CI 的一部分，改提示词、换模型、加工具都必须过一遍基线，否则迭代方向无法证伪。

**Kafka 与 RocketMQ 的存储结构差异**：Kafka 是分区日志模型，每个 Partition 对应一组分段文件（.log 数据文件、.index 偏移索引、.timeindex 时间索引），消息顺序追加写，读时按 offset 先查稀疏索引定位到最近的物理位置再顺序扫，靠顺序 IO 与页缓存获得高吞吐；分区数决定并行度，但分区多了会放大文件句柄与选举成本。RocketMQ 是共享提交日志模型，所有 Topic 的消息统一追加到一个 CommitLog，另用 ConsumeQueue 为每个 Topic 的每个队列存「物理偏移、消息长度、tag 哈希」的定长索引，消费时先读 ConsumeQueue 再回 CommitLog 取消息体；好处是写入完全顺序、单机队列数不受文件数限制，代价是读消息多一次随机读，所以依赖 PageCache 与预读。一句话对比：Kafka 每分区独立日志、读写都顺序；RocketMQ 全局一份日志加轻量索引、写顺序读近似随机。

**Offset 定位**：消费者提交的 offset 是分区内的逻辑序号。Kafka 用分段文件，文件名是基准 offset，内存里维护「基准 offset → 物理位置」的稀疏索引，查找时二分定位到不大于目标 offset 的最大索引项，再从该物理位置顺序扫描直到命中目标 offset。这也是为什么顺序消费快、随机跳读慢。

**零拷贝**：传统 read/write 要四次拷贝（磁盘 → 内核页缓存 → 用户缓冲区 → socket 缓冲区 → 网卡）与四次上下文切换。Kafka 用 sendfile，数据从页缓存直接送到 socket 缓冲区再由网卡发出，只保留必要的 DMA 拷贝，省掉用户态中转；配合批量发送与压缩，吞吐显著提升。要注意 sendfile 与 TLS 加密不兼容（加密必须在用户态做），所以开启 SSL 时零拷贝会失效，这是常见追问点。

**Redis Cluster 的 Gossip**：集群用二进制协议在节点间传播状态，主要消息类型有 PING/PONG（携带自身与部分其他节点的槽位与状态）、MEET（邀请新节点入群）、FAIL（广播某节点客观下线）。每个节点每秒随机选几个节点发 PING，把最近通信过的节点、随机节点、疑似下线节点混在一起选，收到的 PONG 里带回对方视角的节点表，信息以指数级扩散。判定下线是「主观下线 + 客观下线」：单节点认为失联记 pfail，超过半数主节点在时限内都认为失联则标记 fail 并广播。槽位变更（迁移）也通过 Gossip 传播，客户端拿到 MOVED 后刷新本地槽位缓存。

**平衡二叉树**：任意节点的左右子树高度差不超过 1，且左右子树本身都是平衡二叉树。它保证查找、插入、删除都是 O(log n)。为了维持平衡需要旋转：LL 型右旋、RR 型左旋、LR 型先左旋再右旋、RL 型先右旋再左旋。数据库索引不用它而用 B+ 树，原因是磁盘按页读取，AVL 每个节点只存一个 key，树高远大于 B+ 树，IO 次数多；B+ 树一个节点存多个 key、非叶节点不存数据，三层即可支撑千万级数据。
