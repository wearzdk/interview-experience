### 《面试题目》

1. 自我介绍。
2. 目前的基本情况（毕业时间、实习安排等）。
3. 项目拷打：项目是做什么的？你主要负责哪些部分？有哪些创新点、解决什么问题（skill 分层设计、审查机制、上下文压缩等）？是个人独立完成的吗？有没有具体应用场景？
4. 为什么投递游戏测试岗位？
5. 你对游戏测试岗位有哪些了解？包括日常事务、基础测试方法、怎么处理 bug。
6. 你怎么理解 bug 的生命周期？
7. 介绍测试理论：黑盒与白盒、边界值、等价类等。
8. TCP 和 UDP 的区别是什么？分别会用在游戏的哪些部分？
9. 考察 Linux 常用命令。
10. 测试用例包含哪些部分？游戏测试岗的作用是什么？
11. 有一个 1–100 的整数输入框，怎么设计测试用例？
12. 平时玩哪些游戏最多？
13. 介绍一下公孙离的技能，怎么对一技能进行测试？用到哪些测试方法？
14. 介绍一个你在游戏中遇到的 bug。
15. 游戏中有哪些影响平衡性的东西？如果让你来处理，你会怎么做平衡？
16. 现在有 5 个游戏任务，每日 0 点刷新，完成后自动领取，让你来测试，你会怎么做？说得越全越好。
17. 针对某一项任务，它完成前和完成后有哪些变化？
18. 反问。

### 《参考解析》

**测试用例的骨架与 1–100 输入框的拆法。** 一条用例至少包含：编号、标题、前置条件、操作步骤、预期结果、优先级、用例类型，工程上还会带需求关联、测试数据与环境。1–100 的整数输入框按等价类划分为有效类（1 到 100 的整数）与无效类（小于 1、大于 100、非整数、空、非数字字符），边界值取 0、1、2、99、100、101，再补特殊输入：负数、小数、科学计数法、前导零、正负号、全角数字、前后空格、超长数字、粘贴与输入法组合输入、脚本与 SQL 注入串。除数据本身，还要覆盖 UI 与交互（失焦校验、错误提示、提交按钮状态、回车提交）、并发与重复提交、网络中断与重试、权限与越权、兼容性（分辨率、系统、输入法）、性能（连续快速输入）、可访问性与本地化。这样拆的价值在于每一类都有明确的预期，而不是堆一堆「输入 1 试试」。

**公孙离一技能的测试要围绕「位移 + 留伞 + 二段回位」的状态机。** 一技能向指定方向位移，同时把纸伞留在原地，短时间内可以再次释放回到伞的位置。测试点因此分成几组：位移本身——距离是否与技能描述一致、落点是否被地形与墙体阻挡、能否穿越特定地形、位移过程中是否可被打断或被控制、前摇后摇与帧数据是否稳定；纸伞状态——伞的落点是否与释放位置一致、存在时长、二段返回的冷却窗口、期间再次使用其他技能或回城时伞的状态如何变化；交互——与闪现、位移装备、其他技能的连招顺序，与压制、击飞、沉默等控制的优先级，死亡或复活时伞是否清理；表现与同步——网络延迟、丢包、帧率波动下的位置回拉与技能图标状态，观战与回放是否一致；边界——地图边缘、草丛、视野外释放、多人同时释放。方法上会用到等价类、边界值、状态迁移（手中伞 / 伞在地上 / 伞飞行中）、正交组合与故障注入。回答时先讲清技能机制，再按状态维度展开，比直接报一堆测试点更有条理。

**每日任务系统的测试核心是时间边界、计数一致性与奖励幂等。** 五个任务每日 0 点刷新、完成后自动领取，涉及三类状态：任务进度、领取状态、奖励发放。时间维度要测服务器时间与客户端时间不一致、跨天时在线、0 点整的并发刷新、时区与夏令时、维护延迟开服后的刷新补偿、断线重连后任务列表是否回滚。计数维度要测正常完成、重复计数、异常退出与中途掉线、对局无效或平局、多任务同时达成、任务进度上限与溢出。领取维度要测自动领取是否只发一次、背包满时的邮件补发、领取与刷新并发、重复登录、跨设备登录、奖励到账延迟与补发。此外还要覆盖活动叠加、任务依赖、客户端缓存导致的显示不一致、大量玩家同时刷新时的服务端压力，以及回档与数据修复。每一项都能落到具体的预期结果与验证手段（日志、数据库对账、抓包、GM 工具），才是可执行的测试设计。

**bug 生命周期与测试岗的职责。** 缺陷从发现、提交、确认、分配、修复、验证到关闭，可能因复现失败、需求变更、无法修复而进入挂起或拒绝，验证不通过则重开。提交时要带版本、环境、账号、复现步骤、实际结果与预期结果、日志与截图/录屏，严重级别看影响面（崩溃、卡死、资损、体验），优先级看修复排期，两者不能混为一谈。测试岗的价值不只在找 bug，还在需求评审阶段发现不可测与歧义、在开发阶段补齐可观测性、在上线前给出风险评估、上线后做回归与线上问题复盘。只会执行用例的测试很容易被替代，能把缺陷聚类成系统性问题、推动流程改进的才有议价能力。

**TCP 与 UDP 在游戏里按「能否忍受延迟与丢失」分工。** TCP 提供可靠、有序、带流量控制与拥塞控制的字节流，代价是重传与队头阻塞，适合登录鉴权、支付、商城、背包、排行榜、聊天这类不能丢也不能乱序的数据。UDP 不保证送达与顺序，开销小、延迟低，适合实时对战的位置同步、技能释放、语音与观战推流；但游戏不能直接裸用 UDP，通常在其上自研可靠层（序列号、ACK、重传、冗余发送、FEC 前向纠错，或直接用 KCP、QUIC、ENet），并对不同消息分级：位置包允许丢、关键事件必须可靠。还要考虑 MTU 与分片、Nagle 算法对延迟的影响、心跳与 NAT 超时、弱网与切换网络时的重连。能说清「为什么实时对战不用 TCP」以及「用了 UDP 之后可靠性由谁补」，比背协议头字段更接近实际工作。

**平衡性调整是数据、机制与玩家感知三者的折中。** 数据侧看胜率、pick/ban 率、经济曲线、对局时长、分位段差异，单看总体胜率会被出场率与玩家水平污染，需要分高分段、普通段与赛事数据；机制侧看克制关系、资源获取效率、阵容搭配与地图节奏，避免「数值一调就连锁失衡」；感知侧看玩家对「强度」的主观判断，它往往滞后于真实数据，却直接影响体验与舆论。调整方法上宜小步快跑：先定目标（削弱上限还是提升下限）、再做小幅度数值或机制改动、灰度或限时模式验证、观察一周以上数据、必要时回滚；同时准备补偿与公告口径。测试在其中负责验证改动是否按预期生效、是否引入新的极端组合、以及旧存档与旧对局数据是否兼容。
