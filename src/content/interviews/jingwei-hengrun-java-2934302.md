### 《参考解析》

**问题重写与子问题拆分**：用户在多轮对话里常有指代和省略（「那它呢」「那第二种方案」），直接拿去检索会召回错误内容。问题重写就是用模型结合对话历史把当前问题补全成独立、可检索的完整问句；子问题拆分是把复合问题（「A 和 B 在 C 场景下怎么选」）拆成多个可分别检索的子问，各自检索后再合并答案。工程上要给重写加约束（不能引入新实体）、保留原始问题做并行检索、并缓存重写结果避免重复调用。

**上下文窗口满了**：四种策略按成本排序——裁剪（保留系统提示 + 最近 N 轮 + 与当前问题相关的历史，其余丢弃）；摘要（把老对话压成一段结构化摘要，保留事实与结论）；检索化（把历史存进向量库，每轮按需召回相关片段，即「长期记忆」）；以及换更长上下文的模型。生产上通常是「系统提示固定 + 摘要 + 最近若干轮 + 按需召回」组合。要提醒：摘要会丢细节，涉及数字、订单号这类精确信息时不能只靠摘要。

**多路混合检索与过度检索率**：多路指同时用多种召回通道——BM25 关键词、向量语义、结构化条件（时间、类目）、图/关系召回，各自取 top-k 后融合（RRF 或加权分数），再交叉编码器重排。「过度检索率」指的是召回了大量不相关片段的比例：上下文里塞进无关内容会让模型答偏、也会挤占窗口。降低手段：提高相似度阈值、限制每路 top-k、去重与多样性（MMR）、按问题类型只走必要通道（简单事实题不必触发多路）、以及重排后只保留分数断层以上的片段。

**static**：修饰成员变量（类级共享，类加载时初始化）、方法（无 this、不能访问实例成员、可被类名调用）、代码块（类加载时执行一次，用于初始化静态资源）、内部类（不持有外部类引用）、静态导入。实际使用场景：常量、工具方法、单例的静态实例、缓存。要提一句坑：静态变量在 JVM 内共享，多实例部署时它不是「全局」而是「每进程一份」，别拿它做分布式状态。

**HashMap**：数组 + 链表 + 红黑树。`hash` 扰动后 `(n-1) & hash` 定位，冲突挂链表，链长 ≥ 8 且容量 ≥ 64 转红黑树，扩容翻倍并重新分布（要么原位要么 +oldCap）。常用方法：`put/get/remove/computeIfAbsent/merge/forEach/getOrDefault`。要说清「为什么容量是 2 的幂」「为什么扩容是翻倍」，以及「多线程下 1.7 的头插会成环，1.8 改成尾插但仍不安全，并发场景用 ConcurrentHashMap」。

**设计模式结合项目**：挑两个真用过的讲——策略模式（不同支付渠道 / 不同模型供应商统一接口）、模板方法（导入流程的固定骨架 + 子类实现差异）、责任链（风控规则链）、工厂（按类型创建处理器）。讲的时候给出「不用的后果」，比如 if-else 会随渠道增加而爆炸。

**离职原因与背景问题**：实习没留用统一归因到外部客观（无 HC、方向不匹配），不评价前东家；跨专业讲清动机与自学证据；薪资给出区间并说明依据。
