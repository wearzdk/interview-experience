6. 你项目里的混合检索，单路检索分别是怎么做的？
7. 你输出的 Top-K 是什么？这个得分是谁和谁比出来的？

13. 如果两路 Top-K 都取 10，企业里相关文档很多、召回片段也多，正确答案可能被 rank 模型排到后面，你会怎么处理这种情况？

### 《参考解析》

**排产优化的回答要有「模型三要素」**：决策变量（每道工序在哪台机器、什么时间开始 / 结束、批次如何合并）、目标函数（最小化 makespan、最小化拖期、最小化换型次数，通常是加权组合）、约束（机器产能、工序先后、物料齐套、班次与人员、换型时间）。求解方法上，小规模用 MILP（Gurobi / OR-Tools CP-SAT）能拿最优，规模大了用启发式（贪心 + 局部搜索、遗传、模拟退火）拿可接受解，工程上常见「规则排产 + 优化修正」的两段式，重点是能说清「为什么选这个方法、解的质量如何衡量、求解时间多长」。

**RAG 的 pipeline 按「离线 / 在线」两条线讲**：离线是文档采集 → 解析抽文本 → 清洗去重 → 切块 → embedding → 入向量库与关键词索引（同时存元数据）；在线是 query 改写（多轮时补全指代、拆分子问题）→ 双路召回（向量 + BM25）→ 融合 → rerank → 上下文组装（去重、按预算截断、带来源）→ 生成 → 引用与后处理。Corrective RAG 在「检索后」判断召回质量，不达标就换 query 重查或退化成联网/直接回答；Adaptive RAG 在「检索前」判断问题是否需要检索（闲聊、常识直接生成），两级都在节省无效检索与错误引用。

**Top-K 与打分要说准「谁和谁比」**：向量召回的分数是 query embedding 和 chunk embedding 的相似度（余弦 / 内积 / 欧氏距离换算），BM25 的分数是 query 词与文档的词频统计（不同量纲，不能直接相加）；融合常用 RRF（只看排名，倒数求和）或分数归一化后加权；rerank 的分数是（query, chunk）成对输入 cross-encoder 或 LLM 打出的相关性分，它才与「是否回答这个问题」直接相关。

**「正确答案被排到后面」是典型的 top-k 截断与排序偏差问题**，处置手段分层：加大召回 K 并让 rerank 处理更多候选（成本换准确率）、把 rerank 从 pointwise 换成 listwise（一次看整组候选，避免单条打分失真）、对高分簇做多样性重排（MMR，防同质片段占满）、把文档结构（章节、标题、更新日期）作为特征参与打分、以及用「答案是否可被已召回片段支持」的判定兜底——不满足就让模型明确说没找到，而不是用低质片段硬编。企业文档多、重复度高时，元数据过滤（部门、制度类型、生效年份）往往比调排序更有效。

**端到端耗时**要能拆开报：query 改写 200~500ms、双路召回各几十到几百毫秒、rerank 依模型在几百毫秒到 1 秒、生成首字 1 秒左右、整体 2~5 秒是常见区间；优化靠并行召回、缓存（相同 query 或 embedding 缓存）、流式输出首字、把 rerank 放在流式生成之前但只对 top 20 做。
