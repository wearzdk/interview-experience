### 《面试题目》

1. 如果 vibe coding（氛围编程）始终无法得到正确结果，你怎么办？
2. 秒杀场景如何避免超卖，但不准用 Redis？
3. 用 200MB 内存排序硬盘中 2GB 的 int32 数据，两种解法？

### 《参考解析》

**vibe coding 卡住：先判断失败类型，再决定接管还是继续。** 反复报错的循环里，「换模型、改 prompt」是最贵且最不收敛的做法。正确的第一步是分类：是上下文没给够（AI 不知道框架版本、内部约定、数据结构长什么样），是约束没显式表达（性能、兼容性、并发安全只在你脑子里），还是需求本身没想清。三类都只能靠工程手段解决，不能靠对话解决。具体动作：把问题缩到最小可复现（从几百行缩到三十行，去掉业务无关依赖）；去读它引用的库的真实源码与文档确认 API 真的存在——模型编造不存在的配置项和函数签名是最常见的失败源；把它要满足的隐式约束写成会失败的测试用例，让「错」变成可执行的断言，而不是你俩互相说服；用二分法定位从哪一行开始偏离预期。决定接管的判据要说得很硬：同一个问题两轮没有实质进展就自己写；触碰资金、并发、安全、核心链路的代码直接自己写；样板代码、脚本、测试用例、UI 草稿可以继续交给 AI。再往上一层是团队视角——AI 产出的代码必须有 review 和测试门禁，把项目约定沉淀成 AI 能读到的文件（规范、目录说明、示例实现），让下一次不用重复解释同一件事。这题考的其实不是会用工具，而是知道工具的边界在哪、什么时候人来兜。

**不准用 Redis 防超卖：把判断和扣减压成一条原子 SQL。** 核心只有一句：绝对不写「先 select 库存再 update」，而是

```sql
UPDATE stock SET available = available - 1
 WHERE sku_id = ? AND available >= 1;
```

看受影响行数，0 就是卖完了。InnoDB 会给这一行加排他锁，并发请求在这条语句上串行化，判断与扣减不可能被插队。配套三件事：幂等（订单表建 `(activity_id, user_id, sku_id)` 唯一索引，重复提交与客户端重试被数据库直接挡掉，再配一张请求号去重表）；一致性（扣库存与建订单放同一个本地事务，跨库则用本地消息表 + 可靠投递 + 消费端幂等，超时未支付由定时任务回补）；兜底对账（日终比对库存流水与订单，差多少补多少，这是所有方案的最后一层）。

单行热点是这套方案的天花板：同一行的锁排队，事务越长吞吐越低，单行扣减大致在几百到两千 TPS 量级。要往上走得拆库存：把一行拆成 N 个桶（`stock_shard` 表 N 行），请求按 hash 或随机挑桶扣，吞吐近似线性放大；代价是要维护总库存视图、某桶扣空时要换桶或回补、对账复杂度上升。乐观锁（version CAS）也能用，但冲突率高时重试放大反而更慢，只适合冲突稀疏的场景。

面试官封死 Redis 是想听你讲清代价：无 Redis 本质是拿数据库的串行化换正确性，QPS 上限由单点写入决定；大厂仍然把 Redis 放前面做预扣和削峰，但数据库的 `available >= 1` 和唯一索引必须永远保留——Redis 只是加速层，不能是唯一真相，它挂了也不能超卖。

**200MB 内存排序 2GB int32：两个解法都要说清 IO。** 先算数：2GB / 4B ≈ 5.37 亿个整数，200MB 只能放 5000 万个，内存只装得下十分之一，必须用外排序。

解法一，多路归并。按 100MB 一块读入（剩下的留给读缓冲、输出缓冲和排序的临时空间），内存里快排或堆排后写有序临时文件，约 22 块；再做 k 路归并，用大小为 k 的最小堆，k 受文件句柄和每路读缓冲限制，取 16~32 路，块数超过就分两阶段归并。IO 量：读 2GB + 写 2GB 临时文件 + 归并读 2GB + 写 2GB 结果，约 8GB，全是顺序 IO。

解法二，分桶（基数思想）。int32 有符号，先异或符号位当成无符号看，按高 8 位分 256 个桶，一遍扫描顺序写到 256 个文件，平均每桶 8MB，200MB 内存能整桶装下；然后逐桶读进内存排序、直接顺序输出，结果天然全局有序。IO 量同样是约 8GB，但没有比较开销，常数更小。缺点是分布倾斜时桶不均，工程做法是先采样确定分位点做等频分桶，或对超大桶按次 8 位再分一层。

还有第三种可以加分：位图。`2^32` bit 是 512MB，装不进 200MB，但可以分三遍，每遍只覆盖三分之一值域（约 179MB 位图），逐遍扫描标记、按位顺序输出，IO 是读三遍数据。坑是位图会把重复元素吃掉，要保留重复次数得改用计数数组或多存一遍。

怎么选：通用可比较类型选归并，值域小且分布已知选分桶，要判存在性或去重选位图。最后补一句工程细节——内存里一定要给读缓冲留余量，缓冲区开太小会让顺序 IO 退化成大量小随机读，这是外排序实际跑起来比理论慢的主要原因。
