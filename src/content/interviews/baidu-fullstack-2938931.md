### 《参考解析》

**B+ 树作为索引结构的理由**：B+ 树是多路平衡树，非叶子节点只存键、叶子节点存数据并用链表相连，因此树高很低（三层可支撑千万级），一次查询只需少数几次磁盘 IO，范围查询顺着叶子链表扫描即可。红黑树是二叉结构，树高随数据量对数增长，每次下降一层都可能是一次随机 IO，范围查询还要中序遍历，磁盘友好性差；它的优势在内存场景（如 Java 的 TreeMap）与插入删除的局部旋转代价可控。跳表用多层链表加随机层级实现近似对数查找，实现简单、范围查询友好、并发插入容易（Redis 的 ZSET 就用跳表），但同样的数据量下内存开销比 B+ 树大，且没有为磁盘页做优化。结论：磁盘存储选 B+ 树，内存有序集合选跳表，红黑树适合内存中的小规模有序结构。

**百万级要不要分库分表**：百万行对 MySQL 单表不算大，做好索引与查询优化即可；真正需要拆分的信号是单表数据量到千万级且增长快、单库连接数或写入成为瓶颈、或者单表体积影响备份与 DDL。分库分表会带来跨分片查询、分布式事务、全局 ID、扩容迁移等成本，应该先用读写分离、归档冷数据、加缓存、优化索引这些手段。回答时给判断依据，比直接说「要」或「不要」好。

**隔离级别与幻读**：四种级别是读未提交（能读到别人未提交的数据，脏读）、读已提交（只能读已提交，但同一事务两次读可能不同，不可重复读）、可重复读（同一事务内多次读一致，MySQL 默认）、串行化（加锁串行执行）。幻读指同一事务内两次范围查询返回的行数不同（别人插入了符合条件的新行）。RR 下靠 MVCC 快照读避免大部分幻读：快照读读的是事务开始时的 ReadView，看不到新插入的行；但当前读（`SELECT ... FOR UPDATE`、`UPDATE`、`DELETE`）读最新版本，需要用间隙锁（Next-Key Lock）锁住范围来阻止插入，否则当前读仍可能看到幻行。所以准确说法是：RR 的快照读无幻读，当前读靠间隙锁防幻读，但间隙锁在并发下会带来死锁风险。

**什么时候需要缓存**：读多写少、热点集中、下游查询成本高（复杂 join、跨服务调用）、能接受短暂不一致的场景适合加缓存；写多读少、强一致要求（账户余额、库存扣减的强一致部分）、数据量小到一次查询就够快、或者缓存命中率注定很低时，加缓存只会增加复杂度与不一致风险。判断指标是命中率、访问延迟收益、以及数据变更频率，不是「别人都加所以我也加」。

**排行榜与 ZSET 大 Key**：排行榜用 ZSET，`ZADD` 写分数、`ZREVRANGE` 取 TopN、`ZREVRANK` 查排名，复杂度都是对数级。ZSET 的「大 Key」通常指单个 key 的成员数过大（经验阈值几十万到百万级）或单个 value 体积过大（几 MB 以上），判据是「操作它会不会阻塞主线程」——`ZRANGE key 0 -1` 这种全量操作在几十万元素时就会明显卡顿。治理手段：按业务维度拆分（如按榜单周期、按地区分成多个 key）、只保留 TopN（用 `ZREMRANGEBYRANK` 定期裁剪尾部）、把历史榜单归档到数据库或对象存储、读取时限制返回条数并分页；监控上用 `MEMORY USAGE` 与慢日志定位。

**Redis 集群故障与主节点不可用**：Cluster 模式把数据分 16384 个槽，主节点故障由集群总线检测，多数主节点投票判定客观下线后，从节点选举提升为主并接管槽位，客户端按 `MOVED`/`ASK` 重定向；哨兵模式则由哨兵集群完成故障转移。提高可用性的做法：每主至少一从、跨机架或跨可用区部署、合理设置 `cluster-node-timeout` 与 `min-replicas-to-write`（防止脑裂时旧主继续写）、开启 AOF everysec 或 RDB 加从库持久化、客户端配置重试与只读从库分流。要注意故障转移期间的写失败与数据丢失窗口（异步复制），业务侧要能容忍并补偿。

**AI 写代码与 Code Review**：合理的分工是让 AI 生成样板、测试、迁移脚本与文档，自己负责设计、边界与评审。评审重点看四类：正确性（边界、空值、并发、错误处理）、安全性（注入、越权、密钥泄露）、与现有代码的一致性（命名、分层、复用）、以及可维护性（是否引入了不必要的依赖）。「纯用 AI 写」的风险不在于代码能不能跑，而在于你失去了对系统的理解，出问题时无法定位。保持技术成长的路径是：先自己写关键路径，再用 AI 对照；读 AI 的方案并追问为什么这样设计；定期重写一段自己熟悉的模块做对照练习。

**前后端分界与 AI 的影响**：分界在工程上仍然存在（职责、部署、性能模型不同），但边界在变模糊——全栈工具链让一个人能覆盖更多环节，AI 又能补齐不熟的语言与框架。选择做哪一端要看兴趣与长期积累：前端更贴近用户体验与交互，后端更贴近数据与稳定性。回答时说明自己的选择与理由，不必迎合岗位说「都可以」。

**摩尔投票法**：核心是「不同则抵消」——维护候选值与计数，遇到相同值计数加一，不同则减一，减到零换候选。正确性来自数学事实：若某元素出现次数超过一半，把它与其他元素两两配对抵消后，剩下的必然是它。时间复杂度 O(n)、空间 O(1)。变体常见两类：求出现次数超过 n/3 的元素（最多两个，用两个候选与两个计数，最后再验证一遍）；以及带条件的抵消（如每次可抵消 k 个不同元素）。一定要补「最后验证候选的出现次数是否真的超过阈值」，因为投票只保证「可能存在」。
