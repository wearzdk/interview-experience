### 《面试题目》

1. 幂等怎么做？
2. 你项目里到底怎么做的、出过什么问题？
3. 为什么第一选择是数据库唯一索引，而不是 Redis？
4. 唯一索引方案踩过什么坑？「先查再插」为什么不行？
5. Token 方案只放 Redis 有什么问题？
6. 支付回调这种场景怎么幂等？
7. MQ 消费端的幂等键用什么？
8. 幂等的边界应该放在哪里？

### 《参考解析》

**真实事故**：大促前夜收到告警，同一用户 3 分钟内下了 7 笔一样的订单。排查下来是前端按钮防重没兜住，网关又因超时重试了一次，请求打到了两个实例上。这类问题的根因是「重复请求来自不同层」，所以幂等不能只在一个接口里做。

**唯一索引为什么优先**：它是数据库层面的最终一致性兜底，只要事务提交成功，重复数据就进不来。给订单表加 `(user_id, biz_no)` 唯一约束，`biz_no` 由客户端或上游生成，服务端不再自己造；插入时捕获 `DuplicateKeyException`，返回已存在的记录。相比 Redis，它不依赖缓存可用性，也不会因为 key 过期而失效。

**两个实战坑**：一是「先查再插」在并发下无效——两个线程同时查不到、同时插，唯一索引报错后整个事务回滚，调用方收到异常；改成「先插，冲突了再查」逻辑更干净。二是唯一索引的列不能允许 `NULL`，MySQL 里 `NULL` 不参与唯一性判断，`biz_no` 允许为空时重复数据会从空值漏进来；同时字段不要选过长的字符串。

**Token 方案的真实问题**：纯 Redis Token 有两个坑。`SETNX` 与业务处理不是原子操作，服务刚 set 完就挂掉，token 已消费但业务没执行，用户重试会被判重复；过期时间设短了用户填表慢一点就失效，设长了 Redis 里堆废 token。帖主的做法是把 token 与业务记录绑在一起——token 作为业务表的一个字段并加唯一索引，Redis 只做前置快速拦截。面试时补一句「Redis 是性能优化，不是正确性保证」，通常能让面试官继续往下问。

**状态机做业务幂等**：支付回调这类场景没法靠唯一索引，同一个支付单的回调可能来很多次、内容还不完全一样。用状态机加乐观锁：`UPDATE orders SET status = 'PAID', version = version + 1 WHERE id = ? AND status = 'WAIT_PAY' AND version = ?`，影响行数为 0 说明已被处理，直接返回成功。关键是「返回成功」而不是报错——对上游来说重复回调不是错误。状态流转与流水记录要放在同一个事务里，否则会出现状态对了但账对不上。

**MQ 幂等**：消费端维护去重表，用消息里的业务唯一键做唯一索引，消费成功与写去重记录在同一个本地事务里。不要用「消费前查一下、消费后记一下」的两段式，中间挂掉照样重复；也不要用 `messageId` 当幂等键，生产端重投时它可能变化。

**幂等的边界**：放在业务唯一键上，而不是请求 ID 上。回答时先问清场景——是用户重复提交、网关重试，还是 MQ 重复消费——再给分层答案：数据库唯一索引兜底、Redis 做前置拦截、状态机管业务流转。
