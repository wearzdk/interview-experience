### 《面试题目》

1. 说说缓存穿透怎么排查？
2. 线上真出这事，你是怎么定位到是穿透的？
3. 穿透、击穿、雪崩长得像，怎么区分？
4. 你的排查顺序是什么？
5. 采样 miss 的 key 具体怎么做？有什么坑？
6. 方案怎么取舍？为什么最后没上布隆过滤器？
7. 空值缓存被恶意刷怎么办？
8. 这道题你会怎么收尾？

### 《参考解析》

**先分清三种失效**：雪崩是大量 key 同一时刻失效，key 本身有数据；击穿是单个热点 key 失效，瞬间并发打穿；穿透是 key 在缓存和 DB 里都不存在，请求永远命中不了缓存。帖主第一反应是雪崩，给存量 key 的过期时间加随机抖动，观察半小时指标没动，才回头做区分。

**定位方法**：抓一段 Redis 的 `slowlog` 与 `monitor` 采样，看 miss 的 key 长什么样——结果高度集中在一个业务前缀下，后缀是递增 ID，且这些 ID 在 DB 里查出来全为空，基本锁定穿透。这一步不要省：把「缓存没预热」误判成穿透的例子很多。

**排查顺序**：第一看命中率曲线与 DB 慢查询——命中率下跌但 DB 查询耗时正常、只是量变大，更像穿透；DB 出现大量慢 SQL，先怀疑击穿或大 key。第二采样 miss 的 key 模式，看前缀是否单一、后缀是否机械递增。第三随机抽几十个 miss 的 key 反查 DB，确认都不存在。第四看请求来源，翻网关或 Nginx 的 access log，看 IP 与 UA 分布，脚本特征通常很明显。帖主那次就是一串请求来自少数几个 IP、UA 还是脚本。

**四条防线各自挡什么**：参数校验挡明显非法的 ID，成本最低先做；空值缓存挡重复查询的不存在 key，TTL 设几十秒，防止被刷满内存；布隆过滤器挡大量随机不存在的 key，适合 key 空间可枚举的场景，但有误判率、删除要额外处理；接口限流挡脚本扫库，治标但能挡住大部分恶意流量。它们是叠加关系，不是替代关系。

**为什么没上布隆**：商品 ID 自增、总量不大，空值缓存加限流已经够用；上布隆要多维护一份数据同步逻辑，还要处理重建与误判，收益不划算。这个取舍在面试里比「全都要」更有说服力。

**空值缓存被恶意刷**：随机 key 会让空值缓存本身变成内存压力。应对是给空值 key 加独立前缀便于监控与批量清理、设置短 TTL 并配淘汰策略、入口限流按来源维度收窄，以及离线分析日志把异常 key 段拉黑。

**收尾**：排查穿透的核心不是知道几个方案，而是能从监控、日志、key 模式三个维度证明「请求查的东西根本不存在」。指标一片红的时候，先分清是哪种失效，再决定往哪加防线。
