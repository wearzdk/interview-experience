### 《参考解析》

**Map 与普通对象的差别**。`Map` 的键可以是任意类型（对象、函数、NaN），普通对象的键只能是字符串或 Symbol，其它类型会被隐式转成字符串——这是最容易踩的坑，用对象当键会全部变成 `"[object Object]"`。顺序上 `Map` 保证插入顺序，普通对象的整数键会被提前并按升序排列。性能上频繁增删键时 `Map` 更稳（对象删除键会让引擎退化到字典模式），纯粹按固定字段存取时对象更快、字面量也更省内存。其它差异：`Map` 有 `size`、可直接迭代、有 `get/set/has/delete`；对象要用 `Object.keys` 再取长度。选择原则：键是动态的、类型不固定的用 `Map`；表示一个实体（配置、DTO）用对象。`WeakMap` 则是键弱引用，适合给对象挂元数据而不阻止回收。

**哈希表的实现原理**。核心是「哈希函数把键映射到桶 + 冲突处理 + 扩容」。插入时算哈希值、对桶数取模定位，冲突用链地址法（桶挂链表或红黑树）或开放寻址法（线性探测、二次探测、双重哈希）。负载因子（元素数/桶数）超过阈值（Java HashMap 0.75、Go map 6.5）就扩容并 rehash，代价是 O(n) 的一次性搬移，所以均摊插入仍是 O(1)。查找最坏是 O(n)（全部冲突），好的哈希函数加扩容让平均为 O(1)。工程细节值得点出：哈希值要再扰动（防止低位规律导致集中）、扩容通常翻倍（便于用位运算取模）、链表过长时转红黑树（Java 8 起阈值为 8）、以及哈希洪泛攻击要靠随机种子防御。

**进程间通信**。按场景分：管道与命名管道（父子进程、简单字节流）、消息队列（有边界、可按类型取）、共享内存（最快，需配信号量/互斥量同步）、信号（异步通知，承载信息极少）、套接字（本机 Unix domain socket 或跨机 TCP，最通用）、文件与内存映射文件（大数据、跨语言）、以及各系统的专有机制（Linux 的 eventfd/signalfd、Android 的 Binder、macOS/iOS 的 XPC 与 Mach port）。iOS 上还要加一层现实约束：App 与扩展之间走 App Group 共享容器或 `CFNotificationCenterDarwin` 通知，跨 App 只能靠 URL Scheme、Universal Links 或 Pasteboard。

**URL 到页面渲染**。分六段答：一是 URL 解析与缓存检查（强缓存命中直接读本地，否则带 If-None-Match/If-Modified-Since 发协商请求）；二是 DNS 解析（浏览器缓存、系统缓存、递归解析，可被 DoH 替代）；三是建立连接（TCP 三次握手，HTTPS 再加 TLS 握手，HTTP/2 多路复用省掉多连接）；四是发请求收响应（状态码、重定向、Content-Encoding 解压）；五是构建渲染树（解析 HTML 生成 DOM，遇到 CSS 阻塞渲染、遇到脚本阻塞解析，合成 CSSOM，生成布局树）；六是布局、绘制、合成（计算几何位置、分层、光栅化、GPU 合成上屏），之后是 JS 执行与可能的回流重绘。可补的性能点：首字节时间、FCP、LCP 分别对应哪一段。

**进程与线程**。进程是资源分配的基本单位，有独立虚拟地址空间、文件描述符表、信号处理；线程是 CPU 调度的基本单位，同进程内线程共享地址空间与堆，各有独立栈、寄存器上下文与线程局部存储。代价上，创建/销毁进程比线程重得多，进程间通信要跨地址空间（拷贝或映射），线程间共享内存但需要同步原语保护。崩溃隔离是决定性差异：一个线程段错误会带走整个进程，进程之间互不影响。协程再往上一层，用户态调度、切换只保存少量寄存器，适合 IO 密集。

**构造函数里能不能用虚函数**。可以写、能编译，但不会产生多态效果：构造基类部分时，对象的动态类型还是基类，虚表指针尚未更新为派生类，调用解析到基类版本；派生类部分还没构造，即便能调到派生实现也会访问未初始化的成员。同理析构函数里调用虚函数也不走派生版本。替代做法是把「构造后必须执行的初始化」拆成显式的 `init()`（两段式构造）或工厂函数，在对象完全构造后调用。

**虚函数实现多态**。每个含虚函数的类有一张虚表（vtable），存放虚函数地址；每个对象头部有一个虚表指针（vptr），在构造时被设为当前类的虚表。通过基类指针或引用调用虚函数时，编译器生成「从 vptr 取表项再间接调用」的代码，实际执行的是对象真实类型的实现——这就是动态绑定。限制：只有指针或引用能触发多态，按值传递会发生对象切片；构造函数与析构函数内不生效；虚函数调用比普通调用多一次间接跳转，且难以内联。C++ 的 `override`/`final` 关键字要用来让编译器检查签名是否真的覆盖。

**浏览器存储与适用场景**。Cookie：随请求自动发送、容量约 4 KB、可设 HttpOnly/SameSite，适合会话标识；`localStorage`：约 5~10 MB、同步 API、永久保存，适合用户偏好这类小配置；`sessionStorage`：同标签页生命周期，适合表单草稿与一次性状态；`IndexedDB`：异步、容量大（按配额）、支持索引与事务，适合离线数据与大量结构化缓存；Cache Storage（配合 Service Worker）：缓存请求响应，做离线与资源加速；此外还有较新的 OPFS（文件级）与较老的 WebSQL（已废弃）。选型看三点：要不要随请求发送、需不需要跨标签页共享、数据量与是否结构化。

**跨域的原因与解决**。原因是同源策略：协议、域名、端口三者任一不同即跨域，浏览器限制的是「读取响应」而不是「发出请求」，所以简单请求会到达服务端但响应被拦，非简单请求（自定义头、JSON、PUT/DELETE）会先发 OPTIONS 预检。解决方式按场景：服务端配置 CORS（`Access-Control-Allow-Origin` 精确回源、`Allow-Credentials` 与 `Allow-Headers`、预检缓存 `Max-Age`）；同主域不同子域用 `document.domain`（已逐步废弃）或反向代理把请求收敛到同源；开发期用 devServer proxy；跨域写操作可用表单提交或 `postMessage` 配合 iframe；纯展示类第三方资源用 JSONP（历史方案，只支持 GET）。注意 CORS 的凭证模式下 `Allow-Origin` 不能为 `*`。

**iOS 的持久化方案**。轻量键值用 `UserDefaults`（自动同步、不适合大对象与敏感信息）；敏感数据用 Keychain（加密存储、可设置访问控制，App 卸载后仍可能保留）；文件系统用 Documents/Library/Caches/tmp 按用途分开（Caches 会被系统清理，需可重建）；结构化数据用 Core Data 或 SQLite（SwiftData 是新的封装层），适合查询与关系；大量二进制用文件 + 元数据入库；跨 App 共享用 App Group 容器。选型原则：按数据量、查询需求、敏感性、是否需要跨设备同步（iCloud）决定，并处理好迁移与加密（`NSFileProtection`）。

**事件传递与响应链**。触摸事件的传递分两阶段：`hitTest` 自上而下找到最深的、包含触点且未隐藏/未禁用交互的视图（`pointInside` 逐层判断），返回它作为第一响应者；随后事件沿响应链自下而上传递——若该视图不处理（不实现 touches 方法或未识别手势），事件交给它的 `nextResponder`（父视图），一直传到视图控制器、窗口、Application，最终无人处理就丢弃。所以「视图不处理事件时怎么传下去」的答案是：不实现或调用 `super`，系统沿 `nextResponder` 链冒泡；要主动拦截可以用 `gestureRecognizer` 的 delegate 或重写 `hitTest` 返回 nil / 指定视图。注意 `hitTest` 只影响触摸命中，不影响 UIEvent 中的运动与远程控制事件（它们走各自的传递路径）。
