### 《参考解析》

**评测体系要先分清「评什么」再谈「怎么评」**。Agent 的评测维度至少六层：任务完成率（端到端是否达成目标，pass@1 与多次采样的 pass@k 要分开看）、步骤效率（平均步数、工具调用次数、token 消耗、端到端时延）、工具调用正确率（工具选对没有、参数是否合法、返回是否被正确解析）、指令遵循（输出格式、约束条件、该拒答时是否拒答）、鲁棒性（缺参数、工具报错、超长上下文、干扰信息下是否还能收敛）、安全合规（越权操作、泄露敏感信息）。评分标准的原则是「能程序化断言的绝不交给模型」：最终状态 diff、接口返回、数据库校验、单测通过率都可以写成断言；只有开放式输出才用 rubric 加 LLM judge，而且 judge 必须先与人工标注对齐过一致率，并锁定模型版本与提示词，否则评测分数会随 judge 漂移。评测集按场景分桶构造（意图、工具链长度、难度各一层），每桶几十条起步，badcase 持续回流，调优集与评测集必须隔离。

**准出条件不是一个总分，而是一组分层门槛**：P0 主路径用例 100% 通过；总体成功率不低于上一版基线（而不是不低于某个绝对值）；关键工程指标不劣化——时延 P95、单任务成本、工具调用失败率都在阈值内；无新增 P0/P1 缺陷。灰度阶段再加第二道门：线上采纳率、人工接管率、用户投诉与回滚次数。只报一个「准确率 85%」的评测结论在面试里会被追问「哪 15% 错、错在哪个环节、能不能接受」，所以要准备好按层拆开的数字。

**badcase 要按链路分层归因，而不是笼统说「模型不行」**：意图识别错、检索该召回没召回或召回噪声过大、规划与工具选择错、参数填错、工具返回解析错、上下文丢失、过早结束、事实幻觉。每条 badcase 都要带可复现输入、期望输出、实际输出，以及 prompt、工具调用与返回的完整日志，聚类后按影响面排序逐类修。修完必须回归——原 badcase 集加上新增集一起跑，否则很容易修好一个弄坏两个。意图识别召回后的迭代是同一套闭环：先定意图分类体系与拒识兜底策略，从线上抽样标注意图做混淆矩阵，找出高频混淆对，再决定是补训练样本、拆细意图、改多轮改写补全上下文，还是加规则兜底；分工上产品定意图边界、算法改模型与样本、工程改规则与兜底、测试出指标与回归集，反馈对象要指得具体。

**模型压测要先把口径说清楚**。压的是并发会话数、QPS、流式输出吞吐与上下文长度这几项的组合，核心指标包括首 token 时延（TTFT）、token 间间隔（TPOT/ITL）、输出 token 吞吐、P95/P99 端到端时延、错误率（429、5xx、超时）以及 GPU 利用率、显存与 KV Cache 命中率。token 吞吐一定要区分单流与聚合：单流是「该请求输出 token 数 ÷ 生成耗时」，聚合是「所有并发流输出 token 总和 ÷ 压测时长」，还要说明统计的是输入还是输出、是否包含 prefill。方法是固定输入长度与输出长度分布、阶梯加压找吞吐拐点与延迟陡升点、区分冷启动与缓存命中，工具上 k6、Locust 或自写的流式客户端都可以，关键是能把 TTFT 与 TPOT 单独打点。

**UI 自动化操控浏览器**的答案要落到工程细节：Playwright、Puppeteer、Selenium 通过 CDP 或 WebDriver 驱动浏览器；选择器优先用 role、label、testid 这类语义定位，避免 nth-child 这类一改版就碎的结构选择器；等待用「等待元素可交互」而不是固定 sleep；要处理 iframe、Shadow DOM、多标签页、文件上传下载与登录态复用（storageState）；排查靠 trace、视频与截图。再补一句 Agent 场景的特殊性：浏览器工具要能返回可被模型理解的页面快照（裁剪后的可交互元素树），而不是整页 HTML，否则 token 会被噪声吃光。

**为什么自研框架而不是 codex + skill**，回答的关键是讲边界而不是贬低现成方案。现成 harness 的循环、工具集与上下文管理是黑盒，适合「给开发者用的通用编码代理」；自研的动机通常是四件事：领域专用工具与权限控制（能碰哪些系统、哪些操作要审批）、可观测与可回放（每一步的工具入参出参、耗时、token 都要留痕，badcase 才能复盘）、评测可控（能对中间步骤打分，而不只看最终结果）、成本与延迟优化（上下文裁剪、缓存、并发策略）。代价也要说清：循环控制、错误重试、上下文压缩、沙箱隔离、并发与限流全要自己维护。判断标准可以归纳成一句：这个场景是否需要「专用工具 + 专用评测 + 专用权限」，三者缺一，用现成方案更划算。

**多 Agent 串上下文不要靠全量拼接**。可行做法是结构化任务契约：主 Agent 维护全局计划与状态，子 Agent 只接收完成当前子任务所需的切片（目标、输入数据引用、输出 schema、验收条件），产物写进共享状态存储或黑板，下游按引用读取而不是把全文塞进 prompt；长任务用摘要加 artifact id 控制上下文长度；并发子任务要约定幂等键与冲突处理规则。这样既能控制 token，也能让每一步可回放。

**语言基础部分**：pytest 常用装饰器包括 `@pytest.fixture`（含 `autouse`、`scope`、`params`）、`@pytest.mark.parametrize`、`@pytest.mark.skip` / `skipif` / `xfail`、`@pytest.mark.usefixtures`，以及自定义 mark（需在配置里注册，strict 模式下未注册会直接报错），超时与重试用插件提供的 mark。Python 字典的常用操作：下标取值与 `get` 带默认值、`setdefault`、`keys` / `values` / `items`、`update`、`pop` / `popitem`、`del`、`in`、`len`、浅拷贝 `copy`、`fromkeys`，3.9 之后还有 `|` 合并；要能说出「键必须可哈希」「3.7 起保持插入顺序」。

**Java 三连问**：接口只声明能力契约，可以有抽象方法、常量、以及 Java 8 之后的 default / static 方法，不能有构造器，一个类可以实现多个接口；抽象类是 is-a 的继承关系，单继承，可以有状态与构造器。重写是子类覆盖父类同签名方法、运行时多态，要求返回类型协变、访问权限不能收窄、受检异常不能扩大；重载是同一类中方法名相同、参数列表不同、编译期决议，返回类型不参与重载判断。基础类型八个：byte、short、int、long、float、double、char、boolean，要能说出位数与默认值，以及包装类缓存（Integer 默认缓存 -128 到 127）带来的 `==` 陷阱。

**HTTP 与 HTTPS**：HTTP 明文传输，HTTPS 在 HTTP 与 TCP 之间加了 TLS，用非对称握手协商出对称密钥再加密业务数据，靠证书链验证服务端身份，能防窃听与中间人；默认端口 80 与 443；代价是握手与加解密的开销，TLS 1.3、会话复用与 HTTP/2、HTTP/3 已经把这块压得很低。Linux 常用命令按场景记：看资源用 top、free、df、du，看进程与端口用 ps、ss、lsof，看日志用 tail -f、grep、awk、sed，找文件用 find，打包用 tar，服务管理用 systemctl、journalctl。

**chmod 777 的含义与风险**：三位八进制分别对应属主、属组、其他人的 rwx，7 = 4（读）+ 2（写）+ 1（执行），777 就是任何人都能读、写、执行。它能「让问题消失」，但把写入权限开放给所有人，任何被攻破的低权限进程都能改写这个文件，生产环境不应使用；常规做法是目录 755、文件 644、脚本 755，配合 chown 设属主、umask 控默认权限，`chmod -R` 要先确认路径再执行。

**快速排序**：分治加划分，选 pivot 后把小于与大于它的元素分到两侧，再递归处理。Lomuto 划分好写但遇到大量重复元素会退化，Hoare 划分交换次数少；平均与最好 O(n log n)，最坏 O(n²)（已有序且取首元素作 pivot），靠随机化或三数取中规避；空间是递归栈 O(log n)，不稳定。工程上还会加两个优化：小数组切换到插入排序、三路划分处理重复键。面试时先写能跑通的基础版，再主动说出这几处优化，比一上来写复杂版本更稳。
