### 《参考解析》

**无卫星信号下的场内定位，答的是「用什么观测量 + 怎么融合」，不是堆名词。** 场内常用的是 UWB（TWR 测距或 TDOA 到达时差，精度 10~30cm）、蓝牙 AoA/AoD（米级、成本低）、视觉 SLAM 与激光 SLAM（不依赖外部基站但怕光照与几何退化）、以及二维码/反光标靶这类绝对基准。工程上通常是「UWB 提供绝对位置 + IMU 做短时递推 + 轮速计做里程约束」的松耦合或紧耦合融合，用扩展卡尔曼滤波或因子图优化输出位姿。要主动讲清每个方案的失效条件：UWB 在金属遮挡下非视距误差大、需要基站几何布局良好；视觉在弱光与白墙前退化；SLAM 长时间会漂移，所以要有回环或标靶做重定位。这题面试官想听的是「你知道每种方案什么时候会坏」。

**多类目标检测的干扰过滤，是一道「分层降误检」的题。** 第一层是模型本身：训练数据里补负样本与相似类难例、加分类头置信度阈值与 NMS 的 IoU 阈值调节；第二层是时序：用跟踪（卡尔曼 + 匈牙利匹配）要求目标连续多帧出现才确认，单帧跳变直接丢；第三层是空间与业务约束：用 ROI 掩膜排除画面里不可能出现的区域、用目标与场景的几何关系（尺寸、地面接触点）过滤；第四层是身份：分类模型之外再加 ReID 特征或二维码/工牌做确认。答的时候按「模型 → 时序 → 空间 → 身份」四层讲，比只说「调阈值」完整得多。

**端侧还是移动端的取舍，本质是延迟、带宽、算力、隐私四个约束的平衡。** 端侧推理延迟低（十几到几十毫秒）、不依赖网络、隐私好，但算力与功耗受限，模型要量化剪枝、分辨率要降；放移动端或云端可以用大模型，但要吃传输延迟与断网风险。常见折中是「端侧跑轻量检测做粗筛与触发，关键帧上传做精细识别」，或者端侧 NPU 跑 INT8 模型、CPU 跑后处理。回答时给一个具体数字（比如端侧 30fps 下每帧 20ms 预算）会显得真的做过。

**模型量化的收益要落到「精度掉了多少、速度涨了多少、怎么补回来」。** 常见路径是 FP32 → FP16（几乎无损、需要硬件支持）→ INT8（需要校准集做 per-tensor 或 per-channel 量化，注意激活值的离群点）。收益是显存/内存占用降到 1/4、带宽压力下降、NPU 的 INT8 算力通常是 FP16 的数倍。精度补偿手段：量化感知训练（QAT）在训练时插入伪量化节点、对敏感层（第一层与检测头）保留高精度、用 KL 散度或最小化 MSE 选阈值。验证要对比 mAP、逐类召回率，以及真实场景的漏检率，不能只看整体精度。

**U-Boot 的两个阶段：SPL（或 MLO）与 U-Boot proper。** 第一阶段跑在片上 SRAM 里，做最基础的初始化（时钟、引脚复用、DDR 控制器），把完整的 U-Boot 从存储介质（eMMC/NAND/SPI Flash）载入 DDR；第二阶段在 DDR 里运行，初始化外设、解析环境变量、加载设备树与内核、把控制权交给内核。移植工作主要是改 DDR 初始化参数（时序、容量、位宽）、改 bootcmd 与分区表、适配存储与外设驱动、以及打开串口与 fastboot 方便调试。

**DDR 参数与行命中/缺失/冲突要能串起来讲。** 需要调的参数包括：时钟频率、CAS Latency 等一组时序（tRCD、tRP、tRAS、tWR）、刷新间隔 tREFI、以及控制器侧的调度策略。DRAM 内部是 bank × row × column 的阵列，访问时先激活（ACT）把整行读进行缓冲，再列选读写，最后预充电（PRE）关行。**行命中**：要访问的行已在缓冲里，直接列读写，最快；**行缺失**：换到同 bank 的另一行，要先预充电再激活，多出 tRP + tRCD 的延迟；**行冲突**：多个请求争抢同一个 bank 的不同行，只能串行，频繁换行会让有效带宽大幅下降。优化手段是让连续访问尽量落在同一行（数据布局按行优先）、把不同 bank 的访问交错排布、避免多个高带宽主设备同时打同一个 bank。

**CAN 的完整链路要按「硬件 → 驱动 → 协议栈 → 应用」讲。** 硬件是 CAN 收发器 + 控制器（很多 MCU 内置），差分总线 CAN_H/CAN_L，两端 120Ω 终端电阻；驱动层做位时序配置（波特率与采样点）、过滤器（按 ID 掩码只收关心的帧）、收发邮箱与中断；协议栈层做分帧与重组（经典 CAN 单帧最多 8 字节，长数据要 ISO-TP 分段，CAN FD 可到 64 字节）、流控与超时重传；应用层是 UDS 诊断或自定义的节点协议。工程落地难的原因要具体：不同厂商的 DBC 定义与信号缩放不一致、总线负载高时低优先级帧被长期推迟（仲裁按 ID 优先级）、错误帧与节点离线（bus-off）恢复策略、EMC 干扰导致偶发位错误、以及整车厂与供应商之间的协议版本对齐。

**「标准协议为什么落地还是难」，答案在协议之外。** 协议只规定格式与交互，不规定时序容差、异常恢复、节点上下线、以及双方的实现缺陷；真实系统里还有版本兼容（老节点不支持新报文）、总线负载与实时性、线束与接地带来的物理层问题、以及跨团队的联调窗口。能举一个自己踩过的例子（比如某节点 bus-off 后没有自动恢复导致整段总线静默）最加分。

**「通信成功率 95-97% 为什么不是 100%」要分层归因。** 协议层面：CAN 的重传机制在总线错误计数超限时会进入错误被动甚至 bus-off，仲裁失败与 ACK 缺失都会让单次发送失败；TCP 有重传但超时判定与拥塞窗口会让长尾延迟变长。工程层面：电磁干扰、接插件接触不良、线束过长导致信号反射、终端电阻缺失、供电波动、固件里的缓冲区溢出与丢帧、以及对方节点处理不过来。要把 95-97% 这样的数字拆成「物理层错误率 / 协议重传后仍失败率 / 应用层丢帧率」，再讲怎么用误码率统计、错误计数器、抓包工具定位，这比笼统说「干扰」有说服力。
