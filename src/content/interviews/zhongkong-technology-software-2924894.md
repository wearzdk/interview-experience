### 《面试题目》

1. 介绍你的项目
2. JVM 调优怎么做？
3. SQL 调优怎么做？
4. MySQL 索引相关问题

### 《参考解析》

**JVM 调优的正确姿势是「先有指标、再有动作」，而不是背参数。** 第一步确定目标：是要降 Full GC 频率、压 P99 延迟，还是解决 OOM。第二步取证据：看 GC 日志（`-Xlog:gc*` 或 GCLogAnalysis）、用 `jstat -gcutil` 看各代占用与 GC 次数耗时，`jmap`/堆 dump 看对象分布，`jstack` 配合 `top -H` 找 CPU 热点线程。常见结论和对策：对象创建速率高导致 Young GC 频繁 → 加大新生代或调 `SurvivorRatio`，让短命对象在 Young 阶段就回收掉；对象提前晋升到老年代导致 Full GC → 检查是否有大对象直接进老年代（`PretenureSizeThreshold`）、是否 Survivor 太小，必要时用 G1/ZGC 这类低停顿收集器；OOM 则按 dump 里的支配树找泄漏点，而不是简单加大堆。要主动说清「调优的收益上限取决于代码」，池化、减少无谓对象、避免大对象拷贝往往比调参数有效得多。

**SQL 调优的标准流程是「找出慢的那条 → 看执行计划 → 减少扫描行数与随机 IO」。** 用慢查询日志（`long_query_time`）或 APM 定位到具体 SQL，再 `EXPLAIN` 看 `type`（避免 ALL 全表扫）、`key`（实际命中的索引）、`rows`、`Extra`（避免 Using filesort / Using temporary）。优化手段按性价比排序：补齐或改造索引（联合索引注意最左前缀与区分度，把范围条件放最后）、消除索引失效（不在列上做函数运算/隐式类型转换、避免前导 `%` 模糊）、只查需要的列以利用覆盖索引避免回表、拆分大 SQL 与批量操作、深分页改延迟关联或游标分页、以及把高频复杂查询结果做缓存或预聚合。如果单表数据量本身很大，再考虑分区或归档冷数据。

**索引相关的问题一般会往这三个方向问。** 一是原理：InnoDB 用 B+ 树，非叶节点只存键所以树矮（千万级数据约 3 层）、叶子节点双向链表支持范围扫描与排序、聚簇索引的叶子就是数据行、二级索引的叶子存主键因此需要回表。二是设计：联合索引的顺序按「等值条件在前、区分度高的在前、范围条件在后」，尽量让查询走覆盖索引；区分度极低的列（性别、状态）单独建索引意义不大。三是失效场景与代价：索引会占用空间并拖慢写入（每次写入要维护所有二级索引），所以不是越多越好。面试时把「为什么快」和「代价是什么」都答上，比只背失效清单更完整。
