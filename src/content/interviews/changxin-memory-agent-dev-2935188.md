### 《参考解析》

**「为什么自己做」这道题只有一种答法能被接受：说出通用工具做不到的具体约束。** 合格的约束是可验证的：代码与数据不能出内网（私有化）、要接公司自己的代码规范与内部框架、要跟内部 CI / 代码评审 / 工单系统打通、要在几十万文件的大仓里做检索而通用工具会超上下文、要按项目隔离上下文与权限。不合格的答法是「想做得更好」「想学习」。面试官问这题其实是在问「你有没有想清楚这件事的边界」，回答时顺带说明「哪些部分我们会直接用现成的」（比如模型、协议、部分工具）反而加分，因为它证明你不是为了造轮子而造轮子。

**Agent 分层不要背，要能解释每层之间靠什么接口。** 常见的五层是：交互层（CLI / IDE / Web，负责展示与打断）、编排层（任务规划、循环控制、终止条件）、能力层（工具：读写文件、跑命令、搜代码、调外部服务）、上下文层（会话历史、检索、记忆、压缩）、模型层（选模型、参数、重试与兜底）。被追问「能不能简化成三层」时，正确答案是能——合并成交互 / 编排 + 能力 / 上下文 + 模型，代价是编排和能力耦合之后，工具注册与权限控制会散在业务代码里。这个追问考的是你有没有真的做过取舍，而不是背了一张架构图。

**Coordinator 中心模式的设计初衷是「让决策只有一个来源」。** 自组织 swarm 里每个 Agent 都基于局部信息做决定，冲突靠协商解决，结果是不收敛、重复劳动、以及「谁改了什么」说不清。中心模式把全局状态（任务树、进度、已改文件、验收标准）收在一处，子 Agent 只负责执行一个封闭的子任务并回传结果，于是有了三个直接收益：任务可以审计、冲突能在派发前避免（同一文件分给两个人就是拆分错误）、失败能重试。代价也很清楚：中心是瓶颈、中心是单点、中心的理解能力决定了整体上限。

**单点局限要分层答，不能只说「会挂」。** 三个层面：吞吐（所有子任务的派发与汇总都要过中心，中心的模型调用次数是 O(子任务数)）、认知（中心要维护全局状态，上下文一长就开始丢细节，最终决策质量下降）、可用性（中心进程挂了整条任务链断掉，而子 Agent 的工作可能已经产生副作用）。对应的缓解分别是：子任务批量化 + 中心只做摘要决策、外置结构化状态（任务树存到磁盘/数据库，中心每次只读它需要的部分）、以及检查点 + 断点续跑。

**「多个 Coordinator 消除单点」是陷阱题。** 多个中心之间就又出现了协调问题——它们对同一份代码的分支、同一个文件的修改、同一个任务的归属要达成一致，这本质上回到了分布式共识，成本比单点高得多。正确的答法是：不做多主，做「主备 + 任务分片」。主备解决可用性（带租约的选主，主挂了备接管，未完成的子任务从检查点重放）；分片解决吞吐（按模块/目录把任务切成互不重叠的片，每个片有自己的小中心，片之间靠文件所有权约定避免交叉）。这样既没有多主冲突，也不是单点。

**任务拆分粒度看两个信号：可验证性和上下文独立性。** 一个子任务如果能写出明确的验收标准（跑哪个测试、改哪个文件、输出什么格式），并且执行它不需要另一个子任务的中间结果，就可以拆出来；反之就并回父任务。工程上的经验值是「一个子任务要能在一次模型上下文里做完，并且失败后重试的成本可接受」。拆得太细的代价是中心的调度开销与子任务之间的接口成本超过收益；拆得太粗的代价是失败无法定位、上下文爆掉。

**「中途发现规划错了」要答成一套机制，而不是「重新规划」。** 触发信号有三类：子任务连续失败、子任务的产出与验收标准不符、执行过程中发现了规划时不知道的事实（比如依赖的模块根本不存在）。机制是：先把已完成的部分固化成检查点（哪些文件已改、哪些结论已确认），再做影响面分析（错误会影响哪几个下游子任务），只重规划受影响的那一段，最后把「为什么改」写进状态里供后续参考。全量推翻重来是最差的做法，因为已经产生的副作用（改过的文件）不会自动回滚。

**动态重规划的风险是「震荡」。** 每一轮都基于当前局部信息调整计划，可能出现在两个方案之间反复横跳、每轮都推翻上一轮的结论，任务永远不收敛。防护手段：给重规划设次数上限和成本上限、要求重规划必须给出「与上一版的差异及理由」、以及把「已确认的事实」与「待验证的假设」分开存——只有假设可以被推翻，事实不能。

**「为什么不直接用单 Agent 做大重构」考的是你对上下文与失败代价的理解。** 大重构的特征是跨文件、跨模块、需要长期保持一致的设计决策。单 Agent 做它的三个硬伤：上下文装不下（大仓的相关代码本身就超过窗口）、错误会累积（前面理解错了一个接口，后面几十处修改全错，而且要到最后编译才发现）、无法并行（一次只能改一处，时间成本是线性的）。多 Agent 的收益正是把「理解」和「执行」分开：中心维护一致的设计决策，执行者各自在封闭上下文里改一小块。

**Coordinator 与「Planner / Coder / Reviewer 角色式多 Agent」的本质差别在状态所有权。** 角色式里每个角色都持有完整上下文、平级互相传消息，好处是灵活，坏处是没有唯一真相、消息会爆炸。Coordinator 式里只有中心持有全局状态，子 Agent 是「无状态的一次性执行者」，输入是任务契约、输出是结果，彼此不直接通信。判据可以用一句：如果两个 Agent 需要来回商量才能完成任务，那它们是角色式；如果它们只需要各自对着契约干活、结果由第三方汇总，那是中心式。

**任务无法完全隔离时，靠「所有权 + 顺序」而不是靠商量。** 具体三层：文件级所有权（同一时刻一个文件只有一个 Agent 可写，中心在派发时就知道谁会碰哪些文件，冲突的片串行化）、接口冻结（跨模块的契约先由中心定下来并写成文件，执行者只能读不能改）、合并阶段（各片产出先落到独立的 diff/分支，由中心统一合并并跑全量测试，冲突在合并时暴露而不是在执行时互相踩）。这也解释了为什么「耦合度评估」要放在派发前：一旦派发出去才发现两个子任务要改同一个文件，就只能回滚重来。

**Code Agent 的幻觉要用「可验证」来治，不能靠提示词。** 三类高频幻觉：编造不存在的文件或函数、编造命令输出、声称改完了但实际没改。对应三种硬约束：所有路径和符号必须先经检索确认存在才允许引用（工具返回 not found 就让模型重新检索，而不是继续写）、所有结论必须来自工具的真实返回（不许模型自己复述「测试通过了」）、所有修改必须回读确认（读回文件内容、跑对应测试）。这套思路和「工具报成功必须回读确认」是同一条。

**上下文压缩的触发条件应该是「预算」而不是「感觉」。** 常见触发：token 用量超过窗口的某个比例（比如 70%）、对话轮次超过阈值、或者每次任务阶段切换时主动整理。压缩会丢信息，所以要做成有损但可控的：先按重要性分级（system 与硬约束逐字保留、工具结果只留摘要和关键输出、早期对话做结构化摘要），摘要必须包含「已确认的事实 / 未完成的待办 / 用户给过的约束」三块。验证压缩没压坏的办法是探针问题，而不是相信摘要看起来通顺。
