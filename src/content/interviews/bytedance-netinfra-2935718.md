### 《参考解析》

1. **任务不丢**：生产端要等 broker 确认（acks=all）并处理发送失败重试，消费端先处理再提交位点，处理失败进重试队列或死信，位点提交与业务写入放在同一个事务或同一份幂等记录里。核心是「至少一次投递 + 消费端幂等」，而不是追求恰好一次。

2. **分 key**：按业务主键哈希，保证同一实体落到同一分区从而有序；热点 key 会倾斜，需要加盐打散或对热点单独建通道。分 key 的目标是「顺序性」和「均衡」两个约束的折中。

3. **幂等**：用业务唯一键（订单号 + 操作类型）建唯一索引或写幂等表，写入前先判重，重复请求直接返回上次结果。下游响应丢失时不能靠「没收到成功响应就重试」判断失败，要靠查询补偿——先按幂等键查结果，查不到再重试，且重试本身也必须带同一个幂等键。

4. **全流程幂等**：从入口生成全局唯一请求 ID，一路透传到下游，每一层都用这个 ID 判重；状态机上的状态迁移要带条件更新（`where status = 旧状态`），避免并发重复推进。

5. **令牌桶按需补令牌**：定时补充要为每个桶维持一个定时器，桶多了开销大且精度受调度影响。按需补充只记录上次补充时间，取令牌时按经过的时间差算出应补数量，O(1) 且无后台任务，天然支持海量桶。

6. **互斥锁不保证正确性**：锁只能保证临界区的互斥，如果漏锁了某个读写路径、锁的粒度不对、或者有代码在锁外持有并修改了共享数据，仍然会错。另外要区分「数据竞争」和「逻辑正确」——用 `-race` 能查出前者，后者要靠设计。

7. **扣库存加锁位置**：最可靠的是数据库层的条件更新 `update stock set count = count - 1 where id = ? and count > 0`，靠行锁和原子性保证不超卖；热点商品再在前面加 Redis 预扣减削峰，Redis 里扣成功才落库，失败回滚。应用层锁用来减少无效竞争，不能作为唯一保证。

8. **GMP 与 M**：G 是协程，M 是内核线程（由操作系统调度，是真正的执行体），P 是逻辑处理器，持有本地运行队列。M 必须绑定 P 才能执行 G，P 的数量默认等于 CPU 核数。M 是内核态线程，Go 运行时通过它把大量 G 复用到少量 M 上。

9. **Go 为什么能开大量协程**：goroutine 初始栈只有 2KB 且可动态增长，创建和切换都在用户态由运行时完成，不需要陷入内核；而 Java 线程默认栈 1MB 左右，创建、销毁和上下文切换都要操作系统参与。再加上 netpoller 让阻塞的 IO 不占线程，所以十万级协程是常态。

10. **启动 goroutine**：用 `go func()` 加 `sync.WaitGroup` 或 `errgroup` 管理生命周期，用带缓冲的 channel 或信号量控制并发度，配合 `context` 做取消和超时，避免无限制地起协程把下游打挂。

11. **订单扣减系统设计**：入口做限流和幂等，库存用 Redis 预扣加数据库条件更新兜底，扣减与订单创建放在本地事务里，跨服务用可靠消息或事务消息保证最终一致，失败走补偿与对账。要讲清「超卖、重复扣减、扣了没下单」三种异常各由哪一层兜住。

12. **Redis 宕机**：单靠 Redis 锁在宕机或主从切换时会丢锁，所以关键路径必须有数据库层的唯一约束或条件更新兜底。工程上可以用 Redlock 降低风险，但更实际的做法是「锁只做优化，正确性交给数据库」，并给锁设过期时间和续期。

13. **事务的使用**：本地事务包住「扣库存 + 建订单 + 写幂等记录」；跨服务不能用分布式事务硬扛时，用本地消息表加补偿，保证最终一致。

14. **LRU**：哈希表加双向链表，get 命中后把节点移到头部，put 时若容量满则删尾部。热点 key 问题会让单个分片过载，解法是对热点 key 做本地缓存、读多写少时多副本、或者按 key 前缀二次分桶把压力摊开。
