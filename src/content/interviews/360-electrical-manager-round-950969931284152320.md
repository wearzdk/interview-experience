### 《参考解析》

**`==`、`equals` 与 `hashCode`**：`==` 比的是引用（基本类型比的是值），`equals` 默认也是引用比较，需要按业务语义重写。`hashCode` 必须与 `equals` 保持一致——两个对象 `equals` 为真则哈希值必须相等，否则放进 HashMap/HashSet 会出现「同一个键找不回来」的情况；反过来哈希相等不要求 equals 相等，这就是哈希冲突。重写后要用同一组字段，且字段不可变，否则对象作为键后哈希值变化会脱离原来的桶。

**String、StringBuilder、StringBuffer**：String 不可变，每次拼接都产生新对象，适合常量、作为 Map 的键（不可变才能保证哈希稳定）；StringBuilder 可变、非线程安全，单线程拼接用它；StringBuffer 可变、方法加了 `synchronized`，线程安全但有锁开销，只在确实跨线程共享同一个缓冲区时才需要考虑，实际工程里更常见的是每个线程各用一个 StringBuilder。

**接口与抽象类**：接口描述能力与契约，可以多实现，Java 8 之后可有 default / static 方法，字段只能是常量；抽象类描述「是什么」，单继承，可以有状态和构造器、可以有具体实现。选型看语义：需要多继承行为、给不相关的类加统一能力用接口；一族对象共享状态和骨架实现用抽象类，常见做法是抽象类实现接口、留一两个模板方法给子类。

**HashMap 1.7 与 1.8**：1.7 是数组 + 链表，头插法，扩容时会重新计算索引，并发扩容可能成环导致 CPU 打满；1.8 改为数组 + 链表 + 红黑树，尾插法，扩容用高低位拆分避免重算哈希，链表长度到 8 且容量不小于 64 时树化、退化到 6 时链化。树化的意义在于把最坏情况的查找从 O(n) 降到 O(log n)——攻击者可以用大量同哈希的键把链表拉长做哈希碰撞攻击，树化是缓解手段。要能顺带讲清容量为何恒为 2 的幂、负载因子 0.75 的时间与空间权衡。

**ConcurrentHashMap**：JDK 7 用分段锁，Segment 继承 ReentrantLock，锁粒度是一段，并发度等于段数；JDK 8 去掉分段，用 CAS 插入空桶、`synchronized` 锁住单个桶的头节点，锁粒度降到桶级，读操作靠 `volatile` 保证可见性、完全不加锁，扩容时支持多线程协助迁移。答题时讲清「锁粒度从表到段再到桶」的演进，以及 `size()` 为什么只能给近似值（需要统计多个 CounterCell）。

**fail-fast 与 fail-safe**：fail-fast 指集合在迭代过程中被结构性修改（增删）时，`modCount` 与迭代器保存的期望值不一致，立刻抛 `ConcurrentModificationException`，ArrayList、HashMap 都是这种；`iterator.remove()` 是唯一允许的修改方式。fail-safe 指迭代时操作副本或快照，不抛异常但可能读不到最新数据，例如 `CopyOnWriteArrayList` 与 `ConcurrentHashMap` 的弱一致迭代器。注意 `modCount` 检查是尽力而为的，不能当并发安全机制用。

**synchronized 与 ReentrantLock**：synchronized 是 JVM 层面的管程实现，自动加锁释放、不可中断、非公平（可通过锁升级优化），代码简洁；ReentrantLock 是 AQS 上的实现，支持公平与非公平、可中断获取、超时获取、多个条件队列（`Condition`），必须手动 `unlock`，通常写在 try/finally 里。选型上优先 synchronized，需要超时、可中断、公平或条件变量时才用 ReentrantLock。锁升级路径（偏向锁 → 轻量级锁 → 重量级锁）与「锁的是对象头 Mark Word」是常见追问。

**volatile 与原子性**：volatile 保证可见性与禁止指令重排（通过内存屏障），不保证复合操作的原子性——`count++` 是读改写三步，多线程下依然会丢更新，要用 `AtomicInteger` 或加锁。典型用途是状态标志位、双重检查锁定的单例（防止「分配内存—初始化—赋引用」重排导致拿到半初始化对象）。

**线程池参数与拒绝策略**：核心线程数、最大线程数、空闲存活时间、任务队列、线程工厂、拒绝策略、allowCoreThreadTimeOut。执行顺序是先核心线程、再入队、队列满才扩到最大线程数、再满则走拒绝策略——顺序记错是最常见的失分点。核心数按任务类型定：CPU 密集接近核数，IO 密集按 `核数 × (1 + 等待时间/计算时间)` 估算。拒绝策略四种：AbortPolicy 抛异常、CallerRunsPolicy 由提交线程执行（天然反压）、DiscardPolicy 静默丢弃、DiscardOldestPolicy 丢最老的。队列选择上，用无界队列会让最大线程数失效，可能堆到 OOM。

**ThreadLocal 与内存泄漏**：每个 Thread 持有一个 `ThreadLocalMap`，键是 ThreadLocal 的弱引用，值是强引用。泄漏发生在「ThreadLocal 对象被回收但线程还活着」时：键没了、值还在，且因为键为 null 无法再被访问，只能等线程结束。线程池的线程长期存活，泄漏会累积，所以必须在 finally 里 `remove()`。追问「为什么不用参数传递」的答法是：调用链很深、中间层不关心该上下文时才用 ThreadLocal（如用户身份、traceId），否则显式传参更清晰、更可测；线上出过的问题通常是异步线程或线程池切换导致上下文丢失，需要 `TransmittableThreadLocal` 或手动传递。

**AQS 与两类同步器**：AQS 是一个 `volatile int state` 加一个 CLH 变体的双向等待队列，子类通过 `tryAcquire / tryRelease` 定义 state 的语义（ReentrantLock 用它表示重入次数，Semaphore 表示许可数，CountDownLatch 表示剩余计数）。`CountDownLatch` 是一次性的，计数到 0 后不能重置，用于「等 N 个任务都完成」；`CyclicBarrier` 可循环使用，用于「N 个线程互相等待到齐后一起继续」，还能带一个到齐时执行的动作。语义差别是「一个线程等多个」还是「多个线程互等」。

**项目深挖的答法**：每个数字都要能说清来源——QPS 和 RT 是压测得到的还是监控采的、压测的并发与数据量是多少；瓶颈定位要给出证据链（火焰图、慢查询日志、GC 日志、连接池等待），而不是「感觉是数据库慢」。为什么选 Redis 而不是本地缓存，答案在一致性、容量与多实例共享三点上：本地缓存快但没有跨实例一致性、容量受单机内存限制、重启即失效。如果重做一遍，给出一个具体的改进点并说明代价，比笼统说「加监控」更有说服力。
