### 《参考解析》

**两种生成模式与 Prompt 增强**：普通模式直接让模型出 HTML，快但只能应付单页；工作流模式把「需求分析 → Prompt 增强 → 并行素材收集 → 复杂度路由 → 代码生成 → 质量检查 → 工程构建」串成图，由路由决定产出单页还是整个 Vue 工程。Prompt 增强是最值钱的一环：用户说的是「做个卖咖啡的官网」，下游需要的是页面结构、技术栈、必备功能、视觉风格和硬约束（不要外链、移动端适配）。所以别把增强当「多写一段提示词」，产出必须是结构化字段，下游才能稳定消费，也才能拿来评测。LangChain4j 管模型调用与工具集成，LangGraph4j 管节点编排、条件边和把质检结果回灌成重试。

**质检节点与构建失败**：规范不通过时把问题回灌给生成节点、限定最多三次重试，方向是对的；构建失败直接结束则是短板——应该截断并结构化构建日志（错误类型、文件、行号），带着错误做定点修复，同时设重试与成本上限，超限就降级交付：返回能跑的最小版本加明确的失败原因。重试要带 diff，让模型只改不通过的部分，整项目重写既烧 token 又引入新错。

**用户手改代码后的多轮修改**：核心是把「重新生成」换成「打补丁」：每次生成后留代码基线快照，下一轮先做差异定位，产出 patch 而不是整文件覆盖；用户编辑过的区间打标记，冲突时不静默覆盖，交回模型重写或提示用户确认。底座是版本管理与回滚，没有基线就谈不上保护用户改动。

**单 Agent 与多 Agent**：节点和路径由开发者预定义的是 Workflow，可控、可测、成本可估；由模型看工具返回决定下一步的是 Agent Loop，灵活但不确定。真实系统一般是外层工作流、内层局部 loop。多 Agent 的收益在任务可并行、上下文可隔离、子任务能独立验收；代价是上下文传递损耗、状态同步、失败归因变难、token 翻倍。流程明确时单 Agent 更划算。

**工具调用安全**：Prompt 层（明确禁止事项、防注入）只能降低概率，不能当边界。硬约束要落在 runtime：工具白名单、参数 schema 校验、文件访问限定工作区、命令走沙箱与超时、危险操作人工确认、调用留审计日志、按步数与 token 设上限。一句话：不假设模型始终可靠，关键权限由程序强制控制。

**Harness、MCP 与子 Agent**：Harness 是围绕模型的执行环境——上下文装配、工具注册、权限、状态、重试与日志。MCP 是工具与数据源的接入协议，规定 server 怎么暴露能力、client 怎么发现调用；CLI 是交互界面，跟 MCP 不在一个层面。子 Agent 适合信息收集可并行或上下文必须隔离的场景，主 Agent 只留规划与验收，否则检索结果会把主上下文撑爆。

**评测**：推广到团队前最缺的是「任务真的完成了」的证据链。任务层看成功率并按失败类型分类（选错工具、参数错、构建失败、需求理解错），过程层看步数、工具调用数、token、时延、重试率，质量层对客观任务跑测试、对主观任务用人工评分加与之对齐过的模型评审。回归集从线上失败样本回流，改提示词或换模型都重跑。

**RAG 与幻觉**：幻觉来自按概率生成、训练数据缺口和上下文不足或冲突。链路是解析 → 分块 → embedding → 向量库 → 召回 → rerank → 拼上下文 → 生成。效果不好先分检索还是生成：检索看召回里有没有答案、分块有没有切断语义、embedding 是否适配领域，指标看 recall@k；生成侧看提示词是否要求引用、长上下文有没有稀释关键段落、是否允许「没依据就说不知道」。混合检索用 BM25 补型号与错误码这类精确匹配，向量补语义，融合后再 rerank。
