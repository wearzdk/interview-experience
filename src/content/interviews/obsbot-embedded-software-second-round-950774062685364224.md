### 《参考解析》

**U-boot 移植改了什么**：移植的实质是让 bootloader 认识这块板子的内存、时钟与外设，并能把内核与设备树加载起来。典型改动包括：新增板级配置（`CONFIG_TARGET_*`、`defconfig`、板级目录与 Kconfig 条目）；DDR 初始化参数（颗粒容量、位宽、时序参数 tRCD/tRP/tRAS、刷新率），这部分通常由厂商提供的初始化脚本或 `ddr` 训练工具生成；时钟树配置（PLL 倍频分频、CPU/AXI/外设时钟、UART 时钟源）；启动介质与加载地址（eMMC、SD、NAND、SPI NOR 的分区与偏移，SPL 与 uboot 镜像布局）；串口控制台与网络（MAC 地址、PHY 复位）；环境变量分区。答的时候按「内存—时钟—存储—控制台」四条线组织，比逐条罗列更有条理。

**内核裁剪与 rootfs**：裁剪从 defconfig 出发，用 `menuconfig` 关掉无关的驱动、文件系统、调试选项与架构支持，把非必需功能编成模块按需加载，再通过启动时间、镜像体积与功能回归三项验证裁剪没有伤到业务。裁剪的常见误区是只删驱动不看依赖，导致运行时才发现某个子系统缺失。rootfs 常用 Buildroot 或 Yocto 构建，最小系统用 BusyBox 提供 init 与常用命令，按需加入库、固件与启动脚本；量产设备通常把 rootfs 做成只读分区，再挂一个可写的数据分区或 overlay，避免异常掉电把文件系统写坏。

**`probe` 与设备树**：`probe` 是驱动与设备匹配成功后的入口，典型工作是从设备树或平台数据取出寄存器基址、中断号、GPIO、时钟与 regulator，申请并映射资源（`devm_ioremap_resource`、`devm_request_irq`、`devm_clk_get`），初始化硬件到可用状态，注册字符设备或子系统接口（如 input、LED、backlight、hwmon），最后把私有数据挂到 `dev_set_drvdata`。设备树的改动通常是新增节点、填 `compatible`、补 `reg`、`interrupts`、`pinctrl` 与自定义属性；改完要用 `dmesg` 确认 probe 是否被调用、资源是否取到，匹配失败时先查 `compatible` 字符串与驱动表是否一致。

**用户空间与内核空间的数据交换**：最基础的是 `copy_to_user` 与 `copy_from_user`，它们会做地址合法性检查并处理缺页，驱动不能直接解引用用户指针；控制类命令走 `ioctl`，大数据或零拷贝走 `mmap` 把内核缓冲区映射到用户态，DMA 场景则把物理地址交给设备、由用户态或内核态共享同一块缓冲区，需要保证缓存一致性（`dma_sync_single_for_cpu/device`）。此外还有 `procfs`、`sysfs`、`netlink`、`eventfd` 等通道，选择依据是数据量、方向与是否需要阻塞通知。

**进程的内存布局**：从低地址到高地址依次是：代码段（只读可执行）、数据段（已初始化的全局与静态变量）、BSS（未初始化或零初始化的全局与静态变量，不占文件空间）、堆（`malloc` 向上增长）、共享库与 `mmap` 映射区（通常向下增长）、栈（局部变量与调用帧，向下增长），最高处是内核空间与 `vDSO`。多线程共享代码、数据、堆与文件描述符，但每个线程有独立的栈与寄存器上下文。这道题常被用来引出「栈溢出为什么表现为 HardFault」「堆和栈相向增长会不会相撞」。

**SPI 四种模式**：由时钟极性 CPOL 与时钟相位 CPHA 组合而成。CPOL=0 表示空闲时时钟为低，CPOL=1 表示空闲为高；CPHA=0 表示在第一个边沿采样、第二个边沿移出数据，CPHA=1 则相反。组合出 Mode 0 到 Mode 3。主从双方必须一致，否则数据错位；多数 Flash 与传感器支持 Mode 0 或 Mode 3。速率取决于器件手册（常见几十 MHz），实际还要看走线长度、负载与采样时序，速率过高会出现误码，需要用示波器或逻辑分析仪看波形与建立保持时间。

**丢包排查与环形缓冲区溢出**：丢包先分层定位：物理层看线序、地线、终端电阻与走线干扰；链路层看波特率误差、帧格式与校验；驱动层看 DMA 描述符、接收中断延迟与缓冲区大小；应用层看解析是否阻塞、是否在中断里做耗时操作。环形缓冲区溢出通常源于生产速度大于消费速度或临界区过长。解决方式包括：区分满与空（牺牲一个空位或维护计数）、用单生产者单消费者模型配合原子指针、用 DMA 的半满/全满双中断降低中断频率、加大缓冲并加流控、溢出时丢弃最旧数据并计数上报，让上层知道发生了丢包而不是静默丢数据。回答里带上「丢弃策略与统计」会显得有实际调试经验。

**C 语言里亮眼的设计**：可从 Linux 内核的设计讲起。`list_head` 把链表节点嵌进任意结构体，配合 `container_of` 由成员地址反推结构体地址，实现零成本泛型容器；`file_operations`、`platform_driver` 这类函数指针表实现了 C 语言下的面向接口编程与运行时多态；用 `static inline` 与宏在编译期消除抽象开销；用位域与联合体做寄存器映射；用状态表替代长 `switch`。评判标准是「抽象是否零成本、边界是否清晰、错误是否可发现」，而不是技巧是否花哨。

**AI 时代是否还要学基础**：需要，而且判断标准变了。AI 能写出看起来正确的代码，但无法替你判断它在边界条件、并发、内存生命周期与硬件时序上是否成立；没有基础就只能靠试错，出了问题也无法定位。合理的学习方式是：用 AI 生成初稿与测试，自己负责读规范、读源码、做代码审查与验证；把学习重心从记忆语法转向系统设计、调试能力与领域知识（内核、协议、硬件手册）；遇到不懂的实现让它解释并追问到能复述为止。面试中这样回答，既承认工具价值，也说明了自己的判断力。
