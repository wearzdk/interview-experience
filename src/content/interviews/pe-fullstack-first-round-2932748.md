### 《面试题目》

1. 自我介绍，介绍项目。
2. 项目是用 React 做的，为什么不用 LangChain、LangGraph？Chain 和 Graph 分别是什么，有什么区别？
3. 最近有没有了解哪些新技术？
4. 多 Agent 之间怎么交互？Answer Agent 出问题时没办法回复用户，该怎么解决——降级、兜底还是别的？
5. 项目里遇到的最大的问题是什么？（追问：参数缺失时系统自动填充了一个起终点，这种「编造」的专业术语怎么说？）
6. MySQL 了解到什么程度？
7. 项目里的意图识别是指什么？意图识别出错怎么解决？
8. 这个工具现在有多少人在用？为什么没推广开？
9. 介绍实习内容。
10. 用了这个 Agent 之后，性能提升体现在哪里？各个 Agent 的分工是什么？
11. 后端技术栈了解哪些？
12. 反问：团队现在的重点是什么？（面试官答：项目里 AI 现在不是必须项，重点还是后端开发，前端也不是重点）

### 《参考解析》

**「React 项目为什么不用 LangChain」是个陷阱题**：React 是前端渲染层，LangChain / LangGraph 是服务端的编排层，两者不在一个位置上，不存在替代关系。正确的答法是先拆层——前端负责会话、流式渲染和状态，编排在服务端；再说选型理由：链路是固定几步就不需要框架，自己写反而可控、依赖少、好调试；一旦出现分支、回环、多 Agent 交接、需要断点续跑和人工介入，才值得上 LangGraph。面试官问这个，是在确认你的项目是自己搭的还是拼的。

**Chain 与 Graph 的区别要一句话说透**：Chain 是线性的 DAG，节点按顺序串起来，适合「检索 → 拼 prompt → 生成」这种一条道走到底的流程；Graph 是带状态的有向图，支持条件边、环和共享 state，能表达「路由到不同 Agent、失败回到上一步、等待人工确认」。多 Agent 场景本质是图不是链，因为要循环和回退。

**多 Agent 交互的三种常见形态**：共享一份 state 由 supervisor 路由（最常用）、通过工具调用互相委托、流水线式串联。要讲清上下文怎么传（只传必要字段，避免全量 history 膨胀）、失败怎么隔离（一个 Agent 崩了不能拖垮整条链）、可观测性（每次调用记 trace id、输入输出、耗时），否则线上出问题只能靠猜。

**Answer Agent 失败的兜底是这道面试的核心**。分层答：超时和异常先重试一次（幂等的前提是不重复产生副作用）；仍失败则降级到规则/模板回答或通用模型直答；再不行就明确告知用户「这一步没查到」并给出下一步建议，而不是编一个答案；同时熔断该上游、打点告警。关键是要说清「兜底回答不能假装是正常回答」——用户能接受失败，不能接受被骗。

**「参数缺失时自动补一个起终点」的术语就是幻觉（hallucination）**，更准确地说是「无依据补全」。工程上不该靠模型自觉：工具层做参数校验，缺什么就回问用户；用结构化输出（JSON Schema / function calling）约束字段；对关键实体做存在性校验（起终点是否在库里）；再加一层置信度和 trace，事后能查到这次补全是哪一步产生的。这一段答得好，等于同时回答了第 4 题和第 7 题。

**意图识别**要答出「分类 + 兜底」：常见做法是规则/关键词兜底 + 模型分类（few-shot 或小模型），输出里必须有 `unknown` 这一档，落到 unknown 就走澄清话术而不是硬猜。错分的处理分两种：低置信度澄清、高置信度错分靠反馈回路（用户纠正后落标注，定期回流训练/改 prompt）。不同意图的错分成本不一样，把成本高的那类（比如会触发写操作的）单独加确认，是能加分的细节。

**用户量和「为什么没推广」是压力题**，诚实比包装有效：说清当前是内部/小范围试用、卡在哪（权限、稳定性、接入成本），以及你为推广做过什么。承认阶段早不扣分，吹一个数字被追问 DAU 会立刻穿。

**性能提升必须给指标**：原来多久、现在多久、怎么测的、样本多大。答「快了很多」等于没答。

**最后面试官说 AI 不是必须项、重点在后端**，说明这个岗位的权重在后端工程上。反问该顺着问：后端用什么栈、AI 模块在路线图里的位置、这个岗位一年内的主要交付是什么。
