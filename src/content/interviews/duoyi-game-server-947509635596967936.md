### 《参考解析》

**不用 MongoDB 怎么存快照**：先明确快照的读写特征——写多、按玩家与时间点读、单条体积中等、需要按版本回溯。可选方案有四类。一是关系库加宽表或 JSON 列，玩家 id 加时间戳做主键，适合强事务与复杂查询，缺点是单表膨胀后要按时间分区。二是对象存储，把快照序列化后按 `playerId/version` 存成文件，元数据放关系库，成本最低、适合冷数据，缺点是读要两次请求、不适合高频读。三是列式或时序库，如果快照是固定字段的数值集合，按时间序列存压缩率高。四是内存库加热数据，只保留最近几个版本，历史版本落冷存储。选型要讲清取舍：一致性要求高就放关系库并走事务；只做回溯就放对象存储；读取频繁就加缓存分层。面试官问这题的目的是看你是否会先分析访问模式再选型，而不是背产品名。

**Redis 常用数据结构**：String（缓存、计数器、分布式锁）、Hash（对象字段的部分更新，如玩家属性）、List（简单队列、时间线）、Set（去重、共同好友）、ZSet（排行榜、延时队列、滑动窗口限流）、Bitmap（签到、布尔标记）、HyperLogLog（基数估算）、GEO（地理位置）、Stream（消息流，支持消费组）。要能说出每种结构的典型命令与复杂度，以及底层编码的转换（小数据量用紧凑编码，超过阈值转哈希表或跳表）。

**ZSet 的实战用法**：常见三类。排行榜用 `ZADD` 写分数、`ZREVRANGE` 取前 N、`ZREVRANK` 查排名，分数相同时按成员字典序排序，需要严格时间序时把时间戳编码进分数的高位。延时队列用分数存到期时间戳，消费端 `ZRANGEBYSCORE` 取到期任务并用 `ZREM` 原子摘除，注意多消费者下的重复摘取要用 Lua 保证原子。滑动窗口限流用分数存请求时间戳、成员存唯一请求 id，每次先 `ZREMRANGEBYSCORE` 清掉窗口外的旧记录再 `ZCARD` 判断，整个判断与写入用 Lua 一次完成，避免竞态。

**跳表复杂度**：查找、插入、删除平均 O(log n)，最坏 O(n)。原理是有序链表加多级索引，每层以概率 p（通常 1/2 或 1/4）向上提升节点，期望层数 O(log n)，每层期望遍历常数个节点。相比红黑树，跳表实现简单、范围查询友好（底层链表天然有序），代价是额外指针空间与随机性带来的常数波动。Redis 的 ZSet 在元素少或成员短时用压缩列表，超过阈值才转跳表加字典，字典负责 O(1) 按成员查分数，跳表负责按分数范围与排名查询。

**手撕要能讲清思路**：面试官要求讲「为什么这么写」，本质是考复杂度分析与边界处理。写之前先口述：输入规模、目标复杂度、用什么数据结构、边界有哪些（空输入、单元素、重复元素、越界）。写完主动报时间与空间复杂度，并指出可以优化的点。游戏服务端的算法题常考链表、字符串、排序与简单动态规划，写的时候注意不要用递归处理可能很深的输入。
