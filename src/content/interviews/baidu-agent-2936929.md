### 《参考解析》

**代码生成后的编译与预览**：链路是「生成代码 → 写入隔离目录 → 安装依赖 → 构建 → 产出静态文件 → 托管预览」。构建在服务端容器里做，每个项目一个临时工作目录，构建完成后把产物（dist）上传到对象存储或静态托管，用子路径或子域名区分项目。不依赖用户本机 npm：构建全在服务端完成，用户只拿到预览 URL。资源隔离靠容器（限制 CPU、内存、构建超时）加队列（构建任务排队，限制单用户并发），并缓存依赖（预装常用依赖的镜像层或 pnpm store），避免每次重新下载。

**端口与多用户**：不要让每个项目起独立服务占端口。构建产物是静态文件时，用同一个静态服务器按路径区分（`/preview/{projectId}/`），或用通配子域名加反向代理；需要运行时的项目（Node SSR、后端接口）才起容器，用容器编排按需拉起并限流，闲置一段时间回收。预览链接加签名与过期时间，防止被遍历。

**为什么 Prompt 越来越长**：多轮执行中每一步的工具结果、历史动作、中间产物都会追加进上下文；如果每轮都把完整文件内容塞进去，长度会线性膨胀。解法是上下文管理：只保留最近若干轮、对历史做摘要、把大文件改为按需读取（给模型文件索引与检索工具而不是全文）、把稳定的系统提示与工具定义放在前缀以命中缓存。这也解释了为什么 ReAct 的效果会波动：提示词范围变小意味着模型看到的约束变少，需要用工具把缺失的信息按需取回。

**多 Agent 通信失败**：先定义失败类型：超时、返回格式错误、任务失败、消息丢失。工程上把 Agent 间通信做成「有状态的任务协议」：每个子任务有 id 与状态，调用方发起后轮询或等回调，超时重试要带幂等键，失败进重试队列并设最大次数，最终失败要能降级（返回部分结果或转人工）。如果是同一进程内的组件调用，用内存队列加超时；跨服务用消息队列并持久化。要能说明「重试不等于重复执行」：子任务本身要幂等。

**优惠券超卖与防重**：超卖是库存扣成负数，根因是「读-判断-写」不是原子操作。方案演化：`SETNX` 做简单锁，问题是锁无续期、可能死锁、不可重入；Redisson 提供看门狗续期与可重入，但仍是串行化，热点下吞吐有限；最终用 Lua 脚本把「判断库存 + 扣减 + 记录用户已领」合成一次原子操作，再把下单落库异步化走 MQ，Redis 只做库存与去重的前置闸门。防重复领取用「用户 id 加券 id」作为去重键写入 Set 或唯一索引。同一用户并发多请求靠 Lua 原子性与唯一约束兜底，不能只靠先查后写。

**Redis 与 MySQL 一致性**：常用 Cache Aside：读时先读缓存，未命中读库并回写；写时先更新库再删除缓存。延迟双删用于降低并发读写导致的旧值回填。更强的一致性靠「订阅 binlog 异步刷新缓存」或「库存类操作以 Redis 为准、异步落库并以对账兜底」。要说明没有绝对强一致，只有「最终一致加对账」，并给出差错处理路径。

**库存预热与幂等**：预热在活动开始前把库存从库读到 Redis，写入时用 Lua 保证不覆盖已扣减的值；预热失败要有补偿。消息幂等用全局消息 id 加消费记录表（唯一索引），或用业务唯一键；消费前先插入幂等记录，插入成功才执行业务，失败则跳过。两次查询间隔很短时，用请求合并或本地缓存挡一层，避免同一份数据被反复打穿到下游。

**两数之和**：哈希表一遍扫描，对每个元素查 `target - x` 是否在表中，在则返回下标，不在则把当前值与其下标存入。时间 O(n)、空间 O(n)。边界：数组不足两个元素、有重复值、要求返回所有组合时改多值映射。
