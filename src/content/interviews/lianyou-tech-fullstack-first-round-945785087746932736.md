### 《面试题目》

### 《参考解析》

**「对实习业务的理解」考的是你有没有跳出写代码看业务**：说清这个业务解决谁的什么问题、核心指标是什么、你负责的模块在链路里的位置、你的改动让哪个指标变化了。只讲技术栈会被认为在「执行层」，能讲清业务价值才是他们想要的。

**AI coding 的日常流程**：先自己读代码建立上下文，把任务拆成可验证的小步；给 AI 明确的输入（相关文件、约束、验收标准），让它先出计划再动手；产出必须过编译、lint、测试，自己只看 diff；不确定的实现不合并。解决模型幻觉的手段是「给事实」而不是「求它别说错」——把接口文档、类型定义、真实数据结构喂进上下文，让它基于事实生成；对关键结论要求给出处（文件与行号），并在验证层（类型检查、单测、运行时断言）兜住。

**MySQL 索引要讲到「为什么 B+ 树 + 什么时候失效」**：InnoDB 用 B+ 树，非叶子节点只存键、叶子节点存数据并成链，扇出大、树高低，范围查询友好；聚簇索引的叶子就是行数据，二级索引叶子存主键，所以二级索引查非索引列要回表。失效场景：对索引列做函数或运算、隐式类型转换（字符串列传数字）、`like '%x'` 前缀模糊、联合索引不满足最左前缀、`or` 两侧有一侧无索引、以及优化器估算回表成本过高时主动放弃索引。

**性能排查要有「依据链」**：先看监控定位是哪个接口、哪一段（应用、DB、缓存、下游），再看日志与链路追踪的具体耗时分布；应用侧看 CPU、GC、线程池、连接池；DB 侧看慢查询日志、`SHOW PROCESSLIST`、锁等待、以及执行计划。所谓「依据」就是每一步都有数据支撑，而不是凭经验猜。

**慢 SQL 要看的字段**：执行计划里的 `type`（是否全表扫描 ALL、索引范围 range、ref/const）、`key` 与 `key_len`（实际用了哪个索引、用了联合索引的几列）、`rows`（预估扫描行数）、`filtered`（过滤比例）、`Extra`（Using filesort、Using temporary 说明排序或分组没走索引，Using index 是覆盖索引，Using index condition 是索引条件下推）。再看慢日志里的 `Query_time`、`Lock_time`、`Rows_examined` 与 `Rows_sent` 的比例——扫描行数远大于返回行数就是索引没选对。
