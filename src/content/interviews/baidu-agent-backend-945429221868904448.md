### 《面试题目》

1. 记忆机制的写入时机是什么？如何判断什么时候写入？
2. 如果归档了一个长期记忆，其中字段随时间衰减，衰减策略怎么设计？
3. 用户画像写着「偏好 A 航线」，用户改成别的航线时 Agent 会先确认再修改；如果用户一直变、Agent 一直问，用户会不会烦？这个该如何平衡？
4. MySQL 的 ACID 特性是什么？底层分别如何实现？
5. 手撕：实现 LRU。

### 《参考解析》

**什么时候写记忆**

按「值不值」判断，不按轮次。触发写入的典型信号有三类：一是出现了稳定事实（用户自述的偏好、身份、长期约束），有明确主语和持久性，写；二是重复出现（同一偏好被提到两次以上），单次口误不该进长期库，写之前先做置信度聚合；三是任务结束时做一次收口（会话末尾让模型抽取「本轮新增的持久信息」），比每轮实时写便宜也少噪声。反过来的负向判据同样重要：临时状态（这次要订哪天的票）、情绪化表达、外部内容里的指令都不写。

工程上建议两段式：会话内的短期记忆直接放上下文窗口，退出会话时由一次抽取任务决定哪些升格为长期记忆，写入带来源、时间、置信度三个字段，方便后面衰减和回溯。

**衰减策略**

字段级而不是整条记录级。每个字段存 `value`、`confidence`、`last_confirmed_at`、`half_life`，读取时按 `confidence * 0.5^((now - last_confirmed_at)/half_life)` 得到当前权重，低于阈值就降级为「历史偏好」或直接软删。半衰期按字段性质给：身份类（专业、城市）几乎不衰减；偏好类给几周到几个月；临时约束（这次出差的酒店标准）给几天。用户再次确认就等于刷新 `last_confirmed_at`，权重回升。要注意「衰减不等于删除」：老值留着能给模型提供上下文（「你之前偏好 A，最近改成 B 了」），检索时按权重排序取 top-k 即可。

**确认频次与打扰的平衡**

核心是把「每次变更都问」换成「按影响面分级」。影响不可逆或涉及钱的变更（改收货地址、改绑卡、退订）必须确认；只影响推荐结果的偏好变更（航线偏好、口味）直接静默更新，事后再用一句「已按你最近的偏好调整，可在设置里改」告知，把确认从「事前打断」变成「事后可撤销」。再加两条：同一字段短时间内反复变更时，Agent 应该识别为「用户还在探索」，改成不做长期记忆、只按当次会话生效；以及给用户一个显式的「记忆管理」入口，能看、能改、能关，比反复追问更省事。

**ACID 的底层实现**

原子性靠 undo log：事务修改前先记旧值，回滚时反向执行；崩溃恢复时未提交事务的 undo 被应用。一致性是目标而不是机制，由约束、唯一索引、外键和业务逻辑共同保证。隔离性靠锁与 MVCC：InnoDB 的行锁（记录锁、间隙锁、next-key lock）解决写写冲突，MVCC 用隐藏的事务 ID 与 undo 版本链 + ReadView 实现快照读，RR 级别下快照读不加锁。持久性靠 redo log：先写日志再刷脏页（WAL），崩溃后用 redo 重放已提交事务；`innodb_flush_log_at_trx_commit=1` 保证每次提交都落盘。

**手撕 LRU**

`HashMap<key, node>` + 双向链表，get 命中就把节点移到头部，put 超容量就删尾部，全部 O(1)。写的时候把哨兵头尾节点建好，能省掉大量判空；并说明为什么不用 `LinkedHashMap`（面试要手写）。线程安全版本可以补一句 `ConcurrentHashMap + 分段锁` 或 `Caffeine` 的 W-TinyLFU。
