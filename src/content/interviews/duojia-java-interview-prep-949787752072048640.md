### 《面试题目》

1. ThreadLocal 的追问链是怎么展开的：标准答案之后面试官还会问什么？
2. 「Redis 缓存与数据库一致性怎么保证」按什么结构回答？
3. 设计一个秒杀系统，你会怎么架构？
4. 接口 RT 突然从 50ms 涨到 2s，排查思路是什么？
5. 线上 CPU 100% 怎么定位？
6. 百万数据导出怎么避免 OOM？
7. 订单超时未支付怎么自动关闭？
8. 登录态在分布式系统怎么管理？
9. 热点 key 问题怎么处理？
10. 服务发布怎么做无损上线？
11. 从 0 设计一个支付回调系统，核心模块有哪些？
12. HR 面问期望薪资，应届生怎么答？

### 《参考解析》

**三层答法的实质**：第一层是能复述标准答案，第二层是能讲清「为什么这样设计、替代方案的代价是什么」，第三层是能落到自己的项目上，说清用过没有、踩过什么坑。面试的筛选点在于：基础题答到第二层才算合格，有两三个模块能到第三层就有竞争力。判断自己是否真的到了第二层，用一个标准——被问「为什么」时能不能继续往下讲，而不是把题干重复一遍。

**ThreadLocal 的追问链**：标准答案是线程隔离、每个线程持有独立的 ThreadLocalMap、key 是弱引用而 value 是强引用、线程池下不 remove 会泄漏。追问通常有四层：项目里哪里用了它、为什么不用参数传递、线上有没有因此出过问题、线程池场景下为什么更危险。要能答出：用它的场景是「跨层传递上下文」（用户身份、链路追踪 id、租户信息）；不传参是为了避免污染方法签名；线程池的危险在于线程复用导致上一个任务的 value 残留给下一个任务，既泄漏又可能串数据，所以必须在 `finally` 里 `remove()`；Web 容器里可以用拦截器统一清理。

**缓存一致性的四段式回答**：结论——采用 Cache Aside，写时先更新数据库再删除缓存，强一致场景配合延迟双删或消息队列做最终一致。原理——读时未命中查库回填，写时更新库再删缓存，避免并发读把旧值回填。场景——商品详情页缓存，改价时先写 MySQL 再删 Redis，删失败进重试队列。注意点——先删缓存再更新库在并发下会读到旧值；热点 key 要考虑击穿；删除失败要有补偿；对一致性要求极高时读主库或加分布式锁。这个结构比罗列五种方案名称有用，因为它展示了判断过程。

**秒杀系统**：分四层。前端做按钮防重、静态资源 CDN、活动预约；网关做限流与黑名单；服务层把库存预热到 Redis，用 Lua 脚本把「判断库存、扣减、记录用户已购」做成原子操作，一人一单用 `SETNX` 或 Set 标记；异步层用 MQ 削峰，消费者落库建单；数据库层用唯一索引（用户 + 商品）与 `UPDATE stock SET stock = stock - 1 WHERE stock > 0` 兜底。配套要有超时未支付关单、超卖核对任务、以及 Redis 故障时的降级策略（直接拒绝而不是打穿数据库）。

**RT 飙高的排查**：先分层看影响面（哪些接口、哪些机器、什么时间开始），再看依赖（数据库慢查询、Redis 延迟、下游 RPC、MQ 堆积），然后看自身（GC 日志、线程栈、连接池与线程池是否耗尽、是否有锁竞争），最后看流量（突增、缓存击穿、爬虫）。应急顺序是先止损再定位：限流、降级非核心、扩容、回滚最近发布。工具是链路追踪定位慢在哪一段、`arthas` 看方法耗时、`jstack` 看阻塞、慢查询日志与 `redis-cli --latency`。

**CPU 100% 的定位**：`top -Hp <pid>` 找出占 CPU 最高的线程，把线程 id 转成十六进制，`jstack <pid> | grep -A 30 <hex>` 找到对应栈；常见原因是死循环、频繁 Full GC（看 `jstat -gcutil`）、正则回溯、以及大量线程上下文切换。GC 导致的还要看堆dump 找大对象。回答时把「定位到线程 → 对应到代码」这条链讲清楚。

**百万数据导出避免 OOM**：不要一次性查全量再写文件。用游标或分页流式读取（`ResultSet` 的 `setFetchSize`、MyBatis 的 `Cursor`、或按主键区间切片），边读边写；导出文件用流式写入（EasyExcel、CSV 逐行 flush），避免在内存里拼大对象；任务异步化，前端拿任务 id 轮询进度；限制单次导出量与并发数，超大导出走离线任务并通知下载。

**订单超时关闭**：方案按精度与成本选。延迟队列（RabbitMQ 的 TTL + 死信、RocketMQ 的延迟消息）精度高但有消息堆积与重复投递问题；定时任务扫表（每分钟扫超时未支付订单）实现简单但有时延与扫表压力，需要按时间索引分片；Redis 的 ZSet 存到期时间轮询，适合中等规模；时间轮适合单机高频场景。无论哪种，关闭前必须再查一次订单状态（防用户刚好支付），并用状态机保证幂等。

**分布式登录态**：把会话存到共享存储（Redis），key 为 token，value 存用户 id 与权限，设置滑动过期；token 用 JWT 时要做吊销（黑名单或短有效期加刷新令牌），并处理多端登录互踢（记录设备与登录序号）。网关统一校验，业务服务从上下文取用户，不重复解析。

**热点 key**：先识别（监控 key 的 QPS、用 `redis-cli --hotkeys`），再做本地缓存（一级缓存加短过期，注意一致性）、key 拆分（把热点商品库存拆成多个子 key 汇总）、读写分离与多副本、以及请求合并（同一 key 的并发请求合并为一次回源）。

**无损发布**：发布前把实例从负载均衡摘除，等待存量请求处理完（优雅停机，注册中心下线 + 健康检查失败），再停进程；新实例启动后通过就绪探针再接入流量；数据库变更要先兼容新旧两个版本（加字段不删字段、双写过渡），避免滚动发布期间新旧代码不兼容。长连接场景（WebSocket）要主动通知客户端重连并做重连风暴保护。

**支付回调系统**：核心模块包括签名验签（防伪造）、幂等处理（同一笔回调重复到达只处理一次，用支付流水号做唯一键）、状态机（待支付 → 支付中 → 已支付 → 已退款，非法流转拒绝）、异步通知商户（重试 + 退避 + 最大次数 + 人工补偿）、对账（与渠道账单按日核对，处理单边账）、以及审计与告警。设计要点是「回调可能乱序、重复、延迟」，所以不能依赖到达顺序，要用渠道的最终状态与流水号做幂等。

**期望薪资怎么答**：先问清结构（月薪几薪、绩效占比、补贴、签字费、股票），再给区间并说明依据（同城同岗位水平、自己的实习与项目匹配度）。应届生不宜报一个精确到千的数字，也不宜说「都可以」。给出区间后补一句「如果整体包合适，我更看重岗位方向与成长」，把谈判空间留出来。拿到口头 offer 后要求书面确认，避免只谈总包不看结构。
