### 《面试题目》

6. 效果提升究竟来自「本体结构」，还是来自你们投入了大量人工整理？
7. 你说本体化可以做强 Schema 校验，但普通 Tool Calling 和接口本身不也能校验参数吗？
8. 本体现在靠人工维护，还是已经有自动抽取和更新机制？

11. 你看过哪些本体化资料和行业实践？如何判断某个业务对象应该成为本体？本体之间的关系怎么确定？

17. 自适应 RAG 和混合检索优化具体做了什么？为什么需要混合检索？
18. 个人项目不是企业生产系统，简历里的故障排查效果指标从哪里来？
19. 从零构建一个 Agent，需要哪些关键组件？要解决哪些关键问题？
20. System Prompt 应该怎么组织？如果要加入当前时间，可以直接放在第一行吗？
21. 工具返回的信息太长、无法直接放进上下文，有哪些处理办法？上下文压缩怎么做？
22. 聊天工具里的 Session / Message 是怎么存储的？你了解具体的数据结构吗？

### 《参考解析》

**本体化与 RAG 的差别在「约束」而不只是「结构化」。** RAG 把文档切片后按相似度召回，优点是可扩展、更新成本低，缺点是同一实体的不同表述、字段口径与关系散落在不同片段里，模型需要在生成时自行拼装，容易出错且难以校验。本体的做法是先定义业务对象（实体、属性、关系、取值范围、约束），把文档与接口映射到这套模型上，检索与推理都在模型层进行，因此可以做类型检查、关系一致性校验与确定性推理。代价是建模与维护成本高、覆盖面有限。合理的落地方式是混合：核心高频对象本体化，长尾与叙述性内容仍走 RAG。

**「效果提升来自结构还是人工整理」是这一场最尖锐的问题。** 诚实答案是两者都有，需要用对照实验拆开：固定知识内容，只改变组织方式（纯切片 vs 本体映射），比较同一批问题的准确率与错误类型；再固定组织方式，减少人工整理量，看效果下降多少。若效果主要来自人工整理，说明瓶颈是知识质量而非结构，应该先解决抽取与校验的自动化；若两者都贡献显著，就应给出各自的成本曲线，并说明在什么规模下本体化才划算。

**强 Schema 校验与 Tool Calling 的参数校验不是同一层。** 接口校验保证「参数类型与必填项合法」，本体校验保证「这个概念在此业务下是否成立」——例如设备型号与固件版本是否兼容、工单类型与故障现象是否匹配、某属性是否允许出现在该对象上。前者是语法，后者是语义与约束传播，接口无法在不了解业务模型的情况下完成。

**三层架构不等于三个 Agent，也不等于三次模型调用。** 常见的分层是 Planner（理解目标、拆解任务、选择工具）、Executor（执行具体工具调用、处理返回）、Verifier/Reflector（校验结果、决定重试或收敛）。每一层可以是模型调用，也可以是确定性代码或状态机；关键在于层间契约（输入输出结构）与失败语义。用具体场景讲：用户描述「某航班值机失败」，Planner 拆出「查订单状态 → 查值机记录 → 查航司接口返回码」，Executor 依次调用并回传结构化结果，Verifier 判断证据是否足以定位，不足则回到 Planner 补充假设。

**拆层还是单 Agent ReAct，取决于可观测性与可控性。** 单 Agent ReAct 实现简单、灵活，但错误归因困难、容易在长链路里跑偏、成本不可控。分层的价值是每一步的输入输出可记录、可断言、可回放，失败时能定位到「计划错」还是「执行错」；代价是设计复杂度与可能的信息损失（Planner 看不到执行细节）。合理的答法是给出选择条件：任务步骤稳定、需要审计与回归时分层；探索性强、步骤不确定时用 ReAct，并在外层加预算与校验。

**「没有生产环境，指标从哪来」要如实说明评测方法。** 可以构造评测集：从公开故障案例、论坛问答、手册条目中抽取问题，人工标注标准答案与证据来源；用离线回放跑完整链路，统计定位准确率、证据命中率、平均调用步数与成本；对无法自动判定的事项做人工评审并给出一致性系数。要明确这些指标是离线评测结果，不等于线上效果，并说明样本量、构造方式与已知偏差。

**从零构建 Agent 的关键组件。** 模型接入与路由（多模型、超时与降级）、提示与上下文组装、工具层（声明、参数校验、权限、幂等、超时与重试）、状态与记忆（会话、任务状态、长期记忆）、执行循环（计划—执行—观察—收敛）、可观测性（链路追踪、日志、成本）、评测与回归、以及安全边界（越权、注入、敏感信息）。关键问题集中在四件事：上下文如何组织、工具如何可靠、失败如何收敛、效果如何度量。

**System Prompt 的组织顺序影响模型注意力。** 常用结构是：角色与目标 → 硬约束（不可违反的规则、安全边界）→ 可用工具与调用约定 → 输出格式 → 少量示例。当前时间这类可变信息不宜放在第一行，因为它会破坏前缀稳定性并影响缓存命中；更合理的做法是放在固定的「环境信息」区块末尾，或作为一条系统消息追加在历史之后（保持前缀不变）。

**工具返回过长时有四种处理。** 截断并保留结构化摘要（字段名 + 关键值）；在应用侧先做过滤与聚合，只把相关字段交给模型；把大结果落到外部存储，上下文里只放引用 ID 与索引，需要时再按需取；以及分页/分段读取。上下文压缩要在「保信息」与「控长度」之间取舍：优先保留实体、数值、时间、约束条件与未完成的子目标，丢弃重复描述与已完成的中间步骤；压缩后要用探针问题回归，确认关键依据没有丢。

**Session / Message 的存储要区分「会话元数据」与「消息流」。** 典型结构是 Session（id、用户、标题、创建与更新时间、状态、模型配置）与 Message（id、session_id、角色、内容、工具调用与结果、token 数、时间戳、父消息 id）。工具调用与结果建议作为独立消息类型存储，保留调用 ID 以便配对；长内容（文件、图片、大结果）存对象存储，消息里放引用。多轮对话还需要保存「上下文快照」或可重建的摘要，否则压缩后无法回溯。

**暂停与恢复靠「持久化的执行状态」而不是靠模型记住。** 当 Agent 需要用户授权或补充信息时，把当前任务状态（已完成步骤、待执行的工具调用、已收集的参数、中断原因）落库，返回一个待处理状态给前端；用户回复后，用同一个任务 ID 恢复执行，把回复作为新的输入追加到历史，再继续循环。要处理超时、重复提交与并发恢复（同一任务只允许一个执行者），并为「用户拒绝授权」定义明确的终止路径。

**Agent Memory 通常分三层，各自的时效与更新策略不同。** 工作记忆（当前任务的上下文，随会话结束丢弃）、情景记忆（历史会话与事件，按时间与主题索引，可摘要、可衰减）、语义记忆（稳定的事实与偏好，需要校验与去重）。时效性处理包括：给记忆打时间戳与置信度，按最近使用与重要性做衰减，冲突时以更新的高置信来源覆盖，并保留可追溯的变更记录；用户显式纠正优先级最高。检索时按任务相关性召回，而不是把全部记忆塞进上下文。
