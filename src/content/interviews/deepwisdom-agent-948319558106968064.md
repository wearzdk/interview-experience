### 《面试题目》

1. 项目三人里你做了什么，贡献排名第三的人做了什么？
2. 对比各 harness 之间的区别，你为什么用 Pi？介绍其中一个 harness。
3. Codex 的 apply patch 和普通 edit 之间有什么区别？
4. Codex 的 session 恢复是怎么做的？
5. 普通 edit 在同一文件匹配到多个相同字符串怎么办？
6. 云端工具与本地工具的区别？
7. 设计题：coding agent 做网页成本过高，怎么优化？
8. 设计题：长任务、大项目怎么做？
9. 你在项目里学到了什么软性的能力？
10. 反问。

### 《参考解析》

**项目贡献要经得起提交记录核对**：面试官看了 GitHub 提交，说明他关心真实分工。回答时按模块讲「我设计/实现了什么、别人做了什么、我审查或接手了哪部分」，不要夸大；排名第三的人做的事也要能客观描述，避免贬低队友。被问到不熟悉的部分，如实说边界。

**harness 对比**：从工具集、上下文管理、权限与沙箱、循环控制、会话持久化、扩展方式几个维度比。Pi 这类轻量 harness 胜在简单、可改、启动快，适合定制；Codex 的 runtime 把补丁、shell、会话恢复做得更完整；Claude Code 的工具粒度细、权限模型清晰。回答时选一个自己真正用过的，讲清「为什么这个场景选它」，不要泛泛背功能。

**apply patch 与 edit**：apply_patch 用带上下文的补丁描述多处增删改，能一次表达跨行、跨段的修改，格式严格、可审查；普通 edit 通常是「精确匹配一段原文并替换」，实现简单，但对重复文本敏感、难以表达大范围重排。补丁方式的失败模式是上下文不匹配，编辑方式的失败模式是匹配不唯一。

**session 恢复**：会话内容追加写入 JSONL（每条消息、工具调用与结果），元数据（会话 ID、工作目录、模型、时间、状态）存 SQLite 或索引文件；恢复时按会话 ID 读取 JSONL 重建消息历史，校验工作目录与文件状态，必要时重放未完成的工具调用。关键是追加写、可截断、版本兼容，以及不要把密钥写进日志。

**同一文件匹配到多个相同字符串**：正确做法是返回「匹配不唯一」错误，要求 Agent 补充更多上下文或改用行号范围，而不是猜一个替换。实现上先统计匹配次数，等于 1 才替换，大于 1 报错并返回候选位置；也可以要求 old_string 带足够上下文，或提供 `replace_all` 显式选项。

**云端工具与本地工具**：云端工具环境一致、易扩展、不占本地资源，但有网络延迟、数据出域与凭据管理问题；本地工具访问文件与系统方便、延迟低，但环境漂移、隔离弱。选择按「数据敏感度、延迟要求、环境一致性、权限」权衡，常见是控制面在本地、执行面在远端沙箱。

**网页生成成本优化**：按任务与环节选模型，规划用强模型、样板代码用便宜模型；提高缓存命中率（稳定前缀、少改系统提示）；前端反馈用 DOM/可访问性树做常规校验，截图只在视觉问题时用；每一步配编译、测试、lint 验证，减少返工；限制重试次数与上下文长度，失败快速上报而不是无限循环。

**长任务与大项目**：递归分解成可验证的子任务；设计、编码、验收分给不同角色，每个角色的上下文只装当前任务需要的信息；用 Verifier 做阶段验收，验收标准要客观、不能被模型自己糊弄；用 markdown 文件或任务板跨上下文传递进展与决策；设置检查点与人工介入点，定期回看整体目标，避免局部最优。

**软性能力**：主动性（发现问题自己推进）、学习能力（陌生领域快速建立知识框架）、沟通（把技术问题讲给非技术同学）。每个能力配一个具体例子，比形容词有说服力。
