### 《参考解析》

**测试流程与用例设计方法要落到具体案例。** 流程按「需求评审—测试计划—用例设计—用例评审—环境准备—执行与提 bug—回归—测试报告—上线验证」讲，每一段说自己实际做过什么。用例设计方法不要只报名词，配合一个真实模块展开：登录用等价类与边界值（账号长度、特殊字符、密码错误次数锁定）、支付用场景法与状态迁移（待支付—支付中—成功—超时—退款）、搜索用正交组合（关键词、筛选、排序、分页）、异常用错误推测（网络中断、重复提交、并发扣减）。面试官听到「我用了边界值」会继续问「边界取在哪、为什么」，所以要准备好取值依据。

**bug 单的关键信息。** 标题（一句话说清现象与条件）、环境（版本、设备、系统、账号）、前置条件、复现步骤（编号、可被他人照做）、实际结果与预期结果、复现概率、日志与截图／录屏、影响范围与严重程度、关联需求或接口。车载类还要带总线报文、故障码与实车／台架标识。缺哪一项都会让开发来回问，这一点是面试官判断有没有真实提过 bug 的依据。

**用例优先级。** 常用 P0—P3：P0 是主流程与安全相关（上车、启动、制动信号、告警），必须每次回归；P1 是核心功能的异常分支；P2 是次要功能与兼容性；P3 是边界与极端场景。定级依据是「失败的业务代价 × 触发概率」，不是「写起来难不难」。同时要说明优先级与执行策略挂钩：冒烟只跑 P0，日常回归跑 P0+P1，发版前跑全量。

**冒烟、回归、全功能的阶段。** 冒烟在每次构建后、提测入口处，验证主流程是否可测，不通过直接打回；回归在缺陷修复后与版本迭代时，覆盖变更影响面与历史高发模块；全功能在版本发布前或大版本上线前执行全量用例。补充一句「回归范围由变更分析决定」，比机械地说「都跑一遍」更专业。

**需求歧义的处理。** 评审当场提出，用「我理解是 A，文档写的是 B，实际应该是哪个」的问法把分歧显性化，让产品给出结论并写回文档；会后用邮件或需求单留痕，避免口头确认失效。如果影响用例设计，先按最可能的解释写用例并标注待确认，不阻塞整体进度。

**bug 生命周期与开发不认可。** 生命周期是新建—指派—确认／驳回—修复中—待验证—关闭／重新打开，驳回要写理由。开发不认可时先自证：给出复现步骤、环境、日志与录屏，确认不是环境或数据问题；仍不一致就拉产品一起判定「预期结果以谁为准」，必要时上升给测试负责人。核心是把争论从「我觉得有 bug」变成「预期结果的定义是什么」。

**AI 辅助生成用例的问题识别。** 常见问题有四类：覆盖偏差（只写主流程，异常与边界缺失）、事实错误（编造不存在的字段、接口、按钮）、预期结果不可判定（写「显示正常」这类无法验证的描述）、以及过度泛化（把某个模块的规则套到另一个模块）。发现手段是逐条对照需求与接口文档核验，跑一遍看用例是否可执行，再用缺陷注入检查它能不能抓出已知 bug。

**医疗业务测试与 Web 测试的差异。** 医疗系统的核心是数据正确性与合规：剂量、单位、时间窗、患者身份匹配不能出错，涉及电子病历、医嘱、检验结果互认、权限与审计留痕（谁在什么时候看了谁的病历）、数据脱敏与留存期限；Web 测试更关注功能与体验。测试手段上医疗更强调规则校验、状态机完整性、跨系统接口一致性，以及大量回归（法规变更或版本升级后必须全量验证）。举一个具体例子，比如「医嘱剂量单位从 mg 改成 g 时的换算与越界拦截」，比抽象对比有说服力。

**回归效率的提升。** 先量化现状（多少条用例、人工执行多久、失败率），再给三类手段：分层（冒烟＋核心回归＋全量的分级执行）、自动化（接口与稳定的 UI 流程脚本化，接入 Jenkins 定时跑）、精准（按代码变更与需求影响面圈定回归范围，去掉长期零缺陷的冗余用例）。给出改造前后的数字，例如「全量 3 天压到核心回归 4 小时＋每晚自动跑全量」。

**接口用例的通过判定。** 不只看 HTTP 200：状态码、业务码、响应结构与字段类型、关键字段值（金额、状态、时间）、数据库落库结果、以及对下游的影响（消息是否发出、库存是否扣减）。JSON 断言用 JSONPath 取字段做精确匹配或正则／范围匹配，动态字段（时间戳、ID）单独处理。要说明「断言要写业务不变量，不是把返回值原样贴进去」。

**Jenkins 大批失败的排查。** 先分类再看单条：是不是同一个报错（服务未启动、数据库连接失败、环境变量缺失、证书过期、依赖镜像拉取失败），是不是同一批用例（同一模块、同一账号），是不是时间集中（并发冲突、测试数据被前一个任务污染）。然后看构建日志与测试报告的趋势，对比上一次成功构建的差异（代码、配置、环境镜像），本地复跑定位。最后补一句治理：加健康检查前置、隔离测试数据、失败自动重试一次并标记 flaky。

**适合与不适合自动化的用例。** 适合：接口与协议层、稳定的主流程、需要重复执行与大数据量组合的校验、性能与稳定性。不适合：一次性的探索性测试、界面频繁变更且维护成本高于收益的流程、依赖人主观判断的体验类场景（音质、显示效果、驾驶感受）、以及需要真实物理环境的实车路测。判断标准是「执行频次 × 稳定性 ÷ 维护成本」。

**座舱测试的 adb 常用命令。** `adb devices` 看设备、`adb shell` 进系统、`adb shell dumpsys activity` 看当前界面、`adb shell dumpsys window` 看窗口与焦点、`adb shell input tap/swipe/text/keyevent` 做点击滑动输入与按键、`adb shell am start -n 包名/Activity` 拉起应用、`adb shell pm list packages` 列应用、`adb logcat -s TAG` 抓日志、`adb shell screencap` 截图、`adb shell dumpsys meminfo/cpuinfo` 看资源、`adb push/pull` 传文件、`adb shell settings put` 改系统设置。车机上还要注意多屏与多用户（`--user`）、以及车辆信号需要走 CAN 工具而非 adb。

**CAN 与 CANoe。** CAN 是车载总线的差分串行协议，报文按 ID 仲裁、数据帧 8 字节（CAN FD 到 64 字节），测试里通常用 DBC 文件描述信号与报文映射。CANoe 用来做仿真与监控：加载 DBC 后可以发模拟报文、看信号实时值、写 CAPL 脚本做自动化激励与检查、配合 VT System 做硬件在环。测试场景包括信号丢帧、超时、非法值、总线负载过高、以及节点掉线后的降级策略。

**小程序 UI 自动化架构。** 常用 miniprogram-automator 通过开发者工具提供的自动化端口驱动，脚本侧用 Jest 组织用例；架构分四层：页面对象层（把页面元素与操作封装）、用例层（业务步骤与断言）、数据层（测试账号与数据准备／清理）、执行层（CI 定时跑、报告与截图留存）。难点是元素定位不稳定（用选择器与文本组合、加等待与重试）、多端差异、以及授权与支付类流程需要 mock。要能讲清「为什么这样分层」：元素一变只改页面对象层，用例不动。

**Web 应用的用例设计维度。** 功能（各模块主流程与异常）、界面与交互（布局、文案、响应式）、兼容性（浏览器、分辨率、系统）、性能（首屏、并发）、安全（越权、注入、敏感信息）、接口（参数校验、幂等、错误码）、数据（边界、脏数据、并发）、以及可访问性与国际化。回答时按「模块 × 维度」给一张简表，比逐条罗列更有结构。

帖主在文末提到，这家公司属于汽车行业的 Tier 2 供应商，公开资料与面经都很少，苏州岗位在子公司办公。投递这类公司时，面试里问清「主体是哪家公司、社保与合同签在哪、项目驻场与否」比只问业务更有用。
