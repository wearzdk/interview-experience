### 《参考解析》

**Git 三件套。** `git add` 把工作区的改动放进暂存区（index），是「挑选这次要提交什么」；`git commit` 把暂存区的内容生成一个提交对象写进本地仓库（带父提交、作者、时间、树对象），此时还没到远端；`git push` 把本地分支的提交同步到远端仓库。三者对应「工作区 → 暂存区 → 本地仓库 → 远程仓库」的迁移。补充：`git commit -am` 可以跳过 add 但只对已跟踪文件有效；`git push` 前通常要先 `pull --rebase` 避免非快进；`git reset --soft/--mixed/--hard` 分别回退到三个区域的某一层。

**JDK 1.8 为什么加红黑树。** 链表查询是 O(n)，当哈希函数不够好或遭遇恶意构造的键（哈希碰撞攻击）时，所有元素挤在同一个桶里，`get` 退化成线性扫描，CPU 与响应时间被打爆。树化后桶内查询降到 O(log n)，把最坏情况从 O(n) 拉到 O(logn)。触发条件是「链表长度 ≥8 且数组容量 ≥64」（容量不足时优先扩容，因为扩容能打散冲突），退化阈值是 6，中间留了缓冲避免频繁转换。红黑树而不是 AVL，是因为红黑树插入删除的旋转次数更少，适合 HashMap 这种写多读也多的场景。

**JDK 版本与新特性。** JDK 8：Lambda、Stream、`Optional`、接口默认方法、`CompletableFuture`、元空间替代永久代、`HashMap` 树化。JDK 11：`var`（10 引入）、HttpClient 标准化、`String` 新增方法、ZGC 实验性。JDK 17（LTS）：密封类、`record`、模式匹配 `instanceof`、强封装 JDK 内部 API。JDK 21（LTS）：虚拟线程正式版、`switch` 模式匹配、分代 ZGC、Sequenced Collections。作者提到泛型（JDK 5）与虚拟线程（21），回答时按 LTS 版本组织更清楚，别把 preview 特性说成正式。

**虚拟线程为什么开销小。** 平台线程（1:1 映射到内核线程）的栈默认 1MB、创建与切换要走内核、数量受限于内存与调度开销，几千个就到顶。虚拟线程是 JVM 调度的用户态线程（M:N，多个虚拟线程跑在少量载体线程上），栈按需增长（初始只有几百字节，存在堆里），阻塞时（IO、`sleep`、`park`）由 JVM 把虚拟线程从载体线程上卸载（unmount），载体线程去跑别的虚拟线程，不需要占一个内核线程。所以能轻松创建百万级、写起来还是同步阻塞的风格（不用回调或响应式）。要注意的点：CPU 密集型任务用它没收益；`synchronized` 块里阻塞会「钉住」载体线程（JDK 21 有 pinning 问题，JDK 24 起改善），应改用 `ReentrantLock`；线程本地变量（ThreadLocal）在百万虚拟线程下会放大内存，要慎用；连接池大小仍要限制，否则会把下游打爆。

**MySQL 事务与原子性。** 事务是一组要么全做要么全不做的操作，ACID 四性分别由：原子性靠 undo log（记录反向操作，回滚时按版本链恢复）、持久性靠 redo log（WAL，先写日志再刷数据页，崩溃后重放）、隔离性靠锁与 MVCC、一致性是前三者加业务约束的结果。回滚的实现细节：每次修改前把旧值写进 undo log（`DB_ROLL_PTR` 串成版本链），`rollback` 时沿链反向应用；同时 undo log 也服务 MVCC 的快照读。两阶段提交（redo 的 prepare + binlog 的写入 + commit）保证 binlog 与 redo 一致，这是主从复制正确的前提。

**链表反转（ACM 模式）。** 迭代三指针：`prev = null`，`cur = head`，循环里先存 `next = cur.next`，再 `cur.next = prev`，然后 `prev = cur; cur = next`，最后返回 `prev`。ACM 模式要自己处理输入输出（按行读、可能有多组、注意空行），以及「12345 → 54321」如果是数字而非链表，就要取模逐位构造。写完用手推一个两节点和单节点用例。

**超时取消订单（海量数据 + 高并发）。** 标准答案是「延迟消息 + 状态机 + 幂等」，分层讲：

- 触发：订单创建时投递一条延迟消息（RocketMQ 延迟级别 / RabbitMQ 死信队列 / Redis Zset 按到期时间存 + 定时扫 / 时间轮），到期后消费。
- 校验：消费时先查订单当前状态，只有「待支付」才取消——这就是状态机（待支付 → 已取消 / 已支付），用条件更新 `update orders set status='CANCELLED' where id=? and status='PENDING'` 保证只有一个消费者成功，天然幂等。
- 补偿：取消要释放库存、退优惠券、关支付单，这些动作走本地消息表/事务消息保证最终一致；失败重试 + 死信 + 人工兜底。
- 海量数据：不要全表扫（`where status=0 and create_time < now()-30min` 会打爆数据库），用延迟消息按订单维度触发；如果必须扫，按时间分片 + 索引 + 限流，或把「待支付订单」单独放一张表/一个 Redis Zset。
- 高并发：消费端限流、批量处理、分片消费（按订单 ID 分区保证同单有序）；对「用户刚支付、取消消息同时到达」的竞态，靠上面的条件更新 + 支付回调也走同一状态机来兜住。
- 兜底：定时对账任务扫「超时仍未关闭」的订单，作为消息丢失的补偿；监控「待支付超时未取消」的数量作为核心指标。

这题面试官真正想听的是「消息可能丢/重复、支付与取消会竞争、扫表会打爆数据库」这三点你有没有想到，以及你的方案能否说清幂等键与补偿路径。
