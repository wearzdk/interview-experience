### 《参考解析》

**MCP 的工具是怎么进上下文的**：这是整场追问的主线。MCP 是「模型 ↔ 工具/资源」的协议，Server 通过 `tools/list` 暴露工具名、描述、JSON Schema 形式的入参；Client（可以是宿主应用内的一个组件，也可以是独立进程）负责连接 Server、取回清单、把「模型返回的工具调用意图」翻译成对 Server 的实际调用（`tools/call`），再把结果回灌给模型。所以「只传一个 MCP 列表、Agent 没主动连接 Server 怎么调通」的正确答案是：**调不通**——上下文里没有 schema 就没有可组装的参数，只能先让 Client 去拿 tools 再进第二轮请求。这就是所谓「两段式」：第一轮拿清单（或按 name 精确请求某一个 Server 的 tools），第二轮才带 schema 生成调用。追问「为什么不让模型自己猜参数」时要点明：参数正确性靠 schema 约束，不靠模型记忆；把工具清单塞进上下文是「有成本的正确性」，工具多时要按需检索而不是全量注入。

**为什么要 MCP 而不是写进 Skill 或 SQL**：三类东西的分工要能一句话说清——Skill 放程序性知识（这类任务按什么步骤做、踩过什么坑），MCP 放能力与数据的边界（有哪些工具、参数是什么、权限归谁），SQL 是某一次具体查询的实现。把远程信息硬写进 Skill 的问题是：数据变了要改提示词、没有权限校验、无法审计、也无法复用给别的 Agent；把 MCP 拉回来的数据再塞进 SQL 是绕路——SQL 只能查你已有的库，外部系统的实时状态本来就该由工具去取。MCP 这层的价值是标准化（换模型/换客户端不用重写集成）、权限与审计（工具级授权、每次调用可留痕）、以及按需加载（工具清单不进常驻上下文）。

**request 与 response 的组装**：一次请求本体是 `model + messages + tools + 参数（temperature、max_tokens、thinking 等）`。`messages` 按角色分 system / user / assistant / tool（OpenAI 叫 tool，Anthropic 叫 tool_result），system prompt 放身份与规则，Skill 的操作规范通常也拼进 system 或作为前缀消息，MCP 的工具清单放在顶层 `tools` 字段而不是消息里。响应里模型要调工具时给出的是结构化的 `tool_calls`（OpenAI：`choices[0].message.tool_calls[]`，每项含 `id`、`function.name`、`function.arguments` 的 JSON 字符串；Anthropic：`content` 数组里的 `tool_use` block，含 `id`/`name`/`input`），纯文本回答则在 `content`/`message.content`。拿到调用后由宿主执行，把结果作为一条新消息（带对应的 `tool_call_id`）追加进 `messages` 再请求一次。流式下这些都是增量的 delta，要按 index 拼装。

**LangGraph**：把 Agent 建模成状态图——定义全局 State（字段可带 reducer 决定如何合并），节点是函数（读 State、返回局部更新），边是流转（普通边、条件边按 State 决定下一跳），编译成可执行图后按「节点 → 更新状态 → 下一节点」循环，直到到达 END。相比自己写 while 循环，它的价值是显式的状态与分支（可读、可测）、检查点（每步可持久化，支持断点续跑与人机协同）、以及可观测的轨迹。节点怎么拼要能说清：一个节点只做一件事（调模型、调工具、做校验），条件边里做路由判断，循环靠「回到某个节点」表达，并要设最大步数防死循环。

**什么时候该用向量检索**：向量检索解决的是「语义相近但字面不同」的召回，比如用户说「退不了款」要命中「退款流程与时限」。它不适合：数据量极小（二十条数据全塞进上下文更准也更省事）、需要精确匹配或聚合的查询（订单号、金额区间、计数）、强结构化约束（权限、时间范围）——这些用 SQL 或倒排索引更可靠。工程上常见的是混合召回：向量管语义、BM25 管关键词，两路融合再重排；过滤条件（权限、版本、时间）在检索前应用，不能指望模型自己筛。被问「二十条数据也要向量库吗」，正确回答是不要——这是过度设计，直接全量放进提示词或者用关键词匹配即可，向量库的成本在运维与一致性上。

**知识图谱与 RAG 的边界**：RAG 给的是「相关文本片段」，模型自己从片段里拼关系；知识图谱给的是「已经确定下来的实体与关系」，多跳查询是显式的图遍历。什么时候必须上图：关系本身就是答案（A 的供应商的控股股东是谁）、需要多跳且每跳都要精确（医疗诊断的症状→疾病→用药禁忌）、需要一致性与可解释（同一实体在不同文档里有不同叫法，必须先归一）、以及需要做约束推理（哪些组合不允许）。什么时候不必上图：知识以长文本描述为主、问题基本是「找到那段话」、或者图规模太小（两跳、几十个节点）——这时模型自己在几段文本里跳两跳就够了，上图只是多一层维护成本。被追问「准确率 80% 怎么算的」，要能说清评测集怎么构造（问句从真实日志采样还是人工写）、标注口径（多跳是否算对、部分正确怎么计）、以及分母是什么；说不清口径的准确率等于没有。

**面试里的自保**：这场面试的特点是「连续追问到你答不出」，遇到确实没深入过的点（比如某个 response 字段），直接说「这块我没有特别关注，我的理解是……回去我会去确认」，比硬编一个细节安全——面试官明显在验证边界，瞎编会被立刻抓住。
