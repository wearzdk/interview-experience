### 《参考解析》

1. **HashMap 多线程**：JDK 8 之前的头插法在并发扩容时可能形成环形链表导致死循环；JDK 8 改成尾插后不再成环，但并发 put 仍会丢数据、size 计数不准，并发扩容还可能互相覆盖。所以并发场景要么用 `ConcurrentHashMap`，要么在入口就串行化。回答时要顺带说出「为什么 JDK 8 之后仍然不安全」，这才是加分点。

2. **异步的适用场景**：把不阻塞主流程、失败可补偿的事情挪出去，比如发通知、写日志、生成报表、调外部接口。异步的代价是结果最终一致、错误处理复杂，所以涉及用户能立刻看到的结果时不能异步。

3. **线程池自己配**：核心线程数按任务属性定，CPU 密集型接近核数，IO 密集型按「核数 × (1 + 等待时间/计算时间)」估；队列要有界，拒绝策略要显式选，线程命名要带业务前缀方便排查。用 `ThreadPoolExecutor` 手动构造而不是 `Executors` 的默认工厂，是因为后者队列无界或线程数无上限。

4. **事务不生效**：常见原因是同类内部方法调用绕过代理、方法不是 public、异常被自己 catch 掉了、抛的是受检异常而默认只回滚 RuntimeException、数据库引擎不支持事务、多数据源没配对事务管理器。排查顺序就是先看代理有没有生效，再看异常有没有被吞。

5. **多条件筛选慢**：先看执行计划，确认有没有走索引、有没有回表、扫描行数是多少；再看是不是动态拼接导致索引失效（比如对字段做函数运算、前导模糊匹配、条件列类型不一致）。优化方向是按选择性建联合索引、让最左前缀能命中、把大偏移分页改成游标、必要时上覆盖索引或宽表。

6. **并发预约防重**：数据库层用唯一索引兜底是最可靠的一道，业务层再加分布式锁或 Redis 的 `SET NX` 抢占，扣减库存用带条件的原子更新。要点是「锁只是减少冲突，最终一致性要靠唯一约束和幂等键」，只靠应用层锁在有多个实例或锁过期时会漏。

7. **缓存到期瞬间涌入大量请求**：这就是缓存击穿。方案有三种：加互斥锁让一个请求回源、其余等待；逻辑过期，值里带过期时间，异步刷新时先返回旧值；热点数据提前预热并设置随机过期时间打散。选哪种取决于能不能接受短暂脏读。

8. **超时时间设计**：按下游的 P99 延迟往下压，保证「上游超时 > 下游超时」形成逐层收敛，避免请求在一层层重试里放大。缓存过期时间加随机抖动，防止同一时刻批量失效。

9. **Redis 黑名单**：用 set 或布隆过滤器存封禁标识，查询放在拦截器最前面；用布隆过滤器时要注意它只能判「一定不在」，误判方向是「可能在」，所以命中后还要回源确认。黑名单要有 TTL 或定期重建，否则永久累积。
