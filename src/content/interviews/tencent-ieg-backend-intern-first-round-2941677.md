### 《参考解析》

**进程、线程、协程的本质区别在「资源与调度单位」**：进程是资源分配的基本单位，有独立地址空间，切换要走内核、成本最高；线程是 CPU 调度的基本单位，同进程内共享地址空间与文件描述符，只需保存寄存器与栈，切换在内核；协程是用户态的协作式调度，切换不经过内核、由程序自行让出，开销在百纳秒级，但无法利用多核（要配多线程或调度器）。协程适合 IO 密集的高并发（Go 的 goroutine、Python 的 asyncio），线程适合需要并行计算或已有阻塞式库的场景。

**线程通信与进程通信**：线程共享内存，同步靠互斥锁、条件变量、信号量、原子变量，传递数据直接读写共享变量，因此重点在「可见性与原子性」而不是「传输」。进程隔离，通信必须经内核：管道、消息队列、共享内存（配信号量）、信号、Socket、文件锁。共享内存最快但要自己做同步，管道与消息队列简单但有拷贝开销，Socket 可跨机。

**多进程还是多线程**：CPU 密集且希望利用多核、需要强隔离（一个任务崩溃不影响其他）时用多进程；IO 密集、任务间需要频繁共享状态时用多线程；有 GIL 的语言（CPython）CPU 密集任务只能用多进程绕过。

**复合索引是最左前缀**：能命中的是「从最左列开始连续匹配」的查询条件；范围查询（`>`、`<`、`between`、`like 'x%'`）之后的列无法再用索引定位，只能做索引条件下推（ICP）在回表前过滤，所以看起来「部分命中」。判断某选项是否部分命中，看它的等值列是否覆盖了索引最左的连续几列、范围列在不在中间。

**频繁 GC 的排查路径**：先确认现象——`jstat -gcutil` 看 Young / Full GC 频率与耗时，GC 日志（`-Xlog:gc*`）确认是 Minor 还是 Full、停顿是否超标。再定位对象来源：`jmap -histo:live` 看占比最高的类，`jmap -dump` 配合 MAT 找支配树与大对象、看是否有集合无界增长或缓存没设上限。常见根因是促销或大查询导致单次拉取数据过多、本地缓存无淘汰、线程池队列堆积、连接与流未关闭。调参只是缓解，先找分配速率异常的那条路径。若确属正常流量增长，再考虑堆与收集器选型（G1 / ZGC）与对象晋升策略。

**用 Agent 把游戏信息爬到英雄、技能、伤害粒度**：要先解决「结构化」而不是「抓取」。抓取层用无头浏览器渲染动态页面，落原始 HTML 与截图；抽取层不要指望一次大模型调用吐出全量 JSON，按「页面 → 英雄列表 → 英雄详情 → 技能 → 数值」分层抽取，每层定义 schema 并用结构化输出约束；校验层用规则交叉验证（技能数量与页面目录数对得上、伤害数值区间合理、与上一版本 diff 只有预期变化），不一致的样本回到人工或二次抽取。数值类内容必须保留出处（页面 URL + 抓取时间），因为它会随版本更新。

**怎么让 AI 高质量完成开发**：把任务切成可验证的小步——先让它读现有代码与约定、产出方案再动手；给明确的输入输出与边界（改哪个文件、不许改哪些、错误怎么处理）；要求它自证（写测试或给出可执行的验证命令并运行）；最后由人 review 关键逻辑与边界条件。反过来，只丢一句需求、拿到代码不看就提交，是最容易出事的用法。

**「AI 替代程序员」这类开放题**：给出分层判断——重复性的、模式固定的代码生成会被大量替代；需求拆解、系统设计、故障归因、跨团队对齐这些需要承担后果的部分仍然要人。核心竞争力落在「能把模糊需求变成可验证的方案」和「能对线上结果负责」，而不是背 API。
