### 《面试题目》

1. Redis 的基础数据类型你用过哪些，具体怎么用的？
2. 跳表的结构是怎样的？
3. 走非聚集索引是否必须回表？
4. ThreadLocal 的 key 是弱引用，为什么还会造成内存泄漏？
5. 布隆过滤器了解吗？
6. 实际生产中接口变慢，你怎么处理？

### 《参考解析》

**Redis 数据类型要答「结构 + 典型用法 + 复杂度」**：String 用于计数、缓存对象序列化、分布式锁（SET NX PX + Lua 释放）；Hash 用于存对象的多个字段、支持单字段更新；List 用于简单队列与时间线（LPUSH + BRPOP）；Set 用于去重、交集并集（共同关注）；ZSet 用于排行榜、延迟队列（score 存到期时间戳）；再往上还有 Bitmap（签到、活跃统计）、HyperLogLog（UV 估算）、GEO（附近的人）、Stream（消息流）。答题时给一个你真实用过的场景 + 为什么不用别的结构，比背清单有效。

**跳表是「多层有序链表 + 概率提升」**：最底层是全量有序链表，每层以 1/2 概率把节点提升到上一层，查找从最高层开始向右走，遇到更大的就下降一层，期望时间复杂度 O(log n)，插入删除也是 O(log n)。相比平衡树，它实现简单、范围查询天然友好（底层就是链表）、并发下更容易做无锁实现，Redis 的 ZSet 在元素多或字符串长时就用「跳表 + 字典」组合：字典保证按 member 查 score 是 O(1)，跳表保证按 score 范围与排名查询高效。

**非聚集索引不一定回表**：如果查询需要的列全部在二级索引里（覆盖索引），直接从索引拿到结果，不需要回表；只有需要索引里没有的列时才回表取整行。另外，即使需要回表，MySQL 也可能用 MRR（Multi-Range Read）先把主键排序再批量回表，减少随机 IO。判断依据看执行计划的 Extra 是否出现 `Using index`（覆盖索引）与 `Using index condition`（索引条件下推）。

**ThreadLocal 的弱引用只解决了 key，没解决 value**：Entry 继承 WeakReference，key 是 ThreadLocal 对象的弱引用，GC 后 key 变 null，但 value 仍被 Entry 强引用，而 Entry 又被 Thread 的 ThreadLocalMap 持有——只要线程还活着（线程池里线程长期存活），value 就回收不掉，形成 key 为 null 的僵尸 Entry。ThreadLocal 自己会在 get/set/remove 时顺带清理部分脏 Entry，但不保证及时。所以规范是 try/finally 里显式 `remove()`，线程池场景尤其必须。

**布隆过滤器是「用位数组 + 多个哈希做存在性判断」**：能确定「一定不存在」，只能判断「可能存在」，有假阳性没有假阴性；不支持删除（要用计数版 Counting Bloom）。典型用途是缓存穿透防护（先过布隆再查库）、爬虫 URL 去重、推荐已读过滤。参数上，误判率由位数组长度 m、哈希个数 k、元素个数 n 共同决定，工程上按预估容量留余量。

**线上接口慢的排查顺序：先定位再优化**。第一步看监控与链路追踪，确定是哪一个接口、哪一段耗时（网关、应用、缓存、DB、下游 RPC）；第二步看现象特征（偶发还是持续、是否与流量相关、是否与某次发布相关）；第三步逐层取证：应用侧看线程栈与 GC 日志（是否有长停顿、线程池是否打满）、慢查询日志与执行计划（是否走错索引、是否回表过多、锁等待）、缓存命中率与热 key、下游 RTPS 与超时。修复手段按代价排序：加索引或改写 SQL、加缓存、批量合并请求、异步化、限流降级，最后才是扩容。
