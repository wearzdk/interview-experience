### 《面试题目》

1. 请介绍你的实习和项目。
2. 你为什么不用 LangChain，而是选择自研一套执行层？
3. 如果自研的某个节点执行失败、超时或短路，你怎么处理？
4. 扫描版 PDF 和图表是怎么入库的？
5. 如果 OCR 模型出错、表格语义无法文本化，或者 VLM 无法翻译图表，你会怎么处理？
6. 工作流节点配置和节点流用了 zod，zod 和 TypeScript 有什么区别？
7. 哪些数据交给 zod，哪些数据交给 TypeScript 处理？

### 《参考解析》

**自研执行层和用 LangChain 不是“谁更高级”，而是控制权和维护成本的取舍。** 自研通常是为了掌控节点生命周期、重试与超时、流式输出、可观测性和私有工具接入，避免框架升级带来的破坏性变更；代价是调度、状态持久化、错误恢复这些基础设施都要自己维护。回答时先讲业务约束：节点是否需要断点续跑、是否要按租户隔离、是否需要精确的计费和日志；再说 LangChain 能提供什么、哪些地方不够贴合。如果标准链路已经够用，直接用框架更划算；只有当框架的抽象挡住关键需求时，自研才成立。

**节点失败要按“可重试 / 不可重试 / 部分成功”分类。** 网络抖动、限流、临时超时可以做带退避的重试，但必须保证节点幂等，否则重试会重复写数据；参数错误、权限不足这类不可重试错误直接失败并给出明确信息。每个节点要有超时和取消信号，长链路要能 checkpoint，失败后从最后一个成功节点恢复，而不是整条重跑。短路可以是业务上的提前结束，也可以是熔断：下游连续失败时暂时跳过，走降级结果或人工队列。最终要有 dead letter 和可观测性，能回答“哪个节点、哪次执行、为什么失败”。

**PDF 入库的难点在版面理解和可追溯性。** 扫描版先做 OCR，保留页码、坐标和置信度；表格单独走表格识别，别把整页当成一段文本；图表用 VLM 生成描述时，要把图注、上下文和原始页码一起存进 metadata，方便回溯。入库前做质量闸：OCR 置信度低、表格行列数异常、图表描述为空的内容进入人工复核队列，不要直接喂给检索。检索时按文档结构分块，表格块带表头，图片块带描述和出处；回答“表格被分到不同 chunk”时，可以说按表头重复、按行聚合、或把整表作为父块、行作为子块。

**zod 和 TypeScript 是运行时与编译期两道防线。** TypeScript 的类型在编译后被擦除，管的是开发阶段的静态检查；zod 的 schema 在运行时真正校验外部数据，适合接口响应、表单、配置和工作流节点输入这些不可信边界。通常用 `z.infer` 从 schema 推导静态类型，做到“一份 schema、两头使用”。不是所有数据都要 zod：内部已经由类型系统保证的结构不必重复校验，外部输入、持久化数据、跨服务消息才需要。把校验放在边界上，既不会让业务代码到处是防御性判断，也不会把脏数据放进系统。
