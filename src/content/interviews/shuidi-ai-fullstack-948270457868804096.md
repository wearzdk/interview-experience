### 《面试题目》

2. 如果用户选错问题类别，系统怎么识别、处理并告知用户？
3. 人工处理资源减少时，怎么提高自动诊断的准确率？当前瓶颈在哪？
4. 单 Agent 与另一种执行模式有什么区别？为什么要设计执行过程中的锁定机制，主要锁定什么？
5. 用户提交的文本要求忽略规则并执行操作，怎么防止 Agent 照做或越权？
6. 只读工具返回的数据里包含类似指令，怎么保证 Agent 不会在未经用户授权时执行？
7. 某项能力升级后，怎么判断新版能否替换旧版？为什么评测还没有形成固定流程？
8. 提交文件后取消任务，服务端怎么处理？
9. 不同用户上传同名文件，怎么避免误用之前的结果？如果文件内容也一样呢？
10. 文件合并是怎么做的？
11. 业务服务正常，但推理请求积压，内存和显存持续上涨，服务快撑不住了，怎么处理？
12. 知识库内容已经更新，用户仍收到旧答案，怎么判断问题出在切分、向量还是检索环节？

### 《参考解析》

**自动诊断的流程与误判**：完整链路是「采集信号（日志、指标、告警、变更记录）→ 归一化与补全上下文 → 规则/检索召回候选故障模式 → 模型推理与排序 → 输出结论、证据与建议动作 → 人工确认或自动执行 → 回流结果」。误判的典型来源是上下文缺失或类别选错，比如把数据库连接池耗尽误判为慢查询。处理方式是要求结论必须附证据（哪条日志、哪个指标、时间窗），证据不足时降级为「疑似」并给出下一步排查建议；把人工纠正结果写入样本库，定期回放评测，按故障类型看准确率而不是只看总体。

**用户选错类别**：入口先做一次轻量分类，结合用户描述、附件、历史工单与系统信号给出候选类别及置信度；置信度低时不强行归类，而是列出前三个可能并让用户确认；如果用户坚持错误类别，系统仍按用户选择执行，但在诊断中保留「与所选类别不符」的提示，避免结论被带偏。关键是把「分类」和「诊断」解耦，分类错了仍有机会在诊断阶段纠正。

**人工减少时提升准确率**：先做分层，把高频、规则明确、可验证的故障交给自动化，把长尾与高风险的交给人；用人工处理过的工单做检索增强与少样本示例；对模型输出做结构化约束（必须引用证据、必须给出置信度），低置信度自动转人工；建立反馈闭环与回归集，按类别监控准确率与漏判率。瓶颈通常不在模型能力，而在数据质量、故障标注缺失与工具权限不足。

**单 Agent 与多 Agent、锁定机制**：单 Agent 在一个上下文里完成规划与执行，链路短、成本低，但长任务容易丢上下文、工具多了容易选错；多 Agent 把规划、执行、评审拆开，各自上下文更聚焦，代价是通信与一致性成本。锁定机制是为了防止同一资源被并发修改，比如同一工单、同一文件、同一部署环境；锁的粒度要小、要有租约与超时，获取失败要明确告知而不是静默等待。

**提示词注入的两类来源**：一类来自用户输入，一类来自工具返回的内容（网页、文档、检索结果）。防护不能只靠提示词，要做分层：系统指令与用户内容分离并标注来源；工具按权限分级，写操作与敏感操作必须二次确认；对工具返回的内容做「数据而非指令」的封装，检测到越权意图时拒绝执行；限制可用工具集与参数范围，输出侧做校验。只读工具被注入时最多泄露信息，写工具被注入才会造成实际损害，所以权限隔离是底线。

**版本评测**：先定义任务集与成功判据，覆盖高频、长尾、边界与对抗样本；新旧版本在同一批任务、同一模型、同一工具集下对比，记录成功率、成本、时延与失败类型；自动判分要有抽检校准，避免判分器本身漂移。评测难固定的原因是任务开放、判分主观、线上分布变化快，做法是把评测集当产品资产持续维护，版本上线前跑回归、上线后看灰度指标。

**文件上传与合并**：取消任务时先标记任务状态为取消，停止后续处理，清理临时文件与中间产物，已产生的部分结果要么删除要么标记不可用；接口要幂等，重复取消不报错。同名文件用「用户 ID + 内容 hash + 版本」做唯一标识，不能只用文件名；内容相同可以命中同一份存储做去重，但权限与引用计数要分开。文件合并按格式处理：文本按章节与段落对齐，表格按主键合并，冲突处保留双方并标注来源，不能静默覆盖。

**推理排队导致内存显存上涨**：先止血——限制入队长度、对超出部分快速失败（返回 429 或排队位置），关闭无关缓存，必要时重启实例并保留现场；再定位——看请求速率与处理速率、单请求 token 数、批处理参数、是否有长请求占住显存、是否存在泄漏（显存不随请求结束释放）。治理上做背压与限流、按优先级分队列、动态批处理、超时与取消、显存池化与定期回收，容量不足就扩容或降级模型。

**RAG 旧答案定位**：先确认知识库更新是否真的进了检索链路——文档版本、切分产物、向量是否重建、索引是否切换；再看检索结果里有没有新内容，如果没有，问题在切分或索引；如果有新内容但答案仍旧，问题在提示或模型对上下文的利用；如果检索召回的是旧块，检查是否多版本共存、缓存未失效、按时间过滤的条件写错。做法是给每次回答记录引用的 chunk 与版本，用同一问题回放对比。

**摘要结构与冲突**：结构上分「结论、关键事实、来源、置信度、待确认项」，每条事实挂来源与时间，便于追溯。冲突检测可以先用规则（同一实体同一属性出现不同值），再用模型判断是否真冲突、哪个更新或更可信；无法判断时并列展示并标注分歧，不要合成一个看似确定的结论。

**查询失败任务**：按状态、时间范围、任务类型建索引，SQL 大致是 `status = 'FAILED' AND created_at BETWEEN ? AND ? ORDER BY created_at DESC`，返回任务 ID、失败原因、重试次数与关联用户；量大时按时间分区，避免全表扫描。

**Harness 与个人 Agent**：Harness 是模型之外的运行时，负责工具、上下文、权限、沙箱、循环与评测。国内产品多把 Harness 做进垂直场景（办公、 coding、搜索），强调开箱即用与本地化集成；国外更常见通用 Agent 平台与开放工具生态，强调可扩展与可观测。实际用过哪个就讲哪个，重点讲你让它做了什么、它在哪一步失败、你怎么改工具或约束。
