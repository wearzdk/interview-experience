### 《参考解析》

**二段式交易（两阶段提交/两段式确认）在支付场景里指的是「先预下单、再确认扣款」。** 拆成两段的目的是把「不可逆的扣款」和「耗时的业务处理」解耦：第一阶段创建交易单并冻结/预占额度（此时状态是待确认，幂等键已落库），第二阶段在确认条件满足后执行真正的扣款与发货，状态机只能单向迁移。跨机房扫码确认的核心难点是**数据一致性与时钟**：A 机房的交易单需要在 B 机房的确认请求下推进状态，不能依赖单机内存锁，必须用带版本号的乐观锁更新（`update ... where status = ? and version = ?`），并在跨机房调用失败时用「回查 + 对账」确认最终状态；网络分区时需要明确以哪一侧为准（通常是交易单归属机房），避免双写。

**通用幂等框架要回答「幂等键怎么来、状态怎么存、重复请求怎么返回」。** 典型实现：入口处由框架提取幂等键（业务单号或 客户端请求号 + 用户 id + 接口标识），在幂等表或 Redis 上用唯一约束/`SETNX` 抢占；第一个请求执行并把结果（或状态）写回幂等记录，后续重复请求直接返回第一次的结果而不是再执行一遍。要强调的细节：抢到锁后如果业务执行失败，必须**删除幂等记录或标记失败**，否则会把一次失败永久固化；幂等记录的 TTL 要覆盖业务重试窗口；返回「处理中」而不是「成功」以避免把未完成当完成；以及数据库唯一索引是最后一道保证，缓存锁只是降冲突。**为什么不用雪花算法做幂等 ID**：雪花 ID 每次生成都不同，同一个用户重试会生成新的 ID，起不到「同一业务动作只处理一次」的作用——幂等键必须**由业务事实决定**（订单号、用户 + 时间窗 + 动作），而不是由机器生成的唯一值；雪花算法解决的是「ID 全局唯一且有序」，它适合做主键，不适合做幂等判据。另外雪花算法强依赖时钟，回拨会导致重复 ID，本身也需要额外处理。

**CountDownLatch 的内部实现是「AQS 共享模式 + 状态计数」。** 它内部持有 `Sync extends AbstractQueuedSynchronizer`，构造函数把 `state` 设为计数值；`countDown()` 每次都 `releaseShared(1)`，即 CAS 把 state 减 1，减到 0 时把同步队列里等待的线程全部唤醒；`await()` 尝试 `tryAcquireShared`，state 不为 0 就进入 AQS 队列 park 等待。**为什么能准确计数**：`state` 是 volatile 字段，所有修改都走 CAS，失败就自旋重试，因此并发 `countDown` 不会丢计数；同时 state 的变化对其他线程立即可见。需要注意的边界：CountDownLatch 是一次性的（计数归零后不能重置，要复用请用 CyclicBarrier 或 Phaser），以及 `await` 要带超时避免永久阻塞。

**volatile 与 i++ 那题的标准答案是「都会丢更新」。** volatile 保证的是**可见性与有序性**（禁止指令重排、写后立即对其他线程可见），但**不保证原子性**：`i++` 在字节码上是「读 → 加一 → 写」三步，10 个线程并发执行时会出现两个线程读到同一个旧值、各自加一后写回，最终结果小于 100000，这是典型的竞态。换成 `volatile int` 也一样丢。正确做法是 `AtomicInteger`（CAS 自旋）或 `synchronized`/`ReentrantLock` 加锁；`LongAdder` 在高并发下性能更好（分散热点 + 最后求和）。这题还常被追问「volatile 什么时候够用」——单纯的标志位读写（一个线程写、其他线程读）就够用，例如 `while(!stop)`。

**并发与并行的区别是「同时处理」与「同时执行」。** 并发是任务在时间片上交替推进（宏观同时、微观串行），目标是提高资源利用率与响应性；并行是同一时刻真的有多个执行单元在跑（多核/多机），目标是提高吞吐。单核也能并发，并行一定需要多个执行单元。回答时顺带把「异步」也区分开：异步是调用方不等待结果的编程模型，它可以用并发实现（事件循环），也可以靠并行实现（多线程），三者不在一个维度。

**关于实习经历的追问，答题主线是「业务问题 → 方案 → 代价与验证」。** 面试官问「跟原来比优化点在哪」「直接查数据库会不会很慢」这类问题，想要的不是形容词而是**数字与机制**：优化前的 QPS/延迟是多少、改了什么（加缓存、减少回表、合并请求）、优化后多少、怎么压测验证、有没有副作用（缓存一致性怎么保证）。**缓存与数据库的关系**要主动说清：缓存是为了挡住读热点，不是替代数据库；扫码确认这类判断「是否已支付」的读，走缓存能降低延迟但必须保证写入时的一致性（先更新数据库再删缓存 + 延迟双删，或直接让缓存有过期兜底），关键的资金状态仍应以数据库为最终依据。
