### 《参考解析》

**表结构演化要讲「为什么变」，而不是「现在长什么样」。** 这类题的标准答法是三代：第一代按最直观的实体建表（用户、素材、分类），字段冗余在业务表里，查询快但一改口径就要写脚本回刷；第二代做范式拆分，把分类、标签、权限抽成独立表加关联表，解决了复用问题，代价是列表页要多次 join；第三代针对读多写少的列表做反范式——在素材主表上冗余 `tag_names`、`category_path` 这类展示字段，用「写时同步 + 定期对账」换查询性能。面试官追问「演化过程」时，你要能说出每一代的触发原因（某次需求、某个慢查询、某个数据量拐点），以及当时的取舍代价。索引部分同理：不是列清单，而是说明「这个列表页按 `仓库 + 状态 + 更新时间` 倒序分页，所以建了联合索引，最左前缀能覆盖过滤，排序字段放在最后避免 filesort」。

**「多仓库、多产业线素材」的场景题，本质是层级 + 权限 + 数据隔离三件事。** 一个可用的设计是：`repo`（仓库）、`material`（素材，带 `repo_id`）、`material_category`（仓库内的分类树，用 `parent_id` + `path` 存祖先链）、`material_tag` 多对多。产业线作为仓库的一个属性而不是独立维度，避免「仓库 × 产业线」的笛卡尔爆炸。查询侧的关键问题是「跨仓库检索」：如果运营要在一个页面看多条产业线的素材，纯 `repo_id` 过滤会变成多表扫，通常要再建一张检索表（或直接上 ES）按「产业线 + 标签 + 时间」冗余一份读模型，用 binlog 或消息同步，允许秒级延迟。这道题的加分点不是 schema 多漂亮，而是你主动问清楚「素材的可见范围是按仓库还是按产业线」「单仓素材量级多少」，把设计约束先固定下来。

**权限包改造要落到数据模型，而不是嘴上说「加个 RBAC」。** 最小改动是引入 `role`（角色/权限包）与 `role_permission`、`user_role` 两张关联表，权限点用 `resource:action` 的字符串（`repo:read`、`material:delete`）表达，鉴权时把用户的所有权限点拍平成一个集合放进缓存，请求进来只做集合判断，避免每次递归查表。要注意的两个坑：一是「仓库级」和「产业线级」的作用域，权限点必须带上资源 id 或作用域字段，否则一个 `material:delete` 会越权删到别的仓库；二是权限变更后的缓存失效，通常用「用户维度版本号」在写操作时自增，读侧比对版本号决定是否重载，比逐 key 删除可靠。

**「通用上传接口被打崩」这题考的是限流与隔离，不是加机器。** 顺序应该是：先做入口治理——按用户和租户的令牌桶限流、单文件大小与并发连接数上限、分片上传 + 断点续传；再做资源隔离——把大文件上传走到独立的上传服务与独立带宽/线程池，避免和普通接口抢同一个连接池，这一步是关键，因为「接口被打崩」往往不是 CPU 打满，而是上传占满了 Tomcat/Netty 的 worker 线程或连接数；最后是异步化——上传只负责落对象存储和写一条任务记录，后续的转码、抽帧、病毒扫描走消息队列，前端拿 taskId 轮询进度。答「加机器」「加缓存」都会被继续追问，因为上传是 IO 与带宽型负载，加缓存没有帮助。

**内存缓存 vs 独立缓存服务，答差异要落到「多实例一致性」。** 进程内缓存（Guava/Caffeine、Node 的 lru-cache）省一次网络往返，微秒级，适合极少变更的字典数据；问题是多实例之间不共享，一个实例更新了、其他实例还是旧值，只能靠 TTL 兜底或广播失效，而且它占的是业务进程的堆，大对象会把 GC 压力带进主链路，进程重启后全部丢失。独立缓存（Redis/Memcached）多一次 RTT，但天然共享、可独立扩容、支持原子操作与过期策略；代价是多一层依赖，要考虑穿透、雪崩、热 key 与大 key。实践里常见组合是「Redis 做共享层 + 进程内做极热的少量只读数据」，两级都要有 TTL 和失效通道，别指望单靠一级。

**Node 与 Java 写后端的差异，讲清「并发模型决定的适用面」。** Node 是单线程事件循环 + 非阻塞 IO，天生适合高并发、低计算量的 IO 密集场景（BFF 聚合、SSR、网关、实时推送、上传下载代理），同样的机器能扛更多空闲连接，冷启动和迭代速度也快；短板是 CPU 密集任务会阻塞整个事件循环（大 JSON 序列化、图片处理、复杂计算），要靠 `worker_threads` 或拆服务，另外生态里缺少 Java 那套成熟的分布式事务、连接池治理与 JVM 级观测工具链。Java 是多线程 + 线程池，CPU 密集和长事务场景更稳，生态（Spring、Dubbo、各类中间件客户端）和团队治理经验更成熟，代价是内存占用与启动时间。落到「哪些场景适合 Node」，答 BFF/聚合层、SSR、轻量网关、实时消息这类最稳。
