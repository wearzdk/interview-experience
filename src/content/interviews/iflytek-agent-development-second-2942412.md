### 《参考解析》

**高风险操作的约束**。分三层：动作分级（只读、可逆写、不可逆写、涉及资金或删除），不同级别对应不同策略；执行前确认（不可逆操作必须由用户显式确认，确认态要绑定参数快照）；执行中防护（超时、批量上限、幂等键、失败可回滚）。约束应落在服务端工具层而不是提示词里——提示词可以被绕过，工具层的能力边界绕不过去。审计日志要记全：谁、在哪个会话、调用了什么、参数是什么、结果如何。

**工具失败的处理**。把错误结构化返回给模型：错误类型（参数错误 / 权限 / 资源不存在 / 超时 / 上游 5xx）、可重试性、建议动作。可重试的由框架按退避重试并有次数上限，不可重试的直接告知模型换策略；同一工具同一参数连续失败要拦截并升级给用户。禁止把异常吞掉返回空结果，模型会把「没结果」当成「没有数据」，从而给出错误结论。

**取消正在执行的副作用工具**。先明确定义「取消成功」：任务已开始执行时，取消只能是尽力而为。落地做法是状态机：`running` → `cancel_requested`，工具在执行的关键步骤前检查取消标志（协作式取消），能中断的中断（HTTP 请求取消、子进程 kill），不能中断的（已经发出的支付、已提交的写请求）执行完后按补偿逻辑处理，并向用户明确回报「已取消」还是「已执行完成，已发起补偿」。对外接口的语义要写清，不能让用户以为一定没有副作用。

**确认参数后被更新**。核心是「确认即快照」：用户确认时把参数序列化成不可变快照，附带版本号或内容哈希；执行时用快照而不是重新读取当前值，并在提交前用乐观锁（版本号 / ETag / `WHERE version = ?`）校验资源没被改过；校验失败就中止并要求用户重新确认。这样保证「执行的一定是用户看到并点过确认的那一版」，而不是静默用新参数执行。

**SSE 断开后台任务继续**。任务的生命周期要与连接解耦：接请求时创建任务记录（任务 ID + 状态 + 事件流），后台执行器跑任务并把事件写入持久化的事件表 / 消息队列；SSE 只是订阅这个事件流的通道，断线后客户端用任务 ID 重新订阅并从 `Last-Event-ID` 续传，或者轮询状态。要注意的是断线不能触发取消（除非用户显式取消），并且事件要可重放以避免丢消息。

**模型中途超时切换**。影响有四处：上下文格式差异（不同模型对消息角色、工具调用格式的支持不同，需要适配层）、已生成的部分内容是否要保留（保留可能造成重复或风格断裂，重生成则浪费）、工具调用状态（新模型不知道已经调用过哪些工具，需要把工具结果摘要重新注入）、以及成本与限流（切换后可能命中不同配额）。设计上要把「模型无关的会话状态」与「模型特定的消息格式」分开存。

**身份与权限传递**。用户身份在入口处解析成不可伪造的凭证（签名 token 或服务端会话），随任务上下文一路传递，工具层只信任这个上下文而不是模型给的参数。工具执行前做两件事：认证（这是谁）与授权（这个人在这个项目里能不能操作这个资源），资源归属要在服务端查询验证，不能由模型传入的 `project_id` 决定。跨团队共用工具时用「工具 + 资源 + 动作」的权限模型，审计按用户维度记录。

**第三方插件与命令行的限制**。沙箱化执行：文件访问限制在工作目录（容器或 namespace 隔离）、网络按白名单出网或默认禁网、凭证通过短期 token 注入而不是环境变量常驻、限制 CPU / 内存 / 执行时长与进程数、禁用危险系统调用。插件要有权限声明（需要读哪些目录、访问哪些域名），安装时由用户确认；执行输出要截断并留痕。

**租户长任务占满资源**。三层控制：队列按租户分区并设权重（保证小租户不被饿死），并发按租户配额限制（同时执行数、每分钟提交数），预算按租户设 token 与费用上限，超限降级或排队。调度上区分交互任务与批任务，交互任务走优先队列；长任务设置最大执行时长与检查点，避免单个任务长期占用。还要有公平性指标（各租户的排队时长分位数）来验证没有饿死。

**P95 突然上升怎么定位**。先确认范围：是全部租户还是特定租户、特定工具、特定模型。再按链路拆：排队时长（队列积压）、模型调用时长（上游延迟、限流、超时重试）、工具执行时长（下游慢）、序列化与传输（大 payload）。对照最近变更（发布、配置、提示词、工具描述）与流量变化。方法上用分位数时间序列加分层维度（租户 / 模型 / 工具）定位到一段后，再取该段的 trace 看单条慢在哪一步。

**评测机制**。分三层：单步（工具选择、参数正确率）、任务（完成率、步数、成本）、人工抽检（质量）。case 从真实日志采样并脱敏，按场景分层并保留难例，版本化维护；每次改动跑同一批 case 做 A/B 对照，看差异是否显著。评测要能回答「这版比上版好在哪、坏了哪」，而不是只给一个总分。

**开源贡献与工具偏好**。这类问题如实回答即可：说清你提过什么 PR、解决了什么问题、被维护者如何 review，比罗列 star 数有说服力。AI 编程工具按实际使用情况讲，重点说清在什么环节用它、怎么校验它的输出。
