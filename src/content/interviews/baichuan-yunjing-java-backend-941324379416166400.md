### 《参考解析》

**拆微服务要讲“边界”和“代价”，不能只讲“更先进”。** 单体拆服务的正当理由通常是三件事：不同模块的发布频率和伸缩需求差异大、团队规模变大后代码所有权不清、单体的构建和故障隔离已经到了瓶颈。拆分粒度按业务能力走，而不是按 controller/service/dao 技术分层去切；购物车这种围绕用户购买链路的 capability 可以独立，但订单、库存、支付之间强一致的地方不能为了“看起来像微服务”硬拆。拆完的代价也要主动说：远程调用带来的网络失败、分布式事务、链路追踪、配置和部署复杂度都会上升。用购物车举例时，要能说清拆之前它依赖哪些表、拆之后用户、商品、价格这些数据从哪来，而不是只说“独立部署了”。

**改造路径用绞杀者模式更容易讲清楚。** 先在单体内部把模块边界和接口理出来，把跨模块调用收口到明确的服务接口；然后按优先级抽第一个服务，网关做路由，老代码继续跑，新流量逐步切过去；数据层先共享库、再按服务拆表，跨库一致性用本地消息表、事务消息或 Saga 这类可补偿方案，避免大爆炸式重写。Nacos 在这里承担注册中心和配置中心两件事：服务实例启动后注册、消费者按服务名发现实例，配置变更可以热更新；临时实例靠心跳保活，永久实例靠服务端主动探测。还要能说出它的边界——Nacos 解决的是发现和配置，不解决熔断、限流和链路追踪，那些要配合 Sentinel、网关和可观测性体系。

**MyBatis-Plus 不是另一个 ORM，而是在 MyBatis 上做增强。** 它保留了 MyBatis 的 SQL 映射能力，同时提供通用 Mapper、条件构造器、分页插件、逻辑删除、乐观锁等能力，简单 CRUD 可以少写 XML；复杂多表查询、窗口函数、特殊优化仍然应该写 XML 或原生 SQL。被追问时最好补一个坑：`updateById` 默认会忽略 null 字段，想清空某列要显式配置或写 SQL；逻辑删除后唯一索引、关联查询和统计口径都要跟着调整。权限体系则按“用户—角色—权限点”或“用户—角色—菜单/按钮/数据范围”来讲，认证解决“你是谁”，授权解决“你能做什么”，数据权限再单独一层，不要把三者混成一个角色字段。

**AI 代码质量差异的核心不在模型，而在输入和验收。** 同一个模型，给它的需求描述、上下文、约束和示例不同，产出会差很多；有没有把项目规范、接口契约、错误处理要求讲清楚，有没有让它先读现有代码再改，都会直接影响结果。更关键的是人有没有做 review、有没有测试和静态检查兜底。回答时可以讲自己的做法：小步生成、每步跑测试、关键路径手写、生成代码必须过 lint 和 code review；再用缺陷率、返工次数、线上问题这些指标判断 AI 是否真的提效。token 花多少不是质量指标，只能说明用量。
