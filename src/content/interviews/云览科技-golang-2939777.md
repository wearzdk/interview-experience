### 《面试题目》

1. 先做一下自我介绍，然后说说你的技术栈和 Go 使用的版本。
2. Go 中 context 有哪些作用？
3. channel 有缓冲和无缓冲的区别是什么，分别适合什么场景？
4. 你熟悉哪些 RPC 框架？
5. 如何排查线上服务的问题，性能瓶颈在哪里？
6. 实习项目里是怎么做性能监控的？
7. 未来对发展方向和 base 地有什么期望？

### 《参考解析》

**context 的作用**：一是传递取消信号，上游请求超时或被客户端断开时，通过 `ctx.Done()` 让下游的数据库查询、RPC 调用、协程及时退出，避免 goroutine 泄漏；二是传递超时与截止时间，`context.WithTimeout` 把整条调用链的预算往下传，每一层只花剩余时间；三是携带请求级元数据（trace id、用户身份），用 `WithValue` 传递，但只放请求范围的小对象，不要拿它当全局配置容器。使用时注意 `context` 作为函数第一个参数、不要存进结构体、`WithValue` 的 key 用自定义类型避免冲突。

**有缓冲与无缓冲 channel**：无缓冲 channel 的发送与接收必须同时就绪，天然做同步点，适合「交接任务、等待某个事件完成」；有缓冲 channel 解耦生产与消费的速度差，适合削峰、工作池的任务队列。缓冲大小要按消费能力设，设太大问题会被推迟暴露（内存涨、延迟高），设太小则退化成无缓冲。还要考虑关闭语义：只由发送方关闭、关闭后不能再发送、用 `v, ok := <-ch` 或 `range` 判断，配合 `select` 加 `ctx.Done()` 做退出。

**RPC 框架怎么答**：按使用场景说，不要只报名字。gRPC 基于 HTTP/2 与 Protobuf，支持流式、跨语言、生态成熟，适合内部服务间调用；Kitex、Kratos 这类 Go 生态框架在服务治理（限流、熔断、注册发现、链路追踪）上更完整；Dubbo 在 Java 体系里更常见，跨语言场景会用 Triple 协议。能说出「为什么选它」比列出五个框架更加分：接口定义怎么管、超时与重试怎么配、序列化用什么。

**线上问题排查**：先看现象分层——是全部请求慢还是个别接口、是某一台机器还是全集群、是发布后开始还是一直存在。工具上，指标看 QPS、延迟分位（P50/P95/P99）、错误率、CPU/内存/GC、连接数与队列长度；链路追踪定位慢在哪一跳；日志找具体错误；Go 服务用 `pprof` 抓 CPU、heap、goroutine、block、mutex profile。常见瓶颈按层列：数据库慢查询与锁等待、连接池耗尽、下游超时与重试放大、GC 停顿、锁竞争、goroutine 泄漏。排查顺序是先排除最近变更，再用数据定位，不要凭经验猜。

**性能监控怎么讲**：说清采集了什么、怎么告警、出问题怎么用。例如接口层用中间件记录耗时与状态码上报 Prometheus，按路由打标签；运行时用 `runtime/metrics` 或 `prometheus/client_golang` 暴露 goroutine 数、堆大小、GC 次数；关键依赖单独埋点（数据库、Redis、下游 RPC）；告警按分位延迟与错误率设阈值，并附上仪表盘链接。只答「接了 Prometheus」不够，要能讲出一次真实的排查过程。
