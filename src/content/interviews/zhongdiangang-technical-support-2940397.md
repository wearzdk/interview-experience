### 《参考解析》

**x86 与 Jetson 的部署差异**：x86 服务器通常配一张独立显卡，显存独立，功耗与散热不受限，开发机上就能直接构建 TensorRT engine；Jetson 是 ARM64 的 SoC，CPU、GPU、DLA 与编解码器共享同一块 LPDDR，属于统一内存架构，整机功耗被限制在几瓦到几十瓦，软件栈由 JetPack 统一提供，L4T 内核、CUDA、cuDNN 与 TensorRT 的版本互相绑定。由此有四条实际差别：一是交叉编译，板端程序要用 aarch64 工具链构建或直接在板上编译；二是 engine 与平台型号及 TensorRT 版本强绑定，必须在目标板或同型号同版本环境中生成；三是内存带宽与容量成为瓶颈，部署时应尽量零拷贝，减少 Host 与 Device 之间的往返；四是温度与功耗会触发降频，测性能前需用 nvpmodel 固定功耗模式、用 jetson_clocks 锁定频率，否则延迟数据无法复现。

**JetPack 版本的选择顺序**：按「模组型号、所需 TensorRT 与 CUDA 版本、外设与内核支持、稳定性」依次收敛。先在 Jetson Linux 发布说明里确认目标模组在支持列表内；再确认推理框架与算子对 TensorRT 版本的要求，已有的 engine 不能跨大版本复用；然后确认相机 sensor 驱动、PCIe 采集卡等外设在对应 BSP 上是否可用；量产设备优先选仍在维护的稳定版本，而不是最新版本。刷机用 SDK Manager 或 flash.sh，并保留与 BSP 一致的 kernel 源码，否则后续改设备树、加驱动会对不上版本。

**模型部署的优化层次**：图层面先做 ONNX 简化、常量折叠与算子融合（Conv+BN+激活），把框架特有算子换成 TensorRT 原生算子或写成 plugin，输入尺寸尽量固定，需要多尺寸时用 optimization profile。精度层面先上 FP16，多数视觉模型损失可以接受；再考虑 INT8，需要代表性校准集，按层做敏感度分析，把掉点严重的层回退到 FP16。结构层面是降低输入分辨率、换轻量主干、剪枝或蒸馏、必要时跳帧。运行时层面是增大 batch、开多流、用 DLA 卸载部分层、避免频繁同步与内存拷贝。最后用 trtexec 测各段延迟，用 tegrastats 观察功耗与温度，预热后取稳定值。

**Linux 内核移植的主要步骤**：取与 L4T 版本一致的 kernel 源码，用 tegra_defconfig 生成基础配置，按需打开或新增驱动；修改设备树，配置 pinmux、I2C、SPI、UART、CAN 等节点以及中断与 GPIO；用 aarch64 交叉工具链编译 Image、dtbs 与 modules 并安装模块；把 Image 与 dtb 打包进 boot.img，或用 extlinux.conf 指定启动项；刷机后从串口读启动日志，用 dmesg 确认设备树匹配（compatible 字符串）与驱动 probe 是否成功；最后做反复上下电与长时间压测。多数移植问题出在设备树与 pinmux，而不是驱动代码本身。

**客户问题无法复现时的处理**：第一步固化现场信息，包括软件与固件版本、JetPack 与 L4T 版本、完整日志与 dmesg、配置项、负载情况与复现步骤，最好提供一键采集脚本，减少来回追问。第二步缩小变量，用同一镜像换一台设备、换电源与线缆、换负载，对比正常与异常两组。第三步针对时序与并发类问题加日志埋点、放大压力、做故障注入。若仍无法复现，就把现象、已排除项与规避方案记录为已知问题，给出监控手段与升级路径，而不是让客户反复重试。
