### 《参考解析》

**协程的本质与结构化并发**：Kotlin 协程是编译器与标准库共同实现的用户态并发方案。`suspend` 函数在编译期被改写成带 `Continuation` 参数的状态机（CPS 变换），挂起时保存当前状态并返回挂起标记，恢复时通过 `resumeWith` 回到挂起点，因此挂起并不阻塞线程，切换开销远小于线程。调度由 `CoroutineDispatcher` 决定：`Dispatchers.Main` 走主线程消息队列，`IO` 用可弹性扩容的线程池，`Default` 面向 CPU 密集任务。更值得讲的是结构化并发：协程在 `CoroutineScope` 中启动，父 `Job` 管理子 `Job`，父取消会向下传播，父要等所有子协程结束才算完成；`viewModelScope`、`lifecycleScope` 把作用域绑定到生命周期，页面销毁即自动取消，这是避免协程泄漏的关键。落到实践可以说清并行请求的写法：用 `async` 同时发起两个请求、`awaitAll` 汇总，异常在其中任一处抛出时其余会被取消。

**协程的异常处理与「不影响主流程」**：`launch` 中未捕获的异常会先取消父协程，再交给 `CoroutineExceptionHandler`（未配置则落到线程的未捕获异常处理器）；`async` 的异常则保存在 `Deferred` 里，只在 `await` 时才抛出，两者行为不同，是常见追问点。要做到「一个任务出错不影响系统」，可以分层处理：用 `supervisorScope` 或 `SupervisorJob` 让某个子协程失败不取消兄弟协程；给启动协程的作用域配置 `CoroutineExceptionHandler` 做兜底记录；在协程体内 `try/catch` 捕获具体异常并上报。特别注意 `CancellationException` 是取消的正常信号，不能被普通 `catch` 吞掉，否则会破坏取消传播，需要捕获时先判断类型再重新抛出。工程上常把「单任务失败互不影响」放在 `supervisorScope` 内，把「整体失败必须一起回滚」放在 `coroutineScope` 内，主动讲出这个区别，比只背 API 名更能体现理解。

**Flow 的冷流特性与常用操作符**：Flow 是冷流，只有被收集时才执行，`emit` 是挂起函数，上游按下游的处理速度生产，天然具备背压能力。操作符可以按用途分类：创建（`flow {}`、`flowOf`、`asFlow`、`callbackFlow`）、转换（`map`、`filter`、`transform`、`flatMapConcat`、`flatMapMerge`、`flatMapLatest`）、节流与缓冲（`debounce`、`sample`、`conflate`、`buffer`）、组合（`zip`、`combine`）、异常与重试（`catch`、`retry`、`retryWhen`）、生命周期（`onStart`、`onCompletion`、`onEach`）。搜索联想是经典组合：`debounce` 去掉输入抖动、`flatMapLatest` 取消上一次未完成的请求、`catch` 兜住网络异常。还要能区分热流：`StateFlow` 有初始值、相同值不重复发射、适合承载 UI 状态；`SharedFlow` 无初始值、可配置重放次数与缓冲溢出策略，适合一次性事件。`collectLatest` 会在新值到来时取消上一次尚未处理完的收集，`flowOn` 只影响它上游的执行上下文，这两点常被拿来考细节。

**OkHttp 该怎么用，以及项目架构怎么讲**：`OkHttpClient` 内部持有连接池、调度线程池与缓存，应当做成单例长期复用；每个请求新建一个客户端会导致连接池与线程池反复创建，是典型的性能与泄漏问题。请求通过 `Request.Builder` 构造，同步用 `execute`、异步用 `enqueue`，回调运行在 OkHttp 的线程池上，更新 UI 必须切回主线程。拦截器分两类：应用拦截器（`addInterceptor`）每个请求只经过一次，适合统一加 token、改 header、打日志；网络拦截器（`addNetworkInterceptor`）在重定向与重试时每次都会经过，能看到真实的网络往返。Retrofit 只是在 OkHttp 之上做接口到 HTTP 的映射，底层仍是 OkHttp。常见追问包括超时设置（连接、读取、写入）、HTTPS 与证书校验、缓存策略、请求取消，以及在拦截器里读取响应体后未关闭导致的泄漏。架构题则要给出分层与数据流：表现层持有 UI 状态、数据层由 Repository 聚合网络与本地并作为单一数据源、层间通过接口依赖，配合单向数据流与依赖注入；能讲清为什么这样分（可测试、数据源可替换、状态可恢复）以及代价（模板代码、小项目容易过度设计），比背 MVVM、MVI 的名词更有说服力。

**从代码到 APK：编译流程与签名**：源码先由 `kotlinc`、`javac` 编译成 `.class`，再由 D8 转成 dex 字节码，release 构建走 R8 同时完成压缩、混淆与优化；资源由 aapt2 处理（compile 阶段生成中间文件，link 阶段生成 `resources.arsc` 与 R 类引用）；随后打包工具把 dex、资源、清单文件与 so 库合成 APK，`zipalign` 做四字节对齐以减少运行时的内存映射开销，最后由 `apksigner` 签名。签名方案要能分清版本：v1 是逐文件的 JAR 签名，v2 对整个 APK 签名、校验更快且能发现任何字节改动，v3 支持密钥轮换，v4 配合增量安装。debug 构建使用自动生成的调试签名，release 必须使用自己的 keystore；签名不一致会导致覆盖安装失败，手工改动 APK 内容会让 v2 校验直接失败，必须重新签名。至于 C++ 与 AOSP，回答时如实说明掌握程度即可：C++ 至少能讲清指针与引用、内存管理、编译链接过程；AOSP 能说出代码分层（内核、HAL、系统服务、框架、应用）与构建产物的大致形态，若岗位兼做系统开发，这些是后续要补的部分，坦诚比含糊更有效。
