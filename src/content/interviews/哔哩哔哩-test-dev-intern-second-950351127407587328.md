### 《参考解析》

**RAG 链路怎么讲**：按「离线入库 + 在线问答」两条线讲。离线侧做文档解析（PDF/Word/HTML 转文本，处理表格与多栏）、清洗、分块（按标题层级或固定长度加重叠，块太大召回不准、太小丢上下文）、向量化后写入向量库并保留元数据（来源、章节、权限）。在线侧对用户问题做改写与向量化，检索 top-k 片段，必要时加重排与关键词混合检索，再把片段拼进提示词交给模型生成，并要求模型标注引用。追问「分块之后怎么存储和检索」时，要能说出向量库选型、索引类型（HNSW/IVF）、相似度度量，以及按权限过滤发生在检索前还是检索后。

**三数之和的边界**：标准解法是排序后固定第一个数、剩下两数用双指针，整体 O(n²)。三个去重点必须都处理：外层跳过重复的第一个数、双指针命中后分别跳过重复的左右值、提前终止（第一个数大于 0 直接结束；最小和大于 0 或最大和小于 0 可剪枝）。面试现场写不出来时，先写暴力解保底没错，但要主动说明复杂度 O(n³) 与去重方式（用集合存排序后的三元组），再讲双指针思路——帖主正是靠这一步把过程分拿了回来。

**TCP 握手与挥手**：三次握手是为了双方都确认「自己的发送与接收能力正常」并同步初始序列号，两次无法让被动方确认主动方能收到自己的包。四次挥手是因为 TCP 是全双工，主动方发 FIN 只表示自己没有数据要发了，被动方可能还有数据要发，所以 ACK 与 FIN 分两次发；被动方发完剩余数据再发 FIN，主动方回 ACK 后进入 TIME_WAIT，等 2MSL 确保最后的 ACK 能到达并让旧连接的报文在网络中消散。

**Python 装饰器**：装饰器是接收函数并返回新函数的可调用对象，用来在不改动原函数的前提下增加日志、计时、缓存、鉴权、重试等横切逻辑，基于函数是一等对象与闭包实现。带参数的装饰器要多一层嵌套，`functools.wraps` 用来保留原函数的名字与文档。

**判断 MySQL 没走索引**：用 `EXPLAIN` 看 `type`（ALL 是全表扫描，index 是全索引扫描）、`key` 是否为 NULL、`rows` 扫描行数、`Extra` 里有没有 `Using filesort`/`Using temporary`。常见原因：条件列上用了函数或隐式类型转换、联合索引不满足最左前缀、`like '%x'` 前导通配、区分度太低优化器主动放弃、统计信息过期。排查顺序是先 `EXPLAIN` 确认，再看索引定义与数据分布，必要时 `ANALYZE TABLE` 或强制索引做对照。

**抢券测试方案**：按维度拆。功能：正常领取、重复领取拦截、库存为零、活动未开始/已结束、券的使用门槛与有效期。时间边界：7:59:59、8:00:00、9:59:59、10:00:00，以及服务器时区与客户端时间不一致。并发：同一用户并发请求（幂等）、多用户抢同一库存（超卖）、库存扣减与订单创建的事务一致性。多端：H5、Web、App 的入口与状态同步，弱网与重复点击。数据一致性：券记录、用户券包、库存三方对账。异常：支付/领取接口超时后的补偿、消息重复消费。

**「显示抢券成功但不可用」怎么排查**：先确认数据是否真的落库——查用户券包表有没有记录、事务是否提交、库存是否扣减成功；再核对券的状态与时间窗口（是否未到使用时间、是否已过期、是否限定了商品或门店）；然后查前后端状态是否同步（前端拿到的是缓存或乐观更新，服务端实际失败）；最后看异步链路（发券走消息队列时消费失败或延迟）。定位手段是对比同一用户的券包记录、领取流水与服务端日志，按「写入—状态—同步—异步」四段逐一排除。
