### 《参考解析》

**HTTPS 握手**：TLS 1.2 是四次交互——ClientHello（支持的套件、随机数、SNI），ServerHello（选定套件、随机数、证书链），客户端验证证书并生成预主密钥用服务器公钥加密发过去，双方用三个随机数导出会话密钥，之后 ChangeCipherSpec + Finished 互相确认。TLS 1.3 压到一次往返（1-RTT，会话恢复可 0-RTT），并把密钥交换改成 ECDHE（前向安全）。要能说清两件事：为什么用非对称加密交换对称密钥（非对称太慢，只用来解决密钥分发），以及为什么需要随机数（防重放）。

**证书校验与证书链**：客户端用内置的根 CA 公钥验证服务器证书上的签名，看签发者是否可信；服务器证书一般不是根 CA 直接签的，中间是「根证书 → 中间 CA → 服务器证书」的链，逐级验证签名直到根。除了签名，还要校验有效期、域名（SAN）、用途（KU/EKU）、是否被吊销（CRL/OCSP），以及链上每一级的签名算法是否可接受。

**TCP 流量控制**：靠滑动窗口。接收方在 ACK 里带 `rwnd`（接收窗口），告诉发送方自己还能收多少，发送方据此限制未确认数据量，避免把接收方缓冲区打爆。窗口为 0 时发送方启动持续计时器，定期发窗口探测，防止窗口更新包丢失导致双方死等。区别于拥塞控制：流量控制是端到端的接收能力约束，拥塞控制是对网络容量的探测。

**TIME_WAIT**：主动关闭连接的一方进入 TIME_WAIT，等 2MSL。所以客户端先关就是客户端 TIME_WAIT，服务端先关就是服务端——大量 TIME_WAIT 堆在服务端通常说明是服务端主动关闭（或短连接 + 服务端超时关闭）。它的作用是保证最后一个 ACK 能重传（否则对方重发的 FIN 会收到 RST），以及让旧连接的迷路报文在网络中消散，不会污染使用相同四元组的新连接。

**Redis 数据结构与跳表**：string、list、hash、set、zset，加上 bitmap、HyperLogLog、GEO、Stream。zset 的底层是跳表 + 字典：字典给「按成员查分数」O(1)，跳表给「按分数范围查」O(log n)。跳表用多级索引把链表查询从 O(n) 降到期望 O(log n)，实现比平衡树简单、范围查询天然有序，代价是空间换时间（平均每元素约 1.33 个指针）。

**MySQL 三种锁**：都在 InnoDB 的行锁范畴，且锁的是索引。记录锁（Record Lock）锁住某一条索引记录；间隙锁（Gap Lock）锁住两条记录之间的开区间，作用是阻止其他事务在间隙里插入，从而在 RR 隔离级别下防幻读；临键锁（Next-Key Lock）是「记录锁 + 前面的间隙」，锁住左开右闭区间，是 RR 下的默认加锁单位。要点：查询走唯一索引且精确命中时会退化为记录锁；没走索引的更新会锁全表（所有间隙都锁）；间隙锁只在 RR 及以上存在，RC 下没有。

**分表后按时间排序查**：这是本场最实际的一题。核心矛盾是「按 userid 分片，但查询按 date 排序」。可行方案按代价排序：一，如果查询总是带 userId，就在分片内查再排序，天然没问题；二，如果查询不带 userId（全局按时间取最新 N 条），分表上做不到高效，应该另建一个按时间维度组织的索引表或宽表（比如 `user_latest` 按日期分区，写入时同步），也就是「读模型按查询维度冗余一份」；三，用搜索引擎（ES）同步一份按时间排序的文档，查询走 ES；四，各分片各取 Top-N 再归并（只在 N 小、分片数少时可行，且要有覆盖索引避免回表）。要主动指出「分表键与排序键不一致」是这类问题的根因——设计分片键时就要把主要查询模式列出来，必要时做异构索引，而不是事后在分片间做归并。

**快排**：分治，选基准把数组分成「小于」和「大于」两段，递归。平均 O(n log n)，最坏 O(n²)（已排序数组 + 取首元素做基准），空间 O(log n) 递归栈。工程优化：三数取中或随机选基准避免最坏、小区间（小于十几）改用插入排序、三路划分处理大量重复元素、尾递归优化减少栈深度。要能当场写出并说清 partition 的边界条件（`while (i < j)` 里先动 j 还是先动 i 决定基准落点）。稳定性上快排不稳定，需要稳定就用归并。
