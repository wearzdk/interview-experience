### 《参考解析》

**DDoS 要按层讲，防护也要按层答。** 攻击面分四层：网络层是流量洪泛（UDP flood、ICMP flood）和反射放大（伪造源 IP 打 DNS/NTP/memcached，几百字节请求换几万字节响应）；传输层是 SYN flood（半连接队列占满）、ACK flood、连接耗尽；应用层是 CC 攻击（大量看似合法的请求打贵接口，比如登录、匹配、排行榜）和慢连接（slowloris）；游戏还有独有的一类——协议层攻击，伪造的 UDP 包直接打房间服，或者复用合法协议的畸形包触发解析开销。防护的核心思路是「把过滤点放到越前面越好」：上游用 Anycast 加流量清洗做容量吸收，传输层开 SYN cookie、缩短半连接超时、按源 IP 做新建连接速率限制，应用层做鉴权前置（连接建立的第一件事是校验 token，未通过不分配任何游戏对象）、接口级限流与熔断、七层人机校验。要能说出一个反直觉的点：清洗设备只能挡量和特征，挡不住「像真人的慢速 CC」，那类只能靠业务侧的配额（单账号单 IP 的操作频率、并发连接数上限）和成本不对称设计（让攻击者每发一个包付出的计算比我们多）。

单个恶意用户打满链路，解法是把「每用户配额 + 状态前置 + 无状态校验」显式化——游戏服最怕的不是带宽被占满，而是「一个连接触发的服务端工作量」没有上限：比如一个客户端能每秒发 1000 个移动包，每个包都触发一次 AOI 计算和广播，服务端 CPU 直接被一个人吃掉。工程做法是把资源分配显式化：连接级令牌桶（按包类型分桶，移动包和技能包配额不同，超限直接丢弃而不是排队，排队会把延迟传染给正常玩家）、单 IP/单账号的连接数与会话数上限、协议层固定长度与字段范围校验（长度不合法立刻断开，不进入反序列化）、鉴权通过前不分配任何内存和实体、以及把重逻辑（伤害结算、掉落）挪到通过校验之后。兜底要提：把这类异常流量计数打点，超过阈值自动把该 IP 或账号切到「只读/隔离」状态，而不是等运维发现 CPU 打满。

**unlikely 的本质是给编译器一个概率提示，让冷代码离开热路径。** 展开是 `__builtin_expect(expr, 0)`，C++20 起有标准写法 `[[unlikely]]`。它的作用有两层：一是静态分支预测提示，编译器据此决定分支的布局——把「大概率执行」的那条路径排成 fall-through（顺序执行、不跳转），把冷路径挪到函数尾部甚至单独的 `.text.unlikely` 段；二是代码局部性，热路径的指令被挤在连续的几段 cache line 里，i-cache 命中率更高、取指跳转更少，在长函数、错误处理代码很多的场景里收益明显（典型是解析器、协议处理、内核风格代码）。要讲的边界：它不是让分支变快，现代 CPU 的动态预测器在规律分支上比静态提示更准，所以收益主要体现在「冷热极度不均 + 热路径很长」的情况；用反了（把热路径标成 unlikely）会让布局变差，反而掉性能；而且不同编译器/优化等级下效果不一致，必须实测。

**lock_free 和 wait_free 的区别在「保证的强度」，不是「有没有锁」。** lock-free 指系统整体总能推进：任意时刻至少有一个线程能在有限步内完成操作，其他线程可能一直重试（活锁/饥饿在理论上允许）；wait-free 更强，要求每个线程都能在有限步内完成，与其它线程的快慢无关。所以 wait-free 是 lock-free 的子集，实现难度和代价都更高（通常要用原子读改写加协作式帮助机制，比如无锁队列里让慢线程帮快线程完成收尾）。基于 CAS 重试的队列是 lock-free 不是 wait-free——因为某个线程可能永远 CAS 失败。要顺带说清两个坑：ABA 问题（用带版本号的指针或 tagged pointer 解决）、内存序（`relaxed` 只保原子性，跨线程可见性要 `acquire/release` 或 `seq_cst`），以及回收难题（节点被摘除后不能立刻 delete，需要 hazard pointer、epoch 或引用计数）。

锁的选型同样要按「语义」而不是按名字列：互斥类：`std::mutex`（不可重入）、`std::recursive_mutex`（同线程可重入，一般说明设计有问题）、`std::timed_mutex`（带超时尝试）、`std::shared_mutex`（C++17，读写分离，读共享写独占）；自旋类：`std::atomic_flag` 自制的自旋锁、平台提供的 `pthread_spinlock`，适合临界区极短且不希望睡眠的场景；条件变量 `condition_variable` 不是锁，是配合 mutex 做等待通知；RAII 包装有 `lock_guard`、`unique_lock`、`scoped_lock`（C++17 一次锁多个，内部用死锁避免算法）。`lock_guard` 与 `unique_lock` 的差别就是「够用」和「灵活」：前者构造即锁、析构即解，不能手动解锁、不能延迟加锁、不能移动；后者支持延迟加锁（`defer_lock`）、手动 `lock/unlock`、带超时的 `try_lock_for`、可移动到函数外，代价是多存一个「是否持有」的状态和少量开销。选型口径：作用域内一把锁用完就走的用 `lock_guard`；需要条件变量（必须传 `unique_lock`）、需要中途解锁、需要超时或转移所有权时才用 `unique_lock`。死锁那题按四条件讲，再给工程解法：固定加锁顺序、用 `scoped_lock`/`std::lock` 一次性拿多把、缩小临界区、给锁加超时并记录持锁栈（线上定位死锁靠 `gdb` 的 `thread apply all bt` 或 `pstack` 看谁在等谁）。

**「保证一定踢掉」的答案是：服务端状态是唯一真相，断开连接只是副作用。** 优雅的做法分四步：一，把踢人做成一个带版本的状态变更（房间成员表里把该 uid 标记为 `kicked` 并递增 epoch），这样即使客户端还在发包，服务端在处理任何请求前都能看到 epoch 不匹配而拒绝；二，主动关闭连接（先发一条踢出通知再 `shutdown`，让客户端能区分「被踢」和「网络断」），并从所有广播列表、AOI 视野、匹配队列里摘除；三，写一条带 TTL 的拒绝重连记录（按账号而不是连接，否则换条连接就回来了），重连鉴权时先查它；四，跨服/跨进程场景下，房间可能不在网关所在进程，得通过中心服或消息总线广播这个状态变更，并且要幂等（重复踢不报错）。「一定」这个词的边界要主动说：网络分区时服务端无法证明客户端已收到，能保证的是「服务端不再为该用户提供服务」，客户端的表现只能是最终一致。加分项：踢人操作用异步队列串行化，避免和正在结算的战斗逻辑抢锁。

**二维数组的行列遍历，考的是 cache line 和预取。** C/C++ 是行主序，`a[i][j]` 的地址是 `base + (i * cols + j) * sizeof(T)`，按行遍历时内存访问是连续的：一次读入 64 字节的 cache line 就顺带拿到了后面十几个元素，硬件预取器也能识别这种步长为 1 的模式提前拉数据；按列遍历的步长是 `cols * 4` 字节，每次访问都落到不同 cache line，几乎每次都是 miss，还要额外消耗 TLB（跨页）。所以行遍历通常快几倍到十几倍，矩阵越大差距越明显（超过 LLC 容量后就是纯内存带宽和延迟的差距）。「速率相同」的追问要答出至少三种可能：数据规模太小，整个数组能装进 L1（此时第二次访问就已经在缓存里，列遍历的 miss 只在第一遍发生，甚至被编译器向量化抹平）；列数很少，一行不超过一个 cache line（64 字节 = 16 个 int），按列走两步还是同一行；编译器做了循环交换或分块（`-O3` 下的 interchange/blocking），或者用了 SIMD 把两种顺序都优化成连续访存；也可能是测量方法有问题（没关优化、没预热、计时粒度太粗、编译器把整个循环优化掉了）。32 位系统那一问要算：int 4 字节，一个 cache line 装 16 个，L1 通常 32KB，能装 8192 个 int，所以「整块能进 L1」对应的规模是 10^3~10^4 量级（比如 90×90 左右）；另一个口径是「一行不超过 16 个元素」对应列数是 10^1 量级。答出数量级再加一句「具体取决于 cache 大小和行宽，要用 perf 的 cache-miss 计数验证」。

**一万人的范围伤害，标准解法是空间划分 + 事件化。** 朴素做法对每个玩家遍历所有人算距离，是 10^8 次距离计算，按每 tick 20Hz 算就是每秒 20 亿次，服务端扛不住。正确做法是把空间切成均匀网格（格子边长取技能半径，1 米），每帧把玩家按坐标放进格子（O(n)），一次范围技能只需枚举覆盖到的 3×3 或 5×5 个格子里的玩家（局部密度 k 通常是个位数），总代价从 O(n²) 降到 O(n·k)。选择均匀网格而不是四叉树/kd-tree 的理由要说清：玩家分布相对均匀、对象每帧都在动、重建树的开销比查询收益还大；网格的插入删除都是 O(1)，缓存友好。进一步的优化：同一格子里多个技能命中同一批目标时合并结算（一次遍历算出总伤害），而不是每个技能各遍历一遍；伤害结算放到 tick 末统一应用，避免「边打边改血量」导致的顺序依赖；跨格边界的技能用「查询半径 + 格子边长」保证不漏（枚举范围向上取整）。

**持续多帧的技能，关键是把「每帧查询」换成「激活区间」。** 一帧的技能即时结算即可；持续十帧的技能如果每帧都重算范围，等于把一次查询放大十倍，而且玩家在移动时结果还会变。两种处理：一是「开始帧算一次影响集合，持续期内复用」，适合范围固定、判定不看位置的技能（比如以施法点为中心的AOE），代价是目标走出范围也不会掉——如果规则要求实时判定就不能用；二是「维护激活列表」，把正在生效的技能放进一个按剩余帧数排序的结构，每帧只处理还没结束的，进入/离开范围用格子做增量判断（只检查目标所在格是否在技能覆盖格集合里），这样每帧代价正比于「活跃技能数 × 局部目标数」而不是全部技能。还要处理叠加与去重：同一个技能对同一目标一帧只结算一次，用「技能实例 ID + 目标 ID」做去重键；结算顺序要稳定（按玩家 ID 排序），否则同帧互杀的结果不可复现。

再退一步，如果把判定从每帧降到每秒统计，就会立刻出现两个问题：一是漏判，持续一帧的技能如果恰好落在两次采样之间就完全不生效，表现为「技能放出去了没伤害」，而且这个 bug 是概率性的、极难复现；二是判定延迟，玩家看到特效和掉血之间差最多 1 秒，操作手感直接崩掉，PVP 里更是不可接受。优化的方向不是提高采样率（那就回到原点了），而是把「高频的判定」和「低频的统计」拆开：判定仍然按帧或按事件驱动（技能释放是个事件，不需要轮询），结算也走事件队列；只有统计类的工作（伤害报表、成就、排行榜、反作弊的聚合指标）才降频，并且用增量累计 + 定时落库，而不是每次重新扫全量。如果一定要做低频采样，就必须用「时间区间重叠」而不是「瞬时快照」：记录技能的起止帧，采样时判断区间是否与统计窗口相交，这样漏判只发生在窗口边界，可以用补帧修正；同时把采样周期和 tick 对齐（整数倍关系），避免抖动。

**这一场的题面全是「是什么 → 底层原理 → 边界/数量级」的三段式，答的时候别停在第一段。** unlikely 要能说到 i-cache 和 fall-through，二维数组要能算出 cache line 装几个 int，lock_free 要能说到 CAS 重试和内存回收，锁的题要能说出选型口径而不只是名字。游戏服务端这一侧还有一个隐含考点：所有优化都要回答「在 20Hz tick、1 万在线、单帧预算 50ms」这种预算下是否成立，脱离预算讲方案会被追问到崩。
