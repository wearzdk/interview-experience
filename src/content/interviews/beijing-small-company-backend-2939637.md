### 《参考解析》

**ES 的底层与优化**：Lucene 的倒排索引加段（segment）结构，写入先进内存 buffer 与 translog，refresh 时生成新的 segment 使其可被搜索（默认 1 秒），merge 时把小段合并成大段并真正删除标记删除的文档。优化的抓手是：写入侧用批量 `_bulk`、调大 `refresh_interval`、避免频繁更新（更新是「标记删除 + 新增」）；查询侧避免深分页，用 `scroll` 或 `search_after` 替代 `from + size`，因为后者要在每个分片上取 `from + size` 条再归并，越翻越贵；再配合合理的 mapping（`keyword` 与 `text` 分开、关闭不需要的字段、控制分片数）。

**深分页的替代方案**：`scroll` 适合一次性导出，会持有快照占用资源，不适合实时请求；`search_after` 用上一页最后一条的排序值作为游标，无状态、可实时，是现在的首选。两者的前提都是「有稳定且唯一的排序键」，否则翻页会重复或漏数据。

**MySQL 的四个隔离级别**：读未提交、读已提交、可重复读、串行化。默认是可重复读，它解决了不可重复读，并用间隙锁在很大程度上避免幻读。

**可重复读靠 MVCC 快照**：行上有隐藏的事务 ID 与回滚指针，undo log 串成版本链；事务第一次快照读时生成 ReadView，之后按「自己的修改可见、ReadView 创建前已提交的可见、之后提交的不可见」判断版本，于是同一事务内多次读结果一致。当前读（加锁读、更新、删除）不看快照，走行锁与间隙锁。

**索引与顺序查找**：InnoDB 用 B+ 树，非叶子节点只存键与指针，扇出大、树矮，一次查询的磁盘 IO 次数稳定在个位数；叶子节点按序双向链表相连，范围查询顺着链表扫即可。所谓「顺序找得快」要分清两层——B+ 树内部节点里存的是有序键，可以用二分定位到子页；叶子层的顺序排列让范围扫描和排序不用回表重组。另外聚簇索引的叶子直接存整行，二级索引叶子存主键、需要回表，覆盖索引能省掉这一次回表。

**RAG 的流程**：文档解析与切分（按标题层级与语义边界切、保留来源）、向量化（选 embedding 模型，必要时叠加关键词检索做混合召回）、写入向量库、查询时把问题向量化后召回 top-k、重排（cross-encoder 或规则）、拼装上下文并附出处、交给模型生成。工程上还要有「召回的阈值与兜底」：分数太低时明确告诉模型没有相关资料，而不是硬凑。

**MCP 与 function calling 的区别**：function calling 是模型侧的能力——你把工具的函数签名放进请求，模型输出「要调哪个函数、参数是什么」，执行与结果回传由你的应用完成。MCP 是协议层——它标准化了「客户端如何发现工具、如何调用、如何传资源与提示模板」，把工具提供方从应用里解耦出来，一个 MCP Server 可以被多个客户端复用。简单说：function calling 解决「模型怎么表达要调工具」，MCP 解决「工具怎么被标准化地接入」。两者不冲突，MCP Server 暴露的工具最终仍然以 function calling 的形式交给模型。

**HashMap 为什么线程不安全**：底层是数组加链表加红黑树（链表长度到 8 且容量到 64 时树化）。并发 `put` 时两个线程可能同时判断某个桶为空并各自写入，后写的覆盖先写的；扩容时迁移数据没有同步，JDK 7 的头插法在并发下会形成环形链表导致死循环，JDK 8 改成尾插避免了成环，但仍会丢数据、size 计数不准。并发场景用 `ConcurrentHashMap`，它用 CAS 加桶级 synchronized，只锁单个桶。

**内存泄漏与内存溢出**：泄漏是对象已经不再使用但仍被引用、GC 回收不掉，表现为老年代占用持续上涨、Full GC 后也降不下来；溢出是申请内存超出可用空间，直接抛 `OutOfMemoryError`。泄漏是原因，溢出是结果之一。排查用 `jmap` 导出堆、MAT 看支配树与 GC Root 引用链，常见源头是静态集合缓存、监听器未注销、ThreadLocal 未 `remove`、连接与流未关闭。

**G1 的 STW**：G1 把堆切成大小相等的 Region，年轻代回收与混合回收都会 STW，但停顿时间可通过 `MaxGCPauseMillis` 设定目标，回收时优先选「垃圾最多、收益最高」的 Region（Garbage First 的名字来源）。它用 Remembered Set 记录跨 Region 引用，避免全堆扫描；并发标记阶段与应用线程并行，只有初始标记、最终标记、筛选回收等阶段短暂停顿。要注意「可预测停顿」是目标而非保证，对象分配过快时仍会出现长停顿。

**离职原因与 AI 工具**：离职原因按事实讲，聚焦「想做什么」而不是「原公司哪里不好」。AI 工具的问题通常在看两件事——你是否真的把它用进工作流（读代码、写测试、查日志、生成脚手架），以及你是否知道它的边界（生成结果要审、敏感信息不外传）。
