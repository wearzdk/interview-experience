### 《参考解析》

**Agent 方向与 SRE 的结合点**：SRE 的日常是告警处置、容量评估、故障复盘，其中大量步骤是「查指标、比对基线、执行既定处置、记录结论」的固定流程，正好适合交给 Agent 编排工具完成。回答要落到具体能力：工具调用、长流程状态管理、失败重试与人工接管，而不是泛泛地说「Agent 是趋势」。

**模型对比与效果衡量**：对比要固定任务集与提示词，只替换模型，记录任务成功率、工具调用正确率（参数是否正确）、平均交互轮次、首字延迟与单次成本。效果衡量分三层：离线评测集上的端到端通过率、按失败类型分类的错误分布（选错工具、参数编造、循环调用、提前结束）、线上灰度中的人工接管率与平均处理时长。只看单轮回答质量的评分不足以说明 Agent 是否可用。

**重做会改的地方**：常见答案是评测先行——先建评测集与失败分类，再改提示词或换模型；把工具契约做稳定，参数校验与错误返回结构化；补可观测性，记录每一步的工具调用、耗时与 token；把流程状态持久化，支持中断恢复。

**字符串轮转**：按空格切分后逆序拼接，时间 O(n)、空间 O(n)（切分产生的列表与结果字符串）。O(1) 额外空间的做法是三次反转：整体反转得到 `CBA olleh`，再分别反转两个单词，得到 `ABC hello`。实现时原地交换字符，只占用常数个临时变量。

**Python 字符串为何不可变**：`str` 在 CPython 中是变长对象，创建后其缓冲区长度与内容都不再改变。不可变带来三个直接收益：可以安全地共享与驻留（相同字面量复用同一对象）、哈希值可以缓存从而作为字典键、多线程读取无需加锁。代价是任何「修改」都要新建对象，因此 O(1) 空间的原地轮转在 Python 层面无法实现，只能退到 `bytearray` 或列表上操作。

**虚拟内存**：每个进程拥有独立的虚拟地址空间，CPU 通过 MMU 查页表把虚拟地址翻译为物理地址，TLB 缓存近期映射。访问未映射或未载入的页触发缺页中断，由内核分配物理页并从磁盘或交换区载入；写时复制让 `fork` 后的父子进程共享只读页，直到任一方写入才复制。虚拟内存带来的好处是进程隔离、地址连续（便于链接与内存分配）、可按需换入换出，以及文件映射与共享内存。

**地址空间大小**：由架构的位数决定。32 位下用户态通常 3GB、内核 1GB；64 位下虽然地址宽度是 64 位，实际有效位受页表层级限制（x86-64 常见 48 位，开启五级页表后 57 位），因此单进程可寻址范围远小于 2 的 64 次方。回答时区分「寄存器宽度」「有效虚拟地址位数」与「物理内存上限」三个概念。

**数据库查询优化**：先用执行计划确认是否走索引、扫描行数与回表次数，再针对性地建联合索引或覆盖索引；避免在索引列上做函数运算和隐式类型转换，避免 `like '%x'` 前导通配；深分页改用游标（记住上一页的最大 id）；大结果集分页与导出放到从库或异步任务；热点数据加缓存并明确失效策略。索引不是越多越好：每个索引都带来写放大与存储开销，优化器在过多候选索引下也可能选错，低频列与选择性差的列不应单独建索引，联合索引要按最左匹配与实际查询模式设计。
