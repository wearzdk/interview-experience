### 《参考解析》

1. **channel 与 map / slice**：channel 底层是 `hchan`，环形缓冲区加发送、接收两个等待队列，收发在锁内完成，关闭后读返回零值、写 panic。map 是哈希桶数组，负载因子超阈值触发等量扩容、溢出桶过多触发增量搬迁，所以并发读写要加锁。slice 是「指针 + 长度 + 容量」的描述符，`append` 超容量时按约两倍（大切片约 1.25 倍）扩容并整体拷贝，这也是共享底层数组时容易踩坑的地方。

2. **GMP**：G 是 goroutine，M 是内核线程，P 是本地可运行队列和调度上下文。M 必须绑定 P 才能执行 G，P 的数量默认等于 CPU 核数。调度上靠 work stealing 平衡负载，遇到阻塞系统调用时 P 会被 hand off 给其他 M，网络 IO 则挂到 netpoller 上，靠 epoll 唤醒而不是占线程。

3. **GC 优化**：Go 用并发三色标记加混合写屏障，STW 只在标记开始和结束的极短阶段。看火焰图先分清楚 CPU 时间是花在 mutator 还是 GC worker 上，再对照 `GODEBUG=gctrace=1` 的 GC 周期、堆大小和辅助标记（mark assist）时间。常见手法是减少小对象分配、用 `sync.Pool` 复用、预分配切片容量、避免指针密集的大结构，把分配速率降下来比调 `GOGC` 更根本。

4. **每日温度**：维护一个存下标的单调递减栈，遍历时把栈顶所有比当前温度低的下标弹出并写入答案，当前下标入栈，整体 O(n)。

5. **slices 内存池**：按容量分档维护若干 `sync.Pool` 或分层空闲链表，取用时向上取整到合适档位，归还时按容量放回并清空元素避免逃逸引用；要防大对象长期占住池子，可以设上限，超大切片直接交给 GC。

6. **网络 IO 高性能**：DMA 让设备直接访存，省掉 CPU 逐字节搬运；DPDK 用轮询模式驱动加用户态协议栈绕过内核，省掉中断和拷贝；Netfilter 是内核的包过滤框架，在 hook 点上做 NAT、过滤和连接跟踪。三者组合起来就是「少拷贝、少中断、少上下文切换」。

7. **Kafka**：分区加副本的架构，Controller 管元数据，消费组靠 rebalance 分配分区。性能来自顺序写日志、页缓存、零拷贝（sendfile）、批量发送与压缩、分区并行。追问时要点出「Kafka 的吞吐不是靠快，是靠把随机写变成顺序写」。

8. **列存与行存**：行存按行连续存放，适合点查、事务和整行更新；列存按列压缩存放，同列数据类型一致、压缩率高，做聚合和扫描时只读需要的列，适合 OLAP。代价是单行写入和更新昂贵，通常配合批量导入和排序键。

9. **Redis 数据结构**：string 是 SDS；list 用 quicklist（listpack 组成的双向链表）；hash 和 zset 小数据量用 listpack，大了转 dict 和 skiplist；set 用 intset 或 dict。要讲清「编码随规模切换」这件事，它直接决定了内存和操作复杂度。

10. **单词拆分**：`dp[i]` 表示前 i 个字符能否被拼出，枚举切分点 j，`dp[i] = dp[j] && words.contains(s[j:i])`，用哈希集合查词，复杂度 O(n²) 时间。

11. **无法实现的需求**：先确认「无法实现」是技术上做不到，还是当前资源与排期做不到。技术上做不到就给替代方案和边界；资源问题就拆出最小可交付版本，把依赖和风险写清楚，让对方在几个方案里选，而不是直接回绝。

12. **需求频繁变动**：把变更显性化——冻结当期范围、变更走评审、评估对排期的影响并同步给相关方，用原型和验收标准提前对齐，减少「做完了才发现理解不一致」的返工。

13. **排期管理**：按依赖关系排出关键路径，把不确定的部分拆成可验证的小里程碑并留缓冲，风险项提前暴露，定期对齐进度而不是最后一天才报延期。
