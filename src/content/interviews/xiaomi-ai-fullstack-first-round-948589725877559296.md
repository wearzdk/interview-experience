### 《参考解析》

**Redis 幂等的正确姿势是先想清「幂等窗口」有多长。** 用 `SET key value NX EX ttl` 抢占，处理完成后删除 key，这套写法的漏洞在删除时机：如果处理耗时超过 TTL，锁已过期，第二个请求会重新拿到锁并重复执行。两个方向各有代价——处理完比对 value 再用 Lua 删除，能避免误删别人的锁，但依赖 TTL 估算大于最大处理时间；不删除、让 TTL 自然过期，则窗口由 TTL 决定，代价是残留 key 占用内存、且真实业务窗口被拉长。工程上更稳妥的是把幂等记录落到数据库唯一约束或状态机（同一业务单号只允许一次状态跃迁），Redis 只做加速；删除动作本身不应成为幂等语义的组成部分。

**Agent 的停止条件要当成一套降级策略，而不是一个 if。** 至少四层：模型给出终止信号（stop token 或结构化 finished 字段）；状态机判定目标条件已满足（必需字段齐全、工具调用成功）；预算耗尽（最大轮次、token、时间）；外部强制中断（用户取消、超时）。关键在输出语义：每一层停止都要映射到明确的结果状态，例如「已完成」「部分完成（缺哪些信息）」「未能完成（原因）」，不能让预算耗尽伪装成正常结束。前端要能展示「未完成」并给出继续或补充信息的入口，否则用户会把半成品当结论。

**线程池参数要由下游容量反推。** 队列无界时最大线程数永远用不上，任务会一直排队直至内存或超时；队列有界加拒绝策略才能形成背压。线程数估算的经典公式是 `线程数 ≈ QPS × 平均 RT`（含等待），CPU 密集型约为核数 + 1，IO 密集型按等待时间与计算时间之比放大，例如 RT 中 90% 在等下游，线程数可以到核数的数倍。真正的约束是下游能承受的并发：数据库连接数、下游服务的连接池与限流阈值。回答时把「参数怎么算」和「上限由谁决定」分开讲，才算完整。

**上下文压缩的评估要分层，不能只看最终答案。** 事实类信息可以用抽取式比对（压缩前后的实体、数值、时间、约束条件是否保留）；指令类信息用规则或断言校验（必须遵守的格式、禁止的动作）；推理类只能看结果，但要额外标注依据链是否完整——即答案引用的证据是否仍在上下文中。更实用的做法是构造「只有压缩后上下文才能答对」的探针问题集，逐条回归；同时保留原始上下文做对照实验，观察加入干扰后错误率的变化。

**Skill 与 workflow 的分界可以按「谁决定下一步」来划。** workflow 把步骤写死在代码里，可预测、可测试，但遇到分支多的场景会膨胀成状态机；Skill 把流程写成模型可读的文档，由模型决定何时调用哪一步，灵活但不确定。合理的边界是：确定性逻辑（鉴权、参数校验、状态流转、幂等）留在代码里，判断性逻辑（要不要查资料、查哪个源、如何组织答案）交给 Skill。判断一个 Skill 写得好不好，看三件事：模型能否在没看示例的情况下选对工具、失败时是否有明确的回退路径、以及是否有可回归的评测集。

**手撕重试器的三个坑正好对应三条要求。** 抖动要加在退避区间上（`sleep = random(0, base × 2^n)` 或 `base × 2^n × (1 + random())`），加在固定值上等于没加；只对可重试错误重试（网络超时、5xx、限流），参数校验失败、业务拒绝不重试；幂等键必须在首次调用时生成并在整个重试链中复用，每次重新生成等于没有幂等。此外要有总时长上限与并发上限，否则下游故障时重试会把流量放大数倍——作者复盘时压测发现下游 500 时重试量放大四倍，正是缺了这两条。
