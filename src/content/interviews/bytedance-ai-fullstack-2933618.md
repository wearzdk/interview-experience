### 《参考解析》

**指标题必须先说清分子分母，再说为什么要监控**。告警归属率这类指标的隐含定义通常是「归属于某个责任方的告警中，被该责任方认可的比例」，分子是「被认可归属的告警数」，分母是「所有已归属的告警数」。面试官追问「怎样才算归属正确」，答案是「责任方复核后确认为其服务导致的」，而不是「我们系统算出来的」——这两者的差别正是这个指标的价值所在，它衡量的是归属算法的准确度而不是告警量。为什么要对这一节点监控：告警如果归错人，落地页会推给不相关的人，响应延迟上升、且会消耗信任，长期下来告警就没人看了。

**分级治理要能讲出「机制」而不是「我人工筛了」**。常见做法是按「影响面 × 紧急度」两维定级，再为每一级绑定不同的处理动作（P0 自动拉起、P1 进值班队列、P2 只归档）；收敛则是去找高噪音的规则做合并与降噪（同一根因的告警聚合成一条、抖动抑制、历史基线判断）。面试官问「人工看还是有机制」，是在确认你有没有把一次性的工作沉淀成系统。

**上传成功率提升的叙述要有归因**。典型拆解：失败原因分布（网络超时、服务端 5xx、鉴权过期、文件过大、客户端崩溃）→ 针对占比最高的那一类做改动 → 改动用成功率曲线验证。凭证（通常是临时上传凭证或 STS token）的作用是不把长期密钥放到客户端，同时能对单次上传做权限和时效限制；引入凭证后常见的坑是凭证过期导致的大文件上传失败，解法是在过期前刷新或分片续传。

**iOS 热修这题要给出可行与不可行的边界**。下发可执行代码在 App Store 的规则下是受限的（热更新可执行代码通常不被允许），合规的做法是下发配置、模板、DSL、资源包，由已安装的二进制解释执行。所以「不升级版本推送代码改动」这个需求，正确的答法是先问清改动属于哪一类：文案与配置走配置下发；页面结构变化走模板或 JSON 描述；逻辑变化受限于规则只能走发版。技术上的候选方案有 JSPatch（已因合规问题被弃用）、React Native/Weex 这类动态化容器、以及自研的 DSL 解释器——选哪个取决于团队已有的技术栈，而不是纯技术优劣。

**断点续传用 HTTP Range**。`Range: bytes=<start>-` 是请求头，服务端返回 `206 Partial Content` 并带 `Content-Range`；客户端在上传前先查询已上传的分片（服务端记录或本地记录），只发送未完成的部分。传 2.5M 时如果服务端支持 Range，就不必从头传——它可以从断点开始。除了 Range，相关的还有 `Content-Length`、`ETag`（用于校验分片是否与之前一致）、以及分片上传协议里每个 part 的 ETag 校验。

**AI Coding 的可靠性靠流程而不是靠模型自觉**。可讲的抓手：改动前先让它读相关代码并给出方案（而不是直接改）、每次改动限制范围（一次一个模块）、生成后立刻跑类型检查与测试、用 diff 视角而不是逐行阅读来理解改动、以及用 git 保证随时可回退。生成上万行代码看不完，解法不是硬看，而是让范围变小——如果一次生成上万行，说明任务拆分本身就失败了。

**「改坏了其他模块怎么办」的答案是可观测与隔离**：靠测试覆盖（尤其是有回归测试的公共模块）、靠类型系统在编译期拦住接口不匹配、靠代码所有者的 review 拦住语义变化。个人集群上测试则是先在本地或沙箱跑一遍，用 mock 替掉外部依赖。

**死锁四条件与检测算法**：互斥、持有并等待、不可剥夺、循环等待。检测的本质是找环：把「谁在等谁」建成有向图（资源分配图，或简化成线程等待图），跑 DFS 找环、或者用拓扑排序看是否能把所有节点排完（排不完说明有环）。工程上要注意的是采样的时机和开销——每次加锁都记录等待关系成本很高，常见折中是周期性采样（比如每隔一段时间抓取所有线程的调用栈与锁持有状态）或者在超时未获取到锁时上报。

**回溯加剪枝**：先写清递归的「选择、路径、结束条件」三要素，剪枝的判据通常是「当前路径已经不可能优于已知最优解」或「已经违反约束」。这题的评分点是能不能说明剪枝为什么正确、而不是把模板背出来。
