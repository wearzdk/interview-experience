### 《参考解析》

**Claude Code 二开要讲清「改了哪一层」**：这类 CLI Agent 的结构大致分四层——入口与交互（REPL、斜杠命令、权限确认）、模型调用与提示组装（system prompt、工具表、消息历史）、工具执行（文件读写、搜索、shell、子 Agent 派生）、状态与持久化（会话存储、配置、记忆文件）。二开的常见方向是加工具、改提示与规则文件、加钩子（pre/post tool use 做校验与审计）、改权限模型、接自有模型渠道。回答时按「问题 → 改哪一层 → 效果怎么验证」组织，只说「我改了 prompt」会被追问到底改了什么、为什么原版不行。

**评测集与 goal loop 的测法**：goal loop 指 Agent 反复「执行—观察—修正」直到目标达成的循环，测它要拆成三个可量化的量：达成率（在 N 个任务里有多少个最终状态满足断言）、轮次效率（平均用了几轮、是否出现原地打转）、成本（token 与工具调用次数）。评测集要覆盖任务类型（单文件修改、跨文件重构、需要跑测试验证的修复、需要检索的问答）与难度分层，每个任务配一个可程序化判定的验收条件（跑测试、比对文件、检查输出结构），而不是让模型自评。goal loop 特有的失败模式要单独建用例：提前宣布完成、反复修改同一处、忽略测试失败、把「看起来对」当成「验证过」。测出来的指标要看分布而不只看均值，并保留失败样本做人工复盘。

**多 worker 协调是这道面的分水岭**：面试官的追问方向是「异步并发下的数据一致性与 edit 覆写」，也就是说，真正难的不是「任务怎么分配」，而是多个 worker 同时对同一份代码库动手时的冲突。可答的机制有四类。① 任务分配与依赖：用 DAG 描述子任务，无依赖的并行、有依赖的串行，分配时按文件或目录做亲和性划分，避免两个 worker 碰同一片区域。② 隔离：每个 worker 在独立的 worktree 或沙箱里改，结束再合并，合并冲突交给上层裁决而不是让 worker 互相覆盖。③ 并发控制：对文件加乐观锁（读时记版本号，写时校验版本，冲突则重读重做），或对关键资源用租约。④ 一致性与幂等：工具调用要可重放，写操作带幂等键；结果汇总时以「最后验证通过的状态」为准，而不是「最后写入者」。还要讲失败处理：某个 worker 崩溃或超时，它的任务要能被重新领取，已产生的半成品要能回滚。答完机制再补一句度量——冲突率、重试率、合并失败率，这些是判断协调策略是否有效的指标。

**四层记忆压缩的设计意图**：长会话的上下文有限，压缩的目标是在有限预算里保住「继续干活需要的信息」。分层通常按「信息的新鲜度与稳定性」切：最近若干轮保留原文（保证局部连贯）、较早的对话压成结构化摘要（保留决策与结论、丢弃过程）、再往前的会话压成任务级摘要（目标、已完成、未决问题）、最外层是跨会话的长期记忆（项目约定、用户偏好、踩过的坑，落在规则文件或记忆库里）。触发点是 harness 实现的，不是模型主动——由 token 用量阈值、轮次阈值或工具调用次数触发，因为让模型自己判断「该压缩了」既不稳定也无法保证预算。每层的设计理由要对上它的读者：最近原文给模型看细节，摘要给模型看决策，长期记忆给模型的下一场会话看约束。讲清「压缩会丢什么、怎么降低丢失代价」（例如保留文件路径与错误原文、把结论与依据分开存）比背层数更加分。

**对 harness 的理解**：harness 是模型之外的执行骨架——负责把用户意图变成一轮轮的模型调用，组装提示与工具表，执行工具并把结果回填，管理上下文与压缩，处理权限与沙箱，记录轨迹与成本，以及在失败时重试或换策略。一句话概括：模型决定「做什么」，harness 决定「能做什么、做完怎么验证、失败了怎么办」。面试官问这题是在判断你是否理解「Agent 的能力上限很大程度由 harness 决定」，答的时候举一个具体例子（例如工具返回被截断导致模型反复重试，属于 harness 的问题而不是模型的问题）会更有说服力。
