### 《参考解析》

**Python 字典是开放寻址的哈希表**：紧凑布局（一个索引数组指向 entries 数组），3.6 起保证插入顺序；冲突用探测（CPython 用扰动序列的伪随机探测），装载因子超过 2/3 就扩容（容量按 2 的幂增长，`resize` 时重排）；key 必须可哈希（有 `__hash__` 与 `__eq__`），平均 O(1) 查找，最坏 O(n)。

**堆与栈**：栈由系统自动管理、存函数调用帧与局部变量、大小固定（几 MB）、分配释放是移动栈指针、连续且 cache 友好；堆由分配器管理、大小受限于可用内存、分配需要查找空闲块、容易碎片化、跨线程要加锁。Python 的对象都在堆上、变量名只是引用，这点答出来能体现你分得清语言层与运行时层。

**聚簇索引**把数据行存在索引叶子节点上（InnoDB 的主键索引），一张表只有一个，按主键顺序物理排列，范围查询快；**非聚簇索引**叶子只存索引列 + 主键（或称行指针），查非索引列要回表。MyISAM 全是非聚簇（叶子存行地址）。

**Agent 崩溃后重复点击那题是幂等设计题**，答案要落到「状态机 + 幂等键」：用户每次确认带一个 `requestId`（或 `conversationId + stepId`），服务端把任务状态持久化（`PENDING/RUNNING/DONE/FAILED`）并记录输出；恢复时先按 `requestId` 查任务，已 DONE 就直接返回结果、RUNNING 就订阅或返回「处理中」、FAILED 才允许重试；真正的副作用（下单、发消息、写库）必须带唯一键（数据库唯一索引或 Redis `SETNX`），保证「执行多次 = 执行一次」。再补一句「用 outbox / 本地消息表把副作用与状态变更放在同一事务里」，就完整了。

**节点调错工具**：短期靠工具描述写清楚（何时该用、参数含义、反例）、名字不与相似工具混淆、给模型一个「先查再调」的中间步骤；执行层做参数校验（schema 校验、必填与取值域），错了把错误原文回给模型让它自我纠正，同时限制同一步的重试次数；长期靠失败样本回流成评测集，用评测驱动提示词与工具集的调整。

**vibe coding 的问题**最能体现经验：模型会自信地编造不存在的 API、大改时不自知地破坏已有约定、绕过错误而不是修复、测试写得过于宽松导致假绿。应对是「小步提交 + 每次改动都要能跑起来 + 关键路径自己 review diff + 让它先写失败测试」。
