### 《参考解析》

**用 ZSet 做延迟队列的本质是「把到期时间当 score」**：投递时 `ZADD delay_set <executeAt> <taskId>`，消费端用一个轮询线程 `ZRANGEBYSCORE ... 0 now LIMIT 0 N` 取出到期任务，取到后用 Lua 或 `ZREM` 的返回值做原子抢占，保证多实例下只有一个消费者执行。它的优势是实现简单、延迟精度由轮询间隔决定、能按时间排序；代价是轮询有开销、任务多时占内存、没有 Kafka 那样的持久化与回溯能力。选它的场景通常是「延迟精度要求不高、任务量中等、已经依赖 Redis」；如果要强可靠、要重放、要削峰，就该上 Kafka 或专门的时间轮/延迟消息中间件。

**延迟队列的一致性靠「状态机 + 补偿」**：任务要有明确状态（待投递、已投递、已消费、失败），消费端先落库改状态再执行业务，用业务唯一键做幂等；执行失败的进重试队列并指数退避，超过上限进死信并告警；还要有一个扫描任务，定期把「已投递但长时间未消费」的任务重新投出去。只靠 ZSet 单点做不到这点，补偿与对账才是可靠性的主力。

**HashMap 的两个常考细节**：put 流程是「算 hash（高 16 位异或低 16 位扰动）→ 定位桶 → 桶空直接放 → 桶是链表则遍历比较 hash 与 equals，尾插 → 链表长度到 8 且数组长度到 64 转红黑树（否则先扩容）→ 元素数超阈值扩容 rehash」。为什么是 8 和 64：8 是在泊松分布下链表长度达到 8 的概率极低（约千万分之六），到时说明哈希质量或容量有问题，转红黑树把查询从 O(n) 降到 O(log n)；容量到 64 之前优先扩容，是因为扩容能真正打散冲突，比转树更划算。

**ConcurrentHashMap 读不加锁靠的是 volatile + 节点不可变**：JDK 8 用「CAS 插入空桶 + synchronized 锁桶首节点」写，读操作只读 volatile 的 table 与节点的 val/next，不加锁；扩容用 ForwardingNode 做多线程协同迁移。所以读是弱一致的——能看到已经完成的写，但不保证看到正在进行的写，这在绝大多数缓存/计数场景可接受。

**缓存击穿的三种解法要分清场景**：击穿是「热点 key 过期瞬间大量请求打到库」，解法是互斥重建（分布式锁，只让一个请求回源，其余等待）、逻辑过期（不设 TTL，异步刷新）、或热点永不过期 + 后台更新；穿透是「查不存在的数据」，用布隆过滤器或空值缓存；雪崩是「大量 key 同时过期或 Redis 挂了」，用过期的随机抖动、多级缓存、熔断降级。

**Kafka 的「不丢」要三段都成立**：生产端 `acks=all` + 重试 + 幂等 producer； broker 端 `replication.factor >= 3`、`min.insync.replicas >= 2`、关闭 `unclean.leader.election`；消费端关闭自动提交、处理完再手动提交 offset。重复消费无法完全避免（至少一次语义），所以业务侧必须幂等：用业务唯一键 + 唯一索引/去重表，或状态机校验（已处理过的状态直接跳过）。

**线程池的执行流程与异常处理**：核心线程未满则新建核心线程；满了进队列；队列满则扩到最大线程数；再满就走拒绝策略（Abort、CallerRuns、Discard、DiscardOldest，或自定义）。`execute` 抛出的异常会被未捕获异常处理器接住并让线程退出重建；`submit` 把异常包在 Future 里，不调用 `get()` 就永远看不到——这是线上「任务静默失败」的常见原因，所以要么用 execute，要么在任务内部 try/catch 并打日志。

**Agent 与 LLM 的区别在「有没有行动闭环」**：LLM 是「输入文本输出文本」，Agent 在模型外面加了目标、规划、工具调用、记忆和终止条件，能读文件、调接口、改状态并根据结果调整下一步。核心组成可以概括为：模型（决策）、工具（行动）、记忆（状态）、编排循环（何时继续、何时停）、以及护栏（权限、预算、审计）。

**function calling、skills、MCP 是三层的不同东西**：function calling 是模型输出结构化调用意图的协议能力；skills 是把「一类任务的步骤与知识」封装成可复用的能力包（提示词 + 脚本 + 资源）；MCP 是把外部工具与数据源以统一协议暴露给任意客户端的标准接口。前者是模型能力，中者是任务封装，后者是集成协议。

**生产级 Agent 的安全设计要覆盖五面**：权限（最小权限、按工具而非按人授权、危险操作二次确认）、隔离（每个会话独立工作目录与上下文，禁止跨会话读数据）、输入（提示注入防护，外部内容不被当指令）、输出（敏感信息脱敏、代码执行沙箱）、可观测（每次工具调用留痕、成本与步数上限、失败可回放）。高并发与上游波动的应对是：队列 + 并发上限 + 超时 + 熔断 + 降级到更小模型或纯检索答案 + 幂等重试。

**一句话两个任务的处理方式**：先做意图拆分（让模型输出结构化的任务列表），再判断依赖关系——无依赖的并行执行，有依赖的串行编排；执行完做结果合并。关键是给每个子任务独立的上下文与预算，避免一个任务失败拖垮全部，并在回复里说清哪部分完成、哪部分没完成。
