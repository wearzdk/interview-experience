### 《面试题目》

1. 讲一个你负责的项目，优化前后的 QPS 和 RT 分别是多少？怎么测的？
2. 当时的瓶颈在哪里？怎么定位到是数据库、缓存还是代码逻辑？
3. 为什么选 Redis 而不是本地缓存？两者的取舍是什么？
4. 如果让你重做这个项目，你会怎么改？
5. 接口 RT 突然从 50ms 涨到 2s，你的排查思路是什么？
6. 线上 CPU 使用率打到 100%，怎么定位？
7. 缓存与数据库不一致怎么处理？延迟双删解决什么问题，又没解决什么？
8. 消息重复消费怎么保证幂等？消息顺序性怎么保证？
9. 限流、熔断、降级分别解决什么问题？你们怎么落地？
10. HashMap 的扩容流程和树化条件是什么？
11. AQS 的原理是什么？ReentrantLock 的公平与非公平体现在哪？
12. 线程池的 execute 流程是怎样的？
13. Spring 如何解决循环依赖？三级缓存分别存什么？
14. Java 21 的虚拟线程适合什么场景？和线程池相比资源模型有什么不同？

### 《参考解析》

**项目深挖的关键是「数字有口径、因果有链路」。** 面试官问 QPS 和 RT，实际在验证三件事：你有没有真的压测过、知不知道数字怎么来的、优化收益是否归因正确。回答时给出口径（并发数、压测工具、数据量、硬件配置）、基线（优化前）与结果（优化后），并说明瓶颈定位过程：先看监控（CPU、GC、连接池、慢查询、缓存命中率），再用火焰图或链路追踪定位到具体方法。常见的瓶颈是数据库连接池过小、慢 SQL 缺索引、缓存击穿、锁竞争、序列化开销，每一类都有对应的证据。

**为什么用 Redis 而不是本地缓存**：本地缓存访问快、无网络开销，但多实例之间不一致、容量受堆内存限制、重启即失效；Redis 共享、容量大、有丰富的数据结构，但多一次网络往返，还要考虑可用性。实际项目常是两级缓存：本地缓存扛热点、Redis 做共享层，代价是一致性维护更复杂。回答时把「数据一致性要求、热点集中度、可接受的内存成本」三个变量讲清楚。

**接口 RT 飙高的排查**：先分层定位——入口层（网关、负载均衡）看流量与错误率，应用层看线程池与 GC，存储层看慢查询与连接池，下游看超时与重试。常用手段：看 RT 分位数而不是平均值、对比同时段的其他接口、查最近的发布与配置变更、看是否有流量突增或热点 key、用 Arthas 的 `trace` / `profiler` 抓耗时。结论要落到具体原因，比如「某条 SQL 在数据量增长后走了全表扫描」而不是「数据库慢」。

**CPU 100%**：先用 `top -Hp` 找到占用的线程，转成十六进制后 `jstack` 查栈，常见原因是死循环、频繁 Full GC、正则回溯、序列化大对象、锁自旋。若是 GC 引起，再看 `jstat` 与 GC 日志，区分内存泄漏与分配过快。回答时给出「定位—验证—修复—回归」的完整链路。

**缓存一致性**：Cache Aside 是主流：读先查缓存、未命中查库回填；写先更新数据库再删除缓存。删除失败会不一致，于是有重试、消息补偿、延迟双删（写完库延迟一段时间再删一次，覆盖并发读回填的旧值）。延迟双删只能降低概率，不能保证强一致；强一致要靠分布式锁、读主库、或让缓存只存不可变数据。面试官常追问「先删缓存再写库行不行」——在并发读下更容易脏，通常不推荐。

**消息重复与顺序**：重复消费靠幂等解决——业务唯一键 + 去重表、状态机（只有合法状态迁移才执行）、或 Redis 的 `setnx` 占位。顺序性要求同一业务键的消息进同一分区（Kafka 的 partition key、RocketMQ 的顺序队列），消费端单线程处理该分区；跨分区的全局顺序代价很高，通常不需要。

**限流、熔断、降级**：限流控制入口速率（令牌桶、滑动窗口、Sentinel 的 QPS 限流），熔断在下游持续失败时快速失败、避免雪崩（失败率阈值 + 半开探测），降级是在资源不足时关闭非核心功能、返回兜底结果。三者解决的是不同层面的问题，不能互相替代。

**HashMap**：默认容量 16、负载因子 0.75，元素数超过阈值（容量 × 0.75）扩容为两倍，扩容时重新分配桶；JDK 8 起链表长度到 8 且容量不小于 64 时转红黑树，退化到 6 时转回链表。扩容采用高低位拆分，避免重新计算 hash。追问常落在「为什么是 8」「为什么容量是 2 的幂」「为什么线程不安全」。

**AQS**：用一个 `volatile int state` 表示同步状态，加锁失败的线程进入 CLH 变体的双向队列并 `LockSupport.park`，释放时唤醒后继。公平锁在获取时先检查队列是否有前驱，非公平锁直接 CAS 抢一次，抢不到再排队——这就是非公平吞吐更高但可能饥饿的原因。

**Spring 循环依赖**：三级缓存分别是 `singletonObjects`（成品）、`earlySingletonObjects`（提前暴露的早期引用）、`singletonFactories`（生成早期引用的工厂，用于 AOP 代理）。创建 A 时把工厂放入三级缓存，注入 B 时 B 需要 A，就从三级缓存拿到早期引用（必要时生成代理）放入二级缓存，B 创建完成后 A 继续完成初始化。只能解决单例的 setter / 字段注入循环依赖，构造器注入和原型作用域的循环依赖解决不了。

**虚拟线程**：由 JVM 调度的轻量线程，阻塞时自动让出载体线程，适合大量 IO 阻塞、并发连接数高的场景；它不适合 CPU 密集型任务，也不能解决下游容量不足的问题。和线程池的区别在于不再需要「池化」来复用昂贵线程，但连接池、限流这些资源约束仍然存在。回答时说明适用边界，比背概念更加分。
