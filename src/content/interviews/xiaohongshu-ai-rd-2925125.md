### 《参考解析》

**Agent 采集被质疑「一个个很麻烦」，要把「分类接入」讲成架构而不是工作量。** 面试官说「这么多 Agent 一个个很麻烦」，他真正在问的是接入成本随 Agent 数量怎么增长。稳妥的答法是把采集层拆成两层：下层是统一的埋点协议（一次调用上报什么字段、trace/span/parent 关系、token 与耗时、工具入参与结果摘要都定死），上层才是每种 Agent 框架的适配器。适配器只做「把框架自己的回调翻译成统一协议」这一件事，所以新增一个 Agent 框架时改的是一个薄薄的 adapter，而不是重写采集逻辑。规范协议的价值就在这里——它把 N 个 Agent × M 个采集维度的乘法，压成了 N 个 adapter 加一份协议。被贬低时不用急着反驳，把「不加协议会怎样」讲清楚：字段各写各的、trace 断链、统计口径不统一，最后连成功率都算不出来。如果框架本身支持 OpenTelemetry 这类标准，就直接复用语义约定（GenAI semantic conventions），少造一套私有格式。

**观测平台的查询优化，要落到具体手段而不是「加了索引」。** 观测数据是典型的写多读少、时间序列、基数高的数据：写入侧通常按批缓冲再落列式存储，避免一条 span 一次写；查询侧的核心是「先收敛时间范围与过滤条件，再取明细」。可以按这个顺序讲：一是分区与排序键，按天甚至按小时分区、按 trace_id 或时间戳排序，让范围扫描只碰需要的片段；二是预聚合，把 QPS、P95、错误率这类看板指标离线按分钟预计算，看板只查聚合表，不做到明细表的全量扫描；三是索引策略，对高频过滤字段（服务名、模型、状态码）建索引，但不要给高基数字段（trace_id）建稀疏索引；四是采样，明细查询走采样数据、问题定位再按 trace_id 精确回捞；五是查询改写，把「模糊搜索 + 排序 + 分页」这类慢查询改成先按时间过滤再走游标分页，避免大 offset。回答时最好带一个「优化前 P95 多少、优化后多少」的数字，哪怕量级，也比只报手段可信。

**评测回放的关键是「可复现」，所以要把输入、环境与判定三样都固化下来。** 回放系统的骨架：一是数据集，每条 case 存原始输入（prompt、上下文、工具返回）、期望结果与判定方式；二是执行器，按同样的模型版本、温度、工具 mock 重跑，把过程中每一步的调用与产物落成 trace；三是判分器，规则断言（字段存在、格式合法、工具调用序列正确）+ 模型裁判（rubric 打分）+ 人工抽检三层。技术细节上经常被追问的是「环境怎么一致」：外部工具要能录播（第一次真实调用录下响应，之后回放），否则同一份 case 每次结果都不一样；模型侧要锁版本与参数，能开缓存就开；结果要有 diff 视图，把「这次和上次哪里不一样」直接标出来。还有一点容易被忽略：评测集本身要能演进，线上出现的新 failure 要能回流补进集合，否则分数涨了但线上没改善。

**多智能体协同，面试官想听的是「谁在什么时候把什么交给谁」。** 先把架构讲清楚：是编排式（一个 planner 拆任务、worker 执行、由 orchestrator 决定下一步）还是去中心式（消息总线 + 黑板）。再讲协同机制：任务怎么拆、状态存在哪里（共享黑板 / 数据库 / 消息队列）、结果怎么汇总、冲突怎么裁决、失败怎么重试与回滚。通信协议这层可以分两档说：进程内用函数调用或事件总线；跨服务用 HTTP/gRPC 传结构化消息，或者干脆走 MCP 这类标准化的工具/资源协议，好处是工具与 Agent 解耦、可以被不同框架复用。最后一定要补上「怎么知道协同有效」——单 Agent 基线对比、任务成功率、token 成本、端到端延迟，以及出现死循环或互相等待时的终止条件。能主动说出「多智能体不是越多越好，很多任务单 Agent 加工具就够了」，是加分项。

**Redis 分布式锁：能锁住、能过期、解锁的人只能是自己。** 标准做法是 `SET key value NX PX ttl`，value 放一个只有自己知道的随机值（或客户端 id + 线程 id），释放时用 Lua 脚本「比较 value 相等才 DEL」，保证不会误删别人的锁。要能说清三个经典坑：一是「先 SETNX 再 EXPIRE」不是原子操作，中间宕机就永久死锁，所以必须用一条 SET 带 NX 与 PX；二是业务执行时间可能超过 TTL，需要看门狗式续期（Redisson 的 watchdog 默认每 1/3 租期续一次）；三是主从切换会丢锁——主库写入后还没同步给从库就宕机，从库升主后别人能拿到同一把锁，所以对正确性要求极高的场景要用 RedLock 或直接上 ZooKeeper / etcd 这类基于共识的实现。如果面试官追问「为什么不用数据库唯一索引」，答案是：可以用（插入唯一键成功者持锁），实现简单、天然持久，但吞吐受数据库写入能力限制，且没有自动过期，需要额外的清理机制。

**MySQL 索引原理与失效场景：从 B+ 树讲到最左前缀。** InnoDB 的索引是 B+ 树：非叶子节点只存键、叶子节点存数据并用双向链表串起来，所以树高通常只有 3 到 4 层、一次查询最多三四次 IO；聚簇索引的叶子直接是行数据（按主键组织），二级索引的叶子存主键值，因此走二级索引查非索引列要「回表」。联合索引遵循最左前缀：`(a,b,c)` 能命中 a、ab、abc 的前缀查询，跳过 a 直接查 b 只能走覆盖索引的松散扫描或不走索引。常见失效场景要能一口报出来：对索引列做函数或运算（`where year(dt)=2026`）、隐式类型转换（字符串列传数字）、前导模糊匹配（`like '%x'`）、`or` 连接的两侧不是全都有索引、范围条件后面的列失去有序性、否定条件（`!=`、`not in`）与 `is null` 在大表上常被判为全表更便宜、以及优化器估算区分度太低（比如性别列）主动放弃索引。答题时一并说清「怎么验证」：用 `EXPLAIN` 看 type（全表 ALL / 索引 index / 范围 range / 等值 ref / 唯一 const）、key 与 rows，以及 Extra 里的 filesort、temporary、Using index（覆盖索引不回表）。

**手撕最长公共子序列：先把状态定义说出口，再写转移。** 定义 `dp[i][j]` 为 `s1[0..i)` 与 `s2[0..j)` 的最长公共子序列长度，转移是：字符相等时 `dp[i][j] = dp[i-1][j-1] + 1`，不相等时取 `dp[i][j] = max(dp[i-1][j], dp[i][j-1])`；边界是第一行第一列全 0。答案是 `dp[n][m]`，长度 O(nm)、空间 O(nm)，可以用滚动数组压到 O(min(n,m))。要让面试官看到你分得清「子序列」和「子串」：子串必须连续，转移在不匹配时直接清零，这是最容易写错的地方。如果想再拿分，可以提一句「要输出具体序列就再回填一张方向表，或者记录转移来源」，以及「如果只关心长度且字符集小，还有 Hunt–Szymanski 之类的优化」。写完主动跑一个样例（比如 `abcde` 与 `ace` 得 3），比写完就停更稳。
