### 《参考解析》

**LangChain 与 LangGraph 的分工。** LangChain 提供的是「组件与调用链」：模型封装、提示模板、输出解析、检索器、工具接口，以及线性的 Chain 组合；它解决的是「把模型和外部能力接起来」。LangGraph 提供的是「有状态的图编排」：节点是有输入输出的函数，边可以是条件边，状态是贯穿全图的可变对象，支持循环、分支、暂停与恢复、子图嵌套；它解决的是「多步骤、可回退、需要人介入的流程」。选择依据是控制流形态：一次调用、线性流水线用 LangChain 足够；需要循环（ReAct）、条件分支、断点续跑、多 Agent 协作时才需要 LangGraph。两者不是替代关系，LangGraph 的节点内部经常复用 LangChain 的组件。

**Agent 的核心模块。** 一个可用的 Agent 至少包含六块：模型（决策与生成）、工具集（含 schema 与错误契约）、上下文管理（历史、检索、压缩）、执行器（工具调用、超时、重试、沙箱）、状态与记忆（任务状态、跨会话记忆）、可观测与评测（日志、trace、指标）。完整链路是：接收输入 → 装配系统提示与工具表 → 模型决策（直接回答或调用工具）→ 解析调用 → 执行工具并回填观察 → 判断继续或结束 → 产出结果并记录轨迹。工程上还要加上权限校验（能不能调这个工具）、成本控制（token 与轮次预算）与降级路径（模型不可用时怎么办）。

**ReAct 的本质。** ReAct 是「推理 + 行动」交替的循环：模型先输出一段思考（当前知道什么、还缺什么），再选择一个动作（调用某个工具、参数是什么），环境执行后返回观察（工具结果），观察进入上下文，下一轮继续。关键点是决策依据来自观察而不是凭空推测，因此工具返回的质量与格式直接影响效果。它的局限也在这里：每一步都依赖上一步的观察，长任务容易走偏、上下文迅速膨胀、错误会被后续步骤放大。改进方向是加规划（先出计划再执行）、加反思（失败后总结再重试）、加验证（每步结果做校验）。

**Agent 与 Workflow 的边界。** 判断标准是「路径是否可枚举」。步骤固定、分支可枚举、验收标准明确的流程用 workflow：可控、可测、成本可预估、出错可定位。路径不可枚举、需要模型根据中间结果决定下一步（例如排查一个未知的线上问题、从一堆文档里找答案）才用 Agent。实际系统多是混合：外层用 workflow 保证流程与合规，内层在需要判断的节点上用 Agent。面试里被问「为什么用 Agent」，要能说出「不用 Agent 的方案是什么、差在哪」，例如规则覆盖不了的长尾占比、固定链路无法处理的异常分支。

**意图模糊与路由兜底。** 处理分三步：先澄清（把缺失的关键槽位列出来，一次性回问，而不是反复追问），再兜底（超出能力范围时明确说明能做什么、给出替代路径），最后记录（把未命中的输入沉淀成新场景的候选）。路由层要有「不确定」这个选项，而不是强行分到某一类；置信度低时走通用问答或转人工，比错误路由后一路执行到底要好。

**LangGraph 的状态设计。** 状态是整张图共享的数据结构，设计原则是「只放需要跨节点传递的东西」：任务目标、已完成的步骤、中间结论、待办、错误信息、用户身份与权限。节点应当是纯函数式的（读状态、返回状态增量），副作用集中在工具节点。条件边负责分支，判断可以是规则（字段是否为空）也可以是模型（分类），规则优先。子图用于封装可复用的子流程（例如「检索—验证—回答」），父子图之间用明确的输入输出契约通信。状态要可序列化，才能支持断点恢复与人工审批。

**任务完成判定。** 与前一篇面试里的结论一致：完成判定要分层，模型信号、状态机条件、预算耗尽、外部中断，每层都要有状态码。检索类任务还要有「检索充分性」判断：是否覆盖了必要的信息源、结果是否互相印证、是否还有未探索的分支。工程上给每类任务定义验收清单（字段齐否、格式对否、引用是否可追溯），把「完成」变成可检查的条件，而不是模型的自我声明。

**Human-in-the-Loop 的暂停与恢复。** 设计要点是「在哪里停、停多久、恢复用什么状态」。暂停点应放在不可逆操作之前（付款、删除、对外发送），暂停时把当前状态持久化并展示给审批人（做了什么、要做什么、影响范围），审批结果写回状态后从断点继续。恢复要幂等：同一次审批重复提交不能重复执行。超时策略要明确：审批超时是取消、降级还是转人工，不能无限挂起。

**死循环与路径震荡。** 检测手段有三类：计数（同一工具 + 同一参数在窗口内调用超过 N 次）、状态（连续多轮状态无变化或变化很小）、路径（在几个节点之间来回跳转的图模式）。发现后的处置是打断并降级：换策略、缩小范围、回问用户或直接报告失败。路径震荡常见于工具返回不稳定或目标定义模糊，治本要修工具与目标，治标才是加检测。

**任务粒度与规划。** 粒度过细会导致步骤爆炸、每步都要一次模型调用、上下文被中间结果塞满；过粗则一步失败全盘重来、无法定位。经验是「一步对应一个可验证的结果」，例如「找到候选文档」是一步，「读第三篇并抽取字段」是一步，而不是「研究这个问题」。规划由模型出草案、框架做校验（依赖是否成环、步骤是否可执行、预算是否够），执行中允许 replan，但 replan 要有次数上限并记录原因。

**长任务防漂移。** 三个机制：目标锚定（每轮把原始目标与验收标准重新注入，或放在固定的系统提示位置）、进展台账（已完成、待办、已知约束，每步更新，压缩时优先保留台账）、阶段校验（每完成一个阶段就对照验收清单检查一次，而不是等到最后）。此外要有预算与心跳：超时、超轮次就停下来汇报，而不是继续空转。

**Reflexion 与重试的区别。** 普通重试是原样再来一次，适合瞬时故障（网络抖动、限流）；Reflexion 是失败后先让模型总结「为什么失败、下次改什么」，把反思写入记忆再重试，适合策略性错误（工具选错、思路不对）。代价是多一次模型调用、反思本身可能错、错误反思会固化。ToT/LATS 则是在候选路径上做搜索：ToT 展开多条思路并按评估剪枝，LATS 结合蒙特卡洛树搜索与外部反馈。收益是复杂推理的成功率提升，代价是 token 与延迟成倍增长，通常只用于离线或高价值低频任务。
