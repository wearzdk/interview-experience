### 《参考解析》

**1. 向量检索与 BM25 混合检索，权重怎么分配**。两种召回器的失效模式互补：向量检索按语义相似度工作，能召回换了说法的同义表述，但对专有名词、产品型号、错误码、人名这类「字面精确」的信号不敏感，甚至会把语义相近但事实不同的段落排在前面；BM25 靠词频与逆文档频率精确匹配关键词，专有名词一击即中，但完全没有语义泛化能力，用户换个说法就召不回。混起来能同时覆盖「模糊问法」和「精确术语」两类查询，尤其是企业知识库里大量存在的编号、SKU、工单号类查询。融合方式有三种：加权分数融合（各自归一化后 `score = α·vec + (1-α)·bm25`，α 常见取 0.5~0.7，偏语义），RRF 倒数排名融合（`Σ 1/(k + rank)`，k 常取 60，只用排名不用分数，免去归一化、对不同检索器更稳），或者先各自取 Top-20 再交给 rerank 模型统一打分。权重不要手拍：构造带标准答案出处的评测集，扫 α 看 Recall@K 与 MRR，选最优；不同知识库的最优 α 不一样，技术文档偏 BM25、客服问答偏向量，所以权重应该做成可配置并按知识库调。

**2. Agent 的多跳检索怎么实现**。多跳指第一轮检索拿到的信息不足以回答，需要用它作为线索再查一轮（例如「A 产品的负责人现在负责哪个项目」要先查到负责人，再查他的项目）。实现上是一个「检索 → 判断 → 再检索」的循环：把问题交给规划器拆成有序子问题，每轮用上一轮的答案或实体作为新的 query 去检索，把已获得的证据累积到上下文，再由模型判断「信息是否足够回答，不够则生成下一个 query」，直到满足条件或达到最大跳数（一般限 3~5 跳，防死循环和成本爆炸）。工程要点：每跳都要做去重，避免同一文档反复进入上下文；要维护一个「已查过的 query 集合」防止原地打转；每跳检索结果按相关性截断，否则上下文会被中间结果撑爆；最好把每跳的证据与来源记下来，便于最终答案给引用，也便于排查是哪一跳跑偏。另一种更省成本的形态是「先分解后并行」：让模型一次性输出多个子查询并行检索再合并，效果接近但延迟低得多，缺点是子查询之间的依赖关系处理不了，所以依赖链强的场景仍要用串行迭代。

**3. Query Rewrite 怎么做，收益在哪**。用户提问和知识库文本之间普遍存在表述鸿沟：口语化、省略主语、带错别字、多轮对话里有代词（「它的保修期多久」）。改写就是把这层鸿沟填平，常见手段有四类：一是指代消解与省略补全，结合对话历史把「它」「这个」替换成具体实体，这就是所谓对话历史感知改写；二是查询扩展，生成同义表述或专业术语变体，用多个改写并行检索再合并去重；三是查询分解，把复合问题拆成多个子问题（往往和多跳检索配套）；四是查询压缩，把冗长口语提问压成关键词密集的检索式，对 BM25 尤其友好。实现上用一次轻量 LLM 调用（小模型加少样本示例即可，延迟几十到几百毫秒），也可以用专门的改写模型。收益要量化：在同一评测集上对比改写前后的 Recall@K 和最终答案正确率，多轮场景的收益通常最明显（可达十几个百分点），单轮且提问规范的场景收益有限，那就别加这一次调用，省的延迟比涨的那点召回值钱。

**4. 文档访问控制与 PII 脱敏**。访问控制的关键是「检索前过滤」：给每个 chunk 带上租户、部门、密级、可见用户组等元数据，把当前用户的权限编译成过滤条件交给向量库做前置过滤，再叠加文档级 ACL，权限变更时按短 TTL 缓存失效或实时查权限服务，保证调整权限后立刻生效；同时要处理向量残留——文档被移出权限范围时删除或标记其向量。PII（Personally Identifiable Information）指能单独或结合其他信息识别到具体自然人的数据，典型如身份证号、手机号、银行卡号、家庭住址、邮箱、人脸与声纹。脱敏一般分两步：入库前用正则 + NER 模型识别敏感字段并替换成占位符（`138****1234`）或做不可逆哈希/令牌化，同时把「原文 ↔ 令牌」的映射放在受控的单独存储里，只有具备权限的服务能还原；输出侧再做一次兜底检测，防止模型从上下文里把敏感信息原样吐出来。要注意脱敏要保留可检索性——把手机号整体替换成 `<PHONE>` 会让「按手机号查工单」失效，所以常见做法是保留哈希后的可精确匹配字段，同时展示层脱敏。合规上还要记录谁在什么时候检索了哪些文档，审计日志本身就是访问控制的一部分。

**5. 长对话摘要压缩**。上下文窗口有限、token 又是按量计费的，长对话必须做压缩。常用策略是分层：最近 N 轮保留原文（保证当前问答的细节和语气），更早的对话滚动压缩成结构化摘要，摘要里固定保留几类信息——用户身份与偏好、已确认的事实与结论、未解决的问题、以及关键实体（订单号、产品名）。压缩时机通常按 token 水位触发（例如用到窗口的 70% 时触发一次），而不是每轮都压，否则既贵又容易把细节磨掉。实现上有几种做法：LLM 滚动摘要（把旧摘要 + 新增对话喂给模型生成新摘要，成本可控）；结构化抽取（把对话转成 JSON 状态对象，只把状态放进 prompt）；检索式记忆（历史全存库，需要时按当前问题检索相关片段拼回来），后者对「用户很久前提过的事」支持最好，通常和摘要方案组合使用。压缩的风险是信息有损，所以关键事实要「钉住」不参与压缩，并且保留原始对话可回溯。

**6. 存储查询优化与完整存储链路（实习项目类问题）**。回答存储优化要给出可量化的路径：先定位瓶颈（慢查询日志、火焰图、连接池等待、索引命中率），再按手段收益排序——加合适的复合索引或分区键、把宽表查询改成覆盖索引、热点数据加缓存（Redis / 本地缓存 + 失效策略）、大结果集分页与游标、写多读少的场景改异步批写、冷热数据分层（近期热数据留热存储，历史数据下沉对象存储或列存）。面试官追问「为什么没有进一步分析底层存储和机器性能」通常是在试探你有没有下钻到磁盘 IO、Page Cache、副本同步、网络 RTT 这一层，答不上就应该老实说当时以业务侧优化为主、没做下钻，并补一句如果要继续会怎么看（比如 iostat/fio 看 IO 利用率、看 p99 写延迟与 fsync 次数、看是否受单机网卡或副本多数派确认拖累）。「一次完整的存储过程」在分布式存储里指：客户端请求 → 路由/元数据查询定位分片 → 权限与配额校验 → 写入 WAL/日志保证持久性 → 写内存与磁盘、按副本策略同步到从节点 → 多数派确认后返回 → 后台做刷盘、compaction 与副本修复。把「持久性由日志保证、一致性由副本数保证、可用性由故障转移保证」这三句话讲清楚，比背名词有用。
