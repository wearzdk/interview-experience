### 《面试题目》

1. 用户说「找出下周三场复盘，优先把最长的挪到周四，别和客户会撞」。如果你来设计这个 Agent，第一轮给模型哪些工具？哪些步骤要等结果回来？
2. 一串有依赖关系的工具调用，用有向无环图和状态机分别擅长表达什么？用户中途改主意怎么表示？
3. 正在查周四空档时，用户说「等等，改周五，客户会照样避开」。旧查询慢了两秒才返回，你会保留哪些结果？
4. 两个执行者都读取了版本 7，一个先写入版本 8，另一个随后也要更新。比较并交换能保证什么，不能保证什么？
5. 用户看到「周五三点到四点」的草稿并点了确认，原会议却刚被组织者延长到 90 分钟。你的 Agent 怎么办？
6. 评测 Agent 时，逐条比对标准工具调用序列，和检查环境最终状态，各会漏掉什么？
7. 你会怎么把「组织者中途改了时长」做成一个能反复跑的 Agent 测试？录一段标准对话够吗？
8. 把任务分成查空档、多轮更正、冲突恢复三类，微平均和宏平均的成功率有什么差别？什么情况下排名会反过来？
9. 80 道查空档、10 道更正、10 道冲突恢复，旧版分别做对 76、7、6 道，新版做对 79、8、3 道。你会怎么解读？
10. 新版同时换了模型和工具描述，你只有一次小规模回归预算，怎么找出该改哪里，并给出放行依据？

### 《参考解析》

**第一轮只给只读工具，排序交给程序**：先给能查事件和查忙闲的只读工具，第一步取回三场复盘的事件标识、起止时间和可见日历。排序不需要模型做——「最长」是确定性比较，程序排完把结果给模型，模型负责理解「优先」「别和客户会撞」在用户语境里的含义。模型不能凭标题猜时长。若只查到两场要向用户说明覆盖范围，两场并列最长要请用户区分或给两个方案。确定目标后才需要知道周四要找多长的空档，再去查客户会所在的授权日历；确定新旧时间后生成变更草稿，只改被选中的那一场。「优先」还意味着退让策略：最长的那场挪不开时可以提议挪第二场，但这个替换必须由用户决定。每一步拿到的对象和约束都要有来处，这是这类 Agent 的核心约束。

**DAG 描述一轮计划，状态机描述任务所处阶段**：依赖图适合表达一轮计划内哪些结果必须先得到——一个节点要用事件标识和候选时间，就必须等这两份输入齐备；没有依赖的只读查询可以并行。状态机适合表达任务处于查找、待选择、待确认还是已终止，以及哪些事件能触发转换；等用户回答后回到查找，在状态机里是自然的循环。两者组合使用：把当前任务状态与计划版本保存下来，在一个状态里执行一小段依赖图。用户更正目标时进入新的计划版本，保留仍然有效的观察、作废依赖旧条件的节点。只沿原图走到底的问题是——每个节点都执行成功，最终完成的却是用户已经放弃的目标。

**用户改目标后，按依赖关系判断哪些结果仍有效**：三场复盘的排序取决于原始会议与其时长，改目标日期不会改变它，所以如果事件版本仍有效，排序、选中的会议和「避开客户会」这一约束都可以保留；周四的忙闲以及依赖它生成的建议全部失效。做法是让周五的查询携带新的计划版本，工具返回时检查结果对应的版本与条件，旧版本的结果只能写进旧计划的记录。取消旧请求可以省算力，但即使取消失败、周四结果最后才到，也不能影响新计划。验证方式是控制返回顺序：先让周五产生候选，再让周四返回，检查预览与后续工具参数里只有周五；若原会议此时被改长，则从「时长」这个依赖点重算，不能只把日期替换一下。

**比较并交换只能保证「基于旧版本的覆盖会被发现」**：原子条件更新把「当前版本仍是 7」作为写入前提，成功时推进版本；先提交的一方成功，后一方的条件不成立，从而暴露它基于过期数据。若把检查版本和写入拆成两个独立操作，两者之间仍有被别人抢先修改的窗口。它不保证参与比较之外的资源——检查草稿版本不能证明外部日历仍然空闲，也不能证明用户批准了后来变化的内容。冲突之后要重新读取状态、判断哪些假设失效；直接换成最新版号把同一个旧动作重试，等于用应用自己覆盖掉比较并交换本想保护的那次更改。

**确认之后源数据变了，要让用户看到新方案**：先看这次确认覆盖了什么——用户确认的是一个具体会议、一小时的改动方案，原会议变成 90 分钟后，旧确认并没有包含多出来的半小时。正确做法是标记旧草稿失效，核查周五 15:00 到 16:30 是否可行，再把时长变化告诉用户并请他重新确认；即便多出的半小时恰好有空，也要让用户看到新方案，不能默默扩大改动范围。若目标系统支持条件写入，把预期事件版本带进工具，让执行时发生的更新也能被发现。这一题的元点是：助手的默认交付只到草稿，它能可靠报告的是「变更草稿已准备好」，扩展接入真实改期工具时才按其权限与条件更新能力报告是否生效。

**两种评测口径各漏一半**：逐条比对标准工具调用序列适合检查有先后要求的动作（例如必须在确认之后才能发起写入），但合法路径往往不止一条——一个助手一次批量取回三场会议，另一个先列标识再逐个读详情，两者可能得到同一个正确草稿，硬性匹配唯一轨迹会把后者误判为失败。最终状态检查允许合理的路径差异，却会漏掉过程中的越界动作：先改错一场再改回来，最终状态也能一致。可行做法是给结果写可验证条件、给过程写少量必须满足的约束，同时记录步数与成本，这样评分能区分「完成了任务」「违反了确认要求」和「正确但绕了远路」，排查方向也不同。

**冲突测试要可重置、由事件触发，而不是脚本化的第六句话**：建一个可重置的小日历环境，预置三场会议和周五忙闲；助手展示一小时草稿后，测试驱动器用组织者身份把目标会议改成 90 分钟，再让用户确认旧预览。触发点应取决于任务事件（草稿已生成、确认已发出）而不是固定的对话轮次，这样两个工具顺序不同的助手都能遇到同一冲突。验收检查三项：旧确认没有被提交、新建议覆盖 90 分钟、其他会议保持原值；若周五只剩 60 分钟，说明冲突并请求新选择也算通过。设计上可以参考 τ²-Bench 在电信场景中让用户与 Agent 都能改变共享环境的思路，该项目方在 2026 年 10 月 19 日发布的 2.0.0 也调整了评分口径并明确提示与 1.x 的分数不可直接比较——自己的回归集同样要把环境、任务和评分器的版本一起固定。

**微平均与宏平均的分母不同，结论会反过来**：微平均是全部成功任务数除以全部任务数，样本多的类别权重大；宏平均先算各类成功率再等权平均。当系统 A 擅长高频查询、系统 B 擅长低频冲突时，大量查询样本会把 A 推到微平均第一，等权计类时则可能是 B 领先。两者都必须先定义「成功」——冲突题的正确结果可能是停下来澄清，若一律把「生成了草稿」记为成功，平均方式再精细也无济于事。另外要报告每类分母：只测两道冲突题时答对一道就会让该类跳动 50 个百分点，这种宏平均不适合独自承担发布决策。

**这组数字的正确读法是「平均掩盖了退化」**：旧版微平均 89%、新版 90%，看似持平略升；宏平均从 75% 降到约 69.6%，因为查询与更正多做对的两三题掩盖了冲突恢复从 6/10 掉到 3/10。第一步不是看总分，而是把两版结果不同的冲突样本挑出来，区分三种情况——新版只是多问了一句、还没完成；新版拿着过期确认继续提议写入；新版直接拒绝了。三者对用户的影响差别很大。如果发现旧草稿被当成有效确认，应当先挡住新版的改期路径，保留只读查询作为独立候选，再补「改时长、改对象、撤回授权」这类有明确触发条件的测试。

**换模型又换工具描述时，用交叉分组定位**：选少量能稳定体现差异的冲突题，配上表述相近、无需重规划的正常题；固定用户、环境变化、解码设置和评分器，把「旧模型 / 新模型」与「旧工具描述 / 新工具描述」交叉成四组，同一任务在各组使用相同的起始快照。这样既能看单项变化，也能发现只有两者组合时才出现的退化；模型服务仍有随机性时，把有限的重复次数优先给结果摇摆的样本。诊断时找轨迹中第一个有意义的分歧：若模型在工具失败后继续执行，先看描述与返回值有没有区分「过期」与「成功」；若工具已明确报过期而模型仍复用旧确认，就由执行器把旧版本彻底置为不可提交。修好后用未参与定位的会议和不同措辞再跑一遍，确认过期确认被拦住、用户重新确认的新方案能通过、正常查询没有普遍多问。小规模回归能给出的是「是否恢复受限试用」的依据，真实完成率还要靠后续试用数据。
