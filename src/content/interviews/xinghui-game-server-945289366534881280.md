### 《面试题目》

1. 自我介绍。
2. 你在实习里做了一个游戏内聊天与通知服务，如果让你从连接接入、消息转发、异步落库到故障恢复完整讲一遍，你会怎么设计？
3. 为什么使用 RabbitMQ 去做异步的落盘？
4. RabbitMQ 已经开启消息持久化了，为什么服务仍然可能丢消息或者产生重复消息？
5. 如果数据库挂了怎么办，你怎么做消息的持久化？
6. 游戏服务器发现 MySQL CPU 已经接近满载，但当前在线人数还在持续上涨，你会怎样定位究竟是 SQL、锁竞争还是架构问题？
7. 如果游戏业务大量使用 Redis 缓存，某个热点 Key 突然失效导致请求全部打到数据库，你会怎么处理？
8. 为什么消息的转发用 WebSocket？如果连接数量比较大的话，怎么管理连接比较好？
9. 一个 Gateway 要支撑十万级长连接时，为什么不能简单地把所有连接都塞进一个线程？你会怎样设计线程模型？
10. TCP 四次挥手是什么？

### 《参考解析》

**聊天通知服务的链路：每一环都要说清失败怎么办**

按数据流答，而不是按技术栈罗列。**连接接入**：客户端用 WebSocket 连到网关，网关鉴权（token 换 uid）、把连接注册进本地连接表，并向路由层写一条「uid 在哪台网关」。**消息转发**：上行消息先做协议解析与合法性校验，私聊按目标 uid 查路由直接投递，世界频道按订阅关系扇出；在线走网关推送，离线落离线消息表。**异步落库**：聊天记录不必同步写库，投一条到 MQ 由消费者批量写，最近 N 条放 Redis 供快速拉历史。**故障恢复**：网关掉线后客户端重连到任意一台网关、重新注册路由，服务端按 uid 拉断线期间的离线消息补推；消息带客户端序号，接收方按序号去重排序。这题真正被追问的是「哪一环崩了会怎样」：网关挂了靠多实例加退避重连、路由表过期靠登录覆盖写加 TTL、消费者挂了看队列深度和消费延迟。

**为什么用 RabbitMQ，以及持久化为什么还不保险**

同步写库会把数据库延迟直接叠到请求链路上，峰值时连接池和磁盘 IO 瞬间打满。MQ 起三个作用：削峰（把突发流量摊平到数据库能承受的速率）、解耦（落库、推送、统计各自订阅）、批量（消费者攒一批再写，事务和网络开销都降）。选 RabbitMQ 而非 Kafka，理由通常在消息量级与路由灵活性（交换机、routing key、死信、延迟能力），不在吞吐。

「开了持久化为什么还会丢」要分三段。生产端：`basic_publish` 只是写进 TCP 缓冲区就返回，进程这时崩掉 Broker 可能没收到，所以要开 publisher confirm；Broker 端：队列要 durable、消息要设持久化属性，两者缺一个重启就丢；消费端最大的问题其实是**重复**——事务提交后、ack 之前宕机，Broker 会重新投递，业务就执行两次。所以端到端只能做到 at-least-once，幂等必须自己做：用消息 ID 或业务唯一键建唯一索引，重复写入转成幂等成功。关键消息可以用 Quorum Queue 提升单节点故障下的可靠性，代价是复制与确认路径更长，按消息等级分级而不是全部上最高可靠。

**数据库挂了：停止硬重试，让消息等在队列里**

最危险的动作是让消费者疯狂重试 SQL——原本只是 DB 故障，很快演变成消费线程、连接池全部堵死，恢复后还要面对雪崩式重连。正确做法是先降速或暂停消费，消息留在持久化队列不丢；已取出的消息用 nack 加延迟重试（TTL 队列加死信交换机），而不是立即 requeue 形成热循环；超过最大重试次数进人工队列并告警。恢复阶段同样要克制：按当前 QPS 和连接池水位逐步提高消费速率，先恢复核心业务；业务表用唯一索引或幂等表防止重复消费。这题的重点其实是「故障期间怎么不把事情搞得更糟」。

**MySQL CPU 满载：先定位忙在哪，再谈加机器**

看到 CPU 高就扩容是第一个坑。第一步看证据：慢查询日志找执行时间长、扫描行数大的 SQL；`performance_schema` 按总耗时排序找**执行频率高**的语句（单条 1ms 但每秒十万次，比单条 1s 更致命）；`EXPLAIN ANALYZE` 对比预估行数与实际行数，判断是统计信息失真还是缺索引。第二步区分 SQL 与锁：单条不慢但 TPS 一上来延迟就飙，要查锁等待和长事务（`information_schema.innodb_trx`、`data_lock_waits`），游戏场景的典型是**热点行**——同一玩家、同一公会、同一全局计数被并发更新，瓶颈在行锁排队而不在查询，解法是拆桶、合并写入或把强一致降级成异步累加。第三步才看架构：排行榜、在线状态、房间状态这类高频数据不该实时压 MySQL，读走 Redis、非强一致写走 MQ、日志批量落盘。优化目标是减少数据库必须承担的工作量，不是让某条 SQL 快 10%。

**热点 Key 失效：击穿、穿透、雪崩要分开答**

热点 Key 突然过期、请求全打到数据库，这是缓存击穿，加 TTL 只能降低概率。两种解法：**只放一个请求回源**（singleflight 或分布式锁），其余等待或返回旧值；**逻辑过期**——缓存不真删，值里带业务过期时间，发现过期后由一个线程异步重建，其余继续用旧数据。要主动切开三个概念：查大量不存在的 ID 是**穿透**（空值缓存或布隆过滤器）；大批 Key 同时过期是**雪崩**（TTL 加随机抖动，配限流降级）；击穿是单个热点失效。补一句「重建动作也要限流」，是做过线上的人才想到的。

**WebSocket 与十万连接：瓶颈不是「存不下 fd」**

用 WebSocket 是因为**服务端要主动推**：聊天、组队邀请、世界事件都要求双向实时，HTTP 请求响应做不到，轮询又有延迟和无效请求。连接管理要维护 `uid → connection`、`fd → connection` 两张索引，连接对象有明确生命周期（建立、鉴权、心跳、关闭），心跳用来清半开连接。规模上来后真正的危险是**慢客户端**：某个玩家网络差，服务端还不断往它的发送队列塞消息，一条连接就能吃掉大量内存，所以每条连接要有独立发送缓冲上限和背压——超过阈值丢低优先级消息（比如世界频道广播），再严重直接断开。多机部署还要解决「玩家在哪台网关」，登录时注册路由，业务服务按 uid 查网关再投递。

十万连接的线程模型：epoll 能监听十万个 fd，不代表一个线程能处理这些连接的所有工作。网络事件本身很轻，但协议解析、序列化、加解密、业务调用一旦塞进事件循环，任何一次耗时操作都会阻塞同一条线程上的其它连接。常见设计是少量 I/O 线程各自持有 epoll、**每条连接固定归属某个 I/O 线程**（避免 fd 和发送缓冲区跨线程操作），收齐完整业务包后投给逻辑线程池或 Actor，处理完把待发数据回投给连接所属 I/O 线程。线程不是越多越好，更好的思路是按玩家、房间、地图做逻辑分片，让同一实体始终在同一执行上下文串行处理，从根上减少锁。

**TCP 四次挥手：为什么不能像建连一样三次**

TCP 是全双工，两个方向要分别关闭，所以是四次：主动方发 FIN 表示「我没数据要发了」，被动方回 ACK（此时它还能继续发，这就是半关闭），等它也发完再发自己的 FIN，主动方回最后一个 ACK。主动方不会立刻删连接，而要 TIME_WAIT 等 2MSL——保证最后一个 ACK 丢了还能重发，也让旧报文在网络中消散，不污染复用同一四元组的新连接。工程上的落点是：短连接堆积 TIME_WAIT 会吃端口，解法是用长连接与连接池，而不是简单调小等待时间。
