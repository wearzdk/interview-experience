### 《参考解析》

**登录功能的测试点怎么设计**

登录是「一个入口、多条分支」的典型场景，先把输入拆成手机号、密码、验证码、记住密码、忘记密码几块，再按功能、异常、安全、兼容性、性能分层。

功能上：手机号要覆盖合法号段、位数不足/超出、含空格或特殊字符、带国际区号、已注册与未注册；密码覆盖正确、错误、长度边界、大小写敏感、含特殊字符、前后空格；验证码覆盖正确、错误、过期、重复使用、不区分大小写、连续点击「获取验证码」是否有倒计时与次数上限。组合场景是重点：手机号对密码错、密码对验证码错、验证码过期后提交、多次错误后的账号锁定与解锁、锁定期间换设备登录。

「记住密码」要验证勾选后重启 App / 重启手机 / 杀进程后是否仍保持登录，以及 token 过期后是否自动跳登录页、是否安全退出清了本地凭据；「忘记密码」要覆盖找回链路本身（验证码校验、新密码与旧密码相同、两次输入不一致、重置后旧密码是否立即失效、重置后其他设备是否被踢下线）。

再往上走：安全侧考虑密码是否明文传输、是否可被暴力破解、验证码是否可被脚本绕过、登录接口是否做了频率限制；兼容性覆盖不同机型、系统版本、深色模式、弱网与断网；性能上看并发登录与冷启动耗时。最后补一条容易被忽略的——登录成功后返回原页面（比如从购物车被踢到登录页，登录完要回到购物车），这类「业务上下文不丢」的用例，面试官很吃。

**购物车删除订单后仍然存在，怎么排查**

这是典型的「现象在前端、原因可能在后端」的问题，排查要按「客户端缓存 → 请求是否真的发出 → 服务端是否真的删了 → 数据是否真的落库 → 下次读取是不是读了旧数据」这条链路走。

第一步先定位复现条件与范围：必现还是偶现、只在弱网下出现还是一直出现、是当前设备还是多设备都能看到、杀掉 App 重进还在不在。如果重进就没了，基本可以判定是前端本地状态或接口缓存没刷新，属于客户端问题；如果重进还在，就要往下查。

第二步抓包看删除请求：请求有没有发出去、HTTP 状态码是多少、返回体里的业务码是不是成功。弱网下请求超时但 UI 已经乐观地把条目删掉了，一旦下拉刷新又会「复活」——这是最常见的乐观更新没做回滚。

第三步查服务端：删除接口是不是逻辑删除（只置 is_deleted），后续查询的 SQL 有没有带上过滤条件；有没有走缓存（Redis 里的购物车列表没同步失效）；有没有读写分离导致的从库延迟；删除的是「购物车条目」还是「订单」，两者在数据模型上可能压根不是一张表。

定位手段是日志 + 数据：按用户 ID 和商品 ID 去查数据库里这条记录的状态、查接口调用日志与耗时、必要时在测试环境加断点复现。写出结论时要带上「哪一层出的问题、影响范围多大、属于前端还是后端、怎么修、要不要加回归用例」，这也是测试岗面试官真正想听的回答结构。

**手机拨打电话功能怎么从软硬件结合角度设计测试点**

「软件、硬件、软硬件结合」这三层其实就是让你把测试面铺开。软件侧覆盖拨号盘交互（输入、删除、粘贴、长按、特殊号码如 110/400/带 +86 的国际号码）、联系人联想与去重、通话中界面（静音、免提、保持、录音、切换、挂断）、通话记录与未接来电、多路通话与呼叫等待、来电时的接听/拒接/短信拒接。

硬件侧覆盖听筒与扬声器切换、麦克风与降噪、距离传感器（贴近熄屏、离开亮屏）、光线传感器（自动亮度）、音量键、耳机（有线/蓝牙）插拔时音频路由是否正确、蓝牙车机配对与自动接听、SIM 卡插拔与双卡双待的选卡、飞行模式、电量极低时的通话、以及弱信号/无信号下的提示。

软硬件结合是这类题的高分点：通话中插入耳机声音是否从耳机出、拔出是否自动切回听筒；通话中来电是否提示；通话中锁屏、息屏、旋转、多任务切换是否影响；地铁进隧道信号丢失后是否自动重连、通话是否保活；免提时音量与回声、外放是否啸叫；充电时通话是否有电流音干扰。测试方法上再补一句「真机实验室 + 弱网仪表 + 抓 baseband 日志」，比只罗列用例更能体现工程意识。
