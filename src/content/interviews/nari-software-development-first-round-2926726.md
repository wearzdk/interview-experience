### 《面试题目》

1. 为什么读研期间没做过横向项目？
2. 科研项目来源于哪里，解决什么问题，效果如何？
3. 为什么用两个 Agent 协作，它们是怎么协作的？
4. 怎么保证 AI 生成的代码是正确的？
5. 有没有想过用 AI 对原有的旧代码进行检查和修改？
6. 七类工具是怎么设计的？
7. 用的是什么大模型，自己部署过吗？
8. Spring Boot 里了解哪些注解？
9. 自动注入讲一下。
10. 为什么选南瑞？

### 《参考解析》

**多个面试官同场，本质是四场小面试拼在一起，要按人切换叙事粒度。** 负责人关心「你能不能扛住压力、简历是否真实」，问法常带质疑色彩（比如为什么没做过横向），这种问题不要辩解也不要情绪化，直接给客观约束加替代证明（组里不接横向，所以能力是在课题与实习里练的，并给出具体产出）。博士偏技术深度与判断力，回答要给原理和边界。组长关心工程落地与团队协作，回答要落到「怎么分工、怎么保证质量、怎么上线」。HR 关心动机与稳定性，回答要和个人规划挂钩。同一段实习经历，对四个人的讲述重点应该不同——这是多人面试最容易被忽略的准备点。

**科研项目要讲成「问题—方法—结果」三段，而不是讲课题名。** 说清项目来源（纵向课题、企业合作还是自选）、要解决的真实问题是什么、你的方法相比已有做法改了什么、效果用什么指标衡量。横向项目的有无本身不构成能力判断，面试官真正在筛的是「你有没有独立把一件事从模糊需求推到可验证结果」的经历，如果确实没有横向，就用课题里的实验设计、数据规模、复现与论文产出补上这条证据链。

**多 Agent 协作要答出「为什么是两个」，也就是单 Agent 为什么不够。** 常见动机有三类：职责隔离（一个负责生成、一个负责校验，把评审权从同一个模型里拆出来，避免自我确认偏误）、上下文与工具隔离（不同 Agent 拿不同的工具集和知识，减少互相污染与越权）、以及并行与流水线（可并发的子任务分给不同 Agent）。协作机制要讲清通信方式（共享黑板、消息传递还是编排者调度）、状态与终止条件（什么情况下判定完成、什么情况下放弃）、以及代价（token 成本上升、延迟上升、错误会在 Agent 之间传播、日志与责任归属更难定位）。最后一定要落到怎么评测：单个 Agent 的效果、协作链路整体的成功率、以及失败时能不能定位到是哪一个环节错了。答不出代价，很容易被判断成只跑过 demo。

**AI 生成代码的正确性，是把「模型输出」变成「工程可验证」的过程。** 可控手段按性价比排序：把生成范围切小（一次只改一个函数、diff 尽量短）、输出必须过静态检查与类型检查、改动必须伴随可运行的测试、关键路径的双人评审、以及上线前的灰度与回滚预案。明确哪些代码不允许 AI 独立产出也很重要（鉴权、资金、数据订正这类不可逆逻辑）。用 AI 改旧代码的实践同理：先给旧代码补上描述现有行为的测试（characterization test），再动手改造，分批提交、每批都能回滚，这样即使模型理解错了也能当场发现——回答里带上「先固化行为、再改结构」这条，是这类问题最容易被认可的思路。

**工具设计是 Agent 工程的核心功夫，考的是边界感。** 工具数量不是越多越好，每个工具应当职责单一、参数有严格 schema、错误信息对人可读、副作用明确（是否幂等、是否需要二次确认）、权限最小化（读与写分开、危险的删除与提交类操作单独设卡）。命名与描述是写给模型看的文档，要说清什么时候该用、什么时候不该用、参数含义与取值范围。七类工具如果能按「查信息 / 改状态 / 跑计算 / 调外部服务」这类维度分组并说明为什么这么切，就能自然回答「怎么保证模型选对工具」这个追问——工具之间的边界清晰，混淆的几率才会降下来。

**大模型选型与自部署别只答「用过哪个模型」。** 选型维度至少包括：任务难度与效果基线、上下文长度是否够装下检索结果与历史、推理成本与延迟、以及数据合规（能不能把业务数据发到外部 API）。自部署的动机通常是数据不出域、成本可控、可微调；代价是显存与并发吞吐的硬约束、量化带来的效果损失、运维与扩容成本，以及模型迭代速度跟不上。回答时给一个具体判断，比如「数据敏感的链路自部署小模型兜底、效果吃紧的环节走 API 并做脱敏」，比罗列模型名更能体现工程判断。

**Spring Boot 的注解与自动注入，答法按三层展开。** 一是核心注解的分类：`@SpringBootApplication`（等于 `@Configuration` + `@EnableAutoConfiguration` + `@ComponentScan`）、组件注册类（`@Component` 及其派生的 `@Service` / `@Repository` / `@Controller` / `@RestController`）、配置类（`@Configuration` + `@Bean`）、注入类（`@Autowired` / `@Qualifier` / `@Value` / `@Resource`）、配置绑定（`@ConfigurationProperties` / `@Profile` / `@Conditional` 系列）。二是自动注入的流程：启动时扫描并注册 BeanDefinition → 容器刷新阶段执行 `BeanFactoryPostProcessor`（自动配置类就是这样被加载筛选的）→ 实例化时由 `AutowiredAnnotationBeanPostProcessor` 按类型找候选、再用 `@Qualifier` 或变量名消歧 → 三级缓存解决单例的循环依赖。三是实践取舍：优先构造器注入（依赖不可变、便于测试、启动即暴露循环依赖），`@Resource` 按名称、`@Autowired` 按类型，多实现场景用 `@Primary` 或 `@Qualifier` 指定。追问常落在「循环依赖怎么解决」「`@Transactional` 为什么同类内部调用不生效」上，前者答三级缓存与代理对象提前暴露，后者答自调用绕过了代理。

**「为什么选南瑞」这类动机题的答法是把它变成信息采集题。** 先给与自身相关的具体理由（业务方向与做过的项目对口、想留在电力行业的数字化方向、看重稳定的工程体系），再顺势反问对方当前项目用什么技术栈、新人多久能独立负责模块、团队在 AI 与传统业务结合上有什么尝试。这样既回答了动机，又把单向回答变成双向了解，比背一段公司简介有效。
