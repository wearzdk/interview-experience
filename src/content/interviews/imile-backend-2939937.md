### 《参考解析》

**幂等的分层设计**：最可靠的是数据库唯一约束——它不依赖应用层逻辑，天然能扛并发与重试。做法是把「业务唯一键」建唯一索引（用户 id + 活动 id + 场次 id），插入冲突时捕获 `DuplicateKeyException` 返回已有结果。第二层是状态机：订单从「待支付」到「已支付」只能流转一次，重复回调直接返回成功。第三层是请求级去重：客户端带幂等 token，服务端用 Redis `SETNX` 或去重表记录，注意「setnx + 设置过期」必须原子（Lua 或 `SET key val NX EX`）。第四层是消息消费的幂等：消息 ID 落库，消费前查是否处理过。

**抢票场景加锁的问题**：单机 `synchronized` 在集群下无效；Redis 分布式锁要处理锁超时、续期、误删（value 存持有者标识，解锁用 Lua 比对）、主从切换丢锁；数据库行锁在热点行上会把所有请求排成一队，QPS 直接掉到几百；更根本的是「为一个用户加锁」不能解决「一万个用户抢同一批库存」——那是库存扣减问题，应该用 Redis 预扣（Lua 原子减库存）+ 异步落库，或者消息队列串行化。

**同一用户重复下单的唯一索引**：`unique key (user_id, activity_id)` 能挡住「一次活动只能下一单」，但挡不住「同一用户买两张票」。后者的业务唯一键应该是「票/座位」而不是「用户 + 活动」：如果每张票有唯一编号，就对 `(activity_id, seat_id)` 建唯一索引；如果允许一个用户买 N 张，就用「用户 + 活动 + 序号」或在订单表加 `buy_seq`，并对 `(user_id, activity_id, buy_seq)` 建唯一索引，同时在库存侧用 Redis 计数控制总量。用「数量」做幂等只能校验「没超上限」，无法区分「重试」和「真的想买第二张」，所以不能只靠数量。

**缓存与数据库不一致**：典型流程是「线程 A 写库成功 → 线程 B 读缓存未命中 → B 读库拿到旧值（A 还没提交或读到旧快照）→ B 把旧值写回缓存 → A 提交」，缓存里就留下了旧数据。还有「先删缓存再写库」的经典竞态：A 删缓存 → B 读库旧值 → B 写缓存 → A 写库，缓存仍是旧值。先更新库再删缓存能大幅降低概率（删除比更新安全，且下一次读会重建），但不能完全消除——删除失败、主从延迟、并发读回填都会导致不一致。

**怎么保证强一致**：没有银弹。可行手段：延迟双删（更新后删一次，隔几百毫秒再删一次）、订阅 binlog（Canal）异步删缓存、把「读缓存」和「写库」放在同一个分布式锁里（性能差）、对强一致要求高的数据干脆不缓存、或者用「缓存只存不可变快照 + 版本号」，读时校验版本。抢单场景更常见的是「Redis 预扣 + 异步落库 + 对账补偿」，接受最终一致，用对账把差异收敛。

**活动缓存一小时、活动结束后怎么办**：给缓存设 TTL 略大于活动时长（比如活动 1 小时、TTL 设 70 分钟），活动结束后由定时任务或活动状态变更事件主动删除；同时用「活动状态 + 版本号」做逻辑过期，避免 TTL 到期瞬间大量请求打穿到数据库（加互斥锁只放一个请求回源，其余等待或返回兜底值）。活动数据本身应该是「读多写少」的，真正的库存扣减走 Redis 计数，不走缓存。

**MQ 异步落库是最终一致**：消息发出即返回，库可能还没写，中间有延迟窗口，所以是最终一致。金融场景要强一致，通常不用「MQ 异步落库」做主路径，而是：本地事务 + 事务消息（RocketMQ）+ 消费端幂等 + 对账；或者直接同步写库，用 TCC / Saga 处理跨服务。核心是「钱的操作不能只依赖消息到达」。

**分布式事务解决什么**：解决「跨多个数据库/服务的一组操作要么全成功要么全回滚」。单服务单库用本地事务就够了，不需要引入——很多候选人会把「用了 MQ」和「需要分布式事务」划等号，这是错的。异步本身不等于分布式事务：如果业务能接受中间状态并用对账兜底，就不必上 Seata/TCC，那会把复杂度抬高一个量级。

**Lua 与 Redis 事务的取舍**：Redis 的 `MULTI/EXEC` 只保证「命令打包按顺序执行、不被其他命令插入」，但不支持回滚——中间某条命令失败，其余命令照样执行；而且事务里没法根据前一条命令的结果做判断。Lua 脚本在服务端原子执行，可以在脚本里读值、判断、写值，实现「检查并设置」这类逻辑，是分布式锁、限流、库存扣减的常用手段。代价是脚本要短（阻塞单线程）、集群下 key 要在同一 slot、调试不便。Redis 7 的 Function 是 Lua 的演进形态，能力类似。所以「需要条件判断的原子操作」选 Lua，「单纯打包多条写命令」可以用事务。

**深拷贝与浅拷贝**：浅拷贝只复制对象本身和其中的基本类型字段，引用类型字段仍指向同一个对象；深拷贝递归复制所有引用对象。实现方式：手写 `clone`、序列化反序列化（JSON、Kryo、Java 原生序列化）、`BeanUtils.copyProperties`（浅拷贝）、MapStruct（默认浅拷贝，引用字段直接赋值）。判断标准是「改副本会不会影响原对象」。

**MapStruct 原理**：编译期注解处理器（APT）读取 `@Mapper` 接口，为每个方法生成实现类（`XxxMapperImpl`），在里面逐字段赋值，字段同名同类型直接赋值，不同名用 `@Mapping(source, target)` 指定，复杂转换可以挂 `@Named` 的自定义方法或 `expression`。因为它生成的是普通 Java 代码，运行时没有反射开销，比 `BeanUtils`（反射 + 内省）快得多，且编译期就能发现类型不匹配。生成的 class 在 `target/generated-sources/annotations` 下，可以直接打开看。

**MySQL 隐式类型转换**：字符串列和数字比较时，MySQL 会把字符串转成数字再比，索引列上发生转换就用不上索引（因为要对每一行做转换）。所以 `varchar` 的 `user_id` 传 `123`（int）会全表扫描，必须传字符串 `'123'`。反过来，int 列传字符串 `'123'` 时，是把常量转成数字，索引仍然可用。规则记一句：**转换发生在列上就失效，发生在常量上不影响**。

**ES 与 MySQL 的映射**：ES 的 `text` 会分词、用于全文检索，对应 MySQL 里需要模糊匹配的字段；`keyword` 不分词、用于精确匹配、排序、聚合，对应 MySQL 的索引列；`long/integer/date/boolean` 对应数值、日期、布尔；`nested` 对应关联表（但查询方式不同）；`object` 是内嵌对象。倒排索引是「词 → 文档列表」的映射，写入时分词建立词典，查询时直接按词拿到文档集合，避免全表扫描；优点是全文检索快、支持相关性打分，代价是写入放大、存储占用高、更新是「标记删除 + 重建段」。

**分布式 ID 方案**：UUID（本地生成、无网络开销，但 128 位太长、无序导致 B+ 树随机插入、可读性差）；数据库自增（简单但单点、分库分表难）；号段模式（中心服务一次发一批 ID 区间给应用，应用本地递增，用完再取，DB 压力小、性能高，缺点是服务重启会浪费一段、号段服务本身要高可用）；雪花算法（64 位：1 位符号 + 41 位时间戳 + 10 位机器 ID + 12 位序列，趋势递增、本地生成、高并发）；Redis `INCR`（简单，但要考虑持久化与单点）。业务上常用「雪花 + 号段」组合，或直接用美团 Leaf、百度 UidGenerator。

**雪花算法的时钟回拨**：回拨会让新生成的 ID 小于已发出的 ID，导致主键冲突或乱序。解决办法：检测到回拨时直接抛异常拒绝服务（等时钟追上）；回拨幅度小（几十毫秒）时短暂等待；用「上次时间戳」做单调校验，回拨时把序列号继续递增或借用未来时间；更彻底的是不依赖系统时钟——用号段模式、或「逻辑时钟 + 持久化的 lastTimestamp」。帖主提到的「提前生成一批存 Redis，回拨时从 Redis 取」是空间换时间的思路，可行但要把「预生成池」的消费与补充做成原子操作，且池子耗尽时仍要回到拒绝或等待。

**Harness 思想辅助 AI 编程**：把 AI 当成「需要被约束的执行者」，围绕它搭一套外部骨架：明确的任务描述与验收标准（spec）、可读的代码库与文档（上下文）、工具（读写文件、跑测试、查日志）、反馈回路（编译错误、测试结果回灌给模型）、边界（权限、沙箱、必须人工确认的操作）。落地时先做「小步提交 + 每步验证」，再逐步放开自主性；用固定的评测任务衡量改动前后的效果。开源工具可以提 Claude Code、Codex CLI、Aider、OpenHands 这类，但重点讲你怎么用，而不是列名字。
