### 《参考解析》

**「每个用户只留最近一条记录」要给出至少三种写法，并说清各自的坑。** 最通用的是窗口函数：`SELECT ... FROM (SELECT t.*, ROW_NUMBER() OVER (PARTITION BY user_id ORDER BY order_time DESC) AS rn FROM orders t) x WHERE x.rn = 1`，注意窗口函数在 `WHERE` 之后才计算，所以必须套一层子查询或 CTE，不能直接写进 `WHERE`。第二种是「先聚合再回连」：子查询 `MAX(order_time)` 按 user_id 分组，再 join 回原表取该时间对应的行——坑在于同一用户同一时间可能有多条订单，join 会返回多行，需要再用订单号或主键取一条。第三种是相关子查询（`WHERE order_time = (SELECT MAX(...) WHERE user_id = o.user_id)`），写法直观但在大数据量下容易退化成逐行执行，不如窗口函数。还要主动提索引：`(user_id, order_time DESC)` 的联合索引能让分组取 TopN 走索引扫描，避免全表排序；如果表很大，可以先按时间分区再取，减少扫描量。面试官顺着问「有哪些方式」，要的就是你能比较而不是只会背一种。

**ROW_NUMBER() 与窗口函数的定位：先解释它做什么，再解释它和聚合函数的区别。** `ROW_NUMBER()` 是给结果集按指定的 `PARTITION BY` 分组、按 `ORDER BY` 排序后，为每一行分配一个从 1 开始的连续序号；它不改变行数（这点与 `GROUP BY` 聚合相反），所以常被用来做「分组取 TopN」和「去重」。同一族里 `RANK()` 遇到并列会跳号（1、1、3），`DENSE_RANK()` 并列不跳号（1、1、2），要严格取一条时用 `ROW_NUMBER()` 并给排序键加足够的唯一性（比如再按订单号），否则并列行的顺序不确定、结果会在不同执行计划下漂移。窗口函数还分排行类（`ROW_NUMBER`/`RANK`/`LAG`/`LEAD`）与聚合类（`SUM`/`AVG` 加 `OVER`），后者常用来算累计值和占比；执行上它在 `GROUP BY`、`HAVING` 之后、`ORDER BY` 之前计算，这也是「为什么不能直接在 `WHERE` 里过滤序号」的原因。被问「你偏熟还是一般」时不要硬撑熟，给真实用例更有说服力：明确说出自己在哪些场景用过（分组取最新、去重、算同环比与累计），以及在哪个点被坑过（并列、`WHERE` 位置、大表全排序的性能），比笼统答「挺熟的」可信得多。

**Spark 只停在「会用」层面时，诚实说边界并给出可迁移的经验。** 面试官问「底层其实也不太熟对吧」是给你台阶，不是挖坑——顺着承认并立刻补上你会的那部分最稳。可以这样组织：日常以 Spark SQL 和 DataFrame API 为主，负责把业务逻辑翻译成 SQL、调优参数与排查数据问题；对底层原理的了解集中在影响日常使用的几点上——RDD 与 DataFrame 的区别（前者是弹性分布式数据集、编程式；后者带 schema、能被 Catalyst 优化）、宽窄依赖与 shuffle 的代价（`groupBy`、`join`、`distinct` 会触发 shuffle，是性能瓶颈主要来源）、数据倾斜的常见表现与处理（个别 key 过大导致长尾任务，用加盐打散、广播小表、预处理去重缓解）、以及广播 join 的适用条件。再给一个真实排查案例（任务卡在最后几个 partition、怎么定位到倾斜并解决），这比背原理更能证明你会用。要避免的坑是硬装：一旦说熟，面试官会接着问 shuffle 的写盘过程、内存管理模型、动态资源分配，答不上来反而更亏。

**HashMap 与 GET/POST 的设计取舍。** HashMap 的底层是数组 + 链表 + 红黑树：先对 key 的 `hashCode` 做扰动（高 16 位与低 16 位异或，让高位也参与运算）再对数组长度取模定位桶；桶内哈希冲突时先用链表，链表长度超过 8 且数组长度达到 64 转红黑树，查询从 O(n) 降到 O(log n)；负载因子 0.75，元素数超过「容量 × 0.75」就扩容为两倍并重新分布（1.8 用高低位拆分避免重新计算哈希）。要提的关键点：HashMap 非线程安全，并发扩容在 1.7 会成环（1.8 改成尾插缓解但仍然会丢数据），并发场景用 `ConcurrentHashMap`；key 必须正确实现 `equals` 与 `hashCode`，可变对象做 key 会导致取不回来；初始容量按预估元素数给，能避免反复扩容。GET 与 POST 的取舍按语义和约束讲：GET 用于读取、幂等、可缓存、参数在 URL 上有长度限制、会进日志与浏览器历史，所以不能放敏感信息；POST 用于提交与创建、非幂等、参数在 body 里、没有长度限制，适合敏感与大数据量场景。实际设计还要补两句：安全与幂等不能只看方法名（GET 也可以被滥用成写操作，POST 也可以设计成幂等——加幂等键），以及查询条件复杂或需要保密的「查询」用 POST 也是常见工程妥协；RESTful 语义上要求 GET 查、POST 建、PUT 改、DELETE 删，团队内保持一致比抠定义重要。

**AI 排障 Agent 的追问：把「准确率」翻译成可度量的指标。** 面试官问「准确率大概多少」，直接给一个百分比很容易翻车，因为它取决于你怎么定义正确。稳妥的答法是先说清口径：排障结论可以分层的看——定位到的故障组件是否正确、给出的原因是否与事后复盘一致、以及建议的处理动作是否有效，这三个口径的准确率完全不同（组件级通常高，根因级明显低）。再说度量方式：从历史告警里挑带复盘结论的工单做评测集，人工或规则判定结论对错；线上则看采纳率（工程师是否按它的结论处理）与平均定位时长有没有下降。最后说清它的边界与兜底：定位不确定时输出候选原因并带上证据（哪个指标在什么时间点变化、关联到哪个组件），而不是给一个斩钉截铁的结论；涉及重启、扩容、回滚这类有副作用的操作只出建议、由人确认执行。这样回答既诚实又有工程感——面试官其实是在判断你有没有把 AI 能力当作可评测的系统来运营。

**Text-to-SQL 系统设计：相似度、分步路线与工期估算。** 相似度上，两者共享「意图识别 → 数据/工具选择 → 生成 → 执行 → 解读」的主干，区别在于输入是自然语言问题、输出必须是可执行且安全的 SQL，所以正确性校验的权重更高，人机交互也更重。分步做法建议五步：第一步把「表与字段」变成可检索的知识（给十几张表建立业务语义描述、字段注释、同义词与常用指标口径，做成 schema 检索而不是把所有建表语句塞进 prompt）；第二步做意图识别与澄清（识别是查数还是排障、抽取时间范围与维度指标，缺关键条件就反问，而不是猜）；第三步生成与校验 SQL（few-shot 加业务口径约束、生成后做语法与权限校验，用 `EXPLAIN` 或 `LIMIT` 小样试跑，只允许只读账号、禁止 DDL/DML、加超时与扫描量上限，这一步是安全底线）；第四步结果解读（把结果与问题对齐，给出结论与口径说明，异常值要提示，不能无中生有地解释相关性为因果）；第五步多轮追问与沉淀（把用户修正回填成 few-shot 或口径规则，把高频问题固化成模板，形成越用越准的闭环）。工期上要分阶段报而不是给一个总数：把「查数闭环可用」拆成表语义与检索、意图识别、SQL 生成与安全执行、结果解读四块，按单人投入给出阶段性时间，并说明最大的不确定性在数据治理与口径统一（这部分往往比模型调优更耗时），最后补一句先服务一个明确场景做通的建议——这比承诺「两周做完」专业得多。

**统计字符出现次数：讲思路要讲清数据结构与边界。** 最直接的做法是用哈希表（或按字符集大小开一个计数数组，ASCII 用 256 个桶，一趟遍历边统计边自增），时间 O(n)、空间 O(字符集)；如果面试官追问「字符串很大，内存放不下」，就答流式处理——分块读取、每块累加计数、最后合并，或者用外部排序后线性扫描计数。还要主动提边界与细节：大小写是否区分、空格与标点算不算、Unicode 下按码点而不是按字节切分（对中文尤其重要，直接按 `char` 或字节统计会出错）。如果被要求「输出出现次数最多的 K 个」，就在计数完成后用一个大小为 K 的最小堆或桶排序取 TopK，复杂度从 O(n) 变 O(n + m log K)。这类题的价值不在难度，而在你有没有主动界定输入输出与规模假设。
