### 《参考解析》

1. **测试用例优先级怎么定**：常用的是按「业务影响 × 发生概率」分档——核心链路、资金与权限相关、历史缺陷高发模块放 P0；次要流程、异常分支放 P1/P2；文案样式这类放末档。面试官把「怎么定优先级」和「覆盖缺失怎么避免」放在一起问，说明他想看的是这套分档在真实项目里怎么落地：P0 通常很小（10% 上下），回归时先跑 P0/P1 再加改动相关模块，漏测则靠需求评审逐条转用例和缺陷回溯补漏来堵，这才是能自圆其说的口径。

2. **用例设计题（手机号登录）的答法**：按等价类与边界值铺开——号码格式（位数、纯数字、含字母、前后空格、带国际区号）、验证码（长度、过期、错误、重复使用、频繁发送限流）、账号状态（未注册、已注册、被冻结）、登录方式（验证码、密码、一键登录）、异常与安全（并发多端登录、弱网与超时、防撞库与验证码防刷）、兼容性（iOS/Android、小程序/App/Web）。面试官多半要的是结构完整而非穷举，先给分类再各举两条，比一口气报二十条更有条理。

3. **测试覆盖率缺失怎么避免**：一是需求评审阶段就把验收标准逐条转成用例，避免漏功能点；二是用代码覆盖率工具看增量代码的覆盖盲区，补齐分支与异常路径；三是把线上缺陷回溯成用例（缺陷驱动补漏），每次漏测都沉淀成回归项；四是对高风险模块做交叉评审或结对设计。关键是能说清「你怎么知道漏了」——没有度量手段的保证都是空话。

4. **不写代码怎么做接口测试**：用 Postman、Apifox、JMeter 这类工具做请求组装与断言，配合环境变量、前置脚本处理登录态与参数关联；接口文档可以用 Swagger/OpenAPI 导入，生成集合后批量跑；断言不只看 HTTP 状态码，还要校验业务码和关键字段结构。数据准备靠现成的测试账号或库表直连（有权限的前提下），结果比对可以用工具自带的 diff 能力。

5. **UI 自动化元素缺失或错位怎么判断**：先区分是环境问题还是产品问题——元素找不到时保存失败截图与页面 DOM 快照，看是加载超时、页面结构改了还是弹窗遮挡；错位通常是分辨率、缩放或等待策略不当。工程上要把定位方式往稳定的属性上迁移（测试专用 id、语义化属性），少用绝对 XPath；对动态内容用显式等待而不是 sleep。二面问自动化稳定性、三面问元素丢失怎么判断，本质是同一个考点——脚本挂了你怎么判责。

6. **服务访问不了的定位思路（三面网络题）**：自上而下按层排查——先确认是自己这台机器还是所有人都访问不了（缩小范围）；再 ping 通不通、DNS 解析是否正常；然后 `telnet`/`nc` 探端口是否可达，`curl -v` 看卡在哪一步；服务侧看进程是否存活、监听端口与日志、依赖的数据库或下游是否异常；最后查防火墙、安全组与负载均衡配置。回答时把「先分层再缩小范围」的方法论讲出来，比罗列命令更得分。

7. **8081 端口是否开放的测法**：本机 `netstat -tunlp | grep 8081` 或 `ss -lntp` 看监听情况；远程用 `telnet host 8081` 或 `nc -zv host 8081` 探连通性，`nmap -p 8081 host` 也能判断；有返回但应用不对，再上 `curl -v http://host:8081/` 看响应头。注意区分「端口开着」和「服务正常」——端口通只说明 TCP 层可达。

8. **FTP 端口与 ICMP 命令这类基础题别丢分**：FTP 控制端口 21、主动模式数据端口 20，被动模式的数据端口是服务端在配置范围内随机协商的；ICMP 常用命令是 `ping`、`traceroute`（Windows 下 `tracert`）、`mtr`，这些属于背下来就有的分，笔试面试前过一遍网络与 Linux 基础清单最划算。
