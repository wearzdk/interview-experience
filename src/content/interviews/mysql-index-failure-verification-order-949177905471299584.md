### 《面试题目》

1. 你知道哪些索引失效的场景？
2. 隐式转换为什么失效？
3. 你怎么证明是它失效，不是优化器不想用？
4. 为什么在测试表上有时看不出隐式转换的差异？
5. 函数和运算为什么会让索引失效？怎么改写？
6. 最左前缀和 `OR` 的结论对，但要注意什么？
7. 你现在的判断顺序是什么？

### 《参考解析》

**隐式转换不是「类型不匹配」这么简单**：`user_id` 建的是 `varchar`、查询写成 `WHERE user_id = 10086` 时，MySQL 会把字符串列转成数字比较，等于在列上套了转换函数，`EXPLAIN` 里 `key` 为 `NULL`、`type` 为 `ALL`。但帖主发现它不一定每次都能复现：数据量小时优化器直接全表扫，你分不清是「转换导致失效」还是「它觉得全表更快」。把数据灌到几十万行后再对比 `user_id = '10086'` 与 `user_id = 10086`，前者走 `ref`、后者 `ALL`，差异才稳定。这一点很关键——很多人在空测试库上 `EXPLAIN` 出 `ALL` 就慌张改 SQL，结论并不可靠。

**函数与运算**：`WHERE DATE(created_at) = '2024-03-01'` 用不上索引，因为 B+ 树存的是原始 `datetime`，不是函数计算后的结果，数据库没法拿日期字符串去树上定位。改成 `created_at >= '2024-03-01' AND created_at < '2024-03-02'` 即可。同类还有 `id + 1 = 100`、`amount * 2 > 500`。习惯是：只要等号或比较符号左边出现了函数和算术，就先想能不能把运算挪到右边。

**最左前缀与 `OR` 的细节**：联合索引 `(a, b, c)` 上 `WHERE b = 1 AND c = 2` 用不上，这是结论；容易被追问翻车的是范围之后的列——`WHERE a = 1 AND b > 10 AND c = 2` 里 c 基本用不上索引的有序性，只能回表后过滤，`EXPLAIN` 的 `rows` 明显偏大就说明后面的条件没帮上忙。`OR` 不是「有 OR 就失效」，而是两边都得有可用索引，优化器才可能走 index merge；只要有一边是普通列，大概率退回全表扫。帖主遇到 `WHERE a = 1 OR remark LIKE '%xx%'` 时直接拆成两条查询在业务层合并。

**判断顺序**：先 `EXPLAIN` 看 `type`、`key`、`rows`、`Extra`，确认到底走没走索引；再看 WHERE 里列有没有被函数、运算、隐式转换包住；再看联合索引顺序与查询条件是否对得上；最后才怀疑优化器——数据分布倾斜、区分度太低、回表成本太高，它主动放弃索引也是合理的。

**能区分两件事才算理解**：「语法层面用不上」是写法问题，「优化器主动不用」是成本问题。回答时把这两类分开，比背十条清单更像真排查过。
