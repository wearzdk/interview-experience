### 《参考解析》

**Agent 的工具调用闭环**

工具调用是一个「模型 → 程序 → 模型」的循环。请求里带上每个工具的名字、描述和参数 JSON Schema，模型由此知道该传什么；它返回的 tool_call 只有工具名和参数，没有函数体，由外层程序路由到真实实现，并校验参数类型与必填项，校验失败时把结构化错误回传让模型改参数，而不是抛异常断链路。执行结果序列化成一条 tool 消息追加进对话，再发起下一轮。工程上要处理三件事：同一轮多个 tool_call 并发执行、超时与重试（写操作必须带幂等键，否则重试等于重复执行）、以及超长结果先摘要或落外部存储，上下文只留引用，否则几轮就撑满窗口。

**读文件工具的分片与续读**

单次读取必须有上限，不能让一个大文件一次灌进上下文。以 1 万行、每次 2500 行为例，返回值应包含四样东西：本段内容、本段起止行号、文件总行数、以及是否还有剩余（has_more 或 next_offset）。模型判断「没读完」靠的是这些显式字段而不是自己数行数：只要 next_offset 非空，就带新偏移再调一次，直到 has_more 为 false。文件不存在要返回可区分的错误结构（错误码加原因与建议动作），不能返回空字符串——空字符串和「文件确实是空的」无法区分。超大文件还要加字节上限，某一行几兆时按字节截断并标注该行被截断。

**上下文与持久化策略**

内存只放本轮推理必需的：当前消息、本轮工具结果、临时状态；数据库放需要跨会话或跨进程存活的：会话与消息、任务与步骤状态、工具调用审计、产物引用、用户偏好。判据是「进程重启后重建得出来吗」——能重建的留内存，重建代价高或必须留痕的落库。10 轮工具调用、每轮结果都很大时，绝不能全量入库或全量留在上下文：原始产物写对象存储，库里只留元数据和引用，进上下文的是摘要或裁剪片段；接近预算时按最旧优先淘汰，并留一条压缩摘要保住主线。这套策略应由代码里的确定性规则决定，模型只在规则给的选项里取舍，否则行为不可复现、也没法压测。

**安全执行：命令判定与授权**

拆成四层。①解析与规范化：把命令和路径解成结构化形式——真实绝对路径、是否含 ../ 逃逸、是否软链到目录外，别拿字符串匹配当判据。②策略判定：工作目录白名单、危险动作清单（递归删除、下载后管道执行、改系统配置），读取 .ssh、.env 这类密钥文件必须拦截。③批准流程：命中需确认的动作先暂停，向用户展示完整命令与影响范围；批准可以是一次、本会话或长期，拒绝要把原因回给模型，授权范围显式记录、不可静默放大。④沙盒兜底：即使用户批准也在受限环境里跑，把判错的后果限制在可恢复范围内。

**Agent 评测体系**

评测要回答三件事：数据集从哪来、指标是什么、改动后怎么知道没退化。数据集分层构造：线上问题脱敏回流、按能力维度人工改写（多步推理、含糊指代、应当拒答）、对抗样本（工具报错、参数缺失、超长输入）。纯 AI 生成必须配覆盖度检查——按意图和难度聚类、每类抽样人工过一遍，否则同一种问法刷满集合，指标好看但能力没涨。指标分两层：终态（任务成功率、答案正确率，靠规则校验加模型打分加人工抽检交叉验证）和过程（步数、token、工具调用次数、错误恢复率、人工接管率）；只看终态会把碰巧答对算成能力。回归集固定，评分口径随 prompt 版本一起版本化。

**LangGraph 选型与工作流**

选它的理由是流程被显式建模成状态图：节点是函数、边是转移条件、共享可持久化的 State，天然支持分支、循环、中断和人工介入，这些在 Chain 抽象里要靠回调硬凑。工作流通常写成「入口 → 意图路由 → 检索或工具节点 → 生成 → 校验 → 条件回边 → 输出」，把 Agent 的自主循环限制在受控子图内。Checkpoint 是关键：每个节点执行后把 State 快照落盘（内存、SQLite、Postgres 都能接），同一 thread_id 可断点续跑、回放、等人工审批后继续。它和 ReAct 不是替代关系：ReAct 是循环范式，状态图是承载它的编排框架，中间还能插入确定性的固定步骤。

**RAG 切块与混合检索**

切块按结构走：Markdown 按标题层级切并把标题路径带进块内，TXT 按段落加重叠窗口，PDF 先做版面还原再按段落和表格切，别按页切。BM25 与向量互补——前者擅长专有名词、编号、缩写，后者擅长语义改写；两路别直接加分数，因为量纲不同（BM25 无界、余弦在 -1 到 1），归一化也对不齐，稳妥做法是 RRF：按排名取 1/(k+rank) 求和重排，只依赖顺序。召回后上 Cross-Encoder，是因为双塔分别编码、彼此没有交互，而它把 query 与文档拼在一起过模型，能建模词级交互；代价是耗时随候选数线性增长，所以只在 top-20~50 上跑，或蒸馏小模型控成本。

**MySQL 索引原理**

本质是用额外的有序结构换更少的扫描量。InnoDB 用 B+ 树：非叶子节点只存键和指针，一页能放几百个键，百万行表的树高通常只有 3~4 层，一次等值查询约 3~4 次页 IO，复杂度 O(log n)；没有索引就是 O(n) 全表扫描，这个差距在百万行量级上就是几百毫秒和几毫秒的区别。叶子节点按序链表串联，范围查询和 order by 能顺序读、省掉排序。索引不是免费的：占空间，写入要维护树、可能触发页分裂，所以联合索引按「等值在前、范围在后」排。被问「快多少」时给量级判断和测算方法（扫描行数、IO 次数、实测），不要报拍出来的倍数。

**慢 SQL 与接口性能排查**

先量化再动手。几百毫秒的 SQL 先 EXPLAIN 看访问类型、命中哪个索引、预估扫描行数、有没有 Using filesort 或 temporary，再对慢日志和真实返回行数；常见病因是没走索引（函数包列、隐式类型转换、前导通配 like）、索引选择性差、回表太多、一次捞太多。SQL 降到 50ms 接口还慢，说明瓶颈不在这条 SQL：看单次请求的调用次数（N+1）、连接池排队、事务持锁、结果序列化与网络、下游 RPC。接口 80ms 而 SQL 只占 10ms，就把时间切段看框架开销、模板渲染、同步日志、GC 与跨机房往返，解法是合并请求、加缓存、异步化。答题顺序是测量、定位、再优化。

**Redis Bitmap 与点赞落库**

Bitmap 把用户 id 当偏移量、一个用户一位，置 1 表示已点赞：统计用 BITCOUNT，判断单人是否点过用 GETBIT，把去重和计数压到极小内存，适合 id 连续、基数可控的场景（签到、点赞、活跃统计）；id 稀疏时会按最大偏移量分配，反而浪费，得压缩位图或分片。点赞不能只存 Redis：还要支撑「谁赞过、赞了什么、什么时候」，这是关系数据，落库用 (user_id, target_id) 唯一索引保幂等。常见做法是 Redis 抗住并发写入并原子计数，异步或定时批量落库，点赞与取消用队列保序，重复消费也不重复计数；缓存与库的最终一致靠对账兜底。

**本地 Agent 迁移到云端的架构分层**

大致分六层：接入层（网关、鉴权、限流、长连接）、会话与任务层（会话管理、任务编排、状态机与 checkpoint）、Agent 运行时层（模型调用、工具执行、上下文与记忆）、工具与沙盒层（每会话一个隔离容器，带资源与网络策略）、存储层（会话消息、向量库、对象存储放产物）、可观测层（trace、token 与成本计量）。模型接入放运行时层，用统一 Provider 抽象收敛：模型名、超时、重试、降级、密钥都由配置中心下发，上层只认「任务名到模型能力」的映射。真正难的是多租户隔离与配额、用户代码碰不到别人数据和内网、以及状态从进程内存改成可持久化的共享状态。

**算法与数据结构手撕**

括号匹配用栈：左括号入栈，右括号比对栈顶并弹出，最后栈空即合法；要主动报边界用例——空串、只有右括号、交叉嵌套、类型不匹配、超长输入，先讲思路再写代码。大数相加用字符串逐位相加处理进位，注意结果可能多一位、前导零与符号。二叉树右视图用 BFS 每层取最后一个，或 DFS 按深度优先记录右侧节点。前缀树用字符做边的多叉树，插入查询都是 O(词长)，适合前缀检索、自动补全、敏感词过滤，代价是内存开销大。堆是完全二叉树，取极值 O(1)、插入删除 O(log n)，常用于 topK。一致性哈希把节点与 key 映射到环上顺时针归属，增删只影响相邻区间，配虚拟节点解决倾斜。
