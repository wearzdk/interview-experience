### 《参考解析》

**十万行表加索引的决策**：先确认慢在哪：开慢查询日志拿到具体 SQL，用 EXPLAIN 看 type、key、rows、Extra，判断是全表扫、回表多还是排序开销。再看数据分布：10 万行对 MySQL 不算大，慢往往不是行数而是缺索引、索引失效、返回列太多或锁等待。设计索引时考虑：查询条件与排序字段的组合、联合索引的列顺序（等值在前、范围在后）、区分度、是否能用覆盖索引避免回表、写入频率（索引会拖慢写入）、现有索引是否冗余。执行前在影子库或从库验证，用 `EXPLAIN` 与真实耗时对比；上线用在线 DDL 工具避免锁表；上线后观察慢查询与写入延迟。还要考虑边界：如果查询条件组合很多，可能需要多个索引或调整查询方式（如把多条件查询拆开、用搜索引擎）。

**int 与 Integer**：int 是基本类型，存数值，默认 0，不能为 null；Integer 是包装类，是对象引用，默认 null，可参与泛型与集合。自动装箱拆箱在编译期插入 `Integer.valueOf` 与 `intValue`。Integer 缓存 -128 到 127，范围内 `==` 比较为 true，范围外比较地址为 false，必须用 equals。包装类参与运算时若为 null 会抛空指针，这是常见线上问题。

**存储位置**：int 局部变量存在栈帧的局部变量表；int 成员变量随对象存在堆里。Integer 引用本身是栈上的引用（局部变量时），它指向的 Integer 对象在堆上；缓存范围内的 Integer 来自方法区的常量池缓存（`IntegerCache`）。字符串常量、类元数据在元空间。回答时区分「引用」与「对象」是关键。

**JVM 参数**：堆大小 `-Xms`、`-Xmx`；新生代 `-Xmn` 或 `-XX:NewRatio`；Survivor 比例 `-XX:SurvivorRatio`；元空间 `-XX:MetaspaceSize`、`-XX:MaxMetaspaceSize`；栈大小 `-Xss`；垃圾收集器选择 `-XX:+UseG1GC`；G1 停顿目标 `-XX:MaxGCPauseMillis`；GC 日志 `-Xlog:gc*`；OOM 时 dump `-XX:+HeapDumpOnOutOfMemoryError`；直接内存 `-XX:MaxDirectMemorySize`。要能说清每个参数解决什么问题，以及设置不当的后果（如 Xmx 过大导致 Full GC 时间长）。

**接口耗时指标怎么测**：分三层：客户端侧（真实用户视角的端到端耗时，含网络）、服务端侧（应用内埋点，按阶段拆分：参数校验、DB、缓存、RPC、序列化）、依赖侧（DB 慢查询、下游 RT）。对比优化前后要用同一口径：同样的压测模型、同样的数据量、同样的机器配置，取 P50/P95/P99 而不是平均值，并给出样本量与观测窗口。生产上可以用灰度对比或 A/B。

**压测怎么做**：工具选 JMeter、wrk、Locust 或 Gatling，按协议与场景选。配置要点：施压模型（并发数、Ramp-up、持续时间）、请求分布（按真实流量比例混合接口）、参数化（避免缓存命中造成虚高）、监控（应用指标、DB、中间件、机器资源）、隔离（独立环境或低峰期，避免影响线上）。结论要写清瓶颈在哪一段、系统容量上限、以及压测本身是否成为瓶颈（施压机 CPU、网络）。

**AI 工具的选择与代码上线标准**：按任务选模型：长上下文与复杂重构用强模型，样板代码与单测用快模型，检索与问答用带工具的组合。评价维度是准确率、可维护性、成本、延迟。AI 生成的代码要过与人工代码相同的门槛：能通过编译与静态检查、有测试覆盖、边界与异常处理完整、无安全隐患（SQL 注入、越权、日志泄露）、经过 code review、在预发环境验证。额外要检查「看起来对但语义错」的部分：类型转换、并发、事务边界。
