### 《参考解析》

**AEC 与回声**：回声来自扬声器播放的声音被麦克风再次采集（近端回声），或通话说另一端的信号反射回来（远端回声）。不消除会导致啸叫、听感浑浊、ASR 识别率下降。客户端难点在于：播放与采集的时钟不同步（需要估计延迟并对齐）、设备与音量差异导致参考信号不准、双讲（双方同时说话）时不能把近端人声也消掉、移动端算力与功耗限制。工程上常用 WebRTC 的 AEC3，客户端负责采集参数（采样率、声道、缓冲区）、参考信号回灌、与系统音频路由（听筒/扬声器/蓝牙）配合。

**音频分段上传与拼接**：长音频按固定时长或静音点切段，每段带序号与总段数；上传用分片 + 断点续传（记录已上传分片，重试只补缺失的）；服务端按序号合并并做整体校验（时长、采样率、是否缺段）。要注意段与段之间的重叠与淡入淡出，避免拼接处爆音；AEC 要在整段连续流上做，分段处理会破坏参考信号与自适应滤波器的连续性。

**断点续传与任务状态**：上传侧用「文件哈希 + 分片索引」，服务端返回已收到的分片位图；生成侧用任务 ID + 状态机（排队/处理中/成功/失败/取消），客户端轮询带指数退避或走推送，本地持久化任务 ID 以支持杀进程后恢复；对重复提交用幂等键去重。

**IM 消息乱序**：原因有网络多路径（TCP 连接重建、消息走不同通道）、服务端多节点写入顺序不一致、客户端重试导致重复、离线消息与实时消息合并。客户端处理：每条消息带服务端生成的单调序号（seq）与会话 ID，本地按 seq 排序；用「消息 ID + 发送方 + 客户端生成 ID」去重；分页拉历史时用游标而不是页码；对「先到的后发消息」做短暂缓冲再上屏，避免界面跳动；本地数据库以 seq 为主键做幂等写入。

**RAG 链路与分工**：解析 → 切块 → 向量化 → 索引 → 检索（向量 + 关键词）→ 重排 → 拼上下文 → 生成 → 引用。回答时要分清「我写的」与「用的开源/云服务」：例如自己做了切块策略与评测、向量库用 Milvus、embedding 用某开源模型、生成用某 API。面试官追问的是你到底解决了哪一段的问题。

**线程池设计**：先定任务类型（CPU 密集 / IO 密集 / 阻塞等待），再定核心线程数与队列。固定线程池适合稳定负载、可控资源；动态（缓存线程池或按负载伸缩）适合突发流量，但要防止无限创建。大量任务到来时：有界队列 + 拒绝策略（CallerRuns 让提交者自己跑，形成反压）、按业务拆分多个池（避免互相拖死）、监控队列长度与拒绝次数、必要时降级。Android 上还要考虑主线程不能阻塞、后台任务受 Doze 限制。

**C++ 避免内存泄漏**：RAII（`unique_ptr`、`shared_ptr`、容器管理对象）、避免裸 `new/delete`、注意异常安全（构造失败要释放已分配资源）、循环引用用 `weak_ptr`、`shared_ptr` 不要从同一个裸指针构造两次（会双重释放）、注意回调里捕获 `this` 的生命周期（用 `weak_ptr` 或显式取消注册）。排查用 ASan、Valgrind、heaptrack。

**shared_ptr 与 weak_ptr**：`shared_ptr` 共享所有权，引用计数归零才析构，适合「多个持有者共同决定生命周期」；`weak_ptr` 不增加计数，用于观察、打破循环引用（父子互指、观察者模式）、缓存（`lock()` 失败说明对象已销毁）。`shared_ptr` 的控制块是线程安全的（计数原子），但对象本身不是。

**消息队列设计**：先定语义——是否需要持久化、是否允许丢、是否要顺序、消费模式（单播/广播）。结构：生产者 → 队列（有界、环形缓冲或阻塞队列）→ 消费者（单/多线程）。关键点：背压（队列满时阻塞或丢最旧）、批量与超时（攒批提高吞吐、超时保证延迟）、确认与重试（至少一次语义要配幂等）、优雅关闭（停止入队、排空、超时强制退出）、监控（积压长度、消费延迟）。

**任务编排**：把任务建成有向无环图（DAG），拓扑排序决定执行顺序，同一层的任务并行；用 `CompletableFuture`（Java）或协程/线程池 + 计数器实现；失败策略要明确（快速失败、重试、跳过后续）。检测循环依赖：拓扑排序后如果还有入度不为 0 的节点就存在环，直接拒绝。线程安全：每个任务的结果只写一次，用不可变对象或加锁；共享状态用并发容器。

**锁与同步机制**：互斥锁（`mutex`/`synchronized`）适合临界区；读写锁适合读多写少；自旋锁适合极短临界区（不能睡眠）；条件变量用于等待/通知；信号量控制并发数量；屏障（barrier）用于多线程分阶段同步；原子操作适合单变量计数。选择依据是临界区长度、是否需要睡眠、竞争强度。

**Activity 与 Fragment 生命周期**：Activity 有 onCreate/onStart/onResume/onPause/onStop/onDestroy，还有 onSaveInstanceState/onRestoreInstanceState；Fragment 多出 onAttach/onCreateView/onViewCreated/onDestroyView/onDetach。关键差异：Fragment 的 View 生命周期与 Fragment 本身生命周期不同（`onDestroyView` 后 View 已销毁，但 Fragment 还在，异步回调要判 `view != null` 或用 `viewLifecycleOwner`）；配置变更（旋转）会重建；Fragment 的 `onCreate` 可能早于 Activity 的 `onCreate` 完成。实践中用 `viewLifecycleOwner` 绑定 LiveData、在 `onDestroyView` 取消请求。

**Android 设计模式**：观察者（LiveData/Flow）、单例（Application、Manager）、建造者（Dialog、Retrofit）、工厂（ViewModelProvider）、适配器（RecyclerView.Adapter）、策略（多种加载/缓存策略）、责任链（OkHttp 拦截器）、MVP/MVVM（架构模式）。挑两个说清楚解决了什么问题即可。

**AI 辅助开发工作流**：如果只是「让模型生成代码、复制粘贴、能跑就行」，那就是 Vibe Coding；如果流程是「写清需求与验收标准 → 让模型出计划 → 人审 → 分步实现 → 跑测试 → 人工 review 关键路径」，那是有约束的 AI 辅助工程。回答时把两者的边界说清楚，并承认自己在哪些环节仍然手写。
