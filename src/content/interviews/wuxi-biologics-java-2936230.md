### 《参考解析》

**800ms 到 100ms 的 SQL 优化，要讲成一条因果链。** 先定位慢在哪：`EXPLAIN` 看 `type` 是不是 `ALL`、`rows` 扫了多少、有没有 `Using filesort` / `Using temporary`，再结合慢日志确认是单次慢还是高频调用累积。常见三类手段——索引（按查询条件的顺序建联合索引，遵守最左前缀，尽量做成覆盖索引避免回表）、改 SQL（去掉 `SELECT *`、子查询改 JOIN、别在索引列上套函数或做隐式类型转换、深分页改游标）、结构（高频聚合落汇总表）。回答时把「原来扫描多少行、加了哪个索引、降到多少毫秒」这三点说清，比背优化清单可信得多。

**11 张表聚合的优化顺序**：先把统计口径和最小粒度问清楚，能过滤的条件全部下推到最内层；大表先做预聚合再 JOIN，避免 11 张表直接连成一张宽表后行数爆炸；用小表驱动、确认连接列都有索引；注意 JOIN 后被放大的 `COUNT`，该用 `COUNT(DISTINCT)` 或先按主键去重再统计；离线场景直接建按天/按板块的汇总表，把 11 表关联从查询期挪到写入期。

**ThreadLocal 在线程池里为什么失效。** 值存在 `Thread` 对象的 `ThreadLocalMap` 里，线程池复用线程就复用了这张 map：上一个请求 set 的值会残留给下一个请求（脏数据），key 是弱引用、value 是强引用，线程不死则 value 不回收（内存泄漏）。三层解法：业务代码 `finally` 里 `remove()`；用 `TaskDecorator` 或包装 `Runnable`，在提交时捕获、执行前设置、执行后清理；直接上阿里 TTL——`TransmittableThreadLocal` 在任务提交那一刻把父线程的值快照进 holder，子线程执行时 replay、结束后 restore，配合 `TtlRunnable` / `TtlExecutors`（或 agent 修饰线程池）覆盖 `submit` 与定时任务。

**为什么要 ContextualSerializer。** 普通 `JsonSerializer` 是全局单例，拿不到「这个字段」上的注解参数；脱敏规则往往按字段不同（手机号留前三后四、身份证留前六后四、姓名只留姓），必须让序列化器知道自己在给哪个字段干活。实现 `ContextualSerializer` 的 `createContextual`，从 `BeanProperty` 上读出注解里的保留位数与掩码字符，为每个字段创建一个专属实例并缓存，这样一套注解就能覆盖所有字段，不用为每种脱敏写一个类。

**AI 编码占比接近 100% 时怎么答质量。** 把「生成」和「负责」分开：AI 出草稿（样板代码、单测、不熟的语法、日志与文档），人负责正确性——逐行读 diff、跑静态检查与单测、核心链路（计费、权限、数据写入）自己写。可以补具体做法：提示词里带项目规范与上下文、让 AI 先输出方案再写码、用 AI 反向 review 自己的改动、把重复出错的点固化成规则。面试官真正想确认的是你会不会盲信生成结果。

**两个容易被问穿的地方**：简历上的排名与平均分要能当场对上成绩单，写「前 10%」就得知道是按什么口径算的；「每段实习只干四个月」要有一个一致的解释（学期节奏、项目制实习、想换方向），不要每段给不同理由。
