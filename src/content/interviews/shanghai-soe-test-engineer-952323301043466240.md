### 《参考解析》

**Agent 的沙盒隔离**：LLM 生成的代码在隔离环境里执行——容器（Docker / gVisor / Firecracker 微虚拟机）提供文件系统与网络隔离，限制 CPU、内存、磁盘与执行时长，禁止访问内网与宿主目录，产出物只通过受控通道回传；高安全要求时用「无网络 + 只读挂载 + 一次性容器」。业务上需要在沙盒里跑的通常是代码执行、命令执行、文件解析、浏览器操作；纯文本生成不需要沙盒。回答时要补「沙盒逃逸」这一层风险：内核漏洞、容器特权模式、挂载了 docker socket 都会让隔离失效。

**Agent 测试的覆盖面**：功能正确性（能否完成任务、工具调用参数是否正确）、工具调用可靠性（失败重试、超时、参数校验）、多轮与上下文（跨轮记忆、指代消解、上下文压缩后是否丢信息）、鲁棒性（含糊需求、矛盾指令、超长输入、恶意输入与提示注入）、安全（越权访问、数据外泄、执行危险命令）、成本与性能（token 消耗、端到端时延、并发下的稳定性）、以及可观测性（每一步的 trace 是否完整可回放）。测试方式上要区分确定性断言（结果是否可执行、字段是否齐全）与模型判定（用 rubric + LLM judge，并做人机对齐）。

**Agent 性能测试怎么做**：与普通接口不同，Agent 的时延由多轮模型调用与工具执行叠加而成，所以要分层压测——单轮模型的 TTFT 与吞吐、工具调用的耗时分布、端到端任务完成时间（P50 / P95）、并发下的成功率与降级情况。指标要含 token 消耗与成本上限，压测时用固定的评估集保证可比，并注入慢上游、限流、超时来验证降级与重试策略。

**Agent 安全测试怎么做**：提示注入（把指令藏在网页、文档、工具返回里，看模型是否被劫持）、越权（能否通过工具访问其他用户的数据或系统文件）、数据外泄（是否会把敏感信息写进输出或外发请求）、工具滥用（能否被诱导执行删除、转账、发邮件）、以及成本攻击（诱导无限循环调用）。测试用例要沉淀成回归集，每次改提示词或工具都跑一遍。

**典型 bad case**：工具名或参数选错导致反复重试、把工具返回的内容当指令执行、上下文被截断后遗忘已确认的约束、格式要求没遵守导致下游解析失败、多步任务中间失败却没有回滚、对「不知道」不设边界而编造结果。每个 bad case 都要能对应到「哪一层出了问题」（提示词、工具描述、上下文组装、状态管理），这是面试官真正想听的。

**线上吞吐怎么回答**：给出可量化的口径——QPS / 并发会话数、P95 端到端时延、单会话平均模型调用次数与 token、上游限流下的排队策略。没有精确数字时给量级与瓶颈位置（卡在模型上游还是工具执行），并说明扩容方式（多实例 + 队列削峰 + 模型侧限流与降级）。

**SSE 与 WebSocket**：SSE 是基于 HTTP 的单向服务端推送（`text/event-stream`），实现简单、自动重连、可穿过大多数代理与 CDN，适合「服务端持续输出、客户端只收」的场景（大模型流式输出、进度推送、通知）；WebSocket 是全双工长连接，需要握手升级与心跳保活，适合双向实时交互（协同编辑、聊天、游戏）。AI 场景选 SSE 的主要原因是输出是单向流、能复用 HTTP 的鉴权与网关设施、断线后按 offset 续传更容易实现。

**命令类问题**：TCP 端口连通性用 `nc -zv host port`、`telnet host port`、`curl -v telnet://host:port`，服务端侧用 `ss -lntp` / `netstat -lntp` 看监听。vim 光标到行尾是 `$`（普通模式），到行首是 `0` / `^`。查看文件行数 `wc -l file`。Docker 查容器日志 `docker logs -f --tail 100 <容器名>`，带时间戳 `-t`，看某时间之后 `--since`。

**乐观锁与悲观锁**：悲观锁假设冲突会发生，先加锁再操作（`select ... for update`、Redis 分布式锁），并发高时锁竞争与死锁风险大，适合写多且冲突频繁；乐观锁假设冲突少，读时不加锁，写入时用版本号或 CAS 校验（`update ... where version = ?`），冲突则重试，适合读多写少，代价是失败重试与 ABA 问题。

**判断链表有环**：快慢指针，慢指针走一步、快指针走两步，相遇则有环；相遇后把一个指针放回头节点、两者同速前进，再次相遇处即环入口。时间 O(n)、空间 O(1)。也可以用哈希表存访问过的节点，但空间 O(n)。
