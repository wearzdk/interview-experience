### 《参考解析》

**乱序完成与并发写的一致性**：两次评估乱序返回、中间还有人工改字段，本质是两个写者各自基于旧快照覆盖对方。手段要叠加使用：记录带版本号或递增 revision，写入时执行 `UPDATE ... WHERE id = ? AND version = ?`，影响行数为 0 就说明中途被改过，转为重试或合并；评估结果以「一次评估」为不可变事件追加，最终状态由事件归并得出，而不是整行覆盖；同一实体的写用乐观锁或按实体分片的串行队列；跨服务重试用幂等键去重。还要显式定义字段级的优先级——人工修改与机器结果谁覆盖谁，否则锁只能保证不丢更新，保证不了语义正确。

**DDD、本体建模与工具开放的分工**：DDD 解决业务边界与一致性边界，产出限界上下文与聚合根；本体建模解决「业务概念对模型可解释」，把实体、关系、动作的语义统一，使模型知道有哪些对象、对象之间是什么关系；工具能力开放解决「模型怎么安全地调用」，把接口包成带语义描述、参数 Schema 与副作用声明的工具，并配鉴权与审计。三者层次不同：DDD 是代码与团队的组织方式，本体是语义层，工具开放是执行层。缺任何一层都会出现「模型能调但不懂业务」或「懂业务却没有可调入口」。

**JSON Schema 的能力边界**：能降低的是结构与类型错误——字段缺失、类型不符、枚举越界、必填项漏传，这些在调用前即可拦下，并让模型自我修正一轮。降不了的是语义错误：参数类型正确但业务上不成立（时间范围写反、资源 ID 属于别的租户）、多步操作的顺序错误、该查证的事实靠猜。补充手段是业务校验（存在性、归属、权限、数值范围）、执行前的预检或 dry-run，以及把常见失败样例写进工具描述。回答时要明确区分「Schema 保证形状」与「业务保证含义」。

**错误率下降的口径与过拟合**：先定口径：分母是一次会话、一次任务还是一次工具调用；什么算错误，是任务失败、结果不可用还是需要人工接管；由谁判定，自动校验还是人工标注。口径不定，两个百分比之间无法比较。避免只对样本有效的手段：规则从错误类型归纳，而不是对单条样本硬编码；保留与调参集不同分布的回测集（不同业务方、不同时间段、不同文档版本）；上线后按周采样复核，同时监控规则命中率与误杀率；规则增多后做消融，确认每条仍有独立收益。

**排障 Agent 的预算与 60 秒时延**：12 次工具调用、60 秒返回，意味着平均每次调用连同模型思考只有 5 秒左右，设计上必须并行与剪枝。先并行拉取指标与最近变更，这两类信息最常定位问题；再依据结果决定是否查日志与知识库。工具返回要做摘要与截断，避免大段日志进入上下文后每一步都变慢。给整个任务设总预算（步数、token、墙钟时间），到阈值就收敛成「结论加待确认项」，而不是继续试。知识库检索放在前几步，用历史案例缩小假设空间，比后期盲目重试更省预算。

**人工审批的状态机**：状态至少要有等待审批、已通过、已拒绝、已超时、已取消，加上执行中与成功、失败两个终态。等待审批时任务必须挂起并持久化，不能占着进程或连接；审批通过后从挂起点继续，而不是从头重跑；超时要定义默认动作，多数场景是拒绝并回滚已做的准备动作；取消要能中断正在等待的调用。审批人、审批时间、审批意见与当时的参数快照一并落库，事后才能回答「批的到底是什么」。

**重启后的恢复起点与副作用幂等**：恢复点不能只存「第几步」，要存可重放的状态：已完成步骤的结果、已产生副作用的标识、当前待执行的工具与参数。副作用工具必须幂等：调用前写意图记录，调用后用同一幂等键回写结果；重启后先查该键是否已有结果，有则跳过执行直接取结果。对无法幂等的操作（发消息、扣款、提交表单），用「预占加确认」两阶段，或要求外部系统支持去重键；确实做不到的，恢复时转人工确认，不自动重试。

**单 Agent 与多 Agent 的取舍**：多 Agent 的收益来自上下文隔离与职责分工——不同的工具集、不同的提示词、可并行的子任务；代价是通信开销、状态同步、错误沿链路传播与调试难度上升。判断标准是拆开之后每个 Agent 的上下文是否显著变短、工具集是否显著变窄、子任务是否真能并行。若几个 Agent 共享同一份上下文、串行调用同一批工具，拆开只会多出几次模型调用。需要合并的典型场景是链路短、状态强耦合、要求全局一致判断（例如同一个工单的多步处置），此时单 Agent 加清晰的工具分层更稳。

**AI 生成代码的评审重点**：测试通过只证明被覆盖的路径正确。半小时评审一个点赞接口，优先看四件事：并发，同一用户重复点赞与计数更新是否原子，是否用唯一索引或原子自增而不是先查后写；幂等，重试与消息重复会不会产生多条记录；一致性，缓存与数据库的更新顺序、事务边界、失败回滚是否成立；权限与边界，谁能点赞、对象是否存在、参数是否校验。其次看可观测性与错误处理，异常是否被吞掉、日志是否带请求标识。测试本身也要看：是否只覆盖正常路径，断言是否真的验证了副作用。
