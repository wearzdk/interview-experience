### 《面试题目》

1. 接口自动化覆盖核心链路 70%，字段改名的那一周，用例是谁改的？
2. 失败的断言看的是返回码，还是库里的数据？
3. 接口字段还在变的时候，用例应该一次铺满还是先守几条？
4. 用例共用一个测试账号时，怎么保证结果可信？
5. 断言失败时你保留哪些现场信息？
6. 用例接进流水线之后，红灯由谁处理、怎么区分产品缺陷和脚本问题？
7. 同一类误报反复出现，你怎么收敛？
8. 页面自动化与接口自动化各自适合留什么？

### 《参考解析》

**先守三条，等接口稳定再扩**：接口刚交付时字段与状态流转都在改，此时铺满用例，第二天字段改名就会有几十条断言同时变红，团队会直接关掉任务。可行的做法是先固化三条与资金和数据安全直接相关的用例：创建成功——除返回成功外，核对库中存在且仅存在预期的那一行；重复提交——同一请求号再打一次，不得多出第二行订单或第二次库存扣减；缺必填字段——失败提示明确，且数据库没有产生脏数据。路径连续一个版本没有变化，再补状态流转与越权。讲选型时可以说明：这三条挡住的是脏数据，比先追求分支覆盖更划算。

**断言要落到数据，不只看返回码**：只断言 HTTP 200 是最常见的问题。同样是「创建订单」，只看返回码时，重复点击产生两行数据也发现不了；断言订单号唯一且库存只减一次，这条缺陷在合并前就会变红。写断言时把「接口返回、库中状态、下游副作用」三层分开：返回层校验结构与错误码，数据层校验目标表的行数与关键字段，副作用层校验库存、余额、消息是否只发生一次。失败信息中带上请求号与关键字段，打开就能与日志对照。

**数据与环境隔离**：共用一个测试账号，谁先跑谁就把状态改掉，后面的失败看起来像产品缺陷。可行的做法是每条用例自己准备数据、自己清理：账号、优惠券、库存由工厂方法生成，不手改数据库；用例之间不共享可变状态；并行执行前先确认没有隐式依赖，不能并行的用例放到不同阶段。第一条用例把用户改成禁用、第二条还用这个用户登录，是这类问题最典型的例子，讲清这个例子比说「我们做了数据驱动」有效。

**红灯的闭环**：接进流水线之前先定归属。红灯当天区分两类：产品缺陷提单给开发，脚本问题当天修。同一类误报出现两次，就改等待或断言，而不是再加一行重试；重试只能作为辅助，第一次失败的现场要留下。连续多次无人处理的任务从流水线里拿掉，留着只增加噪音。页面自动化只保留主路径，接口用例进入每次合并前的检查，这个分工的依据是变更频率与断言稳定性。

**讲项目准备三句话**：挑一个真正维护过的接口模块，说明最初只留了哪三条、后来为什么增加或删减、有一次失败是靠哪条断言发现的。这三句话比覆盖率百分比更难被追问穿。数字可以报，但要放在这三句话之后；若被追问框架，再补一句为什么留在接口层、不先铺 UI——框架可以更换，断言与数据隔离换不掉。
