2. 过去做过的 Agent 项目里，任务拆解是怎么设计的？
3. 工具调用失败时怎么兜底？
4. 多轮对话中如何保持上下文一致性？
5. 有没有遇到过模型输出不稳定、需要人工干预的情况？
6. Agent 的架构为什么选单 Agent 还是多 Agent 协作？
7. 记忆模块是怎么设计的？
8. 检索增强在哪些环节起作用？
9. 提示词迭代的过程是怎样的？效果怎么评估？
10. 为什么选择这个岗位？对工作地点怎么考虑？
11. 过往经历中遇到分歧怎么处理？
12. 对自己未来一两年的成长预期是什么？

### 《参考解析》

**Agent 的任务拆解要讲「拆分依据 + 失败处理」**：拆分依据通常是可验证性——每一步都要有明确的输入输出和判定标准，能独立重试；不能把「查资料并写报告」当成一步，而要拆成检索、筛选、成稿、核对。失败处理分三层：工具层做参数校验与幂等重试（只对超时、限流重试，参数错误直接回灌给模型改）；编排层设最大步数与无进展检测，超了就降级成「先给部分结果 + 说明缺口」；产品层保留人工接管入口。

**上下文一致性靠「显式状态」而不是长对话**：把关键约束（用户偏好、已确认的事实、禁止项）抽成结构化槽位，每轮注入；历史消息做滚动摘要并保留数字与否定条件；工具结果只保留结论和引用，原文按需检索。这样即使对话很长，模型看到的「事实底座」是稳定且短的。

**单 Agent 还是多 Agent，取决于「职责是否需要独立上下文与独立工具权限」**：单 Agent 简单、链路短、调试容易，适合任务边界清晰的场景；多 Agent 适合需要不同角色视角（检索、审校、执行）或需要隔离权限的场合，代价是编排复杂、成本高、错误传播链变长。回答时给出你的选择依据和实测结果，比说「多 Agent 更先进」可信。

**提示词迭代要有对照组**：固定一批真实用例做评测集，每次只改一个变量（指令、示例、输出格式），跑同一批用例对比通过率与人工评分；把失败样本沉淀成回归用例。面试官问「效果怎么评估」，想听的是这套流程，而不是「感觉变好了」。

**HR 环节的准备方式**：把项目按「背景、方案、难点、结果」四块各准备一分钟版本与三分钟版本；分歧类问题用真实事件 + 你的判断依据 + 结果；成长预期要与岗位日常对齐（比如一年内独立负责一个模块的端到端交付），而不是空泛的「成为技术专家」。
