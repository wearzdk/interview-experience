### 《参考解析》

**重构的正确性验证**：把验证拆成三段递进。空跑（shadow run）是让新旧两套规则同时吃历史流量或离线样本，只记录不生效，逐条比对判定结果；灰度是按用户或流量比例切一小部分真实请求到新框架，观察业务指标与错误率；diff 对比是把同一批输入的两套输出做结构化比对，按「结论不同」「同类但字段不同」「新框架报错」分类统计。空跑阶段的关键是样本要覆盖边界——历史流量里长期不出现的规则与字段，空跑永远发现不了问题，因此要额外构造规则覆盖率报告，把未命中的分支单独补样本。

**前置过滤为什么干扰 diff**：如果前置过滤在新旧链路里执行时机或顺序不同，被过滤掉的请求会进入不同的分支，两边的样本集合就不再一致，diff 出来的差异里混着「样本不同」而不是「规则不同」。处理办法是把前置过滤的结果作为固定输入喂给两边，或者先对齐过滤逻辑再比对后续步骤，并对被过滤的样本单独统计数量与原因。

**字段迁移遗漏为什么上线才暴露**：空跑通常只覆盖了读路径或部分写路径，迁移遗漏的字段在读取时被默认值兜住，看起来一切正常；一旦新链路承担真实写入与下游消费，缺失字段才在序列化、对账或下游解析时炸出来。根治办法是把「字段清单」做成契约测试：按 schema 逐一生成用例，比对新旧两套输出的完整字段集合，而不是只比业务结论。

**MVCC 与 ReadView**：InnoDB 在每行记录上维护 `DB_TRX_ID`（最后修改它的事务 id）与 `DB_ROLL_PTR`（指向 undo log 的版本链）。快照读时用 ReadView 判断某个版本是否可见，ReadView 里有当前活跃事务 id 列表、最小活跃 id、下一个待分配 id 与创建者事务 id。读已提交（RC）在每条 SELECT 前都新建 ReadView，所以能看到别人已提交的最新数据；可重复读（RR）在事务的第一条快照读时建一次 ReadView 并复用，因此整个事务看到同一份快照。RR 下当前读（`SELECT ... FOR UPDATE`、UPDATE、DELETE）仍读最新版本，这解释了「快照读与当前读结果不一致」的现象。

**B+ 树为什么胜出**：B+ 树非叶子节点只存键、不存数据，同样大小的页能容纳更多键，树高更低，一次查询的磁盘 IO 更少；叶子节点用双向链表串起来，范围查询与排序只需顺着链表扫，不用回到上层；数据都在叶子层，查询路径长度稳定。B 树每个节点都带数据，扇出小、树更高；红黑树是二叉结构，百万级数据树高约 20 层，每层一次随机 IO，磁盘场景不可接受。

**缓存与数据库一致性**：主流做法是「先更新数据库，再删除缓存」（Cache Aside），并给删除失败加重试或走 binlog 订阅（如 Canal）异步删除，用最终一致兜底。先删缓存再更新数据库的窗口更大：删完到更新完成之间，读请求会把旧值重新写回缓存，之后长期是脏数据。并发下的经典问题是最先读到旧值的那次回填晚于删除，解决办法是延迟双删（更新后延迟几百毫秒再删一次）、给缓存加版本号，或对强一致要求高的数据直接读主库并加分布式锁。

**Redis 分布式锁**：`SET key value NX PX 30000` 一条命令完成「不存在才设置 + 过期时间」，避免 `SETNX` 与 `EXPIRE` 两步之间进程挂掉造成死锁；value 用唯一标识，释放时用 Lua 脚本比对后再删，防止误删别人的锁。单机 Redis 在故障切换时可能丢锁，强一致场景用 Redlock 或改用 etcd / ZooKeeper。锁只解决互斥，续期（watchdog）与可重入要按业务补。

**MySQL 实现分布式锁**：建一张锁表，`lock_key` 加唯一索引，抢锁即 `INSERT`，成功者持有；释放即删除该行。为了防持有者崩溃，表里带 `owner`、`expire_at`，抢锁失败时用 `UPDATE ... WHERE lock_key = ? AND expire_at < NOW()` 抢占过期锁。优点是简单、与业务数据同库可放进同一事务；缺点是数据库成为热点、锁等待要靠轮询、长事务会拖住连接，只适合低频场景。

**幂等与订单防重**：幂等是同一个请求执行多次与执行一次的结果一致。实现分四类：唯一索引（最可靠，订单号或「业务键 + 用户」建唯一键，重复插入直接报冲突）、状态机（只允许从待支付流转到已支付，重复回调命中状态不符即返回成功）、去重表 / 分布式锁（按请求 id 加锁或落去重记录）、令牌机制（下单前先领 token，提交时校验并删除）。订单场景通常组合使用：客户端带幂等号，服务端唯一索引兜底，支付回调再按订单状态判重，三层里任意一层生效都不会重复扣款。

**手写死锁**：两个线程以相反顺序获取两把锁即可稳定复现——线程 A 先锁 `lock1` 再请求 `lock2`，线程 B 先锁 `lock2` 再请求 `lock1`，中间各睡一小会儿放大交错窗口。用 `synchronized` 嵌套或 `ReentrantLock.lock()` 都能写；面试官追问「为什么不用 JDK 的 API」，答 `ReentrantLock` 提供 `tryLock(timeout)`、可中断、公平锁与条件队列，能在拿不到锁时放弃，从设计上避免死锁，而 `synchronized` 只能阻塞等待。实际排查用 `jstack` 看 `Found one Java-level deadlock`。
