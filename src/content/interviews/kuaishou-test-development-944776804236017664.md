### 《参考解析》

**MySQL 四道题是一条线**。事务特性是 ACID，重点能讲清隔离级别的实现：InnoDB 用 MVCC 读快照 + 间隙锁防幻读，RR 下大部分快照读不加锁、当前读加锁。聚簇索引指数据行本身就挂在主键 B+ 树的叶子节点上，所以主键查询一次 B+ 树就能拿到整行，二级索引查到主键后要再回表一次——这也是「覆盖索引」能省掉回表的原因，以及为什么主键要短、要单调（UUID 做主键会让页分裂变频繁）。定位慢 SQL 的标准路径是先开 slow_query_log 抓到语句，用 EXPLAIN 看 type、key、rows、Extra（出现 Using filesort / Using temporary 就要注意），再针对性加索引、改写成覆盖索引、避免在索引列上做函数运算和隐式类型转换。

**JVM 手动 GC 这题容易答偏**。`System.gc()` 只是建议，能不能真的触发取决于 `-XX:+DisableExplicitGC` 有没有开，以及用的是哪种收集器；生产环境通常建议关掉显式 GC，因为它会打断正常的回收节奏、引发 STW。要谈内存问题更该谈的是怎么定位：`jstat -gcutil` 看各代占用和 GC 频率、`jmap -histo` 看对象分布、`jmap -dump` 拿堆快照配合 MAT 找支配树，而不是靠 System.gc() 去「试」。

**压测这组题考的是方法论不是工具**。场景设计要覆盖正常峰值、超峰值、以及长时间稳定性（soak test），每个场景都要有明确的通过标准——通常是 P99 响应时间、吞吐量、错误率三条线一起看，只写「TPS 达到 5000」是不够的，因为可能是靠加并发堆出来的。压测报告的结构：压测目标与场景、环境与数据量级（数据量不真实是最常见的失真原因）、脚本与参数、性能曲线（并发数与 TPS/RT 的关系拐点）、发现的瓶颈与定位过程（CPU、GC、慢 SQL、连接池、锁竞争）、结论与建议。

**容错测试要能讲出注入手段**。网络中断用 tc netem 加丢包或断链、或用 iptables DROP；服务宕机直接 kill 进程或用容器暂停；延迟用 tc 加 delay；下游超时用 mock 服务。验证的不仅是「有没有报错」，而是「降级是否生效、重试是否幂等、监控有没有告警、恢复后状态是否自动收敛」。这几条能说出来，比背压测工具名有用得多。

**直播间测试用例**要有分类意识：功能（开播、连麦、礼物、弹幕、回放）、并发（万人同时进房、礼物刷屏）、弱网（切网、丢包下的音画同步）、异常（主播掉线重连、礼物重复到账）、兼容（不同机型与系统版本）、数据（在线人数、GMV 统计是否准确）。按「场景 × 维度」列成表格，面试官一看就知道你有没有真的测过。

**两道算法**：回文串判断的双指针写法是左右各一个指针向中间靠，遇到不等就 false，时间 $O(n)$、空间 $O(1)$；如果允许删除一个字符再判断，就退化成「遇到不等时分别尝试跳左或跳右」。两数之和用哈希表一遍扫，对每个数查 `target - num` 是否出现过，时间 $O(n)$。快手那道两数之和当时输入输出格式有问题，跑不出结果，处理办法是把思路讲清楚——这在很多场次里是能被接受的。
