### 《参考解析》

**沙箱的实现骨架**：四层——隔离层负责进程与文件系统视图（容器、namespace、写时复制工作区），策略层负责路径、网络、命令的准入判断，资源层限制 CPU、内存、进程数与执行时长，审计层记录每次工具调用的命令、退出码与产物。真正难的不是起一个容器，而是把「模型想做什么」翻译成可判定的策略，并在拒绝时给出模型能理解并修正的原因。

**调研他人实现的可靠方法**：优先读源码与官方文档，其次用行为测试反推——构造几个边界命令观察其拦截结果与报错文案，再对照其 release note 与 issue。只看二手博客容易把推测当成事实，面试里被追问「你怎么确认的」时要能说出具体来源。

**本地沙箱与云端沙箱的差别**：比较维度是隔离强度、启动开销、环境一致性、快照与恢复能力、以及可观测数据的获取方式。本地进程级隔离启动快、贴近开发者环境，但隔离弱、清理不彻底；云端微虚拟机隔离强、可快照，但启动慢、需要网络与镜像管理。选型取决于要跑的是不可信代码还是自己的脚本。

**Go 语言的特点**：调度器把大量 goroutine 复用到少量线程，适合 IO 密集的服务；接口是隐式实现，便于解耦；GC 是并发的，停顿短但仍有分配压力，热路径要控制逃逸与临时对象；错误处理显式，样板多但可读性稳定。短板在泛型表达力与运行时调试的直观性。

**Harness 的组成**：可以按六块讲——模型接入与路由、上下文构建与压缩、工具层（schema、执行、权限）、运行循环（规划、调用、终止条件）、执行环境（沙箱与资源）、观测与评测（轨迹、成本、成功率）。再往外是产品层的人机交互与审批。Harness 的价值在于把模型的非确定性收敛成可运维的系统行为。

**上下文冗余或不足**：冗余靠分层与压缩解决——稳定指令与工具表放前缀，历史按轮次裁剪与摘要，检索结果按相关性阈值过滤；不足靠主动补全——缺文件就让工具去读、缺约束就反问用户、缺领域知识就检索。产品上应把「模型还需要什么」显式化，例如在关键步骤前生成待确认清单，而不是让模型在信息缺失时自行编造。

**跨 Session 的重复上下文**：把稳定部分（项目说明、用户偏好、长期目标）沉淀为可检索的记忆，会话开始时按需注入摘要；易变部分（当前任务状态、临时决定）留在会话内。Memory 解决的是「同一事实不要每次重新问」，不是「把所有历史都带上」。

**工具调用与可观测性的改进方向**：工具侧可以做参数校验前移、结果裁剪、并行调用与失败重试策略；可观测侧需要把一次任务的完整轨迹（模型输入输出、工具参数与结果、耗时与成本）串成可回放的链路，并在此基础上做成功率、平均步数、无效调用率的统计，否则优化没有依据。

**LRU 的实现**：用哈希表加双向链表。哈希表存 key 到链表节点的映射，链表头放最近使用、尾部放最久未使用；Get 命中后把节点移到头部，Put 时若 key 存在则更新并移到头部，不存在则新建插到头部，容量超限时删尾节点并从哈希表移除。必须是双向链表，因为删除任意节点需要 O(1) 拿到前驱，单链表删除要找前驱，退化成 O(n)。并发场景还要加锁或分片，并按需处理「写入时正在读」的一致性问题。
