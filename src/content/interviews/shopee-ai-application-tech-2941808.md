### 《面试题目》

1. ReAct 核心思想是什么？与 CoT 有什么区别？ReAct 的短板是什么？
2. MCP 协议是什么？在 Agent 工具生态中起什么作用？Function Calling 与 MCP 有什么异同？
3. 长上下文工程常用哪些手段？超长上下文在位置编码、注意力开销、信息遗忘上的挑战与解决方案是什么？
4. RAG 的完整链路是什么？检索阶段、生成阶段各自的幻觉类型与缓解办法是什么？
5. Function Calling 的底层原理是什么？什么时候会出现格式错误？提升调用准确率的方案有哪些？
6. Agent 的多层记忆如何划分？会话记忆、个人记忆、团队记忆在存储载体、生命周期、检索方式上有什么差异？
7. 长时记忆如何做选择性遗忘？如何防止记忆库无限膨胀？
8. 多用户共用 Agent 时，记忆归属会冲突，如何设计权限隔离？

### 《参考解析》

**ReAct 与 CoT**：CoT 是在一次生成里把推理过程展开，模型仍然只依据自身参数与输入作答；ReAct 把「推理」和「行动」交替起来——Thought 决定下一步做什么，Action 调用工具，Observation 把外部结果写回上下文，再进入下一轮 Thought。区别在于信息来源：CoT 靠模型内部知识，ReAct 靠外部反馈，因此 ReAct 能处理需要实时数据、计算或多步操作的任务。短板也很明确：① 步数一多，上下文迅速膨胀，早期观察被挤出窗口；② 错误会沿轨迹传播，一次错误的工具调用或误读的 Observation 会让后续推理全错；③ 循环与死锁，模型可能反复调用同一个工具；④ 延迟与成本随轮次线性增长；⑤ 对工具描述与返回格式高度敏感。工程上要配最大步数、工具结果摘要、失败重试与终止条件，并记录完整轨迹便于回放。

**MCP 与 Function Calling**：Function Calling 是模型侧的能力——把工具定义（名称、描述、JSON Schema 参数）放进请求，模型输出一个结构化的调用意图，由宿主程序执行后把结果回传。MCP 是连接协议——把「工具 / 资源 / 提示」的发现与调用标准化，让一个客户端可以接入多个服务端的工具，解决的是生态与互操作，不是模型如何生成调用。两者是互补关系：MCP Server 暴露的工具，最终仍以 Function Calling 的形式进入模型上下文；MCP 额外提供工具发现、能力协商、传输层与权限边界。回答时要点明「协议层 vs 模型能力层」，不要把 MCP 说成一种新的推理方式。

**长上下文工程**：常用手段分四类。① 位置编码：RoPE 外推（NTK 插值、YaRN、位置插值）让模型在训练长度之外仍能区分位置；ALiBi 用距离惩罚替代绝对位置。② 注意力开销：FlashAttention 降低显存读写、稀疏 / 滑窗注意力、GQA / MQA 减少 KV 头数、KV Cache 量化与分页（PagedAttention）、前缀缓存复用。③ 信息组织：分段摘要、层次化摘要、把长文改写成结构化事实、按需检索而不是全塞。④ 训练侧：长上下文继续预训练、位置编码与数据配比调整。信息遗忘的根因是注意力被稀释与「lost in the middle」——关键信息放在长上下文中部时召回明显下降。缓解办法是把关键约束放在开头和结尾、显式复述任务、用检索把相关内容集中到少量 token、以及在每轮把「当前状态」重写成短摘要，而不是依赖模型自己记住。

**RAG 的两段幻觉**：检索阶段的幻觉是「该找到的没找到」或「找到了错的」——切分粒度不当、embedding 与查询语义不匹配、关键词与向量单路召回覆盖不足、元数据过滤过严、top-k 太小或太大引入噪声。缓解：混合检索（BM25 + 向量）、查询改写与多查询、按文档结构切分并保留标题路径、加 rerank、按证据阈值决定「不答」。生成阶段的幻觉是「有证据但答错」——忽略检索内容凭参数记忆作答、把多个来源拼接成不存在的事实、数字与单位错配、引用与结论不对应。缓解：要求逐句引用来源、把回答限制在给定证据内、给出「证据不足」的出口、对数字与实体做程序化校验、生成后再做一次「结论是否被引用支持」的检查。两段要分开评估：召回率、MRR 是一组指标，答案正确率与引用准确率是另一组。

**Function Calling 的底层原理**：工具定义被序列化进系统提示或专用字段，模型在解码时生成符合约定格式的调用（早期靠提示词与 few-shot，现在多用受约束解码 / 语法引导，把 JSON Schema 转成状态机限制合法 token）。格式错误常见于：Schema 太复杂或嵌套过深、参数有大量可选与联合类型、工具描述含糊导致模型选错工具、上下文里工具太多互相干扰、模型被要求同时输出自然语言与 JSON、以及流式输出被截断。提升准确率的做法：工具数量控制在当前任务真正需要的范围、名称与描述写清「什么时候用 / 什么时候不用」、参数用枚举与示例收敛、必填项尽量少、给 2–3 个正反例、返回结构化错误让模型能重试、对关键调用做参数校验与二次确认。不要把「加一句请严格输出 JSON」当成主要手段。

**三层记忆**：会话记忆活在当前上下文与短期存储里（消息列表、滚动摘要、工具观察），生命周期等于一次会话，检索就是按时间顺序取最近若干轮加摘要；个人记忆跨会话绑定单个用户（偏好、历史结论、长期目标），通常放结构化数据库加向量索引，按用户命名空间检索，生命周期以月计并需要用户可见可删；团队记忆是共享知识（规范、案例、术语），放在文档库或知识库中，按组织 / 项目命名空间检索，生命周期最长，需要有版本、来源与权限。三者的差别不只是存储，还包括写入权限（谁能写）、一致性要求（团队记忆要求可追溯）与删除策略（个人记忆要支持导出与删除）。

**选择性遗忘**：不能只靠「超过 N 条就删最旧」。可用四层：① 重要性打分，写入时按来源、被引用次数、与用户目标的相关度打分；② 时间衰减，按半衰期降权，长期不被召回的自然沉底；③ 合并与抽象，把多条同类事实压成一条结论，原文降级为可追溯的来源；④ 容量与配额，按用户 / 租户设上限，超限时按分数淘汰并保留索引。还要有去重（近义合并）与冲突处理（新事实覆盖旧事实时保留版本），以及「被用户明确要求忘记」的硬删除通道。评估上要看「召回是否仍命中关键事实」与「存储增长是否收敛」两个指标，而不是只看删了多少。

**多用户共用 Agent 的记忆隔离**：核心是「写入带归属、检索带过滤、越权不可见」。① 命名空间按租户 / 用户分层，物理上可分库分表或至少分区；② 每条记忆写入时记录 owner、可见范围（私有 / 团队 / 公开）与来源；③ 检索时在查询层强制附加权限过滤，不能先召回再在应用层筛（会泄露到日志、缓存与模型上下文）；④ 团队共享记忆走显式的授权模型（角色 / 群组），跨用户引用要校验；⑤ 缓存键必须包含租户与权限版本，避免串号；⑥ 审计每一次跨范围读取。若多用户共用同一个模型会话，还要在上下文里明确「当前用户是谁」，并对工具调用做用户级鉴权，防止 A 的会话读到 B 的记忆。
