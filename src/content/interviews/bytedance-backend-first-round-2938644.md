### 《参考解析》

**RPC 与 KV 的「主路径」要讲到可验证的细节。** 面试官问主路径，考的是能否把一次请求从入口讲到出口，并在每一步说清你做了什么、瓶颈在哪。RPC 的主路径是：客户端经 stub 组装请求、序列化、寻址与负载均衡、建连与多路复用、服务端解码、派发到线程池或协程、执行业务、回包与超时重试。要主动给出数字，例如单机 QPS、P99、序列化耗时占比、连接复用率，以及你为此改过哪一段。KV 的主路径分读写两路：写路径进 WAL、写 memtable、memtable 满了转 immutable 并落成 SSTable、后台 compaction 合并；读路径先查 block cache 与 memtable，再按层查 SSTable，Bloom filter 用来跳过不含该 key 的文件。被追问「你自己写了哪一块」时，答负责的模块、当时的取舍与验证方式，比复述整体架构有效。

**MySQL 的分层与一条 SQL 的执行顺序。** Server 层包含连接器（鉴权、连接池）、查询缓存（8.0 已移除）、解析器（词法语法分析生成语法树）、优化器（选索引、决定 join 顺序、条件下推）与执行器（按执行计划调用引擎接口）；引擎层是可插拔的存储引擎，InnoDB 负责索引组织、事务、锁与崩溃恢复，MyISAM 只提供表级锁与非事务存储。一条 SQL 的执行顺序可答成：连接器取连接 → 解析器生成语法树 → 优化器产出执行计划 → 执行器逐行向引擎取记录 → 引擎在 Buffer Pool 里读写页并记 redo。补充两阶段提交有助于加分：redo 处于 prepare、写 binlog、redo 置 commit，保证崩溃后主从一致。

**LSM tree 与 InnoDB 的差异，实质是读写放大之间的取舍。** LSM 把随机写转成顺序写：写只追加 WAL 与内存表，落盘是整块顺序写 SSTable，因此写吞吐高、写放大可控；代价是读要跨多层查找、需要 compaction 持续整理，读放大与空间放大更高，compaction 还会抢占 IO 与 CPU。InnoDB 是 B+ 树聚簇索引，数据按主键有序存放，点查与范围查都是 O(log n) 级别的页访问，读性能稳定、事务与 MVCC 成熟；代价是随机写要维护页分裂与 Buffer Pool 脏页刷盘，写放大明显。「为什么选 LSM」的回答应落到负载特征：写多读少、写入吞吐优先、能接受读路径多一层缓存，就选 LSM；读多写少、需要强事务与范围查询，选 InnoDB。

**虚函数的实现。** 含虚函数的类，对象头部有一个 vptr 指向该类的虚表，虚表在只读数据段、编译期由编译器生成，槽位按声明顺序排列；派生类覆写时替换对应槽位，多继承会持有多个 vptr 并需要 this 指针调整。要补两个常见追问：构造与析构期间 vptr 分阶段更新，此时调用虚函数只会调到当前正在构造或析构的那一层；通过基类指针 delete 时基类析构必须是虚函数，否则派生类资源不会释放。

**RAII 与三种智能指针。** RAII 是把资源的生命周期绑定到对象生命周期：构造时获取、析构时释放，栈展开与异常路径都能保证释放，锁的 guard、文件句柄、内存都适用。`unique_ptr` 独占所有权、大小与裸指针一致、只能移动，应作为默认选择；`shared_ptr` 共享所有权，控制块里原子维护强引用与弱引用计数，拷贝有原子操作开销，互相持有会形成循环引用；`weak_ptr` 不增加强引用计数，用来观察与打破循环，使用前 lock 提升并判空。补充一句工程建议：优先 make_shared（一次分配同时容纳对象与控制块），跨线程传递所有权用移动而不是拷贝。

**有栈协程与无栈协程。** 有栈协程每个协程持有独立栈，可在任意函数调用深度挂起与恢复，写法接近同步代码，代价是栈内存（通常几十 KB 到 MB）与上下文切换成本，适合协程数量有限的场景。无栈协程不持有独立栈，编译器把函数改写成状态机、挂起点状态存在堆上的协程帧里，内存开销小、可支撑海量并发，但只能在协程函数体内的挂起点挂起，无法穿透普通函数调用。C++20 的 coroutine 属于无栈，Go 的 goroutine 属于有栈。与异步回调相比，协程把「回调地狱」里的状态显式保存在局部变量中，控制流是顺序的，可读性与异常处理都更好。

**系统调用与 `ls` 的数量。** 系统调用是用户态程序请求内核服务的唯一入口，通过软中断或 syscall 指令陷入内核，伴随特权级切换与上下文保存，因此单次开销远高于普通函数调用，批量与小消息合并是常见优化方向。`ls` 涉及的调用取决于实现与输出是否重定向，通常包括：打开目录（openat）、读取目录项（getdents64）、对每个文件取元数据（newfstatat）、写出结果（write）、关闭描述符（close），另外还有启动阶段的动态链接与内存分配（mmap、brk）。这题的正确答法不是背一个固定数字，而是说明判定方法：用 strace 统计，并指出重定向到文件、管道与终端时调用序列的差别。

**io_uring。** 它在用户态与内核之间共享一对环形队列：提交队列放请求、完成队列放结果，应用批量提交后由内核异步执行，一次 enter 可以收割多个完成事件。相比 epoll 的就绪通知模型——通知到位后仍要自己发起 read/write 系统调用——io_uring 把「发起 IO」也搬进了共享内存，配合注册文件描述符与固定缓冲区，可显著降低高 IOPS 场景的系统调用次数与拷贝开销；SQPOLL 模式下还可由内核线程轮询提交队列，进一步省掉陷入开销。适用面是大量小块随机读写（存储引擎、代理转发），对少量大块顺序 IO 收益有限。

**Redis 的缓存用法与三个经典问题。** 业务侧最常用 Cache Aside：读先查缓存、未命中回源并回填；写先更新数据库再删除缓存，删除失败用延迟双删或订阅 binlog 补偿，避免长时间脏数据。穿透是查不存在的数据，用布隆过滤器或空值缓存拦截；击穿是热点 key 过期瞬间大量回源，用互斥重建或逻辑过期；雪崩是大量 key 同时失效或实例故障，用过期时间打散、多级缓存与熔断降级。此外要能答出淘汰策略（allkeys-lru、volatile-lru 等）、持久化（RDB 快照与 AOF 重写的取舍）、单线程模型为何快（内存操作、无锁、IO 多路复用），以及大 key 与热 key 的排查手段。
