### 《面试题目》

**开场与项目**

1. 请简单做个自我介绍。
2. 选一个你做过的项目，讲讲背景、开发思路和遇到的难点。

**场景设计**

3. 设计一个工具：同一个需求经过多轮规划和修改，怎样把分散的记录关联到对应的需求或代码提交？
4. 怎样从执行记录中找出资源消耗异常的任务，并验证重复操作是否是原因？

**Java 基础与并发**

5. 你比较擅长哪些技术？
6. Java 的 HashMap 底层是怎么实现的？
7. Java 中有哪些线程安全的 Map？它们分别如何保证线程安全？

**限流**

8. 服务 A 和服务 B 都有多个实例，如何限制整个 A 集群调用 B 的总 QPS？
9. 如果用 Redis 实现令牌桶，Key 和 Value 怎么设计？怎么按指定速率补充令牌？需要定时任务吗？有没有更简单的 Redis KV 设计来限流？一条 Redis 命令能做到什么程度？
10. 固定窗口限流为什么可能在窗口边界出现接近两倍上限的流量？

**手撕**

11. 如何重排一个单向链表，使节点按首、尾、第二个、倒数第二个的顺序交替排列？例如把 1 → 2 → 3 → 4 → 5 改为 1 → 5 → 2 → 4 → 3。单向链表怎么处理尾端节点？请写出实现，并分析时间和空间复杂度。

**收尾**

### 《参考解析》

**执行记录怎么关联回需求与代码提交**：核心是给一次需求一个贯穿全链路的标识，而不是事后靠文本去猜。需求侧生成一个稳定的 `requirementId`，它随每一次规划、每一轮对话、每一次工具调用与提交一路透传：模型产出的计划带上它，工具调用的入参与出参记下它，代码提交在 message 或 PR 描述里带上它，CI 与部署记录再把它沿链路往下带。这样任何一条记录都能反查到需求，反之亦然。多轮修改会分裂出分支版本，因此还要记录 `parentRunId` 与计划版本号，形成一棵可追溯的树。文本层面的相似度匹配只能做补充手段——它能把历史数据临时对齐，但一旦命名或表述变化就会失效。

**资源消耗异常的定位与归因**：先建立可比的基线，再谈异常。按任务类型、模型、输入规模分组，统计 token 消耗、工具调用次数、墙钟耗时、重试次数的分位数（P50/P95/P99），单条记录超过同组 P99 或偏离自身历史中位数数倍即标记为候选异常。归因时看三点：一是输入侧是否有超长上下文或大文件；二是调用侧是否有重复调用、重试风暴、循环规划；三是输出侧是否有截断导致的反复续写。验证「重复操作是原因」要用对照而不是猜测：把同一任务的执行轨迹按工具与参数归一化后做频次统计，看是否存在同参数连续重复调用；有条件时重放该任务，观察去掉重复调用后消耗是否回落到基线；也可以对比同类任务在幂等缓存命中与未命中两种情况下的消耗差。

**HashMap 的底层结构**：JDK 8 是数组 + 链表 + 红黑树。`put` 时先由 `hash(key)` 扰动（高 16 位异或低 16 位）再对容量取模定位桶；桶空则直接放，非空则比较哈希与 `equals`，相同则覆盖，不同则尾插链表；链表长度达到 8 且容量不小于 64 时树化为红黑树，退化到 6 时链化。扩容阈值为容量乘以负载因子（默认 0.75），扩容翻倍并做高低位拆分，JDK 8 因此避免了 JDK 7 头插法在并发扩容下成环的问题。要能顺带说明：容量恒为 2 的幂是为了用位运算取模，扰动函数是为了让高位也参与定位、减少碰撞。

**线程安全的 Map**：`Hashtable` 用 `synchronized` 修饰整张表的方法，全表串行，基本已被弃用；`Collections.synchronizedMap` 是同一思路的包装器，遍历仍需外部加锁；`ConcurrentHashMap` 是正解，JDK 7 用分段锁（Segment 继承 ReentrantLock，锁粒度是段），JDK 8 改为 CAS + `synchronized` 锁单个桶头节点，并发度等于桶数量，扩容时多线程协助迁移。此外 `ConcurrentSkipListMap` 基于跳表，无锁读、有序，适合需要按 key 排序的并发场景。答题要点是讲清「锁的粒度从表降到段再降到桶」这条演进线索，以及为什么读操作在 JDK 8 可以完全无锁（`volatile` 保证可见性）。

**集群总 QPS 的限流落点**：单机限流只能保证每台机器不超，集群总量会随实例数线性放大，所以总量必须有一个共享的计数中心。常见做法是把限流器放到调用方与服务方之间的公共位置：网关层统一限流（最简单，但要确认所有调用都经过网关）；或者用 Redis 做分布式计数器，每次调用前 `INCR` 并设置过期，超过阈值即拒绝，代价是每次多一次网络往返，可用本地批量预取额度降低开销；也可以用中心化的令牌桶服务按实例配额下发令牌，各实例本地消费。要说明取舍：Redis 方案强一致但有延迟与单点压力，本地预取方案吞吐高但存在配额浪费与短暂超发。

**Redis 令牌桶的键值设计与补充方式**：Key 形如 `rate:{resource}:{windowStart}` 或直接 `bucket:{resource}`，Value 用 Hash 存 `tokens` 与 `lastRefillMs`——只存令牌数不够，因为不知道上次补充到什么时候。补充有两种做法：定时任务按固定间隔 `HINCRBY` 补令牌并 `HDEL` 过期桶，实现简单但要维护调度、且桶多时任务压力大；更常见的是惰性补充，每次请求时用 Lua 脚本读出 `tokens` 与 `lastRefillMs`，按 `(now - lastRefillMs) * rate` 算出应补数量、取 `min(capacity, tokens + delta)`，判断是否够用后写回，同一个脚本内完成「算补充 + 判断 + 扣减 + 更新lastRefillMs」，天然原子，也不需要定时任务。

**一条 Redis 命令能做到什么程度**：`INCR` 加 `EXPIRE` 可以做最简的固定窗口计数——用一个按窗口命名的 Key，第一次 `INCR` 后设置过期时间，返回值为当前窗口内的请求数。它的问题是边界效应与「先自增再判断」的超发（并发下多个请求同时读到临界值），而且 `INCR` 与 `EXPIRE` 是两条命令，中间失败会留下永不过期的 Key。要更严谨就必须上 Lua 脚本或 Redis 7 的 `EXPIRE NX`，把判断与写入合成一次原子操作；令牌桶与滑动窗口这类需要读改写多个值的逻辑，一条原生命令做不到，Lua 是最小代价的方案。

**固定窗口的边界问题**：固定窗口把时间切成不重叠的桶，每桶独立计数。假设上限 100 次/分钟，用户在 12:00:59 用满 100 次、12:01:00 又用满 100 次，这两批请求都合法，但落在任意连续 60 秒内的实际速率达到 200 次——接近两倍上限。根治办法是滑动窗口：记录每个请求的时间戳或用多个小格（如 1 分钟切 6 个 10 秒格）做加权统计，或者直接用令牌桶 / 漏桶把速率平滑到任意时刻。工程上常用「固定窗口 + 每格细分」折中，用少量精度换取可控的内存与计算。

**单链表首尾交替重排**：三步走。第一步用快慢指针找中点，把链表切成前后两半（`1→2→3` 与 `4→5`，注意奇数个节点时前半多一个）；第二步把后半段原地反转，`4→5` 变成 `5→4`；第三步把两段交替合并，每次从前半取一个、从后半取一个，串成 `1→5→2→4→3`。三个步骤都是原地操作，时间复杂度 O(n)，空间 O(1)。边界要处理：空链表、单节点直接返回；偶数节点时后半段与前半段等长，合并到最后一次后半段为空即停；反转后要在合并时把每个节点的 `next` 重新指向，避免残留成环。面试时先说清三步，再动手写，比直接写更容易过。

**项目复盘与职业规划**：项目不要平铺直叙，按「背景—我的职责—关键决策—结果—复盘」讲，重点放在至少一个可被追问的决策点上（为什么选这个方案、替代方案是什么、踩过什么坑），面试官几乎一定会顺着这个点往下问。职业规划那题讲方向与匹配度，不讲职级时间表：说清你想在哪个技术方向做深（例如把 AI 应用侧的工程化做扎实），以及这个岗位能提供什么对应的场景。
