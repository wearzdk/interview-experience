### 《参考解析》

**无重复字符的最长子串：滑动窗口要讲清「窗口里维护的是什么」。** 双指针加哈希：右指针扩张，遇到已出现过的字符就把左指针移到「该字符上次出现位置 + 1」，同时更新字符最近位置，过程中记录窗口最大长度；用数组（字符集大小 128 或 256）代替哈希表可以把常数压到最低，用 `map` 则天然支持任意字符集。两个常见坑：左指针只能右移不能回退（要写 `left = max(left, last[c] + 1)`，否则遇到陈旧记录会把窗口撑错）；以及要明确字符集边界（是否按字节、是否支持中文码点）。复杂度 O(n) 时间、O(字符集) 空间，说完可以补一句「这题是变长窗口模板，同一模板能解至少 K 个重复字符、最长替换后重复字符等一批题」。

**秒杀系统：把「到点放开」和「不超卖」拆成两件事做。** 时间闸门交给服务端统一时间：前端倒计时只是展示，服务端在下单接口校验当前时间是否早于活动开始（用统一时间源，必要时加一个秒级的安全缓冲），早于开始一律拒绝，避免客户端改时间或提前压测打进来。防超卖的核心是「库存扣减必须原子且只有一处权威」：活动开始前把库存预热进 Redis，用 Lua 脚本把「校验时间、判断库存、扣减、记录用户去重标记」放在一次原子执行里，只有扣减成功的请求才拿到资格，然后发消息进 MQ 异步创建订单，前端返回「排队中」并靠轮询或推送拿结果。这一层刻意把同步链路压到最短，数据库不参与争抢。配套要有：用户维度的限流与去重（同一用户只能抢到一单，用集合或唯一索引兜底）、网关层的整体限流与削峰、库存分段（把一份热库存拆成 N 个分片降低单 key 竞争）、以及「少卖兜底」——异步下单失败要把库存回补，别只做减法。最后补一致性收口：Redis 与数据库的库存以数据库为准，活动结束后对账修正，避免缓存扣减成功但订单没落库产生黑账。

**分布式锁与异步转存的安全检查：讲清临界区和失效兜底。** 分布式锁先回答「保护什么」——通常是同一份资源被多个实例或线程并发修改（例如同一单据被重复转存、同一账户被并发扣减）。方案是 Redis `SET key uniqueValue NX PX ttl`，释放时用 Lua 校验 value 再删，防止删掉别人重新获取的锁；业务执行时间不确定要加续期（看门狗），并说明单点 Redis 的锁在故障切换时可能失效、Redlock 也有争议，所以业务侧必须用幂等键与唯一索引做最终防护——「锁防并发，幂等防重复」这两句要一起说。异步转存的安全检查按四层答：鉴权与数据归属校验（这次操作的对象属不属于当前用户/租户）、参数与路径校验（防止越权读写、路径穿越）、额度与频率校验（防刷、防放大）、以及审计与可追溯（谁在什么时候转存了什么、失败可重放）。如果转存涉及外发或二次转发，还要提内容合规与敏感信息脱敏。

**ReAct 的工程化：循环、终止、上下文三件事一起讲。** ReAct 的实现就是「思考 → 行动（工具调用）→ 观察（结果）→ 再思考」的循环，工程上要把它做成有预算的闭环：每轮记录步骤与 token 消耗，设最大步数与总时长上限，同工具同参数的重复调用做指纹检测，再叠加「当前信息是否已足够回答」的状态评估，三者任一触发就收尾——只设 `max_iterations` 挡不住「每轮都合法但原地打转」，这是面试官最想听的差别。防死循环还要区分工具性质：只读工具可以放心重放，写操作必须有幂等键或先落意图再执行，否则重试会重复下单。上下文管理按分层讲：短期是当前会话窗口，用滑动窗口加摘要压缩、把稳定内容前置吃前缀缓存；长期记忆存用户偏好与历史结论，检索时召回而不是全量塞。工具结果回填要强调「先归一化再入上下文」——统一成约定结构、超长先裁剪或摘要、大产物落外部存储只在上下文里留引用和摘要，否则一次检索就能把窗口占满。

**连续消息、断点续传与消息冲突：本质是会话状态放哪、由谁串行化。** 「用户连发两条消息，第二条要读到第一条的上下文」意味着会话上下文不能只存在某台机器的内存里，同一会话的消息必须按序处理：可以用会话维度的队列或分片（同一 sessionId 固定路由到同一个消费者），也可以在处理前从共享存储（Redis / 数据库）加载最新上下文并加乐观锁版本号，做到「读-改-写」不丢更新。断点续传要区分两种语义：一是推理过程与已生成内容的续传，把已生成部分与任务状态落库，用户重连时从断点继续并靠消息序号去重；二是流式连接断开后的补发，服务端把每个会话的产出按序号持久化，客户端重连时带上次收到的序号请求增量——否则重连就只能重跑一遍，既费钱又会产生重复回答。防止消息冲突的通用做法是会话级串行 + 消息幂等：给每条用户消息一个 ID，处理时检查是否已在处理中，工具调用产生的中间态与最终回答用不同的消息类型，前端只按序号追加，服务端保证同一会话同一时刻只有一个活跃的推理任务，新的用户输入要么进队列、要么中断旧任务并记录中断点。

**八股四连：MQ 不丢、双写一致、热 Key、慢 SQL 与多表联查。** MQ 消息丢失分三段防：生产者侧用同步发送或带本地消息表/事务消息确认「已投递」，Broker 侧多副本加刷盘策略（同步刷盘、`acks=all`、`min.insync.replicas`）保证落盘不丢，消费者侧关闭自动提交、业务处理成功后再手动 ack，失败进重试与死信队列，消费端还要幂等（业务唯一键或消息 ID 去重）。Redis 与 MySQL 双写一致性按「能不能接受短暂不一致」选方案：强一致要慎用缓存或走分布式事务（代价大，一般不划算）；主流做法是先更新数据库再删缓存（不是更新缓存），配合延迟双删或订阅 binlog 异步失效，缓存侧加过期时间作为最终兜底，并说明为什么「先删缓存再更新库」在并发读下更容易脏。热 Key 的解法有一组：本地缓存扛读、key 打散加随机后缀分片、把集中写入改成异步或批量合并、读写分离与多副本、以及限流降级保护后端。慢 SQL 按「发现（慢查询日志、监控 TOP SQL）→ 定位（`EXPLAIN` 看 type、key、rows、Extra）→ 优化（补索引消除函数与隐式转换、覆盖索引、改写 SQL、处理深分页）→ 验证（对比扫描行数与耗时，压测确认没拖慢别人）」四步讲。多表联查的优化方向：先确认是否真的需要 join（能不能拆成两次查询在应用层拼装）、再保证连接字段类型与字符集一致且都有索引、小表驱动大表、必要时用覆盖索引或冗余字段反范式、把超大 join 拆成分批与临时表，以及警惕 join 后排序分组产生的临时表与 filesort。
