### 《面试题目》

1. 自动化测试为什么在很多团队里跑不起来？
2. 接口压测时并发加到 500，TPS 停滞不前，但服务端 CPU 和内存使用率都不到 30%，可能是什么原因？
3. 测开岗手撕代码要注意什么？怎样在写完之后体现测试思维？
4. 你的核心竞争力是什么？如果简历上只有一堆工具名词，面试官会怎么看？

### 《参考解析》

**自动化跑不起来的三个根因**。第一是定位与等待机制不规范：大量写死的绝对路径 XPath、固定 `sleep()`，前端一改样式或网络一抖动就大面积误报，团队跑几次就不再信任结果——信任一旦崩掉，后面做什么都没人看。正确做法是稳定的选择器策略（测试专用 `data-testid` 优先，其次语义定位）、显式等待（等元素可点击/可见，而不是等固定秒数）、失败重试与失败截图留证。第二是数据与环境耦合：用例之间共享账号与数据，前一条改了状态后一条就报错，每次回归前要人工造半天数据；解法是每条用例自建数据、用工厂或 API 造数、跑完清理，环境用容器化隔离。第三是分层投入失衡：把大量精力放在最易变的 UI 层做全量覆盖，忽略更稳定的接口层；合理的金字塔是接口测试占大头（覆盖业务逻辑与异常分支），UI 只覆盖关键主流程，单元测试由开发负责。答这题要给出「我自己怎么落地」的具体动作与数字（覆盖率、稳定率、回归时长从多久降到多久）。

**TPS 上不去但服务端很闲，怎么排查**。按「由外向内、从客户端到链路再到数据库」的顺序：先看施压机自身——CPU、内存、网络带宽是否打满，JMeter 单机线程数开太大导致 GC 频繁，请求根本没发出去；连接数与会话复用是否受限（HTTP 客户端连接池、Keep-Alive 关闭导致频繁握手）。再看链路中间件——Nginx 的 `worker_connections`、`keepalive` 配置，负载均衡的连接上限，TLS 握手开销。再看服务端资源池——数据库连接池（HikariCP 的 `maximumPoolSize`）太小会让请求排队等连接，Tomcat/Netty 的工作线程数不足同理；这些等待不消耗 CPU，正好解释「CPU 很闲」。最后看代码与外部依赖——对同一热点数据的同步锁、串行化的临界区，或者接口内部同步调用第三方慢接口，线程全卡在 IO 等待上。定位手段是分层打点：在施压端看发出的 RPS 与响应时间分布（p99 而不是均值），在网关看 upstream 响应时间，在服务端看线程栈（jstack 采样看多少线程阻塞在获取连接或锁上）。给结论时要说清「平均值掩盖长尾」这一点。

**手撕代码怎么体现测试思维**。测开的手撕难度通常中等偏下（字符串、数组、常见数据结构），但面试官更看健壮性。写完核心逻辑后主动口述四类边界：空值（空字符串、空数组、null 指针）、极端值（`Integer.MAX_VALUE` 溢出、长度为 1、全是相同元素）、非法格式（多余空格、大小写混杂、非法字符、超长输入）、资源与复杂度（文件流与集合是否释放、时间与空间复杂度推导）。再补一条工程习惯：先跟面试官确认输入约束与返回约定（异常还是返回特定值），再动手；写的时候把校验前置、把边界条件写成独立的分支，方便面试官一眼看出你想过。能主动给出两三个测试用例（含一个反例）会比只交代码高一个档次。

**「唯工具论」为什么扣分**。简历上罗列 Selenium、JMeter、Appium、Postman 只能证明你见过这些工具，一深挖原理或异常排查就答不上来。面试官真正想听的是「你解决过什么质量问题」：发现问题—定位根因—用工具或脚本提效—用数据量化结果，这个闭环讲透一个，胜过罗列十个工具名。准备时给每个项目准备一个这样的故事，并记住其中的数字（覆盖了多少用例、回归时间缩短多少、线上缺陷漏出率降了多少）。
