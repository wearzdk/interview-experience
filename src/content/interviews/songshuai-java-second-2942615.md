### 《参考解析》

**ArrayList 与 LinkedList**：ArrayList 基于动态数组，随机访问 O(1)、尾部插入摊还 O(1)、中间插入删除要搬移元素 O(n)，扩容 1.5 倍并复制；LinkedList 基于双向链表，按索引访问 O(n)、已知节点时插删 O(1)，每个节点额外存两个指针、缓存不友好。多数业务场景 ArrayList 更快，只有频繁在头部或中间插删且已持有节点时才考虑 LinkedList，或用 ArrayDeque 做队列。

**equals 与 ==**：`==` 比较基本类型的值或引用地址；`equals` 是方法，Object 默认等价于 `==`，String、包装类等重写后比较内容。重写 equals 必须同时重写 hashCode，否则放进 HashMap/HashSet 会定位不到。包装类比较要用 equals，`Integer` 在 -128~127 之外不会复用缓存对象。

**异常体系**：Throwable 分 Error（JVM 层严重问题，如 OOM、StackOverflow，不应捕获处理）与 Exception；Exception 分受检异常（编译期要求处理，如 IOException）与非受检异常（RuntimeException，如 NPE、IllegalArgument）。实践上业务异常自定义并携带错误码，资源用 try-with-resources 释放，不要吞异常，捕获后要么处理要么包装抛出。

**String 三者**：String 不可变，每次拼接产生新对象，适合常量与作为 Map 的 key；StringBuilder 可变、非线程安全、单线程拼接首选；StringBuffer 可变、方法加 synchronized、线程安全但性能略低。循环内拼接必须用 StringBuilder，编译器对简单的 `+` 会优化但循环里不会。

**索引失效**：对索引列做函数或运算、隐式类型转换、前导模糊 `LIKE '%x'`、联合索引不满足最左前缀、`OR` 连接非索引列、区分度太低导致优化器放弃、以及数据量小全表更快。判断靠 `EXPLAIN` 看 type、key、rows 与 Extra，不要只看「有没有走索引」。

**Redis 三剑客**：通常指缓存穿透、缓存击穿、缓存雪崩。穿透是查不存在的数据，用布隆过滤器或缓存空值；击穿是热点 key 过期瞬间大量请求回源，用互斥锁重建或逻辑过期；雪崩是大量 key 同时失效或缓存层故障，用过期时间打散、多级缓存、高可用与限流降级。

**MQ 重复消费**：消息投递至少一次，消费端必须幂等。用业务唯一键建唯一索引或去重表，处理与落库同事务；状态机按当前状态判断是否可迁移，避免重复累加；Redis 去重只能做前置拦截。

**OSS 分片上传**：客户端初始化分片任务拿到 uploadId，把大文件切成固定大小分片并行上传，服务端记录每片 ETag，全部完成后调 Complete 合并；失败可只重传失败分片，支持断点续传。要注意分片大小限制、并发数与带宽、合并时的顺序、以及未完成分片的清理（生命周期规则）。

**点赞**：高频写，用 Redis 存计数与用户点赞集合（Set 或 Bitmap），异步批量落库；展示时读缓存，缓存未命中回源并重建。要处理重复点赞（Set 天然去重）、计数与明细的一致性（以明细为准做校准）、以及热点 key 的分片。

**多级评论**：常见两种模型——邻接表（每条评论存 parentId，递归查询）与路径枚举/嵌套集（存物化路径，一次查出子树）。实际多用「根评论 + 楼中楼」两级：根评论分页，子评论按根 ID 批量查。要注意分页深度、删除时的级联与软删、以及计数维护。

**AI 调用链**：一次请求的链路通常是：鉴权与配额检查 → 组装上下文（系统提示、历史、检索结果）→ 选择模型与参数 → 调用上游（流式）→ 解析与后处理 → 落库与计费 → 埋点。要讲清超时与重试、降级模型、token 统计、失败补偿，以及如何用 Trace 串起每一段耗时。

**微信支付**：下单生成预支付单拿 prepay_id，前端唤起支付，用户支付后微信异步回调；回调必须验签、幂等处理（同一订单号只处理一次）、校验金额与订单状态，处理成功返回成功应答，失败要让微信重试。还要处理查单补偿、退款与对账。

**长上下文处理**：分块与摘要（把历史压缩成结构化要点）、检索增强（只取相关片段）、滑动窗口保留最近若干轮、把大文档落盘按需检索、控制工具输出体积。压缩后要保留目标、约束与未完成事项。

**前后端一起做的提示词**：先给角色与目标，再给约束（技术栈、目录结构、接口契约、错误码），把任务拆成可验证的步骤（先定 API 再写后端再写前端），要求输出改动文件清单与自测方式，最后让它先复述理解再动手。避免一次让它生成整个系统。
