### 《面试题目》

1. 自我介绍，重点讲腾讯 QT 迁移项目、自研 Agent 项目。
2. 介绍腾讯 QQ 本组内部人员分工，业务开发、跨端底座、AI 提效小组分别负责什么。
3. PC 端 QQ 与移动端的用户体量认知，QT 重构是研发驱动还是产品驱动？
4. PC-QQ Electron 迁移 QT 之后整体技术分层，哪些模块保留、哪些替换，线程间 IPC 通信方式？
5. 端渲染与自渲染各自优缺点，团队为什么选择端渲染路线？
6. 端渲染会遇到大量 CSS 兼容性缺失，如何划定工作边界，怎么做需求优先级划分？
7. 企业内部自研 AI Harness 对比直接使用 ChatGPT/Codex 这类通用 Agent，核心价值是什么？
8. Coding Agent 上下文不断膨胀、token 爆炸，如何实现上下文压缩、滚动窗口管理？
9. AI 生成 MR 代码之后，Verify 验证闭环如何设计，怎么保障生成代码满足业务需求？
10. 提问毕业之后 1-2 年个人的技术成长规划。

### 《参考解析》

**技术分层怎么讲**：迁移不是「把 Electron 换成 QT」这一句话，而是把系统切成几层，逐层说明「保留、替换、重写」。可以按「壳与进程模型、UI 渲染层、业务逻辑层、跨端能力层、基础设施层」来分：壳层负责窗口、生命周期、更新与崩溃恢复；渲染层决定用哪套绘制与布局能力，是这次迁移的主战场；业务逻辑尽量留在与 UI 无关的模块里，通过接口适配，避免重写；跨端能力（网络、存储、文件、系统集成）收敛成统一 SDK，Electron 侧和 QT 侧各实现一份；基础设施包括日志、埋点、灰度、崩溃上报，迁移期间要双端可用。IPC 要讲清楚通道与语义：进程边界在哪、消息如何序列化、同步还是异步、超时与重试、背压、以及大对象（图片、文件）怎么走共享内存而不是拷贝。面试官关心的是你有没有「分层与边界」的意识，而不是记住多少 QT API。

**端渲染与自渲染**：先把词落到项目语境——端渲染指复用端上已有的 Web 渲染能力（系统 WebView 或内置浏览器内核），自渲染指自己实现布局、绘制与合成。端渲染的优点是研发成本低、Web 生态与现成组件可直接复用、迭代快，缺点是受宿主内核版本影响，CSS/JS 兼容性参差，性能和内存上限受制于宿主；自渲染的优点是渲染结果完全可控、跨平台一致、能做深度性能优化，缺点是人力投入大、要自己补布局/文本/动画/无障碍等一整套能力、生态迁移成本高。团队选端渲染，通常是因为业务迭代速度和存量 Web 资产更重要，兼容性坑可以用「支持矩阵 + 降级样式 + 自动化视觉回归」控制；选自渲染则通常是因为性能、包体或一致性是硬指标。回答时把「业务阶段、团队规模、性能要求、迁移成本」四个约束摆出来，再说选择，比单纯说哪个好更有说服力。

**CSS 兼容性的边界与优先级**：先定支持矩阵——哪些系统版本、哪些内核版本、哪些分辨率必须支持，矩阵外的降级而不是适配。再把样式能力分层：基础布局与排版必须一致；高级效果（滤镜、复杂动画、某些选择器）按内核能力做渐进增强；完全不可用的能力提供静态降级。工程上用「样式 lint + 兼容性检查 + 多端视觉回归截图」把问题挡在合并前，运行时用特性检测而不是 UA 判断。优先级按「影响用户数 × 业务价值 ÷ 修复成本」排，P0 是影响主流程可用性的（按钮点不到、文字重叠），P1 是明显影响体验的，P2 是视觉细节；每个版本留固定比例的兼容性预算，避免被长尾拖死。还要有兜底：线上出现未覆盖的内核问题时，能通过配置降级到简化样式，而不是等发版。

**企业内部 AI Harness 的价值**：通用 Agent（ChatGPT/Codex）强在通用推理和代码生成，但它不知道你的代码库结构、内部规范、发布流程、权限边界和数据口径。自研 Harness 的核心价值是四件事：上下文——把仓库索引、代码规范、历史 PR、内部文档、监控数据接进来，让模型在正确的信息里工作；工具——把构建、测试、发布、日志查询、工单系统做成受控工具，模型能动手而不只是给建议；治理——权限最小化、操作审计、数据不出域、危险动作审批，满足企业安全要求；闭环——把「生成 → 验证 → 反馈 → 改进」做成可度量的流水线，用内部评测集持续优化，而不是每次靠人肉试。通用 Agent 适合探索和一次性任务，Harness 适合规模化、可重复、要担责的研发流程，两者不是替代关系。

**上下文压缩与滚动窗口**：不要把所有历史原样塞进上下文，而是维护「结构化状态 + 可检索记忆」。滚动窗口保留最近若干轮原文，保证指代和语气连续；更早的对话压缩成摘要，只留决策、约束、待办和关键文件；代码与文档不整篇塞，改成文件地图 + 符号索引 + 按需检索片段；工具输出截断并保留引用（文件路径、行号、URL），需要时再取；稳定不变的系统提示与工具定义放前缀并命中缓存，变化的状态追加到末尾，避免破坏缓存。预算上给每一步设 token 上限，按「任务阶段」动态分配（探索期多给检索，执行期多给代码），快到上限时触发摘要或让子 Agent 分担。判断压缩是否有效，看任务成功率、平均步数和重复读取率，不能只看 token 降了多少。

**AI 生成代码的验证闭环**：分层次卡：静态层跑 lint、类型检查、格式与依赖审计；行为层跑单测、集成测试、针对改动文件的定向测试，要求新增行为有对应用例；构建层跑完整构建与打包，确保产物可生成；运行层在沙箱或预发环境跑关键路径，接口用契约测试比对；评审层由人看 diff 的风险点（权限、数据迁移、并发、回滚），高风险改动强制人工批准；发布层走灰度和自动回滚，观察错误率与延迟。要让「需求 → 测试」可追溯：AI 生成代码时同时产出测试意图和验收条件，验证阶段逐条对照，缺哪条就退回。指标上记录一次通过率、返工率、回滚率、人工评审时长，按仓库和任务类型分层看，持续挑最差的一类补规则或补上下文。

**职业规划怎么答**：不要背「三年做技术专家」这种空话，给一条有因果的路径：先把一个方向做深（比如客户端架构与性能，能独立负责复杂模块的选型与落地），再补跨端与 AI 工程能力（能把 Agent 接进研发流程并量化收益），同时练协作与表达（能写清方案、推动跨团队落地）。每一段都给一个可验证的目标，比如「一年内主导一个跨端模块的架构升级」「两年内把某类需求的交付周期降多少」。最后说明为什么是这家公司、这个团队——业务阶段、技术栈、能拿到的场景与导师资源，让面试官看到匹配而不是套话。
