### 《参考解析》

**芯片与器件选型是一张约束表**：主控先看算力与主频（要不要跑 RTOS、有没有 DSP 或 NPU 需求）、片上 Flash 与 RAM（代码体积、缓冲区、协议栈占用）、外设资源（几路 UART / SPI / I2C / CAN、ADC 通道与精度、定时器与 PWM、DMA、USB、以太网）、功耗与低功耗模式、封装与引脚数、工作温度等级、供货周期与生命周期、价格与最小起订量，以及工具链与生态（SDK 质量、调试器支持、是否有成熟参考设计）。外围器件看接口匹配、精度与量程、采样率、供电与电平、封装、温度漂移、是否需要外部基准。回答时给一个具体取舍：为了省 BOM 选了集成度高的 MCU，代价是某路外设复用冲突，最后用软件模拟或换脚解决——这种细节比背诵参数表更能证明真选过。

**和硬件配合调板的分工**：硬件负责原理图、PCB、电源与上电时序，软件负责引脚复用、时钟树、驱动与协议时序，交界处最容易出问题。有效的配合方式是先把「谁在什么条件下测什么」定下来：上电前对一遍原理图与引脚定义、确认电平与上下拉；上电后用万用表与示波器量电源纹波与复位时序；通信不通时用逻辑分析仪同时抓 MCU 侧与从设备侧，一眼就能分清是没发、发错还是对方没回。软件侧的自证手段是回环测试（MOSI 短接 MISO）与 GPIO 翻转测时序。

**SPI 不通的排查顺序**：先物理层——供电、地是否共、片选有没有真的拉低、时钟与数据线有没有接反或虚焊、电平是否匹配（3.3V 与 5V 之间要不要电平转换）、上拉是否需要。再配置层——主机模式、CPOL/CPHA 四种模式是否与从设备手册一致、波特率先降到 1 MHz 以下、位序（MSB/LSB first）、数据宽度（8 位还是 16 位）、片选是硬件自动还是软件手动、DMA 与中断是否真的使能。然后看时序——用逻辑分析仪抓 SCK / MOSI / MISO / CS 四根线，确认时钟真的出来了、片选窗口覆盖了整帧、从设备是否在预期时钟沿采样。最后才是协议层——命令字与寄存器地址对不对、从设备是否需要上电延时或软复位、是否处在休眠、返回的状态位是否报错。软件排查的杀手锏是回环：短接 MOSI 与 MISO，若收到的就是发出的，说明主机侧完全正常，问题在从设备或接线。

**偶发死机的定位思路**：先让「偶发」变得可观测——加看门狗并在复位后保存复位原因（看门狗、硬件异常、掉电），把关键状态与最近若干条日志写进不掉电的 RAM 或 Flash 环形区；打开 HardFault 处理，从栈帧里取 PC / LR 与 CFSR、BFAR 定位到出错指令与访问地址；怀疑内存问题时开 MPU 把栈、只读区、外设区保护起来，越界会立即触发异常而不是随机踩坏数据；怀疑中断问题时统计中断频率与最长关中断时间。复现条件要记录环境（温度、供电、外设插拔、运行时长、并发负载），很多「偶发」最终是电源跌落、堆碎片、栈溢出或竞态。帖主被问这一题，答「加日志 + 看门狗 + 找复现条件」是及格，能说出 HardFault 栈帧与 MPU 才是加分。

**栈溢出的发现手段**：静态上估算最深调用链加上中断嵌套的最坏情况；动态上用栈 painting（启动时把栈区填成 0xAA，运行一段时间后看高水位线在哪）、在栈顶放 canary 值并定期检查、用 MPU 在栈底设保护区、或用 RTOS 自带的 `uxTaskGetStackHighWaterMark` 看剩余量。常见成因是大局部数组（`char buf[4096]` 放在栈上）、深递归、函数里定义大结构体、中断里再嵌套中断、以及任务栈开得太小。工程上的习惯是把大缓冲区放静态区或堆、限制递归深度、给栈留 30% 余量、并在 CI 里跑一遍高水位检查。

**内存对齐的原因**：总线按字（4 字节或 8 字节）访问，对齐访问一次总线周期就能完成；非对齐访问要么被硬件拆成两次、要么直接触发异常（Cortex-M 上由 CCR.UNALIGN_TRAP 决定），在带 DMA 与外设寄存器的场景还可能读到错误的值。对齐还影响原子性——跨 cache line 或跨字边界的读写不是原子的，多核与中断并发下会读到半新半旧的数据。编译器按 ABI 给结构体插 padding 就是为了保证每个成员落在自己的对齐边界上；协议报文要紧凑就得显式 `pack`，代价是非对齐访问，通常靠 `memcpy` 到对齐缓冲区再解析来规避。

**GDB 与「驱动该不该死等」**：常用命令要能随口说：`b` 下断点、`run` / `continue`、`next` / `step`、`finish`、`bt` 看调用栈、`info locals` / `info registers`、`p` 与 `x` 查看内存、`watch` 监视变量、`disassemble` 看汇编、`core-file` 分析 core dump，远程调试用 `target remote :3333` 配 OpenOCD / J-Link。SPI 从设备不响应时驱动绝不能在 `while` 里死等——正确做法是设超时（按传输长度与波特率算出理论上限的几倍），超时后返回错误码、复位外设、必要时重试有限次并把故障上报；中断或 DMA 传输要配完成量与错误中断，状态机区分空闲、发送中、等待响应、错误；对必须保证实时性的链路，把重试与降级写进设计，而不是让一个外设拖死整个系统。

**成长规划这一类问题**：面试官想听的是「你知道这个岗位三年后长什么样」。可落地的答法是分三层：一年内把负责的模块吃透（能独立定位问题、能改驱动、能看硬件手册），两到三年形成一块专长（比如低功耗、通信协议栈、Bootloader 与 OTA、或某个芯片平台的 BSP），三到五年能主导一个子系统并对接硬件、测试与产线。城市与团队偏好如实说，但给出理由（产业链、家人、技术方向），比含糊地说「都可以」更可信。
