### 《参考解析》

**上下文管理要同时管「窗口」和「成本」**。短期上下文按轮次保留最近若干轮，超出后做摘要压缩（保留事实和结论、丢弃寒暄），并给系统提示、检索内容和工具结果分配固定预算；长期记忆按用户维度存事实和偏好，写入时机通常是对话结束或出现稳定偏好时，读取时按相关性召回。压缩最怕丢关键约束，所以摘要要保留数字、时间、否定条件。

**Agent Loop 的终止条件要显式设计**：最大轮次、最大工具调用次数、总 token 预算、连续无进展检测、以及「模型输出最终答案」信号。重试要区分错误类型：网络超时、限流可重试并退避；参数非法、权限拒绝、业务错误不重试，直接回灌给模型让它改。

**权限拦截用「多层 + 短路」**：路径沙箱、命令白名单、敏感操作确认、只读模式和审计日志分层检查，命中拒绝就直接终止并记录原因，不再往下走。规则要由程序读取执行，写进提示词只能算引导，不能被当成安全边界。

**MySQL 迁 PostgreSQL 的无缝切换靠双写 + 影子读 + 灰度切流**：先全量迁移历史数据并校验，再双写保证增量一致，读路径按比例灰度切到新库并比对结果，确认无差异后停旧库写。迁移进度靠位点或版本号记录，失败可回放。

**Feed 系统的核心是「召回 → 排序 → 去重 → 分页」**。去重靠曝光表或布隆过滤器记录已推内容；关注流的新内容用推拉结合——大 V 走拉模式、普通用户走推模式，避免写扩散。游标分页比 offset 稳，能避免内容插入导致的重复和漏读。

**限流要分层**：网关按 IP/用户限流防刷，服务按接口限流保容量，核心链路（下单）单独配额，不能被浏览流量挤占。只按 Request ID 限流防不住总量，因为 ID 可以随便生成。

**扣减预算/库存的完整流程**：Redis 预扣（Lua 保证原子）→ 发消息 → 消费端落 MySQL 并做幂等 → 失败回滚 Redis。Redis 与 MySQL 不一致时以 MySQL 为准对账修复，别用 MySQL 反向覆盖 Redis 的实时值，否则会把已扣的额度放大。
