### 《面试题目》

1. 每秒约一万个任务提交，怎样设计提交与取消接口？要求不直接使用成熟框架。
2. 延迟任务的取消接口怎么实现？任务可能已经被执行进程拿走，取消成功到底怎么算？
3. QPS 较高时怎样轮询？每次拉多少、轮询频率怎么定？
4. 多个实例都读到同一批任务时，怎样避免重复执行？

### 《参考解析》

**先把需求问清楚再设计**。这场面试的关键动作是先反问三件事：允许晚执行多久（决定扫描粒度与批量大小）、重启后能不能丢任务（决定是否需要持久化）、取消的时效要求（决定是尽力而为还是强一致）。这三个答案直接决定存储选型：能丢就用内存时间轮，不能丢就要落库。

**提交接口**。任务表（或 KV）字段至少包含：`task_id`（客户端生成或服务端生成，用于幂等）、`run_at`（到期时间）、`payload`、`status`（待执行 / 执行中 / 成功 / 失败 / 已取消 / 取消中）、`version`、`lease_until`（执行租约）、`retry_count`。提交接口要做两件事：幂等写入（同一 `task_id` 重复提交返回同一条记录，用唯一索引或 `INSERT ... ON CONFLICT`）和可查询（返回任务 ID 供取消与查询状态）。索引建在 `(status, run_at)` 上，扫描只走这一条。

**取消接口的核心是状态机与原子改状态**。取消不能理解为「从到期索引里删掉」，因为任务可能已经被执行进程取走。正确做法是把取消做成一次条件更新：`UPDATE tasks SET status='cancelled' WHERE task_id=? AND status='pending'`。改成功表示任务还没开始，取消确定生效；改不动说明已被取走，此时要么把状态置为 `cancel_requested`，由执行方在开始前再检查一次并主动放弃，要么明确告知调用方「已开始执行，无法撤销」。`cancel_requested` 与 `cancelled` 必须区分：前者是意图，后者是结果。已经开始执行的任务，取消成功只能保证「后续步骤不再执行」，已经发生的副作用收不回来——所以对外接口要么给出「尽力取消」的语义，要么要求业务侧提供补偿。取消成功与否必须回读状态确认，不能以接口返回码为准。

**抢占执行权**。多个实例扫到同一批候选任务时，读到只是候选，真正执行前要抢：`UPDATE tasks SET status='running', lease_until=now()+30s, version=version+1 WHERE task_id=? AND status='pending' AND version=?`，影响行数为 1 才算抢到。这一步必须是一次原子更新，分成「先查再改」必然撞车。租约用于处理执行进程崩溃：执行中定期续租，租约过期后允许其他实例回收（把状态改回 pending 或标记失败重试），回收同样走条件更新并带上 version，避免和原实例互相覆盖。

**轮询与批量**。不要张口报一个固定间隔。做法是按到期时间批量拉取：`SELECT ... WHERE status='pending' AND run_at <= now() LIMIT batch`，取到后 sleep 到下一批最早到期时间（有上限，比如最多 1 秒），避免空转。批量大小由执行端处理能力和允许延迟共同决定：单实例每秒能处理 M 条，就按 M 定批大小，批太小扫描开销大、批太大一次拉太多导致延迟抖动。积压时按队列深度自适应放大批量或临时加消费者。多实例扫描同一批候选必然有竞争，用「分区扫描」（按 `task_id` 哈希取模分配给实例）可以把无效抢占降到最低。

**避免重复执行的第二道防线是业务幂等**。抢占只能保证同一时刻只有一个实例在执行；任务做完但结果还没写回时进程挂掉，重试仍可能让同一件事做两遍。所以业务处理必须用稳定的 `task_id` 做去重键（下游接口幂等、或写一张去重表带唯一索引），让重复请求只生效一次。回答时要把这两层分开讲：调度层保证不并发，业务层保证不重复生效。

**验证方式**。面试里能加分的收尾是说明怎么测：写一个小程序让「取消」和「开始执行」并发抢同一条任务，把两种先后顺序都跑一遍，检查接口返回、最终状态、副作用次数三者是否一致；再模拟执行进程被 kill，验证租约过期后的回收与幂等是否成立。
