### 《参考解析》

**数据清洗的两个重点**：一是去重，代码每次提交都会打点，重复提交会带来重复数据；二是口径对齐，不同团队的埋点定义不一致，要先监控字段口径再 JOIN 与开发。去重放在哪里取决于任务形态：这个课题以离线为主、每日增量写入，写入阶段不做大量去重，而是在拉取使用时做 T+1 全量清洗后重新入库。

**看板的价值怎么体现**：指标与图表本身实现难度不高，难点是让看板能反映业务特征、支撑定位问题。做法是先由数据同学基于对效能的理解产出初版（ADS 指标 + 下钻维度），再由 DA 与业务方给优化建议迭代。判断一个看板是否有用，看它能否把「某个指标异常」顺着下钻维度收敛到具体团队、链路或版本，而不是只展示一个总数。

**知识库召回怎么测**：通过接口调用 Agent，让它读需求文档、生成测试用例与执行脚本并返回结果；测试时读 Agent 的思考日志，确认调用了哪个 Skill、对需求的理解是否正确、召回的知识条目是否相关。SQL 执行出错要区分是能力边界（优化 SQL、明确 Agent 可执行范围）还是召回异常（调整知识库参数与内容）。此外重点测记忆隔离：多用户共用同一个 Agent 时，公共记忆与私有记忆必须分开，这部分测试周期最长。

**为什么二次开发 OpenClaw 而不是轻量方案**：这类选择的判断依据是需要的执行能力边界——是否需要浏览器操作、文件读写、多步工具编排与可扩展的 Skill 机制。轻量框架在单轮问答够用，但要做长流程任务时需要自己补编排、状态与权限，二次开发的成本反而更低。回答时要把需求清单与框架能力逐项对应，而不是只谈偏好。
