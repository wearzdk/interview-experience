### 《参考解析》

**C 与 C++ 的区别**：C 是面向过程的，没有类、模板、异常、RAII，内存手动管理；C++ 在 C 之上加了面向对象、泛型、标准库（STL）、异常与 RAII，编译期能力更强（模板元编程、constexpr）。C++ 尽量兼容 C，但两者语义有差异（如 `void*` 隐式转换、函数重载、名字修饰）。运行开销上 C++ 的抽象大多可零成本，但虚函数、异常、RTTI 有代价。

**智能指针**：`unique_ptr` 独占所有权、不可拷贝只可移动，零额外开销，默认首选；`shared_ptr` 共享所有权，内部有引用计数（控制块），拷贝有原子操作开销，循环引用会泄漏；`weak_ptr` 不增加引用计数，用来打破循环、观察对象是否还活着（`lock()` 提升为 shared_ptr）。`make_shared` 一次分配把对象和控制块放一起，比 `shared_ptr(new T)` 少一次分配。项目里用它们管理 socket、缓冲区、回调生命周期。

**多态与虚函数**：编译期多态靠模板与重载，运行期多态靠虚函数——每个含虚函数的类有一张虚表，对象头存虚表指针，调用时通过虚表间接跳转。构造函数里调用虚函数不会派发到子类（此时虚表还是父类的），析构函数要写成 virtual，否则通过基类指针 delete 子类对象是未定义行为。`override`、`final` 能帮编译器检查。

**多线程避免数据竞争与死锁**：数据竞争靠「不共享」优先——线程封闭、消息传递、无锁结构（原子操作、CAS）；必须共享时用互斥量保护，锁的粒度尽量小、持锁时间尽量短。死锁的四个必要条件是互斥、持有并等待、不可剥夺、循环等待，破坏任意一个即可：固定加锁顺序（按地址或 ID 排序）、`std::lock` 一次性锁多个、带超时的 `try_lock`、避免在持锁时调用外部回调。工程上还要注意伪共享、内存序（`memory_order`）与条件变量的虚假唤醒。

**单链表 O(1) 删除给定节点**：把后继节点的值拷贝到当前节点，然后删除后继节点。限制有三：不能是尾节点（没有后继可拷）、节点必须确实在链表里、如果是「不允许修改值」的场景（节点值不可变或外部持有引用）就不适用。这是「狸猫换太子」的经典题，面试官通常接着问「尾节点怎么办」——只能 O(n) 找前驱，或者改用双向链表。

**二叉树遍历与高度**：前序、中序、后序（DFS，递归或显式栈）、层序（BFS，队列）。高度是 `1 + max(height(left), height(right))`，递归 O(n)；最短路径在无权树上是 BFS 首次到达的层数。要注意空树高度定义为 0 还是 -1，面试时先说清楚约定。

**红黑树特性**：节点非红即黑、根节点黑、叶子（NIL）黑、红节点的子节点必须是黑、从任一节点到其所有叶子的路径上黑节点数量相同。这五条保证最长路径不超过最短路径的两倍，因此增删查都是 O(log n)。相比 AVL，红黑树插入删除时的旋转次数更少，适合写多的场景；STL 的 `map`、`set` 底层就是红黑树。

**匹配系统设计**：核心是把「段位差」和「等待时长」做成一个可调的分数。常见做法是给每个玩家维护一个匹配分（MMR），匹配时先按分数分桶（例如 ±100 分），桶内按等待时间排序，等待越久桶的宽度逐步放大（每 5 秒扩 50 分），保证高分段玩家不会无限等。工程上要注意：用优先队列或时间轮管理等待队列；同一玩家不能被重复匹配（加锁或用状态机标记）；组队匹配要把队伍当成一个整体算平均分与最大分差；匹配成功后要有确认与超时回退，防止有人不点确认导致其他人重新排队。数据上要监控匹配时长分布、分段胜率差，避免「为了快而匹配到实力差距过大的人」。

**UDP 上做可靠传输**：在应用层实现序号 + 确认 + 重传 + 去重 + 重排序：每个包带递增序号，接收方回 ACK（可累积确认），发送方维护发送窗口与超时重传（RTO 参考 RTT 动态计算），接收方用缓冲区按序号重排后交付。要处理拥塞控制（类似 TCP 的慢启动、拥塞避免，或游戏里常用的基于丢包的码率调整）与 MTU（避免 IP 分片，单包控制在 1200 字节左右）。现成方案有 KCP、QUIC、ENet。

**游戏业务怎么选协议**：TCP 适合「不能丢、可以慢一点」的：登录、支付、背包与交易、聊天、排行榜拉取。UDP 适合「实时性优先、旧数据没价值」的：位置同步、技能释放、语音、射击判定。实时对战通常是 UDP + 应用层可靠（关键事件可靠、状态快照不可靠），并用插值/外推掩盖丢包。选型还要考虑 NAT 穿透、移动网络切换、服务器承载。

**RAG 链路**：文档解析与清洗 → 切块（按语义或固定长度 + 重叠）→ 向量化入库 → 查询改写（可选）→ 检索（向量 + 关键词混合）→ 重排（rerank）→ 拼上下文生成 → 引用与后处理。面试官会追问每一步的坑：切块丢语义、召回不全、rerank 太慢、上下文超长、答案没有出处。

**多 Agent 分工**：策划、执行、审查这类角色拆分适合「任务可分解且每步上下文差异大」的场景；拆分的代价是上下文传递、错误放大与成本翻倍。回答时给一个具体的拆分例子和它的收益/代价，比泛泛而谈「多 Agent 更强」要好。
