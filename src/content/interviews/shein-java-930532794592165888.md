### 《参考解析》

**先说明库存的权威记录在哪里**

数据库扣减可以使用带库存条件的原子更新，例如扣一件时要求 `stock > 0`，并核对受影响行数。订单创建、库存预占、支付确认和超时释放之间，要有明确状态和唯一业务标识。重复消息不能重复扣减，重复取消也不能多放回库存。

少卖时要沿这条链检查是否存在过期未释放的预占、处理失败的补偿、缓存旧值或订单状态不一致。看到还剩一件库存，不应直接把某个数字加一；先确认它属于哪个业务状态。

**ThreadLocal 的生命周期往往比一次请求长**

线程池会复用线程，放进去的请求上下文可能一直跟随工作线程。ThreadLocalMap 中键的弱引用并不意味着值一定会立即释放；不再使用时，应在 finally 中调用 remove。若值本身很大，长时间保留会加重内存压力；若值属于上个请求，还可能出现上下文串用。

**事务注解要经过实际代理入口**

在基于代理的事务管理中，同一对象内部直接调用另一个标注事务的方法，通常不会经过代理，因而不会开启那个方法声明的事务。还应检查事务管理器、传播行为和回滚规则。把异常捕获后当成功返回，也可能让事务正常提交，不能只看方法上有没有注解。

**Full GC 先看回收前后差了多少**

把 GC 日志、堆占用变化与业务负载对起来看。回收后占用仍持续增长，要检查长寿命对象的引用链；回收有效但频率高，则继续检查分配速度、堆容量与晋升压力。分析时保留运行参数和时间线，避免只凭“Full GC 多”就认定是内存泄漏。

**深分页可以改为从上一条继续找**

按稳定且可索引的键排序，下一页使用上一页末尾的排序键作为查询边界，避免反复跳过大量前序记录。排序字段不唯一时，应加唯一键作为第二排序条件。这个方案适合连续翻页；任意跳到第几页的需求，需要另行权衡。
