### 《参考解析》

**GIL。** CPython 的全局解释器锁保证同一时刻只有一个线程执行字节码，所以多线程做 CPU 密集任务拿不到并行，只能多进程或把计算下沉到 C 扩展（NumPy 在释放 GIL 的段里能并行）。IO 密集场景多线程仍有效，因为阻塞调用会释放 GIL。3.13 起有实验性的 free-threaded 构建，但生态兼容性和单线程性能都有代价，生产上仍按有 GIL 设计。答这题要落到「我的服务怎么绕」：CPU 密集用进程池或向量化，IO 密集用 asyncio。

**Tool 与 Skill。** Tool 是一次可调用的动作，有明确 JSON Schema——名字、参数、返回值、错误码，模型选它并填参数，执行完拿到结构化结果。Skill 是一套打包好的流程知识：这类任务按什么步骤做、用哪些工具、注意什么，写成可加载的文档或代码包，模型读进去改变的是自己的行为策略，而不是发起一次调用。形态上 Tool 是函数、Skill 是说明书加脚本集；粒度上 Tool 原子、Skill 面向一类任务；加载上 Tool 常驻工具表，Skill 按需检索、渐进式披露（先给索引摘要，用到再展开正文）。把流程写进工具描述会让工具表膨胀到模型选不动。

**RAG 的召回与切分。** 召回一般混合：向量管语义相近，BM25 管专有名词和编号，两路结果用 RRF 或加权融合后 rerank。切分没有通用最优解，取决于文档结构：Markdown 按标题层级切，代码按函数/类切，表格整块保留，PDF 先版面还原再按段落切。通用做法是结构优先加定长兜底：先按语义边界切，超阈值再按 token 硬切，相邻块留 10%–20% 重叠，防止一个定义和它的条件被切到两块里。块大小要同时对齐 embedding 模型的最大长度和塞进上下文的预算。

**Agent 与 Workflow。** Workflow 的控制流由代码写死：步骤、分支、失败处理都在编排层，模型只在节点里做分类或生成。Agent 把「下一步做什么」交给模型，代码只提供工具、约束和停止条件。任务路径固定、要可审计可回归就用 Workflow；开放度高、路径无法预先枚举才用 Agent，代价是延迟、成本和不确定性一起上升。工程上多为混合：外层 Workflow 控主流程，内层某个节点用 Agent 处理开放子任务。

**1GB 内存查 10GB 文件。** 不能整读，也不适合 `mmap` 整个文件（地址空间与缺页压力都顶不住），只能流式分片：按 32–64MB 顺序读入 buffer，片间保留 `len(pattern) − 1` 字节重叠，否则跨片边界的匹配会漏。片内用 `memchr` 找首字符再逐字节比对，比正则快得多；同时累计换行数维护全局行号，命中时用「片起始行号 + 片内偏移前的换行数」还原。内存是 buffer 加常数，与文件大小无关。还能优化：多进程各扫一段并行（总内存仍受控）、布隆过滤器先粗筛、模式多时换 AC 自动机一次扫描。注意重叠区要按行边界对齐，把上一片末尾的半行带到下一片开头。
