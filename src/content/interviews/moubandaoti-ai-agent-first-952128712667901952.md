### 《参考解析》

**上下文压缩要讲清输入、触发、过程与失败处理**。面试官连问的实质是「这个模块是谁在跑、什么时候跑、输入输出是什么、失败怎么办」。一个可落地的描述：每次会话请求前统计消息 token 数（含工具返回），超过窗口预算的某个比例（常见 70%~80%，要给依据而不是拍数字）时触发压缩；输入是最近若干轮之外的历史消息，输出是一段结构化摘要 + 若干条抽取出的长期记忆；压缩由一次独立的模型调用完成，把「角色、目标、已确认的事实、未完成的待办、用户偏好、被否决的方案」分字段输出，写入存储后再把这段摘要作为一条 system 或 user 消息放回上下文头部，原始消息归档但不删除。失败处理要写明：压缩调用超时或输出解析失败时不丢历史，降级为滑动窗口截断并记一条告警；摘要落库与替换上下文要在一个事务或可重试的幂等步骤里完成，避免「摘要写了一半、上下文已替换」。

**压缩与存储的关系，以及为什么换 PostgreSQL**。压缩产出的摘要和记忆条目是文本，原始消息也是文本，MySQL 存这些没有问题，所以「换成 PostgreSQL」的真实理由通常不是压缩本身，而是向量检索：pgvector 让向量列和业务数据在同一张表、同一个事务里，省掉一套独立向量库的同步链路，过滤条件（用户 id、时间、类型）可以和向量近邻查询写在同一条 SQL 里，也不会出现向量库删了而关系库还留着的孤儿数据。代价是规模上限与索引维护：HNSW 索引内存占用高、写入放大，百万级以上要考虑分区、按用户分片或迁到专用向量库。答这题时把「当初为什么选 MySQL」「什么信号出现才换」讲清楚，比背 PostgreSQL 的优点更有说服力。

**向量的生成与检索链路**。写入侧：把一条记忆（一句话、一段摘要、一个事实三元组）经 embedding 模型转成定长向量，连同原文、用户 id、类型、来源会话、创建时间、置信度一起入库；同一份文本换模型必须重建，所以表里要存模型名与维度。检索侧：查询文本同样过 embedding，用余弦或内积做近邻（pgvector 的 `<=>`、`<#>` 运算符），可加 `ivfflat`（需先灌数据再建索引，靠 `lists`/`probes` 调召回）或 `hnsw`（查询快、内存吃得多）；再叠一层元数据过滤与时间衰减，最后做相关性阈值截断，别把 top-k 硬塞进上下文。工程上还要处理：去重（同一事实反复出现）、过期（旧偏好被新偏好覆盖）、以及「检索不到时的兜底」——宁可少给，也别把无关记忆塞进 prompt 污染回答。

**百万级用户的数据表设计**。最小可用的一套是四张表：`users`（档案与配额）、`sessions`（会话元信息）、`messages`（原始消息，按 `(user_id, session_id, seq)` 建索引，内容大字段可单独拆表或放对象存储）、`memories`（记忆条目，含 `vector` 列与类型、置信度、最后命中时间）。分片的第一原则是让同一用户的读写落在同一分片：按 `user_id` 哈希分库分表，或按 `user_id` 做范围分区；`messages` 是增长最快、查询最局部（几乎只按会话查）的表，最适合先分片，甚至可以冷数据归档到列存或对象存储，只把摘要留在热库。索引上要避免在 `messages` 上建大范围时间索引后做全表扫，改用 `(user_id, created_at)` 复合索引。至于「分库分表方案有依据吗」——诚实回答更好：单表预估行数与单行字节数、目标 QPS、索引大小与内存的关系，算出什么时候必须分；没有压测数据就说是设计推演，不要包装成已验证。面试官问这句，往往就是在分辨「你做过」和「你读过」。

**判断一条信息值不值得存成长期记忆**。不要用一个模糊的「重要」标准，拆成可判定的规则：是否属于稳定属性（职业、技术栈、长期偏好、所在城市、目标岗位）而非一次性状态（今天想改简历）；是否会在未来会话中被复用（复用概率靠类型先验 + 命中统计）；是否与已有记忆冲突（冲突时走更新而不是新增）；是否敏感（证件号、联系方式默认不入长期库）。工程上常见做法是让模型按固定 schema 输出「是否保存 / 类型 / 内容 / 置信度 / 有效期」，再用阈值与规则过滤，并保留人工可查的删除入口。用户明确说「记住」时应无条件保存，这是唯一可以绕开模型判断的入口。

**各家 Agent 的记忆机制要讲结构性差异，而不是产品名**。Claude Code 这一类的做法是把项目级约定写进仓库里的 `CLAUDE.md` 文件，靠读文件把「长期记忆」注入上下文，会话历史超长时做压缩摘要，本质是「文件即记忆 + 上下文压缩」；Cursor 侧是编辑器内的规则文件加上代码库索引，索引服务于检索而不是对话记忆；ChatGPT 类产品是服务端维护的记忆条目，按相关性检索后注入提示词，并给用户可见的编辑与删除入口。共同点值得点出：都在「上下文之外存一份可检索的状态」，都在上下文接近上限时做摘要或丢弃，都区分「事实型长期记忆」与「会话内短期历史」。不确定的细节要说不确定，别编造实现。

**Agent 是否一定需要记忆**。不是。记忆解决的是「跨会话的状态延续」和「上下文装不下的信息复用」，如果任务是单轮、无状态、输入自带全部信息（比如一次代码审查、一次格式转换），加记忆只会引入污染与成本。判断标准是三条：任务是否跨轮依赖前文、信息是否超出窗口、用户是否期待被记住。需要记忆时也要选形态——结构化档案（字段明确、可查询）、向量检索（模糊相关）、文件规则（确定性注入）各有适用面，混用时要明确谁的优先级高。

**关于这场面试本身**。候选人自评不理想，原因值得记下来：项目里写了「长期记忆、上下文压缩、向量检索」，就要能继续回答谁执行、何时执行、输入输出、失败兜底、为什么需要这五问；介绍别人的产品时要有官方文档或源码依据，把「我实现的」「我调研确认的」「我设想中的」三件事分开讲，否则一个追问就会露出边界。
