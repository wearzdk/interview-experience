### 《参考解析》

**意图识别与工作流：先分清「编排」和「自主决策」。** 意图识别本质是分类加路由：输入先经过一个分类环节（可以是小模型分类器，也可以是 LLM 结构化输出），得到意图标签，再由编排层决定走哪条链路。工作流和 Agent 的区别面试官很爱追——工作流是确定性编排，路径在写代码时就定死了，模型只在节点内做事；Agent 是模型自己决定下一步调什么工具。决定「要不要调外部工具（天气、深度分析）」这件事，工程上应该收敛成分类输出加工具白名单，而不是让模型自由发挥，否则不可测、也没法做权限控制。被问「用量高不高」「是不是正式上线」时，直接报真实数字与状态——这类追问本身就是真伪校验，含糊其辞比数字小更致命。常见追问点：多轮里上一轮意图污染下一轮、低置信度时该澄清而不是硬答、分类体系变更后要跑回归集。

**高并发库存一致性：同步扣减 + 异步补偿，边界必须讲清。** 面试官连着问「异步校验什么时候跑、是定时跑吗、你刚说的是同步还是异步」，就是在验是否真做过。合理分工是：同步主链路上完成资格校验、扣库存、扣券、生成订单，用 Redis 的 Lua 脚本把「读余量 + 判断 + 扣减」做成一次原子操作，数据库层再用带条件的 `update` 兜底；异步部分只做对账、超时未支付的库存回滚、核销通知这类允许延迟的事，绝不能把「扣减」本身放到异步里——那就会出现超卖窗口。说清「哪一步不允许失败、失败后靠什么补偿」比罗列组件更重要。

**库表设计：券模板、用户券、库存三层，再加唯一索引兜幂等。** 典型划分是券模板表（模板 ID、总量、剩余、限领规则、生效时间）、用户券表（用户 ID、模板 ID、状态机：已领取/已使用/已过期、领取时间）、库存表或计数器。扣减要靠三层保证：Redis 原子预扣挡住绝大部分流量、DB 的条件更新 `stock = stock - 1 where stock > 0` 用行锁保证不超卖、`(user_id, template_id)` 唯一索引保证同一个人不会重复领取（重复请求直接撞唯一键，天然幂等）。回答时按「先讲表、再讲字段变化、最后讲异常路径」的顺序说，面试官问「表名、字段加一减一」就是想听这个粒度。

**联合索引与 explain：范围条件会截断后面的列。** A=5 走唯一索引等值命中；B=5 无索引只能全表扫；C=5 命中联合索引 `(C,D)` 的最左前缀，只用 C 这一列（key_len 能看出只用了 C 的长度）；`C>5 and D=5` 里 C 是范围条件，范围之后的列无法再用于索引定位，仍然只用到 C，D 只有靠索引条件下推（ICP）在存储引擎层过滤，能少回表但不能减少扫描范围。验证方式：`EXPLAIN` 看 `type`（`const`/`ref`/`range`/`index`/`ALL`）、`key`、`key_len`、`rows`、`filtered`，重点看 `Extra`：`Using index` 是覆盖索引不回表、`Using index condition` 是 ICP、`Using filesort`/`Using temporary` 是要优化的信号；MySQL 8.0 还能用 `EXPLAIN ANALYZE` 看真实耗时与行数。追问一般是「最左前缀能不能跳过中间列」「范围条件为什么后面失效」，答到「B+ 树按列依次比较、范围之后不再有序」就算到位。

**缓存穿透与击穿要分开答，顺带把雪崩带上。** 穿透是查一个数据库里也不存在的数据，缓存永远不命中，请求全打到 DB——方案是缓存空值（带短过期）、布隆过滤器挡在前面、入口做参数合法性校验。击穿是某个热点 key 恰好过期，瞬间大量请求同时回源——方案是互斥重建（只有一个线程去加载，其余等待或返回旧值）、逻辑过期加后台异步刷新、热点 key 干脆不设过期时间。雪崩是一大批 key 同时失效或缓存整体不可用，靠过期时间打散、多级缓存、熔断降级。三者的区别在于「请求打的是不存在的、单个热点的、还是大批量的」。

**跳表：用随机层数换取范围查询和实现简单。** 跳表是多层链表，每层是下一层的抽样，查找从最高层开始向右走、走不动就下降一层，期望复杂度 O(log n)。插入时新元素的层数由随机函数决定（例如每次以 1/4 的概率继续往上加一层），期望层数是常数级，用「概率平衡」代替红黑树的严格旋转平衡。Redis 的有序集合 `zset` 就是跳表 + 哈希表：哈希表保证 O(1) 按成员取分数，跳表负责按分数排序和范围查询（`ZRANGEBYSCORE`）。选它而不是红黑树的原因是范围查询更自然、实现更简单、并发实现（如 Java 的 `ConcurrentSkipListMap`）更容易做无锁。

**网络分层：记住对应关系，别背一个「标准答案」。** OSI 七层从下到上是物理层、数据链路层、网络层、传输层、会话层、表示层、应用层；TCP/UDP 在传输层，HTTP 在应用层，MAC 地址属于数据链路层。实际教学与工程里常用 TCP/IP 四层（网络接口层、网际层、传输层、应用层）或五层模型，面试官问「你们学的是几层」是想看你知不知道这几套模型怎么对应，答的时候把层次和协议一起摆出来即可。

**非对称加密：两个密钥不是「都能解开同一个密文」，而是分工不同。** 公钥加密、私钥解密用于保密，私钥签名、公钥验签用于身份与完整性。之所以成立，是因为 RSA 里公钥指数 e 与私钥指数 d 互为模 φ(n) 的乘法逆元，对明文做幂运算可以互相还原。RSA 的安全性建立在大整数分解困难问题上（大素数乘积容易、分解极难），椭圆曲线（ECC）建立在离散对数问题上，同等安全强度下 ECC 密钥更短。实际 TLS 里非对称只用来协商出对称密钥，因为非对称运算慢几个数量级，业务数据是用对称加密传的。

**TCP 四次挥手：因为连接是双向关闭的。** 主动方发 FIN 表示「我没有数据要发了」，被动方回 ACK（此时主动方进入 FIN_WAIT_2），但被动方可能还有数据要发，所以它的 FIN 要等自己发完才发，于是 ACK 与 FIN 不能合并，就比三次握手多了一次。被动方发完 FIN 后主动方回 ACK 并进入 TIME_WAIT，等 2MSL 再关闭：一是保证最后的 ACK 能到达（丢了对方会重发 FIN），二是让本次连接的残留报文在网络中失效，避免影响复用同一四元组的新连接。追问常是「服务端出现大量 CLOSE_WAIT 说明什么」——说明应用层没调用 close，通常是代码漏关连接。

**Skill 与 MCP 的区别：一个管流程知识，一个管能力通道。** Skill 是写给模型看的「这类事情该怎么做」的流程与知识（提示词、文档、脚本模板，加载进上下文，影响它的行为与文风）；MCP 是模型与外部系统之间的标准接口协议，服务端暴露 tools、resources、prompts，给的是「能碰什么、能读什么」的能力边界与鉴权。工程上两者是互补的：skill 描述流程，流程里需要的能力由 MCP 的工具提供。追问问到点上会问「工具多了模型选错怎么办」「MCP 的鉴权与最小权限怎么设计」——按工具白名单分组、按场景只暴露相关工具、写操作强制确认和幂等。

**二面重点：平台券与商家券，以及热点分桶。** 平台券是全平台一个模板，库存是一行热点数据，压力集中在单个 key；商家券按商家拆分成多个模板，天然分散但会跟着商家热度走。商家券的热点处理思路是水平分桶：把「某模板的库存」切成 N 份，按 `hash(userId) % N` 或按批次落到不同桶，写请求就分散到不同 key 甚至不同节点上；分桶位置要讲清是在缓存/库存层的 key 上分（`stock:{templateId}:{bucket}`），不是把数据库表拆开。桶内余额不足时走桶间借调或回源数据库，同时接受「总库存没超卖但某个桶先空」的短暂不均衡。

**券的归属与不串券：靠数据模型和唯一索引，不靠逻辑自觉。** 券记录上必须同时写 `userId`、`merchantId`、`templateId`，查询和核销都带上这三个维度；领取时用 `(userId, templateId)` 唯一索引保证幂等，服务端的 `userId` 一律从会话里取、绝不信前端传参；核销时校验券的商家与当前订单的商家一致。面试官反复问「第一次领券怎么保证不领错」「用户动线」是在检查你有没有把发放、查询、核销三段串成一条完整链路——领券发生在进入商家页或活动页时，查券发生在「我的卡包」按用户维度查，核销发生在下单时按订单商家与券模板匹配，三段的主键维度不一样，这个区别讲清楚就赢一半。

**JVM GC：先答「解决什么」，再答「怎么选」。** GC 解决的是堆内存的自动回收——从 GC Roots 出发做可达性分析，回收不可达对象，避免手工释放带来的泄漏与悬垂指针。回收器按代际分：Serial/ParNew 是年轻代复制算法，Parallel Scavenge 系列追求吞吐（适合批处理），CMS 用并发标记清除追求低停顿但有内存碎片和并发模式失败，G1 把堆分成 Region、按 `-XX:MaxGCPauseMillis` 挑选回收集合做可预测停顿，JDK 9 起是默认；ZGC/Shenandoah 用染色指针和读屏障把停顿压到亚毫秒级，代价是额外内存和吞吐损失。触发时机：Eden 满触发 Minor GC，对象晋升失败、大对象分配失败、元空间耗尽或显式 `System.gc()` 触发 Full GC，G1 则是根据停顿目标决定是否做 Mixed GC。结合回收器讲就是讲三色标记、卡表/记忆集解决跨代引用、以及并发标记期间靠 SATB 或增量更新保证不漏标——能主动提「漏标」比背参数表更像读过源码。

**两道手撕的答法。** 合并两个有序链表：递归写法是「取较小的头节点，让它的 next 等于剩下的合并结果」，基准情形是任一链表为空；边界要覆盖两个都为空、只有一个为空、相等时取哪边（结果都对，但要说明稳定性）、以及递归深度为 O(m+n) 可能栈溢出——生产代码里用迭代加哨兵节点更稳。第二题题干只有「小于 n 的最大值」一句，实际面试里第一步是澄清输入形态（数字数组、数字字符串还是整数）和限制条件，再给贪心构造思路：从低位向前找到第一个可以「变小」的位置，把它减一，后面的位全取最大；如果不允许前导零或需要保持位数，还要额外处理。这类题考的是沟通与边界意识，不是背一道原题。

**凉经复盘。** 原帖的时间线是周六一面、面完二十分钟约二面、次日下午收到感谢信——面试节奏极快，说明一面表现足够进二面，挂点在二面。二面的问题几乎全部围绕优惠券的平台券/商家券设计、分桶定位、并发上限和用户动线，属于「你到底有没有真正设计过这套系统」的深挖，同一件事从业务、数据、缓存、并发四个角度反复问；一面八股答得出来但项目细节撑不住，是这类面试最常见的挂法。准备时的正确姿势是：给简历上每个项目准备一条「业务目标 → 数据模型 → 关键链路 → 容量与瓶颈 → 踩过的坑」的自述，并且能在任何一点被追问三层。
