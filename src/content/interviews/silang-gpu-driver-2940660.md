### 《参考解析》

**KMD 与 UMD 的分工**：UMD 跑在用户态，负责把图形或计算 API 翻译成硬件能执行的命令缓冲（command buffer），做资源分配的上层决策、shader 编译、状态校验与批处理；它不能直接碰硬件，只能通过系统调用找 KMD。KMD 跑在内核态，负责设备初始化与电源管理、显存与 GEM/TTM 类的对象管理、页表与 GPU MMU 的维护、命令提交与调度、中断与 fence 完成通知、以及进程上下文隔离。一次典型提交是：用户态在 GPU 可访问的内存里构建命令缓冲，把缓冲区句柄、依赖的 fence、目标上下文打包进 ioctl；KMD 校验参数与句柄归属、把缓冲 pin 住并映射到 GPU 地址空间、写入 ring buffer 或 doorbell 寄存器；GPU 执行完发中断，KMD 在中断里推进 fence、唤醒等待者，必要时触发调度下一批。这条链路要能讲清「为什么命令缓冲要放在共享内存而不是每次拷贝」。

**MMU 走表流程**：以 ARM64 的 4 级页表、4KB 页为例，48 位虚拟地址拆成 9 + 9 + 9 + 9 + 12：最高的 9 位索引 L0，依次到 L3，最后 12 位是页内偏移；TTBR0 管用户空间、TTBR1 管内核空间。CPU 发出虚拟地址后先查 TLB，命中直接得到物理地址；miss 时由硬件（或软件，取决于架构）做 page table walk：逐级读页表项，检查有效位与权限位，遇到大页（L2 的 2MB、L3 的 1GB 在 L1）就提前结束；任一级无效则触发缺页异常，由内核决定是补映射、换页还是给进程发 SIGSEGV。页表项里除了物理页号，还有可读可写可执行、用户/内核、访问位与脏位、以及属于哪个地址空间标识（ASID）的信息。GPU 自己的 MMU 逻辑类似，只是页表由驱动维护、粒度与格式按硬件手册来。

**TLB 与一致性**：TLB 是页表项的缓存，避免每次访存都走多级页表；miss 的代价是几级内存访问（几十到上百周期，若页表本身也被换出还要更多），所以大页能显著减少 TLB 压力和走表层数。TLB 一致性指 TLB 里的映射必须与内存中的页表一致：改了页表（unmap、改权限、换页）而没让对应的 TLB 项失效，CPU 就会继续用旧映射访问已经释放的物理页，属于典型的 use-after-free 型安全漏洞。需要 flush 的场景：进程切换且硬件不支持 ASID（有 ASID 时只切 ASID 即可）、`munmap` 或 `mprotect` 之后、页表页被释放前、模块卸载、以及内核修改了自身映射。多核场景还要做 TLB shootdown，用 IPI 让其他核一起失效，这也是为什么高频 `mmap`/`munmap` 会成为性能瓶颈。

**DMA 的地址与一致性**：DMA 让外设直接读写内存，CPU 只负责配置，传输参数至少要给源地址、目的地址、长度、位宽与突发长度、传输方向、通道或描述符、以及完成通知方式（中断或轮询）。设备侧看到的一般是物理地址，或者经 IOMMU/SMMU 映射后的 IOVA；不能直接给它 CPU 的虚拟地址，因为设备没有能力走 CPU 的页表，而且进程的虚拟地址随时可能被换出或重映射。用 IOVA 的好处是隔离与安全（设备只能访问被映射的区间），代价是多一层映射与缺页处理。一致性上分两种：coherent 内存由硬件保证（`dma_alloc_coherent`），非一致内存要在 CPU 写完后 clean cache（把脏行写回）、设备写完后 invalidate cache（丢弃旧行），否则 CPU 读到的是缓存里的旧数据——这正是二面那道「GPU DMA 后 CPU 读不到最新数据」的根因。

**启动链路与 OpenSBI 的特权级**：上电后 CPU 在 M 模式从 BootROM 取指，BootROM 按启动介质把下一级镜像搬到 SRAM；RISC-V 平台上通常是 BootROM → FSBL/SPL → OpenSBI（M 模式固件）→ U-Boot（S 模式）→ Linux 内核（S 模式）+ dtb。OpenSBI 运行在 M 模式，实现 SBI 接口，向上提供定时器、IPI、远程 fence、重启与关机等能力，并在 S 模式与 M 模式之间做 trap 转发；U-Boot 负责初始化 DRAM 与外设、加载内核与设备树，把控制权交给内核并把 dtb 的物理地址按约定放进寄存器（RISC-V 是 a1，ARM64 是 x0）。dtb 是设备树二进制，描述硬件拓扑与外设参数，内核据此匹配驱动；它不属于可执行代码，只是数据，由 U-Boot 从存储或网络加载并在启动时传递。

**接口设计：ioctl 与 mmap 的分工**：控制平面走 ioctl（创建/销毁上下文、提交命令、查询状态、设置参数），数据平面走 mmap（把显存或命令缓冲映射进用户态，实现零拷贝）与共享内存 / dma-buf。全部走 ioctl 的问题是每次都要 `copy_from_user` 把大块命令缓冲拷进内核再拷给设备，双份拷贝带来延迟与内存带宽浪费，命令缓冲动辄几百 KB 到几 MB 时完全不可接受；而且内核里还要额外分配中转缓冲。mmap 的问题在安全：映射出去的页必须校验来源与权限，不能让用户态映射任意物理页，卸载与进程退出时要能追踪并回收。工程上的常用做法是「句柄 + 懒映射」：ioctl 创建对象返回句柄，mmap 按句柄映射，KMD 维护每个进程的句柄表并在 `release` 时统一清理。

**显存与 buffer 的生命周期**：分配侧要有分级（小块用 slab/buddy、大块按页或按 2MB 大页）、区分本地显存与系统内存、支持可迁移与可压缩；对象用句柄管理，记录大小、对齐、用途（命令、纹理、输出）、以及被谁引用。映射侧维护 GPU 页表项与 CPU 映射，做 pin/unpin 与 eviction（显存不足时换出到系统内存），必要时挂 shrinker 响应内存压力。生命周期上最容易漏的是进程被 `SIGKILL` 时的清理：文件描述符关闭触发 `release`，要释放该进程全部句柄、解除映射、回收 fence 与信号量、从调度队列里摘掉未完成的任务；共享对象（dma-buf）用引用计数，最后一个引用消失才真正释放。答这道题要主动提「泄漏与悬垂引用怎么防」，比如句柄表按进程隔离、对象带引用计数、卸载时遍历清理。

**从零写一个字符设备驱动**：先 `alloc_chrdev_region` 拿设备号（或 `register_chrdev` 用主设备号），`cdev_init` 绑 `file_operations` 再 `cdev_add`，用 `class_create` + `device_create` 在 sysfs 下生成节点让 udev 建 `/dev` 文件，模块初始化和退出分别注册与反注册。`open` 里做权限与上下文初始化、把私有结构挂到 `file->private_data`；`release` 里释放；`read`/`write` 做数据搬运；`ioctl` 用 `_IOW`/`_IOR` 定义命令号并 `switch` 分发；`mmap` 用 `remap_pfn_range` 或 `vm_insert_page` 映射。用户态与内核态之间传递数据必须用 `copy_from_user` / `copy_to_user`（它们会处理缺页与非法地址），指针参数要先用 `access_ok` 校验，长度要有上限，结构体里不能有用户态指针（要用句柄或固定长度数组），命令号用 `_IO` 宏族生成以避免与架构位宽不一致。
