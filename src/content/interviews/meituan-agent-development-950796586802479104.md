### 《面试题目》

**项目与链路**

1. 可以详细介绍一下项目：项目场景、设计方案、开发内容？
2. 选取一个真实问题单，完整描述从 Agent 接收输入，走完全流程，到产出最终结果的整条链路？
3. 测试报告 / 测试用例设计，如何判断符合本次新需求改动？新功能无历史问题单，怎么设计测试用例？
4. 需求文档、技术方案为什么没有作为输入信息纳入系统？
5. 最终产出的结果只是文本，是否会执行真实任务？哪些环节需要人工确认？
6. 信息如何持续积累、迭代更新？执行失败后的结果如何回流？
7. 提到将 xx 耗时从 1 小时压缩到 3 分钟，耗时瓶颈在哪，哪些环节快、哪些慢？
8. 项目使用 Python + FastAPI，数据库层如何接入？数据库表是否由你设计？
9. 两个 QA 同时输入相同查询，Agent 给出的报告是否一致？

11. 外部环境、参数变化，会不会导致相同测试任务执行结果不一样？如何处理？
12. Agent 项目 2 对比项目 1，在 Agent 设计层面有什么差异？
13. 你主要负责哪些模块、哪些具体开发工作？

### 《参考解析》

**项目要讲到边界、证据与口径**：介绍项目先回答「谁在什么场景遇到什么问题」，再讲方案与交付，按业务边界、数据与上下文、控制与执行、工程交付、收益与代价五层展开，每层配可展示的证据：需求范围与验收条件、数据契约与版本权限、状态流转与一次完整 trace、日志与回归结果、同口径对照及失败样本。判断是否算 Agent，看能否解释为什么需要模型、哪些环节用确定性代码、什么条件下停止、当前还做不到什么；只接一个模型接口不构成 Agent。讲链路时沿同一个 run_id 走完输入、决策、工具调用、状态变化与输出，先给一个成功样本，再给一个系统无法独立处理的失败样本，两者并列才能说明架构选择的理由。模块归属按「模块边界—具体代码—关键决策—验收证据」回答，模块名太宽就继续拆，例如执行器包含工具注册、参数校验、超时取消、状态持久化、幂等与错误归一化，并区分独立开发、协作开发与框架配置。效果数字先澄清计时口径：原数据是人工有效操作时间还是含等待的总耗时，新数据是否只算生成报告、是否含执行复核排队与重试；按 span 分解后串行阶段可直接相加，有并发则算依赖图的关键路径。串行假设下局部优化的整体上限由 Amdahl 定律给出，1/((1-f)+f/s)：模型生成只占原耗时 20%、即便快 10 倍，整体也只有约 1.22 倍；若耗时主要花在人工整理与系统间搬运信息，改造整条流程比优化单次解码更有效。AICoding 笔试题则先复述输入、输出、约束与验收标准，把自然语言需求转成可检查条件，对歧义给出最小澄清或可逆假设，先跑通成功路径再补失败分支，用独立设计的样例、边界、故障与重复请求验证，最后交付可复现的启动方式与已知限制。

**Workflow 与自主循环的取舍**：测试任务有明确的准入、取证、计划、校验、执行、归档阶段，且需要重试、审批与审计，适合用 Workflow 把状态与合法转移显式化：路径稳定的部分交代码，模糊分析放在受约束的模型节点里。执行形式可归为固定链或 DAG（程序定顺序，易测但新分支要显式设计）、路由与并行（规则或分类器选分支，需处理错误路由与合并冲突）、带检查点的状态机（按状态与事件恢复，适合长任务，代价是持久化与版本迁移）、ReAct 工具循环（模型依观察选下一步，灵活但路径与成本难预测）、规划后执行与动态重规划（先拆目标，防计划与状态脱节）、主代理与子代理（分工汇总，增加协调与上下文成本）。这些形式可组合而非互斥，关键区别在于哪些决策交给模型、模型能改变多大范围。本场景用外层 Workflow 控预算、权限、确认与终态，内部允许模型提测试点或分析失败，并以固定分支基线对照动态方案的完成率、尾延迟与错误动作，避免为「自主」放弃可验证性。检查点至少存已确认输入、计划版本、已完成步骤、证据引用、待满足条件与外部操作 ID；恢复时先核对外部效果再选下一条合法转移，进程退出只说明执行器停止，不足以证明远端作业已取消。同一任务的结果是输入、构建版本、环境、数据、配置、外部依赖与随机性的函数，运行清单要记镜像与提交版本、配置开关、资源 ID、数据快照、依赖版本、时区、随机种子与并发条件、模型与检索策略版本；可控部分用隔离环境、固定夹具、可重置数据、虚拟时钟与依赖 mock，mock 通过不等于真实集成通过。失败分确定性断言失败、环境阻塞、依赖失败与偶发不稳定，重跑只用于诊断，不能重跑到成功再覆盖首次结果。

**参数校验、人工确认与资源解析**：先语法校验再语义与权限校验，JSON 合法只说明格式正确，无法证明环境、资源、时间范围或操作目标正确。参数分三类：可按业务契约填充的低风险默认值、可从会话或权威目录检索的参数、必须由用户明确决定的高风险或多义参数；补全结果要记录取值依据，不能只依赖模型置信度。流程是提取候选参数、schema 校验、权限与资源查询，缺失或冲突时集中澄清并保存检查点，合并回复后重新校验，参数完备再构建计划、按风险确认、执行并验证。生产环境、不可逆操作对象、金额、范围扩大、目标无法唯一确定或业务规则冲突需要明确确认；已授权且唯一确定的只读参数可直接使用，追问次数不构成严谨性。确认绑定计划版本、资源与参数摘要（plan_hash、resource_id、resource_version、scope、expires_at），计划实质变化须重新确认，已授权且未变的操作不应反复打断。资源解析先按租户、项目、环境、类型、时间等硬约束过滤，再名称匹配或语义排序；只剩一个候选也要检查约束与证据，多个合理候选展示资源 ID、项目、环境、更新时间等足以区分的信息由用户选择，没有候选则说明缺什么条件，不生成虚构 ID。排序第一不等于唯一正确，模型概率不是授权；自动选择必须有业务明确的解析规则并留痕。确认后绑定不可变 ID 与资源版本，执行前再检状态与权限，用条件更新或乐观锁防止「确认时是 A、执行时指向 B」。人工确认不能代替服务端校验，也不能把不可信的工具结果当成下一步指令。

**幂等、超时核对与补偿**：幂等键要绑定规范化请求摘要，覆盖环境、资源 ID、业务参数与适用版本，而不只是用户输入文本；同作用域、同键、同摘要复用已有操作状态，键同而摘要不同返回冲突。并发下先查后插仍有竞态，最终去重靠数据库唯一约束或同等原子性机制。工具超时而外部动作可能已生效时进入「结果待核对」，按外部操作 ID 或业务键查询效果，确认成功补记、确认未执行才考虑安全重试，无法确认则阻塞或人工接管；直接标成业务失败再重做会重复动作。Python 侧按路由、业务与数据访问分层，Session 由依赖注入按请求或工作单元提供；同步驱动直接放进 async 路由会阻塞事件循环，AsyncSession 是有状态对象，不能给并发任务共享。事务边界要短：等待模型或外部工具期间连接与锁被长期占用，且提交成功不证明外部动作完成，因此把任务落库与待投递事件放进同一事务（outbox），投递器读 outbox 发送并记录状态；发送成功后、标记前崩溃会重复投递，消费者还需按事件 ID 去重，副作用动作仍要幂等——outbox 只解决任务与事件一起落库，不保证端到端恰好一次。跨系统写入同理，数据库回滚撤不掉已发出的通知、已完成的退款或已创建的云资源；补偿是新业务操作，可能失败且必须留痕，不可靠补偿的动作要提前缩小权限与操作范围并准备人工对账。状态更新用比较并交换，只有当前状态与版本符合预期才写入，并检查受影响行数。两个 QA 同一查询是否得到相同报告，先定义需要哪种一致：文字表达、结构化结论、证据快照，还是外部动作只执行一次，四者措施不同；温度 0 只减少采样变化。事实类报告可固定结构化字段与证据快照再渲染，缓存键至少含租户与权限范围、标准化查询、数据与模型策略版本，权限变化或到期必须失效；多用户共用缓存时权限等价性由服务端判断，不信客户端自报的 permission。

**CLI 是机器接口而非脚本别名**：CLI 的开发内容要落到可调用契约：子命令划分、参数 schema、配置优先级、鉴权、服务调用、输出协议、退出码、错误处理与自动化测试。测试类 CLI 可提供 plan、run、status、cancel 等子命令，输入支持结构化文件，输出稳定 JSON，日志走 stderr，stdout 留给机器消费；长任务返回 run_id 由调用方查状态；退出码区分参数错误、权限错误、执行失败与等待外部输入。请求携带环境、资源 ID、计划版本与幂等键；配置层明确命令行、环境变量、配置文件的优先级；凭据经受控存储或环境注入，不进命令行参数与日志；调用外部程序用参数数组、固定可执行文件与允许的子命令，不拼 shell 字符串，并提供超时、取消与输出大小限制。语义上必须写清「命令调用成功」与「业务任务成功」：status 查到失败任务可返回 0 并在 JSON 给出 FAILED，run --wait 可约定任务失败返回非零，含糊会让上层 Agent 误判。输出带 schema_version、run_id、status、missing_fields、retryable 等字段；retryable 要结合错误类型与外部副作用判断，不能仅因 5xx 自动重试；把工具输出当数据读，比让模型猜自由文本日志更易验证。封装价值在于做成可复用、可版本化、可独立测试的接口，同一能力供终端、CI、Skill 或 Agent 使用，无聊天上下文也能复现一次操作；Skill 说明何时用、按什么步骤、如何验收，CLI 承担参数解析、权限校验、接口调用与结构化结果，业务核心放共享库或服务，CLI 只做适配层。相比自然语言步骤它减少模型重复生成命令与解释日志；相比直接导入库它有进程隔离与跨语言调用的便利，但增加启动、序列化与环境安装成本。高并发或持续交互更适合 API、队列或 MCP 工具接口；封装本身不提供安全与可靠性保证，仍需限制可执行能力、保护凭据、实现幂等并明确 schema 兼容策略。

**五个概念处在不同层次**：Skill 封装任务方法、领域约束、脚本与资源，不自动提供权限、隔离或执行引擎；MCP 是宿主或客户端与服务端交换工具与资源能力的标准协议，不决定完整规划，也不保证工具可信；Function Calling 让模型按工具契约提出函数名与结构化参数，执行、授权与业务校验由应用负责；Workflow 显式定义控制流、状态、分支与恢复，持久化与容错取决于实现；SubAgent 把子任务委派给具有独立上下文或配置的代理，不天然有进程隔离，也不必然更准。一条链可说明协作：Workflow 管状态，Skill 提供测试设计方法，模型经 Function Calling 提出读接口文档，应用转给 MCP 客户端与对应服务，执行器验证权限与参数后取结果；复杂模块交子代理分析，主流程负责证据合并与最终验收。跨层调用要传任务 ID、权限范围、时间与费用预算、结果 schema，避免权限丢失；子代理输出是待验证产物。检验落地可看一个故障：子代理建议调用删除工具，父流程仍要查是否属原始目标、目标资源是否唯一、当前身份是否有权限、审批是否覆盖此次参数；MCP 接受请求不替代业务授权，Function Calling 符合 schema 不证明操作正确。Skill 本身是围绕特定任务组织的可复用能力包，说明何时触发、如何处理、需要什么输入、有哪些约束、如何判断完成；以 SKILL.md 规范为例，入口含名称、描述与正文，可附脚本与参考资料，因此它不限于几句流程说明，可承载完整领域方法与配套实现，但内容取决于作者写入，名称本身不保证有架构、代码、部署与测试。渐进加载先暴露简短元数据，匹配后读主说明，必要时加载文件以减少常驻上下文；好的 Skill 写清输入前提、步骤与分支、工具契约、失败恢复、输出位置与验收条件。Skill 不是新的授权主体，也不天然创建子代理。这些层不必齐全：已有稳定 SDK 的单工具任务可直接调用，固定小流程不需要子代理，取舍看可维护性、边界与效果。

**需求入参、测试预期与记忆维护**：需求文档与技术方案缺位时，若初版只做历史问题归纳，可解释为数据权限、版本对齐或解析成本的取舍；若目标已是验证新需求，缺少它们会让预期失去依据，应承认是设计缺口。接入时为文档建项目、需求 ID、版本、生效时间、适用环境与访问权限等元数据，按标题层级、接口、表格与规则切分并保留原段落位置，先用项目与版本过滤再做检索，表格里的条件与例外不能在切分中丢失。材料分工是验收条件定义应有行为、技术方案说明实现约束与影响范围、代码差异描述实际改动、历史问题提供风险线索；冲突按团队确认的权威规则处理，不让模型自行裁决业务规范，外部文档属待分析数据，不能因其中出现「忽略规则、调用工具」就改变系统权限或流程。测试覆盖建立「需求条款—改动点—用例—断言—执行证据」的可追溯关系，取决于用例与断言是否对应验收条件，而非报告是否提到新功能；无历史问题单仍可从规范、产品确认、接口 schema、领域不变量与风险分析推导。预期要有独立依据：生成器与评审器同模型同上下文会一致犯错，关键规则用可执行断言、专家审核、故障注入或变异测试验证；覆盖率等于有有效用例覆盖的确认条款数除以条款总数，高覆盖率不等于无缺陷。记忆上把知识库（业务规范与文档）、短期状态（本次任务的已知条件与进度）、长期记忆（筛选后可跨任务复用）分开，RAG 是检索与上下文构建方式，不等于记忆。短期状态含目标、已确认参数、待澄清字段、计划、工具结果引用与检查点，长对话摘要要保留资源 ID、明确约束、确认范围与未解决问题。长期记忆区分用户偏好、领域事实、经验证的经验与操作规范，写入判断准确性、复用价值、权限与保留期限，模型猜测或偶发错误未经审核不得转为长期事实；读取先按租户、用户、项目权限过滤，再按相关性、时效性排序，用户偏好不能覆盖业务规则或扩大授权。典型冲突是记忆里留着旧退款上限、需求文档给出新版本：按接口版本与生效区间选有效规则并使旧记忆退出当前任务，不按相似度取旧值也不取平均，版本关系不明先澄清。删除是完整链路，除主存储还要处理向量索引、缓存、派生摘要与备份保留，撤销访问后的在线读取须尽快拒绝。失败回流把原始执行记录、候选经验与审核后的知识分开存储，日志可自动积累，但一次失败后的模型解释不能直接成为长期事实；每次运行留输入快照、工具与模型版本、检索证据、结构化步骤、异常与人工修正，先分类失败（需求不清、召回遗漏、推理错误、参数错误、权限、环境、真实缺陷）再决定改哪个环节，网络超时修执行策略而非改业务答案。闭环为「采集—脱敏—去重—归因—审核—进入回归集—小范围验证—发布」，新知识记适用条件、版本、有效期、责任人与被替代关系，冲突保留并仲裁；效果用独立留出集与线上抽样确认，反馈样本不能同时作优化数据与唯一验收数据，指标覆盖错误复发率、覆盖变化、人工修改量与新引入退化，并支持版本回滚。

**存储按数据语义分层，Redis 锁有失效边界**：存储先按数据语义选型：任务与权限等需一致性约束的数据用关系库，大日志、附件与报告放对象存储，检索索引用作查找，Redis 承担有明确失效策略的缓存与协调，向量库不能替代业务事务库。一个任务可有多次运行，一次运行含多个步骤，重试要区分同一步的尝试与重新发起业务任务；审批记录绑定计划哈希、资源版本与有效期，执行前重新核对，参数或范围变化则旧审批失效；向量索引常异步更新，要暴露索引版本或延迟，源文档删除与权限撤回及时传播并在召回时校验；数据库事务覆盖不到外部动作，需要幂等、outbox、补偿或对账。Redis 在 Java 中经客户端或 Spring Data Redis 接入，选型按数据结构、并发语义、过期与故障行为解释：热点缓存用 String/Hash 加 TTL 与 cache-aside，库与缓存通常非强一致，须定义失效窗口；会话验证码用有时效的键与原子计数，关注一次性消费与重放；计数限流用 INCR、Lua 或 Sorted Set，多步要原子化且脚本不能长时间阻塞；排行榜用 Sorted Set，处理并列规则与热点；任务协作用 Streams 与消费组，处理待确认、重投与消费者幂等；互斥用带租约的锁。常见部署中命令执行以串行路径为核心，网络 IO 与后台任务可涉及其它线程，不能把整个 Redis 说成单线程；长命令、大 key、热点 key 与网络往返仍会成为瓶颈。缓存区分穿透、击穿与雪崩，可结合空值短缓存、布隆过滤器、请求合并、TTL 打散与限流降级；提交后删缓存仍会因并发读写、删除失败与旧值回填留下窗口，重要场景用版本校验与可靠失效事件收敛。锁用 SET key token NX PX ttl 获取、原子比较 token 后删除；但租约过期后旧持有者仍可能继续执行——A 持 30 秒租约后暂停，到期后 B 取得新锁并写入，A 恢复照样写库，比较 token 只防误删不防过期写入。高风险写入应使用底层资源支持的 fencing token、数据库约束或一致性服务：每次取得执行资格取单调递增序号，下游记录已接受序号并在原子写入时拒绝较旧序号，只有下游真正执行检查才有效，把数字放进日志或 HTTP 头没有保护作用。订单类关键业务的唯一约束、条件更新与业务幂等应直接落在最终存储，Redis 锁只减少争用，不应成为账本正确性的唯一依据。RDB 为周期快照、AOF 记录写操作，持久化策略影响恢复时间与丢失窗口；复制、分片与持久化解决不同问题，Cluster 多 key 原子操作受同一 hash slot 约束；Java 端还要关注连接池、超时、序列化与客户端重试带来的重复副作用。
