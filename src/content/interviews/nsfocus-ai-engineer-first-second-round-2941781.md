### 《参考解析》

**传统 RAG 的问题与解法方向**：问题集中在四段——解析（表格、扫描件、跨页结构丢失）、分块（切断语义、上下文不全）、检索（纯向量的字面不敏感、召回不全、多跳问题答不了）、生成（不看检索内容、引用错误）。对应的技术方向是：结构化解析与版面理解、语义分块与父子块（小块检索、大块喂给模型）、混合检索（向量 + BM25）加 rerank、查询改写与多跳检索（把问题拆成子问题迭代检索）、GraphRAG（把实体关系抽成图，做多跳与全局摘要）、以及生成侧强制引用与忠实度校验。除知识图谱之外，还可以用实体链接 + 文档元数据过滤、层次化摘要树（先摘要再下钻）、以及把长文档转成结构化表格（适合参数、条款类）。

**HTTP 与长连接**：HTTP 是应用层协议、基于 TCP（HTTP/3 基于 QUIC / UDP），报文由起始行、头部、空行与主体组成，无状态。版本差异主要说：HTTP/1.1 引入持久连接与管道化但仍有队头阻塞；HTTP/2 用二进制分帧与多路复用解决应用层队头阻塞、支持头部压缩（HPACK）与服务端推送；HTTP/3 用 QUIC 把可靠传输放到 UDP 上，解决 TCP 层队头阻塞并支持连接迁移与 0-RTT。长连接实现方式有：轮询、长轮询（comet）、SSE、WebSocket、以及 WebTransport / gRPC streaming。

**为什么 AI 场景用 SSE**：模型输出是单向的、服务端持续产生 token，客户端只收不发；SSE 基于普通 HTTP 响应流（`text/event-stream`），能复用现有的鉴权、网关、日志与 CDN，天然支持断线重连与 `Last-Event-ID` 续传，服务端实现成本低（就是一个流式响应）；WebSocket 是全双工，需要额外的握手升级、连接管理与心跳，且在部分代理与网关下更容易被中断。代价是 SSE 单向、受浏览器同域连接数限制（HTTP/1.1 下每个域约 6 个，HTTP/2 下不成问题），需要 POST 长请求时得用 fetch 流式读取而不是 EventSource。

**事务 ACID**：原子性靠 undo log 回滚，一致性是事务前后满足约束（由应用与数据库共同保证），隔离性靠锁与 MVCC，持久性靠 redo log（WAL，先写日志再刷脏页，崩溃后重放）。要能说清「哪个特性由哪个机制支撑」，这是这题的考点。

**索引与 B+ 树**：索引类型按结构分 B+ 树、哈希、全文、空间（R-Tree）；按物理组织分聚簇索引（主键，叶子存整行）与二级索引（叶子存索引列 + 主键）；按约束分主键、唯一、普通、联合、前缀。InnoDB 选 B+ 树的原因：磁盘 IO 以页为单位，B+ 树一个节点存大量键、树高通常 3~4 层即可支撑千万级数据，一次查询只需几次页访问；叶子节点用链表相连，天然支持范围查询与排序；所有数据都在叶子层，查询路径长度稳定。红黑树是二叉结构、树高 log₂N 远大于 B+ 树的多叉高度，磁盘访问次数多；B 树把数据也存在内部节点，单节点能放的键更少、范围查询要中序遍历、节点分裂更复杂；跳表的查询路径是链表式的多层跳跃，节点分散存储、无法利用页的局部性，范围扫描要沿底层链表走，磁盘场景下 IO 次数不可控，且不支持聚簇存储。

**慢查询分析**：先 `EXPLAIN` / `EXPLAIN ANALYZE` 看访问类型（`ALL` 全表扫、`index` 全索引扫、`range`、`ref`、`const`）、key 是否命中、rows 估算、filtered、Extra（`Using filesort`、`Using temporary`）。再看慢查询日志与 `performance_schema` 定位高频与高耗时语句。

**走了索引仍然慢的原因**：回表次数太多（二级索引命中大量行再逐行回表，范围大时不如全表扫，优化器可能选错；用覆盖索引或调整选择性）；索引选择性差（区分度低，扫描行数仍大）；`Using filesort` 或 `Using temporary`（排序与分组无法用索引，数据量大时落磁盘）；深度分页（`limit 100000, 20` 要扫过前十万行，改用游标 / 延迟关联）；锁等待与事务长（`innodb_lock_wait`）；返回数据量大导致网络传输与序列化开销；统计信息过期导致执行计划选错（`analyze table`）；以及索引列上有隐式转换或函数运算使索引失效（这时 EXPLAIN 看起来命中了但实际类型不是 range）。

**AI coding 的问题与规避**：作者提到用 SDD（先写规范 / 设计再让 AI 实现）。其余常见问题与对策：上下文不足导致瞎猜（先让它读相关文件与约定）、跨文件改动不完整（拆成小步、每步验证）、幻觉出不存在的 API（要求给出来源或先跑类型检查）、测试与代码一起编（要求先写测试再实现，人审测试是否真的在测行为）、风格漂移（用 lint 与既有代码做参照）、以及「改坏了不承认」（要求给出可执行的验证命令并运行）。subagent 的用法是把检索、实现、审查拆给不同上下文，主 Agent 只做编排与最终判断。

**Agent 需要具备的能力**：工具调用（发现、选择、参数构造、失败处理）、规划与拆解（多步任务分解与状态跟踪）、记忆（短期上下文、长期记忆、任务状态）、自我校验（能否验证自己的输出）、以及边界感（不知道时问人或停止，而不是编）。工程侧还要有可观测性与可恢复性。

**上下文压缩与断线恢复**：压缩的常见做法是滑动窗口（保留最近 N 轮）+ 摘要（把更早的轮次压成一段结构化摘要，保留决策、约束、实体与未完成事项）+ 检索式记忆（把历史存起来，按需检索相关片段回填）。滑动窗口每一轮都做全量重压会让成本线性增长且反复丢信息，通常是「窗口滑动 + 分段增量摘要」：新滑出窗口的若干轮增量并入摘要，摘要过长时再做二级摘要。断线恢复靠 checkpoint：把会话状态（消息历史或摘要、工具调用的中间结果、任务进度、待确认项）持久化，重连时按 sessionId 载入并重放最后一步。checkpoint 里的内容通常分为「对话状态（消息 / 摘要）」「任务状态（计划、已完成步骤、产物引用）」「环境状态（沙盒 ID、文件句柄、凭证的外部引用）」。

**两份 state 的同步设计**：运行时的内存 state 是权威、Redis 是持久化副本，同步时机有三种可选——每一步工具调用后同步（恢复粒度细、写放大、延迟高）、按时间或轮次批量同步（折中，最多丢最近几步）、只在关键节点（用户提交、任务阶段切换）同步。回答时要给出取舍依据：优先保证可恢复且不重复执行有副作用的操作，因此有副作用的工具调用前必须先落 checkpoint（否则恢复后会重复扣款 / 重复发消息）；同时用单调递增的 step 号做幂等，恢复时从最后一个已提交的 step 继续。Redis 侧要设 TTL 与容量上限，并说明它只是「可重建的缓存」还是「唯一副本」——如果是唯一副本，就必须做持久化（AOF everysec + RDB）与主从，宕机后从副本或数据库恢复。

**发布与分支管理**：发布流程通常是 CI（构建、单测、静态检查）→ 制品（镜像 / 包 + 版本号）→ 部署到预发 → 灰度 / 金丝雀 → 全量，回滚靠保留上一个可用的制品与一键切换。发布冲突的解法是：小批量频繁合并而不是长期并存的大分支、功能开关（feature flag）把未完成的功能合进主干但默认关闭、按模块拆服务减少同一文件的写冲突、以及用 rebase / 合并前先拉取主干并跑 CI。多人共用一个 dev 分支且只测了其中一个人的功能时，正确做法是把每个人的功能放进独立分支 + 开关，或者用按 commit 出预发环境（每个 PR 一个环境），而不是在同一分支上「先合了再挑着发」。

**Python 协程与 FastAPI**：协程是用户态协作式并发，`async def` 函数调用返回协程对象，由事件循环调度；`await` 处让出控制权，切换由事件循环完成，不经过内核。Python 用生成器（`yield` / `yield from`）实现协程语义，`asyncio` 提供事件循环、Task 与 Future；CPython 的 GIL 意味着协程只在 IO 等待时并发，CPU 密集仍需多进程。FastAPI 的注意事项：路由函数若是 `async def`，里面不能调用阻塞库（`requests`、`time.sleep`、同步 DB 驱动），否则会阻塞整个事件循环，要用异步客户端（`httpx`、`asyncpg`）或 `run_in_threadpool` / 把路由改成普通 `def`（FastAPI 会放到线程池）；外部调用都要设超时与重试，并做并发上限（信号量）防止打爆下游；用依赖注入管理连接与生命周期，注意后台任务与请求取消的清理。

**怎么评估 AI 产出的方案**：先看它对问题的理解是否正确（有没有漏需求、有没有误解约束），再看方案是否与现有架构一致（是否引入了新的依赖、是否绕过既有机制），然后看边界与错误处理（异常、超时、并发、权限），最后看可验证性（有没有测试、能不能跑起来）。修改时优先让它按你的意见重写而不是自己手改，保留「为什么这么改」的记录。

**发布后快速响应用户反馈**：要有可观测性（日志、指标、trace、告警）与灰度能力（按用户或比例放量、可一键回滚），加上反馈入口与值班机制；把「发现问题 → 定位到版本或变更 → 回滚或热修 → 复盘」这条链路做成流程，而不是靠人盯。

**AI 时代的 DevOps**：可以给出有依据的判断——AI 降低了写代码与写脚本的成本，DevOps 的重心从「手工搭流水线」转向「定义正确的约束与验证」：流水线的门禁、环境的可复现、变更的可回滚、以及可观测性变得更关键，因为产出速度变快后，错误的传播速度也变快。绿盟这类安全公司还会强调供应链与权限（谁能改流水线、谁能发布）。
