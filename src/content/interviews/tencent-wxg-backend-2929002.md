### 《面试题目》

1. 手撕算法：合并区间。
2. 手撕算法：实现一个优先级队列，支持插入、取出、删除三个操作。
3. 追问：用堆实现时，删除任务只是加标记位、并没有真正删除；如果要真正删除该怎么做？
4. 追问：用链表实现时，插入中间优先级的效率是不是很低？怎么优化？
5. 追问：有没有一种数据结构既能保持有序，又能快速找到中间位置？
6. 手撕算法：一道动态规划题（原帖未记录具体题目）。
7. 实习与项目深挖：围绕实习经历、项目细节连续追问，约 80 分钟。
8. 场景题：微信公众号每个用户查看一篇文章，这篇文章的阅读量加一，如何设计这个系统？（连续追问约 30 分钟）

### 《参考解析》

**合并区间**：先按左端点排序，再线性扫描合并。排序后维护一个结果列表，遍历每个区间：若结果末尾区间的右端点小于当前区间的左端点，说明不相交，直接追加；否则说明有重叠，把末尾区间的右端点更新为两者右端点的较大值。时间复杂度 O(n log n)（排序主导），空间 O(n)。边界要主动说明：空数组直接返回空；一个区间完全包含另一个区间时取 max 而不是直接覆盖；`[1,2]` 与 `[2,3]` 端点相接是否算重叠要跟面试官确认，通常按闭区间合并成 `[1,3]`。手写时注意原地复用与返回值类型，写完用一个包含「完全包含、端点相接、乱序输入」的例子自测。

**优先级队列的真删除**：懒删除省事但有代价，要能说清代价并给出替代方案。堆加标记位（懒删除）的删除是 O(1)，但元素仍留在堆里占空间，取堆顶时要循环弹出已删除元素，堆会持续膨胀，长期运行的服务不适合。要真正删除，常见做法是额外维护一张哈希表记录「任务 id → 堆数组下标」，删除时把目标位置与堆尾交换、弹出堆尾，再对换上去的元素做一次上浮或下沉，删除降到 O(log n)；每次交换都要同步更新哈希表里的下标，这是最容易写错的地方。用「每个优先级一条链表」的桶结构，插入中间优先级要遍历找位置，是 O(n)；加哈希只能做到按 id O(1) 定位节点，插到正确位置仍要 O(n)。既有序又能快速定位中间位置，答案是跳表：多层索引把查找、插入、删除都做到期望 O(log n)，并且天然支持按排名取第 k 个；平衡二叉搜索树（如带 size 字段的红黑树）同样能按排名定位，也可以作为并列答案提出来。

**公众号阅读量系统**：这是典型的「写极多、读更多、允许短时不一致」的计数场景，核心是不让每次浏览都去打数据库同一行。写入侧先在 Redis 用 `INCR` 累加，按文章 id 做分片（或加 hash tag 分桶）避免单 key 成为热点；更进一步可以在接入层或本地内存做批量聚合，同一篇文章几百毫秒内的浏览合并成一次 `INCRBY`，把 Redis 的 QPS 压下来。落库侧用定时任务把增量批量刷回 MySQL（`UPDATE ... SET read_count = read_count + delta`），或先写流水表再异步汇总，刷失败要能重试且幂等。读取侧直接读缓存，接受分钟级延迟，页面不必强一致。追问通常会打到三个点：一是去重，同一用户反复刷新算不算一次，要按「用户 + 文章」做 Set 或布隆过滤，UV 场景可以用 HyperLogLog 换空间但要知道它有误差；二是防刷，按 uid、IP 限频，异常流量走风控旁路不计数；三是可靠性，Redis 挂了怎么办，可以用本地缓冲加补偿，或接受少量丢失并说明业务上可容忍。回答时按「写路径—存储—汇总—读取—一致性与防刷」分层讲，每层主动说取舍，比堆技术名词更加分。

**实习项目与压力面**：这类二面项目环节能占到八成时间，准备的重点是「经得起连续追问」。每个项目按背景、目标、自己负责的部分、方案选型、量化结果五段准备，尤其要能回答「为什么不用另一种方案」「数据量多大、QPS 多少、压测结果如何」「出过什么故障、怎么定位和兜底」。面试官顺着一个点往下挖时，答不上来就说清自己的思路边界和会去验证的方向，不要编造没做过的细节。场景题被追问半小时是常态，可以主动把问题拆成写入、存储、汇总、读取、一致性几块，每块先给结论再讲理由，被质疑时先确认约束再调整方案。
