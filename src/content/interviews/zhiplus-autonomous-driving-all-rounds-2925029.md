### 《参考解析》

**准确率、召回率的定义必须能现场写出分子分母。** 以检索场景为例：相关文档集合为 R、被检索出的文档集合为 A，则**召回率 = |R ∩ A| / |R|**（该找的找到了多少，分母是「所有真正的相关文档」），**准确率（精确率）= |R ∩ A| / |A|**（找出来的有多少是对的，分母是「检索出来的结果数」）。RAG 里常说的 Recall@K 是「前 K 条里是否包含正确文档」，Precision@K 是「前 K 条里正确文档的比例」。要主动补两点：① 这两个指标此消彼长（提高 K 会提升召回、降低精确），所以要用 F1 或 NDCG/MRR 这类兼顾问顺序的指标；② **准确率有个坑**——分类场景下「准确率」是 (TP+TN)/总数，与检索里的精确率不是一回事，回答时要先说明语境。至于具体数值，**不能编**：要么给出真实评测结果（数据集规模、评测方法），要么说明「我按 X 条样本评测得到 Y，样本量小所以置信区间宽」，讲不出口径就说明没做过。

**「为什么 Code Agent 会误判性能瓶颈」是个很有针对性的问题。** 原因可以归为几类：① **观测缺失**：Agent 只看代码不看运行时数据（没有 profiler、火焰图、真实 QPS 与延迟分布），于是凭代码直觉猜「这里有循环所以慢」；② **数据规模失真**：本地跑的样本量小、数据分布与线上不同，O(n²) 的代码在小数据上根本看不出问题；③ **混淆瓶颈层次**：把 CPU 热点、IO 等待、锁竞争、GC、网络往返混为一谈，实际上延迟常常来自下游调用而不是本地计算；④ **上下文偏差**：既然代码里注释或提交信息说「这里做了优化」，模型会倾向于相信它。正确的做法是**用数据驱动**：先测分段耗时（entrypoint 埋点、火焰图、pprof/perf、分布式追踪），定位到具体函数与调用次数，再验证「改掉它延迟是否真的下降」（A/B 或开关对比）。**Reranker 是否通用**：它不是 RAG 的必需步骤——检索量小、相关性要求低时可以不用；它的价值在「候选集较大且排序质量重要」时最明显，因为 cross-encoder 逐对计算相关性精度高但成本随候选数线性增长，所以总是先用便宜的双塔/BM25 召回几十到上百条，再用 reranker 精排 TopN。所以正确的说法是「reranker 是精度与成本的折中手段，不是通用步骤」。

**「你做的两个服务算微服务吗」这类问题，考察的是对概念的判据。** 微服务的核心不是「拆成多个进程」，而是**围绕业务能力独立部署、独立演进、有明确边界与契约、能独立扩缩容**：每个服务有自己的数据存储（避免共享库导致的隐式耦合）、通过 API/RPC/消息通信、有独立的发布与回滚流程、失败要能隔离（熔断降级）。只把单体按技术分层（前端服务 + 后端服务）拆开、但仍共享数据库与发布节奏，那更像「分布式单体」，会同时吃到单体的耦合与分布式的复杂度。**为什么选 C++ 做服务端**：如果是延迟敏感、需要复用已有 C++ 库（音视频、算法、推理）、或团队本来就以 C++ 为主，那合理；否则 Web 服务端生态（框架、ORM、调试、招聘、迭代速度）Java/Go 更成熟，代价要诚实说出来。**C++ 做 Web 服务的生态**：网络库有 Boost.Asio、libevent/libuv、muduo、Seastar，HTTP 框架有 Drogon、oatpp、cpp-httplib，RPC 有 gRPC（C++ 是原生生实现）、Thrift，序列化有 Protobuf/FlatBuffers，但**确实没有 Spring 这样的一体化生态**，也没有成熟的 ORM（主流做法是查询构建器或手写 SQL 映射），依赖管理靠 vcpkg/Conan，调试与热部署体验也弱。**自己实现类 ORM 会用到的 C++ 技术**：编译期反射的替代方案（宏/模板元编程生成映射代码、代码生成器产出元数据）、可变参数模板 + 折叠表达式做参数绑定、`type_traits`/`if constexpr` 做类型与数据库类型的转换、RAII 管理连接与结果集生命周期、以及用 `std::variant`/`optional` 表达可空字段；难点在类型安全与 SQL 注入防护（必须用预编译参数绑定而不是字符串拼接）。**Redis 分布式锁**：用 `SET key value NX PX ttl`（value 存唯一标识如 UUID，NX 保证互斥，PX 防死锁），释放时用 Lua 脚本先比对 value 再删除（防止误删他人的锁）；要讨论的边界是：业务执行时间超过 TTL 会导致锁提前失效（需看门狗续期，如 Redisson 的实现）、Redis 主从切换可能丢锁（严格场景要用 Redlock——但 Redlock 本身也争议不小，或用 fencing token + 幂等兜底），以及**本地缓存 + 分布式锁**组合下的可见性问题。
