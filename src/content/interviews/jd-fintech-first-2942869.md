### 《参考解析》

**热点数据怎么识别**：先定义「热点」的口径——按访问频次（QPS 排名）、按集中度（同一 key 在短时间内的请求占比）、按业务事件（大促、突发热点）。识别手段有实时统计（滑动窗口计数、Redis 的 `zset` 或本地计数器上报）、链路追踪里的 TopN 接口、以及慢查询与缓存命中率监控。识别出来后做本地缓存、热点探测与隔离（单 key 限流、防止打穿到数据库），并注意热点 key 在 Redis 集群里会压到单个分片。

**流式生成如何不丢字**：服务端用 SSE 或 WebSocket 逐块下发，每块带序号；客户端按序号拼接，发现缺口就请求补发或重连续传。服务端侧要保证「生成完成」与「发送完成」分离——模型流结束后发一个明确的结束事件（含总块数与校验），客户端收到才算完成；网络中断时用 `Last-Event-ID` 或自定义游标重连续传，服务端保留最近一段缓冲。还要处理代理层缓冲（Nginx 关 `proxy_buffering`、加 `X-Accel-Buffering: no`）、心跳保活防中间层超时断连、以及客户端渲染与接收解耦（接收队列满了不阻塞读）。落库时把完整结果单独存一份，前端展示与历史记录以落库版本为准。

**旅游 Agent 怎么设计**：分四层。意图与槽位层解析目的地、时间、人数、预算、偏好（亲子、美食、小众），缺失的关键槽位主动追问；规划层把任务拆成交通、住宿、景点、餐饮、行程编排，用工具调用查实时数据（航班、酒店库存、天气、门票），LLM 负责组合与解释，不用它编造价格与库存；执行层负责预订类写操作，必须二次确认、幂等、可取消；记忆层保存用户长期偏好（忌口、常旅客信息、到访过的城市）与会话内约束。工程上要处理工具失败的降级（查不到航班就说明并给替代方案）、预算与时间的硬约束校验、以及行程的可解释性（每条推荐附来源）。

**记忆与输入冲突**：当前输入优先于长期记忆，因为记忆是历史推断、输入是当下意图。做法是给每条记忆带时间戳、来源与置信度，冲突时以最新输入为准，并把旧记忆标记为「已被覆盖」而不是直接删除（用户可能只是这次例外）。如果用户说「这次不吃辣」，不要改掉「爱吃辣」的长期偏好，而是加一条会话级约束。冲突无法自行判断时直接问一句，比猜更可靠。

**记忆与知识库冲突**：两者性质不同——记忆是用户个体事实（我住杭州、我对花生过敏），知识库是通用或企业事实（签证政策、酒店政策）。冲突时个体事实优先用于个性化，但涉及规则与安全的内容以知识库为准，并向用户说明依据。实现上分别检索、分别标注来源，在提示词里明确优先级与「冲突时如何表述」，同时记录冲突样本用于后续清理错误记忆。

**怎么验证做得对不对**：分三层——单元与集成测试验证确定性逻辑；离线评测集验证模型输出（准备带标准答案的样本，比较关键字段与人工评分）；线上指标验证真实效果（成功率、人工采纳率、投诉率、延迟与成本）。Agent 类功能还要看轨迹：是否选对工具、参数是否正确、是否多走弯路。上线用灰度与小流量对照，保留回滚开关。

**复杂系统怎么排查**：先定位层次（前端、网关、服务、中间件、数据库、下游依赖），用 trace id 串起全链路，看日志、指标、链路追踪三件套；再缩小范围（按时间、按用户、按接口、按版本比对），确认是单点还是面；最后复现与验证。复杂系统里最重要的不是记住所有模块，而是知道「谁负责什么、出问题找谁、有哪些观测手段」，以及改动前先确认影响面与回滚方案。
