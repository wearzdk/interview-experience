### 《面试题目》

1. 简历上写「负责订单模块优化」，优化前的 QPS 和 RT 是多少？怎么量的？
2. 瓶颈在哪？是数据库、缓存还是代码逻辑？
3. 为什么选 Redis 而不是本地缓存？
4. 如果让你重做一遍，还有什么改进空间？
5. 消息队列怎么保证顺序消费？同一订单的状态变更和支付回调乱序了怎么办？
6. 你们线上 QPS 多少？慢 SQL 怎么定位？
7. Redis 和数据库不一致，你是怎么处理的？
8. ThreadLocal 在你们项目里哪里用了？为什么不用参数传递？线程池场景下为什么危险？
9. 接口 RT 突然从 50ms 涨到 2s，排查思路是什么？
10. 线上 CPU 100% 怎么定位？
11. 设计一个秒杀系统，你会怎么架构？

### 《参考解析》

**项目追问的三层结构**：第一层是标准答案，第二层是为什么这样设计、有什么取舍，第三层是你在项目里怎么用、踩过什么坑。面试官的追问路径基本是从简历上的一个名词出发，逐层向下，停在候选人讲不出细节的位置。准备方式不是再背一遍定义，而是为简历上每个技术点准备一条「背景 → 方案 → 数据 → 坑 → 复盘」的口述线索。

**量化与测量**：说「优化了订单模块」没有信息量，要说清优化前后的 QPS 与 P99 延迟、用什么工具测的（压测工具、APM、慢查询日志）、样本量与测试环境。没有精确数据时如实说明口径，例如「取自生产监控的七天均值」，不要编造。瓶颈的判断要有证据：CPU 使用率、GC 暂停、数据库慢查询占比、缓存命中率、下游调用耗时，逐段排除后指向具体环节。

**选型的取舍**：为什么用 Redis 而不是本地缓存，取决于一致性要求与部署形态——本地缓存快但多实例之间不一致、容量受进程内存限制；Redis 集中但多一次网络往返。回答要给出替代方案与放弃理由，并说明失效策略、击穿与雪崩的防护、热点 key 的处理。

**顺序消费与幂等**：Kafka 只能在分区内保证顺序，同一订单的事件必须用订单号做分区键才能落在同一分区；跨系统的时间乱序不能靠 MQ 解决，要用状态机加版本号，拒绝旧状态覆盖新状态，并用业务唯一键做幂等。支付回调与状态变更乱序时，以版本号或事件时间较大者为准，冲突记录留待对账。

**慢 SQL 与不一致**：慢 SQL 用慢查询日志定位，结合执行计划看是否走索引、扫描行数与回表次数，再决定加联合索引、改写查询或做归档。缓存与数据库的一致性常用 Cache Aside：读先查缓存、未命中查库回填；写先更新数据库再删除缓存，删除失败靠重试或消息补偿，强一致场景用延迟双删或加分布式锁，但要说明延迟双删仍有时间窗。

**ThreadLocal**：用于在同一次请求的线程内传递上下文（用户身份、traceId），避免层层传参；底层是线程持有的 ThreadLocalMap，key 为弱引用、value 为强引用，线程池中线程复用且不清理时会残留上一次请求的数据并造成内存泄漏，因此必须在 `finally` 中 `remove()`。线程池场景危险的原因正是复用与未清理。

**排查场景**：RT 从 50ms 涨到 2s，先看是全量还是部分请求、是否与发布或流量变化对齐，再看依赖耗时（数据库、缓存、下游 RPC）、连接池等待、线程池排队、GC 与 CPU；用链路追踪定位耗时最长的 span。CPU 100% 用 `top -Hp` 找到线程，转成十六进制去 `jstack` 里找栈，常见原因是死循环、频繁 Full GC、正则回溯与锁竞争。秒杀系统的核心是限流、库存预扣与异步下单：前端答题与静态化削峰，网关限流，Redis 原子扣减库存并记录流水，MQ 异步落库，超卖靠 Lua 脚本或分段库存避免，最后做对账与补偿。
