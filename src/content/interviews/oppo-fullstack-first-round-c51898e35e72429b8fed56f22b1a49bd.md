### 《面试题目》

**一、基础问题**

1. 自我介绍，包括学历和工作经历。
2. 在学校学过的比较难的课程是什么？难点在哪里？你是怎么掌握的？

**二、项目经历**

1. 这个项目是实际需求，还是自己做的实验性项目？
2. 项目的输入、输出分别是什么？整体技术链路是怎样的？
3. 项目中前端、后端和算法部分分别是怎么实现的？
4. 多 Agent 之间是如何通信的？
5. Agent 工作流是如何编排的？
6. RAG/检索库是自己实现的吗？
7. 知识库的素材来源是什么？
8. 如何实现上下文记忆？
9. 多用户、多会议场景下，如何保证不同用户之间的数据不互相影响？
10. 如何评估知识库或 RAG 的准确性？
11. 如何根据评估结果迭代和更新知识库？
12. 项目最终上线了吗？
13. 如果作为完整服务上线，考虑过哪些性能问题？
14. 使用的是自部署开源模型，还是第三方大模型 API？为什么这样选择？

**三、AI 全栈相关**

1. 你如何理解 AI 全栈工程师？
2. 如果产品经理只给你一份比较简陋的 PRD，并要求一周完成一个 App，你会如何开展工作？

### 《参考解析》

**这一轮的主线是「顺着一个项目往下挖」，所以项目必须能被拆到每一层。** 面试官从「真实需求还是实验项目」开始，问的不是性质本身，而是**你在这个项目里的角色边界**——实验性项目不丢分，讲不清需求来源、边界和取舍才丢分。诚实说明「这是我自己的探索项目，需求是我自己定义的，目标是把某类问题自动化」，然后立刻接上「我做了哪些技术决策、验证了什么结论」，比含糊地暗示它是商业项目安全得多。紧接着的「输入输出 + 技术链路」是在建一张地图，后面所有追问都挂在这张地图上，所以这一问要答得极其具体：输入是什么形态（用户上传的文档、语音、表单）、经过哪些环节（解析 → 切块 → 索引 → 检索 → 编排 → 生成 → 落库/回显）、输出是什么（结构化结果、报告、流式回复）、每一步涉及哪些组件与外部依赖。**答完立刻补一句「这条链路里最不确定的一环是 X」**——主动暴露风险点，面试官多半会顺着这个点问下去，等于把话题引到你准备过的地方。前后端与算法分工这一问，全栈岗看的是你能不能同时说清三层的接口约定（前端拿什么数据结构、后端暴露哪些接口和鉴权方式、算法侧输入输出的契约和超时降级），而不是让你把三层都做一遍。

**多 Agent 通信：先分清是「真并发协作」还是「串行角色扮演」。** 实际工程里的通信机制就那么几种：① **共享状态/黑板**——所有 Agent 读写同一份结构化状态（LangGraph 的 State、AutoGen 的共享消息），实现简单、可观测性好，代价是并发写要加锁或做版本控制；② **消息传递**——通过消息队列或直接函数调用把上一个 Agent 的输出交给下一个，解耦彻底、可以分布部署，代价是链路追踪和错误传播变复杂；③ **编排器路由**——由一个 Supervisor/Orchestrator 决定下一步交给谁，Agent 之间不直接说话，可控但编排器会成为瓶颈与单点；④ **工具调用即通信**——把另一个 Agent 能力包装成工具，靠 function calling 触发。回答时要给判据：**需要强一致和可回溯就选共享状态 + 明确的状态 schema，需要跨进程跨团队就上消息队列**。这里有个高频追问的陷阱——如果被问「为什么不用共享内存/全局变量直接通信」，答案是进程内外、语言异构、故障隔离三件事；如果被问「Agent 死循环怎么办」，答最大步数与重复动作检测。

**工作流编排：编排的本体是「状态机 + 检查点」，不是 prompt。** 必修的三件事：**节点定义**（每个节点做什么、输入输出 schema）、**流转条件**（串行、并行、条件分支、循环，以及终止条件）、**状态与持久化**（每步的中间结果落盘，进程挂了能从最后一个成功节点续跑）。用现成框架（LangGraph、Temporal、Dify）还是自己写，判据是「链路是否会长期演进 + 是否需要人工介入」——需要人工审批插在中间（发邮件前确认、写操作前确认）就必须要检查点。落到可观测性上：每个节点记输入、输出、耗时、token 消耗和错误，这样出问题才能定位到节点；再加上超时和重试策略（重试要区分幂等与非幂等操作）。如果面试官追问「多 Agent 串行跑太慢怎么办」，可答并行化无依赖节点、把长任务异步化 + 回调通知、以及对简单路径降级成单次大模型调用——**不是所有任务都值得多 Agent**，这句话要主动说。

**RAG/检索库是否自研：这题在探你的技术判断力，不在探你造轮子的数量。** 标准答法是分层说：检索算法和向量索引没必要自研（FAISS/Milvus/pgvector 已经很成熟），自研的应该只有**与业务强绑定的那部分**——切块策略、元数据过滤规则、query 改写、以及融合与重排的策略。如果真自研了某一块，要能说出动机（现成方案在这个场景下哪一点不满足）和代价（维护成本、能力上限）。知识库素材来源这一问，紧接着会被问「素材质量怎么保证」——所以要提前准备素材的治理流程：来源是否可授权、是否有时效、是否去重、是否做了结构化清洗、以及谁负责维护。**容易被忽略的是「知识库的更新责任」**：如果素材来自客户或业务方，就要约定交付格式和更新频率，否则索引会慢慢腐烂。这两问连起来其实是在验证一个判断——你分得清「模型能力问题」和「数据问题」，而实际项目里大多数 RAG 效果差都是后者。

**上下文记忆：短期、长期、以及「哪些不该记」。** 短期记忆是当前会话的对话窗口，管控手段是 token 预算 + 摘要压缩 + 滑动窗口，但**关键约束（用户身份、已确认的事实、否定条件）必须固定保留**，不能随窗口滑出去。长期记忆是跨会话的，通常是向量库 + 结构化画像：写入要有触发条件（什么时候值得记——用户明确表达的偏好、长期有效的事实），召回要有阈值和类型过滤，还要有过期与覆盖机制（新偏好覆盖旧偏好，避免把三年前的信息当现在的事实）。多轮 Agent 场景下还有一层**任务态记忆**：当前任务进行到哪一步、已调用了哪些工具、哪些中间结果还能复用，这部分最适合做成显式状态而不是靠模型从对话里回忆。回答时主动提一句「记忆最大的风险是污染」——召回了错误或过期的记忆比没有记忆更糟，所以宁少勿滥、并且要能在日志里看到「这次回答引用了哪条记忆」。

**多用户、多会议的数据隔离：这是工程红线，答得含糊会直接被判定没做过线上。** 隔离要按层次讲清楚：① **数据层**——所有表和向量集合都必须带 `tenant_id`/`user_id`/`session_id` 字段，检索时**在向量库的过滤条件里带上租户**（不能只在应用层过滤，要在检索语句里过滤，否则 Top-K 会被别人家的数据占满，既泄露又降低准确率）；② **存储层**——要求高就用独立库/独立 collection，成本敏感就用共享库加行级隔离 + 强制查询条件（可用数据库 RLS 或在 ORM 层统一注入，防止有人漏写 `where`）；③ **会话层**——每个会议独立 session，实时链路（WebSocket/SSE 房间）按 session 建 channel，服务端绝不靠客户端传来的 `sessionId` 直接取数据，而是从鉴权 token 里解出租户再校验归属；④ **运行时隔离**——共享的缓存 key、临时文件目录、向量索引都要带租户前缀，避免键冲突和串数据；⑤ **审计**——敏感数据的访问要留日志。这一问的常见追问是「如果两个用户同时开会话会怎样」和「你怎么测试隔离有效」，后者答：写一组跨租户的越权用例（用 A 的 token 请求 B 的 session/文档 ID），纳入回归集每次发版跑。**「靠 prompt 让模型别说别人家的数据」不是隔离方案**，这句话一定要说出口。

**RAG 准确性评估：检索层和生成层要分开评，否则你不知道该改哪。** 检索层指标是 `recall@k`（正确片段有没有进 Top-K）、`precision`、`MRR`/`NDCG`（排得够不够前），依赖一份标注好的评测集：从真实问题里抽样、人工标出每个问题对应的正确文档/片段，规模几十到几百条就能看出趋势。生成层指标是**忠实度**（答案有没有编造、是否只用了检索到的内容）、**答案相关性**（有没有回答问题）、**上下文利用率**，可以人工打分也可以用模型做裁判（LLM-as-a-judge，但要用固定 rubric 并抽查裁判本身的一致性）。工具上 RAGAS、TruLens 这类框架能省不少事。工程上还要看线上指标：用户追问率（说明第一次没答好）、点踩率、检索命中率为零的比例、平均检索耗时。**「准确性」这个词本身要先定义清楚**——是检索不到，还是检索到了但答错，还是答对了但用户不认，这三种问题的修法完全不同，把这一点讲出来就是加分项。

**按评估结果迭代知识库：闭环的关键是「可归因 + 可回归」。** 拿到 badcase 先做归因分类：① 知识库里根本没有 → 补素材（并登记来源）；② 有但没召回 → 修切块/加关键词召回/加 rerank/改 query 改写；③ 召回了但被噪声淹没 → 收紧 Top-K 或加过滤；④ 召回正确但模型答错 → 改 prompt、换模型或加结构化输出约束；⑤ 知识本身过期/矛盾 → 修数据治理。每一类对应不同的动作，**不要一上来就调 prompt**。迭代流程要版本化：文档、切块参数、embedding 模型、prompt 都各自有版本号，改一次就跑一遍回归评测集，防止「修好一个坏掉三个」。增量更新上，文档变更要能触发重切块和索引重建（只更新变化的文档，别全量重建），并且新旧索引切换要能回滚。最后补一句运营侧的动作：把 badcase 沉淀成固定的评测集，随版本增长——**评测集是这个系统唯一能持续变好的依据**。

**上线与性能：先分清在线链路和离线链路。** 如果项目没上线，就诚实说没上线，然后讲清「如果上线我会怎么改」——这一问考的是意识不是事实。在线链路的性能瓶颈通常依次是：大模型调用（延迟与并发上限）、向量检索（QPS 与索引大小）、以及你自己的服务（线程池、连接池、内存）。对应手段：**流式输出**降首字延迟、**并发限流与排队**保护上游（令牌桶 + 队列 + 超时降级）、**缓存**（相同问题的答案缓存、embedding 结果缓存、检索结果缓存，注意按租户分区）、**异步化**长任务（提交后返回任务 ID，进度用 SSE/轮询推）、**连接池与超时**必须显式配置（默认值几乎都不适合 LLM 调用），以及**降级链**（主模型超时切备用模型、检索失败退化为纯生成并明确告知）。离线链路的性能是索引构建与批量处理，用批处理和并行度控制解决。还有一个容易被忘的点：**成本也是性能指标**，单次对话的 token 消耗要能按用户/租户统计。

**自部署开源模型还是第三方 API：这是一道纯粹的成本-效果-合规三角题。** 选第三方 API 的理由：接入快、效果通常在同类里最强、没有 GPU 运维成本、弹性好；代价是数据出境/出域（To-B 和政企客户常常直接否掉）、单价随量线性增长、版本不可控（上游一改行为你的评测就失效）、以及被限流。选自部署的理由：数据不出内网、单位推理成本随量摊薄、模型和行为完全可控、可以针对领域微调；代价是 GPU 资本开支与运维、并发能力受显存限制、模型效果通常落后前沿一到两代、还要自己做推理优化（vLLM/TensorRT-LLM、量化、批处理）。真实项目里最合理的是**混合路由**：常规请求走自部署、复杂或长尾请求走 API 兜底，敏感数据强制本地，并且把「哪类请求走哪条路」做成配置而不是写死在代码里。回答时把客户类型（To-C / To-B / 政企）作为选择的前提说出来，会显得你是在做工程决策而不是背优缺点。

**「你如何理解 AI 全栈工程师」：别把它答成「会前端的算法工程师」。** 这个岗位的核心不是把三种活都干一遍，而是**能独立把一个 AI 能力端到端跑通并且交付出去**：能把模糊需求翻译成可验证的产品形态、能选型和串起模型/检索/编排这些 AI 组件、能写前后端把它变成一个用户真的会用的界面、还要能评估效果并持续迭代。和传统全栈的区别在于多了一层「不确定性」——传统后端的接口是确定的，AI 链路的输出是概率性的，所以 AI 全栈必须额外具备评估能力（怎么定义好坏、怎么量化、怎么防退化）和成本意识（token、延迟、并发）。表达上可以给一个具体的判断标准：「一个功能从想法到上线，中间不需要别人替你翻译技术方案，并且效果好坏我能拿数据说清楚，就算是全栈。」再补一句边界：全栈不等于什么都是自己写，而是知道哪些该用现成方案、哪些必须自己控住。

**一周做一个 App（PRD 还很简陋）：考点是拆解与取舍，不是承诺。** 一个能在面试里站住的答法分四步：① **当天对齐需求**——简陋的 PRD 不能直接开工，先和产品确认三件事：目标用户是谁、这一周要验证的核心假设是什么、什么功能是必须有、什么是可以砍的。找 3~5 个目标用户聊 20 分钟，比对着文档猜要快得多；② **定义最小可交付**——把 PRD 拆成「一周内能做出并给真人试用」的版本，AI 能力部分先做一条主链路的 happy path（选一个模型、一套 prompt/工具、一个检索库），其余全部用最笨的方案兜（表单代替后台、手动代替自动化）；③ **技术选型优先复用**——能托管就不自建（BaaS、Serverless、现成的模型 API、现成的 UI 组件库），因为一周的时间预算里最贵的是运维和部署，不是写代码；④ **倒排节奏并留缓冲**——第 1 天需求与原型、第 2~4 天主链路、第 5 天联调与埋点、第 6 天给真用户试用、第 7 天收反馈定下一步，明确留出至少半天缓冲。最后一定要说**风险和交付口径**：一周能交付的是「可试用版本」而不是「生产可用服务」，鉴权、并发、监控、合规这些要么简化要么明确列为不包含——**先把口径讲清楚，比硬承诺一周上线更能体现工程判断**。

**基础题里的「最难的课程」：这是在测学习方法和自我认知。** 面试官不在乎你选哪门课，在乎三点：你判断「难」的标准是什么、你用了什么方法啃下来、以及你现在回头看会怎么做得更好。答法建议选一门**有客观难度**的课（编译原理、操作系统、算法设计、分布式系统），说清难在哪（抽象层次高、需要同时理解多个概念、缺少直观反馈），再讲你具体怎么做的——拆解成可验证的小问题、找一手材料（教材/规范/源码）、动手实现一个最小版本（比如写一个正则引擎或一个简化调度器）、以及用输出倒逼输入（给别人讲一遍、写成笔记）。**要落到「我现在还能讲清其中的 X」这种可验证的结论上**，而不是「我花了很多时间」。自我介绍部分对全栈岗的关键是：学历和工作经历要服务于一个明确的定位（我做什么方向、擅长什么、为什么是这个岗位），别按时间线念简历。
