### 《参考解析》

**插件开发机制与 AI 写出的代码怎么验证**

陌生宿主插件的开发机制，可靠路径是四条一起走：先读官方文档里的生命周期与扩展点清单，再找一个官方示例跑起来打断点，顺着调用栈看宿主什么时候回调你的代码，最后用最小 demo 把每个钩子单独验一遍。真正卡人的不是 API 名字，而是宿主的约束：哪些线程上执行、超时限制、状态存哪里、升级后兼容性。被追问「AI 写的 TypeScript 你没学过，怎么验证」时，要分层回答：类型检查和 lint 只能拦住第一层错误，重点在行为层——按接口契约写最小调用用例，在真实宿主里跑通主路径，再补异常分支（字段缺失、超时、并发触发），最后人工读一遍关键代码确认它没有调用不存在的 API。AI 写插件代码最常见的坑就是幻觉 API 和错误的作用域假设，编译能过但运行时静默失败，所以「跑得通 + 边界对」比「看得懂」更值得强调。

**翻译链路：为什么用 ES 召回而不是把历史译文全塞进提示词**

这一题最值得展开。第一是成本与窗口：历史译文动辄上万条，全量塞进去会直接顶到上下文上限，单次调用成本也随之失控。第二是注意力稀释：提示词里无关句对越多，模型越容易抄错相邻的句子，翻译一致性反而下降。第三是术语一致性：专有名词必须靠术语库做硬匹配，这是机翻质量的下限，靠模型自由发挥不稳。所以工程上是「检索做上下文压缩、术语库做硬约束、模型做生成」三层分工：先用待译句在 ES 里做相似句对召回，命中阈值以上的历史译文作为少样本示例给模型，术语命中则强制替换。ES 在这里的价值是近邻检索快、能拿相似度分数做阈值、可以做增量索引；代价是要维护双语语料索引与质量分层（人工确认过的译文才进示例池）。追问常落在「检索不到怎么办」，答案要给出回退：无命中就退化到术语库 + 通用提示词，并在结果里标注低置信度供校对页面优先看。

**知识库增量更新：从文件修改时间改成 Git PR 记录**

按文件修改时间判断，问题出在 mtime 根本不代表内容变更：克隆、checkout、CI 拉取、批量构建都会刷新时间戳，内容没变也会重跑；文件被删除、重命名感知不到；也无法回答「这次变更是谁提的、为什么改」。改成基于 Git PR 记录后，变更集是权威来源：只处理 diff 涉及的文档，删除和重命名能被识别，每个切片可以绑定提交哈希，出问题能回溯到具体版本，还能顺带拿到提交人作为增量更新的通知对象。代价要一起说：首次全量仍要走一次冷启动扫描，非 Git 来源的文档（网盘、接口同步）需要另开一条变更通道，以及历史提交里可能有未走 PR 的直接提交，需要兜底规则。把「为什么旧方案看起来能用」讲清楚，比只讲新方案更像做过这件事。

**Agent 的工具选择与 Chat Memory**

工具数量一多模型就开始选错，控制手段有层次：最外层是工具本身的质量——名称可读、描述写清「什么时候该用、什么时候不要用」、参数带示例；再往上是候选裁剪，按当前场景只挂相关工具子集，或用规则与轻量分类先缩一圈；还可以在系统提示里给工具选择策略（先查再写、优先用专用工具）。记忆这块，面试官想区分的是「你是有意识分层还是把所有历史都塞进去」。判定一条内容该不该长期存储，看三点：是否跨会话仍然成立、是否是稳定的偏好而非一次性需求、用户是否显式要求记住；短期会话记忆只服务当前窗口，用滑动窗口加摘要控制长度，长期记忆则要能写入、去重、并在需要时检索回来。存储选型要讲取舍而不是背参数：MongoDB 的文档模型适合变长对话、聚合查询方便、持久化可靠，但单文档会随对话增长，要考虑分集合或按会话分片；Redis 读写在内存里、适合最近窗口和 TTL 过期，但长对话会持续占内存、成本高且复杂查询弱。常见落地是组合：Redis 存最近若干轮会话，MongoDB 存全量记录与长期记忆。

**岗位理解与职业动机**

「为什么从深度学习科研转到工程岗」不能用「想赚钱」或「科研没意思」收尾。可用的逻辑是：科研训练给你的读论文、做实验、归因能力是可迁移的，而工程岗要求把能力交付成稳定系统，两者的差别在于约束——延迟、成本、可维护性、上线后的排障。AI 全栈的吸引力在于链路完整：前端插件、后端服务、检索与模型调用都在自己手里，能闭环验证效果。被问「为什么不选 Agent 开发」时不要贬低那个方向，讲匹配即可：Agent 开发更偏能力探索与效果调优，后端加 AI 应用更偏工程约束下的稳定性与成本控制，你更擅长后者，并举一个项目里为稳定性做出取舍的实例。最后，「AI 全栈这个岗位你怎么理解」要答具体职责边界，而不是形容词堆砌。
