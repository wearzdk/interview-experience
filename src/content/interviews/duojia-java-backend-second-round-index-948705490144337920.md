### 《面试题目》

1. 说说索引在什么情况下会失效。
2. `WHERE user_id > 100 AND status = 1`，联合索引 `(user_id, status)` 能用上几列？
3. `status != 1` 走不走索引？为什么？
4. `status = 1` 单独查询时为什么可能全表扫描？
5. `IS NULL` 与 `IS NOT NULL` 走不走索引？
6. 索引「失效」可以分成哪两类？判断依据是什么？
7. 具体是不是失效，你会怎么验证？

### 《参考解析》

**问题二的答案是一列。** 联合索引 `(user_id, status)` 中 `user_id` 是范围条件，范围之后的 `status` 在索引里已经无序，无法再用于定位，只能被索引下推在存储引擎层做过滤（`Extra` 显示 `Using index condition`）。若把范围拆成 `IN` 列表，且业务上取值有限，`status` 可以重新参与定位与排序。

**问题三是这场面试的分水岭。** 作者答「不走，因为是范围查询」，面试官纠正：「!= 不是范围，是排除。」本地实验更有说服力：给 `status` 造两万行、只排除一行的数据，`EXPLAIN` 显示查询走了索引。原因是当排除的行占比极小时，走索引回表的代价低于全表扫描，优化器自然选择索引。所以「`!=` 导致索引失效」是一个过度简化的结论，它的真实前提是区分度太低、优化器认为全表扫描更便宜。

**把失效分成两类，回答立刻有层次。** 第一类是硬性失效，解析或类型层面就断了：索引列上套函数（`WHERE DATE(created_at) = ?`，改写成范围查询）、隐式类型转换（`varchar` 列传数字，列被转成数字比较；反过来 int 列传字符串没事）、前导 `%` 的模糊查询（只能上全文索引或改数据结构）、联合索引缺少最左列（MySQL 8.0.13 之后有 skip scan，但使用条件受限，日常不要指望）。第二类是成本性失效，索引明明可用，优化器选择不用：回表代价太大（`SELECT *` 命中大量行）、区分度太低（性别、状态这种）、统计信息过期导致估算错误，`type` 从 `ref` 掉到 `ALL`。这两类要分开讲，因为解决方向不同——前者改写法或改索引，后者调统计信息、改索引设计或接受现实。

**`IS NULL` 与 `IS NOT NULL` 要分开看。** `IS NULL` 在 InnoDB 里可以走索引（索引中存储 NULL 值）；`IS NOT NULL` 是否走索引取决于 NULL 的占比与回表代价，NULL 很少时走索引划算，NULL 很多时优化器可能放弃。

**验证方式固定三步。** `EXPLAIN` 看 `type`、`key`、`rows`、`filtered`；`SHOW WARNINGS` 看优化器改写后的 SQL；必要时 `FORCE INDEX` 对比强制走索引与不走的实际耗时。如果强制走索引反而更慢，说明优化器的判断是对的——这本身就是结论。

**重答时的组织顺序。** 先讲规则层面的硬性失效（最左前缀、函数、隐式转换、前导模糊），再讲优化器层面的成本性失效（区分度低、回表代价高、范围导致后续列退化、OR 无法合并），最后说明验证手段。作者复盘说，那次二面最后过了，但这个问题让他把之前背的「索引失效十条」全部推翻重写了一遍——结论性的东西好记，一旦被追问下一层就会露馅。
