### 《面试题目》

3. 这种一致性怎么权衡，举一些具体业务例子。
4. 实习过程中你们的分工是怎么分的？
5. 讲一下 KV Cache 的原理。
6. 你怎么看待下一步 Agent 的发展？
7. 你对我们这个岗位的理解有哪些？

### 《参考解析》

**Agent 项目的效果对比**：业务效果要能给出前后对照：任务完成率、平均步数、人工介入率、单任务成本与延迟，最好说明测试集怎么构造、评测是否人工复核。记忆部分讲清存什么、何时写入、如何召回与过期；沙箱部分讲清隔离级别、哪些操作被限制、越权时如何拒绝并回传原因。

**三级缓存的一致性**：常见组合是本地缓存（进程内，最快但多实例间不一致）、Redis（集中式，跨实例一致但有网络开销）、数据库（权威源）。保证一致性的手段包括：更新时先写数据库再删缓存（Cache Aside），删除失败则重试或投递消息补偿；用消息队列或 binlog 订阅做缓存失效广播，让各实例的本地缓存被动过期；给缓存设置较短的 TTL 作为兜底；对强一致要求的场景用分布式锁或直接读主库。要明确系统接受的是最终一致还是强一致。

**权衡与业务例子**：商品详情、用户资料这类读多写少、短暂不一致可接受的场景，用短 TTL 加删除广播即可；库存、余额这类不能超卖的场景，缓存只做读加速，扣减必须以数据库或 Redis 原子操作为准，必要时加锁或使用 Lua 脚本；配置类数据可以接受秒级延迟，用版本号轮询更简单。

**KV Cache 原理**：自回归生成时，每一层的注意力需要历史 token 的 Key 与 Value。若每生成一个 token 都重新计算全部历史，计算量随序列长度平方增长。KV Cache 把已计算的 K、V 按层缓存起来，生成新 token 时只计算当前 token 的 K、V 并追加，注意力只对缓存做查询，把每步复杂度从随长度增长降为与长度线性相关。代价是显存占用随序列长度与层数线性增长，因此有分页管理（PagedAttention）、量化与淘汰策略。前缀相同可复用缓存，这也是提示词把稳定内容放前缀的原因。

**Agent 的发展判断**：可以从能力与工程两条线讲。能力上长程任务、工具使用与多模态在提升；工程上瓶颈在可靠性、成本与可观测性——如何评估成功率、如何控制上下文与调用成本、如何让失败可恢复。产品形态上会更像「带审批的自动化流程」，而不是完全放手的自治体。

**对 PE 岗的理解**：平台工程是把重复的工程问题做成内部产品：构建与发布、环境与配置、可观测性、权限与审计。核心指标是研发效率与线上稳定性，工作方式更接近产品经理加基础设施工程师，需要理解业务方的真实痛点。

**按插入顺序迭代的哈希表**：在哈希表基础上维护一条双向链表，节点同时挂在桶与链表上；插入新 key 时追加到链表尾部，更新已有 key 不改变位置；迭代时沿链表顺序输出。删除时同时从桶与链表摘除。这样查找仍是平均 O(1)，迭代顺序为插入顺序，代价是每个节点多两个指针。若要支持并发，按桶分段加锁，链表操作需要独立锁或改用并发安全结构。Java 的 LinkedHashMap 就是这一思路。

**接雨水**：双指针法最简洁。左右指针从两端向中间移动，维护左侧最大值 leftMax 与右侧最大值 rightMax；每次移动较矮的一侧，该位置能接的水为对应最大值减当前高度，累加后更新最大值。时间 O(n)，空间 O(1)。另一种是单调栈，按行计算积水，适合解释「凹槽」的形成；还有前后缀最大值数组的解法，时间 O(n)、空间 O(n)，便于理解但不最优。
