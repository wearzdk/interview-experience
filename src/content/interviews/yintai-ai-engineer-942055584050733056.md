### 《面试题目》

### 《参考解析》

**SDD 的价值**：Spec-Driven Development 不是「多写一份文档」，而是把需求变成可执行、可评审、可验证的契约。Agent 能从对话里提取任务，但对话是易变的、上下文是私有的，Spec 提供的是稳定的单一事实源：范围、输入输出、约束、验收标准、失败处理都写清楚，生成代码和测试才有共同依据。它还能让变更可审计——改了什么、为什么改、影响哪些接口，都能在版本里追溯。团队规范落地的关键不是模板多漂亮，而是 Spec 和代码、测试、CI 真正联动，否则就是另一份没人看的文档。

**AI-kit 与索引**：讲项目时先说清边界：AI-kit 是给业务方用的工具层，还是给模型用的工具协议层；人调还是 AI 调，取决于权限和风险，低风险只读工具可以放开自动调用，写操作和外部副作用要人确认。和直接用 Claude 的区别要落在「领域知识、工具编排、权限控制、结果校验、可观测性」上，而不是「我们包了一层」。知识库索引的构建链路是解析文档、清洗、切块、向量化、写向量库、建元数据索引，再配合关键词索引和权限过滤；增量更新要靠文档版本和内容哈希，避免全量重建。

**多 Agent 与审核**：多 Agent 适合任务能拆成独立子问题、工具集或权限不同、需要并行或对抗验证的场景；简单问答硬拆多 Agent 只会增加延迟和协调成本。内容审核可以分层：规则和黑名单先挡明显违规，小模型做高召回初筛，大模型做语义复核，人工处理边界和申诉。音视频要抽帧、转写、多模态理解，文字图片走文本和图像审核。大模型审核的优势是语义理解，缺点是成本、延迟和稳定性，所以生产上通常是「模型给分 + 阈值 + 人工兜底」。

**消息队列可靠性**：生产者侧要开确认机制，失败重试并保证业务幂等；Broker 侧靠持久化、多副本、同步刷盘和 leader 选举保证不丢；消费者侧关闭自动 ack，处理成功后再提交位点，失败进入重试队列或死信队列。端到端还要有唯一消息 ID 和去重表，避免重复消费。人工 review 代码在 AI 时代不会消失，但会从逐行看语法转向看边界、权限、数据流和测试覆盖。
