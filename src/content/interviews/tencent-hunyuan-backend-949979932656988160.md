### 《面试题目》

2. 补令牌、判断、扣减这几步的并发怎么保证？两个请求同时读到「还有一个令牌」都放行怎么办？
3. synchronized 和 volatile 有什么区别？
4. 为什么 `count++` 只加 volatile 不够？
5. Redis + Lua 怎样应对百万级的队列式并发限流？
6. 请求在哪里排队、什么时候扣额度、排太久怎么办？
7. 「百万级」是每秒进来这么多，还是已经积压这么多？
8. 什么是 RAG？

### 《参考解析》

**令牌桶的实现要点是「懒补充 + 原子扣减」**：桶里存当前令牌数 `tokens` 与上次补充时间 `lastRefill`，每次请求先按 `(now - lastRefill) * rate` 算出应补的量，取 `min(capacity, tokens + 补充量)`，再判断是否够扣。不要在后台起线程定时加令牌——定时器精度与唤醒开销都不划算，而且空闲时白跑；懒补充把「时间」本身当成令牌来源，天然平滑。突发能力由 `capacity` 决定，长期平均速率由 `rate` 决定，这两个参数就是限流的全部语义。

**并发下的正确性**：读 `tokens`、算补充、比较、扣减必须是一个原子操作，否则两个线程都读到 1、都判断通过、都扣减，实际放行了两个。单机做法是用一把锁把整段包住（临界区很短，锁竞争可接受），或者用 CAS 循环重试（读快照、算新值、`compareAndSet`，失败重来）。分布式做法是把这段逻辑写成 Lua 脚本在 Redis 里执行——Redis 单线程执行脚本，脚本内的读改写天然原子，把 `tokens` 与 `lastRefill` 存在同一个 key 的 hash 里，脚本返回是否放行以及建议的重试等待时间。

**synchronized 与 volatile**：volatile 提供可见性与禁止重排，读写直接落到主存，但复合操作不原子；synchronized 提供互斥（原子性）加可见性（解锁前的写对随后加锁的线程可见），还能保证临界区的有序。`count++` 是「读—加—写」三步，中间可能被其他线程插入，所以必须用 synchronized、`AtomicInteger` 的 `incrementAndGet`（底层 CAS），或者 `LongAdder`（分段累加，高并发写更优）。反过来说，如果一个变量只被一个线程写、多个线程读，用 volatile 就够了，用锁是浪费。

**Redis + Lua 的百万级限流**：先澄清量级口径——是 QPS 百万，还是要支撑百万个并发排队；前者靠分片与本地预扣，后者要考虑内存与超时。工程做法通常是两级：网关本地用令牌桶做粗粒度拦截（每实例按比例分配配额，避免每个请求都打 Redis），Redis 侧用 Lua 做全局精确配额与跨实例一致性，本地配额定期从 Redis 领取。队列语义要明确：是「排队等令牌」还是「拿不到就快速失败」。排队需要有序结构（List 或 ZSet 按时间戳），并且必须设最长等待时间与队列上限，否则延迟会无限增长、内存被撑爆；超时直接返回 429 并给 `Retry-After`，比让请求一直挂着更好。集群模式下 Lua 脚本操作的 key 必须落在同一个 slot，用 hash tag 固定；脚本要短，避免长时间阻塞 Redis 单线程。

**RAG 的完整链路**：先把文档按语义边界切块（固定长度会切断句子，按标题层级或段落切再加重叠更稳），用 embedding 模型把块编码成向量存进向量库，同时保留原文与元数据（来源、时间、权限）。查询时把问题编码，做向量检索（可混合关键词检索做召回融合），再用 rerank 模型精排取 Top-K，把选中的块拼进提示词交给模型生成答案，并要求模型在无依据时明确说不知道。评估分检索与生成两段：检索看召回率与命中位置，生成看答案正确性、引用是否对得上、有没有编造。常见问题是切块破坏上下文、只做向量检索漏掉精确匹配的词、以及把不相关块塞进上下文导致模型被误导。
