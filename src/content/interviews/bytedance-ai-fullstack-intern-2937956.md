### 《面试题目》

1. 项目整体架构是什么？为什么选择这些技术和框架？Spring AI 和 Pi 的职责有什么区别？
2. 上下文和项目记忆做了哪些建设？多 Agent 之间如何协作？
3. MCP 是怎么接入的？MCP 和 A2A 有什么区别？
4. MCP 暴露的工具太多会带来什么问题？能否在工具注册阶段处理？
5. 有了 MCP 和 A2A，为什么还需要 Skill？Skill 的实现机制是什么？
6. 如果有几百个 Skill，怎么减少上下文占用？领域划分不清、选错领域或者任务跨领域时怎么办？
7. Agent 任务轮次多、Token 消耗大，面对几百上千用户时如何降低成本？
8. 算法题：求字符串中最长回文子串的长度，要求 O(N²) 时间复杂度。

### 《参考解析》

**MCP、A2A、Skill 分属三层，不要混着答**：MCP 解决的是「模型怎么调用外部能力」——它是一套客户端与服务端之间的协议，把工具、资源、提示模板以标准方式暴露出来，重点是能力的接入与发现；A2A 解决的是「Agent 之间怎么协作」——任务委派、能力卡片、状态与产物的传递，重点是跨进程、跨组织的任务编排；Skill 是「怎么做一件事」的知识封装，通常包含指令、脚本与参考资料，按需加载进上下文。一句话概括：MCP 给手脚，A2A 给同事，Skill 给作业手册。

**工具过多的问题要在注册阶段解决**：每个工具的名称、描述、参数 schema 都占系统提示的 token，几百个工具会挤占上下文、拖慢首字、并显著降低选择准确率（相近描述的工具互相干扰）。注册阶段可以做的事：按领域分组并以「组」为单位暴露，提供 `search_tools` 之类的元工具做二次检索，工具描述去重与规范化，把低频工具下沉为「先查文档再调用」的两段式。运行时再配合权限过滤——只把当前任务允许的工具放进上下文。

**几百个 Skill 的上下文策略是分层路由加按需加载**：第一层放每个 Skill 的一行摘要（名称、适用场景、触发词），由路由器选出候选；第二层加载候选 Skill 的正文与脚本；第三层在执行中按需读取引用文件。领域划分不清时用「多标签 + 置信度阈值」，低于阈值就走澄清或让模型先做意图分类；任务跨领域时不要强行归到一个领域，而是允许多个 Skill 组合，并在执行计划里显式列出依赖顺序。衡量指标是路由准确率与平均加载 token 数，两者要一起看。

**Token 成本要先归因再优化**：把一次任务的消耗拆成系统提示、Skill 正文、历史对话、工具返回、模型输出五部分，找出占比最大的那块。常见手段：稳定前缀（系统提示与工具表）保持字节级不变以命中 KV Cache，历史按轮次摘要并保留结构化结论，工具返回只取必要字段并对大结果做截断加引用，简单子任务路由到小模型，批量任务做请求合并与结果缓存。注意缓存命中率是成本的主变量——前缀里插入时间戳、动态权限列表这类「每次都不一样」的内容，会让整段缓存失效。

**最长回文子串的中心扩展**：枚举 2n−1 个中心（n 个单字符中心 + n−1 个间隙中心），每个中心向两侧扩展直到不相等，记录最大半径；奇数长度答案为 `2r+1`，偶数长度为 `2r`。时间复杂度 O(N²)、空间 O(1)。边界要处理空串与单字符；若面试官追加「能不能更快」，再提 Manacher 的 O(N)——预处理插入分隔符统一奇偶，维护当前最右回文边界与对称点，可避免重复扩展。
