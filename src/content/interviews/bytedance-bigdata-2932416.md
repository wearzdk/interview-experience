### 《面试题目》

1. 介绍一下 Agent，它最好的地方和最坏的地方分别是什么？
2. 哪些表应该放到知识库上？
3. 线上代码改了怎么办？
4. 为什么要用 MCP 去读代码？
5. 团队的知识库会有什么问题？
6. Agent 的底层原理是什么？
7. MCP 和 Skill 的区别是什么？

### 《参考解析》

**这场面试的信息量在「团队在做 AI 数仓」**，所以问题虽然都是 Agent，落点全在「数据工程怎么被 Agent 改造」。答题时把自己放进这个场景，比背 Agent 的通用定义有效得多。

**「介绍 Agent + 优缺点」要答成一个闭环**：模型负责决策，工具负责与环境交互，规划与记忆负责多步任务的连续性。优点是能处理开放式的多步任务、把非结构化的入口（自然语言、截图、日志）接到确定性的执行上；缺点也很具体——错误会沿调用链放大、工具调用的边界不清时容易越权或死循环、上下文与成本随轮次膨胀、以及可评估性差（同一任务两次执行结果可能不同）。把缺点落到工程手段上（幂等、限步、人工确认点、轨迹回放），比泛泛说「幻觉」更像做过。

**「哪些表进知识库」考的是数据治理意识**。不是把所有表都塞进去，而是按「被问到的频率 × 口径稳定性 × 解释成本」筛：指标表与维表、口径有明确定义的宽表优先；原始明细表不进，改让 Agent 生成 SQL 去查；涉及权限隔离的表要按角色切分知识库。回答时补一句「知识库要带元数据（口径、负责人、更新频率）」，否则 Agent 拿到表名也不知道该怎么用。

**「线上代码改了怎么办」「知识库会有什么问题」是同一类问题：知识会过期**。改代码之后，依赖代码语义的知识文档、提示词里的示例 SQL、以及字段口径说明都会失效。工程上的解法是让知识可追溯——文档绑定到代码路径/Schema 版本，CI 里跑一致性检查，Schema 变更触发对应条目的失效标记与重建；知识库本身的问题则包括口径冲突（同一指标两套定义）、更新滞后、检索粒度不当（整篇文档召回导致上下文被灌满）、以及权限泄漏。

**「为什么用 MCP 读代码」要讲协议层的价值**：MCP 把「工具」标准化成可发现、可复用的服务，模型不需要为每个数据源写死集成，权限与审计也能统一挂在服务端，换模型不换工具。对比直接给模型一堆文件路径，MCP 提供的是有 schema 的能力描述，调用更可控。

**MCP 与 Skill 的区别**一句话能说清：MCP 是「连接与能力的协议」，解决的是 Agent 怎么安全、标准化地调外部工具和数据；Skill 是「做事的方法包」，把某类任务的知识、步骤和脚本封装起来供模型按需加载。前者偏基础设施，后者偏经验沉淀，实际系统里通常是 Skill 决定「怎么干」、MCP 提供「能调用什么」。

**最后一条实用建议**：这场 SQL 题不难但面评仍然不好，说明字节这类岗位对「讲清楚」的要求高于「做出来」。准备 Agent 类问题最好的方式是自己搭一个能跑的小链路（读表 → 生成 SQL → 执行 → 校验），把每一步的失败模式和兜底讲出来，比背概念强。
