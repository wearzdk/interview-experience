### 《参考解析》

**Spark 数据倾斜**：现象是某个 key 的数据量远大于其他 key，导致个别 task 处理时间极长、整体卡在最后几个 task 上，伴随单节点内存暴涨与 OOM、shuffle 读写量异常。定位方法是看 Spark UI 里各 task 的耗时与 shuffle 读写分布，或者按 key 统计 top N（`group by key order by count desc`）。解决分三层：预处理层做热点 key 过滤（业务上无效的脏 key 直接过滤）、对热点 key 加随机前缀打散（两阶段聚合：加盐聚合后再去盐聚合）；任务层把倾斜的 key 单独抽出来处理，结果再 union 回主数据；参数层调节分区数与并行度（`spark.sql.shuffle.partitions`、AQE 的自适应倾斜处理）、开启 map 端聚合（`reduceByKey` 优于 `groupByKey`）、小表广播避免 shuffle join。答题时最好带一个真实案例的量级变化（原本 40 分钟 → 优化后 5 分钟）。

**指标口径变更**：这是数据岗最真实的场景题，核心是「上游改一个口径，下游可能全错」。规范做法分三步：事前确认——口径必须先书面确认（谁提出、为什么改、影响哪些表与报表），并评估上下游影响面（血缘关系、有多少下游依赖、历史数据要不要重刷）；按影响面分流——小范围且无血缘依赖的，后续迭代中修改即可；大范围且有血缘依赖的，要制定变更方案（新老口径并行一段时间做对比验证、回刷策略、通知所有下游），并准备回滚预案；变更后要做一致性校验（新旧指标差异是否在预期内）。回答里带出「血缘」和「回滚预案」两个词，基本就能拿满分。

**AIGC 与职业期望**：答 AIGC 要分层：底层是大模型（对话 + 工具调用，能自主判断是否调工具）；中层是应用形态（智能体、RAG、Copilot）；落地层是「把 AI 嵌进完整研发或数据流程」。学习渠道的偏好可以如实讲——企业内部落地文档比外网博客更贴近生产，博客偏理论、和真实环境差距大。职业期望方面，这位作者答的是「在大数据基础上持续向 AI 发展，希望负责从数据产生到报表产出的完整链路，而不是只做中间片段」——这种表述对面试官很友好，因为它明确表达了成长诉求和岗位理解。

**反问**：数据岗可以问的问题包括团队规模与业务方向、数据链路的完整度（有没有数据治理、血缘平台、调度系统）、指标口径的管理方式、以及团队内部的 AI 落地现状与工具链。后者既能了解技术氛围，也能顺势表达自己的兴趣。
