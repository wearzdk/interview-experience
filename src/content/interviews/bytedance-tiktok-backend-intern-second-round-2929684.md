### 《面试题目》

6. 如果一个服务调用另一个服务超时，重试机制应该怎么设计？为什么不能无限重试？
7. 什么情况下使用同步调用，什么情况下使用 MQ 异步处理？

### 《参考解析》

**链路容错要按“每一跳都可能挂”来答**：入口层做限流和黑白名单，网关层做鉴权、路由与超时，服务间调用设置连接超时、读超时和重试预算，Redis 与 MySQL 都要有降级路径。核心是区分“强依赖”和“弱依赖”：下单、扣库存这类强一致链路失败要快速失败并给出明确错误；评论数、推荐位这类弱依赖失败可以返回兜底数据。再做舱壁隔离，避免一个下游把线程池打满拖垮整个服务。

**超时与重试的关键是预算和幂等**：每次调用设置小于上游剩余时间的超时，重试只针对幂等操作或可去重的写操作，采用指数退避加抖动，并限制总重试次数和总耗时；不能无限重试，否则会放大流量并在下游故障时形成雪崩。跨服务写操作要带业务唯一键，消费端用唯一索引或状态机做幂等。MQ 不丢消息要三段都做：生产端确认与本地消息表/事务消息，Broker 持久化与副本，消费端手动 ACK 且业务成功后再确认；ACK 前宕机会导致重复消费，所以幂等是必需项而不是可选项。

**锁与数据库部分要讲出边界**：Redis 锁用 `SET key value NX PX` 加唯一 value，释放和续期用 Lua 保证原子；TTL 要大于业务最长执行时间，并用看门狗续期，同时接受“极端情况下锁失效”的事实，关键资源再加数据库乐观锁或唯一约束兜底。MVCC 由隐藏事务 ID、undo log 和 ReadView 实现，RR 下快照读复用第一次读的 ReadView；当前读的幻读靠 next-key lock（记录锁 + 间隙锁）解决。慢查询按“是否走索引、索引是否失效、扫描行数、回表次数、锁等待”逐层看执行计划和慢日志。

**系统设计与手撕**：直播间评论读多写少，按直播间分片，写侧先落 MQ 削峰再异步批量入库，读侧用 Redis List/ZSet 保存最近 N 条并做本地缓存，热点直播间单独扩容；同时要有敏感词过滤、限流和降级。LRU 用哈希表加双向链表，`get` 命中后移到表头，`put` 超容量淘汰表尾，Java 里可以用 `LinkedHashMap` 的 `accessOrder` 快速实现，但面试最好手写双链表展示对指针操作的理解。
