### 《参考解析》

**海量登录与排队削峰**：新服开服是典型的瞬时脉冲流量，直接放量打 DB 和登录服必崩。常规做法是网关层先限流（令牌桶按 QPS 放行），登录请求进消息队列，后端按可控速率消费，队列入队时给每个请求分配一个自增序号作为排队号。排队位次用 Redis 的有序集合或计数器维护，客户端拿排队号轮询或走长连接接收位次推送，同时展示预估等待时间。消息不能丢：生产端开 confirm、消费端手动 ack 且做幂等（用 userId + 请求唯一 id 做去重表或 Redis SETNX），失败进重试队列、多次失败进死信队列人工兜底。体验上的平衡点是"分批放行 + 可视化等待 + 可取消"：一批放 N 个人、给出剩余时间、允许玩家取消排队，避免所有人干等；同时防重连风暴（客户端指数退避、同设备去重），并准备降级方案，比如排队期间只开放角色创建预览、不写库。

**同账号多端登录**：核心是服务端维护一份"账号 → 当前会话"的映射，登录时用 Redis 做原子占位（比如 `SET account:session <token> NX EX`），已有会话时要么踢掉旧会话（顶号），要么拒绝新登录并提示。关键是旧连接要被主动断开（网关层推一条 kick 消息）并让旧客户端停止发包，否则两个客户端会互相覆盖存档。再多一层是设备指纹与登录态校验，防止 token 被复制到第二台机器上直接用。

**FPS 开火与伤害判定**：客户端开火时优先给"手感反馈"——枪口火焰、音效、后坐力、抛壳、命中准星反馈、弹道曳光，这些都在本地立刻播放，不等服务器；伤害判定必须服务端权威。如果让客户端自己判伤害，改内存或改包就能一枪秒人，反作弊无从谈起。服务端权威 + 客户端预测 + 延迟补偿（lag compensation）是主流：服务端按玩家上报的射击时刻回溯其他玩家当时的位置做命中校验，命中结果再下发。防作弊的层次包括：服务端全量校验（射线、射速、弹药、移动速度）、输入频率与弹道合法性检查、统计异常检测（爆头率、命中率离群）、客户端完整性校验与反调试、以及举报与人工复核。

**高速射击/高速移动的问题**：一是穿模与隧穿——子弹在两帧之间跨过了目标，纯离散检测会漏判，要用连续碰撞检测（CCD）或分段采样；二是延迟与不同步——高延迟玩家看到的敌人位置是旧的，需要回溯补偿，但补偿窗口太大会被利用（打"鬼影"），通常限制在 100~200ms；三是插值与外推导致的位置误差，快移目标会出现"瞬移/回拉"，需要合理的外推上限和服务器纠正；四是命中判定与表现不一致，客户端看到命中但服务端判未命中，要有明确的反馈（比如命中标记延迟出现）避免玩家困惑。

**弹道下坠与射线检测**：射线检测就是从枪口或摄像机沿方向构造一条射线，和场景/角色的碰撞体做相交测试，取最近交点。引擎里通常用 BVH 或空间划分加速，物理引擎提供 raycast 接口。真实弹道有重力下坠和飞行时间，常见两种实现：一是分段射线（每帧沿抛物线推进做一小段射线检测），二是用快速子弹（fast projectile）先做射线命中预测、再让可见弹丸沿抛物线飞到命中点，视觉与判定分离。狙击枪和远距离武器更适合真实弹道，近战武器直接用射线就够了；霰弹枪是多条射线做弹丸散布。

**自动化框架的结构与缺陷**：典型分层是驱动层（设备/浏览器操作）→ 页面对象层（元素定位与页面动作）→ 用例层（业务场景与断言）→ 报告与调度层。缺陷通常在三处：定位器写死、用例之间共享状态（前一个用例失败污染后面）、断言只看"没报错"不看业务结果。健壮性靠显式等待替代 sleep、失败重试 + 截图 + 日志留存、用例间数据隔离、以及把环境准备和清理放进 fixture。交付给别人时最容易出问题的是环境依赖和隐式前置条件，所以要有自检命令（依赖版本、设备连接、账号可用）和一份"失败怎么定位"的排查手册。

**页面变更少改脚本**：把定位器从脚本里抽出来集中管理（页面对象/配置），优先用稳定的语义化属性（testid、data-*）而不是层级选择器；定位策略做多候选兜底（首选 testid，退化到文案、角色、相邻元素），配合图像/OCR 作为最后手段；再进一步是"自愈"——定位失败时自动尝试候选并记录告警，让人只处理真正变了的页面。根本上还是推动研发在页面上留稳定标识，这是测试和开发之间的契约。

**AI 写码与 review**：日常用法是分层的——样板代码、单测、脚本、文档交给 AI 快速产出，核心逻辑自己写或至少自己重写关键部分。review 时重点看它容易错的地方：边界条件（空值、越界、并发）、异常分支是否被吞掉、资源释放、事务边界、权限校验、以及"看起来合理但实际不存在的 API"。避免隐藏错误的办法是让代码必须过编译、过单测、过静态检查，再补针对性的用例；对 AI 声称的"已修复"一律用可复现的验证来确认，而不是读一遍觉得对。

**多 agent 与方案分歧**：一个 agent 做实现时容易陷入自己的假设，多 agent 的价值在于引入独立视角——实现、评审、测试分开，评审方不带实现的上下文，更容易发现"自洽但错误"的逻辑。分歧大时不要投票，回到可验证的事实：各自给出假设、影响面和一个能证伪的实验（写个小 demo、跑个基准、查文档/源码），用结果收敛；实在收敛不了就选改动小、可回滚的那条，先把风险控制在可逆范围内。

**测试用例是否齐全**：判断标准不是"数量够不够"，而是覆盖维度全不全——正常路径、边界值、异常与错误码、并发与幂等、权限与越权、兼容性、以及业务规则里的特殊分支。做法是先用需求/接口契约列出功能点和风险点，让 AI 按清单生成用例，再人工补齐它系统性漏掉的部分（通常是把异常当正常、忽略状态机非法流转）；最后用覆盖率（代码/接口/场景）和线上缺陷回流来校准，漏测的 bug 要补成回归用例。
