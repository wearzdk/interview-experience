### 《参考解析》

**Function Calling 是四步闭环，模型只负责出「调用意图」**：请求里带上工具的 JSON Schema（名称、描述、参数的类型与必填项），模型返回一条 `tool_calls` 消息——工具名加一段 JSON 参数，注意它不执行任何东西；应用侧收到后做校验、鉴权、真正调用，再把结果以 `tool` 角色、对应 `tool_call_id` 的消息回填；模型读到结果后继续推理，直到给出最终回答或再次发起调用。理解这一点之后，绝大多数追问都有了落点：执行在应用侧，所以超时、重试、限流、幂等都由应用负责；模型的输入只有 Schema 与描述，所以工具描述写得含糊，模型就会选错工具或填错参数。

**MCP 是「工具怎么被接入」的协议，与 Function Calling 处在不同层**：MCP 用 JSON-RPC 2.0 交换消息，角色分 host（承载模型的宿主，例如 IDE、客户端）、client（host 内为每个 server 维护的连接）、server（暴露能力的一方）。服务端暴露三类能力——tools（可调用动作）、resources（可读取的数据，按 URI 寻址）、prompts（预置的提示模板）。会话以 `initialize` 开始，双方协商协议版本与 capabilities，之后 `tools/list` 取清单、`tools/call` 执行。传输有 stdio（本地子进程，最常见）与 Streamable HTTP（远程，早期是 SSE）。所以「MCP 与 Function Calling 的边界」可以一句话回答：Function Calling 规定模型如何表达调用意图，MCP 规定宿主如何发现与调用外部能力；两者可组合——host 把 MCP server 的 tools 转成模型可见的 Schema，模型出 `tool_calls`，host 再翻译成 MCP 的 `tools/call`。

**失败、超时与空值的恢复要分类处理**：先把错误分成可重试（网络超时、429、5xx、临时不可用）与不可重试（参数类型错误、权限拒绝、资源不存在、业务规则拒绝），前者按指数退避重试 1–2 次，后者立刻把错误原文回填给模型让它改参数或换工具，而不是原样重试。空值是最容易被忽略的一类——工具查不到数据时如果返回空字符串或 `null`，模型往往认为工具坏了、反复重试；正确做法是返回结构化结果，明确写「查询成功，结果为 0 条」并附上用的查询条件，模型才知道该换条件而不是重试。回填内容要带三样：成功与否、错误码与原文、可执行的下一步提示（例如「该参数应为 ISO 日期」）。重试还要设总预算（次数与总时长），否则一个坏工具能把整轮对话拖死。

**防越权不能只靠提示词**：工具层的约束要落在三处——Schema 层用枚举、范围、正则把自由文本收紧；执行层做服务端校验与权限判定（当前用户能否操作这个资源、这个动作是否允许在只读模式下发起）；流程层把高危动作（删除、支付、提交）设计成两步确认，并保留人工确认点。描述里写「仅用于查询」挡不住模型，服务端的鉴权才是边界。审计同样重要：每次调用至少记录时间、会话与用户、工具名、参数摘要（敏感字段脱敏）、结果状态与错误码、耗时、模型与 token 用量，这些字段决定了事后能不能复盘「它为什么调了这个工具」。

**工具多了以后，问题从「会不会调」变成「调得准不准、上下文够不够」**：几十上百个工具的完整 Schema 很容易吃掉几千 token，还会让模型在相似工具之间摇摆。常见做法是分层——先给一组场景级的粗粒度工具（或先让模型选领域），命中后再加载该领域的具体工具；用检索按用户意图召回 Top-K 工具；把 Schema 精简到「描述一句话、参数尽量少、能用枚举不用自由文本」；把大结果外置（落文件或对象存储，只回摘要加引用与分页游标），需要细节时再取。这与「工具粒度怎么划分」是同一个问题的两面：工具太少则一个工具参数过于复杂、模型填不对；工具太多则选择困难、上下文吃紧。经验判据是「一个工具只做一件事，参数不超过五六个，名称与描述能让人一眼分清」。

**幂等与鉴权是生产环境的硬要求**：超时后重试是必然发生的，所以有副作用的工具要带幂等键（业务主键 + 操作类型，或客户端生成的 request id），服务端按幂等键去重并返回首次结果；没有幂等键时，宁可把工具设计成「先查询再执行」的两步，也不要在超时后盲目重试。鉴权上，MCP 的远程接入用 OAuth 2.1 + PKCE，token 存在宿主或服务端，按用户隔离，绝不写进提示词或模型可见的工具参数；工具调用时由宿主注入凭据，模型只看到「这个工具可用」。密钥管理同理——放密钥管理服务或环境变量，日志里不落明文。

**选型看的是复用边界与调用成本**：MCP 适合「同一个能力要被多个宿主复用」「需要标准化发现与鉴权」「第三方提供能力」的场景，代价是多一层协议与部署；CLI 适合本地一次性操作与脚本编排，简单直接，但输出解析脆弱、权限边界模糊；直接调 API 适合内部服务之间调用关系固定的场景，性能最好、可控性最强。判断标准不是「谁更先进」，而是这个能力要被谁调用、调用频率多高、是否需要跨产品复用。至于「已有微服务注册与 API 为什么还要 MCP」——微服务的注册发现解决的是服务之间的寻址与负载均衡，MCP 解决的是「模型如何理解并安全地调用一个能力」，前者面向服务，后者面向模型，需要的是语义化的描述、受控的参数与面向模型的错误信息，这一层微服务接口本身并不提供。
