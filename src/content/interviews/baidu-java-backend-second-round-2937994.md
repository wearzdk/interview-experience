### 《参考解析》

**热点 key 要分「读热」与「写热」两条路**：读热可以做本地缓存（Caffeine）加短 TTL、把 key 拆成多个副本分散到不同节点（后缀随机）、读请求走从节点或就近节点；写热更麻烦，通常改成异步批量写、按 key 分片聚合，或把计数类需求换成 Redis 的原子命令并限制返回体大小。同 key 并发回源的标准解法是请求合并（singleflight）或互斥锁重建：只让一个请求查库，其余等待结果；对一致性要求低的场景改用逻辑过期，先返回旧值再异步刷新。回答时要说明热 key 是怎么发现的——`hotkeys` 采样、代理层统计、业务埋点。

**B+ 树的高度可以现场算**：InnoDB 页默认 16KB，非叶子节点存「主键 + 6 字节页指针」，BIGINT 主键 8 字节，一条目录项约 14 字节，一页约 1170 项；叶子节点存整行，假设一行 1KB，一页约 16 行。三层即 1170 × 1170 × 16 ≈ 2100 万行，四层则到百亿级。所以「千万级数据 B+ 树三层」是算出来的，不是背的。这也解释了为什么主键要短、为什么大字段要拆表——行越长，叶子页能放的行越少，树越高，I/O 越多。

**「从链表里怎么过滤」问的是索引定位过程**：B+ 树的叶子节点之间用双向链表相连，支持范围扫描；单点查询是从根节点开始按 key 比较逐层下降，到叶子页后在页内的有序记录（页目录 + 二分）中定位，不是遍历链表。范围查询才用叶子链表顺序扫。答清这两条，才能接住「查具体某一个值」的追问。

**JMM 与 GC 要连起来讲**：JMM 规定线程通过工作内存读写主内存，`volatile` 保证可见性与禁止重排序、`synchronized` 保证原子性加可见性，happens-before 是判断可见性的规则。GC 的标记从 GC Roots（栈上引用、静态变量、常量、JNI 引用）出发做可达性分析，不是引用计数（无法处理循环引用）。分代回收：新生代用复制算法（Eden 与两个 Survivor，对象晋升老年代），老年代用标记-清除或标记-整理，G1 把堆切成 Region 做可预测停顿的回收，ZGC 用染色指针与读屏障做并发整理。回答时把「什么对象进老年代」（大对象、长期存活、动态年龄判定）说清，比罗列收集器名字有用。

**SSE 断线重连的关键是「消息可重放」**：SSE 自带 `Last-Event-ID`，客户端重连时会带上最后收到的事件 id，服务端据此从该 id 之后继续推送；因此每个事件要有单调递增的 id，并且服务端把生成中的回答按段落持久化（或写入 Redis Stream），刷新页面后先拉一次快照再续接增量。多实例部署时会话必须粘性路由或把事件流写入共享存储由任意实例续推；服务重启后从持久化的最后一段继续生成，未完成的标记为中断并允许重新生成，而不是假装没发生。

**对话数据结构按「会话—消息」两级设计**：会话表存用户、标题、模型、状态、时间；消息表存会话 id、角色、内容（或对象存储指针）、token 数、序号、创建时间，序号保证顺序与断点续传，索引建在 (session_id, seq)。长内容与工具返回的大对象放对象存储，表里存指针与哈希。多实例一致性靠数据库或 Redis 作为唯一状态源，内存只做缓存。

**合并两个有序链表用哨兵节点加双指针**：比较两个头节点，把较小的接到结果尾部，指针前移，任一链表耗尽后接上另一条剩余部分，时间 O(m+n)、空间 O(1)。递归写法代码更短但栈深度为链表长度，面试里先写迭代版再提递归版更稳。
