### 《面试题目》

1. 你们生产上数据库连接池为什么总被打满？
2. 如果慢日志里没有慢 SQL 呢？
3. 连接池参数应该怎么定？是不是调大就能解决？
4. 怎么判断是连接泄漏、长事务还是流量放大？
5. 排查连接池问题你用过哪些工具？

### 《参考解析》

**先看现象组合，再决定查哪条线。** 连接池打满有三种典型形态：`active` 顶满、`pending` 很高而数据库 CPU 只有三成——说明连接不是被计算占着，而是被业务代码攥在手里（泄漏或长事务）；`active` 高、数据库 CPU 也高——慢 SQL 或锁等待；`pending` 高但 `active` 不高——获取连接超时，问题在网络或池参数。这个组合判断比盯着连接池参数有用得多。

**坑一：异常路径没还连接。** 手写 JDBC 时 `conn.prepareStatement()` 或 `execute()` 抛异常，`close()` 就永远走不到；连接池虽然有泄漏检测，默认阈值通常不短，高峰期几十个请求就能把池子拖死。改法是统一用 try-with-resources 或模板方法（`JdbcTemplate`、`SqlSession`），异步线程里同样要走同一套借还封装。

**坑二：事务里做远程调用。** `@Transactional` 方法里先更新数据库、再调一个平均两秒的 HTTP 接口、然后更新状态——事务一开连接就被占住，远程调用多慢连接就多晚归还。QPS 二十、平均占用两秒，理论上就要四十个连接，加一点波动直接打满。改法是把远程调用挪到事务外，或拆成两段短事务；判断标准很简单：事务里只留数据库操作，任何网络调用都不该出现。

**坑三：入口流量把池子放大。** 上游重试导致线程池堆积，Tomcat 两百个线程都卡在等连接，`pending` 很高但数据库很闲。这看起来像池子小，实际是入口没有限流。此时把连接池调到两百只会把压力往后传——数据库最大连接数有限，连接数应按核数、SQL 平均耗时与并发量估算，真正的解法是压测、限流与熔断。

**排查手段。** 测试环境把 `leakDetectionThreshold` 调到几秒，让池子打印借出连接的堆栈；查 `processlist` 里长时间 `Sleep` 或长事务的连接；用 Arthas 看线程卡在哪个方法上。多数时候堆栈比监控更早给出答案。

**面试里的答法。** 面试官想听的不是「调大连接池」，而是「连接是稀缺资源，谁借的、什么时候还、为什么还不了」。标准回答是先区分泄漏、长事务与流量放大三类，再给监控组合与取证手段，最后补一句结论：连接池打满往往是代码问题，不是参数问题。
