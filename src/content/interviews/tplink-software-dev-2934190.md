### 《面试题目》

1. 一段非均匀分布的绳子烧完需要 1 小时，如何精确计时 15 分钟？
2. 两个人轮流抛硬币，先投到正面的人吃掉苹果，第一个投硬币的人吃到苹果的概率是多少？
3. 住宅高楼和办公楼的电梯效率低下，你有什么办法提高运行效率？
4. 父组件和子组件的 `mounted` / `destroy` 谁先完成？
5. Windows 任务栏把应用最小化然后再点开，经历了哪些事件？最小化会调用销毁吗？
6. 若有一个 `setInterval` 计时器，应该放在哪个生命周期？能放在 `created` 里吗？为什么？
7. `std::map` 的实现原理？B+ 树的原理与增删改查优势？和 `std::unordered_map` 有什么区别，一般会用什么？
8. `std::priority_queue` 是怎么实现的？
9. 项目重难点，挑一个得意的地方介绍。
10. 对 Agent 使用的经验和困难，以及解决方案，用的免费还是付费模型？

### 《参考解析》

**绳子计时 15 分钟**：关键是把「一根绳子」变成「两条燃烧前沿」。同时点燃第一根绳子的两端和第二根绳子的一端；第一根烧完时过去 30 分钟，此时立刻点燃第二根的另一端，第二根剩余部分两端同时烧，15 分钟烧完。要点是说明「不均匀不影响结论」——两端同时点燃等价于双倍速度烧完。

**抛硬币概率**：第一人胜率 `p = 1/2 + (1/2)²·(1/2) + ... `，即 `1/2 · (1 + 1/4 + 1/16 + ...) = (1/2)/(1-1/4) = 2/3`。用等比数列求和，或列方程 `p = 1/2 + (1/2)²p` 更快。

**电梯效率**：从调度算法与硬件两侧答。调度上用群控算法（按楼层与方向聚簇、预测客流、分区停靠、高峰期直达专梯）、减少停靠次数（分层停靠、目的楼层预约系统 Destination Dispatch）；硬件上提高加减速曲线、双轿厢、以及把货梯与客梯分流。这类题考的是「先量化问题（等待时长、能耗），再给可验证的改法」。

**Vue 父子生命周期**：挂载顺序是父 `beforeCreate/created/beforeMount` → 子 `beforeCreate/created/beforeMount/mounted` → 父 `mounted`，即子先 mounted；销毁时父 `beforeDestroy` → 子 `beforeDestroy/destroyed` → 父 `destroyed`，即子先销毁。

**最小化与事件**：最小化不会触发 `destroy`，页面只是隐藏，DOM 仍然存在。经历的是窗口大小/可见性变化相关事件（浏览器里对应 `visibilitychange`、`resize`，Electron/桌面封装下是窗口的最小化/恢复事件）。要说明「销毁是组件卸载，不可与窗口最小化混淆」。

**setInterval 放哪**：放 `mounted` 最稳妥（DOM 已可用，且能保证只注册一次）；放 `created` 也能跑（此时 DOM 还没挂载，若回调里操作 DOM 会拿不到元素），但要在 `beforeUnmount` 里 `clearInterval`，否则组件销毁后定时器仍在跑、造成内存泄漏与重复请求。

**std::map 与 B+ 树**：`std::map` 是红黑树（自平衡 BST），保证有序、增删查 O(log n)、迭代器稳定。B+ 树是多叉平衡树、叶子链表相连，适合磁盘（一次 IO 读一页、扇出大、树矮），数据库索引用它；内存里的 `std::map` 用红黑树是因为内存随机访问代价低、实现简单、常数因子小。`unordered_map` 是哈希表，平均 O(1)、无序、最坏 O(n)，需要有序遍历或范围查询时用 `map`，只做点查用 `unordered_map`。

**priority_queue**：底层是 `std::vector` + 堆算法（`push_heap`/`pop_heap`），默认大顶堆（`less`）。要小顶堆就传 `greater<T>` 或自定义比较器；要稳定同优先级顺序就在元素里带序号。

**Agent 使用经验**：讲一个真实场景（读陌生代码库、批量改写、写单测），说清遇到的困难（上下文不够导致漏改、模型编造不存在的 API）与解法（分步小改、每步验证、给出接口定义、用测试兜底），免费与付费模型的差别可以落在「复杂推理用付费、批量机械操作用便宜模型」。
