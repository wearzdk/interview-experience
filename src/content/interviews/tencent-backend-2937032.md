### 《参考解析》

**逻辑过期防击穿**：热点 key 设逻辑过期时间（存在 value 里）而不设物理 TTL，读到时判断是否逻辑过期：未过期直接返回；已过期则尝试获取分布式锁，拿到锁的线程异步重建缓存，其他线程返回旧值。这样避免了「物理过期瞬间大量请求同时回源」的击穿，也避免了互斥锁让所有请求排队等待。用分布式锁而不是本地锁，是因为多实例部署下本地锁只能挡住本实例的请求，其他实例仍会同时回源。代价是短时间内返回旧数据，需要业务能接受。

**秒杀异步下单链路**：请求先过前置校验（活动状态、用户资格、限流、风控），再用 Redis Lua 原子扣减库存并记录用户已参与，扣减成功则把下单消息写入 MQ 并立即返回「排队中」，前端轮询或推送结果；消费端异步创建订单、扣减真实库存、发券，失败则回滚 Redis 库存并标记失败。核心是「Redis 挡流量、MQ 削峰、异步落库」。

**P99 从 350ms 涨到 5s 的排查**：秒杀接口的响应时间只取决于生产者写 Redis 这一段（面试官已指出），所以先看 Redis：命令耗时（slowlog）、是否有大 key 或热 key、连接池是否耗尽、是否发生主从切换或阻塞命令（如 keys、大范围 zrange）、CPU 与网络。再看应用侧：线程池是否打满、GC 停顿、日志同步写、限流组件本身的开销。排查顺序是先看监控曲线与变更记录（是否刚发版、是否有配置变更），再用链路追踪定位耗时分布，最后做单变量验证。答这题最忌讳把「慢查询、消费慢、积压」当成原因——那些在下游，不在这个接口的关键路径上。

**翻转链表前后半段**：先用快慢指针找中点并统计节点数，拆成两段；分别用迭代法原地反转；再按原顺序拼接（前半段反转后接后半段反转）。奇数时中间节点保持不动，即前半段长度为 n/2 向下取整，中间节点单独保留。时间复杂度 O(n)、空间 O(1)。边界：空链表、单节点、两节点。写的时候先画清指针变化，避免断链。

**进程、线程、协程**：进程是资源分配单位，线程是 CPU 调度单位，协程是用户态的轻量执行单元，由程序自己调度、切换不进入内核。一个进程至少有一个线程（主线程），所以说「线程是调度单位」不意味着进程可以没有线程。多进程适合 CPU 密集、需要隔离与稳定性的场景（一个进程崩溃不影响其他）；多线程适合共享大量状态、IO 密集的场景。秒杀业务里，接入层用多进程或多实例做隔离与水平扩展，单实例内用线程池处理请求，异步下单用消息队列解耦，IO 等待多的地方可以用协程降低线程数。

**TCP 状态机**：建连三次握手：客户端 CLOSED → SYN_SENT → ESTABLISHED；服务端 LISTEN → SYN_RCVD → ESTABLISHED。断连四次挥手：主动方 FIN_WAIT_1 → FIN_WAIT_2 → TIME_WAIT → CLOSED；被动方 CLOSE_WAIT → LAST_ACK → CLOSED。要能解释 TIME_WAIT 的作用（保证最后的 ACK 能重传、让旧连接报文在网络中消散）与 CLOSE_WAIT 堆积的原因（应用没有调用 close）。还有半关闭、同时打开等少见状态。

**SET NX EX 的三个坑**：业务时间超过 TTL，锁会自动释放，其他线程进入临界区——解法是看门狗续期（后台线程定期延长）或把大任务拆小；主从切换时锁可能丢失（主节点写入后未同步就宕机，从节点升主后没有这把锁）——解法是 Redlock 或多副本确认（WAIT 命令），更稳妥的是用带 fencing token 的方案，让下游校验 token 单调递增；30 秒 Full GC 导致锁过期而业务仍在执行——同样是续期失效，解法是 fencing token 或把长任务改为异步加状态机。结论：单靠 SET NX EX 不能保证严格互斥，需要租约加令牌。

**Full GC 频繁**：见前述排查路径。腾讯这题还会追问「30 秒 Full GC 说明什么」——说明堆很大或回收器不合适，G1 或 ZGC 能把停顿压到毫秒级；同时要查是什么导致老年代快速填满（内存泄漏、缓存无上限、大对象）。

**AI 时代还考不考算法**：可以答「考，但考的重点变了」。算法题验证的是基本功与思维严谨性（边界、复杂度），这些不因 AI 而消失；但纯记忆型的题价值下降，更有价值的是「能否判断 AI 生成的解法是否正确、能否优化」。考察 AI 工具能力的方式：给一个真实任务看它如何拆解与验证、看它是否检查生成代码的边界与安全、看它能否说清取舍。

**dirty work**：承认它存在且必要（数据清洗、告警处理、文档维护），但要有把它变少的意识：能自动化的写成脚本，能规范的写进流程，重复三次以上的做成工具。给一个自己把重复工作自动化的例子，比表态更有说服力。
