### 《参考解析》

**Binder 的快，快在「一次拷贝」而不是「不拷贝」。** 传统 Linux IPC（管道、消息队列、Socket）是两次拷贝：发送方用户态到内核缓冲区，再从内核缓冲区到接收方用户态。Binder 用 `mmap` 把内核里的一块缓冲区同时映射进发送方与接收方的用户地址空间，发送方 `ioctl` 写入时做一次拷贝，接收方直接读这块映射，于是省掉了第二次拷贝——这就是「一次拷贝」的由来。被追问「Android 为什么要自造一套」时，要从平台需求答：传输里要能携带对象引用（`IBinder` 句柄）并由内核托管生命周期（引用计数、`linkToDeath` 死亡通知）；要能可靠拿到调用方的 UID/PID 做权限校验，这正是 Android 权限模型的地基；还要有同步调用与线程池管理，这些传统 IPC 都得在用户态自己搭。再补两个工程点：单次传输有大小上限（受 mmap 缓冲区限制，约 1MB 量级，超了要拆包或改走匿名共享内存），Binder 线程池打满会让调用方一直阻塞，这是线上很典型的一类故障。

**SurfaceFlinger 与 VSync：把「一帧怎么上屏」讲成因果链。** 应用把绘制好的图帧通过 BufferQueue 交给 SurfaceFlinger，它按各层（Layer）的 Z 序、位置、透明度和裁剪关系做合成；能整层交给显示控制器叠加的走 Hardware Composer 直接把图送硬件，剩下不支持的才用 GPU 合成，目的是省带宽省电。合成结果交给显示驱动，在 VSync 到来时上屏。VSync 是显示的节拍信号，作用是让绘制与上屏对齐：撕裂（tearing）是新帧在扫描过程中途上屏，一屏之内上下两半属于不同帧，根子在没做双缓冲交换或交换没等 VSync；卡顿（jank）是某帧没在下一次 VSync 的 deadline 前准备好，表现为帧间隔不均匀，常见成因是主线程被 IO 或锁阻塞、合成耗时超预算、BufferQueue 被占满丢帧。答题时把「上屏时间点是固定的，绘制超期就掉帧」这条链讲清楚，再提一句用 `dumpsys SurfaceFlinger`、Perfetto/systrace 去看帧的实际耗时，就是完整回答。

**座舱虚拟化与仪表隔离：安全等级决定了要不要拆系统。** 座舱域控上跑两套甚至多套系统是常态：中控娱乐用 Android（生态好、迭代快），仪表要求高可靠与确定性响应，常见 QNX、Linux + RTOS 或 AGL 方案；两者之上用 Type 1 Hypervisor（QNX Hypervisor、ACRN、裁剪版 Xen 等）做硬件资源的静态划分——CPU 核、内存、外设按虚拟机分配，显示走各自的 plane 或通道，这样娱乐系统崩溃、重启甚至被刷机都不会波及仪表，这就是功能安全里「免受干扰」的诉求。安全等级按 ISO 26262 的 ASIL 划分：仪表上和安全相关的警示（车速、报警灯等）可能落在 ASIL A/B 甚至更高，娱乐系统一般只按 QM 处理，所以必须把安全相关与非安全相关分到不同分区。答题时把「为什么隔离」（独立性、实时性、安全）和「怎么隔离」（Hypervisor 分核分内存、显示通道分离、虚拟机之间走共享内存或 virtio 通信）两块分开讲，比只说一句「因为安全」完整得多。

**共享内存为什么快，以及它到底依不依赖内核。** 无论是 POSIX 的 `shm_open` + `mmap` 还是 System V 的 `shmget`，本质都是把同一段物理页映射进两个进程的页表，数据从写入到被读到全程不拷贝，所以远快于管道和 Socket；映射建立、缺页、容量调整这些一次性开销仍然由内核完成。关键在于后半句：映射建好之后数据面不经过内核，也就意味着内核不提供任何同步——读方凭什么知道写完了？必须自己配信号量、互斥量或事件通知（这时候又进内核了），否则会读到写了一半的数据，这是面试官最想听的那半句。再补几个坑：共享内存没有生命周期管理，进程崩了段还在，要显式 `shm_unlink`；指针不能直接跨进程使用（两边映射地址可能不同，要传偏移）；多核下还要考虑内存可见性，必要时加屏障。

**内存一直涨怎么定位：先分清是真泄漏还是缓存。** 第一步用 `top`、`ps` 和 `/proc/<pid>/status` 里的 `VmRSS` 看曲线形态——单调上涨且不回落是泄漏的典型特征；涨到某个值就稳住，往往只是分配器不归还（glibc malloc 的 arena、mmap 阈值），可以用 `malloc_trim` 或调整 `M_MMAP_THRESHOLD` 验证。确认是真泄漏后按环境选工具：Valgrind memcheck 准但慢，适合小负载跑一遍；ASan/LSan 编译期插桩，适合能稳定复现的用例；`pmap` 与 `/proc/<pid>/smaps` 能看出是哪类映射在变长（堆、匿名 mmap 还是线程栈），据此缩小范围。更工程化的做法是给分配器加一层按模块记账的统计，或在可疑模块的 malloc/free 前后打点计数，直接定位到「谁申请了没释放」。最后加一句预防：把资源收进 RAII 或统一内存池，长跑业务定期做稳定性压测并监控 VmRSS。
