### 《参考解析》

**95% 召回先要交代口径，再谈噪声**：这是 top-k 命中率还是端到端？k 取多少？评测集怎么来？缺了这三项，数字无法比较。高召回的副作用很实在：候选变多，重排与生成的成本延迟同涨，弱相关片段还会把模型带偏。设计上是两阶段——召回放宽保证不漏，重排收紧保证准，再给生成加「无依据就拒答」的出口。精度侧的抓手是负样本与阈值：把线上真实误召回捞出来做 hard negative，按来源设不同门槛，编号、版本这类结构化符号走精确匹配通道，chunk 层再做去重与邻近合并。评估要同时看上下文精确率与答案正确率，否则会把「塞得多」误当成「找得准」。

**为什么不用向量召回，通常有三个理由**：场景里有大量精确符号（错误码、订单号、接口名、专有名词），向量对这类 token 不敏感；语料规模小、词典可控，BM25 加规则就够，上向量要多一套模型、索引与更新链路；以及可解释与可回溯要求高，出错时要能说清为什么召回这一条。真实系统更常见的是混合检索：BM25 打底、向量补语义长尾，再统一重排。

**LangGraph 防发散靠「图有界 + 状态收敛 + 预算兜底」**：图本身固定节点与边，用条件边限制回退路径；每个循环节点带终止判据（信息是否新增、任务是否完成、连续两轮输出是否相同），并用 recursion_limit 硬性截断；外面再加超时、token 预算与工具次数上限，超限就降级给出中间结果。工具调用要幂等并带缓存，否则重试会重复下单、重复发消息。

**多 Agent 的记忆与兜底分三层**：短期用会话内消息，长期用外部存储并配写入策略与过期；Agent 之间传结构化摘要而不是整段对话，避免上下文爆炸与信息失真。信息丢失多发生在摘要压缩和跨 Agent 交接处，所以要保留原始引用（消息 ID、文档 ID）可回溯，关键字段用 schema 校验，缺了就重新取。兜底按「重试 → 换模型或换工具 → 降级返回部分结果 → 转人工」四级设计。

**索引失效与低基数字段，把「能不能用」和「值不值得用」分开**：失效的常见原因是列上做函数或运算、隐式类型转换、前导模糊 LIKE、OR 连接非索引列、联合索引不满足最左前缀，以及优化器估算占比过高主动放弃。性别这种只有两三个值的列，单列索引几乎一定被忽略，回表不如全表扫；但它作为联合索引后置列配合高选择性前导列做覆盖、或数据极度倾斜时查长尾值仍有效。

**SDD 与 AI 提效要拿可比的数说话**：SDD 是先写规格再让模型生成、用测试与评审收敛，优势是需求先被想清楚、产出可复现，风险是规格写歪会把错误放大、也会拖慢小改动。度量别看代码行数，看交付周期、返工率、评审意见数、缺陷密度。效率损失集中在写规格、读懂并修正生成代码、以及上下文给不全导致的反复；改善靠规格模板化、把项目约定与示例喂进上下文、让生成带测试一起出。
