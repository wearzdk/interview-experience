5. 使用 AI 工具生成测试用例，是直接拿来用吗？还是怎么办？

### 《参考解析》

1. **英文自我介绍：准备一段 60 秒的固定结构**：推荐四段式——学校专业与毕业时间、一段与岗位最相关的经历（实习或项目，一句话说清做了什么、什么结果）、能力与岗位的匹配点（自动化或接口测试经验、工具栈）、为什么投这家公司与这个方向。全程用简单句、少用从句，宁可词汇朴素也别卡壳；提前把公司业务、产品线、车载方向的英文说法查好（座舱、车机、OTA、台架这些词要能脱口而出）。面试官用英文提问就尽量用英文答，卡住时可以礼貌地问一句能不能换个说法，别整段切回中文。

2. **自动化测试框架：先讲分层，再讲选型和推进路径**：一个能落地的框架通常分四层——用例层（业务可读的用例描述）、封装层（接口或页面操作的封装，把定位符和请求细节收起来）、数据层（测试数据与配置分离，环境切换靠配置文件或环境变量）、运行与报告层（并发执行、失败重试、Allure 或 HTML 报告、接入 CI 触发）。选型要能说理由：接口用 pytest + requests（或 RestAssured、JMeter），Web UI 用 Playwright 或 Selenium，App 用车机或手机端的 Appium；关键是稳定性和维护成本，而不是工具多新。从 0 到 1 的路径讲成三步：先挑一个高频回归场景跑通冒烟用例，接入流水线让结果自动可见，再按缺陷密度逐步补覆盖率——比一上来铺全量容易活下来。

3. **多项目优先级：按风险和阻塞面排，还要留缓冲**：优先级不是「谁催得急先做谁」。判据依次是——上线时间倒排的硬节点、影响面（核心链路与付费链路优先）、当前风险（新改动、历史缺陷多的模块）、以及是否阻塞别人（阻塞开发的验证要插队）。排完之后要和产品、开发对齐准入准出标准，把「提测质量不达标就退回」写清楚；同时留出 20% 左右的时间给突发问题与回归。被追问「时间不够怎么办」，答法是主动做范围裁剪并同步风险，而不是默默加班或漏测。

4. **接口测试要能报出「测了什么维度」，不是报接口数量**：单接口层面——参数必填与类型校验、边界与特殊字符、错误码与提示语、幂等（重复提交是否重复扣款）、超时与重试；串联层面——依赖接口的数据传递、事务一致性、失败回滚；安全层面——鉴权（无 token、过期 token、越权访问他人数据）、敏感字段是否返回、限流与防重放；性能层面——并发下的响应时间与错误率。工具链讲清就行：Postman 做调试与集合（用环境变量管理 token 与域名），pytest + requests 做自动化回归，数据放 YAML 或 CSV；测试数据用后即清，避免污染环境。

5. **AI 生成的用例不能直接用，这条要有明确态度**：模型生成的初稿看着覆盖面广，实际上有几个固定毛病——大量重复、边界与异常场景缺失、断言写得含糊、以及会编出接口文档里不存在的字段。正确用法是把它当草稿和检查清单：先让它按需求文档列场景清单（这一步人工评审并补异常、兼容、弱网、断电等场景），再生成具体步骤，然后与现有用例库去重、按等价类和边界值补齐，最后逐条人工确认可执行性与预期结果。AI 真正省时间的地方在初稿、日志分析、缺陷描述整理和用例评审清单，而不是「点一下就直接进用例库」。

6. **车载与智能座舱方向的准备要点**：这类岗位的测试对象不只是 App，还包括车机系统与应用、与手机端的互联、以及和整车信号的交互，所以面试里常被问到场景化的测试设计：弱网与断网、隧道与地库的信号丢失、上下电与异常断电、OTA 升级失败回滚、多任务并发（导航播报时来电话）、以及不同车型与硬件版本的兼容矩阵。执行环境要提到台架与 HIL、CAN 报文与信号模拟、实车路测，安全相关功能还要按功能安全要求做故障注入。测试用例类型的标准分类也要能答全：功能、性能、兼容性、安全、可靠性、易用性、异常与边界、冒烟、回归、探索性测试，并各举一个车机场景的例子。最后是自我评价与职业规划两问——优点落到可验证的行为（主动补自动化、把回归时间压下来），缺点说一个真实但不致命的并在改进，规划按「一年能独立负责一个模块、三年能带测试方案」这样的具体路径讲。
