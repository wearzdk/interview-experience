### 《参考解析》

**「多少代码是 AI 写的」这道题在测你的可辩护性，不在测比例**。诚实给一个区间（比如新代码里三到四成由 AI 生成，集中在样板代码、单测、前端表单与工具脚本），然后立刻说明边界：核心业务逻辑、状态机、涉及资金与权限的路径自己写并逐行复核；AI 生成的代码必须能讲清每一行的作用、跑过测试、过 code review。再补一个你纠正 AI 的具体例子（它用了一个不存在的 API、漏了事务边界、把并发当串行），证明你不是复制粘贴。反问「公司内部怎么用 AI」时，可以顺着说你会怎么在团队里用——先用在可验证的环节（单测、文档、脚手架），再逐步放宽到业务代码，并保留评审。

**会话锁与幂等先讲清各自防的是什么**。会话锁防的是同一个会话被并发操作：同一用户在两个标签页同时提交、消息乱序到达、前端重试导致两个请求同时修改同一份会话状态。实现上按 sessionId 加锁（Redis `SET NX PX` 或本地分段锁），锁内做「读状态—校验—写状态」，并给锁设短超时防止死锁；更稳的是把状态变更做成带版本号的条件更新，锁只是减少冲突，正确性靠 CAS。幂等防的是同一个操作被执行多次产生副作用：下单、支付回调、发消息。做法是客户端带幂等键（requestId 或业务唯一键），服务端用唯一索引或去重表记录，重复请求直接返回第一次的结果。两者经常一起用：先幂等去重，再在锁内做状态流转。

**文件上传的不一致主要发生在三个环节**：上传成功但数据库没记录、数据库有记录但文件没落盘、以及分片上传只传了一半。解决办法是把「文件」和「记录」拆成两阶段：先传文件到对象存储或临时目录，拿到唯一 key 与校验和（MD5/ETag），再在数据库写元数据；写库失败就删临时文件（补偿任务兜底扫孤儿文件），写库成功但文件丢失则通过定时对账发现。分片上传要记录每一片的编号与校验和，支持断点续传，所有分片到齐后合并并校验整体 MD5；同一文件重复上传用内容 hash 做秒传。千万不要「先写库再传文件」，那会留下大量指向空文件的记录。

**数据库设计**：先把实体与关系画清楚（用户、文件、业务对象、操作日志），再定字段与约束——主键用自增或雪花、业务唯一键建唯一索引、状态字段用枚举而不是布尔、时间字段统一 UTC、软删除用 `deleted_at` 并让它参与索引。索引按查询建，联合索引遵守最左前缀，避免在区分度低的列上单独建索引。数据量上来后先考虑归档与读写分离，再考虑分库分表；分片键要选分布均匀且查询必带的字段。回答时补一句「表结构变更用 migration 管理，不允许手工改线上表」。

**用户文件与物理文件分离**是元数据与二进制分离的经典做法：数据库只存文件 id、原始名、大小、类型、hash、存储路径、属主、权限与生命周期；真实字节放对象存储或分布式文件系统。好处有五条：数据库不被大字段撑爆，备份与查询都轻；权限与分享逻辑集中在元数据层，换存储不影响业务；同一份内容按 hash 去重，省空间；迁移与冷归档只动存储层；配合 CDN 直接分发，不经过应用服务器。代价是多了一次「元数据与存储对账」的运维工作，需要补偿任务保证两边一致。

**接口与抽象类**：接口是能力契约，只声明方法（可以有常量与 Java 8 之后的 default/static 方法），不能有构造器与实例字段，一个类可以实现多个接口，适合定义「能做什么」；抽象类是继承关系，可以有状态、构造器与部分实现，只能单继承，适合抽取「是什么」的公共骨架。选择标准：需要多实现、跨继承体系复用行为用接口；需要共享状态与模板方法用抽象类。实际项目里常见组合是抽象类实现接口，子类继承抽象类。

**JVM GC 算法**：标记清除（标记可达对象后清除未标记的，简单但产生碎片）、复制（把存活对象复制到另一半，无碎片但浪费空间，适合新生代）、标记整理（标记后把存活对象向一端移动，无碎片但移动成本高，适合老年代）、分代收集（新生代用复制，老年代用标记整理或标记清除）。具体收集器从 Serial、Parallel 到 CMS，再到 G1（分区、可预测停顿）与 ZGC（染色指针、并发整理、亚毫秒级停顿）。回答时把「算法」与「收集器」分开，别把 G1 说成算法。

**MySQL 用 B+ 树做索引**的核心原因是磁盘 IO：B+ 树矮胖，三到四层就能存下千万级数据，一次查询只需几次页读取；非叶子节点只存键不存数据，同样大小的页能放更多键，进一步降低树高；叶子节点用链表相连，范围查询与排序可以顺序扫描；所有数据都在叶子节点，查询路径长度一致，性能稳定。对比 B 树（非叶子也存数据，树更高、范围查询要中序遍历）、哈希索引（等值快但不支持范围与排序）、跳表（内存结构）。

**乐观锁与悲观锁**：悲观锁假设冲突一定会发生，先加锁再操作，数据库的 `SELECT ... FOR UPDATE`、Java 的 `synchronized` 都是；优点是简单可靠，缺点是阻塞与死锁风险，适合写多且冲突频繁的场景。乐观锁假设冲突少，读的时候不加锁，更新时用版本号或状态条件判断（`UPDATE ... WHERE id = ? AND version = ?`），影响行数为 0 就重试或报错；适合读多写少，缺点是冲突高时重试成本大。举例：库存扣减用乐观锁加 CAS 重试，账户余额变动用悲观锁或数据库行锁更稳。

**Redis 快的原因**要分层说：数据在内存，读写不碰磁盘；单线程处理命令，避免锁竞争与上下文切换（6.0 之后网络 IO 多线程，命令执行仍是单线程）；IO 多路复用（epoll）支撑高并发连接；数据结构针对场景优化（SDS、跳表、listpack、渐进式 rehash）；协议简单、避免大 key 与慢命令。要补一句它的快是有条件的：大 key、`keys *`、复杂 Lua、集中过期都会拖慢，生产上要用 `scan`、控制 value 大小、避免热 key 单点。

**设计模式**：不要背 23 种，挑四五个能落在项目里的讲——策略（支付渠道、风控规则，用接口加实现类替换 if-else）、工厂（按类型创建处理器，配合 Spring 的 Bean 注入）、模板方法（导入/导出流程固定、解析步骤可变）、责任链（审批、参数校验串行处理）、观察者（领域事件、消息通知）。每个都说清「不用它会怎样」，比如策略模式解决了新增渠道要改主流程的问题。

**索引失效**的常见情形：在索引列上做函数或运算（`where date(created_at) = ...`）、隐式类型转换（字符串列传数字）、前导模糊匹配（`like '%xx'`）、`or` 连接了未建索引的列、联合索引不满足最左前缀、范围查询之后的列无法再用索引、区分度极低的列、以及优化器估算全表扫描更便宜时主动放弃。排查用 `explain` 看 type、key、rows、Extra（出现 `Using filesort`、`Using temporary` 要留意）。

**ES 多条件查询**：用 `bool` 组合 `must`（参与打分）、`filter`（不打分、可缓存，适合精确过滤）、`should`（满足其一，配合 `minimum_should_match`）、`must_not`。文本字段用 `match` 走分词，精确值用 `term`（注意 `text` 类型默认分词，精确匹配要用 `keyword` 子字段）；数组嵌套对象用 `nested` 查询保证同一对象内条件同时满足；时间范围用 `range`。深分页用 `search_after` 而不是 `from + size`。

**Redis 与数据库一致性**：主流是 cache aside——读时先读缓存、没有再读库并回填；写时先更新数据库、再删除缓存（不是更新缓存）。删除失败或并发读写导致的短暂不一致，用延迟双删、消息队列重试删除、或订阅 binlog（Canal）异步失效来收敛。要接受「缓存与库是最终一致」，对强一致要求高的读走数据库或加分布式锁。另外补两个细节：缓存要有过期时间兜底；删除缓存比更新缓存好，因为更新缓存在并发下可能写入旧值。

**9 个小球找最重**：天平两次即可。第一次分成三组各三个，称其中两组：若不平衡，重的那组三个里有目标；若平衡，目标在未称的那组。第二次从那三个里取两个各放一边：重的那边就是目标，若平衡则第三个是目标。关键是把「三分」讲出来——每次称量有三种结果，两次最多可区分 3² = 9 种情况，正好覆盖 9 个球，所以两次是理论下界。
