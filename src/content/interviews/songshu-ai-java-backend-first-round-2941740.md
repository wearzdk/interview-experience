### 《参考解析》

**IM 通讯的实现要点**：长连接选型（WebSocket 为主，移动端弱网可配 MQTT 或私有 TCP 协议），连接层做鉴权（握手时带 token）、心跳与断线重连、消息可靠投递（客户端 ACK + 服务端重试 + 消息 ID 去重）、离线消息（收件箱存储，上线后按游标拉取）、消息顺序（同一会话用会话 ID 路由到同一节点或按序号排序）、已读回执与未读数（用户维度的 lastReadSeq + 计数）。要讲清「在线推送 + 离线存储 + 拉取补齐」这三段。

**e签宝这类第三方签署的接入要点**：服务端拿自己的应用凭据换 access token，创建签署流程（模板、参与方、签署顺序），拿到签署页面 URL 给前端打开，回调 / 轮询接收签署状态并验签（回调要校验签名与幂等），最后下载存证文件与签署报告归档。坑点在于回调可能重复与乱序（用业务单号做幂等）、签署链接有时效（缓存并刷新）、文件哈希要自己算一遍与平台返回比对。

**RAG 的实现链路**：文档解析（PDF 要处理表格、扫描件走 OCR）→ 清洗与分块（按语义或标题切、带重叠）→ 向量化与入库（embedding 模型、向量库选型与索引类型）→ 检索（向量召回 + 关键词召回混合、rerank 精排、元数据过滤）→ 拼装上下文与生成（控制 token、给引用）。工程上要补三件事：增量更新与删除（文档改了要能失效旧切片）、评测集与召回率指标、以及「检索不到时不要硬编」的兜底。

**OSS 分片上传与中断处理**：先 `initiateMultipartUpload` 拿 uploadId，把文件按固定大小（如 5MB）切片并发上传 `uploadPart`，每片记录 ETag，全部完成后 `completeMultipartUpload` 按序号提交；失败或中断时用 uploadId + 已上传分片列表（`listParts`）续传，只补缺的片；未完成的分片要配生命周期规则自动清理，否则会一直计费。并发度要限流（线程池 + 信号量），单片失败要重试并做退避，大文件还要算 MD5 / CRC 做完整性校验。

**多级权限的实现**：模型上是用户 - 角色 - 权限（RBAC）或用户 - 组织 - 数据域，权限分功能权限（能否访问某接口）与数据权限（能看哪些数据）。实现上接口级用注解 + 拦截器校验，数据级在查询条件里强制注入数据域过滤（不要依赖前端传 orgId），越权校验必须按资源归属判断（`resource.ownerId == currentUser.id` 或在其可见域内）。缓存权限到 Redis 并按角色变更失效，避免每次请求打库。

**HashMap 与 ConcurrentHashMap**：HashMap 非线程安全，JDK 8 是数组 + 链表 + 红黑树，扩容 2 倍并拆分高低位链，并发 put 可能丢数据甚至（JDK 7）成环。ConcurrentHashMap 用 CAS + synchronized 锁单个桶头节点（JDK 8），读操作无锁（volatile 读），扩容支持多线程协助迁移（`transfer` + `ForwardingNode`），size 用 `CounterCell` 分散计数。它保证单次操作原子，但复合操作（先查再写）仍要自己加锁或用 `computeIfAbsent`。

**线程池参数与分片上传**：核心线程数、最大线程数、空闲存活时间与单位、任务队列、线程工厂（命名便于排查）、拒绝策略。分片上传是 IO 密集，线程数可以大于核数（按带宽与分片大小估），队列要有界避免内存堆积，用 `CompletableFuture` 编排所有分片的完成再提交合并，失败片单独重试；要区分「上传池」和「业务池」，避免大文件上传把接口线程占满。

**Lock 与 synchronized**：synchronized 是关键字、由 JVM 实现（偏向 / 轻量 / 重量级锁升级）、自动释放（包括异常），不可中断、不可超时、非公平；`ReentrantLock` 是 API、可中断（`lockInterruptibly`）、可超时（`tryLock`）、可公平、支持多个 Condition。用 `lock()` 之后如果异常没写在 try 里、`unlock()` 不在 finally 里，锁就永远不会释放——这不是「死锁」，而是锁泄漏导致其他线程永久阻塞。回答时要纠正这个措辞：真正的死锁是互相等待对方的锁。

**ThreadLocal**：每个 Thread 持有一个 `ThreadLocalMap`，key 是 ThreadLocal 的弱引用、value 是强引用；因此线程池场景下不 remove 会随线程存活而泄漏（key 被回收后变成 key 为 null 的 Entry，value 仍被持有），也会造成串数据。用完必须 `remove()`，最好在 finally 里。典型用途是请求上下文（用户 ID、traceId）、事务连接绑定。

**AOP 原理**：Spring AOP 基于动态代理——有接口用 JDK Proxy，无接口用 CGLIB 生成子类；容器在 Bean 初始化后由 `BeanPostProcessor` 判断是否需要增强，包装成代理对象返回。切面由切点（Pointcut）与通知（Advice）组成，调用时责任链依次执行。注意类内部方法自调用不走代理、`private` 与 `final` 方法无法被 CGLIB 增强，这也是事务失效的常见原因。

**Bean 作用域**：singleton（默认，容器内一个实例）、prototype（每次获取新建）、request / session / application（Web 环境），以及自定义 scope。singleton 里的成员变量是共享的，所以要注意线程安全；prototype 注入到 singleton 里只会创建一次，需要 `ObjectProvider` 或方法注入。

**「上传 PDF → 解析十几秒 → 调大模型」的设计**：这是典型的长任务异步化。前端先申请上传凭证直传 OSS，提交后写一条任务记录（状态机：待处理 / 解析中 / 生成中 / 完成 / 失败）并投递到消息队列；消费者分两阶段（解析、模型调用）推进状态并落中间结果，前端用任务 ID 轮询或 SSE 订阅状态；失败可重试（幂等键 = 任务 ID + 阶段），超过重试次数转人工；限流与配额按用户与全局控制，避免模型调用被刷；产物存对象存储并设置过期。要主动说明为什么不用同步接口：十几秒超过网关与浏览器的超时、也无法做失败重试与进度反馈。

**AI 相关开放题**：AI 工具类问题按「用它做什么、怎么保证质量」回答（生成单测、重构、查不熟的 API，配合 review 与可执行验证）；「写过 skill 吗」可以讲把重复的工作流固化成脚本或提示模板；「前后端一起做要多长时间、提示词怎么写」的答法是先拆接口契约与数据模型，再分别生成，提示词里给上下文（技术栈、目录结构、既有约定、验收标准）而不是只给一句需求。
