### 《参考解析》

**RAG 知识库搭建**：一条完整链路是“采集 → 解析 → 清洗 → 切分 → 向量化 → 入库 → 检索 → 重排 → 组装上下文 → 生成 → 评测”。切分要按文档结构（标题、段落、表格）而不是固定字数硬切，块大小和 overlap 要拿评测集调；检索通常用向量加 BM25 的混合召回，再加重排模型压 top-k；每条 chunk 带来源、版本、权限等元数据，回答时附引用，方便溯源。知识库要支持增量更新与删除，文档更新后旧向量必须失效，否则会答出过期内容。评测上分别看召回率、上下文相关性、答案忠实度和端到端任务成功率，不能只看最终回答“像不像”。

**错误处理与索引**：AI 链路的错误要分层：文档解析失败、切分后为空、嵌入接口超时、向量库写入失败、检索无结果、模型调用失败、输出格式不合法。每层都要有明确的重试策略、降级路径和可观测日志；写入用幂等键（文档 ID + 内容哈希）避免重复，失败进入重试队列或死信队列。索引出错通常表现为检索报错、召回为空或结果错乱：先确认索引 mapping 与写入字段类型是否一致，再看分片健康状态、别名是否指向正确索引，最后检查查询语句。重建索引要用别名切换，避免线上读写中断。

**性能优化与成功率**：先量化再优化。接口层看 P95/P99、错误率、超时率；依赖层看下游耗时与连接池；模型层看首 token 延迟、总耗时、token 数。常见手段：缓存（热点问答、嵌入结果、检索结果）、并发化（多路检索并行、模型流式返回）、批处理（离线嵌入）、超时与熔断、请求合并、异步化非关键路径。成功率要拆开看：是网络失败、限流、模型拒答还是业务校验失败，不同原因对应不同治理。

**排序间隔与插入排序**：如果数据一开始就按很大的间隔插入，确实能减少频繁搬移，但间隔留得越大，后续查找和范围查询越依赖额外的比较逻辑，极端情况下退化成链表；而且间隔用完后仍要扩容和重排，维护成本高。插入排序适合小规模或基本有序的数据，时间复杂度 O(n²)，数据量大时应该用归并/快排或数据库索引。面试官问这句通常是在考“为什么不用一个看似取巧的方案”，要答出适用边界和 worst case。

**Node.js 事件循环**：Node 基于 libuv，事件循环分 phases：timers（setTimeout/setInterval）、pending callbacks、idle/prepare、poll（I/O 回调）、check（setImmediate）、close callbacks；每个 phase 之间会清空 nextTick 队列和 Promise 微任务队列。`process.nextTick` 优先级高于 Promise，递归 nextTick 会饿死 I/O。CPU 密集型任务会阻塞事件循环，应该拆成小任务、用 worker_threads 或放到独立服务。理解这些才能解释“为什么 setTimeout 0 和 setImmediate 的顺序不固定”以及“为什么大文件读写要用流”。

**学习路径**：不要只报课程名。可以按“语言基础 → 框架与工程化 → 数据库与缓存 → 分布式与中间件 → 线上排障”讲，每层配一个可演示的项目或线上问题。最近学的技术栈要能讲清选型理由、踩过的坑和验证方式，比如学 Node.js 就讲事件循环、流、集群与压测，而不是只背 API。
