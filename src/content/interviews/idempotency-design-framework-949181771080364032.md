### 《面试题目》

1. 讲一个你自己设计过的幂等方案。
2. 重复是怎么产生的？不同来源要用不同策略吗？
3. 幂等键怎么选？能不能用整个请求体的 hash？
4. 三层实现手段分别是什么？各自挡不住什么？
5. 唯一索引冲突时，为什么外层捕获了异常事务还是会回滚？
6. 幂等窗口留多久？超过窗口期的重复怎么办？
7. 第一次成功了但返回失败，重试时应该返回什么？
8. MQ 消费端用什么键做幂等？

### 《参考解析》

**第一步：界定重复来源**。分三类——客户端或用户重试（连续点击、前端重复提交、接口超时重试）、基础设施重试（网关超时重发、RPC 框架重试、MQ 的 at-least-once 投递）、自身调度问题（定时任务重复触发、补偿任务重复执行）。面试官听到这里通常会点头，因为这说明你知道幂等是系统整体的属性。同一时刻的并发重复与隔几秒的重复解法不同：前者靠锁或数据库行锁，后者靠唯一约束与状态判断。

**第二步：选幂等键**。两类：客户端生成的业务单号（适合支付、下单，但需要客户端配合，老接口改造困难）；业务维度组合键（适合 MQ 消费与内部服务调用，要保证组合唯一）。重点坑是不要拿整个请求体的 hash 当幂等键——JSON 序列化字段顺序不稳定、金额类型在传输中可能变化、请求体带毫秒级时间字段，同一个业务请求会算出两个 hash，幂等直接失效。只用业务主键，必要时加版本号。

**第三步：三层手段**。第一层把接口设计成天然幂等，例如 `UPDATE ... SET status = 2 WHERE id = ? AND status = 1`，看影响行数判断是否抢到，比一把锁轻量。第二层用数据库唯一索引兜底，插入去重表并给业务键加唯一约束，冲突后捕获异常再查一次已有记录返回，而不是直接抛 500。第三层用 Redis 做前置拦截，`SET key NX EX 60` 抢占，抢不到就返回「处理中」；但要主动说明它的坑——Redis 抢占成功而事务回滚时 key 还在，后续正常请求会被误拦，所以 value 里塞状态、失败时主动删除，或者干脆只把 Redis 当限流，正确性仍由数据库保证。

**唯一索引与 rollback-only**：帖主实现订单去重时用唯一索引并在 `catch` 里查已有记录返回，结果部分请求报 `UnexpectedRollbackException`。原因是唯一键冲突时插入失败会在事务里留下痕迹，Spring 把当前事务标记成 rollback-only，外层即使捕获异常，提交时仍然失败。三种解法：把去重表插入放到 `REQUIRES_NEW` 的独立事务；用 `INSERT ... ON DUPLICATE KEY UPDATE` 避免抛异常；或者不依赖异常、先查后插并加分布式锁。帖主选了第二种，代价是这条 SQL 没法直接用 JPA 的 `save`。

**三个必答的追问**：幂等窗口按业务保留 7 到 30 天并配合定时清理，超过窗口期的重复要么靠业务状态机兜底，要么承认极小概率重复；第一次成功但返回失败时，重试绝不能重新执行，应返回第一次的结果，所以要把结果单独存一份或按业务当前状态映射；MQ 消费端的幂等键用消息里的业务 ID，不要用 `messageId`，因为生产端重投时它可能变化。
