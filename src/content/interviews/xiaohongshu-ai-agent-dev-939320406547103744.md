### 《参考解析》

**接口幂等：超时重试下的「只做一次」**

「客户端超时但服务端已经入库」是幂等设计的经典入口：超时只说明客户端没拿到响应，不代表服务端没执行，所以幂等必须由服务端承担。做法是调用方带业务幂等键（请求号或客户端生成的 UUID），服务端在同一个事务里「插入幂等记录 + 执行业务」，用唯一索引挡住重复插入，冲突时直接返回首次结果；扣费这类资金动作再叠一层状态机与流水表，任务状态单向流转、扣费记录与任务 ID 一一对应。题目里「先删除再创建」被质疑，是因为它的语义是覆盖而不是判断：并发重试会把别人刚建好的任务删掉，中间还有真空窗口，删除本身也要幂等；正确做法是先按幂等键查询（或直接尝试插入），存在就返回旧结果、不改变已发生的副作用。可以主动补一句幂等窗口的边界——键设有效期，过期重试视为新请求，避免表无限膨胀。

**同一个 JVM 里的共享状态：为什么两个独立对象也救不了**

两个 Agent 实例同时给共享计数器加一却丢更新，根因是「读-改-写」不是原子操作：两个线程都读到 5、各自写回 6，最终只加了一次；再往下追是 Java 内存模型的三件事——原子性（`count++` 是三条字节码指令）、可见性、有序性（编译器与 CPU 可能重排）。共享集合的问题更直接：`ArrayList`、`HashMap` 并发写入会覆盖元素甚至结构损坏。第二问是陷阱：如果计数器是实例字段，各加各的当然不冲突，但业务上不再共享、统计值仍然是错的；如果共享的是静态字段或外部单例（Spring 默认单例 Bean 就是这种），换对象毫无作用。所以答案分两层：先确认共享的到底是什么，再用对的工具——`AtomicLong` 或 `LongAdder` 计数、`ConcurrentHashMap` 或加锁保护复合操作、把状态改成不可变或线程私有；跨进程则换 Redis 原子操作或数据库行锁。追问常在 `LongAdder` 与 `AtomicLong` 的取舍（分段累加高竞争下吞吐更好，读取不精确）以及 volatile 为什么不能用来做计数。

**正文缓存与权限校验：缓存可以脏，权限不能脏**

十分钟的正文缓存遇上「管理员刚撤销权限」，结论是不能直接返回缓存正文——缓存的是内容，鉴权是每次请求都必须重新做的判断，两者不能合并成一个「命中即返回」的快路径。分工是：鉴权层每次请求都执行（权限数据本身可以缓存，但缓存的必须是权限数据而不是判定结果，且要能主动失效），内容缓存层只负责正文读取加速，命中后仍要过鉴权才返回。权限撤销时是否立刻失效正文缓存是成本与时效的权衡：最省事的是把权限版本号拼进缓存键，权限一变版本号加一、旧键自然读不到；也可以主动清理该用户的条目，再用短 TTL 兜底。更好的方案是判定结果不进缓存、只缓存权限数据加版本号，并在网关层做统一的资源级鉴权，同时接受「安全敏感场景宁可牺牲命中率」这个取舍。

**Coding Agent 的设计、Sub-agent 与评测**

设计一个 Coding Agent 要覆盖四层：感知与上下文（代码库检索、文件读写、依赖与错误信息怎么进上下文）、决策（任务拆解、计划与执行循环、失败重试与回退）、行动（读写文件、跑命令与测试、查文档、提交差异，以及每个工具的权限边界）、质量与安全（沙箱、改动范围约束、关键节点人工确认）。核心能力按「能读懂现有代码、能做可验证的最小改动、能在失败后自我诊断、能解释自己的改动」组织，这也顺势回答了什么叫好的 Coding Agent：不是看一次生成多少代码，而是看任务通过率、一次通过率、平均交互轮数、引入回归的比例与单任务成本。用 Sub-agent 的理由讲成「上下文与并行的取舍」——把长任务的大上下文切成多个短上下文以降低污染与成本、让子任务并行试错、给每个子任务更聚焦的角色与工具集；代价是通信开销、子 Agent 看不到全局导致局部正确而整体冲突、结果不可复现；拆分的判据是「子任务的输入输出能不能独立定义、验收标准能不能独立写出来」。评测最容易被追问穿，所以要能给出对照实验：同一批任务跑单 Agent 基线与加 Sub-agent 的方案，比成功率、平均轮数、token 成本、端到端时延与回归率，并说明样本量与显著性；被问「主 Agent 能完成，用 Sub-agent 是什么作用、优化的指标是什么」，答不出数字就只能承认没做对照。

**Agent 工程化细节：prompt、工具 schema、规划与压缩**

system prompt 要把结构说清：角色与边界、工具使用规范、输出格式、领域规则、few-shot 示例各占多少 token，怎么做版本管理与评测；工具变多时靠分组、按场景裁剪可用集、把描述写得可区分来控制选择准确率。工具 schema 覆盖名称、描述、参数类型、枚举值与示例，并解释「约束偏宽松」的取舍：enum 太严会让模型频繁报错、太松会写错值，实务上先用宽松类型接收、再在函数内部规范化校验，把错误变成可纠正的提示回灌——但资金、删除这类危险动作必须严格校验。任务规划要包含「意图识别 → 工具依赖推导 → 执行 → 失败后重新规划」这条链，并说清失败处理差异：参数错误重试、工具超时换路、前置假设不成立则回计划层重规划，同时给循环轮数与预算上限。上下文压缩分两档：限制文档数与截断便宜但粗暴；用小模型做摘要压缩时之所以偏 encoder-decoder，是因为它能在压缩阶段完整读一遍长文再生成短表示，理解与改写比单向模型更稳；无论哪种都要有「压缩后关键信息还在不在」的校验与原文回溯入口。

**RAG 检索优化与模型侧训练**

父子索引的逻辑是「小块检索、大块生成」：小块语义聚焦、区分度高但信息不完整，命中后回溯到父块送进模型，兼顾精确率与可答性。query 侧三件事分清：改写补全口语化与指代、扩写生成多个等价问法提高召回（按结果去重融合）、分解把复合问题拆成子问题分别检索；避免重复生成靠去重聚类加数量上限。HyDE 是先让模型生成一个假想答案再拿它去检索，因为答案的用词分布更接近文档所以更容易命中，代价是多一次生成且假想答案跑偏会把检索带偏。重排的必要性在于向量相似度只是粗筛，交叉编码器逐对打分更准但算不动全量，所以两段式；选 BGE 一路通常是中文效果好、尺寸可选、可本地部署，但要能给出 Recall@K 与 NDCG@K 的前后对比。TOP K 的截断依据是分数分布加上下文预算双约束，低分文档宁可丢掉也不要塞进去稀释注意力。模型侧，字节流替代 BPE 解决词表外与多语言问题：BPE 词表固定，遇到没见过的字符组合就退化或拆碎，字节级把任何文本无损表示进统一词表、对拼写噪声更鲁棒，代价是序列变长。BLEU 与 chrF1 取几何平均是翻译类任务的常规组合，前者对同义改写苛刻、后者对形态变化与中文更友好。伪标签噪声靠多模型一致性筛选、分数阈值与保留干净锚点控制；消融实验是「分数从 30 涨到 32」必须配套的动作，逐个关掉随机掩码、双向互译、随机编码确认边际贡献。SFT 数据量按难度分层，「质量比数量重要」要落地成审核通过率与答案可验证性；全参与 LoRA 看「分布差多远、多少数据、多少卡」。端侧模型的价值除降本还有隐私与低延迟，评价框架要看内存占用、首 token 延迟与量化精度损失。

**传输协议、MCP 适配与缓存鉴权的工程收尾**

HTTP、SSE、WebSocket 按方向性与开销区分：HTTP 一问一答、短连接、无状态；SSE 基于 HTTP 长连接只做服务端到客户端的单向推送，纯文本、实现简单、兼容网关与鉴权，适合逐 token 吐流；WebSocket 全双工，适合高频双向交互，代价是要处理心跳、重连与背压。落地常见组合是 HTTP 做请求加 SSE 做流式返回。MCP 的适配问题是同一个服务端要以 stdio、HTTP、SSE、Streamable HTTP 几种方式暴露，方案是抽出「会话与消息传输」的接口层，让协议语义与传输实现分离；版本兼容靠版本协商、能力声明与向后兼容的字段扩展，不匹配时降级到最小能力集。会话表与消息表的关键字段：会话表放用户、标题、模型与参数、状态、最后消息时间；消息表放会话 ID、角色、内容块、token 数、模型、父消息 ID（支持重新生成与分支）、工具调用记录与耗时，索引按「会话 ID + 创建时间」建，长会话做分页与冷热分离。服务稳定性按「可观测 → 可定位 → 可自愈」三层答：指标、结构化日志与 trace id、跨服务链路追踪，告警分级与抑制、区分用户可感知故障；ES 慢查询先查分片数是否远超必要导致扇出（12 分片却只有 1 QPS 就是这个信号），再查排序字段是否走 doc_values、有没有深分页；重建索引走别名切换而不是原地 reindex 阻塞线上。
