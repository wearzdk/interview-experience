### 《参考解析》

**行程规划 Agent 的采分点在工具编排与澄清闭环**：工具集按「信息获取（地图、天气、门票、评价）—计算（路线时间、预算汇总）—动作（预订、支付）」分层，每类工具给出参数 schema 与幂等键。编排上先做需求解析（出发地、日期、人数、预算、偏好），缺关键槽位就澄清，齐了就规划候选并做约束校验（预算不超、通勤时间合理、营业时间匹配）。澄清策略是「一次问一个最关键且无法推断的槽位」，优先级为时间 > 地点 > 预算 > 偏好，用选择题式提问降低用户负担，判断「澄清够了」的标准是所有硬约束齐备、软偏好允许留空。确认机制上，查改类动作可直接执行，凡是花钱、改订单的动作必须显式确认。异常处理的重头戏是重规划：天气突变时触发「同城室内候选替换 + 行程顺序重排」，用户压缩天数则重跑约束求解并提示被舍弃项，改动前的方案要留快照以便回滚。

**RAG 的每一环都有可问的细节**：完整流程是解析清洗 → 切分 → 向量化 → 索引 → 查询改写 → 召回 → 融合 → 重排 → 生成。Markdown 没标题时不要硬按固定字数切，可以按语义边界切（空行成段、列表项聚合、代码块整块保留），再用滑动窗口重叠兜住跨段语义；切分粒度按「一问一答能被完整覆盖」来定，通常 200–500 token，配合父子块（小块检索、大块喂模型）更好用。短 Query 与长 Chunk 的向量可比性问题，本质是长度与信息密度不对齐：可以给文档侧生成假设性问题或标题摘要再向量化（doc2query）、做查询扩展、或对长 chunk 取关键句，检索时用非对称双编码器训练。混合检索中关键词（BM25）精确、可解释、擅长专名与否定，向量召回擅长语义泛化但会漏精确匹配，融合常用 RRF 或加权归一化打分；RRF 的 k 默认 60，作用是压平头部差异——k 越大越接近只按排名平均，k 越小越放大靠前结果的优势，实践中按数据调 10–100。召回不准时先分层排查：Query 是否有歧义或口语化（改写与多查询）、切分是否丢语义（检查命中片段）、embedding 是否与领域不匹配、是否缺元数据过滤，最后才怀疑重排与生成。拒答则靠相似度阈值加显式指令加「证据不足就说不知道」的评测用例三件套，阈值要用标注数据校准而不是拍脑袋。

**结构化输出与记忆压缩是 Agent 工程的两根支柱**：让模型输出 JSON 要靠「Schema 说明 + few-shot 示例 + 受约束解码（JSON mode／function calling）+ 解析失败回灌重试」，并在落地前做严格校验（必填、类型、枚举、取值范围），校验失败不要静默兜底，而是带上错误信息让模型自我修正，连续失败则降级为自然语言追问。记忆压缩的做法是分层：系统约束与工具契约永不压；最近若干轮原文保留；更早历史按「目标、已完成步骤、当前状态、待办、关键事实」结构化摘要，工具返回只留结论和引用地址；压缩后要做一次一致性校验（关键 ID、金额、日期不能丢）。短期记忆可用会话缓存或内存态加落库，长期记忆用带元数据的向量库加结构化用户档案，写入要有准入与去重，读取按相关性召回，避免把噪声写进长期记忆污染后续所有对话。

**推荐系统部分要能把「召回—排序—生成」串起来**：双塔召回是用户塔与物品塔各自编码成同维向量，用内积／余弦在向量索引里做近邻检索，用户塔输入用户画像、历史行为序列、上下文，物品塔输入类目属性、标题文本、统计特征；两塔必须同维才能算内积，若原始维度不同就在各自塔里加投影层压到统一维度。负样本上，随机负采样简单但太容易区分、学到的东西少，batch 内负采样（in-batch negative）把同批其他样本当负例，代价低、难度适中，但会有「热门物品被误当负例」的偏差，需要用采样概率校正；实际常做混合——batch 内为主，加少量难负例（曝光未点击）与全局随机负例。训练正负极度不均衡时不要直接按原始分布算损失，可以下采样负例、用 focal loss 或对正样本加权，但要注意采样会改变先验，打分阶段需做概率校准。用户行为序列 1000 条显存扛不住时，工程手段有：只取最近 N 条加时间衰减、按类型聚合（把同类行为压成统计特征）、用轻量序列模型或两阶段（先粗筛再精排）、特征分桶与量化、训练时截断／推理时蒸馏。评估除了 CTR 与 GMV，还要看多样性、新颖性、覆盖率、长期留存与退订率；AB 实验要保证分流随机、样本量与实验周期足够、指标口径与埋点一致，若点击率反而下降，排查顺序是埋点与口径、分流是否被污染、新模型上线链路（特征是否实时、是否与训练一致）、然后分层分析（新老用户、品类、曝光位置）与新鲜度效应。

**记忆、客服拆分与大规模调度考的是系统设计能力**：短期记忆是当前会话的工作集（最近对话、当前任务状态、工具中间结果），用内存或会话缓存加落库；长期记忆是跨会话的用户档案与历史结论，用向量库加结构化字段，读时按相关性召回、写时有准入与过期策略。智能客服 Agent 的拆分不要按「售前一个 Agent、售后一个 Agent」硬切，而是按「路由 + 领域技能 + 动作工具」三层：一个路由层做意图分类与会话状态机，技能层拆成咨询问答（RAG）、投诉处理（SOP 流程 + 情绪识别 + 升级人工）、订单查询（结构化查询工具），工具层封装订单、退款、工单系统并全部带幂等键与权限校验；关键是升级人工的触发条件要明确（情绪激动、连续两轮未解决、涉及金额争议）。每天 10 万请求的调度要看峰值而非均值：入口做限流与排队、推理侧做批处理与流式、按任务分级（简单意图走小模型或规则、复杂走大模型）、缓存高频问答与工具结果、密钥与配额池化并做多厂商降级，同时给长任务异步化（提交后返回任务 ID），成本与延迟指标要能分渠道观测。

**手撕双塔前向的采分点是形状与增量更新**：PyTorch 里就是两个 MLP（用户塔、物品塔）各自 forward 得到 `[B, D]` 与 `[N, D]`，做归一化后 `logits = user_emb @ item_emb.T`（或按需除以温度），训练时配 in-batch 负采样的交叉熵。维度不一致的追问，答案是加投影层把两侧都映射到同一维度 D，或者用带权重的双线性形式 `u^T W i`；更规范的做法是让输出层维度作为可配置的 embedding 维度，训练与索引共用。物品塔增量更新的追问，考的是「不能全量重算」——方案是物品塔离线全量建索引 + 新物品或属性变更时单条推理写回向量库（增量 upsert），并处理版本一致性（新旧向量混用会导致近邻结果漂移，可用双写加灰度切换），实时性要求高的场景把物品塔做成可在线推理的小模型或缓存热门物品向量。收尾时主动说清离线指标与线上近邻检索的一致性校验，这通常是这类题最后的加分点。
