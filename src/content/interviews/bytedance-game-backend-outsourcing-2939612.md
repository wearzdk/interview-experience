### 《面试题目》

1. 自我介绍。
2. 上一个项目的服务器架构是怎样的？
3. 围绕项目做了哪些延伸提问。
4. Redis 中数据冷转热是怎么做的？
5. 全服排行榜怎么设计？
6. 线上内测遇到过什么问题，怎么处理的？
7. 平时玩什么游戏比较多？
8. 设计一个背包的写入：`Bag.addItem(int itemid, int count, int maxcount)`，其中 `maxcount` 是堆叠上限。

### 《参考解析》

**服务器架构要按「请求怎么进来、状态放在哪、怎么扩容」讲**：接入层做长连接网关（TCP 或 WebSocket），负责心跳、断线与重连；逻辑层按玩法或场景分服，尽量无状态，状态落到 Redis 与 DB；持久化层 MySQL 存玩家核心数据，Redis 存热数据与排行榜；跨服玩法用中心服或消息队列解耦。要能说出你负责的那一段的 QPS、延迟与数据量，而不是只画框图。

**冷转热的核心是「按访问频率决定去向」**：玩家离线或长期不活跃的数据沉到 MySQL 或冷存储，登录或访问时按需加载进 Redis，并设置合理的 TTL 与淘汰策略（`allkeys-lru` 或 `volatile-lru`）。加载要防击穿——同一玩家的并发请求用分布式锁或单飞（singleflight）合并成一次回源；回源后写回缓存并刷新 TTL；写操作先写缓存再异步落库时要考虑丢数据，关键数据应「先落库再删缓存」。判断冷热的依据可以是最后登录时间、最近 N 天访问次数，或者按玩家等级与付费分层。

**全服排行榜的常规做法是 Redis ZSET**：`ZADD` 更新分数、`ZREVRANGE` 取前 N、`ZREVRANK` 查自己的排名，操作都是 `O(log n)`。玩家量大时按分数段或服务器分片，查询时先查分片榜再合并；跨天或跨赛季的榜单用多个 key 做快照，结算时冻结旧 key、新建新 key。要注意「同分排序」——`ZSET` 分数相同时按成员字典序，业务上通常需要再加一个时间戳做次级排序，或者在成员名里编码时间。榜单一万条以上时，前端只取前 100，自己的排名单独查。

**内测问题的答法**：讲一个具体的、有数据的故障——现象（例如开服十分钟登录成功率跌到 60%）、定位过程（看网关连接数、Redis 慢查询、DB 连接池打满）、根因（比如登录时同步查了三次库、缓存击穿）、修复与后续加固（加缓存、限流、连接池扩容、加监控告警）。面试官想听的是排查路径，而不是「我们修好了」。

**背包写入的设计要覆盖四件事**：容量与堆叠、并发安全、持久化、幂等。先校验 `itemid` 合法、`count > 0`，按堆叠上限把数量拆成「补满已有堆叠 + 新建格子」，检查背包剩余格子是否够，不够就返回明确错误码而不是部分成功；写入时对玩家背包加锁（单玩家串行化，或用版本号做乐观锁），避免两个请求同时读到同一份快照导致超卖；落库用事务保证「扣道具 / 加道具」的原子性，道具变更记流水便于对账；接口带请求 ID 做幂等，重复请求直接返回上次结果。若背包是热数据，缓存与 DB 的更新顺序要固定，并在写路径上做失败重试与补偿。

**「平时玩什么游戏」不是闲聊**：游戏后端岗位会借此判断你是否理解玩法与数值，回答时可以说清你玩的那款游戏的哪些系统（匹配、排行、掉落、交易）在服务端大概怎么实现，把话题引回技术。
