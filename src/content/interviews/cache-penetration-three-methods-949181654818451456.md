1. 缓存穿透怎么处理？
2. 如果布隆过滤器误判，请求还是打到库上了，你怎么办？
3. 缓存空值该怎么设过期时间？
4. 穿透、击穿、雪崩怎么区分？
5. 空值缓存上线后踩过哪些坑？
6. 布隆过滤器有哪些代价？什么时候才值得上？
7. 入口校验和限流具体做什么？
8. 现在再被问，你会怎么答？

### 《参考解析》

**现场与止血**：商品详情接口 `GET /product/{id}` 被爬虫用随机 ID 刷，DB 的 QPS 从两千飙到两万多、慢查询报警。最快的止血是查不到也往 Redis 塞一个空标记，约定一个固定字符串常量而不是真正的 `null`；上线十分钟 DB 压力就下来了。

**空值缓存的三个坑**：第一，过期时间不能拍脑袋——帖主一开始跟正常缓存一样设三十分钟，结果运营在后台新建商品后，用户半小时内还是看到「商品不存在」，客诉就来了；后来空值只放六十秒，正常数据放半小时，因为空值的核心作用是挡住短时间内的重复攻击，不是长期存储。第二，key 会膨胀——爬虫用随机 ID，每个不存在的 ID 都留一个 key，内存肉眼可见地涨，要靠短过期自然淘汰，并给这类 key 加前缀区分。第三，空值标记别用 `null`——有些序列化方式存进去再读出来会变成字符串 `"null"`，判断就失效了。

**布隆过滤器的四个代价**：不能删元素，商品下架后 ID 还在过滤器里，请求会穿过去查一次 DB，只能靠空值缓存兜底；误判是必然的，它只能减少穿透不能消灭穿透，后面仍要配合空值缓存；要预热，服务重启后过滤器是空的，直接对外服务等于没加，通常在启动时异步加载全量 ID，加载完成前用开关把流量挡在降级逻辑里；扩容麻烦，容量估小了误判率会快速上升，一般按业务总量的三倍预估。

**什么时候值得上**：只有当「不存在的 key 高度分散、无法用空值缓存覆盖」时才有意义。否则空值缓存加入口校验就够了，别为了面试答案给系统加复杂度。

**入口校验与限流**：ID 必须是纯数字且长度在合理区间，格式不对直接返回参数错误；对同一来源做频率限制，超过阈值直接拒绝；内部接口加签名校验，挡住没有业务关系的调用方。这些做完之后穿透量下降绝大部分，因为大部分攻击请求连参数校验都过不了。这部分不酷，但性价比最高。

**回答结构**：先确认是穿透还是击穿，再按成本从低到高排——入口参数校验与限流兜底、空值缓存挡重复请求、布隆过滤器应对高度分散的随机 key，三者是叠加关系而非替代关系；最后补一句空值过期时间的取舍，那才是真正踩过坑的地方。
