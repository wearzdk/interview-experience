### 《核心观点》

1. 这是面试官视角的观察，不是某一家的具体面经：一段时间集中面 Agent 方向的候选人，校招与社招各有一批，问题高度集中。
2. 校招生入门多靠跟教程跑 demo，LangGraph、AutoGen 这类框架用得熟，规划、记忆、反思、工具调用这些概念能说，简历上也有自搭的小助手。
3. 但一问线上场景就容易露怯：默认输入都是干净合规的，不主动想异常——模型幻觉怎么办、工具超时怎么办、工具返回脏数据怎么处理、多轮之后上下文膨胀怎么取舍。
4. 大部分人对上述问题只有「改 Prompt」一个答案，很少去归类坏 case，分辨问题究竟出在提示词、检索召回，还是规划逻辑本身发散。
5. 另一个通病是追求全自动闭环，觉得 Agent 越自主越厉害，不划权责边界，分不清哪些决策风险高、需要拦截交给人审核。
6. 他们擅长把组件拼起来，但缺少风险意识——一个上线的 Agent，稳定性远比流程炫酷重要；很多人甚至没想过，这个业务问题是不是非得用 Agent 解决。
7. 社招多数在业务里落地过 Agent，吃过线上的苦，知道加重试、加校验、做降级；但容易路径依赖，遇到新需求先把旧链路套上去，而不是先评估场景是否适合。
8. 还有一部分社招长期做上层封装，调方案靠反复试 Prompt，对模型输出分布、召回偏差引发的连锁问题说不出底层原因，做久了变成「为了做 Agent 而做 Agent」。
9. 少数人的项目是堆人力堆出来的，只负责其中一小块，没有参与完整链路评估、指标观测与迭代复盘，一问整体效果和失败 case 的收敛方案就讲不清。
10. 面试时并不太在意 demo 多好看、上线项目多庞大，更在意候选人能否客观判断 Agent 的适用边界、清楚它的弱点、知道怎么控制风险——这个能力校招社招都不是人人具备。

### 《参考解析》

**为什么「只会改 Prompt」是危险信号**：Prompt 只能影响模型的先验倾向，解决不了系统性问题。工具返回脏数据属于数据校验层的问题，要在入口做 schema 校验、类型收敛与空值兜底；工具超时与失败属于编排层，要设超时、重试上限、幂等键与降级路径；上下文膨胀属于记忆层，要做摘要、检索式召回与优先级裁剪；幻觉导致的事实错误要靠检索证据与结果校验兜底。把这些都归到 Prompt，说明候选人没有分层定位问题的习惯，线上出故障时也只能盲试。正确的做法是先建可观测性——记录每一步的输入、工具调用、返回与耗时，再按「提示词 / 检索 / 规划 / 工具」四类归因坏 case。

**Agent 的适用边界怎么判断**：先问三件事——任务是否可拆成明确步骤、每一步是否有可验证的成功标准、失败时能否回滚或由人接管。满足前两条、第三条有兜底，才适合交给 Agent；如果任务是确定性的规则匹配或固定流程，用工作流或普通接口成本更低、稳定性更高。反过来，开放域的信息搜集、多工具组合的长任务、需要理解非结构化输入的场景，才是 Agent 的强项。面试里能主动说「这个需求我评估过不适合 Agent」，比硬说自己做过多少 Agent 项目更加分。

**权责边界与人工拦截**：高风险动作要分级——只读查询可以全自动，写操作（下单、发消息、改配置、提交表单）要有确认或额度限制，不可逆动作必须人工确认。工程上体现为工具分级、权限白名单、二次确认、操作审计与回滚预案。这不是保守，而是把「模型可能出错」当成前提来设计。面试官问「哪些决策要交给人」，想听的是具体的分级标准和落地方式。

**指标观测与迭代复盘**：上线不是终点。要有任务成功率、端到端时延、工具调用成功率、人工接管率、单次任务成本这几类指标，按任务类型和模型版本拆分；失败 case 要有回流机制，形成评测集，每次改 Prompt、换模型、加工具都跑一遍回归。能讲清「我负责的那一块在整个链路里的位置、上下游是什么、整体指标怎么变」，比只讲自己写的模块更有说服力。

**给候选人的准备建议**：把项目按「背景与目标—方案选型（为什么用 Agent、为什么不用更简单的方案）—架构与关键取舍—上线后的指标与故障—失败 case 怎么收敛—如果重做会改什么」六段准备，每段都能被追问三层。校招生缺线上经验，可以用压测、故障注入、构造脏数据的方式自己造出线上问题，并在项目里体现；社招要主动跳出路径依赖，讲清楚每个新场景的评估过程，而不是只讲复用。
