### 《参考解析》

**Skill 与 Workflow 的差别在控制权**：Workflow 是开发者预先编排好的确定性流程——节点、分支、重试都写死在代码里，模型只负责其中某些节点的生成；Skill 是交给模型的一份能力描述（做什么、什么时候用、怎么做、有哪些工具与约束），由模型在运行时自行决定是否调用、按什么顺序组合。所以两者的关键差异是「谁决定执行路径」：Workflow 可预测、可测试、成本可控，适合步骤固定、合规要求高的业务；Skill 灵活、能处理开放输入，但行为不确定、需要评测与护栏。工程上常见的做法是外层用 Workflow 兜住关键节点，节点内部用 Skill 让模型决策。

**Trace ID 跨线程传递**：MDC（SLF4J）底层是 ThreadLocal，主线程 set 进去的值在新线程里读不到，线程池复用线程还会导致上下文串号。三种做法：用 `TransmittableThreadLocal`（阿里 TTL）配合 `TtlExecutors.getTtlExecutorService` 包装线程池，提交任务时捕获并回放；或者自己包装 `Runnable`/`Callable`，在 `run` 前把父线程的 MDC map 取出、`MDC.setContextMap` 恢复，执行完清理；Spring 场景可用 `TaskDecorator` 统一处理。`CompletableFuture` 的异步回调、`@Async`、消息消费都要单独覆盖。更完整的方案是接 OpenTelemetry，把 trace context 放进 `Context` 并随 RPC/消息透传。

**模型蒸馏**：用一个能力强的教师模型（或集成模型）的输出训练小规模学生模型。关键是软标签——教师输出的概率分布携带了类别间相似性信息，比硬标签提供更多监督信号，通常配合温度参数软化分布。蒸馏能压缩参数量、降低推理成本，也常用于把大模型能力迁移到端侧或专用小模型；实践中还会混入真标签、做中间层特征对齐（feature distillation）。

**从输入域名到页面展示**：浏览器先查本地缓存与 hosts，未命中则发起 DNS 查询（递归解析器 → 根 → 顶级域 → 权威服务器）拿到 IP；与目标建立 TCP 连接（三次握手），HTTPS 还要做 TLS 握手（证书校验、密钥协商、ALPN 协商协议版本）；然后发送 HTTP 请求，经过 CDN、负载均衡、网关到达服务端；服务端处理（查缓存、查库、渲染）返回响应；浏览器解析 HTML 构建 DOM、解析 CSS 构建 CSSOM、合并成渲染树、布局、绘制，期间发起对 JS、图片、字体的子资源请求并执行 JS；最后完成首屏与加载事件。追问点通常在 DNS 各层缓存、连接复用、TLS 握手开销、关键渲染路径。

**DNS 缓存的层次**：浏览器自身的 DNS 缓存、操作系统缓存（含 hosts 文件与 nscd/systemd-resolved 这类本地缓存服务）、路由器或本地网络缓存、递归 DNS 服务器（运营商或公共 DNS，如 8.8.8.8）的缓存，再往上是权威服务器的 TTL 控制。TTL 越短切换越快但查询压力越大，做灰度切流时常把 TTL 提前调小。

**hosts 文件与路径**：Linux 与 macOS 是 `/etc/hosts`，Windows 是 `C:\Windows\System32\drivers\etc\hosts`。在里面加一行 `127.0.0.1 example.com` 即可把域名指向本机，用于本地调试、绕过 DNS 或验证证书；修改后 Windows 可能需要 `ipconfig /flushdns`，浏览器也可能有自己的 DNS 缓存需要清。

**同域名不同地区解析到不同 IP**：智能 DNS（GeoDNS）按解析请求的来源地域返回就近节点，CDN 用这种方式把用户调度到边缘节点；此外还有 Anycast（同一 IP 宣告在多地，路由层面就近）与全局负载均衡（按健康状态、容量调度）。所以「ping 出来不一样」是设计使然，不是异常。

**CDN 与负载均衡的分工**：CDN 是把内容缓存到离用户近的边缘节点，命中直接返回、未命中回源，解决的是「距离与带宽」；负载均衡是把请求分发到后端的多个实例，解决的是「容量与可用性」，分四层（LVS，按 IP/端口转发）与七层（Nginx/Envoy，按路径、Header 路由）。实际链路通常是 CDN → 四层 LB → 七层网关 → 服务实例。

**HTTP 版本的协商**：HTTPS 下在 TLS 握手的 ClientHello 里通过 ALPN 扩展列出支持的协议（h2、http/1.1），服务端选定后在握手中确认，之后的请求直接按选定版本通信；HTTP/3 则在响应头用 `Alt-Svc: h3=":443"` 告知客户端可改用 QUIC，后续连接再升级。明文 HTTP 没有 ALPN，只能用 `Upgrade: h2c` 头协商（实际部署很少启用），或者客户端与服务器事先约定直接讲 HTTP/2；绝大多数明文场景仍是 HTTP/1.1。

**HTTPS 解决的三件事**：机密性（传输内容加密，中间人看不到明文）、完整性（MAC/AEAD 校验，篡改会被发现）、身份认证（证书链验证服务端身份，防假冒与中间人）。它不解决「服务端本身是否可信」和「内容是否合法」，也不隐藏访问的域名与 IP。

**HTTPS 的密钥建立**：TLS 1.3 中客户端发 ClientHello 带密钥共享（ECDHE 公钥），服务端回 ServerHello 带自己的密钥共享，双方用 ECDHE 算出相同的会话密钥；证书与签名用非对称算法（RSA/ECDSA）证明服务端身份。之后的业务数据全部用对称加密（AES-GCM 或 ChaCha20-Poly1305）传输，因为对称加密快几个数量级。非对称只用于身份认证与密钥协商，且 ECDHE 提供前向安全——长期私钥泄露也解不开历史流量。TLS 1.2 时代常见的 RSA 密钥交换没有前向安全，这也是全面转 ECDHE 的原因。

**排序算法的场景选型**：数据量小（几十个以内）用插入排序，常数小；通用场景用快排（原地、平均 O(n log n)，但最坏 O(n²)，需随机化或三数取中）或 TimSort（归并加插入，稳定，适合部分有序的真实数据，Java 与 Python 的内置排序都用它）；要求稳定就选归并；数据范围小且是整数用计数排序或桶排序，可以做到线性；只要前 K 大用堆，O(n log k)；内存放不下用外部排序（分块排序加多路归并）。回答时把「数据规模、是否稳定、内存限制、是否部分有序」四个条件带上，比背复杂度表更能体现工程判断。
