### 《参考解析》

**AI 编程工具与模型差异怎么答**：这类题考察的是"你真的用过并且有判断"，不是背工具名。可以按三个维度讲差异：一是长上下文与仓库级理解（有的模型能一次吃下多个文件、跨文件改引用，有的只适合单文件补全）；二是指令遵循与工具调用稳定性（能不能一次给对 diff、会不会擅自改无关代码、调用格式错误率高不高）；三是推理型与快模型的取舍（复杂重构用推理型、写样板和重命名用快模型，成本与延迟差好几倍）。`plan` 的评估要说清是可验证的：拆出来的步骤有没有覆盖边界与异常分支、每一步能不能落成一个能跑的检查点（编译通过、单测通过、能起服务），而不是"读起来挺合理"。

**AI 生成的代码怎么验证**：按成本从低到高排：编译与类型检查 → lint/静态扫描 → 单测或最小复现脚本 → 逐行读 diff（重点看异常分支、并发、资源释放、SQL 与索引、鉴权）→ 在灰度环境跑影子流量对比。给一个具体例子最有说服力，比如"AI 生成的批量查询忘了分页，压测时内存打满，我补了游标分页并加了单测"。要敢于说"AI 写的代码我从不直接合并，一定会逐行读一遍再改"。

**RAG 项目的讲法**：按链路讲——文档切分（按语义/标题层级、chunk 大小与重叠）、向量化模型选型、召回（向量 + BM25 混合、按业务词表加同义词）、rerank、上下文拼装与引用来源、以及最关键的评测（命中率/召回率、答案忠实度、人工 badcase 集）。单人项目被问"设计方案有谁审过"不用硬撑，可以答：写了设计文档在组内评审、关键选型拉了资深同事 review、上线后按 badcase 迭代；把"没有评审"说成"所以我自己补了哪些验证手段"也站得住。

**多线程与核心线程数**：先说线程池参数（corePoolSize、maximumPoolSize、keepAliveTime、workQueue、threadFactory、拒绝策略）和任务提交顺序，再说核心线程数怎么定——CPU 密集型经验值是核数 + 1，IO 密集型是核数 ×（1 + 等待时间/计算时间），但这两条只是起点，最后一定要靠压测看 QPS、P99 和队列积压来校准。只背公式不提质监会显得很空。

**几 MB 大字段的设计改善**：先判类型。如果是不可检索的大文本/大对象，正确做法是把内容挪出主表——要么垂直拆到扩展表、要么直接放对象存储（OSS/S3）只在主表留 URL 与元信息；如果一定要存库里，注意 MySQL 的超长字段会走行外溢出页（off-page）存储，建议用 `TEXT/BLOB` 而不是 `VARCHAR(超大)`，并避免 `SELECT *` 把大字段带出来（只查需要的列或做延迟加载）。其他可谈的点：压缩后再存、用 protobuf 之类紧凑序列化、读写分离与冷热分层、禁止对大字段建索引。

**反问与岗位信息**：面试官回答的内容值得记一下——岗位是做集团内部系统的后端 Java 开发，目前项目里暂时没有 AI 成分，但明年在跟客户沟通、后续机会不小；线上一次把后面的面试官都叫来了，所以没有二三面；转正机会无法保证。实习面试里"能不能转正"是个该问的问题，但答"无法保证"很常见，判断时更要看岗位是否有真实业务、mentor 是否带人。
