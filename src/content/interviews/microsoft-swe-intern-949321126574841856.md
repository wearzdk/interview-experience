### 《面试题目》

1. 你实习主要在干什么？讲一下 AIGC 生成广告的链路，并在白板上设计。

4. 为什么做 RDMA 的解耦？意义在哪？讲一讲这里的问题。
5. 算法：给定数组如 [1, 3, 5, 5] 和一个最大处理次数 maxBatchCount，选择一个 batchSize，每个元素按 `ceil(a_i / batchSize)` 次处理，求满足总次数不超过上限的最大 batchSize。

7. 你说你做 RAG，什么是 hybrid search？为什么不用纯语义检索？
8. 关键词检索的原理是什么？什么是 BM25？为什么词频低打分也会变高？

11. 算法设计：给一串用户事件（如 `e1 u1 click`、`e2 u2 close`），生产环境下如何设计一个可用的接口，任意获取一个用户某种行为的次数？
12. 你把 map 放到全局变量，这样好吗？线程安全问题怎么解决？

### 《参考解析》

**batchSize 的二分。** 对固定 batchSize，总处理次数是 `sum(ceil(a_i / batchSize))`；batchSize 越大，次数单调不增，因此可以二分答案。下界是 1，上界取数组最大值（再大也不会减少次数），每次判断次数是否不超过 `maxBatchCount`，找满足条件的最大 batchSize。帖主把下界写成 0 导致出错：batchSize 为 0 时除零，且语义上不存在「每批 0 个」。二分写法用 `lo = 1, hi = max(a)`，`mid = lo + (hi - lo + 1) / 2`，满足则 `lo = mid`，否则 `hi = mid - 1`。

**BM25 的分数由三部分相乘。** 词频项做饱和处理，词频从 1 增到 2 的收益大于从 10 增到 11；逆文档频率项让罕见词权重更高；文档长度归一化让长文档不因词多而占优。词频低却高分，常见原因是这个词在整个语料里非常罕见（IDF 高），或者文档很短（长度归一化加分）；如果查询里只有这一个词，它在文档中出现一次就足以让分数领先。回答时把「词频饱和、IDF、长度归一化」三件事分开说，再补一句参数 `k1`、`b` 的作用。

**hybrid search 与纯语义的取舍。** 纯向量检索擅长同义改写、口语化描述，但对精确型号、错误码、专有名词不敏感；关键词检索（BM25）对精确匹配强，却无法处理「意思相近但用词不同」。混合检索分别召回再融合，常见融合方式是 RRF（按排名取倒数求和）或校准后的加权。是否值得上混合，要用固定查询集对比单路与混合的召回率、延迟和成本，不能默认混合更好。

**事件计数接口的设计。** 逻辑模型是「用户 + 行为 → 次数」，最小实现是 `Map<userId, Map<action, count>>`；生产环境要考虑并发写入、内存上限、持久化与查询延迟。单机可用 `ConcurrentHashMap` 加 `LongAdder`，按用户哈希分片降低竞争；多机部署把计数放进 Redis（`HINCRBY user:{id} action 1`）或 ClickHouse / 流处理系统，写入走消息队列削峰，查询走缓存。接口设计成 `GET /users/{id}/actions/{action}/count`，写入侧保证幂等（事件 id 去重），并明确计数的时间窗口（全量、当日、近 7 天）。全局 map 的问题不只是线程安全：无界增长会 OOM、进程重启丢数据、多实例之间不一致。

**RDMA 解耦这件事怎么讲。** 先讲动机：Redis 的网络栈在通用内核路径上开销大，RDMA 把数据通路下沉到网卡，减少拷贝与 CPU 占用；再讲工程问题：RDMA 与 Redis 的事件循环、内存注册、连接管理耦合，改一处影响面大，所以把传输层解耦成可替换模块；最后讲验证：功能对拍、延迟与吞吐对比、异常注入（断链、重连、内存注册失败）。面试官追问「意义在哪」，要落到可测量的收益和可维护性，而不是「这是个新技术」。

**动态加载的可靠性验证。** 动态加载模块要验证四件事：符号解析与版本兼容（依赖缺失、ABI 不一致时明确报错）、加载失败可回滚（旧模块继续服务）、热更新期间的请求一致性（引用计数或读写锁，避免卸载时仍有调用）、资源释放（句柄、内存、线程）。测试上用故障注入制造缺符号、坏二进制、并发加载卸载，再看进程是否稳定、错误是否可观测。
