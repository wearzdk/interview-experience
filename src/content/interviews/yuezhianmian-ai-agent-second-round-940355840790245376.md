### 《参考解析》

**代码生成链路要按「每步的输入输出 + 失败信号」讲，而不是讲功能列表。** 一条能落地的链路是：需求澄清（补齐模糊点）→ 代码库上下文构建（检索相关文件、接口签名、约定）→ 计划与任务分解（可执行的任务图）→ 生成 → 机械校验（编译、lint、单测）→ 修复循环 → 交付与归档。每个环节都要能说清输入输出、以及「什么情况下判定它失败」：例如上下文构建失败是召回为空或召回了过期文件，修复循环失败是连续 N 轮校验不过。把失败信号显式化有两个好处：面试官会认为你真的上过线，以及整个链路才可能被观测和自动重试。

**长流程的核心不是更大的窗口，而是把状态挪出上下文。** 1M 上下文也装不下一个中等仓库加全流程历史，工程解法是四个动作：分层索引（文件树、符号表、调用图、AST 摘要，按需检索而不是全量塞）、任务级分段（每段只带该段需要的上下文 + 全局计划的结构化摘要）、产物落盘（中间产物只留路径与摘要，正文放对象存储或工作区）、以及跨段引用（用符号和文件路径做锚点，让模型按需回查）。断点恢复的做法是每步结束写检查点：任务图、已完成步骤、产物版本、工具调用结果引用、以及当时的工作区版本。恢复时不能直接信检查点，要先校验工作区是否与检查点一致（文件 hash 或版本号），不一致就回滚或重做该步；再靠幂等键跳过已完成的写操作；兜底策略是退化为「重跑该步 → 重跑整段」，并把降级原因记录成指标——没有这条兜底，恢复失败会变成任务永久卡死。

**多 Agent 抢同一个文件，优先改工作划分，锁是最后手段。** 最有效的办法是让写集不重叠：按模块或文件分区，不同 Agent 负责不同的目录，公共文件（配置、接口定义、路由表）指定单一写入者或走串行提交。无法避免并发时，乐观并发（带版本号的 CAS，冲突就重取上下文重做）通常优于悲观锁，因为冲突是低频的、而锁会一直占资源。一定要用锁就用带 TTL 的租约锁：Redis 的 `SET key value NX PX ttl` 加唯一 value，释放时用 Lua 校验持有者再删（防误删别人的锁），执行时间可能超过 TTL 时要续租，粒度到文件而不是整个仓库——整仓级锁会让并行度归零。Redlock 的争议要在点上：它依赖多个独立节点与时钟假设，在故障切换与时钟漂移下不能提供严格互斥，所以对「错了会坏数据」的场景，正确做法是让操作本身幂等或改用强一致的协调服务，而不是把可靠性全押在锁上。

**Codebase Memory 与检索的答案在「增量维护 + 检索时机 + 效果度量」。** 初始化做一次全量扫描建索引（符号、依赖、目录约定、单测位置），之后走增量：文件监听或提交钩子在变更时更新局部索引，并定期做一次全量校正以防漂移（删文件、重命名最容易让索引腐烂）。检索的触发时机应该是关键节点而不是每一步：需求定位时找相关文件、生成前拉接口与约定、修复时按报错找调用方。调优抓手包括查询构造（用符号名、报错文本、变更文件当种子）、召回粒度（函数或类优于整文件）、重排去重、以及把文件路径与行号带进上下文让模型能引用。效果要有指标：正确文件是否进 Top-K 的命中率、下游编译与测试通过率、以及平均 token 消耗；「效果提升多少」这类问题必须给出对照口径，否则等于没调。

**幂等 key 为什么不能交给模型生成：模型输出不确定，同一个逻辑任务可能得到不同的 key。** 幂等的本质是「同一业务意图映射到同一个 key」，所以 key 必须由代码用稳定输入算出来，比如用户 ID + 任务类型 + 规范化后的输入指纹（关键字段排序后哈希）。让模型生成会同时踩三个坑：同一请求两次调用可能给出不同 key（幂等失效）、模型可能被输入里的内容影响而编造（prompt 注入面）、以及不可解释不可审计。另外 key 只有落在有唯一约束的存储上（数据库唯一索引或带 TTL 的分布式键）才真正防重，光生成 key 不校验等于没做。

**数据库与缓存的基础题，答法要「结论 + 为什么 + 代价」。** B+ 树的形状是：非叶节点只存键和指针，所以单页能放更多键、树更矮（千万级数据通常三层左右），叶子节点按顺序双向链表连接、天然支持范围扫描与排序，聚簇索引的叶子就是数据行，二级索引的叶子存主键因此需要回表。不用 B 树是因为 B 树的非叶节点也存数据，单页能容纳的键变少、树更高，范围查询还要在树里中序回溯、随机 IO 更多。「索引存在硬盘还是内存」的正确答法是「持久化在磁盘上，访问时以页为单位读进 buffer pool 缓存，命中内存就快、不命中就走磁盘」——这句话同时解释了为什么索引设计要关注页大小与顺序访问。缓存三兄弟：穿透是查一个不存在的 key，用空值缓存（短 TTL）加布隆过滤器挡住；击穿是热点 key 过期的瞬间流量全打到数据库，用互斥重建、逻辑过期加后台刷新，或干脆不设过期只做更新；雪崩是大量 key 同时过期或缓存整体不可用，用过期时间加随机抖动、多级缓存和熔断限流。

**高并发 Agent 调度、可观测与降级是同一件事的三个面。** 调度上要区分交互式与批处理：优先级队列让交互请求优先，长任务限制并发数并配 token 与步数预算，按用户或租户做配额防止单点打爆全站，同时要防止长任务饿死短任务（老化或时间片）。限流要分层：入口请求限流、模型调用侧的并发与 QPS 限制、工具侧的调用配额。可观测上，一条 Trace 要串起「请求 → 计划 → 每一步模型调用（模型、提示词版本、token）→ 工具调用（名称、参数摘要、耗时、错误码）→ 产物与最终状态」，指标分模型侧（token、时延、失败率、重试率）、工具侧（成功率、P95、超时率）与业务侧（任务成功率、人工介入率），告警阈值按分位数与分层设而不是拍绝对值。排查顺序是先定位**第一个**异常环节而不是最后一个报错，再看时间线上有没有变更（模型、提示词、工具版本）；区分模型问题与工具问题最直接的办法是固定输入换模型或换工具重跑。降级要预设：模型侧挂了就熔断并切备用模型或退化成模板化流程，工具侧挂了就重试加幂等再熔断并提示用户，任何降级都要打点，否则系统会长期在降级状态运行而没人发现。

**LRU Cache 手撕，重点是结构、追问与并发三块。** 基础实现是哈希表加双向链表：哈希表定位节点，链表维护访问顺序，命中就把节点移到头部，插入时超容量就删尾节点，get / put 都是 O(1)。泛型用模板参数加哈希函数即可，注意 key 需要可哈希。支持过期时间的常见做法是节点带过期时间戳，get 时惰性判断（过期就当未命中并删除），另配定期清理或按过期时间排序的结构（最小堆、时间轮）做主动淘汰；这里有个容易翻车的细节：容量满时如果只按 LRU 淘汰，可能先淘汰掉没过期的项却留着已过期的项，所以要先扫过期项。线程安全上要认清一点——LRU 的 get 会改链表结构，所以「读」也是写，读写锁收益有限；更实际的做法是分段锁（按 key 分段，思路接近 ConcurrentHashMap）或单锁加极短临界区，实在要求高并发就退化成近似 LRU（采样若干项淘汰最旧的），用一点命中率换掉全局锁。
