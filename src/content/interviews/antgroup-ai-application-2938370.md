### 《面试题目》

4. 如果工具调用失败，模型开始编造结果，怎么处理？
5. 你们整体上怎么做防幻觉？

7. JSON 格式符合 Schema，但内容判断错了，怎么发现？

9. 这个流程是多轮交互的 ReAct，还是围绕单个简历的一次性任务？什么时候触发？
10. 项目上下文大概有多大？遇到输入或输出过长时怎么处理？
11. 脱离项目，你对 Agent 的上下文管理有哪些了解？
12. 如果压缩把「不能修改生产配置」变成了「修改生产配置」，并写入长期记忆，怎么发现和避免？
13. 设计一个支付失败诊断 Agent：输入自然语言或订单信息，输出失败原因和证据，你会怎么做？

### 《参考解析》

**Tool Calling 的准确性**：三层保障。第一层是工具定义本身——参数名、类型、枚举、必填项写清楚，把「什么情况下该调这个工具」写进描述，避免模型凭名字猜。第二层是调用前校验，参数不合法直接返回结构化错误让模型重试，而不是把错误参数发给下游。第三层是调用后核对，把工具返回与已知事实比对（订单号是否存在、金额是否与库内一致），不一致就标记为不可信。帖主被追问「规则有多少条」时说明工程上确实需要可枚举的规则集，而不是靠提示词嘱咐模型「不要编」。

**工具失败后模型编造结果**：根因是模型在缺信息时倾向补全。处理方式是让「没有结果」成为一种明确的状态：工具失败返回带错误码的结构化结果，提示词规定「失败时必须如实说明并给出下一步」，编排层检测到失败就中断生成或转人工，而不是让模型继续写。事后要有可观测性：记录每次工具调用的入参、出参、耗时与失败原因，抽查模型是否引用了不存在的返回。

**Schema 对但内容错怎么发现**：格式校验只能保证可解析，语义要靠业务校验。做法包括：字段间的交叉校验（金额与明细之和、时间先后、状态与操作是否匹配）、与权威数据源比对（回查订单、账户）、规则引擎兜底（金额阈值、黑名单、频次）、以及抽样人工复核。回答时举一个具体例子，例如「模型抽取的退款金额与订单实付不一致，用订单金额做基准校验」。

**ReAct 与一次性任务的区别**：一次性任务是把输入整体交给模型，输出结构化结果，触发点是事件（提交、上传）；ReAct 是多轮循环，模型根据观察决定下一步调什么工具，适合信息分散、需要逐步收敛的场景。判断标准是「路径是否确定」：路径固定就用 Workflow 编排，路径随中间结果变化才用 ReAct。

**上下文压缩改写语义的风险**：压缩会丢限定词，而限定词往往是否定句与约束条件。防护手段是分层记忆：把「硬约束」（权限、禁止操作、金额上限）单独存成结构化字段，不参与自然语言压缩；压缩后的摘要与原摘要做一致性校验（关键实体、否定词、数值是否保留）；写入长期记忆前要求模型输出「这条记忆的来源与生效范围」，并允许人工审核。帖主被问的「把不能修改生产配置变成修改生产配置」正是否定词在压缩中被吞掉的典型。

**支付失败诊断 Agent 的设计**：输入是自然语言描述或订单号，输出是失败原因、证据链与建议动作。整体应是「Workflow 骨架 + 局部 ReAct」：先做意图识别与信息补全（缺订单号就追问），再按支付链路顺序排查（收银台 → 收单 → 交易 → 渠道 → 银行/账户），每一步是确定性的查询工具，只有「异常原因不明、需要多轮假设验证」的环节才交给模型自主决策。

**单 Agent 还是 Multi-Agent**：支付链路长、领域知识分散、权限边界清晰，适合 Multi-Agent。单 Agent 的问题是一个提示词里塞不下所有领域的排查手册，且权限无法按领域收窄。Multi-Agent 的代价是链路变长、错误会累积，因此需要一个 Supervisor 做路由与结果汇总，而不是让子 Agent 互相调用。

**分层职责**：Supervisor 负责理解问题、判断该找哪个领域、汇总证据并给出结论；Planner 把「诊断失败原因」拆成可执行的排查步骤；Executor 调用具体工具（查订单、查渠道返回码、查账户流水）。业务排查能力应下沉到各领域的子 Agent 或工具集里，由该领域的团队维护，Supervisor 只持有「什么症状找谁」的路由表。

**权限设计**：使用者侧按数据权限收窄（只能查自己权限范围内的订单、敏感字段脱敏）；Agent 内部按最小权限给每个子 Agent 分配工具，例如诊断 Agent 只读、不允许发起退款；所有写操作与对外动作必须经过人工确认。权限判断放在工具层而不是提示词层，因为提示词可以被绕过。

**子 Agent 如何判断故障落在哪个模块**：靠「症状到模块」的映射表加证据。先看错误码与返回信息（渠道返回码、超时、风控拦截），再看链路日志的时间戳定位卡在哪一跳，最后用排除法收敛。这要求每个模块提供标准化的健康查询工具，而不是让模型读原始日志猜。

**本体与知识图谱**：本体是对领域概念及其关系的形式化定义（类、属性、关系、约束），知识图谱是按本体填充的实例数据。本体解决「大家说的是不是同一件事」，知识图谱解决「具体有哪些实体、它们怎么连」。构建路径是先梳理核心实体与关系（订单、支付单、渠道、账户、失败原因），再定义约束与枚举，最后从业务系统与文档中抽取实例。

**大促下的支付架构**：核心是容量、隔离与降级。容量上做压测与弹性扩容、热点账户拆分、异步化与削峰；隔离上按业务线做资源与线程池隔离，避免一个渠道拖垮全局；一致性上用最终一致加对账补偿；可观测性上要有全链路追踪与实时大盘。降级要分级：先降非核心功能（营销、积分、推荐），再降可选支付方式，最后才是限流与排队。关闭某些银行卡选项要谨慎——它直接影响用户能否付款，应作为最后手段并配合明确提示与替代方案。
