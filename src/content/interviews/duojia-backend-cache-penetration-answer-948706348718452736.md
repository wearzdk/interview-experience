### 《面试题目》

1. 缓存穿透怎么解决？
2. 缓存预热解决的是穿透吗？
3. 接口层应该怎么拦？
4. 空值缓存的过期时间设多长？设长了会有什么问题？
5. 布隆过滤器有什么局限？删除和重建怎么处理？
6. 如果刷你的请求 id 格式完全合法、只是不存在，你怎么办？
7. 怎么提前发现这类攻击？

### 《参考解析》

**第一次答错在概念混用。** 穿透是查一个根本不存在的数据，请求绕过缓存直奔数据库；击穿是某个热点 key 过期瞬间，大量并发压到数据库；雪崩是大量 key 同时失效。缓存预热对应的是雪崩与击穿，和穿透不是一个问题。概念说不清，后面的方案就会像在背八股。

**第一层：接口层拦住明显非法的请求。** 订单 id 必须是纯数字且长度固定、商品 id 必须符合生成规则、分页参数有上限——格式不对直接返回。这一步能挡掉脚本乱刷的一大半，成本最低，但很多人一上来就聊布隆过滤器，反而跳过它。

**第二层：空值缓存，重点是短 TTL。** 查不到也写一个空标记，过期时间设几分钟而不是半小时。作者踩过的坑是：空值与正常数据都设成半小时，运营在后台补录数据后前端死活查不到，被当成接口故障。改成短 TTL 后，最坏情况只是几分钟的延迟不一致；同时写入时要主动删除空值 key，而不是干等过期。另一个坑是内存：被刷的是完全随机 key 时，每次都写空值等于把 Redis 当成攻击者的记事本，所以这层只对「id 格式合法但不存在」的请求使用，随机 key 靠第一层挡。

**第三层：布隆过滤器做前置判断。** 它有两个必须说清的点：有假阳性、没有假阴性——说不存在就一定不存在，说存在可能是误判，因此它只能挡请求、不能替代真实查询；删除很麻烦，标准实现不支持删除，数据下线后位还是 1，常见做法是每天凌晨用全量数据重建一次，重建期间用双 buffer 切换，避免出现「过滤器为空、所有请求放行」的窗口。

**追问「id 合法但不存在」是这场的分水岭。** 空值缓存只能挡住同一批 key 的重复请求，对方每次换新 id 时缓存命中率为零，此时只能靠限流与风控：在网关对单 IP、单用户的查询频率做限制，对「查不到」的比例做监控——正常情况下不存在的查询占比很低，一旦异常升高基本可以判定是有人在刷。

**监控要盯命中率，不能只盯 QPS。** 作者吃过一次亏：只监控接口 QPS 与数据库慢查询，数据库快挂了才发现，因为 QPS 看着并不高，只是缓存命中率悄悄掉下去了。加一条「缓存命中率低于阈值即告警」之后，才算是提前能看见。

**总结成一句话。** 缓存穿透的答案本身不难，难的是知道每种方案在什么情况下失效：接口校验永远要做，空值缓存作为默认手段，布隆过滤器只在数据量大且 id 空间可枚举时才上；上来就堆三个方案，反而说明没想清楚每个方案的边界。
