### 《参考解析》

**幂等框架怎么讲清楚**：面试官连问「组件还是进程、一台还是一组、zone 怎么路由」，是在确认真实性。一个典型的服务端幂等框架形态是：以 SDK / 拦截器（AOP 切面）形式嵌在业务进程内，不是独立服务——业务方法加注解，切面在调用前先查幂等记录，调用成功后落记录。存储用 Redis（快、带 TTL）加数据库兜底（持久化），记录内容包含幂等键、状态（处理中 / 成功 / 失败）、结果快照、过期时间。量级回答要给真实数字（日均调用量、峰值 QPS），并说明容量规划（Redis 内存占用 = 键数量 × 单键大小 × TTL 窗口），这些细节才是面试官判断「你参与了多少」的依据。

**幂等 ID 的拼接与阈值**：幂等键一般由「业务标识（应用名 / 接口名）+ 业务参数（用户 id、订单号、请求摘要）」拼接而成，用来在全局唯一标识一次业务请求。为什么超过 64 字节降级 MD5：Redis 的 key 与存储都有成本，长 key 既占内存又增加网络传输，而且很多系统对 key 长度有隐性约束（哈希槽计算、日志可读性）。降级方式是对拼接结果做 MD5 取摘要（可选加盐 / 命名空间前缀），把不定长压成固定 32 字符。至于「为什么是 64 不是 128 或 32」——这类问题的正确答案是「阈值来自压测与容量估算」：统计线上幂等键长度的分布（P99 落在哪），选一个能覆盖绝大多数、又不让内存暴涨的值，并说明如果换成 32 会有更多键触发降级、换成 128 则收益递减。要能讲出 MD5 碰撞的现实风险与缓解手段（前缀分桶、碰撞时以业务唯一约束兜底、双写校验），别只说「MD5 不会碰撞」。

**策略模式与 if/else**：用策略模式回查（比如按幂等记录的不同状态走不同处理、不同的回查方式）的收益是：新增一种状态 / 渠道时只加一个实现类，不改已有分支（对扩展开放），并且每个策略可以单独测试。if/else 的代价是分支会随业务增长不断膨胀、圈复杂度升高、容易漏改。判断标准是「变化频率与维度」：一到两个稳定分支用 if/else 更直观；分支多、会持续增加、每个分支逻辑较重时上策略模式。别把「用了设计模式」当目标——过度设计同样是问题。

**设计模式与单例**：Java 常见模式按用途分——创建型（单例、工厂、建造者、原型）、结构型（适配器、装饰器、代理、门面、组合）、行为型（策略、观察者、模板方法、责任链、状态）。单例要讲清五种写法的演进：饿汉（类加载即初始化，简单但可能浪费）、懒汉加 synchronized（性能差）、双重检查锁 + volatile（为什么必须 volatile：防止指令重排导致拿到未初始化对象）、静态内部类（延迟加载且线程安全，推荐）、枚举（防反射与反序列化破坏，最稳）。破坏单例的手段是反射、序列化、克隆，对应的防御就是枚举或 `readResolve`。

**手撕 k 个一组翻转链表**：思路是分组处理——先走 k 步确认这一组是否够长（不够就保持原样返回），记录组的前驱、首、尾与后继，把这一组内部反转（头插或三指针），再把它接回前驱与后继，然后前驱更新为这一组的原首节点继续下一组。边界是最后一组不足 k 个、k = 1、以及头节点所在组翻转后 head 要更新。写成哑结点 + 循环的版本最不容易错；变形题还有「不足 k 个也翻转」「两两交换」「区间翻转」，本质都是同一套指针操作。

**这一轮的特点**：面试官把一个问题连续追问了十二轮——从「是什么」问到「量级」「部署形态」「参数为什么这么定」。这是最典型的「验证真实性」打法：如果你只参与了外围，问到第三四层就会答不上来。应对方式是提前给自己的项目做「十层自问」：它是什么、多大、怎么部署、为什么这么设计、参数怎么来的、出过什么故障、有没有替代方案、你怎么验证的。作者这场面试的信息量也说明，大厂外包 / 子公司类的实习面试同样会在项目细节上深挖，不能因为「只是实习」就准备不足。
