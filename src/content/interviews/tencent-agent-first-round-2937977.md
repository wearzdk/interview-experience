### 《面试题目》

1. 介绍项目架构。为什么组合使用 LangChain 和 LangGraph？技术选型依据是什么？
2. 系统如何判断生成方案不合格？审核指标如何确定，审核结果怎样反馈到执行链路？
3. 项目建设了哪些可观测能力？能否通过运行记录还原任务执行过程？
4. 主 Agent 调用子 Agent 时，传递哪些上下文？内容过长如何处理，压缩机制采用自研还是框架能力？
5. 实际做过哪些 Token 优化？提高 KV Cache 命中效率，还能采用哪些方法？
6. Skill 被折叠或移出上下文后，对缓存复用有什么影响？是否比较过保留与移除正文的实际成本？
7. 模型通过工具调用执行动作，Skill 的调用机制如何实现？一个 Skill 对应单个工具还是多个工具？
8. 项目使用了哪些模型？针对方案审核，是否建立了独立评测？
9. 一次请求输入更短，但缓存失效导致费用反而增加，如何定位并验证原因？
10. 审核 Agent 与生成 Agent 使用同一个模型，如何识别二者可能存在的共同盲点？

### 《参考解析》

**LangChain 与 LangGraph 的分工要讲清「组件库」与「编排层」**：LangChain 提供模型、检索器、工具、输出解析这些可替换的组件与统一接口；LangGraph 负责把多步流程表达成带状态的图——节点是动作，边是转移，支持条件分支、循环、检查点与中断恢复。选它的理由是流程里有回退与重试（审核不通过要回到生成）、需要持久化中间状态、需要人工介入点；如果只是线性的「检索—生成」，直接用 SDK 更简单。技术选型要能说出替代方案（直接调 SDK、Temporal 这类工作流引擎、自研状态机）与放弃原因。

**审核要可判定、可回传**：判定指标分硬规则与模型评分两类——硬规则（格式、字段完整性、事实引用是否存在、数值范围）用程序判，模型评分（相关性、可执行性、风险）用 rubric 加少量示例，输出结构化结果与理由。审核结果回传执行链路的方式是「带原因的失败」：把未通过的条目与修改建议作为新消息追加到生成节点的输入，限制重试次数，仍不通过则降级为人工复核或返回带标记的结果。指标本身要能被评测：固定一批样本，人工标注通过与否，算审核器与人工的一致率（准确率、召回、误杀率）。

**可观测的最低要求是「能回放一次任务」**：每次任务一个 trace，节点级 span 记录输入摘要、模型与参数、token 用量、耗时、工具调用与返回、审核结论；日志带 trace id 与步骤序号，产物版本化存储。有了这些，才能回答「为什么这次输出不对」——是检索没给对、模型没按指令、还是审核放过了。指标上盯 P50/P95 步数、每步 token、失败率与重试率。

**主 Agent 传子 Agent 的上下文要「最小充分」**：传任务目标、约束（格式、边界、禁止项）、必要的事实片段与工具权限，不传整段对话历史。压缩通常分层——对历史做结构化摘要（目标、已确认事实、已完成步骤、待办），工具结果只留关键字段与引用，长文档放外部存储按需读取。框架能提供消息裁剪与摘要节点，但「哪些字段必须保留」是业务判断，一般要自研；回答时说清哪部分是框架能力、哪部分是自己写的。

**KV Cache 的前提是前缀逐字节稳定**：把系统提示、工具表、Skill 目录放在最前且保持不变，动态内容（时间、用户信息、检索结果）一律追加在后面；避免在前缀里插入时间戳、随机 id、未排序的列表；多轮对话只追加不修改历史；同一会话固定模型与参数。此外可以缩短输出、把重复的固定说明移到前缀、对批量子任务复用同一前缀、按缓存 TTL 安排请求密度。衡量方式是看用量里的 cached tokens 占比与单位任务成本，而不是凭感觉。

**Skill 折叠与缓存是一对矛盾**：把 Skill 正文移出上下文能省 token，但会让前缀变化、后续请求的缓存全部失效。是否划算要做对照：设 Skill 正文为 S，缓存命中时每 token 的价格约为未命中的十分之一，若折叠后同一前缀的请求次数足够多，省的 S 抵不过缓存失效的损失，就不该折叠；更好的做法是把 Skill 正文放在稳定前缀的末尾、按会话固定加载集合，会话内不改动。答这一题要给出可计算的判据，而不是「看情况」。

**Skill 与工具是多对多**：一个 Skill 往往编排多个工具（例如「生成周报」要查数据、算指标、套模板、发消息），也可能只对应一个；工具是可执行的原子能力，Skill 是完成一件事的流程知识与约束。实现上 Skill 以指令加脚本的形式注入，脚本内部调工具，模型只负责选择 Skill 与填参数。

**输入更短但费用更高，问题几乎一定在缓存**：定位方法是按请求比对前缀哈希（对系统提示与工具表做规范化后哈希），看命中率与 cached tokens 是否下降；检查是否有动态内容被插到前缀、工具列表顺序是否变化、Skill 集合是否按会话漂移、是否切了渠道或模型导致缓存池不共享。验证要拿两组请求做对照：固定前缀跑一批、故意插入动态字段跑一批，比较单位 token 成本。

**同模型生成与审核的共同盲点靠「换视角」发现**：同一模型对同一类错误有稳定的偏好，自审容易放过。可行手段包括换模型或换提示做交叉审核、引入规则与外部工具校验（编译、单测、schema 校验、检索比对）、用另一套 rubric 与少样本示例、对高价值样本做人工抽检并回流成评测集。度量上要看「审核通过但人工判错」的比例，这个数字才反映盲点大小。
