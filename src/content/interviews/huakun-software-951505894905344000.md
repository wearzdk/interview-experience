### 《参考解析》

**Agent 的记忆要分层**：短期记忆是当前会话的消息序列，受上下文窗口约束；长期记忆是从会话中抽取的稳定事实（用户偏好、项目约定、历史结论），需要落盘并可按相关性检索。工程上通常分三层：会话内上下文（直接拼进 prompt）、工作记忆（当前任务的中间状态，如计划、已完成的步骤）、长期存储（向量库或数据库 + 结构化字段）。检索不能只靠向量相似度，要混合关键词、时间衰减与显式标签（用户、项目、类型），召回后再做重排与截断，避免把无关记忆塞进上下文反而干扰模型。

**保存格式与可编辑性**：每轮全量写 JSON 的做法在会话变长后会迅速膨胀，且并发写容易损坏，合理做法是追加式日志 + 定期整理：原始消息按行追加（JSONL），抽取出的记忆单独存结构化记录（id、类型、内容、来源、时间、置信度），需要时再生成索引。用户应当能找到并编辑这些文件——这是可解释性的一部分，Codex、Claude Code 一类工具把配置与记忆放在用户目录的纯文本文件里，好处是可用编辑器直接改、可进版本控制、出问题能人工修正；代价是要处理格式校验与并发冲突。若记忆只在数据库里，就必须提供查看、修改、删除的界面，否则用户无法纠正错误记忆。

**大型 Agent 的整体流程**：接收输入 → 组装上下文（系统提示、工具表、检索到的记忆、当前任务状态）→ 模型决策（直接回答或调用工具）→ 执行工具并回填结果 → 判断是否继续循环 → 输出并写回记忆。工程上的关键点不在循环本身，而在上下文管理与错误处理：工具结果要截断与结构化，长任务要落盘检查点以便恢复，工具失败要把错误原文回传给模型而不是吞掉，循环要有步数与成本上限。

**硬件排查**：笔记本黑屏先分「有没有供电、有没有自检、有没有显示输出」三段。电源适配器与电池供电分别试，看指示灯与风扇；外接显示器判断是屏幕还是显卡/主板；内存条重新插拔、单条轮换是最常见的有效手段；听蜂鸣码或看主板诊断灯；再往下是清 CMOS、最小系统法（只留 CPU、一条内存、电源）逐项加回。要说明这些步骤的先后依据是「从外到内、从便宜到贵」，而不是背清单。

**Qt 项目崩溃后打不开**：最常见原因是上次保存写坏了文件（写到一半断电），或配置文件/缓存损坏导致启动即崩。做法是保存时先写临时文件再原子替换（`QSaveFile` 就是为此设计），保留上一版备份，启动时校验文件完整性，损坏则回退到备份并提示；同时把崩溃信息写入日志，便于定位是数据问题还是代码问题。

**图片上传后前端不显示**：按链路逐段排查——浏览器开发者工具的 Network 看请求是否发出、状态码与响应体；上传接口返回的 URL 是否可访问（直接在新标签打开）；对象存储的跨域与防盗链配置；返回的地址是内网地址还是公网地址；Content-Type 是否正确；前端渲染时是否被 CSS 隐藏或图片加载失败（看 Console 与 img 的 error 事件）。结论要落到具体一段，而不是「后端问题」。

**NAS 外网访问**：没有公网 IPv4 时，常见方案是 IPv6 + DDNS（运营商给 IPv6 且防火墙放行）、内网穿透（frp、Cloudflare Tunnel、Tailscale 组网）。frp 需要一个有公网 IP 的中转服务器，配置简单、可控；Cloudflare Tunnel 不需要公网 IP，但流量经第三方；Tailscale/WireGuard 是组网方案，只有加入网络的设备能访问，安全性最好。选择依据是「有没有公网地址、是否要给非技术用户访问、对带宽与延迟的要求」。

**AVL 树与红黑树**：需要有序结构与范围查询时用树，而不是哈希表。AVL 树严格平衡（任一节点左右子树高度差不超过 1），查找更快，但插入删除的旋转次数多，适合读多写少；红黑树用颜色约束把最长路径限制在最短路径的两倍以内，平衡条件更松，插入删除的调整次数少，因此标准库的 map/set 用它。两者查找、插入、删除都是 O(log n)，差别在常数与旋转代价。

**Git 已提交后想改**：还没推送时用 `git commit --amend` 修改最后一条，或用 `git rebase -i` 合并、改写多条；已经推送且不允许改写公共历史时，用 `git revert` 生成一条反向提交。要讲清 `--amend` 与 rebase 都会改写提交哈希，只对尚未共享的本地历史使用；团队分支上强推（`--force-with-lease`）要先确认没有他人在此分支工作。常用命令还包括 `status`、`diff`、`log --oneline --graph`、`stash`、`cherry-pick`、`bisect`，能说出各自解决什么问题比罗列参数有用。
