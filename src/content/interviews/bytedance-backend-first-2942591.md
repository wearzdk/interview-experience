### 《参考解析》

**缓存 Key 与版本号**：Key 要能唯一表达「哪个实体、哪种请求、哪个模型版本」，例如 `score:{modelVer}:{driverId}:{orderId}`；把版本号放进 Key 是为了让新旧版本的缓存天然隔离，切换时可灰度放量、出问题能立刻切回。用 String 存序列化后的结果而不是 Hash，是因为一次读取整体返回、避免多次 field 读取的往返，也便于设置统一 TTL；但要注意单 Key 体积，控制候选集大小、必要时拆分或只缓存 ID 列表。

**版本切换的回源保护**：新版本上线初期缓存全空，流量会直接打到模型服务。做法是预热（离线跑热点集合写入新 Key）、分批放量（按流量比例或白名单切换）、回源限流与单飞（同一 Key 并发只放一个请求回源）、旧版本缓存保留一段时间兜底。灰度期间同时观察命中率与模型指标，异常即回滚版本号。

**TTL 与命中率**：TTL 取决于数据变化频率与业务可接受的陈旧度——实时性强的特征短 TTL，稳定的画像类可以长。评估方式是看「TTL 延长带来的命中率提升」与「陈旧数据导致的指标损失」的平衡点，用小流量实验对比。命中率低的常见原因：Key 设计过细（含时间戳、随机数）、TTL 过短、缓存穿透（不存在的 Key 反复查）、写入与读取的版本不一致、热点集中导致被淘汰。

**异步日志与 context**：同步打日志会在 IO 上阻塞业务线程。改造为有界队列 + 后台消费线程，业务线程只做入队，队列满时按策略丢弃或降级（打点计数、采样）。context 复用（`sync.Pool`）要注意：日志异步化后，如果 context 在打印前就被回收复用，日志内容会串，所以入队时要深拷贝需要的字段，或者引用计数等消费完成再归还。收益看 P99 而不是平均值，尾部延迟才是用户体感。日志丢失要能感知：队列积压、丢弃计数、关键日志落本地文件兜底。

**过滤前置**：把不依赖模型打分的硬性条件（黑名单、地理围栏、服务类型不匹配、库存为零）提前到调用模型之前，减少无效计算与下游请求。判断标准是「这个条件是否依赖打分结果」——依赖就不能前置。收益是双向的：省掉模型调用与特征读取，同时缩短链路。

**N+1 与索引**：N+1 是先查一批主记录，再对每条记录单独查关联表，1 次查询变 N+1 次。优化是用 `IN` 批量查、JOIN、或应用层做 Map 聚合。对关联字段做 `CAST` 会让索引列参与函数运算，无法使用索引；同类问题还有隐式类型转换、函数包裹、前导模糊匹配、联合索引不满足最左前缀。除索引外，慢查询还可能来自数据量过大、锁等待、返回列过多、排序与临时表、网络传输。

**排查流程**：页面慢 → 看接口耗时分布（网关、应用、DB）→ 应用侧看慢调用与线程栈 → 开启慢查询日志定位 SQL → `EXPLAIN` 看执行计划 → 结合 `rows`、`filtered`、`Extra` 与真实耗时决定加索引、改 SQL 还是改数据模型。索引设计按查询模式来：区分度高的列在前、覆盖高频查询列、控制索引数量避免写放大。

**MVCC**：InnoDB 通过 undo log、行记录的隐藏字段（`DB_TRX_ID`、`DB_ROLL_PTR`）与 ReadView 实现多版本读。ReadView 记录活跃事务列表，判断行版本对当前事务是否可见；不可见就沿 undo log 找上一个版本。RC 每次查询生成新 ReadView，所以能看到别的事务已提交的变更；RR 在事务首次快照读时生成并复用，保证同一事务内多次读一致。读未提交直接读最新版本；串行化加锁读，牺牲并发换一致。

**InnoDB 持久性**：靠 redo log 的 WAL——事务提交时先顺序写 redo 并刷盘（`innodb_flush_log_at_trx_commit=1`），数据页异步刷；崩溃后用 redo 重放已提交事务，用 undo 回滚未提交事务。binlog 与 redo 的两阶段提交保证主从一致。

**HashMap**：JDK8 是数组 + 链表 + 红黑树。哈希冲突用链地址法；链表长度达到 8 且数组容量不小于 64 时转红黑树，退化到 6 转回链表。扩容是容量翻倍，元素按 `hash & (newCap-1)` 重新分配，JDK8 用高低位拆分避免重新计算哈希。

**限流与并发控制**：常见算法有固定窗口（简单但有临界突刺）、滑动窗口（平滑、需存储）、漏桶（恒定速率）、令牌桶（允许突发）。双层限流通常是「入口按用户/接口限流 + 下游按资源（线程池、连接池）限流」。信号量限制同时执行的请求数，不排队、拿不到直接失败或等待；线程池限制并发并管理队列，能隔离故障但参数不当会积压。选择取决于要不要排队、以及失败时如何反馈。

**@Transactional**：Spring 声明式事务基于 AOP 代理，同类内部调用、非 public 方法、异常被吞、抛受检异常未配 `rollbackFor`、多线程执行都会让事务失效。
