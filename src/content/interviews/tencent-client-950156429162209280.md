### 《面试题目》

1. 设计一个秒杀系统，你会怎么架构？
2. 接口 RT 突然从 50ms 涨到 2s，排查思路是什么？
3. 线上 CPU 100% 怎么定位？
4. 百万级数据导出怎么避免 OOM？
5. 短链服务怎么做高可用？
6. 订单超时未支付怎么自动关闭？
7. 登录态在分布式系统中怎么管理？
8. 热点 key 问题怎么处理？
9. 服务发布怎么做无损上线？
10. 如果让你从 0 设计一个支付回调系统，核心模块有哪些？
11. 线程池的 `execute` 流程是怎样的？拒绝策略怎么选型？
12. HashMap 的扩容与树化条件是什么？AQS 的状态机与 CLH 队列如何工作？
13. 业务系统接大模型，常见架构是什么？虚拟线程适合什么场景、不适合什么场景？

### 《参考解析》

**场景题的作答结构**：结论先行给出方案，再解释为什么这样选、替代方案是什么，然后落到 key 设计、过期策略、失败补偿这类细节，最后主动说风险点（超卖、热点、依赖宕机）。四段缺一段，面试官就会继续追问，因此准备时按这个结构写口述稿比背方案名有效。

**秒杀**：前端静态化与答题削峰，网关按用户与商品维度限流，库存放 Redis 用 Lua 原子扣减并记录流水，扣减成功后发消息异步创建订单，数据库只做最终落库与对账；超卖用预扣加流水校验兜底，重复下单用用户与商品维度的幂等键，热点商品做库存分段。风险点是 Redis 宕机后的降级与消息重复消费。

**排查类**：RT 飙高先确认影响面（全量还是单接口、是否与发布或流量对齐），再看依赖耗时（数据库、缓存、下游 RPC）与资源等待（连接池、线程池排队、GC）。CPU 100% 用 `top -Hp` 找线程、转十六进制查 `jstack`，常见原因是死循环、频繁 GC、正则回溯与锁竞争；配合火焰图确认热点函数。

**百万导出**：不要一次性查全量再写文件。用游标分页或流式查询逐批读取，边读边写并定期 flush，配合 SXSSF 这类磁盘溢写的 Excel 写法；导出任务异步化，前端拿任务 id 轮询进度，产物存对象存储给下载链接，并限制并发导出数防止拖垮数据库。

**短链、关单与登录态**：短链用发号器生成唯一 id 再做进制转换，读多写少适合多级缓存，跳转用 302 便于统计；高可用靠缓存 + 布隆过滤器防穿透、分片与多副本。订单超时用延迟消息（RocketMQ 延迟级别、RabbitMQ 死信队列）或时间轮扫描，消费时先查订单状态保证幂等，避免消息重复导致重复关单。分布式登录态用 Redis 存 token 与用户映射，设置滑动过期，多端登录按设备维度记录并在改密时批量失效。

**热点 key 与无损发布**：热点 key 用本地缓存加多级缓存、按 key 拆分副本、读写分离与限流保护，监控上按 key 维度统计 QPS。无损发布靠优雅停机（先从注册中心摘除、等待在途请求结束、再关闭线程池）、就绪探针、灰度与回滚预案，长连接服务要先停止接收新连接再排空。

**支付回调系统**：核心模块包括签名验签与来源校验、幂等处理（业务单号唯一索引）、状态机（待支付→已支付→已发货/已退款）、异步通知与重试、对账与差错处理、审计与告警。回调必须先落库再返回成功，重试要指数退避并限制次数，重复回调按状态机拒绝。

**源码关键路径**：线程池 `execute` 先判断核心线程数，未满则新建线程；满了入队列；队列满则尝试扩容到最大线程数；仍失败则执行拒绝策略。理解它能解释为什么无界队列会让最大线程数失效。HashMap 在链表长度达到 8 且容量不小于 64 时树化，扩容按两倍进行并重新分布高低位。AQS 用 `state` 表示同步状态、CLH 变体队列存放等待线程，`acquire` 失败后入队并自旋检查前驱，释放时唤醒后继。这些路径的价值在于能解释方案为什么成立，而不是背结论。

**大模型接入与虚拟线程**：常见架构是网关统一鉴权与限流、业务层组装上下文、向量库做检索、模型服务流式返回，配合缓存与降级。虚拟线程适合大量阻塞在 IO 的任务（下游调用、数据库访问），能以同步写法获得接近异步的吞吐；不适合 CPU 密集型任务与长时间持有 `synchronized` 的场景，因为载体线程被固定会导致调度器阻塞（JDK 24 起已缓解）。
