### 《面试题目》

1. MCP 的通信架构是怎样的？为什么 Server 不主动发请求？能力与生命周期怎么约束？消息 id 与通知怎么设计？
2. MCP 的 transport 有哪几种？stdio 怎么分帧？Streamable HTTP 怎么支持流式？自定义传输要保留什么？
3. 150 人团队的 AI 开发者网关，归因与评价方案怎么做？没有严格 A/B 怎么做归因？样本量够不够？代码行数为什么不能当主指标？
4. 混元开源智能体的应用场景怎么设计？为什么用专用小模型做记忆？Agent 进生产的安全底线是什么？MCP 与 Function Call 怎么选？
5. MCP 的安全隔离如何实现？Host 如何统一管控？

### 《参考解析》

**MCP 的三层模型与消息语义**：协议基于 JSON-RPC 2.0，分 Host、Client、Server 三层。Host 是面向用户的宿主应用（IDE、桌面客户端），负责协调多个 Server、管理权限与生命周期；每个 Client 与一个 Server 保持一对一连接；Server 暴露三类能力——Resources（可读的上下文数据）、Tools（可被模型调用的动作）、Prompts（可复用的提示模板）。消息类型只有三种：Request（带 id，需回应）、Response（带同一 id，含 result 或 error）、Notification（不带 id，不需要回应）。Server 不主动发请求，是因为它没有独立的用户上下文与授权来源，若允许它主动调用会破坏「Host 统一管控」的权限模型；需要通知时用 Notification 单向推送。能力协商在 `initialize` 阶段完成：双方各自声明支持的协议版本、capabilities（是否支持 tools、resources、prompts、日志、采样等），之后只使用协商过的能力，未声明的能力不得调用。生命周期是 `initialize` → `initialized` 通知 → 正常运行 → 关闭，任何一方都可以发起关闭，关闭前应释放资源。

**transport 选型**：① stdio——本地子进程，通过 stdin/stdout 传 JSON-RPC，按行（换行符）分帧，必须使用 UTF-8 且消息内不能含裸换行（JSON 序列化后本身不含），适合本地工具、零网络开销、天然隔离。② Streamable HTTP——远程推荐方案，单一 MCP 端点，客户端 POST 请求，服务端可以用普通 JSON 响应，也可以用 SSE 流式返回多条消息；支持会话 id 与断线恢复（通过事件 id 重放）。③ HTTP + SSE（旧方案）——已弃用，因为它需要两个端点、连接长期占用、与无状态网关不兼容。④ 自定义传输——协议本身与传输无关，但必须保留 JSON-RPC 的报文格式、请求/响应配对、能力协商与生命周期，否则就不再是 MCP。

**AI 开发者网关的归因方案**：先把网关的定位说清——它不是计费器，而是归因基础设施。每次调用携带结构化标签（团队、项目、场景、用户），强制「归因护照」，未携带直接拒绝，这样数据才有分析价值。采集四类数据：身份（谁在用）、用量（token、请求数）、运行质量（延迟、错误率、重试）、成本。指标体系分层：采纳与渗透（活跃开发者、使用频次）、交付效率（DORA 四项 + 需求交付周期）、质量与返工（缺陷率、逃逸率、返工率）、开发者感知（问卷校准）。归因方法在没有严格 A/B 时用三类替代：基线对比（使用前后同团队的纵向对比）、交错采纳 DiD（不同团队先后接入，用双重差分剥离时间趋势）、多信号三角验证（网关 token × Git/PR 产出 × 缺陷系统 × 问卷）。要主动讲清边界：150 人的样本量做团队级比较够、做个人级排名不够（噪声大且会诱发刷指标）；代码行数不能当主指标，因为它与价值不相关、且会被 AI 生成量放大；J-Curve 效应意味着短期看不到收益是正常的，评估窗口要拉长到季度。

**智能体的场景设计**：核心原则是场景驱动，不做通用 Agent。分层解耦：模型层负责理解与生成，框架层负责编排（Workflow、RAG、Multi-Agent），应用层负责具体业务与交互。记忆用专用小模型做读写，是因为主模型的上下文宝贵、且记忆的写入需要「提炼与摘要」这类高频小任务，用主模型做既贵又慢；记忆的生命周期分写入提炼、动态更新与遗忘、多路检索、精准注入四步，注入时按当前任务相关性裁剪。安全治理的底线是权限最小化（工具只拿必要的凭证）、全量审计（谁在何时调用了什么、参数与结果）、高风险动作人工确认、沙箱隔离（代码执行、文件写入在受限环境）。MCP 与 Function Call 的选择：Function Call 是模型厂商的私有协议，接入快、与模型耦合；MCP 是开放协议，工具可跨宿主复用、有标准的能力协商与权限模型，适合工具生态与多客户端场景，代价是多一层进程与协议开销。

**MCP 的安全隔离**：Server 之间相互隔离，各自只能访问被授予的资源；Host 统一管控权限（哪些 Server 可以被这个会话调用、调用前是否需用户确认），并对工具调用做审计。实现上要给每个 Server 独立的进程或容器、限制文件系统与网络范围、对返回值做长度与内容校验（防止提示注入藏在工具结果里）。面试里常被追问「工具结果里带指令怎么办」，答案是「工具结果只是数据，不能提升为指令」，Host 侧应对其做标记与转义，并在提示中明确数据与指令的边界。
