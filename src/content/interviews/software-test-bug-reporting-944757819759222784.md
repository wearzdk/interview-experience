### 《面试题目》

1. 测试人员一般用什么工具提 Bug？整个提单流程是怎样的？
2. 一个 Bug 单里要填写哪些信息？哪些是面试重点？
3. Bug 的类型、严重程度、优先级分别怎么划分？
4. 怎么评估一个 Bug 的优先级？
5. Bug 描述里必须写清什么？
6. 提完 Bug 之后呢——指派给谁、怎么跟？

### 《参考解析》

**提单流程**：落在缺陷管理工具（JIRA、禅道、TAPD 都行）里的标准链路是：登录工具 → 在对应项目里选「创建缺陷」→ 填完整信息 → 指派给模块负责人或经办人 → 保存。流程本身没什么可答的，面试官问这段是在看你有没有真的在团队里跑过这套，所以别只背步骤，顺带说清你们团队的分工（谁 triage、谁确认、谁来关单）。

**一个 Bug 单的核心字段**，按重要性排：

- **标题**：一句话说清「在哪、做什么、出了什么错」。好的标题是「购物车页删除最后一件商品后，页面空白且不跳转」，坏的是「购物车有 Bug」。
- **复现步骤**：编号列出，精确到可被另一个人照着重现——账号状态、前置数据、操作路径、每一步的预期。步骤不能复现的 Bug，开发第一句就会打回来。
- **实际结果 vs 期望结果**：这两栏是 bug 的立论。实际结果是客观描述（看到了什么、报错文案原文），期望结果要给出依据（需求文档哪一条、同类功能的既有行为），不能只写「应该正常」。
- **严重程度（Severity）**：Bug 对系统的客观破坏力。分档一般是致命 / 严重 / 一般 / 轻微 / 建议——崩溃、数据丢失、主流程阻断是致命；核心功能不可用或金额算错是严重；非核心功能异常、有绕行方案是一般；UI 错位、文案错误是轻微。
- **优先级（Priority）**：这个 Bug 该多快被修，是排期决策。P0 是必须立刻修、否则阻塞发版；P1 是本迭代必修；P2/P3 可排到后续版本。
- **类型**：功能缺陷、界面 / UI、性能、兼容性、安全、数据、需求理解偏差等，用于统计归因。
- **附件**：日志、截图、录屏、请求响应报文、复现用的测试数据。有现场证据的 Bug 处理速度通常快一倍。
- **环境信息**：版本号、机型 / 系统版本、浏览器、网络环境。跨端问题里这一栏比描述还关键。

**严重程度和优先级为什么不能混为一谈**：严重程度是技术事实，优先级是业务决策。一个只在 iOS 16 以下崩溃的支付按钮，严重程度是致命，但如果你们的用户里这个系统版本占比不到 0.5% 且下个版本就要停支持，优先级可能只给 P2。反过来，一个错别字出现在官网首页 banner 上，严重程度是轻微，但品牌影响让它值得插队。所以提单时严重程度按影响面客观填，优先级留给产品 / 项目跟测试一起定，测试可以给建议但不能单方面决定。这条差异是这道题真正的考点。

**怎么评估优先级**：按几个维度叠加打分——影响用户比例（全量 / 特定条件 / 极少数）、是否有绕行方案（能绕过就降级）、是否影响核心链路（注册登录、下单支付、数据安全）、是否阻塞测试或发版（阻塞就升）、有没有合规或资损风险（资损一律顶格）。实际团队里往往还有一条隐性规则：新功能首次提测阶段的 Bug 优先级普遍偏低（功能本来就没做完），回归阶段和上线后的 Bug 优先级普遍上调。

**提完之后别撒手**：指派要指到具体的人而不是「开发组」；跟进的是三件事——开发是否认可（不认可就走需求对齐，不是争论）、修复版本是否已包含、修复后是否回归验证。关闭 Bug 的人应该是提单的测试，不是开发自己改状态。
