### 《参考解析》

**AI 接入数据链路的实际问题**：难点不在开发，开发有文档和 AI 辅助相对可控；难在业务侧要反复对齐字段口径、评估需求价值。Agent 能产出结果但质量不稳定，对口径理解容易偏差，需要人工复核它的思考链路与查表逻辑——比如给自然语言需求，它可能生成错误 SQL 或错误报表口径。团队尝试多 Agent 协作让 Agent 自生成、自校验，仍在开发阶段。

**知识库的三个要点**：第一，业务隔离，不同场景配独立知识库，不共用一套；第二，面向 Agent 适配，不能沿用给人读的文档标准，结构、粒度、字段说明要改成模型容易解析的形式；第三，优化检索规则，除权限控制外还要规范内容结构、给检索加约束，让 Agent 能精准定位到对应条目与业务依据。

**电商信息 Agent 的设计**：分知识库与能力两部分。知识库侧梳理项目背景、业务字段、口径定义与换算规则；PDF 等原始文档切片时标记来源章节与所属业务场景，因为同一字段在不同场景口径不同，检索要同时匹配关键词与业务上下文，保证 RAG 命中正确条目。Agent 侧按能力拆分职责（取数、绘图、图表分析等），为每类定义 Skill，明确 SQL 能力边界、限定可访问的库，避免自由发散产出错误数据。

**AI 之后数据研发的变化**：传统数据开发大量时间在写 SQL、做分层、开发 ETL，现在这些基础环节可以大量自动化；人的重心转到维护适配 Agent 的知识库、把控输入输出质量、校验结果正确性。人不再独立维护整条链路，由 Agent 承载数据闭环执行，人负责质量管控，同时因为要盯全链路，工作范围比传统数仓开发更宽。

**离线与实时的取舍**：离线开发居多，接触的是开发质量域、测试域的数据，业务复杂度低于电商业务域；工作重心在链路实现、调优与维护。被问到是否做过在线服务或实时工具时，要如实说明边界，并讲清离线链路的产出如何被在线消费。
