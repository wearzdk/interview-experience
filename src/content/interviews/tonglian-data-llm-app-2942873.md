### 《参考解析》

**PDF 解析的选型要能说清代价**：PyMuPDF 快、依赖少、对文本型 PDF 提取准确，但对扫描件、双栏排版、表格与公式几乎无能为力——它只按内容流取文字，不理解版面。选型时应按文档类型分情况：文本型用 PyMuPDF 或 pdfplumber，扫描件走 OCR（PaddleOCR、云 OCR），复杂版面与表格用版面分析模型（如基于 LayoutLM 的方案）或商用解析服务（Unstructured、LlamaParse、MinerU 一类）。评估用「抽取字符准确率 + 表格还原度 + 阅读顺序正确率」在真实样本上打分，而不是凭直觉。面试官追问「为什么选它」，想听的是对比与适用边界，不是库名。

**BGE-M3 为什么合适**：它同时支持稠密、稀疏与多向量三种检索表示，中文效果在开源模型里靠前，支持长文本（8192 token），一次编码可同时产出多种向量，省一次推理。对比对象包括 multilingual-e5、GTE、Conan 以及各家 API 嵌入模型。选型要在自己的语料上做检索评测（Recall@K、MRR），而不是看榜单；同时考虑维度与成本、是否支持本地部署、是否需要多语言。

**Reranker 的作用不止「排前面」**：向量检索是双塔结构，query 与文档分别编码后算相似度，速度快但交互弱，容易召回「语义相近但不回答问题」的片段。Reranker 是交叉编码器，把 query 与每个候选拼在一起过模型，能捕捉词级交互与否定、限定条件，因此能在 Top-50 里挑出真正相关的几条。它的价值是「用可接受的延迟换取精度上限」，配合「粗排召回多、精排取少」的两段式，既控制成本又提升答案质量。说「只是把准确 chunk 放前面」会被认为没理解机制。

**证据溯源怎么做**：chunk 层面最简单——返回答案时附带每个 chunk 的 id、原文、页码与坐标，前端按坐标高亮（PDF 用文本层坐标，网页用 DOM 定位）。但要精确到「哪句话」，需要在生成时要求模型输出引用标记（如 `[1]`），并把每个标记绑定到具体句子；更细的做法是把文档预处理成句子级索引，检索命中句子而非整块，答案里只引命中句。chunk 之外的路径包括：用倒排索引做关键词回查（把答案里的句子拿去原文里定位）、用句子级向量索引、用抽取式模型先定位支撑句再生成、以及用知识图谱把实体关系作为证据。倒排索引的优点是精确匹配、可解释、成本低；缺点是同义改写与跨句推理找不到。工程上通常组合：先按 chunk 召回，再在 chunk 内做句子级对齐，最后把对齐结果作为引用返回。

**框架的区别与选型**：LangChain 偏「组件库 + 链式编排」，适合快速搭 RAG 与工具调用原型，抽象多、版本变动快；LangGraph 把流程建模成状态图（节点、边、条件跳转、检查点），适合有循环、多角色、需要人工介入与断点续跑的长流程 Agent；DeepAgent 一类偏「自主规划 + 子任务分解」的高层封装；Pi Agent SDK 更轻，聚焦工具调用与运行时。选型看的是控制粒度与可观测性需求：流程固定用 LangChain 或直接写代码，状态复杂、需要回滚与恢复用 LangGraph，追求开箱即用选高层框架。注意面试官提到的版本问题——LangGraph 近一年在封装度上进步很大，预置了持久化、人工审核、流式输出等能力，「太底层什么都要自己搭」的说法已经过时，回答前先确认版本与文档。

**LangGraph 的缺点**：图结构带来学习成本，简单线性流程用它反而更啰嗦；状态设计不当会导致节点间耦合、调试困难（需要可视化与检查点）；生态与最佳实践仍在演进，版本升级有破坏性变更；对不熟悉状态机的团队，容易把业务逻辑散落在节点里，缺少统一的事务与错误处理。应对是先用小图验证、明确状态 schema、给每个节点加超时与幂等，并保留可回退的纯代码路径。
