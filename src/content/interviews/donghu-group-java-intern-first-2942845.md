### 《参考解析》

**为什么要做问题重写与子问题拆分**：用户的第一句话往往带指代（「这个怎么弄」）、口语省略、以及多个混在一起的问题。直接拿原句去向量检索，召回的是「字面相似」而不是「语义需要」的片段，多领域问题还会被单一查询向量平均掉，导致每个子问题都召回不准。重写是把口语补全成独立可检索的查询（补上上下文里的主语、时间、对象），拆分是把复合问题拆成若干单一意图的子问题，分别检索后再合并上下文交给模型作答。判断是否要拆，可以先用意图分类或让模型输出「该问题包含几个独立子问题」，简单问题不拆以免引入噪声。

**具体实现**：链路是「会话上下文 → 重写（LLM 输出结构化 JSON：改写后的 query 列表 + 每个子问题的意图标签）→ 每个子问题分别向量化检索（可加关键词检索做混合召回）→ 重排（Rerank）取 Top-K → 按子问题组织上下文 → 生成答案并附引用」。工程上要缓存重写结果（同一轮对话内不重复调用）、给重写加超时与降级（失败时用原句检索）、限制子问题数量（通常不超过 3~4 个，否则延迟与成本不可控），并用评测集对比「重写前后」的召回命中率与答案正确率，而不是凭感觉。

**意图识别的做法**：小场景用规则 + 关键词 + 分类模型（FastText、BERT 微调）；大模型场景直接让模型输出枚举标签并约束 JSON Schema，配合少量 few-shot 示例；也有「先用向量把用户问题与意图描述做相似度召回，再让模型确认」的两段式，成本更低。关键是意图标签要互斥且可穷举，不确定时给「其他」并由兜底流程处理，而不是硬塞进某个类。

**提示词怎么写**：结构上分角色、任务、输入、约束、输出格式、示例六块。约束要写成可检验的规则（「只输出 JSON，不要解释」「子问题不超过 3 个」「保留原文中的专有名词」），示例给正例与一个反例。把易变的部分（用户问题、检索到的上下文）放在后面，固定指令放前面以便命中缓存。上线后按失败样本迭代，而不是一次写很长。

**联合索引的字段顺序**：B+ 树按索引定义的列顺序逐列排序，先按第一列排、第一列相同再按第二列排。所以查询条件必须从最左列开始连续匹配才能用到索引，这就是最左前缀原则。`(a, b)` 的索引里，只查 `b` 时 `b` 的取值在整棵树上是「全局无序、局部有序」——同一个 `a` 下的 `b` 有序，但不同 `a` 之间无法比较，无法二分定位，只能全表扫，因此用不上索引（可能走覆盖索引扫描，但仍是扫全部索引项）。建索引时把等值条件、区分度高的列放前面，范围条件放最后；`(a, b)` 能服务 `a`、`a AND b`、`a` 加排序，但不能服务单独的 `b`。

**短链系统设计**：核心是三件事——发号生成短码、映射存储、跳转。生成短码常用自增 id 转 62 进制（无冲突、长度可控）、哈希（MD5 取前几位，需处理冲突）、或预生成号段（美团 Leaf 思路）；存储用 KV（Redis + MySQL 持久化），`短码 → 长链` 为主键查询。跳转时查缓存，命中直接 302；未命中回源数据库并回填缓存；同时记录点击埋点（异步写消息队列，不阻塞跳转）。还要考虑：自定义短码与敏感词、有效期与回收、防刷与限流、恶意链接检测、以及统计去重。

**十万到百万 QPS 的映射设计**：单机 Redis 撑不住百万级读，要做多层——本地缓存（Caffeine，存最热的一批短码）+ Redis 集群（按短码哈希分片）+ 数据库只作冷数据与持久化。读多写少适合「缓存优先、异步回填」，热点短码加本地缓存并设置短过期，防止缓存击穿时打穿到数据库（用 singleflight 合并回源）。写路径用号段模式批量取号，避免每次生成都访问数据库；跨机房用多副本 + 就近读。百万 QPS 还要考虑带宽与连接数：短链响应体极小，主要成本在 TLS 握手与重定向，可用 HTTP/2、长连接、CDN 边缘 302。

**哈希冲突**：若用哈希生成短码，冲突处理有几种——冲突后加盐重算（最简单，但高负载下重试次数上升）、开放寻址（在短码后追加序号，需保证可解析）、布隆过滤器预判（先查是否已存在，减少无效写入）、或者干脆改用自增 id 转 62 进制从根上避免冲突。业务上更稳的做法是「发号器 + 唯一索引」：短码唯一索引兜底，插入冲突即重新取号，冲突概率极低且不会产生错误映射。
