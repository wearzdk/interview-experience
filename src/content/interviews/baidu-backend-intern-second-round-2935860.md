### 《参考解析》

**事务与消息的一致性。** 直接「先提交事务再发消息」存在窗口：commit 成功、发消息前进程挂掉，消息就永久丢了。常见解法有三条。本地消息表（outbox）：在同一个数据库事务里写业务表和一条待发消息记录，事务提交后由独立投递器轮询未发送记录投递 Kafka，成功后标记；投递失败可重试，天然不丢。事务消息：RocketMQ 的半消息 + 回查机制，本质也是让 broker 回查本地事务状态。CDC：订阅 binlog 把变更投递到消息队列。消费端必须幂等（业务唯一键 + 状态机），并用定时对账任务兜底，扫「状态已变但下游未重算」的数据补发。

**锁竞争的处理。** 三种都不该无条件用。正确做法是先判断业务语义：如果是同一账户的增量变更，应该把变更事件投递到一个按账户 ID 分区的队列，由单消费者串行处理，锁只是优化而非正确性来源；如果必须同步处理，就设一个短超时（如 200ms）的重试，超时后返回「处理中」让上游重试，绝不能长时间阻塞占用连接。直接丢弃会丢变更，无限阻塞会拖垮线程池，无条件重入队列可能造成惊群和顺序错乱。配合版本号做 CAS 更新，重复处理也能被识别。

**防旧覆盖新。** 数据行加版本号或单调递增的 seq，更新时 `WHERE version = ?`，影响行数为 0 就说明已被改过，重新读取再决策；也可以带更新时间做「只允许新时间戳写入」。缓存侧用「先更新库、再删缓存」并给缓存设 TTL，延迟双删处理并发读写；消息侧用分区内有序 + 消费端按版本号丢弃过期事件。核心是让「新旧」有可比较的依据，而不是依赖执行顺序。

**内存索引的数据结构与容量。** Go 里常用 `map[uint64]*Account`，高并发读多写少时用 `sync.Map` 或分片锁（把 key 哈希到 N 个 map，各自一把 RWMutex）降低争用；需要范围查询就用跳表或有序切片。容量要能算出来：map 每个桶加指针有额外开销，一条「key 8 字节 + 指针 8 字节 + 结构体本身」按几十到上百字节估，百万级账户大致在百 MB 量级，评估时要按峰值账户数和结构体字段对齐后的实际大小算，并留出扩容时的双倍瞬时内存。

**会话内并发指令。** 同一话题里 A 没处理完又来 B，要做的是「串行化 + 可打断 + 可合并」：按会话 ID 维护一个任务队列，同一个会话同时只有一个在执行，新指令入队；如果新指令是对当前任务的补充或修正，就把当前任务标记为需要重规划，在下一个安全点（一次工具调用返回后）读取最新指令重新规划，而不是硬跑完旧任务；如果是明确的新任务，则排队并在回复里告知前面还在处理。多次改需求同理，保留一份「当前生效的需求快照」，每次改动更新快照并记录版本，执行时以最新版本为准，同时把变更写进上下文避免模型拿旧需求继续做。

**双路比对的容差。** 配置要按字段类型分开：浮点数用相对误差加绝对误差双阈值（`abs(a-b) <= max(eps_abs, eps_rel * max(abs(a),abs(b)))`），金额按最小货币单位比较；时间戳先统一单位（秒/毫秒）与时区，再允许一个时间窗；JSON 要做规范化——对象 key 排序后逐键递归比较，数组则视语义选择「排序后比较」或「按业务主键匹配后比较」，并允许字段白名单忽略（如 requestId、时间戳字段）。容差阈值应该配置化、随场景不同（金额严格、展示类宽松），并输出差异明细方便定位。

**点踩权重分摊。** 整条回答点踩只能说明「这条回答里至少有一处错」，直接平均分给所有引用片段会误伤正确片段。可行的做法：按片段对回答的实际贡献加权（被引用的句子长度、被引用的次数、检索得分归一化），把负反馈按权重分配；同时保留「用户是否指定了错误片段」的入口，指定了就 100% 归到那一片段；再结合显式反馈（单片段点赞/点踩）做校准。长期看要用「同一片段被多次独立点踩」的统计量，避免单次误判就下调知识库权重。

**为什么不能只靠行号校验。** 行号是位置而非内容：用户在审批等待期间在上面插入或删除几行，行号会整体偏移，原本要改的那段代码可能已经变了但行号还对得上，补丁应用后改错地方；同一行号在不同版本里也可能是完全不同的内容。可靠的做法是记录目标片段的内容哈希 + 上下文指纹（前后各若干行的哈希），应用前重新计算并比对，不匹配就拒绝并要求重新生成；再加文件级版本号或 git blob hash 做整体校验。

**文件变更的检测。** 服务端可以监听文件系统事件（inotify/FSEvents）或让客户端在保存时上报文件哈希与 mtime；更简单可靠的是在审批记录里存「文件内容哈希」，审批通过时重新读文件算哈希比对，不一致就让审批失效。IDE 插件侧可以在保存事件里主动通知服务端。检测到变更后要把审批置为失效、通知发起人，并让 Agent 基于新内容重新生成补丁，而不是拿旧补丁硬套。

**雪花 ID 做 Bitmap 偏移量的后果。** Bitmap 的内存占用由最大偏移量决定，而不是由元素个数决定。雪花 ID 是 64 位、时间戳在高位，生成的数值极大且极度稀疏，`SETBIT key <userID> 1` 会按 userID/8 字节去分配，一条记录就能让 Redis 分配几十 TB 级别的空间，直接打爆内存或触发 Redis 的字符串长度上限报错。正确做法是不要用业务大 ID 直接做偏移：可以换成自增的稠密编号再映射，或者用布隆过滤器、分片 Bitmap（按 ID 高位分桶、桶内取低位）、Roaring Bitmap 这类压缩位图。
