### 《参考解析》

**数据处理链路与缓冲设计**：典型链路是「采集（设备 / 传感器）→ 预处理（校验、打包）→ 入缓冲（环形队列）→ 发送（socket / 串口）」。单独开线程的理由是生产与消费的速率天然不匹配，采集侧受硬件节拍约束、发送侧受网络带宽与对端接收能力约束，串在一个线程里会让慢的一侧拖住快的一侧。生产快于消费时用有界队列加背压：队列满时按业务选策略——实时监控可以丢最旧帧保住新鲜度，并单独计数丢弃量；数据不能丢时阻塞生产者，但要防止持锁阻塞造成死锁；覆盖最新帧会把未发出的旧数据全部作废，只在「只关心最新状态」的场景成立。面试官继续追问策略选择，是在看有没有按业务代价判断，而不是背一个标准答案。

**线程安全环形队列**：核心是 head、tail 与元素计数三者的一致性。用互斥锁保护入队出队，配两个条件变量 `not_empty` 与 `not_full`：消费者在队列空时等待 `not_empty`，生产者在队满时等待 `not_full`，每次操作后 signal 对侧。空满判定有两种常见写法——维护 `count` 最直观；或者少用一个槽位、以 `(tail + 1) % capacity == head` 判满，代价是牺牲一个元素的空间。贴主在提示后才补上条件变量，说明平时写的是「加锁 + 忙等」，那种写法在实时性上会被面试官追问。无锁版本可以用原子 head / tail 加内存序，但单生产者单消费者之外的正确性很难保证，不适合在面试里强行展开。

**malloc 与物理内存**：`malloc` 只返回虚拟地址，内核在首次写入触发缺页异常时才分配物理页，属于惰性分配；`calloc` 通常先映射到共享的零页，写入时才真正复制。因此「申请了 1 GB 立刻占 1 GB 物理内存」是错的，看实际占用要看 RSS。反过来，释放后 RSS 也未必立刻下降，glibc 的 `free` 一般只归还到自己的 arena，大块才走 `munmap`。

**volatile 与单次读写**：`volatile` 只保证每次都从内存读取、不被编译器优化掉，不保证原子性，也不提供跨线程的顺序约束。两个线程对同一变量做 `++` 是读、改、写三步，丢失更新照旧发生；在 C/C++ 内存模型里，非原子变量的并发读写本身就是数据竞争、属于未定义行为。单次对齐的读或写通常不会被撕裂，但仍然应该用 `std::atomic` 表达意图，需要「读后决定写」时用 CAS 或加锁。

**条件变量必须配互斥锁**：判断条件与进入睡眠必须是原子的。若先检查「队列是否为空」再睡眠，两步之间生产者入队并发出通知，唤醒就丢了，消费者永久阻塞。`pthread_cond_wait` 接收 mutex，在内部原子地释放锁并睡眠、被唤醒后重新加锁，正是为了消除这个窗口；醒来后还要在循环里重新检查条件，防止虚假唤醒。

**内存持续增长的定位**：先区分泄漏、缓存膨胀与碎片。看 `/proc/<pid>/smaps` 或 `pmap` 判断是堆还是匿名映射在涨；用 heaptrack、valgrind massif、tcmalloc 的 heap profile 抓两次快照做增量对比；如果增长呈阶梯状且与请求量相关，多半是缓存或连接对象没回收；如果 RSS 不涨但分配失败，考虑碎片。线上还可加进程内统计：按模块记录分配次数与字节数，比事后猜快得多。

**用户态与内核态切换**：入口有三类——系统调用（`syscall` / `sysenter`）、中断与异常、缺页。切换时保存用户态上下文、换内核栈、提升特权级，返回时反向恢复。成本不只是一条指令，还包括 TLB 与缓存污染，所以高频小 IO 会用 `io_uring`、批量系统调用、vDSO 等手段减少往返。

**字符设备驱动注册**：`alloc_chrdev_region` 或 `register_chrdev_region` 申请设备号 → `cdev_init` 绑定 `file_operations` 后 `cdev_add` 注册 → `class_create` / `device_create` 让 udev 生成 `/dev` 节点 → `module_init` / `module_exit` 挂载初始化与清理。`open`、`read`、`write` 由 VFS 根据 inode 找到 cdev，再回调 `file_operations` 里对应的函数。

**用户态指针不能直接解引用**：用户传入的地址不可信，可能非法、未映射、被换出，甚至指向内核空间。驱动必须走 `copy_from_user` / `copy_to_user`，它们内部先做 `access_ok` 范围检查，再处理缺页；直接 `memcpy` 既可能触发 oops，也会被 SMAP 拦下。数据量大时用 `get_user_pages` 做零拷贝映射。

**中断上下半部**：上半部在关中断的上下文里运行，只做最紧急的事——清中断标志、把数据搬到内存，绝不能睡眠，因为中断上下文没有 `task_struct`，调度器不知道该把谁调回来。下半部承担耗时工作：softirq 性能最好但不能睡眠，tasklet 基于 softirq 且同一个 tasklet 不会并发，workqueue 跑在进程上下文因此可以睡眠。判断标准就是「能不能睡」与「对延迟的容忍度」。

**三次握手不能省成两次**：两次握手无法让服务端确认客户端已经收到自己的初始序列号，也无法排除网络里滞留的旧连接请求——一个迟到的 SYN 会让服务端直接建立连接并占住资源，而客户端根本不认这条连接。三次握手同时完成双方序列号同步与双向可达性确认。

**send 的语义**：`send` 返回成功只表示数据被复制进内核发送缓冲区，链路层的可靠由 ACK 与超时重传保证，应用层要知道对端是否处理，必须自己设计业务确认。粘包源于 TCP 是字节流、没有消息边界，Nagle 算法与内核缓冲会进一步合并小包；解决方式是在应用层定界——长度前缀、分隔符或固定长度。

**断网发现**：协议层靠超时重传与 RTO 指数退避，默认要十几分钟才判定连接失效；TCP keepalive 默认两小时才发第一个探测。工程上不能依赖这两者，应用层心跳加写超时是常规做法，心跳间隔按业务容忍度定，收到心跳才刷新对端存活状态。

**epoll 与 LT/ET**：`select` 有 1024 的 fd 上限，每次调用都要把集合全量拷进内核并 O(n) 轮询；`poll` 去掉了上限但仍是 O(n)；`epoll` 用红黑树管理注册的 fd、用就绪链表返回事件，取就绪是 O(1)，适合大量连接。LT 只要缓冲区还有数据就持续通知，写起来简单、不容易漏读；ET 只在状态变化时通知一次，必须配非阻塞 fd 并循环读到 `EAGAIN`，漏读就会永久挂起。

**链表找环入口**：快慢指针同速出发，快指针每次两步、慢指针一步，若相遇则有环。设头到入口距离为 a、入口到相遇点为 b、环长为 L，则相遇时快指针走了 a + b + kL、慢指针走了 a + b，由 2(a + b) = a + b + kL 得 a = kL - b，即从头与从相遇点同时同速前进会在入口相遇。实现时注意空链表与单节点自环的边界。
