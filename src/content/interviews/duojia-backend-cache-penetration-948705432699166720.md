### 《面试题目》

1. 缓存穿透是怎么产生的？你怎么处理？
2. 空值缓存有什么代价？TTL 设多长合适？
3. 空值缓存与真实数据的一致性怎么保证？
4. 缓存穿透、缓存击穿、缓存雪崩有什么区别？各自的解法是什么？
5. 布隆过滤器你们真上了吗？为什么上或不上？
6. 布隆过滤器的删除和预热问题怎么处理？

### 《参考解析》

**穿透的本质是「查不到」无法证明「不存在」。** 请求查询一个数据库里也没有的 key，缓存永远不命中，流量全部落到数据库；恶意构造大量不存在的 ID 打过来，数据库可能被压垮。常规三板斧是：接口层参数校验（负数、超长、格式不对直接挡掉）、空值缓存（查不到也写一个短 TTL 的空标记）、布隆过滤器（把所有可能存在的 key 预热进去，判定不存在就直接返回）。

```java
public User query(long id) {
    String key = "user:" + id;
    String cached = redis.get(key);
    if (cached != null) {
        return "NULL".equals(cached) ? null : parse(cached);
    }
    User user = userMapper.selectById(id);
    if (user == null) {
        redis.setex(key, 60, "NULL");   // 空值也缓存，TTL 短
        return null;
    }
    redis.setex(key, 1800, toJson(user));
    return user;
}
```

**空值缓存不是免费的。** 有团队把空值 TTL 设成 30 分钟以减少回源，结果被一波递增 ID 扫描撞上——每个 ID 都不存在，每个都种一个 NULL 进 Redis，两天后内存涨了近一倍。改进有两条：空值 TTL 压到 60 秒左右，够挡住瞬时重复请求即可；在网关层对同一 IP 短时间大量 miss 做限流。还有一点容易忽略：空值缓存与真实数据的一致性——如果这个用户后来注册进来、而空值还没过期，就会出现一段时间查不到，正确做法是写入时主动删除该 key，而不是干等 TTL 过期。

**穿透、击穿、雪崩三者解法不通用。** 穿透是 key 根本不存在，解法是参数校验、空值缓存、布隆过滤器；击穿是单个热点 key 过期的瞬间并发全部回源，解法是互斥锁重建或逻辑过期；雪崩是大量 key 同时过期或 Redis 整体不可用，解法是 TTL 打散、多级缓存、熔断降级。拿布隆过滤器去解雪崩是南辕北辙。回答时先说「先判断是 key 不存在，还是 key 存在但缓存没了」，再选工具。

**布隆过滤器的两个犹豫点。** 一是删除困难：普通布隆不支持删除，用户被删后位不会自动清掉，误判率会随时间上升，只能用计数布隆或定期重建；二是预热成本：几千万 key 初始化需要一个离线任务慢慢灌，还要有双写方案保证新增 key 不丢。对于一个日请求量不高的内部服务，为这点收益引入一个需要长期维护的组件并不划算——空值缓存加网关限流已经能兜住绝大部分问题。

**面试里的加分点。** 答完标准答案只是起点，真正拉开差距的是「你踩过哪个坑」和「为什么选 A 不选 B」。清单里的每一项都有成本与副作用：空值缓存吃内存、布隆过滤器要维护、限流会误伤正常用户。能把这些代价讲清楚，比背全三个方案有用。
