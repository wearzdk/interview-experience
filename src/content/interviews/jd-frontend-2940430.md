### 《参考解析》

**React 的更新链路与 Diff**：状态更新先进入调度，React 18 起由 `createRoot` 接管，更新按优先级进入 lane 模型，可中断的并发渲染让高优先级更新（输入、点击）插队。渲染阶段执行组件函数得到新的元素树，与上一次的元素树做 Diff，产出副作用列表；提交阶段再把变更一次性写入真实 DOM。Diff 建立在三条启发式上：只做同层比较、不同类型元素直接替换整棵子树、同层子节点用 `key` 做身份匹配。因此列表的 `key` 必须稳定唯一，用数组下标当 key 会在插入或排序时导致状态错位与多余重建。虚拟 DOM 的价值在于把「描述 UI」与「操作 DOM」解耦，使跨平台渲染与批量更新成为可能；它的开销也真实存在，节点极多时 diff 本身会成为成本，这时应减少节点数量而不是继续优化 diff。

**重渲染条件与避免大量重绘**：组件重渲染的触发源有四类：自身状态变化、父组件重渲染（未做 memo 时会连带渲染）、订阅的 context 或外部 store 变化、以及 `forceUpdate` 这类强制更新。重渲染不等于重排重绘，React 只在提交阶段比对差异后才操作 DOM，但渲染函数本身的开销与大量节点的 layout 仍会掉帧。手段按代价排序：先用 `React.memo`、`useMemo`、`useCallback` 稳定引用，把状态下沉到真正使用它的子组件，避免在顶层存放高频变化的值；长列表用虚拟滚动把 DOM 数量控制在可视区；高频输入用防抖或 `useDeferredValue`；动画与拖拽改用 CSS transform 与 `will-change`，避免触发 layout；确实需要脱离 React 调度时，用 `requestAnimationFrame` 批量提交画布重绘。

**XSS 防御与 Schema 校验**：XSS 分存储型、反射型与 DOM 型，本质是用户可控内容被当成代码执行。防御按位置分层：输出到 HTML 时做上下文相关的转义（文本、属性、URL、JS 各自规则不同），能用框架的自动转义就不要用 `dangerouslySetInnerHTML`；必须渲染富文本时用 DOMPurify 这类基于白名单的清洗器，并配置允许的标签与属性；设置 CSP 限制内联脚本与外部脚本源，Cookie 加 `HttpOnly`；URL 拼接做协议白名单，拦截 `javascript:`。Schema 校验用于数据结构而非安全，常见做法是用 zod 定义 schema，在接口返回、表单输入与本地存储读取三处统一 `parse`，失败时给出字段级错误；校验只能保证形状与类型，不能替代转义，两者职责不同，缺一不可。

**Zustand 订阅粒度的量化**：Zustand 基于 `useSyncExternalStore`，选择器返回值的引用变化会触发订阅组件重渲染，细粒度 selector 能减少无关更新，但每次 store 变更都要执行所有选择器并做相等比较，粒度过细会带来大量小函数调用与比较开销。定位瓶颈先用 React DevTools Profiler 记录交互，看哪些组件在提交阶段耗时最长、渲染次数是否异常；再在 store 变更处统计每次更新的订阅者数量与选择器执行耗时，用 `performance.mark` 打点，或用中间件记录每次 set 触发的重渲染组件集合。判断标准是「减少的渲染成本是否大于增加的选择器成本」，通常按组件边界划分而不是按字段划分，配套 `useShallow` 做浅比较，避免选择器返回新对象导致每次都判定为变化。验证方案可以做成对照实验：固定一组交互脚本，测量不同粒度下的提交耗时与帧率，粒度参数单变量推进，二分只是加速收敛的手段，前提是指标随粒度单调，否则应先修正指标定义。

**Vite 的分包与代码分割**：代码分割的触发点有三处：动态 `import()`、路由级懒加载、以及 `manualChunks` 手工划分。Vite 开发态用原生 ESM 按需加载，构建态交给 Rollup，动态导入会生成独立 chunk 并按需请求。自动分包是 Rollup 依据模块图与共享引用自动切分，common chunk 由 `output.manualChunks` 的默认策略或框架插件决定；手动分包则显式指定模块归属，适合把体积大且更新频率低的依赖（React、图表库、编辑器）单独拆出以利用长缓存。Vite 中在 `build.rollupOptions.output.manualChunks` 里配置，可写成对象映射或用函数按模块路径划分；拆得过细会增加请求数与首屏瀑布，判断依据是构建产物的 chunk 体积报告与真实环境的加载瀑布，而不是 chunk 数量本身。

**前后端升级冲突怎么推动**：先确认分歧的性质，是接口契约变更、排期冲突还是风险评估不同。把主张转成可验证的最小方案：前端先做兼容层，同时支持旧字段与新字段，灰度到小流量验证；给出接口调用的真实数据（调用量、错误率、受影响的用户比例）与回滚方案，降低对方的决策成本。讨论无果时把问题升级到共同的目标上，例如以版本发布节奏或线上故障数为约束，请双方主管或架构评审会裁决，而不是在个人之间反复拉扯。仍然被拒绝时，用数据证明必要性：旧接口的错误率与性能数据、新方案在预发环境的压测结果、以及不改会带来的具体风险与时间点。推动的过程要留书面记录，包括结论、责任人与时间节点。
