### 《参考解析》

**秒杀防超卖**：核心是「把扣减收敛到一个不会并发的点上」。分层做法：接入层用网关限流加答题/验证码削掉脚本流量，静态资源走 CDN；应用层用 Redis 做预扣，Lua 脚本保证「查库存—判断—扣减」原子执行（`if stock > 0 then decr` 一条脚本内完成），扣减成功才发消息进 MQ；消费端落库时再用 `update stock = stock - 1 where id = ? and stock > 0` 这种带条件的更新做最终兜底，影响行数为 0 就回滚 Redis。防重复下单靠「用户 ID + 商品 ID」的唯一索引或分布式锁，同一用户只允许一次。再往上还有库存分桶（把 100 件拆成 10 个桶各自扣，减少单键热点）、异步下单返回排队中、超时未支付回补库存。要主动说出取舍：Redis 预扣是「宁可少卖不可超卖」，弱一致性换吞吐。

**突发流量保护下游**：先分清是「冷门时段的突发」——即平时 QPS 很低、某一刻突然上来，缓存都是冷的。手段：请求侧排队与限流（令牌桶按下游真实容量配额度、不同接口分优先级，下单这类写请求优先于推荐这类读请求）；缓存预热（按历史访问模式提前加载热点，冷启动时用「缓存空值 + 短 TTL」防止穿透打穿 DB）；熔断降级（下游错误率或响应时间超阈值就快速失败、返回兜底内容，而不是把线程池和连接池耗光）；并发隔离（每个下游一个独立线程池/信号量，慢下游不能拖垮全站）；异步化（非关键路径改消息队列）。最后加弹性：冷门时段的突发往往是可预测的（活动、推送），提前扩容量。

**Agent 中断与续跑**：这是本场最容易答浅的题。要点是把「一次任务」建成可持久化的状态机，而不是一个长函数。做法：任务启动时给一个 `task_id`，每一步（模型思考、工具调用、工具结果）都作为事件顺序写入持久化的事件表或检查点（checkpoint），同时记录当前执行到哪个节点、上下文快照、已产生的副作用。用户打断时向执行器发取消信号，执行器在下一个可中断点退出（不能在工具调用中途硬杀，否则副作用状态不明），把任务标记为 paused。继续时按 `task_id` 从最近检查点恢复：重放事件重建上下文，已完成的工具调用不再重发（幂等键保证），从下一个未完成节点继续。两个必须提到的细节：工具调用的副作用要幂等或可补偿（发消息、写文件这类要带幂等键或先写意图日志）；取消要有超时兜底，长时间不响应就强制终止并标记为「状态不可信」，恢复时要求人工确认。

**Skill 编排与不跑偏**：编排上把 Skill 做成有前置条件与产出物的步骤图，每一步声明「需要什么输入、产出什么、失败怎么办」，由执行器按图调度，而不是把步骤写进一段提示词靠模型自觉。防跳步的四层：提示词里写清顺序与禁止项；执行器做程序化校验（该步的前置产出不存在就拒绝进入下一步，这层最硬）；工具层做兜底（工具内部校验参数与状态，比如「未确认收货不能退款」这类业务规则写在工具里而不是提示词里）；事后审计（把轨迹落库，按步骤覆盖率与跳步率做指标）。Skill 内容量要控制：只放模型不知道的流程与判据，通用知识交给模型，超长时按步骤分段加载而不是全量塞进上下文。

**上下文压缩与摘要**：压缩是无损或近无损的结构化裁剪——去掉重复的工具输出、截断大文件只留引用、把长 JSON 换成关键字段，信息还在只是更短；摘要是把一段历史用模型重写成短文本，必然丢细节且可能引入失真。工程上默认先压缩、必要时才摘要，并且摘要要保留「决策与结论」而不是流水账；被摘要掉的内容要留有引用（原始轨迹 ID）以便回溯。

**索引与 MVCC**：聚簇索引按主键组织数据，叶子节点就是行数据，一张表只有一个；二级索引叶子存的是主键值，所以要拿非索引列就得回表——先查二级索引拿主键、再回聚簇索引取整行。覆盖索引指查询需要的列全在索引里，不用回表，`explain` 里显示 `Using index`。MVCC 靠三个东西：行上的隐藏字段（`DB_TRX_ID` 最近修改事务、`DB_ROLL_PTR` 指向 undo 版本链）、undo log 里的旧版本、ReadView（记录当前活跃事务集合）。快照读时沿版本链找到「对本事务可见」的那个版本；RC 每次查询新建 ReadView，RR 只在第一次查询时建，这就是可重复读的实现。当前读（`select ... for update`、`update`）读最新版本并加锁。

**主从复制**：主库把变更写 binlog（`row` 格式最常用），从库的 IO 线程拉取并写入 relay log，SQL 线程重放。异步复制默认有延迟、主库宕机可能丢数据；半同步复制要求至少一个从库确认收到 binlog 才返回；组复制/并行复制用来提吞吐。追问常问「主从延迟怎么发现、怎么缓解」——用 `seconds_behind_master` 与心跳表监控，缓解靠并行复制、把大事务拆小、读请求按业务容忍度分流。

**Redis 热 Key**：先发现（客户端埋点统计 key 访问频次、`redis-cli --hotkeys`、代理层统计），再解决：本地缓存兜一层（带短 TTL 与失效通知）、把热 key 复制成多个副本分散到不同节点（`key:0..n` 随机读）、读写分离让从库分担读、限流降级避免一个 key 打满单核。要注意 Redis 单线程模型下热 key 的瓶颈是 CPU 而非网络。

**过期与淘汰**：过期策略是惰性删除（访问时检查）+ 定期删除（周期性抽样清理）。内存达到 `maxmemory` 时按策略淘汰：`noeviction`（写报错）、`allkeys-lru`、`volatile-lru`、`allkeys-lfu`、`volatile-ttl`、`random` 系列。缓存场景一般 `allkeys-lru` 或 `allkeys-lfu`（后者对偶发批量扫描更抗污染）。

**缓存与数据库一致性**：主流是 Cache Aside：读走缓存、miss 回源并回填；写先更新 DB 再删缓存（不是更新缓存），删失败就重试或走 binlog 订阅（Canal）异步删。延迟双删用于「删完缓存后并发读又回填了旧值」的场景。强一致要么加分布式锁把读写串行化（吞吐大跌），要么接受最终一致并给缓存设短 TTL 兜底。要主动说：任何方案都有窗口，业务能接受多大窗口才是设计输入。

**MQ 不丢不重**：不丢分三段——生产端开启 confirm/事务并处理回调重发；broker 端持久化（队列持久化 + 消息持久化 + 至少两个副本）；消费端手动 ack（处理成功才 ack，失败进重试队列，多次失败进死信队列人工处理）。不重靠消费端幂等：用业务唯一键（订单号）建唯一索引、或用「消息 ID + 处理状态」表做去重，重复消息直接丢弃。语义上只能做到 at-least-once，所以幂等是必须的，不能指望 exactly-once。

**JVM 与 GC**：算法层面是标记-清除（有碎片）、标记-复制（新生代，浪费一半空间但快）、标记-整理（老年代，无碎片但慢）、分代收集。分代假设是「绝大多数对象朝生夕死」：新生代用复制算法（Eden 与两个 Survivor，默认 8:1:1，对象在 Survivor 间来回搬、达到年龄阈值晋升老年代），老年代用标记-整理或标记-清除。常见收集器：Serial、Parallel（吞吐优先）、CMS（并发标记清除，已被废弃）、G1（分区 + 可预测停顿）、ZGC/Shenandoah（染色指针/读屏障，停顿毫秒级）。

**网络与操作系统**：HTTP 是明文、HTTPS 在 TCP 与 HTTP 之间加 TLS——握手阶段协商套件、验证书、用非对称加密交换对称密钥，之后用对称加密传数据，兼顾安全与性能；HTTPS 还能防篡改与中间人。TCP 拥塞控制四阶段：慢启动（拥塞窗口指数增长到阈值）、拥塞避免（线性增长）、快重传（收到三个重复 ACK 立即重传）、快恢复（减半后继续拥塞避免）；现代实现有 CUBIC/BBR。进程创建开销在于分配 PCB、复制页表、拷贝父进程地址空间（`fork` 用写时复制把拷贝推迟到真正写入时）；进程切换要换页表导致 TLB 失效、刷新流水线，所以比线程切换贵。线程太多的问题在于每个线程一份栈（默认 1MB 起）与内核调度结构、上下文切换占 CPU、锁竞争加剧、缓存局部性变差，线程池的意义就是把这些成本固定下来。

**虚拟内存**：见上，重点是「隔离 + 按需 + 共享 + 可换出」，以及缺页中断是唯一的补充路径。
