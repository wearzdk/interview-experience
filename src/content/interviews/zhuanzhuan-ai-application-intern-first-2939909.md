### 《面试题目》

1. 请做个自我介绍。
2. 你现在是什么状态？
3. 上一份实习离职的原因是什么？
4. 讲一讲你在上家公司做的项目。
5. 在这个项目里你承担的职责是什么？
6. 日常团队是怎么协作分工的？
7. 你怎么看待现在 AI 背景下岗位边界模糊这件事，你的择业方向大概是什么样的？
8. 找实习是否希望岗位有 headcount？
9. 我们这边希望实习生稳定实习 3–4 个月以上，你这边能不能满足？同时你还要准备秋招，这块怎么平衡？
10. 你做的 RAG 是传统基于语义相似度召回的 RAG 吗？
11. 对于知识图谱、GraphRAG 这块有了解吗？
12. 谈谈业务场景下，单 Agent 跟多 Agent 分别适合什么场景？什么时候用单 Agent，什么时候用多 Agent？
13. 简单任务、复杂任务是由你们自己区分，还是会在业务场景下对比不同方案效果？
14. 你了解 FDE 这个角色吗？
15. 你这边有什么想要了解的？

### 《参考解析》

**稳定性怎么答**：面试官反复问实习时长与秋招平衡，说明这个岗位的真实风险是「人来了两个月就走」。回答要给可验证的承诺：明确能到岗的日期、每周几天、能连续几个月；秋招安排讲清楚（已经投递完 / 集中在一段时间 / 可以线上面），并说明你会怎么把面试集中到非工作时间。不要为了拿 offer 硬承诺一个做不到的时长，入职后断裂对双方成本更高。

**离职原因**：讲事实与判断，不评价前东家与人。结构可以是「实习目标（想做什么）—实际情况（做的是什么）—差距—因此选择换一个更贴近目标的环境」。避免「太累」「学不到东西」这类无法验证的说法。

**岗位边界模糊怎么看**：AI 让「一个人能做完整链路」成为可能，边界模糊的真实变化是：产品、前端、后端、算法的交接点从「人」变成了「产物」（原型、prompt、评测集）。择业方向可以落在「能把业务问题翻译成 AI 方案并交付上线」的位置，也就是既懂业务又懂工程，而不是只做某一层的实现。这个回答和 FDE 岗位的定位是吻合的。

**传统 RAG 与 GraphRAG**：传统 RAG 是把文档切块、向量化、按语义相似度召回 top-k 再拼进上下文，优点是实现简单、延迟低，缺点是对「跨文档、多跳、需要全局归纳」的问题不擅长——它只会捞回和问句字面语义接近的片段。GraphRAG 先用模型从文档里抽实体与关系建图（社区检测、分层摘要），查询时可以沿关系扩展、也可以先用社区摘要回答全局性问题。代价是建图成本高、更新麻烦，适合实体关系密集、问题需要多跳推理的知识库（规章制度、故障排查、法律条文）。落地时常见的组合是「向量召回打底 + 图扩展补充 + 结构化过滤」，而不是二选一。

**单 Agent 与多 Agent**：单 Agent 适合任务边界清晰、工具数量可控（十几个以内）、上下文能装下的场景，调试和观测都简单，成本也低。多 Agent 适合三类情况：任务可以明确拆成角色（检索、写作、审核）且每步的上下文差异极大；需要并行处理多个独立子任务；需要「一个执行、一个审查」的对抗结构来提高质量。不应该用多 Agent 的情况更多：拆完之后 Agent 之间要来回传大量上下文、错误在链路里放大、token 成本翻几倍、出了问题定位不到是哪一环。判断标准不是「复杂就用多 Agent」，而是「拆开之后每一环的上下文是否更干净、是否可独立验证」。

**简单任务与复杂任务怎么区分**：工程上一般不做静态分类，而是用「路由 + 对比」：先用规则或小模型判断（意图、是否需要检索、是否需要多步），再用 A/B 或离线评测对比两套方案的效果与成本，数据说话。帖主的回答是「会在业务场景下对比不同方案效果」，这是更稳的答法；如果能补一句「对比时看任务完成率、平均轮数、单次成本三个指标」，说服力更强。

**FDE 是什么**：Forward Deployed Engineer，源自 Palantir 一类公司的交付模式——工程师前置到客户业务现场，理解真实流程，把通用平台能力改造成能解决这家客户问题的方案，再反哺产品。在 AI 应用里，FDE 的日常是：梳理业务场景与数据、设计 prompt 与工具链、搭评测集、做试点与培训、把共性问题沉淀成平台能力。它要求技术能力 + 业务理解 + 沟通，和纯研发的差别在于交付对象是「业务结果」而不是「功能」。

**反问可以问什么**：这个岗位的具体交付物是什么（内部系统、客户项目还是平台能力）、实习生会独立负责哪一块、团队现在用的是什么模型与工具链、转正与 headcount 的情况。问这些能显示你在认真评估匹配度，也能帮你判断这是不是「业务提效」而不是「给销售做 demo」。
