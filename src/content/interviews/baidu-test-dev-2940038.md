### 《参考解析》

**软件生命周期**：需求分析 → 计划 → 设计 → 编码 → 测试 → 发布 → 运维/维护，常见模型有瀑布、V 模型、敏捷迭代、DevOps 持续交付。测试在不同阶段的对应物：需求评审时做可测性分析、设计阶段写测试方案、编码阶段做单元测试、集成阶段做接口测试、系统阶段做功能与性能、上线后做监控与回归。答这题要能说出「测试不是最后一道工序」。

**测试用例的组成**：用例编号、标题、前置条件、测试数据、操作步骤、预期结果、优先级、用例类型（功能/边界/异常/性能/安全）、关联需求。设计方法：等价类划分、边界值、判定表、因果图、正交实验、场景法、错误推测。写用例时要覆盖正常流、异常流、边界与并发。

**Linux 排查命令**：`top`/`htop`（CPU、内存）、`free -h`、`df -h`/`du -sh`（磁盘）、`iostat`/`iotop`（IO）、`ss -lntp`/`netstat`（端口与连接）、`ps -ef`/`pgrep`、`tail -f`/`grep`/`awk`（日志）、`strace`（系统调用）、`lsof`（文件句柄）、`dmesg`（内核日志）、`journalctl`（服务日志）、`curl`/`tcpdump`（网络）、`vmstat`/`pidstat`（性能）。要能说「我用哪个命令定位过什么问题」。

**QPS 口径**：QPS 是「每秒成功处理的请求数」，必须附带条件才有意义：并发数、请求的读写比例、数据量、硬件规格、是否命中缓存、P95/P99 延迟、错误率。3000 QPS 可能来自压测工具（JMeter/wrk/locust）在 N 并发下持续跑 M 分钟的平均值，也可能是监控统计的峰值。面试官追问「多少并发下得出」，就是在检查你有没有真的压测过——「3000 QPS 在 200 并发、P99 80ms、读多写少、4 核 8G 单机」才是完整表述。

**Agent 与 Harness**：Agent 是「能感知、决策、行动」的智能体，核心是模型 + 工具 + 循环；Harness 是承载它的执行框架，负责工具注册与调用、上下文管理、循环控制、错误处理、权限与沙箱、轨迹记录。两者是「驾驶员与车」的关系：模型决定做什么，Harness 决定能做什么、怎么执行、怎么被观测。区别在于 Agent 偏「策略」，Harness 偏「基础设施」。

**ReAct 为什么要双层循环**：外层是「任务级」循环——判断整体目标是否完成、决定下一步做什么；内层是「步骤级」循环——一次工具调用后的结果解析、参数修正、重试。单循环也能实现（把所有逻辑塞进一个 while），但会导致：终止条件混乱、错误处理与任务规划耦合、上下文难以裁剪、调试时无法区分「任务没完成」和「这一步失败了」。双层结构把「策略」与「执行」分开，便于加超时、重试、人工确认与轨迹记录。单循环适合简单任务（固定几步、无分支）。

**Agent 评估的细粒度手段**：端到端看任务完成率；细粒度看：单步工具选择的准确率、参数正确率、工具调用次数与冗余步骤、轨迹是否走了最短路径、错误恢复成功率、上下文长度与成本、延迟分布、以及「在哪些类型的子任务上失败」。方法上有规则断言、状态检查（执行后环境是否达到预期）、LLM-as-judge（带 rubric）、人工抽检、以及用「固定任务集 + 可复现环境」做回归。

**手撕与排查引导**：最长不重复子串用滑动窗口 + 哈希表记录上次位置；要求输出子串就要额外记录起点。面试官引导排查编译报错、作用域、命名，说明测试岗看重「读代码与定位问题的能力」——写完代码要主动检查：变量是否在使用前定义、循环边界是否正确、返回值类型是否匹配、命名是否清晰。

**岗位认知**：测试开发不是「点点点」，而是用工程手段保证质量：写自动化用例、搭测试平台、做性能与稳定性测试、白盒审查、用 AI 辅助生成用例与评估 Agent。反问可以问团队负责的业务、自动化覆盖率、以及测试在发布流程中的卡点。
