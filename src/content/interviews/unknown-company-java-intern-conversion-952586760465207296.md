### 《参考解析》

**混合检索的融合方式**：两路（向量召回与关键词召回，如 BM25 / ES）分数量纲不同，不能直接相加。常用做法有三类：一是倒数排名融合（RRF），只取名次、按 `Σ 1/(k + rank)` 计算，对量纲不敏感、实现简单，是默认起点；二是加权分数融合，先把每路分数归一化（min-max 或 z-score）再按权重相加，权重靠离线评测调；三是先各自召回 Top-K，合并后用 cross-encoder 重排模型统一打分，效果最好但延迟高。工程上常见组合是「RRF 粗排 + 重排模型精排」，并对两路结果做去重（按文档 id 或内容指纹）。回答时要说明为什么选这种融合（量纲、延迟、可调性）以及评测上带来的提升。

**检索优化的抓手**：查询侧做改写与扩展（同义改写、错别字纠正、多查询、HyDE）；切分侧调 chunk 大小与重叠、按标题层级切、给 chunk 加上下文摘要；索引侧加关键词字段、做多语言 embedding 或按语言分库；召回侧调 Top-K、加元数据过滤（学科、年级、题型）；排序侧加重排与业务规则（优先最近教材版本）；最后是缓存与降级。每项都要能用评测集证明收益，否则只是堆技术。

**评测集怎么建**：先定义任务与指标（召回率@K、MRR、答案正确率、引用准确率），再从真实日志里采样查询（按频次分层，别只挑简单的），为每条查询标注「相关文档 / 标准答案」，规模不必大（几百条即可起步），但要覆盖长尾与边界（多语言、表格、公式、无答案的问题）。用 LLM 辅助标注时必须人工抽检，并固定一份 holdout 不参与调参，避免过拟合。上线后把线上 bad case 回流进评测集，形成闭环。

**中越混合文档的处理**：先做语言识别（按字符集或 fastText），中文按字、越南语按词（越南语是拉丁字母、带声调符号，需要分词与 Unicode 规范化，注意 NFC/NFD 两种形式要统一）。检索上用多语言 embedding（如 multilingual-e5、bge-m3）或按语言分索引后合并结果；切分时避免把两种语言切进同一个 chunk 导致语义漂移；答案生成时要求模型用提问语言作答，并在 prompt 里声明文档可能含多语言、引用原文时要保留原文。若数据里中文与越南语是「同一道题的两种表述」，可以做对齐后只索引一份。

**规则 + 大模型双路判定怎么结合**：规则负责高确定性与可解释的部分（命中白名单、格式校验、明确的错因模板），模型负责语义判断与开放情况。结合方式按置信度分层：规则命中且置信度高直接出结果；规则与模型一致时直接采用；不一致时进入仲裁（升级到更强的模型、或用第二个 prompt 复核、或转人工）；两者都没把握时给默认结果并记录待复核。要避免「模型覆盖规则」和「规则压死模型」两种极端，把每路的准确率与覆盖率分开统计，再决定阈值。

**FactStore 的字段设计**：至少包含 `fact_id`、`session_id`、`subject`（主体，如学生/题目）、`slot`（槽位，如「答案」「错因」「掌握程度」）、`value`、`source`（哪一轮、哪条消息、原文片段）、`confidence`、`valid_from`、`superseded_by`（被哪条新事实替代）、`created_at`。覆盖旧值时不要原地改，而是插入新版本并把旧记录标记为失效（软删除 + 指针），这样既能追溯「用户什么时候改的」，也能在冲突时回滚。查询时只取 `superseded_by` 为空的最新版本。

**长对话压缩怎么不丢信息**：分层做——原始消息全量落库（这是唯一可信源），上下文里放「摘要 + 关键事实 + 最近 N 轮原文」。摘要按段滚动生成（旧段摘要 + 新段原文 → 新摘要），关键事实抽到 FactStore 外置，不依赖摘要携带。第二次压缩时不要对「上一轮摘要」再摘要（信息会指数衰减），而是用「上一轮摘要 + 新增原文」重新生成一份覆盖全历史的摘要，并保留原始消息 id 以供回溯。判断信息是否丢失要看评测：抽一组需要早期信息才能回答的问题，压缩前后各跑一遍，掉分就说明摘要策略有问题。真正不可丢的内容（用户明确陈述的偏好、已确认的结论）一律进事实表，而不是留在摘要里。

**多会话并发与会话状态**：每个会话一个独立的状态容器（按 session_id 分片），状态读写走同一把会话级锁或单写者队列，避免两个请求同时改同一份历史；跨会话共享的只有用户级事实与配置。状态持久化上，热数据放 Redis（带 TTL）、冷数据落库，写入用「先写库再更新缓存」或事件日志，重启后从库恢复；关键是区分「可重建的」（上下文可由消息表重建）与「不可重建的」（模型已生成但未落库的中间结果），后者要显式持久化或设计成幂等重算。

**Git 冲突怎么处理**：先 `git status` / `git diff` 看清冲突文件与冲突块，理解双方的意图（谁改了什么、为什么），再决定保留、合并还是重写；小冲突直接在编辑器里解决并删掉冲突标记，大冲突用 `git checkout --ours/--theirs` 取一侧后再手工补另一侧的语义。解决后 `git add` 标记已解决、跑测试再提交。预防手段是频繁拉取、小步提交、按模块划分文件所有权、对生成文件（lock、构建产物）加 `.gitattributes` 或干脆不入库。团队协作里 code review 与保护分支比事后解冲突更有效。
