### 《参考解析》

**指针与数组**：数组名在表达式里退化为指向首元素的指针，但 `sizeof` 对数组给整个数组大小、对指针给指针宽度；`&arr` 的类型是「指向数组的指针」，`arr+1` 与 `&arr+1` 步长不同。函数形参写成 `int a[]` 实际就是 `int *a`，无法在其中求长度。typedef 是类型别名、受作用域约束、由编译器处理；define 是预处理期文本替换、没有类型检查，宏参数多次求值还会引发副作用，所以常量与类型用 typedef/const/enum，只有需要条件编译或字符串拼接时才用宏。

**内存分布与对齐**：代码段放指令与只读常量，数据段放已初始化的全局与静态变量，BSS 放未初始化（或初始化为 0）的全局与静态变量，堆向上增长由 malloc 管理，栈向下增长放函数调用帧与局部变量。对齐是为了让 CPU 用一次总线事务取到数据：结构体每个成员按自身对齐要求放置，中间填填充字节，整体大小再补齐到最大成员对齐的整数倍，所以成员顺序会影响结构体大小，把大类型排前面通常更省空间。联合体所有成员共享同一块内存、大小取最大成员，常用于类型双关、协议报文的多种视图，或省空间的变体表示。

**野指针与悬空指针**：野指针是未初始化的指针，悬空指针指向已释放或已失效的对象（free 之后、函数返回后的栈地址）。避免方式：定义即初始化、free 之后立即置 NULL、释放前先判断、用带长度信息的接口替代裸指针、开启编译告警与静态检查（-Wall -Wextra、ASan、静态分析），以及明确所有权约定。

**I2C 的工程细节**：标准模式 100kHz、快速模式 400kHz、快速加 1MHz、高速模式 3.4MHz；7 位地址理论上 112 个可用（保留地址除外），实际受总线电容 400pF 限制，挂太多会导致上升沿变缓。NACK 排查顺序：从机是否上电与复位、地址是否含读写位搞反、上拉电阻与总线电容、时序是否超出从机支持、从机是否忙或处于写保护。总线被拉低不恢复的典型原因是某从机在传输中途复位，把 SDA 一直拉低形成死锁；恢复办法是手动时钟脉冲——把 SCL 当 GPIO 输出 9 个时钟，让从机把剩余位吐完，再发一个 STOP，然后重新初始化控制器。i2cdetect 扫描地址、i2cget 读寄存器、i2cset 写寄存器，配合示波器或逻辑分析仪看波形。

**SPI 四种模式**：CPOL 决定空闲时钟极性（0 低、1 高），CPHA 决定在第一个还是第二个边沿采样（0 第一边沿、1 第二边沿），组合出 mode 0 至 3。主从必须同模式，否则数据整体错位一位。传输出错先确认模式与位序（MSB/LSB first）、片选时序与片选间的间隔、时钟频率是否超过从机上限、走线与地回流（长线引起过冲与振铃），再看 MISO 采样点是否落在数据稳定窗口内。

**设备树与 platform 总线**：内核把设备树里的节点展开成 platform_device（或 i2c/spi 设备），驱动用 `of_match_table` 里的 compatible 与节点的 compatible 匹配，匹配成功调用驱动的 probe。设备树的价值是把板级硬件描述（地址、中断号、GPIO、时钟、引脚复用）从驱动代码里分离出去，同一份驱动源码可以配不同板子，改硬件只改 dts 不改驱动——这正是早年板级文件（board file）时代每个板子一份 C 代码的问题所在。DTS 是板级文件，DTSI 是可被 include 的公共描述（SoC 级），编译成 DTB 供内核解析；覆盖规则是后包含的节点按路径合并、同名属性后者覆盖前者，删除用 `/delete-node/` 与 `/delete-property/`。

**字符设备与 open 路径**：字符设备驱动注册主次设备号（alloc_chrdev_region）、初始化 cdev 并 cdev_add、创建 class 与 device 节点；用户 open `/dev/xxx` 时内核按 inode 的设备号在 cdev_map 里找到 cdev，取出其中的 file_operations 填进 struct file，再调用 fops->open。read/write 走 `copy_to_user`/`copy_from_user` 与内核缓冲，ioctl 用于非数据类控制命令（配置、读写寄存器、启动采集）。不让用户态直接操作寄存器，是因为需要权限与地址空间隔离、需要串行化并发访问、需要把硬件差异封装成稳定接口，否则一个用户态越界写就能让整个系统崩溃。

**中断上下半部**：硬件中断到来后，CPU 保存现场、跳中断向量、执行驱动注册的 handler。上半部在关中断或屏蔽同号中断的上下文里运行，不能睡眠、要尽快返回，只做「确认中断源、取走数据、清标志、唤醒下半部」；下半部承担耗时处理。softirq 与 tasklet 运行在中断上下文（BH 被禁用），不能睡眠；workqueue 把工作交给内核线程，运行在进程上下文，可以睡眠、可以做 I2C 读写与内存分配。所以「中断里为什么不能睡眠」的答案是：睡眠意味着让出 CPU 并可能触发调度，而中断上下文没有关联的任务结构，调度器无法保存与恢复它的上下文，也无法被唤醒。

**自旋锁与互斥锁**：自旋锁忙等、不睡眠，适合临界区极短且不能睡眠的场合，中断上下文只能用 spinlock，并且要用 `spin_lock_irqsave` 关本地中断避免死锁；互斥锁在争用时睡眠，适合可能长时间持锁、临界区内需要睡眠（等 I/O、分配内存）的场合，不能在中断上下文使用。多核之间的抢占与中断都会影响选择，判据是「这段代码可能运行在什么上下文、持锁期间会不会睡眠」。

**启动与开机时间优化**：U-Boot 阶段可裁剪无用驱动与命令、关掉串口打印与延时、跳过不必要的自检、用 SPL 直接加载内核并传递已初始化的外设状态；内核阶段可裁掉不用的子系统与驱动、把必须的驱动编进内核而不是模块、关闭不需要的调试与 printk、并行化 probe（`-EPROBE_DEFER` 处理依赖顺序）、用 initramfs 或直接挂载；用户态阶段用 systemd 的 `systemd-analyze blame/critical-chain` 找串行链路，把非关键服务改为按需启动或延后。压到 5 秒要先测基线并画出启动时间线，找出最长的串行段，逐段定目标，每次改动都复测同一口径（从上电到某个可服务标志），否则只是把时间挪到了别处。

**内存异常与性能排查**：段错误先看 dmesg 的 oops 信息（出错地址、调用栈、是读还是写），有 core dump 就用 gdb 看 backtrace、寄存器与出问题的变量，没有就开 core_pattern 或改用 coredumpctl；strace 看系统调用在哪里失败（EACCES、ENOENT、ENOMEM）；内存泄漏用 valgrind 或 ASan，内核态用 kmemleak。性能瓶颈先分清是 CPU、内存、I/O 还是锁：top/pidstat 看 CPU 与上下文切换，free 看内存与 swap，iostat 看磁盘，perf top/record 找热点函数，perf trace 看系统调用，ftrace 看调度延迟与中断关闭时长。不要一上来就调参数，先定位到具体的资源。

**丢包与 MTU**：tcpdump 在两端同时抓，比对同一序号是否在发送侧出现、在接收侧缺失，就能区分「没发出去」还是「路上丢了」或「上层没读走」；Wireshark 看 TCP 重传、零窗口、RST、重复 ACK 与乱序。MTU 是链路层单帧可承载的最大数据量，以太网 1500，路径上某段更小又没做 ICMP 分片通告（PMTUD 被防火墙丢弃）就会出现大包不通、小包正常，表现为握手成功但传大文件卡住。可调参数包括 socket 收发缓冲、拥塞控制算法、`tcp_rmem/wmem`、`tcp_fastopen`、`tcp_tw_reuse` 等，但先确认瓶颈在带宽、时延还是丢包，再动参数。

**已交付驱动的稳定性验证**：把改动限定在最小范围并记录基线；跑长时间压测（连续读写数小时至数天）观察内存与句柄是否增长；做异常注入（总线拔插、从机掉电重启、超时与 NACK、并发打开与关闭、中断风暴）；做电源循环与休眠唤醒各若干轮；对比改动前后的错误日志计数与性能指标；在真实板子上而不是只在开发板上验证。上线后保留可回滚的固件与配置，并给现场留一份故障自检清单。
