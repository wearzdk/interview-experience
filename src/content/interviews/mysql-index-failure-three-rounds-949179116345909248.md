### 《面试题目》

1. 说说索引失效的场景。
2. 联合索引 (a, b, c)，`select * from t where a = 1 and b > 2 and c = 3`，c 还能用上索引吗？是完全没参与，还是参与了？
3. 隐式转换的方向为什么关键？`phone` 是 varchar 查数字、`age` 是 int 查 `'18'`，哪条会失效？
4. 索引没失效、条件也满足最左前缀，优化器还是不走索引，可能是什么原因？
5. 只有「区分度低」这一个原因吗？
6. 看到没走索引就 `force index`，合适吗？
7. 你现在固定的排查顺序是什么？

### 《参考解析》

**第一轮：范围之后的列算不算失效**。`WHERE a = 1 AND b > 2 AND c = 3` 中 c 没法用来定位扫描区间，但可以参与过滤。`EXPLAIN` 的 `key` 能看到索引用上了，`Extra` 里可能出现 `Using index condition`，这就是索引条件下推（ICP）：存储引擎遍历 `b > 2` 那段索引时顺手把 `c = 3` 在索引上比一遍，不满足的直接丢掉，少回表几次。所以「失效」这个词不准确，准确的描述是「不能用来缩小扫描范围」。很多八股文说 c 完全用不上，是偷懒的说法。

**第二轮：隐式转换的方向**。`phone` 是 `varchar`、`WHERE phone = 13800000000` 会失效——字符串与数字比较时把字符串转成数字，索引上的字符串顺序就废了；`age` 是 `int`、`WHERE age = '18'` 不失效——转的是常量侧，列本身类型没变。帖主在实习里真踩过：后台查询接口前端把 `order_no`（varchar）当数字传，本地几百毫秒看不出问题，上线后几十万行的表直接超时，`EXPLAIN` 一看 `type=ALL`、`rows` 是全表行数，才反应过来是引号丢了。习惯是看到慢查询先看 `type` 与 `rows` 估算的真实扫描量，别急着怀疑索引建得不对。

**第三轮：优化器为什么不走**。除了区分度低，还有几种：回表量太大，条件筛完还剩大部分行，二级索引扫一遍再回表比全表扫更贵；统计信息过期，`ANALYZE TABLE` 很久没跑，优化器对数据分布判断错了；排序与分组，`ORDER BY` 的列和索引顺序对不上，走索引反而要额外排序（`Using filesort`），也就放弃了。

**`force index` 慎用**：除非确认统计信息没问题、且业务查询模式稳定，否则不要随手强推——换个数据分布可能更糟。优先改 SQL 或调整索引顺序。

**固定排查顺序**：先 `EXPLAIN` 看 `type`、`key`、`rows`，再看 `Extra` 里有没有 `Using index condition` 或 `Using filesort`，最后才去怀疑 SQL 本身有没有函数、类型转换、前导 `%` 这类问题。

**这场面试的收获**：面试官连追三次，其实是在确认你是否真的看过 `EXPLAIN`、是否理解优化器在做成本选择。八股能过简历关，但被追两层，还是得靠线上被慢查询教育过的经历。
