### 《面试题目》

一、内化机制

1. 模型内化的核心设计目标是什么？只是为了省 token 吗？
2. 长期内化通用知识，会不会累积偏差，最后变成幻觉？
3. 知识冲突发生了怎么处理？以谁为准？
4. 相比纯检索、纯长上下文，内化除了省 token 还有什么增益？
5. 传统 RL 和常规对齐已经够用了，你这套流程不可替代在哪？
6. 内化的知识，你能否溯源到原始数据？
7. 用户问一个和内化内容矛盾的新事实，你的系统怎么办？
8. 内化之后模型的通用能力会不会退化？怎么测？
9. 如果只能保留内化或检索中的一个，你保哪个？

二、训练流程

10. 你这套框架的 Agentic 特性具体落在哪几个模块？
11. 哪些环节是真自主决策，哪些其实还是固定流程？
12. 训练耗时不均衡、算力大量压在 rollout，你怎么优化？
13. 推理阶段 GPU 利用率低，除了加卡还有什么办法？
14. 异步 rollout 会带来什么新问题？
15. prefix cache 在这个场景能复用到什么程度？
16. 你设计了哪些指标验证内化的真实提升？
17. 怎么区分「提升了」和「测出来提升了」？

三、灵魂拷问

18. 你这套框架本质上是不是自动搜参？和自动调参的差异化在哪？
19. 把方案砍掉一半，你砍哪一半？
20. 如果给你同样的预算但只许做一个方向，你选什么？

手撕：实现一个异步批量推理调度器，把到来的请求按 token 预算打包成 batch，单个请求等待超过 T 毫秒必须强制出队，且不能超过最大并发。

### 《参考解析》

1. **内化的目标不只是省 token**：真正的目标是让模型在没有外部上下文时也具备领域判断力——减少对检索质量的依赖、降低首字延迟、让推理链更短。省 token 是附带收益，不是设计目标。答「为了省 token」会被追问「那为什么不直接缩短 prompt」。

2. **内化会不会累积偏差**：会。持续用自己生成的数据训练会放大已有偏差（模型自噬），幻觉也会被当成事实固化下来。防护手段是保留高质量原始语料的比例、定期用人工标注集校准、监控输出分布偏移、以及让检索在冲突时拥有更高优先级。

3. **知识冲突以谁为准**：按「时效性 + 权威性」定优先级：实时业务规则和数据库事实 > 官方文档 > 模型内化知识。工程上要在提示里明确「当内化知识与检索结果冲突时以检索为准」，并在答案里标注来源。

4. **内化相比检索的增益**：一是延迟（不用等检索）、二是鲁棒性（检索服务挂了仍能回答）、三是推理连贯性（不用把长文档塞进上下文，注意力不被稀释）。代价是更新慢、不可溯源、不好纠错。

5. **不可替代性怎么答**：要能说出「哪些问题检索解决不了」——需要跨文档推理的、需要隐式常识的、检索召回不到但模型见过的。如果答不出来，说明方案确实可以被「检索 + 长上下文」替代，面试官就是在等这个。

6. **溯源**：内化后无法逐条溯源，这是它的根本缺陷。缓解办法是记录训练数据的来源与版本、对关键结论保留引用索引、以及在回答时同时触发一次检索做校验。

7. **通用能力退化**：用一组固定的能力评测（通用问答、代码、数学、指令遵循）做回归，对比训练前后的分数；同时看输出分布的熵和长度变化。只测目标任务是测不出退化的。

8. **rollout 慢怎么优化（核心题）**：把采样和训练解耦。同步做法是采一批、等齐、训练、再采样，中间 GPU 大量空转；改成异步后采样引擎持续产出、训练侧按批次消费，允许一定程度的 stale 并用 importance ratio 修正。不花钱的部分还有：控制生成长度、按难度分组采样、复用 prefix cache、把短样本优先打包。

9. **异步 rollout 的新问题**：数据陈旧导致 off-policy 偏差变大；长尾样本拖慢整体节奏，需要丢弃或分段回收；采样和训练抢同一批卡，需要做资源配额和隔离。

10. **prefix cache 能复用到什么程度**：同一个 prompt 采样 G 条时前缀完全一致，命中后每条只需算增量，收益最大；组内如果改了温度或加了随机前缀，命中率就掉。工程上要保证系统提示和工具定义在前缀里固定不变，会变的状态追加到末尾——这既是缓存友好的写法，也是多轮对话的基本设计原则。KV 显存要按 G 条并发估算，超了就减小 G 或分批。

11. **怎么区分真提升和测出来提升**：留出独立测试集、做多随机种子重复实验、看置信区间而不是单点、用对抗性样本和分布外样本验证、以及做消融确认提升来自你说的那个改动。还要防「测试集泄漏」和「评测 prompt 过拟合」。

12. **把方案砍一半砍哪半**：砍掉对最终指标贡献最小、维护成本最高的模块，保留「数据构造 + 训练 + 评测」这条主链。回答时要给出判断依据（消融数据），而不是凭感觉。

13. **手撕：异步批量推理调度器**：维护一个按到达时间有序的等待队列和一个新请求缓冲；每轮先算可用 token 预算，从队头贪心取到装不下为止；计时器扫描队头，超时的请求强制放入当前 batch 并标记 forced。三个坑：超时请求本身可能超过预算要单独放行、新请求优先级过高会让老请求饥饿所以要留余量、forced 请求不能因为 batch 满被挤掉否则超时承诺失效。请求量涨十倍时队列积压会导致超时的批量放行、单批过大，需要加硬上限并开始拒绝——这也是「第一天能跑、第三个月会炸」的典型，要提前说清炸在哪和怎么加监控。
