### 《参考解析》

**SaaS 的 RBAC 比单机版多两层**：经典 RBAC 是「用户—角色—权限」三层，SaaS 里必须再加租户隔离与数据权限。租户隔离要落到存储层：所有表带 `tenant_id`，唯一索引和查询条件都必须包含它，否则跨租户串数据是迟早的事（可以用行级过滤或中间件强制注入条件来防止漏写）。数据权限是第二个维度：同一个人在不同范围（自己、本部门、全公司）能看到的行不同，常见做法是「功能权限用角色控制，数据范围用角色上挂的 scope 字段控制」，查询时按 scope 拼条件。再往上要注意三点：角色继承与最小权限（别把 admin 当默认角色用）、权限判定的入口收敛到统一的鉴权函数（避免散落在业务代码里）、以及权限变更后的缓存失效（用户量大的时候鉴权结果要缓存，改角色就得让缓存立刻失效）。审计日志是 SaaS 的硬需求，谁在什么时候对哪条数据做了什么必须可回溯。

**文件权限场景题：把「谁能对什么做什么」拆开**：回答这类场景题，先问清场景的约束（是网盘、知识库还是代码仓库？有没有共享和外部链接？），再给三层模型。第一层是所有权与分组：文件有 owner、可以归到目录或项目组，权限按目录继承（新建文件默认继承父目录的 ACL），避免逐个文件配置。第二层是操作粒度：读、写、删除、分享、下载分开授权，尤其是「可见」和「可下载」要分开——很多泄露都发生在只能预览的文档被直接下载。第三层是共享与外部访问：分享链接要带有效期、可撤销、必要时带提取码，服务端用预签名 URL 而不是把真实路径暴露出去，下载前必须再校验一次权限（防止拿到 URL 就越权）。工程上最容易出事的是 IDOR（改一下 URL 里的文件 ID 就能拿到别人的文件），所以任何按 ID 取文件的接口都要先做「资源归属校验」，并且把 `share` 与 `read` 两条路径都覆盖。

**Outbox：解决「数据库写了、消息没发出去」的经典模式**：本地事务和消息投递无法原子，直接把发消息写在事务里会出现两种不一致：事务回滚了消息已发出，或者事务提交了消息丢失。Outbox 的做法是在同一个数据库事务里写业务表和一张 outbox 表（记录事件类型、载荷、状态、重试次数），事务提交后由独立的投递器（轮询扫表或用 binlog 订阅）把未投递的记录发到 MQ，成功后标记已发送。要讲清四个配套细节：投递是 at-least-once，所以消费端必须幂等（用事件 ID 去重）；投递器要支持多实例抢锁或按分片捞取，避免重复投递同一批；失败要指数退避并限制重试次数，超限落死信并告警；已发送的记录要定期归档清理，别让 outbox 表无限膨胀。面试官常追问「用轮询还是有 CDC」，答法是：轮询实现简单、延迟可控（秒级），CDC 延迟更低但对运维要求更高，按业务对延迟的容忍度选。

**token 超额与结构化输出是同一类工程问题：先把不确定性关起来**：token 超额的治理顺序是「限额 → 预算 → 降级」。限额按租户、用户、单请求三层设，超限直接拒绝或排队并给出明确提示；预算用来做成本控制与告警（按会话累计，超过阈值降级）；降级路径要预先定义好，比如只保留最近几轮上下文、把长工具输出截断成摘要、切换更小或更便宜的模型、把非关键步骤去掉。要能指出来：prompt 压缩和上下文裁剪必须保业务关键信息（ID、约束），不能无脑截断末尾。结构化输出方面，首选工具调用或 JSON Schema 约束解码，让模型在解码阶段就不可能产出非法结构；其次服务端必须再校验一次（schema 校验 + 业务校验），校验失败就把错误原文回灌让模型修复，最多重试一两次；最后要有兜底——把失败样本落库、返回可读的降级结果，而不是把半截 JSON 直接返回给前端或写库。

**邮箱回执这个追问，考的是「别把提交当送达」**：SMTP 交互里服务端返回的 250 只代表「已接收」，不等于对方邮箱真正收到，中间还可能被灰名单延迟、被判垃圾邮件或直接退信。想要送达证据，得用邮件服务商提供的回执与事件回流机制：退信会回到发信域配置的退信地址，投递/打开/点击这类事件要在控制台开启数据追踪并配置追踪域名，然后通过回调或接口拉取。落到博客这种场景，建议用独立子域发信、配好 SPF、DKIM、DMARC（这三个配不齐，进垃圾箱的概率会明显上升），把退信接收地址和事件回调都接进自己的日志，这样「用户说他没收到验证码」这类问题才有事实可查，而不是靠猜。
