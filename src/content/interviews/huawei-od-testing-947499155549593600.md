### 《参考解析》

**接口测试的流程与风险点**：流程按「接口清单 → 契约 → 用例 → 执行 → 回归」组织。先梳理被测系统的接口清单与调用链，确认哪些是内部接口、哪些对外；再拿到接口文档或抓包确认真实契约（路径、方法、入参类型与必填、返回码、超时）；用例按单接口（正常、边界、异常入参、鉴权、幂等）与场景串联（上下游数据依赖、事务回滚）两层写；执行阶段用工具做参数化与断言，把响应码、业务码、关键字段、响应时间都纳入断言；最后固化进流水线做回归。风险点集中在四处：一是契约漂移，文档与实现不一致，必须以抓包或代码为准；二是鉴权与越权，缺 token、过期 token、他人资源 id 直接替换；三是数据依赖，前一个接口造的数据被后一个用例改掉，导致偶发失败；四是幂等与并发，重复提交、并发扣减这类问题单次调用测不出来，要专门构造。

**性能指标的依据**：指标不是拍出来的，来源有三类。业务侧给容量目标（日活、峰值 QPS、并发用户数），据此推算需要支撑的吞吐；历史监控给基线（当前 P99 是多少、大促时抬到多少）；系统自身给上限（连接池大小、线程池、数据库最大连接、下游限流阈值）。三者的较小值才是可验证的目标。指标要成组看：吞吐（TPS/QPS）、响应时间（平均不够，必须看 P95/P99）、错误率、资源水位（CPU、内存、IO、连接数）。只报平均值会把长尾掩盖掉，压测结论必须写清施压模型（并发数、思考时间、数据分布）与观测窗口，否则别人无法复现。

**判断链表是否有环并找入口**：快慢指针。两指针同从头出发，慢指针每次一步、快指针每次两步，若相遇则有环；相遇后把一个指针放回头节点，两指针同速前进，再次相遇的位置即环入口。原理是设头到入口距离 a、入口到相遇点距离 b、环长 L，相遇时慢指针走了 a+b、快指针走了 a+b+kL，且快指针路程是慢指针两倍，解得 a = (k-1)L + (L-b)，即从头走 a 步与从相遇点走 a 步会同时到达入口。要能说明为什么快指针不能一次走三步以上：步长过大时可能跳过慢指针，无法保证相遇。

**订单支付流程的用例设计**：先画状态机，订单从待支付、支付中、已支付、已关闭、退款中到已退款，每条边都是一组用例。正常场景覆盖各支付渠道（余额、优惠券、组合支付）、金额边界（0.01 元、刚好等于余额、超过单笔限额）、优惠叠加规则。异常场景是重点：重复提交与幂等（同一订单号多次回调只入账一次）、支付超时后回调才到（要先查单再决定是否补单）、金额被篡改、渠道返回成功但本地落库失败（对账兜底）、并发支付同一订单、退款金额大于实付、部分退款后再次退款。还要覆盖对账：T+1 渠道账单与本地流水逐笔比对，差错单进入人工处理。用例写完后按风险排序，资金相关的必须进回归集。

**索引与隔离级别**：索引优化先看慢查询日志定位 SQL，再用 EXPLAIN 看 type、key、rows、Extra；type 到 ALL 说明全表扫，Extra 出现 Using filesort、Using temporary 要警惕。常见手段是按查询条件与排序字段建联合索引并守住最左前缀、尽量做覆盖索引避免回表、不在索引列上做函数运算或隐式类型转换、避免前置通配的 like、深分页改成基于上一页最大 id 的游标查询。隔离级别四级：读未提交会脏读；读已提交解决脏读但可能不可重复读；可重复读解决不可重复读，MySQL 默认级别，靠 MVCC 加间隙锁在大部分场景规避幻读；串行化最严格但并发度最低。要能说清 MVCC 的组成：隐藏事务 id、undo 版本链、ReadView。

**主管面**：主管面考的是稳定性与动机。对 OD 的文化了解不要说空话，可以落到「以项目交付为中心、流程规范、考核看结果」这些公开可查的特征上，并说明自己为什么适配。加班问题给具体边界比表态更有说服力，例如「项目冲刺期可以接受连续加班，长期无节制的加班我会先确认是不是排期问题」。技术学习讲清路径与产出：看什么资料、做了什么练习、最后落到项目里的哪个改动。
