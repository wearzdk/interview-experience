5. Spring 依赖注入有哪几种方式？@Autowired 和 @Resource 有什么区别？
6. 重写（Override）和重载（Overload）的区别？
7. 前端重复点击支付、多次提交请求，后端如何防止重复支付？
8. 如果大量接口都需要防重，如何统一处理？

### 《参考解析》

**Spring 的单例 Bean 默认不是线程安全的。** 容器只是保证「一个 Bean 定义对应一个实例」，是否安全取决于这个 Bean 有没有可变共享状态：无状态的 Service/Controller（只依赖其他 Bean、方法内用局部变量）天然安全；一旦有可变成员变量（比如缓存了一个 `SimpleDateFormat`、或者用成员变量暂存请求数据），多线程并发访问就会出问题。正确做法是把状态放在方法局部变量或用 ThreadLocal，不可变对象尽量声明为 final；确实需要每请求一份实例时把作用域改成 `prototype` 或 `request`（注意 prototype 注入到单例里需要用 `@Lookup` 或 ObjectFactory 才能每次拿到新实例）。顺带可以提：`SimpleDateFormat` 换成 `DateTimeFormatter`（不可变），以及 `HashMap` 换 `ConcurrentHashMap`。

**依赖注入三种方式的取舍。** 构造器注入是首选：依赖不可变（final）、对象创建即完整、循环依赖会在启动时报错暴露出来、也方便单元测试；Setter 注入适合可选依赖和需要重新配置的场景；字段注入（`@Autowired` 打在成员上）写起来最短但依赖不可见、不能声明 final、脱离容器无法测试，Spring 官方已不推荐。`@Autowired` 是 Spring 自己的注解，默认**按类型**注入，类型不唯一时再用 `@Qualifier` 或字段名兜底，`required=false` 允许为空；`@Resource` 是 JSR-250 标准注解，默认**按名称**注入，名称找不到才退回按类型。业务代码里用哪个都能跑，但团队要统一。

**重写与重载的区别是「同一个方法还是两个方法」。** 重载发生在同一个类里，方法名相同、参数列表不同（类型/个数/顺序），与返回值无关，编译期就能确定调用哪个（静态分派）；重写是子类覆盖父类方法，签名必须一致，运行期根据实际对象类型决定调用哪个（动态分派），规则上有「两同两小一大」的约束（方法名参数相同、返回值和异常更小或相同、访问权限更大）。

**防重复支付这道场景题，答题要分层，不能只说「加锁」。** 第一层是**前端防抖 + 按钮置灰**，但它只是体验优化，不是安全边界（接口可以被绕过）。第二层是**服务端幂等**：下单时生成全局唯一订单号/请求号，用户点第二次时携带同一个业务标识，服务端用数据库唯一索引（订单号或 `biz_id + user_id`）拦重复写入——这是最可靠的一道闸，因为它由数据库保证原子性。第三层是**状态机**：支付单只能从「待支付」迁移到「支付中/已支付」，用乐观锁 `update ... where status = '待支付'` 判断受影响行数，返回 0 说明已被处理。第四层是**分布式锁**（Redis `SETNX + 过期时间` 或 Redisson），用于拦截并发窗口内的重复请求，但必须和数据层的唯一约束配合，锁只是降低冲突、不能当唯一保证。最后是**支付渠道回调的幂等**：第三方可能重复通知，要按渠道流水号去重并记录处理状态，同时注意「先落库再发货」的顺序，避免重复发放权益。

**「大量接口都要防重」的答案就是把它做成通用能力。** 定义 `@RepeatSubmit` 之类的注解（或拦截器/过滤器 + 路径规则），配合拦截器从请求里提取幂等键（token + 用户 id + 接口路径 + 请求体 hash），统一走 Redis 的 `SET key value NX EX ttl`：成功放行、失败直接返回「请勿重复提交」。要点是：幂等键的粒度要按接口设计（有的按用户，有的按业务单号），TTL 要覆盖业务的最长处理时间，锁的释放要小心（不能误删别人的锁，用 value 校验或 Lua），以及区分「重复提交」和「用户真的想再下一次单」——后者要靠业务单号而不是短时间窗口来判断。进阶一点可以提基于状态机的幂等表（请求号 + 处理结果落库），保证接口重试也能返回同一结果，而不只是拒绝。
