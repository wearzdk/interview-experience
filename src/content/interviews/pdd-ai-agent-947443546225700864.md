### 《面试题目》

1. RAG 的 Chunk 怎么切，效果怎么测？
2. 短期记忆、长期记忆各存什么？
3. 多 Agent 怎么分工、共享状态？意见不一样怎么办？
4. 手写：LRU 怎么实现？

### 《参考解析》

**Chunk 切分的原则是「不要把一个语义单元拆散」，评估的原则是「检索与生成分开看」。** 切分时先保留结构化信息（标题、来源、版本、章节层级），再按段落或语义边界切，宁可让一个块里带上它所属的小标题，也不要把一个定义和它的例外条件分到两个块里。块大小与重叠量没有普适最优值，要按文档类型调：制度类文档段落长、块可以大一些；FAQ 类短问答适合一问一块；代码文档要按函数或类切。工程上常用递归切分（先按标题、再按段落、最后按句子）+ 父文档检索（小块用于召回、召回后带出它所属的大块给模型），能在精度和上下文完整性之间折中。

**评估要拆成检索和生成两段，这是回答里最能加分的地方。** 检索段看：该命中的证据有没有被召回（Recall@K）、排序有没有把它排到前面（MRR / NDCG）、以及召回的内容里有多少是噪声（准确率）。生成段看：给定正确上下文时答案是否用对了证据、有没有超出上下文的编造。做法是给每个测试问题标注一条或多条「必须命中的证据片段」，然后用固定问题集做对照实验，每次只改一个变量（切块大小、重叠、embedding 模型、rerank 是否开启），看证据召回与答案正确率的联动。另外必须专门准备「知识库没有答案」的题，测模型会不会胡编——这是 RAG 上线后最容易出事的地方。

**记忆分层的关键是「什么该跨会话保留、什么只在这一轮有用」。** 工作记忆/短期记忆存当前任务的执行状态：处理到哪一步、已确认的事实、待办事项、临时工具结果，要求可恢复、可截断（超长时按重要性或时间淘汰）；长期记忆存跨会话仍然成立的偏好、身份信息、历史结论，写入要有触发条件（用户明确说「记住」、或多次重复出现的事实），并且必须带过期时间与删除入口。原文（转写、文档）与摘要要分开存：摘要方便检索但会丢细节，回答需要引用时回到原文核对。向量库做语义检索，结构化字段（时间、人物、项目）做过滤，两者结合比纯向量更准。

**多 Agent 的分工要先写清每个角色的输入与验收条件，再决定要不要拆。** 典型划分是按职责：一个找证据、一个产出结论、一个做校验，协调者负责汇总与冲突处理。共享状态用一份带版本号的任务黑板（谁改了什么、基于哪个版本的输入），交接时带齐任务描述、输入版本、产物和待确认项。冲突处理的原则是「回到原始证据」而不是投票：两个 Agent 结论不一致时，看各自引用的原文是否支持自己的结论，谁引不出来谁让步；如果都无法判定，升级给人或给出两个候选并标注不确定。还要能说出不拆的理由——如果拆完只是多一次转述、没有并行收益或专业分工，单 Agent 加工具更简单可靠。

**LRU 的实现是哈希表 + 双向链表：** 哈希表存 key 到链表节点的映射，实现 O(1) 定位；双向链表维护使用顺序，头部是最近使用、尾部是最久未使用。`get` 命中就把节点移到头部并返回值，未命中返回 -1；`put` 时若 key 已存在则更新值并移到头部，不存在则新建节点插到头部、哈希表记录，若超出容量则删掉尾部节点并同步删哈希表项。用哨兵头尾节点可以省掉大量判空分支。要主动补边界用例：容量为 1、重复更新同一个 key（不能算两次占用）、`get` 也会改变淘汰顺序、容量为 0 的退化处理。如果面试官继续追问，可以接「并发场景怎么加锁」（分段锁或 `ConcurrentHashMap` + 同步链表）、「怎么做到近似 LRU 又省内存」（Redis 的采样淘汰）、以及「TTL 怎么加」（每个节点带过期时间 + 惰性删除 + 定期清理）。
