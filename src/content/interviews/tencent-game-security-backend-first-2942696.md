### 《参考解析》

**起一个 .py 脚本在内核眼里发生了什么**：用户在 shell 输入命令后，shell 调 `fork` 复制出子进程，子进程调 `execve` 把 `/usr/bin/python3` 的 ELF 加载进地址空间，内核解析 ELF 头、建立新的内存映射（代码段、数据段、堆栈）、把参数与环境变量压栈，然后把控制权交给解释器的 `_start`。解释器启动后初始化运行时（堆、GC、模块导入系统），读取 `.py` 文件、词法语法分析成 AST、编译成字节码，再由 CPython 的求值循环逐条执行字节码；期间遇到 IO 走系统调用陷入内核。所以「解释器与程序一起执行」的说法不准确：解释器本身就是一个进程，你的脚本是它读入的数据，没有独立进程。

**JVM 与 Java 程序的关系**：同样从进程角度看，`java Main` 启动的是 JVM 这个进程，JVM 用 C++ 写成，先做自己的初始化（解析参数、建堆与元空间、加载核心类库），再通过类加载器把 `Main.class` 读进来、验证、准备、解析、初始化，最后由字节码执行引擎解释执行或 JIT 编译成本地代码。Java 代码不是被内核直接执行的，内核只负责把 JVM 的 ELF 加载起来。自己设计这套机制时，核心是三件事：定义一个可移植的中间表示（字节码）、写一个能加载并解释它的运行时、以及把内存管理与线程调度收进运行时里，代价是启动开销与「不直接跑在硬件上」的性能损失，收益是一次编译到处运行。

**为什么加规则层而不是全用大模型**：关键词意图路由本质是「用确定性手段处理高频明确意图」。全用大模型的代价是延迟、成本与不确定性——每次请求都要过模型，P99 延迟和 token 成本随流量线性上升，而且同一个 query 可能给出不同结果。规则层把高频、边界清晰的 query 用词典或正则精确命中，剩下的长尾再交给模型，既压成本又保稳定。规则维护的关键是把词典做成配置而不是代码：运营可增删词、支持同义词与否定词、按业务线分组、灰度发布并能回滚，同时记录命中日志以便评估覆盖率。面试官追问命中率，是看有没有量化——上线后规则命中的比例、误命中率、以及规则层与模型层结论不一致时怎么处理。

**Agent 的工作原理与工具调用位置**：Agent 是一个循环：把系统提示、对话历史与工具定义一起发给模型，模型输出要么是自然语言回复（结束），要么是一个结构化的工具调用请求（工具名 + 参数）；执行框架在本地或服务端执行该工具，把结果作为一条新消息追加进上下文，再次调用模型，直到模型给出终止信号或达到步数上限。工具执行不在模型侧，模型只产出「要调什么、参数是什么」的文本，真正执行的是宿主程序，因此工具描述（名称、用途、参数 schema）必须写进请求里，模型才知道有哪些工具可用。

**token 生成、终止与 EOS**：模型把输入编码成 token 序列，经过多层注意力与前馈网络得到一个在词表上的概率分布，按采样策略（贪心、温度采样、top-p）选出一个 token，追加到序列后继续下一步，每步只新增一个 token。终止有两种：模型生成特殊的结束符 EOS，或达到 `max_tokens`、命中停止词。EOS 不是外部规则产生的，它在训练数据里就是序列结束的标记，模型学会了在回答完结时给它高概率。KV Cache 缓存历史 token 的 Key/Value，避免每步重算整段注意力，把复杂度从每步 O(n²) 降到 O(n)，代价是显存随上下文长度线性增长。每次都要看前面所有 token，是因为自回归模型的每一层注意力都要对完整上下文做加权，当前 token 的表示依赖于前文。

**无状态请求为什么能记住上下文**：模型本身确实无状态，记忆完全来自「每次把历史重新发一遍」。Agent loop 每一轮都把之前的消息（用户输入、模型输出、工具结果）拼进请求，所以看起来连贯。工程上的问题是上下文会膨胀，需要在长度上限内做裁剪、摘要或检索式召回；同时因为每次都重发，前缀缓存（Prompt Cache）能显著降低成本与首字延迟。

**Spring Boot 的请求路由**：请求到达后由内嵌容器（Tomcat/Netty）接收并解析成 `HttpServletRequest`，交给 `DispatcherServlet`；它从 `HandlerMapping` 里按 URL 与请求方法找到对应的 `HandlerMethod`（`RequestMappingHandlerMapping` 在启动时扫描所有 `@RequestMapping` 注解，建立「路径模式 → 方法」的映射表），再通过 `HandlerAdapter` 反射调用，期间做参数解析、数据绑定、拦截器与过滤器链，返回值经 `HttpMessageConverter` 序列化成 JSON。要自己实现，核心是一个路径匹配器（精确匹配、路径变量、通配符，常用 Trie 或正则表）、一个注册表（启动时扫描注解建立映射）、以及一个调用器（反射 + 参数解析）。用「基类 + 继承」也能做（每个 Controller 继承一个基类并覆写方法），但框架层不会这么做——继承把路由和实现绑死、无法组合，注解加反射/函数式注册更通用。这题答不上来通常是只停留在「写 `@RestController` 就能用」，没有看过 DispatcherServlet 这条链路。
