### 《面试题目》

1. 简历上这个「内化框架」，一句话说清楚它是什么。
2. 省多少 token？3800 值多少钱？按一年算呢？
3. 为了省这些钱，训一次模型花了多少？
4. 你这个「内化」和普通微调有什么区别？为什么不叫微调？
5. 模型能分清「注入事实」和「学格式」这两件事吗？
6. 知识更新了怎么办？增量训一轮要多久？这三天里用户问新知识，模型答什么？那你到底省了什么？
7. 知识冲突怎么处理？旧参数里有 A，新数据说 A 是错的。
8. 混入通用数据的比例怎么来的？试了几组？三组就敢上线？
9. 幻觉率降了吗？怎么测的？谁判的？你自己判自己做的框架？
10. 为什么不用 RAG？RAG 改一个文档五分钟，你改一个事实要三天。
11. RAG 在专业术语上的召回率 71%，这个分母是什么？漏掉的 29% 是检索问题还是切分问题？各占多少？
12. 内化和 RAG 能不能混用？怎么决定一条知识放哪一边？频次阈值多少？第 51 次之前呢？
13. 你说这套框架有 Agentic 特性，具体在哪？这算 Agent 吗，不就是一个脚本跑三遍？中间决策错了怎么办？重跑的钱谁出？
14. 这套自动迭代和 AutoML 有什么区别？那不就是数据版的网格搜索？
15. 整条链路里 rollout 占多少时间？GPU 利用率多少？为什么这么低？为什么不按长度分桶？35% 里有多少是等、多少是算？等什么？
16. 如果预算砍一半，你先砍哪一步？效果掉多少？三个点换一半预算值吗？那你为什么不一开始就这么做？
17. 这套东西不做会死吗？不做成本会高多少？你们团队一年人力成本多少？那你在优化什么？
18. 这套东西里哪些是你做的？框架的想法是谁的？那简历上为什么写「主导」？
19. 手撕：实现一个动态 batching 的调度器。请求随时进来，攒到 batch size 或者超过 20 毫秒就 flush，要求单线程安全，且不能因为一个慢请求拖住整批。

### 《参考解析》

**「内化」与微调的边界要讲清目标而不是名字。** 继续预训练把事实写进参数，微调通常指用标注数据调整输出分布，两者在工程上是同一条链路的不同用法。被追问「模型能分清这两件事吗」，正确的回答是承认模型不区分意图，区分体现在数据构造与损失设计上：内化用的是自动构造的事实型语料（实体—关系—问答），评估看的是事实召回与幻觉率；微调看的是任务格式与指令遵循。如果两者混在一批数据里训，效果归因就说不清，这本身就是一个设计缺陷。

**成本账要能闭环。** 面试官一路把「省 3800 token」逼到「一年七万」再逼到「团队人力成本」，考的是有没有算过投入产出比。合理的答法是给出单位经济模型：单次请求节省 × 日请求量 × 365，对比训练卡时、数据构造与维护人力、以及知识更新延迟带来的业务损失。若结论是「一年省七万而人力成本远高于此」，就应该承认这套方案的价值不在省钱，而在延迟、稳定性或隐私（不出域），把立项理由换到真实收益上。

**知识更新与冲突是内化路线最难的部分。** 参数里的旧事实无法定点删除，只能靠新数据覆盖，覆盖不彻底就会出现新旧并存的矛盾输出。工程上的缓解手段是：给新数据更高权重并混入通用数据防遗忘、保留 RAG 作为长尾与新知识的兜底、对高频变更的知识强制走检索而不是参数。回答时要明确「哪些知识适合内化」——稳定、高频、术语密集的事实；「哪些不适合」——时效性强、需要引用出处的信息。

**GPU 利用率 35% 的追问指向调度而不是分桶。** 长尾样本长度差异大时，padding 会让一个 batch 的有效计算比例下降；分桶能缓解，但收益有限，因为瓶颈是「等最长的那个样本」。真正的解法是 continuous batching / 迭代级调度：以 token 为单位动态进出 batch，而不是按请求整批等待；配合序列并行与 PagedAttention 管理显存碎片。能把「等」和「算」分开度量，说明真的看过 profiling，而不是背优化清单。

**动态 batching 调度器的手撕要点。** 需要三个结构：待处理队列（到达即入队）、当前批次（累计到 batch size 或定时器 20ms 触发 flush）、以及每个请求的超时与回调。单线程安全在单线程事件循环里天然成立，多线程则要一把锁保护队列与批次状态，flush 时整批取出并在锁外执行。慢请求的处理是这道题的核心：不能让它阻塞整批，做法是给它单独的完成回调与超时（超时后先返回、结果到达再补发或丢弃并记录），显存/资源在该请求真正结束时释放，而不是随批次一起释放。面试官最后追问「超时之后结果怎么返回、它占的显存什么时候释放」，正是在验证有没有想清楚生命周期。

**这场面试的方法论价值。** 作者复盘说「没有一道题是我不会的，但每一道都被问到了『然后呢』」。技术面试的深度追问通常在验证三件事：数字是否有出处、方案是否有对照、结论是否由自己得出。准备项目时按「做了什么—为什么这么做—代价是什么—怎么验证」四层各写一遍，比堆技术名词有效。
