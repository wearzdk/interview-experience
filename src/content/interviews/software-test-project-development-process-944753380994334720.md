### 《面试题目》

1. 说一下你理解的项目开发的完整流程是什么？
2. 需求评审、用例评审、技术评审分别在什么时候开？谁来主持？产出什么？
3. 每个环节测试的角色是什么？
4. 流程走完之后，上线后的跟进包含哪些事？

### 《参考解析》

面试里问这条，考的不是你会不会背名词，而是你知不知道自己每一个节点该拿什么、交什么。按阶段答，每个阶段带主持方、参与方和产出物。

**1. 需求评审。** 产品 / 项目经理主持，开发、测试、业务相关方参与。目标是确认需求准确、完整、一致、可行。测试在这一步的产出是「需求疑点清单」——异常流、边界、权限、并发、数据迁移这些有没有写清；模糊表述推动量化（「加载快」→「首屏 ≤ 2 秒」）。这一步吵得越充分，后面返工越少。

**2. 技术方案 / 技术评审。** 开发主导，测试参与。开发讲清楚架构选型、接口设计、数据表结构、依赖的第三方、灰度与回滚方案。测试要在这里拿到可写用例的输入：接口契约、状态流转、错误码，以及识别「哪些改动会影响老功能」——这直接决定回归范围。

**3. 用例设计与用例评审。** 测试主导。用例覆盖三块：正常流（用户按设计路径走）、异常流（输入非法、依赖失败、超时重试、并发冲突）、边界（空值、极值、长度上限、时间与时区）。评审时拉上开发、产品一起过，好处是对齐认知，避免测试自己写自己评。产出是可执行的用例集 + 测试数据。

**4. 提测与执行。** 提测要有门禁：版本号、变更说明、自测记录、能否部署。没有这些就退回，别硬测——否则你花半天发现环境根本不通。执行阶段按优先级排：主流程 → 核心功能回归 → 新增功能 → 异常与边界 → 兼容与性能。过程中提 Bug（标题、步骤、期望 / 实际、严重程度、附件），跟踪到修复并回归关闭。

**5. 复测与回归。** 修复后先验这条 Bug 本身（是否真的修好、修复有没有引入新问题），再跑一轮回归——范围看这次改动的影响面，而不是每次都全量。这个阶段最容易出问题的是「修 A 崩 B」，所以改动涉及公共模块时回归要扩到所有调用方。

**6. 上线。** 上线前确认：回归结论、遗留 Bug 清单（哪些带着上线、影响是什么、有没有绕行方案）、灰度策略、回滚方案、监控项。上线不等于测试结束——要盯发布过程中的告警。

**7. 上线后跟进与监控。** 观察核心指标（成功率、耗时、报错率）、用户反馈、日志里的异常。线上出问题先判影响面决定回滚还是热修。这一段做完整了，下一轮的需求评审才有输入。

**加分点**：说清这套流程在不同团队规模下的变形——小团队可能把三次评审合成一次，但「需求对齐、方案确认、用例覆盖」这三件事不能省；也说明敏捷 Sprint 下这些环节是每个迭代内循环一次，不是项目只走一遍。再点出流程的价值不是流程本身，而是每一环都有明确的准入准出条件，让「能不能进入下一步」不需要靠感觉判断。
