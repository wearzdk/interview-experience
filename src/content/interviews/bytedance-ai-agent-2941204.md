### 《面试题目》

1. Function Calling 的实现原理是什么？模型如何决定调用哪个工具？
2. RAG 的完整链路是什么？召回不准时怎么优化？
3. MCP 解决什么问题？它与直接写函数调用有什么区别？
4. 多轮对话的上下文如何管理？超长时怎么裁剪？
5. ReAct 的循环是怎样的？它和 Plan-and-Execute 有什么区别？
6. Agent 的规划能力怎么实现？任务分解失败时怎么办？
7. Agent 的记忆如何设计？短期与长期记忆分别存什么？
8. 反思（Reflection）机制怎么落地？反思会不会让错误固化？
9. 多 Agent 协作有哪些拓扑？如何避免互相等待或重复劳动？
10. 幻觉如何在工程上兜底？

### 《参考解析》

**Function Calling**：模型并不真的「调用」函数，它输出一段结构化的调用意图（函数名 + 参数 JSON），由宿主程序解析、校验并执行，再把结果作为一条消息回填，模型继续生成。工程要点是 schema 设计（参数类型、枚举、必填项、描述要写清何时该用）、并行调用与串行调用的区分、参数校验与失败回传（把校验错误原文交给模型让它修正，而不是静默重试）、以及调用次数与超时上限。工具描述写得含糊是调用错误的第一大来源。

**RAG**：链路是文档解析与切分 → 向量化入库 → 查询改写 → 召回（向量 + 关键词混合）→ 重排 → 组装上下文 → 生成并给出来源。召回不准的排查顺序是：切分是否破坏了语义单元、embedding 是否适配语种与领域、是否需要混合检索与元数据过滤、重排模型是否缺失、查询是否需要改写或多路召回。生成阶段要求「只依据检索内容回答并标注出处」，检索不到时明确说不知道，比强行编造好。

**MCP**：它标准化的是「工具/资源如何被描述、发现与调用」，让同一套服务端能被不同的宿主复用，解决的是生态与接入的重复劳动。它与函数调用的关系是协议层与执行层：MCP 定义怎么把工具暴露给模型，函数调用是模型表达「我要用哪个工具」的方式。自己写函数调用在单应用内更简单，跨应用复用、需要权限与资源抽象时才值得引入 MCP。

**上下文管理**：分层处理——系统提示与工具表固定；近期对话保留原文；较早的对话做摘要并保留关键事实；检索到的资料按相关性取 Top-K 并压缩。裁剪不能简单截断，否则会丢掉任务约束；常见做法是把「目标、已确认的事实、待办」单独维护成结构化状态，每轮随消息注入，长对话也不会漂移。

**ReAct 与规划**：ReAct 是「思考 → 行动 → 观察」的循环，适合边做边看的探索型任务，代价是步数多、容易绕圈；Plan-and-Execute 先出计划再逐步执行，适合步骤明确的任务，代价是计划本身可能错、且难以应对中途变化。实践中常组合：先出粗计划，执行中按观察结果修订。规划失败的处理是限定重试次数、把失败原因写回状态、必要时降级为人工介入，而不是无限重规划。

**多 Agent 协作**：常见拓扑有主管—工人（一个编排者分派子任务）、流水线（按阶段串联）、辩论/评审（多个角色互评）。失败模式是重复劳动、责任不清、消息风暴与死锁式等待。控制手段是明确每个角色的输入输出契约、限制轮次与预算、由编排者做最终裁决、共享一份结构化状态而不是靠自然语言传话。

**记忆与反思**：记忆分工作记忆（当前任务的中间结果）、情景记忆（历史交互）、语义记忆（抽取出的稳定事实）。写入要有筛选与去重，否则噪声会越积越多；检索要结合时间与来源。反思机制的价值是让 Agent 从失败中提取可复用的教训，风险是把一次偶然的错误总结成规则并长期沿用，所以要给反思结果加置信度、可被后续证据推翻、并保留人工清理入口。

**幻觉兜底**：工程上分三层——输入侧提供可靠上下文并声明边界；生成侧要求引用来源、结构化输出、关键字段用程序校验；输出侧做规则校验、交叉核对与人工复核。对高风险动作（下单、改数据、发消息）必须要求二次确认或 dry-run，不能只靠提示词约束。

**关于本帖的可信度**：帖中「一周从流水线到年薪百万」的叙事与公开的招聘流程不符（大厂校招与社招均有固定轮次与审批周期），且正文没有任何可核对的面试细节，末尾以「不要私我」收束，属于典型的流量文案。其中的技术方向本身是真实的 Agent 考点，可以据此准备，但不应把帖中的经历当作可复现的路径。
