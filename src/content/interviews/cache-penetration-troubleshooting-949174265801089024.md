### 《面试题目》

1. 缓存穿透怎么排查？
2. 你线上真遇到过吗，怎么定位到是穿透的？
3. 怎么区分缓存穿透和缓存击穿？
4. 当时做了哪些止血？空值缓存的过期时间设多少合适？
5. 布隆过滤器是银弹吗？它有什么代价？
6. 只在 Service 层做参数校验有什么问题？
7. 如果攻击者每次换一个随机 ID，空值缓存还挡得住吗？
8. 面试时这道题你会怎么组织回答？

### 《参考解析》

**为什么穿透难认**：它不像雪崩那样一大片 key 同时过期，一眼可见。穿透的流量占比可能只有几个百分点，但每个请求都打到 DB，而 DB 的承载能力比 Redis 低两个数量级，照样能把库压垮。帖主遇到的现象是 MySQL CPU 冲高、接口 P99 从 80ms 涨到两秒多，而 Redis 命中率只是从 98% 掉到 92%——命中率的小幅下跌对应的是 DB 的灾难。

**排查三步**：第一步看 DB 侧，拉慢查询日志，确认是不是大量「耗时不长但 QPS 异常高」的查询，并检查这些查询的结果是否为空——正常未命中查出来的是真实数据，查出空结果且量很大，基本可以锁定穿透。第二步看 Redis 侧 miss 的 key 长什么样，在应用层对缓存未命中的 key 做低采样打点，观察是否集中在伪造或连续递增的 ID 上；这里有个坑，开全量日志会把磁盘写满，采样率要压到千分之一级别。第三步区分穿透与击穿：击穿是单个真实存在的热点 key 过期瞬间被并发打库，穿透是 key 压根不存在、缓存永远不会命中，看 miss 的 key 在库里是否存在即可分辨。

**止血的优先级**：最便宜的是对查询结果为空的 key 也写缓存，TTL 设短（例如 60 秒），几分钟就能上线；其次是网关层按来源限流，掐掉明显的脚本流量；再是入口参数格式校验。空值缓存的时间不能拍脑袋：设长了，运营新建的数据在 TTL 内查不到，会变成用户投诉；设短了挡不住持续攻击。折中做法是空值短 TTL，并在数据创建时主动删除对应的空值 key。

**布隆过滤器的边界**：它能把「一定不存在」的请求挡在缓存之前，但有误判率、需要预热、标准实现不支持删除，重建期间还要处理一致性。业务量没到那个级别时，空值缓存加参数校验已经够用；只有当不存在的 key 高度分散、空值缓存完全覆盖不住时，才值得引入。

**参数校验要放在入口**：写在 Service 里，请求仍然要穿过 Controller、拦截器、参数解析才被拦下，资源已经消耗了。挪到网关和参数校验注解上，才能真正省下后面的开销。

**回答结构**：先讲怎么判断（DB 空结果占比、miss key 分布、穿透与击穿的区别），再讲怎么止血（空值缓存、入口限流、格式校验），最后讲怎么根治（布隆过滤器、热点隔离、异常 ID 分布的监控告警）。补一句自己的判断会更好：穿透排查的难点不在方案，而在于能否快速拿到「miss 的 key 长什么样」，所以平时就要在缓存未命中处留低采样埋点。
