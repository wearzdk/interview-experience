### 《参考解析》

**讲项目要给出「问题—方案—验证」的闭环**：初创团队最关心你能不能独立把一件事做完。先说明问题为什么重要（例如多轮协作中角色之间的信息不同步），再给你的方案与它的取舍（为什么用结构化记忆而不是纯向量检索），最后给验证方式与结果。没有真实用户的阶段，验证方式要落到可复现的评测上，而不是「感觉好多了」。

**harness 与模型的对比要按维度说**：CLI 类 Agent 工具（Claude Code、Codex、Pi 等）的差异主要在工具集与权限模型（能否执行命令、读写文件、联网）、上下文管理与压缩策略、可扩展性（是否支持自定义工具与提示模板）、以及成本与延迟。回答时不要评价谁「更强」，而是说清「我为什么在这个任务上用这个」——例如需要长上下文代码理解时选某个、需要轻量脚本时选另一个。

**benchmark 构建的原理比数量重要**：一套可信的评测要解决四件事——任务来源（真实场景采样还是合成）、难度分层（分桶后看每档表现，避免单一均分掩盖长尾）、判定方式（确定性可验证 vs 主观质量）、以及防污染（训练数据与评测集隔离）。自建数据集的常见问题是有偏（都是自己熟悉的场景）、规模小导致方差大，所以要做置信区间与多轮重复。

**确定性部分与主观部分要分开评**：能用代码判定的（格式、字段、可执行结果、检索是否命中目标文档）一律用代码判定，成本低、可复现、无偏差；只有主观质量才交给 LLM-as-judge，并配 rubric（把评价拆成几个可打分的维度，给出每档的描述），再抽样人工对齐。

**LLM judge 的三个问题与解法**：成本高——先用规则过滤掉确定性的部分，只在必要处调用，且用较小的模型做初筛；偏差——位置偏差（偏好第一个 / 最后一个）、长度偏差（偏好更长）、自我偏好（偏好同族模型的输出），解法是交换 AB 顺序做双向评估、控制长度、用不同家族的模型做裁判，并在 rubric 里明确禁止「长度即质量」；缺乏校准——judge 与人的判断不一致时，要用人标注的小样本校准，定期比对一致率（如 Cohen's kappa），不一致就改 rubric 而不是加提示词。

**评估反哺生成端**：作者说他们还没有，正在尝试用评估指导更有效的合成数据与蒸馏。这是这类团队典型的下一步：把失败案例按类型聚类 → 针对性合成训练数据（或用强模型生成参考答案做蒸馏）→ 用同一套评测验证是否真的提升 → 循环。要注意「对着评测集优化」会导致过拟合，所以需要保留一个不对训练暴露的留出集。

**设计长程记忆题库**：两种形态都值得做。第一种是「大海捞针」式的阅读理解：给一段很长的材料（跨多轮对话或多个文档），先让系统从中抽取事实，再只凭记忆回答需要组合多个事实的问题，通过调整针的位置、数量与干扰项控制难度，判定可以完全自动化。第二种贴近真实项目：多角色（技术 / 产品 / 设计）先后给出信息，之后某个角色提出与早前信息强相关的需求，考察系统能否正确归因到「谁在什么时候说过什么」并保持不冲突；判定要点是信息的一致性、来源归属与冲突消解。除此之外还要设计遗忘与更新（用户改了口径后旧信息应失效）、时序推理（先发生的事影响后发生的决策）与干扰（相似但不相关的信息不应被误用）三类场景，并给每道题标注其考察的记忆能力维度，便于定位失败原因。
