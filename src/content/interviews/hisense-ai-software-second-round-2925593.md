### 《参考解析》

**Nacos 与缓存写策略**：Nacos 同时是注册中心和配置中心。注册中心一侧负责服务注册、健康检查与实例推送，消费者通过它拿到可用实例列表，配合负载均衡完成调用；配置中心一侧负责配置的集中管理与动态刷新，改完配置能推送到客户端而不必重启。回答时要能说出命名空间与分组怎么做环境隔离、临时实例与持久实例在健康检查上的差别、以及它默认偏 AP（可用性优先）但支持 CP 模式。Write-Behind（写回）是缓存写策略的一种：写请求只更新缓存并落一条变更记录，由后台线程异步批量刷回数据库，相比 Write-Through（同步写穿）吞吐高、数据库压力小，代价是存在数据丢失窗口、实现更复杂，需要重试、幂等与对账补偿；Write-Around 则是绕过缓存直接写库，适合写后不马上读的场景。选型看一致性要求与写入压力。

**Redis 加 Lua 限流**：把「读计数、判断阈值、写回计数、设置过期」这几步放进一段 Lua 脚本一次执行，利用 Redis 单线程模型保证原子性，避免先查后写造成的超发。设计上要讲清三个维度：Key 的组成决定限流粒度，常见是「业务前缀 + 接口 + 限流对象」，限流对象可以是用户 ID、设备指纹、IP 或租户；计量单位决定用哪种算法，固定窗口用 INCR + EXPIRE 最简单但有临界突刺，滑动窗口用 ZSet 存时间戳能平滑但有内存成本，令牌桶用哈希存令牌数与上次补充时间更贴近真实流量。还要考虑被限流时的返回（429 与 Retry-After）、阈值按接口分级配置、Redis 集群下同一对象的 Key 要用 hash tag 落到同一分片、以及脚本本身要做参数校验和降级（Redis 挂了要不要放行）。

**Redis ZSet 排行榜**：ZSet 底层是跳表加哈希表，哈希表保证按成员 O(1) 取分值，跳表保证按分值有序，因此 ZINCRBY 更新分数、ZREVRANGE 取 Top N、ZREVRANK 查排名都是对数级，天然适合排行榜。工程细节上：分数要设计成「主指标 + 时间戳尾数」这类复合值来打破同分僵局；不要用 ZRANGE 做深分页（复杂度随偏移增长），大榜要分片或只维护 Top N；热点榜可以定时把结果快照到字符串，读取走快照；成员数上百万时要关注大 key 与内存，并设置过期或归档策略。EXPLAIN 慢 SQL 则重点看 type（要出现 ref/range，尽量别是 ALL 全表扫描）、possible_keys 与 key（实际选了哪个索引、有没有走到预期索引）、key_len、rows（预估扫描行数）、filtered，以及 Extra 里的 Using filesort、Using temporary、Using index（覆盖索引是好事）。据此判断：缺索引就补联合索引并遵守最左前缀，索引失效常见于列上做函数运算、隐式类型转换、以通配符开头的 LIKE。

**SSE 与大模型流式输出**：普通 HTTP 响应是一次性把完整 body 返回，服务端要先算完再发，首字延迟等于整段生成时间，客户端也无法中途取消。SSE（Server-Sent Events）是长连接上的单向流：响应头是 `Content-Type: text/event-stream`，服务端按 `data: ...\n\n` 的帧格式不断推送，基于 HTTP/1.1 分块传输就能实现，浏览器端用 EventSource 或 fetch 流式读取。它相比 WebSocket 的优势是简单、走标准 HTTP、自带断线重连与 Last-Event-ID 续传语义，缺点是单向、纯文本、并发连接数受浏览器同域限制。落地时的坑主要在中间层：Nginx 要关 proxy_buffering、网关与 CDN 要放行长连接，服务端要定期发心跳或注释帧避免被判定空闲超时，还要处理客户端中断后的生成取消，否则会白烧模型算力。

**软性问题的答法**：问「不足之处」不是让你自我否定，而是看你有没有自我认知和改进动作，选一个真实但不致命的短板（比如对某类中间件的生产调优经验不足），紧跟「我通过什么方式在补」。「Offer 情况」如实但克制地回答方向与进度即可，不必报具体公司薪资；重点是表达对当前岗位的兴趣和可到岗时间。「选岗位和团队考虑什么」建议给三条有优先级的理由：业务方向与个人积累是否匹配、技术成长与带教环境、团队协作与稳定性，避免只说薪资或只说稳定。最后一定要留出反问，问清团队负责的模块、新人上手路径和考核方式，这既是收集信息，也能体现你认真在选。
