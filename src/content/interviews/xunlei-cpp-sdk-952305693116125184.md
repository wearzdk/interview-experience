### 《参考解析》

**那段代码的问题是 use-after-free**：`loop.post(lambda)` 只是把任务塞进队列就返回，紧接着 `delete task` 释放了对象；等消息循环真正取出该任务执行时，lambda 捕获的 `this` 已经指向已释放内存，调用 `onData()` 就是一次悬垂指针访问。这类缺陷的特点是编译能过、单跑一次可能不复现，一旦队列延迟就必崩，而且崩溃堆栈看起来与业务无关。正确做法是把所有权做显式：对象用 `std::shared_ptr` 管理并继承 `enable_shared_from_this`，投递时值捕获 `shared_from_this()` 把生命周期延长到回调结束；若担心延长生命周期带来副作用则捕获 `weak_ptr`，回调里 `lock()` 判空后再调用。另外 `void onData();` 只有声明没有定义，链接期会报未定义符号；`new DownloadTask` 与 `new DownloadTask()` 对这个类等价（有隐式默认构造函数时是否值初始化只在聚合 / POD 上有差别），不是主要问题。

**看源码的收获要落到可迁移的结论**：OpenSSL 的 `BIGNUM` 用 digit 数组 + 有效长度 + 符号位表达任意精度整数，容量与长度分离、按 machine word 对齐——这是「定长块 + 长度游标」的通用结构，做内存池、缓冲区、协议解析都能复用；算法上 Karatsuba 把乘法从 O(n²) 降到约 O(n^1.585)，递归到阈值以下切换成更简单的实现，除法先归一化再移位减并修正试商。可以迁移的经验是「大问题递归分解、小规模切换简单算法」和「先归一化再计算，减少分支」。

**shared_ptr 与 weak_ptr 的准确说法**：shared_ptr 解决的是「多个所有者共享同一对象、最后一个所有者销毁时释放」，循环引用是它带来的问题而不是它解决的问题（用 weak_ptr 打断其中一条边）。控制块里强计数归零时立即析构被管理对象，弱计数归零时释放控制块——不是两个都归零才释放对象。weak_ptr 不能直接解引用，必须 `lock()` 提升成 shared_ptr：内部对强计数做一次原子的「比较并加一」，只有控制块存活且强计数非零才成功，因此不存在「检查通过后对象被别处删掉」的窗口；`expired()` / `use_count()` 只是瞬间快照，不能作为安全依据。

**线程安全要分三层**：不同线程各持自己的副本时，控制块的计数增减是原子的，跨线程传递副本安全；多个线程同时读写同一个 shared_ptr 实例（赋值、reset、置空）不安全，因为指针本身与计数在两处内存，需要加锁或用 `std::atomic<std::shared_ptr<T>>`；被管理对象内部的读写是业务数据竞争，要另外同步。unique_ptr 只是独占所有权，同样只保证「不同实例并发安全」。

**无锁编程**：指不依赖互斥量、靠原子操作与内存序保证并发正确，常见手段是 `std::atomic` + CAS 循环、tagged pointer 解决 ABA、`memory_order_acquire/release` 建立 happens-before。典型实现有无锁栈、单生产者单消费者环形队列、引用计数。代价要说清：高竞争下 CAS 反复重试反而更慢，内存序写错会产生极难复现的 bug，lock-free 不等于 wait-free。工程上只在热点路径、临界区短且可预测时才考虑。

**频繁分配释放的代价**：性能上每次分配要走空闲链表或分区、可能有锁竞争与系统调用，小对象占比高时开销显著；空间上长时间运行产生外部碎片，导致大块申请失败、RSS 持续上涨；缓存上对象分散导致命中率下降。对策是内存池 / 对象池：按 size class 分级、预分配大块、freelist 串空闲块、批量归还、线程本地池减少锁竞争；代价是常驻内存抬高、尺寸分布不适配时内部碎片更严重。

**自研内存池一定更快吗**：不一定，通用场景很难超过 tcmalloc / jemalloc / ptmalloc（它们已有 thread cache、size class、per-CPU arena）。自研能赢的前提是命中特定访问模式——对象大小固定、生命周期一致、可整块释放。判断是否值得做池看三个指标：每秒分配次数、对象平均生命周期、尺寸分布是否集中。

**按行与按列的差异根因是空间局部性**：C/C++ 是行主序，一行元素连续存放，按行遍历时一条 64 字节 cache line 里的数据全部被用上，硬件预取器还能识别连续访问；按列遍历步长等于一行长度，每条 cache line 只用一次就跳到很远的下一条，命中率与预取都失效。地址计算本身是常数级加法，还会被编译器强度削减，真正贵的是 cache miss，不要把原因说成「偏移运算多」。

**相邻还是间隔放：要看是否并发写**。如果两个 int 分别被不同线程频繁写，相邻放落在同一条 cache line 内会互相使对方的缓存行失效（MESI 状态来回翻转），性能可能下降数倍，这就是伪共享；解法是用 `alignas(64)` 做填充隔离，或让各线程操作各自的内存块再合并。伪共享不能靠加锁解决，加锁只会更慢。若只读或同一线程访问，相邻更好（一次读入、局部性高）。

**内存被踩乱的调查方法**：典型成因是数组与 `memcpy` 长度算错的越界写、off-by-one、悬垂 / 野指针、结构体对齐错位、DMA 写错地址、多线程无同步的并发写。开发期开 ASan（能报越界与 use-after-free）、UBSan、Valgrind memcheck，并发问题用 TSan；可疑地址用 gdb watchpoint 盯住，配合 core dump 与条件断点；也可以在缓冲区前后撒 canary 值定期校验，或用 `mprotect` 把相邻页设为只读捕捉非法写。线上则靠日志、快照与预期值比对。没做过就如实说，但要给出这套方法。

**TCP 感知断连**：TCP 本身没有「断链通知」，只能靠协议行为或超时发现。对端进程退出或主机重启时内核会回 RST 或 FIN，下一次读写立刻报错；链路静默（路由黑洞、光缆断）时已发数据收不到 ACK，按 RTO 指数退避重传，重传到 `tcp_retries2`（默认 15 次）才报 ETIMEDOUT，Linux 上通常十几分钟；如果双方都不发数据，读写会一直阻塞，永远发现不了。要更快发现就启用 `SO_KEEPALIVE` 并调小 `tcp_keepalive_time/intvl/probes`、用 `TCP_USER_TIMEOUT` 限制未确认数据的存活时长，最稳的是应用层心跳 + 空闲超时（下载类长连接普遍这么做）。

**拥塞控制四阶段**：慢启动阶段 cwnd 每 RTT 翻倍、指数增长到 ssthresh；进入拥塞避免后每 RTT 加约 1 个 MSS、线性增长；收到 3 个重复 ACK 触发快速重传与快速恢复，ssthresh 设为当前窗口一半、cwnd 减半后继续线性增长；RTO 超时才把 cwnd 回退到 1 个 MSS 重新慢启动。所以「涨到什么时候」有两个答案：涨到 ssthresh 就从指数转线性，遇到丢包才下调；实际发送窗口是 `min(cwnd, rwnd)`，还受应用层可写数据与 Nagle 影响。可以补现代算法：CUBIC 用三次函数替代线性增长，BBR 不再以丢包为信号，而是用带宽与最小 RTT 建模。

**map 与 unordered_map**：map 是红黑树，有序、查找插入删除稳定 O(logN)、支持 `lower_bound` 与范围查询、插入不使迭代器失效；unordered_map 是哈希表，平均 O(1)、最坏 O(N)、rehash 后迭代器全部失效、内存开销更大（桶数组 + 节点）。数据量很小或需要有序遍历时 map 反而合适；纯点查选 unordered_map。补一句工程细节：unordered_map 默认负载因子 1.0 触发 rehash，可以预 `reserve` 避免抖动。

**哈希冲突的解法**：开放寻址（线性探测、二次探测、双重哈希）把元素存在表内、缓存友好，但删除要留 tombstone、负载因子高时性能陡降；链地址法（拉链）桶挂链表、负载因子可更高、删除简单，桶内过长时转红黑树。`std::unordered_map` 用链地址法。可以再提 Robin Hood 哈希、Cuckoo 哈希与分布式场景的一致性哈希。

**复杂度**：哈希平均 O(1)，前提是哈希函数均匀、负载因子受控；最坏 O(N)（全部落同一桶），链转树后退化为 O(logN)，而且 O(1) 是摊销值，rehash 那一次是 O(N)。map 的查找、插入、删除都是 O(logN)，中序遍历 O(N) 且有序。
