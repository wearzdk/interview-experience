### 《参考解析》

**除功能与回归还要测什么**：性能（并发、响应时间、资源占用）、兼容性（浏览器/机型/系统版本矩阵）、安全（越权、注入、敏感信息泄露）、稳定性（长时间运行、内存泄漏、断网重连）、以及数据一致性（对账、幂等、并发写）。测试类型要能对应到风险，而不是罗列名词。

**幂等怎么测**：同一请求重复提交（相同 requestId / 相同业务唯一键）应得到同一结果且只产生一次副作用。验证手段：并发发两个相同请求（用脚本同时打），查库确认只有一条记录、余额只扣一次；再测「超时重试」场景（客户端超时但服务端已处理），确认重试不会重复扣款。断言的落点在数据库与账务，而不是接口返回。

**大文件分片上传的测试场景**：正常分片上传与合并、分片顺序乱序、分片重复上传（幂等）、分片丢失后重传、单片失败重试、上传中断后断点续传、秒传（相同文件 hash 已存在）、超大文件与超小文件、文件名与类型异常、并发上传同一文件、磁盘满与网络抖动、以及合并后文件的完整性校验（MD5 对比）。还要测边界：分片大小刚好整除、最后一片不足一片大小。

**秒杀防超卖的验证**：压测工具发 N 倍于库存的并发请求（JMeter / wrk / 自写脚本），断言成功下单数恰好等于库存、无负库存、无重复订单；同时看响应时间与错误率。进阶要测「库存回补」链路（未支付超时释放）与「缓存与 DB 一致性」（对账脚本比对）。用 DB 的 `WHERE stock > 0` 与 Redis 的原子扣减各测一遍，确认两层都拦住。

**高并发下的质量保障**：压测基线（容量与拐点）、限流与降级的验证（触发限流后是否优雅拒绝）、故障注入（依赖超时、Redis 挂掉）、数据一致性巡检（定时对账）、以及监控告警的可用性（告警能不能真的发出来）。

**AI code review 的提示词设计**：把任务拆细比一次问「找 bug」有效——按类别分别提问（空指针与边界、并发与线程安全、资源泄漏、SQL 注入与越权、异常吞掉、日志与敏感信息），每次只给一段 diff 与上下文（调用方约定、接口定义），要求输出「问题位置 + 风险 + 复现条件 + 建议」，并明确「没有问题就回答没有，不要凑数」。落地时把结果当候选清单，人工确认后再提，统计准确率迭代提示词。

**怎么提 bug**：标题写现象（不写猜测），正文给环境、复现步骤、期望与实际、日志与截图、影响范围与严重级别；能稳定复现的给最小复现用例。提之前自己先验证一次，避免浪费开发时间——这是测试在团队里建立信任的关键。
