### 《参考解析》

**IIC、SPI、串口三者的选型可以按「同步还是异步、几根线、能拉多远、能不能多挂」四条来答。** IIC 是同步半双工，两根线（SCL 时钟、SDA 数据）加地址寻址，一条总线可挂多个从设备，速率标准模式 100kHz、快速模式 400kHz、高速 3.4MHz，需要上拉电阻，协议开销大（起始、地址、应答），适合低速的传感器、EEPROM、PMIC 这类配置类器件。SPI 是同步全双工，四根线（SCK、MOSI、MISO、CS），片选决定从设备，没有寻址开销、速率可到几十 MHz，缺点是每多一个从设备就多一根片选、没有硬件应答机制；适合需要高速率或大数据量的场景，比如 Flash、屏幕、以太网控制器、ADC。串口（UART）是异步全双工，没有时钟线，靠双方约定的波特率采样，两根线（TX、RX）点对点，帧里有起始位和停止位，速率一般到几 Mbps，接线上要交叉、要注意电平（TTL 与 RS232/RS485 的差别，485 是差分、支持多点与更远距离）；适合调试串口、模块通信（GPS、蓝牙模组）、板间低速通信。被追问时补三点更有分量：长距离和抗干扰场景用 RS485 或 CAN；IIC 总线死锁（从设备拉低 SDA）怎么恢复，通常靠重新初始化或加总线复位电路；以及 SPI 的多个片选与走线长度对信号完整性的影响。

**驱动开发经历怎么讲才像真做过。** 按「平台 + 子系统 + 具体动作 + 排查过程」组织：比如「基于某 SoC 的设备树适配，把外设寄存器映射进 kernel 后注册字符设备，用 `file_operations` 暴露 ioctl，用 sysfs 做参数配置」。要点分值在于具体的调试手段：`dmesg` 看 probe 结果、`cat /proc/devices` 与 `/sys` 看注册情况、用示波器或逻辑分析仪抓 IIC 时序、用 `devmem` 直读寄存器、必要时用 ftrace 或 perf 定位延迟。如果只是写过 GPIO 点灯或调用过现成驱动，就如实说清楚边界并讲你理解到的层次（用户态 → 系统调用 → 驱动 → 总线控制器 → 外设），面试官问细节时坦白「这部分我只到读过代码的程度」，比硬编要好。

**Python 的垃圾回收是三套机制叠加，回答要分层。** 主机制是引用计数：每个对象的 `ob_refcnt` 归零时立即释放，优点是实时、无停顿，缺点是维护计数有开销而且**处理不了循环引用**（A 引用 B、B 引用 A，计数都不为 0）。所以第二层是分代回收（`gc` 模块）：标记清除处理容器对象的循环引用，对象分三代、新对象在第 0 代、活得越久越往上晋升，因为「大部分对象很快死掉」，所以扫描频率随着代龄降低。第三层是阈值触发：`gc.get_threshold()` 默认 `(700, 10, 10)`，分配数减释放数超过阈值就触发对应代的回收，可以通过 `gc.collect()` 手动触发、`gc.disable()` 关闭。追问点常见：`__del__` 里做的事会不会被调用、`gc.garbage` 是什么（带 `__del__` 的循环引用在早期版本里会进这个列表且不回收）、以及为什么大对象与高频分配会拖慢——回答时可以对比 C 的显式 `malloc/free`：C 没有运行时兜底、写错就是泄漏或野指针，Python 用「引用计数 + 分代」换来了安全但付出了停顿与内存开销，`weakref` 则是打断循环引用的常用手段（缓存里存弱引用）。

**C 与 Python 的运行机制差别在「编译成什么、谁来执行」。** C 是编译型：预处理（宏展开、头文件展开）→ 编译（到汇编）→ 汇编（到机器码目标文件）→ 链接（合并库、重定位符号），产物是平台相关的可执行文件，运行时由操作系统加载并直接由 CPU 执行，所以「零运行时开销」，但换平台要重新编译。Python 通常先编译成字节码（`.pyc`，存在 `__pycache__`）再由 CPython 虚拟机循环解释执行，字节码是平台无关的中间表示，代价是解释开销（所以热点代码要靠 C 扩展或 Cython、numba 掉出解释循环）；也解释了为什么 GIL 存在——CPython 用引用计数做内存管理，为了不让计数操作处处加锁就用了全局解释器锁，所以 CPU 密集型任务多线程拿不到并行，要用多进程。要能顺势说清 JIT（PyPy、JVM）的取舍：用运行时编译换执行速度，代价是启动预热与内存。

**YOLO 训练、过拟合与数据增强要讲清判据和对策。** 过拟合的判据是训练损失持续下降而验证 mAP 停滞或下降，两者背离就说明模型在记数据而不是学特征。对策按性价比排序：加数据（最有效，尤其是补充失败场景与长尾类别）、用更强的增强、加正则（weight decay、Dropout）、减小模型容量或冻结部分 backbone 做微调、早停（按验证集 mAP 保存最佳权重而不是最后一个 epoch）。数据增强在检测任务里常用的有随机缩放与裁剪、马赛克拼接（Mosaic，把四张图拼成一张，等效于小批量里看到更多目标与更多尺度）、MixUp、HSV 色彩抖动、随机翻转（注意水平翻转对左右有语义差别的场景要慎用）、以及 Copy-Paste 与类别平衡采样。回答时要提一句「增强要与部署场景一致」——训练时加了很强的形变而线上目标都是正立清晰的，反而掉点。另外要能把指标说清楚：mAP@0.5 与 mAP@0.5:0.95 的区别、precision/recall 的取舍由置信度阈值决定，以及 NMS 的 IoU 阈值如何影响召回。

**量化精度与显存这题要能算公式。** 精度就是每个参数用多少位存储：FP32（4 字节）、TF32/BF16/FP16（2 字节）、FP8（1 字节）、INT8、INT4。显存占用分三块：权重（参数量 × 每参数字节数，训练时还要乘以优化器状态，Adam 的动量与方差在混合精度下约为权重的 4 到 6 倍，这也是微调比推理更吃显存的原因）、激活与中间张量（与 batch size、分辨率、序列长度正相关）、以及 KV cache（按层数 × 头数 × 序列长度 × 精度算，长上下文推理时它常常是显存大头）。举个数：7B 模型 FP16 权重约 14GB，FP8 约 7GB，再叠加 KV cache 与激活才是实际需求。量化的关键细节：权重可以 per-channel，激活通常 per-tensor；INT8/FP8 需要 scale（以及 zero point），要在校准集上统计范围，否则截断误差会让精度掉得厉害；FP8 有 E4M3 与 E5M2 两种格式，前者精度高适合前向，后者动态范围大适合梯度；硬件支持度决定收益——只有新架构（Hopper、Ada、AMD 的对应代数）才有 FP8 的原生算力，否则量化只省显存不加速，甚至因为反量化而变慢。被追问「量化之后为什么精度还能保住」，答「神经网络的参数冗余度高、且推理对单个权重不敏感，但敏感层（首尾层、LayerNorm、softmax）通常保留高精度」就到位了。

**AI 工具与 Linux 那些问，重点在「说得出用在哪、怎么校验」。** 用 AI 辅助开发的具体例子要落到工程动作上：生成 DTS 与寄存器配置模板、读不懂的内核报错丢给模型要排查思路、把 C 代码的编译告警当输入让它解释、写测试脚本与正则。Codex 的工作树（worktree）机制可以理解为给每个任务开一份独立的仓库检出，多个任务并行时不互相污染工作区，变更以补丁形式评审后合入——这类工具的价值就在于隔离与可回滚。常用 Linux 命令按场景分：文件与查找（`ls -lh`、`find`、`grep -rn`、`rsync`）、进程与资源（`ps/top/htop`、`free`、`iostat`、`vmstat`、`lsof`）、网络（`ip`、`ss`、`ping`、`traceroute`、`tcpdump`、`curl -v`）、日志与排查（`dmesg`、`journalctl -u`、`tail -f`）、权限与磁盘（`chmod/chown`、`df -h`、`du -sh`）、以及文本处理（`awk`、`sed`、`xargs`）。「有没有调过内核」如果答案是「改过配置、编过模块、加过打印」就直说，能讲清 `make menuconfig` 裁剪、insmod 加载与内核日志验证的流程，也是实打实的经验。
