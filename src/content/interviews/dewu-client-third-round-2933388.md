### 《面试题目》

1. 自我介绍，并按简历项目逐条追问：你们自研的算法是怎么做的？
2. 两个用户同时拖拽修改数据，怎么处理并发？
3. 后端数据库已处理完但响应丢了，怎么处理？重试该怎么区分不同场景？
4. 上传链路怎么优化失败率和耗时？
5. 前端发请求修改数据库，如果丢包失败重试，怎么避免重复操作？
6. 你有写 React Native，在低端机上列表滑动卡顿有什么优化想法？
7. 性能指标你是怎么排查的？
8. 平时如何运用 AI？AI 产出逻辑混乱、不符合预期时怎么解决？
9. 除了 SDD 相关的，你平时最常用哪些 skills？有没有自己写过 skills，写了哪些方面？

### 《参考解析》

**并发拖拽这类协同编辑题，核心是「冲突检测 + 合并策略」**：最轻的是字段级锁或乐观锁版本号（提交时带上读到的 version，不匹配就拒绝并让前端提示重试），中等是操作变换 OT / CRDT（每个操作可交换、最终收敛），重的是分段锁住被编辑的实体。答的时候要说清「谁赢」的规则对用户是否可解释——比如「后提交覆盖」会在拖拽场景明显丢操作，所以通常按操作粒度合并而不是整行覆盖。

**「数据库已处理但响应丢失」是分布式经典题**：客户端无法区分「没收到」和「服务端没处理」，所以服务端必须让重复请求安全——客户端给每个业务请求带幂等键（或客户端生成的 requestId），服务端按 key 记录处理结果，重复请求直接返回首次结果（幂等表 / Redis 缓存响应）；写操作落库时用唯一约束兜底。重试策略要区分场景：网络超时、5xx 可重试（指数退避 + 抖动 + 上限），4xx 不重试（尤其 409 冲突要交给人处理），非幂等接口（支付、下单）必须先把幂等做掉再谈自动重试。

**上传链路降失败率与耗时**：分片 + 断点续传（失败只重传该片）、并发度控制（3~5 并发，避免占满带宽）、弱网重试与降级（切小片、降低压缩质量）、走就近接入点与 CDN 加速、上传前压缩与格式选择、失败原因分级上报（网络 / 鉴权 / 服务端）便于定位。指标上要区分「首次成功率」和「最终成功率」，后者才反映用户真实体验。

**RN 低端机列表卡顿**：先定位是 JS 线程还是原生渲染——用 Flipper / Systrace / 自带 profiler 看帧耗时与 JS FPS；常见手段是 `FlatList` 的 `removeClippedSubviews`、`windowSize` / `initialNumToRender` 调小、`getItemLayout` 免测量、`React.memo` + 稳定 key 减少重渲染、图片降采样与占位、复杂动画交给原生驱动（`useNativeDriver`）、长列表换 FlashList / RecyclerListView。低端机额外要注意内存与主线程阻塞，避免在 `onScroll` 里做重计算。

**AI 产出「逻辑混乱」的处理**是这类面试的加分题：把任务拆小、给它明确的输入输出与验收标准（schema、示例）、要求它先给计划再动手、每步产出可运行可验证；自己 review diff 而不是整段接受；反复出错就换模型或换方案，而不是在同一段 prompt 上加更多规矩。
