### 《面试题目》

1. 自我介绍。
2. 盘点一下你平时使用 Agent 的情况（用过哪些、怎么用）。
3. 手撕一：实现一个线程安全的定长事件缓冲区（SSE buffer）。
4. 手撕二：实现 RRF（Reciprocal Rank Fusion，倒数排名融合）多路召回融合。
5. 反问。

### 《参考解析》

**三面直接写代码，考的是工程直觉而不是背诵**。前两轮已经把语言、框架、项目筛过一遍，这一轮看的是：拿到一个含糊需求，你会不会先问约束；写出来的东西有没有边界处理；能不能边写边讲清 trade-off。所以第一句话不该是 `#include`，而应该是「定长是多大、满了是覆盖最旧还是阻塞写端、单生产者还是多生产者」。

**SSE 缓冲区拆开看就是「环形队列 + 条件变量」**。底层用数组加 head / tail / size 三个下标，写满时的语义决定整个设计：事件流场景通常选覆盖最旧（客户端断线重连只关心最新状态，旧 token 没有重放价值），这样写端永不阻塞，读端慢只会丢帧；如果要求不丢事件，就必须阻塞生产者做背压，代价是上游 LLM 流被拖慢。线程安全靠一把 mutex 加两个 condition_variable（非空、非满），而且 `wait` 必须写在谓词循环里防虚假唤醒。工程上还有几个容易被追问的点：每个事件带自增序号，配合 SSE 的 `Last-Event-ID` 做断点续传；持锁期间只做拷贝，绝不持锁写 socket；读端批量取出而不是逐条唤醒，否则高吞吐下上下文切换比拷贝还贵。测试要覆盖空 / 满边界、并发读写、以及「写入后读端没被唤醒」这种丢唤醒 bug。

**RRF 的公式只有一行，但要讲清为什么用它**：`score(d) = Σ_i 1 / (k + rank_i(d))`，k 通常取 60。多路召回（向量、BM25、关键词、规则）各自给出一个有序列表，RRF 只看名次、不看分数，所以不需要把余弦相似度和 BM25 分数归一化到同一量纲——这是它相对加权求和最大的优势，调参成本几乎为零。实现是拿一个 `dict[doc_id] -> score` 聚合，各路遍历时按名次累加，最后排序取 topN，复杂度 O(N log N)。坑在 doc id 对齐：不同召回源的 id 体系可能不一致，必须先统一；同一个文档在同一路里出现多次要按最好名次算，不能重复累加。k 的作用是平滑头部——k 越大，第一名和第二名的差距越小，融合结果越平均；k 越小越偏向单路的头部结果。它的代价是丢掉分数信息，所以工业上常见的是 RRF 做粗融合，再交给精排模型。

**「Agent 使用盘点」不是让你报工具名**。这题想听的是：在哪些环节用（写代码、读陌生仓库、查日志、生成测试）、怎么验证产出（跑一遍、读懂了再合、复杂逻辑不让它独立产出）、踩过什么坑（幻觉 API、改错文件、上下文越滚越脏）。能说出「我怎么判断它什么时候不可信」，比列出十个工具名有效得多。

**最后一条经验**：手撕题写不完很常见，先把接口签名、数据结构和关键路径写清楚，再补边界；中途主动说「这里我选覆盖而不是阻塞，因为……」。面试官看的本来就是你的判断过程，代码只是载体。
