### 《面试题目》

1. 自我介绍。
2. 之前实习负责些什么内容？有做过后端或者全栈的开发经历吗？
3. 介绍一下你之前每段实习做的事情。
4. 之前是怎么一套代码实现多端开发的？
5. 之前实习碰到最难的事情是什么？
6. 你现在 AI Coding 占比多大？有什么 AI Coding 经验分享？
7. 场景题：一个请求经过网关、分发、限流中间件，预期 1 个 IP 请求 20 次，但实际发生了 120 次，你怎么排查？
8. 场景题：上传一份 PDF，解析 PDF、建模 3D 结构、计算尺寸、计算报价并反馈用户，整个流程要 5 秒内响应，怎么优化和实现？
9. 反问：业务做什么？有没有转正？

### 《参考解析》

**多端一套代码要讲清技术选型与代价**：常见方案是跨端框架（Taro、uni-app、React Native、Flutter）或「同一套业务逻辑 + 多套渲染层」。要说明选型理由（团队规模、目标平台、性能要求、生态），以及实际遇到的坑：平台差异（API 能力、导航、支付、分享）、样式兼容、包体积、原生能力调用、调试与发版流程。如果只是「一套 React 代码分别打包 Web 和 App 壳」，如实说明，不要夸大成完整的跨端方案。

**限流场景的排查路径**：先确认限流口径——是按 IP、按用户还是按接口，窗口是固定窗口、滑动窗口还是令牌桶；再看 120 次是否落在同一窗口（固定窗口的边界突刺会让两个窗口各放 20 次，但 120 次明显超出）；然后查 IP 的获取方式，是否经过多层代理导致 `X-Forwarded-For` 被伪造或多值拼接，限流键取错；再查多实例部署下限流状态是否本地内存（每台 20 次，6 台就是 120 次），需要换成 Redis 集中计数；最后看是否有重试、并发重复提交、以及网关与业务层各限一次导致统计口径不一致。排查手段是看网关访问日志按 IP 聚合、比对限流中间件的命中记录、在测试环境复现。

**PDF 转 3D 报价的 5 秒方案**：把链路拆成「上传—解析—建模—算价—返回」，逐段定预算。上传走对象存储直传并做分片与压缩；解析用异步任务队列，PDF 文本层能直接取就用文本解析，扫描件才走 OCR；3D 建模如果依赖几何计算，先做参数化模板匹配而不是全量重建，把重计算放到后台 Worker，前端先返回「已受理 + 进度」；算价是纯计算，做成同步轻量服务并缓存相同规格的结果。5 秒内要给出响应，通常意味着「同步段只做校验与轻量估算，重活异步化 + 结果推送」，并对超时做降级（先给区间报价，精确报价后续更新）。回答时给出各段耗时预算与降级策略，比只讲「用缓存」完整。
