### 《参考解析》

**这场面试的形态值得先说清楚。** 作者的原话是「全程围绕着简历上的项目拷打，没怎么问八股，就连最后的手撕都没了」，追问虽然密但没有压力。这类面试的评分点不在「答对多少知识点」，而在「你对自己写的东西理解到哪一层」——同一个项目，能讲到设计取舍、失败尝试、线上指标，和只能复述用了什么框架，差距很大。

**为什么用 Eino、它和 ADK、Graph 的区别。** Eino 是字节开源的 Go 语言 LLM 应用框架，核心抽象是 Component（模型、工具、检索器）、Graph（把组件编排成有向图，支持分支、循环、并行）和 Chain；选它的直接理由通常是团队主语言是 Go、需要与现有服务同进程集成、以及图编排能表达多步 Agent 流程。ADK 是 Google 的 Agent Development Kit，偏 Agent 生命周期管理（会话、记忆、工具注册、回调），Graph 更偏「把一次请求编排成流程图」。回答这题的关键不是背各自特性，而是说清自己项目需要什么：如果核心是多步、可分支的流程控制，Graph 更合适；如果核心是 Agent 的会话状态与工具调度，ADK 更省事。作者被追问「除了适配 Go 还有别的原因吗」，正是在确认选型是不是只看了语言。

**ES 的特点与写入机制。** 特点三句话：倒排索引支撑全文检索与相关性打分、支持结构化过滤与聚合、天然分布式（分片 + 副本）可水平扩展。写入路径是这题的核心：写请求先到协调节点，按 `_routing`（默认 `_id`）路由到主分片，主分片写入内存 buffer 并同时追加 translog，随后同步到副本分片；`refresh`（默认 1 秒）把 buffer 生成新的 segment 并打开供搜索，所以 ES 是「近实时」而不是实时；`flush` 触发 Lucene commit 并清空 translog；后台 `merge` 把多个小 segment 合并成大 segment 并真正删除标记删除的文档。几个常被追问的点：为什么删除只是标记（segment 不可变）、`refresh_interval` 调大能提升写入吞吐但会拉长可见延迟、translog 的 `durability` 设为 `request` 时每次写都 fsync。

**多路检索与 RRF。** 多路检索是把 BM25（稀疏、关键词精确匹配强）与向量检索（稠密、语义泛化强）并行召回，再合并。BM25 的核心是 TF-IDF 的改进：词频饱和（`k1` 控制饱和速度）、文档长度归一化（`b`）、IDF 按文档频率计算。RRF（Reciprocal Rank Fusion）的公式是 `score(d) = Σ_i 1 / (k + rank_i(d))`，`k` 通常取 60，作者被追问的正是这个常数。为什么不能直接把两路分数相加：BM25 分数是无上界的实数、余弦相似度在 -1 到 1 之间，量纲和分布都不同，直接相加会让某一路主导；RRF 只用排名、不用原始分数，天然免疫量纲问题，代价是丢掉了分数里「差多少」的信息。进阶做法是加权 RRF 或用学习到的融合模型。

**RAG 的窗口与章节补全。** 窗口长度指召回后送给模型的上下文预算，通常按 token 数设定（例如 4k–8k），超过就截断或压缩。截断策略要能回答「截哪一段」：按相关性排序取头部、按句子边界切、或用滑动窗口重叠保留上下文。作者提到的「章节关联」是把同一章节下的相邻 chunk 建立父子或兄弟关系，召回命中某个 chunk 后把它所属章节的标题、前后段落一并带上，解决「chunk 切碎了语义不完整」的问题；章节补全的做法通常是二级检索：先用小 chunk 召回定位，再用它所属的大块（section）替换进上下文。

**长任务的持久化与 SSE 断连。** Agent Run 的持久化一般落在数据库里，记录 run 的状态、已执行的步骤、工具调用结果与 checkpoint；有重放能力意味着能从某个 checkpoint 继续，而不是从头再来。SSE 断连的补全有两个层次：传输层用 `Last-Event-ID` 让客户端重连时带上最后收到的事件序号，服务端从该序号之后续发；业务层用 checkpoint 保存阶段性结果，重连后先补发缺失事件、再继续推。作者坦白「后面部分还没做」，这在实习面里是可以接受的答法——说清方案边界比假装做完更好。

**revision 字段与并发。** revision 是乐观锁的版本号：读取时带出当前 revision，更新时 `WHERE id = ? AND revision = ?` 并 `revision = revision + 1`，影响行数为 0 说明期间被别人改过，重读重试或报冲突。它解决的是「读-改-写」之间的丢失更新，代价是冲突时需要重试；高冲突场景要换悲观锁或串行化。面试官继续追问「如何处理并发」，可以补：冲突重试要设上限、幂等键要带上、以及长事务要拆短。

**seq 与落库。** 聊天系统的 seq 有全局自增和会话内自增两种。全局 seq 便于做全量游标与跨会话排序，但写入热点集中、分库分表后难保证连续；会话内 seq 让同一会话的消息严格有序、写入按会话分散，代价是跨会话无法直接比较。落库过程要讲清三件事：消息先写库还是先推送（一般是先落库拿到 seq 再推送，保证可恢复）、如何保证同一会话内 seq 连续（会话级锁或 Redis 自增）、以及写扩散到收件箱表还是读时聚合。

**Redis 的 Lua、缺点与线程模型。** 红包场景的 Lua 脚本通常做「原子地判断库存 + 扣减 + 记录领取」，把多步操作合成一次原子执行，避免并发超发。Lua 的缺点作者只答了「不能回滚」，面试官纠正那是 Redis 事务的缺点；Lua 真正的缺点是阻塞——脚本在 Redis 主线程里串行执行，脚本越长、循环越多，阻塞其他命令越久，所以脚本要短、不能做大循环，`lua-time-limit` 只是让 Redis 开始拒绝其他命令而不是中断脚本。Redis 的线程模型：命令执行是单线程的（保证原子性与无锁），但 6.0 起 IO 是多线程的（读写 socket、协议解析可以并行），持久化、过期删除、集群同步也有后台线程；所以准确说法是「命令处理单线程，网络 IO 多线程」。

**死锁与推送优化。** 红包领取与退款是否死锁，取决于加锁顺序与是否跨 key：同一份库存用 Lua 原子操作不会死锁；如果领取和退款分别对「红包记录」和「用户余额」加锁且顺序相反，就会死锁，解法是固定顺序、用带超时的锁、或把两步合成一次 Lua。Kafka 推送失败只靠上线后拉取是不够的，可做的优化：消费端维护 offset 与本地游标、失败进重试队列并做退避、客户端长连接断线重连后按游标拉增量、以及把「拉取」从全量轮询改成基于 seq 的增量拉取加服务端推送补偿。批发布是把多条消息合并成一次写入或一次推送，减少网络往返与数据库事务次数，要注意批次大小与延迟的权衡。
