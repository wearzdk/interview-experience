### 《面试题目》

1. 讲讲索引在什么情况下会失效。
2. 你说的隐式转换，能举个例子吗？为什么转换之后就用不上索引？
3. 你项目里那次优化，怎么确定是索引失效导致的？
4. 如果 `key` 有值但查询还是很慢呢？
5. 联合索引里范围查询后面的字段，为什么就用不上了？
6. 索引列上套函数、前导模糊、`OR` 分别破坏了什么？
7. 这三次追问其实考的是同一件事，你会怎么总结？

### 《参考解析》

**第一次追问：隐式转换转的是什么**。订单表 `order_no` 是 `varchar(32)`，代码里用 `Long` 接参，生成 `WHERE order_no = 1001`。测试环境数据量小没感觉，上线后直接拖垮接口。机制是：字符串列与数字比较时，MySQL 会把列上的每一行转成数字再比，索引里存的是字符串的排序，转成数字后 B+ 树的有序性与要比较的值对不上，优化器只能放弃索引。方向性必须记准：字符串列被转才失效；数字列传字符串是常量做转换，索引还能用。

**第二次追问：怎么证明是索引失效**。看 `EXPLAIN` 的 `type` 从 `ref` 变成 `ALL`、`key` 变成 `NULL`、`rows` 从个位数涨到六位数。但面试官追问「如果 `key` 有值但查询还是很慢呢」——这时要讲清覆盖索引与回表：`select *` 走二级索引要回表，命中行数多时回表的随机 IO 比全表顺序扫还贵，优化器会主动放弃索引。这不是失效，是成本选择。验证方式是看 `Extra` 里有没有 `Using index`：有就是覆盖索引，没有就要回表。慢查询先看三样——`type`、`rows`、`filtered`；`rows` 大而 `filtered` 小，往往说明索引选择性差。

**第三次追问：范围查询后面为什么断了**。联合索引 `(a, b, c)` 在 B+ 树里按 `(a, b, c)` 依次排序：a 相等时 b 有序，b 相等时 c 有序。一旦 b 走了范围，命中区间内 b 的值各不相同，c 在这个区间里就不再全局有序，只能逐行回表过滤。所以 c 不是「没建索引」，而是「在这一次查询里用不上索引的有序性」。

**同一类问题的其他表现**：索引列上套函数（`DATE(create_time)`）破坏有序性，改成左闭右开区间；前导模糊 `LIKE '%abc'` 破坏有序性，因为从左往右定位时前面不确定；`OR` 连接的字段只要有一个没索引，整体就可能退化成全表扫。

**总结成一句话**：索引能不能用，取决于查询条件能不能利用 B+ 树上的有序性。隐式转换破坏了有序性，函数破坏了有序性，前导模糊破坏了有序性，范围查询之后有序性局部丢失——所有场景都是这一句话的推论。所以看到「索引失效的十种场景」这类文章时，先自己推一遍原因，推不出来的就打开 `EXPLAIN` 实测。
