### 《面试题目》

1. 先自我介绍一下，说详细点（会讨论几个项目相关的问题）。
2. 页面访问速度慢，让你去排查，你的排查思路是什么？
3. 开放性题：根据我的 AI 项目做一个变种设计。
4. 讲一下你对 Spring Cloud 的理解，有哪些组件？
5. 平时开发的时候用什么样的 AI 开发工具？
6. 说说你对 AI Coding 的理解。
7. 反问。

### 《参考解析》

**页面变慢要先分层、再定位，别一上来就加缓存。** 按请求链路切：客户端（设备性能、网络、 bundle 体积、首屏资源阻塞）→ CDN/网关（命中率、回源、超时、限流）→ 应用（线程池排队、锁竞争、GC、连接池、序列化、慢 SQL 之外的 N+1）→ 依赖（数据库慢查询、缓存命中率、下游 RPC、重试放大）→ 渲染（SSR 耗时、接口瀑布流）。方法上先看分位耗时（P50/P95/P99），单看均值会被长尾掩盖；用 traceId 串链路找最慢 span；前端看 Lighthouse/Performance 面板与资源瀑布图，后端看 APM、GC 日志、线程栈；数据库看慢查询日志和 `EXPLAIN`。定位到瓶颈后再优化，优先级通常是：加/改索引、减少请求数与返回体积、加缓存并设计失效、异步化与削峰、限流降级。上线后用同一份度量对比前后，避免「感觉快了」。

**Spring Cloud 要按「解决什么问题」讲组件。** 服务注册与发现（Nacos/Eureka/Consul）：服务实例上下线、健康检查、客户端负载均衡；配置中心（Nacos/Apollo）：配置集中管理、灰度、热更新；网关（Spring Cloud Gateway）：路由、鉴权、限流、跨域；负载均衡（LoadBalancer/Ribbon）：客户端侧选实例；熔断限流（Sentinel/Resilience4j）：防止故障扩散；远程调用（OpenFeign）：声明式 HTTP 客户端；链路追踪（Sleuth/Micrometer Tracing + Zipkin）；消息驱动（Spring Cloud Stream）；分布式事务（Seata）。答题时补一句「Spring Cloud Alibaba 与 Netflix 系的差异」以及「现在很多团队用 K8s Service + Istio 替代部分能力」，说明你理解演进，而不是只背组件名。

**AI 项目变种题：先澄清需求，再讲取舍。** 开放性题没有标准答案，面试官看的是结构：目标与用户是谁、输入输出是什么、数据从哪来、模型选型与成本、离线/在线链路、如何评估、如何兜底。比如原项目是「简历解析 + 岗位匹配」，变种可能是「多轮对话式岗位推荐」，那就要讲：会话状态怎么存、意图识别与槽位填充、检索（向量 + 关键词）与重排、生成时的引用与免责、以及用户反馈如何回流。别一上来就堆模型名，先把「不确定的地方」问清楚，再给一个最小可行方案和迭代路径。

**AI Coding 的理解要落到工作流。** 工具层面：补全（Copilot）、对话式改代码（Claude Code/Cursor）、批量重构、单测生成、代码审查、日志/报错分析。价值不在「写得更快」，而在把重复劳动（样板代码、测试、迁移、文档）自动化，让人把时间花在设计与判断上。风险：模型会编 API、忽略边界、产生看似合理的错误；所以必须有编译、类型检查、测试、review 四道闸，关键路径不允许「生成即上线」。团队层面要建立规范：哪些场景可以用、生成代码要不要标注、敏感数据不能进 prompt、以及如何度量提效（交付周期、缺陷率，而不是「生成了多少行」）。

**关于转正与选择。** 面试通过但 HR 对转正规则含糊（「看表现」「时间随机」），这本身就是信息：没有明确的转正名额与评估标准，意味着不确定性很高。判断一个实习机会，除了转正概率，还要看：团队是否有人带、做的是不是核心业务、能不能积累可迁移的能力、以及日常实习的时间成本。如果对方连「转正评估的时间点和标准」都说不清，谨慎是对的；拒绝时保持礼貌，留一条以后合作的路。
