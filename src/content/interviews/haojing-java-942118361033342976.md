### 《面试题目》

1. 数据权限体系为什么要重构？原来的 roleKey 硬编码有什么问题？
2. 同步水位线是什么？增量同步时怎么保证不丢不重？
3. xxl-job 的分片广播路由策略怎么用？多个分片同时执行怎么避免重复处理？
4. HashMap 链表长度达到 8、但数组容量小于 64 时，为什么优先扩容而不是直接树化？
5. 设计一个多租户 SaaS 的数据隔离方案。
6. 讲一个你主导过的最复杂的权限系统重构。
7. 线上故障排查：讲一个真实的 P1 级事故，怎么定位、怎么回滚、事后怎么补。

### 《参考解析》

**数据权限重构**的核心是把权限规则从代码里解耦：用 AOP 拦截 Mapper 方法，解析当前用户的部门、角色、数据等级，通过 MyBatis 动态 SQL 追加 WHERE 条件；动态 SQL 必须参数化，不能字符串拼接，规则用本地缓存加 Redis，变更时主动失效。灰度迁移可以新旧权限并行、按用户比例切流，并准备分钟级回滚预案。

**同步水位线**是增量同步的游标，记录上次同步到的位置（时间戳或自增 ID）。不丢不重靠“幂等写入 + 成功后推进水位线”：唯一键冲突更新，失败不推进；同一时间戳多条记录要用 `(timestamp, id)` 组合游标，水位线回退要有补偿任务。xxl-job 分片广播按分片数分配执行器，每个执行器只处理自己的分片（如 ID 取模），重复处理用分布式锁抢占或数据库唯一约束兜底。

**HashMap 树化**：容量小于 64 时冲突主要来自容量不足，扩容比树化更便宜、更有效；容量足够大后冲突才更可能是真实哈希碰撞，此时红黑树的 O(log n) 才有收益。多租户隔离按成本从高到低分独立库、共享库独立 Schema、共享 Schema 加租户 ID，选型看租户规模、合规和运维成本；共享 Schema 要用 SQL 拦截器强制追加租户条件，防止越权。
