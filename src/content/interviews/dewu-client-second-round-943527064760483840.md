### 《参考解析》

**版本号与参数快照的分工。** 版本号解决的是「顺序」问题——每次状态变更带上单调递增的版本，写入时用 `where version < ?` 或 CAS 比较，旧版本的数据无法覆盖新版本。但它只能告诉你「谁更新」，不能告诉你「这个状态是基于什么参数算出来的」。参数快照解决的是「可复现与可解释」——把当时的价格、库存、时段、用户资格等输入固定下来，事后能重算、能对账、能解释「为什么当时显示可预约」。所以两者不是替代关系：版本号防覆盖，快照防「算错了却查不出原因」。还有个现实原因：业务规则会变，半年前的订单用今天的规则重算必然不一致，快照是唯一的事实来源。

**版本号什么时候会重复。** 三种典型情况：① 多端并发写——两个客户端各自基于版本 5 计算，都提交了版本 6，需要服务端用条件更新（`version` 必须等于读到的值）来保证只有一个成功，另一个重试；② 版本由客户端生成（时间戳、自增 ID）——时钟回拨、多设备各自自增都会撞；③ 分库分表或离线任务重新导入数据时，版本号被重置或覆盖。解决方向是「版本号由权威服务端集中生成（数据库序列/Redis INCR）」，并且写入必须带「期望旧版本」做乐观锁，而不是「写入新版本」。

**参数快照会不会太长。** 会。做法是「存引用不存全量」：快照只存计算所需的最小字段集 + 一个内容哈希，完整参数放到对象存储/宽表里按 key 取；或者只存「影响结果的关键参数 + 规则版本号」，规则本身单独版本化管理。读取时按需回表，避免每行都背一个大 JSON（影响写入与索引效率）。如果确实要内联，就限制字段数并做压缩。

**CPU 不高但请求变慢、队列增长，怎么排查。** 先分清「等待」还是「计算」：CPU 不高说明不是算力打满，大概率在下游等待或锁竞争。按层排查：① 线程栈——`jstack` 连续抓几次，看线程都停在哪个方法（`WAITING` 在连接池/HTTP 客户端、`BLOCKED` 在锁、`RUNNABLE` 但在 socketRead 说明是 IO 等待）；② 下游依赖——数据库慢查询（看慢日志与连接池等待数）、Redis 延迟、第三方接口超时；③ 连接池与线程池——池大小是否小于并发、获取连接的超时是否过长、队列是否无界（无界队列会掩盖问题，只表现为延迟上升）；④ GC——Full GC 停顿会让请求整体变慢但 CPU 平均值不高（看 GC 日志的 STW 时间）；⑤ 锁——热点 synchronized、分布式锁排队；⑥ 网络——DNS 解析、TLS 握手、丢包重传。排查动作从「看指标（QPS/RT/队列长度/连接池活跃数）→ 抓线程栈 → 定位下游 → 复现压测」推进，别一上来就加机器。

**客户端导致慢但 CPU 不高。** 常见原因：主线程被网络请求阻塞（同步 IO）、图片解码与下载在主线程、布局层级过深导致多次 measure/layout（CPU 占用体现在渲染线程但平均不高）、磁盘 IO（读写沙盒/数据库）、以及「数据已下载但没触发刷新」这类逻辑问题——作者项目里就是图片下载完了但 UI 没更新，看起来像「加载慢」，实际是回调丢了或列表没 notify。排查用「打点计时」：从发起请求到回调、从回调到渲染各段的耗时分别埋点，先定位是哪一段慢，再谈优化。第一次调用还有作用这个追问，通常指「首次请求做了初始化/鉴权/冷启动预热」，后续请求才能走缓存，所以慢的其实是第一次。

**ConcurrentHashMap 的 JDK 7 与 8。** JDK 7 用「Segment 分段锁 + HashEntry 数组」，默认 16 个 Segment，每个 Segment 继承 ReentrantLock，锁粒度是 Segment，并发度等于 Segment 数；扩容是 Segment 内部扩容。JDK 8 去掉了 Segment，改成「Node 数组 + 链表/红黑树」，锁粒度降到单个桶，空桶用 CAS 直接插入、非空用 `synchronized` 锁头节点，并支持多线程协助扩容；同时把 size 改成 `baseCount + CounterCell[]` 分段计数。JDK 8 的优势是并发度更高（等于桶数而非 16）、内存更省、查询在冲突多时是 O(log n)。

**HashMap 为什么不适合并发写。** 它没有任何同步：并发 `put` 可能同时往同一个桶写，导致元素丢失；JDK 7 的头插法在并发扩容时可能形成环形链表，之后 `get` 会死循环（CPU 100%）；`size` 是普通变量，并发自增会算错，进而影响扩容时机；`modCount` 与迭代器的 fail-fast 也只是「检测到就抛异常」，不是线程安全。并发场景要么用 ConcurrentHashMap，要么外部加锁，要么用线程封闭（每个线程自己的 map 最后合并）。

**AI Coding 的质量把控。** 一条可执行的流程：明确改动范围（告诉它只能动哪些文件）→ 要求先给方案再写代码 → 小步提交、每步能编译能跑 → 关键路径必须补测试 → 人工读 diff（重点看异常处理、边界、有没有偷偷改无关文件、有没有 `catch {}` 吞错）→ CI 必须绿。常见问题：模型「幻觉 API」（调不存在的方法）、过度重构、忽略项目约定（命名、目录、状态管理方式）。解决靠把约定写进仓库的规则文件 + 让它先读相关代码再动手。

**「压力最大的交付」怎么讲。** 用 STAR，重点放在「你怎么做取舍」：时间不够时砍了什么、保了什么、怎么和上下游对齐预期、最后结果如何（有没有延期、有没有降级上线）。面试官在意的是判断力与沟通，不是「你加了多少班」。

**AI 给的学习方案怎么用。** AI 擅长给「路线图 + 资源清单 + 练习题」，但不了解你的真实薄弱点。正确用法是：先自己做一个小项目暴露问题，再让 AI 针对具体卡点解释与出题；把 AI 的方案当成「待验证的假设」，用写代码和讲给别人听来检验。作者被追问「第一次调用还有什么作用」时能答出「初始化/预热」，说明面试官在验证你是真的排查过，而不是背结论。
