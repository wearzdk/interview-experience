### 《参考解析》

**Saga 与 TCC 的分界在「有没有中间态」和「补偿的语义强度」。** TCC 是 Try-Confirm-Cancel：Try 阶段就要预留资源（冻结库存、预扣额度），Confirm 才是真正的提交，Cancel 释放预留。它的强项是资源在 Try 阶段就被锁住，不会出现「扣了款但没货」，适合资金、库存这类必须一致的场景；代价是每个参与方都要改造成三个接口，且要处理空回滚、悬挂、幂等三个经典问题。Saga 是一串本地事务 + 反向补偿：每一步直接提交，失败时按逆序调用补偿接口。它不需要预留资源、改造成本低，适合长流程、跨系统、能接受最终一致且补偿语义天然成立的场景（下单→扣券→发通知）；缺点是中间态对外可见，且补偿不一定可逆（短信已经发了就撤不回），所以必须给每个正向操作配一个语义正确的补偿动作。一句话对比：TCC 靠「预留」避免中间态，Saga 靠「补偿」消化中间态。

**防超卖的本质是把「检查 + 扣减」合并成一次原子操作。** 数据库层面用 `UPDATE stock SET count = count - 1 WHERE id = ? AND count >= 1`，判断行数是否为 0；Redis 层面用 Lua 脚本把「读库存、判断、扣减」包成一次原子执行，或直接用 `DECR` 后判断返回值是否小于 0（小于 0 再补回）。分布式场景还要加一层「预扣 + 异步落库」，让 DB 只做最终一致的对账。要主动说出两个坑：一是「先查再改」在并发下必然超卖，二是热点 key 用 Redis 扣减会有单分片瓶颈，需要把库存拆成多个子桶（分桶扣减）再汇总。

**GMP 与写屏障要能连起来讲。** G 是 goroutine（用户态协程，含栈与状态），M 是 OS 线程（真正执行代码的实体），P 是处理器上下文（持有本地 runq、mcache、以及执行 G 所需的资源），数量由 `GOMAXPROCS` 决定。调度的核心是「M 必须绑定 P 才能跑 G」，本地队列空了会去全局队列或其他 P 偷（work stealing），遇到阻塞系统调用时 M 与 P 解绑，P 交给其他 M 继续跑，这样阻塞不会浪费并行度。并发标记期间，GC 已经扫过的对象如果被程序改成「只被白色对象引用」，而标记阶段不再重扫，这个白色对象就会被误回收——所以需要写屏障。Go 早期用插入写屏障（新指向的对象标灰），但栈上不开屏障、需要 STW 重扫栈；后来改成混合写屏障（Dijkstra 插入 + Yuasa 删除的组合）：被覆盖的旧指针标灰、新写入的指针也标灰，且栈上的对象在标记开始时一律视为黑色不再重扫，从而把 STW 压到只在开始和结束的两个极短停顿。答这题时能说出「为什么栈不需要重扫」是明显的加分点。

**TCC 的三个坑各有对应解法，要成套答。** 空回滚：Try 没执行（比如网络超时被跳过），Cancel 却先到了，此时不能真的回滚，做法是 Cancel 里先查事务记录，没有 Try 记录就直接返回成功并落一条「空回滚」标记。悬挂：Cancel 比 Try 先到，之后 Try 才来并预留了资源，导致资源永久冻结，解法是 Try 执行前先检查是否已有 Cancel 记录，有则拒绝 Try。幂等：Confirm/Cancel 可能被重复调用，用事务控制表的唯一键 + 状态机（TRYING/CONFIRMING/CANCELLED）保证只生效一次。

**下游没有幂等键时，调用方的幂等要靠「自己造一个可去重的凭据」。** 常见做法是用业务单号生成一个全局唯一的 `requestId`，在本地落一张「请求日志表」做状态机（已发起/成功/失败），重试时先查这张表；同时把这个 id 通过 header 传给下游，即使下游不保证幂等，至少能靠它做人工对账。更稳的是把「查询 + 提交」做成两阶段：先提交一个「待确认」的占位记录（唯一键防重），再轮询下游状态，避免盲目重试。分布式 ID 部分：号段模式（一次从 DB 取一段 id 缓存在内存，用完再取）依赖 DB 但有单调性、实现简单；雪花算法是「时间戳 + 机器 id + 序列号」，本地生成、性能高，代价是强依赖时钟，回拨会导致重复，需要做时钟回拨检测。布隆过滤器用位数组 + 多个哈希回答「一定不存在 / 可能存在」，适合缓存穿透防护与去重，但标准版不支持删除（要计数布隆或布谷鸟过滤器）。

**分布式锁的最后一问考的是生命周期管理，很多人只答 SETNX + 过期时间。** 完整要交代：加锁用 `SET key val NX PX ttl`（value 用唯一 token），解锁必须用 Lua 比对 token 再删，避免删掉别人的锁；ttl 要配合看门狗续期，否则业务没跑完锁就过期。续期协程的坑在于「业务已退出但协程还在续」，结果锁被永久持有、其他人永远拿不到。解法是让续期与业务生命周期绑定：用 `context` 的取消信号或一个「业务完成」的 channel 通知续期协程退出；续期循环里每次先检查本地锁记录是否还存在（业务结束时把记录删掉），拿不到记录立即退出；同时给整个锁设置一个「最长持有时间」的硬上限，超过就不再续期。另外要提一致性的边界：单机 Redis 在主从切换时可能丢锁，强一致场景要用 Redlock 或直接上 etcd/ZooKeeper 这类基于共识的锁服务。
