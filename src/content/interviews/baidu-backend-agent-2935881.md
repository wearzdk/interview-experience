### 《参考解析》

1. **多 Agent 架构**：常见形态是一个编排者负责拆任务和汇总，多个执行者各管一类工具或领域；也可以按「规划—执行—校验」分层。要讲清楚每个 Agent 的职责边界、上下文怎么隔离、结果怎么合并。如果只是把一个 prompt 拆成几段串行调用，那不叫多 Agent。

2. **MCP 的调用**：MCP 是模型与外部工具之间的标准协议，客户端启动时连接 server、拉取工具清单（name、description、inputSchema），模型根据描述选择工具并在调用时传结构化参数。要能说出「怎么确定用哪一个」——靠工具描述和参数 schema 让模型判断，而不是硬编码路由；工具多了要做分组和按需暴露。

3. **Skill 与渐进式披露**：Skill 是把一类任务的做法打包成可加载的说明和资源，渐进式披露是指先只把「这个 Skill 能做什么」的摘要给模型，需要时再展开详细说明和脚本，避免一次性把上下文塞满。这直接关系到 token 成本和工具选择的准确率。

4. **多 Agent 没有通信怎么保证准确**：靠任务定义的输入输出契约 + 结果校验。每个 Agent 的输出必须符合 schema，编排者做一致性检查（交叉验证、引用核对），再用评测集回归。没有通信时最容易出现的是「各说各话」，所以契约和校验是必需的。

5. **用户请求到调用 API 的过程**：客户端发起 HTTP 请求 → 网关鉴权限流 → 业务服务 → 组装上下文调模型（可能带工具）→ 模型返回 tool_call → 服务端执行工具 → 结果回填再调模型 → 流式返回。要能讲清每一步的超时、重试和错误处理。

6. **MVCC**：InnoDB 每行有隐藏的事务 ID 和回滚指针，undo log 串成版本链；读操作根据当前事务的 Read View 判断哪个版本可见——读已提交每次查询生成新 Read View，可重复读在事务开始时生成。MVCC 让读不加锁，配合间隙锁解决幻读。

7. **主从复制**：主库把变更写进 binlog，从库的 IO 线程拉取并写入 relay log，SQL 线程重放。异步复制有延迟，半同步保证至少一个从库收到，组复制用一致性协议。延迟带来的典型问题是「刚写就读不到」，解法是读主库或等位点。

8. **热 key**：本地缓存加多级缓存、读请求打散到多个副本、key 加随机后缀分片、限流保护后端。判断热 key 靠监控统计单 key 的 QPS。

9. **Redis 超卖**：Lua 脚本把「判断库存、扣减、记录」合成一个原子操作，因为 Redis 单线程执行脚本不会被打断。但它只能保证 Redis 层面不超卖，最终一致性还要靠数据库的条件更新和异步落库对账。

10. **缓存与数据库不一致**：常用 Cache Aside——读时先读缓存、没有则读库并回填；写时先更新库再删除缓存。不一致的来源有几种：删缓存失败、并发读写导致旧值回填、主从延迟导致读到旧数据、缓存过期时间过长。

11. **长时间不一致的原因**：① 删除缓存失败且没有重试或补偿；② 读写并发——读请求在写之前拿到旧值，写完之后才回填，把旧值写回缓存；③ 数据库主从延迟，读从库拿到旧值再回填；④ 业务代码里有的路径更新了库没失效缓存（漏改），这类最隐蔽，会一直不一致直到缓存过期；⑤ 缓存本身设置了很长的 TTL 或者永不过期。排查顺序是先确认是哪条路径写的库、有没有失效缓存，再查主从延迟和并发时序。工程上的兜底是订阅 binlog 异步失效 + 延迟双删 + 监控不一致告警。

12. **面试官的建议**：Agent 项目里的名词要能落到代码——多 Agent 怎么通信、工具怎么注册、上下文怎么组装、评测怎么做。只背概念，一问实现就露馅。
