### 《参考解析》

**RAG 的检索策略要能拆成「召回—融合—重排—截断」四步讲。** 召回通常同时跑向量检索（语义相似）与关键词检索（BM25，精确匹配术语、编号、专有名词），两路各取 Top-K；融合用 RRF（按排名倒数求和，不依赖分数可比性）或加权归一化分数；重排用一个 cross-encoder 或专用 reranker 模型对候选做精排，取其 Top-N；最后按 token 预算截断并保留来源元信息。翻译场景的特别之处是术语一致性：把术语表作为结构化约束注入，检索时优先召回术语条目，生成后做一次术语校验（出现未译或错译就回退重写），专家校对数据反过来作为评测集与微调/提示样本。这样回答能把「RAG 实现」讲成一个可运行的管线，而不是「用了向量库」。

**向量索引类型按「精度、内存、构建速度」三者的取舍回答。** Flat 是暴力检索，召回率 100%，适合小规模或做评测的基准；IVF 用聚类分桶，查询只扫部分桶，需要训练且对参数 nprobe 敏感；HNSW 是分层可导航小世界图，查询快、召回高，但内存占用大、构建慢、删除麻烦；PQ / IVF-PQ 用乘积量化压缩向量，内存降一个量级但损失精度，适合大规模；DiskANN 把图放磁盘以支撑更大规模。生产上要能说清怎么选：数据量、QPS、可接受的内存、以及是否需要频繁增删（HNSW 的删除是标记删除，需要定期重建）。

**缓解幻觉的手段要分「检索侧」和「生成侧」。** 检索侧：提高召回质量、强制引用来源、对没有召回到证据的问题直接拒答（阈值 + 兜底话术）；生成侧：提示词要求「只根据给定材料回答，材料里没有就说不知道」、输出结构化并带引用编号、用低温度；后处理侧：做事实校验（把答案里的实体与数字回查原文）、关键场景走人工抽检。工程上还要有可观测性：记录每次请求的召回内容与最终答案，出问题能回溯是哪一步错了。

**GraphRAG 的要点是「用实体关系补上向量检索拿不到的全局信息」。** 做法是先用 LLM 从文档抽实体与关系建图、做社区检测并生成社区摘要，查询时既能做局部检索（沿实体邻域扩展），也能做全局检索（用社区摘要回答「这批文档整体在讲什么」这类问题）。代价是构建成本高（每个 chunk 都要跑 LLM）、更新麻烦、对实体抽取质量敏感。适合多跳问答与全局总结，不适合高频更新的知识库。

**MCP 协议的底层原理：** 它把模型与外部工具/数据源的连接标准化成 client-server 架构，Host（如 IDE、客户端）里跑 MCP Client，通过 JSON-RPC 2.0 与 MCP Server 通信，Server 暴露三类能力——Tools（可调用的函数，带 JSON Schema 描述入参）、Resources（可读取的上下文数据，用 URI 标识）、Prompts（预置的提示模板）。传输层支持 stdio（本地进程）与 HTTP+SSE / Streamable HTTP（远程），初始化时双方协商协议版本与能力（capabilities）。价值在于把「每家工具一套插件」变成「一次实现，所有支持 MCP 的客户端都能用」。被追问安全时要能说出：工具描述可能被注入、需要权限控制与人工确认高危操作、Server 要做输入校验与超时限制。

**大模型网关的技术设计按「接入—路由—治理—计费」四层讲。** 接入层统一各家 API 的协议差异（OpenAI 兼容格式做适配层）；路由层做模型映射、按价格/延迟/可用性做负载均衡与故障转移、支持灰度与 A/B；治理层做限流、配额、超时与重试、内容审核、日志与链路追踪；计费层按 token 统计用量、区分输入输出与缓存命中、出账单与预警。产品视角则要回答「凭什么用你的中转」：更便宜（批量采购/多渠道比价）、更稳（多路冗余与自动切换）、更好用（统一 key、用量看板、按项目分账、合规审计）。这题的关键是把技术能力和商业理由对上。

**Agent 的核心理念可以概括成「模型 + 工具 + 循环 + 状态」。** 模型负责决策，工具扩展能力边界，循环是「思考—行动—观察」直到完成，状态管理保证多轮任务不丢上下文。自研优化点通常落在：工具描述的设计（让模型一次选对）、上下文压缩与缓存（长任务的 token 控制）、失败重试与降级、以及可观测（每一步的输入输出都留痕）。被问「模型选型」时，要说清为什么这个任务用这个模型（成本、延迟、工具调用能力、长上下文），以及怎么用评测集验证而不是凭感觉。

**「是否读过源码排障」这类问题，答的是排查方法而不是结论。** 例如 embedding 服务返回的向量维度与索引不一致、reranker 的打分范围与阈值假设不符、批量请求时的截断导致长文档只入了一半——每一类都要说清「怎么发现的（日志/对比实验）、怎么定位到源码的哪一段、怎么修的」。这比说「读过」有说服力得多。

**HR 面的问题都在验证同一件事：你是不是一个能自己推进、也会踩刹车的人。** 「有没有拒绝过需求」考的是判断力，回答要给一个真实例子：需求与当前目标冲突或成本明显不划算时，你拿什么数据说服对方、最后怎么折中；「边界模糊的任务」考的是主动性，讲清你怎么把模糊目标拆成可交付的里程碑、找谁对齐；「跨团队分歧」考的是沟通方式，落到「先对齐目标和事实，再谈方案」。至于「为什么来合肥」「为什么讯飞」，给一个和城市/公司真实特点相关的理由（生活成本、家庭、讯飞在语音与 AI 的积累），比空泛的「平台大」可信。

**这场面试最值得记的一点是流程风险：** 技术面都过了却卡在 VP 面排期一个多月，说明大厂高层面的面试资源本身就是瓶颈。等待期间继续推进其他机会、定期礼貌跟进，是比干等更合理的做法。
